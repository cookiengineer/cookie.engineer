Sandbox Analysis

Build a disposable malware analysis sandbox with podman that isolates, observes, and records the behavior of an unknown binary.

Overview

You have an unknown binary that you cannot safely run on your host. This article builds a disposable container that isolates the sample with namespaces and seccomp, captures its system calls and network traffic, and produces a behavioral report you can read afterward. It covers the isolation layers, the observability tooling, and the sidecar Containerfile that ties them together.

Required Reading

  • Containers - Linux namespaces, cgroups, OverlayFS, podman architecture
  • Process Monitoring - /proc inspection, process trees, resource monitoring
  • System Call Tracing - strace, ltrace, syscall interception, behavioral logging

---

You have an unknown binary. You cannot run it on your host. If it's malware, it will infect you. If it's a crypter, it will encrypt your home directory. If it's a bot, it will phone home and flag your IP as an analyst.

The solution: execute it in a disposable, isolated, observable container. Every action visible. Every network packet captured. Every file write recorded. When analysis is complete, destroy the container. Start fresh next time.

1. Threat Model

Before designing the sandbox, define what you're defending against:

Threat Mechanism Sandbox Mitigation
Filesystem encryption write(), open() with O_CREAT Read-only rootfs
Reverse shell connect(), socket() --network none or fake network
Data exfiltration sendto(), write() to fd Network isolation + file auditing
Credential theft open() ~/.ssh/, read() /etc/shadow User namespace + read-only sensitive dirs
Fork bomb clone(), fork() --pids-limit
Memory exhaustion mmap(), brk() --memory limit
Kernel exploit CVE-20XX-XXXX abuse Defense-in-depth: VM + seccomp + unprivileged user
Container escape CVE-2019-5736 runc vuln Use VM as outer boundary
Debugger detection ptrace(), /proc/self/status Scripting: bypass or patch (see anti-debugging article)

The sandbox is not a guarantee. It's a layered defense. Every layer reduces attack surface.

2. Container Isolation Layers

Podman orchestrates Linux kernel features. Each flag enables a specific namespace or restriction.

2.1 User Namespace: Root != Root

Container UID       Host UID (rootless, no keep-id)
0 (root)       <->  100000 (first subordinate UID)
1000 (user)    <->  1000  (with --userns keep-id)

Without --userns keep-id , root in the container maps to the first subordinate UID on the host, not to the host's real root. The container process thinks it is root - it can chown , setuid , mknod - but those operations apply to the mapped subordinate UIDs, not the host root.

# Verify user namespace mapping
podman run --rm --userns keep-id archlinux cat /proc/self/uid_map
# Output:
#          0       1000          1
#  container_uid host_uid range_length

# Without --userns keep-id, root maps to subuid range
podman run --rm archlinux cat /proc/self/uid_map
# Output:
#          0   100000      65536
# container root (0) maps to host UID 100000

# The host sees container root processes as UID 100000
podman top mycontainer user huser

2.2 PID Namespace: Isolated Process Tree

# Without an init process (PID namespaces enabled by default):
podman run --rm archlinux cat /proc/self/status | grep Pid
# Pid: 1
# The process sees ITSELF as PID 1.

# On the host, the container's PID 1 is some large number:
CONTAINER_PID=$(podman inspect --format '{{.State.Pid}}' mycontainer)
echo "$CONTAINER_PID"  # e.g., 28471 on host

# Compare: what the container sees vs host reality
podman exec mycontainer cat /proc/1/cmdline | tr '\0' ' '  # Container's PID 1
cat /proc/$CONTAINER_PID/cmdline | tr '\0' ' '             # Host's view

This matters for malware: if it uses kill(1, SIGKILL) to kill all processes, it only kills processes in its namespace. The host is unaffected.

2.3 Network Namespace: Air Gap

# Complete isolation: no network devices except loopback
podman run --rm --network none archlinux ip link show
# 1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 ...
# No eth0, no internet access.

# NAT'd network: container gets a private IP behind NAT
podman run --rm archlinux ip addr show eth0
# inet 10.0.2.100/24
# Container can reach internet through host's network stack.

# Custom bridge with traffic capture on host:
podman network create --subnet 192.168.99.0/24 sandbox-net
podman run --rm --network sandbox-net --ip 192.168.99.10 sandbox ./malware
# On host, capture veth interface traffic:
sudo tcpdump -i veth* -w /tmp/malware.pcap

2.4 Mount Namespace: Read-Only Root

# Read-only rootfs: any attempt to write to / fails with EROFS
podman run --rm --read-only archlinux touch /test
# touch: cannot touch '/test': Read-only file system

# Malware expects writable /tmp and /var/run. Mount tmpfs:
podman run --rm --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64M \
  --tmpfs /run:rw,noexec,nosuid,size=16M \
  --tmpfs /var/tmp:rw,noexec,nosuid,size=64M \
  sandbox ./malware

# Mount read-only analysis tools:
podman run --rm --read-only \
  -v /opt/analysis-tools:/tools:ro \
  sandbox /tools/strace -f /malware

# Mount results directory read-write:
podman run --rm --read-only \
  -v $(pwd)/results:/tmp/results:rw \
  sandbox ./malware

3. seccomp: System Call Filtering

Seccomp-bpf filters intercept syscalls during syscall / sysenter transition. The kernel evaluates a BPF program and returns: SECCOMP_RET_ALLOW , SECCOMP_RET_KILL , SECCOMP_RET_ERRNO , SECCOMP_RET_TRAP .

4. Capabilities Drop

Linux capabilities break root's monolithic power into discrete permissions. By default, podman drops nearly all capabilities:

Capability Allows Blocked by default?
CAP_SYS_ADMIN mount, swapon, sethostname, pivot_root YES
CAP_SYS_PTRACE ptrace, process_vm_readv YES
CAP_SYS_MODULE init_module, delete_module YES
CAP_NET_RAW raw sockets YES
CAP_NET_ADMIN interface config, routing YES
CAP_NET_BIND_SERVICE bind to ports < 1024 YES
CAP_SYS_BOOT reboot YES
CAP_SYS_CHROOT chroot YES
CAP_DAC_OVERRIDE bypass file permissions YES
CAP_SETUID setuid, seteuid YES 
# Default bounding set for a rootless container
podman run --rm archlinux capsh --print
# Current: = cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,
#            cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,
#            cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,
#            cap_setfcap+i
# (podman grants a small default set)

# Drop every capability: the result is an empty set
podman run --rm --cap-drop=ALL archlinux capsh --print
# Current: =

# Absolute minimum: drop everything, add explicit
podman run --rm --cap-drop=ALL --cap-add=CAP_SYS_PTRACE sandbox ./malware
# Only ptrace is permitted now.

5. Resource Limits

Prevent denial-of-service and resource exhaustion:

podman run --rm \
  --memory 512m \           # Hard limit: 512 MB RAM
  --memory-swap 512m \      # No swap (same as memory = no swap)
  --cpus 1.5 \              # 1.5 CPU cores max
  --cpu-shares 512 \        # Relative weight (1024 default)
  --pids-limit 50 \         # Max 50 PIDs (prevents fork bombs)
  --ulimit nofile=256:512 \ # Max 256 open files (soft), 512 (hard)
  --ulimit nproc=50:100 \   # Max 50 processes (soft), 100 (hard)
  --blkio-weight 100 \      # 10% of disk I/O (default 500)
  sandbox ./malware

# Verify limits work:
# Fork bomb inside container with --pids-limit 10:
podman run --rm --pids-limit 10 archlinux bash -c 'f() { f | f & }; f'
# Container OOM kills the process tree quickly.

6. Network Setup Strategies

6.1 Air-Gapped (--network none)

podman run --rm --network none --name samplesandbox sandbox ./malware
# Malware has no network reachability. socket() works for AF_UNIX only.
# tcpdump sees nothing. strace will show failed connect() calls.

Use when: you want to see what the malware tries to connect to without letting it succeed.

6.2 Fake Internet with INetSim

INetSim simulates internet services: DNS , HTTP , HTTPS , SMTP , FTP , IRC , NTP , Syslog. Every connection succeeds; responses are fake but protocol-conformant.

# Host: start INetSim
sudo inetsim --data /var/lib/inetsim --report /tmp/inetsim-report

# Create a network with fake gateway
podman network create \
  --subnet 10.13.37.0/24 \
  --gateway 10.13.37.1 \
  inetsim-net

# Route container traffic through INetSim
# INetSim listens on 10.13.37.1 by default
# DNS: configure container to use 10.13.37.1 as DNS server
podman run --rm --network inetsim-net \
  --dns 10.13.37.1 \
  sandbox ./malware

6.3 Capture-Only Network

Let malware reach the internet but capture everything:

# On host, find the veth pair for the container:
podman run --rm -d --name sample --network bridge sandbox sleep 3600
VETH=$(ip link | grep veth | awk -F: '{print $2}' | head -1 | xargs)

# Capture all traffic on the veth interface:
sudo tcpdump -i "$VETH" -w /tmp/malware-capture.pcap -s 0 -n &

# Run analysis
podman exec sample /opt/analyze.sh /malware

# Stop capture
sudo kill %1
podman stop sample

7.2 Runner Script: /opt/run-sample.sh

This script orchestrates a single sample analysis run:

#!/bin/bash
# run-sample.sh - execute a binary under full instrumentation
# Usage: run-sample.sh /path/to/malware [timeout_seconds] [sample_id]

SAMPLE="${1:?Usage: run-sample.sh <binary> [timeout] [id]}"
TIMEOUT="${2:-60}"
SAMPLE_ID="${3:-$(date +%s)}"
RESULT_DIR="/tmp/results/${SAMPLE_ID}"
mkdir -p "$RESULT_DIR"

echo "[*] Analyzing sample: $SAMPLE (ID: $SAMPLE_ID, timeout: ${TIMEOUT}s)"

# 1. Static triage
echo "[*] Running static triage..."
file "$SAMPLE" > "$RESULT_DIR/file-type.txt"
readelf -h "$SAMPLE" > "$RESULT_DIR/elf-header.txt" 2>&1 || true
readelf -l "$SAMPLE" > "$RESULT_DIR/elf-segments.txt" 2>&1 || true
readelf -d "$SAMPLE" > "$RESULT_DIR/elf-dynamic.txt" 2>&1 || true
strings -n 6 "$SAMPLE" | sort -u > "$RESULT_DIR/strings.txt"
objdump -d "$SAMPLE" > "$RESULT_DIR/disassembly.txt" 2>&1 || true
LD_LIBRARY_PATH= ldd "$SAMPLE" > "$RESULT_DIR/ldd-output.txt" 2>&1 || true

# 2. Start network capture on loopback (inter-container traffic)
tcpdump -i lo -w "$RESULT_DIR/network.pcap" -s 0 -n -U &
TCPDUMP_PID=$!
sleep 0.5

# 3. System call trace with fork follow
strace -f -tt -T -e trace=file,process,network,ipc \
  -o "$RESULT_DIR/strace.log" \
  timeout "$TIMEOUT" "$SAMPLE" &
SAMPLE_PID=$!

# 4. Wait for completion or timeout
wait $SAMPLE_PID 2>/dev/null
SAMPLE_EXIT=$?

# 5. Stop capture
sleep 1
kill $TCPDUMP_PID 2>/dev/null
wait $TCPDUMP_PID 2>/dev/null

# 6. Post-run collection
lsof -p $SAMPLE_PID > "$RESULT_DIR/open-files.txt" 2>&1 || true
cp /proc/$SAMPLE_PID/maps "$RESULT_DIR/proc-maps.txt" 2>/dev/null || true

# 7. Generate summary
{
  echo "=== ANALYSIS SUMMARY ==="
  echo "Sample: $SAMPLE"
  echo "Exit code: $SAMPLE_EXIT"
  echo "Syscall count: $(wc -l < "$RESULT_DIR/strace.log")"
  echo "Unique files accessed:"
  grep -oP '"(/[^"]*)"' "$RESULT_DIR/strace.log" | sort -u
  echo "Network connections:"
  grep -E '(connect|socket|bind|sendto)' "$RESULT_DIR/strace.log"
  echo "Child processes:"
  grep -E '(clone|fork|execve)' "$RESULT_DIR/strace.log"
} > "$RESULT_DIR/summary.txt"

echo "[*] Results saved to: $RESULT_DIR"
cat "$RESULT_DIR/summary.txt"

9. Automated Sandbox Runner

Batch analysis wrapper script:

#!/bin/bash
# auto-sandbox.sh - analyze multiple samples in parallel
SAMPLES_DIR="${1:-./samples}"
RESULTS_DIR="${2:-./results}"
MAX_PARALLEL="${3:-4}"
TIMEOUT="${4:-120}"

mkdir -p "$RESULTS_DIR"

running=0
for sample in "$SAMPLES_DIR"/*; do
    [[ -f "$sample" ]] || continue
    sid="$(basename "$sample")-$(date +%s)"
    echo "[*] Launching sandbox for: $sample (ID: $sid)"

    podman run --rm -d --name "sandbox-$sid" \
      --network none --read-only \
      --tmpfs /tmp:rw,noexec,nosuid,size=128M \
      --tmpfs /run:rw,noexec,nosuid,size=16M \
      --cap-drop=ALL --security-opt=no-new-privileges \
      --memory 512m --cpus 1 --pids-limit 50 \
      -v "$(realpath "$sample"):/tmp/malware:ro" \
      -v "$(realpath "$RESULTS_DIR"):/tmp/results:rw" \
      malware-sandbox \
      /opt/run-sample.sh /tmp/malware "$TIMEOUT" "$sid" \
      &>/dev/null &

    ((running++))
    if (( running >= MAX_PARALLEL )); then
        wait -n 2>/dev/null || true
        ((running--))
    fi
done
wait

echo "[*] All samples analyzed. Results in: $RESULTS_DIR"

10. Defense-in-Depth: VM + Container

If the sample contains a kernel exploit, it escapes the container (same kernel). Defense: run the sandbox inside a lightweight VM .

# Using qemu with minimal ArchLinux image:
qemu-system-x86_64 \
  -enable-kvm \
  -m 1G \
  -smp 2 \
  -drive file=arch-sandbox.qcow2,if=virtio \
  -netdev user,id=net0,restrict=on \
  -device virtio-net,netdev=net0 \
  -nographic \
  -append "console=ttyS0 root=/dev/vda1 rw"

# Inside the VM, podman runs containers as above.
# Even a kernel escape now lands inside the VM guest kernel, not the host.

Nested isolation table:

Layer Escape Required Difficulty
Container (user ns) Kernel exploit + user ns escape High
Container (root) Kernel exploit Medium
VM (KVM) VM escape + kernel exploit Very high
Air-gapped host Physical access or supply chain Extreme

11. Practical Analysis Walkthrough

Given a suspicious binary invoice.pdf.bin :

# Step 1: Static triage on host (never execute)
file invoice.pdf.bin
# ELF 64-bit LSB executable, x86-64, statically linked, stripped

strings invoice.pdf.bin | head -30
# Reveals: /tmp/.cache, /proc/self/exe, /etc/ld.so.preload
# Suggests persistence mechanism.

# Step 2: Launch sandbox
podman run --rm --name analysis-1 \
  --network bridge --dns 8.8.8.8 \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64M \
  --tmpfs /run:rw,noexec,nosuid,size=16M \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --memory 256m --cpus 0.5 --pids-limit 20 \
  -v "$(pwd)/invoice.pdf.bin:/tmp/sample:ro" \
  -v "$(pwd)/results:/tmp/results:rw" \
  malware-sandbox \
  /opt/run-sample.sh /tmp/sample 60 invoice-001

# Step 3: Examine results
cat results/invoice-001/summary.txt
# Exit code: 0
# Syscall count: 847
# Files accessed: /tmp/.cache/<random>, /tmp/.X11-unix/X0
# Network: connect(3, {sa_family=AF_INET, sin_port=htons(443),
#                      sin_addr=inet_addr("185.130.5.253")}, 16)

# Step 4: Analyze strace
grep -E '^[0-9]+ ' results/invoice-001/strace.log | awk '{print $2}' | \
  sort | uniq -c | sort -rn | head -10
# Top syscalls: read(247), write(189), futex(98), connect(12), openat(8)

# Step 5: Check network capture
tshark -r results/invoice-001/network.pcap -Y 'tls.handshake.type==1' \
  -T fields -e tls.handshake.extensions_server_name
# TLS SNI: api.stealer-c2.net

# Step 6: Persistence check
grep -i 'autostart\|.config\|systemd\|cron\|.bashrc' \
  results/invoice-001/strings.txt
# Matches: ~/.config/autostart/ - malware drops .desktop file for persistence.

# Step 7: IOCs extracted
echo "C2: 185.130.5.253:443 (TLS SNI: api.stealer-c2.net)"
echo "Persistence: ~/.config/autostart/"
echo "Malware family: Linux infostealer (XLF-stealer variant)"

12. Sandbox Limitations

What the sandbox cannot do: - Time-sensitive malware : If the binary checks for a specific date or run duration, it might sleep/exit. - VM-aware malware : Some malware checks CPU ID, MAC addresses, DMI tables for VM indicators. Detected VM s trigger exit or benign behavior. - Multi-stage droppers : If stage-1 fetches stage-2 from C2 , and C2 is down, analysis is incomplete. - Targeted attacks : Malware keyed to specific hostnames, MAC s, IP s won't trigger in a generic sandbox.

  • Hardware-dependent : Malware requiring GPU , specific USB devices, TPM chips won't execute fully.
  • Kernel-level rootkits : LKMs require init_module which is blocked by seccomp. But if it exploits the kernel directly...

Mitigations: - Multi-sandbox approach : Run sample in multiple configurations (air-gapped, internet, fake internet). - Nested execution : If stage-2 dropped, run stage-2 in a new sandbox. - Time acceleration : Some hypervisors support TSC offsetting. Fake the clock.

  • Stimulus injection : Provide fake responses for protocols the malware expects.

Syscall Categories

File I/O open, openat, read, write, close, stat, mkdir, unlink, rename File drops, config reads, data exfil
Process clone, fork, vfork, execve, exit, wait4, kill, tkill Child spawning, self-destruction
Memory mmap, mprotect, munmap, brk, mremap Code injection, heap spray, RWX pages
Network socket, connect, bind, listen, accept, sendto, recvfrom C2 communication, reverse shell
Signal rt_sigaction, rt_sigprocmask, sigaltstack, kill Signal handlers, anti-debug traps
Identity getuid, geteuid, getgid, getegid, getpid, gettid User detection, sandbox detection

IPC pipe, pipe2, socketpair, shmget, shmat, shmdt Inter-process communication
