TCP Fingerprinting

Passive and active OS detection through TCP / IP stack analysis - TTL , window size, option ordering, ISN generation, and cross-protocol fingerprinting techniques.

Overview

Every operating system implements its TCP / IP stack a little differently: a different default TTL , initial window size, option order, and reset policy. Those differences leak the remote OS without any application banner. This article covers passive fingerprinting from captured SYN packets, active probing with nmap and crafted packets, the p0f signature format, and TLS ClientHello fingerprinting with JA3 and JA4. By the end you can identify a stack from a packet capture and explain which fields give it away.

Required Reading

  • TCP - TCP flags, handshake, state machine, options, window scaling
  • Network Scanning - active probing with nmap

What TCP Fingerprinting Is

TCP fingerprinting identifies an operating system by analyzing subtle differences in how its TCP / IP stack implements the protocol. RFC 793 defines TCP behavior, but it leaves implementation details to each vendor: what TTL value to use, what window size to set, what order to arrange TCP options, how to generate sequence numbers, and how to respond to ambiguous or invalid packets.

Each OS makes different choices. These choices form a unique signature - a fingerprint - that persists regardless of what application is running or what user is logged in.

Why Fingerprinting Works

TCP / IP is a specification, not a reference implementation. The RFC describes a protocol, but every vendor writes their own implementation. The RFC says:

  • "The window size should be set based on available buffer space." Each OS picks a different default.
  • "A TCP MAY implement timestamps." Some do, some don't.
  • "If the port is closed, respond with RST." But what about a packet with no flags set? The RFC is ambiguous. Windows sends RST; Linux drops it silently.
  • "The initial TTL MUST be configurable." Each OS ships with a different default.

These implementation decisions are not bugs - they are engineering trade-offs that happen to create an identifiable signature.

OSI Layers Used for Fingerprinting

Layer 2 (Link):  MAC address OUI -> hardware vendor (not OS-specific, easily spoofed)
Layer 3 (IP):    Initial TTL, IP ID generation, DF bit, fragment handling
Layer 4 (TCP):   Window size, option ordering, ISN generation, RST/FIN behavior,
                 timestamp behavior, ECN support
Layer 7 (TLS):   JA3/JA4 - ClientHello cipher suites, extensions, elliptic curves

Passive Fingerprinting

Passive fingerprinting works by monitoring traffic that the target naturally generates. A SYN packet sent by a web browser to a web server reveals the client OS. A SYN -ACK returned by a server reveals the server OS. No additional packets are sent - the fingerprint is extracted from normal traffic.

Initial TTL Analysis

The TTL (Time To Live) field in the IP header is decremented by each router that forwards the packet. The initial TTL is the value set by the sending OS before the packet enters the network.

OS IPv4 Initial TTL IPv6 Hop Limit
Linux (kernel 2.4+) 64 64
FreeBSD 64 64
OpenBSD 64 64
macOS 64 64
Solaris 255 255
Cisco IOS 255 64
Windows 95/98/ME 32 -
Windows NT/2000/XP 128 128
Windows Vista/7/8/10/11 128 128
Android 64 64
iOS 64 64

How TTL fingerprinting works in practice

When you receive a packet, the TTL you see is the remaining TTL

  • the initial value minus the number of hops traversed. To identify the OS, you guess the
initial TTL by rounding up:

# Received TTL: 51
# Possible initial TTLs: 64 (13 hops), 128 (77 hops), 255 (204 hops)
# 13 hops is plausible -> Linux/BSD/macOS
# 77 hops is unlikely -> probably not Windows
# 204 hops is impossible -> definitely not Solaris

# Check hops with traceroute
traceroute -n 192.168.1.42
# Count the hops -> if 1 hop: received TTL 63 -> initial TTL 64 -> Linux/BSD
# Count the hops -> if 15 hops: received TTL 113 -> initial TTL 128 -> Windows
						
# Extract TTL from a captured SYN packet
sudo tcpdump -i eth0 -nn -v 'tcp[tcpflags] & tcp-syn == tcp-syn' 2>&1 | head -5
# Look for: IP (tos 0x0, ttl 64, id 12345, ...)

# Use tshark for TTL extraction
sudo tshark -i eth0 -T fields -e ip.src -e ip.ttl -e tcp.window_size \
    'tcp.flags.syn == 1 and tcp.flags.ack == 0'

TCP Window Size

The initial window size in the SYN packet is not negotiated - it is set by the OS based on available buffer space. Each OS has a characteristic default.

OS Window Size Notes
Linux 2.4-2.6 5840 Classic Linux
Linux 3.x-5.x 29200 Default tcp_rmem[1] = 87380 (scaled) -> base window
Linux 6.x 65535 Full 16-bit window, scaled by wscale
Windows XP 65535 Always max 16-bit window
Windows 7 8192 Smaller initial window
Windows 10/11 65535 With wscale 8 -> effective 16 MB
macOS 65535
iOS 65535
FreeBSD 65535
OpenBSD 16384
Android 65535 Different option ordering from iOS 
# Extract window size from captured SYN
sudo tcpdump -i eth0 -nn -v 'tcp[tcpflags] & tcp-syn == tcp-syn' 2>&1 | \
    grep -oP 'wscale \d+' | head -20

# Using tshark for window + wscale
sudo tshark -i eth0 -T fields \
    -e ip.src -e ip.ttl -e tcp.window_size -e tcp.window_size_scalefactor \
    -e tcp.options \
    'tcp.flags.syn == 1 and tcp.flags.ack == 0'

TCP Option Ordering

The order of TCP options in the SYN packet is an OS fingerprint. TCP options appear in the SYN packet after the 20-byte fixed header. The order of MSS , Window Scale, SACK-Permitted, Timestamps, and NOP (padding) varies by OS.

OS Option Order
Linux 2.4 MSS, SACK, Timestamp, NOP, Window Scale
Linux 2.6-6.x MSS, SACK, Timestamp, NOP, Window Scale
Windows XP MSS, NOP, Window Scale, NOP, NOP, SACK
Windows 7 MSS, NOP, Window Scale, NOP, NOP, Timestamp, SACK
Windows 10/11 MSS, NOP, Window Scale, SACK, NOP, Timestamp
macOS 10.x MSS, NOP, Window Scale, NOP, NOP, Timestamp, SACK
FreeBSD MSS, NOP, Window Scale, SACK, Timestamp
OpenBSD MSS, Window Scale, SACK, Timestamp
Android 8+ MSS, SACK, Timestamp, NOP, Window Scale
iOS MSS, NOP, Window Scale, NOP, NOP, Timestamp, SACK

Why option ordering differs: TCP options are TLVs - they carry their own length. An implementation that parses options sequentially in a loop will handle any order. But the order an OS sends them reveals the order in which the kernel code initializes the SYN packet's option array. This is a pure implementation artifact.

Don't Fragment (DF) Bit

The DF bit in the IP header tells routers not to fragment the packet. Some OSes set DF by default on SYN packets (used for Path MTU Discovery), others don't.

OS DF on SYN
Linux Yes
Windows Vista+ Yes
macOS Yes
FreeBSD Yes
OpenBSD No
Windows XP No
Solaris No

Timestamp Behavior

Every OS that supports TCP timestamps increments the timestamp value differently:

OS Timestamp Increment Pattern
Linux Clock frequency (varies) Increases by Hz value (100-1000/sec)
Windows ~10 ms Increases by ~100/sec
macOS Variable Tied to mach_absolute_time()
FreeBSD Variable Tied to TCP tick (typically 500 Hz)
OpenBSD 0 Timestamps present but always zero (older versions) 
# Extract timestamp values from captured traffic
sudo tcpdump -i eth0 -nn -v 'tcp[tcpflags] & tcp-syn == 0' 2>&1 | \
    grep -oP 'TS val \d+' | head -10

# Calculate increment between consecutive packets
sudo tshark -i eth0 -T fields -e tcp.options.timestamp.tsval \
    'tcp.flags.syn == 0' | \
    awk 'NR>1 {print $1 - prev} {prev=$1}'

p0f - Passive OS Fingerprinting Tool

p0f analyzes SYN packets (v2 used SYN -ACK; v3 uses SYN ) and matches them against a signature database.

# Install p0f on ArchLinux
sudo pacman -S p0f

# Run p0f on an interface (passive mode - no packets sent)
sudo p0f -i eth0

# Read from a pcap file
sudo p0f -r capture.pcap

# Output format and signature database
cat /usr/share/p0f/p0f.fp | head -50

# p0f output example:
# .-[ 192.168.1.42/49210 -> 10.0.0.1/443 (syn) ]-
# |
# | client   = 192.168.1.42/49210
# | os       = Linux 3.11 and newer
# | dist     = 0
# | params   = generic fuzzy
# | raw_sig  = 4:64+0:0:1460:mss*20,7:mss,sok,ts,nop,ws:df,id+:0

Reading p0f signatures

raw_sig = ver:ittl:olen:mss:wsize,scale:olayout:quirks:pclass

  ver         - IP version (4 or 6)
  ittl        - initial TTL (observed TTL + distance, for example 64+0)
  olen        - IP options or IPv6 extension header length
  mss         - maximum segment size
  wsize,scale - window size and window scale factor
  olayout     - option layout (for example mss,sok,ts,nop,ws)
  quirks      - flags such as df or id+
  pclass      - payload class

Example Breakdown

The signature 4:64+0:0:1460:mss*20,7:mss,sok,ts,nop,ws:df,id+:0 decodes as:

  • IP version 4
  • Initial TTL 64 (distance 0)
  • 0 bytes of IP options
  • MSS 1460
  • Window 20 x MSS = 29200 bytes, window scale factor 7
  • Option order: mss, sackOK, timestamp, NOP, window scale
  • Quirks: DF bit set, IP ID non-zero
  • Payload class 0 (no payload)

Active Fingerprinting

Active fingerprinting sends deliberately unusual or ambiguous packets and analyzes the target's response. Each probe exploits a different area of RFC ambiguity.

nmap OS Detection ( -O )

nmap's -O sends up to 16 TCP / UDP / ICMP probes and matches responses against a database of over 2,600 OS signatures.

# OS detection (requires root for raw sockets)
sudo nmap -O 192.168.1.42

# Aggressive OS detection (guess even with low confidence)
sudo nmap -O --osscan-guess 192.168.1.42

# Limit OS detection to likely matches only
sudo nmap -O --osscan-limit 192.168.1.42

# Combined with service detection for higher accuracy
sudo nmap -O -sV 192.168.1.42

# Full verbose OS fingerprint output
sudo nmap -O -v 192.168.1.42

nmap OS detection output

OS details: Linux 5.4 - 5.11
OS CPE: cpe:/o:linux:linux_kernel:5.4
OS CPE: cpe:/o:linux:linux_kernel:5.10
OS CPE: cpe:/o:linux:linux_kernel:5.11

nmap shows the kernel version range when it can't pinpoint the exact version - many Linux kernel versions produce identical TCP fingerprints because the TCP stack hasn't changed between them.

SYN Probe

The most important probe. Send a SYN to an open port, analyze the SYN -ACK response:

# Manual SYN probe with nping
sudo nping --tcp -p 80 --flags syn 192.168.1.42 -c 1

# Capture and analyze the response
sudo tcpdump -i eth0 -nn -v -c 1 'src 192.168.1.42 and tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack != 0'

NULL Probe

Send a packet with no TCP flags set. RFC 793 says: discard silently (open) or RST (closed). Windows: always RST regardless of port state.

# Send NULL probe (no flags set)
sudo hping3 -c 3 -s 12345 -p 80 192.168.1.42

# Analysis: RST received -> Windows, or closed port on any OS
# Analysis: No response -> Open port on Linux/BSD

FIN Probe

Send FIN to an open port. RFC 793 says: drop silently. Windows sends RST-ACK.

# Send FIN probe
sudo hping3 -c 3 -s 12345 -p 80 -F 192.168.1.42

# RST-ACK response -> Windows
# No response -> Linux, BSD, macOS

TCP Options Probe

Send a SYN with unusual or unexpected TCP option combinations to see which are echoed in the SYN -ACK.

# Using scapy to craft a SYN with custom options
sudo python3 << 'EOF'
from scapy.all import IP, TCP, sr1

# SYN with an unusual option (Kind 77, length 3, value 0xAAAA - nonexistent)
pkt = IP(dst="192.168.1.42") / TCP(
    dport=80, flags="S",
    options=[('MSS', 1460), (77, b'\xAA\xAA')]
)
response = sr1(pkt, timeout=2, verbose=False)
if response and response.haslayer(TCP):
    print(f"Flags: {response[TCP].flags}")
    print(f"Options: {response[TCP].options}")
    # Some OSes echo unknown options, others strip them, others ignore them
EOF

ISN (Initial Sequence Number) Analysis

How the OS chooses the ISN reveals the PRNG algorithm:

OS ISN Generation
Linux 2.6+ Random (MD5 hash of connection tuple + secret key)
Windows XP Time-based increment (~250/ms)
Windows 7+ Random (RFC 6528 algorithm)
FreeBSD 4-7 Time-based increment
FreeBSD 9+ Random
OpenBSD Random (arc4random) 
# Sample ISNs over multiple connections
for i in {1..10}; do
    timeout 1 nc -z 192.168.1.42 80 2>&1 &
done
# Capture with tcpdump and compare sequence numbers
sudo tcpdump -i eth0 -nn -c 10 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack != 0'

IP ID Analysis

The IP Identification field helps reassemble fragmented datagrams. Each OS increments it differently:

OS IP ID Behavior
Windows Sequential (global counter, increments by 1 per packet)
Linux 2.4-4.x Per-destination counter (increments per host)
Linux 5.x+ Per-destination counter (hashed bucket, not global)
FreeBSD Random
OpenBSD Random 
# Sample IP IDs from target responses
sudo tcpdump -i eth0 -nn -v -c 10 'src 192.168.1.42' 2>&1 | grep 'id '
# Sequential pattern (1,2,3,4...) -> Windows
# Random pattern -> Linux/BSD

Fingerprint Evasion

Changing TTL

# Set default TTL to 128 (mimic Windows)
sudo sysctl -w net.ipv4.ip_default_ttl=128

# Persistent
echo "net.ipv4.ip_default_ttl=128" | sudo tee /etc/sysctl.d/99-fingerprint.conf
sudo sysctl -p /etc/sysctl.d/99-fingerprint.conf

# Using iptables mangle (per-packet TTL modification)
sudo iptables -t mangle -A POSTROUTING -j TTL --ttl-set 128

# Using nftables
sudo nft add table inet mangle
sudo nft add chain inet mangle output { type filter hook output priority mangle\; policy accept\; }
sudo nft add rule inet mangle output ip ttl set 128

Modifying TCP Window and Options

# Change TCP initial window via sysctl (affects all connections)
sudo sysctl -w net.ipv4.tcp_rmem="4096 65535 16777216"
# Default receive buffer: min default max
# Default (middle) value affects initial window

# Force specific MSS on all outbound connections
sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --set-mss 1460

# Clear TCP options on outbound SYN (aggressive - may break connections)
sudo iptables -t mangle -A OUTPUT -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --clamp-mss-to-pmtu

VPN-Based Fingerprint Concealment

All TCP fingerprinting relies on analyzing packets that your machine generates. A VPN encapsulates your TCP packets inside another TCP or UDP tunnel. The VPN server's TCP stack generates the outer packets - the fingerprint the target sees is the VPN server's OS, not yours.

# WireGuard tunnel - your packets are encrypted and encapsulated
# Target sees the VPN server's TTL, window size, and option ordering
sudo wg-quick up wg0
curl ifconfig.me  # IP is now the VPN server's IP

NAC Bypass via Fingerprint Manipulation

Network Access Control (NAC) systems often fingerprint devices before granting network access. They check TTL , HTTP User-Agent, DHCP options, and sometimes MAC OUI . Manipulating your fingerprint to match an authorized device class can bypass these checks:

# 1. MAC address spoofing (match authorized vendor OUI)
sudo ip link set dev eth0 down
sudo ip link set dev eth0 address 00:1b:21:aa:bb:cc  # Intel OUI
sudo ip link set dev eth0 up

# 2. TTL matching (Windows = 128, Linux = 64)
sudo sysctl -w net.ipv4.ip_default_ttl=128

# 3. HTTP User-Agent spoofing (tools like curl, wget, browsers)
curl -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36" https://portal.example.com

# 4. DHCP option fingerprinting - dhcpcd sends different options than NetworkManager
# Modify /etc/dhcpcd.conf to match a Windows DHCP client's option set

JA3 and JA4 TLS Fingerprinting

TCP fingerprinting identifies the OS. TLS fingerprinting identifies the application making the connection. JA3 hashes the TLS ClientHello fields (supported cipher suites, extensions, elliptic curves, EC point formats) into an MD5 fingerprint. JA4 extends this with protocol identification and QUIC support.

# Capture TLS ClientHello and extract JA3 hash
sudo tcpdump -i eth0 -nn -w clienthello.pcap 'tcp port 443' &
sleep 1
curl -s -o /dev/null https://example.com
sleep 1
sudo kill %1

# Extract JA3 fingerprint with tshark or custom script
sudo tshark -r clienthello.pcap -T fields \
    -e tls.handshake.ciphersuites \
    -e tls.handshake.extensions.supported_groups \
    -e tls.handshake.extensions.ec_point_formats \
    -e tls.handshake.extensions_length \
    'tls.handshake.type == 1'

Common JA3 fingerprints

Application JA3 Hash Notes
Chrome 120 Linux cd08e314... Distinct from Windows Chrome
Chrome 120 Windows b32309a2... Different elliptic curves prioritized
Firefox 120 e6573e90... Different cipher suite order
Python requests d308d096... Default urllib3/OpenSSL TLS stack
Go net/http 3e71b23d... Go's crypto/tls has its own fingerprint
curl (libcurl) bc6c386f... OpenSSL-based

JA3/JA4 fingerprinting is widely used by CDNs, WAF s, and bot detection systems to block automated traffic even when User-Agent headers are spoofed.

TCP Fingerprint Analyzer in Python

#!/usr/bin/env python3
"""tcp-fingerprint.py - Passive TCP OS fingerprint analyzer using scapy."""
import sys
from collections import OrderedDict
from scapy.all import sniff, IP, TCP

# Known OS fingerprints: (TTL, Window, WScale, OptionOrder)
# Option order: M=MSS, S=SACK, T=Timestamp, N=NOP, W=WindowScale
FINGERPRINT_DB = {
    # (ttl, wscale, option_order)
    (64, 7, ("MSS", "SAckOK", "Timestamp", "NOP", "WScale")): "Linux 2.6 - 6.x",
    (64, 7, ("MSS", "NOP", "WScale", "SAckOK", "Timestamp")): "FreeBSD 12+",
    (64, 3, ("MSS", "NOP", "WScale", "NOP", "NOP", "Timestamp")): "macOS 10.x/11.x",
    (64, 8, ("MSS", "SAckOK", "Timestamp", "NOP", "WScale")): "Linux 5.15+ with custom tcp_rmem",
    (128, 8, ("MSS", "NOP", "WScale", "SAckOK", "NOP", "Timestamp")): "Windows 10/11",
    (128, 0, ("MSS", "NOP", "WScale", "NOP", "NOP", "Timestamp")): "Windows 7/8",
    (128, 0, ("MSS", "NOP", "WScale", "NOP", "NOP", "SAckOK")): "Windows XP",
    (255, 0, ("MSS",)): "Solaris / Cisco IOS",
}

def parse_option_order(tcp_layer):
    """Extract TCP option names in order from a TCP layer."""
    order = []
    for opt_name, opt_value in tcp_layer.options:
        name_map = {
            "MSS": "MSS",
            "SAckOK": "SAckOK",
            "Timestamp": "Timestamp",
            "NOP": "NOP",
            "WScale": "WScale",
            "EOL": "EOL",
        }
        name = name_map.get(opt_name, str(opt_name))
        order.append(name)
    return tuple(order)

def get_wscale(tcp_layer):
    """Extract window scale value from TCP options."""
    for opt_name, opt_value in tcp_layer.options:
        if opt_name == "WScale":
            return opt_value
    return 0

def identify_os(ip_ttl, tcp_window, wscale, option_order):
    """Match observed fingerprint against database."""
    # Direct match
    key = (ip_ttl, wscale, option_order)
    if key in FINGERPRINT_DB:
        return FINGERPRINT_DB[key]

    # Partial match: TTL + option order (ignore wscale)
    for (db_ttl, db_wscale, db_order), os_name in FINGERPRINT_DB.items():
        if db_ttl == ip_ttl and db_order == option_order:
            return f"{os_name} (window mismatch: expected {db_wscale}, got {wscale})"

    # TTL-only match
    ttl_os = {
        64: "Linux/BSD/macOS (64 TTL)",
        128: "Windows (128 TTL)",
        255: "Solaris/Cisco (255 TTL)",
        32: "Legacy Windows 9x (32 TTL)",
    }
    return ttl_os.get(ip_ttl, f"Unknown (TTL {ip_ttl})")

def packet_handler(packet):
    """Process captured SYN packets and identify OS."""
    if not (packet.haslayer(IP) and packet.haslayer(TCP)):
        return

    tcp_layer = packet[TCP]
    ip_layer = packet[IP]

    # Only process SYN packets (connection initiation)
    if not (tcp_layer.flags & 0x02):  # SYN flag
        return
    if tcp_layer.flags & 0x10:  # Ignore SYN-ACK (we want SYN only)
        return

    ttl = ip_layer.ttl
    window = tcp_layer.window
    wscale = get_wscale(tcp_layer)
    option_order = parse_option_order(tcp_layer)
    dport = tcp_layer.dport

    os_guess = identify_os(ttl, window, wscale, option_order)
    effective_window = window * (2 ** wscale) if wscale else window

    print(f"\n[+] New SYN from {ip_layer.src}:{tcp_layer.sport} -> {ip_layer.dst}:{dport}")
    print(f"    TTL: {ttl}   Window: {window} (scale: {wscale}, effective: {effective_window})")
    print(f"    Options: {' > '.join(option_order)}")
    print(f"    OS: {os_guess}")

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print(f"Usage: sudo python3 {sys.argv[0]} <interface> [count]")
        print(f"Example: sudo python3 {sys.argv[0]} eth0 10")
        sys.exit(1)

    iface = sys.argv[1]
    count = int(sys.argv[2]) if len(sys.argv) > 2 else 0

    print(f"[*] Listening on {iface} for TCP SYN packets...")
    try:
        sniff(iface=iface, prn=packet_handler, filter="tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0", count=count, store=0)
    except PermissionError:
        print("Root required. Run with sudo.")
        sys.exit(1)
						
# Run the fingerprint analyzer
sudo python3 tcp-fingerprint.py eth0 10

# Generate test traffic from another terminal
curl -s -o /dev/null https://example.com
nc -z google.com 80

Challenge

Fingerprint the lab container. It runs several TCP listeners and uses nftables to set a different outbound TTL per port, so you can practice passive and active detection against known stacks. Window size and option ordering come from the container kernel, not from the rules, which is itself a lesson in how far packet mangling can go.

tcp-fingerprinting.Containerfile

podman build -t tcp-fingerprinting -f tcp-fingerprinting.Containerfile .
podman run -it --rm \
    -p 8080:8080 -p 9090:9090 -p 7070:7070 -p 6060:6060 \
    -p 5353:5353 -p 3128:3128 \
    tcp-fingerprinting

# The container sets a different outbound TTL per listener:
#   Port 8080 - TTL 64,  Linux-like echo
#   Port 9090 - TTL 128, Windows-like echo
#   Port 7070 - TTL 64,  macOS-like echo
#   Port 6060 - TTL 64,  FreeBSD-like echo
#   Port 5353 - TTL 255, Solaris-like echo
#   Port 3128 - HTTP server that reports your own connection

# From your host, connect to each listener:
nc localhost 8080
nc localhost 9090
nc localhost 7070
nc localhost 6060

# Capture and compare the TTL values:
sudo tcpdump -i lo -nn -v 'tcp port 8080 or tcp port 9090 or tcp port 7070 or tcp port 6060'

# Run p0f against the container:
sudo p0f -i lo
