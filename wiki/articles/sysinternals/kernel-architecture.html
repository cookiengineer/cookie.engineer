Kernel Architecture

Monolithic vs hybrid designs, protection rings, address space layout, kernel subsystems, and the system call boundary on Linux and Windows NT.

Overview

The kernel is the code that runs at the highest privilege level and arbitrates access to hardware. This article compares monolithic, microkernel, and hybrid designs, maps the protection rings the CPU enforces, and walks the Linux address-space layout, subsystem tree, and syscall entry path. It also sketches the Windows NT and XNU architectures for contrast. After reading it you can identify which kernel component handles a given request.

  • Processes - process memory layout, /proc, fork/exec/wait lifecycle, cgroups
  • System Calls - syscall mechanism, syscall table, strace, vDSO
  • Virtual Memory - page tables, TLB, mmap() internals, /proc/PID/maps

What a Kernel Is

The kernel is the operating system core - the piece of software that runs at the CPU 's highest privilege level and arbitrates all access to hardware. Every instruction executed by a user-space program runs at ring 3 (on x86-64). When the program needs memory, a file, a network socket, or a new process, it enters the kernel through a system call. The kernel validates the request, performs it on the hardware's behalf, and returns the result.

The kernel is not a process. It has no /proc/PID/ directory. It is a body of code and data mapped into every process's address space in the upper half of virtual memory - invisible to user code but always present. When a hardware interrupt fires, when a timer tick expires, when a page fault occurs, the CPU transitions into the kernel to handle it.

Kernel Design Taxonomy

Operating system kernels fall into three broad architectural categories. The distinction matters for security: a bug in a monolithic kernel driver can compromise the entire system; a bug in a microkernel server is contained.

Monolithic Kernel (Linux)

All kernel services run in a single privileged address space at ring 0. The filesystem driver, network stack, process scheduler, and memory manager all share the same address space and call each other through direct function calls. This is fast (no IP C overhead) but fragile: a null pointer dereference in a USB driver panics the entire kernel.

Linux is a monolithic kernel with loadable module support. Modules ( *.ko files) extend kernel functionality at runtime - device drivers, filesystems, security modules - but they execute in the same ring 0 address space as the core kernel. A malicious or buggy module can overwrite kernel text, patch the syscall table, or install a rootkit with no special privileges beyond CAP_SYS_MODULE .

Microkernel (Minix, seL4, QNX, GNU Hurd)

Only the minimum necessary code runs in kernel space: address space management, thread scheduling, and inter-process communication ( IP C). Everything else - filesystems, networking, device drivers - runs as user-space servers. The kernel's job is to shuttle messages between these servers securely.

seL4 is the only microkernel with a formal proof of correctness (functional correctness, integrity, confidentiality). It has roughly 10,000 lines of C and 1,000 lines of assembly. QNX powers the BlackBerry PlayBook and many automotive systems. Minix 3 runs inside Intel Management Engine on modern x86 platforms - a full microkernel hidden inside your CPU .

Hybrid Kernel (Windows NT, XNU/macOS)

A "hybrid" kernel attempts to combine monolithic performance with microkernel structure. In practice, this means that some services run in kernel space (like a monolithic kernel) while others run in user space (like a microkernel), or that the design is modular but not fully separated.

XNU (macOS/iOS) Architecture

XNU (X is Not Unix) combines the Mach microkernel with BSD kernel components. Mach provides the scheduler, IP C, and VM subsystem. BSD provides the P OSI X interface, filesystems, and networking. The I/O Kit provides device drivers in a restricted C++ subset.

Protection Rings

x86-64 defines four hierarchical protection rings (0 through 3), but only two are used in practice:

Ring 3 ─── User applications, libraries, system daemons
             ├─ Cannot execute privileged instructions (lgdt, lidt, hlt, invlpg, wrmsr)
             ├─ Cannot access I/O ports directly (unless IOPL allows it)
             ├─ Cannot modify page tables (only the kernel page tables, mapped in upper half)
             ├─ Cannot access kernel memory (page table U/S bit = 0 for kernel pages)
             └─ Segmented by SMAP/SMEP on modern CPUs

Ring 2 ─── UNUSED (originally for device drivers in OS/2)

Ring 1 ─── UNUSED (originally for device drivers in OS/2)

Ring 0 ─── Kernel, device drivers, hypervisor (KVM)
             ├─ Full access to all hardware
             ├─ Can modify page tables, MSRs, I/O ports
             └─ Includes kernel modules (.ko files) and eBPF programs

Ring -1 ── Hypervisor (VMX root mode on Intel, EL2 on ARM64)
             ├─ Manages multiple guest VM ring 0 instances
             └─ Controls second-level address translation (EPT/NPT)

Ring -2 ── System Management Mode (SMM), Intel ME, AMD PSP
             ├─ Invisible to the OS, even the hypervisor
             └─ Has unrestricted access to all memory

Ring transition cost

Crossing from ring 3 to ring 0 is expensive. On modern x86-64, a syscall / sysret pair costs roughly 50-100 CPU cycles, depending on cache state, microcode version, and mitigations (Spectre/Meltdown mitigations dramatically increased this cost due to K PT I page table switching). 

# Measure syscall overhead on your system (requires lmbench or similar)
sudo pacman -S lmbench 2>/dev/null || echo "Install lmbench for syscall latency tests"

# Quick-and-dirty measurement: empty syscall (getpid) latency
python3 -c "
import time
N = 10_000_000
start = time.perf_counter_ns()
for _ in range(N):
    pass
overhead = time.perf_counter_ns() - start

start = time.perf_counter_ns()
for _ in range(N):
    import os; os.getpid()
elapsed = time.perf_counter_ns() - start

ns_per_call = (elapsed - overhead) / N
print(f'getpid() syscall: ~{ns_per_call:.1f} ns')
print(f'Cycles (at 3 GHz): ~{ns_per_call * 3:.0f}')
"

SMEP and SMAP: Supervisor Mode Execution Prevention (SMEP, CR4 bit 20) prevents the kernel from executing code in user-space pages. Supervisor Mode Access Prevention (SM AP , CR4 bit 21) prevents the kernel from reading/writing user-space pages without explicitly using stac / clac instructions. Both are critical for exploit mitigation - without them, a kernel exploit that hijacks control flow could redirect execution to user-controlled ROP chains mapped in the lower half. 

# Check SMEP/SMAP status on your CPU
grep -o 'sme[ap]' /proc/cpuinfo | sort -u
# Should see "smep" and "smap" on modern systems

Kernel vs User Address Space

On x86-64, Linux uses a split address space. The upper half (0xFFFF...) belongs to the kernel, the lower half (0x0000...) belongs to user space. The boundary is fixed by the 48-bit canonical form; the direct-map base ( page_offset_base ) is chosen at boot and can be randomized with CONFIG_RANDOMIZE_MEMORY . 

x86-64 Linux canonical addresses (48-bit virtual, 47:0 effective):

Kernel virtual address regions (typical layout, varies by KASLR):

0xFFFF888000000000  Direct map of all physical memory (PAGE_OFFSET)
0xFFFFC90000000000  vmalloc region (non-contiguous allocations)
0xFFFFEA0000000000  Virtual memory map (vmemmap) for struct page array
0xFFFFFE0000000000  KASAN shadow (if CONFIG_KASAN)
0xFFFFFF0000000000  CPU entry area (per-CPU GDT, TSS, exception stacks)
0xFFFFFF8000000000  Kernel text mapping (phys_base + __START_KERNEL_map)

System Call Interface: The Boundary

The syscall interface is the only legitimate way to transition from ring 3 to ring 0. Every attempt to cross this boundary by other means (direct jumps, interrupts to kernel handlers, MSR manipulation) should trigger a page fault, general protection fault, or be blocked by SMEP/SM AP .

Linux syscall dispatch path

Userspace: write(fd, buf, len)
  → libc: mov $1, %rax; syscall
    → entry_SYSCALL_64 (arch/x86/entry/entry_64.S)
      → do_syscall_64 (arch/x86/entry/common.c)
        → sys_call_table[%rax] (generated array of function pointers)
          → __x64_sys_write (fs/read_write.c)
            → ksys_write → vfs_write → ...

Key structures:
  MSR_LSTAR (0xC0000082)    → address of entry_SYSCALL_64
  MSR_STAR (0xC0000081)     → segment selectors for kernel/user
  MSR_SYSCALL_MASK (0xC0000084)→ which rflags bits to clear on entry

Windows NT syscall dispatch path

Userspace: NtWriteFile (ntdll.dll)
  → mov eax, 0xNN; syscall (or int 0x2E on older systems)
    → KiSystemCall64 (ntoskrnl.exe; written in assembly in MSR_LSTAR)
      → KiSystemServiceHandler
        → KeServiceDescriptorTable[n].KiServiceLimit bounds check
          → KiServiceTable[SSDT index] → NtWriteFile (ring 0)

Finding The Syscall Table

Before Linux 5.7, the syscall table was exported as sys_call_table and trivially accessible from kernel modules. Post-5.7, kallsyms_lookup_name() is no longer exported, and the table must be found by other means: 

# Check kernel version
uname -r

# On older kernels, find syscall table address
sudo cat /proc/kallsyms | grep ' sys_call_table$'
# Expected output: ffffffff8b4001c0 R sys_call_table

# Count number of syscalls
sudo cat /proc/kallsyms | grep ' sys_call_table$' | wc -l

# List all registered syscall handlers (first 20)
sudo cat /proc/kallsyms | grep __x64_sys_ | head -20

Modern KPTI/Kaiser (Meltdown mitigation)

Kernel Page-Table Isolation (K PT I) removes kernel mappings from user-space page tables almost entirely. When a process runs in ring 3, only a tiny stub of kernel code (the trampoline for syscall entry/exit) is mapped. The full kernel is mapped only after the transition to ring 0. This means:

  1. Syscall cost increased - every syscall flushes some TLB entries.
  2. PCID (Process-Context Identifier) reduces the TLB flush penalty by tagging TLB entries with an address-space ID.
  3. The kernel's "direct map" is not accessible from user space - even speculative execution cannot leak kernel data through cache side-channels as easily.
# Check if KPTI is active
dmesg | grep -i 'page.*table.*isolation\|KPTI\|kaiser'
# Or check /proc/cpuinfo
grep -q ' pti' /proc/cpuinfo && echo "KPTI enabled" || echo "KPTI disabled"

# If your kernel has it, check if PCID is used
grep -q ' pcid' /proc/cpuinfo && echo "PCID supported" || echo "PCID not supported"

Kernel Module Lifecycle

Kernel modules are the extensibility mechanism for Linux. They are ELF relocatable objects loaded at runtime via insmod (traditional) or modprobe (dependency-aware). The finit_module() syscall loads a module from a file descriptor. 

// Minimal kernel module: /usr/src/linux/samples/hello-1.c style
// Place at: sysinternals/kernel-architecture.Containerfile (container)
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Kernel Architecture Lab");

static int __init hello_init(void)
{
    printk(KERN_INFO "[arch-lab] Module loaded. Kernel version: %s\n",
           UTS_RELEASE);
    
    // Print current task's comm
    printk(KERN_INFO "[arch-lab] Loaded by process: %s (PID: %d)\n",
           current->comm, current->pid);
    
    // Demonstrate access to kernel symbols
    printk(KERN_INFO "[arch-lab] current pointer: %px\n", current);
    printk(KERN_INFO "[arch-lab] init_task pointer: %px\n", &init_task);
    
    return 0;
}

static void __exit hello_exit(void)
{
    printk(KERN_INFO "[arch-lab] Module unloaded.\n");
}

module_init(hello_init);
module_exit(hello_exit);
						
# Build and load the module
# (In a VM or container with kernel headers)
make -C /lib/modules/$(uname -r)/build M=$(pwd) modules
sudo insmod hello.ko
sudo dmesg | tail -5
sudo rmmod hello

/proc/kallsyms - The Kernel Symbol Map

/proc/kallsyms is a text interface to the kernel's internal symbol table. It lists the address of every function and variable known to the kernel - including unexported internal symbols. On production systems with kptr_restrict , addresses are hidden from unprivileged users. 

# Show all kernel symbols (requires root or kptr_restrict=0)
sudo head -30 /proc/kallsyms

# Typical output format:
# ffffffff81000000 T startup_64         ← T = Text (code in .text)
# ffffffff81000000 T _text              ← Exact same address
# ffffffff81000110 t secondary_startup_64
# ffffffff82000000 D __per_cpu_start    ← D = Data (initialized)
# ffffffff83400000 R __start_rodata     ← R = Read-only data

# Symbol type codes:
# T/t = Text (code), uppercase = global, lowercase = local
# D/d = Initialized data
# B/b = BSS (zero-initialized data)
# R/r = Read-only data
# A   = Absolute (unchanging address)
# W/w = Weak symbol

# Filter for writeable function pointers (potential hijack targets)
sudo cat /proc/kallsyms | grep -E ' [Dd] ' | head -20

# Find module symbols
sudo cat /proc/kallsyms | grep -E ' \[[a-z]' | head -20
# Modules get a [...] suffix: [ext4], [nf_tables], etc.

Kernel Reconnaissance

# 1. Kernel version and build info
uname -a
cat /proc/version

# 2. Kernel cmdline — what was passed at boot
cat /proc/cmdline

# 3. Kernel config (if enabled)
zcat /proc/config.gz | grep -E 'CONFIG_(KALLSYMS|MODULES|KASLR|SECURITY)'

# 4. Loaded modules with memory footprint
lsmod | sort -k2 -n -r | head -20

# 5. Kernel taint state — has a proprietary module loaded?
cat /proc/sys/kernel/tainted
# Bit meanings (values are bit masks, i.e. 1 << position):
#     1 = proprietary module loaded
#     2 = module force-loaded
#     4 = CPU out of specification
#     8 = module force-unloaded
#    16 = machine check exception
#    32 = bad page
#    64 = user-requested taint
#   128 = kernel died recently (oops/panic)
#   256 = overridden ACPI table
#   512 = warning issued
#  1024 = staging/out-of-tree module
#  2048 = firmware workaround
#  4096 = out-of-tree module
#  8192 = unsigned module
# 16384 = soft lockup
# 32768 = livepatched kernel

# 6. Kernel symbol addresses hidden?
cat /proc/sys/kernel/kptr_restrict
# 0 = unrestricted (development), 1 = restricted to CAP_SYSLOG, 2 = hidden

# 7. Kernel stack protector
cat /sys/kernel/security/lsm
# Shows active LSMs (e.g., "capability,lockdown,yama,apparmor,bpf")

# 8. Check available kernel interfaces
ls /sys/kernel/
ls /sys/module/

# 9. Kernel ring buffer (dmesg) — boot and runtime messages
sudo dmesg | tail -50
sudo dmesg --level=err,warn | tail -20

# 10. Kernel threads — processes with no userspace
ps -eo pid,comm,args | grep -E '^[[:space:]]*[0-9]+ [[]' | head -20
# Kernel threads have their name in brackets: [kthreadd], [ksoftirqd/0], [migration/0]
