Kernel Memory

Kernel heap allocators - kmalloc, vmalloc, page allocator, slab/SLUB internals, memory zones, fragmentation, and kernel memory corruption patterns.

Overview

The kernel cannot swap and has no lazy overcommit, so every allocation is backed by physical memory the moment it succeeds. This article walks the layered allocator stack from the page allocator up through slab/SLUB and vmalloc, shows how to inspect each layer through /proc and /sys , and surveys the corruption patterns (out-of-bounds writes, use-after-free, double-free) that turn allocator bugs into kernel exploit primitives.

Kernel Memory Landscape

The kernel is not a process, but it needs to allocate memory. Every kmalloc() , every new task_struct , every network socket buffer, every inode cache - all consume kernel memory. Unlike user space, the kernel has no swap backing, no lazy overcommit, and no second chance. When the kernel runs out of memory, the OOM killer activates, or the system panics.

Page Allocator and the Buddy System

The page allocator is the foundation. All other allocators (slab, vmalloc) sit on top of it. It manages physical memory using the buddy system - a binary splitting algorithm that maintains free page blocks in power-of-two orders.

Buddy System Data Structure:

Order Block Size Number of pages Memory zone(s)
11 8 MiB (2^11) 2048 ZONE_NORMAL
10 4 MiB 1024 ZONE_NORMAL
9 2 MiB 512 ZONE_NORMAL
8 1 MiB 256 ZONE_NORMAL
...
3 32 KiB 8 ZONE_NORMAL
2 16 KiB 4 ZONE_NORMAL
1 8 KiB 2 ZONE_NORMAL
0 4 KiB (1 page) 1 ZONE_NORMAL 
Per-order freelist: free_area[order].free_list
Each node in the freelist points to struct page of the first page in the block.

Allocation (order=2, 16 KiB):
  ┌─────────────────────┐
  │ Check order=2 free  │
  │ list. If empty:     │
  │   Split order=3     │
  │   block -> two      │
  │   order=2 blocks.   │
  │   Use one, put       │
  │   other on order=2. │
  └─────────────────────┘

Free (order=2 block):
  ┌─────────────────────┐
  │ Check if buddy is   │
  │ free (same order).   │
  │ If yes: coalesce    │
  │   -> order=3 block. │
  │ Recurse upward.     │
  │ If no: put on       │
  │ order=2 freelist.   │
  └─────────────────────┘

The buddy formula

Two pages are buddies if they are the same size, contiguous in physical memory, and the first page's PFN is aligned to 2^(order+1) . 

// /usr/src/linux/mm/page_alloc.c — find_buddy_page()
static inline struct page *__page_find_buddy(struct page *page,
                                              unsigned long page_idx,
                                              unsigned int order)
{
    // Buddy PFN = page_idx XOR (1 << order)
    unsigned long buddy_idx = page_idx ^ (1 << order);
    return page + (buddy_idx - page_idx);
}
// Example: page_idx=4, order=1
//   4 ^ (1 << 1) = 4 ^ 2 = 6  → buddy is PFN 6
//   Blocks [4,5] and [6,7] are order-1 buddies
//   They form block [4,5,6,7] (order=2) when coalesced

Memory Zones

Physical memory is divided into zones. Each zone serves a specific purpose. The zone division exists because of hardware addressing limitations - some devices can only DMA to the first 16 MiB of RAM. 

Memory Zones (x86-64, CONFIG_ZONE_DMA=n, CONFIG_ZONE_DMA32=y):

┌───────────────────────────────────────────────────────────┐
│ ZONE_DMA (0–16 MiB)                                        │
│ For legacy ISA devices. Usually empty on modern systems.   │
│ CONFIG_ZONE_DMA can be disabled on x86-64.                 │
└───────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────┐
│ ZONE_DMA32 (16 MiB – 4 GiB)                                │
│ For 32-bit PCI devices that cannot address >4GiB.          │
│ GFP_DMA32 allocations come from here.                      │
└───────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────┐
│ ZONE_NORMAL (4 GiB – 64 TiB)                               │
│ Direct-mapped by the kernel. All normal allocations.       │

└───────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────┐

GFP Flags: Asking the Kernel for Memory

Every kernel allocation specifies GFP (Get Free Pages) flags that control where the allocation comes from and what the allocator is allowed to do. 

// /usr/src/linux/include/linux/gfp_types.h
// Important GFP flag combinations:

// ---- GFP_KERNEL — the default for most kernel code ----
// Can block (sleep), can reclaim pages, can trigger OOM
#define GFP_KERNEL  (__GFP_RECLAIM | __GFP_IO | __GFP_FS)

// ---- GFP_ATOMIC — for interrupt context, cannot sleep ----
// Returns NULL if no memory is immediately available.
// Has a small emergency reserve.
#define GFP_ATOMIC  (__GFP_HIGH | __GFP_ATOMIC | __GFP_KSWAPD_RECLAIM)

// ---- GFP_NOWAIT — do not block, do not reclaim ----
// Like ATOMIC but without the emergency reserve.
#define GFP_NOWAIT  (__GFP_KSWAPD_RECLAIM)

// ---- GFP_NOFS — may block, may reclaim, but NO filesystem operations ----
// Prevents recursion into filesystem code.
#define GFP_NOFS    (__GFP_RECLAIM | __GFP_IO)

// ---- GFP_NOIO — may block, but NO I/O at all ----
// Prevents block layer recursion.
#define GFP_NOIO    (__GFP_RECLAIM)

// ---- GFP_DMA / GFP_DMA32 — request specific zones ----
// GFP_DMA:    ZONE_DMA  (0-16 MiB)
// GFP_DMA32:  ZONE_DMA32 (0-4 GiB)

// ---- GFP_USER — user-space triggered allocation ----
// Allowed to reclaim and trigger OOM.
#define GFP_USER    (__GFP_RECLAIM | __GFP_IO | __GFP_FS | __GFP_HARDWALL)

// ---- Individual flag bits ----
// __GFP_DIRECT_RECLAIM  — caller can block and invoke direct reclaim
// __GFP_KSWAPD_RECLAIM  — caller can wake kswapd (background reclaim)
// __GFP_RECLAIM          — shortcut for both reclaim bits
// __GFP_IO               — allocator can start filesystem I/O
// __GFP_FS               — allocator can call filesystem operations
// __GFP_HIGH             — can use emergency reserves
// __GFP_MEMALLOC          — can access ALL memory (used by reclaim itself)
// __GFP_NOWARN            — suppress allocation failure warning
// __GFP_ZERO              — zero the allocated memory
// __GFP_COMP              — allocate compound pages (for huge pages)

Common GFP Bugs and Exploit Primitives

  • Using GFP_KERNEL in atomic context -> sleeping while atomic -> kernel panic or exploitable state
  • Using GFP_ATOMIC for large allocations -> always failing under memory pressure
  • Forgetting __GFP_ZERO -> information disclosure (uninitialized kernel memory returned to user space)

SLUB: The Default Slab Allocator

SLUB is the default slab allocator since Linux 2.6.23 ( CONFIG_SLUB=y ). It replaced the older SLAB allocator with a simpler, more CPU -cache-friendly design; SLOB is a separate allocator for memory-constrained systems. SLUB does not maintain per-cache freelist arrays - instead, it embeds the freelist pointer directly in free objects. 

SLUB Architecture:

Slab Object Layout and Embedded Freelist

Free object (256 bytes):
┌────────────────────────────────────────────────┐
│ offset 0: <freelist_ptr>  ← points to next free │
│ offset 8: <data... (248 bytes of stale data)>   │
│           ...                                    │
│ offset 255: <last byte>                         │
└────────────────────────────────────────────────┘

Allocated object (256 bytes):
┌────────────────────────────────────────────────┐
│ offset 0: <caller data (256 bytes)>             │
│           The entire object is usable           │
└────────────────────────────────────────────────┘

When freed: freelist pointer is written to offset 0 of the object.
When allocated: caller overwrites offset 0 with their own data.

Kernel hardening (CONFIG_SLAB_FREELIST_HARDENED):
  → freelist_ptr is obfuscated:
    freelist_ptr = (ptr ^ random ^ (address_of_freelist >> 12))
  → Prevents freelist corruption through linear heap overflows
  → Also adds freelist pointer to a different offset (offset field)

kmalloc - The Kernel's malloc()

kmalloc() allocates physically contiguous memory from a slab cache. Internally, it selects a pre-allocated kmem_cache based on the requested size (rounded up to the nearest power of two or common size). 

// /usr/src/linux/include/linux/slab.h
// kmalloc size → cache mapping (kmalloc-96, kmalloc-192, kmalloc-512, etc.)
// Common cache sizes on x86-64:
//   8, 16, 32, 64, 96, 128, 192, 256, 512, 1024, 2048, 4096, 8192

void *ptr = kmalloc(150, GFP_KERNEL);   // Allocates from kmalloc-192 cache
// 150 rounded up to 192 → one of 21 objects in a 4 KiB slab page (192 * 21 = 4032)

// kmalloc can allocate up to ~4 MiB (via kmalloc_large → alloc_pages)
void *large = kmalloc(1024 * 1024, GFP_KERNEL);  // 1 MiB → compound pages
						
# List all kmalloc caches
sudo cat /proc/slabinfo | grep "^kmalloc" | sort -t'-' -k2 -n
# Output shows: kmalloc-8, kmalloc-16, ..., kmalloc-8192, kmalloc-rcl-*, etc.

# Show cache merging (aliases)
sudo cat /sys/kernel/slab/kmalloc-96/aliases 2>/dev/null
# Shows which other caches are merged into this one

vmalloc: Virtual vs Physical Layout

vmalloc() allocates memory that is contiguous in the kernel's virtual address space but may be scattered across arbitrary physical pages. This avoids fragmentation issues but introduces TLB pressure and a minor performance penalty. 

// /usr/src/linux/mm/vmalloc.c
void *vmalloc(unsigned long size);
void *vzalloc(unsigned long size);  // vmalloc + zero
void vfree(const void *addr);

// vmalloc is appropriate when:
//   1. Physical contiguity is not required (most kernel code doesn't need it)
//   2. The allocation is large (> several pages)
//   3. kmalloc() fails due to fragmentation
//   4. The lifecycle is long (no hot-path usage)

// vmalloc drawbacks:
//   - Requires page table updates (TLB shootdown for every mapping)
//   - Slower to allocate and free
//   - Slower access (TLB is finite, vmalloc region is huge)
//   - Cannot be used for DMA (device needs physical addresses)

// Example: kernel module loading uses vmalloc for module .text/.data
						
# Inspect vmalloc region usage
sudo cat /proc/vmallocinfo | head -30
# Output format:
# 0xffff888010000000-0xffff888010001000   4096 module_alloc+0x... pages=1 vmalloc
# StartAddr-EndAddr Size Caller

# Show vmalloc usage summary
sudo cat /proc/vmallocinfo | awk '{sum+=$2} END {printf "Total vmalloc: %d bytes (%.1f MiB)\n", sum, sum/1048576}'

# Who is using vmalloc?
sudo cat /proc/vmallocinfo | awk -F'/' '{print $NF}' | sort | uniq -c | sort -rn | head -10

Kernel Stack

Each thread in Linux gets a kernel stack of THREAD_SIZE bytes (typically 16 KiB = 4 pages on x86-64 with CONFIG_THREAD_SIZE_ORDER=2 ). The task_struct is embedded at the bottom (or referenced from thread_info on older architectures). 

Kernel Stack Layout (x86-64, CONFIG_THREAD_INFO_IN_TASK=y):

High address (stack grows downward)
┌──────────────────────────────┐
│                              │
│  Stack frames (grows ↓)      │
│                              │
│  ...                         │
│  Frame N                     │
│  Frame N-1                   │
│  ...                         │
├──────────────────────────────┤ ← stack pointer (RSP)
│  Unused space                │
├──────────────────────────────┤
│                              │
│  task_struct                 │ ← current pointer (embedded)
│  (allocated separately,      │
│   pointed to by per-CPU var) │
│                              │
└──────────────────────────────┘
Low address

Kernel stack overflow detection:
  - CONFIG_VMAP_STACK: kernel stack allocated from vmalloc,
                       with guard pages (unmapped) on both sides
  - Stack overflow → page fault in guard page → double fault handler → panic
  - Without VMAP_STACK: overflow silently corrupts adjacent memory

grep THREAD_SIZE /boot/config-$(uname -r) 2>/dev/null
# CONFIG_THREAD_SIZE_ORDER=2 → 2^2 pages = 16 KiB

# Check if VMAP_STACK is enabled
grep VMAP_STACK /boot/config-$(uname -r)

# Show per-thread kernel stack usage
sudo cat /proc/1/stack 2>/dev/null
# Shows kernel stack trace for PID 1

# Check stack sizes of kernel threads
for pid in $(ps -eo pid=); do
    [ -f /proc/$pid/status ] && awk '/VmStk/{print "'$pid':", $2}' /proc/$pid/status
done 2>/dev/null | sort -t: -k2 -n | tail -10

Kernel Memory Corruption Patterns

Kernel heap vulnerabilities are exploited differently from userland. There's no exit() - a corrupted kernel must either be stabilized or exploited before the crash.

1. Slab out-of-bounds write

// Vulnerable code pattern:
struct vuln_obj {
    unsigned long data[4];  // 32 bytes on 64-bit
    unsigned long *fn_ptr;  // Function pointer at offset 32
};
// Allocated from a 64-byte slab cache (or merged with another)

struct vuln_obj *obj = kmalloc(sizeof(*obj), GFP_KERNEL);  // 40 bytes
// If sizeof(*obj) >= 32 and written with data[5] = attacker_addr,
// fn_ptr is corrupted.
// Exploit: trigger fn_ptr call → redirect to attacker's ROP/JOP chain

2. Use-after-free in slab

// Vulnerable pattern:
struct vuln_obj *obj = kmalloc(sizeof(*obj), GFP_KERNEL);
// ... use obj ...
kfree(obj);       // Freed back to slab freelist
// ... bug: obj still referenced ...
obj->fn_ptr();    // Use-after-free: fn_ptr slot may now hold
                  // the freelist pointer or attacker-controlled data
                  // if the slab was reallocated.

3. Double-free

// Double free → slab freelist corruption
kfree(obj);       // obj goes to freelist
// ...
kfree(obj);       // Double free!
// Now the freelist has a cycle → next two allocations return same address
// This is a powerful exploit primitive: overlapping allocations

4. Invalid-free / wrong cache

// Freeing a pointer to the wrong slab cache
char *p = kmalloc(256, GFP_KERNEL);  // From kmalloc-256 cache
kfree(p - 16);  // Free with wrong pointer → slab metadata corruption
                // CONFIG_SLAB_FREELIST_HARDENED may detect this
                // Otherwise: silent corruption of slab freelist

#   0xbb = SLAB_RED_INACTIVE (for guard zone when write after free)

Kernel Address Sanitizer (KASAN)

KASAN is a compiler-based tool that detects out-of-bounds accesses and use-after-free bugs in the kernel. It uses a shadow memory region where each byte represents the accessibility of 8 bytes of kernel memory. 

KASAN Shadow Memory Mapping:

Kernel virtual address >> 3 = shadow address (plus offset)
Shadow byte value:
  0x00 = all 8 bytes accessible
  0x01 - 0x07 = that many bytes accessible (partial)
  0xFB = freed slab object (use-after-free)
  0xFC = red zone around a slab object
  0xF1 - 0xF4 = stack red zone (left, mid, right, partial)
  0xFF = freed page
  0xFE = inaccessible (shadow gap or invalid tag)

Shadow memory is 1/8 the size of kernel virtual memory.
Typical offset: 0xdffffc0000000000 (x86-64)
						
# Check if KASAN is enabled in your kernel
grep KASAN /boot/config-$(uname -r) 2>/dev/null

# Most production kernels have CONFIG_KASAN=n because of the 2x slowdown.
# Ubuntu/Debian offer "linux-image-*-kasan" debug kernels.
# For Arch, build a custom kernel with CONFIG_KASAN=y.

# KASAN reports (in dmesg) look like:
# ==================================================================
# BUG: KASAN: slab-out-of-bounds in some_function+0x123/0x456
# Write of size 8 at addr ffff888123456789 by task modprobe/1234

Memory Fragmentation and Exhaustion

Kernel memory fragmentation occurs when the buddy allocator has many free pages but cannot satisfy a contiguous allocation request. 

External fragmentation:
  Free pages: [P] [P] [P] [P] (4 contiguous pages)
  After allocations: [A1] [Free] [A2] [Free]
  Need 2 contig pages → fail (despite 2 pages free)
  
  Solution: compaction (CONFIG_COMPACTION)
    → kcompactd migrates movable pages to create larger contig blocks

Internal fragmentation:
  kmalloc(100) → allocates from kmalloc-192 cache (192 bytes)
  Wastes 92 bytes per allocation.
  
  Slab caches are sized to minimize this, but there's always some waste.
						
# Assess fragmentation
cat /proc/buddyinfo

# Check for compaction activity
cat /proc/vmstat | grep compact

# Memory fragmentation index (higher = more fragmented)
grep -E "extfrag|unusable" /sys/kernel/debug/extfrag/extfrag_index 2>/dev/null | head -5
# Or:
cat /sys/kernel/debug/extfrag/unusable_index 2>/dev/null || echo "debugfs not mounted"

cat /sys/kernel/debug/extfrag/extfrag_index 2>/dev/null | head -20

grep . /sys/kernel/debug/extfrag/unusable_index 2>/dev/null

# Trigger manual compaction
echo 1 | sudo tee /proc/sys/vm/compact_memory 2>/dev/null

Kernel OOM - When the Kernel Runs Out

Unlike user space, the kernel cannot swap itself. When a kernel allocation fails: - For GFP_ATOMIC : returns NULL , caller must handle it - For GFP_KERNEL with __GFP_NORETRY : returns NULL

  • For GFP_KERNEL (default): invokes OOM killer if reclaim fails

However, kernel allocations failing deep in the kernel (page fault handler, filesystem code) often result in a BUG() or panic() because there's no clean recovery path.
