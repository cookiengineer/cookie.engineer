Virtualization

Full virtualization with QEMU and KVM , hardware acceleration, hypervisor types, virtio, libvirt, and virtual machine security.

Overview

Virtualization runs an entire guest operating system, with its own kernel, on top of a host. Unlike a container, which shares the host kernel, a virtual machine is isolated by hardware: the CPU has a special mode for guests, the memory-management unit adds a second translation layer, and device access goes through an emulator or a paravirtualized driver. This article explains how KVM and QEMU split that work, how virtio and libvirt fit in, and how attacks such as VM escape and side channels break the boundary. After reading it you can launch a VM , check the hardware support, and reason about the isolation guarantees.

Required Reading

  • Containers - containers as the lighter isolation layer
  • Processes - process lifecycle and CPU modes
  • Virtual Memory - page tables and address translation

1. Full Virtualization

Full virtualization emulates a complete hardware platform. The guest OS runs unmodified, unaware it is virtualized. The hypervisor intercepts privileged operations and emulates hardware devices. 

Guest VM
  Guest Applications
  Guest OS Kernel
  Virtual Hardware (vCPU, vRAM, vNIC, vDisk) — QEMU emulated
  -----------------------------------------------
  Hypervisor (KVM kernel module)
  -----------------------------------------------
  Host OS Kernel
  -----------------------------------------------
  Physical Hardware (CPU, RAM, NIC, Disk)
Component Function
KVM Kernel module: turns Linux into a hypervisor (uses Intel VT-x / AMD-V)
QEMU Userspace: emulates devices (disk, network, display, USB)
libvirt Management: CLI (virsh), GUI (virt-manager), API
virtio Paravirtualized drivers: aware of hypervisor, high performance

2. Hardware Acceleration

Without hardware acceleration, the hypervisor must use binary translation: scan guest code, rewrite privileged instructions, and emulate them. This is slow.

Intel VT-x and AMD-V add CPU modes specifically for virtualization:

2.1 CPU Modes

Intel VT-x:
  VMX Root Mode    — Hypervisor runs here (ring 0 of the hypervisor)
  VMX Non-Root Mode — Guest runs here (the guest's ring 0)
  
  VMENTRY: Transition root -> non-root (enter guest)
  VMEXIT:  Transition non-root -> root (exit to hypervisor)
  
AMD-V:
  VMRUN — enters guest mode
  #VMEXIT — exits to hypervisor

VMEXIT triggers:
  - I/O instructions (IN, OUT)
  - MSR access (RDMSR, WRMSR)
  - CPUID instruction
  - CR3/CR8 writes (page table changes)
  - Interrupt window
  - HLT (halt) instruction
  - EPT violations (extended page table faults)

When the guest executes a privileged instruction, the CPU exits to the hypervisor. The hypervisor then handles the event: emulate the instruction, update virtual hardware state, or inject a virtual interrupt. The hypervisor then issues VMENTRY to resume the guest.

2.2 Checking Hardware Support

# Check for Intel VT-x
grep -E 'vmx' /proc/cpuinfo | head -1
# flags: ... vmx ...

# Check for AMD-V
grep -E 'svm' /proc/cpuinfo | head -1
# flags: ... svm ...

# Verify KVM module is loaded
lsmod | grep kvm
# kvm_intel          315392  0
# kvm                737280  1 kvm_intel

# Check that /dev/kvm exists
ls -la /dev/kvm
# crw-rw-rw-+ 1 root kvm 10, 232 ...

# Enable nested virtualization (run VMs inside VMs)
# For Intel:
echo "options kvm_intel nested=1" > /etc/modprobe.d/kvm-intel.conf
# For AMD:
echo "options kvm_amd nested=1" > /etc/modprobe.d/kvm-amd.conf
modprobe -r kvm_intel kvm && modprobe kvm_intel
# Verify:
cat /sys/module/kvm_intel/parameters/nested
# Y

# Check if KVM is available to the current user
# (user must be in the 'kvm' group)
usermod -aG kvm $USER

3. QEMU - Hardware Emulation

QEMU emulates the hardware devices that the guest OS sees. Without KVM , QEMU does full software emulation (binary translation, slow). With KVM , QEMU handles device emulation while KVM handles CPU and memory virtualization.

3.1 QEMU Device Emulation

Devices QEMU emulates:
  - CPU: instruction set + features exposed via CPUID
  - Memory: RAM allocated from host, managed by EPT/NPT
  - Storage: virtio-blk, SCSI, IDE, NVMe
  - Network: virtio-net, e1000, rtl8139
  - Display: VGA, virtio-gpu, QXL (SPICE)
  - Input: PS/2 keyboard/mouse, USB tablet
  - Sound: AC97, HDA (Intel HD Audio)
  - Firmware: BIOS (SeaBIOS) or UEFI (OVMF/edk2)
  - Other: PCI bus, USB controller, RTC, ACPI tables

3.2 Running a VM with QEMU/KVM Directly

# Install QEMU
pacman -S qemu-desktop

# Create a disk image
qemu-img create -f qcow2 vm-disk.qcow2 20G

# Basic VM invocation (CD-ROM boot)
qemu-system-x86_64 \
    -enable-kvm \
    -cpu host \
    -m 4096 \
    -smp 4 \
    -drive file=vm-disk.qcow2,if=virtio,format=qcow2 \
    -cdrom archlinux-2024.06.01-x86_64.iso \
    -boot d \
    -netdev user,id=net0 \
    -device virtio-net,netdev=net0 \
    -vga virtio \
    -display gtk \
    -name "Arch Linux VM"

# Explanation of each flag:
#   -enable-kvm         : Use KVM hardware acceleration
#   -cpu host           : Expose host CPU features to guest
#   -m 4096             : 4 GB RAM
#   -smp 4              : 4 virtual CPU cores
#   -drive file=...,if=virtio,format=qcow2 : VirtIO disk
#   -cdrom ...          : Attach ISO as CD-ROM
#   -boot d             : Boot from CD-ROM first
#   -netdev user,id=net0: User-mode networking (NAT, no root needed)
#   -device virtio-net  : VirtIO network adapter
#   -vga virtio         : VirtIO GPU
#   -display gtk        : GTK window output

3.3 QEMU Networking Modes

Mode Command Privileged? Guest Access Notes
User mode (SLIRP) -netdev user,id=net0 No (rootless) NAT to host network Performance limited
Tap bridge -netdev tap,id=net0 Yes (root) Full network (bridge) Highest performance
Socket -netdev socket,id=net0,... No Connected to socket VM-to-VM only
VDE -netdev vde,id=net0,... Depends Virtual switch Legacy 
# User-mode networking with port forwarding
qemu-system-x86_64 \
    -enable-kvm \
    -netdev user,id=net0,hostfwd=tcp::8080-:80,hostfwd=tcp::2222-:22 \
    -device virtio-net,netdev=net0 \
    ...

# Host port 8080 -> guest port 80 (HTTP)
# Host port 2222 -> guest port 22 (SSH)

# Connect via SSH:
ssh -p 2222 user@localhost

4. Paravirtualization and virtio

Paravirtualization means the guest OS is aware it is virtualized and cooperates with the hypervisor. virtio is the Linux standard for paravirtualized devices.

4.1 virtio Architecture

Guest OS
  virtio front-end driver  (e.g., virtio-blk, virtio-net, virtio-rng)
         |
  virtio transport (PCI, MMIO, CCW)
         |
  virtqueue (shared memory ring buffer)
         |
  virtio back-end (in QEMU) — processes I/O requests

virtqueues are shared-memory ring buffers between guest and host. The guest places I/O requests in the queue and kicks the host (via VMEXIT ). The host processes requests and notifies the guest via interrupt. This eliminates per-byte VMEXIT overhead - an entire I/O batch is processed in one transition.

4.2 virtio Drivers

Driver Device Performance Gain vs Emulated
virtio-blk Block storage 2-5x (vs IDE/SATA)
virtio-scsi SCSI storage 2-4x
virtio-net Network 3-10x (vs e1000/rtl8139)
virtio-rng Random number N/A (adds host entropy)
virtio-gpu Graphics (2D) Native-like for 2D
virtio-balloon Memory ballooning N/A (enables overcommit)
virtio-serial Serial/console Multiport serial
virtio-input Input devices Lower latency
virtio-fs Filesystem sharing Host filesystem passthrough

All modern Linux kernels include virtio drivers. Windows requires virtio-win driver package (from Fedora project). 

# Verify virtio drivers are loaded in a Linux guest
lsmod | grep virtio
# virtio_net, virtio_blk, virtio_pci, virtio_ring, virtio

# Check virtio device details
lspci | grep -i virtio
# 00:03.0 Ethernet controller: Red Hat, Inc. Virtio network device
# 00:06.0 SCSI storage controller: Red Hat, Inc. Virtio block device

4.3 Memory Ballooning

virtio-balloon allows the hypervisor to reclaim unused guest memory:

1. Hypervisor requests guest to inflate balloon
2. Guest balloon driver allocates pages, pins them, reports addresses to hypervisor
3. Hypervisor unmaps those pages from guest and reuses host pages
4. Guest memory pressure triggers deflation: hypervisor returns pages to guest

This enables memory overcommit: running VMs whose total RAM exceeds physical host RAM,
because guests rarely use all allocated memory simultaneously.

5. libvirt - Virtualization Management

libvirt provides a unified API for managing KVM /QEMU, Xen, LXC, and other hypervisors. Tools include virsh ( CLI ) and virt-manager ( GUI ).

5.1 libvirt Architecture

virt-manager  |  virsh  |  virt-install  |  virt-viewer
              |         |                |
         libvirt daemon (libvirtd)
              |
       hypervisor drivers
         qemu | xen | lxc | vbox
              |
         KVM/QEMU (hypervisor)

# Add user to libvirt group

# Create an Arch Linux VM

    --name arch-vm \
    --ram 4096 \
    --vcpus 4 \

6.3 Backing Chains

overlay.qcow2 (writable, your changes)
  |  backing file
  v
base.qcow2 (read-only base, e.g., OS installed)
  |  backing file
  v
template.qcow2 (read-only template, e.g., base Arch install)

Only overlay is writable. Changes in overlay override backing file data.
This enables VM pools: 100 VMs with 100 overlays, 1 base image.
						
# Create template base
qemu-img create -f qcow2 template.qcow2 20G
# Install Arch to template.qcow2...

# Create a derived VM image
qemu-img create -f qcow2 -b template.qcow2 -F qcow2 vm1.qcow2
# vm1.qcow2 is tiny (few MB), only stores differences from template.

# Commit changes from overlay into backing
qemu-img commit vm1.qcow2
# WARNING: modifies template.qcow2!

7. Nested Virtualization

Running a hypervisor inside a VM . Requires the host hypervisor to expose VMX / SVM to the guest. 

# Host: Enable nested virtualization
echo "options kvm_intel nested=1" > /etc/modprobe.d/kvm-intel.conf
# Reload KVM module or reboot

# Guest XML: expose VMX/SVM feature
# In the <cpu> element:
<cpu mode='host-passthrough' check='none'>
  <feature policy='require' name='vmx'/>
</cpu>
# Or for AMD:
# <feature policy='require' name='svm'/>

# Inside the guest, verify nested KVM is available
grep -E 'vmx|svm' /proc/cpuinfo
ls -la /dev/kvm

# Now you can run VMs inside VMs.
# Each nesting level adds ~10-15% performance overhead.

9. VM Escape

VM escape is a guest-to-host attack where code running inside a VM gains access to the host hypervisor or other virtual machines. These are the most severe virtualization vulnerabilities.

9.1 Escape Vectors

Vector Mechanism Examples
Hypervisor bug Memory corruption in device emulation VENOM (CVE-2015-3456), Cloudburst (CVE-2009-1244)
Paravirtual driver bug Guest-controlled driver exploits host virtio, VMware Tools, Hyper-V Integration Services
MMIO/PIO emulation Malicious guest MMIO access Various QEMU CVEs
DMA attack Guest DMA to physical memory bypasses IOMMU Thunderclap (Thunderbolt DMA)
Side channel Information leak via shared resources Spectre/Meltdown, L1TF/Foreshadow, MDS

9.2 VENOM (CVE-2015-3456)

QEMU's virtual floppy disk controller ( FDC ) had a buffer overflow. The FDC is present even if no virtual floppy is attached. A privileged user inside the guest could send specially crafted FDC commands to trigger the overflow and execute arbitrary code in the QEMU process (which runs as root or the libvirt-qemu user on the host). 

Vulnerability:
  - QEMU emulated a floppy disk controller (FDC)
  - FDC FIFO buffer was fixed-size
  - Guest could write more data than buffer size
  - Buffer overflow in QEMU process

Impact:
  - Code execution in QEMU process context
  - QEMU runs as root or libvirt-qemu user
  - Access to all VM disk images and configuration

Mitigation:
  - Patch QEMU (fixed in all distributions)
  - Remove unused devices from VM configuration
  - Run QEMU with reduced privileges
  - Use sVirt (SELinux) or AppArmor to confine QEMU

9.3 Mitigation Techniques

# Run QEMU with reduced privileges
# In libvirt, the default is to run as qemu:qemu (not root)
# Verify:
ps aux | grep qemu
# qemu    12345  ...  /usr/bin/qemu-system-x86_64 ...

# Use sVirt (SELinux) or AppArmor confinement
# Each VM gets a unique MCS label (SELinux)
ps -eZ | grep qemu
# system_u:system_r:svirt_t:s0:c123,c456

# Enable IOMMU to prevent DMA attacks
# Kernel command line: intel_iommu=on iommu=pt
# or: amd_iommu=on iommu=pt

# Verify IOMMU is active
dmesg | grep -i iommu
# DMAR: IOMMU enabled
# AMD-Vi: IOMMU enabled

# libvirt can use <iommu> element to map devices with IOMMU

10. Side-Channel Attacks

Shared hardware ( CPU caches, branch predictors, TLBs) creates side channels between virtual machines on the same physical host. This is particularly relevant in cloud environments where multiple customers share the same hardware.

10.1 Cache Side Channels

Spectre v1 (Bounds Check Bypass):
  - Train branch predictor to mispredict a bounds check
  - Access secret memory speculatively
  - Secret affects cache state
  - Measure cache timing to extract secret bits

Spectre v2 (Branch Target Injection):
  - Poison indirect branch predictor (BTB)
  - Victim's indirect branch speculatively jumps to attacker gadget
  - Gadget leaks data through cache

Meltdown:
  - On Intel CPUs (pre-Ice Lake), speculatively access kernel memory
  - Exception is raised late (after speculative execution)
  - Cache state changes are NOT rolled back
  - User-space can read kernel memory

Mitigations (Linux kernel):
  - KPTI (Kernel Page Table Isolation): separate user/kernel page tables
  - Retpoline: indirect branch via return stack (not BTB)
  - IBRS/IBPB: microcode-based speculation control
  - SSBD: Speculative Store Bypass Disable

11. Virtualization Detection

Malware often detects virtualization to avoid analysis. Guest OS can detect it is virtualized through multiple methods:

11.1 CPUID-Based Detection

#include <cpuid.h>
#include <stdio.h>

int is_hypervisor(void) {
    unsigned int eax, ebx, ecx, edx;
    
    // CPUID leaf 0x1: ECX bit 31 = hypervisor present
    __cpuid(1, eax, ebx, ecx, edx);
    if (ecx & (1 << 31))
        return 1;
    
    // CPUID leaf 0x40000000: hypervisor vendor string
    char vendor[13] = {0};
    __cpuid(0x40000000, eax, ebx, ecx, edx);
    *(unsigned int*)(vendor)     = ebx;
    *(unsigned int*)(vendor + 4) = ecx;
    *(unsigned int*)(vendor + 8) = edx;
    
    printf("Hypervisor: %s\n", vendor);
    return 1;
    
    return 0;
}

11.3 Anti-Detection with QEMU

# Hide KVM signature (add to QEMU command line)
-cpu host,kvm=off

# Use a different MAC OUI
-netdev user,id=net0 \
-device virtio-net,netdev=net0,mac=DE:AD:BE:EF:00:01

# Or via libvirt XML:
<features>
  <kvm>
    <hidden state='on'/>
  </kvm>
</features>

# Hide hypervisor CPUID leaf
<cpu mode='host-model'>
  <feature policy='disable' name='hypervisor'/>
</cpu>

These techniques are legitimate for malware analysis environments, compatibility testing, and avoiding unwanted behavior from guest OS licensing or DRM software.

12. Performance Tuning

12.1 CPU Pinning

Pin virtual CPU s to specific physical CPU s to avoid cache migration: 

<cputune>
  <vcpupin vcpu='0' cpuset='0'/>
  <vcpupin vcpu='1' cpuset='1'/>
  <vcpupin vcpu='2' cpuset='2'/>
  <vcpupin vcpu='3' cpuset='3'/>
  <emulatorpin cpuset='0-3'/>
</cputune>

12.2 Huge Pages

Enabling huge pages reduces TLB misses:

# Host: reserve huge pages
echo 2048 > /proc/sys/vm/nr_hugepages

# Or via sysctl:
# vm.nr_hugepages = 2048
# vm.hugetlb_shm_group =  (libvirt group group ID)

# Verify
cat /proc/meminfo | grep Huge
# HugePages_Total:    2048
# Hugepagesize:       2048 kB

# libvirt XML:
<memoryBacking>
  <hugepages/>
</memoryBacking>

12.3 I/O Threads

Dedicated I/O threads prevent VM I/O from competing with vCPU threads: 

<domain>
  <iothreads>1</iothreads>
  <devices>
    <disk type='file' device='disk'>
      <driver name='qemu' type='qcow2' iothread='1'/>
      ...
    </disk>
  </devices>
</domain>

14. Summary

Virtualization provides hardware-level isolation between workloads:

Isolation hierarchy (strongest to weakest):

1. Physical separation — Different machines, different hardware
2. Type 1 Hypervisor — KVM, ESXi, Xen (hardware-enforced boundary)
3. Type 2 Hypervisor — VirtualBox, VMware Workstation
4. Containers — Namespaces, cgroups (kernel boundary)
5. Application sandboxes — chroot, seccomp, Flatpak/Snap

KVM with QEMU:
  - Intel VT-x / AMD-V provide CPU-level isolation
  - EPT/NPT provide memory isolation (guest cannot access host memory)
  - IOMMU protects against malicious DMA
  - virtio provides near-native I/O performance
  - libvirt provides management at scale

Use VMs when you need:
  - Different kernels (Linux + Windows)
  - Stronger isolation (untrusted workloads, multi-tenant)
  - Full OS environment with init system
  - Hardware-level snapshot and migration

Use containers (see Containers article) when you need:
  - Same kernel, isolated userspace
  - Fast startup and high density
  - Lightweight application packaging
  - Development/production parity

Challenge

Write a Go program that detects whether it is running under a hypervisor by reading the CPUID hypervisor bit. The cgo wrapper calls __get_cpuid from GCC's cpuid.h ; the starter only reports the bit, so extend it to read the hypervisor vendor string from leaf 0x40000000 : 

package main

/*
#include <cpuid.h>

static int hypervisor_present(void) {
	unsigned int eax, ebx, ecx, edx;
	if (__get_cpuid(1, &eax, &ebx, &ecx, &edx))
		return (ecx >> 31) & 1;
	return -1;
}
*/
import "C"

import "fmt"

func main() {
	switch C.hypervisor_present() {
	case 1:
		fmt.Println("hypervisor present (CPUID.1:ECX[31] is set)")
	case 0:
		fmt.Println("no hypervisor bit set")
	default:
		fmt.Println("CPUID leaf 1 not supported")
	}
}

Run it with go run main.go on the host and, if you have one available, inside a KVM guest. Then add a second cgo function that executes CPUID leaf 0x40000000 and returns the 12-byte vendor string ( KVMKVMKVM , Microsoft Hv , or VMwareVMware ). Compare all three detection paths: grep -c vmx /proc/cpuinfo , ls -l /dev/kvm , and the CPUID vendor string.
