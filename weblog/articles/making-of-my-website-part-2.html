Making of My Website Part 2 - Cookie Avatar

This is the second article of the series, the first article of this series described the Making of My Website Part 1: Cookie Consent Game

As I already decided on the Galactic Cookie Empire theme, I had to implement my avatar in a matching manner, and make him behave, talk and feel like the dangerous and mysterious Emperor Palpatine .

I think the Cookie Engineer themed avatar was actually quite the ideal candidate for an Anti-Cookie Consent Game . My previous website already featured a little never-ending shooting arcade game, but that was boring after a while.

So this time, I decided to lean into the theme for good and make it as fun as possible.

DOM Shenanigans

By default, the website's HTML structure already positions a placeholder figure element that contains the img element with the placeholder image. This way the website will be usable with JavaScript disabled, so all the folks using uBlock Origin have a good enough experience for the website, while they will miss out on the hidden fun in return, of course! 

<figure id="avatar">
	<img alt="Cookie Engineer's Avatar" src="/design/about/cookiengineer.png" width="256" height="256"/>
	<figcaption>
		Hello, I'm <b>Cookie Engineer</b>,<br/>
		a Cyber Defense Engineer with AI, NetSec, WebSec, and OSINT experience.
	</figcaption>
	<!-- This is where the animated Avatar goes -->
	<canvas></canvas>
</figure>

So when we look at the DOM, the figure element is positioned with position: relative , whereas the canvas element that is overlayed on top of that img element later is positioned with position: absolute and then just from the top left via top: 16px and left: 16px to match the image's offsets. 

figure#avatar {
	display: block;
	position: relative;
	/* ... */
}

figure#avatar > img {
	display: inline-block;
	position: relative;
	width: 256px;
	height: 256px;
	user-select: none;
	z-index: 10;
	/* ... */
}

figure#avatar > canvas {
	display: inline-block;
	position: absolute;
	width: 256px;
	height: 256px;
	top: 16px;
	right: auto;
	bottom: auto;
	left: 16px;
	user-select: none;
	z-index: 11;
	/* ... */
}

Eyes

The most important part of the website interaction is the interaction with the mouse cursor. The Avatar always follows the cookie, and depending on other emotions and interactions, will feel and behave differently.

The eyes always follow the movement of the cursor, which is rendered as a Cookie . If the mouse position gets too close to the Avatar's eyes, they're squinted a little. 

// In part from avatar/draw/DrawEyeBall.mjs
import { eyes } from "./eyes.mjs";

export const DrawEyeBall = (ctx, side, position, feeling) => {

	let eye = eyes[side] || null;
	if (eye !== null) {

		let dist = 128;

		if (typeof position["x"] === "number" && typeof position["y"] === "number") {
			dist = Math.sqrt(Math.pow(eye["ball"]["x"] - position["x"], 2) + Math.pow(eye["ball"]["y"] - position["y"], 2), 2);
		}

		if (feeling === "angry") {
			/* ... Draw Other Emotion ... */
		} else if (dist < 128) {

			ctx.beginPath();
			ctx.ellipse(
				eye["ball"]["x"], eye["ball"]["y"],
				eye["ball"]["r"],
				eye["ball"]["r"] - eye["ball"]["r"] * 0.15 * (1 - (dist / 128)), // This is the squint magic here
				0, 0, Math.PI * 2
			);
			ctx.fillStyle = "#ffffff";
			ctx.fill();
			ctx.closePath();

		} else {
			/* ... Draw Full Eye Ball ... */
		}

	}

};

Emotions

I wanted the Avatar to have different emotions, depending on the interactions with it. I implemented the emotions okay , sick , and angry as its emotions. Technically, there's also the vomit feeling that is a special emotion that the avatar will be in after it had to vomit and is recovering back to okay again.

I tried to make it a little fun to interact with the Avatar, where you can hurt and make it angry by clicking on it, and you can make it sick when it tries to follow the rapidly moving mouse pointer with its eyes.

Color Interpolation

Color Interpolations between Avatar states was a tough one, because I also implemented a timeline feature where the idea was initially that the time position decides how much color towards the other palette entry the face must be rendered with. Afterwards, I added a feature to make the Avatar have a specific state indefinitely (for the Game), so it turned out I had to refactor the whole drawing mechanisms because of it. The most complex emotion was the angry one, because it sometimes depended on a time based interpolation, and sometimes it would be used indefinitely. 

export const DrawFace = (ctx, width, height, feeling, statemap) => {

	let radius = Math.min(width, height) / 2;

	ctx.clearRect(0, 0, width, height);

	if (feeling === "angry") {

		let f1 = 1.0;

		if (typeof statemap["start"] === "number" && typeof statemap["end"] === "number") {

			let dt = Date.now() - statemap["start"];
			f1 = dt / (statemap["end"] - statemap["start"]);

		} else if (typeof statemap["start"] === "number") {

			let dt = Date.now() - statemap["start"];
			let t  = dt / 250;

			if (t > 1.0) {
				f1 = 1.0;
			} else {
				f1 = t / 2;
			}

		}

		if (f1 <= 0.5) {

			let f2    = EaseOut(f1 * 2);
			let color = InterpolateColor(Palette["okay"], Palette["angry"], f2);

			ctx.beginPath();
			ctx.arc(width / 2 | 0, height / 2 | 0, radius | 0, 0, Math.PI * 2);
			ctx.fillStyle = "rgb(" + color[0] + "," + color[1] + "," + color[2] + ")";
			ctx.fill();
			ctx.closePath();

		} else if (f1 > 0.5 && f1 < 1.0) {

			let f2    = EaseOut((f1 - 0.5) * 2);
			let color = InterpolateColor(Palette["angry"], Palette["okay"], f2);

			ctx.beginPath();
			ctx.arc(width / 2 | 0, height / 2 | 0, radius | 0, 0, Math.PI * 2);
			ctx.fillStyle = "rgb(" + color[0] + "," + color[1] + "," + color[2] + ")";
			ctx.fill();
			ctx.closePath();

		} else {

			let color = Palette["angry"];

			ctx.beginPath();
			ctx.arc(width / 2 | 0, height / 2 | 0, radius | 0, 0, Math.PI * 2);
			ctx.fillStyle = "rgb(" + color[0] + "," + color[1] + "," + color[2] + ")";
			ctx.fill();
			ctx.closePath();

		}
	} else {
		/* ... other emotions ... */
	}

};

Mouth

Drawing the mouth turned out to be quite complex. As I wanted to have support for making the Mouth appear to be speaking and being able to contort facial expressions, I overengineered it a little bit. The final simplified approach was that every mouth state has two bezier curves, one for the lower lip, and one for the upper lip.

Each state uses the same curve object with the same properties, so that they can be interpolated between states when the mouth is moving.

The downside of this simplified drawing of the mouth is that you can't really express the l | r phonemes as a facial expression, because all comic animation papers that I've seen want to make them a curved mouth, and the Canvas 2D API can't fill it correctly when there's an overlapping of the lips' curves.

It could probably be done with an expensive stencil like approach, but I gave up on it, it's good enough this way for now. Maybe I'll revisit the DrawMouthPhoneme() method at some point when I have more time to think about it. 

// In part from avatar/mouth/Expressions.mjs
export const Expressions = {

Bezier Interpolation

As the mouth is moving depending on the emotional states and/or the phonemes, the interpolation of bezier curves is important to get right. The interpolation itself was easy once I decided to use the previously mentioned curve object format everywhere, as that saved me the headache of dealing with moveTo() and lineTo() differences in the Canvas 2D API. 

// From avatar/math/InterpolateBezierCurve.mjs
export const InterpolateBezierCurve = (curve1, curve2, f) => {

	if (f >= 1.0) {
		f = 1.0;
	}

	return {
		start: {
			x: curve1.start.x + f * (curve2.start.x - curve1.start.x),
			y: curve1.start.y + f * (curve2.start.y - curve1.start.y)
		},
		end: {
			x: curve1.end.x + f * (curve2.end.x - curve1.end.x),
			y: curve1.end.y + f * (curve2.end.y - curve1.end.y)
		},
		cp1: {
			x: curve1.cp1.x + f * (curve2.cp1.x - curve1.cp1.x),
			y: curve1.cp1.y + f * (curve2.cp1.y - curve1.cp1.y)
		},
		cp2: {
			x: curve1.cp2.x + f * (curve2.cp2.x - curve1.cp2.x),
			y: curve1.cp2.y + f * (curve2.cp2.y - curve1.cp2.y)
		}
	};

};

The usage of this little helper method made it totally worth the time of putting it into a different method, because it eased up reading the code of the DrawMouthExpression() and DrawMouthPhoneme() methods quite a lot : 

// In part from avatar/draw/DrawMouthExpression.mjs
import { EaseOut                } from "../math/EaseOut.mjs";
import { InterpolateBezierCurve } from "../math/InterpolateBezierCurve.mjs";
import { Expressions            } from "../mouth/Expressions.mjs";

export const DrawMouthExpression = (ctx, feeling, statemap, debug) => {

	debug = typeof debug === "boolean" ? debug : false;

	if (feeling === "") {
		feeling = "okay";
	}

	if (feeling === "okay" || feeling === "sick") {

		let f = 0.0;

		if (typeof statemap["nausea"] === "number") {
			f = EaseOut(statemap["nausea"] / 100);
		}

		if (f > 1.0) {
			f = 1.0;
		}

		for (let c = 0; c < Expressions["okay"].length; c++) {

			let curve = InterpolateBezierCurve(Expressions["okay"][c], Expressions["sick"][c], f);

			ctx.beginPath();
			ctx.moveTo(curve.start.x, curve.start.y);
			ctx.fillStyle = "#000000";
			ctx.bezierCurveTo(
				curve.cp1.x,
				curve.cp1.y,
				curve.cp2.x,
				curve.cp2.y,
				curve.end.x,
				curve.end.y
			);
			ctx.fill();
			ctx.closePath();

		}

	} else {
		/* ... other mouth expressions */
	}

};

Phoneme Debugger

Understanding control point math is really, I mean really cumbersome. In my head, it just never makes sense and is completely unpredictable. That's why I implemented a Facial Expression debugger, where you can see the anchor points and control points of the Avatar's mouth's bezier curves.

The Avatar Phoneme Debugger shows how painful control point math is, in case you're curious about it. In order to get the curves right, I implemented some helper tools so that I can measure the differences while I was editing the underlying JSON objects in parallel.

The Phonetic Alphabet and Lip Sync with Phonemes

In order to map the mouth expressions to speech, there's the so-called phoneme guidelines. There's actually lots of papers on the topic on arxiv when it comes to character animation, and all have various opinions on the topic.

As you can see in the screenshot, the l and r phoneme limitations are visible. That was the issue I was writing about earlier when I decided to use only two connected bezier curves for rendering the mouth expressions.

If we map the IPA to ASCII characters so they're easier to parse and map from our sentences and words, we end up with Phoneme groups that look similar to this : 

const phoneme_groups = [
	[ "a", "e", "i"                ],
	[ "o"                          ],
	[ "ou", "u"                    ],
	[ "c", "d", "n", "s", "x", "z" ],
	[ "g", "k"                     ],
	[ "l", "r"                     ],
	[ "b", "m", "p"                ],
	[ "f", "v"                     ],
	[ "ea", "ee"                   ], // sometimes the same as the "g" + "k" group
	[ "th", "t", "h"               ], // sometimes the same as the "g" + "k" group)
	[ "ch", "sh", "j"              ],
	[ "q", "y", "w"                ]
];

We have to sort them so that the longest phonemes are matched against our word splitting algorithm first. This way we can successfully express words like You or Sea where we would have 3 phonemes otherwise. The word splitting algorithm gets quite hacky because usually that's done with CMU dictionaries but I didn't want to overcomplicate this.

As an example, the c phoneme maps in general to the same phoneme mouth expression as d , n , s , x , and z . But that's actually incorrect, because this only applies when the ci- or ce- syllables are spoken. If ca- , co- , or cu- are spoken, it should've been a phoneme in the group of g or k .

And that's exactly what the CMU dictionary does, for a lot of words . For example, the word cookie will actually be mapped to kookie , and You will be mapped to yu instead. It is kind of mindblowing how many exceptions there are in the English language, and depending on the dialect there will be different results. That's why there's many differences, and the opinion on how to speak the word associate is embedded into the dictionary, depending on who wrote it and where they came from.

Speeches

In order to map the speeches that are played via the AudioContext API back to the positions in time when the mouth has to have what kind of phoneme expression, I created a little JSON format that allows lose transcriptions and is much easier to use than the TextGrid alternative.

The little challenge in there was the creation of pause markers so that breaks between words can also be embedded into the format. I used a . character for that, and allowed to use the . , ? , and ! characters to end the sentences.

The audio streams themselves had to be realigned a lot, and I decided to give the Browser 100ms of time to load and play the audio file, that's why every first word starts at 100ms in those audio streams. 

// From avatar/speeches/angry3.json
{
	// sentence transcription
	"sentence": [
		"you", "dare", "challenge", "my", "power", "?"
	],
	// word start positions in ms
	"timeline": [
		100, 500, 890, 1575, 1875, 2600
	],
	// audio duration in ms
	"length": 3036
}

Mapping Phonemes to a Timeline

Right now all phonemes are mapped linearly to their word length, meaning if a word splits up in 4 phonemes, each phoneme will be mapped to 1/4th of the time span of that word. Sometimes this isn't correct, especially when the pronounciation of the words come with more energy and the vibratio for each of the syllables. 

// In part from common/speech/ParseSpeech.mjs
import { phonemes as sorted_phonemes } from "./phonemes.mjs";

const parse_word_into_phonemes = (word, start_time, end_time) => {

	let phonemes = [];
	let timeline = [];

	while (word.length > 0) {

		let found = sorted_phonemes.find((str) => word.startsWith(str)) || null;
		if (found !== null) {
			phonemes.push(found);
			word = word.substr(found.length);
		}

	}

	let time_per_phoneme = (end_time - start_time) / phonemes.length;

	for (let t = 0; t < phonemes.length; t++) {
		timeline.push((start_time + time_per_phoneme * t) | 0);
	}

	return { phonemes, timeline };

};

Speech Debugger

The Avatar Speech Debugger shows how painful the phoneme alignment process actually is. I implemented some helper tools so that I can re-hear an audio time frame over and over again, while deciding exactly when to place the markers for the words.

That debugger saved me a lot of time, because Audio Editors like Audacity are just way too slow for that kind of precision. Turns out, the AudioContext API is really made for real-time applications, and even more precise than classical audio editors on Linux.

I have a prototype in place that tries to detect this, but it's still a lot of remaining work. Turns out, I'm not really good at understanding Fourier Transforms well enough and I need to brush up my knowledge in that quite a bit.

Probably when I have some time left over the coming holidays I'm going to work more on that, because I kind of want to prove the authors of the Phoneme papers and forced alignment generators wrong, and I want to prove that it's possible to detect phoneme boundaries live, in real-time and not only in a pre-generated manner.
