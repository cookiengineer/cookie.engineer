Tholian Firewall

Programmable Defensive Firewall Agent for Go Backends

Overview

GitHub Repository | GitLab Mirror

Most firewalls are asked politely to drop a packet after the kernel has already carried it up the networking stack, matched it against a rule set, and handed it to a userspace process to decide.

The Tholian Firewall declines the meeting. It compiles a small eBPF program and attaches it to the XDP hook, so matching ingress traffic is dropped by the driver before the stack ever allocates a socket for it.

It is built for blue teams and Go backend developers who want a firewall they can call from their own process. A backend can use actions.Forbid, actions.Permit, and actions.Check on addresses, subnets, ports, ASN networks, exact sockets, and domains. Operators get the same engine as a standalone CLI for scripting and fallback backends.

When eBPF is unavailable, the firewall degrades to iptables/ip6tables and a managed /etc/hosts block instead of pretending it can filter. Every mutating action reports whether the ban was actually applied, so an agent can distinguish "forbidden" from "the backend disappeared".

Firewall is the enforcement half of the Tholian Network. Tholian Scout inventories a host, Tholian Core supplies the shared vocabulary, and the Tholian Firewall decides what may reach it. The same targets and matchers work in a shell, in a Go service, and in a remote agent call.

Features

  • Drops ingress traffic in-kernel via XDP before the networking stack runs.
  • Embeds as a Go library with no CGo dependency.
  • Ships as a Go library and a CLI with the same action surface.
  • Blocks addresses, CIDR subnets, ASN networks, ports, exact sockets, and domains.
  • Keeps IP:port bans exact, so a banned socket does not silently ban the whole address.
  • Drops DNS responses for banned domains and installs the resolved A and AAAA addresses as ordinary bans.
  • Recognizes Nmap-style probes and converts repeated warnings into an address ban.
  • Applies line-separated rule files with forbid and permit statements.
  • Falls back to iptables/ip6tables and a delimited /etc/hosts block when eBPF is unavailable.
  • Cross-compiles with CGO_ENABLED=0 for Linux, FreeBSD, NetBSD, and OpenBSD on amd64 and arm64.
  • Exposes the same actions as tholian-firewall.* methods through the Tholian Core network protocol.
  • Reports the active backend and the current bans instead of claiming success unconditionally.

Architecture

CLI or Go caller
       |
       v
actions.Forbid / Permit / Check / Search / Status
       |
       +--> internal/types.ParseTarget -> matchers / structs (tholian-core)
       |
       +--> internal/adapters/mitigations/ebpf
       |          |
       |          +--> BPF maps (addresses, ports, sockets, DNS hashes)
       |          +--> embedded XDP bytecode
       |                   |
       |                   v
       |             xdp_prog_main (kernel)
       |
       +--> iptables / ip6tables fallback
       +--> managed /etc/hosts block for domains

A single XDP program, xdp_prog_main, parses Ethernet plus up to four VLAN tags, IPv4 or IPv6 including extension headers, TCP, UDP, ICMP, and UDP DNS when ENABLE_DNSFILTER is defined. It returns XDP_DROP on a confident match and XDP_PASS otherwise. Anything it cannot parse is passed, so the filter fails open rather than breaking the interface.

Packet Path

Address and socket checks happen after the transport header is parsed. A source or destination address that matches a banned prefix is dropped. A source or destination socket that matches an exact IP:port tuple is dropped, but the rest of that address remains reachable. Port bans match both source and destination ports, which is useful for stopping inbound services and outbound callbacks with the same rule.

ICMP keeps echo requests and replies, destination-unreachable, redirect, time-exceeded, and parameter-problem messages. IPv6 additionally keeps neighbor discovery and router advertisement types. Dropping neighbor discovery breaks IPv6 connectivity, so the program never does it.

BPF Maps

Map Type Key Purpose
domain_bans HASH 8-byte FNV-1a hash Banned DNS names
ipv4_bans LPM_TRIE prefix + 4 address bytes Banned IPv4 addresses and subnets
ipv4_warnings LRU_HASH prefix + 4 address bytes Probe warning counters
ipv6_bans LPM_TRIE prefix + 16 address bytes Banned IPv6 addresses and subnets
ipv6_warnings LRU_HASH prefix + 16 address bytes Probe warning counters
port_bans HASH network-order port Banned TCP and UDP ports
ipv4_sockets HASH 4 address bytes + port Exact IPv4 socket bans
ipv6_sockets HASH 16 address bytes + port Exact IPv6 socket bans

The BTF map definitions in module.c are the schema. The Go bridge has to produce keys of exactly the matching size and byte order. Address prefixes are stored in host byte order, address bytes in network byte order, and ports in network byte order.

Ban Semantics

An address ban matches packets whose source or destination address falls inside the banned prefix. The trie is a longest-prefix-match map, so a /24 ban covers a /32 lookup without a separate rule. A port ban matches both source and destination roles. A socket ban matches an exact source or destination tuple and does not ban the whole address.

permit deletes the matching key. There is no allowlist, no default-deny mode, and no precedence puzzle in the hot path. The tradeoff is that permit cannot carve a hole inside a broader ban; the broader prefix still matches.

When a domain is forbidden, the adapter writes the domain hash so the kernel drops its DNS responses, resolves the domain in user space, and installs the returned A and AAAA addresses in the address maps. permit removes exactly the addresses that were installed, even if DNS has changed in the meantime. This is why a client that already knows the IP still cannot connect after the domain is banned.

DNS Handling

The kernel-side DNS filter is intentionally small. It only inspects UDP responses on ports 53 and 5353, hashes the lowercased question name in wire form, and drops the packet when the hash is banned. Compression pointers are never followed; a pointer terminates parsing, which keeps the packet pointer bounded and the verifier happy.

The filter is drop-only for the domain itself. The resolved-address installation happens in Go, where parsing variable-length DNS answers is cheap and testable. Encrypted DNS over TLS and DNS over HTTPS cannot be inspected for domain names, and DNS over TCP is passed through. Those are real limitations, not hidden features.

Scan Heuristics

The program also recognizes a few Nmap-shaped probes. A FIN-only packet and an RST+ACK packet with a zero window are dropped outright. A SYN packet with the characteristic Nmap window size increments a per-source warning counter, and once that counter passes 16, the source is moved into the ban map. This is a small, fixed heuristic rather than a full intrusion detection engine.

Verifier Constraints

The kernel program is kept small and flat on purpose. The eBPF verifier rejects parser shapes that look reasonable in C but cannot be proven safe after optimization:

  • No DNS compression-pointer following, because the resulting packet offset is not bounded.
  • No nested loops over packet data, because verifier states multiply quickly.
  • Every variable offset is capped, and bounds checks use a constant size immediately before the dereference.
  • Anything with variable structure is parsed in user space instead.
  • Parse failures pass traffic. The filter drops only when it is confident.

The full verifier log is dumped when loading fails. The bridge sets SUPPORTED only after the program and maps load successfully, so the rest of the process never assumes a backend it does not have.

Fallbacks

Backend selection lives in actions/backend.go. Addresses, subnets, ports, and connections prefer eBPF and fall back to iptables/ip6tables. Domains prefer eBPF and fall back to the managed /etc/hosts block.

The iptables adapter detects IPv4 and IPv6 separately, appends idempotent rules to INPUT and OUTPUT, and tracks what it installed for status and cleanup. The hosts adapter rewrites only the block between # BEGIN THOLIAN FIREWALL and # END THOLIAN FIREWALL, writes both 0.0.0.0 and the IPv6 unspecified address, and matches domain names case-insensitively. Both fallbacks are coarser than the in-kernel path and are honest about it.

Building

The module expects tholian-core to be checked out next to firewall. The source/go.mod file uses a relative replacement, and the build expects the shared type system at ../core/source.

cd /path/to/tholian-network;

# expected layout
# core/ firewall/
ls;

cd ./firewall;

Building requires go, clang, llc, and libbpf headers. The embedded source/insights/Internet.json.gz dataset is required for every build target. It is intentionally not tracked by Git and must be provided by an external build toolchain.

# compile the eBPF module, emit LLVM IR, and generate both endiannesses
make build-ebpf;

# cross-compile the CLI variants (also rebuilds the eBPF module)
make build-cli;

ls ./build/linux/*;
# tholian-firewall-linux-amd64
# tholian-firewall-linux-arm64

ls ./build/freebsd/*;
# tholian-firewall-freebsd-amd64
# tholian-firewall-freebsd-arm64

The default matrix covers linux, freebsd, netbsd, and openbsd for amd64 and arm64. Override it with TARGET_OSES and TARGET_ARCHES, for example make build-cli TARGET_OSES=linux TARGET_ARCHES=amd64. Run make help for the complete target list.

The generated module.ll, module.bpfel, and module.bpfeb artifacts are committed, so rebuild and commit them whenever module.c or module.h changes.

Testing

cd /path/to/tholian-network/firewall;

# formatting, vet, and race-enabled unit tests
make check;

# unit tests, eBPF build, and the in-process integration suite
make test;

# external CLI end-to-end suite
make test-e2e;

# both suites, reporting the combined result
make test-all;

The privileged integration suite needs root or CAP_BPF plus CAP_NET_ADMIN. Tests skip themselves when they are not run as root, so a plain go test ./... is safe on a developer machine.

make test compiles the integration tests into one binary with go test -c and runs it under sudo. That is not a style choice: unpinned maps and XDP links are process-scoped, so separate CLI invocations cannot observe each other's state. make test-with-log writes logs/test.log, and make test-e2e-with-log writes logs/test_e2e.log.

Test What it checks
TestModuleLoad Program and maps load; the verifier accepts the program
TestDomainKey Domain keys normalize case and trailing dots
TestAddressRoundTrip Forbid, lookup, and permit for IPv4
TestIPv6AddressRoundTrip Forbid, lookup, and permit for IPv6
TestSubnetRoundTrip Longest-prefix matching for a /24 covering a /32
TestPortRoundTrip Forbid, lookup, and permit for ports
TestDomainRoundTrip FNV-1a domain key with case-insensitive matching
TestDNSDrop A crafted DNS response for a banned domain returns XDP_DROP
TestDomainResolutionInstall Resolved A and AAAA addresses are installed and removed by permit
TestAttachAll Attaches to every non-loopback interface (opt-in)

Unit tests cover target parsing, rule-file loading, the map key encoders including socket keys, and the iptables and hosts adapters. The privileged suite covers the kernel map and packet paths.

TestAttachAll is gated behind THOLIAN_TEST_ATTACH=1 because attaching to host interfaces is intrusive. make test enables it by default. Set THOLIAN_TEST_ATTACH=0 to skip it. When running the compiled test binary directly, use -test.run; the go test driver translates -run.

Usage: CLI

These examples show the target syntax. Because the eBPF maps and links are process-scoped, a standalone forbid only affects the process that created it. The iptables and hosts fallbacks write system state and are the practical CLI path.

# block a whole ASN
sudo tholian-firewall forbid "AS1337";

# block an address, a subnet, and an exact socket
sudo tholian-firewall forbid "1.3.3.7";
sudo tholian-firewall forbid "1.3.3.0/24";
sudo tholian-firewall forbid "1.3.3.7:1338";

# block an IPv6 target (RFC 2732 syntax)
sudo tholian-firewall forbid "[fe80::1337]/64";
sudo tholian-firewall forbid "[fe80::1337]:1338";

# block a domain: drop its DNS responses and ban the resolved addresses
sudo tholian-firewall forbid "evil.example";

# check the state (exit 0 = allowed, 1 = forbidden, 3 = no backend)
sudo tholian-firewall check "1.3.3.7";

# look up the network and ASN details for an address
sudo tholian-firewall search "1.1.1.1";

# attach to all interfaces, inspect bans, and run a map round-trip
sudo tholian-firewall init;
sudo tholian-firewall status;
sudo tholian-firewall selftest;

For continuous filtering, embed the library in a long-running service; a daemon mode with pinned maps is planned but not implemented. selftest runs an in-process map and attach round-trip and is the quickest way to verify that the kernel backend works on a host.

Usage: Rule Files

Bulk rules use the same target syntax. Lines may contain comments after #, and multiple statements may be separated with semicolons.

# rules.txt
forbid 1.3.3.7;
forbid 1.3.3.0/24;
forbid 1.3.3.7:1338;
forbid evil.example;
permit 8.8.8.8;
						
sudo tholian-firewall load rules.txt;

Usage: Embedding

The library is the deployment path for eBPF. Create a console, load the internet dataset, attach the backend once, and then call the actions from the process that should keep filtering.

package main

import "os"
import "tholian-core/structs"
import "tholian-firewall/actions"
import "tholian-firewall/insights"

func main() {

	console := structs.NewConsole(os.Stdout, os.Stderr, 0)

	insights.Init(console)

	if actions.Init(console) == false {
		console.Error("no firewall backend available")
		os.Exit(1)
	}

	if actions.Forbid(console, "1.3.3.7") == false {
		console.Error("could not apply address ban")
		os.Exit(1)
	}

	if actions.Forbid(console, "evil.example") == false {
		console.Error("could not apply domain ban")
		os.Exit(1)
	}

	if actions.Check(console, "1.3.3.7") == true {
		console.Log("traffic from or to 1.3.3.7 is dropped")
	}

	actions.Permit(console, "1.3.3.7")

}

The console is passed to every call so its message log stays complete and can be serialized later. actions.Init attaches to every non-loopback interface and returns true when at least one backend is usable. If the process exits, the unpinned eBPF maps and links go with it.

Usage: Tholian Network Protocol

The action surface is also available through Tholian Core's network protocol. A controller can call tholian-firewall.Init, Check, Search, Status, Load, Forbid, Permit, and the batch and network-specific variants without spawning a shell.

Remote access is split into capabilities:

  • tholian-firewall.read for checks and status
  • tholian-firewall.write for forbid and permit actions
  • tholian-firewall.install for setup and self-test actions

See Tholian Core for the packet format and details about the network protocol and schemas.
