Dynamic Linking

How ld.so resolves shared library symbols - GOT, PLT, lazy binding, LD_PRELOAD, symbol visibility, and the complete dynamic linking lifecycle on Linux.

Overview

A dynamically linked program does not contain its libraries. The kernel maps its interpreter, ld.so , which loads the shared objects, applies relocations, and only then jumps to the program. That indirection is what makes LD_PRELOAD injection, GOT overwrites, and PLT hijacks possible, and it is why a missing or mismatched library stops a binary before main runs. This article traces the full lifecycle from PT_INTERP to the first lazy symbol resolution, and shows how to inspect, inject, and audit a process. After reading it you can read a .dynamic section, explain lazy versus immediate binding, and hook libc calls at runtime.

Required Reading

  • ELF (Executable and Linkable Format) - ELF file structure, program headers, sections, and how the kernel loads ELF files
  • Virtual Memory - virtual memory, mmap, and how shared libraries are mapped into process address space

Static vs Dynamic Linking

Static linking copies all library code into the executable. Every statically linked binary carries its own copy of printf , malloc , and every other function it uses. The result: large binaries, no shared memory between processes, but zero runtime dependencies.

Dynamic linking defers symbol resolution to load time (or run time). One copy of libc.so.6 in physical RAM serves every process that needs it, mapped read-only into each process's address space. The trade-off: complexity, a larger attack surface ( LD_PRELOAD , LD_LIBRARY_PATH ), and the possibility of library version mismatches (" DLL Hell" on Windows, "soname" discipline on Linux).

Static example:

$ gcc -static -o hello_static hello.c
$ ls -lh hello_static
-rwxr-xr-x 1 user user 893K Jun 26 12:00 hello_static
$ ldd hello_static
        not a dynamic executable

Dynamic example:

$ gcc -o hello_dyn hello.c
$ ls -lh hello_dyn
-rwxr-xr-x 1 user user 16K Jun 26 12:01 hello_dyn
$ ldd hello_dyn
        linux-vdso.so.1 (0x00007ffd0b5e0000)
        libc.so.6 => /usr/lib/libc.so.6 (0x00007f1a8bc00000)
        /lib64/ld-linux-x86-64.so.2 (0x00007f1a8c200000)

The dynamic binary is 56x smaller. Every function in libc is shared across all processes on the system.

The Dynamic Linker - ld.so

Every dynamically linked ELF specifies its interpreter via PT_INTERP : 

$ readelf -l hello_dyn | grep INTERP -A1
  INTERP         0x0000000000000318 0x0000000000000318 0x0000000000000318
                 0x000000000000001c 0x000000000000001c  R      0x1

$ readelf -p .interp hello_dyn
String dump of section '.interp':
  [     0]  /lib64/ld-linux-x86-64.so.2

The kernel reads .interp , maps ld.so into the process, and transfers control to it instead of the program's entry point. ld.so then initializes the process:

  1. Parses .dynamic section
  2. Loads all DT_NEEDED libraries (recursively)
  3. Performs all relocations
  4. Calls .init / .init_array constructors
  5. Jumps to the program's entry point ( _start -> __libc_start_main -> main )

The .dynamic Section

.dynamic is an array of tagged entries, each a key-value pair: 

typedef struct {
    Elf64_Sxword d_tag;   // Tag (what type of entry)
    union {
        Elf64_Xword d_val;   // Integer value
        Elf64_Addr  d_ptr;   // Virtual address pointer
    } d_un;
} Elf64_Dyn;

PLT and GOT - The Lazy Binding Mechanism

The PLT (Procedure Linkage Table) and GOT (Global Offset Table) implement lazy binding - functions are resolved on first call, not at load time. This is the default behavior. Setting LD_BIND_NOW=1 or linking with -z now forces all resolution at load time (Full RELRO).

The data structures

  • .plt - code stubs, one per imported function. First call triggers the resolver; subsequent calls jump directly to the function.
  • .got - pointer table for global data symbols.
  • .got.plt - pointer table for PLT function entries. GOT

Step-by-step, first call to 'printf'

Initial state (before any printf call):
    GOT[printf_slot] == addr of PUSH instruction in PLT (points back to PLT stub)

Step 1: Code calls printf -> jmp to PLT[printf]
Step 2: PLT[printf] does:
    jmp *GOT[printf_slot]           ; INDIRECT JUMP through GOT
    push $printf_index              ; Push index into JMPREL table
    jmp PLT[0]                      ; Jump to resolver stub
Step 3: PLT[0] does:
    push GOT[1]                     ; Push link_map pointer
    jmp *GOT[2]                     ; Jump to _dl_runtime_resolve
Step 4: _dl_runtime_resolve(link_map, printf_index):
    - Looks up printf_index in JMPREL table
    - Gets symbol name from .dynstr
    - Walks link_map -> all loaded libraries
    - Finds printf in libc.so.6
    - Returns printf's actual address
Step 5: Resolver writes printf's address into GOT[printf_slot]
Step 6: Resolver jumps to printf

Subsequent calls:
    jmp *GOT[printf_slot]           ; DIRECT JUMP to printf - no overhead

Linking a Program Step-by-Step

Create a shared library:

// libcalc.c - A toy shared library
#include <stdio.h>

int add(int a, int b) {
    return a + b;
}

int multiply(int a, int b) {
    return a * b;
}

void libcalc_init(void) __attribute__((constructor));
void libcalc_init(void) {
    printf("[libcalc] Initialized\n");
}

void libcalc_fini(void) __attribute__((destructor));
void libcalc_fini(void) {
    printf("[libcalc] Finalized\n");
}
						
$ gcc -shared -fPIC -o libcalc.so libcalc.c
$ file libcalc.so
libcalc.so: ELF 64-bit LSB shared object, x86-64, version 1 (SYSV),
dynamically linked, BuildID[sha1]=..., not stripped

-fPIC generates position-independent code ( IP -relative addressing instead of absolute). -shared produces a shared library (ET_DYN) instead of an executable.

Examine the shared library:

$ readelf -d libcalc.so
Dynamic section at offset ...:
  NEEDED    libc.so.6
  SONAME    libcalc.so

$ nm -D libcalc.so
00000000000010f9 T add
0000000000001120 T libcalc_fini
000000000000110e T libcalc_init
0000000000001107 T multiply

The T indicates text-section symbols (functions). nm -D shows dynamic (exported) symbols.

Create a consumer:

// main.c
#include <stdio.h>

extern int add(int, int);
extern int multiply(int, int);

int main(void) {
    printf("add(3, 4) = %d\n", add(3, 4));
    printf("multiply(3, 4) = %d\n", multiply(3, 4));
    return 0;
}

Compile and link:

$ gcc -o calc main.c -L. -lcalc
$ ./calc
./calc: error while loading shared libraries: libcalc.so:
cannot open shared object file: No such file or directory

The error is expected - the dynamic linker doesn't search the current directory by default. Fix with LD_LIBRARY_PATH or compile with rpath: 

# Option 1: LD_LIBRARY_PATH
$ LD_LIBRARY_PATH=. ./calc
[libcalc] Initialized
add(3, 4) = 7
multiply(3, 4) = 12
[libcalc] Finalized

# Option 2: rpath baked into the binary
$ gcc -o calc main.c -L. -lcalc -Wl,-rpath,.
$ ./calc
[libcalc] Initialized
add(3, 4) = 7
multiply(3, 4) = 12
[libcalc] Finalized

Note the constructor/destructor order: libcalc_init runs before main() , libcalc_fini runs after main() returns.

Library Search Order

When resolving DT_NEEDED entries, the dynamic linker ( ld.so ) searches in this order:

  1. DT_RPATH - rpath embedded in the executable's .dynamic section (unless DT_RUNPATH is also present)
  2. LD_LIBRARY_PATH - environment variable (ignored for setuid/setgid binaries)
  3. DT_RUNPATH - runpath embedded in the executable (searched after LD_LIBRARY_PATH , unlike rpath)
  4. /etc/ld.so.cache - binary cache built by ldconfig
  5. /lib , /usr/lib - default system paths (and /lib64, /usr/lib64 on multilib)

The difference between rpath and runpath:

Property DT_RPATH (deprecated) DT_RUNPATH
Searched before LD_LIBRARY_PATH Yes No
Can be overridden at runtime No (LD_LIBRARY_PATH searched later) Yes (LD_LIBRARY_PATH wins)
Set via -Wl,-rpath, -Wl,-rpath,with--enable-new-dtags

Modern linkers default to DT_RUNPATH ( --enable-new-dtags ). Use readelf -d to check which one is present.

LD_PRELOAD - Library Injection

LD_PRELOAD forces the dynamic linker to load specified shared libraries before any others. This overrides functions in any subsequently loaded library, including libc: 

// preload_malloc.c - Intercept malloc and log every allocation
#define _GNU_SOURCE
#include <stdio.h>
#include <dlfcn.h>
#include <stdlib.h>

void *malloc(size_t size) {
    static void *(*real_malloc)(size_t) = NULL;
    if (!real_malloc) {
        real_malloc = dlsym(RTLD_NEXT, "malloc");
    }

    void *ptr = real_malloc(size);
    fprintf(stderr, "[HOOK] malloc(%zu) = %p\n", size, ptr);
    return ptr;
}

Compile and use:

$ gcc -shared -fPIC -o preload_malloc.so preload_malloc.c -ldl
$ LD_PRELOAD=./preload_malloc.so ls -l /dev/null
[HOOK] malloc(1024) = 0x55a1b2c002a0
[HOOK] malloc(384) = 0x55a1b2c006c0
[HOOK] malloc(24) = 0x55a1b2c00850
[HOOK] malloc(120) = 0x55a1b2c00880
[HOOK] malloc(120) = 0x55a1b2c00900
...

RTLD_NEXT tells dlsym to find the next occurrence of malloc in the symbol search order, skipping the current library. Without a handle, dlsym walks the global symbol namespace.

LD_PRELOAD is ignored for setuid/setgid binaries (the kernel sets AT_SECURE=1 in the auxiliary vector, and ld.so clears environment variables that affect library loading).

Symbol Visibility and Binding

GCC's default visibility is default - all symbols are exported from shared libraries. This bloats the dynamic symbol table and increases the attack surface. -fvisibility=hidden makes symbols LOCAL by default: 

// libsecret.c
#include <stdio.h>

// Exported - visible to consumers
__attribute__((visibility("default")))
void public_api(void) {
    internal_helper();  // can call hidden functions internally
}

// Hidden - only callable within this library
__attribute__((visibility("hidden")))
void internal_helper(void) {
    printf("This is hidden from consumers\n");
}

// Protected - always resolved within this library (even if LD_PRELOAD'd)
__attribute__((visibility("protected")))
int critical_value(void) {
    return 42;
}
						
$ gcc -shared -fPIC -fvisibility=hidden -o libsecret.so libsecret.c
$ nm -D libsecret.so
0000000000001142 T public_api
0000000000001151 T critical_value

internal_helper is absent from nm -D - it exists in .symtab (static linking) but not in .dynsym (dynamic linking). This also prevents overrides via LD_PRELOAD .

Visibility effects on performance

Hidden/protected symbols allow the compiler to use direct calls instead of PLT indirection. Within a shared library, calls to hidden functions use call $direct_offset instead of call *GOT[n](%rip) . This eliminates a memory indirection and a GOT entry.

Relocation Types

x86-64 uses Elf64_Rela : 

typedef struct {
    Elf64_Addr r_offset;   // Address to patch
    uint64_t   r_info;     // high 32 = symbol index, low 32 = type
    int64_t    r_addend;   // Addend
} Elf64_Rela;

Common relocation types encountered by the dynamic linker:

Type Value Formula Use
R_X86_64_GLOB_DAT 6 S Global data pointer in GOT
R_X86_64_JUMP_SLOT 7 S PLT function pointer in GOT (lazy)
R_X86_64_RELATIVE 8 B + A Base-relative (for PIE internals)
R_X86_64_COPY 5 Copy data from shared lib to BSS Avoids GOT indirection for data
R_X86_64_IRELATIVE 37 indirect(B + A) STT_GNU_IFUNC resolution

R_X86_64_COPY is interesting: when an executable references a global variable in a shared library, the linker can't use a GOT indirection on the executable side (the code is already compiled). Instead, it creates a .bss copy, and the dynamic linker copies the data at load time. The executable and the shared library now have independent copies.

R_X86_64_IRELATIVE resolves STT_GNU_IFUNC symbols - functions whose implementation is selected at load time based on CPU features (e.g., memcpy choosing between SSE, AVX, AVX-512): 

// ifunc example - select optimal function at load time
void *resolve_memcpy(void) {
    if (__builtin_cpu_supports("avx512f")) return avx512_memcpy;
    if (__builtin_cpu_supports("avx2"))    return avx2_memcpy;
    return generic_memcpy;
}
void *memcpy(void *, const void *, size_t) __attribute__((ifunc("resolve_memcpy")));

Immediate Binding - Full RELRO

Linking with -z relro -z now marks the GOT as read-only after relocation (Full RELRO). This prevents attackers from overwriting GOT entries (a common technique in format string and heap exploit chains): 

$ gcc -o calc main.c -L. -lcalc -Wl,-rpath,. -Wl,-z,relro,-z,now
$ readelf -l calc | grep RELRO -A1
  GNU_RELRO      0x0000000000003db0 0x0000000000003db0 0x0000000000003db0
                 0x0000000000000250 0x0000000000000250  R      0x1
$ readelf -d calc | grep FLAGS
 0x000000000000001e (FLAGS)              BIND_NOW

Compare Partial RELRO (default -z relro , no -z now ) vs Full RELRO ( -z relro -z now ):

Property Partial RELRO Full RELRO
.init_array, .fini_array Read-only after init Read-only after init
.dynamic section Writable (partial protection) Read-only after init
.got section Writable Read-only after init
.got.plt section Writable (lazy binding needs it) Read-only after init
Lazy binding Supported (PLT lazy resolution) Disabled (all resolved at load)
Startup time Faster Slower (resolve all symbols upfront)
GOT overwrite resistance Partial Full

The DL API - Runtime Symbol Lookup

P OSI X defines a runtime symbol resolution API via <dlfcn.h> : 

// dlopen_demo.c - Load a library at runtime and call a function
#include <stdio.h>
#include <dlfcn.h>

int main(void) {
    void *handle = dlopen("./libcalc.so", RTLD_NOW);
    if (!handle) {
        fprintf(stderr, "dlopen: %s\n", dlerror());
        return 1;
    }

    // Clear any previous errors
    dlerror();

    // Find the add function
    int (*add_fn)(int, int) = dlsym(handle, "add");
    char *err = dlerror();
    if (err) {
        fprintf(stderr, "dlsym: %s\n", err);
        dlclose(handle);
        return 1;
    }

    printf("3 + 4 = %d\n", add_fn(3, 4));
    dlclose(handle);
    return 0;
}
						
$ gcc -o dlopen_demo dlopen_demo.c -ldl
$ ./dlopen_demo
3 + 4 = 7

dlopen flags:

Flag Meaning
RTLD_LAZY Lazy binding (defer symbol resolution until first call)
RTLD_NOW Immediate binding (resolve all symbols before dlopen returns)
RTLD_GLOBAL Make symbols available for subsequently loaded libraries
RTLD_LOCAL Symbols are not visible to other libraries (default)
RTLD_NODELETE Do not unload library on dlclose
RTLD_NOLOAD Do not load the library, just validate it

The Audit Interface - LD_AUDIT

LD_AUDIT specifies a shared library that implements the rtld-audit interface - callbacks invoked by ld.so at key linkage events: 

// audit.c - Minimal LD_AUDIT shared library
#define _GNU_SOURCE
#include <link.h>
#include <stdio.h>

unsigned int la_version(unsigned int version) {
    printf("[audit] la_version(%u)\n", version);
    return version;  // Return the version we support
}

unsigned int la_objopen(struct link_map *map, Lmid_t lmid, uintptr_t *cookie) {
    printf("[audit] la_objopen: %s\n", map->l_name ? map->l_name : "(main)");
    return 0;
}

void la_activity(uintptr_t *cookie, unsigned int flag) {
    printf("[audit] la_activity: cookie=%p flag=%u\n", cookie, flag);
}

// Called for every PLT binding (lazy symbol resolution)
uintptr_t la_symbind64(Elf64_Sym *sym, unsigned int ndx,
                       uintptr_t *refcook, uintptr_t *defcook,
                       unsigned int *flags, const char *symname) {
    printf("[audit] la_symbind64: %s\n", symname);
    return sym->st_value;  // Return the actual function address
}
						
$ gcc -shared -fPIC -o audit.so audit.c
$ LD_AUDIT=./audit.so /bin/ls -l /dev/null 2>&1 | head -20

patchelf - Editing ELF Properties

patchelf modifies the .dynamic section and program headers of an existing ELF: 

# Set a new rpath
$ patchelf --set-rpath /opt/mylibs ./calc

# Set a new interpreter (dynamic linker)
$ patchelf --set-interpreter /opt/my-ld.so ./calc

# Add a DT_NEEDED entry (force-load a library)
$ patchelf --add-needed libinjected.so ./calc

# Print current settings
$ patchelf --print-rpath ./calc
/opt/mylibs

$ patchelf --print-interpreter ./calc
/lib64/ld-linux-x86-64.so.2

vDSO - Virtual Dynamic Shared Object

Every Linux process has linux-vdso.so.1 mapped into its address space. It's not a file - it's a small ELF image embedded in the kernel and mapped read-only + executable into every process at execve time. It provides fast implementations of frequently called syscalls (gettimeofday, clock_gettime, getcpu) that don't require a context switch: 

$ ldd /bin/ls | head -1
        linux-vdso.so.1 (0x00007ffff7fc1000)
$ cat /proc/self/maps | grep vdso
7ffff7fc1000-7ffff7fc3000 r--p 00000000 00:00 0  [vvar]
7ffff7fc3000-7ffff7fc5000 r-xp 00000000 00:00 0  [vdso]

The kernel coughs up the vDSO image in the auxiliary vector ( AT_SYSINFO_EHDR ), and the dynamic linker treats it like any other shared library.

Summary - Dynamic Linking Lifecycle

execve("./calc")
  │
  ▼
Kernel: loads ELF header, reads PT_INTERP -> /lib64/ld-linux-x86-64.so.2
  │
  ▼
Kernel: mmaps ld.so, transfers control to ld.so's entry point
  │
  ▼
ld.so: initializes itself (bootstrap relocation)
  │
  ▼
ld.so: reads .dynamic of ./calc
  │  -> DT_NEEDED: libcalc.so, libc.so.6
  │
  ▼
ld.so: loads libcalc.so (mmaps, reads its .dynamic)
  │  -> DT_NEEDED: libc.so.6 (already queued)
  │
  ▼
ld.so: loads libc.so.6 (mmaps, reads its .dynamic)
  │
  ▼
ld.so: breadth-first relocation pass
  │  -> Processes RELA relocations for all loaded libraries
  │  -> R_X86_64_RELATIVE, R_X86_64_GLOB_DAT
  │  -> R_X86_64_JUMP_SLOT (if -z now) or lazy (if default)
  │
  ▼
ld.so: calls DT_INIT functions for each loaded library (bottom-up)
  │  -> libc init, libcalc constructor, etc.
  ▼
ld.so: calls DT_INIT_ARRAY functions
  │
  ▼
ld.so: jumps to ./calc's entry point (_start -> __libc_start_main -> main)
  │
  ▼
main() runs
  │  -> First call to printf: lazy binding via PLT -> _dl_runtime_resolve -> GOT updated
  │  -> Subsequent printf calls: direct jump through GOT
  │
  ▼
main() returns
  │
  ▼
__libc_start_main calls exit() or return from main via atexit handlers
  │
  ▼
ld.so: calls DT_FINI_ARRAY functions, then DT_FINI (reverse order)
  │
  ▼
exit_group() syscall -> process terminates

This sequence runs millions of times a day on every Linux system. Every shell command, every daemon startup, every fork() + execve() triggers this exact chain. Understanding it is foundational to everything that follows - buffer overflows, format strings, PLT/GOT overwrites, and ROP chains all rely on manipulating one or more stages of this process.

Challenge

Reimplement a small readelf -d in Go with the debug/elf package. Print every DT_NEEDED library, then check DT_FLAGS / DT_FLAGS_1 and report whether the binary uses immediate binding (Full RELRO). Extend it to parse the .rela.plt section by hand and print each imported symbol. 

package main

import (
	"debug/elf"
	"fmt"
	"os"
)

func main() {
	f, err := elf.Open(os.Args[1])
	if err != nil {
		panic(err)
	}
	defer f.Close()

	libs, err := f.ImportedLibraries()
	if err != nil {
		panic(err)
	}
	for _, lib := range libs {
		fmt.Println("NEEDED", lib)
	}

	fullRelro := false
	if vals, err := f.DynValue(elf.DT_FLAGS_1); err == nil {
		for _, v := range vals {
			if elf.DynFlag1(v)&elf.DF_1_NOW != 0 {
				fullRelro = true
			}
		}
	}
	if vals, err := f.DynValue(elf.DT_FLAGS); err == nil {
		for _, v := range vals {
			if elf.DynFlag(v)&elf.DF_BIND_NOW != 0 {
				fullRelro = true
			}
		}
	}
	fmt.Println("Full RELRO:", fullRelro)
}
