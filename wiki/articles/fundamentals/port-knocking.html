Port Knocking

Port knocking and Single Packet Authorization hide a service until a client proves knowledge of a secret sequence or key.

Overview

A service that listens on a port is visible to every scanner that reaches it. Port knocking changes that: the real service port stays closed until the client sends a specific sequence of connection attempts (or a single authenticated packet) that only the administrator knows. This article builds the technique from first principles, shows how to configure knockd and fwknop , implements a daemon-less version with the iptables recent module, and explains where port knocking fails and why Single Packet Authorization is the stronger design.

Required Reading

  • TCP - handshake mechanics, flags, and SYN /ACK/RST behavior
  • Network Scanning - port scanning and how nmap discovers open ports

The Problem Port Knocking Solves

A service listening on a TCP port is visible to anyone who scans the network. Even if the service is hardened - SSH with key-only authentication, HTTPS with strong ciphers - the port is open. Attackers can probe it, fingerprint the service version, and attempt exploits against the daemon or its dependencies.

Port knocking hides the service entirely. The port appears closed to everyone - nmap reports it as closed or filtered . The service only becomes reachable after the client sends a specific sequence of connection attempts to a set of closed ports. After authentication, iptables dynamically opens the real service port for the authenticated client's IP address. 

Without port knocking:
  nmap -> Port 22/tcp  open    OpenSSH 9.4   <- visible, attackable

With port knocking:
  nmap -> Port 22/tcp  closed  (or filtered)   <- invisible
  Client knocks: SYN to 7000, SYN to 8000, SYN to 9000
  iptables opens port 22 for client IP
  Client connects to port 22
  After session ends or timeout, port 22 closes again

How Port Knocking Works

Port knocking exploits the fact that iptables (and nftables ) can dynamically modify firewall rules. A userspace daemon such as knockd sniffs packets with libpcap and watches for connection attempts to the configured ports. The iptables recent module instead keeps its own list of source IP addresses in the kernel and needs no daemon. Neither approach reads the connection tracking (conntrack) table.

The sequence is defined by the administrator and acts as a shared secret:

Knock sequence: TCP SYN to 7000 -> TCP SYN to 8000 -> TCP SYN to 9000
Result: ACCEPT rule added for client IP on port 22 (SSH)

Because each SYN that hits a closed port gets an RST, the scanner sees nothing unusual. There is no way to distinguish a port that is part of a knock sequence from a genuinely closed port.

IPtables Architecture

The kernel's netfilter subsystem processes packets through chains: PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING. Port knocking operates primarily on the INPUT chain: 

                             +--------------+
                             |   Packet In  |
                             +------+-------+
                                    |
                                    v
                          +-----------------+
                          |    Raw Table    |
                          |   PREROUTING    |
                          +--------+--------+
                                   |
                                   v
                          +-----------------+
                          |   Mangle Table  |
                          |   PREROUTING    |
                          +--------+--------+
                                   |
                                   v
                          +-----------------+
                          |    NAT Table    |
                          |   PREROUTING    |
                          +--------+--------+
                                   |
                                   v
                          +-----------------+
                          |  Filter Table   |
                          |     INPUT       |  <- knock daemon inserts
                          |                 |     ACCEPT rules here
                          +-----------------+

knockd Configuration

knockd is the standard userspace port knocking daemon. It listens on a raw socket (or reads from pcap) and executes commands when knock sequences match: 

# Install knockd on ArchLinux
sudo pacman -S knockd

Configuration File

[options]
    # Log file for knock events
    LogFile = /var/log/knockd.log

    # Interface to listen on (eth0, wlan0, etc.)
    Interface = eth0

[openSSH]
    # Knock sequence - order and ports matter
    sequence        = 7000:tcp,8000:tcp,9000:tcp
    # Time window to complete the sequence (seconds)
    seq_timeout     = 15
    # Command executed when sequence matches
    command         = /usr/sbin/iptables -A INPUT -s %IP% -p tcp --dport 22 -j ACCEPT
    # iptables chain for the rule
    tcpflags        = syn

[closeSSH]
    sequence        = 9000:tcp,8000:tcp,7000:tcp
    seq_timeout     = 15
    command         = /usr/sbin/iptables -D INPUT -s %IP% -p tcp --dport 22 -j ACCEPT
    tcpflags        = syn

[openHTTPS]
    sequence        = 5000:udp,6000:udp,7000:tcp
    seq_timeout     = 20
    command         = /usr/sbin/iptables -A INPUT -s %IP% -p tcp --dport 443 -j ACCEPT
    tcpflags        = syn

knockd replaces %IP% with the source IP of the knocking client. The tcpflags = syn option ensures only SYN packets count - RST, ACK, or data packets are ignored.

Start and Enable knockd

# Enable knockd for the correct interface
sudo systemctl edit knockd
# Add:
# [Service]
# ExecStart=
# ExecStart=/usr/bin/knockd -i eth0

sudo systemctl enable --now knockd

# Check logs
sudo journalctl -u knockd -f

Client-side Knocking

# Install knock (client tool)
sudo pacman -S knockd  # Includes knock client

# Send the open sequence
knock server.example.com 7000 8000 9000

# SSH in after knocking
ssh user@server.example.com

# Send the close sequence
knock server.example.com 9000 8000 7000

Knocking with netcat

# nc -z attempts a full TCP connection. Against a closed port that is just a
# SYN followed by the server's RST, which is exactly what a knock needs.
nc -z server.example.com 7000
nc -z server.example.com 8000
nc -z server.example.com 9000

# Or with nmap (SYN scan, no full connection)
sudo nmap -sS -Pn -p 7000 --max-retries 0 server.example.com
sudo nmap -sS -Pn -p 8000 --max-retries 0 server.example.com
sudo nmap -sS -Pn -p 9000 --max-retries 0 server.example.com

Single Packet Authorization

Traditional port knocking has critical weaknesses:

  • Replay attacks: A passive observer can capture the knock sequence and replay it
  • No encryption: The sequence is transmitted in cleartext as port numbers
  • No integrity protection: An attacker could inject packets into the sequence
  • Port collision: The knock ports must not be used by legitimate services

Single Packet Authorization solves all of these by encoding the access request in a single, encrypted, authenticated UDP packet. fwknop (FireWall KNock OPerator) is the reference implementation. 

SPA flow:
  1. Client constructs authorization packet:
     - Timestamp (prevents replay)
     - Desired service (e.g., SSH on port 22)
     - Client's source IP
  2. Client encrypts packet with symmetric key (Rijndael/AES) or
     signs with GPG asymmetric key
  3. Client sends single UDP packet to server (default port 62201)
  4. Server (fwknopd) captures the packet via pcap
  5. Server decrypts/verifies the packet
  6. Server validates timestamp (anti-replay)
  7. Server inserts iptables ACCEPT rule for the client IP
  8. After timeout, iptables rule is removed
						
# Install fwknop
sudo pacman -S fwknop

# -- Server Setup --

# Generate keys
fwknop --key-gen

# Edit /etc/fwknop/fwknopd.conf
# PCAP_INTF          eth0;

# Edit /etc/fwknop/access.conf
# SOURCE: ANY;
# OPEN_PORTS: tcp/22;
# KEY_BASE64: <generated-key>;
# HMAC_KEY_BASE64: <generated-hmac-key>;
# FW_ACCESS_TIMEOUT: 60;  (seconds the port stays open)
# MAX_SPA_PACKET_AGE: 120;  (seconds)

# Start fwknopd
sudo systemctl enable --now fwknopd

# -- Client Usage --

# Set up client config (~/.fwknoprc)
# [myserver]
# ACCESS              tcp/22
# SPA_SERVER          server.example.com
# KEY_BASE64          <same-key-as-server>
# HMAC_KEY_BASE64     <same-hmac-key>

# Send SPA packet (opens port 22 for 60 seconds)
fwknop -n myserver

# SPA with GPG (asymmetric)
fwknop -A tcp/22 --gpg-recipient server-key --gpg-signer client-key \
    -D server.example.com

Why SPA Beats Port Knocking

Feature Port Knocking SPA (fwknop)
Replay protection No Yes (timestamp + aging)
Encryption None (cleartext ports) AES/Rijndael or GPG
Number of packets N packets (one per port) 1 packet
Port collision risk Yes (must not conflict with real services) Low (single UDP port, configurable)
Observability Multiple SYN packets visible Single UDP packet (looks like noise)
NAT traversal Works (individual packets) Works (single UDP packet)
Protocol TCP SYN or UDP UDP only

iptables recent Module

The recent module in iptables tracks IP addresses that match rules. It can be used to implement simple port knocking without any userspace daemon: 

#!/bin/bash
# Simple port knocking with iptables recent module
# Knock sequence: 7000 tcp -> 8000 tcp -> 9000 tcp -> opens SSH for 30s

SSH_PORT=22
TIMEOUT_SECONDS=30

# -- Cleanup existing knock rules --
iptables -F KNOCK_OPEN 2>/dev/null
iptables -X KNOCK_OPEN 2>/dev/null

for chain in GATE1 GATE2 PASSPHRASE; do
    iptables -F $chain 2>/dev/null
    iptables -X $chain 2>/dev/null
done

# -- Create chains --
iptables -N GATE1
iptables -N GATE2
iptables -N PASSPHRASE
iptables -N KNOCK_OPEN

# -- Gate 1: port 7000 first knock --
iptables -A INPUT -p tcp --dport 7000 -m state --state NEW \
    -m recent --name GATE1 --set -j DROP
iptables -A INPUT -p tcp --dport 7000 -m state --state ESTABLISHED -j ACCEPT

# -- Gate 2: port 8000 second knock (only from IPs that knocked port 7000) --
iptables -A INPUT -p tcp --dport 8000 -m state --state NEW \
    -m recent --name GATE1 --rcheck --seconds 15 -m recent \
    --name GATE2 --set -j DROP
iptables -A INPUT -p tcp --dport 8000 -m state --state ESTABLISHED -j ACCEPT

# -- Passphrase: port 9000 final knock (only from IPs that knocked 7000+8000) --
iptables -A INPUT -p tcp --dport 9000 -m state --state NEW \
    -m recent --name GATE2 --rcheck --seconds 10 -m recent \
    --name PASSPHRASE --set -j DROP
iptables -A INPUT -p tcp --dport 9000 -m state --state ESTABLISHED -j ACCEPT

# -- KNOCK_OPEN chain: allow SSH from IPs that completed the sequence --
iptables -A KNOCK_OPEN -p tcp --dport $SSH_PORT -m state --state NEW \
    -m recent --name PASSPHRASE --rcheck --seconds 15 \
    -m recent --name KNOCK_OPEN --set -j ACCEPT
iptables -A KNOCK_OPEN -p tcp --dport $SSH_PORT -m state --state ESTABLISHED -j ACCEPT

# -- Insert KNOCK_OPEN into INPUT before the default SSH rule --
iptables -I INPUT 1 -j KNOCK_OPEN

# -- Default: DROP SSH --
iptables -A INPUT -p tcp --dport $SSH_PORT -j DROP

echo "[+] Port knocking configured. SSH on port $SSH_PORT is hidden."
echo "    Knock sequence: nc -z <server> 7000 && nc -z <server> 8000 && nc -z <server> 9000"
echo "    Window opens for ${TIMEOUT_SECONDS}s, then closes."

How the recent Knock Works

1. Client SYN -> port 7000 (GATE1 chain)
   - recent GATE1: set (record this IP)
   - DROP (no response - looks like filtered port)

2. Client SYN -> port 8000 (GATE2 chain)
   - recent GATE1: rcheck (IP must exist in GATE1 list, within 15 seconds)
   - recent GATE2: set (record this IP for next stage)
   - DROP

3. Client SYN -> port 9000 (PASSPHRASE chain)
   - recent GATE2: rcheck (IP must exist in GATE2 list, within 10 seconds)
   - recent PASSPHRASE: set
   - DROP

4. Client SYN -> port 22 (KNOCK_OPEN chain)
   - recent PASSPHRASE: rcheck (IP must exist in PASSPHRASE list, within 15s)
   - ACCEPT -> connection succeeds

After `TIMEOUT_SECONDS`, entries in recent lists expire.
The next SSH connection attempt requires a fresh knock sequence.

The recent module stores IP s in /proc/net/xt_recent/ : 

# View current knock state
cat /proc/net/xt_recent/GATE1
cat /proc/net/xt_recent/GATE2
cat /proc/net/xt_recent/PASSPHRASE

# Manually clear knock state
echo clear | sudo tee /proc/net/xt_recent/GATE1
echo clear | sudo tee /proc/net/xt_recent/GATE2
echo clear | sudo tee /proc/net/xt_recent/PASSPHRASE

SSH Behind Port Knocking

The most common use case: hide SSH entirely from the internet. Combine knockd with SSH hardening: 

#!/bin/bash
# Complete SSH-through-knocking setup

# -- SSH hardening (before knocking) --

# Disable password authentication
sed -i 's/^#PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config
sed -i 's/^PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config

# Disable root login
sed -i 's/^#PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config

# Use non-standard port (defense in depth)
SSH_PORT=2222
sed -i "s/^#Port 22/Port $SSH_PORT/" /etc/ssh/sshd_config

# Restart SSH
sudo systemctl restart sshd

# -- Default firewall: DROP SSH port --
sudo iptables -A INPUT -p tcp --dport $SSH_PORT -j DROP

# -- knockd configuration for SSH --
sudo tee /etc/knockd.conf << 'KNOCKD'
[options]
    Interface = eth0
    LogFile = /var/log/knockd.log

[openSSH]
    sequence    = 7000:tcp,8000:tcp,9000:tcp
    seq_timeout = 15
    command     = /usr/sbin/iptables -I INPUT 1 -s %IP% -p tcp --dport 2222 -j ACCEPT
    tcpflags    = syn

[closeSSH]
    sequence    = 9000:tcp,8000:tcp,7000:tcp
    seq_timeout = 15
    command     = /usr/sbin/iptables -D INPUT -s %IP% -p tcp --dport 2222 -j ACCEPT
    tcpflags    = syn
KNOCKD

# Enable knockd
sudo systemctl enable --now knockd

Sequence Design

The security of port knocking depends on the sequence's unpredictability:

Weak sequence (vulnerable to brute force):
  Ports: 1000, 1001, 1002
  -> Only 3-4 bits of entropy per port in a narrow range

Strong sequence:
  Ports: 17923 tcp, 42001 udp, 28456 tcp
  -> 16 bits of entropy per port, 48 bits total
  -> Mixing protocols (TCP + UDP) adds confusion

Strongest (SPA):
  Single encrypted packet with HMAC
  -> 256 bits of entropy (key), replay protection

Sequence Entropy

For N ports chosen from range [1024, 65535]:
  Entropy per port: log2(65535 - 1024) ~ 16 bits
  Total: N x 16 bits

1-port sequence:  16 bits  (65,536 possibilities) - brute force feasible
2-port sequence:  32 bits  (4 billion) - marginal
3-port sequence:  48 bits  (281 trillion) - impractical
4-port sequence:  64 bits  - strong

Even with 48 bits of entropy, a local attacker can brute force faster because network RTT is the only limiting factor. For truly untrusted networks, SPA's cryptographic approach is necessary.

nftables Port Knocking

nftables provides an alternative to iptables for port knocking:

#!/usr/sbin/nft -f

flush ruleset

table inet knock {
    # Dynamic sets to hold knock state
    set knock_stage1 {
        type ipv4_addr
        timeout 15s
    }

    set knock_stage2 {
        type ipv4_addr
        timeout 10s
    }

    # Dynamic set to hold authenticated IPs
    set authenticated_ips {
        type ipv4_addr
        timeout 60s
    }

    chain input {
        type filter hook input priority filter; policy drop;

        # Allow established/related
        ct state established,related accept
        ct state invalid drop

        # Allow loopback
        iif lo accept

        # -- Knock state tracking --

        # Knock stage 1: port 7000
        tcp dport 7000 ct state new add @knock_stage1 { ip saddr timeout 15s }
        tcp dport 7000 drop

        # Knock stage 2: port 8000 (must be in stage1)
        tcp dport 8000 ct state new ip saddr @knock_stage1 \
            add @knock_stage2 { ip saddr timeout 10s }
        tcp dport 8000 drop

        # Knock stage 3: port 9000 (must be in stage2)
        tcp dport 9000 ct state new ip saddr @knock_stage2 \
            add @authenticated_ips { ip saddr timeout 60s }
        tcp dport 9000 drop

        # -- Access for authenticated IPs --
        tcp dport 22 ip saddr @authenticated_ips accept

        # -- Default deny for SSH --
        tcp dport 22 drop
    }
}

Limitations and Attacks

TCP sequence number reuse: A captured RST from a knock port does not let an attacker replay the original SYN , so the knock itself is not reproducible from the server's reply.

Port collision: The knock ports must not host real services. If port 7000 runs a web server, legitimate HTTP traffic would trigger the first knock stage. Choose ports that are unused on the server - or use SPA which uses a single UDP port.

Knock sequence observation: A passive observer can see the sequence of ports being accessed. With enough observation, the sequence is revealed. SPA eliminates this - the single encrypted packet reveals nothing about the sequence.

NAT complications: If the client is behind NAT , multiple clients share the same source IP . One client completing the knock sequence opens the port for everyone behind that NAT . SPA includes the source IP in the encrypted payload, so the server can whitelist a specific client behind NAT .

Sequence timing: If the time between knocks is too long, earlier stages expire. If too short, the sequence might be difficult to complete over high-latency links. Configuration must balance security (short windows) with usability.

DoS via state exhaustion: An attacker flooding port 7000 can fill the GATE1 recent list with random IP s, potentially exhausting kernel memory. The recent module has configurable size limits: 

# Limit knock table size
echo 100 | sudo tee /sys/module/xt_recent/parameters/ip_list_tot
cat /sys/module/xt_recent/parameters/ip_list_tot

Debugging Port Knocking

# -- Verify knockd is running --
sudo systemctl status knockd
sudo journalctl -u knockd -f

# -- Check iptables rules before/after knocking --
sudo iptables -L INPUT -n -v --line-numbers

# -- Monitor knockd log --
sudo tail -f /var/log/knockd.log

# -- Test knock sequence step by step --
# On server, watch for incoming packets:
sudo tcpdump -i eth0 -nn 'tcp[tcpflags] & (tcp-syn) != 0'

# On client, send individual knocks:
nc -zv server.example.com 7000
nc -zv server.example.com 8000
nc -zv server.example.com 9000

# -- Check recent module state --
sudo ls /proc/net/xt_recent/
sudo cat /proc/net/xt_recent/GATE1

# -- Simulate knock sequence locally (Python) --
python3 << 'EOF'
import socket
import time

target = "127.0.0.1"
sequence = [7000, 8000, 9000]

for port in sequence:
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.settimeout(1)
    try:
        sock.connect((target, port))
    except (ConnectionRefusedError, socket.timeout):
        pass  # Expected - port is closed
    finally:
        sock.close()
    time.sleep(0.5)

print("[+] Knock sequence completed")
EOF

OPSEC Considerations

From a network monitoring perspective:

What a passive observer sees with port knocking:
  - Client IP sends SYN to port 7000, receives RST
  - Client IP sends SYN to port 8000, receives RST
  - Client IP sends SYN to port 9000, receives RST
  - Client IP sends SYN to port 2222, receives SYN-ACK  <- connection succeeds!

The sequence is visible in network logs. A good monitoring setup will flag:
  - Three consecutive RST responses from the same server to the same client
  - Followed by a successful connection to a port that nmap showed as closed

This is anomalous behavior. Port knocking provides security through obscurity,
not cryptographic security. SPA addresses this by encrypting the entire request
in a single packet.

Defense in Depth

Port knocking hides services by requiring a specific sequence of connection attempts before the service port is dynamically opened. knockd provides a daemon-based implementation with configurable sequences and commands. fwknop adds cryptographic security with Single Packet Authorization

  • encrypting, authenticating, and replay-protecting the access request in a single UDP

packet. The iptables recent module enables a daemon-less implementation for simple use cases.

The technique is not a replacement for service hardening - SSH should still use key authentication, HTTPS should still use strong ciphers. Port knocking reduces the attack surface by hiding the service entirely from untargeted scans and automated exploit attempts.

Challenge

Write a Go program that detects a knock sequence from a stream of connection events. Implement a KnockTracker that accepts (SourceIP, Port, Timestamp) tuples and returns true when a given source completes the configured sequence in order, within a timeout. Reset a source's progress when it times out, and ignore out-of-order or duplicate knocks. Test it with a matching sequence and a sequence where one step is reordered. 

package main

import (
	"fmt"
	"time"
)

type Event struct {
	SourceIP string
	Port     int
	At       time.Time
}

type KnockTracker struct {
	sequence []int
	timeout  time.Duration
	progress map[string][]int
	lastSeen map[string]time.Time
}

func NewKnockTracker(sequence []int, timeout time.Duration) *KnockTracker {
	return &KnockTracker{
		sequence: sequence,
		timeout:  timeout,
		progress: make(map[string][]int),
		lastSeen: make(map[string]time.Time),
	}
}

func (k *KnockTracker) Observe(event Event) bool {
	if last, ok := k.lastSeen[event.SourceIP]; ok {
		if event.At.Sub(last) > k.timeout {
			k.progress[event.SourceIP] = nil
		}
	}
	k.lastSeen[event.SourceIP] = event.At

	progress := k.progress[event.SourceIP]
	if event.Port == k.sequence[len(progress)] {
		progress = append(progress, event.Port)
	}

	if len(progress) == len(k.sequence) {
		delete(k.progress, event.SourceIP)
		delete(k.lastSeen, event.SourceIP)
		return true
	}

	k.progress[event.SourceIP] = progress
	return false
}

func main() {
	tracker := NewKnockTracker([]int{7000, 8000, 9000}, 15*time.Second)
	base := time.Now()

	events := []Event{
		{"10.0.0.5", 7000, base},
		{"10.0.0.5", 8000, base.Add(1 * time.Second)},
		{"10.0.0.5", 9000, base.Add(2 * time.Second)},
		{"10.0.0.6", 7000, base.Add(3 * time.Second)},
		{"10.0.0.6", 9000, base.Add(4 * time.Second)},
		{"10.0.0.6", 8000, base.Add(5 * time.Second)},
	}

	for _, event := range events {
		open := tracker.Observe(event)
		fmt.Printf("%s -> %d open=%v\n", event.SourceIP, event.Port, open)
	}
}

go run knock.go;
