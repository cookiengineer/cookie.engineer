EDR Internals

Endpoint Detection and Response architecture, from kernel callbacks and minifilter drivers to eBPF telemetry, Falco, Tetragon, and evasion countermeasures.

Overview

EDR products need deep visibility into endpoint activity, which usually means kernel-level access, yet they must resist an adversary who has that same access. This article follows the telemetry path from Windows kernel callbacks and minifilter drivers through ETW and user-mode hooks, then compares the Linux approaches built from LSM hooks, auditd, kernel modules, and eBPF programs. It ends with the evasion techniques that detection engineers must anticipate.

Required Reading

  • Kernel Architecture - protection rings, kernel subsystems, address space model
  • System Call Dispatch - syscall entry/exit, dispatcher mechanics, kprobes
  • Kernel Observability - tracepoints, ftrace, kernel probes, perf events
  • eBPF - eBPF architecture, verifier, program types, maps, JIT compiler
  • System Calls - syscall mechanism, strace, user-space tracing fundamentals

What EDR Does

EDR (Endpoint Detection and Response) is a category of security software that continuously monitors endpoint activity, detects suspicious behavior, and enables incident response. Unlike signature-based antivirus that looks for known malware at a single point in time, EDR records telemetry across the entire attack lifecycle and correlates events to identify patterns.

EDR operates at a fundamental tension: it needs deep visibility (requiring kernel-level access) but must not be circumventable by the same kernel-level access. Every defense mechanism is an attack surface for an adversary with ring 0 access.

Kernel Callback Architecture

On Windows, EDR products register with a formal callback framework built into the kernel. Linux has no unified EDR callback API - security products use a patchwork of LSM hooks, kprobes, eBPF programs, and auditd rules.

Minifilter Drivers

The Windows Filter Manager (FltMgr.sys) provides a framework for minifilter drivers - kernel modules that intercept filesystem I/O without implementing a full filesystem. Minifilters register for specific I/O operations ( IR P_MJ_CREATE, IR P_MJ_READ, IR P_MJ_WRITE, etc.) and receive pre- and post-operation callbacks.

Altitude allocation (Windows)

A minifilter's altitude is a string that determines its position in the filter stack. Microsoft maintains an altitude allocation table:

Altitude Range Usage
420000-429999 Filter groups
400000-409999 Top-level filters
320000-329999 EDR / Anti-malware filters
300000-309999 Continuous backup
280000-289999 Activity monitor
260000-269999 Content screener
240000-249999 Quota management
220000-229999 System recovery
180000-189999 HSM (Hierarchical Storage Management)
140000-149999 Encryption
130000-139999 Compression
080000-089999 Antivirus (legacy)
040000-049999 Top-level storage device filter
020000-029999 FileInfo (FltMgr-internal)
000000 FSFilter Infrastructure (bottom)

Lower altitude = closer to the file system, higher = closer to user mode. An EDR wants to be above antivirus (328000) so it can detect AV bypasses. The target device filter wants to be at the bottom so it sees raw writes.

ETW Integration

ETW is the high-performance event logging infrastructure that EDR products depend on for user-mode telemetry. It allows instrumented components (the kernel, drivers, user-mode applications) to emit structured events that subscribers consume in near-real-time.

User-Mode Hooking

EDR products on Windows inject DLL s into every process to intercept user-mode API calls. The DLL hooks ntdll.dll syscall stubs - the last user-mode code before the kernel. 

┌──────────────────────────────────────────────────────────────────────┐
│                     USER-MODE HOOKING CHAIN                            │
│                                                                      │
│  Application:                                                        │
│    VirtualAlloc(addr, size, MEM_COMMIT, PAGE_EXECUTE_READWRITE)      │
│       │                                                              │
│       ▼                                                              │
│  kernel32.dll:                                                       │
│    VirtualAlloc() → VirtualAllocEx(GetCurrentProcess(), ...)         │
│       │                                                              │
│       ▼                                                              │
│  kernelbase.dll:                                                     │
│    VirtualAllocEx() { ... } → NtAllocateVirtualMemory()              │
│       │                                                              │
│       ▼                                                              │
│  ntdll.dll (EDR HOOK POINT):                                         │
│    NtAllocateVirtualMemory:                                          │
│       mov r10, rcx          ; syscall number (EDR may intercept)     │
│       mov eax, 0x18         ; syscall number for NtAllocVirtMem      │
│       JMP edr_hook          ; ← EDR redirects here                   │
│       syscall                                                       │
│                                                                      │
│  edr_hook (injected DLL):                                           │
│    Check: is caller allocating RWX memory?                           │
│    If yes: Block or log, depending on policy                         │
│    If no:  syscall (0x18) the real NtAllocateVirtualMemory           │
└──────────────────────────────────────────────────────────────────────┘

Tamper Protection

EDR products must protect themselves from being disabled by malware. On Windows, this involves several mutually reinforcing mechanisms: 

┌──────────────────────────────────────────────────────────────────────┐
│                      TAMPER PROTECTION LAYERS                          │
│                                                                      │
│  1. Early Launch Anti-Malware (ELAM):                                │
│     Boot-start driver loaded before any third-party drivers.         │
│     ELAM driver classifies each boot driver as Good/Bad/Unknown.     │
│     Windows evaluates classifications before initializing drivers.   │
│                                                                      │
│  2. Protected Process Light (PPL):                                   │
│     EDR processes run as Protected Process (PsProtectedSignerAntimalware)│
│     Signer: PsProtectedSignerAntimalware (0x3)                       │
│     Cannot be: terminated, debugged, injected, or memory-read        │
│     Exception: kernel code can override PPL (patch PPL bit in EPROCESS)│
│                                                                      │
│  3. Callback Self-Protection:                                        │
│     EDR's own ObRegisterCallbacks protects the EDR process.           │
│     When another process tries OpenProcess(PROCESS_VM_READ, EDR_PID),│
│     the callback strips access rights to 0.                          │
│     Tools like Mimikatz cannot dump EDR process memory.              │
│                                                                      │
│  4. Minifilter Self-Protection:                                      │
│     EDR's minifilter protects its own files/directories.              │
│     Prevents deletion of: EDR binaries, configuration, signatures    │
│     Even SYSTEM processes cannot delete protected files.             │
│                                                                      │
│  5. Registry Key Protection:                                         │
│     EDR uses CmRegisterCallback to protect:                          │
│     - HKLM\System\CurrentControlSet\Services\<EDR Driver>            │
│     - HKLM\Software\<EDR Vendor>                                     │
│     Prevents service disable, startup type change, file path change  │
│                                                                      │
│  6. Communication Channel Protection:                                │
│     EDR agent → EDR service uses authenticated, encrypted channel    │
│     Certificate pinning prevents MITM                                │
│     Rate limiting prevents DoS on EDR cloud backend                  │
└──────────────────────────────────────────────────────────────────────┘

Linux EDR Approaches

Linux lacks the formalized callback architecture of Windows, so EDR products must build visibility from lower-level primitives. 

┌──────────────────────────────────────────────────────────────────────┐
│                    LINUX EDR APPROACHES                                │
│                                                                      │
│  Approach 1: eBPF-based (Falco, Tetragon)                            │
│    ┌─────────────────────────────────────────────────────────┐      │
│    │  eBPF programs attached to:                               │      │
│    │  - tracepoint:syscalls:sys_enter_execve                  │      │
│    │  - tracepoint:syscalls:sys_enter_connect                 │      │
│    │  - kprobe:security_bprm_creds_for_exec                   │      │
│    │  - kprobe:tcp_v4_connect                                 │      │
│    │                                                           │      │
│    │  Pros: Safe (verifier), fast (JIT), no modules needed     │      │
│    │  Cons: Limited by verifier, can't block calls natively    │      │
│    └─────────────────────────────────────────────────────────┘      │
│                                                                      │
│  Approach 2: auditd-based (Wazuh, Osquery)                           │
│    ┌─────────────────────────────────────────────────────────┐      │
│    │  auditd rules generate events:                            │      │
│    │  -a always,exit -F arch=b64 -S execve                    │      │
│    │  -a always,exit -F arch=b64 -S connect                   │      │
│    │  -a always,exit -F arch=b64 -S ptrace                    │      │
│    │                                                           │      │
│    │  Pros: Stable, no kernel compile needed, SELinux integrate│      │
│    │  Cons: High overhead (every syscall logged to userspace)  │      │
│    │         Can be disabled by root: auditctl -e 0            │      │
│    └─────────────────────────────────────────────────────────┘      │
│                                                                      │
│  Approach 3: LSM-based (AppArmor, SELinux)                           │
│    ┌─────────────────────────────────────────────────────────┐      │
│    │  LSM hooks integrated into every kernel code path:        │      │
│    │  - All file operations pass through security_file_* hooks │      │
│    │  - All socket operations pass through security_socket_*   │      │
│    │  - BPF LSM (5.7+) allows eBPF programs on LSM hooks       │      │
│    │                                                           │      │
│    │  Pros: Authoritative (can deny operations), always-on     │      │
│    │  Cons: Static policy, limited dynamic detection           │      │
│    └─────────────────────────────────────────────────────────┘      │
│                                                                      │
│  Approach 4: Kernel module (proprietary EDR drivers)                 │
│    ┌─────────────────────────────────────────────────────────┐      │
│    │  Custom .ko that hooks:                                   │      │
│    │  - sys_call_table entries (risky on modern kernels)       │      │
│    │  - register_kprobe() on key functions                     │      │
│    │  - netfilter hooks for network visibility                 │      │
│    │                                                           │      │
│    │  Pros: Full control, no verifier limitations              │      │
│    │  Cons: Module signing requirements, can crash kernel,     │      │
│    │        need per-kernel-version builds, security risk      │      │
│    └─────────────────────────────────────────────────────────┘      │
└──────────────────────────────────────────────────────────────────────┘

Falco - eBPF-Based Runtime Security

Falco is a CNCF graduated runtime security tool that uses eBPF probes (or kernel modules) to detect anomalous behavior defined by rules. 

┌──────────────────────────────────────────────────────────────────────┐
│                        FALCO ARCHITECTURE                              │
│                                                                      │
│  ┌─────────────┐                                                     │
│  │  Falco Rule │  rules.yaml:                                        │
│  │   Engine    │   - rule: "Terminal shell in container"             │
│  └──────+──────┘     condition: "spawned_process and container"      │
│         │             and proc.name = bash                           │
│         ▼             output: "Shell opened in container"            │
│  ┌─────────────┐     priority: WARNING                               │
│  │  libsinsp   │                                                     │
│  │  libscap    │  State management:                                  │
│  │  (userspace)│  - Thread table (tracking all processes)            │
│  └──────+──────┘  - FD table (file descriptor tracking)             │
│         │         - Container context (cgroup-based)                 │
│         ▼         - User/group context                                │
│  ┌─────────────┐                                                     │
│  │  eBPF Probe │  Kernel instrumentation:                            │
│  │  OR kernel  │  - sys_enter/sys_exit tracepoints                   │
│  │  module     │  - fillers convert raw args to event structs        │
│  └─────────────┘  - Ring buffer → userspace (perf_event_array map)  │
│                                                                      │
│  Event flow:                                                         │
│    syscall → eBPF → fill arguments → ring buffer → libscap           │
│    → libsinsp (enrich with thread table info) → rule engine          │
│    → match → output (stdout, file, syslog, program)                  │
└──────────────────────────────────────────────────────────────────────┘

Falco rule structure

# /etc/falco/falco_rules.local.yaml
- rule: Write below binary dir
  desc: An attempt to write to a binary directory
  condition: >
    bin_dir and evt.dir = < and evt.is_open_write=true
    and not package_mgmt_procs
    and not exe_running_docker_save
  output: >
    File below a known binary directory opened for writing
    (user=%user.name command=%proc.cmdline file=%fd.name)
  priority: ERROR
  tags: [filesystem, mitre_persistence]

- rule: Launch Suspicious Network Tool in Container
  desc: Detect network tools launched inside containers
  condition: >
    spawned_process and container
    and proc.name in (nmap, tcpdump, tshark, masscan)
  output: >
    Network tool launched in container
    (user=%user.name container=%container.name proc=%proc.name)
  priority: WARNING
  tags: [network, mitre_discovery, container]

- rule: Execution from /dev/shm
  desc: Detects execution from shared memory (common in container escapes)
  condition: >
    spawned_process
    and proc.exe startswith "/dev/shm/"
  output: >
    Executable executed from /dev/shm (user=%user.name
    cmdline=%proc.cmdline)
  priority: CRITICAL
  tags: [process, mitre_execution, container]

Tetragon

Tetragon from Cilium takes a different approach - instead of syscall-level monitoring, it hooks deep into kernel functions to correlate events that syscall-level monitoring misses. 

┌──────────────────────────────────────────────────────────────────────┐
│                       TETRAGON ARCHITECTURE                            │
│                                                                      │
│  Tetragon attaches eBPF programs to:                                  │
│                                                                      │
│  Process lifecycle:                                                   │
│    kprobe:security_bpf_prog (LSM hook)  — BPF load attempts          │
│    kprobe:wake_up_new_task               — new process creation       │
│    kprobe:cgroup_procs_write             — PID namespace changes      │
│    kprobe:security_task_prctl            — PRCTL operations           │
│                                                                      │
│  File operations:                                                     │
│    kprobe:security_file_permission       — file permission checks     │
│    kprobe:vfs_open                       — file open                  │
│                                                                      │
│  Network:                                                             │
│    kprobe:tcp_connect                    — TCP connections            │
│    tracepoint:net/netif_receive_skb      — incoming packets           │
│    kprobe:udp_sendmsg                    — UDP datagrams              │
│                                                                      │
│  Namespace changes:                                                   │
│    kprobe:create_new_namespaces          — namespace creation         │
│    kprobe:unshare                        — namespace unshare          │
│                                                                      │
│  Capabilities:                                                        │
│    kprobe:cap_capable                    — capability check           │
│    kprobe:ns_capable                     — namespace-aware cap check  │
│                                                                      │
│  Why deep hooks matter:                                               │
│    A process doing direct syscalls bypasses libc and ntdll hooks.    │
│    A process forking and exec'ing shows only fork+exec in syscalls.  │
│    Tetragon sees: fork→setns→unshare→cap_set→execve as one chain.    │
└──────────────────────────────────────────────────────────────────────┘

Tetragon TracingPolicy example

apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "detect-container-escape"
spec:
  kprobes:
  - call: "security_bprm_creds_for_exec"
    syscall: false
    args:
    - index: 0
      type: "file"
    return: "int"
    returnArg:
      index: 0
      type: "int"
    selectors:
    - matchArgs:
      - index: 0
        operator: "Prefix"
        values:
        - "/dev/shm/"
        - "/tmp/"
      matchActions:
      - action: Sigkill
      - action: Post
        rateLimit: "5m"

  - call: "cap_capable"
    syscall: false
    args:
    - index: 0
      type: "int"
    selectors:
    - matchArgs:
      - index: 0
        operator: "InMap"
        values:
        - "CAP_SYS_ADMIN:21"
        - "CAP_SYS_PTRACE:19"
        - "CAP_SYS_MODULE:16"
      matchActions:
      - action: Post
        rateLimit: "1m"

  - call: "create_new_namespaces"
    syscall: false
    selectors:
    - matchActions:
      - action: Post
        rateLimit: "1m"

EDR Evasion Techniques

Understanding evasion is critical to building resilient detection systems:

┌──────────────────────────────────────────────────────────────────────┐
│                      EDR EVASION TECHNIQUES                            │
│                                                                      │
│  1. Unhooking ntdll.dll:                                             │
│     Read clean ntdll.dll from disk (or KnownDlls section).           │
│     Overwrite in-memory ntdll.dll .text section with clean copy.     │
│     Result: EDR hooks removed from this process.                     │
│                                                                      │
│  2. Direct System Calls:                                             │
│     Instead of calling kernel32!VirtualAlloc → ntdll!NtAllocVirtMem  │
│     (which goes through EDR hooks), embed raw syscall gadgets.       │
│     syscall numbers must be manually resolved for each Windows build.│
│                                                                      │
│     x86-64 syscall gadget:                                           │
│       mov r10, rcx           ; 1st arg                              │
│       mov eax, <syscall_nr>   ; syscall number                       │
│       syscall                                                       │
│       ret                                                           │
│                                                                      │
│  3. Syscall Number Spoofing:                                         │
│     Call a harmless syscall number but craft args for a different    │
│     operation. EDR sees: harmless syscall → ignores. But through     │
│     controlled register state, achieves malicious outcome.           │
│     (Mostly theoretical — modern kernels validate args per number)   │
│                                                                      │
│  4. Callback Removal:                                                │
│     Malware with kernel access can:                                  │
│     - Walk PsActiveProcessHead and remove EDR callback entries       │
│     - Walk ObpCallbackArray and NULL out EDR entries                 │
│     - Unload the EDR minifilter via FltUnregisterFilter()            │
│                                                                      │
│  5. ETW Patching:                                                    │
│     EtwEventWrite() in ntdll.dll is a common hook target.            │
│     Malware patches EtwEventWrite to return STATUS_SUCCESS.          │
│     Result: ETW events are never emitted by this process.            │
│                                                                      │
│  6. Process Hollowing / Doppelganging:                               │
│     Create a benign process (notepad.exe) in suspended state.        │
│     Replace its memory with malicious code. Resume thread.           │
│     EDR sees: notepad.exe started and ran. But it's running malware. │
│     Defense: inspect process memory at resume time.                  │
│                                                                      │
│  7. Bring Your Own Vulnerable Driver (BYOVD):                        │
│     Load a signed but vulnerable kernel driver.                      │
│     Exploit the vulnerability to disable EDR callbacks from kernel.  │
│     Detection: driver blocklist, vulnerable driver signature DB.     │
└──────────────────────────────────────────────────────────────────────┘

Direct Syscall Example

// Bypass EDR user-mode hooks by making syscalls directly
// Instead of: NtAllocateVirtualMemory(GetCurrentProcess(), ...);
// Do:

#ifdef _WIN64
NTSTATUS NtAllocateVirtualMemory_direct(
    HANDLE ProcessHandle,
    PVOID *BaseAddress,
    ULONG_PTR ZeroBits,
    PSIZE_T RegionSize,
    ULONG AllocationType,
    ULONG Protect)
{
    // Syscall number for NtAllocateVirtualMemory on Windows 10 22H2: 0x18
    // This changes per build — must resolve dynamically in real code
    __asm {
        mov r10, rcx           // syscall convention: first arg → r10
        mov eax, 0x18          // syscall number
        syscall
        ret
    }
}
#endif

False Positive Management

The biggest challenge in any EDR deployment is signal-to-noise ratio. A poorly tuned EDR generates so many false positives that real alerts are ignored. 

┌──────────────────────────────────────────────────────────────────────┐
│                    FALSE POSITIVE MANAGEMENT                           │
│                                                                      │
│  Suppression Rules (suppress known-safe patterns):                    │
│    Example: "Jenkins running 'git clone' → EXPECTED, suppress"       │
│    Suppression must be: time-bounded, reason-documented, audited      │
│                                                                      │
│  Exclusion Lists (exclude known-benign paths/bins):                   │
│    Example: /usr/bin/dnf, /usr/bin/pacman → package manager          │
│    Danger: attacker renames malware to /usr/bin/dnf                  │
│    Mitigation: validate by binary hash, not path name                │
│                                                                      │
│  Machine Learning Baselines:                                          │
│    Build per-user/per-host behavioral profiles.                      │
│    Alert when process_tree, network_pattern, file_access deviates.   │
│    Example: "User alice usually spawns 5 processes/hour.             │
│              Now spawning 200/min → anomalous, investigate."         │
│                                                                      │
│  Severity Tuning:                                                     │
│    Critical: Requires immediate response (ransomware, LPE)            │
│    High: Suspicious, likely malicious (unusual parent, PTH)          │
│    Medium: Unusual but potentially benign (new software installed)   │
│    Low: Informational (first-seen hash, normal administrative action)│
│    Info: Telemetry only, no alert generated                          │
└──────────────────────────────────────────────────────────────────────┘

Verification

# 1. Install and run Falco
sudo pacman -S falco || sudo pacman -S falco-bin
sudo systemctl enable --now falco-bpf.service 2>/dev/null || \
sudo systemctl enable --now falco-kmod.service 2>/dev/null || true

# 2. View Falco rules
sudo cat /etc/falco/falco_rules.yaml | grep -A5 'rule:'
sudo cat /etc/falco/falco.yaml | grep -E 'json_output|buffered_outputs'

# 3. Trigger a Falco detection rule (spawn a shell)
# In another terminal, watch Falco output:
sudo journalctl -u falco -f &
# Then trigger:
bash -c "echo test from suspicious context" 2>/dev/null &
# Kill journalctl after observing: fg; ctrl+c

# 4. Start Falco in foreground for testing
sudo falco --print-additional 2>&1 | head -30 &

# 5. Trigger common detections
curl -s http://example.com &>/dev/null          # network connection
touch /tmp/test.sh && chmod +x /tmp/test.sh     # executable in /tmp
sudo cat /etc/shadow 2>/dev/null                # sensitive file read
sleep 2

# 6. Stop Falco
sudo pkill falco 2>/dev/null

# 7. auditd-based detection
sudo auditctl -l 2>/dev/null || echo "auditd not running"
# Sample audit rules for EDR-like monitoring:
# sudo auditctl -a always,exit -F arch=b64 -S execve -k process_exec
# sudo auditctl -a always,exit -F arch=b64 -S connect -k network_connect
# sudo auditctl -a always,exit -F arch=b64 -S ptrace -k ptrace_attempt

# 8. BPF LSM (kernel 5.7+) — check if supported
cat /sys/kernel/security/lsm
# Look for "bpf" in the output

# 9. eBPF program inspection (what's currently attached)
sudo bpftool prog list 2>/dev/null
sudo bpftool prog show id $(sudo bpftool prog list -j | jq -r '.[].id') --pretty 2>/dev/null | head -50

# 10. Check kernel lockdown (prevents eBPF program loading)
cat /sys/kernel/security/lockdown

# 11. PTrace scope (prevent process injection)
cat /proc/sys/kernel/yama/ptrace_scope
# 0 = no restrictions, 1 = only ancestors can ptrace, 2 = admin-only, 3 = fully disabled

# 12. Check for kernel-based EDR
lsmod | grep -iE 'falco|tetragon|wazuh|sentinel|crowd|defender|cortex'
sudo cat /proc/kallsyms | grep -iE 'falco|tetragon|edr'
