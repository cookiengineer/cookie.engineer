Boot Process

UEFI firmware to kernel init - the complete boot chain from power-on to PID 1, including Secure Boot, initramfs, and systemd activation.

Overview

From power-on to a running login prompt, the boot chain involves at least seven distinct stages. Each stage hands control to the next through a well-defined interface. For a security researcher, understanding this sequence is essential - rootkits, bootkits, and Secure Boot bypasses each target a different link. 

Power-on
  │
  ▼
┌─────────────────────────────────────────────────────────────────┐
│ 1. Firmware (UEFI / BIOS)                                       │
│    - CPU reset vector execution (0xFFFFFFF0 on x86)             │
│    - Platform initialization: memory, PCIe, USB                 │
│    - Device enumeration, DXE phase (UEFI)                       │
│    - Locates EFI System Partition (ESP)                         │
│    - Loads and executes boot manager                            │
└──────────────────────────+──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 2. Boot Manager (systemd-boot / GRUB / Windows Boot Manager)    │
│    - Reads config from ESP/loader/entries/ or /boot/grub/       │
│    - Presents boot menu (if multiple entries)                    │
│    - Loads kernel image (vmlinuz-linux) and initramfs into RAM  │
│    - Sets up kernel command line                                 │
│    - Calls ExitBootServices() to hand off to kernel             │
└──────────────────────────+──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 3. Linux Kernel Boot (arch/x86/boot/)                           │
│    - Real-mode entry, decompression, protected mode switch       │
│    - start_kernel(): architecture init, subsystem init          │
│    - Memory discovery (E820, ACPI), CPU enumeration              │
│    - Initial ramdisk (initramfs) unpacking                       │
└──────────────────────────+──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 4. Early Userspace (initramfs)                                  │
│    - /init script or binary executes                             │
│    - Loads essential kernel modules (storage, filesystem)       │
│    - Mounts root filesystem (pivot_root / switch_root)          │
└──────────────────────────+──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 5. PID 1 (systemd / OpenRC / runit)                             │
│    - Exec'd from initramfs /usr/bin/init -> /usr/lib/systemd     │
│    - Mounts API filesystems (/proc, /sys, /dev)                 │
│    - Reaches default.target (multi-user.target / graphical)     │
│    - Spawns getty on ttys, display manager, services            │
└─────────────────────────────────────────────────────────────────┘

UEFI vs Legacy BIOS

The industry has largely transitioned from legacy BIOS (16-bit real mode, Master Boot Record) to UEFI (32/64-bit, GUID Partition Table, EFI executables). The differences are fundamental and security-relevant.

Legacy BIOS UEFI
16-bit real mode (8086) 32-bit or 64-bit protected mode
1 MiB addressable boot code Full address space for drivers
MBR: 512 bytes boot code GPT: no 2 TiB disk limit
No standard driver model DXE drivers for hardware
Boots first sector of disk Loads EFI executable from ESP
No Secure Boot Secure Boot (PK, KEK, db, dbx)
CSM (Compatibility Support) Native UEFI only (modern)
No network boot standard PXE over UEFI, HTTP Boot
No persistent variables NVRAM variables (BootOrder, etc.)

Legacy BIOS Security

Many cloud virtual machines still use "BIOS" mode (SeaBIOS). In BIOS mode, the bootloader runs in 16-bit real mode, the MBR is trivially overwritten, and there is no Secure Boot. This makes it easier to: - Deploy a hypervisor-level implant that survives guest reboots - Modify the boot chain without triggering TPM PCR measurements - Use bootkits that install to the MBR gap (sectors 1-62 between the MBR and first partition) 

# Check if your system is booted in UEFI or legacy mode
[ -d /sys/firmware/efi ] && echo "UEFI mode" || echo "Legacy BIOS mode (or /sys not mounted)"

# If UEFI, inspect EFI variables
ls /sys/firmware/efi/efivars/ 2>/dev/null | head -20
ls /sys/firmware/efi/ 2>/dev/null

# Check firmware type from dmesg
sudo dmesg | grep -i "efi\|bios\|uefi" | head -10

EFI System Partition

The EFI System Partition is a FAT partition ( GUID C12A7328-F81F-11D2-BA4B-00A0C93EC93B ) that stores EFI executables. On Arch Linux, it is typically mounted at /boot or /efi . 

ESP layout (typical Arch Linux with systemd-boot):
/boot/
├── EFI/
│   ├── BOOT/
│   │   └── BOOTX64.EFI           # Fallback bootloader (UEFI default)
│   ├── Linux/
│   │   └── linux.efi             # Unified kernel image (optional)
│   └── systemd/
│       └── systemd-bootx64.efi   # systemd-boot EFI stub
├── loader/
│   ├── loader.conf               # Boot manager config
│   └── entries/
│       ├── arch.conf             # Default boot entry
│       └── arch-fallback.conf    # Fallback initramfs entry
├── vmlinuz-linux                 # Kernel image
├── initramfs-linux.img           # Default initramfs
├── initramfs-linux-fallback.img  # Fallback initramfs (more drivers)
└── amd-ucode.img                 # CPU microcode (if AMD)
						
# Find and inspect the ESP
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,LABEL | grep -i efi
# Or find by partition type GUID
sudo blkid | grep -i "C12A7328-F81F-11D2-BA4B-00A0C93EC93B"

# List contents of ESP
ls -laR /boot/ 2>/dev/null | head -50

# Check partition layout
sudo fdisk -l $(findmnt -n -o SOURCE /boot | sed 's/[0-9]*$//') 2>/dev/null

GRUB Bootloader

GRUB 2 is more complex than systemd-boot but supports legacy BIOS, encrypted /boot , and LVM . Its modular design loads filesystem drivers before accessing the kernel. 

GRUB boot sequence:
┌──────────────────┐
│ boot.img         │ ← 446 bytes, written to MBR (BIOS) or as EFI app
│ (LBA of core)    │
└────────+─────────┘
         ▼
┌──────────────────┐
│ core.img         │ ← Sector 1+, contains GRUB kernel + filesystem modules
│ (diskboot +      │   Loaded from post-MBR gap (BIOS) or ESP (UEFI)
│  kernel + mods)  │
└────────+─────────┘
         ▼
┌──────────────────┐
│ /boot/grub/      │ ← Filesystem accessible: reads grub.cfg
│ grub.cfg         │   Loads kernel + initramfs from actual filesystem
│ modules (*.mod)  │
└────────+─────────┘
         ▼
┌──────────────────┐
│ Linux kernel     │ ← vmlinuz-linux, loaded via the `linux` command
│ + initramfs      │
└──────────────────┘

cat /boot/grub/grub.cfg 2>/dev/null | head -60

# Regenerate GRUB config

# List GRUB modules

Linux Kernel Boot

The kernel boot is divided into architecture-specific early boot and architecture-independent initialization. This is where rootkits that patch the kernel image on disk take effect.

Stage 1 - Protected Mode

arch/x86/boot/
├── header.S        # Boot sector header, setup header, kernel version
├── main.c          # main() — decompress kernel, detect memory, set video
├── cpucheck.c      # CPU feature detection (64-bit, SSE, etc.)
├── memory.c        # E820 and E801 memory detection
├── pm.c            # Protected mode switch (16-bit → 32-bit)
└── video.c         # Video mode selection

Stage 2 - Decompression

arch/x86/boot/compressed/
├── head_64.S       # startup_64 — 64-bit entry, set up early page tables
├── misc.c          # decompress_kernel() — extract vmlinux.bin
└── pgtable_64.c    # Early identity mapping and kernel mapping

The compressed kernel image (bzImage) contains a self-extractor. The real kernel is uncompressed at boot: 

# Kernel image sizes
ls -lh /boot/vmlinuz-linux
# vmlinuz-linux: ~13 MiB (compressed bzImage)
# After decompression, vmlinux is ~40+ MiB

# Extract and inspect the kernel image
sudo pacman -S binutils
# vmlinuz is a bzImage; the actual ELF (vmlinux) is embedded inside
file /boot/vmlinuz-linux
# Output: Linux kernel x86 boot executable bzImage, version X.XX

Stage 3: 'start_kernel()' (init/main.c)

start_kernel() in init/main.c is the first architecture-independent C function. It initializes every kernel subsystem in a strict order: 

// init/main.c — start_kernel() (simplified call chain)
asmlinkage __visible void __init __no_sanitize_address start_kernel(void)
{
    // ─── Architecture setup ───
    setup_arch(&command_line);       // arch/x86/kernel/setup.c
    //   → Parse kernel command line
    //   → Initialize memory map (E820)
    //   → Setup paging, early_ioremap
    //   → Initialize APIC, timers

    // ─── Scheduler ───
    sched_init();                    // kernel/sched/core.c
    //   → Initialize runqueues
    //   → Set up idle threads per CPU

    // ─── Memory ───
    mm_init();                       // init/main.c → mm_init()
    //   → Bootmem allocator
    //   → Page allocator (buddy system)
    //   → Slab allocator (SLUB)
    //   → vmalloc

    // ─── Core subsystems ───
    rcu_init();                      // RCU subsystem
    init_IRQ();                      // Interrupt handling
    init_timers();                   // Timer subsystem
    timekeeping_init();              // Timekeeping
    console_init();                  // Console (VGA, fbcon, serial)
    vfs_caches_init();               // VFS dentry/inode caches
    signals_init();                  // Signal subsystem
    pagecache_init();                // Page cache
    acpi_early_init();               // ACPI tables

    // ─── The final step ───
    arch_call_rest_init();           // → rest_init()
    //   → Creates kernel_init thread (PID 1)
    //   → Creates kthreadd (PID 2)
    //   → CPU 0 enters idle loop
}
						
# See the boot call trace from the kernel log
sudo dmesg | grep -E "^\[" | head -60

# Filter for key milestones
sudo dmesg | grep -iE "Linux version|Command line|BIOS-e820|Memory:|DMI:|smpboot|write through the L1|sched_clock|Calibrating"

Memory Discovery: E820 and ACPI

The BIOS/UEFI provides the kernel with a map of physical memory through the E820 interface. This map tells the kernel which physical address ranges are RAM (usable), reserved (firmware, ACPI, PCIe MMIO), or defective. 

Typical E820 memory map (from dmesg):
BIOS-e820: [mem 0x0000000000000000-0x000000000009ffff] usable       ← RAM
BIOS-e820: [mem 0x00000000000a0000-0x00000000000fffff] reserved     ← Legacy VGA
BIOS-e820: [mem 0x0000000000100000-0x000000007fffffff] usable       ← RAM
BIOS-e820: [mem 0x0000000080000000-0x000000008fffffff] reserved     ← PCIe MMIO?
BIOS-e820: [mem 0x00000000f0000000-0x00000000f7ffffff] reserved     ← GPU?
BIOS-e820: [mem 0x00000000fed1c000-0x00000000fed1ffff] reserved     ← HPET
BIOS-e820: [mem 0x0000000100000000-0x000000083fffffff] usable       ← RAM above 4GiB
						
# Inspect firmware-provided memory map
sudo dmesg | grep "BIOS-e820"
sudo dmesg | grep "e820"

# View the kernel's internal memory map
sudo cat /proc/iomem | head -40
# Typical: System RAM, Kernel code, Kernel data, ACPI Tables, PCI Bus, etc.

# Check ACPI tables
sudo ls /sys/firmware/acpi/tables/
# ACPI tables: DSDT, FADT, MADT, MCFG, etc.

# Dump a specific ACPI table
sudo cat /sys/firmware/acpi/tables/DSDT > /tmp/dsdt.dat

CPU Detection and Microcode Loading

During boot, the kernel identifies the CPU model, family, stepping, and features. Microcode updates ( CPU firmware patches) are applied early in the boot process because they can fix security vulnerabilities (Spectre, Meltdown variants, MMIO stale data).

Microcode loading timeline:

UEFI/BIOS Applies early microcode
Bootloader Loads ucode.cpio/initrd
Linux kernel (early boot) Applies microcode from initramfs (if present)
Linux kernel (runtime) /lib/firmware/amd-ucode/ or intel-ucode/; can reload via /sys 
# Check current CPU microcode version
cat /proc/cpuinfo | grep -E "microcode|model name" | head -4

# Microcode revision comparison
grep microcode /proc/cpuinfo | head -1

# Check if microcode was loaded at boot
sudo dmesg | grep -i microcode

# Reload microcode at runtime (if newer version available)
ls /lib/firmware/amd-ucode/ 2>/dev/null || ls /lib/firmware/intel-ucode/ 2>/dev/null
# On Arch: install amd-ucode or intel-ucode packages
sudo pacman -S amd-ucode 2>/dev/null || sudo pacman -S intel-ucode 2>/dev/null

# Manual microcode reload (root):
# echo 1 > /sys/devices/system/cpu/microcode/reload

initramfs / initrd

The initramfs is a CPIO archive (optionally compressed) that contains a minimal root filesystem. Its purpose is to provide drivers and tools needed to mount the real root filesystem - LVM , LUKS, RAID, network storage, or exotic filesystems.

Why Use an initramfs

  • Smaller kernel = faster to load
  • Flexibility: change storage layout without recompiling
  • Early crypto: LUKS passphrase prompt before root is mounted
  • License separation: proprietary drivers need not be in the kernel image
initramfs contents (typical Arch mkinitcpio):
/
├── init                      # Init script or systemd binary
├── usr/
│   ├── bin/                  # Busybox utils or full binary set
│   │   └── systemd-tmpfiles
│   └── lib/systemd/          # systemd in initramfs
├── lib/
│   └── modules/              # Kernel modules for root fs
│       └── $(uname -r)/
│           └── kernel/
│               ├── drivers/scsi/
│               ├── drivers/nvme/
│               └── fs/ext4/
├── etc/
│   └── crypttab              # LUKS configuration
├── proc/ sys/ dev/ run/      # Mount points
└── root/                     # New root mount point for switch_root
						
# Inspect initramfs contents
lsinitcpio /boot/initramfs-linux.img | head -40

# List kernel modules included in initramfs
lsinitcpio /boot/initramfs-linux.img | grep '\.ko'

# Check initramfs size
ls -lh /boot/initramfs-linux.img /boot/initramfs-linux-fallback.img

# Extract initramfs for forensic analysis
mkdir /tmp/initramfs-inspect
cd /tmp/initramfs-inspect
sudo zstd -d -c /boot/initramfs-linux.img | sudo cpio -idmv 2>/dev/null || \
    sudo cat /boot/initramfs-linux.img | sudo cpio -idmv 2>/dev/null
ls -la
cd ~

# Check mkinitcpio configuration
cat /etc/mkinitcpio.conf

# Rebuild initramfs after changes
sudo mkinitcpio -P

The pivot_root / switch_root transition

At the end of early userspace, the initramfs must hand control to the real root filesystem. The sequence: 

initramfs /init script:
  1. Load kernel modules (modprobe ext4, modprobe nvme)
  2. Assemble storage (LVM, mdraid)
  3. Unlock encryption (cryptsetup luksOpen)
  4. Mount real root on /new_root
  5. switch_root /new_root /sbin/init
     → Moves /proc, /sys, /dev to /new_root
     → chroots to /new_root
     → execs /sbin/init (systemd)
     → Old initramfs memory is freed
						
# Trace the pivot/switch_root in kernel log
sudo dmesg | grep -iE "root|mount|switch|pivot|initramfs" | head -20

# Check root filesystem mount info
findmnt /

# See the device backing your root filesystem
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,UUID

systemd as PID 1

systemd is the de facto init system on Linux. It is PID 1 - the first user-space process - and inherits all orphaned processes. Its design is fundamentally different from SysV init: it activates units in parallel based on dependency graphs, uses socket activation for on-demand service start, and manages cgroups for process tracking.

systemd boot sequence

systemd (PID 1)
  │
  ├─► default.target (symlink to graphical.target or multi-user.target)
  │     │
  │     ├─► sysinit.target (system initialization)
  │     │     ├─► local-fs.target      ← mount local filesystems
  │     │     ├─► swap.target          ← activate swap
  │     │     ├─► systemd-sysctl       ← apply sysctl settings
  │     │     ├─► systemd-modules-load ← load kernel modules
  │     │     └─► systemd-tmpfiles     ← create volatile files
  │     │
  │     ├─► basic.target (basic system)
  │     │     ├─► sockets.target       ← socket-activated services
  │     │     ├─► timers.target        ← timer-activated services
  │     │     └─► paths.target         ← path-activated services
  │     │
  │     └─► multi-user.target
  │           ├─► network.target       ← network up
  │           ├─► sshd.service         ← SSH daemon
  │           ├─► cronie.service       ← Cron daemon
  │           └─► getty@tty1.service   ← Login prompts
						
# Boot time analysis
systemd-analyze
systemd-analyze blame | head -20           # What took the most time
systemd-analyze critical-chain             # Dependency chain on critical path
systemd-analyze plot > /tmp/boot.svg       # Generate SVG graph of boot

# List all active units
systemctl list-units --state=running | head -20
systemctl list-units --type=target

# See the dependency tree of a unit
systemctl list-dependencies multi-user.target

# Which units failed?
systemctl --failed

# Show default target
systemctl get-default

# Switch to a different target at runtime
sudo systemctl isolate multi-user.target    # Drop from graphical to console
sudo systemctl isolate rescue.target        # Single-user rescue mode
sudo systemctl isolate emergency.target     # Emergency shell (minimal)

Secure Boot

Secure Boot is a UEFI feature that ensures only cryptographically signed code executes during boot. The trust chain starts at the Platform Key (PK) and cascades through the Key Exchange Key (KEK) to the Signature Database (db) and Forbidden Signature Database (dbx). 

Secure Boot trust chain:

Platform Key (PK)
  │  Owned by platform owner (or OEM)
  │  Private key used to sign KEK updates
  │
  ▼
Key Exchange Key (KEK)
  │  Owned by Microsoft + platform owner
  │  Private key used to sign db/dbx updates
  │
  ├──────────────+──────────────────┐
  ▼              ▼                  ▼
Signature       Forbidden          Timestamp
Database (db)   Signatures (dbx)   Database (dbt)
  │              │
  │ Allowed      │ Revoked
  │ signatures   │ signatures
  │              │
  ▼              ▼
EFI binary → checked against db → if found → OK
             checked against dbx → if found → REJECTED
             not in db → NOT ALLOWED (unless Setup Mode)

MOK and the Shim Bootloader

For Linux distributions, the shim bootloader serves as a bridge. Shim is signed by Microsoft's UEFI CA (present in the default db). Shim then trusts binaries signed by the distribution's MOK (Machine Owner Key), which is enrolled at install time or via mokutil . 

UEFI Firmware → db (Microsoft CA)
  → shimx64.efi (signed by Microsoft)
    → GRUB/systemd-boot (signed by distro MOK)
      → Linux kernel (signed by distro MOK)
        → Kernel modules (signature checked by kernel, not UEFI)
						
# Check Secure Boot status
bootctl status | grep "Secure Boot"
# Or:
mokutil --sb-state
# Or directly from efivars:
sudo cat /sys/firmware/efi/efivars/SecureBoot-8be4df61-93ca-11d2-aa0d-00e098032b8c 2>/dev/null | xxd

# List enrolled MOK keys
mokutil --list-enrolled | head -20

# Check if kernel enforces module signature verification
cat /sys/module/kernel/parameters/module_sig_enforce
# 1 = only signed modules can be loaded

# See kernel lockdown status (Secure Boot enforces lockdown)
cat /sys/kernel/security/lockdown
# none = no lockdown
# integrity = kernel features restricted (no raw MSR access, no /dev/mem)
# confidentiality = even stricter (no kprobes on certain functions)

Secure Boot Bypass Techniques

  • shim vulnerability : CVE-2020-14372 - GRUB2 acpi command allowed loading unsigned ACPI tables, bypassing Secure Boot
  • Boothole (CVE-2020-10713) : GRUB2 buffer overflow in config parser allowed arbitrary code execution before ExitBootServices
  • Incomplete dbx revocation : a signed bootloader that is vulnerable but not yet listed in dbx can still chain-load unsigned code
  • Setup Mode : If the PK is deleted (via firmware menu or physical access), Secure Boot enters Setup Mode where db/dbx can be freely modified
  • LogoFAIL : UEFI image parsers (BMP, PNG, etc.) in firmware can be exploited during the boot logo display
# Check for known Secure Boot bypass CVEs
# Boothole mitigation: check if GRUB is updated
pacman -Qi grub 2>/dev/null | grep Version

# Check if shim is installed
pacman -Qi shim 2>/dev/null || echo "shim not installed — custom Secure Boot keys likely in use"

# Verify kernel module signature enforcement (if Secure Boot is active)
grep -r "CONFIG_MODULE_SIG_FORCE" /boot/config-$(uname -r)

The Boot Chain as an Attack Surface

Every stage in the boot chain is a potential persistence or privilege escalation target:

Stage Attack Vector Artifact
UEFI firmware DXE driver implant (LoJax, MosaicRegressor) SPI flash write
Boot manager (systemd-boot/GRUB) Modified EFI binary on ESP; GRUB config modification; BootHole GRUB exploit Replaced .efi file; grub.cfg with init=/bin/bash
Kernel + initramfs Kernel module rootkit; Modified initramfs; Patched kernel image on /boot Modified .ko in initramfs (persists across mkinitcpio)
Early userspace initramfs /init hook; Kernel cmdline injection (rd.break, init=/bin/bash) Hook in /etc/mkinitcpio.conf HOOKS array
PID 1 / systemd Malicious systemd service; systemd generator script; User unit persistence .service unit file; /etc/systemd/system/;~/.config/systemd/user/ 
# Forensics: Detect boot chain tampering

# 1. Check ESP for unexpected EFI binaries
sudo find /boot -name "*.efi" -exec sha256sum {} \;

# 2. Verify initramfs integrity (compare against freshly built)
mkinitcpio -P 2>/dev/null
sha256sum /boot/initramfs-linux.img

# 3. Check kernel cmdline for suspicious parameters
cat /proc/cmdline

# 4. Look for unexpected kernel modules loaded at boot
sudo dmesg | grep -i "module.*loaded"
lsmod | awk '{print $1}' | while read mod; do
    [ "$mod" != "Module" ] && modinfo -F signature "$mod" 2>/dev/null
done | grep -v "^$" | head -10

# 5. Check TPM PCR values (if TPM is present)
sudo tpm2_pcrread 2>/dev/null || echo "No TPM 2.0 device accessible"

# 6. systemd services that start at boot

UEFI Runtime Variables and efibootmgr

UEFI stores persistent configuration in NVRAM variables accessible via efivars . The boot order, boot entries, and Secure Boot databases are all stored there. 

# List UEFI boot entries
efibootmgr
# Typical output:
# BootCurrent: 0002
# BootOrder: 0002,0001,0000
# Boot0000* Windows Boot Manager
# Boot0001* UEFI: USB Drive
# Boot0002* Linux Boot Manager

# Create a new boot entry
sudo efibootmgr --create --disk /dev/nvme0n1 --part 1 --label "TestKernel" --loader /vmlinuz-linux

# Delete a boot entry
sudo efibootmgr --delete-bootnum --bootnum 0004

# Set next boot to a specific entry (one-time boot override)
sudo efibootmgr --bootnext 0001

# List all UEFI variables (huge output — pipe to head)
ls /sys/firmware/efi/efivars/ | head -30

# Read a specific EFI variable
# Note: efivars filenames are NAME-VENDOR_GUID
sudo xxd /sys/firmware/efi/efivars/BootOrder-8be4df61-93ca-11d2-aa0d-00e098032b8c 2>/dev/null

# Dump the full Boot Order as hex
sudo cat /sys/firmware/efi/efivars/BootOrder-8be4df61-93ca-11d2-aa0d-00e098032b8c 2>/dev/null | xxd

Challenge

Write a Go tool that reconstructs the boot chain of the running system: detect the firmware mode, read the kernel command line, report the lockdown state, and list the UEFI boot variables. Run it and verify each value against the shell commands below. 

package main

import (
	"fmt"
	"os"
	"strings"
)

func main() {
	if _, err := os.Stat("/sys/firmware/efi"); err == nil {
		fmt.Println("Firmware: UEFI")
	} else {
		fmt.Println("Firmware: Legacy BIOS")
	}

	cmdline, _ := os.ReadFile("/proc/cmdline")
	fmt.Println("Command line:", strings.TrimSpace(string(cmdline)))

	if lockdown, err := os.ReadFile("/sys/kernel/security/lockdown"); err == nil {
		fmt.Println("Lockdown:", strings.TrimSpace(string(lockdown)))
	}

	entries, err := os.ReadDir("/sys/firmware/efi/efivars")
	if err != nil {
		fmt.Println("EFI variables: not available")
		return
	}
	fmt.Printf("EFI variables: %d\n", len(entries))
	for _, entry := range entries {
		if strings.HasPrefix(entry.Name(), "Boot") {
			fmt.Println("  ", entry.Name())
		}
	}
}
