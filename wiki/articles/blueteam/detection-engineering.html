Detection Engineering

Writing reliable detections with minimal false positives across the full detection lifecycle.

Overview

Detection engineering turns raw telemetry into alerts that a human can act on. After reading this article you can write a behavioural rule, test it against known-good and known-bad data, and decide when it is ready for production. You will also see why generic rules copied from the internet fail, and how to measure coverage against MITRE ATT&CK .

Required Reading

  • Processes - process lifecycle, fork/exec, /proc filesystem
  • TCP - connection establishment, flags, state machine
  • DNS - resolution hierarchy, record types, tunneling

Concept

Detection engineering is the discipline of building, testing, deploying, and tuning automated alerting to identify malicious activity. It bridges the gap between "we have logs" and "we detect attacks." A detection is not a signature: it is a logic statement that, when true, indicates a specific threat with enough fidelity that an analyst can act on it.

The cardinal rule: every alert must be actionable. If an alert fires and the analyst cannot determine what to do, the detection has failed. No alert is better than a noisy alert that trains analysts to ignore the detection system.

The false positive rate is the key metric. A detection with a 1 percent false positive rate on a dataset of 1 billion events generates 10 million false alarms. That detection is useless. Aim for a false positive rate near 0 percent in your environment. This requires environment-specific tuning; generic detections are never production-ready.

Detection Lifecycle

The cycle is continuous, not linear:

Requirement -> Design -> Implement -> Test -> Deploy -> Tune
     ^                                                   |
     +---------------------------------------------------+

Requirement Phase

Define what threat you are detecting. Use MITRE ATT&CK technique IDs. Be specific: not "detect ransomware" but "detect T1486, files encrypted by a ransomware process via abnormal file extension modifications."

Design Phase

Identify data sources and logic. Ask what telemetry you have, what normal looks like, and what the attacker's observable artifact is. Design the logic before touching any query language.

Implement Phase

Write the detection rule in the target format: Sigma, YARA , SIEM query, or EDR rule. Use version control. Every rule has an author, a date, and a rationale.

Test Phase

Simulate the attack in a controlled environment with Atomic Red Team, Caldera, or manual simulation. Confirm the detection fires, then confirm it does not fire on benign activity.

Deploy Phase

Roll out to production monitoring. Start in alert-only mode with no automated response. Monitor alert volume for 48 to 72 hours before enabling any automated actions.

Tune Phase

Analyze false positives. Adjust thresholds, add filter conditions, and allow-list known-good behaviour. Document every exclusion with a business justification.

Detection Types

Atomic / Signature

Matches a single known-bad indicator: hash, IP , domain, filename, registry key, or certificate thumbprint. 

# Example: known C2 domain
detection:
  domain:
    - evil-c2.evil.com
    - backup-update.suspicious.net
  condition: domain

Strengths: low false positives for precise indicators, easy to implement. Weaknesses: trivial to evade by changing the indicator. Lowest tier on the Pyramid of Pain.

State-Based

Detects when a system transitions into a known-bad state: a service account added to Domain Admins, a firewall rule disabled, or a registry key modified. 

title: Service Account Added to Domain Admins Group
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4728
    GroupName: 'Domain Admins'
  filter:
    MemberSid|endswith: '-500'
  condition: selection and not filter

Strengths: hard to evade without undoing the state change. Medium tier on the Pyramid of Pain.

Behavioural / TTP

Detects attacker techniques regardless of tooling. It focuses on what the attacker does, not on what they use. 

title: Suspicious Process Creation via WMIC
logsource:
  product: windows
  service: sysmon
detection:
  selection:
    EventID: 1
    Image|endswith: '\wmic.exe'
    CommandLine|contains: 'process call create'
  condition: selection

Strengths: highest tier on the Pyramid of Pain; the attacker must change technique to evade. Hardest to implement correctly. Weaknesses: higher false positive risk, and it requires a deep understanding of both normal and malicious behaviour.

Anomaly-Based

Statistical deviation from a baseline. It requires profiling normal activity first.

# Simplified example: beacon detection via connection interval
import numpy as np

def detect_beacon(timestamps, threshold_seconds=0.5):
    """Detect regular-interval connections (C2 beaconing)."""
    if len(timestamps) < 10:
        return False

    deltas = np.diff(sorted(timestamps))
    mean_delta = np.mean(deltas)
    std_delta = np.std(deltas)

    # Low standard deviation = regular intervals = beacon
    if std_delta < threshold_seconds and mean_delta > 60:
        return True
    return False

Strengths: can detect unknown threats. Weaknesses: requires baselines and constant tuning as the environment changes.

Correlation-Based

Combines multiple weak signals into a single high-confidence detection. No single event is malicious, but the combination is. 

# Pseudocode: detection requires 3 of 5 weak signals
signals = [
    process_created_from_temp(),
    process_made_network_connection(),
    process_accessed_lsass(),
    process_has_no_digital_signature(),
    parent_process_is_office_app(),
]
if sum(signals) >= 3:
    raise_alert("Potential malicious Office macro execution")

Pyramid of Pain

David Bianco's Pyramid of Pain ranks indicators by how much pain an attacker feels when a defender blocks them: 

           +--------------+
           |     TTPs     |  <- Hardest to evade (change behaviour)
           +--------------+
           |    Tools     |  <- New tool, new C2 framework
           +--------------+
           |  Host/Network|  <- New domain, new IP, new ASN
           |   Artifacts  |
           +--------------+
           | Domain Names |  <- New domain registration
           +--------------+
           |  IP Addresses|  <- New VPS, VPN, proxy
           +--------------+
           |  Hash Values |  <- Recompile, pack, obfuscate
           +--------------+

Invest your effort at the top. Hash-based detections are the easiest to create and the easiest for attackers to evade. TTP -based detections are the hardest to create but force the attacker to change their approach fundamentally.

False Positive Reduction

Stack Counting

Count occurrence frequency across your environment. Rare events are more interesting than common events. 

-- Stack counting: find rare parent-child process combinations
SELECT
    parent_process_name,
    process_name,
    COUNT(*) AS occurrence_count
FROM process_creation_events
WHERE event_time > NOW() - INTERVAL '7 days'
GROUP BY parent_process_name, process_name
ORDER BY occurrence_count ASC
LIMIT 50;

Risk-Based Thresholds

Apply higher thresholds to high-volume events and lower thresholds to rare events.

RISK_THRESHOLDS = {
    "process_creation": 500,      # very common - high threshold
    "dns_query": 100,             # common
    "registry_modification": 20,  # somewhat common
    "service_creation": 3,        # rare - low threshold
    "lsass_access": 1,            # very rare - alert immediately
    "ntds_dit_access": 1,         # never normal - always alert
}

Environment Profiling

Build a baseline of what is normal for your specific environment before writing detections.

# Profile normal DNS query patterns
sudo tcpdump -i eth0 -w /tmp/dns-baseline.pcap port 53 &
# Capture during a representative window, then analyze the pcap
						
# Analyze a text export of query names to find "normal" top domains
import collections

domain_counts = collections.Counter()
with open('dns-baseline.txt') as f:
    for line in f:
        domain = line.strip().split(' ')[-1]
        domain_counts[domain] += 1

# Top 500 domains = normal. Anything outside = suspicious.
NORMAL_DOMAINS = set(d for d, c in domain_counts.most_common(500))

Detection-as-Code

Treat detection rules like software: version control, code review, CI/CD , and automated testing. 

# Directory structure for detection-as-code
mkdir -p detections/{sigma,yara,suricata,queries}/{production,staging,retired}
mkdir -p detections/tests/{simulations,unit}
						
# .github/workflows/detection-ci.yml
name: Detection CI
on: [push, pull_request]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Validate Sigma rules
        run: |
          podman run --rm -v $(pwd):/rules docker.io/sigmahq/sigma \
            sigma check /rules/sigma/
      - name: Validate YARA rules
        run: |
          podman run --rm -v $(pwd):/rules docker.io/metascan/yara \
            yara -C /rules/yara/
      - name: Run simulation tests
        run: |
          cd tests && ./run-simulations.sh

Each rule must pass four checks:

  1. Syntax validation - the rule parses without errors.
  2. Unit test - the rule matches a known-bad event.
  3. False positive test - the rule does not match known-good events.
  4. Peer review - another engineer approves the logic.

Testing Detections

Execute atomic attack techniques and verify that detections fire.

Alert Design

Every alert must carry these fields:

  • Unique ID - traceable, stable identifier.
  • Severity - Critical, High, Medium, or Low, with definitions.
  • Title - one-line description of what happened.
  • Description - what the alert means and what the attacker achieved.
  • MITRE ATT&CK mapping - technique ID and tactic.
  • Impacted assets - hostname, user, IP .
  • Evidence - raw log, process tree, network connection details.
  • Response steps - numbered list of what the analyst should do.
  • False positive guidance - under what conditions this is a false positive.
{
  "alert_id": "DET-2024-001",
  "severity": "High",
  "title": "Suspicious LSASS Memory Access",
  "technique": "T1003.001 - OS Credential Dumping: LSASS Memory",
  "tactic": "Credential Access",
  "hostname": "SRV-DC01",
  "username": "NT AUTHORITY\\SYSTEM",
  "process": "C:\\Windows\\Temp\\mimikatz.exe",
  "parent_process": "C:\\Windows\\System32\\cmd.exe",
  "timestamp": "2026-06-26T14:33:22Z",
  "evidence": {
    "event_id": 10,
    "source_image": "C:\\Windows\\Temp\\mimikatz.exe",
    "target_image": "C:\\Windows\\System32\\lsass.exe",
    "granted_access": "0x1010"
  },
  "response": [
    "1. Isolate SRV-DC01 from network immediately",
    "2. Dump memory of mimikatz.exe process (pid from evidence)",
    "3. Check for newly created domain accounts",
    "4. Force password reset for all accounts that authenticated to SRV-DC01 in the last 24h",
    "5. Collect mimikatz.exe binary for reverse engineering"
  ],
  "false_positive_guidance": "May trigger from legitimate security tools (AV, EDR, vulnerability scanners). Verify file hash and digital signature of source_image before escalating. Known legitimate triggers: CrowdStrike Falcon sensor, Qualys agent."
}

Mapping to MITRE ATT&CK

Every detection should map to at least one MITRE ATT&CK technique. This provides a common language for measuring detection coverage and identifying gaps. 

# Sigma rule with MITRE ATT&CK mapping
tags:
  - attack.t1003.001
  - attack.tactic.credential_access

Measure your coverage:

# Quick coverage gap analysis
import json

with open('mitre-attack-enterprise.json') as f:
    attack = json.load(f)

techniques = [t for t in attack['objects'] if t['type'] == 'attack-pattern']
detected = set()  # populate from your detection rule tags

for technique in techniques:
    ext_id = next(ref['external_id'] for ref in technique.get('external_references', [])
                  if ref.get('source_name') == 'mitre-attack')
    status = "DETECTED" if ext_id in detected else "GAP"
    print(f"{status}: {ext_id} - {technique['name']}")

coverage_pct = len(detected) / len(techniques) * 100
print(f"\nCoverage: {coverage_pct:.1f}% ({len(detected)}/{len(techniques)})")

Common Pitfalls

  1. Detecting tools instead of techniques - a rule matching mimikatz.exe is bypassed by renaming the file; detect the behaviour ( LSASS access with a specific access mask).
  2. Copy-paste detections - rules from the internet almost never work in your environment without tuning; baseline first.
  3. Excessive severity inflation - if every alert is Critical, none are; reserve Critical for confirmed compromise with business impact.
  4. Orphaned detections - every rule must have an owner who is accountable for its performance and tuning.
  5. Neglecting detection of detection failures - monitor when detections stop firing; an attacker who disables your EDR should trigger a detection.

Challenge

Write a Go detection engine that reads Sysmon-style JSON events (one object per line) from standard input and raises an alert for behavioural patterns: wmic.exe spawning process call create , and access to lsass.exe with a granted access mask that includes 0x10 (the PROCESS_VM_READ bit). 

package main

import (
	"bufio"
	"encoding/json"
	"fmt"
	"os"
	"strings"
)

type event struct {
	EventID       int    `json:"EventID"`
	Image         string `json:"Image"`
	CommandLine   string `json:"CommandLine"`
	TargetImage   string `json:"TargetImage"`
	GrantedAccess string `json:"GrantedAccess"`
}

type alert struct {
	name  string
	match func(event) bool
}

func main() {
	alerts := []alert{
		{
			name: "WMIC process creation",
			match: func(e event) bool {
				return e.EventID == 1 &&
					strings.HasSuffix(strings.ToLower(e.Image), `\wmic.exe`) &&
					strings.Contains(strings.ToLower(e.CommandLine), "process call create")
			},
		},
		{
			name: "LSASS memory access",
			match: func(e event) bool {
				return e.EventID == 10 &&
					strings.HasSuffix(strings.ToLower(e.TargetImage), `\lsass.exe`) &&
					strings.Contains(strings.ToLower(e.GrantedAccess), "0x10")
			},
		},
	}

	scanner := bufio.NewScanner(os.Stdin)
	for scanner.Scan() {
		var e event
		if err := json.Unmarshal(scanner.Bytes(), &e); err != nil {
			continue
		}
		for _, a := range alerts {
			if a.match(e) {
				fmt.Printf("[ALERT] %s: %s\n", a.name, e.Image)
			}
		}
	}
}

Feed it sample events and check the output:

cat > events.jsonl <<'EOF'
{"EventID":1,"Image":"C:\\Windows\\System32\\wmic.exe","CommandLine":"wmic process call create calc.exe"}
{"EventID":10,"TargetImage":"C:\\Windows\\System32\\lsass.exe","GrantedAccess":"0x1010"}
EOF

go run detection.go < events.jsonl

Then extend the engine with a third rule of your own and confirm it does not fire on a benign event (for example, notepad.exe ).
