Network Scanning

Network scanning is about finding out which hosts are alive on a network, and which ports are open on those hosts. Every attack or defense operation starts here. You cannot interact with what you cannot find.

OSI Layers

Scanning operates at different OSI layers, each with different reach and reliability characteristics. The choice of scan type determines what you can detect and what defenses you can bypass. 

Layer 1 (Physical):  Ethernet framing, everyone can broadcast anything
Layer 2 (Data Link): ARP scanning, in the same broadcast domain
Layer 3 (Network):   ICMP echo/timestamp, cross-network, often filtered
Layer 4 (Transport): TCP SYN/ACK, UDP, most reliable, exploits protocol guarantees
Layer 5 (Session):   TCP/HTTP/WS, exploits naive session guarantees

ARP Scanning

ARP maps IP addresses to MAC addresses. It is an OSI layer 2 protocol, it only works within the same broadcast domain, meaning in the same subnet and same VLAN . ARP has no concept of routing and cannot cross a router.

ARP Host Discovery

A host sends a broadcast ARP request with the message "Who has 192.168.1.5? Tell 192.168.1.10". Every host on the subnet receives this broadcast. The host with the matching IP responds with a unicast ARP reply containing its MAC address. The requesting host caches this mapping in its ARP table ( ip neigh ).

ARP cannot be blocked without breaking IPv4 on Ethernet networks. If a host has an IP address on the subnet, it must respond to ARP requests for that address. This is required for any IP communication to happen. This makes ARP scanning the most reliable form of host discovery on a local network. 

# View current ARP cache
ip neigh show;

# Install arp-scan (ArchLinux)
sudo pacman -S arp-scan;

# Scan the local subnet (auto-detects interface and netmask)
sudo arp-scan -l;

# Scan a specific subnet
sudo arp-scan 192.168.1.0/24;

# arp-scan output:
# 192.168.1.1     aa:bb:cc:dd:ee:ff    Router Manufacturer
# 192.168.1.42    11:22:33:44:55:66    Dell Inc.
# 192.168.1.128   77:88:99:aa:bb:cc    Raspberry Pi Foundation
# 3 packets received by filter, 0 packets dropped by kernel

arp-scan builds an Ethernet frame with ARP payload for every IP in the range, sends it, and waits for replies. Because it operates at layer 2, it bypasses any IP -level firewall. A host can run iptables -P INPUT DROP and still respond to ARP queries. 

# Single-host ARP ping with arping
sudo arping -c 3 -I eth0 192.168.1.1;

# Manual ARP request construction with scapy
sudo python3 << 'EOF'
from scapy.all import Ether, ARP, srp
packet = Ether(dst="ff:ff:ff:ff:ff:ff") / ARP(pdst="192.168.1.0/24")
answered, unanswered = srp(packet, timeout=2, verbose=False)
for sent, received in answered:
    print(f"{received.psrc} → {received.hwsrc}")
EOF

The ARP cache stores learned MAC -to- IP mappings. The kernel uses it to avoid ARP requests for every packet. Entries have a timeout which is typically 30-60 seconds for incomplete, and 300+ seconds for reachable replies. You can manipulate the cache to cause traffic redirection: 

# Check stale entries
ip neigh show nud stale;

# Static ARP entry (prevents ARP spoofing of gateway)
sudo ip neigh add 192.168.1.1 lladdr aa:bb:cc:dd:ee:ff dev eth0 nud permanent;

# Flush ARP cache
sudo ip neigh flush all;

ICMP

ICMP is the error reporting and diagnostic protocol for IP . Unlike ARP , ICMP is routable. It is an OSI layer 3 protocol. It can cross network boundaries. However, it is commonly filtered by firewalls and hosts because it exposes the network topology.

ICMP Echo

The ICMP Echo Request network packet is Type: 8 and the equivalent Echo Reply network packet is Type: 0 . This is the classic ping . The sender transmits an ICMP Echo Request with an identifier, sequence number, and payload. The receiver copies the payload into an Echo Reply. If the target is alive and not filtering ICMP Echo, you get a reply. 

# Standard ping
ping -c 3 8.8.8.8;

# nmap ICMP Echo sweep (-PE)
sudo nmap -sn -PE 192.168.1.0/24;

# fping - fast parallel ping
sudo pacman -S fping;
fping -a -g 192.168.1.0/24; # -a: show alive, -g: generate

ICMP Echo is usually blocked because it is the most common host discovery probe. Every single scanning tool uses it. Since there is no legitimate reason for arbitrary hosts to ping a server, blocking Echo doesn't break anything real.

ICMP Timestamp

The ICMP Timestamp Request network packet is Type: 13 and the equivalent Timestamp Reply network packet is Type: 14 . This requests the current time from a host. Less commonly filtered than Echo because it is obscure. Most administrators often don't even know that it exists. 

# nmap ICMP Timestamp sweep
sudo nmap -sn -PP 192.168.1.0/24;

# Manual timestamp request with nping
sudo nping --icmp-type 13 -c 3 192.168.1.1;

# Manual with hping3
sudo hping3 --icmp --icmptype 13 192.168.1.1 -c 3;

ICMP Address Mask

The ICMP Address Mask Request network packet is Type: 17 and the equivalent Address Mask Reply network packet is Type: 18 . This requests the subnet mask of a host. Deprecated (RFC 6918), rarely ever responded to. Only works against very old systems or misconfigured modern ones. 

# nmap ICMP Address Mask sweep
sudo nmap -sn -PM 192.168.1.0/24;

ICMP might be blocked because ICMP sits directly on IP (protocol number 1). A firewall rule like iptables -A INPUT -p icmp -j DROP blocks all ICMP types before the application layer even sees them. Many hardening guides recommend dropping all ICMP , which is misguided. It breaks Path MTU Discovery and other essential functions.

TCP

TCP host discovery exploits the fundamental reliability guarantees of TCP . As TCP is an OSI layer 4 protocol, the underlying network stack must respond to certain network packets, as otherwise the network protocol would break. This makes TCP based discovery effective even when all ICMP packets are dropped by a firewall.

TCP SYN Ping

Sends a TCP SYN to a port. If the host is alive and the port is open, you get a SYN -ACK. If the port is closed, you get a RST. Either response proves the host exists. No response (after retries) means the host is down or the probe is being filtered. 

# TCP SYN ping to port 80
sudo nmap -sn -PS80 192.168.1.0/24;

# Multiple ports (try common ones)
sudo nmap -sn -PS22,80,443,8080,8443 192.168.1.0/24;

# Default: nmap -PS uses port 443
sudo nmap -sn -PS 192.168.1.0/24;

TCP ACK Ping

Sends a TCP ACK to a port (with no prior handshake). RFC 793 says that if a host receives an ACK for a connection it knows nothing about, it must respond with RST. An ACK provokes a RST from both open and closed ports. This is unlike SYN , which only gets a RST from closed ports. This makes ACK pings unique as they always get a RST regardless of port state. 

# TCP ACK ping to port 80
sudo nmap -sn -PA80 192.168.1.0/24;

# Manual ACK probe with hping3
sudo hping3 -A -p 80 192.168.1.1 -c 3;

TCP is fundamental to almost all network communication. A firewall cannot blindly drop all TCP packets without breaking services it intends to allow. A stateful firewall inspects TCP flags and connection state, but ACK and SYN probes can still leak host existence information through RST responses.

UDP ping

Sends a UDP packet to a port. If the port is closed, the host sends ICMP Port Unreachable (Type 3, Code 3). If the port is open, most services send no response to an empty UDP probe. UDP host discovery is inherently unreliable. No response could mean alive and open, or alive and filtered, or dead. Only an ICMP Port Unreachable is definitive. 

# UDP ping to port 53 (DNS)
sudo nmap -sn -PU53 192.168.1.0/24;

# Multiple UDP ports
sudo nmap -sn -PU53,123,161,500 192.168.1.0/24;

Port Scanning

Once you know which hosts are alive, you determine which ports are open. Ports represent services. An open port means a process is listening. Port states reveal attack surface.

State Meaning TCP SYN Response TCP ACK Response UDP Response
open Application listening SYN-ACK RST (likely) No response (usually)
closed No application listening RST RST ICMP Port unreachable
filtered Firewall drops probe No response No response No response
unfiltered Probe reaches host but unknown N/A (for ACK scan) RST received N/A
open or filtered Open or filtered but unknown N/A (NULL/FIN/Xmas) N/A No response
closed or filtered Closed or filtered but unknown N/A No response N/A

TCP SYN Scan

This scan mode is the best. Send SYN , receive SYN -ACK means port is open (respond with RST to close). Receive RST means port is closed. Receive nothing means filtered. The handshake is never completed, so most applications don't log the connection. Requires raw socket capability (root). 

# SYN scan common ports
sudo nmap -sS 192.168.1.42;

# SYN scan specific ports
sudo nmap -sS -p 22,80,443 192.168.1.42;

# SYN scan all 65535 ports
sudo nmap -sS -p- 192.168.1.42;

# Fast SYN scan (top 100 ports)
sudo nmap -sS --top-ports 100 192.168.1.42;

The three-way handshake is Client sends SYN , Server sends SYN-ACK , Client sends ACK . A SYN scan sends SYN , receives SYN-ACK , then sends RST instead of ACK. The target's TCP stack transitions from SYN_RECEIVED back to CLOSED immediately without ever notifying the application.

TCP CONNECT Scan

Completes the full three-way handshake using the OS connect() syscall. Does not require root. Every application that is listening logs this connection. Slower and noisier than SYN scan. 

# Connect scan (no root needed)
nmap -sT 192.168.1.42;

# Compare SYN vs Connect: SYN scan terminates with RST, Connect with FIN
# sudo tcpdump -i eth0 -nn 'host 192.168.1.42;

TCP NULL Scan

Sends a TCP packet with no flags set (all zero). RFC 793 says that if the port is closed, respond with RST. If the port is open, the packet should be silently dropped. Exploits an implementation ambiguity in the RFC. 

sudo nmap -sN 192.168.1.42;

NULL , FIN , and Xmas scans only work reliably against systems that follow RFC 793. Microsoft Windows ignores the RFC and always responds with RST regardless of port state, making those scans show all ports as "open or filtered" on Windows. Linux and BSD follow the RFC correctly.

TCP FIN Scan

Sends a packet with only the FIN flag set. Same logic as the NULL scan. Closed port results in an RST response, open port results in a silent drop. 

sudo nmap -sF 192.168.1.42;

TCP XMAS Scan

Sends a packet with FIN , PSH , and URG flags all set (the packet "lights up like a Christmas tree"). Same logic as the other scans. Closed port results in RST response, open port results in a silent drop. 

sudo nmap -sX 192.168.1.42;

TCP ACK Scan

The ACK scan does not determine whether the port is open or closed. It maps firewall rules. Send an ACK to a port. If you receive RST , the port is unfiltered aka the packet reached the host and was processed by the TCP stack. If you receive nothing or ICMP unreachable, the port is filtered and a firewall dropped the packet before it reached the host. 

sudo nmap -sA 192.168.1.42;

# ACK scan specific ports
sudo nmap -sA -p 22,80,443 192.168.1.42;

Run a SYN scan for open ports. Run an ACK scan and all ports marked unfiltered (no firewall) vs some filtered (firewall present). The difference between filtered and unfiltered ACK responses tells you which ports are behind a stateful firewall.

TCP Window Scan

Similar to the ACK scan but examines the TCP Window field in the RST response. Some implementations set different window sizes depending on whether the port was open or closed when they received the unexpected ACK . Rarely useful today because most modern stacks use the same window size regardless. 

sudo nmap -sW -p 22,80 192.168.1.42;

UDP Port Scanning

UDP is connectionless. There is no handshake, no acknowledgment. When you send a UDP packet to a closed port, the target sends an ICMP Port Unreachable (Type 3, Code 3). When you send to an open port, the service typically returns nothing unless the packet matches its expected protocol format. For example, a DNS query to port 53 receives a DNS response.

UDP scanning is slow for two reasons:

  1. The kernel rate-limits ICMP Port Unreachable messages. Typically set to 1 per second on Linux via net.ipv4.icmp_ratelimit .
  2. Open ports produce no response, so nmap must wait for a timeout before deciding whether it was "open" or "filtered".
# UDP scan common ports
sudo nmap -sU 192.168.1.42;

# UDP scan specific service ports
sudo nmap -sU -p 53,67,68,69,123,161,500 192.168.1.42;

# Combined TCP+UDP scan
sudo nmap -sS -sU -p U:53,123,161,T:22,80,443 192.168.1.42;

# Speed up UDP with version detection probes
sudo nmap -sU -sV -p 53,161 192.168.1.42;

Advanced Scanning

Service Detection

Once ports are discovered, -sV probes the service to identify what software is listening and which version it is. nmap sends protocol-specific probes like a NULL probe, generic TCP , HTTP GET, SSL ClientHello etc. and matches the response against a database of 10,000+ service signatures. 

# Service detection on open ports
sudo nmap -sV 192.168.1.42;

# Aggressive version detection (more probes)
sudo nmap -sV --version-intensity 9 192.168.1.42;

# Light version detection (faster)
sudo nmap -sV --version-intensity 2 192.168.1.42;

# Version detection with OS detection
sudo nmap -sV -O 192.168.1.42;

nmap opens the TCP connection and completes the handshake, waits for the service banner of that service, then sends crafted probes. The response is matched against nmap-service-probes .

Timing Templates

nmap's timing templates control the trade-off between speed and stealth/accuracy:

Template Flag Probe Delay Timeout Scan Delay Parallelism Use Case
Paranoid -T0 5 min Long 5 min Serial Evade IDS through extreme slowness
Sneaky -T1 15 sec Long 15 sec Serial Evade IDS on WAN
Polite -T2 0.4 sec Long None Serial Slow links, reduce bandwidth
Normal -T3 1 sec 1 sec None Parallel Default
Aggressive -T4 1.25 sec 1.25 sec None Parallel Fast LAN, assume reliable network
Insane -T5 0.3 sec 0.75 sec None Aggressive Local network, no IDS concern 
# Custom timing parameters
sudo nmap -sS --min-rate 1000 --max-rate 5000 192.168.1.0/24;

# --min-rate: Send at least N packets/second (don't go slower)
# --max-rate: Send at most N packets/second (don't go faster, IDS avoidance)

# Retransmission control
sudo nmap -sS --max-retries 2 --host-timeout 5m 192.168.1.0/24;

# --max-retries: Maximum SYN retransmissions per port (default varies by -T)
# --host-timeout: Give up on a host after N time (skip unresponsive hosts)

# Scan delay (time between probes to a single host)
sudo nmap -sS --scan-delay 1s 192.168.1.0/24;

# Parallel host scanning
sudo nmap -sS --min-hostgroup 64 --max-hostgroup 256 192.168.1.0/24;

When to use each timing option:

  • -T4 on a local network. Fast, reliable, minimal packet loss.
  • -T3 on WAN /internet targets. Avoids overwhelming intermediate routers.
  • -T2 when scanning through rate-limited paths ( IDS , WAF , cloud providers).
  • -T1 or -T0 for IDS / IPS evasion. Below most detection thresholds but takes hours.
  • --min-rate 10000 when you need results fast and don't care about noise.

Output Formats

# Normal output (human-readable)
nmap -oN scan-results.nmap 192.168.1.42;

# XML output (machine-parsable, most complete)
nmap -oX scan-results.xml 192.168.1.42;

# Greppable output (legacy, one host:port per line)
nmap -oG scan-results.gnmap 192.168.1.42;

# All three formats at once
nmap -oA scan-results 192.168.1.42;

# Parse nmap XML with xmlstarlet
sudo pacman -S xmlstarlet;
xmlstarlet sel -t -m "//port[state/@state='open']" \
    -v "ancestor::host/address/@addr" -o ":" \
    -v "@portid" -o "/" -v "@protocol" -n scan-results.xml

# Parse nmap XML with Python
python3 << 'EOF'
import xml.etree.ElementTree as ET
tree = ET.parse("scan-results.xml")
root = tree.getroot()
for host in root.findall("host"):
    ip = host.find("address").get("addr")
    for port in host.findall(".//port"):
        if port.find("state").get("state") == "open":
            portid = port.get("portid")
            proto = port.get("protocol")
            svc = port.find("service")
            name = svc.get("name") if svc is not None else "unknown"
            print(f"{ip}:{portid}/{proto} → {name}")
EOF;

IPv6 Scanning

IPv6 presents a fundamental challenge for scanning because the address space is too large. A /64 subnet has 2^64 addresses. Brute-force scanning at 1 million probes per second would take over 500,000 years .

IPv6 scanning largely requires alternative enumeration. DNS zone transfers, SNMP walks, HTTP headers ( X-Forwarded-For , Via ), or application-level data leaks.

IPv6 Neighbor Discovery

# Ping all link-local hosts (multicast)
ping6 -c 2 -I eth0 ff02::1;

# Discover neighbors via NDP (Neighbor Discovery Protocol)
ip -6 neigh show;

# Use alive6 (from the thc-ipv6 package)
sudo pacman -S thc-ipv6;
sudo alive6 eth0;

IPv6 Host Discovery

# nmap IPv6 ping sweep (link-local multicast)
sudo nmap -6 -sn ff02::1%eth0;

# nmap IPv6 on a known address
sudo nmap -6 -sS 2001:db8::1;

# Enumerate via DNS reverse lookups
for host in $(dig -x 2001:db8::/64 axfr @ns.example.com 2>/dev/null | grep PTR); do
    echo $host;
done;

# Use IPv4 side channels: scan IPv4, then check if same hosts have IPv6
nmap -sn 192.168.1.0/24 -oX ipv4.xml;
# Then query those hostnames for AAAA records

Internet Scanning

masscan

masscan uses a custom userspace TCP / IP stack and asynchronous transmission to scan at internet scale. It can scan the entire public IPv4 address space on a single port in under 6 minutes with sufficient network bandwidth. 

sudo pacman -S masscan;

# Scan a /24 for ports 80 and 443 at 1000 packets/sec
sudo masscan 192.168.1.0/24 -p80,443 --rate 1000;

# Scan specific ports with banner grabbing
sudo masscan 192.168.1.0/24 -p22,80,443 --banners --rate 1000;

# Scan entire 10.0.0.0/8 (16 million IPs) on port 80
sudo masscan 10.0.0.0/8 -p80 --rate 100000;

# Output formats
sudo masscan 192.168.1.0/24 -p80,443 -oJ scan.json;   # JSON
sudo masscan 192.168.1.0/24 -p80,443 -oG scan.gnmap;  # Greppable
sudo masscan 192.168.1.0/24 -p80,443 -oB scan.bin;    # Binary (fastest)

masscan differences

Feature nmap masscan
TCP/IP stack Kernel (via raw sockets) Custom userspace stack
Speed ~1000-10000 ports/sec Up to 10+ million packets/sec
Service detection Yes (-sV) Limited (--banners)
OS detection Yes (-O) No
NSE scripts Yes No
Rate control -Ttemplates + fine-grained --rate(packets/sec)
Accuracy High (with retransmissions) Lower (may miss responses under load)
Use case Targeted scans, service/OS detection Internet-wide surveys, massive port sweeps

masscan is a reconnaissance tool for covering enormous address spaces. Use nmap for anything requiring accuracy, version detection, or script execution.

Decoys and Evasion

# Decoy scan: hide your IP among decoys
# nmap sends probes from all decoy IPs and the real IP
sudo nmap -sS -D 192.168.1.100,192.168.1.200,ME 10.0.0.1;
# ME = your real IP. Order matters — put ME in the middle.

# Spoof source address (one-way scan — you won't see responses)
sudo nmap -sS -S 192.168.1.100 -e eth0 10.0.0.1;
# Requires control of the spoofed IP or a network that doesn't RPF-filter.

# Source port manipulation (bypass weak firewalls trusting source port)
sudo nmap -sS --source-port 53 10.0.0.1;    # DNS source port
sudo nmap -sS --source-port 80 10.0.0.1;    # HTTP source port
# Firewalls that permit DNS replies (src port 53) or HTTP (src port 80)
# will pass these probes.

# Random data in probes (evade signature-based IDS)
sudo nmap -sS --data-length 200 10.0.0.1;    # Append 200 random bytes

# Fragment packets (bypass simple firewalls that can't reassemble)
sudo nmap -sS -f 10.0.0.1;                   # Split into 8-byte fragments
sudo nmap -sS --mtu 24 10.0.0.1;             # Fragment at custom MTU

# Idle scan — spoof scan using a zombie host
sudo nmap -sI 192.168.1.100:80 10.0.0.1;
# Exploits predictable IP ID increments on the zombie.
# Your IP never appears in the target's logs.

Target logs show connections from all decoy IP s. Without correlation across targets, because you pick different decoys each time, the real scanner is indistinguishable from the decoys.

Some firewalls inspect only the first fragment and the TCP header. Later fragments bypass inspection because reassembly is expensive. The target's TCP stack reassembles the fragments and processes the full SYN , therefore bypassing the firewall.

Practical Workflow

# Phase 1: Discover live hosts
# Local network: ARP is fastest and most reliable
sudo arp-scan -l > hosts-arp.txt;

# Remote network: combine multiple discovery methods
sudo nmap -sn -PE -PP -PS22,80,443,8080 -PU53,123,161 10.0.0.0/24 -oN hosts-discovered.txt;

# Phase 2: Port scan live hosts
# Extract live IPs from discovery output
grep "Nmap scan report" hosts-discovered.txt | awk '{print $5}' > live-ips.txt;

# Full port scan on discovered hosts (just top 1000 ports for speed)
sudo nmap -sS -sU -iL live-ips.txt -oA phase2-ports;

# Phase 3: Service and version detection
# On the open ports found in phase 2
sudo nmap -sV -sC -p $(grep "open" phase2-ports.gnmap | cut -d: -f2 | cut -d/ -f1 | paste -sd,) -iL live-ips.txt -oA phase3-services;

# Phase 4: OS detection
sudo nmap -O --osscan-guess -iL live-ips.txt -oN phase4-os.txt;

# Phase 5: Full sweep of a specific host
sudo nmap -sS -sU -sV -O -p- --script default,safe 10.0.0.42 -oA target-full;
