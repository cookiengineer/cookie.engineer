Tholian Core

Open Type System and Network Protocol Schemas

Overview

GitHub Repository | GitLab Mirror

Every security toolchain eventually grows a private dialect for an IP address. Tholian Core exists so the agents in the Tholian Network do not. It is the open type system and wire contract. One canonical string for an address, one JSON format for a system report, and one packet envelope for remote actions.

It is built for blue teams, platform engineers, and integrators who need to move data between agents and third-party SIEM or SOAR stacks without rewriting a parser for every collector.

Tholian Scout writes a System report, Tholian Firewall consumes network matchers, and the Guard and Watchtower components exchange incidents, responses, and capability tokens. They all agree on the same values because the values are defined once.

The module is deliberately small and standard-library-first. It contains canonical value types, nested data structures, selector matchers, concurrency-safe caches, distribution parsers, the filesystem layout for the Tholian Insights database, and the versioned RPC packet schema used by the agent stack. It is a canonical contract between multiple agents.

The schema definitions are published under the MIT license, while the Go implementation is licensed separately. The canonical JSON formats are designed to become standalone JSON Schema Draft 2020-12 definitions, so consumers will not need a Go toolchain to interpret Tholian data.

Features

  • Defines canonical value types plus the Map and SliceMap containers.
  • Ships nested data structures for systems, packages, incidents, responses, vulnerabilities, and more.
  • Provides selector matchers with any wildcards and range semantics.
  • Includes concurrency-safe caches with JSON marshalling and deterministic query indexes.
  • Keeps simple values as canonical JSON strings and structured values as documented JSON objects.
  • Validates ranges, prefixes, labels, protocol names, and canonical string forms at the parse boundary.
  • Derives deterministic hashes for deduplication, cache keys, and filesystem record names.
  • Parses distribution metadata for all supported Linux and BSD distributions.
  • Provides OVAL schema structs for vulnerability and assessment data.
  • Defines a versioned RPC packet schema with request, response, event, and error types.
  • Authenticates agents with TLS and Ed25519 challenge-response handshakes.
  • Issues short-lived capability tokens with per-system, purpose-bound, time-bounded, and scope-limited grants.
  • Targets JSON Schema Draft 2020-12 for the wire contract, with semantic versioning.
  • Depends only on the standard library and x/term for terminal handling.

Architecture

Layer Package Implementations
canonical values types IPv4, IPv6, ASN, Domain, Socket, Connection, Version
nested records structs System, Package, Incident, Vulnerability, Network
selectors matchers Package, Connection, Network, Incident, Datetime
indexes caches Packages, Incidents, Networks, Vulnerabilities
wire contract protocols Packet, methods, parameters, results, permissions
storage insights Cache, Database, generated embeds

The layers are intentionally one-directional. Types know nothing about structs, structs know nothing about caches, and the RPC contract builds on the same values that the agents put in their reports. That keeps a connection string in an incident identical to the connection string in a firewall rule.

Canonical Wire Format

A network with one subnet is encoded as:

{
  "name": "AS13335",
  "subnets": [
    {
      "name": "Cloudflare",
      "country": "US",
      "address": "1.1.1.0",
      "scope": "public",
      "type": "ipv4",
      "prefix": 24
    }
  ]
}

The exact string forms are part of the API contract:

  • IPv6 addresses expand to eight lowercase groups.
  • Sockets use host:port or *:port.
  • Subnets use address/prefix.
  • Domains use sub.domain.tld without a trailing dot.
  • Connections use [protocol] source <direction> target.
  • Groups use name:type:id:password.
  • Users use name:type:id:folder:shell:password:groups.
  • and so on...

Selectors and Caches

Matchers are the query language of the type system. String selectors initialize to any, numeric selectors such as Port initialize to 0, and most Set* methods normalize all, *, and any to the wildcard value.

A matcher exposes Matches(...) or individual Matches* methods, so a controller can ask whether a package, connection, network, incident, or datetime range fits a rule without knowing which agent produced the record.

Caches are the in-memory indexes built from those records. They are concurrency-safe, marshal to JSON, and provide Add, Length, Remove, Query, and QueryBy* methods. Incidents, responses, and mitigations can share one network index instead of duplicating subnet data per record. Deterministic hashes make records stable across runs, which matters when the same finding is reported twice or when a record is used as a filesystem key.

Tholian Network Protocol

The protocols/tholian package defines the shared wire contract for all Agents in the network. It uses WebSocket version 13 over TLS 1.2 or newer, encodes JSON text frames, and negotiates permessage-deflate for large system reports. The subprotocol name is tholian-rpc.v1 and the packet version is 1.

A request looks like this:

{
  "version": "1",
  "id": "req-1337",
  "type": "request",
  "method": "tholian-firewall.Forbid",
  "parameters": {
    "system": "3f2a9c",
    "target": "1.3.3.7"
  }
}

Requests use parameters, responses use result, and errors use a stable error object with a code message depending on the type. Events use parameters as well.

Method names are project-scoped as <module>.<ExportedActionName>. The catalog covers tholian-core.*, tholian-firewall.*, tholian-scout.*, tholian-guard.*, and tholian-watchtower.*.

Typed parameter and result structs live next to the method catalog under protocols/tholian/parameters and protocols/tholian/results, so a client does not need to guess the data format of a call.

Authentication and Grants

A connection starts with tholian-core.Challenge.

The client answers with tholian-core.Hello, which carries its role, ID, Ed25519 public key, a signature over tholian-hello-v1:<nonce>:<id>, an optional one-time enrollment token, and the protocol version.

The server verifies the token or the registered public key and replies with tholian-core.Welcome, including its own public key and a signature over tholian-welcome-v1:<nonce>:<id>.

Capabilities are project-scoped strings. Firewall grants use tholian-firewall.read, tholian-firewall.write, and tholian-firewall.install; Scout and Guard have equivalent read, write, and install capabilities.

Watchtower issues short-lived Ed25519-signed capability tokens for each forwarded call. A token binds the issuer, subject, system, method, parameters hash, purpose, grant, expiry, and a replay nonce.

Grants are per system, time-bounded, use-limited, and optionally scope-limited with the same core matchers that appear in incident records.

Schema Publication

The canonical JSON forms are designed to be published as standalone JSON Schema Draft 2020-12 definitions under schemas/. The schema files are being prepared for public consumption. Until they ship, the Go implementations and their unit tests are the reference for the wire format.

Once available, the schemas follow semantic versioning:

  • Patch releases clarify descriptions or examples without changing validation.
  • Minor releases add optional fields or new type definitions.
  • Major releases may change canonical string forms or required fields.

Threat Intelligence Insights Database

source/insights contains the filesystem layout and generators used by the separate Tholian Insights repository. It is split into a small folder-scoped Cache helper and a Database that manages the canonical layout:

countries/               devices/                distributions/
networks/                providers/              proxies/
timeslots/               weaknesses/             credentials/embedded/
incidents/embedded/      mitigations/embedded/   products/embedded/
responses/embedded/      vulnerabilities/embedded/

Cache-backed types such as countries, devices, distributions, networks, providers, proxies, timeslots, and weaknesses are held in memory and written by Flush(). Flushing writes both Type.json and Type.json.gz and generates the corresponding Go cache package.

File-backed types such as credentials, incidents, mitigations, products, responses, and vulnerabilities persist one record per file, keyed by Name or by the sorted Hash.

Writes are deterministic. Nested collections are sorted by their Hash() before serialization, so regenerating the same data produces line-by-line identical JSON. Generated cache packages use the scout, guard, and oversight build tags, with distribution-aware variants for the types that support them.

Incident Types

The type system defines six incident types that agents can report:

Type Meaning
Recon Probes, scans, failed logins, and exposed listeners
Intel Threat intelligence and vulnerability context
Conquer Successful access or a change of control
Persist Persistence mechanisms and persistence-shaped events
Exfil Active exfiltration, remote access, or backdoor traffic
Destroy Destructive activity, injected code, and tampered executables

The records themselves carry matchers for connections, distributions, networks, packages, products, programs, users, vulnerabilities, and weaknesses. That is what makes an incident portable. Another tool can match against the same fields without knowing which collector produced the finding.

Testing

The module source has no build tags. Generated Insights cache files do use build tags, but they are produced at runtime and are not part of the checked-in module.

cd /path/to/tholian-network/core;

# full suite: source tests and distribution end-to-end tests
make test;

# or run the suites individually
go -C source test ./...;
go -C source test -race ./insights/...;
go -C source vet ./...;
go -C e2e-tests test ./...;

The end-to-end suite exercises the distribution parsers against real release metadata for AlmaLinux, Alpine Linux, Amazon Linux, Antergos, Arch Linux, CBL-Mariner, CentOS, Debian, Fedora, FreeBSD, Gentoo Linux, Linux Mint, Manjaro, NetBSD, openSUSE, OpenWrt, Oracle Linux, Photon OS, Red Hat, Rocky Linux, SUSE, Trisquel, and Ubuntu.

Usage: Go Module

The module is consumed through Go's module system. In the Tholian Network, repositories are checked out next to each other and referenced with a local replacement:

/path/to/Software/tholian-network/
\- core/
   \- source/
						
module example

go 1.27.1

require tholian-core v0.0.0

replace tholian-core => ../../core/source

The following example builds a network and parses a connection string. Both values marshal to their canonical JSON forms.

package main

import "encoding/json"
import "fmt"
import "tholian-core/structs"
import "tholian-core/types"

func main() {

	network := structs.NewNetwork("AS13335")
	network.AddSubnet(structs.NewSubnet("1.1.1.0", 24))

	connection := types.ParseConnection("[tcp] 1.3.3.7:1338 -> 1.3.3.7:443")

	payload := struct {
		Network    structs.Network   `json:"network"`
		Connection *types.Connection `json:"connection"`
	}{
		Network:    network,
		Connection: connection,
	}

	blob, err := json.Marshal(payload)

	if err == nil {
		fmt.Println(string(blob))
	}

}

Usage: JSON Integration

An incident record is the best example of the shared format. It combines a system identity, an incident type, a timestamp, and matcher collections:

{
  "system": "3f2a9c",
  "type": "Exfil",
  "datetime": "2026-11-16 12:00:00",
  "connections": [
    {
      "host": "1.3.3.7",
      "port": 443,
      "protocol": "tcp",
      "type": "client"
    }
  ],
  "programs": [
    {
      "name": "curl",
      "command": "/usr/bin/curl",
      "arguments": ["-x", "socks5://127.0.0.1:1080", "https://example.com"]
    }
  ],
  "evidence": [
    {
      "type": "application/json",
      "datetime": "2026-11-16 12:00:00",
      "data": "e30="
    }
  ]
}

The field names are documented and stable. The values are canonical strings where a canonical form exists, and structured objects where the field is a matcher or a nested record. Evidence data is base64-encoded in JSON, so a pipeline can store packet captures, text, or arbitrary recordings without inventing a second envelope.

Usage: Elastic and Kibana

The preferred mapping strategy is to keep the canonical value intact and use a native field type where one exists:

Tholian value Suggested Elasticsearch and Kibana field type
IPv4 and IPv6 address ip
Subnet keyword, or ip with a CIDR-aware pipeline
ASN keyword
Domain keyword
Socket keyword
Connection keyword
Protocol keyword
Architecture keyword
Time and Datetime date or keyword depending on precision

A representative payload for an ingest pipeline looks like this:

{
  "connection": "[tcp] 1.3.3.7:1338 -> 1.3.3.7:443",
  "source": "1.3.3.7:1338",
  "target": "1.3.3.7:443",
  "subnet": "1.3.3.0/24",
  "asn": "AS1337",
  "domain": "example.com",
  "datetime": "2026-10-19 11:59:59"
}

External consumers should preserve the original canonical string alongside any normalized field. That keeps the source value available for auditing and avoids losing information when a downstream index uses a different representation. The mapping above is guidance for integrators; a dedicated ECS mapping will only be documented once it is actually published and tested.

Usage: RPC Protocol

A client builds a request with tholian.NewRequest, encodes it with Packet.Bytes, and decodes the reply with tholian.Parse and the typed parameter and result helpers. The method constants live in protocols/tholian/methods.

package main

import "tholian-core/protocols/tholian"
import "tholian-core/protocols/tholian/methods"
import firewall_parameters "tholian-core/protocols/tholian/parameters/firewall"

func NewForbidRequest() (tholian.Packet, error) {

	return tholian.NewRequest(
		"req-1337",
		methods.FirewallForbid,
		firewall_parameters.Forbid{
			System: "3f2a9c",
			Target: "1.3.3.7",
		},
	)

}

On the receiving side, tholian.Parse validates the envelope and tholian.DecodeParameters unmarshals the typed payload:

func HandleRequest(buffer []byte) {

	incoming := tholian.Parse(buffer)

	if incoming.IsRequest() && incoming.Method == methods.FirewallForbid {

		parameters, err := tholian.DecodeParameters[firewall_parameters.Forbid](incoming)

		if err == nil {
			// parameters.System and parameters.Target are now typed
		}

	}

}

A real client also performs the TLS and Ed25519 handshake and carries a capability token in the packet metadata. The token is verified against the system binding, method, parameters hash, scope, expiry, and replay cache before a guard executes the action.
