Linux Assembly Part 6: Shellcoding

Learn Linux assembly to write shellcode and spawn a shell.

Overview

This is the sixth article of the Linux Assembly series, the previous article described the Linux Assembly Part 5: Addressing . This time, we finally put everything together and write our first piece of shellcode: a tiny, self-contained blob of machine code that spawns a shell. This is the point where the articles connect back to the binary exploitation topics that I mentioned at the beginning of the series.

The execve Syscall

In order to spawn a shell, we need the execve() syscall, which replaces the current process image with a new program. On amd64 Linux, that is syscall number 59 , and its signature looks like this:

int execve(const char *pathname, char *const argv[], char *const envp[]);

Following the calling convention from Linux Assembly Part 1 about Syscalls , we can translate the signature into the registers we need to set up before the syscall :

  • rax must contain the syscall number 59 .
  • rdi must contain the pathname , a pointer to the executable we want to run.
  • rsi must contain the argv array, a pointer to an array of argument strings.
  • rdx must contain the envp array, a pointer to an array of environment strings.

On Linux, both argv and envp may be NULL , in which case the kernel treats them as empty. That makes our life a lot easier, because we don't have to construct a proper argument vector just to spawn a shell.

A First Shell Program

As a starting point, we write a program that spawns /bin/sh in the same way we wrote our previous programs. We store the path in the .data section and reference it by its label:

section .data
    shell: db "/bin/sh", 0

section .text
    global _start

_start:
    mov rax, 59      ; syscall 59 = execve
    mov rdi, shell   ; path to the executable
    mov rsi, 0       ; argv = NULL
    mov rdx, 0       ; envp = NULL
    syscall

The shell program can also be downloaded from here . If we compile and run our program, it spawns a shell:

nasm -f elf64 -o shell.o shell.asm;
ld -o shell.bin shell.o;
chmod +x shell.bin;

./shell.bin;

This works, but it is not yet shellcode. Shellcode is not a normal executable that the operating system loads for us. It is a raw blob of machine code that is injected into an already running program, for example through a buffer overflow. That imposes two additional constraints on the code that our .data -based program does not satisfy.

What Shellcode Must Be

The first constraint is about null bytes. Shellcode is usually delivered through functions that process strings, like strcpy() or gets() . Those functions stop as soon as they hit a 0x00 byte, because that is the string terminator in the C ABI . If our shellcode contains a single null byte in the middle, everything after it gets truncated and the injection fails.

Let's look at our first program under a microscope. The mov rax, 59 instruction is encoded with a 32 bit immediate, so its machine code contains several null bytes:

48 b8 3b 00 00 00 00 00 00 00   mov rax, 59

The mov rsi, 0 and mov rdx, 0 instructions contain null bytes for the same reason. We need to rewrite every instruction so that no null byte appears anywhere in the final machine code.

The second constraint is about position independence. When our code is injected into another program, we have no idea at which address it will end up, and we certainly cannot rely on the .data section being present or at a known location. All data must therefore live either in registers or on the stack.

Null-Free Shellcode

Let's solve both constraints step by step. First, the string. Instead of storing /bin/sh in the .data section, we push it onto the stack. The stack is at a known position relative to rsp , so we can always find our string through the stack pointer.

xor rsi, rsi                  ; rsi = 0
push rsi                      ; push the null terminator
mov rbx, 0x68732f2f6e69622f  ; "/bin//sh" in little endian
push rbx                      ; push the string onto the stack
mov rdi, rsp                  ; rdi points to "/bin//sh"

We use /bin//sh instead of /bin/sh , because the double slash is harmless (the kernel resolves the path exactly the same way) and it pads the string to exactly 8 bytes, so it fits into a single 64 bit immediate with no null bytes. The null terminator comes from the push rsi before it, because we zeroed rsi first.

Next, the argument and environment pointers. Instead of mov rsi, 0 and mov rdx, 0 , we use xor which never produces null bytes:

xor rdx, rdx                  ; rdx = 0 (envp)
push rdx                      ; NULL terminator for argv
push rdi                      ; argv[0] = pointer to "/bin//sh"
mov rsi, rsp                  ; rsi points to the argv array

Finally, the syscall number. Instead of mov rax, 59 with its null-padded immediate, we push the value and pop it into rax :

push 59                       ; syscall 59 = execve
pop rax
syscall

Putting it all together gives us our first piece of real shellcode:

section .text
    global _start

_start:
    xor rsi, rsi                  ; rsi = NULL
    push rsi                      ; null terminator for the string
    mov rbx, 0x68732f2f6e69622f  ; "/bin//sh"
    push rbx                      ; push the string onto the stack
    mov rdi, rsp                  ; rdi = pointer to "/bin//sh"

    xor rdx, rdx                  ; rdx = NULL (envp)
    push rdx                      ; NULL terminator for argv
    push rdi                      ; argv[0] = pointer to "/bin//sh"
    mov rsi, rsp                  ; rsi = pointer to the argv array

    push 59                       ; syscall 59 = execve
    pop rax
    syscall

The null-free shellcode can also be downloaded from here . If we compile and run it, it spawns a shell just like the first program, but this time the code is self-contained and can run anywhere:

nasm -f elf64 -o shellcode.o shellcode.asm;
ld -o shellcode.bin shellcode.o;
chmod +x shellcode.bin;

./shellcode.bin;

Extracting the Shellcode

The raw machine code of our shellcode is the .text section of the assembled object file. We can extract it with objcopy and inspect it with xxd :

objcopy -O binary --only-section=.text shellcode.o shellcode.bin;
xxd -i shellcode.bin;

The output is the final shellcode, a 31 byte array that does not contain a single null byte:

unsigned char shellcode[] = {
  0x48, 0x31, 0xf6, 0x56, 0x48, 0xbb, 0x2f, 0x62, 0x69, 0x6e, 0x2f, 0x2f,
  0x73, 0x68, 0x53, 0x48, 0x89, 0xe7, 0x48, 0x31, 0xd2, 0x52, 0x57, 0x48,
  0x89, 0xe6, 0x6a, 0x3b, 0x58, 0x0f, 0x05
};

That is exactly what a real exploit would inject into a vulnerable program.

Running Shellcode from C

To verify that the shellcode works in a more realistic scenario, we embed it in a C program and jump to it through a function pointer:

#include <stdio.h>

int main() {
    unsigned char shellcode[] =
        "\x48\x31\xf6\x56\x48\xbb\x2f\x62\x69\x6e\x2f\x2f\x73\x68\x53"
        "\x48\x89\xe7\x48\x31\xd2\x52\x57\x48\x89\xe6\x6a\x3b\x58\x0f\x05";

    void (*run)() = (void (*)()) shellcode;
    run();

    return 0;
}

Modern systems mark memory as non-executable ( NX ), so we have to tell the compiler to make the stack executable with the -z execstack flag. We also place the shellcode in a local array so that it lives on the stack and is covered by that flag:

gcc -z execstack -fno-stack-protector -o loader loader.c;
./loader;

The NX bit is one of the main mitigations that modern exploits have to deal with, which is why so many of them chain a mprotect() call before jumping to the shellcode. We are going to learn more about those mitigations and how to deal with them in the upcoming articles.
