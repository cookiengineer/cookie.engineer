PE (Portable Executable)

The Windows Portable Executable format: its headers, sections, import and export tables, and how the loader maps it into memory.

Overview

PE (Portable Executable) is the executable and object format of Windows. It evolved from the Unix COFF format, and unlike ELF the loader works from a section table rather than program headers, resolving external symbols through dedicated import and export tables. This article walks the DOS header, the COFF and Optional headers, the section table, the data directory, imports, exports, relocations, and the loader sequence. After reading you can inspect a Windows binary with objdump or pev and write your own parser.

Required Reading

  • ELF - the Linux binary format and its program headers
  • Dynamic Linking - GOT, PLT, and symbol resolution

The Windows Executable Format

PE (Portable Executable) is the binary format for Windows executables (.exe) and dynamic-link libraries (.dll). Despite its name, PE is not portable - it is specific to Windows NT and its derivatives (Windows 10, 11, ReactOS, Wine).

PE evolved from the COFF format used in Unix System V and was formalized for Windows NT 3.1 in 1993. The key difference from ELF is that PE is section-based , not segment-based - the loader works through sections directly rather than through program headers.

PE File Layout at a Glance

A PE file, from start to end:

+---------------------------+  Offset 0x000
|        DOS Header         |  (64 bytes, starts with "MZ")
+---------------------------+
|        DOS Stub           |  (variable, "This program cannot be run in DOS mode")
+---------------------------+  Offset 0x03C → PE signature offset (e_lfanew)
|      PE Signature         |  (4 bytes: "PE\0\0")
+---------------------------+
|      COFF File Header     |  (20 bytes: machine, sections count, timestamp, ...)
+---------------------------+
|      Optional Header      |  (240 bytes for PE32+: entry point, image base, ...)
+---------------------------+
|      Section Table        |  (array of IMAGE_SECTION_HEADER, one per section)
+---------------------------+
|      Section 1 Data       |  (.text — code)
+---------------------------+
|      Section 2 Data       |  (.rdata — read-only data, imports, exports)
+---------------------------+
|      Section 3 Data       |  (.data — writable data)
+---------------------------+
|      ...                  |  (.rsrc, .reloc, .pdata, ...)
+---------------------------+

Identity check:

$ file /usr/x86_64-w64-mingw32/bin/myprogram.exe
myprogram.exe: PE32+ executable (console) x86-64, for MS Windows

Or using objdump:

$ objdump -f myprogram.exe
myprogram.exe:     file format pei-x86-64
architecture: i386:x86-64, flags 0x0000012f:
HAS_RELOC, EXEC_P, HAS_LINENO, HAS_DEBUG, HAS_LOCALS, D_PAGED
start address 0x00000001400013c0

DOS Header - The "MZ" Legacy

Every PE file begins with a DOS (MS-DOS) header. This is historical - PE files are valid MS-DOS executables that print a message and exit when run under DOS: 

typedef struct _IMAGE_DOS_HEADER {
    uint16_t e_magic;        // "MZ" (0x5A4D) — Mark Zbikowski's initials
    uint16_t e_cblp;         // Bytes on last page of file
    uint16_t e_cp;           // Pages in file
    uint16_t e_crlc;         // Relocations
    uint16_t e_cparhdr;      // Size of header in paragraphs
    uint16_t e_minalloc;     // Minimum extra paragraphs
    uint16_t e_maxalloc;     // Maximum extra paragraphs
    uint16_t e_ss;           // Initial SS value (relative)
    uint16_t e_sp;           // Initial SP value
    uint16_t e_csum;         // Checksum
    uint16_t e_ip;           // Initial IP value
    uint16_t e_cs;           // Initial CS value (relative)
    uint16_t e_lfarlc;       // File address of relocation table
    uint16_t e_ovno;         // Overlay number
    uint16_t e_res[4];       // Reserved
    uint16_t e_oemid;        // OEM identifier
    uint16_t e_oeminfo;      // OEM information
    uint16_t e_res2[10];     // Reserved
    uint32_t e_lfanew;       // Offset to PE signature (at offset 0x3C)
} IMAGE_DOS_HEADER;

Only two fields matter:

  • e_magic (0x5A4D) - "MZ" identifies the file
  • e_lfanew (at offset 0x3C) - file offset of the PE signature ("PE\0\0")
$ hd -n 64 myprogram.exe
00000000  4d 5a 90 00 03 00 00 00  04 00 00 00 ff ff 00 00  |MZ..............|
00000010  b8 00 00 00 00 00 00 00  40 00 00 00 00 00 00 00  |........@.......|
00000020  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
00000030  00 00 00 00 00 00 00 00  00 00 00 00 80 00 00 00  |................|

At offset 0x3C, e_lfanew = 0x00000080 - the PE signature is at file offset 0x80.

DOS Stub

Immediately after the DOS header is the DOS stub - a tiny 16-bit MS-DOS program. It usually prints "This program cannot be run in DOS mode" and exits: 

$ strings -n 5 myprogram.exe | head
!This program cannot be run in DOS mode.

The stub is 64 bytes in typical MSVC output, padded to align the PE signature to an 8-byte boundary:

; Typical DOS stub (16-bit x86):
    mov    ah, 9
    mov    dx, 0x008e    ; "This program cannot be run in DOS mode$\r\n"
    int    0x21          ; DOS print string
    mov    ax, 0x4c01    ; Exit with code 1
    int    0x21          ; DOS exit

PE Signature and COFF File Header

At e_lfanew , the PE signature is "PE\0\0" ( 0x00004550 ). Directly after it comes the COFF File Header: 

typedef struct _IMAGE_FILE_HEADER {
    uint16_t Machine;              // Target CPU
    uint16_t NumberOfSections;     // Count of section headers
    uint32_t TimeDateStamp;        // Build timestamp (Unix epoch)
    uint32_t PointerToSymbolTable; // Deprecated (debug)
    uint32_t NumberOfSymbols;      // Deprecated (debug)
    uint16_t SizeOfOptionalHeader; // Size of the optional header (varies)
    uint16_t Characteristics;      // Flags describing the file
} IMAGE_FILE_HEADER;

Machine field - target architecture

0x0200 IA-64 (Itanium)
0x8664 x86-64 (AMD64)
0xAA64 ARM64 (AArch64)

0x0100 IMAGE_FILE_32BIT_MACHINE 32-bit word architecture

0x2000 IMAGE_FILE_DLL This is a DLL

The Optional Header

Despite its name, the Optional Header is mandatory for executables. It comes in two sizes: PE32 (for 32-bit, 224 bytes) and PE32+ (for 64-bit, 240 bytes): 

typedef struct _IMAGE_OPTIONAL_HEADER64 {
    // Standard fields
    uint16_t Magic;                     // 0x020B = PE32+
    uint8_t  MajorLinkerVersion;
    uint8_t  MinorLinkerVersion;
    uint32_t SizeOfCode;                // Sum of all code sections
    uint32_t SizeOfInitializedData;
    uint32_t SizeOfUninitializedData;
    uint32_t AddressOfEntryPoint;       // RVA of entry point
    uint32_t BaseOfCode;                // RVA of start of code section

    // NT-specific fields
    uint64_t ImageBase;                 // Preferred load address
    uint32_t SectionAlignment;          // Alignment of sections in memory
    uint32_t FileAlignment;             // Alignment of raw data in file
    uint16_t MajorOperatingSystemVersion;
    uint16_t MinorOperatingSystemVersion;
    uint16_t MajorImageVersion;
    uint16_t MinorImageVersion;
    uint16_t MajorSubsystemVersion;
    uint16_t MinorSubsystemVersion;
    uint32_t Win32VersionValue;         // Reserved (0)
    uint32_t SizeOfImage;               // Total size of image (all sections + headers)
    uint32_t SizeOfHeaders;             // Size of all headers + section table (file-aligned)
    uint32_t CheckSum;                  // CRC checksum (drivers require valid checksum)
    uint16_t Subsystem;                 // GUI:2, CUI:3
    uint16_t DllCharacteristics;        // Security flags (ASLR, DEP, ...)
    uint64_t SizeOfStackReserve;        // Stack size to reserve
    uint64_t SizeOfStackCommit;         // Stack size to initially commit
    uint64_t SizeOfHeapReserve;         // Heap size to reserve
    uint64_t SizeOfHeapCommit;          // Heap size to initially commit
    uint32_t LoaderFlags;               // Obsolete
    uint32_t NumberOfRvaAndSizes;       // Number of Data Directory entries

    // Data Directory (array of IMAGE_DATA_DIRECTORY[16])
    IMAGE_DATA_DIRECTORY DataDirectory[16];
} IMAGE_OPTIONAL_HEADER64;

Key fields

Field Purpose
AddressOfEntryPoint RVA where execution begins (added to ImageBase for VA)

SectionAlignment Must be >= page size (typically 0x1000 = 4 KB)

Subsystem GUI (2) or Console (3) - tells Windows whether to allocate a console
SizeOfStackReserve Virtual memory reserved for the main thread's stack (default 1 MB)

Subsystem values:

0x01 IMAGE_SUBSYSTEM_NATIVE (device drivers)
0x02 IMAGE_SUBSYSTEM_WINDOWS_GUI
0x03 IMAGE_SUBSYSTEM_WINDOWS_CUI (console)

DLL characteristics - security flags:

Value Flag Meaning
0x0040 IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE ASLR enabled (image can load anywhere)
0x0100 IMAGE_DLLCHARACTERISTICS_NX_COMPAT DEP enabled (no execute on data pages)
0x0020 IMAGE_DLLCHARACTERISTICS_HIGH_ENTROPY_VA 64-bit ASLR (full address space)

RVA - Relative Virtual Address

Central to PE is the concept of RVA (Relative Virtual Address). An RVA is an offset from the ImageBase - the virtual address at which the PE file is loaded into memory. The actual virtual address (VA) is ImageBase + RVA .

When the PE is loaded at an address different from ImageBase (because of ASLR), all RVAs remain valid - they are offsets within the image. Only absolute addresses in the image need relocation fixups.

Mapping a file offset to an RVA requires walking the section table:

def rva_to_offset(sections, rva):
    for sec in sections:
        if sec.VirtualAddress <= rva < sec.VirtualAddress + sec.VirtualSize:
            return rva - sec.VirtualAddress + sec.PointerToRawData
    return None

Section Table

Each section (what ELF calls "segments" for loading) has a header:

typedef struct _IMAGE_SECTION_HEADER {
    uint8_t  Name[8];               // Section name (padded with nulls, max 8 chars)
    union {
        uint32_t PhysicalAddress;
        uint32_t VirtualSize;       // Size of section in memory
    } Misc;
    uint32_t VirtualAddress;        // RVA of section in memory
    uint32_t SizeOfRawData;         // Size of section data in file
    uint32_t PointerToRawData;      // File offset of section data
    uint32_t PointerToRelocations;  // File offset of relocations (obj files only)
    uint32_t PointerToLinenumbers;  // File offset of line numbers (debug)
    uint16_t NumberOfRelocations;   // Relocation count
    uint16_t NumberOfLinenumbers;   // Line number count
    uint32_t Characteristics;       // Flags: code/data/readable/writable/executable
} IMAGE_SECTION_HEADER;

Standard PE sections

Section Characteristics Contents
.text 0x60000020 (CODE + EXECUTE + READ) Executable code
.rdata 0x40000040 (INITIALIZED_DATA + READ) Read-only data, import/export tables, debug info
.data 0xC0000040 (INITIALIZED_DATA + READ + WRITE) Initialized global/static data
.rsrc 0x40000040 (INITIALIZED_DATA + READ) Resources (icons, dialogs, manifests, version info)
.reloc 0x42000040 (INITIALIZED_DATA + READ + DISCARDABLE) Base relocations
.pdata 0x40000040 (INITIALIZED_DATA + READ) Exception handling data (x86-64)

Import Table and IAT

When a PE imports a function (e.g., CreateFileW from kernel32.dll ), the import mechanism works through three structures:

1. IMAGE_IMPORT_DESCRIPTOR - one per imported DLL : 

typedef struct _IMAGE_IMPORT_DESCRIPTOR {
    uint32_t OriginalFirstThunk;  // RVA to Import Name Table (INT)
    uint32_t TimeDateStamp;       // Bound imports timestamp (0 if not bound)
    uint32_t ForwarderChain;      // Forwarder chain index
    uint32_t Name;                // RVA to DLL name string
    uint32_t FirstThunk;          // RVA to Import Address Table (IAT)
} IMAGE_IMPORT_DESCRIPTOR;

2. Import Name Table (INT) - array of RVAs to IMAGE_IMPORT_BY_NAME entries, terminated by NULL. During load, the loader reads each name, finds the function in the DLL , and writes its address into the corresponding IAT slot.

3. Import Address Table (IAT) - array of function pointers. Before loading, it mirrors the INT (or the bound address). After loading, it contains the resolved addresses.

The resolve flow:

INT[n] → RVA → IMAGE_IMPORT_BY_NAME { Hint, "FunctionName" }
                                          ↓
Loader: GetProcAddress(DLL, "FunctionName") → 64-bit address
                                          ↓
IAT[n] = resolved_address

Code: CALL [IAT + n]   ← Indirect call through IAT

Export Table - How PE Exposes Functions

DLL s export functions so other modules can import them. The Export Directory maps function names (or ordinals) to RVAs: 

typedef struct _IMAGE_EXPORT_DIRECTORY {
    uint32_t Characteristics;       // Unused
    uint32_t TimeDateStamp;
    uint16_t MajorVersion;
    uint16_t MinorVersion;
    uint32_t Name;                  // RVA to DLL name
    uint32_t Base;                  // Starting ordinal number
    uint32_t NumberOfFunctions;     // Total exported functions
    uint32_t NumberOfNames;         // Number of functions exported by name
    uint32_t AddressOfFunctions;    // RVA to Export Address Table (EAT)
    uint32_t AddressOfNames;        // RVA to array of function name RVAs
    uint32_t AddressOfNameOrdinals; // RVA to array of ordinal indices
} IMAGE_EXPORT_DIRECTORY;

Finding an exported function by name:

1. Binary search AddressOfNames array for "FunctionName"
2. Get index i from the name array
3. Read ordinal = AddressOfNameOrdinals[i] + Base
4. Read function_RVA = AddressOfFunctions[ordinal - Base]
5. Function_VA = ImageBase + function_RVA

Base Relocations

When ASLR loads the PE at an address different from ImageBase, absolute addresses in the image must be fixed. The .reloc section contains fixup entries: 

typedef struct _IMAGE_BASE_RELOCATION {
    uint32_t VirtualAddress;    // RVA of page to fix
    uint32_t SizeOfBlock;       // Total block size including this header
    // Followed by SizeOfBlock - 8 bytes of fixup entries:
    // uint16_t fixup[SizeOfBlock - 8];
    // Each: high 4 bits = type, low 12 bits = offset from VirtualAddress
} IMAGE_BASE_RELOCATION;

Relocation types:

Type Value Meaning
IMAGE_REL_BASED_ABSOLUTE 0 Padding (no fixup)
IMAGE_REL_BASED_HIGHLOW 3 Full 32-bit address (x86)
IMAGE_REL_BASED_DIR64 10 Full 64-bit address (x86-64)

Fixup calculation:

*((uint64_t*)(ImageBase + block->VirtualAddress + offset)) += (actual_base - ImageBase)

Digital Signatures (Authenticode)

PE supports embedded digital signatures in the Security Directory (Data Directory index 4). The structure is PKCS#7 (RFC 2315), embedding X.509 certificate chains that chain to a Microsoft-trusted root CA . The signature covers the entire file except the certificates themselves and the checksum field. 

$ osslsigncode verify myprogram.exe
Current PE checksum   : 00000000
Calculated PE checksum: 0001A2B4
Signature verification: ok
Signer #0:
    Subject: /C=US/ST=Washington/L=Redmond/O=Microsoft Corporation/CN=Microsoft Corporation
    Serial : 33000000...

The Authenticode signature verification process hashes the entire file, verifying no byte has been tampered with - a far stronger guarantee than ELF's GNU build ID.

PE Loading - The Windows Loader Sequence

When CreateProcess() is called: 

1. Kernel opens the .exe file, creates a section object (file mapping)
2. Checks subsystem: GUI vs CUI → allocates console if needed
3. Maps the PE into memory at ImageBase (or another base if ASLR)
4. Walks the section table, maps each section:
   - Creates memory region for section
   - Copies raw data (SizeOfRawData) from file
   - Zero-fills remaining (VirtualSize - SizeOfRawData)
   - Applies page protections from Characteristics
5. Resolves imports:
   - For each IMAGE_IMPORT_DESCRIPTOR, loads the DLL
   - Walks the IAT, calls GetProcAddress for each entry
   - Writes resolved addresses into IAT
6. Applies base relocations (if actual base ≠ ImageBase)
7. Processes TLS callbacks (Thread-Local Storage initialization)
8. Creates the main thread, sets RIP = ImageBase + AddressOfEntryPoint
9. Resumes the thread

PE Parser in Python

A cross-platform PE parser that reads headers and enumerates imports:

#!/usr/bin/env python3
"""Minimal PE parser — reads COFF header, optional header, and imports."""
import struct
import sys

def pe_parse(path):
    with open(path, 'rb') as f:
        # DOS header
        dos_hdr = f.read(64)
        if dos_hdr[:2] != b'MZ':
            print("Not a PE file")
            return
        e_lfanew = struct.unpack_from('<I', dos_hdr, 0x3C)[0]

        # PE signature + COFF header
        f.seek(e_lfanew)
        sig = f.read(4)
        if sig != b'PE\0\0':
            print("PE signature not found")
            return

        coff = f.read(20)
        machine, nsections, timestamp, symtab, nsyms, optsize, chars = \
            struct.unpack('<HHIIIHH', coff)

        MACHINE = {0x14C: 'x86', 0x8664: 'x86-64', 0xAA64: 'ARM64'}
        print(f"Machine:   {MACHINE.get(machine, hex(machine))}")
        print(f"Sections:  {nsections}")
        print(f"Timestamp: {timestamp}")
        print(f"Chars:     {hex(chars)}")

        # Optional header
        opt = f.read(optsize)
        magic = struct.unpack_from('<H', opt, 0)[0]
        is_pe32plus = (magic == 0x020B)
        print(f"PE32{'+' if is_pe32plus else ''} (magic {hex(magic)})")

        if is_pe32plus:
            entry_rva = struct.unpack_from('<I', opt, 16)[0]
            image_base = struct.unpack_from('<Q', opt, 24)[0]
            subsystem = struct.unpack_from('<H', opt, 68)[0]
            dll_chars = struct.unpack_from('<H', opt, 70)[0]
        else:
            entry_rva = struct.unpack_from('<I', opt, 16)[0]
            image_base = struct.unpack_from('<I', opt, 28)[0]
            subsystem = struct.unpack_from('<H', opt, 68)[0]
            dll_chars = struct.unpack_from('<H', opt, 70)[0]

        SUBSYS = {2: 'GUI', 3: 'CUI', 1: 'NATIVE'}
        print(f"Entry RVA: {hex(entry_rva)}")
        print(f"VA:        {hex(image_base + entry_rva)}")
        print(f"Subsystem: {SUBSYS.get(subsystem, str(subsystem))}")
        print(f"DLL Chars: {hex(dll_chars)}")
        if dll_chars & 0x0040: print("  ASLR (DYNAMIC_BASE)")
        if dll_chars & 0x0100: print("  DEP  (NX_COMPAT)")

        # Data directory: at offset 96 (PE32) or 112 (PE32+)
        dd_offset = 112 if is_pe32plus else 96
        dd = opt[dd_offset:dd_offset + 16 * 8]  # 16 entries × 8 bytes

        # Import Directory = data directory[1]
        imp_rva, imp_size = struct.unpack_from('<II', dd, 8)
        print(f"\nImport Directory: RVA={hex(imp_rva)} Size={imp_size}")

if __name__ == '__main__':
    if len(sys.argv) < 2:
        print(f"Usage: {sys.argv[0]} <pe-file>")
        sys.exit(1)
    pe_parse(sys.argv[1])

      TimeDateStamp:          1750061822 (Mon Jun 16 2026)
      ...

Imphash - Import Table Hash

pehash computes the "imphash," a fuzzy hash of the import table that fingerprints a PE by what DLL s and functions it imports. Malware families often share identical import tables: 

$ pehash hello.exe
file:                   hello.exe
md5:                    ec5f8b2c8e31f7ee9532aa8c52520d11
sha1:                   aaf4c61ddcc5e8a2dabede0f3b482cd9aea9434d
imphash:                16d2a4617186e0a74e5f928e14e1827e
...

.NET PE Files - The CLR Header

.NET executables are still PE files, but the entry point jumps into the CLR (Common Language Runtime). The CLR header is at Data Directory index 14: 

typedef struct _IMAGE_COR20_HEADER {
    uint32_t cb;                    // Header size
    uint16_t MajorRuntimeVersion;
    uint16_t MinorRuntimeVersion;
    IMAGE_DATA_DIRECTORY MetaData;  // .NET metadata tables
    uint32_t Flags;                 // IL_ONLY, 32BITREQUIRED, etc.
    uint32_t EntryPointToken;       // Token of Main() in metadata
    IMAGE_DATA_DIRECTORY Resources;
    IMAGE_DATA_DIRECTORY StrongNameSignature;
    // ...
} IMAGE_COR20_HEADER;

The .text section contains only a small stub that loads mscoree.dll and calls _CorExeMain . All application code lives in .NET IL (Intermediate Language) stored as metadata.

PE Security Features by Era

Windows Version Features Introduced
NT 3.1 (1993) Base PE format, basic section protection
XP SP2 (2004) Hardware DEP (/NXCOMPAT), /GS stack cookies
Vista (2006) ASLR (IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE)
7 (2009) SEHOP (Structured Exception Handler Overwrite Protection)
8 (2012) High Entropy ASLR (64-bit), /DYNAMICBASE default
8.1 U3 (2014) Control Flow Guard (CFG)
10 (2015) Arbitrary Code Guard (ACG), Code Integrity Guard (CIG)
10 1607 Strict handle checking, child process restriction
10 2004 (2020) Hardware-enforced stack protection (CET shadow stack)

Modern Windows compilers enable most protections by default:

/DYNAMICBASE           ASLR
/HIGHENTROPYVA         64-bit high-entropy ASLR
/NXCOMPAT              DEP (hardware-enforced W^X)
/GUARD:CF              Control Flow Guard
/CETCOMPAT              Shadow Stack compatible
/GS                    Stack cookies (canaries)

Challenge

Write a Go PE header parser. It should validate the MZ and PE signatures, read the COFF and Optional headers with encoding/binary , and print the machine type, section count, entry point, subsystem, and the ASLR and DEP flags. 

package main

import (
	"encoding/binary"
	"errors"
	"fmt"
	"io"
	"os"
)

type coffHeader struct {
	Machine              uint16
	NumberOfSections     uint16
	TimeDateStamp        uint32
	PointerToSymbolTable uint32
	NumberOfSymbols      uint32
	SizeOfOptionalHeader uint16
	Characteristics      uint16
}

func readPE(path string) error {
	file, err := os.Open(path)
	if err != nil {
		return err
	}
	defer file.Close()

	dos := make([]byte, 64)
	if _, err := io.ReadFull(file, dos); err != nil {
		return err
	}
	if dos[0] != 'M' || dos[1] != 'Z' {
		return errors.New("not a PE file: missing MZ signature")
	}

	e_lfanew := binary.LittleEndian.Uint32(dos[0x3C:])
	if _, err := file.Seek(int64(e_lfanew), io.SeekStart); err != nil {
		return err
	}

	signature := make([]byte, 4)
	if _, err := io.ReadFull(file, signature); err != nil {
		return err
	}
	if string(signature) != "PE\x00\x00" {
		return errors.New("not a PE file: missing PE signature")
	}

	var coff coffHeader
	if err := binary.Read(file, binary.LittleEndian, &coff); err != nil {
		return err
	}

	optional := make([]byte, coff.SizeOfOptionalHeader)
	if _, err := io.ReadFull(file, optional); err != nil {
		return err
	}

	magic := binary.LittleEndian.Uint16(optional[0:])
	entry := binary.LittleEndian.Uint32(optional[16:])
	subsystem := binary.LittleEndian.Uint16(optional[68:])
	dllChars := binary.LittleEndian.Uint16(optional[70:])

	var imageBase uint64
	if magic == 0x20B {
		imageBase = binary.LittleEndian.Uint64(optional[24:])
	} else {
		imageBase = uint64(binary.LittleEndian.Uint32(optional[28:]))
	}

	fmt.Printf("machine:          0x%04X\n", coff.Machine)
	fmt.Printf("sections:         %d\n", coff.NumberOfSections)
	fmt.Printf("image base:       0x%X\n", imageBase)
	fmt.Printf("entry point (VA): 0x%X\n", imageBase+uint64(entry))
	fmt.Printf("subsystem:        %d\n", subsystem)
	fmt.Printf("dll chars:        0x%04X\n", dllChars)
	if dllChars&0x0040 != 0 {
		fmt.Println("  DYNAMIC_BASE")
	}
	if dllChars&0x0100 != 0 {
		fmt.Println("  NX_COMPAT")
	}
	return nil
}

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "usage: %s <pe-file>\n", os.Args[0])
		os.Exit(1)
	}
	if err := readPE(os.Args[1]); err != nil {
		fmt.Fprintln(os.Stderr, "error:", err)
		os.Exit(1)
	}
}

Build a test binary on Linux with pacman -S mingw-w64-gcc and x86_64-w64-mingw32-gcc -o hello.exe hello.c , then run the parser against it.
