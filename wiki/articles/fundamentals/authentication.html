Authentication

Proving identity through knowledge, possession, and inherence factors on Linux systems

Overview

Authentication is the process of verifying that a subject (user, process, device) is who it claims to be. It is distinct from authorization, which determines what that verified subject may then do, and confusing the two is a common source of security architecture failures. This article covers the three factor types, password transport and storage, challenge-response, Kerberos, NTLM , TOTP, SSH keys, PAM , certificates, and session management. After reading it you can audit and reason about the authentication stack on a Linux system.

Required Reading

  • Authorization - access control for a verified identity
  • Password Hashing - one-way password storage
  • Public Key Cryptography - asymmetric keys and signatures
  • TLS - encrypted transport and certificates

1. The Three Authentication Factors

Every authentication mechanism relies on one or more of three factor types:

Factor Category Examples
Knowledge Something youknow Password, PIN, passphrase, secret question answer
Possession Something youhave Smart card, YubiKey, phone (SMS/TOTP), hardware token
Inherence Something youare Fingerprint, face geometry, iris pattern, voiceprint, typing cadence

Two-factor authentication (2FA) means combining two distinct factor types - typically knowledge

  • possession. Multi-factor ( MFA ) means two or more factors.

Using two passwords is not 2FA; that is two knowledge factors.

Single-factor authentication is trivially broken when the factor is compromised. A stolen password grants full access. A lost phone with SMS-based OTP grants nothing without the password. A fingerprint without the device is useless. Each factor protects the others.

2. Password Authentication

2.1 Transmission

Passwords must never travel in cleartext. The standard mechanism on the web is to send the password over a TLS -encrypted channel. The password arrives at the server in plaintext inside the encrypted tunnel, and the server immediately hashes it for comparison against stored hashes. 

Client                          Server
  |                               |
  |---- TLS handshake ----------->|
  |<--- TLS established ----------|
  |                               |
  |---- POST /login (password) -->|  (encrypted by TLS)
  |                               |  server hashes password
  |                               |  compare to stored hash
  |<--- 200 OK (session cookie) --|
  |                               |

An alternative is PAKE (Password-Authenticated Key Exchange) such as SRP (Secure Remote Password) or OPAQUE, where the password never leaves the client. These are superior but not yet universal.

For SSH , password authentication sends the password through the encrypted SSH tunnel. Key-based authentication avoids transmitting any password entirely.

2.2 Storage

Passwords must never be stored in plaintext. They must not be encrypted (encryption implies a decryption key exists - if the server is compromised, the attacker obtains both the key and the encrypted passwords). Instead, passwords are stored as the output of a one-way cryptographic hash function designed to be deliberately slow.

This topic is covered in depth in the Password Hashing article. In summary: 

/etc/shadow on a modern Linux system:

user:$y$j9T$salt$hash:19500:0:99999:7:::
      |   |   |    |
      |   |   |    +-- actual hash output
      |   |   +------- random salt
      |   +----------- yescrypt identifier ($y$)
      +--------------- full hash string

The $y$ prefix indicates yescrypt, the default on modern Arch Linux. Older systems may show $6$ (SHA-512crypt) or $2b$ (bcrypt).

2.3 Complexity Policies

Password entropy, measured in bits, is:

entropy = length × log2(charset_size)
Policy Example Entropy
8 chars, lowercase only abcxyzpd 8 x 4.7 = 37.6 bits
8 chars, full ASCII aB3$xYq! 8 x 6.55 = 52.4 bits
4-word Diceware correct horse battery staple 4 x 12.9 = 51.6 bits
6-word Diceware unmoved spike helium ravioli vowel drawn 6 x 12.9 = 77.4 bits
20-char truly random Dx3#kL9$mP2@vR7!qN5^ 20 x 6.55 = 131 bits

The famous NIST SP 800-63B recommendation (2017): minimum 8 characters, allow up to 64, screen against known compromised passwords, eliminate periodic change requirements, and eliminate arbitrary composition rules (no mandatory special characters). Check passwords against haveibeenpwned's SHA1 range API or the k-anonymity model.

2.4 Rate Limiting

Password authentication is vulnerable to online brute force. Mitigations:

# Arch Linux: PAM tally2 for account lockout
# /etc/pam.d/system-auth

auth     required   pam_tally2.so   file=/var/log/tallylog deny=5 unlock_time=900
account  required   pam_tally2.so
						
# /etc/security/faillock.conf (modern alternative)
deny = 5
unlock_time = 600

SSH brute force mitigation: 

# /etc/ssh/sshd_config
MaxAuthTries 3
MaxSessions 5

# With fail2ban installed:
# /etc/fail2ban/jail.local
[sshd]
enabled  = true
maxretry = 3
bantime  = 3600

3. Challenge-Response Authentication

Challenge-response avoids sending secrets over the wire. The server sends a random challenge (nonce), and the client must produce a response that proves knowledge of a shared secret without revealing it.

3.1 HMAC-Based Challenge-Response

Server                            Client
  |                                 |
  |---- nonce (random 256-bit) ---->|
  |                                 |  response = HMAC-SHA256(secret, nonce)
  |<--- response ------------------|
  |                                 |
  |  Expected = HMAC-SHA256(secret, nonce)
  |  Compare(response, Expected)

The secret is never transmitted. An eavesdropper captures nonce and response but cannot compute valid responses for different nonces without the secret. A replay attack fails because the nonce is never reused (servers track used nonces).

3.2 Digital Signature Challenge-Response

With asymmetric keys, the client signs the challenge with its private key:

#!/bin/bash
# Server generates challenge
CHALLENGE=$(openssl rand -hex 32)
echo "Challenge: $CHALLENGE"

# Client signs challenge with private key
# SIGNATURE=$(ssh-keygen -Y sign -f ~/.ssh/id_ed25519 -n file <(echo "$CHALLENGE"))

# Server verifies with client's public key
# ssh-keygen -Y verify -f allowed_signers -I user -n file -s SIGNATURE <(echo "$CHALLENGE")

4. Kerberos Authentication

Kerberos is a trusted-third-party authentication protocol using symmetric cryptography. All parties trust the Key Distribution Center ( KDC ).

4.1 Architecture

          KDC (Key Distribution Center)
          +---------------------------+
          |  AS  (Authentication      |
          |       Service)            |
          |  TGS (Ticket Granting     |
          |       Service)            |
          +---------------------------+
                ^              ^
               /                \
              /                  \
             /                    \
        Client                  Service

4.2 Authentication Flow

Step 1: AS-REQ (Authentication Service Request)
  Client → KDC:  {principal, TGT_REQUEST}
  Client sends its principal name. No credentials yet.

Step 2: AS-REP (Authentication Service Reply)
  KDC → Client:  {K_C_TGS}K_c, TGT
  KDC looks up client's secret key K_c (derived from password).
  KDC generates a session key K_C_TGS for client↔TGS communication.
  KDC creates TGT = {client, K_C_TGS, expiration}K_TGS (encrypted with TGS secret key).
  KDC sends both: the session key encrypted with K_c, and the TGT.
  Client decrypts the session key using K_c. The TGT it cannot decrypt (encrypted with K_TGS).

Step 3: TGS-REQ (Ticket Granting Service Request)
  Client → KDC:  {service_name, TGT, authenticator}
  authenticator = {client, timestamp}K_C_TGS
  The authenticator proves the client knows the session key.

Step 4: TGS-REP (Ticket Granting Service Reply)
  KDC → Client:  {K_C_S}K_C_TGS, service_ticket
  KDC decrypts TGT, verifies authenticator.
  KDC generates session key K_C_S for client↔service.
  KDC creates service_ticket = {client, K_C_S, expiration}K_S.
  Client receives the service ticket (encrypted with service key, unreadable by client).

Step 5: AP-REQ (Application Request)
  Client → Service:  {service_ticket, {client, timestamp}K_C_S}
  Service decrypts ticket with its own key K_S to obtain K_C_S.
  Service decrypts authenticator with K_C_S.
  Service verifies timestamp (within clock skew window, typically 5 minutes).
  Service grants access.

Step 6: AP-REP (Application Reply, optional mutual auth)
  Service → Client:  {timestamp+1}K_C_S
  Client verifies: the service knows the session key, proving it decrypted the ticket.

4.3 Kerberos on Arch Linux

# Install Kerberos client
pacman -S krb5

# /etc/krb5.conf
[libdefaults]
    default_realm = EXAMPLE.COM
    dns_lookup_realm = false
    dns_lookup_kdc = false

[realms]
    EXAMPLE.COM = {
        kdc = kdc.example.com
        admin_server = kdc.example.com
    }

# Obtain a TGT
kinit user@EXAMPLE.COM
# Enter password. This sends AS-REQ and receives TGT (stored in credential cache).

# List tickets
klist

# Destroy tickets
kdestroy

4.4 Kerberos Strengths and Weaknesses

Strengths: mutual authentication, delegation (forwardable tickets), time-limited tickets, single sign-on within a realm, no password sent over wire (password-derived key only used once to decrypt TGT).

Weaknesses: the KDC is a single point of failure and compromise; time synchronization is critical ( NTP ); password-derived key is susceptible to offline brute force if AS-REP is captured (Kerberoasting); complex setup.

5. NTLM Authentication

NTLM (NT LAN Manager) is Microsoft's legacy challenge-response protocol. The fundamentals are covered here; the NTLM Attacks article covers relay and hash-passing techniques in depth.

5.1 NTLMv2 Flow

Client                          Server
  |                               |
  |--- NEGOTIATE_MESSAGE -------->|
  |                               |
  |<-- CHALLENGE_MESSAGE ---------|
  |    (server_nonce: 8 bytes)    |
  |                               |
  |--- AUTHENTICATE_MESSAGE ----->|
  |    (client_nonce, timestamp,  |
  |     HMAC-MD5 response)        |
  |                               |

Response = HMAC-MD5(
    HMAC_MD5(NT_Hash(password), upper(username) + domain),
    server_nonce + client_nonce + timestamp
)

NTLM hashes the password with MD4 (NT hash), then uses HMAC -MD5 for challenge-response. Critically, the password hash is equivalent to the password: if an attacker captures the NT hash, they can perform Pass-the-Hash without knowing the plaintext. No salt is used - identical passwords produce identical NT hashes.

6. TOTP and HOTP

One-Time Passwords (OTPs) provide the "something you have" factor. The two standards are:

  • HOTP ( HMAC -based OTP, RFC 4226): counter-based
  • TOTP (Time-based OTP, RFC 6238): time-based (HOTP with Unix epoch time as counter)

6.1 How TOTP Works

Both sides share:
  - A secret key (20 bytes, typically Base32 encoded)
  - A time step (usually 30 seconds)

TOTP = HOTP(K, T)
     = Truncate(HMAC-SHA1(K, T))

Where T = floor((current_unix_time - T0) / time_step)

The HMAC-SHA1 output is 20 bytes.
Truncate extracts 31 bits via dynamic truncation:
  1. Take the last 4 bits of the last byte → offset (0-15)
  2. Take 4 bytes starting at offset
  3. Mask off the most significant bit (to avoid signed integer issues)
  4. Modulo 10^digits (usually 6 digits)

Output: 6 or 8 decimal digits

6.2 Generating TOTP on Linux

# Generate a random TOTP secret (20 bytes, Base32)
TOTP_SECRET=$(openssl rand 20 | base32)
echo "Secret: $TOTP_SECRET"

# Compute TOTP code (using oathtool)
pacman -S oath-toolkit
oathtool --totp --base32 "$TOTP_SECRET"

# Verify with current time step
oathtool --totp --base32 --now="$(date +%s)" "$TOTP_SECRET"

6.3 TOTP in C

#include <stdint.h>
#include <string.h>
#include <time.h>
#include <openssl/hmac.h>
#include <stdlib.h>

uint32_t hotp(const uint8_t *key, size_t key_len, uint64_t counter) {
    uint8_t counter_be[8];
    for (int i = 7; i >= 0; i--) {
        counter_be[i] = counter & 0xFF;
        counter >>= 8;
    }

    uint8_t hmac_result[20];
    unsigned int result_len;
    HMAC(EVP_sha1(), key, key_len, counter_be, 8,
         hmac_result, &result_len);

    uint8_t offset = hmac_result[19] & 0x0F;
    uint32_t binary = (hmac_result[offset]     & 0x7F) << 24
                    | (hmac_result[offset + 1] & 0xFF) << 16
                    | (hmac_result[offset + 2] & 0xFF) << 8
                    | (hmac_result[offset + 3] & 0xFF);

    return binary % 1000000;
}

uint32_t totp(const uint8_t *key, size_t key_len, uint32_t time_step) {
    uint64_t counter = time(NULL) / time_step;
    return hotp(key, key_len, counter);
}

6.4 TOTP Security Properties

  • Time synchronization : Both client and server must agree on time. Typically +/-1 time step is allowed (30-second grace window).
  • Shared secret compromise : If the secret is stolen from the server's database, all OTPs can be generated. The secret must be protected as strongly as passwords.
  • No protection against real-time phishing : An attacker who captures the OTP via a phishing page and replays it within the same 30-second window can authenticate. FIDO2/ U2F solves this by binding to the TLS channel (origin-bound).
  • Replay protection : Servers must track the last used counter/time window and reject reuse.

7. SSH Key Authentication

SSH public key authentication uses asymmetric cryptography to prove identity without transmitting secrets.

7.1 Key Types

Type Algorithm Recommended
ssh-ed25519 Ed25519 (Curve25519) Yes - preferred
ecdsa-sha2-nistp256 ECDSA over NIST P-256 Okay
ecdsa-sha2-nistp384 ECDSA over NIST P-384 Okay
ecdsa-sha2-nistp521 ECDSA over NIST P-521 Okay
ssh-rsa RSA with SHA-1 signatures DeprecatedOpenSSH 8.8+
rsa-sha2-256 RSA with SHA-256 signatures Acceptable (3072+ bits)
rsa-sha2-512 RSA with SHA-512 signatures Acceptable (3072+ bits)

7.2 Key Generation

# Ed25519 (recommended)
ssh-keygen -t ed25519 -C "user@host" -f ~/.ssh/id_ed25519

# RSA 4096 (acceptable alternative)
ssh-keygen -t rsa -b 4096 -C "user@host" -f ~/.ssh/id_rsa

# Extract public key from private key
ssh-keygen -y -f ~/.ssh/id_ed25519

7.3 Authentication Flow

Client                                              Server
  |                                                   |
  |--- SSH_MSG_USERAUTH_REQUEST ------------------->  |
  |    (username, "publickey", key_algorithm, pubkey)  |
  |                                                   | Checks authorized_keys
  |                                                   | If key found for user:
  |<-- SSH_MSG_USERAUTH_PK_OK ---------------------   |
  |    (key_algorithm, pubkey)                         |
  |                                                   |
  |    signature = sign(private_key,                  |
  |        session_id +                                |
  |        SSH_MSG_USERAUTH_REQUEST +                  |
  |        username + service + "publickey" +          |
  |        TRUE + key_algorithm + pubkey)              |
  |                                                   |
  |--- SSH_MSG_USERAUTH_REQUEST ------------------->  |
  |    (username, "publickey", TRUE,                   |
  |     key_algorithm, pubkey, signature)              |
  |                                                   | verify(pubkey, data, signature)
  |<-- SSH_MSG_USERAUTH_SUCCESS -------------------   |

The message signed includes the SSH session identifier, binding the authentication to this specific encrypted session. This prevents a server from recording an authentication attempt and replaying it against a different server (the session IDs would differ).

7.4 authorized_keys File

~/.ssh/authorized_keys (one key per line):
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... user@host

Options can restrict keys:

# Restrict to a specific command
command="/usr/local/bin/backup.sh",no-agent-forwarding,no-port-forwarding,no-pty ssh-ed25519 AAA... backup-bot

# Restrict by source IP
from="10.0.0.0/8,192.168.1.0/24" ssh-ed25519 AAA... user@host

7.5 SSH Agent

ssh-agent holds decrypted private keys in memory, allowing use without re-entering passphrases: 

# Start agent (typically done by DM/shell init)
eval $(ssh-agent)

# Add key (prompts for passphrase, decrypts, stores in agent)
ssh-add ~/.ssh/id_ed25519

# List loaded keys
ssh-add -l

# Forward agent to remote host (USE WITH CAUTION)
ssh -A user@host
# Then on remote host, ssh-agent socket forwards to local agent.
# The remote root user can use your forwarded agent.

Agent forwarding is dangerous: anyone with root on the intermediate host can use your agent socket to authenticate as you to other hosts.

8. PAM Modules

PAM is the authentication framework on Linux. Applications call PAM ; PAM calls configured modules. This allows changing authentication policies without modifying applications.

8.1 PAM Stack Configuration

/etc/pam.d/
  ├── system-auth    (main authentication stack)
  ├── system-login   (login-specific)
  ├── passwd         (password changes)
  ├── sudo           (privilege escalation)
  └── sshd           (SSH daemon)

A PAM configuration file consists of lines in the format: 

type    control    module-path    module-arguments

8.2 PAM Types

Type Purpose
auth Authenticate the user (prove identity)
account Account management (expiration, time restrictions)
session Session setup/teardown (logging, environment, home directory)
password Password updates (quality checking, hash update)

8.3 Control Flags

Control Behavior
required Module must succeed. If it fails, subsequent modules still run but overall auth fails.
requisite Module must succeed. If it fails, return immediately (no further modules).
sufficient If this module succeeds and norequiredmodules have failed, return success immediately.
optional Only matters if no other module determines success/failure.
include Pull in another config file's stack.
substack Like include, but the included stack's results are aggregated into a single result.

8.4 Common PAM Modules

# /etc/pam.d/system-auth (Arch Linux example)

# Authenticate
auth      required  pam_unix.so     try_first_pass nullok
auth      required  pam_faillock.so preauth silent
auth      optional  pam_permit.so

# Account
account   required  pam_unix.so
account   required  pam_time.so
account   optional  pam_permit.so

# Password
password  required  pam_unix.so     sha512 shadow nullok
password  optional  pam_permit.so

# Session
session   required  pam_unix.so
session   optional  pam_permit.so

Important modules:

Module Purpose
pam_unix.so Traditional Unix password authentication (/etc/shadow)
pam_faillock.so Account lockout after failed attempts
pam_tally2.so Account lockout (legacy, replaced by faillock)
pam_google_authenticator.so TOTP second factor
pam_u2f.so FIDO U2F hardware token support
pam_ssh.so SSH key authentication via PAM
pam_ldap.so LDAP directory authentication
pam_mount.so Auto-mount volumes on login
pam_env.so Set environment variables
pam_limits.so Enforce resource limits (/etc/security/limits.conf)
pam_access.so Host-based access control (/etc/security/access.conf)
pam_time.so Time-based access restrictions
pam_shells.so Verify user's shell is in /etc/shells
pam_ecryptfs.so Mount encrypted home directories

8.5 Setting Up MFA with PAM

# Install Google Authenticator PAM module
pacman -S libpam-google-authenticator

# Generate secret for user
google-authenticator -t -d -f -r 3 -R 30 -W
# This creates ~/.google_authenticator with the shared secret

# /etc/pam.d/sshd
# Add before the pam_unix.so line:
auth     required  pam_google_authenticator.so

# /etc/pam.d/sudo (for sudo MFA)
auth     required  pam_google_authenticator.so

# /etc/ssh/sshd_config
ChallengeResponseAuthentication yes
UsePAM yes

9. Certificate-Based Authentication

TLS client certificates provide mutual authentication: not only does the client verify the server (standard TLS ), but the server verifies the client via a certificate.

9.1 How It Works

1. Client generates key pair and CSR (Certificate Signing Request)
2. CA signs the CSR, producing a client certificate
3. Server's trust store contains the CA certificate
4. During TLS handshake, server sends CertificateRequest
5. Client sends its certificate
6. Client signs the handshake data with its private key (CertificateVerify)
7. Server verifies: certificate chain → CA trust, signature matches public key

9.2 Creating Client Certificates

# Create a CA (Certificate Authority)
openssl genpkey -algorithm ed25519 -out ca-key.pem
openssl req -new -x509 -key ca-key.pem -out ca-cert.pem -days 3650 \
    -subj "/CN=My CA"

# Create client key and CSR
openssl genpkey -algorithm ed25519 -out client-key.pem
openssl req -new -key client-key.pem -out client.csr \
    -subj "/CN=client.example.com"

# Sign client CSR with CA
openssl x509 -req -in client.csr -CA ca-cert.pem -CAkey ca-key.pem \
    -out client-cert.pem -days 365 -set_serial 01

# Configure nginx to require client certificates
cat > /etc/nginx/sites-available/secure << 'EOF'
server {
    listen 443 ssl;
    ssl_certificate     /etc/nginx/ssl/server-cert.pem;
    ssl_certificate_key /etc/nginx/ssl/server-key.pem;

    ssl_client_certificate /etc/nginx/ssl/ca-cert.pem;
    ssl_verify_client on;
    ssl_verify_depth 1;

    location / {
        root /srv/http;
    }
}
EOF

10. Session Management

After authentication, a session is established to avoid re-authenticating every request.

10.1 HTTP Sessions

POST /login (credentials) → 200 OK
Set-Cookie: session_id=<random_256bit_token>; HttpOnly; Secure; SameSite=Lax

All subsequent requests:
Cookie: session_id=<random_256bit_token>

Server looks up session_id in server-side store:
{ session_id -> { user_id, created_at, expires_at, ... } }

The session token must be: - Generated from a CSP RNG (not rand() or Math.random() ) - At least 128 bits of entropy (256 bits recommended) - Transmitted only over HTTPS ( Secure flag) - Inaccessible to JavaScript ( HttpOnly flag) - Protected against CSRF ( SameSite=Lax or SameSite=Strict )

10.2 SSH Sessions

SSH sessions are inherent in the encrypted TCP connection. The session persists until the connection closes. SSH supports session multiplexing: 

# Configure multiplexing
# ~/.ssh/config
Host *
    ControlMaster auto
    ControlPath ~/.ssh/control/%C
    ControlPersist 10m

# First connection creates master
ssh user@host  # Authenticates, starts master

# Subsequent connections reuse master (no re-auth)
ssh user@host  # Uses existing master connection

10.3 Session Fixation

Session fixation occurs when an attacker forces a victim to use a known session ID. After the victim authenticates, the attacker's known session ID becomes authenticated.

Mitigations: - Regenerate the session ID on authentication ( PHP 's session_regenerate_id(true) ) - Never accept session IDs from URL parameters - Bind session to additional attributes ( IP , User-Agent - with caution)

10.4 Session Hijacking

If an attacker steals a valid session token (via XSS , network sniffing, malware), they can impersonate the victim. Mitigations: - TLS everywhere (encrypt the token in transit) - HttpOnly cookies (prevent XSS access)

  • Short session lifetimes + absolute timeouts
  • Session binding ( IP , user agent fingerprint)

11. Authentication vs Authorization

Authentication Authorization
Who are you? What can you do?
Verifies identity Determines permissions
Occurs first Depends on authentication
Passwords, keys, biometrics ACLs, roles, capabilities
Results in a session/principal Results in access decisions

This distinction is fundamental to security architecture. Many breaches occur because authentication is strong but authorization is weak - the attacker gets in (or bypasses auth), and the system assumes the authenticated user should have broad access. The principle of least privilege dictates that authorization should grant only what is strictly necessary, regardless of the strength of authentication.

Challenge

Implement TOTP verification in Go and compare the result with oathtool . Decode a Base32 secret, compute HOTP for the current 30-second time step with crypto/hmac and crypto/sha1 , apply the dynamic truncation, then reduce modulo 10^6 . The example computes the code; extend it to accept a window of plus or minus one time step when verifying user input. 

package main

import (
	"crypto/hmac"
	"crypto/sha1"
	"encoding/base32"
	"encoding/binary"
	"fmt"
	"os"
	"strings"
	"time"
)

func hotp(key []byte, counter uint64, digits int) int {
	var buf [8]byte
	binary.BigEndian.PutUint64(buf[:], counter)

	mac := hmac.New(sha1.New, key)
	mac.Write(buf[:])
	sum := mac.Sum(nil)

	offset := sum[len(sum)-1] & 0x0f
	code := binary.BigEndian.Uint32(sum[offset:offset+4]) & 0x7fffffff

	mod := 1
	for i := 0; i < digits; i++ {
		mod *= 10
	}
	return int(code) % mod
}

func totp(secret string, step time.Duration, digits int) (int, error) {
	key, err := base32.StdEncoding.WithPadding(base32.NoPadding).
		DecodeString(strings.ToUpper(strings.TrimSpace(secret)))
	if err != nil {
		return 0, err
	}
	counter := uint64(time.Now().Unix()) / uint64(step.Seconds())
	return hotp(key, counter, digits), nil
}

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "usage: %s <base32-secret>\n", os.Args[0])
		os.Exit(1)
	}
	code, err := totp(os.Args[1], 30*time.Second, 6)
	if err != nil {
		panic(err)
	}
	fmt.Printf("%06d\n", code)
}
