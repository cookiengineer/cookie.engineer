Context Switching

The CPU 's most expensive bookkeeping - saving and restoring execution state between threads, processes, and privilege levels on x86-64 Linux.

Overview

Every scheduler decision ends in a context switch: the kernel saves the outgoing execution state and restores the incoming one. This article separates a plain ring transition from a full context switch, follows the x86-64 save/restore path through switch_to() and XSAVE, and shows how to measure the cost with perf and /proc . After reading it you can explain why a process switch is far more expensive than a thread switch and how PCID and KPTI change the TLB bill.

Required Reading

  • Processes - process fundamentals, /proc, fork/exec
  • Threads - thread creation, clone(2), thread models
  • Scheduler - scheduling classes, runtime vs deadline
  • Virtual Memory - page tables, MMU, TLB

What Is a Context Switch

A context switch is the kernel act of suspending one execution context and resuming another. The CPU must save every architectural register that the outgoing context may depend on and restore the saved register state of the incoming context. On x86-64, a context switch saves or restores general-purpose registers, floating-point/SSE/ AVX state, control registers, segment registers, instruction pointer, stack pointer, page table root, and a growing collection of model-specific state bits. 

Time ──────────────────────────────────────────────────────────────────────►

Task A  ████████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░███████████
                            │                               │
                            ▼                               ▼
                    ┌───────────────┐               ┌───────────────┐
                    │ Save A state  │               │ Restore A     │
                    │ Pick next task │               │ Resume A      │
                    │ Restore B     │               │               │
                    └───────────────┘               └───────────────┘
                            │                               ▲
                            ▼                               │
Task B  ░░░░░░░░░░░░░░░░░░░░████████████████████████████████░░░░░░░░░░░░░░░

                    ◄──────── context switch ────────►
                            50 ns ─ 5 μs

A context switch is distinct from a user-kernel transition. When a user process invokes write() , the syscall instruction transitions to ring 0, but no context switch occurs - the kernel runs in the context of the calling thread. A true context switch happens only when the scheduler decides to run a different task.

Transition vs Context Switch

Not every ring transition is a context switch. The kernel distinguishes three levels:

Transition Trigger Cost (approx) State Saved
Mode switch Syscall, interrupt, exception ~100-300 cycles rcx, r11, rip, rflags (bysyscallinstr.)
Thread switch schedule()called, same mm ~1-3 us GPRs + FPU + kernel stack
Process switch schedule()called, different mm ~2-5 us GPRs + FPU + kernel stack + mm/cr3 
Mode switch (no ctx switch):
  user code → syscall → kernel handler → sysret → user code (same task)

Thread context switch:
  Task A user → syscall → kernel → schedule() → Task B kernel → sysret → Task B user
  cr3 unchanged (threads share mm)

Process context switch:
  Task A user → syscall → kernel → schedule() → switch_mm() → Task B kernel → sysret → Task B user
  cr3 changed, TLB invalidated (partial with PCID)

Hardware Context

The kernel must preserve every piece of architectural state that user code may depend on. The complete hardware context on x86-64 comprises:

Category Registers / State
General rax, rbx, rcx, rdx, rsi, rdi, rsp, rbp, r8-r15
Segment cs, ds, es, fs, gs, ss
Control cr0, cr2, cr3, cr4, cr8
Flags rflags
Instruction rip
FPU/MMX/x87 st0-st7, fcw, fsw, ftw, fop, fip, fdp, mxcsr
SSE/AVX xmm0-xmm15 (+ ymm/zmm hi bits if AVX/AVX-512)
XSAVE area XCR0-controlled state components
Model-Spec MSRs: FS_BASE, GS_BASE, KERNEL_GS_BASE, TSC_AUX
Debug dr0-dr7
PKRU Protection Key Rights for Userspace (if PKS)
CET Shadow stack pointer, IBT state (if enabled)

The size of the XSAVE area alone can reach several kilobytes when AVX-512 is active. On a server CPU with AVX-512 , the full xsave buffer is~2.5 KB per task.

Kernel Stack Switching

Every task has two stacks: one user stack (rsp in ring 3) and one kernel stack (used when running in ring 0). During a context switch, the kernel switches to the incoming task's kernel stack. The thread_struct inside task_struct stores the stack pointer: 

struct task_struct {
    ...
    struct thread_struct thread;  // arch-specific thread state
    ...
};

// arch/x86/include/asm/processor.h
struct thread_struct {
    unsigned long           sp;             // kernel stack pointer
    unsigned long           sp0;            // top of kernel stack (for syscall)
    unsigned long           usersp;         // user stack pointer (saved)
    unsigned long           fsbase;
    unsigned long           gsbase;
    struct fpu              fpu;            // FPU/SSE/AVX state
    unsigned long           cr2;
    unsigned long           trap_nr;
    unsigned long           error_code;
    ...
};

The current pointer - used in thousands of kernel code paths - does NOT require a lookup. It is derived from the kernel stack pointer directly: 

// arch/x86/include/asm/current.h
static __always_inline struct task_struct *get_current(void)
{
    // On x86-64, per-CPU variable 'current_task' is at a fixed offset
    // from the GS segment base. A single mov instruction suffices.
    struct task_struct *cur;
    asm volatile("movq %%gs:%c1, %0"
                 : "=r" (cur)
                 : "i" (offsetof(struct pcpu_hot, current_task)));
    return cur;
}

The kernel stack is 16 KB (four page frames) by default:

# Check kernel stack size
cat /proc/meminfo | grep KernelStack
# KernelStack:      18432 kB  (total across all tasks)

# Per-task stack (16 KB default, 8 KB on some configs)
zcat /proc/config.gz | grep KERNEL_STACK
# Or: grep CONFIG_THREAD_SIZE_ORDER /boot/config-$(uname -r)

The switch_to() Macro

The core of x86-64 context switching is the __switch_to() function and the switch_to() macro that wraps it. The actual register save/restore is a concert of inline assembly, C code, and architectural state management. 

schedule()
  │
  ▼
__schedule()                    // kernel/sched/core.c
  │
  ├─ pick_next_task(rq, prev)
  │
  ▼
context_switch(rq, prev, next)  // kernel/sched/core.c
  │
  ├─ prepare_task_switch(rq, prev, next)
  │
  ├─ switch_mm_irqs_off(prev->active_mm, next->mm, next)
  │   │
  │   └─ load_new_mm_cr3()      // Set CR3 to next->mm->pgd
  │       └─ mov %rax, %cr3      // CPU invalidates TLB entries (unless PCID)
  │
  ├─ switch_to(prev, next, prev)
  │   │
  │   └─ __switch_to()           // arch/x86/kernel/process_64.c
  │       │
  │       ├─ save_fsgs()          // save prev FS/GS base
  │       ├─ save_fpregs_to_fpstate(prev->thread.fpu)
  │       ├─ switch_to_xtregs()   // handle extended state (XSAVE)
  │       ├─ this_cpu_write(current_task, next)
  │       ├─ load_fsgs()          // restore next FS/GS base
  │       └─ switch_gdt()         // if per-CPU GDT entries differ
  │
  └─ finish_task_switch(prev)

switch_to Macro

#define switch_to(prev, next, last)                              \
do {                                                             \
    /* Save callee-saved regs: rbp, rbx, r12-r15 (ABI covers) */\
    /* Stack pointer swap happens implicitly via RSP switch */   \
    ((last) = __switch_to_asm((prev), (next)));                  \
} while (0)

__switch_to_asm

/*
 * %rdi = pointer to prev task_struct
 * %rsi = pointer to next task_struct
 *
 * Returns: prev task_struct pointer (becomes 'last' in the caller)
 */
__switch_to_asm:
    /* Save callee-saved registers onto prev's kernel stack */
    pushq   %rbp
    pushq   %rbx
    pushq   %r12
    pushq   %r13
    pushq   %r14
    pushq   %r15

    /* Save prev's kernel stack pointer */
    movq    %rsp, THREAD_SP(%rdi)       /* prev->thread.sp = rsp */

    /* Load next's kernel stack pointer */
    movq    THREAD_SP(%rsi), %rsp       /* rsp = next->thread.sp */

    /* Return value: prev (rdi) — will be stored in 'last' */
    movq    %rdi, %rax

    /* Update current_task per-CPU variable */
    movq    %rsi, PER_CPU_CURRENT_TASK

    /* Restore callee-saved registers from next's stack */
    popq    %r15
    popq    %r14
    popq    %r13
    popq    %r12
    popq    %rbx
    popq    %rbp

    ret

The stack pointer switch is the key insight: by changing rsp , the pop instructions restore the next task's saved registers, and ret returns to wherever the next task was when it last called __switch_to_asm .

FPU State and XSAVE/XRSTOR

Floating-point and SIMD state is large and expensive to save. The kernel uses lazy FPU switching with a hardware assist. The TS (Task Switched) flag in CR0 causes any FPU/SSE/ AVX instruction to trap with a #NM (No Math / Device Not Available) exception. This allows the kernel to defer saving FPU state until another task actually needs the FPU. 

Lazy FPU switching flow:

Task A (FPU dirty) → schedule() → Task B
  │                                    │
  │  ┌──────────────────────────────────┘
  │  │
  │  │  TS flag stays SET in CR0
  │  │  Task B does NOT yet own the FPU
  │  │
  │  │  Task B executes xmm instruction
  │  │        │
  │  │        ▼
  │  │  #NM exception (Device Not Available)
  │  │        │
  │  │        ▼
  │  │  do_device_not_available()
  │  │        │
  │  │        ├─ save_fpregs_to_fpstate(&prev->thread.fpu)  ──► Saves Task A FPU
  │  │        ├─ clts()  ──► Clear TS flag in CR0
  │  │        ├─ restore_fpregs_from_fpstate(&next->thread.fpu) ──► Restore Task B FPU
  │  │        └─ Set current->thread.fpu.last_cpu
  │  │
  │  │  Return to Task B, retry xmm instruction → succeeds

XSAVE and XRSTOR

// arch/x86/kernel/fpu/xstate.c

// Save all extended state to the XSAVE area:
void copy_fpregs_to_fpstate(struct fpu *fpu)
{
    if (likely(use_xsave())) {
        xsave(fpu->fpstate, fpu->fpstate_mask);
    } else if (use_fxsr()) {
        fxsave(fpu->fpstate);
    } else {
        fnsave(fpu->fpstate);  // legacy x87
    }
}

// Restore all extended state:
void copy_fpregs_from_fpstate(struct fpu *fpu)
{
    if (likely(use_xsave())) {
        xrstor(fpu->fpstate, fpu->fpstate_mask);
    } else if (use_fxsr()) {
        fxrstor(fpu->fpstate);
    } else {
        frstor(fpu->fpstate);
    }
}

XSAVE area layout

Offset Component Size XCR0 bit
0x000 x87/MMX state 160 bytes 0
0x0A0 SSE state (xmm0-15) 256 bytes 1
0x200 YMM_Hi128 (AVX-256) 256 bytes 2
0x300 BNDREGS (MPX) 64 bytes 3
0x340 BNDCSR (MPX) 64 bytes 4
0x380 Opmask (AVX-512) 64 bytes 5
0x3C0 ZMM_Hi256 (AVX-512) 512 bytes 6
0x5C0 Hi16_ZMM (AVX-512) 1024 bytes 7
0x9C0 PKRU 8 bytes 9
0x9C8 CET_U / CET_S 16 bytes 11, 12
0x9D8 HDC (Hardware Duty) 8 bytes 13
0x9E0 HWP (P-state hint) 8 bytes 16-18

Total XSAVE area size with AVX-512 is about 2696 bytes.

TLB Invalidation

When switching between processes (different mm ), the CPU must load a different page table root (CR3). Historically, every mov %cr3 invalidated the entire TLB (Translation Lookaside Buffer) for non-global pages. This is devastating for performance

  • the TLB has~1024 entries, and reloading each requires a page walk of 4-5 memory accesses.

TLB flush cost during process switch

Approach TLB state after CR3 Cost
No PCID (legacy) All entries flushed 1000+ cycles to refill hot pages
PCID (Haswell+) Entries tagged, kept Only new-process misses
INVPCID (opt.) Selective flush Precision flush of specific PCID

PCID (Process Context Identifiers)

Intel introduced PCID in Haswell (2013). Each process address space gets a unique 12-bit identifier. The TLB tags each entry with the PCID , so entries from multiple processes can coexist in the TLB simultaneously. Switching CR3 no longer flushes entries from other PCIDs . 

Without PCID:
  ┌────────────────┐   Task A → Task B   ┌────────────────┐
  │ TLB: A entries │─────────────────────►│ TLB: (empty)   │
  └────────────────┘   mov %cr3 flushes   └────────────────┘

With PCID:
  ┌────────────────┐   Task A → Task B   ┌──────────────────────────┐
  │ TLB: A entries │─────────────────────►│ TLB: A entries (stale)   │
  │                │   mov %cr3 (no flush)│       B entries (fresh)  │
  └────────────────┘                      └──────────────────────────┘

Meltdown and PCID

After Meltdown was disclosed in 2018, Linux adopted KPTI (Kernel Page Table Isolation), which gives each process two page tables: one for user mode (minimal kernel mappings) and one for kernel mode. Each CR3 switch now costs more because the CPU must manage two address spaces. PCID becomes critical here: 

Post-KPTI address space switch:
  Task A user cr3 (PCID=1)  →  Task A kernel cr3 (PCID=2, KPTI trampoline)
                              →  Task B kernel cr3 (PCID=3)
                              →  Task B user cr3 (PCID=4)

  Without PCID: 4 full TLB flushes
  With PCID:    0 TLB flushes (just PCID tag filtering)
						
# Check if PCID is available
grep pcid /proc/cpuinfo | head -1

# Check KPTI status
dmesg | grep -i 'page.*table.*isolation\|KPTI\|PTI'
cat /sys/devices/system/cpu/vulnerabilities/meltdown

The Full context_switch() Flow

The context_switch() function in kernel/sched/core.c orchestrates the entire transition: 

// kernel/sched/core.c (conceptually reconstructed)

static __always_inline struct rq *
context_switch(struct rq *rq, struct task_struct *prev,
               struct task_struct *next, struct rq_flags *rf)
{
    prepare_task_switch(rq, prev, next);

    /*
     * switch_mm_irqs_off() handles the virtual memory context:
     *   - If prev->mm == next->mm (threads): no op
     *   - If next->mm == NULL (kernel thread): borrow prev->active_mm
     *   - Otherwise: load next->mm->pgd into CR3
     */
    arch_start_context_switch(prev);

    if (!next->mm) {
        // Kernel thread: it has no own mm, borrow the previous one
        enter_lazy_tlb(prev->active_mm, next);
        next->active_mm = prev->active_mm;
    } else {
        switch_mm_irqs_off(prev->active_mm, next->mm, next);

        if (!prev->mm) {
            // Prev is kernel thread leaving borrowed mm
            prev->active_mm = NULL;
            rq->prev_mm = prev->active_mm;
        }
    }

    switch_to(prev, next, prev);
    // ---- We no longer execute in prev's context ----
    // prev is now the task that switched *out*, preserved in 'last'

    barrier();

    return finish_task_switch(prev);
}

Kernel thread special case

Kernel threads ( kworker , kthreadd , ksoftirqd/N ) have mm == NULL . They don't execute user code, so they don't need their own page tables. When scheduled, they "borrow" the previous task's active_mm , avoiding an expensive CR3 write. 

# Find kernel threads (no user memory)
ps aux | grep '\[.*\]'
# The square brackets indicate kernel threads

# Check which tasks have mm == NULL (requires debugfs)
sudo cat /proc/$(pidof kworker/0:0 | cut -d' ' -f1)/maps 2>&1 || echo "No userspace maps"

Voluntary vs Involuntary

The kernel tracks two categories of context switches for each task:

/proc/PID/status field              Meaning
═══════════════════════              ═══════
voluntary_ctxt_switches              Task yielded CPU willingly:
                                     - Called sleep(), wait(), poll()
                                     - Blocked on I/O, mutex, semaphore
                                     - Called sched_yield()

nonvoluntary_ctxt_switches           Task was preempted:
                                     - Time slice expired
                                     - Higher-priority task woke up
                                     - Kernel preemption (CONFIG_PREEMPT)

cat /proc/self/status | grep ctxt

Measuring Context Switch Cost

# perf stat — count events during a workload
sudo perf stat -e context-switches,cpu-migrations,page-faults \
    -e cycles,instructions,branches,branch-misses \
    -e L1-dcache-loads,L1-dcache-load-misses,LLC-loads,LLC-load-misses \
    -e dTLB-loads,dTLB-load-misses \
    sleep 5

# Isolate context switch events
sudo perf stat -e context-switches -a sleep 10
# -a: system-wide

# Profile scheduler functions

# Shows which tasks are being switched and why

# Count context switches per CPU
sudo perf stat -e 'context-switches' -C 0,1 -a -- sleep 5

Cache Pollution and TLB Misses

Context switches destroy the microarchitectural state: branch predictors reset, cache lines become cold, TLB entries become useless. The indirect costs often exceed the direct register-save costs.

Cost breakdown of a process context switch (approx., modern Intel processor):

Component Approx. Cost
Save/restore GPRs ~20 cycles
Save/restore FPU (XSAVE/XRSTOR) ~100-300
CR3 write (process switch only) ~500-1000
TLB refill (cold pages after CR3) ~5000-10000
L1 cache repopulation ~1000-5000
L2/L3 cache pollution ~2000-10000
Branch predictor reset ~500-2000
Kernel entry/exit ~100-200
Scheduler overhead ~200-500
Total (thread switch, same mm) ~500-2000
Total (process switch, diff mm) ~3000-20000+

Preemption

Linux can preempt kernel code if CONFIG_PREEMPT or CONFIG_PREEMPT_VOLUNTARY is enabled. The NEED_RESCHED flag in thread_info triggers preemption: 

// kernel/sched/core.c
void __sched schedule(void)
{
    struct task_struct *tsk = current;

    do {
        preempt_disable();
        __schedule(SM_NONE);
        sched_preempt_enable_no_resched();
    } while (need_resched());
}

// Preemption check happens on:
// 1. Return from interrupt/syscall to user space
// 2. preempt_enable() in kernel code (CONFIG_PREEMPT)
// 3. Explicit cond_resched() calls (CONFIG_PREEMPT_VOLUNTARY)
						
# Check preemption model
zcat /proc/config.gz | grep PREEMPT
# CONFIG_PREEMPT=y          → full preemption (low-latency desktop)
# CONFIG_PREEMPT_VOLUNTARY=y → voluntary preemption points only
# CONFIG_PREEMPT_NONE=y      → no kernel preemption
# CONFIG_PREEMPT_RT=y        → real-time preemption

# Monitor involuntary switches — indicator of preemption pressure
sudo perf top -e 'sched:sched_switch' -e 'sched:sched_wakeup'

Context Switching in Containers

Container runtimes (podman) do not add extra context switch overhead for the workload itself

  • containers are just processes with namespaced views. However, the overhead of podman's conmon

monitor process and runc can add marginal switches during container lifecycle events.
