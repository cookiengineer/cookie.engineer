Scheduler

Linux CFS and EEVDF scheduling, vruntime, red-black trees, scheduling classes, load balancing, preemption, and cgroup CPU control.

Overview

The scheduler decides which task runs on which CPU at every moment, trading fairness, throughput, and latency against each other. This article walks through the scheduling classes, CFS and EEVDF, per- CPU runqueues, load balancing, preemption, cgroup CPU limits, and the tracepoints that reveal what the scheduler does. After reading it you can pick a policy and measure the result.

  • Processes - process fundamentals, task_struct, process states, lifecycle
  • Threads - threads vs processes, clone(), pthreads, TID vs PID

The Scheduler's Job

The scheduler decides which thread runs on which CPU at every moment. It must balance three contradictory goals:

  1. Fairness : Every runnable thread gets a proportional share of CPU time.
  2. Throughput : Maximize total work completed per unit time.
  3. Latency : Interactive tasks ( GUI , typing, gaming) respond within human-perceptible deadlines.

These goals are fundamentally in tension. Frequent context switches improve latency but reduce throughput (cache/TLB thrashing). Prioritizing one long-running job maximizes throughput but starves interactive tasks. The scheduler is a compromise: a carefully tuned heuristic that is perpetually being patched. 

Scheduler life cycle of a thread:

 ┌──────────┐
 │  CREATED  │ ← fork()/clone() → task_struct created
 └────+─────┘    sched_fork() → init vruntime, enqueue
      │
      ▼
 ┌──────────┐     ┌──────────────┐
 │ READY     │────►│  RUNNING     │ ← __schedule() picks this task
 │(runnable) │◄────│  (on CPU)    │    preemption → back to READY
 └────+─────┘     └──────+───────┘
      │                   │
      │ sleep/interrupt   │ block (I/O, lock, wait)
      ▼                   ▼
 ┌──────────┐     ┌──────────────┐
 │ SLEEPING │     │  BLOCKED     │
 │(interrup)│     │(uninterrupt) │
 └────+─────┘     └──────+───────┘
      │                   │
      │ signal/wake       │ resource available → wake_up()
      ▼                   ▼
    back to READY      back to READY
      │
      ▼
 ┌──────────┐
 │ EXITED   │ ← do_exit() → scheduler removes task
 └──────────┘

Scheduling Classes

Linux defines a hierarchy of scheduling classes, each with its own runqueue, pick_next_task() logic, and priority rules. Higher-priority classes run before lower-priority ones: a RT task will always preempt a CFS task. 

Priority Order (highest to lowest):

┌────────────────────────────────────────────────────────────────┐
│ stop_sched_class (SCHED_STOP)                                   │
│  For CPU hotplug and migration threads. Cannot be preempted.    │
│  Used for: migration/N, cpuhp/N threads.                        │
├────────────────────────────────────────────────────────────────┤
│ dl_sched_class (SCHED_DEADLINE)                                 │
│  Earliest Deadline First (EDF). Each task has runtime,         │
│  deadline, and period. Guaranteed (if admission control        │
│  allows). Uses Constant Bandwidth Server (CBS).                │
├────────────────────────────────────────────────────────────────┤
│ rt_sched_class (SCHED_FIFO, SCHED_RR)                           │
│  Real-time. 100 static priority levels (0-99). Higher number   │
│  = higher priority. FIFO: runs until it yields. RR: timeslice  │
│  rotation within same priority. Can starve CFS tasks.          │
├────────────────────────────────────────────────────────────────┤
│ fair_sched_class (SCHED_OTHER, SCHED_BATCH, SCHED_IDLE)         │
│  CFS (Completely Fair Scheduler) — the default Linux scheduler. │
│  Proportional share based on vruntime. Uses red-black tree.    │
│  SCHED_OTHER: normal interactive/batch tasks                    │
│  SCHED_BATCH: throughput-optimized, less preemption             │
│  SCHED_IDLE:  only runs when nothing else wants the CPU         │
├────────────────────────────────────────────────────────────────┤
│ idle_sched_class (SCHED_IDLE)                                   │
│  Per-CPU idle task. Runs when no other task is runnable.        │
│  Enters CPU sleep states (C-states). Lowest overhead path.      │
└────────────────────────────────────────────────────────────────┘
						
# See scheduling classes in kernel config
grep -E "CONFIG_(SCHED_CLASS|SCHED_DEBUG|SCHED_INFO|SCHEDSTAT)" /boot/config-$(uname -r)

# Kernel threads and their scheduling classes
ps -eo pid,cls,rtprio,comm | head -20
# CLS: TS = SCHED_OTHER, FF = SCHED_FIFO, RR = SCHED_RR, DLN = SCHED_DEADLINE, IDL = SCHED_IDLE

Per-CPU Runqueues

Each CPU has its own runqueue ( struct rq ) containing per-scheduling-class sub-queues. This per- CPU design avoids contention on a global runqueue lock, but it requires load balancing to keep all CPU s busy. 

Per-CPU runqueue (struct rq):
┌──────────────────────────────────────────────────────┐
│  CPU 0 runqueue                                       │
│                                                       │
│  ├─ nr_running        : 3  (total runnable tasks)    │
│  ├─ nr_switches       : 1234567  (context switches)  │
│  ├─ nr_load_updates   : 3456789                      │
│  ├─ nr_uninterruptible: 0  (tasks in D state)        │
│  │                                                    │
│  ├─ cfs_rq ──► red-black tree of sched_entity        │
│  │   ├─ nr_running: 3                                │
│  │   ├──► task A (vruntime=1234.5 ms)               │
│  │   ├──► task B (vruntime=1235.1 ms)               │
│  │   └──► task C (vruntime=1238.9 ms)               │
│  │                                                    │
│  ├─ rt_rq ──► priority bitmap + 100 lists           │
│  │   ├─ nr_running: 1                                │
│  │   └──► RT task (prio=50)                          │
│  │                                                    │
│  ├─ dl_rq ──► red-black tree of sched_dl_entity      │
│  │   └─ nr_running: 0                                │
│  │                                                    │
│  ├─ clock          : 1234567890123  (ns)             │
│  ├─ clock_task     : 1234567890000  (ns, minus steal)│
│  ├─ curr           : ─► task B (currently running)   │
│  ├─ idle           : ─► idle task (swapper/0)        │
│  └─ stop           : ─► migration/0                  │
└──────────────────────────────────────────────────────┘

CFS - Completely Fair Scheduler

CFS (Linux 2.6.23 through 6.5) is based on the idea that every task should receive a fair share of CPU time. It tracks vruntime , the amount of time a task has spent on the CPU , weighted by its priority (nice value). Tasks with lower vruntime are "more deserving" and are scheduled first. 

CFS vruntime calculation:

vruntime += delta_exec * (NICE_0_LOAD / task_weight)

Where:
  delta_exec  = actual time spent running (in ns)
  NICE_0_LOAD = 1024 (nice 0 weight, SCHED_OTHER default)
  task_weight = weight derived from nice value

Nice → Weight mapping (partial):
  nice -20  → weight 88761  (highest priority, huge share)
  nice  -5  → weight  3121
  nice   0  → weight  1024  (default)
  nice   5  → weight   335
  nice  19  → weight    15  (lowest priority, tiny share)

Example: nice 0 task running for 10ms:
  vruntime += 10ms * (1024/1024) = 10ms

Example: nice 5 task running for 10ms:
  vruntime += 10ms * (1024/335) = 30.6ms
  → vruntime increases 3x faster → gets scheduled 3x less often

The scheduler picks the task with the SMALLEST vruntime from the
red-black tree. This gives each task CPU time proportional to its weight.

The CFS Red-Black Tree

rbtree (sorted by vruntime, smallest = leftmost):

            ┌─────┐
            │ B   │  vruntime = 1235.1
            └──+──┘
       ┌───────+───────┐
    ┌──+──┐         ┌──+──┐
    │ A   │         │ C   │
    │1234.5│         │1238.9│  ← pick_next_task() returns A (leftmost)
    └─────┘         └─────┘

When A runs, its vruntime advances. If A's vruntime exceeds B's,
A is re-inserted to the right of B. B becomes the new leftmost.

Enqueue: O(log n) — insert into red-black tree
Dequeue: O(log n) — remove from red-black tree
Pick next: O(1) — cache the leftmost node

# Shows: se.exec_start, se.vruntime, se.sum_exec_runtime, policy, prio

# See scheduling statistics
cat /proc/sched_debug 2>/dev/null | head -60 || \
sudo cat /sys/kernel/debug/sched/debug 2>/dev/null | head -60

EEVDF Scheduler

Starting with Linux 6.6 (October 2023), EEVDF replaced CFS as the default fair scheduler. EEVDF solves a fundamental issue with CFS: CFS was a work-conserving proportional-share scheduler, but it had bad tail latency: a newly woken task could "game" the system by having a tiny vruntime (it hadn't run yet) and immediately preempt long-running tasks. 

EEVDF Concepts:

Each sched_entity now has:
  → deadline = vruntime + (slice / weight)
  → eligible if: vruntime >= cfs_rq->min_vruntime - latency_ns

EEVDF picks the task with the EARLIEST DEADLINE among ELIGIBLE tasks.

Timeline:
  Task A wakes, eligible, deadline = 100ms
  Task B wakes, eligible, deadline =  50ms  ← earlier deadline
  → B runs first despite arriving later

  CFS would have just picked the lowest vruntime, which could be
  a task that just arrived and hasn't run yet (vruntime ≈ min_vruntime).
  EEVDF adds the deadline dimension to prevent latency abuse.

EEVDF tick:
  1. Update current task's vruntime
  2. If current is still the earliest deadline among eligible → keep running
  3. If another eligible task has an earlier deadline → request reschedule
  4. period: 6ms (default), slice = period * (weight / total_weight)
						
# Check if running EEVDF (Linux 6.6+)
uname -r | awk -F. '{if ($1>=6 && $2>=6) print "Likely EEVDF"; else print "CFS"}'
grep CONFIG_EEVDF /boot/config-$(uname -r) 2>/dev/null || echo "EEVDF not separately configurable"

# sched_feat shows scheduler tuning knobs
cat /sys/kernel/debug/sched/features 2>/dev/null | grep -i eevdf || echo "Check if debugfs is mounted"

Scheduling Policies

Policy Class Description
SCHED_OTHER CFS/EEVDF Default time-sharing, uses nice values
SCHED_BATCH CFS/EEVDF Like OTHER but assumes CPU-bound, less preemption
SCHED_IDLE CFS/EEVDF Ultra-low priority, runs only when idle
SCHED_FIFO RT Static priority 1-99, runs until blocks or yields
SCHED_RR RT Static priority 1-99, round-robin within same prio
SCHED_DEADLINE DL EDF with admission control, runtime/deadline/period 
// Setting scheduling policy programmatically (C):
#include <sched.h>
#include <stdio.h>

int main(void) {
    struct sched_param param;

    // Set SCHED_FIFO with priority 50
    param.sched_priority = 50;
    if (sched_setscheduler(0, SCHED_FIFO, &param) == -1) {
        perror("sched_setscheduler");
        printf("Need CAP_SYS_NICE or run as root with limits bumped\n");
        return 1;
    }

    printf("Now running as SCHED_FIFO, priority %d\n", param.sched_priority);

    // Busy-loop to hold the CPU (CAUTION: can hang system without RT throttling)
    while (1) {
        // CPU-bound work
    }

    return 0;
}
						
# Set scheduling policy from the command line
# Run a command with SCHED_FIFO priority 50
sudo chrt -f 50 stress-ng --cpu 1 --timeout 5s

# Run with SCHED_RR
sudo chrt -r 30 dd if=/dev/zero of=/dev/null bs=1M count=1000

# Run with SCHED_IDLE (lowest priority)
chrt -i 0 sha256sum /dev/zero &
CHRT_PID=$!
ps -o pid,cls,rtprio,comm -p $CHRT_PID
kill $CHRT_PID 2>/dev/null

# Change priority of a running process
sudo renice -n -10 -p $$    # Higher priority (lower nice value = more CPU)
sudo renice -n 19 -p $$     # Lower priority (higher nice value = less CPU)

# Set CPU affinity
taskset -c 0,2 stress-ng --cpu 2 --timeout 5s &
taskset -p $!

Load Balancing

When one CPU 's runqueue is long and another's is short, the kernel migrates tasks to keep the load balanced. Load balancing runs on an active CPU when it becomes idle (pull), or periodically via the scheduler tick on busy CPU s (push). 

Load Balancing Domains (topology-aware):

System (NUMA nodes)
  │
  ├── NUMA Node 0
  │     │
  │     ├── Socket 0
  │     │     │
  │     │     ├── Core 0 (SMT siblings: CPU 0, CPU 4)
  │     │     ├── Core 1 (SMT siblings: CPU 1, CPU 5)
  │     │     └── Core 2 (SMT siblings: CPU 2, CPU 6)
  │     │
  └── NUMA Node 1 (if present)
        │
        └── Socket 1
              ├── Core 3 ...

Scheduling domains (hierarchical):
  Level 0: SMT (hyperthread) — share L1/L2 cache
  Level 1: MC  (multi-core) — share LLC (L3 cache)
  Level 2: DIE (package)    — share nothing (or memory via local interconnect)
  Level 3: NUMA (node)      — share local memory controller

load_balance() runs at each domain level, moving tasks from the busiest
group to the current CPU's group. Higher levels are balanced less frequently
(higher cost of migration = more cache/TLB misses).
						
# Inspect scheduling domains
cat /proc/schedstat | head -5
# cpu0: yields, sched_switch, sched_wakeup, etc.

# View scheduling domain topology
cat /sys/kernel/debug/sched/domains/cpu0/domain*/name 2>/dev/null
cat /sys/kernel/debug/sched/domains/cpu0/domain*/flags 2>/dev/null

# Per-CPU load tracking
cat /proc/loadavg
sar -u 1 5 2>/dev/null || echo "Install sysstat for sar"

# NUMA-aware load balancing
cat /proc/schedstat | head -1 | awk '{printf "CPU0: sched_yield=%s sched_switch=%s sched_wake=%s\n", $2, $3, $4}'

Preemption

Preemption is the mechanism by which a running task is forcibly removed from the CPU to make way for a higher-priority task. Linux supports several preemption models:

Model Description
PREEMPT_NONE (CONFIG_PREEMPT_NONE) No forced preemption in kernel mode. Tasks yield voluntarily. Lowest overhead, worst latency. Used on servers.
PREEMPT_VOLUNTARY (CONFIG_PREEMPT_VOLUNTARY) Kernel code can voluntarily call schedule() via might_sleep(). Lower overhead than full preemption. Desktop default.
PREEMPT (full) (CONFIG_PREEMPT) Kernel is fully preemptible except for spinlock-held and IRQ-disabled regions. Lowest latency, higher overhead. Required for real-time applications.
PREEMPT_RT (CONFIG_PREEMPT_RT) Nearly all spinlocks become preemptible mutexes. IRQ handlers run as kernel threads. Hard real-time capable. Merged in 6.12. 
# Check preemption model
grep PREEMPT /boot/config-$(uname -r) | grep -v "^#"
# Look for: CONFIG_PREEMPT=y or CONFIG_PREEMPT_VOLUNTARY=y or CONFIG_PREEMPT_NONE=y

# For -rt kernels:
uname -r | grep rt && echo "Real-time kernel" || echo "Standard kernel"

The 'TIF_NEED_RESCHED' flag

When the scheduler decides a task should be preempted, it sets TIF_NEED_RESCHED in the task's thread_info flags. The actual preemption happens at the next safe point: on return from interrupt, system call, or explicit preemption check: 

// /usr/src/linux/include/linux/sched.h
static __always_inline bool need_resched(void)
{
    return unlikely(tif_need_resched());
}

// /usr/src/linux/kernel/sched/core.c — __schedule()
// Called when need_resched() returns true and preemption is safe:
static void __sched notrace __schedule(unsigned int sched_mode)
{
    struct task_struct *prev, *next;
    struct rq *rq = cpu_rq(cpu);

    prev = rq->curr;

    // Pick the next task from the runqueue
    next = pick_next_task(rq, prev, &rf);

    if (likely(prev != next)) {
        rq->nr_switches++;
        rq->curr = next;

        // Context switch: save prev, restore next
        context_switch(rq, prev, next, &rf);
    }
}

Context Switching

A context switch saves the CPU state of the outgoing task and restores the state of the incoming task. It is expensive, typically 1-5 microseconds on modern hardware. 

Context Switch Cost Breakdown:
  ┌─────────────────────────────────────────────────┐
  │ 1. Save registers (GPRs, FPU/SSE/AVX)           │  ~100 cycles
  │ 2. Switch address space (CR3 reload)            │  ~100-1000 cycles
  │    → TLB flush (partial with PCID)              │
  │ 3. Save/restore CPU context (stack, IP, flags) │  ~200 cycles
  │ 4. Cache effects (cold caches after switch)     │  ~1000-10000 cycles
  │ 5. Indirect branch predictor reset              │  varies
  └─────────────────────────────────────────────────┘
  Total: ~1000-1500 cycles (best case, cache-warm)
         ~5000-15000 cycles (worst case, cache-cold)

At 3 GHz: 1 μs = 3000 cycles → ctx switch ≈ 0.3-5 μs
						
# Measure context switch rate
sudo perf stat -e context-switches -a sleep 2 2>&1 | grep context-switches

# Context switch latency
# (Requires CONFIG_SCHEDSTATS or cyclictest)
cyclictest -t 1 -p 80 -i 1000 -l 10000 -q 2>/dev/null || echo "Install rt-tests for cyclictest"

# Count context switches per second
sar -w 1 5 2>/dev/null || echo "Install sysstat"

Voluntary vs Involuntary

  • Voluntary: Task calls schedule() explicitly (yields, blocks on I/O, sleep)
  • Involuntary: Task is preempted (time slice expired, higher priority task woken)

# nonvoluntary_ctxt_switches: 678

Cgroups v2 CPU Controller

The cgroup CPU controller limits and weights CPU usage for groups of processes. This is how containers (podman, Docker) implement --cpus and --cpu-shares . 

Cgroup v2 CPU controller interface:
  cpu.stat         — usage_usec, user_usec, system_usec, nr_periods, nr_throttled
  cpu.weight       — proportional weight (1-10000, default 100)
  cpu.max          — bandwidth cap: "$MAX $PERIOD" (e.g., "200000 1000000"
                     = 200ms CPU per 1s = 0.2 CPU)

Bandwidth Control:
  Period (default 100ms): accounting period
  Quota: max CPU time within the period
  If quota is 0.2 CPUs and period is 100ms:
    → 20ms CPU time per 100ms window
    → Throttled to 20% of one CPU

Weight (proportional share):
  If group A has weight 200 and group B has weight 100:
    When both are CPU-bound, A gets 2x the CPU time of B
    (200/100 = 2x)
						
# Inspect CPU controller for current cgroup
CGROUP_PATH=$(cat /proc/$$/cgroup | grep ':memory:' | cut -d: -f3)
CPU_PATH="/sys/fs/cgroup${CGROUP_PATH}"

# Check CPU weight and max
cat $CPU_PATH/cpu.weight 2>/dev/null
cat $CPU_PATH/cpu.max 2>/dev/null  # Format: $MAX $PERIOD

# Check CPU statistics
cat $CPU_PATH/cpu.stat 2>/dev/null

# Create a test cgroup with CPU limit
sudo mkdir /sys/fs/cgroup/testcpu
echo "20000 100000" | sudo tee /sys/fs/cgroup/testcpu/cpu.max  # 20% of one CPU
echo "$$" | sudo tee /sys/fs/cgroup/testcpu/cgroup.procs
# Now this shell is limited to 20% CPU!

# Return to original cgroup
echo "$$" | sudo tee /sys/fs/cgroup/cgroup.procs
sudo rmdir /sys/fs/cgroup/testcpu

RT Throttling and Inversion

Real-time throttling prevents rogue SCHED_FIFO tasks from starving the system. By default, RT tasks are limited to 0.95s of CPU time per 1s period. If they exceed this, they are throttled (forced to SCHED_OTHER) for the remainder of the period. 

# RT throttling parameters
cat /proc/sys/kernel/sched_rt_runtime_us   # Default: 950000 (0.95s)
cat /proc/sys/kernel/sched_rt_period_us     # Default: 1000000 (1s)

# Disable RT throttling (dangerous — RT task can hang system)
# echo -1 > /proc/sys/kernel/sched_rt_runtime_us

Priority inversion occurs when a high-priority task is blocked waiting for a resource held by a low-priority task, which itself is preempted by a medium-priority task. Linux mitigates this via priority inheritance (for rt_mutex) and priority ceiling (for certain kernel paths). 

Priority Inversion Example:
  Task A: priority 80 (high) — needs mutex
  Task B: priority 50 (medium) — CPU-bound
  Task C: priority 20 (low) — holds mutex

  1. C acquires mutex
  2. B preempts C (B has higher priority)
  3. A tries to acquire mutex → blocks (C holds it)
  4. B keeps running (no conflict with mutex)
  5. A is starved (waiting on C, but C can't run because B is running)

  Solution: Priority inheritance — C inherits A's priority (80)
  while holding the mutex. C runs to completion, releases mutex,
  then returns to priority 20. A gets the mutex.

Scheduler Tracing

Linux has extensive tracepoints in the scheduler. Every context switch, wakeup, migration, and load balance event is instrumented. 

Key sched tracepoints:
  sched:sched_switch       — prev_comm, prev_pid, next_comm, next_pid
  sched:sched_wakeup       — comm, pid, prio, target_cpu
  sched:sched_wakeup_new   — comm, pid (newly created task)
  sched:sched_migrate_task — comm, pid, orig_cpu, dest_cpu
  sched:sched_process_exec — filename, pid (exec event)
  sched:sched_process_fork — parent_comm, parent_pid, child_comm, child_pid
  sched:sched_process_exit — comm, pid (task exit)
  sched:sched_process_free — comm, pid (task_struct freed)
  sched:sched_wait_task    — comm, pid (waiting for task)
  sched:sched_wake_idle_without_ipi — CPU woken without IPI

CPU Affinity and Isolation

Pinning tasks to specific CPU s via taskset or sched_setaffinity() is essential for performance-critical workloads, but also for covert operations (a rootkit might isolate itself on a CPU the sysadmin never monitors). 

# Set CPU affinity
taskset -c 0,2,4 stress-ng --cpu 3 --timeout 5s &

# Check affinity
taskset -p $$
# pid 12345's current affinity mask: ffff  (all 16 CPUs)

# Isolate CPUs at boot (add to kernel cmdline):
#   isolcpus=2,3  — scheduler will never place tasks on CPUs 2,3
#   nohz_full=2,3 — disable timer tick on those CPUs (tickless)
#   rcu_nocbs=2,3 — offload RCU callbacks from those CPUs

# Check isolated CPUs
cat /sys/devices/system/cpu/isolated 2>/dev/null
cat /proc/cmdline | grep -o 'isolcpus=[^ ]*'

Power-Aware Scheduling

On asymmetric CPU designs (ARM big.LITTLE , Intel hybrid: P-cores

  • E-cores), the scheduler must decide not only which task gets the CPU

, but which type of CPU it gets. Bursty, low-utilization tasks go to E-cores; sustained high-utilization tasks go to P-cores. 

Intel hybrid scheduling (Alder Lake+):
  P-core (Performance): high IPC, SMT, high power
  E-core (Efficiency):   lower IPC, no SMT, low power

  ITMT (Intel Turbo Boost Max Technology 3.0):
    Some P-cores boost higher than others → scheduler prefers them.
  
  EAS (Energy-Aware Scheduling, primarily ARM):
    Computes energy cost for each CPU → picks most efficient.

#!/usr/bin/env python3
"""
Scheduler demonstration: CPU-bound vs I/O-bound workloads,
cgroup CPU limits, and scheduling behavior.
"""
import os, time, multiprocessing, subprocess, sys

def cpu_bound_worker(name, seconds):
    """Pure CPU-bound loop — always ready to run."""
    start = time.monotonic()
    pid = os.getpid()
    print(f"[{name}] PID={pid} started (CPU-bound, {seconds}s)")
    end = start + seconds
    while time.monotonic() < end:
        _ = sum(range(100000))  # Burn CPU
    elapsed = time.monotonic() - start
    print(f"[{name}] PID={pid} finished in {elapsed:.2f}s")

def io_bound_worker(name, seconds, duty=0.1):
    """I/O-bound — sleeps most of the time, wakes briefly."""
    pid = os.getpid()
    print(f"[{name}] PID={pid} started (I/O-bound, {seconds}s, duty={duty})")
    start = time.monotonic()
    bursts = 0
    while time.monotonic() < start + seconds:
        time.sleep(duty)
        _ = sum(range(50000))  # Short CPU burst
        bursts += 1
    elapsed = time.monotonic() - start
    print(f"[{name}] PID={pid} finished in {elapsed:.2f}s ({bursts} bursts)")

if __name__ == "__main__":
    print("=== Scheduler Lab ===")
    print(f"Main PID: {os.getpid()}")
    print(f"CPU count: {multiprocessing.cpu_count()}")
    print(f"Scheduling policy: ", end="")
    try:
        policy = os.sched_getparam(0)
        print(f"param={policy}")
    except:
        print("SCHED_OTHER (default)")

    print()
    print("--- Test 1: Two CPU-bound workers (competing for CPU) ---")
    procs = []
    for i in range(2):
        p = multiprocessing.Process(target=cpu_bound_worker, args=(f"CPU-Worker-{i}", 3))
        p.start()
        procs.append(p)
    for p in procs:
        p.join()

    print()
    print("--- Test 2: Two I/O-bound workers (little CPU contention) ---")
    procs = []
    for i in range(4):
        p = multiprocessing.Process(
            target=io_bound_worker,
            args=(f"IO-Worker-{i}", 3)
        )
        p.start()
        procs.append(p)
    for p in procs:
        p.join()

    print()
    print("Done. Use 'perf sched record -- sleep 2 && perf sched latency' to analyze.")
