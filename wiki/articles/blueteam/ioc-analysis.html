IOC Analysis

Working with indicators of compromise, covering creation, validation, enrichment, and threat hunting.

Overview

An IOC is an observable that indicates a known intrusion: a file hash, a C2 address, a domain, a registry key, or a mutex. This article covers the IOC lifecycle from extraction to expiration, the data models used to share them ( MISP , STIX 2.1, TAXII), how to validate and enrich a feed before trusting it, and how to turn static indicators into hunting queries. After reading you can take a raw threat-intel report and deploy its indicators without drowning your team in false positives.

Required Reading

  • DNS - resolution hierarchy, record types, passive DNS
  • HTTP - request/response structure, user-agents, URI patterns

Concept

An Indicator of Compromise ( IOC ) is an artefact observed on a network or system that indicates an intrusion with high confidence. IOC s are the forensic breadcrumbs attackers leave behind: file hashes of dropped tools, IP addresses of C2 servers, domain names generated by DGA algorithms, registry keys modified for persistence, mutex names used for single-instance checks.

IOC s are not detections. They are evidence that a specific known intrusion occurred. They are the lowest tier on the Pyramid of Pain and have the shortest operational lifespan. An IOC from last month's phishing campaign is probably useless today - but an IOC from an ongoing incident is a critical hunting tool.

IOC Types

Type Example Operational Lifespan Confidence
File Hash (MD5) d41d8cd98f00b204e9800998ecf8427e Minutes (polymorphic malware) High (exact match)
File Hash (SHA256) e3b0c442... Hours-Days High
IPv4 Address 185.130.5.253 Hours-Days (VPS rotation) Medium
IPv6 Address 2a00:1450:4001:: Hours-Days Medium
Domain Name evil-c2.evil.com Days-Weeks Medium
URL https://evil.com/drop/payload.exe Hours-Days Medium-High
Registry Key HKLM\..\Run\EvilService Weeks-Months High
Mutex Name Global\EvilBotMutex123 Weeks-Months Medium
X.509 Certificate Serial01:23:45:67:89:AB:CD:EF Months High

File Path C:\Users\*\AppData\Local\Temp\svchost.exe Days-Weeks Medium
YARA Rule (entire rule) Months-Years Very High

MD5 is deprecated for IOC purposes. Collisions are trivial. Only SHA256 (or better) should be used as file hash IOC s.

IOC Lifecycle

  Creation  →  Distribution  →  Consumption  →  Expiration
      │              │               │              │
  (analyst      (MISP, STIX,   (SIEM, EDR,    (IOC removed
   extracts       TAXII, CSV)   firewall,      from active
   from DFIR)                   DNS filter)    rule sets)

Creation

An analyst identifies an IOC during incident response, threat research, or malware analysis. The IOC must include context: what malware family, which campaign, when observed, confidence level, and TLP marking.

Distribution

IOC s are shared via MISP , STIX/TAXII feeds, email lists, or commercial threat intel platforms. Format matters - unstructured IOC s (plain text email) are nearly useless compared to structured STIX bundles.

Consumption

IOC s are ingested into security tools: SIEM correlation rules, EDR blocklists, firewall ACL s, DNS RPZ zones, email filters, and web proxies.

Expiration

Every IOC must have an expiry date. Stale IOC s cause false positives, bloated blocklists, and degraded performance. An IOC that hasn't matched in 90 days should be reviewed and likely expired.

MISP - Threat Intelligence Platform

MISP is the open-source standard for IOC management and sharing.

MISP Data Model

  Event (one incident/campaign)
    ├── Attribute (individual IOC)
    │     ├── type: ip-dst, domain, sha256, url, filename, regkey, mutex
    │     ├── category: Network activity, External analysis, Persistence
    │     ├── value: "185.130.5.253"
    │     ├── to_ids: true (export to IDS/suricata rules)
    │     └── comment: "C2 server, observed 2026-06-25"
    ├── Object (structured combination of attributes)
    │     └── File object: { filename, size, sha256, md5, mimetype }
    ├── Galaxy (knowledge base: MITRE ATT&CK, threat actors, malware)
    └── Tag (classification: TLP:AMBER, workflow:complete, etc.)

Exporting IOCs from MISP

# Export all IOCs from last 7 days as CSV
curl -H "Authorization: YOUR_API_KEY" \
  "https://misp.local/events/csv/download/false/false/7d/" \
  -o iocs_7d.csv

# Export as STIX 2.1
curl -H "Authorization: YOUR_API_KEY" \
  -H "Accept: application/json" \
  "https://misp.local/events/restSearch/returnFormat:stix2" \
  -o iocs_stix.json

# Export Suricata rules from network IOCs
curl -H "Authorization: YOUR_API_KEY" \
  "https://misp.local/events/nids/suricata/download" \
  -o suricata_iocs.rules

Consuming IOCs Locally

import requests
import json

# Pull recent IOCs from MISP
url = "https://misp.local/events/restSearch"
headers = {"Authorization": "YOUR_API_KEY", "Accept": "application/json"}
payload = {
    "returnFormat": "json",
    "last": "7d",
    "type": ["ip-dst", "domain", "sha256", "url"],
    "to_ids": True,
    "includeEventTags": True,
    "includeContext": True,
}
response = requests.post(url, headers=headers, json=payload)
events = response.json()

# Parse and categorize
for event in events.get("response", []):
    for attr in event.get("Attribute", []):
        ioc_type = attr["type"]
        ioc_value = attr["value"]
        tags = [t["name"] for t in event.get("Tag", [])]
        tlp = next((t.split(":")[1] for t in tags if t.startswith("tlp:")), "UNKNOWN")
        print(f"[{tlp}] {ioc_type}: {ioc_value}")

IOC Validation

Blindly trusting external IOC s is dangerous. Validate before deploying to production.

File Hashes - check against multiple sources: 

# VirusTotal API
curl -H "x-apikey: YOUR_VT_KEY" \
  "https://www.virustotal.com/api/v3/files/8f0c99f12f3c4c8f8bee1c6f3e0e8a31"

# Response includes: detection_ratio, first_seen, tags, names, submission names

IP Addresses - check reputation and context: 

# Passive DNS (resolve historic domain associations)
whois 185.130.5.253

# AbuseIPDB check
curl "https://api.abuseipdb.com/api/v2/check?ipAddress=185.130.5.253" \
  -H "Key: YOUR_KEY"

# Shodan (services running on this IP)
curl "https://api.shodan.io/shodan/host/185.130.5.253?key=YOUR_KEY"

Domain Names - investigate registration and history: 

# WHOIS - when was it registered? Newly registered = more suspicious
whois evil-c2.evil.com

# Passive DNS - what IPs has this domain resolved to?
# (VirusTotal, SecurityTrails, PassiveTotal)

# DNS history - has the A record changed recently?
dig +short evil-c2.evil.com A

Validation Checklist

  1. Is this a known good host? (CDN, cloud provider, legitimate service)
  2. When was this IOC first observed? (recent = more relevant)
  3. What is the threat context? (which malware/campaign/actor)
  4. Has this IOC been seen in your environment before?
  5. What is the confidence of the source? ( TLP:CLEAR from a trusted ISAC != random tweet)

IOC Enrichment

Raw IOC s have limited value. Enrichment adds context that enables prioritization. 

import requests
from datetime import datetime, timedelta

def enrich_ioc(ioc_value, ioc_type):
    """Enrich an IOC with context from multiple sources."""
    enriched = {
        "ioc": ioc_value,
        "type": ioc_type,
        "enrichment_timestamp": datetime.utcnow().isoformat(),
        "sources": {}
    }

    # Passive DNS (via SecurityTrails API - free tier available)
    if ioc_type in ("domain", "ip"):
        resp = requests.get(
            f"https://api.securitytrails.com/v1/history/{ioc_value}/dns/a",
            headers={"APIKEY": "YOUR_KEY"}
        )
        enriched["sources"]["passive_dns"] = resp.json()

    # WHOIS for domains
    if ioc_type == "domain":
        import whois
        w = whois.whois(ioc_value)
        enriched["sources"]["whois"] = {
            "creation_date": str(w.creation_date),
            "registrar": w.registrar,
            "age_days": (datetime.now() - w.creation_date).days
        }

    # Certificate Transparency logs (via crt.sh)
    if ioc_type == "domain":
        resp = requests.get(
            f"https://crt.sh/?q={ioc_value}&output=json"
        )
        enriched["sources"]["cert_transparency"] = resp.json()

    return enriched

False Positive Risks

Shared IOC s carry inherent risk:

  1. CDN / shared hosting IPs : Blocking a Cloudflare IP blocks thousands of legitimate sites.
  2. Internal IP space : IOC s that leaked internal RFC1918 addresses from another org are meaningless (and dangerous) in yours.
  3. DNS sinkhole IPs : Many orgs share the same sinkhole IP . The IOC creator may have tagged it as " C2 " when it's actually a sinkhole.
  4. URL shorteners : Blocking bit.ly/xyz blocks all bit.ly traffic - thousands of legitimate shortened URL s.
  5. Reputation services : Not all "malicious" IP s in VirusTotal are equally malicious. Some are false positives from overzealous contributors.
# Always sanity-check network IOCs before blocking
# Example: check if an IP belongs to a major cloud provider
whois 13.107.42.14 | grep -i "OrgName\|NetName"

# If org is Microsoft/AWS/Google/Cloudflare - think twice before blocking

Hunting with IOCs

IOC s are not passive block rules. They are hunting queries.

Hunting File Hashes in EDR

-- Find any execution of a known-bad SHA256
SELECT
    hostname, username, process_name, process_command_line,
    file_path, timestamp
FROM process_events
WHERE sha256 IN (
    'e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855',
    'a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a'
)
AND timestamp > NOW() - INTERVAL '30 days';

Hunting IPs in Firewall Logs

-- Find any outbound connection to known-bad IPs
SELECT
    src_ip, dst_ip, dst_port, protocol, bytes_sent, timestamp
FROM firewall_logs
WHERE dst_ip IN ('185.130.5.253', '194.26.29.114', '5.255.96.245')
AND action = 'allow'
AND timestamp > NOW() - INTERVAL '7 days';

Hunting Domains in DNS Logs

-- Find any DNS resolution to known-bad domains
SELECT
    client_ip, query, query_type, answer, timestamp
FROM dns_logs
WHERE query IN ('evil-c2.evil.com', 'phish.example.com', 'malware.drop.xyz')
AND timestamp > NOW() - INTERVAL '30 days';

Scoring IOCs for Hunting

def score_ioc_for_hunt(ioc, enrichment):
    """Calculate hunt priority score (0-100). Higher = hunt first."""
    score = 0

    # Recent sightings: higher score
    if enrichment.get("last_seen"):
        days_since = (datetime.now() - enrichment["last_seen"]).days
        if days_since < 7:
            score += 30
        elif days_since < 30:
            score += 15

    # TLP level: WHITE = higher confidence
    if enrichment.get("tlp") == "TLP:CLEAR":
        score += 20

    # Source reputation: trusted ISAC/source
    trusted_sources = {"CISA", "NCSC", "CERT-EU", "MS-ISAC"}
    if enrichment.get("source") in trusted_sources:
        score += 25

    # IOC type hierarchy: hashes are transient, IPs rotate
    type_weight = {
        "sha256": 10, "sha1": 8, "md5": 3,
        "ip-dst": 5, "domain": 15, "url": 20,
        "mutex": 25, "regkey": 25, "x509-cert": 30,
        "yara": 50
    }
    score += type_weight.get(ioc.type, 5)

    return min(score, 100)

IOC Distribution Checklist

When you create an IOC from your own incident response:

  1. Redact internal hostnames, IPs, usernames - SRV-INTERNAL-DC01.admin.internal should become <redacted> . External parties don't need your internal naming conventions.
  1. Include context - what malware, which campaign, when observed, what the IOC represents ( C2 , dropped file, persistence mechanism).
  1. Set TLP appropriately : TLP:RED (recipient only, no sharing), TLP:AMBER (share within organization/community), TLP:GREEN (share with peers), TLP:CLEAR (public disclosure).
  1. Include a confidence score : High (observed in your own incident), Medium (from trusted third party), Low (unverified, open source).
  1. Set an expiry date - IOC reports that never expire are irresponsible. Default: 90 days for IP s/domains, 365 days for certificates/registry keys.
  1. Test the IOC - does it match a known sample? Did you test it against a benign baseline to check for false positives?

Challenge

Write a Go tool that reads a STIX 2.1 bundle and prints every indicator as object,value,valid_until . Extract the object path and value from the STIX pattern string, deduplicate, and sort the output. Then extend it to emit a Suricata rule for each ipv4-addr and domain-name indicator. 

package main

import (
	"encoding/json"
	"fmt"
	"os"
	"regexp"
	"sort"
)

type Bundle struct {
	Type    string      `json:"type"`
	Objects []Indicator `json:"objects"`
}

type Indicator struct {
	Type       string   `json:"type"`
	Pattern    string   `json:"pattern"`
	ValidUntil string   `json:"valid_until"`
}

var pattern = regexp.MustCompile(`([a-z0-9_-]+):([^=\s]+)\s*=\s*'([^']+)'`)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "usage: iocs bundle.json")
		os.Exit(2)
	}

	raw, err := os.ReadFile(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	var bundle Bundle
	if err := json.Unmarshal(raw, &bundle); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	seen := make(map[string]bool)
	rows := make([]string, 0)

	for _, object := range bundle.Objects {
		if object.Type != "indicator" {
			continue
		}
		for _, match := range pattern.FindAllStringSubmatch(object.Pattern, -1) {
			objectPath := match[1] + ":" + match[2]
			value := match[3]
			key := objectPath + "=" + value
			if seen[key] {
				continue
			}
			seen[key] = true
			rows = append(rows, fmt.Sprintf("%s,%s,%s", objectPath, value, object.ValidUntil))
		}
	}

	sort.Strings(rows)
	fmt.Println("object,value,valid_until")
	for _, row := range rows {
		fmt.Println(row)
	}
}
