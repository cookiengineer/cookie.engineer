Handle Tables

Process handle tables, including handle encoding, table expansion, access validation, inheritance, handle leaks, and the Linux file descriptor table analogue.

Overview

A handle is an opaque integer that indexes a per-process table, translating a user-space value such as 0x60 into a kernel object pointer. Handle tables keep raw kernel addresses out of user mode while giving the kernel a place to cache access rights and inheritance flags. This article covers the Windows HANDLE_TABLE encoding and three-level expansion, then compares it with the Linux files_struct and fdtable and the abuse patterns that both structures enable.

Required Reading

  • Processes - process fundamentals, /proc, fork/exec
  • Object Manager - Object Manager architecture, object types, namespaces, reference counting

Why Handle Tables Exist

A process interacts with kernel objects - files, threads, mutexes, shared memory sections - through handles . A handle is an opaque integer that indexes into a per-process table.

The handle table serves as the translation layer between user-space handle values (like 0x60) and kernel-space object pointers (like &FileObject ). Without handle tables, user mode would need to store raw kernel pointers - a security disaster, as it would expose kernel memory layout and enable arbitrary kernel read/write.

══════════                            ═══════════

fd == 3                               │
  │                                   ▼
  ▼                              ┌────────────────┐

  │                              │                │
  │  syscall(SYS_read)           │ fdt->fd[3] ───►│ struct file *
  └──────────────────────────────►│                │
                                  └────────────────┘

                Linux: file descriptor table

  │                                  ▼
  ▼                             ┌───────────────────┐

Linux uses a flat array fdtable (inside struct files_struct ), indexed directly by fd number. Windows uses a more complex, multi-level table for scalability.

The HANDLE_TABLE Structure

Every Windows process has an EPROCESS structure. Inside it, ObjectTable points to a HANDLE_TABLE :

                         │  HandleLock     (EX_PUSH_LOCK)   │ ◄── lock for table operations
                         │  HandleTableList(LIST_ENTRY)     │ ◄── linked into global list
                         │  HandleContentionEvent           │ ◄── for blocking on expansion
                         │  DebugInfo      (PVOID)          │ ◄── debug handle tracing

Handle Value Encoding

A Windows handle is a 32-bit or 64-bit value encoded with both the table index and flags in its low bits: 

32-bit Handle Encoding:
┌──────────────────────────────────+───────┐
│  Table Index (bits 31:2)         │ Flags │
│                                   │ (1:0) │
└──────────────────────────────────+───────┘
  Index = handle >> 2

64-bit Handle Encoding:
┌─────────────────────────────────────+───────┐
│  Table Index (bits 63:2)            │ Flags │
│                                      │ (1:0) │
└─────────────────────────────────────+───────┘
  Index = handle >> 2

Flag bits (low 2 bits):
  Bit 0: INHERIT             - handle inherited by child processes
  Bit 1: PROTECT_FROM_CLOSE  - handle cannot be closed

Example:
  Handle 0x64 = 0110 0100
  >> 2 = 0x19 = index 25
  & 0x3 = 0x0 = no flags set

  Handle 0x67 = 0110 0111
  >> 2 = 0x19 = index 25
  & 0x3 = 0x3 = PROTECT_FROM_CLOSE | INHERIT

In Linux, file descriptors use no encoding - the fd number directly indexes the fd array. The O_CLOEXEC flag is stored in a separate bitmap, not encoded in the fd number: 

# Linux fd allocation: simple sequential allocation
# No encoding, just direct array index

python3 -c "
import os, fcntl
# Open several files, observe fd numbers
fds = [os.open('/dev/null', os.O_RDONLY) for _ in range(5)]
print('Allocated fds:', fds)  # [3, 4, 5, 6, 7]

# Show close-on-exec flag (separate bitmap)
for fd in fds[:3]:
    flags = fcntl.fcntl(fd, fcntl.F_GETFD)
    print(f'fd {fd}: CLOEXEC={bool(flags & fcntl.FD_CLOEXEC)}')
    os.close(fd)
"

Low-Level Handle Creation

When ObInsertObject() needs to create a user-mode handle for a kernel object, it calls ObpCreateHandle() : 

ObpCreateHandle(Process, Object, AccessMask, Flags)
    │
    ├── 1. Lock HandleTable
    ├── 2. Find free entry in handle table
    │       ├── Scan starting from FirstFree
    │       └── If table full → expand table (ObpExpandHandleTable)
    ├── 3. Allocate/initialize OBJECT_HANDLE_TABLE_ENTRY
    │       ├── Entry.Object = ObjectBody pointer
    │       ├── Entry.GrantedAccess = computed access mask
    │       └── Entry.Attributes = inheritance & audit flags
    ├── 4. Encode handle value: Index << 2 | Flags
    ├── 5. Increment HandleCount in OBJECT_HEADER
    ├── 6. If auditing enabled → ObpAuditObjectAccess()
    ├── 7. Unlock HandleTable
    └── 8. Return encoded handle to caller

Each table entry is an OBJECT_HANDLE_TABLE_ENTRY : 

┌──────────────────────────────────────────────┐
│  OBJECT_HANDLE_TABLE_ENTRY (bytes may vary)  │
│                                              │
│  union {                                     │
│      PVOID Object;          // pointer to body│
│      ULONG_PTR ObAttributes; // or attributes│
│  };                                          │
│  union {                                     │
│      ACCESS_MASK GrantedAccess;              │
│      ULONG_PTR GrantedAccessIndex;           │
│  };                                          │
│  union {                                     │
│      ULONG_PTR NextFreeEntry; // if entry free│
│      ULONG_PTR Spare;                        │
│  };                                          │
└──────────────────────────────────────────────┘

Linux fd allocation is simpler - get_unused_fd_flags() finds the next zero bit in the open_fds bitmap, expands the table if needed, and returns the fd number: 

# Trace fd allocation in Linux
sudo bpftrace -e '
kprobe:__alloc_fd {
    $files = (struct files_struct *)arg0;
    $fd = arg3;
    printf("alloc_fd: pid=%d target=%d\n", pid, $fd);
}
kprobe:__put_unused_fd {
    printf("free_fd: pid=%d fd=%d\n", pid, arg1);
}
'

Handle Table Expansion

The Windows handle table uses a three-level (sparse) scheme to conserve memory for processes with few handles while supporting millions of handles: 

TableCode Encoding:
  ┌────────────────────────────────┐
  │  TableCode = Level | TableAddr │
  │  Level = TableCode & 0x3       │
  │  TableAddr = TableCode & ~0x3  │
  └────────────────────────────────┘

Level 0 (TableCode & 3 == 0): Direct table — up to 512 entries
  ┌──────────────────────────────────────────┐
  │  TableCode ──► Entry[512] (4K page)      │
  │  Handles: 0x04 through 0x7FC             │
  └──────────────────────────────────────────┘

Level 1 (TableCode & 3 == 1): Mid-table — up to 1,024 × 512 entries
  ┌──────────────────────────────────────────┐
  │  TableCode ──► Mid[1024] (4K page)       │
  │    Mid[i] ──► Low_Table[512] (4K each)   │
  │  Handles: up to 0x200000                 │
  └──────────────────────────────────────────┘

Level 2 (TableCode & 3 == 2): High-table — up to 1,024 × 1,024 × 512
  ┌──────────────────────────────────────────┐
  │  TableCode ──► High[1024] (4K page)      │
  │    High[i] ──► Mid[1024] (4K each)       │
  │      Mid[j] ──► Low_Table[512] (4K each) │
  │  Handles: up to ~16 million              │
  └──────────────────────────────────────────┘

Handle → Entry Translation:
                              Level 0   Level 1         Level 2
  Index = Handle >> 2
  if Level == 0: Entry = Table[Index]
  if Level == 1: Entry = Table[Index >> 9][Index & 0x1FF]
  if Level == 2: Entry = Table[Index >> 18][(Index >> 9) & 0x1FF][Index & 0x1FF]

Linux file descriptor expansion is simpler - the fdtable is a flat array that's reallocated when full: 

# Linux fd table expansion: flat array with bitmap
# Default: 64 inline entries in files_struct
# Beyond 64: allocated page(s) — 512 fds per page
# Beyond that: realloc to 2×, up to RLIMIT_NOFILE

# Check current and max fd limits
cat /proc/$$/limits | grep "open files"
# Max open files      1024      524288

# Expand fd table by opening many files
python3 -c "
import os, resource
soft, hard = resource.getrlimit(resource.RLIMIT_NOFILE)
print(f'Limits: soft={soft}, hard={hard}')
resource.setrlimit(resource.RLIMIT_NOFILE, (100000, hard))

fds = []
try:
    for i in range(10000):
        fds.append(os.open('/dev/null', os.O_RDONLY))
except OSError as e:
    print(f'Failed at {i}: {e}')
finally:
    for fd in fds:
        os.close(fd)
"

# Inspect fd table size
sudo bpftrace -e '
kprobe:expand_files {
    $files = (struct files_struct *)arg0;
    $nr = arg1;
    printf("expand_files: pid=%d nr=%d count=%d\n", pid, $nr, $files->count.counter);
}
'

Access Validation

When a handle is created, the Object Manager validates that the caller has sufficient access rights. The desired access mask (what the caller wants) is compared against the granted access mask (what the security subsystem allows): 

ACCESS_MASK Structure (32 bits):
┌────+───+──+──────────────────────────────+─────────────────────────┐
│ G  │ S │ R│  Standard Rights (bits 23:16)│ Specific & Generic (15:0)│
│ E  │ A │ e│                              │                         │
│ N  │ C │ s│  DELETE      (0x00010000)    │  GENERIC_READ  (0x80000000)│
│ E  │ L │ e│  READ_CONTROL(0x00020000)    │  GENERIC_WRITE (0x40000000)│
│ R  │   │ r│  WRITE_DAC   (0x00040000)    │  GENERIC_EXEC  (0x20000000)│
│ I  │   │ v│  WRITE_OWNER (0x00080000)    │  GENERIC_ALL   (0x10000000)│
│ C  │   │ e│  SYNCHRONIZE (0x00100000)    │  MAXIMUM_ALLOWED(0x02000000)│
└────+───+──+──────────────────────────────+─────────────────────────┘

AccessCheck Algorithm (simplified):
  ObpGrantAccess(DesiredAccess, Token, SecurityDescriptor):
      if (DesiredAccess & MAXIMUM_ALLOWED):
          GrantedAccess = EvaluateDacl(Token, DesiredAccess)
      else:
          GrantedAccess = DesiredAccess & EvaluateDacl(Token, DesiredAccess)
      
      if (GrantedAccess == 0):
          return STATUS_ACCESS_DENIED
      
      if (GENERIC_READ in DesiredAccess):
          GrantedAccess |= MapGenericToSpecific(GENERIC_READ)
      if (GENERIC_WRITE in DesiredAccess):
          GrantedAccess |= MapGenericToSpecific(GENERIC_WRITE)
      ...
      return GrantedAccess

The granted access mask is stored in the handle table entry. Subsequent operations using the handle automatically succeed because the access was pre-validated: 

# Linux access validation: checked at open() time, not encoded in fd
# The struct file carries f_mode (FMODE_READ, FMODE_WRITE) but runtime
# access checks happen per-syscall (capabilities, euid/egid)

# Show file access mode (read/write) for each fd
ls -la /proc/$$/fd/ | head -10
# lr-x------ 1 user user 64 Jun 26 12:00 0 -> /dev/pts/0
# l-wx------ 1 user user 64 Jun 26 12:00 1 -> /dev/pts/0
# lrwx------ 1 user user 64 Jun 26 12:00 3 -> /home/user/file.txt
#  ^
#  l=link, r=read, w=write, x=execute (meaningless for fd symlinks)

cat /proc/$$/fdinfo/3
# pos:    0
# flags:  0100000     (O_RDONLY = 0, O_WRONLY = 1, O_RDWR = 2)
# mnt_id: 27
# ino:    123456

# Trace access decisions
sudo bpftrace -e '
kprobe:generic_permission {
    $inode = (struct inode *)arg0;
    $mask = arg1;
    printf("check_access: inode=%p mask=%d comm=%s\n", $inode, $mask, comm);
}
'

Handle Inheritance and DuplicateHandle

Windows handles can be inherited by child processes. Three mechanisms control inheritance:

  1. OBJ_INHERIT flag on OBJECT_ATTRIBUTES - the handle itself is inheritable
  2. 'bInheritHandles' in 'CreateProcess' - parent controls whether any handles are inherited
  3. 'PROCESS_DUP_HANDLE' access - duplicate handle into another process's table
Handle Inheritance Flow:
══════════════════════════════════════════════════════════════

Parent Process (PID 1000)              Child Process (PID 2000)
│                                     │
│ CreateEvent(..., "MyEvent")         │
│ HANDLE h = 0x60 (inheritable)       │
│                                     │
│ CreateProcess("child.exe",          │
│   bInheritHandles = TRUE) ─────────►│ child.exe starts
│                                     │ h = 0x60 is valid in child!
│                                     │ WaitForSingleObject(h, INFINITE)
│                                     │   → references the SAME event object
│                                     │ HandleCount in OBJECT_HEADER incremented
│                                     │
│ CloseHandle(h)                      │
│ HandleCount-- (child still has it)  │
│                                     │ CloseHandle(h)
│                                     │ HandleCount = 0 → event destroyed

DuplicateHandle() allows one process to inject a handle into another: 

DuplicateHandle(srcProcess, srcHandle,
                dstProcess, &dstHandle,
                desiredAccess, inherit, options)

    │
    ├── 1. Look up source object from srcProcess handle table
    ├── 2. Verify PROCES_DUP_HANDLE access on srcProcess
    ├── 3. Verify desiredAccess against object's security
    ├── 4. Verify PROCESS_CREATE_THREAD/VM_WRITE access on dstProcess
    ├── 5. Insert new handle into dstProcess's handle table
    └── 6. Return dstHandle (indexed in dstProcess's table)

Options:
  DUPLICATE_CLOSE_SOURCE   — close srcHandle after duplication
  DUPLICATE_SAME_ACCESS    — copy granted access from source handle

Linux fd inheritance uses O_CLOEXEC flag and close-on-exec bitmap: 

# Linux fd inheritance across fork/exec

python3 << 'EOF'
import os, fcntl, subprocess

# Open a file without CLOEXEC (inherited by child after exec)
fd_inherit = os.open('/tmp/parent_file', os.O_CREAT | os.O_RDWR, 0o644)
os.write(fd_inherit, b'PARENT DATA\n')

# Open a file WITH CLOEXEC (closed on exec)
fd_noinherit = os.open('/tmp/noinherit_file', os.O_CREAT | os.O_RDWR | os.O_CLOEXEC, 0o644)

print(f'Parent PID: {os.getpid()}')
print(f'fd_inherit={fd_inherit} (CLOEXEC={bool(fcntl.fcntl(fd_inherit, fcntl.F_GETFD) & fcntl.FD_CLOEXEC)})')
print(f'fd_noinherit={fd_noinherit} (CLOEXEC={bool(fcntl.fcntl(fd_noinherit, fcntl.F_GETFD) & fcntl.FD_CLOEXEC)})')

# Execute child that lists its fds
subprocess.run(['bash', '-c', 'echo "Child fds:"; ls -la /proc/$$/fd/'], pass_fds=[fd_inherit])

os.close(fd_inherit)
os.close(fd_noinherit)
os.unlink('/tmp/parent_file')
os.unlink('/tmp/noinherit_file')
EOF

# Linux has no direct "DuplicateHandle" between arbitrary processes,
# but UNIX domain sockets with SCM_RIGHTS can pass fds:
python3 -c "
import socket, os
s = socket.socketpair(socket.AF_UNIX, socket.SOCK_STREAM)
fd_to_send = os.open('/etc/hostname', os.O_RDONLY)
with open('/proc/self/fd/' + str(fd_to_send)) as f:
    print(f'Sending fd {fd_to_send}: {f.read().strip()}')
"

Handle Auditing: ObpAuditObjectAccess

Windows can generate audit events when handles are created or closed for objects with a System Access Control List (S ACL ). The kernel routine ObpAuditObjectAccess() records:

  • Subject (user SID, process ID)
  • Object (name, type)
  • Access requested / granted
  • Result (success / access denied)
Audit Flow:
  ObpCreateHandle()
    │
    ├── Check SACL on object's security descriptor
    │     │
    │     ├── SACL present + AUDIT_SUCCESS → log success
    │     └── SACL present + AUDIT_FAILURE → log failure
    │
    └── ObpAuditObjectAccess()
          │
          ├── Build AUDIT_HANDLE_CREATE record
          │     ├── User SID
          │     ├── Object name, type
          │     ├── DesiredAccess, GrantedAccess
          │     └── Timestamp
          │
          └── SeAuditWithClosure → EventLog

Linux auditing uses auditd with syscall rules: 

# Linux file descriptor audit equivalent
# Enable auditing and add rules for specific files

sudo auditctl -l                              # List current rules
sudo auditctl -a exit,always -F path=/etc/shadow -F perm=r -F key=shadow-read
sudo auditctl -a exit,always -S openat -F success=0 -k failed-open

# Trigger an audit event
cat /etc/shadow 2>&1 || true

# View the audit log
sudo ausearch -k shadow-read --interpret
# Output includes: uid, pid, comm, exe, path, fd, result

# Clean up
sudo auditctl -d exit,always -F path=/etc/shadow -F perm=r -F key=shadow-read

Handle Leaks

A handle leak occurs when a process opens handles but never closes them. Over time, the handle table grows, the kernel objects accumulate, and the process eventually hits its handle quota. 

Handle Leak Example (Windows):
══════════════════════════════════════════════════════════════

void LeakyThread() {
    while (true) {
        HANDLE h = CreateEvent(NULL, FALSE, FALSE, NULL);
        // BUG: never calls CloseHandle(h)
        // Handle table grows by one entry each iteration
        // Event object persists (HandleCount > 0 in OBJECT_HEADER)
        Sleep(100);
    }
}

Detection:
  handle -p <PID> -s             ← increasing HandleCount
  Process Explorer handle view   ← hundreds of unnamed Event objects
  !handle in WinDbg              ← kernel debugger: dump handle table

Linux fd leaks are analogous - unreachable fds (no O_CLOEXEC ) that are never closed: 

# Linux fd leak detection

# 1. Check fd count for a suspicious process
ls /proc/$$/fd/ | wc -l
cat /proc/$$/status | grep FDSize

# 2. Monitor fd growth over time
watch -n 1 'ls /proc/<PID>/fd/ | wc -l'

# 3. Find processes with most open fds
sudo ls /proc/*/fd 2>/dev/null | awk -F/ '{print $3}' | sort | uniq -c | sort -rn | head -10

# 4. Show leaked fds and what they reference
for pid in $(pgrep -f "leaky_program"); do
    echo "PID $pid: $(ls /proc/$pid/fd/ 2>/dev/null | wc -l) fds"
    ls -la /proc/$pid/fd/ 2>/dev/null | head -20
done

# 5. Trace fd lifecycle for potential leaks
sudo bpftrace -e '
kprobe:__alloc_fd  { @open[pid] = count(); }
kprobe:__close_fd  { @close[pid] = count(); }
interval:s:10 {
    printf("=== FD Stats ===\n");
    print(@open);
    print(@close);
    printf("Net open for each PID:\n");
    print(hist(@open - @close));
}
'

# 6. Intentional leak demo and detection
python3 -c "
import os, time
fds = []
for i in range(100):
    fds.append(os.open('/dev/null', os.O_RDONLY))
    time.sleep(0.1)
print(f'Leaked {len(fds)} fds. PID={os.getpid()}')
input('Press Enter to close...')
for fd in fds:
    os.close(fd)
"

Abuse Patterns

Handle Hijacking - an attacker with sufficient privileges ( PROCESS_DUP_HANDLE ) duplicates a handle from a privileged process into their own handle table: 

Attacker (PID 5000)                    LSASS (PID 600)
│                                      │
│ NtOpenProcess(600,                   │  (LSASS holds HANDLE to
│   PROCESS_DUP_HANDLE) ──────────────►│   \Registry\Machine\SAM)
│                                      │
│ NtDuplicateObject(                   │
│   hLSASS,          // source proc    │
│   0x1A4,           // source handle  │
│   GetCurrentProcess(),               │
│   &stolenHandle,   // out: stolen    │
│   KEY_READ,                          │
│   0,                                  │
│   0) ────────────────────────────────┤
│                                      │
│ Now attacker has KEY_READ access     │
│ to SAM hive through stolenHandle     │

LSASS Handle Theft - attackers with SeDebugPrivilege can open LSASS with PROCESS_DUP_HANDLE , enumerate its handle table, and duplicate handles to authentication tokens or cached credentials.

CSRSS Handle Extraction - CSRSS (Client/Server Runtime Subsystem) holds handles to every console process. In older Windows versions, duplicating a CSRSS handle to a target process gave full process access.

Linux equivalent abuse patterns:

# Linux "handle hijacking" equivalent: fd passing, /proc/PID/fd/ access

# 1. Ptrace-based fd stealing (requires CAP_SYS_PTRACE or same uid)
# Attacker attaches to a privileged process, inspects fd table, dup2's fds

# 2. /proc/PID/fd/ access — if process has open fd to a restricted file
# and attacker can read /proc/PID/fd/, they can access the file
sudo ls -la /proc/1/fd/              # PID 1's open file descriptors
sudo cat /proc/1/fd/3                # Read fd 3 of PID 1 (if perms allow)

# 3. Check for processes with interesting handles
sudo lsof -nP | grep -E "shadow|passwd|private_key|\.pem" 2>/dev/null | head -10

# 4. SCM_RIGHTS fd passing over unix sockets (legitimate DuplicateHandle)
# Process A sends fd to Process B via sendmsg(SCM_RIGHTS)
# This is the Linux equivalent of DuplicateHandle between processes

SeDebugPrivilege Escalation

SeDebugPrivilege is the most powerful Windows privilege for handle manipulation. It grants: 

SeDebugPrivilege Effects on Handle Operations:
  - NtOpenProcess: bypass DACL — can open ANY process
  - NtOpenThread: bypass DACL — can open ANY thread
  - Maximizes granted access: PROCESS_ALL_ACCESS, THREAD_ALL_ACCESS
  - Combine with PROCESS_DUP_HANDLE → steal any handle

Escalation chain

1. Acquire SeDebugPrivilege (admin token adjustment)
2. Open winlogon.exe (PID always fixed) with PROCESS_DUP_HANDLE
3. Enumerate winlogon handle table → find handle to SYSTEM token
4. DuplicateHandle(winlogon, tokenHandle, self, &myToken)
5. ImpersonateLoggedOnUser(myToken) or SetThreadToken(NULL, myToken)
6. Now running as SYSTEM

Challenge

Write a Go tool that decodes a Linux process handle table. Read /proc/<pid>/fd and /proc/<pid>/fdinfo/<fd> , resolve the target path, and print the file descriptor, its access mode, and what it points to. Run it against a shell and watch new descriptors appear as you open files. 

package main

import (
	"fmt"
	"os"
	"path/filepath"
	"strconv"
	"strings"
)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "usage: %s <pid>\n", os.Args[0])
		os.Exit(1)
	}

	pid := os.Args[1]
	dir := filepath.Join("/proc", pid, "fd")

	entries, err := os.ReadDir(dir)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	for _, entry := range entries {
		target, _ := os.Readlink(filepath.Join(dir, entry.Name()))
		fmt.Printf("fd %-4s %-9s %s\n", entry.Name(), accessMode(pid, entry.Name()), target)
	}
}

// accessMode parses the octal flags field from fdinfo and returns the low
// two bits, which encode read, write, or read-write access.
func accessMode(pid string, fd string) string {
	data, err := os.ReadFile(filepath.Join("/proc", pid, "fdinfo", fd))
	if err != nil {
		return "?"
	}

	for _, line := range strings.Split(string(data), "\n") {
		if strings.HasPrefix(line, "flags:") {
			octal := strings.TrimSpace(strings.TrimPrefix(line, "flags:"))
			value, err := strconv.ParseUint(octal, 8, 64)
			if err != nil {
				return "?"
			}
			switch value & 3 {
			case 0:
				return "O_RDONLY"
			case 1:
				return "O_WRONLY"
			case 2:
				return "O_RDWR"
			}
		}
	}

	return "?"
}
