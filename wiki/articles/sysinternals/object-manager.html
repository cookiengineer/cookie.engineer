Object Manager

Kernel object namespaces - Windows Object Manager architecture, object types, reference counting, symbolic links, and the Linux /proc /sys analogue

Overview

Every kernel resource a process can name - a file, event, mutex, section, or process - is an object with a type, a reference count, and a place in a namespace. This article describes how the Windows Object Manager implements that model and how the Linux VFS and /proc expose an equivalent, then surveys the abuse patterns that follow from name squatting and lifetime bugs.

Required Reading

  • Processes - process memory layout, /proc, fork/exec lifecycle
  • Security Subsystem - SRM access control, tokens, security descriptors

Why an Object Manager Exists

Every operating system must manage kernel resources - processes, threads, files, events, semaphores, shared memory sections, registry keys, and device drivers. Without a unified object model, each subsystem would independently track allocation, naming, security, and lifetime. That leads to duplicated logic, inconsistent security checks, and resource leak bugs.

Windows solves this with the Object Manager - a centralized kernel subsystem (in ntoskrnl.exe , source in ob/ ) that provides a uniform interface for creating, naming, referencing, securing, and destroying kernel objects. Linux does not have a single Object Manager, but achieves similar goals through three complementary mechanisms: the Virtual File System (VFS) acting as a namespace, reference-counted kernel objects (krefs), and per-subsystem registries. 

Windows:                            Linux:
────────────────────────────────────────────────────────────
Object Manager (Ob*)          →     VFS (/proc, /sys, /dev)
  Directory                          filesystem directories
  SymbolicLink                       symlinks
  Event                              eventfd
  Mutant (mutex)                     futex / pthread mutex
  Semaphore                          semaphore (semget)
  Section                            memfd / shm
  Key (Registry)                     configfs
  Process                            /proc/PID/
  Thread                             /proc/PID/task/TID/
  Job                                cgroups
  Token                              (no unified namespace)
  File                               regular file

The Windows Object Manager Namespace

The Windows Object Manager maintains a hierarchical, session-aware namespace of named kernel objects. The root is \ , and well-known directories partition the namespace: 

\
├── ArcName              (symbolic links: arc paths → NT paths)
├── BaseNamedObjects     (per-session: events, mutexes, semaphores)
├── Callback             (callback objects for kernel notifications)
├── Device               (device objects for drivers: \Device\Harddisk0)
├── Driver               (loaded driver objects)
├── FileSystem           (filesystem recognizer objects)
├── GLOBAL??             (global DOS device namespace: C: → \Device\HarddiskVolume1)
├── KernelObjects        (kernel-internal events: low memory, session change)
├── KnownDlls            (known DLL section objects: kernel32.dll, ntdll.dll)
├── ObjectTypes          (directory of all registered object types)
├── RPC Control          (RPC endpoint objects)
├── Security             (security-related objects)
├── Sessions             (per-session root: \Sessions\0\, \Sessions\1\, ...)
└── ??                   (per-session DOS device namespace: C:, CON, NUL)

Session isolation is critical: interactive session 1 (the first logged-on user) sees \Sessions\1\BaseNamedObjects , while session 0 (services) sees \Sessions\0\BaseNamedObjects . A named mutex MyApp_SingleInstance created in session 1 is invisible to session 2 - preventing cross-session interference. The Global\ prefix forces creation/opening in \BaseNamedObjects (session-global), while Local\ maps to the current session's namespace. 

# Linux analogue: explore session-like namespaces via /proc
# Each process sees its own /proc/self/ but the kernel global namespace is unified
ls /proc/self/ns/        # Linux namespace file descriptors
# Output: cgroup ipc mnt net pid pid_for_children time time_for_children user uts

# Compare with Windows — different sessions are like different mount namespaces
sudo lsns -p $$           # List namespaces of current shell

Object Types and the Type System

The Object Manager defines every kernel resource as an object with a specific type . The type determines: initialization, cleanup, access validation, and the set of allowed operations. Each type is registered at boot via ObCreateObjectType() or the newer ObCreateObjectTypeEx() .

Windows Type Linux Analogue Purpose
Directory directory inode Container for other objects
SymbolicLink symlink Redirect to another object path
Event eventfd(2) Synchronization: set/reset/pulse
Mutant pthread_mutex_t / futex Mutual exclusion with ownership
Semaphore sem_t / semget() Counting semaphore (n concurrent users)
Section memfd_create() / shmget() Shared memory region
Key configfs / sysfs node Hierarchical key-value store (Registry)
Process task_struct -> /proc/PID/ Running program instance
Thread task_struct (group leader) Unit of CPU scheduling
Job cgroup Group of processes with resource limits
Token struct cred Security context (user, groups, privileges)
File struct file Open instance of a file/device
Timer timerfd_create() Notification after interval elapses
ALPC Port unix domain socket Inter-process communication endpoint
IoCompletion eventfd + aio ring Async I/O completion notification
Desktop - GUI desktop object (Windows-specific)
WindowStation - GUI session container (Windows-specific)

The OBJECT_HEADER

Every Windows kernel object is represented by a body (type-specific data) prefixed with a fixed OBJECT_HEADER . This header stores metadata that applies uniformly across all object types: 

Physical Memory Layout of a Windows Kernel Object:
┌──────────────────────────────────────────────┐
│  OBJECT_HEADER                               │
│  ├── PointerCount         (uint32)           │ ◄── kernel reference count
│  ├── HandleCount          (uint32)           │ ◄── user-mode handle count
│  ├── NextToFree           (void *)           │ ◄── free-list link
│  ├── Type                 (POBJECT_TYPE)     │ ◄── pointer to type object
│  ├── NameInfoOffset       (uint8)            │ ◄── object header name offset
│  ├── HandleInfoOffset     (uint8)            │ ◄── handle database info offset
│  ├── QuotaInfoOffset      (uint8)            │ ◄── quota charges offset
│  ├── Flags                (uint8)            │ ◄── flag bits
│  ├── SecurityDescriptor   (void *)           │ ◄── optional ACL
│  └── Body                 (object body)      │ ◄── body begins immediately after
├──────────────────────────────────────────────┤
│  Optional Headers (depend on Flags):          │
│  ├── OBJECT_HEADER_NAME_INFO                 │ ◄── name string (if named)
│  ├── OBJECT_HEADER_HANDLE_INFO               │ ◄── handle database entry list
│  ├── OBJECT_HEADER_QUOTA_INFO                │ ◄── charged quota block
│  └── OBJECT_HEADER_CREATOR_INFO              │ ◄── creator process/tid
├──────────────────────────────────────────────┤
│  Object Body (type-specific)                  │
│  ├── e.g., EPROCESS, ETHREAD, FILE_OBJECT    │
│  └── ...                                      │
└──────────────────────────────────────────────┘

In Linux, the equivalent concept is embedding a struct kref inside a subsystem object, plus manual registration in a subsystem directory: 

// Linux: reference-counted object pattern (include/linux/kref.h)
struct my_object {
    struct kref refcount;        // reference counter
    struct list_head list;       // subsystem's global list
    char name[256];              // object name
    void *type_data;             // type-specific body
};

void my_object_release(struct kref *kref) {
    struct my_object *obj = container_of(kref, struct my_object, refcount);
    kfree(obj->type_data);
    kfree(obj);
}

void my_object_get(struct my_object *obj) {
    kref_get(&obj->refcount);
}

void my_object_put(struct my_object *obj) {
    kref_put(&obj->refcount, my_object_release);
}

OBJECT_ATTRIBUTES

Every object creation and open operation in Windows uses an OBJECT_ATTRIBUTES structure: 

┌──────────────────────────────────────────────┐
│  OBJECT_ATTRIBUTES                           │
│  ├── Length                  (ULONG)         │ ◄── sizeof(OBJECT_ATTRIBUTES)
│  ├── RootDirectory           (HANDLE)        │ ◄── relative path root
│  ├── ObjectName              (PUNICODE_STRING)│ ◄── absolute or relative name
│  ├── Attributes              (ULONG)         │ ◄── OBJ_CASE_INSENSITIVE, etc.
│  ├── SecurityDescriptor      (PVOID)         │ ◄── explicit security
│  └── SecurityQualityOfService(PVOID)         │ ◄── impersonation level
└──────────────────────────────────────────────┘

The Attributes field controls naming behavior:

Flag Value Meaning
OBJ_INHERIT 0x00000002 Handle can be inherited by child processes
OBJ_PERMANENT 0x00000010 Object persists even with zero handles
OBJ_EXCLUSIVE 0x00000020 Fail if object with this name already exists
OBJ_CASE_INSENSITIVE 0x00000040 Name comparison is case-insensitive
OBJ_OPENIF 0x00000080 Open existing object instead of creating new
OBJ_KERNEL_HANDLE 0x00000200 Handle is kernel-mode (TableCode = 0xFFFFFFFF)
OBJ_FORCE_ACCESS_CHECK 0x00000400 Always check access, even in kernel mode 
# Linux analogue: different APIs use different attribute patterns
# open() uses flags, mmap() uses prot+flags, socket() uses type+protocol
# There is no unified OBJECT_ATTRIBUTES in Linux

# Example: creating a named object (shared memory) with attributes
# memfd_create allows a name + seals (similar to OBJ flags)
memfd_create("my-section", MFD_ALLOW_SEALING | MFD_CLOEXEC)

# Example: opening a POSIX named semaphore
# sem_open uses O_CREAT|O_EXCL pattern (like OBJ_EXCLUSIVE | OBJ_OPENIF)
sem_open("/myapp_mutex", O_CREAT | O_EXCL, 0644, 1)

Object Creation and Insertion

Creating a kernel object in Windows follows a two-phase protocol:

Phase 1: ObCreateObject()
         ┌──────────────────────────────────────────────┐
         │  1. Validate ObjectType exists                │
         │  2. Verify caller has create access           │
         │  3. Allocate memory (pool): header + body     │
         │  4. Initialize OBJECT_HEADER:                 │
         │     - Type = ObjectType                       │
         │     - PointerCount = 1                        │
         │     - HandleCount = 0                         │
         │  5. Call type's CreateProcedure (if any)     │
         │  6. Set Flags if requested                    │
         │  7. Return pointer to body (not header!)      │
         └──────────────────────────────────────────────┘
                           │
                           ▼
Phase 2: ObInsertObject()
         ┌──────────────────────────────────────────────┐
         │  1. Validate ACCESS_MASK against type         │
         │  2. If (ObjectName != NULL):                  │
         │     a. Parse path through object namespace    │
         │     b. Look up parent directory               │
         │     c. Check OBJ_EXCLUSIVE flag               │
         │     d. Insert into directory (hash table)     │
         │  3. Call ObpCreateHandle() for user-mode      │
         │  4. Charge quota to process                   │
         │  5. Call SeAccessCheck() for security         │
         │  6. Return handle to caller                   │
         └──────────────────────────────────────────────┘

Linux divides this into per-subsystem creation routines:

# Trace kernel object creation and naming in Linux
# Each subsystem has its own creation path

# Process creation: clone() → copy_process() → /proc/PID/
strace -f bash -c ''

# Memory object creation: memfd_create()
strace -e memfd_create python3 -c "import os; fd=os.memfd_create('test');"

# File object creation: open() → dentry → inode → file
strace -e openat touch /tmp/obj_test

# POSIX IPC object creation: semget(), shmget(), msgget()
ipcs -a            # List all System V IPC objects
ls /dev/shm/       # POSIX shared memory objects
ls /dev/mqueue/    # POSIX message queues

Namespaces: Global and Session

Windows isolates named objects by session. This prevents a malicious low-privilege user in session 1 from squatting on a mutex name that a service in session 0 depends on. 

Namespace Architecture:
═══════════════════════════════════════════════════════════

\ (Global Root)                          Kernel-only namespace
│
├── \BaseNamedObjects                    Session-global namespace
│   ├── Global\MyEvent                   (session 0 only, but visible from all)
│   └── ...
│
├── \Sessions\0\BaseNamedObjects         Session 0 (services) namespace
│   └── Local\MyEvent                   
│
├── \Sessions\1\BaseNamedObjects         Session 1 (user Alice) namespace
│   ├── Local\MyEvent                   
│   └── ...
│
└── \Sessions\1\Windows\WindowStations\  Per-desktop namespace
    └── WinSta0\Default\                 Default desktop objects

In Linux, namespace isolation is achieved differently - through kernel namespaces (nsproxy) : 

# Linux namespace isolation — similar concept, different mechanism
# Each namespace type isolates a subsystem

# Show all namespaces of current process
ls -la /proc/$$/ns/
# lrwxrwxrwx cgroup -> 'cgroup:[4026531835]'
# lrwxrwxrwx ipc -> 'ipc:[4026531839]'        ← analogous to \Session\N\BaseNamedObjects
# lrwxrwxrwx mnt -> 'mnt:[4026531841]'
# lrwxrwxrwx net -> 'net:[4026531840]'
# lrwxrwxrwx pid -> 'pid:[4026531836]'
# lrwxrwxrwx user -> 'user:[4026531837]'
# lrwxrwxrwx uts -> 'uts:[4026531838]'

# Compare IPC objects between namespaces
sudo nsenter -t <pid_in_other_container> -- ipcs -a

Reference and Handle Counts

Windows objects have two reference counts: 

┌─────────────────────────────────────────────────────────────┐
│  PointerCount  = kernel-mode references (ObReferenceObjectByPointer)
│  HandleCount   = user-mode handle references
│                                                             │
│  Total references = PointerCount + HandleCount              │
│  When both hit 0 → ObpRemoveObjectRoutine() → type DeleteProc│
└─────────────────────────────────────────────────────────────┘
						
Reference Lifecycle:
══════════════════════════════════════════════════════════════

1. ObCreateObject(..., &pObject)
   PointerCount = 1 (creator's kernel reference)
   HandleCount  = 0

2. ObInsertObject(pObject, &handle)
   HandleCount  = 1 (caller's handle)
   PointerCount = 1 (directory entry reference)

3. ObReferenceObjectByPointer(pObject)
   PointerCount = 2 (driver now holding a reference)

4. ObDereferenceObject(pObject)
   PointerCount = 1 (driver released its reference)

5. NtClose(handle)
   HandleCount  = 0 (user closed handle)
   PointerCount = 1 (directory entry still holds it)

6. ObpRemoveObjectRoutine() — called when user deletes the name
   PointerCount = 0 → Object freed

Linux uses struct kref for a unified reference count: 

# Linux reference counting: simpler, unified
# Every object using kref has ONE count

# Inspect kernel object reference counts via /proc
cat /proc/slabinfo | grep -E "dentry|inode|file" | head -10
# slabinfo shows active objects and total in each slab cache
# dentry            123456  130000    192   21    1 : tunables ...
# inode_cache        87654   90000    592   27    4 : tunables ...

# Trace object creation/destruction with bpftrace
sudo bpftrace -e '
kprobe:kref_init  { printf("kref+ %s\n", ((struct dentry *)arg0)->d_name.name); }
kprobe:kref_put   { printf("kref- %p\n", arg0); }
'

Object Directories and Lookup

Windows object directories are hash tables mapping names -> object pointers. The lookup function ObpLookupDirectoryEntry() walks the directory's hash bucket, comparing names with RtlEqualUnicodeString() : 

Directory Structure:
┌─────────────────────────────────────────┐
│  OBJECT_DIRECTORY                       │
│  ├── HashBuckets[37]  (linked lists)    │
│  │   ├── bucket[0] → Entry → Entry → ...│
│  │   ├── bucket[1] → Entry             │
│  │   ├── ...                           │
│  │   └── bucket[36] → Entry → Entry    │
│  └── SessionId        (if per-session)  │
└─────────────────────────────────────────┘

Lookup pseudocode:
ObpLookupDirectoryEntry(dir, name, case_insensitive):
    hash = HashUnicodeString(name) % 37
    for each entry in dir->HashBuckets[hash]:
        if Compare(entry->Name, name, case_insensitive):
            return entry->Object
    return NULL (not found)

Linux VFS directory lookups work analogously through the dentry cache : 

# Linux dentry cache — analogous to Object Manager directories
# dentry entries map name → inode, cached in a hash table

cat /proc/sys/fs/dentry-state
# Output: 123456  100000  45  0  0  0
#         ^dentry  ^unused ^age_limit ^want_pages ^dummy ^dummy

# View the dcache statistics
sudo slabtop -s c --once | grep dentry

# Trace directory lookups
sudo bpftrace -e '
kprobe:__d_lookup {
    $d = (struct dentry *)arg0;
    printf("lookup: %s\n", str($d->d_name.name));
}
kretprobe:__d_lookup /retval != 0/ {
    printf("  → found %p\n", retval);
}
kretprobe:__d_lookup /retval == 0/ {
    printf("  → NOT found\n");
}
'

Symbolic Links and DOS Devices

Windows uses symbolic link objects to redirect object paths. The most important ones are in \??\ (per-session DOS device namespace) and \GLOBAL??\ (global DOS device namespace): 

\??\C:                → \Device\HarddiskVolume3
\??\CON               → \Device\ConDrv\Console
\??\NUL               → \Device\Null
\??\PIPE\             → \Device\NamedPipe\
\GLOBAL??\C:          → \Device\HarddiskVolume1  (global, visible from all sessions)

When a user-mode application calls CreateFileW(L"C:\\Windows\\notepad.exe", ...) , the path is converted: 

C:\Windows\notepad.exe
    │
    ▼ (substitute DOS device prefix)
\??\C:\Windows\notepad.exe
    │
    ▼ (resolve symlink traversal: \??\C: → \Device\HarddiskVolume3)
\Device\HarddiskVolume3\Windows\notepad.exe
    │
    ▼ (parse through filesystem device stack)
\Device\HarddiskVolume3\Windows\notepad.exe → FILE_OBJECT

The Linux equivalent is the VFS symlink mechanism:

# Linux symlink chain — analogous to \??\ symbolic links
# /dev/stdin → /proc/self/fd/0 → /dev/pts/0

# Inspect symlink resolution step by step
namei -l /dev/stdin
# f: /dev/stdin
# drwxr-xr-x /
# drwxr-xr-x dev
# lrwxrwxrwx stdin -> /proc/self/fd/0
#   drwxr-xr-x /
#   dr-xr-xr-x proc
#   lrwxrwxrwx self -> 12345
#     dr-x------ 12345
#     dr-x------ fd
#     lrwx------ 0 -> /dev/pts/0

# The /proc/self symlink is analogous to Windows \Sessions\N\ —
# it automatically resolves to the calling process's PID
readlink /proc/self
# Output: 12345

# Linux /dev directory is like Windows \??\ namespace
ls -la /dev/ | head -20

Object Lifetime

The full lifecycle of a named Windows kernel object:

                         ┌─────────────────┐
                         │  ObCreateObject  │
                         └────────+────────┘
                                  │ PointerCount=1, HandleCount=0
                                  ▼
                         ┌─────────────────┐
                         │  ObInsertObject  │  (name="Global\MyMutex")
                         │  → ObpLookupDir  │
                         │  → InsertHash    │
                         │  → ObpCreateHandle│
                         └────────+────────┘
                                  │ HandleCount=1, PointerCount=2
                                  ▼
           ┌──────────────────────────────────────────────┐
           │  Object is alive and accessible               │
           │  - User-mode: NtOpenMutant, NtReleaseMutant   │
           │  - Kernel-mode: ObReferenceObjectByPointer    │
           └──────────────────────+───────────────────────┘
                                  │
                  ┌───────────────+───────────────┐
                  ▼               ▼               ▼
            NtClose()       ObDereference      ObDereference
            HandleCount--    ObjectPointer()   ObjectPointer()
                  │           PointerCount--   PointerCount--
                  ▼               │               │
            HandleCount==0?       ▼               ▼
            ObpCloseHandle   PointerCount==0?  PointerCount==0?
                  │               │               │
                  └───────+───────┘               │
                          ▼                       ▼
                    Both counts == 0     Directory entry removed?
                          │               │
                          ▼               ▼
                  ┌─────────────────────────────┐
                  │  ObpRemoveObjectRoutine()    │
                  │  → type->DeleteProcedure()   │
                  │  → ObpFreeObject()           │
                  │  → pool freed                │
                  └─────────────────────────────┘
						
# Linux object lifecycle tracing
# Create a temporary file to observe object creation and deletion

# Watch VFS objects being created and destroyed
sudo bpftrace -e '

Access via WinObj / WinObjEx64

On Windows, the Sysinternals tool WinObj (by Mark Russinovich) provides a graphical explorer of the entire Object Manager namespace. WinObjEx64 is an open-source alternative with additional features like security descriptor inspection.

When using WinObjEx64, a user can: - Browse the hierarchical object tree ( \ , \Sessions , \BaseNamedObjects ) - Inspect object attributes (name, type, reference counts) - View security descriptors (owner, D ACL , S ACL ) - Create/destroy test objects - Symbolic link tracing (right-click -> "Resolve Link")

The Linux equivalent is the combination of /proc , /sys , and /dev filesystems: 

# Linux "WinObj" — exploring the kernel object namespace

# 1. Browse all registered filesystem types (like ObjectTypes directory)
cat /proc/filesystems
# nodev   sysfs
# nodev   rootfs
# nodev   bdev
# nodev   proc
# nodev   tmpfs
#         ext4
#         btrfs

# 2. Browse kernel objects via sysfs (like \Device and \Driver)
ls /sys/devices/
ls /sys/class/
ls /sys/kernel/

# 3. Browse /proc like \BaseNamedObjects and \Sessions
ls /proc/ | head -20          # PIDs like session directories
ls /proc/self/                 # Current process "session"

# 4. Inspect kernel slab objects (like Object Manager stats)
sudo cat /proc/slabinfo | awk '{if($3>0) print $1,$3}' | head -20
# dentry 123456
# inode_cache 87654
# file 43210

# 5. /dev is the Linux "DOS device namespace" analogue
ls -la /dev/disk/by-uuid/       # Like \??\Volume{...} symbolic links
ls -la /dev/disk/by-path/      # Like \Device\HarddiskVolume...

Abuse and Attack Patterns

Named Pipe Squatting - Windows-specific attack where a malicious process creates a named pipe with the same name as a legitimate service's pipe, intercepting client connections: 

Victim                         Attacker        Legitimate Service
  │                               │                    │
  │  CreateFile("\\\\.\\pipe\\svc")│                   │
  ├──────────────────────────────►│                    │
  │                               │  (owns pipe)       │
  │  WriteFile(request)           │                    │
  ├──────────────────────────────►│  ← steals data     │
  │  ReadFile(response) ← faked   │                    │
  │◄──────────────────────────────┤                    │

Section Object Races - racing between a section object creation and its content validation. An attacker maps a shared memory section, writes malicious data, and a privileged process reads it - all between checks.

Linux equivalents

# Linux named pipe squatting scenario
# Attacker creates a UNIX socket before the legitimate daemon starts
# The filesystem namespace acts as the synchronization point

# Legitimate service expects /run/myapp/api.sock
# Attacker:
mkdir -p /run/myapp
socat UNIX-LISTEN:/run/myapp/api.sock,fork EXEC:'/bin/cat /etc/shadow'

# Detect squatting by comparing process ownership
lsof /run/myapp/api.sock
ss -xlp | grep /run/myapp/api.sock

# Section object race equivalent: TOCTOU on shared memory
# Attacker mmaps a file, bait-and-switches the content between check and use
# Detection: use inotify to watch file modifications, auditd for mmap syscalls

Linux /proc and /sys Equivalent

While Linux lacks a centralized Object Manager, the VFS-based /proc and /sys pseudo-filesystems collectively serve the same purpose - a discoverable, hierarchical namespace for kernel objects: 

Windows Object Manager               Linux Equivalent
═══════════════════════════════════════════════════════
\                                    / (VFS root)
\BaseNamedObjects                    /proc (per-process), /dev/shm (IPC)
\Device\                             /dev/
\Driver\                             /sys/module/
\FileSystem\                         /proc/filesystems
\GLOBAL??\                           /dev/disk/by-*
\KnownDlls\                          /usr/lib/ (but no section objects)
\ObjectTypes\                        /proc/filesystems, /sys/class/
\Sessions\N\                         /proc/PID/ns/ (namespace fd)
\??\C:                               /dev/sda1 or /dev/nvme0n1p1

Object Directory                     directory inode + dentry hash
SymbolicLink                         symlink inode
Event                                eventfd (anon), /dev/shm/sem.X (named)
Mutant                               pthread mutex (anon), futex (anon)
Semaphore                            sem_t (anon), semget() (named)
Section                              memfd_create() (anon), shmget() (named)
Process                              /proc/PID/ directory
Thread                               /proc/PID/task/TID/ directory
Job                                  /sys/fs/cgroup/<controller>/<name>/
Token                                (no unified — struct cred per task)
File                                 struct file → anonymous fd
						
# Explore Linux kernel objects like WinObj
# ── Process objects ──
ls /proc/$$/fd/                    # Open file handles
ls /proc/$$/fdinfo/                # Handle details (flags, position)
cat /proc/$$/status | head -20     # Process metadata

# ── Thread objects ──
ls /proc/$$/task/                  # Thread group members
cat /proc/$$/task/*/status | grep -E "^Name:|^Pid:|^Tgid:"

# ── IPC objects ──
ls /dev/shm/                       # POSIX shared memory sections
ls /dev/mqueue/                    # POSIX message queues (need mounting)
ipcs -a                            # System V semaphores, shared memory, msg queues

# ── Section objects ──
# memfd_create creates anonymous sections; tmpfs provides named
mount | grep tmpfs
ls /run/user/$(id -u)/             # per-user tmpfs (like per-session namespace)

# ── Device objects ──

Challenge

Write a Go tool that lists the objects behind the current process's handles by reading /proc/self/fd . Open a file, a pipe, a TCP socket, and an anonymous inode (for example an eventfd or epoll instance) so all four types appear, then classify each handle by its readlink target. 

package main

import (
	"fmt"
	"os"
	"path/filepath"
	"sort"
	"strings"
)

func objectType(target string) string {
	switch {
	case strings.HasPrefix(target, "socket:"):
		return "socket"
	case strings.HasPrefix(target, "pipe:"):
		return "pipe"
	case strings.HasPrefix(target, "anon_inode:"):
		return "anon-inode"
	case strings.HasPrefix(target, "memfd:"):
		return "memfd"
	default:
		return "file"
	}
}

func main() {
	entries, err := os.ReadDir("/proc/self/fd")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	counts := make(map[string]int)
	names := make([]string, 0, len(entries))
	for _, e := range entries {
		target, err := os.Readlink(filepath.Join("/proc/self/fd", e.Name()))
		if err != nil {
			continue
		}
		kind := objectType(target)
		counts[kind]++
		names = append(names, fmt.Sprintf("handle %-3s %-11s %s", e.Name(), kind, target))
	}

	sort.Strings(names)
	for _, line := range names {
		fmt.Println(line)
	}
	for kind, n := range counts {
		fmt.Printf("%-11s %d handles\n", kind, n)
	}
}

Run it with go run main.go , then close one object at a time and re-run it to watch the handle count fall. A pipe with no remaining handle is freed immediately, but a named System V shm segment or a memfd can outlive its handles.
