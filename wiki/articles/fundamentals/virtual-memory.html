Virtual Memory

Page tables, TLB, page faults, mmap() internals, malloc() backend, /proc/PID/maps dissection, huge pages, ASLR, overcommit, and the OOM killer.

Overview

Every process on Linux runs on its own virtual address space, but the physical RAM underneath is shared, fragmented, and limited. Virtual memory is the translation layer that turns virtual addresses into physical frames, isolates processes from each other, and lets the kernel overcommit memory safely. This article follows the path from a virtual address through the page tables and the TLB, explains how mmap() and malloc() obtain memory, and shows how to read the kernel's own accounting in /proc/PID/maps , smaps , and pagemap . After reading it you can inspect any process's memory map and explain where its pages actually live.

Why Virtual Memory Exists

Every process on Linux sees a private, contiguous address space - typically 128 TiB on x86-64 (47-bit virtual addresses). In reality, physical RAM is shared by all processes, fragmented across DIMMs, and interspersed with memory-mapped I/O holes. Virtual memory solves four problems:

  1. Isolation : Process A cannot read/write Process B's memory. One crashing process cannot corrupt the kernel or other processes.
  2. Abstraction : Every program can assume its code starts at the same virtual address (0x400000 for traditional executables, 0x555555554000 for PIEs). The linker and loader don't need to know about physical memory layout.
  3. Overcommit : Processes can request more virtual memory than available physical RAM. Physical pages are allocated on first write (demand paging).
  4. Shared memory : The same physical page (e.g., libc code) can be mapped into multiple processes simultaneously.

Virtual -> Physical Translation

The CPU 's Memory Management Unit (MMU) translates every virtual address to a physical address on every memory access. If the translation fails (no page mapped, insufficient permissions), the MMU raises a page fault.

Virtual Address (48 bits on x86-64)

PML4 PDPT PD PT Offset
(9 bit) (9 bit) (9 bit) (9 bit) (12 bit) 
Page Table Walk:
                                       
CR3 ──► PML4 ──► PDPT ──► PD ──► PT ──► Physical Page
        │        │       │      │
        ▼        ▼       ▼      ▼
    4KiB page of 512 x 8-byte entries per level
    Each entry points to next level's page or final physical page

   PML4E     PDPTE      PDE       PTE        Physical address
   [47:39]   [38:30]    [29:21]   [20:12]    [frame 40 bits] + [offset 12 bits]
						
# Examine page table entries via /proc/PID/pagemap
# Each entry is 8 bytes:
# bit 63 = page present
# bit 62 = swapped
# bits 54-0 = physical frame number (PFN)
sudo python3 -c "
import os, struct

def virt_to_phys(pid, vaddr):
    pagemap_path = f'/proc/{pid}/pagemap'
    pagesize = os.sysconf('SC_PAGE_SIZE')
    offset = (vaddr // pagesize) * 8
    
    with open(pagemap_path, 'rb') as f:
        f.seek(offset)
        entry = struct.unpack('Q', f.read(8))[0]
    
    present = bool(entry & (1 << 63))
    pfn = entry & ((1 << 55) - 1)  # bits 54:0

    if present:
        return (pfn * pagesize) + (vaddr % pagesize)
    return None

# id() of a live CPython object is its virtual address
page = bytearray(4096)
phys = virt_to_phys(os.getpid(), id(page))
print(f'virtual: {id(page):#x} physical: {phys}')
"

TLB - Translation Lookaside Buffer

A full 4-level page table walk requires 4 memory accesses - far too slow for every instruction fetch and data access. The TLB is a small, fast, CPU -internal cache of recently used virtual-to-physical translations. 

Virtual Address
      │
      ▼
  ┌──────┐
  │ TLB  │  ← Checked first (parallel with L1 cache)
  │ Look │
  └──────┘
     │
  Hit│    Miss
     │     │
     ▼     ▼
  Return  4-level page table walk (4+ memory accesses)
  phys     │
  addr     ▼
         Load PTE into TLB
           │
           ▼
         Retry TLB lookup (now hits)
TLB Level Typical Size Latency
L1 Data TLB 64 entries 1 cycle
L1 Instruction TLB 128 entries 1 cycle
L2 Unified TLB (STLB) 1024-2048 entries 5-10 cycles

A single 4 KiB page covers only 2 MiB of virtual space when the TLB has 512 entries. Huge pages reduce TLB pressure significantly.

Page Faults

A page fault occurs when the MMU cannot translate the virtual address. The kernel's page fault handler ( do_page_fault ) determines the cause:

Fault Type Condition Kernel Action
Minor (soft) Page exists in physical memory but PTE not set (e.g., copy-on-write, lazy allocation) Just update PTE; very fast
Major (hard) Page on disk (swap, mmap'd file not cached) I/O read from disk; slow
Invalid Address not in any VMA, or permission mismatch SIGSEGV - segmentation fault 
# Time page faults for a process
/usr/bin/time -v ls / >/dev/null 2>&1
# Output includes:
#   Minor (reclaiming a frame) page faults: 142
#   Major (requiring I/O) page faults: 0

# Monitor page faults in real time with perf
perf stat -e minor-faults,major-faults ls -R /usr/share >/dev/null

Demand paging: When mmap() creates a mapping, the kernel reserves virtual address space but does NOT allocate physical pages. Physical pages are assigned on first access (read or write), triggering a minor page fault. This is why mmap() is fast even for large mappings.

mmap() - The Memory Mapping Workhorse

mmap() creates a new mapping in the process's virtual address space. It's the foundation for malloc() (large allocations), shared memory, file I/O, and stack/guard page creation. 

#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

int main() {
    // 1. Anonymous mapping (backed by zero pages, not a file)
    size_t size = 4096 * 10;  // 10 pages
    void* anon = mmap(NULL, size, PROT_READ | PROT_WRITE,
                      MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (anon == MAP_FAILED) { perror("mmap anon"); return 1; }

    strcpy(anon, "Hello from anonymous mmap!");
    printf("Anonymous: %s\n", (char*)anon);
    munmap(anon, size);

    // 2. File-backed mapping (maps file contents to memory)
    int fd = open("/etc/hostname", O_RDONLY);
    if (fd == -1) { perror("open"); return 1; }

    off_t file_size = lseek(fd, 0, SEEK_END);
    void* file_map = mmap(NULL, file_size, PROT_READ,
                           MAP_PRIVATE, fd, 0);
    if (file_map == MAP_FAILED) { perror("mmap file"); return 1; }

    printf("File contents via memory: %.*s\n", (int)file_size, (char*)file_map);
    munmap(file_map, file_size);
    close(fd);

    return 0;
}
						
gcc -o mmap-demo mmap-demo.c && ./mmap-demo

mmap Flags

Flag Meaning
MAP_PRIVATE Copy-on-write: modifications are private; not visible to other processes or written to file
MAP_SHARED Modifications are visible to other processes and written back to file
MAP_ANONYMOUS Not backed by a file; fd must be -1; pages initialized to zero
MAP_FIXED Place mapping at exactlyaddr; clobbers existing mappings (dangerous)
MAP_FIXED_NOREPLACE Like MAP_FIXED but fails if anything exists ataddr(safer)
MAP_POPULATE Pre-fault pages (read them in now, not on-demand)
MAP_LOCKED Lock pages in memory (like mlock)
MAP_GROWSDOWN Used for stack - mapping grows downward on fault
MAP_HUGETLB Use huge pages for this mapping

Protection Flags

Flag Effect
PROT_NONE No access - page cannot be read, written, or executed
PROT_READ Readable
PROT_WRITE Writable
PROT_EXEC Executable
PROT_READ | PROT_WRITE Read + Write (typical for data)

malloc() Internals

malloc() is a user-space memory allocator, not a syscall. It manages a pool of memory obtained from the kernel through two mechanisms: 

malloc(size) called:
    │
    ▼
┌──────────────────────────────────────┐
│  size ≤ 128 KiB (adjustable)         │
│  │                                   │
│  ▼                                   │
│  Use arena (via sbrk()):             │
│  - Moves program break upward        │
│  - Fast: no kernel syscall needed    │
│  - Freed memory can't be returned    │
│    to OS easily (fragmentation)      │
└──────────────────────────────────────┘
    │
    ▼ size > 128 KiB
┌──────────────────────────────────────┐
│  Use mmap(MAP_ANONYMOUS):            │
│  - Separate mapping per allocation   │
│  - munmap() returns memory to OS     │
│  - Slightly more overhead            │
└──────────────────────────────────────┘
						
/* malloc-demo.c */
#include <stdlib.h>
#include <string.h>

int main() {
    void *small = malloc(1000);        /* served from the main arena */
    void *large = malloc(200 * 1024);  /* above the mmap threshold */
    memset(small, 0, 1000);
    memset(large, 0, 200 * 1024);
    free(small);
    free(large);
    return 0;
}

/proc/PID/maps - Reading the Memory Map

Every process exposes its complete virtual memory layout via /proc/PID/maps . Each line represents one virtual memory area ( VMA ). 

cat /proc/self/maps
						
// C program that prints its own memory map
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>

int global_init = 42;
int global_uninit;
const char* const_str = "I am in .rodata";

int main() {
    char stack_var = 'S';
    char* heap_var = malloc(64);
    strcpy(heap_var, "heap data");

    printf("PID: %d\n", getpid());
    printf("Text (main):          %p\n", main);
    printf("Read-only data:       %p\n", const_str);
    printf("Data (initialized):   %p\n", &global_init);
    printf("BSS (uninitialized):  %p\n", &global_uninit);
    printf("Heap:                 %p\n", heap_var);
    printf("Stack:                %p\n", &stack_var);

    printf("\n--- /proc/self/maps ---\n");
    FILE* f = fopen("/proc/self/maps", "r");
    char line[256];
    while (fgets(line, sizeof(line), f))
        fputs(line, stdout);
    fclose(f);

    free(heap_var);
    return 0;
}

/proc/PID/smaps

While /proc/PID/maps shows what is mapped, /proc/PID/smaps shows how much of each mapping is actually used: 

cat /proc/$$/smaps | head -50
Field Meaning
Size Total size of the mapping
KernelPageSize Page size the kernel uses (4 KiB)
MMUPageSize Page size the MMU uses (4 KiB)
Rss Resident Set Size - pages actually in RAM
Pss Proportional Set Size - RSS divided by number of processes sharing the page
Shared_Clean Clean pages shared with other processes
Shared_Dirty Dirty pages shared with other processes
Private_Clean Private clean pages (code, read-only data)
Private_Dirty Private dirty pages (modified heap, stack, data)
Referenced Pages marked as accessed
Anonymous Pages not backed by a file (heap, stack)
LazyFree Pages marked for lazy freeing
AnonHugePages Transparent huge pages used
Swap Pages swapped to disk
SwapPss Proportional swap size
Locked Pages locked in RAM (mlock) 
# Sum up RSS for a process
awk '/^Rss:/{sum+=$2} END{print sum " kB"}' /proc/$$/smaps

# Sum up PSS (precise memory accounting)
awk '/^Pss:/{sum+=$2} END{print sum " kB"}' /proc/$$/smaps

# Private dirty pages (writable memory unique to this process)
awk '/^Private_Dirty:/{sum+=$2} END{print sum " kB"}' /proc/$$/smaps

Huge Pages

Default page size on x86-64 is 4 KiB. With 128 TiB of virtual space, a process that touches 10 GiB of RAM needs~2.6 million page table entries. Huge pages reduce this by factors of 512 (2 MiB pages) or 262144 (1 GiB pages).

Page Size PTE entries for 10 GiB TLB coverage
4 KiB ~2,621,440 PTEs 2 MiB (512 entries)
2 MiB ~5,120 PDEs 1 GiB (512 entries)
1 GiB ~10 PDPTEs 512 GiB (512 entries) 
# Check huge page configuration
cat /proc/meminfo | grep -i huge
# HugePages_Total:       0     ← Pre-allocated (reserved) huge pages
# HugePages_Free:        0
# Hugepagesize:       2048 kB  ← 2 MiB huge pages

# Allocate huge pages at boot (kernel cmdline):
# hugepages=512 hugepagesz=2M

# Or at runtime:
echo 512 | sudo tee /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages

# Transparent Huge Pages (THP) — kernel automatically promotes 4K pages to 2M
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never

# Use huge pages explicitly in mmap():
#include <sys/mman.h>
void* ptr = mmap(NULL, 2*1024*1024, PROT_READ|PROT_WRITE,
                 MAP_PRIVATE|MAP_ANONYMOUS|MAP_HUGETLB, -1, 0);

ASLR

ASLR randomizes the base addresses of memory regions to make exploitation harder. Without ASLR, every program's stack, heap, and libraries are at predictable addresses. 

# Check ASLR status
cat /proc/sys/kernel/randomize_va_space
# 0 = No randomization
# 1 = Randomize stack, mmap, VDSO (conservative)
# 2 = Full randomization + brk() (default on ArchLinux)

# Demonstrate ASLR — run twice, observe different addresses
for i in 1 2 3; do
    cat /proc/self/maps | grep -E 'heap|stack|libc' | head -3
    echo "---"
done

What ASLR Randomizes

Region Randomized? Entropy (bits)
Executable (PIE) Yes (if PIE) 28 bits
Shared libraries Yes 28 bits
Stack Yes 22 bits
Heap (brk) Yes (mode 2) 13 bits
mmap() base Yes 28 bits
VDSO Yes 28 bits

Memory Overcommit and the OOM Killer

Linux, by default, allows processes to request more memory than the system physically has (overcommit). Memory is only assigned when pages are actually written to (demand paging + copy-on-write). 

cat /proc/sys/vm/overcommit_memory
# 0 = Heuristic overcommit (default) — kernel estimates if enough RAM+swap
# 1 = Always overcommit — processes can allocate unlimited virtual memory
# 2 = No overcommit — refuse allocations that exceed RAM + swap

cat /proc/sys/vm/overcommit_ratio
# Percentage of physical RAM allowed when overcommit_memory = 2
# Default: 50 → total allocatable = RAM * (50/100) + swap

# View overcommit state
cat /proc/meminfo | grep -i commit
# CommitLimit:     Total virtual memory that can be allocated
# Committed_AS:    Total virtual memory currently requested by all processes

The OOM Killer: When the kernel runs out of physical memory and cannot reclaim pages, it invokes the OOM (Out Of Memory) killer. It selects a process to kill based on a heuristic score: 

# OOM score of a process (0 = never killed, 1000 = first to die)
cat /proc/$$/oom_score

# OOM adjustment value (-1000 to 1000; lower = less likely to be killed)
cat /proc/$$/oom_score_adj

# Protect a critical daemon from OOM:
echo -1000 | sudo tee /proc/$(pidof sshd)/oom_score_adj

# Make a process the OOM target:
echo 1000 | sudo tee /proc/$(pidof misbehaving-app)/oom_score_adj

# Check OOM killer logs
dmesg | grep -i 'oom\|killed'
journalctl -k | grep -i oom

The OOM score formula roughly: score = (total_RSS / total_RAM) * 1000 + oom_score_adj . The kernel picks the process with the highest oom_score that it can kill (not PID 1, not kernel threads, not with oom_score_adj = -1000 ).

Inspecting Page Tables with pagemap

# Read pagemap entries for a running process
# Each 8-byte entry contains PFN and flags:
sudo python3 << 'EOF'
import os, struct

pid = os.getpid()
page_size = os.sysconf('SC_PAGE_SIZE')

with open(f'/proc/{pid}/pagemap', 'rb') as f:
    # Read first 10 entries
    for i in range(10):
        f.seek(i * 8)
        entry = struct.unpack('Q', f.read(8))[0]
        present = bool(entry & (1 << 63))
        swapped = bool(entry & (1 << 62))
        soft_dirty = bool(entry & (1 << 55))
        exclusive = bool(entry & (1 << 56))
        pfn = entry & ((1 << 55) - 1)

        status = "PRESENT" if present else ("SWAPPED" if swapped else "ABSENT")
        extra = []
        if soft_dirty: extra.append("SOFT_DIRTY")
        if exclusive: extra.append("EXCLUSIVE")

        print(f"VPN {i:4d} → PFN {pfn:#010x} [{status}] {','.join(extra)}")
EOF

Verification Checklist

# 1. Check page size
getconf PAGE_SIZE

# 2. Examine your process memory map
cat /proc/self/maps | head -30
cat /proc/self/smaps | head -60

# 3. Count page faults since process start
cat /proc/$$/stat | awk '{print "Minor faults:", $10, "Major faults:", $12}'

# 4. Check ASLR status
cat /proc/sys/kernel/randomize_va_space

# 5. Check overcommit policy
cat /proc/sys/vm/overcommit_memory
cat /proc/meminfo | grep Commit

# 6. Huge pages status
cat /proc/meminfo | grep -i huge

# 7. Find physical address of a virtual address (needs root)
sudo cat /proc/$$/pagemap | xxd | head -4

# 8. Trace mmap/munmap/brk calls of a program
strace -e mmap,munmap,brk,mprotect ls 2>&1 | head -20

# 9. Check Transparent Huge Pages status
cat /sys/kernel/mm/transparent_hugepage/enabled

# 10. Memory usage summary of current shell
awk '/^(Vm|Rss)/{printf "%-20s %s kB\n", $1, $2}' /proc/$$/status

Challenge

Write a Go program that reports how much resident memory your process uses by parsing /proc/self/smaps . The starter sums nothing yet; complete the Pss parsing and confirm that touching a freshly allocated 8 MiB buffer increases the total: 

package main

import (
	"bufio"
	"fmt"
	"os"
	"strconv"
	"strings"
)

func totalPss(path string) (int, error) {
	f, err := os.Open(path)
	if err != nil {
		return 0, err
	}
	defer f.Close()

	total := 0
	scanner := bufio.NewScanner(f)
	for scanner.Scan() {
		line := scanner.Text()
		// TODO: for lines starting with "Pss:", parse the kB value
		//       (the second whitespace-separated field) and add it to total.
		_ = line
	}
	return total, scanner.Err()
}

func main() {
	before, err := totalPss("/proc/self/smaps")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	blob := make([]byte, 8<<20)
	for i := range blob {
		blob[i] = byte(i) // fault in every page
	}

	after, _ := totalPss("/proc/self/smaps")
	fmt.Printf("Pss before: %d kB\nafter:     %d kB\ndelta:     %d kB\n",
		before, after, after-before)
}

Run it with go run main.go and explain why delta is close to the buffer size. Then change the loop so it writes only every 4096th byte and explain why the delta shrinks.
