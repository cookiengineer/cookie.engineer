Threat Hunting

Proactively searching for attacker behaviour before alerts trigger, using a hypothesis-driven hunting methodology.

Overview

Threat hunting is the proactive search for attacker activity that automated detection missed. Instead of waiting for an alert, an analyst states a falsifiable hypothesis about a technique, queries the available telemetry, and either converts the finding into a detection or documents a gap. This article covers the hunting hypothesis, the PEAK methodology, the data sources a hunt depends on, and five techniques that turn raw logs into evidence.

Required Reading

  • Processes - process lifecycle, fork/exec, parent-child relationships
  • TCP - connection establishment, flags, state machine
  • DNS - resolution hierarchy, record types, tunneling detection

Concept

Detection waits for an alert. Hunting goes looking. Detection is reactive: something triggered a rule. Hunting is proactive: an analyst formulates a hypothesis about attacker behaviour and interrogates data to prove or disprove it.

The distinction matters: a detection gap exists when an attacker can perform a technique without triggering any rule. Hunting is how you find those gaps. Every successful hunt either confirms a hypothesis (and gets converted into a detection) or disproves it (and documents that the technique is not currently in use).

Hunting is not alert triage. If you are investigating an alert, you are doing incident response. Hunting starts with a hypothesis, not an alert.

The Hunting Hypothesis

Every hunt begins with a falsifiable statement:

> "An attacker has gained initial access and is using LOLBins for code execution on workstations."

This hypothesis makes four claims:

  • The attacker is already in the environment (breach assumption).
  • The technique is LOLBin execution.
  • The scope is workstations.
  • The claim is falsifiable: a thorough search either finds evidence or finds none.

Bad Hypotheses

Untestable or vague statements are not hunting hypotheses:

  • "We might have been compromised." Against what data, using what technique?
  • "Are we secure?" Unfalsifiable, so there is nothing to test.
  • "Let me look for suspicious things." Hunting without a hypothesis is just browsing logs.

The PEAK Framework

PEAK (Prepare, Execute, Act with Knowledge) is a threat hunting framework from Splunk. Each hunt moves through three stages, and knowledge feeds every stage rather than forming a fourth:

Prepare

Define the hypothesis, identify the required data sources, and verify the data is available at sufficient fidelity.

Execute

Query the data, apply hunt techniques, and identify anomalies.

Act

Investigate anomalies, decide whether they are malicious, and escalate true positives to incident response.

Knowledge, drawn from threat intelligence, business context, and prior hunts, is recorded throughout and reused in the next hunt. 

  Knowledge .................
     |          |            |
     v          v            v
  Prepare -> Execute ----> Act

Data Sources for Hunting

The quality of your hunt is bounded by the quality of your data. Required telemetry:

Data Source Key Fields What It Reveals
Process creation (Sysmon EID 1 / auditd execve) Image, CommandLine, ParentImage, User, IntegrityLevel What ran, how it was launched, who ran it
Network connections (Sysmon EID 3 / netflow) SourceIP, DestIP, DestPort, Protocol, Image What processes communicated externally
DNS queries (Sysmon EID 22 / DNS logs) QueryName, QueryResults, Image What domains were resolved, by which process
File creation/modification (Sysmon EID 11 / inotify) TargetFilename, Image, CreationUtcTime What files were written, by what process
Authentication (Windows EID 4624/4625 / auth.log) TargetUserName, LogonType, IpAddress, WorkstationName Who logged in, from where, using what method
WMI events (Sysmon EID 19/20/21) EventNamespace, Name, Query WMI-based lateral movement and persistence
Registry modifications (Sysmon EID 13) TargetObject, Details, Image Registry-based persistence
Scheduled tasks (Windows EID 4698 / cron) TaskName, TaskContent, User Persistence via scheduled tasks

Hunt Technique 1: Stack Counting

Count everything, then look at the bottom of the list. Rare events are more interesting than common events. 

-- Hunt: rare parent-child process relationships
-- Hypothesis: attacker is spawning unusual child processes from unexpected parents
SELECT
    parent_process_name,
    process_name,
    COUNT(*) AS occurrence_count
FROM process_creation_events
WHERE event_time > NOW() - INTERVAL '7 days'
  AND parent_process_name NOT IN ('Idle', 'System')
GROUP BY parent_process_name, process_name
ORDER BY occurrence_count ASC
LIMIT 100;
						
import pandas as pd

# Load process creation logs
df = pd.read_csv('process_events_7d.csv')

# Stack counting by parent-child combination
stacks = df.groupby(['ParentImage', 'Image']).size().reset_index(name='count')
stacks = stacks.sort_values('count')

# Rare combinations (bottom 1%)
threshold = stacks['count'].quantile(0.01)
rare_stacks = stacks[stacks['count'] <= threshold]

print(f"Total unique parent-child pairs: {len(stacks)}")
print(f"Rare pairs (<= {threshold} occurrences): {len(rare_stacks)}")
print("\nSuspicious combinations:")
print(rare_stacks.head(20))

Process Lineage Anomalies

Attackers often spawn processes from unusual parents. Legitimate processes have predictable parent-child relationships. Malicious ones don't. 

-- Hunt: processes spawned by unexpected parents
-- Hypothesis: web shells, exploits, and macro malware spawn processes from IIS, w3wp, Apache, or Office apps
SELECT
    parent_process_name,
    process_name,
    process_command_line,
    hostname,
    event_time
FROM process_creation_events
WHERE parent_process_name IN (
    'w3wp.exe', 'httpd', 'apache2',
    'WINWORD.EXE', 'EXCEL.EXE', 'OUTLOOK.EXE',
    'java.exe', 'tomcat8.exe'
)
AND process_name IN (
    'cmd.exe', 'powershell.exe', 'bash', 'sh',
    'net.exe', 'whoami.exe', 'nslookup.exe',
    'wmic.exe', 'cscript.exe', 'wscript.exe'
)
AND event_time > NOW() - INTERVAL '7 days';
						
-- Hunt: svchost.exe spawned from anywhere except services.exe
-- This is a massive red flag — svchost should ONLY be spawned by services.exe
SELECT hostname, parent_image, image, command_line, event_time
FROM process_creation_events
WHERE image LIKE '%\\svchost.exe'
  AND parent_image NOT LIKE '%\\services.exe'
  AND event_time > NOW() - INTERVAL '30 days';

Hunt Technique 3: Beacon Detection

C2 beacons connect at regular intervals. Normal user traffic is bursty. Finding periodicity in network connections is one of the most reliable hunting techniques. 

import pandas as pd
import numpy as np
from scipy.signal import find_peaks

def detect_beacons(df, min_connections=10, jitter_tolerance=0.3):
    """
    Detect C2 beaconing by analyzing connection timing intervals.
    Input: DataFrame with [src_ip, dst_ip, dst_port, timestamp] per connection.
    Returns: array of (src_ip, dst_ip, dst_port, periodicity_score).
    """
    beacons = []

    for (src, dst, port), group in df.groupby(['src_ip', 'dst_ip', 'dst_port']):
        if len(group) < min_connections:
            continue

        timestamps = sorted(group['timestamp'].values)
        deltas = np.diff(timestamps).astype(float)

        if len(deltas) == 0:
            continue

        mean_delta = np.mean(deltas)
        std_delta = np.std(deltas)

        # Low standard deviation relative to mean = regular intervals
        if mean_delta > 0:
            coefficient_of_variation = std_delta / mean_delta
            if coefficient_of_variation < jitter_tolerance:
                # Calculate periodicity score (0 = perfectly periodic, 1 = random)
                beacons.append({
                    'src_ip': src,
                    'dst_ip': dst,
                    'dst_port': port,
                    'connections': len(group),
                    'mean_interval': mean_delta,
                    'cv': coefficient_of_variation,
                    'score': 1.0 - coefficient_of_variation
                })

    return sorted(beacons, key=lambda x: x['score'], reverse=True)

# Example usage
df = pd.read_csv('netflow_7d.csv')
df['timestamp'] = pd.to_datetime(df['timestamp']).astype('int64') // 10**9
beacons = detect_beacons(df)
for b in beacons[:10]:
    print(f"{b['src_ip']} → {b['dst_ip']}:{b['dst_port']} "
          f"| {b['connections']} connections "
          f"| interval={b['mean_interval']:.1f}s "
          f"| score={b['score']:.2f}")

Hunt Technique 4: Rare DNS Queries

Most systems in an enterprise resolve a predictable set of domains. Deviations from this baseline are worth investigating. 

import pandas as pd
import tldextract
from collections import Counter

def rare_domain_analysis(dns_log, top_n=1000, rarity_threshold=5):
    """
    Find domains resolved by fewer than N hosts.
    Hypothesis: C2 domains or DGA domains are resolved by only one or two hosts.
    """
    df = pd.DataFrame(dns_log)
    df['domain'] = df['query'].apply(lambda q: '.'.join(tldextract.extract(q)[-2:]))

    # Count unique client IPs per domain
    client_counts = df.groupby('domain')['client_ip'].nunique().reset_index()
    client_counts.columns = ['domain', 'unique_clients']

    # Rare domains: resolved by few clients
    rare = client_counts[client_counts['unique_clients'] <= rarity_threshold]
    rare = rare.sort_values('unique_clients')

    # Exclude known infrastructure
    INFRA_DOMAINS = {'microsoft.com', 'windows.com', 'office.com',
                     'google.com', 'amazonaws.com', 'cloudflare.com'}
    rare = rare[~rare['domain'].str.contains('|'.join(INFRA_DOMAINS), na=False)]

    return rare

# Detect potential DGA (domain generation algorithm) domains
# DGA domains typically have high entropy and are unique per host
def detect_dga_domains(dns_data, entropy_threshold=3.5):
    import math
    results = []
    for domain in set(dns_data):
        if '.' not in domain:
            continue
        sld = domain.split('.')[-2]
        if len(sld) < 8:
            continue
        # Shannon entropy
        prob = [float(sld.count(c)) / len(sld) for c in set(sld)]
        entropy = -sum(p * math.log(p, 2) for p in prob)
        if entropy > entropy_threshold:
            results.append((domain, entropy))
    return sorted(results, key=lambda x: x[1], reverse=True)

Hunt Technique 5: LOLBin Usage

Living-off-the-land binaries are legitimate Microsoft-signed tools abused for malicious purposes. Their mere existence is not suspicious, but specific usage patterns are. 

-- Hunt: certutil downloading files (common malware download cradle)
SELECT hostname, user, command_line, event_time
FROM process_creation_events
WHERE image LIKE '%\\certutil.exe'
  AND command_line LIKE '%urlcache%'
  AND command_line LIKE '%split%'
  AND event_time > NOW() - INTERVAL '30 days';

-- Hunt: mshta executing remote scripts
SELECT hostname, user, command_line, event_time
FROM process_creation_events
WHERE image LIKE '%\\mshta.exe'
  AND (command_line LIKE '%http%' OR command_line LIKE '%javascript%')
  AND event_time > NOW() - INTERVAL '30 days';

-- Hunt: regsvr32 executing remote .sct files
SELECT hostname, user, command_line, event_time
FROM process_creation_events
WHERE image LIKE '%\\regsvr32.exe'
  AND command_line LIKE '%/i:%'
  AND (command_line LIKE '%http%' OR command_line LIKE '%scrobj.dll%')
  AND event_time > NOW() - INTERVAL '30 days';

Automated Hunting with Jupyter + pandas

# hunting_notebook.ipynb
import pandas as pd
import matplotlib.pyplot as plt
from datetime import datetime, timedelta

# Load 7 days of process events
START = datetime.now() - timedelta(days=7)
df = pd.read_parquet('process_events_7d.parquet')
df['timestamp'] = pd.to_datetime(df['timestamp'])

# Hunt 1: New processes that appeared in the last 24 hours
last_24h = df[df['timestamp'] > datetime.now() - timedelta(hours=24)]
last_7d_except_24h = df[df['timestamp'] <= datetime.now() - timedelta(hours=24)]

known_processes = set(last_7d_except_24h['image'].unique())
new_processes = last_24h[~last_24h['image'].isin(known_processes)]

print(f"=== New processes in last 24h: {len(new_processes)} ===")
print(new_processes[['hostname', 'user', 'image', 'command_line']].head(20))

# Hunt 2: Process launches at unusual hours (midnight-5am)
df['hour'] = df['timestamp'].dt.hour
unusual_hours = df[(df['hour'] >= 0) & (df['hour'] <= 5)]

# Focus on interactive processes (not services)
interactive_processes = unusual_hours[
    ~unusual_hours['image'].str.contains('svchost|system|services|lsass|csrss', case=False)
]
print(f"\n=== Processes launched 00:00-05:00: {len(interactive_processes)} ===")
print(interactive_processes[['hostname', 'user', 'image', 'hour']].value_counts().head(20))

# Hunt 3: Process count anomalies per host
avg_processes = df.groupby('hostname').size().reset_index(name='count')
avg = avg_processes['count'].mean()
std = avg_processes['count'].std()
anomalies = avg_processes[avg_processes['count'] > avg + 2 * std]
print(f"\n=== Hosts with unusually high process counts: {len(anomalies)} ===")
print(anomalies.sort_values('count', ascending=False))

Documenting Hunts

Every hunt produces a report, even (especially) the ones that find nothing:

# Hunt Report: LOLBin Execution from Office Applications
## Metadata
- Hunt ID: HUNT-2026-0626-001
- Author: analyst@org.local
- Date: 2026-06-26
- Hypothesis: Attackers are using phishing lures to execute LOLBins from Office document macros
- Data Sources: Sysmon Event ID 1 (process creation), 30 days
- MITRE ATT&CK: T1204.002, T1059.001

## Methodology
Queried all process creation events where parent process is an Office application
(WINWORD.EXE, EXCEL.EXE, POWERPNT.EXE) and child process is a known LOLBin
(cmd.exe, powershell.exe, wmic.exe, mshta.exe, certutil.exe).

## Results
- Total events analyzed: 847,293,104
- Events matching criteria: 12
- False positives: 12 (legitimate Office macros from finance department monthly reports)
- True positives: 0

## Findings
No malicious activity detected. The hypothesis is FALSE for this time period.
All 12 hits were traced to approved macros in FINANCE/MonthlyReports/ directory.

## Recommendations
1. Create exclusion for FINANCE/MonthlyReports/ macros to reduce noise.
2. Add SIGMA detection rule for this pattern with exclusions applied.
3. Re-run hunt monthly — TTP may be used in future campaigns.

## Detection Rule Created
[Link to Sigma rule: office_lolbin_spawn.yml]

Converting Hunts to Detections

When a hunt finds malicious activity, convert the methodology to a permanent detection:

# Hunt: LOLBin from Office ⇒ Detection: Sigma rule
title: LOLBin Execution from Office Application
id: a1b2c3d4-e5f6-7890-abcd-ef1234567890
status: stable
description: Detects LOLBin execution spawned by Office applications — commonly abused by phishing macros.
logsource:
  product: windows
  service: sysmon
detection:
  selection_parent:
    ParentImage|endswith:
      - '\WINWORD.EXE'
      - '\EXCEL.EXE'
      - '\POWERPNT.EXE'
      - '\OUTLOOK.EXE'
  selection_child:
    Image|endswith:
      - '\cmd.exe'
      - '\powershell.exe'
      - '\wmic.exe'
      - '\mshta.exe'
      - '\certutil.exe'
      - '\cscript.exe'
      - '\wscript.exe'
      - '\regsvr32.exe'
  condition: selection_parent and selection_child
falsepositives:
  - Approved macros from Finance department in FINANCE/MonthlyReports/ path
level: high

Challenge

Write a Go tool that reads a CSV of network connections from standard input and flags suspected C2 beaconing. Each row has the form src,dst,port,timestamp with an RFC3339 timestamp. Group connections by source, destination, and port, then compute the coefficient of variation of the inter-arrival times. A low value means regular intervals, so print every flow with at least ten connections and a coefficient below 0.3 , most regular first. 

package main

import (
	"encoding/csv"
	"fmt"
	"math"
	"os"
	"sort"
	"time"
)

type flow struct {
	times []time.Time
}

type beacon struct {
	key   string
	count int
	mean  float64
	cv    float64
	score float64
}

func main() {

	reader := csv.NewReader(os.Stdin)

	rows, err := reader.ReadAll()

	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	flows := make(map[string]*flow)

	for i, row := range rows {

		if i == 0 || len(row) < 4 {
			continue
		}

		stamp, err := time.Parse(time.RFC3339, row[3])

		if err != nil {
			continue
		}

		key := row[0] + "|" + row[1] + "|" + row[2]

		if _, ok := flows[key]; ok == false {
			flows[key] = &flow{}
		}

		flows[key].times = append(flows[key].times, stamp)

	}

	beacons := make([]beacon, 0)

	for key, f := range flows {

		if len(f.times) < 10 {
			continue
		}

		sort.Slice(f.times, func(a int, b int) bool {
			return f.times[a].Before(f.times[b])
		})

		deltas := make([]float64, 0, len(f.times)-1)

		for i := 1; i < len(f.times); i++ {
			deltas = append(deltas, f.times[i].Sub(f.times[i-1]).Seconds())
		}

		var sum float64

		for _, d := range deltas {
			sum += d
		}

		mean := sum / float64(len(deltas))

		if mean == 0 {
			continue
		}

		var variance float64

		for _, d := range deltas {
			variance += (d - mean) * (d - mean)
		}

		std := math.Sqrt(variance / float64(len(deltas)))
		cv := std / mean

		if cv < 0.3 {
			beacons = append(beacons, beacon{
				key:   key,
				count: len(f.times),
				mean:  mean,
				cv:    cv,
				score: 1.0 - cv,
			})
		}

	}

	sort.Slice(beacons, func(a int, b int) bool {
		return beacons[a].score > beacons[b].score
	})

	for _, b := range beacons {
		fmt.Printf("%-40s connections=%d mean=%.1fs cv=%.2f score=%.2f\n",
			b.key, b.count, b.mean, b.cv, b.score)
	}

}

  ts=$(date -u -d "@$((base + i * 30))" +%Y-%m-%dT%H:%M:%SZ)
  echo "10.0.0.5,203.0.113.9,8443,$ts" >> flows.csv
done
