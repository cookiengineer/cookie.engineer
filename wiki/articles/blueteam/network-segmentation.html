Network Segmentation

Architectural boundaries, VLAN s, VRFs, and firewall zones that contain attacker lateral movement.

Overview

Network segmentation is the practice of dividing a network into isolated zones with controlled communication paths between them. The goal is containment: if an attacker compromises a host in Zone A, they should not have unrestricted access to Zone B.

The historical approach - a flat network with a single perimeter firewall - is insufficient because once the perimeter is breached (phishing, VPN compromise, infected USB ), the attacker has unrestricted east-west movement across the entire internal network.

  • TCP Handshake - TCP flags, states, connection lifecycle
  • ARP - address resolution, ARP spoofing, broadcast domains

Core Principles

Defense in Depth

Multiple independent barriers. No single firewall or VLAN should be the sole security control.

Least Privilege for Networks

A host in zone X can talk to zone Y only if there is a documented operational requirement. The default is "no communication."

Bidirectional Firewalling

Rules must consider both directions. Allowing A -> B:443 does not mean B can initiate connections to A.

Jump Hosts / Bastions

Administrative access to sensitive zones should flow through a hardened intermediate host, never direct from user workstations.

Zone Models

Internet
   │
[External Firewall]
   │
   ├── DMZ (public services)
   │     ├── Web servers (public)
   │     ├── Mail relays
   │     └── Reverse proxies
   │
   ├── [Internal Firewall]
   │     │
   │     ├── Application Zone
   │     │     ├── App servers
   │     │     └── Message queues
   │     │
   │     ├── Data Zone
   │     │     ├── Database servers
   │     │     └── File servers
   │     │
   │     ├── Management Zone
   │     │     ├── Jump hosts / bastions
   │     │     ├── Monitoring (Nagios, Prometheus)
   │     │     └── Log aggregation
   │     │
   │     └── User Zone
   │           ├── Workstations
   │           └── Printers
   │
   └── [OT / IoT Zone]
         ├── SCADA / ICS
         └── Building management

Communication rules:

  • DMZ -> Internet: allowed (web servers serve public traffic)
  • Internet -> DMZ: only to specific ports on specific IP addresses
  • DMZ -> App Zone: only on app-specific ports (for example 8080)
  • DMZ -> Data Zone: blocked (DMZ hosts should never touch databases directly)
  • App Zone -> Data Zone: only on database ports (for example 3306, 5432)
  • User Zone -> Management Zone: blocked (except via bastion)
  • Management Zone -> All: allowed for monitoring/management purposes
  • OT/ IoT -> All: blocked by default, specific exceptions only

VLANs (802.1Q)

VLAN s provide Layer 2 isolation. A switch assigns each port to a VLAN . Traffic between VLAN s must go through a Layer 3 device (router/firewall).

Switch Configuration (conceptual — switch-vendor commands vary):

VLAN 10: DMZ         (10.0.10.0/24)
VLAN 20: Application (10.0.20.0/24)
VLAN 30: Database     (10.0.30.0/24)
VLAN 40: Management   (10.0.40.0/24)
VLAN 50: Users        (10.0.50.0/24)
VLAN 99: Native VLAN  (unused — should not carry data traffic)

VLAN security considerations:

# Always change the native VLAN to an unused VLAN
# The native VLAN carries untagged traffic — attackers can access it by sending untagged frames

# Disable Dynamic Trunking Protocol (DTP) on all access ports
# DTP allows a port to automatically become a trunk — VLAN hopping vector

# Use a dedicated "dead" VLAN for unused switch ports
# Do not leave ports in the default VLAN 1

# Enable BPDU guard on access ports to prevent rogue switch introduction

VRFs (Virtual Routing and Forwarding)

VRFs provide Layer 3 isolation by maintaining independent routing tables per VRF. Unlike VLAN s which separate at Layer 2, VRFs create completely separate routing domains - devices in different VRFs cannot communicate even with correct IP addressing unless explicitly routed.

# Create VRFs on Linux
sudo ip link add vrf-mgmt type vrf table 10
sudo ip link set vrf-mgmt up
sudo ip link set eth1 master vrf-mgmt

# Routes in VRF 10 are completely isolated from the default table
sudo ip route add 10.0.40.0/24 dev eth1 vrf vrf-mgmt

# Processes can bind to a specific VRF
ip vrf exec vrf-mgmt ssh admin@10.0.40.5

# Check VRF membership
ip link show vrf vrf-mgmt

Zero Trust Networking

Zero Trust inverts the segmentation model. Instead of "trust the internal network, distrust the external," ZT assumes compromise can happen anywhere and authenticates every connection.

Core principles:

  1. No implicit trust based on network location. An internal IP address is

not an authorization. 1. Microsegmentation: a perimeter around every workload, not just the network edge.

  1. Authentication and authorization per session: TLS , SPIFFE, and

JWT on every request. 1. Continuous monitoring and validation: trust scores and behavioral analysis.

# Example: Service mesh policy (Istio/Kubernetes context)
# Only payments-service can reach the ledger database
# Even other pods on the same node/VLAN cannot

apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: ledger-db-policy
  namespace: production
spec:
  selector:
    matchLabels:
      app: ledger-database
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/production/sa/payments-service"]
    to:
    - operation:
        ports: ["5432"]

Host-Level Segmentation

Even on a single Linux host, use netfilter to enforce zone boundaries:

# nftables.conf — Host-based segmentation rules

table inet segmentation {

    chain input {
        type filter hook input priority 0; policy drop;

        # Allow loopback (internal communication)
        iif lo accept

        # Allow established/related connections
        ct state established,related accept

        # Management interface (eth0 = management VLAN)
        iif eth0 ip saddr 10.0.40.0/24 tcp dport 22 accept  # SSH from mgmt
        iif eth0 ip saddr 10.0.40.0/24 tcp dport 9100 accept # Node exporter

        # Application interface (eth1 = app VLAN)
        iif eth1 ip saddr 10.0.20.0/24 tcp dport 8080 accept # App port

        # Everything else: drop and log
        log prefix "INPUT_DROP: " level warn
        counter drop
    }

    chain output {
        type filter hook output priority 0; policy drop;

        # Loopback
        oif lo accept

        # Established reverse traffic
        ct state established,related accept

        # App server can reach database in data zone
        oif eth2 ip daddr 10.0.30.0/24 tcp dport 5432 accept

        # DNS
        oif eth0 udp dport 53 accept

        log prefix "OUTPUT_DROP: " level warn
        counter drop
    }

    chain forward {
        type filter hook forward priority 0; policy drop;
        # This host is not a router — forward nothing
        counter drop
    }
}
						
# Apply nftables rules
sudo nft -f /etc/nftables.conf

# List current ruleset
sudo nft list ruleset

# Monitor drops in real time
sudo nft monitor

Network Namespace Isolation

Linux network namespaces provide complete network stack isolation within a single host. Each namespace has its own interfaces, routing table, and firewall rules.

# Create isolated namespaces for sensitive services
sudo ip netns add isolated-db
sudo ip netns add isolated-app

# Create virtual ethernet pairs connecting them
sudo ip link add veth-db type veth peer name veth-db-ns
sudo ip link add veth-app type veth peer name veth-app-ns

# Move one end of each pair into its namespace
sudo ip link set veth-db-ns netns isolated-db
sudo ip link set veth-app-ns netns isolated-app

# Configure interfaces
sudo ip addr add 10.99.0.1/30 dev veth-db
sudo ip netns exec isolated-db ip addr add 10.99.0.2/30 dev veth-db-ns

sudo ip addr add 10.99.1.1/30 dev veth-app
sudo ip netns exec isolated-app ip addr add 10.99.1.2/30 dev veth-app-ns

# Bring interfaces up
sudo ip link set veth-db up && sudo ip netns exec isolated-db ip link set veth-db-ns up
sudo ip link set veth-app up && sudo ip netns exec isolated-app ip link set veth-app-ns up

# Run a process in the isolated namespace
sudo ip netns exec isolated-db su - postgres -c 'postgres -D /var/lib/postgres/data'

# Verify isolation
sudo ip netns exec isolated-db ip addr show
sudo ip netns exec isolated-db ss -tulnp

NAC (Network Access Control)

NAC ensures only authorized and compliant devices connect to the network:

802.1X Port Authentication

A device must authenticate (RADIUS) before the switch opens the port.

# FreeRADIUS / hostapd integration with 802.1X on a Linux router
# /etc/hostapd/hostapd-wired.conf

interface=eth1
driver=wired
ieee8021x=1
auth_server_addr=127.0.0.1
auth_server_port=1812
auth_server_shared_secret=radius_secret

Segmentation for OT/IoT

Operational Technology and IoT devices require the most restrictive segmentation because: - They rarely receive security patches - They run embedded, often outdated, operating systems - They cannot run endpoint protection - Compromise can cause physical damage

# OT/IoT segmentation rules (nftables)
# These devices should ONLY communicate with their controller,
# never with the internet or other network segments

table inet ot_iot {

    chain forward {
        type filter hook forward priority 0; policy drop;

        # PLC can only talk to the SCADA controller on port 502 (Modbus)
        iifname "iot-vlan" oifname "scada-vlan" \
            ip saddr 10.0.100.0/24 ip daddr 10.0.90.10 \
            tcp dport 502 accept

        # SCADA controller can talk to PLCs
        iifname "scada-vlan" oifname "iot-vlan" \
            ip saddr 10.0.90.10 ip daddr 10.0.100.0/24 \
            tcp sport 502 accept

        # Building management can reach HVAC controller on BACnet (UDP 47808)
        iifname "mgmt-vlan" oifname "iot-vlan" \
            ip saddr 10.0.40.0/24 ip daddr 10.0.100.50 \
            udp dport 47808 accept

        ct state established,related accept

        # Everything else — including IoT → Internet — DROP silently
        counter drop
    }
}

Testing Segmentation

# Test reachability between segments
# From host A (10.0.20.5) to host B (10.0.30.10)

# TCP connectivity
nc -zv -w 2 10.0.30.10 5432

# Full port scan from allowed zone
nmap -sS -p 1-65535 10.0.30.10

# Test that specific ports are blocked
nc -zv -w 2 10.0.30.10 22
# Expected: Connection refused (or timeout)

# Check if ICMP is allowed between zones (it shouldn't be for most)
ping -c 1 -W 2 10.0.30.10

# Traceroute to verify path through firewall
traceroute -n -T -p 5432 10.0.30.10

Practical Deployment Order

Step 1: Network diagram — document every zone and required communication
Step 2: Assign VLANs/IP ranges to each zone
Step 3: Configure switch VLANs and trunk ports
Step 4: Deploy firewall rules between zones (start with logging only)
Step 5: Audit logs for 1-2 weeks (identify undocumented traffic)
Step 6: Add explicit rules for documented traffic
Step 7: Switch default policy to DROP for inter-zone traffic
Step 8: Never revert to the "allow everything first" approach

Detection

# Monitor zone-crossing violations
# iptables logging
iptables -A FORWARD -i vlan-users -o vlan-db -j LOG \
  --log-prefix "SEG_VIOLATION:user_to_db:" --log-level 4
iptables -A FORWARD -i vlan-users -o vlan-db -j DROP

# Check logs for violations
journalctl -k | grep SEG_VIOLATION

# nftables set for tracking violator IPs
nft add set inet segmentation violators { type ipv4_addr\; }
nft add rule inet segmentation forward \
  ip saddr @violators counter drop

# Add violating IPs to the set
nft add element inet segmentation violators { 10.0.50.42 }

Challenge

Write a Go tool that evaluates a flow against a default-deny zone policy. The tool maps source and destination addresses to zones by CIDR , looks the flow up in the allow list, and flags every denied east-west flow as a segmentation violation. Run it against a list of captured flows and confirm that the DMZ cannot reach the data zone.

package main

import (
	"bufio"
	"fmt"
	"net"
	"os"
	"strconv"
	"strings"
)

type zone struct {
	name  string
	block *net.IPNet
}

type allow struct {
	src  string
	dst  string
	port int
}

var zones = []zone{
	{"dmz", mustCIDR("10.0.10.0/24")},
	{"app", mustCIDR("10.0.20.0/24")},
	{"data", mustCIDR("10.0.30.0/24")},
	{"mgmt", mustCIDR("10.0.40.0/24")},
	{"users", mustCIDR("10.0.50.0/24")},
}

var policy = []allow{
	{"dmz", "app", 8080},
	{"app", "data", 5432},
	{"mgmt", "app", 22},
	{"mgmt", "data", 22},
}

func mustCIDR(s string) *net.IPNet {
	_, n, err := net.ParseCIDR(s)
	if err != nil {
		panic(err)
	}
	return n
}

func zoneOf(ip net.IP) string {
	for _, z := range zones {
		if z.block.Contains(ip) {
			return z.name
		}
	}
	return "external"
}

func allowed(src, dst string, port int) bool {
	for _, a := range policy {
		if a.src == src && a.dst == dst && a.port == port {
			return true
		}
	}
	return false
}

func main() {
	scanner := bufio.NewScanner(os.Stdin)
	violations := 0

	for scanner.Scan() {
		fields := strings.Fields(scanner.Text())
		if len(fields) != 3 {
			continue
		}
		src := net.ParseIP(fields[0])
		dst := net.ParseIP(fields[1])
		port, _ := strconv.Atoi(fields[2])
		sz := zoneOf(src)
		dz := zoneOf(dst)
		if allowed(sz, dz, port) {
			fmt.Printf("ALLOW %-8s -> %-8s :%d\n", sz, dz, port)
		} else {
			violations++
			fmt.Printf("DENY  %-8s -> %-8s :%d  SEGMENTATION VIOLATION\n", sz, dz, port)
		}
	}

	fmt.Printf("%d violations\n", violations)
}

Save the program as segcheck.go and feed it a list of flows:

cat > flows.txt <<'EOF'
10.0.10.5 10.0.20.7 8080
10.0.50.9 10.0.30.10 5432
10.0.40.2 10.0.30.10 22
10.0.10.5 10.0.30.10 5432
EOF

go run segcheck.go < flows.txt
