Web Enumeration

Systematic discovery of web application attack surface through directories, subdomains, virtual hosts, API s, and technology fingerprinting.

Overview

Enumeration maps the attack surface before any exploit is attempted. Every request returns a status code, size, timing, header set, and body that reveal something about the target, and the work is separating signal from the noise that brute-force tools produce. This article covers the baseline-first methodology, directory and virtual-host fuzzing, subdomain discovery, technology fingerprinting, and the sensitive files and API endpoints that are most often left exposed.

Required Reading

  • HTTP - HTTP methods, headers, status codes, request/response structure
  • DNS - DNS resolution, record types, subdomain delegation, zone transfers

The Enumeration Mindset

Web enumeration is not running a tool and accepting its output. It is the systematic reduction of unknown attack surface. Every request returns data - the status code, response size, response time, headers, and body all carry signal. The skill is extracting that signal.

Consider a target example.com . Before you send a single payload, the server has already told you its web server (Server header), its programming language (X-Powered-By), its cookie format (Set-Cookie), and possibly its framework (default error pages). A 404 from nginx looks different from a 404 from Apache. A 403 from a WAF looks different from a 403 from the application. These differences are the first footholds.

The HTTP Baseline

Before brute forcing, establish the baseline. Send known-good and known-bad requests and record every response attribute.

# Establish baseline — what does a 200, 404, 403, 500 look like?
curl -s -o /dev/null -w "%{http_code} %{size_download} %{redirect_url}" \
  -D - https://example.com/

# Known 404 — deliberately request something that doesn't exist
curl -s -o /dev/null -w "%{http_code} %{size_download}" \
  -D - https://example.com/this-does-not-exist-xyzzy123

# Known 403 — request a path that's normally blocked
curl -s -o /dev/null -w "%{http_code} %{size_download}" \
  -D - https://example.com/.git/config

# Request a known static file to get Content-Type, caching headers
curl -s -D - https://example.com/robots.txt

Record these in your notes. The baseline tells you when a response is anomalous. If the target serves a custom 404 with a 3KB body, then a 200 with a 500-byte body on a brute-forced path deserves investigation - even if the body says "not found."

Working with Custom Wordlists

Generic wordlists find generic paths. Target-specific wordlists find target-specific paths. cewl scrapes a website and builds a wordlist from its visible content.

# Generate a custom wordlist from target content
cewl https://example.com -d 3 -m 5 -w target-words.txt

# Include email addresses found on the site (often reveal usernames, internal naming)
cewl https://example.com -d 3 -m 5 -e --email_file target-emails.txt

# Combine with standard wordlists for breadth + depth
cat /usr/share/wordlists/dirb/common.txt target-words.txt | sort -u > combined.txt

# Generate a wordlist from all visible JavaScript files (API endpoints, routes)
curl -s https://example.com | grep -oP 'src="([^"]+\.js)"' | \
  sed 's/src="\|"//g' | while read url; do
    curl -s "$url" | grep -oP '["'\''](/[a-zA-Z0-9_/-]+)["'\'']' | \
    tr -d '"'\''/' | sort -u >> js-routes.txt
  done

Scrape error messages, form labels, URL parameters, and HTML comments - these contain the developer's vocabulary, which maps to the filesystem and API structure.

Directory and File Brute Forcing

Directory brute forcing sends HTTP requests for a list of paths and analyzes the responses. The tool matters less than the methodology: wordlist selection, filter configuration, and response interpretation.

gobuster - fast, concurrent, written in Go:

# Basic directory scan — extensions matter enormously
gobuster dir -u https://example.com \
  -w /usr/share/wordlists/dirb/common.txt \
  -x php,html,txt,bak,old,zip,tar.gz,sql,conf,config,log

# Fine-tuning with status code filters
gobuster dir -u https://example.com \
  -w /usr/share/seclists/Discovery/Web-Content/raft-large-directories.txt \
  -x php,html,asp,aspx \
  -s 200,204,301,302,307,401,403 \
  --exclude-length 3456 \
  -t 50

# Use patterns to filter out noise — match responses that differ from baseline
gobuster dir -u https://example.com \
  -w /usr/share/seclists/Discovery/Web-Content/directory-list-2.3-medium.txt \
  -x php,html,txt \
  -b 404,500

ffuf - faster, more flexible, filter by response size, word count, lines, or regex:

# ffuf with recursive filtering — ignore responses matching the 404 size
BASELINE_404=$(curl -s -o /dev/null -w '%{size_download}' \
  https://example.com/nonexistent-xyzzy)
ffuf -u https://example.com/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/raft-large-directories.txt \
  -fs "$BASELINE_404"

# Multi-extension fuzzing with ffuf
ffuf -u https://example.com/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-words.txt \
  -e .php,.html,.txt,.bak,.old,.zip,.sql,.conf \
  -fc 403,404

# Filter by word count to find pages with actual content
ffuf -u https://example.com/FUZZ \
  -w /usr/share/wordlists/dirb/common.txt \
  -fw 12 \
  -t 100

Response size analysis - the most reliable filter:

# Step 1: Determine baseline 404 response size
for i in $(seq 1 20); do
  curl -s -o /dev/null -w '%{size_download}\n' \
    "https://example.com/$(head -c 8 /dev/urandom | base64 | tr -dc 'a-z')"
done | sort -n | uniq -c
# Most common = baseline 404 size. Anything different warrants investigation.

# Step 2: Run directory scan, output only results with non-baseline size
gobuster dir -u https://example.com \
  -w /usr/share/wordlists/dirb/common.txt \
  --exclude-length "$BASELINE_404_SIZE"

Virtual Host Enumeration

Virtual hosts serve different content based on the Host header. A single IP can host hundreds of applications. Subdomain enumeration finds the names; VHost enumeration finds all content behind a given IP .

The key insight: when you request a VHost that doesn't exist, the server returns a default response. The baseline default response has a characteristic size and content. Brute-forcing VHosts means sending requests with different Host headers and finding responses that differ from the default.

# Step 1: Establish the default VHost baseline
curl -s -H "Host: nonexistent-$(head -c 6 /dev/urandom | base64 | tr -dc 'a-z').example.com" \
  https://192.168.1.100/ -o /dev/null -w '%{size_download}'
# This is the baseline. Record it.

# Step 2: Fuzz VHosts with ffuf
ffuf -u https://192.168.1.100/ \
  -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
  -H "Host: FUZZ.example.com" \
  -fs "$BASELINE_SIZE"

# ffuf detecting VHosts by response body content difference
ffuf -u https://192.168.1.100/ \
  -w /usr/share/seclists/Discovery/DNS/bitquark-subdomains-top100000.txt \
  -H "Host: FUZZ.example.com" \
  -fr "Welcome to nginx" \
  -t 100

VHost enumeration via gobuster

gobuster vhost -u https://example.com \
  -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
  --append-domain \
  --exclude-length "$BASELINE_SIZE"

DNS-based subdomain enumeration runs first - it finds subdomains that resolve to IP s. VHost enumeration follows - it finds subdomains that share IP s with the target.

Subdomain Enumeration

Subdomains expose development servers, staging environments, admin panels, API s, and forgotten services. Multiple techniques exist because no single technique finds everything.

Certificate Transparency (CT) Logs - every publicly-trusted certificate is logged. The log includes all subdomain names in the certificate. This is passive and leaves zero traces on the target.

# crt.sh — query certificate transparency logs
curl -s "https://crt.sh/?q=%25.example.com&output=json" | \
  jq -r '.[].name_value' | sed 's/\\n/\n/g' | sort -u > ct-subdomains.txt

# Certspotter API
curl -s "https://api.certspotter.com/v1/issuances?domain=example.com&include_subdomains=true&expand=dns_names" | \
  jq -r '.[].dns_names[]' | sort -u

# Manual inspection of a certificate for SANs
openssl s_client -connect example.com:443 -servername example.com 2>&1 | \
  openssl x509 -noout -text | grep -A1 "Subject Alternative Name" | \
  tr ',' '\n' | sed 's/DNS://g' | tr -d ' ' | sort -u

DNS brute forcing - resolves candidate subdomains and records A/AAAA/CNAME records:

# Subfinder — fast, uses multiple passive sources
subfinder -d example.com -all -o subfinder-results.txt

# Amass — deeper, passive + active enumeration modes
amass enum -passive -d example.com -o amass-passive.txt
amass enum -active -d example.com -brute -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
  -o amass-active.txt

# Pure DNS resolution with dnsrecon
dnsrecon -d example.com -t brt -D /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt

# MassDNS — fastest bulk resolver, read wordlist, resolve all
massdns -r /usr/share/seclists/Discovery/DNS/resolvers.txt \
  -t A -o S -w massdns-results.txt \
  <(sed 's/$/.example.com/' /usr/share/seclists/Discovery/DNS/bitquark-subdomains-top100000.txt)

Permutation scanning - discovered subdomains suggest naming patterns:

# Given subdomains: dev.example.com, staging.example.com, api.example.com
# Generate permutations: dev-api, api-dev, dev-staging, api-staging, admin-dev, etc.
gotator -sub subdomains.txt -perm permutations.txt -depth 2 -numbers 3 -md \
  | massdns -r /usr/share/seclists/Discovery/DNS/resolvers.txt -t A -o S -w permutations-resolved.txt

Passive sources - search engines, DNS DB, SecurityTrails:

# gau (Get All URLs) — pulls from Wayback Machine, CommonCrawl, URLScan
gau example.com | grep -oP 'https?://([a-zA-Z0-9.-]+\.)?example\.com' | \
  sed -E 's|https?://||' | sort -u

# waybackurls — Wayback Machine URLs
waybackurls example.com | grep -oP 'https?://([a-zA-Z0-9.-]+\.)?example\.com' | \
  sed -E 's|https?://||' | sort -u

# Full enumeration script combining passive + active
#!/bin/bash
TARGET="example.com"
WORDLIST="/usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt"
RESOLVERS="/usr/share/seclists/Discovery/DNS/resolvers.txt"

mkdir -p recon/$TARGET

# Passive subdomain discovery
subfinder -d "$TARGET" -all -o "recon/$TARGET/subfinder.txt"
amass enum -passive -d "$TARGET" -o "recon/$TARGET/amass-passive.txt"
curl -s "https://crt.sh/?q=%25.$TARGET&output=json" | \
  jq -r '.[].name_value' | sed 's/\\n/\n/g' | sort -u > "recon/$TARGET/crtsh.txt"

# Merge, deduplicate, and resolve
cat "recon/$TARGET/"subfinder.txt \
    "recon/$TARGET/"amass-passive.txt \
    "recon/$TARGET/"crtsh.txt | sort -u > "recon/$TARGET/subdomains-passive.txt"
massdns -r "$RESOLVERS" -t A -o S -w "recon/$TARGET/resolved.txt" \
  "recon/$TARGET/subdomains-passive.txt"

# Brute force remaining
massdns -r "$RESOLVERS" -t A -o S -w "recon/$TARGET/bruteforce-resolved.txt" \
  <(sed "s/$/.$TARGET/" "$WORDLIST")

Technology Stack Fingerprinting

Knowing the stack tells you which exploits to attempt. PHP applications are vulnerable to different things than Python or Node.js applications. Apache behaves differently from nginx under certain path traversal scenarios. WordPress has well-known plugin vulnerabilities; a custom framework requires source code review.

Header-based fingerprinting

# Comprehensive header inspection
curl -s -D - https://example.com/ -o /dev/null

# Key headers to inspect:
# Server:          reveals web server and sometimes version
# X-Powered-By:    reveals backend technology (PHP/7.4.3, Express, ASP.NET)
# Set-Cookie:      PHPSESSID → PHP, JSESSIONID → Java/Tomcat, ASP.NET_SessionId → .NET
# X-AspNet-Version: direct .NET version disclosure
# X-Generator:     reveals CMS (WordPress, Drupal)
# X-Drupal-Cache:  Drupal
# Link:            WordPress REST API headers

# Detect nginx vs Apache via URL encoding behavior
# Apache decodes %2e → . before matching location blocks
# nginx rejects encoded sequences with 404 before decoding
curl -s -o /dev/null -w '%{http_code}' 'https://example.com/static/%2e%2e/etc/passwd'

# Detect IIS via method case sensitivity
curl -X 'get' -s -o /dev/null -w '%{http_code}' https://example.com/
# nginx returns 405 or 400, Apache returns 200, IIS returns 200

# Detect via header ordering (nginx reorders; Apache preserves order)
curl -v https://example.com/ 2>&1 | grep '^< '

Error page finger - different frameworks produce distinct error pages:

# Trigger common error pages and fingerprint
curl -s 'https://example.com/?id[]=1'            # PHP array injection in query
curl -s 'https://example.com/{{7*7}}'            # Jinja2/Twig template syntax
curl -s 'https://example.com/${7*7}'             # Java EL / Spring expression
curl -s 'https://example.com/<%=7*7%>'           # ERB (Ruby)
curl -s 'https://example.com/' -H 'Accept: ../..'  # Some frameworks error on malformed Accept

Favicon hashing - identical favicons across sites mean identical CMS or stack. Compute the MurmurHash3 of the favicon and search Shodan for matches.

# Download and hash favicon
curl -s https://example.com/favicon.ico -o favicon.ico
python3 -c "
import mmh3, codecs
with open('favicon.ico', 'rb') as f:
    favicon_b64 = codecs.encode(f.read(), 'base64')
    print(mmh3.hash(favicon_b64))
"
# Search: https://www.shodan.io/search?query=http.favicon.hash:HASH

JavaScript source map analysis - .map files expose the original source tree:

# Detect source maps in bundled JavaScript
curl -s https://example.com/static/js/app.js | tail -1
# Look for: //# sourceMappingURL=app.js.map

# If found, download and extract source tree
curl -s https://example.com/static/js/app.js.map | python3 -c "
import sys, json
data = json.load(sys.stdin)
print('\n'.join(data.get('sources', [])))
# Outputs original filenames: src/controllers/AuthController.ts, src/utils/db.ts, etc.
"

# Extract all source files from a source map
curl -s https://example.com/static/js/app.js.map | python3 -c "
import sys, json
data = json.load(sys.stdin)
for i, src in enumerate(data.get('sources', [])):
    content = data.get('sourcesContent', [''])[i] if 'sourcesContent' in data else ''
    print(f'## {src}\n{content}\n')
"

API Endpoint Discovery

API s leak through documentation, introspection, JavaScript references, and predictable paths.

OpenAPI / Swagger

# Discover OpenAPI specifications
ffuf -u https://api.example.com/FUZZ \
  -w <(echo -e "swagger.json\nswagger.yaml\nswagger.yml\nopenapi.json\nopenapi.yaml\ndocs\napi-docs\napi/docs\nv1/swagger.json\nv2/swagger.json\napi/v1/swagger.json\napi/v2/openapi.json") \
  -fc 404,403

# Parse discovered OpenAPI spec
curl -s https://api.example.com/api-docs | python3 -c "
import sys, json
spec = json.load(sys.stdin)
for path, methods in spec.get('paths', {}).items():
    for method in methods.keys():
        print(f'{method.upper()} {path}')
"

GraphQL introspection - if enabled, exposes the entire API schema:

# GraphQL endpoint discovery
ffuf -u https://example.com/FUZZ \
  -w <(echo -e "graphql\ngraphiql\napi/graphql\ngql\nquery\nv1/graphql\nv2/graphql") \
  -fc 404,403

# Introspection query — full schema extraction
curl -s -X POST https://example.com/graphql \
  -H 'Content-Type: application/json' \
  -d '{"query":"{__schema{types{name,fields{name,args{name,type{name,kinds}}}},isDeprecated,deprecationReason}}}}"' \
  | python3 -m json.tool > graphql-schema.json

# Detect if introspection is enabled (simplified query)
curl -s -X POST https://example.com/graphql \
  -H 'Content-Type: application/json' \
  -d '{"query":"{__schema{queryType{name}}}"}'
# If response contains queryType → introspection enabled

Parameter discovery - find hidden query parameters, form fields, and JSON keys:

# arjun — parameter discovery by brute force
arjun -u https://example.com/page -o arjun-results.json

# Manual parameter fuzzing with ffuf
ffuf -u 'https://example.com/search?FUZZ=test' \
  -w /usr/share/seclists/Discovery/Web-Content/api-endpoints.txt \
  -fs "$BASELINE_SIZE" -fc 400,404

# Parameter miner via Burp or custom: fuzz common params
ffuf -u 'https://example.com/search?FUZZ=test1234' \
  -w <(echo -e "id\nuser\nusername\npassword\nsearch\nquery\nq\npage\noffset\nlimit\nsort\norder\nfilter\ntoken\nkey\napi_key\nsecret\ndebug\ntest\nadmin\nfile\npath\ndir\nurl\nredirect\nnext\nreturn") \
  -fs "$BASELINE_SIZE"

# Paramspider — extracts parameters from linked pages
paramspider -d example.com

.git/ exposure - when the .git directory is web-accessible, the entire repository can be reconstructed:

# Verify .git/ is exposed

curl -s https://example.com/.git/HEAD

# If 200, clone via git-dumper

Complete Enumeration Workflow

The following script implements the full enumeration chain. Run it against the lab container (see Dockerfile below).

#!/bin/bash
# web-enumerate.sh — complete web enumeration workflow
# Usage: ./web-enumerate.sh target.com [IP]

TARGET="${1:?Usage: $0 target.com [IP]}"
IP="${2}"
OUTDIR="recon/$TARGET"
mkdir -p "$OUTDIR"

echo "[*] Starting enumeration of $TARGET"

# === PHASE 1: DNS + Subdomain Discovery ===
echo "[1/7] DNS and subdomain enumeration"

# Certificate transparency
curl -s "https://crt.sh/?q=%25.$TARGET&output=json" | \
  jq -r '.[].name_value' 2>/dev/null | sed 's/\\n/\n/g' | sort -u > "$OUTDIR/crtsh.txt"

# Passive subdomain discovery
subfinder -d "$TARGET" -silent -all > "$OUTDIR/subfinder.txt" 2>/dev/null
amass enum -passive -d "$TARGET" -o "$OUTDIR/amass-passive.txt" 2>/dev/null

# Merge subdomains
cat "$OUTDIR/crtsh.txt" "$OUTDIR/subfinder.txt" "$OUTDIR/amass-passive.txt" 2>/dev/null | \
  sort -u > "$OUTDIR/all-subdomains.txt"
COUNT=$(wc -l < "$OUTDIR/all-subdomains.txt")
echo "[*] Found $COUNT unique subdomains"

# === PHASE 2: Virtual Host Enumeration ===
echo "[2/7] Virtual host enumeration"

if [ -n "$IP" ]; then
  BASELINE=$(curl -s -o /dev/null -w '%{size_download}' \
    -H "Host: nonexistent-$(head -c 4 /dev/urandom | base64 | tr -dc 'a-z').$TARGET" \
    "https://$IP/" 2>/dev/null)
  ffuf -u "https://$IP/" \
    -w "$OUTDIR/all-subdomains.txt" \
    -H "Host: FUZZ" \
    -fs "$BASELINE" \
    -o "$OUTDIR/vhosts.json" -of json -t 100 2>/dev/null
  echo "[*] VHost enumeration complete"
else
  echo "[*] No IP provided, skipping VHost enumeration"
fi

# === PHASE 3: Technology Fingerprinting ===
echo "[3/7] Technology fingerprinting"

curl -s -D - "https://$TARGET/" -o /dev/null > "$OUTDIR/headers.txt"
curl -s "https://$TARGET/" > "$OUTDIR/index.html"

# Extract technologies from headers
grep -iE '(Server|X-Powered-By|X-Generator|Set-Cookie|X-AspNet)' \
  "$OUTDIR/headers.txt" | sed 's/^[<>] //' > "$OUTDIR/technologies.txt"

# Detect CMS patterns
if grep -q '/wp-content/' "$OUTDIR/index.html"; then
  echo "WordPress detected" >> "$OUTDIR/technologies.txt"
fi
if grep -q 'Drupal.settings' "$OUTDIR/index.html"; then
  echo "Drupal detected" >> "$OUTDIR/technologies.txt"
fi
echo "[*] Technologies:"
cat "$OUTDIR/technologies.txt"

# === PHASE 4: Directory Enumeration ===
echo "[4/7] Directory enumeration"

BASELINE_404=$(curl -s -o /dev/null -w '%{size_download}' \
  "https://$TARGET/$(head -c 8 /dev/urandom | base64 | tr -dc 'a-z')" 2>/dev/null)

gobuster dir -u "https://$TARGET" \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -x php,html,txt,bak,old,zip,sql,conf \
  --exclude-length "$BASELINE_404" \
  -b 404 -t 50 \
  -o "$OUTDIR/gobuster-dirs.txt" 2>/dev/null
echo "[*] Directory enumeration complete"

# === PHASE 5: Sensitive File Discovery ===
echo "[5/7] Sensitive file discovery"

ROBOTS=$(curl -s "https://$TARGET/robots.txt")
if [ -n "$ROBOTS" ]; then
  echo "$ROBOTS" | grep -i disallow > "$OUTDIR/robots-disallowed.txt"
fi
SITEMAP=$(curl -s "https://$TARGET/sitemap.xml")
if [ -n "$SITEMAP" ]; then
  echo "$SITEMAP" | grep -oP 'https?://[^<]+' | sort -u > "$OUTDIR/sitemap-urls.txt"
fi

# Check common sensitive files
for file in .git/config .env .env.backup config.php.bak backup.sql dump.sql phpinfo.php; do
  code=$(curl -s -o /dev/null -w '%{http_code}' "https://$TARGET/$file")
  [ "$code" != "404" ] && echo "[$code] /$file" >> "$OUTDIR/sensitive-files.txt"
done

# === PHASE 6: API Endpoint Discovery ===
echo "[6/7] API endpoint discovery"

API_ENDPOINTS=(
  "api" "api/v1" "api/v2" "graphql" "swagger.json"
  "openapi.json" "api-docs" "swagger-ui.html" "docs"
)

for endpoint in "${API_ENDPOINTS[@]}"; do
  code=$(curl -s -o /dev/null -w '%{http_code}' "https://$TARGET/$endpoint")
  [ "$code" != "404" ] && echo "[$code] /$endpoint ← API endpoint" >> "$OUTDIR/api-endpoints.txt"
done

# GraphQL introspection check
GRAPHQL_RESP=$(curl -s -X POST "https://$TARGET/graphql" \
  -H 'Content-Type: application/json' \
  -d '{"query":"{__schema{queryType{name}}}"}' 2>/dev/null)
if echo "$GRAPHQL_RESP" | grep -q "queryType"; then
  echo "GraphQL introspection enabled at /graphql" >> "$OUTDIR/api-endpoints.txt"
fi

# === PHASE 7: JavaScript Analysis ===
echo "[7/7] JavaScript source analysis"

# Extract JS files from page
curl -s "https://$TARGET/" | grep -oP '(src|href)="([^"]+\.js)"' | \
  sed 's/.*="//;s/"//' | while read jsurl; do
    # Handle relative URLs
    [[ "$jsurl" != http* ]] && jsurl="https://$TARGET/$jsurl"
    jscontent=$(curl -s "$jsurl")
    if echo "$jscontent" | grep -q "sourceMappingURL"; then
      echo "Source map found: $jsurl" >> "$OUTDIR/js-sourcemaps.txt"
      mapurl=$(echo "$jscontent" | grep "sourceMappingURL" | sed 's/.*sourceMappingURL=//')
      [[ "$mapurl" != http* ]] && mapurl="https://$TARGET/$mapurl"
      curl -s "$mapurl" | python3 -c "
import sys, json
data = json.load(sys.stdin)
[print(s) for s in data.get('sources', [])]
" >> "$OUTDIR/js-sources.txt" 2>/dev/null
    fi
    # Extract endpoints and paths from JS
    echo "$jscontent" | grep -oP '["'\''](/[a-zA-Z0-9_/-]+)["'\'']' | \
      tr -d '"'\''/' | sort -u >> "$OUTDIR/js-routes.txt"
  done

echo "[*] Enumeration complete. Results in $OUTDIR/"
echo "    Subdomains:        $(wc -l < "$OUTDIR/all-subdomains.txt" 2>/dev/null || echo 0)"
echo "    Technologies:      $(wc -l < "$OUTDIR/technologies.txt" 2>/dev/null || echo 0)"
echo "    Sensitive files:   $(wc -l < "$OUTDIR/sensitive-files.txt" 2>/dev/null || echo 0)"
echo "    API endpoints:     $(wc -l < "$OUTDIR/api-endpoints.txt" 2>/dev/null || echo 0)"
echo "    JS routes:         $(wc -l < "$OUTDIR/js-routes.txt" 2>/dev/null || echo 0)"

Common Mistakes During Enumeration

  1. Trusting status codes blindly. A 200 with "not found" in the body is a 404. Always check response body content.
  2. Ignoring response time differences. Blind/time-based detection: if /admin takes 500ms and /random takes 50ms, /admin exists but is redirecting or authenticating.
  3. Not tracking redirects. A 302 from /admin -> /login means /admin exists. Follow redirect chains.
  4. Using the same wordlist everywhere. A WordPress site needs WordPress-specific paths; an API needs API endpoint names. Match the wordlist to the technology.
  5. Enumerating at the wrong URL depth. If the target is example.com/app/ , enumerate from that base path, not the root.
  6. Ignoring HTTP methods. Some paths respond 404 to GET but 200 to POST or DELETE. Re-check interesting paths with different methods: curl -X POST , curl -X PUT , curl -X DELETE , curl -X OPTIONS .
  7. Not normalizing URLs. Trailing slashes matter: /admin may 404 while /admin/ returns 200.

Verification Steps

After enumeration, verify every finding:

# Verify each discovered path is reachable and inspect its content
while IFS= read -r path; do
  echo "=== $path ==="
  curl -s -D - "https://$TARGET$path" | head -30
  echo -e "\n---\n"
done < "$OUTDIR/gobuster-dirs.txt"

# Verify subdomains resolve
while IFS= read -r sub; do
  result=$(dig +short "$sub" A 2>/dev/null)
  [ -n "$result" ] && echo "LIVE: $sub → $result"
done < "$OUTDIR/all-subdomains.txt"

# Verify VHosts serve different content
while IFS= read -r vhost; do
  size=$(curl -s -o /dev/null -w '%{size_download}' -H "Host: $vhost" "https://$IP/")
  [ "$size" != "$BASELINE" ] && echo "VHOST DIFFERENT: $vhost (size: $size)"
done < "$OUTDIR/all-subdomains.txt"
