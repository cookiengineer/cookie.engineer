Incident Response

End-to-end incident response lifecycle from detection through recovery and post-incident analysis.

Overview

Incident response is the process framework that keeps an organization's reaction to a breach consistent and defensible under pressure. This article walks the SANS PICERL phases: preparation, identification, containment, eradication, recovery, and lessons learned. It covers evidence collection order, chain of custody, rebuild-versus-clean decisions, and the communication templates used during and after an incident. After reading you can run a structured response from the first alert to the post-incident report.

Required Reading

  • Processes - process lifecycle, /proc, signals, namespaces
  • Filesystems - inodes, timestamps, journaling, recovery

Concept

Incident Response ( IR ) is the structured methodology for handling security breaches. An incident is not just a malware infection - it is any event that compromises the confidentiality, integrity, or availability of systems or data. IR is not a tool. It is a process framework that ensures consistent, defensible actions under stress.

The two dominant frameworks are functionally equivalent: - SANS PICERL : Preparation -> Identification -> Containment -> Eradication -> Recovery -> Lessons Learned - NIST SP 800-61 : Preparation -> Detection & Analysis -> Containment, Eradication & Recovery -> Post-Incident Activity

This article follows the SANS PICERL model with practical procedures.

Phase 1 - Preparation

You cannot build IR processes during an incident. Preparation is the entire body of work done before an alert fires.

IR Team Structure

Role Responsibility
Incident Commander Coordinates response, makes final decisions, communicates with stakeholders
Lead Investigator Technical lead, owns forensic analysis and timeline construction
Communications Lead Manages internal/external notifications, legal, PR
Scribe Documents every action with timestamp - critical for post-incident reports
IT Liaisons SMEs for affected systems (AD, network, database, cloud)

Preparation Checklist

# 1. Establish out-of-band communications
# If the domain controller is compromised, your corporate email and chat are compromised.
# Have a pre-arranged Signal/Element group or separate OOB Slack instance.

# 2. Document escalation procedures
cat > /opt/ir/escalation.md << 'EOF'
# Escalation Path
1. Triage analyst identifies potential incident
2. Notify shift lead within 15 minutes
3. Shift lead declares incident within 30 minutes if criteria met
4. IR team assembled within 1 hour
5. Incident Commander assigned
6. Legal/Compliance notified if PII/PHI involved (within 4 hours per GDPR/HIPAA)
EOF

# 3. Build an incident response jump kit
mkdir -p /opt/ir/jumpkit/{forensics,network,scripts,reporting}

Jump Kit Essentials

Keep these tools available offline. They must not be installed during an incident, because the attacker may have tampered with the package manager.

Phase 2 - Identification

An incident is identified either by an alert (detection fired), an external notification (third party, law enforcement, bug bounty), or a user report. The identification phase determines whether this is a real incident and, if so, its scope and severity.

Triage Questions

Answer these before escalating.

  1. What is the source of the alert? (detection rule ID, external notify, user report)
  2. What system(s) are affected? (hostname, IP , owner, criticality)
  3. What is the observed behaviour? (malware execution, data exfiltration, privilege escalation)
  4. When was the first observed activity? (timestamp, still ongoing?)
  5. What is the blast radius? (one host? entire subnet? domain-wide?)
  6. Is sensitive data (PII, PHI, PCI , IP ) potentially involved?

Severity Classification

Severity Definition Response Time Example
Critical Active compromise of critical systems or confirmed data exfiltration 15 min Ransomware on a DC, customer DB exfiltrated
High Active compromise of non-critical system or lateral movement detected 30 min C2 beacon on workstation, privilege escalation
Medium Suspicious activity, no confirmed compromise 2 hours Phishing email delivered, suspicious login
Low Policy violation, no malicious activity 24 hours Port scan detected, expired cert

Phase 3 - Containment

Containment stops the bleeding. The goal is to prevent the attacker from causing further damage while preserving evidence for investigation.

Decision Tree

  Is the attacker actively in the system?
       │
  ┌────+────┐
  Yes       No (historical incident)
  │         └── Proceed to investigation + eradication
  └── Isolate immediately
       │
  ┌────+────┐
  │         │
  Network    Host
  Isolation  Isolation

Network Isolation

Network isolation is preferred for active attacks.

# Linux: block all ingress/egress except IR workstation
sudo iptables -A INPUT -s 192.168.10.50/32 -j ACCEPT  # IR workstation
sudo iptables -A INPUT -j DROP
sudo iptables -A OUTPUT -d 192.168.10.50/32 -j ACCEPT
sudo iptables -A OUTPUT -j DROP

# Or at the switch level - shutdown switchport
# This prevents the attacker from killing the host when they detect isolation

Host Isolation

Host isolation is more targeted and preserves network visibility.

# Disable all non-system accounts temporarily
sudo passwd -l alice
sudo passwd -l bob

# Kill the attacker's sessions without shutting down
# Find all bash/sh/zsh processes owned by the compromised user
ps aux | grep -E '(bash|sh|zsh)' | grep 'compromised_user'
# DO NOT kill - first dump memory of these processes

# If you must kill (active attack in progress):
kill -STOP <pid>   # SIGSTOP freezes the process - analysable
# ...investigate...
kill -KILL <pid>   # only after analysis complete

Cloud Containment

Cloud containment commands for AWS , Azure, and GCP: 

# AWS: revoke all active sessions for a compromised IAM user
aws iam list-access-keys --user-name compromised_user
aws iam update-access-key --user-name compromised_user --access-key-id AKIA... --status Inactive

# AWS: isolate an EC2 instance using security group
aws ec2 modify-instance-attribute --instance-id i-123456789 \
  --groups sg-isolation

# Azure: disable a compromised user account
az ad user update --id compromised_user@org.com --account-enabled false

# Revoke all refresh tokens (forces re-authentication)
az ad user revoke-sign-in-sessions --id compromised_user@org.com

Containment Strategy

Strategy Short-Term Long-Term
Network Isolate host from network Keep isolated, route through IR VLAN for analysis
Accounts Disable compromised user Reset password, revoke all sessions/tokens
Systems Kill attacker processes, block IPs Rebuild from known-good baseline
Data Prevent egress (firewall egress filtering) Review all access logs for exfiltration

Evidence Collection Order

Collect evidence from most volatile to least volatile. Volatile data disappears on reboot. Non-volatile data survives reboots. 

  MOST VOLATILE
  1. Memory (RAM dump)           ← seconds to capture, gone on reboot
  2. Network state (sockets)     ← minutes, stops when process exits
  3. Running processes           ← disappears when killed
  4. Logged-in users             ← disappears on logout
  5. File system metadata        ← persists until overwritten
  6. Disk image                  ← persists indefinitely
  LEAST VOLATILE

Live response script (Linux): 

#!/bin/bash
# live-response.sh - collect volatile data BEFORE isolating host
OUTDIR="/mnt/evidence/$(hostname)-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$OUTDIR"

# 1. Memory dump (via LiME or /proc/kcore)
# Module method (preferred, requires pre-compiled LiME .ko):
# insmod /opt/ir/lime.ko "path=$OUTDIR/memory.dump format=lime"
# Or: dd if=/proc/kcore of="$OUTDIR/kcore.dump" bs=1M

# 2. Network state
ss -tulnp > "$OUTDIR/netstat.txt"
netstat -anp > "$OUTDIR/netstat_full.txt"
# Capture ARP cache
arp -an > "$OUTDIR/arp.txt"

# 3. Running processes
ps auxwww > "$OUTDIR/ps_aux.txt"
ps -ef > "$OUTDIR/ps_ef.txt"
# Process tree
pstree -ap > "$OUTDIR/pstree.txt"
# /proc details for each process
for pid in $(ls /proc | grep -E '^[0-9]+$'); do
    ls -la /proc/$pid/exe 2>/dev/null >> "$OUTDIR/proc_exe_links.txt"
    cat /proc/$pid/cmdline 2>/dev/null | tr '\0' ' ' >> "$OUTDIR/proc_cmdlines.txt"
    echo >> "$OUTDIR/proc_cmdlines.txt"
done

# 4. Logged-in users
w > "$OUTDIR/w.txt"
who > "$OUTDIR/who.txt"
last -n 100 > "$OUTDIR/last.txt"

# 5. Open files
lsof -nP > "$OUTDIR/lsof.txt"

# 6. Kernel modules
lsmod > "$OUTDIR/lsmod.txt"

# 7. Mounted filesystems
mount > "$OUTDIR/mount.txt"
df -h > "$OUTDIR/df.txt"

# 8. Scheduled tasks
crontab -l > "$OUTDIR/crontab_root.txt" 2>/dev/null
for user in $(cut -f1 -d: /etc/passwd); do
    crontab -u "$user" -l >> "$OUTDIR/crontabs.txt" 2>/dev/null
done
cat /etc/crontab >> "$OUTDIR/crontab_system.txt" 2>/dev/null

# 9. Bash history for all users
for home in /home/* /root; do
    user=$(basename "$home")
    cp "$home/.bash_history" "$OUTDIR/bash_history_$user.txt" 2>/dev/null
done

# 10. System logs (collect before they rotate)
cp /var/log/auth.log "$OUTDIR/" 2>/dev/null
cp /var/log/syslog "$OUTDIR/" 2>/dev/null
cp /var/log/audit/audit.log "$OUTDIR/" 2>/dev/null

echo "Live response collection complete: $OUTDIR"
ls -la "$OUTDIR/"

Phase 4 - Eradication

Eradication removes the attacker's presence and the root cause of the compromise.

Rebuild vs Clean Decision

Factor Rebuild Clean
Confidence in forensic findings Low (don't know full scope) High (know exactly what was modified)
System criticality Low-Medium (can tolerate downtime) High (cannot take offline)
Attacker privilege level Root/Domain Admin User-level
Time since compromise Unknown or >30 days Known, <24 hours
Backdoor risk High Low

Rule of Thumb

If the attacker had root or administrator access, rebuild. You cannot trust a system where the attacker modified kernel modules, system binaries, or boot configurations.

Eradication by Cleaning

# 1. Remove persistence mechanisms
## Linux
sudo crontab -u compromised_user -r
sudo rm /etc/cron.d/malicious_job
sudo rm /etc/systemd/system/evil.service
sudo systemctl daemon-reload

## Remove SSH authorized keys
sudo rm /home/compromised_user/.ssh/authorized_keys
sudo rm /root/.ssh/authorized_keys

## Check for modified .bashrc / .profile
sudo grep -r 'ssh\|wget\|curl\|nc\|bash -i' /home/*/.bashrc /root/.bashrc

# 2. Kill malicious processes
sudo kill -9 <pid>

# 3. Remove dropped malware
sudo find /tmp /var/tmp /dev/shm /var/www -type f -mtime -7 -ls

# 4. Reset compromised credentials
sudo passwd compromised_user
sudo passwd -e compromised_user  # Force password change on next login

# 5. Remove malicious firewall rules
sudo iptables -L -n --line-numbers
sudo iptables -D INPUT <rule_number>

Eradication by Rebuilding

# 1. Before wiping: collect final forensic image
sudo dd if=/dev/sda of=/mnt/evidence_host/sda_final.img bs=4M status=progress

# 2. Wipe the disk
sudo dd if=/dev/zero of=/dev/sda bs=4M status=progress
# Or: sudo blkdiscard /dev/sda  (for SSDs - TRIM all blocks)

# 3. Reinstall from known-good, offline media
# Do NOT reinstall from a network boot server that may be compromised
# Do NOT restore from latest backup - it may contain the attacker's backdoor

# 4. Restore data from pre-compromise backup (validated clean)
# Check backup dates - any backup after the earliest known compromise is suspect

Phase 5 - Recovery

Return systems to production in a controlled, phased manner.

# Phased recovery plan
# Phase 1: Restore critical infrastructure
#   - Domain Controller (restore from backup > 90 days old if possible)
#   - DNS/DHCP
#   - Authentication systems (LDAP, SSO)
#   - Validate: no unknown accounts, no unexpected GPOs

# Phase 2: Restore business-critical services
#   - Database servers
#   - Application servers
#   - File servers
#   - Validate: application functionality, data integrity

# Phase 3: Restore user access
#   - All users reset passwords BEFORE reconnecting
#   - VPN access enabled
#   - Email restored
#   - Validate: no unusual login patterns

# Phase 4: Enhanced monitoring
#   - Deploy additional EDR agents
#   - Enable verbose logging on all restored systems
#   - 24/7 monitoring for 2 weeks post-recovery

Verification Testing

# After rebuilding a Linux server, verify hardening baseline
sudo oscap xccdf eval \
  --profile xccdf_org.ssgproject.content_profile_cis \
  --results /tmp/recovery-scan.xml \
  /usr/share/xml/scap/ssg/content/ssg-archlinux-ds.xml

# Check for common misconfigurations introduced during rebuild
sudo lynis audit system --quick

# Verify no unexpected network listeners
sudo ss -tulnp | diff /var/log/hardening/ports-baseline.txt -

Phase 6 - Lessons Learned

Within 1 week of incident closure, conduct a blameless post-mortem.

Incident Communication Templates

Initial Notification

Send this within the first 30 minutes.

Subject: INCIDENT: Unauthorized Access - Database Server

Severity: High
Status: Active - containment in progress
Incident Commander: [Name], [Phone]
Lead Investigator: [Name], [Phone]

Summary: At 04:10 UTC, DLP detected a database dump from SRV-DB01.
The activity was traced to an attacker who gained initial access via
phishing at 22:15 UTC. Containment was initiated at 04:35 UTC
(network isolation of SRV-DB01, disabling compromised user account).

Next update: 06:00 UTC

Status Update

Send this hourly until the incident is closed.

Subject: UPDATE #1 - Incident IR-2026-0626-001

Containment: Complete - SRV-DB01 isolated, compromised accounts disabled
Investigation: Ongoing - memory analysis in progress, full scope TBD
Estimated impact: Under investigation - database dump detected but exfiltration unconfirmed
Estimated recovery: 24-48 hours
Next update: 08:00 UTC

Challenge

Write a Go tool that reconstructs an incident timeline from an SSH authentication log. Parse /var/log/auth.log , count failed logins per source address, and alert when an address succeeds after exceeding a failure threshold. That is the signal which separates a blocked brute-force attempt from a successful one. 

package main

import (
	"bufio"
	"fmt"
	"os"
	"regexp"
	"sort"
)

var (
	failedRe  = regexp.MustCompile(`Failed password for (?:invalid user )?(\S+) from (\S+) port`)
	successRe = regexp.MustCompile(`Accepted (?:password|publickey) for (\S+) from (\S+) port`)
	threshold = 5
)

type stat struct {
	failures  int
	successes int
}

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "usage: timeline auth.log")
		os.Exit(2)
	}

	logFile, err := os.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer logFile.Close()

	stats := make(map[string]*stat)
	scanner := bufio.NewScanner(logFile)

	for scanner.Scan() {
		line := scanner.Text()

		if match := failedRe.FindStringSubmatch(line); match != nil {
			entry := stats[match[2]]
			if entry == nil {
				entry = &stat{}
				stats[match[2]] = entry
			}
			entry.failures++
		} else if match := successRe.FindStringSubmatch(line); match != nil {
			entry := stats[match[2]]
			if entry == nil {
				entry = &stat{}
				stats[match[2]] = entry
			}
			entry.successes++
			if entry.failures >= threshold {
				fmt.Printf("ALERT: %s logged in from %s after %d failures\n",
					match[1], match[2], entry.failures)
			}
		}
	}

	addresses := make([]string, 0, len(stats))
	for address := range stats {
		addresses = append(addresses, address)
	}
	sort.Slice(addresses, func(a int, b int) bool {
		return stats[addresses[a]].failures > stats[addresses[b]].failures
	})

	fmt.Println("ip,failures,successes")
	for _, address := range addresses {
		fmt.Printf("%s,%d,%d\n", address, stats[address].failures, stats[address].successes)
	}
}
