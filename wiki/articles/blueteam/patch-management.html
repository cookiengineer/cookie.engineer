Patch Management

Deploying updates safely and efficiently with staged rollouts, Linux and Windows tooling, and rollback procedures.

Overview

Patch management is the discipline of getting vendor fixes onto systems before attackers use the flaws they close. This article covers risk-based prioritization, staged rollouts, Linux and Windows tooling, rollback planning, and a challenge that builds a patch-priority scorer in Go.

Required Reading

  • Processes - process lifecycle, service control, systemd
  • Containers - immutable infrastructure, image layering, podman

Concept

Patch management is the process of applying vendor-supplied updates to fix vulnerabilities, resolve bugs, and maintain software supportability. An unpatched vulnerability that has a published exploit is not a security finding - it is an incident waiting to happen.

The tension: patching can break production. The solution: staged rollouts, automated testing, and fast rollback. Never let fear of downtime become the reason for a breach.

Patch Prioritization

Not all patches are equal. Prioritize on three axes:

Priority = Exploitability × Asset Criticality × Patch Complexity

Exploitability:
  5 — Weaponized exploit in the wild (CISA KEV)
  4 — Published PoC, easy to execute
  3 — Published PoC, requires authentication
  2 — Technical analysis published, no PoC
  1 — Theoretical, no known exploitation

Asset Criticality:
  5 — Internet-facing, contains PII/credentials
  4 — Internet-facing, no sensitive data
  3 — Internal, critical business function
  2 — Internal, non-critical
  1 — Isolated / air-gapped

Patch Complexity:
  5 — Single package, no dependencies, automated
  4 — Multiple packages, automated
  3 — Requires service restart (planned downtime)
  2 — Requires OS reboot
  1 — Complex upgrade (DB migration, config changes)

Emergency patching threshold: Any CVE in CISA KEV on a Tier 0/1 asset -> patch within 24 hours, bypassing normal change control (emergency process).

#!/bin/bash
# patch-prioritize.sh — calculate patch urgency
# Compares installed packages against known CVEs

# Get a list of CVEs for your installed packages and cross-ref with KEV
curl -s 'https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json' \
  | jq -r '.vulnerabilities[] | "\(.cveID) \(.vulnerabilityName) \(.dateAdded)"' \
  > /tmp/kev-catalog.txt

# Check which are relevant to your stack
for pkg in nginx openssh postgresql linux; do
  pacman -Q "$pkg" 2>/dev/null && echo "--- check KEV for $pkg ---"
done

Staged Rollout Strategy

Never patch everywhere at once. The blast radius of a bad patch is proportional to the number of hosts it hits simultaneously.

Canary (1–5% of estate) → 24h observation → Phased (25% per day) → Full

Emergency: Canary (1 host) → 2h observation → Phased (50%) → Full
						
#!/bin/bash
# staged-update.sh — phased update across server groups
# Inventory is tagged: group=canary, group=phased-1, group=phased-2, group=prod

GROUP="$1"
ANSIBLE_INV="/etc/ansible/hosts"

case "$GROUP" in
  canary)
    echo "Stage 1: Patching canary group (5% of estate)"
    ansible-playbook -i "$ANSIBLE_INV" -l canary patch.yml
    echo "Monitor for 24h before proceeding to phased-1"
    ;;
  phased-1)
    echo "Stage 2: Patching phased-1 (25%)"
    ansible-playbook -i "$ANSIBLE_INV" -l phased-1 patch.yml
    ;;
  phased-2)
    echo "Stage 3: Patching phased-2 (next 25%)"
    ansible-playbook -i "$ANSIBLE_INV" -l phased-2 patch.yml
    ;;
  full)
    echo "Stage 4: Full rollout"
    ansible-playbook -i "$ANSIBLE_INV" -l prod patch.yml
    ;;
esac

Patch Testing in Staging

A staging environment must mirror production. If staging runs different kernel versions, different library versions, or different database schemas, your testing is worthless.

# Snapshot production state for staging replication
# Method 1: Clone VM snapshot
virsh snapshot-create-as prod-web-01 prod-preview "pre-patch snapshot $(date +%Y%m%d)"

# Method 2: Replay production data into staging DB
pg_dump -h prod-db-01 production_db | psql -h staging-db staging_db

# Method 3: Containerized staging
podman run -d --name staging-web \
  -v staging-config:/etc/nginx:ro \
  -p 8080:443 \
  nginx:latest

# Run automated test suite against staging after patching
curl -sSf https://staging.internal/health || echo "HEALTH CHECK FAILED"
curl -sSf https://staging.internal/api/v1/status || echo "API STATUS FAILED"

# Integration smoke tests
python3 -m pytest tests/smoke/ -v --base-url https://staging.internal

Testing checklist (minimum)

  • Health endpoint returns HTTP 200
  • Authentication works (login and token refresh)
  • Core API endpoints return expected status codes
  • Database connectivity works for reads and writes
  • File upload and download work where applicable
  • Third-party integrations still function (payment, email, SSO )
  • TLS certificate is valid with the expected cipher suites
  • CPU , memory, and disk stay within acceptable limits

Linux Patch Management - ArchLinux

# Standard update — always read the news first
# https://archlinux.org/news/ — check before major updates
sudo pacman -Syu

# Check for available security updates specifically
# Install arch-audit for CVE tracking
sudo pacman -S arch-audit
arch-audit

# Output example:
# CVE-2026-XXXXX: openssh (9.6p1-2 → 9.8p1-1) — CRITICAL
# CVE-2026-YYYYY: glibc (2.39-1 → 2.40-1) — HIGH

# List all upgradable packages
pacman -Qu

# Dry-run to see what will change
pacman -Syuw --noconfirm  # download only
pacman -Sup                # print URLs only

Unattended Upgrades

# ArchLinux doesn't have apt's unattended-upgrades equivalent.
# Use a systemd timer for controlled auto-patching:

# /etc/systemd/system/pacman-auto-update.service
						
[Unit]
Description=Automated pacman update
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStartPre=/usr/bin/pacman -Sy
ExecStart=/usr/bin/pacman --noconfirm --disable-download-timeout -Su
# Exclude kernel packages to prevent unbootable state
ExecStart=/usr/bin/pacman --noconfirm -Su --ignore linux,linux-headers,linux-firmware
StandardOutput=journal
StandardError=journal
						
# /etc/systemd/system/pacman-auto-update.timer
						
[Unit]
Description=Weekly pacman auto-update
Requires=pacman-auto-update.service

[Timer]
OnCalendar=Sun 03:00:00
RandomizedDelaySec=1800
Persistent=true

[Install]
WantedBy=timers.target
						
sudo systemctl enable --now pacman-auto-update.timer

Kernel Live Patching

# ArchLinux: kpatch for kernel live patching
yay -S kpatch

# Check all running kernel version
uname -r

# List available live patches
kpatch list

# Apply a live patch (requires kernel built with CONFIG_LIVEPATCH=y)
sudo kpatch apply /path/to/patch.kpatch

# Livepatch is a stopgap — schedule a reboot within the maintenance window
# Some kernel bugs can only be fixed with a full reboot

Config Drift Detection

# Before patching, snapshot current configs
mkdir -p /var/backups/configs/$(date +%Y%m%d)
cp -a /etc/{ssh,nginx,postgresql,systemd} /var/backups/configs/$(date +%Y%m%d)/

# After patching, diff to identify changes
diff -r /var/backups/configs/20260620/ssh/ /etc/ssh/

# etckeeper / etckeeper — version control for /etc
sudo pacman -S etckeeper
sudo etckeeper init
sudo etckeeper commit "pre-patch snapshot $(date +%Y%m%d)"

# After patching:
sudo etckeeper commit "post-patch $(date +%Y%m%d)"
sudo git -C /etc diff HEAD~1

Windows Patch Management

Patch Sources:
  Windows Update (consumer)
  WSUS (Windows Server Update Services) — on-premises
  Windows Update for Business (WUfB) — cloud-managed
  Microsoft Configuration Manager (SCCM) — enterprise

Deployment Rings (WUfB):
  Ring 0 — IT test devices (0-day deployment)
  Ring 1 — Early adopters (deploy after 2 days)
  Ring 2 — Broad deployment (deploy after 7 days)
  Ring 3 — Critical systems (deploy after 14 days)

Emergency Patch:
  Set deadline to immediate for the target security group
  Override normal ring delays

Rollback Procedures

Every patch deployment must have a documented and tested rollback plan. If you can't roll back in under 10 minutes, the patch risk is high.

# Linux: rollback with pacman cache
# pacman keeps previous versions in /var/cache/pacman/pkg/

# List cached versions of a package
ls -l /var/cache/pacman/pkg/openssh-*

# Downgrade to previous version
sudo pacman -U /var/cache/pacman/pkg/openssh-9.6p1-1-x86_64.pkg.tar.zst

# Prevent the package from being updated again (temporarily)
sudo sed -i 's/^#IgnorePkg/IgnorePkg = openssh/' /etc/pacman.conf

# System-wide snapshot rollback (btrfs / ZFS)
# If using btrfs with snapper:
sudo snapper list
sudo snapper undochange 42..43  # undo changes between snapshot 42 and 43

# ZFS rollback
sudo zfs rollback tank/root@pre-patch-20260626
						
# Kernel rollback — if new kernel doesn't boot
# At bootloader, select previous kernel entry
# Then make it permanent:
# List installed kernels
pacman -Q | grep linux
# If both old and new are installed, set default in bootloader
sudo grub-set-default 1  # index 0 = newest, 1 = previous

Rollback runbook template

# rollback-playbook.yml — ansible playbook for server rollback
- name: Rollback patch
  hosts: "{{ target_hosts }}"
  become: yes
  tasks:
    - name: Stop affected services
      systemd:
        name: "{{ item }}"
        state: stopped
      loop: "{{ affected_services }}"

    - name: Downgrade packages to previous versions
      pacman:
        name: "{{ item.package }}"
        state: present
        force: yes
      loop: "{{ rollback_packages }}"
      when: ansible_os_family == "Archlinux"

    - name: Restore configuration files
      copy:
        src: "{{ backup_path }}/{{ item }}"
        dest: "/etc/{{ item }}"
        remote_src: yes
      loop: "{{ config_files }}"

    - name: Restart services
      systemd:
        name: "{{ item }}"
        state: started
      loop: "{{ affected_services }}"

    - name: Verify service health
      uri:
        url: "https://{{ inventory_hostname }}/health"
        validate_certs: no
        status_code: 200
      retries: 5
      delay: 5

Emergency Patching Process

When a critical vulnerability drops (e.g., Log4Shell, ProxyShell, Heartbleed) and it's being actively exploited:

T+0h   — CVE published, exploit observed in the wild
T+0.5h — Security team confirms relevance, declares emergency
T+1h   — Emergency change request approved (post-facto)
T+2h   — Canary host patched, monitored 30 min
T+3h   — Phase 1 (50% of internet-facing hosts) patched
T+4h   — Phase 2 (remaining internet-facing) patched
T+12h  — Internal critical systems patched
T+24h  — Full estate patched, post-incident review scheduled

Emergency patches skip staging (accept risk of patch instability vs. certainty of compromise). Document the exception.

Database and Application Patching

Database patches are high-risk because they can introduce query plan changes, replication breaks, or incompatibility with client libraries.

# PostgreSQL — always check release notes for breaking changes
# pg_upgrade checklist:
# 1. Backup database
pg_dumpall -f /backups/postgres-full-$(date +%Y%m%d).sql
# 2. Test upgrade on staging with production data
# 3. Check extension compatibility
SELECT * FROM pg_available_extensions WHERE installed_version IS NOT NULL;
# 4. Schedule maintenance window
# 5. Run pg_upgrade --check first
sudo -u postgres pg_upgrade --check -b /usr/lib/postgresql/old -B /usr/lib/postgresql/new
# 6. Execute upgrade
sudo -u postgres pg_upgrade -b /usr/lib/postgresql/old -B /usr/lib/postgresql/new \
  -d /var/lib/postgres/old/data -D /var/lib/postgres/new/data
# 7. Verify: run application test suite immediately

Patching Containers

With immutable infrastructure, you don't patch running containers - you rebuild and redeploy.

# Build new image with patched base
cat <<'HEREDOC' | podman build -t myapp:patched -f - .
FROM docker.io/alpine:3.20
RUN apk update && apk upgrade
COPY --from=builder /build/myapp /usr/local/bin/myapp
HEREDOC

# Scan the new image for vulnerabilities before deploy
trivy image myapp:patched

# Rolling update with zero downtime
# Kubernetes: kubectl rollout restart deployment/myapp
# Podman pods:
podman pod create --name myapp
podman run -d --pod myapp --name myapp-v2 myapp:patched
# After health check passes:
podman stop myapp-v1 && podman rm myapp-v1

# Tag and track
podman tag myapp:patched registry.internal/myapp:$(date +%Y%m%d-%H%M)
podman push registry.internal/myapp:$(date +%Y%m%d-%H%M)

Immutable Patching Workflow

1. Patch base image (docker.io/alpine:3.20 → 3.21)
2. Rebuild all downstream images
3. Scan rebuilt images (trivy / grype)
4. Deploy to canary, run smoke tests
5. Gradual rollout: replace 25% → 50% → 100% of pods
6. Retire old images

Compliance Reporting

#!/bin/bash
# patch-compliance.sh — generate a compliance report
# Shows % systems patched, overdue patches, exception count

echo "# Patch Compliance Report — $(date +%Y-%m-%d)"
echo
echo "## Coverage"
total=$(wc -l < /var/lib/patchmgmt/inventory.txt)
patched=$(grep -c "STATUS=COMPLIANT" /var/lib/patchmgmt/status.txt || echo 0)
echo "- Total systems: $total"
echo "- Compliant: $patched ($(( patched * 100 / total ))%)"
echo

echo "## Critical Patches Outstanding (> 24h)"
comm -23 \
  <(arch-audit --upgradable | grep CRITICAL | cut -d: -f1 | sort) \
  <(cat /var/lib/patchmgmt/patched-cves.txt | sort)

echo
echo "## Exceptions Active"
ls /var/lib/patchmgmt/exceptions/ | wc -l
echo "(see /var/lib/patchmgmt/exceptions/ for details)"

Challenge

Write a Go tool that cross-references an installed package inventory against the CISA Known Exploited Vulnerabilities catalog and prints every affected package, ordered by the date the vulnerability was added.

The tool takes two arguments: a pacman -Q style inventory ( name version ) and the KEV catalog as JSON . Fetch both inputs first:

curl -s https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json \
    -o kev.json
pacman -Q > installed.txt
						
package main

import (
	"bufio"
	"encoding/json"
	"fmt"
	"os"
	"sort"
	"strings"
)

type kevCatalog struct {
	Vulnerabilities []struct {
		CveID     string `json:"cveID"`
		Product   string `json:"product"`
		DateAdded string `json:"dateAdded"`
	} `json:"vulnerabilities"`
}

type finding struct {
	Package   string
	Version   string
	CveID     string
	Product   string
	DateAdded string
}

func loadPackages(path string) (map[string]string, error) {
	file, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer file.Close()

	installed := make(map[string]string)
	scanner := bufio.NewScanner(file)
	for scanner.Scan() {
		fields := strings.Fields(scanner.Text())
		if len(fields) >= 2 {
			installed[strings.ToLower(fields[0])] = fields[1]
		}
	}
	return installed, scanner.Err()
}

func main() {
	if len(os.Args) != 3 {
		fmt.Fprintln(os.Stderr, "usage: patch-priority installed.txt kev.json")
		os.Exit(1)
	}

	installed, err := loadPackages(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	raw, err := os.ReadFile(os.Args[2])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	var kev kevCatalog
	if err := json.Unmarshal(raw, &kev); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	findings := make([]finding, 0)
	for _, vuln := range kev.Vulnerabilities {
		product := strings.ToLower(vuln.Product)
		for name, version := range installed {
			if strings.Contains(product, name) {
				findings = append(findings, finding{name, version, vuln.CveID, vuln.Product, vuln.DateAdded})
			}
		}
	}

	sort.Slice(findings, func(i int, j int) bool {
		return findings[i].DateAdded < findings[j].DateAdded
	})

	for _, f := range findings {
		fmt.Printf("%-20s %-14s %-18s %s\n", f.Package, f.Version, f.CveID, f.DateAdded)
	}
}
						
go build -o patch-priority patch-priority.go
./patch-priority installed.txt kev.json

Extend the tool to read each package's changelog, then rank findings by the product of exploitability, asset criticality, and patch complexity from the scoring model above.
