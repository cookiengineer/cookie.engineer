Application Whitelisting

Restricting executable code to known-good binaries through fapolicyd, AppLocker/ WDAC , and code signing trust anchors.

Overview

Application whitelisting inverts antivirus: instead of listing known-bad files, it lists known-good files and denies everything else. That removes whole attack classes, but every legitimate binary and library must be approved first. After reading this article you can configure fapolicyd on Linux, AppLocker and WDAC on Windows, and reason about the bypasses each one fails to stop.

Required Reading

  • ELF (Executable and Linkable Format) - ELF headers, segments, interpreter, dynamic linker
  • PE (Portable Executable) - PE headers, sections, import/export, digital signatures
  • Processes - execve(), process lifecycle, memory layout

Concept

Application whitelisting (allowlisting) inverts signature-based antivirus: instead of maintaining a list of known-bad executables and hoping to catch them all, you maintain a list of known-good executables and deny everything else. This eliminates entire classes of attacks, including malware downloaders, fileless malware, and living-off-the-land binaries, because the malicious code never executes.

The trade-off is operational: every legitimate executable and shared library must be pre-approved. This requires understanding your software inventory at a granular level.

Linux fapolicyd

fapolicyd (File Access Policy Daemon) is the primary application control framework on Linux. It intercepts file execution via the fanotify kernel interface and makes allow/deny decisions based on a trust database.

Architecture

+--------------------------------------------------+
|                  execve(path)                    |
+--------------------------------------------------+
                     |
+--------------------v-----------------------------+
|              fanotify (FAN_OPEN_EXEC)            |
|            Kernel passes event to fapolicyd      |
+--------------------+-----------------------------+
                     |
+--------------------v-----------------------------+
|           fapolicyd Decision Engine              |
|                                                  |
|  1. Check rules.d/ rules (first match wins)      |
|  2. Check trust database (hash, signature)       |
|  3. Default: deny                                |
+--------------------+-----------------------------+
                     |
            +--------v--------+
            |  ALLOW  |  DENY  |
            +-----------------+

Installation

# Install from the AUR
yay -S fapolicyd

# Or build manually
git clone https://github.com/linux-application-whitelisting/fapolicyd.git
cd fapolicyd
./autogen.sh && ./configure --with-audit --sysconfdir=/etc
make && sudo make install

# Enable and start
sudo systemctl enable --now fapolicyd

Trust Database

The trust database is the core of fapolicyd. It keeps a list of known-good files identified by hash (SHA-256) or by filesystem source (RPM/dpkg package origin, or a custom trust entry). 

# Initialize the trust database from installed packages
sudo fapolicyd-cli --update

# The trust database is populated from:
# 1. RPM/dpkg database - all files from installed packages
# 2. Custom trust files you define
# 3. Integrity measurement (IMA) if configured

# List the trust database
sudo fapolicyd-cli --dump-db

# Check if a specific file is trusted
sudo fapolicyd-cli --check-file /usr/bin/bash

# Manually add a file to the trust database (by hash)
sudo fapolicyd-cli --file add /usr/local/bin/my-custom-app

# Add a directory to the trust database
sudo fapolicyd-cli --trust add /opt/my-company/

Rule Configuration

Rules in /etc/fapolicyd/rules.d/ are evaluated top-to-bottom, first-match-wins: 

# /etc/fapolicyd/rules.d/10-base.rules

# Allow everything from trusted RPM/DKMS sources
allow perm=any all : ftype=application/x-executable trust=1

# Allow scripts interpreted by trusted interpreters
allow perm=any all : ftype=text/x-shellscript trust=1
allow perm=any all : ftype=text/x-python trust=1

# Deny execution from /tmp, /dev/shm, /var/tmp (common malware staging)
deny_audit perm=any uid=0 gid=0 : dir=/tmp/ ftype=application/x-executable
deny_audit perm=any all : dir=/tmp/ ftype=application/x-executable
deny_audit perm=any all : dir=/dev/shm/ ftype=application/x-executable
deny_audit perm=any all : dir=/var/tmp/ ftype=application/x-executable

# Deny execution from user home directories (except specific paths)
deny_audit perm=any all : dir=/home/ ftype=application/x-executable
deny_audit perm=any all : dir=/root/ ftype=application/x-executable

# Allow specific company software from /opt
allow perm=any all : dir=/opt/my-company/ ftype=application/x-executable trust=1

# Default - deny everything not matched above
deny_audit perm=any all : all

Integrity Checking

fapolicyd integrates with IMA (Integrity Measurement Architecture) to detect tampered binaries:

# Enable IMA in the kernel cmdline (grub)
# /etc/default/grub
GRUB_CMDLINE_LINUX="... ima=on ima_template=ima-ng ima_hash=sha256 ima_appraise=enforce"

# IMA policy - measure and appraise executables
# /etc/ima/ima-policy
measure func=BPRM_CHECK
appraise func=BPRM_CHECK appraise_type=imasig

# Regenerate grub config
sudo grub-mkconfig -o /boot/grub/grub.cfg

Audit Mode

Always deploy fapolicyd in audit mode first to avoid breaking production:

# /etc/fapolicyd/rules.d/ - use deny_audit instead of deny
# deny_audit logs but does not block

# Monitor denials
sudo journalctl -u fapolicyd -f

# Check the audit log for fapolicyd events
sudo ausearch -m FANOTIFY -ts recent

# After 1-2 weeks of operation with no unexpected denials,
# switch deny_audit rules to deny

Custom Policies

# /etc/fapolicyd/rules.d/20-development.rules

# Allow developers to execute their own compiled binaries from ~/projects/
allow perm=any uid=1000-1999 gid=1000-1999 : dir=/home/%/projects/ ftype=application/x-executable

# Allow pip-installed binaries in user virtualenvs
allow perm=any uid=1000-1999 : dir=/home/%/.local/bin/ ftype=application/x-executable
allow perm=any uid=1000-1999 : dir=/home/%/.virtualenvs/ ftype=application/x-executable

# But still deny from ~/Downloads (spear phishing attachment execution)
deny_audit perm=any all : dir=/home/%/Downloads/ ftype=application/x-executable

Windows AppLocker

AppLocker is the built-in Windows application control mechanism, available in Enterprise and Education editions. It supports rules based on publisher, path, and hash.

Rule Types

Rule Type Granularity Maintenance Security
Path File path Low Low (rename bypass)
Hash Specific file High (every update) Medium
Publisher Code signing certificate Medium High

Publisher rules are the recommended approach: "Allow anything signed by Microsoft Corporation, version >= X."

Default Rules

Generate the default rules first; without them Windows will not boot. In production these are created by the AppLocker MMC snap-in. The XML below shows the shape of a publisher allow rule: 

<!-- Default rules - allow signed software and the standard Windows paths -->
<RuleCollection Type="Exe" EnforcementMode="Enabled">
  <FilePublisherRule Id="11111111-1111-1111-1111-111111111111" Name="All signed software"
    Description="" UserOrGroupSid="S-1-1-0" Action="Allow">
    <Conditions>
      <FilePublisherCondition PublisherName="*" ProductName="*" BinaryName="*">
        <BinaryVersionRange LowSection="*" HighSection="*" />
      </FilePublisherCondition>
    </Conditions>
  </FilePublisherRule>
  <FilePathRule Id="22222222-2222-2222-2222-222222222222" Name="Default Windows Path"
    Description="" UserOrGroupSid="S-1-1-0" Action="Allow">
    <Conditions>
      <FilePathCondition Path="%WINDIR%\*" />
    </Conditions>
  </FilePathRule>
  <FilePathRule Id="33333333-3333-3333-3333-333333333333" Name="Default Program Files Path"
    Description="" UserOrGroupSid="S-1-1-0" Action="Allow">
    <Conditions>
      <FilePathCondition Path="%PROGRAMFILES%\*" />
    </Conditions>
  </FilePathRule>
</RuleCollection>
						
# Deploy the AppLocker policy
Set-AppLockerPolicy -XmlPolicy C:\Policies\AppLocker.xml

# Verify the service is running
Get-Service AppIDSvc | Format-List Name,Status,StartType
Set-Service AppIDSvc -StartupType Automatic
Start-Service AppIDSvc

# Audit events
Get-AppLockerFileInformation -EventLog -LogName "AppLocker - EXE and DLL"

Windows WDAC

WDAC is the kernel-level successor to AppLocker. It operates at the Code Integrity level: if WDAC blocks something, it cannot execute. AppLocker operates in user mode.

WDAC vs AppLocker

WDAC AppLocker
Enforcement level Kernel (CI) User-mode
Bypass difficulty Requires kernel exploit User-mode bypasses possible
Managed installer Yes No
Supplemental policies Yes (merge) No
DLL control Yes Yes (high maintenance)
Script enforcement Yes (via AMSI) Yes
Management complexity High Medium

WDAC Policy Example

<!-- WDAC.xml - Base policy: Allow Microsoft + WHQL signed -->
<?xml version="1.0" encoding="utf-8"?>
<SiPolicy xmlns="urn:schemas-microsoft-com:sipolicy"
          PolicyType="Base Policy">
  <VersionEx>10.0.0.0</VersionEx>
  <PolicyID>{A244370E-44C9-4C06-B551-F6016E563076}</PolicyID>
  <BasePolicyID>{A244370E-44C9-4C06-B551-F6016E563076}</BasePolicyID>
  <Rules>
    <Rule>
      <Option>Enabled:UMCI</Option>
    </Rule>
    <Rule>
      <Option>Enabled:Update Policy No Reboot</Option>
    </Rule>
    <Rule>
      <Option>Required:WHQL</Option>
    </Rule>
  </Rules>
  <FileRules>
    <!-- Allow Microsoft-signed kernel drivers -->
    <Allow ID="ID_ALLOW_MICROSOFT_KERNEL"
           FileName="*"
           MinimumFileVersion="0.0.0.0"
           PackageFamilyName="Microsoft.Windows.Kernel"/>
  </FileRules>
  <Signers>
    <Signer ID="ID_SIGNER_MICROSOFT" Name="Microsoft Corporation">
      <CertRoot Type="TBS" Value="FC9EDE71EC7B935A96F14E2F3F01E70E82B7B0F3F8E5CB14EB4E2D3FA3A3C3ED" />
    </Signer>
  </Signers>
  <SigningScenarios>
    <SigningScenario Value="131" ID="ID_SIGNINGSCENARIO_KMCI" FriendlyName="Kernel Mode">
      <ProductSigners>
        <AllowedSigners>
          <AllowedSigner SignerId="ID_SIGNER_MICROSOFT" />
        </AllowedSigners>
      </ProductSigners>
    </SigningScenario>
    <SigningScenario Value="12" ID="ID_SIGNINGSCENARIO_UMCI" FriendlyName="User Mode">
      <ProductSigners>
        <AllowedSigners>
          <AllowedSigner SignerId="ID_SIGNER_MICROSOFT" />
        </AllowedSigners>
      </ProductSigners>
    </SigningScenario>
  </SigningScenarios>
</SiPolicy>
						
# Convert and deploy
ConvertFrom-CIPolicy -XmlFilePath WDAC.xml -BinaryFilePath WDAC.bin
Copy-Item WDAC.bin C:\Windows\System32\CodeIntegrity\SiPolicy.p7b

# On newer Windows versions the deployed policy file is SiPolicy.cip
# Audit events: Event ID 3076
# Applications and Services Logs > Microsoft > Windows > CodeIntegrity > Operational

macOS Gatekeeper and SIP

Reference information only; the concepts translate across platforms.

  • Gatekeeper : checks code signatures on first launch, using the quarantine flag from downloaded files.
  • SIP (System Integrity Protection) : kernel-level protection that prevents modification of system files even by root.
  • Notarization : Apple scans submitted software for malware before signing.
  • Hardened Runtime : opt-in sandbox and entitlement capabilities for macOS apps.

Code Signing Trust Anchors

All three platforms depend on code signing:

# Linux: check ELF binary signatures
# (requires IMA appraisal or RPM GPG signatures)
rpm -Kv /usr/bin/bash
# Shows: Digest, Signature (GPG key ID)

# Verify a detached signature
gpg --verify /usr/bin/some-binary.sig /usr/bin/some-binary
						
# Windows: check the Authenticode signature
Get-AuthenticodeSignature -FilePath C:\Windows\System32\notepad.exe

# Output includes:
# SignerCertificate: CN=Microsoft Windows, O=Microsoft Corporation...
# Status: Valid
# Path: C:\Windows\System32\notepad.exe
						
# macOS: check the code signature
codesign -dvvv /Applications/Safari.app
# Shows: Identifier, Authority (cert chain), TeamIdentifier

Bypass Techniques

Understanding bypasses is essential for building effective policies:

  • Path-rule bypass : malware writes to an allowed path, for example a writable subdirectory of %PROGRAMFILES% .
  • Hash-rule bypass : any file modification invalidates the hash; impractical for frequently updated software.
  • LOLBin abuse : a trusted binary (PowerShell, mshta, regsvr32, certutil) executes malicious code. Mitigation: WDAC plus Constrained Language Mode for PowerShell.
  • DLL side-loading : a trusted signed executable loads an unsigned malicious DLL . Mitigation: WDAC DLL rules and app-specific search path restrictions.
  • Script interpreters : Python, PowerShell, Windows Script Host, and CScript are trusted but can execute arbitrary scripts. Mitigation: script enforcement via AMSI , WDAC script rules, and software restriction policies.
  • Linux preloading : LD_PRELOAD loads a shared library into a trusted binary. Mitigation: block untrusted shared libraries with ftype=application/x-sharedlib rules, and combine with IMA appraisal so modified libraries are caught.

Audit Before Enforce

Every platform supports an audit or log-only mode. The sequence is always:

1. Deploy in audit mode
2. Collect logs for 1-2 weeks of normal operation
3. Analyze deny_audit events:
   - Legitimate software that needs an allow rule -> add rule
   - Expected malware/attack -> these will be blocked in enforcement mode
   - False positives -> adjust rules
4. Once deny_audit events are only for expected-malicious patterns:
   - Switch deny_audit to deny
   - Monitor for 1 week
5. Fully operational

For in-house developed or locally compiled software, trust it by path (less secure, easier), by hash with fapolicyd-cli --file add (more secure, manual), or by signing key (most secure, but you must package the software as RPMs or import your public key).

Challenge

Write a Go policy evaluator with fapolicyd-style first-match-wins semantics. It reads a rules file of allow <prefix> and deny <prefix> lines and an executable path, then prints ALLOW or DENY. The default action is DENY. 

package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"
)

type rule struct {
	allow  bool
	prefix string
}

func loadRules(path string) ([]rule, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()

	rules := make([]rule, 0)
	scanner := bufio.NewScanner(f)
	for scanner.Scan() {
		line := strings.TrimSpace(scanner.Text())
		if line == "" || strings.HasPrefix(line, "#") {
			continue
		}
		fields := strings.Fields(line)
		if len(fields) != 2 {
			continue
		}
		rules = append(rules, rule{allow: fields[0] == "allow", prefix: fields[1]})
	}
	return rules, scanner.Err()
}

func decide(rules []rule, path string) (bool, string) {
	for _, r := range rules {
		if strings.HasPrefix(path, r.prefix) {
			return r.allow, r.prefix
		}
	}
	return false, "default"
}

func main() {
	if len(os.Args) != 3 {
		fmt.Fprintf(os.Stderr, "usage: %s <rules.txt> <path>\n", os.Args[0])
		os.Exit(2)
	}

	rules, err := loadRules(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	allowed, matched := decide(rules, os.Args[2])
	verdict := "DENY"
	if allowed {
		verdict = "ALLOW"
	}
	fmt.Printf("%s %s (matched: %s)\n", verdict, os.Args[2], matched)
}

Try it with a small rules file and the interesting paths:

cat > rules.txt <<'EOF'
# trusted system paths
allow /usr/
allow /opt/myapp/
# never execute from staging directories
deny /tmp/
deny /home/
EOF

go run fapolicy.go rules.txt /usr/bin/bash
go run fapolicy.go rules.txt /tmp/payload
go run fapolicy.go rules.txt /home/student/.cache/run

Then add a rule that allows a developer path before the broad deny /home/ line and confirm that first-match-wins ordering is what decides the outcome.
