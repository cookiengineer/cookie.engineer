Unix Permissions

Traditional rwx permissions, the setuid, setgid, and sticky bits, umask, kernel access checks, extended attributes, and POSIX access control lists with getfacl and setfacl.

Overview

Unix permissions decide which users may read, write, or execute every file and directory on the system. The model looks simple - three bits each for owner, group, and other - but the special bits, the umask, the kernel's access check order, extended attributes, and POSIX access control lists all change the outcome. Misreading this layer is a common source of privilege escalation bugs. After this article you can decode a mode, predict access decisions, and audit a system for dangerous permission bits.

  • Filesystems - inodes, stat(), directory structure
  • Processes - RUID, EUID, SUID, and supplementary groups
  • Capabilities - root privileges split into independent bits

The Traditional Permission Model

Every inode carries a mode field whose low 16 bits encode the file type and the access permissions. The low 12 bits are the permission bits, the type occupies the next 4 bits: 

st_mode (low 16 bits):
+-------+-----+-----+-----+-----+-----+-----+-----+
| type  |suid |sgid |stky | rwx | rwx | rwx |     |
| (4)   | (1) | (1) | (1) | (3) | (3) | (3) |     |
|       |     |     |     |owner|group|other|     |
+-------+-----+-----+-----+-----+-----+-----+-----+

File type bits (octal):
  0100000 = regular file     (S_IFREG)
  0040000 = directory        (S_IFDIR)
  0120000 = symbolic link    (S_IFLNK)
  0010000 = FIFO/pipe        (S_IFIFO)
  0020000 = character device (S_IFCHR)
  0060000 = block device     (S_IFBLK)
  0140000 = socket           (S_IFSOCK)

Special mode bits (octal):
  004000 = setuid bit
  002000 = setgid bit
  001000 = sticky bit

Permission bits (octal):
  000400 = owner read
  000200 = owner write
  000100 = owner execute
  000040 = group read
  000020 = group write
  000010 = group execute
  000004 = other read
  000002 = other write
  000001 = other execute

Regular Files

Bit Symbol Meaning
r Read Can read the file contents
w Write Can modify (write, truncate, append) the file
x Execute Can execute the file as a program (or via its #! interpreter)

Directories

Bit Symbol Meaning
r Read Can list directory entries (ls)
w Write Can create, delete, and rename files within the directory
x Execute (search) Can traverse the directory (cd, or use as a path component)

A common misconception: rw- on /foo without x prevents access to /foo/bar even if /foo/bar is rwx . The x bit on a directory controls traversal, not listing. 

# Demonstrate directory traversal dependency on 'x'
mkdir -p /tmp/permdemo/secret
chmod 644 /tmp/permdemo      # rw-r--r-- (no x)
cat /tmp/permdemo/secret     # Permission denied - cannot traverse
chmod 755 /tmp/permdemo      # rwxr-xr-x
cat /tmp/permdemo/secret     # OK - can traverse
rm -rf /tmp/permdemo

The Special Permission Bits

Three bits extend the basic rwx model. They live above the permission bits in the mode word and change how the kernel treats a file or directory.

setuid (04000)

When set on an executable, the process runs with the effective UID of the file owner, not the invoker: 

# /usr/bin/passwd is the classic example
ls -l /usr/bin/passwd
# -rwsr-xr-x 1 root root ... /usr/bin/passwd
#   ^
#   s in the owner execute position = setuid + execute

# The 's' vs 'S' distinction:
# s = setuid + executable by owner (lowercase)
# S = setuid but NOT executable by owner (uppercase, uncommon)

setgid (02000)

On an executable, the process runs with the effective GID of the file's group. On a directory, new files and subdirectories inherit the directory's group instead of the creator's primary group. New subdirectories also inherit the setgid bit automatically: 

mkdir /tmp/setgid-demo
chgrp wheel /tmp/setgid-demo   # Or any group the user is in
chmod 2775 /tmp/setgid-demo    # drwxrwsr-x
touch /tmp/setgid-demo/test
ls -l /tmp/setgid-demo/test
# -rw-r--r-- 1 user wheel 0 ... test
#                  ^^^^^ inherited group
rm -rf /tmp/setgid-demo

sticky (01000)

The sticky bit is only meaningful on directories. When set, only the file's owner, the directory's owner, or root can delete or rename files inside that directory. The classic use is /tmp : 

ls -ld /tmp
# drwxrwxrwt 21 root root 4096 ... /tmp
#          ^
#          t in the other execute position = sticky + other-execute

# /tmp is world-writable but sticky prevents users from deleting
# each other's files. Without the sticky bit, any user with write
# permission on /tmp could delete any file there.

chmod - Symbolic and Octal

# Octal - set entire permissions at once
chmod 755 script.sh        # rwxr-xr-x
chmod 600 id_rsa           # rw-------
chmod 1777 /tmp/shared     # rwxrwxrwt (sticky)

# Symbolic - modify specific parts
chmod u+x script.sh        # Add execute for owner
chmod go-w file.txt        # Remove write for group and other
chmod a+r document.pdf     # Add read for all (user+group+other)
chmod ug=rwx,o=rx dir/     # Set exact: owner/group rwx, other rx

# Recursive
chmod -R 755 /opt/myapp/   # Recursively set

# Reference: copy permissions from one file to another
chmod --reference=good_perms.txt new_file.txt

chown and chgrp

# Change owner
sudo chown alice file.txt

# Change owner and group
sudo chown alice:developers file.txt

# Change only group
chgrp developers file.txt

# Recursively change group
chgrp -R developers /opt/team-project/

# Reference: copy ownership from another file
sudo chown --reference=template.txt new_file.txt

# Only root can change file ownership (CAP_CHOWN capability)
# Users can change a file's group to any group they belong to

umask - Default Permission Mask

umask defines which permission bits are masked out when a new file or directory is created. It is a per-process setting, inherited from the parent at fork. 

# View current umask
umask
# Output: 0022

# 0022 means:
#  - Full directory permissions start at 0777
#  - umask 0022 removes ----w--w- (group write, other write)
#  - New directory gets 0755 (rwxr-xr-x)
#
# For files (which start at 0666 - no execute by default):
#  - 0666 minus 0022 = 0644 (rw-r--r--)

# Set umask
umask 0007  # Other gets NO permissions (files: 0660, dirs: 0770)
umask 0077  # Only owner gets permissions (files: 0600, dirs: 0700)

# Common umask values:
# 0022 -> files: 0644, dirs: 0755  (standard)
# 0002 -> files: 0664, dirs: 0775  (group-writable)
# 0077 -> files: 0600, dirs: 0700  (private)
						
#include <stdio.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>

int main() {
    mode_t old = umask(0);          // Read current
    printf("Current umask: %04o\n", old);

    umask(0022);                    // Set new
    printf("Set to: %04o\n", umask(0022));

    // Create file - permissions = 0666 & ~umask
    int fd = creat("/tmp/umask-test-file", 0666);
    close(fd);

    struct stat sb;
    stat("/tmp/umask-test-file", &sb);
    printf("Created file mode: %04o\n", sb.st_mode & 0777);
    // Output: 0644  (0666 & ~0022)

    unlink("/tmp/umask-test-file");
    return 0;
}

How the Kernel Checks Permissions

When a process tries to access an inode, the kernel applies this decision procedure:

process_requests_access(inode, requested_mask):
    if process.EUID == 0:     <- Root bypasses most checks
        if requested is EXEC and NO x bits at all: deny
        else: allow
    elif process.EUID == inode.UID:
        check owner bits (mode[8:6])
    elif process.EGID in (inode.GID, supplementary_groups):
        check group bits (mode[5:3])
    else:
        check other bits (mode[2:0])
						
# Check process credentials
id
# uid=1000(user) gid=1000(user) groups=1000(user),10(wheel),998(docker)

# The kernel checks EUID first, then EGID/supplementary groups,
# then falls through to "other." Only the first match is used:
# if you own the file, group and other permissions are ignored.

If ACLs are present, the ACL check replaces the owner, group, and other steps. See the ACL section below.

How setuid Works - UID Transitions

Each process has three user IDs: the real UID (RUID, who started it), the effective UID (EUID, used for access checks), and the saved set-user-ID (SUID, which remembers a privilege that can be regained): 

#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main() {
    uid_t ruid, euid, suid;
    getresuid(&ruid, &euid, &suid);
    printf("RUID=%d  EUID=%d  SUID=%d\n", ruid, euid, suid);

    // Drop privileges temporarily:
    seteuid(ruid);  // EUID -> RUID; SUID saves old EUID
    getresuid(&ruid, &euid, &suid);
    printf("After seteuid(RUID): RUID=%d  EUID=%d  SUID=%d\n",
           ruid, euid, suid);

    // Restore privileges:
    seteuid(suid);  // EUID <- SUID
    getresuid(&ruid, &euid, &suid);
    printf("After seteuid(SUID): RUID=%d  EUID=%d  SUID=%d\n",
           ruid, euid, suid);
    return 0;
}
						
gcc -o uid-demo uid-demo.c && ./uid-demo

# Make it setuid root to observe the privilege model:
sudo chown root:root uid-demo
sudo chmod 4755 uid-demo
./uid-demo

A setuid program must be defensive:

  • system() and exec*() inherit the real UID, so a shell started by a setuid program runs

without the elevated privileges unless the program explicitly raises them. - Environment variables such as LD_PRELOAD , PATH , and IFS must be sanitized. The dynamic

loader ignores LD_PRELOAD for setuid binaries, but other variables are not always safe. - File descriptors inherited from a less-privileged parent can surprise the setuid process. - The kernel ignores the setuid bit on #! scripts; it follows the interpreter binary's setuid

bit instead. Use sudo or capabilities when a script needs privilege.

Extended Attributes (xattr)

Extended attributes are name-value pairs attached to inodes and stored separately from the file data. SELinux, ACLs , and applications use them: 

# List all xattrs on a file
getfattr -d somefile
# Or: attr -l somefile

# Set a user xattr
setfattr -n user.comment -v "Important document" somefile
# Or: attr -s comment -V "Important document" somefile

# Get a specific xattr
getfattr -n user.comment somefile

# Namespaces:
# user.*       - set by unprivileged users on regular files (requires attr mount option)
# trusted.*    - set by CAP_SYS_ADMIN only
# security.*   - set by security modules (SELinux: security.selinux)
# system.*     - set by kernel (system.posix_acl_access, system.posix_acl_default)
						
# Check if filesystem supports xattrs
mount | grep ' / '
# Look for 'user_xattr' or 'xattr' in mount options (default on ext4)

# Enable user xattrs if not present:
sudo mount -o remount,user_xattr /

POSIX Access Control Lists

Traditional Unix permissions give three categories (owner, group, other). POSIX access control lists allow per-user and per-group permissions with fine granularity: 

Traditional:       ACLs:
+------------+     +----------------------+
| owner  rwx |     | owner:: rwx          |
| group  r-x |     | user:bob: rwx        | <- extra user
| other  --- |     | user:carol: r--      | <- extra user
+------------+     | group:: r-x          |
                   | group:devs: rwx      | <- extra group
                   | mask:: rwx           | <- max for named users/groups + group
                   | other:: ---          |
                   +----------------------+

The ACL mask limits the permissions granted to all named users, named groups, and the owning group. It does not affect the file owner or the other entries. This provides backward compatibility: tools that use chmod on the group bits actually modify the ACL mask. 

# View ACLs
getfacl important_file.txt

# Set ACLs
setfacl -m u:alice:rwx important_file.txt     # Add user alice with rwx
setfacl -m g:developers:rx important_file.txt  # Add group developers with rx
setfacl -m u:carol:--- important_file.txt       # Explicitly deny carol
setfacl -x u:alice important_file.txt          # Remove alice's entry
setfacl -b important_file.txt                  # Remove all ACLs

# Default ACLs on a directory (inherited by new objects inside)
setfacl -m d:u:alice:rwx /shared/dir/
setfacl -m d:g:developers:rwx /shared/dir/

# New files in /shared/dir/ automatically inherit these ACLs

ACL Mask and chmod

touch test
setfacl -m u:alice:rwx test
getfacl test
# user:alice:rwx        <- Alice has rwx
# mask::rwx             <- Mask allows full rwx

chmod g-w test          # Remove group write - this modifies the MASK
getfacl test
# user:alice:rwx        # Still stored as rwx
# mask::r-x             # But effective permissions are r-x
# Effective: r-x        <- Alice's effective permission is limited by mask

The ls -l group permission field shows the mask when ACLs are present. An ACL file shows + after the permission string: 

ls -l test
# -rwxr-x---+ 1 user user 0 ... test
#          ^
#          '+' indicates ACLs are present

Practical ACL Examples

# Scenario: Shared project directory
mkdir /opt/project
chown root:devteam /opt/project

# Default: new directories get 2770, new files get 0660
# Plus: alice and bob get full access regardless of group
setfacl -m g:devteam:rwx /opt/project
setfacl -m d:g:devteam:rwx /opt/project
setfacl -m u:alice:rwx /opt/project
setfacl -m d:u:alice:rwx /opt/project
setfacl -m u:bob:rwx /opt/project
setfacl -m d:u:bob:rwx /opt/project

# Verify setup
getfacl /opt/project

# Create a test file
su - alice -c 'touch /opt/project/alice-file'
ls -l /opt/project/alice-file
getfacl /opt/project/alice-file

# Scenario: Web server directory
setfacl -m u:http:rx /srv/www/site
setfacl -m u:http:rwx /srv/www/site/uploads
setfacl -m d:u:http:rwx /srv/www/site/uploads
setfacl -m d:g:webdevs:rwx /srv/www/site/uploads

ls -l Interpretation Guide

-rwxrw-r-- 1 alice devs 4096 Jun 26 12:00 script.sh
|  |     |  |   |    |    |              |
|  |     |  |   |    |    |              +-- File name
|  |     |  |   |    |    +-- Modification time
|  |     |  |   |    +-- Size in bytes
|  |     |  |   +-- Group owner
|  |     |  +-- User owner
|  |     +-- Link count
|  +-- Permissions string (detailed below)
+-- File type (-=file, d=dir, l=symlink, c=char, b=block, p=FIFO, s=socket)

Permissions string breakdown (rwxrw-r--):
Position 1  (owner): rwx - read, write, execute
Position 4  (group): rw- - read, write, no execute
Position 7  (other): r-- - read only

Special cases:
Position 3: s = setuid + execute, S = setuid, no execute
Position 6: s = setgid + execute, S = setgid, no execute
Position 9: t = sticky + execute, T = sticky, no execute
Position *: + = ACLs present
Position *: @ = extended attributes present (macOS)

Verification Checklist

# 1. Check current umask
umask

# 2. Find all setuid binaries on the system
find /usr/bin /usr/sbin /bin /sbin -perm -4000 -ls 2>/dev/null

# 3. Find all setgid directories on the system
find / -perm -2000 -type d -ls 2>/dev/null | head -20

# 4. Check for world-writable files (security audit)
find /etc -perm -0002 -type f -ls 2>/dev/null

# 5. Check if a specific file has ACLs
getfacl /etc/hostname 2>/dev/null
ls -l /etc/hostname | grep '+'

# 6. Check filesystem ACL and xattr support
mount | grep -E 'acl|user_xattr|xattr'

# 7. Inspect all permission bits on a file
stat -c '%a %A %n' /etc/hostname

# 8. Demonstrate sticky bit
mkdir /tmp/sticky-test /tmp/nosticky-test
chmod 1777 /tmp/sticky-test     # Sticky
chmod 0777 /tmp/nosticky-test   # No sticky
# As user1: touch /tmp/sticky-test/user1-file /tmp/nosticky-test/user1-file
# As user2: rm /tmp/sticky-test/user1-file    -> Operation not permitted
# As user2: rm /tmp/nosticky-test/user1-file  -> SUCCESS (deleted user1's file)
rm -rf /tmp/sticky-test /tmp/nosticky-test

# 9. See effective permissions with namei
namei -l /var/log/syslog  # Shows ownership and perms at each path component

# 10. Show process credentials that affect file access
cat /proc/$$/status | grep -E "^Uid:|^Gid:|^Groups:"

Challenge

Write a Go program that decodes a Unix mode into its ls -l symbolic form. The starter below renders the nine rwx bits but ignores the special bits. Complete decode so it produces the s and t characters, then check it against stat -c %A for the modes 4755 , 2775 , 1777 , 0644 , and 0000 : 

package main

import (
	"fmt"
	"os"
	"strconv"
)

// decode renders the low 12 bits of a mode the way ls -l does.
// TODO: handle setuid (04000), setgid (02000), and sticky (01000),
//       which use the s/S and t/T positions.
func decode(mode uint32) string {
	symbolic := []byte("---------")
	for i := 0; i < 9; i++ {
		if mode&(1<<(8-i)) != 0 {
			symbolic[i] = "rwx"[i%3]
		}
	}
	return string(symbolic)
}

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "usage: perms <octal-mode>")
		os.Exit(1)
	}

	value, err := strconv.ParseUint(os.Args[1], 8, 32)
	if err != nil {
		fmt.Fprintln(os.Stderr, "invalid octal mode:", err)
		os.Exit(1)
	}

	fmt.Printf("0%o -> %s\n", value, decode(uint32(value)))
}

Run it with go run . 4755 and compare the output with stat -c %A /usr/bin/passwd . Then extend the program to take a path, read the mode with os.Stat , and print the user and group owners from syscall.Stat_t .
