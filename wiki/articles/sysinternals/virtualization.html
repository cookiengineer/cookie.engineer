Virtualization Internals

Hardware-assisted virtualization internals, from CPU privilege modes and hypervisor control structures to two-level address translation, paravirtual I/O, and guest escape attacks.

Overview

Guest isolation on x86 once required binary translation or paravirtualization, because the hypervisor and the guest kernel competed for ring 0. Hardware extensions removed that conflict: Intel VMX and AMD SVM add a privilege dimension above ring 0, a control structure ( VMCS or VMCB ), and second-level address translation ( EPT or NPT ). This article follows those mechanisms down to the KVM interface at /dev/kvm , then covers Hyper-V hypercalls, virtio paravirtual I/O, nested virtualization, and the escape and side-channel attacks that target hypervisors.

  • Virtualization Fundamentals - hypervisors, QEMU, libvirt basics

The Virtualization Problem

Virtualization is the problem of running multiple guest operating systems on a single physical machine while maintaining isolation, performance, and compatibility. Before hardware virtualization extensions (Intel VT-x in 2005, AMD-V in 2006), x86 virtualization relied on binary translation: the hypervisor scanned guest code at runtime and rewrote privileged instructions on the fly. This was slow and complex.

Hardware virtualization adds a new CPU operating mode - a dimension orthogonal to ring 0-3 - that allows the hypervisor to run at a higher privilege level than the guest kernel without binary translation.

VMCS Control Structure

The VMCS is a 4 KB (one page) data structure that controls VMX non-root operation and records VM exit information. It is configured via VMREAD and VMWRITE instructions and is always associated with exactly one logical processor.

Extended Page Tables (EPT)

Without EPT , the hypervisor must maintain shadow page tables - a synthetic set of page tables that combine guest-virtual to guest-physical and guest-physical to host-physical translations. Shadow page tables are expensive: every guest CR3 change requires rebuilding the shadow tables.

EPT provides hardware-level second-level address translation. The guest manages its own page tables (guest-virtual to guest-physical), and the hypervisor configures EPT (guest-physical to host-physical). The CPU 's MMU walks both tables in hardware, in a single TLB lookup. 

┌──────────────────────────────────────────────────────────────────────┐
│                    TWO-LEVEL ADDRESS TRANSLATION (EPT)                 │
│                                                                      │
│  Guest Virtual Address (GVA)                                          │
│       │                                                              │
│       ▼                                                              │
│  ┌──────────────────────────────────────────┐                        │
│  │   Guest Page Tables (managed by guest)   │   CR3 (guest)          │
│  │   GVA → GPA translation                  │                        │
│  │   PML4 → PDPT → PD → PT → 4KB page      │                        │
│  └──────────────────+───────────────────────┘                        │
│                     │ Guest Physical Address (GPA)                    │
│                     ▼                                                │
│  ┌──────────────────────────────────────────┐                        │
│  │   Extended Page Tables (managed by host) │   EPT pointer (VMCS)   │
│  │   GPA → HPA translation                  │                        │
│  │   EPT PML4 → EPT PDPT → EPT PD → EPT PT │                        │
│  └──────────────────+───────────────────────┘                        │
│                     │ Host Physical Address (HPA)                     │
│                     ▼                                                │
│              ┌──────────────┐                                        │
│              │  DRAM PAGE   │                                        │
│              └──────────────┘                                        │
│                                                                      │
│  EPT Violations occur when:                                          │
│  - GPA does not map to any HPA (not present)                        │
│  - Access type not permitted by EPT entry (read/write/execute)      │
│  - The EPT paging-structure entry is misconfigured                  │
│                                                                      │
│  Hardware walks both tables, interleaved:                            │
│    TLB stores: {GVA → HPA} directly                                 │
│    On TLB miss: walks GVA→GPA then GPA→HPA in hardware              │
│    VPID tags TLB entries per-VM to avoid flush on VM exit            │
└──────────────────────────────────────────────────────────────────────┘

AMD-V (SVM)

AMD's SVM (Secure Virtual Machine) offers equivalent functionality with a different architecture:

Feature Intel VMX AMD SVM
Control structure VMCS (4 KB) VMCB (4 KB)
VM entry instruction VMLAUNCH/VMRESUME VMRUN
VM exit return VM-exit handler + VMRESUME #VMEXIT followed by VMRUN
Nested page tables EPT NPT (Nested Page Tables)
Virtual processor ID VPID ASID (Address Space Identifier)
Posted interrupts APICv AVIC (Advanced Virtual Interrupt Controller)
Intercept bitmap VM-execution controls VMCB.intercept bitmaps (legacy) + VMCB.ctrl_area
Virtual interrupt injection VMCS fields for vector info VMCB.vintr
Nested virtualization VMCS shadowing + VMCS link VMRUN from within guest (nv=VMRUN)

AMD VMRUN Flow

; Hypervisor entry point after guest #VMEXIT:
vmrun_handler:
    ; The VMCB contains the saved guest state
    ; The #VMEXIT reason is the EXITCODE field at VMCB offset 0x70
    mov rax, vmcb.exitcode
    cmp rax, 0x000   ; SVM_EXIT_READ_CR0
    je  handle_cr0_read
    cmp rax, 0x072   ; SVM_EXIT_CPUID
    je  handle_cpuid
    cmp rax, 0x081   ; SVM_EXIT_VMMCALL
    je  handle_hypercall
    ; ... handle other exit reasons ...

    ; After handling, resume guest:
    mov rax, vmcb_phys_addr
    vmrun rax        ; Enters guest at guest RIP from VMCB
    ; At this point, execution continues inside the guest
    ; The next instruction to execute here is the return
    ; from the NEXT #VMEXIT

KVM Architecture

Creating a KVM Guest

#include <fcntl.h>
#include <linux/kvm.h>
#include <sys/ioctl.h>
#include <sys/mman.h>

// 1. Open /dev/kvm
int kvm_fd = open("/dev/kvm", O_RDWR);
if (kvm_fd < 0) { perror("open /dev/kvm"); exit(1); }

// 2. Check KVM API version
int api_version = ioctl(kvm_fd, KVM_GET_API_VERSION, 0);
assert(api_version == 12);

// 3. Create a VM
int vm_fd = ioctl(kvm_fd, KVM_CREATE_VM, 0);

// 4. Allocate guest physical memory
size_t guest_mem_size = 128 * 1024 * 1024;  // 128 MB
void *guest_mem = mmap(NULL, guest_mem_size,
    PROT_READ | PROT_WRITE, MAP_SHARED | MAP_ANONYMOUS, -1, 0);

struct kvm_userspace_memory_region region = {
    .slot = 0,
    .guest_phys_addr = 0,
    .memory_size = guest_mem_size,
    .userspace_addr = (uint64_t)guest_mem,
    .flags = 0,
};
ioctl(vm_fd, KVM_SET_USER_MEMORY_REGION, &region);

// 5. Create a vCPU
int vcpu_fd = ioctl(vm_fd, KVM_CREATE_VCPU, 0);
int vcpu_mmap_size = ioctl(kvm_fd, KVM_GET_VCPU_MMAP_SIZE, 0);
struct kvm_run *run = mmap(NULL, vcpu_mmap_size,
    PROT_READ | PROT_WRITE, MAP_SHARED, vcpu_fd, 0);

// 6. Initialize vCPU state (registers, page tables, etc.)
struct kvm_regs regs = {0};
struct kvm_sregs sregs = {0};
// ... set up regs.rip to entry point, sregs.cr3 to page tables ...
ioctl(vcpu_fd, KVM_SET_REGS, &regs);
ioctl(vcpu_fd, KVM_SET_SREGS, &sregs);

// 7. Run the guest — main loop
while (1) {
    int ret = ioctl(vcpu_fd, KVM_RUN, 0);
    if (ret < 0) { perror("KVM_RUN"); break; }

    switch (run->exit_reason) {
    case KVM_EXIT_IO:
        // Handle PIO (port I/O) — e.g., serial console output
        if (run->io.direction == KVM_EXIT_IO_OUT &&
            run->io.port == 0x3F8) {  // COM1
            write(STDOUT_FILENO,
                  (char*)guest_mem + run->io.data_offset,
                  run->io.size);
        }
        break;
    case KVM_EXIT_HLT:
        // Guest halted — we're done
        goto done;
    case KVM_EXIT_FAIL_ENTRY:
        fprintf(stderr, "KVM: failed entry, hardware reason %llx\n",
                run->fail_entry.hardware_entry_failure_reason);
        goto done;
    default:
        fprintf(stderr, "KVM: exit reason %d\n", run->exit_reason);
        goto done;
    }
}
done:

QEMU + KVM Interaction

QEMU emulates hardware devices; KVM accelerates CPU and memory. Together they form a full virtualization platform: 

┌──────────────────────────────────────────────────────────────────────┐
│                     QEMU + KVM RESPONSIBILITY SPLIT                    │
│                                                                      │
│  KVM (kernel) handles:                                                │
│    - CPU execution (VMX non-root mode)                                │
│    - Memory virtualization (EPT/NPT)                                  │
│    - Interrupt injection (APICv/AVIC)                                │
│    - Timers (TSC offset, preemption timer)                            │
│    - Selective VM exits (CPUID, MSR, I/O)                            │
│                                                                      │
│  QEMU (userspace) handles:                                            │
│    - Device emulation (NIC, disk, USB, VGA, serial)                   │
│    - Firmware (SeaBIOS, OVMF/edk2 for UEFI)                          │
│    - ACPI/SMBIOS tables                                               │
│    - Live migration orchestration                                     │
│    - VM configuration (CPU topology, NUMA)                            │
│    - QMP (QEMU Machine Protocol) monitoring                           │
│                                                                      │
│  Flow:                                                                │
│    Guest executes I/O instruction (e.g., outb to disk controller)    │
│    → VM Exit (KVM_EXIT_IO)                                            │
│    → KVM delivers to QEMU via kvm_run struct                          │
│    → QEMU emulates the device                                         │
│    → QEMU ioctl(KVM_RUN) to re-enter guest                            │
└──────────────────────────────────────────────────────────────────────┘

Hyper-V Architecture

Hyper-V is Microsoft's Type 1 hypervisor. On Windows, the "root partition" runs the management OS and device drivers; "child partitions" run guests. On Linux, the Hyper-V synthetic devices (netvsc, storvsc) use the VMBus channel for paravirtualized I/O.

Hyper-V Hypercalls

// Hyper-V hypercall ABI: the guest invokes VMCALL through a hypercall page
// that the hypervisor fills with code stubs.

// Hypercall input registers (64-bit):
//   RCX = hypercall input value (control + input GPA)
//   RDX = input parameter GPA (for rep hypercalls) or immediate value
//   R8  = output parameter GPA

// Example: HvCallPostMessage (post a message to a VMBus channel)
// The control value encodes:
//   Call code: 0x005C (HVCALL_POST_MESSAGE)
//   Fast: 0 (memory-based, uses GPA pointers)
//   Rep count: bits 30:17

struct hv_input_post_message {
    u32 connection_id;
    u32 reserved;
    u32 message_type;
    u32 payload_size;
    u8  payload[240];  // max 240 bytes
};

// The guest writes the hypercall page GPA into MSR 0x40000001
// (HV_X64_MSR_HYPERCALL), and Hyper-V populates that page in place.
// CPUID leaf 0x40000002 reports the hypervisor version, not the page address.

Virtio Paravirtualized I/O

Virtio is the standard interface for paravirtualized devices on Linux/ KVM . Unlike emulated devices, where every MMIO or PIO access triggers a VM exit, virtio uses shared memory rings (virtqueues) to batch I/O operations and minimize exits.

Nested Virtualization

Nested virtualization runs a hypervisor inside a VM . L0 is the physical hypervisor, L1 is the guest hypervisor, and L2 is the innermost guest. 

┌──────────────────────────────────────────────────────────────────────┐
│                     NESTED VIRTUALIZATION                              │
│                                                                      │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │                         L2 Guest                              │   │
│  │  (VM running inside L1 hypervisor)                            │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                              │                                       │
│  ┌───────────────────────────▼──────────────────────────────────┐   │
│  │                     L1 Hypervisor (guest)                      │   │
│  │  e.g., KVM inside KVM, Hyper-V inside KVM                     │   │
│  │  - L1 executes VMXON/VMRUN (causes VM exit to L0)              │   │
│  │  - L0 emulates or accelerates these instructions              │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                              │                                       │
│  ┌───────────────────────────▼──────────────────────────────────┐   │
│  │                     L0 Hypervisor (host)                       │   │
│  │  Hardware VMX support with VMCS shadowing                     │   │
│  │  - L1's VMCS is "shadowed" in hardware                        │   │
│  │  - VM exits from L2 first go to L0 (or directly to L1)       │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  Without VMCS shadowing: every L1→L2 VMRESUME causes exit to L0.    │
│  With VMCS shadowing: L1 writes to its VMCS → L0 merges into        │
│  hardware VMCS → L2 executes directly. Fewer exits, better perf.    │
└──────────────────────────────────────────────────────────────────────┘

VM Escape Vulnerabilities

A VM escape occurs when code inside a guest VM breaks isolation and executes on the host hypervisor. This is the most severe virtualization vulnerability.

Notable VM Escape CVEs

CVE Affected Mechanism Impact
CVE-2015-3456 (VENOM) QEMU floppy disk controller Buffer overflow in FDC emulation Code execution on host
CVE-2015-7504 QEMU AMD PCnet NIC Heap overflow in pcnet_receive() Code execution on host
CVE-2016-3710 QEMU VGA (VMware) Improper bounds checking in VGA Code execution on host
CVE-2020-14364 QEMU USB emulation Out-of-bounds read/write in USB Code execution on host
CVE-2021-28476 Hyper-V vmswitch Malformed packet handling Host code execution
CVE-2021-29657 KVM AMD SVM Nested VMCB double fetch (TOCTOU) Host privilege escalation

VM Escape Attack Chain

1. Guest user → Guest kernel privilege escalation (LPE)
2. Guest kernel → Identify hypervisor interface
   - CPUID vendor string ("KVMKVMKVM", "Microsoft Hv", "VMwareVMware")
   - I/O port probing (0x5658 = VMware backdoor)
   - Device enumeration (virtio, Hyper-V synthetic devices)
3. Trigger vulnerability in emulated device:
   - Craft malicious I/O operation → VM exit → QEMU processes request
   - Trigger buffer overflow in QEMU device emulation
   - Gain code execution in QEMU process (host userspace)
4. QEMU → Host ring 0 (further exploit if QEMU is not sandboxed)

Virtualization Side Channels

Shared microarchitectural state crosses the guest boundary even when memory is isolated. The following classes leak data between guests or from host to guest: 

┌──────────────────────────────────────────────────────────────────────┐
│               VIRTUALIZATION SIDE-CHANNEL ATTACKS                      │
│                                                                      │
│  L1TF (L1 Terminal Fault):                                           │
│    - CPU speculative execution reads PTE "not present" entries.      │
│    - Attacker VM maps page, then unmaps.                             │
│    - Speculative access leaks data through cache timing.             │
│    - Mitigation: PTE inversion (mark all not-present PTEs with       │
│      invalid physical address), disable SMT, or flush L1 on VM entry.│
│                                                                      │
│  MDS (Microarchitectural Data Sampling):                              │
│    - Leaks stale data from CPU internal buffers.                     │
│    - Cross-VM: attacker VM can read data left in buffers by victim.  │
│    - Mitigation: VERW instruction on kernel entry, clear buffers.    │
│                                                                      │
│  Cross-VM Cache Attacks (Prime+Probe):                                │
│    ┌──────────────────────────────────────────────────────------─┐  │
│    │  Step 1: Attacker VM primes L1/L3 cache with known data     │  │
│    │  Step 2: Victim VM executes — evicts some attacker cache    │  │
│    │          lines based on its memory access patterns           │  │
│    │  Step 3: Attacker probes cache to see which lines were      │  │
│    │          evicted → infers victim's memory access pattern    │  │
│    │                                                              │  │
│    │  Used to: steal AES keys, infer keystroke timing, etc.      │  │
│    └──────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  Mitigations:                                                         │
│    - Cache partitioning (Intel CAT — Cache Allocation Technology)    │
│    - Core scheduling (pin VMs to dedicated cores)                     │
│    - Disable SMT (Hyper-Threading) on security-sensitive hosts        │
│    - Flush L1/L2 on VM entry (slow)                                   │
└──────────────────────────────────────────────────────────────────────┘

Verification

# 1. Check CPU virtualization support
egrep -o '(vmx|svm)' /proc/cpuinfo | sort -u
# vmx = Intel VT-x supported, svm = AMD-V supported

# 2. Check KVM kernel modules
lsmod | grep kvm
# Expected: kvm_intel (or kvm_amd), kvm

# 3. KVM module parameters
cat /sys/module/kvm/parameters/halt_poll_ns
modinfo kvm | grep -E 'filename|version'
for param in /sys/module/kvm/parameters/*; do
    echo "$(basename $param) = $(cat $param 2>/dev/null)"
done

# 4. KVM Intel/AMD-specific parameters
if lsmod | grep -q kvm_intel; then
    echo "=== Intel KVM parameters ==="
    cat /sys/module/kvm_intel/parameters/ept           # EPT enabled?
    cat /sys/module/kvm_intel/parameters/enable_shadow_vmcs
    cat /sys/module/kvm_intel/parameters/nested        # Nested virt?
    cat /sys/module/kvm_intel/parameters/vpid          # VPID?
    cat /sys/module/kvm_intel/parameters/unrestricted_guest
elif lsmod | grep -q kvm_amd; then
    echo "=== AMD KVM parameters ==="
    cat /sys/module/kvm_amd/parameters/npt             # NPT enabled?
    cat /sys/module/kvm_amd/parameters/nested          # Nested virt?
fi

# 5. Check /dev/kvm permissions
ls -la /dev/kvm
# Expected: crw-rw---- 1 root kvm

# 6. Check virtualized environment (are we inside a VM?)
systemd-detect-virt 2>/dev/null || \
  (grep -qi hypervisor /proc/cpuinfo && echo "VM detected (hypervisor flag)")

# 7. Hypervisor CPUID leaves (install the cpuid package first)
cpuid -1 | grep -i hypervisor
cpuid -r 0x40000000 2>/dev/null    # Hypervisor CPUID range (KVM signature)
cpuid -r 0x40000001 2>/dev/null    # KVM feature flags

# 8. Check for KVM virtual machines
sudo virsh list --all 2>/dev/null || echo "libvirt not installed (optional)"

# 9. CPU virtualization vulnerabilities (side-channel)
for f in /sys/devices/system/cpu/vulnerabilities/*; do
    echo "$(basename $f): $(cat $f)"
done

# 10. TSC and timing checks inside VM
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
cat /sys/devices/system/clocksource/clocksource0/available_clocksource

# 11. Memory encryption (SEV/TDX)
dmesg | grep -i 'SEV\|SME\|TDX' 2>/dev/null
# For AMD SEV: cat /sys/module/kvm_amd/parameters/sev

# 12. Check EPT/NPT features (Intel/AMD specific)
if lsmod | grep -q kvm_intel; then
    dmesg | grep -i 'EPT\|VPID\|VMX' | head -10
elif lsmod | grep -q kvm_amd; then
    dmesg | grep -i 'NPT\|AVIC\|SVM' | head -10
fi

# 13. Run a lightweight VM with QEMU/KVM verification
qemu-system-x86_64 -enable-kvm -cpu host -m 64 -nographic \
  -kernel /boot/vmlinuz-linux -append "console=ttyS0 quiet" \
  -initrd /boot/initramfs-linux.img -serial mon:stdio 2>&1 | head -20
# Ctrl-A X to exit if QEMU starts

# 14. Verify nested virtualization status
cat /sys/module/kvm_intel/parameters/nested 2>/dev/null
cat /sys/module/kvm_amd/parameters/nested 2>/dev/null

Challenge

Write a Go tool that reports whether the local machine can run hardware-accelerated guests. It reads /proc/cpuinfo for the vmx or svm flag, lists the loaded kvm modules, and prints every entry under /sys/devices/system/cpu/vulnerabilities/ that mentions a virtualization or SMT mitigation. Run it on a bare-metal host and inside a virtual machine, then compare the two outputs. 

package main

import (
	"bufio"
	"fmt"
	"os"
	"path/filepath"
	"strings"
)

func cpuFlags(path string) map[string]bool {
	flags := make(map[string]bool)
	file, err := os.Open(path)
	if err != nil {
		return flags
	}
	defer file.Close()

	scanner := bufio.NewScanner(file)
	for scanner.Scan() {
		line := scanner.Text()
		if strings.HasPrefix(line, "flags") {
			parts := strings.SplitN(line, ":", 2)
			if len(parts) == 2 {
				for _, flag := range strings.Fields(parts[1]) {
					flags[flag] = true
				}
			}
		}
	}
	return flags
}

func readParam(path string) string {
	data, err := os.ReadFile(path)
	if err != nil {
		return "n/a"
	}
	return strings.TrimSpace(string(data))
}

func main() {
	flags := cpuFlags("/proc/cpuinfo")

	switch {
	case flags["vmx"]:
		fmt.Println("CPU: Intel VT-x (vmx) available")
		fmt.Println("nested:", readParam("/sys/module/kvm_intel/parameters/nested"))
	case flags["svm"]:
		fmt.Println("CPU: AMD-V (svm) available")
		fmt.Println("nested:", readParam("/sys/module/kvm_amd/parameters/nested"))
	default:
		fmt.Println("CPU: no hardware virtualization extension")
	}

	modules, _ := os.ReadDir("/sys/module")
	for _, module := range modules {
		if strings.HasPrefix(module.Name(), "kvm") {
			fmt.Println("module:", module.Name())
		}
	}

	if info, err := os.Stat("/dev/kvm"); err == nil {
		fmt.Println("/dev/kvm:", info.Mode())
	} else {
		fmt.Println("/dev/kvm: unavailable")
	}

	files, _ := filepath.Glob("/sys/devices/system/cpu/vulnerabilities/*")
	for _, file := range files {
		data, err := os.ReadFile(file)
		if err != nil {
			continue
		}
		text := strings.TrimSpace(string(data))
		if strings.Contains(text, "VMX") || strings.Contains(text, "SVM") ||
			strings.Contains(text, "SMT") || strings.Contains(text, "PTE") {
			fmt.Printf("%-28s %s\n", filepath.Base(file), text)
		}
	}
}

Build and run it:

go build -o virtcheck virtcheck.go
./virtcheck
