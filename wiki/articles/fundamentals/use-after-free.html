Use After Free

Dangling pointers, heap reuse, object layout overlap, and vtable hijack via UAF - why freeing memory does not null the pointer and how reused chunks become type-confused.

Overview

A use-after-free (UAF) is a temporal memory safety violation: a program keeps using a pointer after the memory it points to has been freed. The allocator returns that chunk to a free list and may hand the same bytes to the next allocation. The dangling pointer then sees whatever the new owner wrote, which turns a simple lifetime bug into type confusion and, with a function pointer or vtable in the reused memory, into control-flow hijack. After this article you can trigger a UAF, observe the chunk reuse in GDB, and explain why the bug class still survives modern mitigations.

The Core Mechanism

A use-after-free (UAF) occurs when a program continues to use a pointer after the memory it points to has been freed. The freed chunk is returned to the allocator and may be reused by a subsequent allocation of a different type. The dangling pointer now references memory holding data of an entirely different logical type - type confusion via the allocator.

Three events in sequence:

  1. Allocate object A: struct Auth *auth = malloc(sizeof(struct Auth)) - auth points to heap chunk X.
  2. Free object A: free(auth) - chunk X returns to the free list, but auth still holds the address of X.
  3. Allocate object B: struct Config *cfg = malloc(sizeof(struct Config)) - the allocator reuses chunk X. auth now points to cfg 's memory.

The pointer auth (type struct Auth* ) actually references a struct Config . Any read through auth->is_admin reads cfg 's bytes. Any write through auth corrupts cfg .

Why free() Does Not Null the Pointer

free(ptr) receives the pointer by value. C passes all arguments by value, so free() gets a copy of the address. It can modify the memory at that address (write free-list links, coalesce with neighbors) but it cannot reach back into the caller's stack frame or global variable to set the original pointer to NULL.

void free(void *ptr);  // takes ptr by value, cannot modify caller's variable

char *p = malloc(32);
free(p);
// p still holds 0x5555555592a0 - a dangling pointer

p = NULL;  // programmer must do this manually

The allocator does write into the chunk. free() stores forward pointers ( fd / bk in the tcache, fastbin, or smallbin chains) in the chunk's user-data area. The first 8-16 bytes of freed user memory become the linked-list node structure. This is why a UAF read on a freed chunk leaks heap metadata or pointer values.

Heap Reuse After free()

glibc's allocator maintains per-thread caches (tcache), fastbins, smallbins, largebins, and the unsorted bin. Each serves a different size range. The allocator prefers the fastest path: if a freed chunk of the right size sits in tcache, the very next malloc() of that size returns it.

malloc(32) -> checks tcache bin for 32-byte chunks -> pop head -> return
free(p)    -> push p onto tcache bin for 32-byte chunks -> set p->fd = old head
malloc(32) -> pop head -> returns p (the same pointer)

This deterministic reuse makes UAF highly reliable in practice. The probability of reuse increases with matching allocation sizes, low fragmentation, and tcache presence.

Consider the exact sequence in the glibc source:

// glibc/malloc/malloc.c - tcache_get()
static void *tcache_get(size_t tc_idx) {
    tcache_entry *e = tcache->entries[tc_idx];
    tcache->entries[tc_idx] = e->next;
    --(tcache->counts[tc_idx]);
    return (void *) e;
}

There is no check that the chunk is not still referenced elsewhere and no validation that the caller is the sole owner. It just pops and returns.

Minimal UAF Demonstration

/* uaf_demo.c - basic use-after-free, compile with -g, no optimizations */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

struct Secret {
    char data[24];
    void (*print)(const char *);
};

void safe_print(const char *msg) {
    printf("SAFE: %s\n", msg);
}

void dangerous_print(const char *msg) {
    printf("OWNED: %s\n", msg);
}

int main() {
    /* 1. Allocate struct Secret */
    struct Secret *sec = malloc(sizeof(struct Secret));
    strcpy(sec->data, "top-secret-key");
    sec->print = safe_print;
    sec->print(sec->data);

    /* 2. Free it - sec is now dangling */
    free(sec);

    /* 3. Allocate a different struct that will likely reuse sec's chunk */
    struct {
        char padding[24];
        void (*callback)(const char *);
    } *attacker = malloc(sizeof(*attacker));
    strcpy(attacker->padding, "garbage data");
    attacker->callback = dangerous_print;

    /* 4. Use the dangling sec pointer - reads attacker's memory layout */
    /* sec->print now points to dangerous_print because attacker->callback
       overlaps the same memory offset */
    sec->print(sec->data);  /* UAF: calls dangerous_print */

    free(attacker);
    return 0;
}

Compile and run:

gcc -g -o uaf_demo uaf_demo.c -no-pie -fno-stack-protector
./uaf_demo

# Output:
# SAFE: top-secret-key
# OWNED: garbage data        <-- sec->print resolved to dangerous_print

GDB session showing the overlap:

(gdb) b main
(gdb) r
(gdb) n   # past first malloc
(gdb) p sec
$1 = (struct Secret *) 0x5555555592a0

(gdb) n   # past free(sec)
(gdb) n   # past attacker malloc
(gdb) p attacker
$2 = (void *) 0x5555555592a0    # same address as sec!

(gdb) x/16gx 0x5555555592a0
0x5555555592a0: 0x6567616272616720  0x6174616420656761    # "garbage data"
0x5555555592b0: 0x0000000000000000  0x555555555169        # dangerous_print addr
0x5555555592c0: 0x0000000000000000  0x0000000000000021

(gdb) p sec->print
$3 = (void (*)(const char *)) 0x555555555169 <dangerous_print>

(gdb) continue
OWNED: garbage data

The overlap at offset 24 (after the 24-byte padding/data) is where the function pointer sits. sec->print resolves to the same memory bytes that attacker->callback wrote.

Type Confusion via Heap Reuse

A UAF enables type confusion without any type cast. The compiler believes sec is a struct Secret* and generates code accordingly. At the machine level, sec->print is simply a load from [sec + 24] , so the compiler's type checking evaporates. The hardware dereferences whatever 8 bytes sit at that offset. After heap reuse, those 8 bytes are whatever object B placed there.

This is the fundamental power of the UAF: it bypasses the type system through the allocator. No amount of -Wall -Wextra catches it, because the compiler cannot track aliasing through malloc and free .

C++ vtables and UAF

C++ objects with virtual functions carry a hidden vtable pointer as their first field. When an object is freed and its memory is reused by a different class, that vtable pointer can be overwritten. A subsequent virtual call through the dangling pointer then reads the attacker-controlled vtable entry and dispatches to an attacker-chosen address.

/* vtable_uaf.cpp - compile with g++ -g -O0 */
#include <cstdio>
#include <cstring>

class User {
public:
    char name[16];
    virtual void greet() {
        std::printf("Hello, %s\n", name);
    }
};

struct Attacker {
    void **vptr;      // overlaps User's vptr
    char data[16];    // overlaps User::name
};

static void mal_greet(Attacker *self) {
    std::printf("OWNED via fake vtable: %s\n", self->data);
}

int main() {
    User *u = new User();
    std::strcpy(u->name, "Alice");
    u->greet();

    delete u;  // u is dangling

    static void *fake_vtable[] = { (void *)&mal_greet };

    Attacker *at = new Attacker();
    at->vptr = fake_vtable;
    std::strcpy(at->data, "EVIL");

    u->greet();  // dispatches through fake_vtable[0]

    delete at;
    return 0;
}

The object layout on 64-bit:

sizeof(User)     = 8 (vptr) + 16 (name) = 24 bytes
sizeof(Attacker) = 8 (vptr) + 16 (data) = 24 bytes

Both request the same malloc size class, so reuse is likely.

User layout:     [vptr][name............]
Attacker layout: [vptr][data............]
                  ^-- u->vptr now points at the attacker's fake vtable

When u->greet() executes, the CPU does three things:

  1. Loads u->vptr (the first 8 bytes) and gets the address of fake_vtable .
  2. Loads fake_vtable[0] , which is the address of mal_greet .
  3. Calls it with this = u (which is at 's address), so self->data prints "EVIL".

UAF in the Real World

Browser DOM objects. A JavaScript object allocated on the heap can be freed by a garbage collection pass while a C++ ImageElement* still dangles. A new ArrayBuffer allocation reuses the memory, and the type system still thinks it is an ImageElement . Calling ->src() then reads ArrayBuffer backing-store metadata. Exploitation involves crafting the overlapping object to gain an arbitrary read/write primitive.

Kernel use-after-free. A struct file is freed when a process closes an fd, but a concurrent thread still holds a file pointer. A struct pipe_buffer allocation reuses the slab. The dangling file->f_op->write now reads from pipe_buffer data. Kernel UAFs are exploited via heap spraying: allocating many objects of a controlled type (for example struct tty_struct ) to groom the heap and make reuse predictable.

V8 JIT engine. JavaScript objects live in V8's managed heap. The optimizing compiler (TurboFan) may embed raw pointers to objects that the garbage collector later frees. If the JIT-compiled code runs with a dangling pointer to freed object memory that now holds a different type, the type confusion enables arbitrary memory access from JavaScript. The V8 sandbox and pointer compression are mitigations against this class.

Double Free Relationship

A double free ( free(ptr) followed by free(ptr) on the same pointer) is a related bug. Both involve dangling pointers; the difference is the exploitation primitive:

Bug Primitive Mechanism
UAF Read/write through dangling pointer Type confusion via reuse
Double free Corrupt free list metadata fd/bk pointer overwrite in free chunk

A UAF write can become a double free: if the UAF gives you the ability to overwrite a chunk's fd pointer (the first 8 bytes of the freed chunk's user data), you can corrupt the free list and achieve tcache poisoning - the same outcome as a double free. Many real-world exploits chain UAF, then corrupt the fd, then force an arbitrary allocation.

Prevention

Smart pointers (C++). std::unique_ptr<T> releases the owned object exactly once when it goes out of scope, so no raw pointer is left to dangle. std::shared_ptr<T> uses reference counting: the object is freed only when the last shared_ptr is destroyed.

std::unique_ptr<User> u = std::make_unique<User>();
u->greet();
// u goes out of scope -> delete called -> no dangling pointer remains

Rust's ownership model. Rust eliminates UAF at compile time through the borrow checker. An owned value is freed when its owner goes out of scope, and references to the value must not outlive the owner. The compiler rejects any code that would create a dangling reference. Box<T> (heap allocation) follows the same rule: the memory is freed when the Box is dropped, and the compiler statically verifies that no references remain.

let u = Box::new(User { name: "Alice".into() });
// u is freed here - the compiler guarantees no references exist past this point

Garbage collection. Tracing GC (Go, Java, JavaScript, Python) never frees an object while a reachable reference exists. The collector performs reachability analysis from root pointers, so only objects with zero incoming references are collected. This eliminates use-after-free but introduces its own costs (GC pauses, memory pressure, finalization ordering).

Static analysis. Tools such as Coverity, CodeQL, and the Clang Static Analyzer track pointer lifetimes and look for paths where a pointer is dereferenced after a free: free(p) followed by p->field in the same function, or free(p) where p escapes to a caller or a global.

AddressSanitizer (ASAN) instruments every memory access and places freed allocations in a quarantine (a FIFO queue of freed chunks that are not immediately reused). A UAF access to a quarantined chunk triggers an immediate crash with a detailed report:

gcc -g -fsanitize=address -o uaf_asan uaf_demo.c
./uaf_asan

# ==12345==ERROR: AddressSanitizer: heap-use-after-free
# READ of size 8 at 0x603000000050 thread T0
#   #0 0x... in main uaf_demo.c:31
# 0x603000000050 is located 24 bytes inside of 32-byte region [0x603000000030,0x603000000050)
# freed by thread T0 here:
#   #0 0x... in free
#   #1 0x... in main uaf_demo.c:22
# previously allocated by thread T0 here:
#   #0 0x... in malloc
#   #1 0x... in main uaf_demo.c:17

GWP-ASAN (in production). Google's probabilistic sampling allocator is embedded in Chrome and Android. A fraction of allocations and deallocations are sampled, and sampled allocations go to a separate pool with guard pages and delayed reuse. UAFs on sampled allocations are caught in production with minimal overhead.

Kernel Mitigations

SLAB quarantine (Linux KASAN). KASAN is similar to ASAN but for kernel slab allocations. Freed objects sit in a quarantine before reuse, so a UAF access triggers a KASAN report.

Use-after-free detection via canaries. Some allocators place a canary value in freed memory. Before dereferencing a freed-pointer-lookalike, they check whether the canary is intact. This is probabilistic and is not deployed in mainline glibc.

Memory tagging. ARM's Memory Tagging Extension (MTE) tags each 16-byte granule with a 4-bit tag stored in the upper bits of the pointer. malloc assigns a random tag and free clears it, so any access with a mismatched tag traps. Intel's Linear Address Masking (LAM) instead masks the upper address bits to reduce the entropy available to an attacker who already has a pointer.

(gdb) info proc mappings

(gdb) x/32gx $rdi   # $rdi = ptr passed to free (chunk start - 0x10 on glibc)
# Examine the chunk header (size field) and user data (fd/bk)

(gdb) set $main_arena = (struct malloc_state*)&main_arena
(gdb) p $main_arena
# inspect the bins[] array, fastbinsY[], and the top chunk

Heap Grooming for Exploitation

When a UAF exists but reuse is non-deterministic (the freed chunk might go to a different bin, get coalesced, or be served to a different thread), heap grooming forces predictable reuse:

  1. Spray: allocate many objects of type B before freeing A. This fills tcache/fastbins with B-sized allocations. When A is freed and later malloc'd, the allocator is more likely to reuse A's memory for a B request.
  2. Defragment: allocate and free objects of various sizes to coalesce adjacent free chunks and reduce fragmentation, ensuring A lands in a clean free list.
  3. Cross-thread grooming: if the target thread has its own tcache, spray allocations from that thread so its tcache has free slots for the exact size class.
// Grooming example: spray B-sized objects before triggering the UAF
#define SPRAY 256
void *spray[SPRAY];

for (int i = 0; i < SPRAY; i++)
    spray[i] = malloc(48);  // same size class as target

free(target);       // target goes to the free list
void *reuse = malloc(48);   // highly likely to get target back

Summary

A use-after-free is a temporal memory safety violation. The allocator recycles memory without knowledge of outstanding pointers. The dangling pointer becomes a window into whichever object reuses the chunk, which is type confusion enforced by the heap. Mitigations range from compile-time ownership tracking (Rust) to runtime quarantine (ASAN) to hardware tagging (ARM MTE). The bug class persists because C and C++ give the programmer full control over pointer lifetimes, and the allocator optimizes for speed over safety.

Challenge

Demonstrate chunk reuse from Go with cgo. Allocate a 48-byte chunk with C.malloc , free it, and then allocate the same size again. Because both requests fall in the same size class, libc's tcache usually hands back the very same address:

package main

/*
#include <stdlib.h>
#include <string.h>
*/
import "C"

import "fmt"

func main() {
	// Free a chunk, then allocate again - libc often hands back the same memory.
	p := C.malloc(48)
	C.memset(p, 'A', 48)
	C.free(p)

	q := C.malloc(48)
	C.memset(q, 'B', 48)

	// p is a dangling pointer: read through it after the chunk was reused.
	contents := C.GoBytes(p, 48)

	fmt.Printf("p = %p\n", p)
	fmt.Printf("q = %p\n", q)
	fmt.Printf("p == q: %v\n", p == q)
	fmt.Printf("read through p after free: %s\n", contents)
}

Run it with go run main.go (cgo needs a C compiler). Explain why libc returns the same address, then extend the program to write a new value through the dangling p and read it back through q to show that the two pointers alias one chunk.
