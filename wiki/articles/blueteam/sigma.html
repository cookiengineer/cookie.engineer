Sigma

Portable SIEM detection rules that you write once and convert to any backend query language.

Overview

Sigma is a vendor-neutral rule format for detection content. A single YAML document describes the log source, the fields to match, and a boolean condition, and a converter rewrites that logic into the native query language of whatever SIEM or endpoint platform you run. This article covers the rule anatomy, the field modifiers and condition grammar, how pipelines adapt a rule to a backend, and how to test and version rules like code.

Required Reading

  • HTTP - request/response structure, headers, methods, status codes
  • Processes - process lifecycle, /proc, command-line arguments

Concept

Sigma is a generic, open signature format that allows you to write detection rules once and convert them to the query language of any SIEM platform. A rule written in Sigma YAML can be converted to Splunk SPL, Elasticsearch Query DSL, QRadar AQL, Microsoft Sentinel KQL, and dozens of other backends.

The core insight: detection logic should be platform-independent. Your SIEM will change. Your rules shouldn't.

Rule Anatomy

Every Sigma rule is a YAML document with a fixed structure: 

title: Suspicious Process Creation — CMD Launching PowerShell
id: 8f0c99f1-2f3c-4c8f-8bee-1c6f3e0e8a31
status: stable
description: |
  Detects cmd.exe spawning powershell.exe with encoded or hidden window flags.
  Common pattern for fileless malware, download cradles, and post-exploitation.
author: You
date: 2026-06-26
references:
  - https://attack.mitre.org/techniques/T1059/001/
tags:
  - attack.execution
  - attack.t1059.001
logsource:
  product: windows
  category: process_creation
detection:
  selection_parent:
    Image|endswith: '\cmd.exe'
  selection_child:
    Image|endswith: '\powershell.exe'
    CommandLine|contains:
      - '-EncodedCommand'
      - '-enc'
      - '-e '
      - '-WindowStyle Hidden'
      - '-w hidden'
      - '-nop'
      - '-noprofile'
  condition: selection_parent and selection_child
falsepositives:
  - Administrative scripts that use encoded commands (rare — consider whitelisting)
level: high

Mandatory fields : title , id (UUID v4 for uniqueness), status , description , logsource , detection .

Status values : stable (vetted, low FPR), test (needs validation), experimental (draft, expect FPs), deprecated (superseded), unsupported (abandoned).

Generate a UUID:

uuidgen
# Output: 8f0c99f1-2f3c-4c8f-8bee-1c6f3e0e8a31

Logsource Definitions

The logsource section defines which log type the rule applies to: 

# Windows Security Event Log
logsource:
  product: windows
  service: security

# Sysmon process creation (EventID 1)
logsource:
  product: windows
  service: sysmon

# Linux auditd logs
logsource:
  product: linux
  service: auditd
  category: process_creation

# Generic web server logs
logsource:
  product: webserver
  service: access

# Firewall logs (product-agnostic)
logsource:
  category: firewall

The product field identifies the OS/application. The service identifies the specific log source within that product. The category is a high-level event type that can apply across products.

Detection Logic

The detection section defines named sub-expressions (called "search identifiers") and a boolean condition that combines them. 

detection:
  # Search identifier: finds events matching these field-value pairs
  selection_powershell:
    Image|endswith: '\powershell.exe'

  selection_network:
    Initiated: true
    DestinationPort: 443

  # Filter identifier: excludes matching events
  filter_legitimate:
    DestinationIp|startswith: '10.0.0.'

  # Timeframe: events within 30 seconds of each other
  timeframe: 30s

  # Condition: boolean logic combining identifiers
  condition: selection_powershell and selection_network and not filter_legitimate

Search identifiers logically OR their field-value pairs. Values listed as YAML arrays are OR'd within that field. 

selection:
  CommandLine|contains:
    - '-enc'        # matches if CommandLine contains "-enc"
    - '-Encoded'    # OR if CommandLine contains "-Encoded"
  Image|endswith: '\powershell.exe'  # AND Image must end with \powershell.exe

Field Modifiers

Modifiers are appended to field names with | :

Modifier Description Example
contains Substring match CommandLine\|contains: 'whoami'
startswith Prefix match Image\|startswith: 'C:\\Windows\\'
endswith Suffix match Image\|endswith: '\cmd.exe'
re Regex match CommandLine\|re: '.*-enc [A-Za-z0-9+/=]{100,}'
gt/lt/gte/lte Numeric comparison dst_port\|gt: 1024
all All values must match (AND within a list) CommandLine\|all: ['-nop', '-enc']
cased Case-sensitive match (off by default) Image\|endswith\|cased: '\cmd.exe'
base64 Field value is base64-encoded CommandLine\|base64: 'd2hvYW1p'

Condition Expressions

# Simple conditions
condition: selection
condition: selection_1 and selection_2
condition: selection_1 or selection_2
condition: selection_1 and not filter_1

# Complex conditions
condition: (selection_1 or selection_2) and not filter_1

# Counting: alert if N of M conditions are true
condition: 2 of them
# "them" refers to all search identifiers NOT starting with "filter_"

condition: 1 of selection_*
# Matches if any identifier starting with "selection_" is true

condition: all of selection_*
# Short for: selection_1 and selection_2 and ...

condition: 1 of them and not 1 of filter_*

# Near: events within a time window
detection:
  selection_a:
    EventID: 4688
    NewProcessName|endswith: '\net.exe'
  selection_b:
    EventID: 5156
    Application|endswith: '\net.exe'
  timeframe: 60s
  condition: selection_a | near selection_b

Writing Rules for Common Attacks

LSASS Credential Dumping

title: LSASS Memory Access by Unsigned Binary
id: 32d0d3e2-e58a-4c2f-b0db-2e3c755d7e1b
status: stable
description: Detects non-Microsoft processes accessing LSASS memory.
logsource:
  product: windows
  service: sysmon
detection:
  selection:
    EventID: 10
    TargetImage|endswith: '\lsass.exe'
    SourceImage|startswith: 'C:\Windows\'
  filter_system:
    SourceImage|contains:
      - 'C:\Windows\System32\'
      - 'C:\Windows\SysWOW64\'
      - 'C:\Windows\SystemApps\'
  condition: selection and not filter_system
level: high

Service Creation

title: New Service Created with Suspicious Binary Path
id: 0fa0a8c7-c8e0-4acb-9d3c-27a5f3e4f2d1
status: stable
description: Detects service creation where the binary path points to temp or user-writable directories.
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4697
    ServiceFileName|contains:
      - 'C:\Users\'
      - 'C:\Windows\Temp\'
      - 'C:\ProgramData\'
      - '\AppData\'
  filter_adobe:
    ServiceFileName|contains: 'Adobe'
  condition: selection and not filter_adobe
falsepositives:
  - Legitimate software installed to user profile (e.g., Chrome updater, OneDrive, Teams)
level: medium

Web Shell Upload

title: Web Shell Upload — PHP File in Upload Directory
id: 5b3a2c1d-8f4e-4a6b-9c1d-2e3f4a5b6c7d
status: stable
description: Detects successful POST requests uploading PHP files to web-accessible directories.
logsource:
  product: linux
  service: apache
detection:
  selection:
    cs-method: POST
    sc-status: 200
    cs-uri-stem|endswith: '.php'
    cs-uri-stem|contains: '/uploads/'
  timeframe: 10s
  condition: selection | count() by cs-username > 3
level: medium

sigma-cli

The sigma CLI tool converts rules between formats and validates rule syntax. 

# Install on ArchLinux
sudo pacman -S python-pipx
pipx install sigma-cli

# Add a backend plugin, for example the Splunk backend
pipx inject sigma-cli pysigma-backend-splunk

Common operations:

# Validate all rules in a directory
sigma check rules/

# Convert a Sigma rule to Splunk SPL
sigma convert -t splunk rules/windows/process_creation/suspicious_powershell.yml

# Convert to Elasticsearch Lucene query
sigma convert -t es-ql rules/linux/webserver_web_shell.yml

# Convert to Microsoft Sentinel KQL
sigma convert -t sentinel rules/windows/credential_access/lsass_dump.yml

# List available backends (target formats)
sigma list targets

# List available pipelines (processing chains)
sigma list pipelines

Output example - Sigma to Splunk:

sigma convert -t splunk rules/suspicious_powershell.yml
						
(Image="*\\cmd.exe") (Image="*\\powershell.exe" (CommandLine="*-EncodedCommand*" OR CommandLine="*-enc*"))

Sigma Pipelines

Pipelines transform rules between the generic Sigma format and backend-specific queries. The pipeline handles field name mappings, log source selectors, and backend quirks. 

# Example pipeline stage: field name mapping
name: windows_field_mapping
priority: 10
transformations:
  - type: field_name_mapping
    mapping:
      Image: NewProcessName
      CommandLine: ProcessCommandLine
      EventID: EventCode

Pipeline stages execute in priority order. Standard pipeline stages:

Stage Purpose
logsource selection Map Sigma logsource to backend index/table
field name resolution Map Sigma field names to backend field names
value transformation Convert Sigma values (regex -> backend regex, contains -> wildcard)
condition transformation Convert Sigma condition to backend boolean expression
output formatting Wrap in backend-specific boilerplate

Performance Considerations

  1. Prefer startswith/endswith over contains - they enable index prefix scans. contains requires a full scan.
  1. Never use regex on high-volume events - process creation events can number hundreds per second. A regex across the full command line on every event will kill SIEM performance.
  1. Use EventID as first filter - EventID is indexed, narrows the search to a tiny fraction of events before evaluating other conditions.
  1. Aggregation rules are expensive - count() by , near , and timeframe require stateful tracking. Use sparingly on high-volume log sources.
  1. Filter early, filter often - not filter_* conditions should appear as early as possible in the condition to short-circuit evaluation.

Integration with Detection-as-Code

#!/bin/bash
# CI pipeline: validate all rules, run tests, convert to backend
set -e

echo "=== Validating Sigma rules ==="
sigma check rules/**/*.yml

echo "=== Running tests ==="
find tests -name '*.yml' -exec sigma test {} \;

echo "=== Converting to Splunk ==="
mkdir -p output/splunk
find rules -name '*.yml' ! -path '*/tests/*' \
  -exec sigma convert -t splunk -o output/splunk/ {} \;

echo "=== Converting to Elasticsearch ==="
mkdir -p output/es
find rules -name '*.yml' ! -path '*/tests/*' \
  -exec sigma convert -t es-ql -o output/es/ {} \;

echo "=== All checks passed ==="
