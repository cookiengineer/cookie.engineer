DEP (Data Execution Prevention)

How NX/W^X/ DEP enforces memory execute permissions via page table entries, the CPU fault mechanism, ELF segments, and JIT compiler mitigations.

Overview

Before hardware NX there was no per-page way to stop the CPU from executing data. A buffer overflow could write shellcode to the stack or heap and then jump to it. This article explains how the NX bit in the page tables, exposed as DEP on Windows and W^X on OpenBSD, makes writable pages non-executable. It covers the CPU fault path, the PT_GNU_STACK ELF metadata that marks the stack NX, and the JIT techniques that keep write and execute permissions separate.

Required Reading

  • Virtual Memory - page tables, virtual address translation, page table entries
  • ELF - ELF segments, program headers, ELF loader behavior
  • Buffer Overflows - why attackers write shellcode to writable buffers

The Problem DEP Solves

Before 2004, memory on x86 was either completely executable or completely non-executable - there was no per-page execution control. The x86 protected mode segmented memory model (introduced with the 80286 in 1982, refined with the 80386 paging in 1985) could enforce read/write protection per page via the Page Table Entry ( PTE ) R/W bit, but had no equivalent for execute permission. A page marked as writable was implicitly executable.

This meant a buffer overflow on the stack, in the heap, or in the BSS segment gave an attacker:

  1. Write arbitrary shellcode to the writable buffer.
  2. Overwrite the return address to point at that buffer.
  3. When the function returns, the CPU fetches and executes the shellcode.

Classic shellcode exploits from the 1990s through mid-2000s exploited this directly. The famous Aleph1 "Smashing the Stack for Fun and Profit" (Phrack 49, 1996) assumed an executable stack was the natural default state.

DEP (Microsoft's branding) or NX (No-eXecute, AMD's branding) or W^X (Write XOR Execute, OpenBSD's policy name) fundamentally changes this: memory can be writable or executable, but not both simultaneously . The stack and heap - the targets of buffer overflows - are marked non-executable. Shellcode written there will cause a page fault, not arbitrary code execution.

CPU-Level Implementation

On x86-64 (AMD64 and Intel 64), every Page Table Entry ( PTE ) and Page Directory Entry (PDE) is 8 bytes (64 bits). The PTE format for a 4 KiB page: 

 63  62     52 51             32 31             12 11     9 8 7 6 5 4 3 2 1 0
+--+--------+-----------------+-----------------+--------+-+-+-+-+-+-+-+-+-+-+
|NX|Ignored | Physical Addr   | Physical Addr   |Ignored |G|P|D|A|P|P|U|R|P|
|  | (MBZ)  | (bits 51..32)   | (bits 31..12)   |(MK+7)  | |A| | |C|W|/|/|
|  |        |                 |                 |        | |T| | |D|T|S|W| |
+--+--------+-----------------+-----------------+--------+-+-+-+-+-+-+-+-+-+-+

Bit 63 - NX (No-eXecute) / XD (eXecute Disable in Intel terminology):

  • 0: instructions may be fetched from this page
  • 1: instruction fetch from this page triggers a page fault

When the CPU 's instruction fetch unit requests bytes from a virtual address, the Memory Management Unit (MMU) walks the page tables:

  1. CR3 register -> PML4 table -> PDPT -> PD -> PT -> PTE
  2. CPU checks the NX bit in the final PTE
  3. If NX = 1, the MMU raises a page fault (interrupt #14, exception vector 14)
  4. The kernel's page fault handler receives a struct vm_area_struct with VM_EXEC not set
  5. If the faulting address has no VM_EXEC VM A, the kernel delivers SIGSEGV (signal 11) with si_code = SEGV_ACCERR

The key register-level pathway:

IA32_EFER (Extended Feature Enable Register) - MSR 0xC0000080:
  Bit 11 (NXE): No-Execute Enable. Must be 1 for NX to work.
  Bit 8  (LME): Long Mode Enable. Set when entering 64-bit mode.

Page Fault Error Code (pushed onto stack by CPU):
  Bit 4: 1 = instruction fetch, 0 = data access
  Bit 0: 1 = protection violation, 0 = not-present page

If IA32_EFER.NXE is 0 (legacy mode or kernel didn't enable it), bit 63 of PTE s is ignored - any page can execute regardless. All modern Linux kernels set NXE during boot.

x86 History

The original 80386 (1985) paging system had a 2-level page table with 32-bit PTE s. The PTE format had no execute bit: 

80386 PTE (32-bit):
 31                  12 11 9 8 7 6 5 4 3 2 1 0
+---------------------+---+-+-+-+---+-+-+-+---+-+
| Physical Page (4KiB)|Avl|0|0|D|A|0|0|U|R|P|
| address, bits 31-12 |   | | | | | | |/|/| |
+---------------------+---+-+-+-+---+-+-+-+---+-+
                                          S W

Only two protection bits: R/W (Read/Write, bit 1) and U/S (User/Supervisor, bit 2). No execute bit.

The Pentium Pro (1995) introduced PAE (Physical Address Extension) with 64-bit PTE s but still no execute bit. It wasn't until 2003 that AMD defined the NX bit in the AMD64 architecture specification, and Intel followed in 2004 with XD on Prescott-core Pentium 4 processors.

Timeline

Year Milestone
1985 80386 paging - per-page R/W, no execute
1995 PAE - 64-bit PTEs, still no execute bit
1996 Linux 2.0 - initial mmap implementation; exec perm always implied
2001 PaX patches for Linux - first software NX via segmentation tricks
2003 AMD64 specification - NX bit (bit 63) defined
2003 Linux 2.6.0-test3 - kernel support for NX by Ingo Molnar (Red Hat)
2004 Intel Prescott - XD bit (same concept, different name)
2004 OpenBSD 3.3 - W^X policy enforced in kernel (Munro, de Raadt)
2004 Windows XP SP2 - DEP introduced
2005 GCC 4.0 - PT_GNU_STACK segment, -z execstack / -z noexecstack

Before hardware NX, the PaX project implemented software NX via x86 segmentation: the code segment descriptor's limit was set below the data segment's base, so the CPU 's segmentation unit would fault on instruction fetches from data regions before the paging unit ever saw them. This was clever but incurred overhead from segment register manipulation and didn't work on all microarchitectures.

Kernel View: VM_EXEC

Every virtual memory region in a Linux process is described by a vm_area_struct (defined in include/linux/mm_types.h ). The vm_flags field is a bitmask of VM_* flags. The relevant subset: 

#define VM_READ          0x00000001  // Page is readable
#define VM_WRITE         0x00000002  // Page is writable
#define VM_EXEC          0x00000004  // Page is executable
#define VM_SHARED        0x00000008  // Page is shared between processes
#define VM_MAYREAD       0x00000010  // Read access may be granted
#define VM_MAYWRITE      0x00000020  // Write access may be granted
#define VM_MAYEXEC       0x00000040  // Execute access may be granted
#define VM_GROWSDOWN     0x00000100  // Stack grows downward
#define VM_GROWSUP       0x00000200  // Stack (for other archs) grows upward
#define VM_DENYWRITE     0x00000800  // ETXTBSY - deny writes to executable

When mmap or mprotect sets a VM A, the kernel translates PROT_* flags: 

// arch/x86/include/asm/mman.h
// Kernel internal flag mapping:
// PROT_READ  -> VM_READ  | VM_MAYREAD
// PROT_WRITE -> VM_WRITE | VM_MAYWRITE
// PROT_EXEC  -> VM_EXEC  | VM_MAYEXEC

The VM_WRITE and VM_EXEC flags are checked during page fault handling. If a region has VM_WRITE but not VM_EXEC , the PTE is populated with NX=1 . If the CPU then tries to fetch from that page, the hardware raises a page fault with the instruction-fetch bit set in the error code. The kernel's do_page_fault then calls __bad_area -> force_sig_fault(SIGSEGV, SEGV_ACCERR, address) .

Kernel W^X Hardening

The kernel enforces W^X on its own mappings (CONFIG_DEBUG_WX and CONFIG_STRICT_KERNEL_RWX):

// Kernel .text is mapped read-only + execute
// Kernel .rodata is mapped read-only
// Kernel .data and .bss are mapped read-write, no-exec
// Kernel modules follow the same rules
// Any RWX page in kernel space is a W^X violation and triggers a WARN()

You can verify this at runtime:

# Check kernel page table permissions
cat /sys/kernel/debug/kernel_page_tables | head -50
# Look for "RW" entries - there should be none with "x" appended

mmap and mprotect

Userspace requests memory protection via mmap (new mapping) or mprotect (change existing mapping): 

#include <sys/mman.h>

// mmap: create a new mapping
void *addr = mmap(
    NULL,                       // let kernel choose address
    4096,                       // length: one page
    PROT_READ | PROT_WRITE,     // protection: no execute
    MAP_PRIVATE | MAP_ANONYMOUS,// flags: private anonymous memory
    -1,                         // fd: not used for anonymous
    0                           // offset: not used
);

// mprotect: change protection of existing mapping
mprotect(addr, 4096, PROT_READ | PROT_EXEC);
// After this, the page is readable and executable but NOT writable.
// W^X is enforced by discipline: {R,X} is allowed, {R,W} is allowed, {R,W,X} is usually avoided.

Unlike some hardened operating systems, mainline Linux does not forbid a userspace PROT_READ | PROT_WRITE | PROT_EXEC mapping by default. The hardware only provides the per-page NX bit; the kernel trusts userspace not to request RWX, and W^X is a design discipline that JITs follow. Security modules such as SELinux and AppArmor can deny execute permission on writable mappings ( execmem / execstack checks), and some distributions ship stricter policies. 

# SELinux can block executable writable memory
sestatus 2>/dev/null | head -3
sesearch -A -t unconfined_t -c process -p execmem 2>/dev/null

# Check current mappings for RWX regions
grep 'rwx' /proc/self/maps

ELF Program Headers: PT_GNU_STACK

The ELF loader uses the PT_GNU_STACK program header to decide whether the process's main stack should be executable. This segment has no data - it exists purely as metadata.

The p_flags field of PT_GNU_STACK

p_flags value Stack permissions Note
PF_R(4) Read-only, non-executable Unusual; stack must be writable
PF_R \| PF_W(6) Read-Write, NO-EXEC Default: NX stack
PF_R \| PF_W \| PF_X(7) Read-Write-EXEC Executable stack(vulnerable)

The flag is set by the linker based on whether any input object file has .note.GNU-stack with executable permissions. The compiler sets this based on the -z execstack / -z noexecstack flags.

Check a binary's stack executability:

# Method 1: readelf (most direct)
readelf -l /bin/ls | grep GNU_STACK
# Output: GNU_STACK  0x... 0x... 0x... 0x... 0x... RWE 0x10
#                                              ^^^
#                                        RWE = executable
#                                        RW  = not executable

# Method 2: scanelf (from pax-utils, installed by default on Arch)
scanelf -e /bin/ls
# TYPE   STACK/RELRO  FILE
# ET_EXEC RW- R--     /bin/ls
#         ^^^
#         RW- = NX stack (R=read, W=write, -=no-exec)
#         RWE = executable stack

# Method 3: execstack (from prelink)
execstack -q /bin/ls
# - /bin/ls
# "-" means the stack is not executable; "X" is printed if it is

# Method 4: check all binaries on system
scanelf -e /usr/bin/* | grep -v 'RW-'
# Shows binaries with executable stacks - should be empty on modern Arch

ELF Program Headers: PT_GNU_RELRO

RELRO (RELocation Read-Only) makes parts of the Global Offset Table (GOT) read-only after the dynamic linker resolves all relocations, preventing GOT overwrite attacks.

How RELRO Works

  1. The dynamic linker maps the GOT as read-write during process startup.
  2. All necessary relocations are resolved (lazy binding must be disabled for full RELRO).
  3. The dynamic linker calls mprotect to mark the GOT region as read-only.
  4. Any subsequent write attempt to the GOT triggers SIGSEGV.

Two levels of RELRO

Flag Linker flag Behavior
None -z norelro GOT remains writable forever - vulnerable to GOT overwrite
Partial -z relro(default) .got.pltsection writable (for lazy binding),.gotread-only after startup
Full -z relro -z now All GOT entries resolved at startup, entire GOT marked read-only

Full RELRO requires -z now (bind now), which disables lazy binding - all PLT function resolutions happen at startup, increasing load time slightly but eliminating the writable GOT as an attack surface. 

# Check RELRO status
readelf -l /bin/ls | grep GNU_RELRO
# GNU_RELRO  0x... 0x... 0x... 0x... 0x... R   0x10
#                                          ^
#                                          R  = present

# Full vs partial RELRO
readelf -d /bin/ls | grep -E 'BIND_NOW|FLAGS_1'
# 0x0000000000000006 (BIND_NOW)          # Present = full RELRO
# 0x000000006ffffffb (FLAGS_1)  Flags_1: NOW
# If BIND_NOW is absent: partial RELRO (lazy binding enabled)

# scanelf summarizes both stack and RELRO
scanelf -e /bin/ls
# TYPE   STACK/RELRO  FILE
# ET_DYN RW- R--      /bin/ls
#            ^^^
#            RELRO permissions (read-only once relocated)

Runtime Verification

Each process's /proc/PID/maps file shows all VM As with their permissions: 

# cat /proc/self/maps
5d4b9d600000-5d4b9d601000 r--p 00000000 ...  /bin/cat
5d4b9d601000-5d4b9d602000 r-xp 00001000 ...  /bin/cat      # text: R+X
5d4b9d602000-5d4b9d603000 r--p 00002000 ...  /bin/cat      # rodata: R
5d4b9d603000-5d4b9d604000 r--p 00002000 ...  /bin/cat
5d4b9d604000-5d4b9d605000 rw-p 00003000 ...  /bin/cat      # data: R+W
7f8a6c000000-7f8a6c001000 rw-p 00000000 ...                 # heap (anon): RW
7ffe12340000-7ffe12361000 rw-p 00000000 ...  [stack]        # stack: RW
7ffe123f2000-7ffe123f6000 r--p 00000000 ...  [vvar]         # vvar: R
7ffe123f6000-7ffe123f8000 r-xp 00000000 ...  [vdso]         # vdso: R+X

Permission characters: r = read, w = write, x = execute, p = private, s = shared.

Key observations:

  • .text segment: r-xp (read + execute, not writable)
  • .data segment: rw-p (read + write, not executable)
  • [stack] : rw-p (RW, NX stack - DEP active)
  • [vdso] : r-xp (kernel-provided code, executable)
  • [heap] : rw-p (RW, NX heap - DEP active)

Detecting a missing PT_GNU_STACK: if [stack] shows rwxp , the stack is executable: 

# Find processes with executable stacks
grep 'rwx.*\[stack\]' /proc/*/maps 2>/dev/null
# (should return nothing on a properly configured system)

Use pmap for more readable output: 

pmap $$ | tail -20
# Shows the current shell's memory map with permissions

NX Stack Example

This C program places shellcode on the stack and tries to execute it via a function pointer:

// test_nx.c - verify DEP/NX on the stack
// Compile: gcc -o test_nx_nx test_nx.c -z noexecstack
// Compile: gcc -o test_nx_exec test_nx.c -z execstack
// Run: ./test_nx_nx && ./test_nx_exec
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <unistd.h>

// exit(0) shellcode - x86-64 Linux
// mov eax, 60; xor edi, edi; syscall
unsigned char exit_shellcode[] = {
    0xb8, 0x3c, 0x00, 0x00, 0x00,   // mov eax, 60
    0x31, 0xff,                       // xor edi, edi
    0x0f, 0x05                        // syscall
};

int main(void) {
    char buffer[64];
    void (*func)(void);

    printf("Stack buffer at  : %p\n", (void *)buffer);
    printf("shellcode size  : %lu bytes\n", sizeof(exit_shellcode));

    memcpy(buffer, exit_shellcode, sizeof(exit_shellcode));
    func = (void (*)(void))buffer;

    printf("Attempting to execute shellcode on stack...\n");
    fflush(stdout);

    func();  // SIGSEGV if NX enabled, clean exit(0) if executable stack

    printf("This line should never be reached.\n");
    return 1;
}

Compilation and verification

# Compile WITH NX (default, secure)
gcc -o test_nx_nx test_nx.c -z noexecstack
readelf -l test_nx_nx | grep GNU_STACK
# GNU_STACK   0x0000  0x0000  0x0000  0x0000  0x0000  RW  0x10  <- RW, not RWE

# Compile WITHOUT NX stack (legacy, vulnerable)
gcc -o test_nx_exec test_nx.c -z execstack
readelf -l test_nx_exec | grep GNU_STACK
# GNU_STACK   0x0000  0x0000  0x0000  0x0000  0x0000  RWE 0x10  <- RWE, executable

# Run both:
./test_nx_nx
# -> Segmentation fault (SIGSEGV) - DEP prevents execution

./test_nx_exec
# -> Clean exit(0) - shellcode executed from stack successfully

Bypassing NX with mprotect

// mprotect_demo.c - show how JITs make memory executable
// Compile: gcc -o mprotect_demo mprotect_demo.c
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <unistd.h>

unsigned char shellcode[] = {
    0xb8, 0x3c, 0x00, 0x00, 0x00,   // mov eax, 60
    0x31, 0xff,                       // xor edi, edi
    0x0f, 0x05                        // syscall
};

int main(void) {
    // Allocate one page of RW memory (not executable)
    void *page = mmap(NULL, 4096,
                      PROT_READ | PROT_WRITE,
                      MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);

    printf("Allocated RW page at: %p\n", page);

    // Copy shellcode to the page
    memcpy(page, shellcode, sizeof(shellcode));

    // At this point, page is RW. Executing would SIGSEGV.
    // JITs flip page to RX before executing:
    mprotect(page, 4096, PROT_READ | PROT_EXEC);

    printf("Page flipped to RX. Executing shellcode...\n");

    void (*code)(void) = page;
    code();  // works: page is now RX (R+X, not W+X)

    munmap(page, 4096);
    printf("This line is not reached (clean exit via syscall).\n");
    return 0;
}

The critical detail: the page was never simultaneously writable and executable . The JIT wrote code while it was RW, then flipped to RX. This is the dual-mapping technique - W^X is respected because at no point is a single page both W and X.

JIT Compilation Under W^X

JIT compilers (JavaScript engines, .NET, Java HotSpot) must generate and execute native code at runtime. Since a single page should not be both writable and executable, JITs use one of these strategies:

Strategy 1: Flip (mprotect)

1. mmap(PROT_READ | PROT_WRITE)
2. Generate native code -> write to buffer
3. mprotect(buffer, len, PROT_READ | PROT_EXEC)
4. Execute
5. If recompilation needed: mprotect back to RW, modify, flip back to RX

Used by: simpler JITs, older V8 (now uses strategy 2). Drawback: mprotect flushes TLBs for the affected pages, and making syscalls per compilation unit is expensive.

Strategy 2: Dual Mapping

1. Allocate RESERVED region at fixed address with memfd_create or shm_open
2. mmap the same physical pages TWICE at different virtual addresses:
   - mapping A: PROT_READ | PROT_WRITE  (writable view)
   - mapping B: PROT_READ | PROT_EXEC   (executable view)
3. Write code through mapping A
4. Execute code from mapping B

The physical page is accessible via two virtual aliases with different permissions. The CPU 's page table has two entries pointing to the same physical frame - one with NX=1 (RW alias), one with NX=0 (RX alias). The writable alias cannot be executed; the executable alias cannot be written. W^X is satisfied.

Used by: V8 (modern), JavaScriptCore (WebKit), SpiderMonkey.

Strategy 3: Out-of-Process JIT

1. Fork a child process with an RWX mapping (or use a separate JIT process)
2. Generate native code in the child's address space
3. Share the code pages back to the parent via shared memory (with RX permissions)

Used by: some hardened browser configurations, Apple's "bulletproof JIT" on iOS.

Strategy 4: Separate W and X

1. Thread A: maps region as RW, writes code
2. Thread B: maps same region as RX, executes code
3. Coordination via atomics/futexes

Rare in practice due to complexity; mostly a research concept.

Verifying DEP System-Wide

# 1. Check kernel NX support (should be present on all 64-bit kernels)
dmesg | grep -i "nx.*protection"
# Output: NX (Execute Disable) protection: active

# 2. Check /proc/cpuinfo for NX capability (all x86-64 CPUs have it)
grep -o 'nx' /proc/cpuinfo | sort -u
# Output: nx
# (if empty, your CPU doesn't support the NX bit - impossible on x86-64)

# 3. Check CPU flags for "nx" or "xd" (AMD vs Intel naming)
lscpu | grep -i flags | grep -o '\bnx\b'
# Output: nx

# 4. Check if the kernel compiled with NX support
zgrep NX /proc/config.gz 2>/dev/null || grep NX /boot/config-$(uname -r)
# CONFIG_X86_64=y (implies NX support on 64-bit)
# CONFIG_DEBUG_WX=y (W^X hardening in kernel)

# 5. Check all running processes for executable stacks
for pid in $(ls /proc | grep -E '^[0-9]+$'); do
    if grep -q 'rwx.*\[stack\]' /proc/$pid/maps 2>/dev/null; then
        exe=$(readlink /proc/$pid/exe 2>/dev/null)
        echo "PID $pid ($exe): executable stack"
    fi
done

# 6. Audit installed binaries for executable stacks
scanelf -e /usr/bin/* 2>/dev/null | grep -v 'RW-'

# 7. Check for RWX mappings in any process (should be empty or minimal)
grep 'rwx' /proc/self/maps
# Should show nothing (or only [vvar] which isn't really RWX)

DEP Bypass Techniques

No mitigation is absolute. DEP eliminates the simplest attack - shellcode execution from writable data regions. Attackers adapted:

Return-to-Libc (ret2libc): Instead of executing shellcode, redirect execution to existing libc functions like system() , execve() , or mprotect() . These functions are already in executable memory (.text segment). Set up function arguments on the stack (or via ROP gadgets), then return to system("/bin/sh") .

Return-Oriented Programming (ROP): An extension of ret2libc that chains together short code snippets (gadgets) ending in ret . Each gadget is 2-5 instructions from existing executable code. ROP can express arbitrary computation without writing a single instruction - see ROP .

JIT Spraying: Exploit a JIT compiler to generate native code that, when interpreted at different byte alignments, produces attacker-controlled instructions. The JIT writes "benign" code but the attacker jumps into the middle of an instruction stream where the bytes form a different, malicious instruction sequence. Mitigated by constant blinding and instruction alignment randomization in modern JITs.

mprotect/stack-protector disabling: Chain a call to mprotect(stack_base, size, PROT_READ|PROT_WRITE|PROT_EXEC) to make the stack executable, then jump to shellcode. Blocked by seccomp filters that prevent mprotect from setting PROT_EXEC on writable pages.

Compiler and Linker Flags

Flag Effect
-z noexecstack MarkPT_GNU_STACKasPF_R \| PF_W(NX stack) -default since GCC 4.x
-z execstack MarkPT_GNU_STACKasPF_R \| PF_W \| PF_X(executable stack) -insecure
-z relro Enable partial RELRO - GOT read-only after startup except.got.plt
-z norelro Disable RELRO - GOT remains writable
-z now Resolve all symbols at load time (bind now) - required for full RELRO
-z lazy Lazy binding - PLT stubs resolved on first call (default, incompatible with full RELRO)
-z separate-code Map ELF segments with separate PROT for code vs data (enables W^X at .text boundary)
-z noseparate-code Map code+data as one big read-execute segment (legacy)

Kernel Hardening SMEP and SMAP

Beyond userspace, the CPU provides supervisor-mode execution prevention:

SMEP (Supervisor Mode Execution Prevention) - bit 20 of CR4:

  • Prevents the kernel from executing code at userspace addresses.
  • Blocks attacks where the kernel's instruction pointer is redirected to a userspace buffer.
  • Enabled by default on Linux since kernel 3.0.
  • Check: grep smep /proc/cpuinfo or dmesg | grep SMEP

SMAP (Supervisor Mode Access Prevention) - bit 21 of CR4:

  • Prevents the kernel from reading or writing userspace memory directly.
  • Must use copy_from_user / copy_to_user which temporarily disable SMAP via STAC / CLAC instructions.
  • Check: grep smap /proc/cpuinfo

PXN (Privileged eXecute Never) - ARM64 equivalent of SMEP:

  • Prevents the kernel from executing userspace code.
  • Part of the ARMv8 architecture.
# Check all CPU mitigation features on Linux
cat /sys/devices/system/cpu/vulnerabilities/*

# Check SMEP/SMAP
journalctl -k --grep='SM[EAP][P ]'
# or
dmesg | grep -i 'sm[ea][mp]'

Shellcode on heap Yes Heap allocations NX by default
Shellcode in BSS/data Yes Data segments NX by default
ret2libc No libc .text is legitimately executable
ROP No Gadgets come from executable code
JIT spraying Partial Can bypass if JIT doesn't use constant blinding
GOT overwrite -> code redirect No Redirects to existing executable code
vtable overwrite No Indirect control flow, not code injection

Challenge

Write a Go tool that reads an ELF binary and reports whether its stack is executable and whether RELRO is present. This reproduces the checksec checks using only the standard library: 

package main

import (
	"debug/elf"
	"fmt"
	"os"
)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "usage: check-nx binary")
		os.Exit(2)
	}

	f, err := elf.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer f.Close()

	for _, prog := range f.Progs {
		switch prog.Type {
		case elf.PT_GNU_STACK:
			exec := prog.Flags&elf.PF_X != 0
			fmt.Printf("PT_GNU_STACK: R=%v W=%v X=%v\n",
				prog.Flags&elf.PF_R != 0,
				prog.Flags&elf.PF_W != 0,
				exec)
			fmt.Printf("NX stack:     %v\n", !exec)
		case elf.PT_GNU_RELRO:
			fmt.Println("PT_GNU_RELRO: present")
		}
	}
}

Build a test binary with gcc -z execstack -o exec.bin test_nx.c and one with plain gcc -o nx.bin test_nx.c , then run the tool against both. The first should report X=true and NX stack: false ; the second X=false and NX stack: true . Extend the tool to walk a directory tree and flag every binary with an executable stack.
