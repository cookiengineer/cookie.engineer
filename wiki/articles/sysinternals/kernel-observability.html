Kernel Observability

Complete kernel observability stack - tracepoints, ftrace, perf events, BPF probes, /proc and /sys, printk, ring buffers, sampling strategies, overhead analysis, and designing an observability pipeline.

Overview

You cannot debug or defend a kernel you cannot see. This article maps the telemetry sources a Linux kernel exposes - tracepoints, kprobes, perf hardware counters, ftrace, BPF, /proc , /sys , and printk - and explains their stability, overhead, and intended use so you can pick the right tool for a question.

Required Reading

  • Kernel Architecture - kernel layout, compilation units, kernel threads, system events
  • Interrupts - IR Q handling, softirqs, N API , scheduling latency, preemption

The Four Pillars of Observability

Observability is not the same as monitoring. Monitoring tells you whether something is wrong ( CPU > 90%). Observability tells you why (a specific function in a specific driver is spinning on a lock while holding an interrupt disabled). The four pillars

  • logs, metrics, traces, and profiles - answer different questions:

Pillar Question Kernel data source
Logs What happened? printk, devkmsg, trace_printk(), ftrace events, ebpf events
Metrics How much? How fast? /proc/stat, /proc/meminfo, /sys/class/net/*/statistics, perf stat, BPF counters
Traces How did it happen? tracepoints, kprobes, ftrace function graph, perf trace, BPF
Profiles Where is time spent? perf record (hardware PMU), ftrace function_graph, BPF stack trace, timer interrupt sampling

Kernel Telemetry Sources - Taxonomy

The Linux kernel exposes telemetry through at least eight distinct mechanisms. Each has different overhead, stability guarantees, and data richness: 

Telemetry Source Taxonomy:
═══════════════════════════

1. Static Tracepoints (TRACE_EVENT)
   ├── Location: inserted by kernel developers in source code
   ├── Stability: stable ABI — maintained across kernel versions
   ├── Overhead: near-zero when disabled (static key), ~100ns when enabled
   ├── Granularity: hundreds of predefined hook points
   ├── Access: /sys/kernel/debug/tracing/events/*/
   └── API: perf_event_open(), BPF(raw_tracepoint), ftrace

2. Kprobes / Kretprobes
   ├── Location: any kernel instruction (dynamically placed)
   ├── Stability: none — function signatures change between versions
   ├── Overhead: ~200ns per probe hit (int3 trap + single-step)
   ├── Granularity: function entry/exit, arbitrary addresses
   ├── Access: /sys/kernel/debug/tracing/kprobe_events
   └── API: perf_event_open(), BPF(kprobe), ftrace

3. Hardware PMU (Performance Monitoring Unit)
   ├── Location: CPU microarchitecture counters
   ├── Stability: architecture-dependent (Intel, AMD, ARM PMUs)
   ├── Overhead: ~50-100ns when counting, ~1μs when sampling
   ├── Granularity: cycles, instructions, cache misses, branches
   ├── Access: perf_event_open(type=PERF_TYPE_HARDWARE)
   └── API: perf stat, perf record, BPF(perf_event)

4. Ftrace function tracer
   ├── Location: mcount call inserted at every function prologue
   ├── Stability: none — every kernel build changes function list
   ├── Overhead: ~1-5μs per traced function (nop → call + trace)
   ├── Granularity: every kernel function (~60,000+)
   ├── Access: /sys/kernel/debug/tracing/trace
   └── API: trace-cmd, KernelShark, perf ftrace

5. eBPF Programs
   ├── Location: attached to kprobes, tracepoints, perf events,
   │            uprobes, raw tracepoints, LSM hooks, socket filters
   ├── Stability: depends on attachment type (tracepoints = stable)
   ├── Overhead: ~1-10μs per event (JIT-compiled BPF code)
   ├── Granularity: programmable — filter, aggregate, count in-kernel
   ├── Access: bpftool prog list, bpftool map dump
   └── API: bpf() syscall, libbpf, BCC, bpftrace

6. /proc filesystem (procfs)
   ├── Location: generated on read from kernel data structures
   ├── Stability: mostly stable (documented in man 5 proc)
   ├── Overhead: ~1-50μs per read (depends on complexity)
   ├── Granularity: process-level, memory, I/O, scheduling stats
   └── Examples: /proc/stat, /proc/meminfo, /proc/PID/status

7. /sys filesystem (sysfs)
   ├── Location: kobject-based, one value per file
   ├── Stability: reasonably stable (ABI by convention)
   ├── Overhead: ~1-10μs per read
   ├── Granularity: device-level, per-CPU, per-driver
   └── Examples: /sys/class/net, /sys/devices/system/cpu

8. debugfs
   ├── Location: /sys/kernel/debug/
   ├── Stability: explicitly UNSTABLE — no ABI guarantees
   ├── Overhead: variable, often negligible
   ├── Granularity: subsystem-level debugging data
   └── Examples: tracing/, dri/, usb/, kprobes/

echo "Tracepoints:"; ls /sys/kernel/debug/tracing/events/*/ | grep '_' | head -10
echo "Kprobes:"; cat /sys/kernel/debug/tracing/kprobe_events 2>/dev/null || echo "(none)"
echo "Perf events:"; perf list | head -10
echo "Ftrace:"; cat /sys/kernel/debug/tracing/available_filter_functions | wc -l

Tracepoints: The Stable Kernel ABI

Tracepoints are the primary stable observability interface. They are defined with TRACE_EVENT() macros that generate the hook point, the tracepoint data structure, the fast-path check, the format string, and the trace output function - all from a single definition. 

// include/trace/events/sched.h — the sched_switch tracepoint
TRACE_EVENT(sched_switch,

    // 1. Args to the tracepoint hook (what the caller passes)
    TP_PROTO(bool preempt, struct task_struct *prev,
             struct task_struct *next, unsigned int prev_state),

    // 2. Data fields stored in ring buffer (what gets recorded)
    TP_STRUCT__entry(
        __array( char, prev_comm, TASK_COMM_LEN )
        __field( pid_t, prev_pid )
        __field( int,  prev_prio )
        __field( long, prev_state )
        __array( char, next_comm, TASK_COMM_LEN )
        __field( pid_t, next_pid )
        __field( int,  next_prio )
    ),

    // 3. How to fill the fields from the args
    TP_fast_assign(
        memcpy(__entry->next_comm, next->comm, TASK_COMM_LEN);
        __entry->prev_pid    = prev->pid;
        __entry->prev_prio   = prev->prio;
        __entry->prev_state  = __trace_sched_switch_state(preempt, prev, prev_state);
        memcpy(__entry->prev_comm, prev->comm, TASK_COMM_LEN);
        __entry->next_pid    = next->pid;
        __entry->next_prio   = next->prio;
    ),

    // 4. Format string for human-readable trace output
    TP_printk("prev_comm=%s prev_pid=%d prev_prio=%d prev_state=%s%s ==> "
              "next_comm=%s next_pid=%d next_prio=%d",
        __entry->prev_comm, __entry->prev_pid, __entry->prev_prio,
        __entry->prev_state & (TASK_REPORT_MAX-1) ?
          __print_flags(__entry->prev_state & (TASK_REPORT_MAX-1), "|",
                { ... }) : "R",
        __entry->prev_state & TASK_REPORT_MAX ? "+" : "",
        __entry->next_comm, __entry->next_pid, __entry->next_prio)
);

    printf "%-20s %s\n" "$(basename $d)" "$(ls $d | wc -l)"

Ftrace: The Kernel's Built-in Tracer

Ftrace is the Swiss Army knife of kernel tracing. It lives entirely in the kernel and exposes its interface through debugfs ( /sys/kernel/debug/tracing/ ). 

Ftrace Architecture:
═══════════════════

    User Space                  Kernel Space
    ──────────                  ────────────

    echo function_graph >       ftrace uses mcount calls:
    current_tracer              ┌──────────────────┐
    ───────────────────►        │ func() {          │
                                │   _mcount();      │ ← compiler inserts call
                                │   // body         │    at every function
                                │   _mcount();      │    entry (can be NOP'd)
                                │ }                 │
                                └──────────────────┘

                                During tracing:
    echo func1 >                mcount → ftrace_call
    set_ftrace_filter               │
    ───────────────────►            ├── filter check (func in list?)
                                    ├── save return address
                                    ├── call trace function
                                    ├── write entry to ring buffer
                                    ├── restore return address
                                    └── return to func body

    cat trace                   Ring Buffer (per-CPU, lockless)
    ◄───────────────────        ┌─────────────────────────┐
                                │ CPU 0: [entry1][entry2] │
                                │ CPU 1: [entry3][entry4] │
                                │ CPU 2: [entry5]         │
                                │ CPU 3: [entry6][entry7] │
                                └─────────────────────────┘

Ftrace tracers

Tracer Description
function Trace every kernel function execution
function_graph Nested call graph with duration
blk Block I/O tracer (deprecated: use tracepoints)
mmiotrace Trace MMIO register reads/writes
wakeup Max latency from wakeup -> schedule
wakeup_rt Max latency for RT tasks (PREEMPT_RT)
irqsoff Max time with interrupts disabled
preemptoff Max time with preemption disabled
preemptirqsoff Maximum of irqsoff + preemptoff
hwlat Detect firmware/SMM caused hardware latency
nop Tracepoints only (no function tracing)

Perf Events and Counters

perf bridges the gap between counting (how many?) and sampling (why?). It uses perf_event_open() to program PMU counters, tracepoints, or software events, with results delivered via mmap'd ring buffers. 

perf Architecture:
══════════════════

                          perf user tool
                               │
                               │ perf_event_open() syscall
                               ▼
    ┌────────────────── Kernel ──────────────────────┐
    │                                                │
    │  perf_event_open() → struct perf_event         │
    │       │                                        │
    │       ├── type=HARDWARE → PMU counter          │
    │       │   └── config: event select + umask      │
    │       │                                        │
    │       ├── type=TRACEPOINT → tracepoint         │
    │       │   └── config: tp_event->id              │
    │       │                                        │
    │       ├── type=SOFTWARE → software events       │
    │       │   └── config: PERF_COUNT_SW_PAGE_FAULTS│
    │       │                                        │
    │       └── type=BPF → BPF program               │
    │           └── BPF runs on each sample           │
    │                                                │
    │  Ring Buffer (per-CPU, mmap'd to user)          │
    │  ┌──────────────────────────────────────┐       │
    │  │ Sample {ip, pid, tid, timestamp,      │       │
    │  │          callchain, raw data}          │       │
    │  │ Sample {ip, pid, tid, ...}             │       │
    │  └──────────────────────────────────────┘       │
    └────────────────────────────────────────────────┘
                               │
                               │ mmap read
                               ▼
                          perf record / perf stat

# Count events (aggregated, no sampling)
perf stat -e cycles,instructions,cache-misses,branch-misses ls -R /usr/share

# Sample at 99 Hz with callgraphs (dwarf unwinding)
sudo perf record -F 99 -g -a -- sleep 10
sudo perf report --stdio | head -50

# Trace syscalls with perf trace (like strace but kernel-side)
sudo perf trace ls 2>&1 | head -30
sudo perf trace -e '!syscall' ls 2>&1 | head -30  # exclude syscalls from trace

# Stat: per-CPU and per-thread
perf stat -e cycles,instructions --per-thread -a sleep 1

# List all events
perf list

# Monitor tracepoints
sudo perf stat -e 'sched:sched_switch' -a sleep 5
sudo perf record -e 'sched:sched_stat*' -a sleep 5
sudo perf script | head -20

# Profiling with hardware events specific to a process
sudo perf record -e cycles:k -p $(pidof nginx | cut -d' ' -f1) -- sleep 10
sudo perf report

BPF: The Universal Observability Layer

eBPF allows running sandboxed programs inside the kernel at kprobe, tracepoint, uprobe, or perf_event attachment points. BPF programs can filter events, aggregate data into maps, and export results to user space - all with bounded overhead and guaranteed termination. 

BPF Observability Architecture:
════════════════════════════════

    User Space                          Kernel Space
    ──────────                          ────────────

    bpftool / bpftrace / BCC            tracepoint / kprobe
         │                                    │
         │  bpf(BPF_PROG_LOAD)                │
         │───────────────────────────────────►│
         │                                    │  Verifier
         │  bpf(BPF_MAP_CREATE)               │  ────────
         │───────────────────────────────────►│  - loops? (back-edge)
         │                                    │  - bounds? (ctx access)
         │  bpf(BPF_PROG_ATTACH)              │  - memory? (map access)
         │───────────────────────────────────►│  - instructions < 1M
         │                                    │
         │                                    │  JIT → native code
         │◄────────── event ──────────────────│
         │                                    │
         │  bpf(BPF_MAP_LOOKUP)               │
         │───────────────────────────────────►│  Read aggregated data
         │◄────────── value ──────────────────│

bpftrace: kernel awk for quick probing

# List all available probes
sudo bpftrace -l 'tracepoint:syscalls:*' | head -20
sudo bpftrace -l 'kprobe:do_sys_open*'

# Count syscalls by type
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }' \
    -c 'sleep 5'
# Output:
# @[tracepoint:syscalls:sys_enter_nanosleep]: 2
# @[tracepoint:syscalls:sys_enter_read]: 15
# @[tracepoint:syscalls:sys_enter_write]: 8

# Count open files per process
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_openat {
    @opens[comm] = count();
}
interval:s:5 { exit(); }
'

# Histogram of read() sizes
sudo bpftrace -e '
tracepoint:syscalls:sys_exit_read {
    @read_bytes = hist(args->ret);
}
interval:s:5 { exit(); }
'

# Trace function entry with arguments (kprobe)
sudo bpftrace -e '
kprobe:vfs_read {
    printf("vfs_read: comm=%s pid=%d count=%d\n", comm, pid, arg2);
}
' -c 'cat /etc/hostname'

# Block I/O latency histogram
sudo bpftrace -e '
kprobe:blk_account_io_start {
    @start[arg0] = nsecs;
}
kretprobe:blk_account_io_done /@start[retval]/ {
    @io_lat_us = hist((nsecs - @start[retval]) / 1000);
    delete(@start[retval]);
}
interval:s:5 { exit(); }
'

BPF CO-RE (Compile Once, Run Everywhere)

Traditional BPF:                      CO-RE BPF:
────────────────                      ────────
Compile against specific kernel       Compile once against vmlinux.h
headers on target machine             Run on any kernel ≥ 5.5
Requires llvm/clang on target         BPF_READ() macros handle field
Known struct layouts at compile time  BTF provides field offsets at
                                      load time — relocations fix up

/proc and /sys Interfaces

Procfs and sysfs provide instantaneous snapshots of kernel state. They are the simplest observability interface - no tools required beyond cat . 

Key /proc observability files:
══════════════════════════════

/proc/stat            ── CPU time (user, nice, system, idle, iowait, irq, softirq, steal)
/proc/meminfo         ── Memory breakdown (MemTotal, MemFree, Cached, Buffers, SwapTotal, ...)
/proc/vmstat          ── Virtual memory statistics (pgfault, pgmajfault, pgsteal, pgscan, ...)
/proc/diskstats       ── Per-disk I/O: reads, writes, sectors, time in-flight
/proc/net/dev         ── Per-interface: bytes, packets, errors, drops
/proc/net/tcp         ── All TCP sockets (slab table dump)
/proc/loadavg         ── 1/5/15 min load averages + running/blocked tasks
/proc/softirqs        ── Per-CPU softirq counts (HI, TIMER, NET_TX, NET_RX, BLOCK, ...)
/proc/interrupts      ── Per-CPU IRQ counts
/proc/buddyinfo       ── Per-zone buddy allocator free page counts (order 0-10)
/proc/slabinfo        ── Slab cache statistics (root only, often disabled)
/proc/PID/status      ── Process: memory, signals, capabilities, cgroups
/proc/PID/io          ── Process: read_bytes, write_bytes, cancelled_write_bytes
/proc/PID/sched       ── Process: scheduling statistics
/proc/PID/schedstat   ── Process: runtime, wait time, timeslices
/proc/PID/smaps       ── Process: detailed memory maps with RSS/PSS/swap per VMA
/proc/PID/stack       ── Kernel stack trace of a blocked task
						
# Common observability one-liners
# CPU saturation
grep -w cpu /proc/stat
# Memory pressure (0-1000: low→high)
cat /proc/pressure/memory
# IO pressure
cat /proc/pressure/io
# Top slab consumers
sudo cat /proc/slabinfo 2>/dev/null | sort -k3 -rn | head -10
# Disk latency
cat /proc/diskstats | awk '{print $3, $8, $12}'  # device, ms_reading, ms_writing
# Soft IRQ distribution
cat /proc/softirqs

printk and the Kernel Log Buffer

printk() is the oldest observability mechanism - logging strings to a ring buffer. Despite its simplicity, it remains critical for boots, panics, and driver debugging. 

// include/linux/printk.h
// Ring buffer: CONFIG_LOG_BUF_SHIFT determines size (default 17 = 128KB)

// Log levels (include/linux/kern_levels.h):
#define KERN_EMERG    "<0>"  // System is unusable
#define KERN_ALERT    "<1>"  // Action must be taken immediately
#define KERN_CRIT     "<2>"  // Critical conditions
#define KERN_ERR      "<3>"  // Error conditions
#define KERN_WARNING  "<4>"  // Warning conditions
#define KERN_NOTICE   "<5>"  // Normal but significant
#define KERN_INFO     "<6>"  // Informational
#define KERN_DEBUG    "<7>"  // Debug-level messages

// Usage:
pr_emerg("System crash imminent\n");
pr_err("Failed to allocate %zu bytes\n", size);
pr_warn("Deprecated API still in use by %s\n", current->comm);
pr_info("Driver %s loaded\n", drv->name);
pr_debug("Received %zu bytes on fd %d\n", count, fd);

// Conditional debug (enabled via dynamic debug):
pr_debug("Debug message: %p\n", ptr);
// Only printed if dynamic debug is enabled for this callsite

// Fast but unstructed:
trace_printk("vfs_read(%s, %zu) = %zd\n",
             file->f_path.dentry->d_name.name, count, ret);
						
# Kernel log levels
cat /proc/sys/kernel/printk
# 1 4 1 7 — console loglevel, default loglevel, minimum loglevel, default console loglevel

# Dynamic debug: enable debug prints for specific files
sudo bash -c 'echo "file drivers/char/mem.c +p" > /sys/kernel/debug/dynamic_debug/control'

# List all dynamic debug statements
sudo cat /sys/kernel/debug/dynamic_debug/control | head -20

# Follow kernel messages in real time
journalctl -k -f

# Access printk ring buffer directly
cat /dev/kmsg | head -5  # Follows — prints new messages as they arrive

BPF program (unattached) ~0 ns ~1-10 us Per-attachment + per-event
BPF program (attached) ~1-10 us N/A Per-event
PMU counter (counting) ~50-100 ns N/A Per-CPU
PMU counter (sampling) ~1-5 us N/A Per-N samples
procfs read ~0 ns ~1-50 us Per-read
sysfs read ~0 ns ~1-10 us Per-read
printk (partial) ~1-5 us N/A Per-write
printk (full, to console) ~100 us-10ms N/A Per-write

Sampling Strategies

For profiling, sampling is far cheaper than tracing every event. The key question: at what rate and what to sample? 

Sampling Rate Selection:
════════════════════════

    1 Hz     — lightweight, Long-term profiling (days)
    49 Hz    — Standard production profiling (avoids aligning with
               power/thermal management ticks at 50 Hz)
    99 Hz    — Standard for perf (avoids 100 Hz lock-step with timers)
    997 Hz   — Highest resolution before PMU overflows become frequent
    4000 Hz  — Maximum recommended (significant overhead)

    Why avoid round numbers?
    Sampling at 100 Hz on a 100 Hz timer tick locks you to
    one phase of the timer interrupt. 99 Hz gives uniform coverage.

PMU Sample Types:
═════════════════

    PERF_SAMPLE_IP           — Instruction pointer (always recorded)
    PERF_SAMPLE_TID          — PID, TID
    PERF_SAMPLE_TIME         — Timestamp
    PERF_SAMPLE_CALLCHAIN    — Stack trace (requires frame pointer or dwarf)
    PERF_SAMPLE_RAW          — Raw tracepoint data
    PERF_SAMPLE_CPU          — CPU number
    PERF_SAMPLE_PERIOD       — Sampling period at time of sample
    PERF_SAMPLE_BRANCH_STACK — Last N branches (LBR)
						
# Different sample rates
sudo perf record -F 99 -a -g -- sleep 10     # 99 Hz (standard)
sudo perf record -c 100000 -a -- sleep 10    # Every 100k cycles
sudo perf record -e cache-misses -c 1000 -a -- sleep 10  # Every 1000 cache misses
