eBPF

The eBPF in-kernel virtual machine, covering its architecture, instruction set, verifier, program types, maps, helper functions, BTF, and CO-RE.

Overview

eBPF (extended Berkeley Packet Filter) is an in-kernel virtual machine that executes sandboxed programs inside the Linux kernel. Originally designed for network packet filtering, it has grown into a general-purpose execution engine for tracing, security, networking, and observability, all without loading a kernel module. An eBPF program is verified at load time for safety, compiled and JIT-translated to native instructions, and then attached to a kernel hook point.

This article dissects the eBPF subsystem from the instruction set upward: registers, verifier, maps, helpers, program types, BTF, CO-RE, and the loading pipeline.

2. eBPF VM and Instruction Set

The eBPF VM is a 64-bit RISC-like register machine with 11 registers and a stack.

2.2 Instruction Encoding

Each eBPF instruction is exactly 64 bits (8 bytes) wide:

opcode (MSB) src dst offset (16) immediate (32) (LSB)
8 bits 1 bit 1 bit signed signed
Instruction Class Opcode Range Examples
BPF_LD 0x00 lddw (load 64-bit immediate)
BPF_LDX 0x01 ldxb, ldxh, ldxw, ldxdw (load from memory)
BPF_ST 0x02 stb, sth, stw, stdw (store to memory)
BPF_STX 0x03 stxb, stxh, stxw, stxdw (store from register)
BPF_ALU 0x04 add, sub, mul, div, or, and, lsh, rsh, neg, mod, xor, mov, arsh, end
BPF_JMP 0x05 ja, jeq, jgt, jge, jset, jne, jsgt, jsge, jlt, jle, jslt, jsle, call, exit
BPF_ALU64 0x07 Same as ALU but on 64-bit registers

eBPF Call Instruction

The call instruction has several modes, distinguished by the src field:

src = BPF_PSEUDO_CALL (1):   call another BPF function (BPF-to-BPF call)
src = BPF_PSEUDO_KFUNC_CALL (2):   call a kernel function (kfunc)
src = 0 (normal):            call a helper function (imm = helper ID)

3. The Verifier

The verifier is the security boundary of eBPF . It statically analyzes every instruction of every possible execution path before the kernel allows the program to run. A rejected program cannot compromise the kernel.

3.1 Verifier Pipeline

 ┌──────────────┐    ┌───────────────┐    ┌──────────────────┐
 │ check_cfg()  │───►│ do_check()    │───►│ convert_ctx()    │
 │ DAG + loops  │    │ instruction   │    │ context access   │
 │              │    │ simulation    │    │ rewriting        │
 └──────────────┘    └───────+───────┘    └──────────────────┘
                             │
                    ┌────────▼────────┐
                    │ Bounds Tracking │
                    │ Type Tracking   │
                    │ Pointer Leaks   │
                    │ Helper Args     │
                    └─────────────────┘

Step 1: 'check_cfg()' - Builds a control flow graph (CFG) from the bytecode. The graph must be a DA G except for bounded loops, which are allowed since kernel 5.3. Any unreachable code is rejected, and the verifier must prove that every loop terminates. The stack depth must never exceed 512 bytes.

Step 2: 'do_check()' - Symbolically executes every instruction, tracking the type and possible value range of each register. For each instruction, the verifier: - Ensures registers hold expected types before use ( PT R_TO_CTX, PT R_TO_M AP _VALUE, S CA LAR_VALUE, etc.) - For pointer registers, tracks the valid offset range (e.g., map value pointer + 0 to size-1) - For arithmetic, propagates known bounds

Step 3: 'convert_ctx_accesses()' - Rewrites context accesses (e.g., ctx->data ) into direct offsets into the kernel's actual data structure.

3.2 Register Type System

Every register has a type tracked by the verifier:

enum bpf_reg_type {
    NOT_INIT = 0,          // unused, must be written before read
    SCALAR_VALUE,          // holds an integer, can be used for arithmetic
    PTR_TO_CTX,            // pointer to program-specific context (sk_buff, xdp_md, pt_regs)
    CONST_PTR_TO_MAP,      // constant pointer to a map descriptor (for helpers)
    PTR_TO_MAP_VALUE,      // pointer to a map element value
    PTR_TO_MAP_VALUE_OR_NULL, // pointer to map value or NULL (must check before deref)
    PTR_TO_STACK,          // pointer to stack memory (validated range)
    PTR_TO_PACKET,         // pointer to network packet data (validated range)
    PTR_TO_PACKET_END,     // pointer to one-past-end of packet data
    PTR_TO_MEM,            // pointer to valid memory (from helper)
    PTR_TO_MEM_OR_NULL,    // pointer to valid memory or NULL
    PTR_TO_BTF_ID,         // pointer to kernel object (BTF-typed)
    PTR_TO_BTF_ID_OR_NULL, // as above, possibly NULL
    PTR_TO_SOCKET,         // pointer to kernel socket
    PTR_TO_TCP_SOCK,       // pointer to TCP socket
    PTR_TO_TP_BUFFER,      // pointer to tracepoint buffer
    PTR_TO_FLOW_KEYS,      // pointer to flow dissector keys
    PTR_TO_XDP_SOCK,       // pointer to XDP socket
};

3.3 Bounds Tracking

struct bpf_reg_state {
    enum bpf_reg_type type;
    // ... union of type-specific fields ...
    struct {
        s64 smin_value;   // signed minimum known value
        s64 smax_value;   // signed maximum known value
        u64 umin_value;   // unsigned minimum known value
        u64 umax_value;   // unsigned maximum known value
        s32 s32_min_value;
        s32 s32_max_value;
        u32 u32_min_value;
        u32 u32_max_value;
        struct tnum var_off; // bitwise: known 0s and 1s mask
        s64 s64_max;
        u64 u64_max;
        u32 u32_max;
        s32 s32_max;
    };
    // ...
    s32 off;            // offset from the variable pointed to
    u32 id;             // ID for pointer tracking (correlated pointers)
    u32 ref_obj_id;     // reference tracking ID
};

Example: After if (r1 < 100) , the verifier tracks r1 <= 99 on the true branch and r1 >= 100 on the false branch. The tnum (tristate number) tracks exact bit patterns:

struct tnum {
    u64 value;  // bits known to be 1
    u64 mask;   // bits known (0 = unknown, 1 = known)
};
// Example: r1 = 0x??00FF00 → value=0x0000FF00, mask=0xFF00FFFF

3.4 Safety Guarantees

The verifier enforces these guarantees:

  1. No uninitialized registers : Every register must be written before read
  2. Bounded loops : All loops must provably terminate; bpf_loop() helper or explicit bounded counter
  3. No out-of-bounds access : All pointer arithmetic checked against known sizes
  4. No type confusion : Registers cannot change type in unsafe ways
  5. No pointer leaks : Pointer values cannot be stored to maps or returned to user space (prevents ASLR bypass)
  6. Proper helper arguments : Every bpf_helper call checked for correct argument types
  7. Stack depth limit : MAX_BPF_STACK = 512 bytes
  8. Maximum instruction count : 1 million instructions (Linux 5.2+), previously 4096

XDP is the earliest possible BPF hook for network packets - it runs in the NIC driver context, before sk_buff allocation, before the kernel TCP / IP stack touches the packet. This makes XDP extremely fast (can process millions of packets per second per core).

6. Ring Buffer (BPF_MAP_TYPE_RINGBUF)

The ring buffer is the modern replacement for BPF_MAP_TYPE_PERF_EVENT_ARRAY for streaming data from BPF to user space. It is lock-free, supports variable-length records, and handles multiple producers.

 ┌────────────────────────────────────────────────────┐
 │  Ring Buffer Layout                                 │
 │                                                      │
 │  consumer_pos                                       │
 │  ┌──────────────────────────────────────────────┐  │
 │  │         Ring Buffer Memory                     │  │
 │  │  ┌───────────────────────────────────────┐    │  │
 │  │  │ Record 0 | Record 1 | ... | Free      │    │  │
 │  │  │ 8B header│ variable payload           │    │  │
 │  │  └───────────────────────────────────────┘    │  │
 │  │  ┌──────────────┐ (currently being written)   │  │
 │  │  │  producer_pos │                              │  │
 │  └──────────────────────────────────────────────┘  │
 └────────────────────────────────────────────────────┘

Each record header (8 bytes):
 +------------------------------+-------------------+
 | len (32 bit: high 2 = flags) | pg_off (32 bit)   |
 +------------------------------+-------------------+
 Busy = bit 31 of len, Discard = bit 30 of len.

BPF-side API :

// Reserve space in the ring buffer
void *bpf_ringbuf_reserve(struct bpf_map *ringbuf, u64 size, u64 flags);
// Submit the reserved record (makes it visible to consumer)
long bpf_ringbuf_submit(void *data, u64 flags);
// Discard the reservation (record not published)
long bpf_ringbuf_discard(void *data, u64 flags);
// Direct output (reserve + copy + submit in one call)
long bpf_ringbuf_output(struct bpf_map *ringbuf, void *data, u64 size, u64 flags);

User-space API :

7. BTF - BPF Type Format

BTF is the metadata format that describes the types used in BPF programs and the kernel. It is the enabling technology for CO-RE (Compile Once - Run Everywhere).

7.1 BTF Structure

 ┌────────────────────────────────────────────────────────────┐
 │  BTF data:                                                  │
 │  ┌──────────────────────────────────────────────────────┐  │
 │  │ Header                                                │  │
 │  │  magic = 0xeb9f                                       │  │
 │  │  version = 1                                          │  │
 │  │  hdr_len, type_len, str_len                          │  │
 │  ├──────────────────────────────────────────────────────┤  │
 │  │ Type section (array of btf_type entries)              │  │
 │  │  ┌─────+─────+─────+─────┐                           │  │
 │  │  │ INT │ PTR │STRUCT│ FUNC│ ...                       │  │
 │  │  └─────+─────+─────+─────┘                           │  │
 │  │  Each type has: name_off, info (kind+vlen), size/type│  │
 │  ├──────────────────────────────────────────────────────┤  │
 │  │ String section (null-terminated C identifiers)        │  │
 │  │  "int\0sk_buff\0xdp_md\0unsigned int\0..."           │  │
 │  └──────────────────────────────────────────────────────┘  │
 └────────────────────────────────────────────────────────────┘

7.3 CO-RE - Compile Once, Run Everywhere

CO-RE allows a single BPF binary to run on different kernel versions without recompilation. It works through relocations that are resolved at load time based on the target kernel's BTF.

Traditional BPF:                 CO-RE BPF:
 ┌──────────────┐                ┌──────────────┐
 │ Compile for │                │ Compile once │
 │ kernel 5.10 │                │ (with BTF)   │
 └──────+───────┘                └──────+───────┘
        │                               │
        ▼                               ▼
 Load on 5.10 ✓                ┌────────────────────┐
 Load on 5.15 ✗ (wrong offsets)│ libbpf relocation  │
                               │ resolver           │
                               │                    │
                               │ 1. Read vmlinux.h  │
                               │    types            │
                               │ 2. Match struct by │
                               │    name             │
                               │ 3. Resolve field    │
                               │    offsets via BTF  │
                               │ 4. Patch eBPF insns │
                               └────────+───────────┘
                                        │
                                        ▼
                               Load on 5.10 ✓
                               Load on 5.15 ✓
                               Load on 6.1  ✓

CO-RE relies on these BPF instructions and relocations:

// Field existence check
if (bpf_core_field_exists(skb->queue_mapping)) { ... }

// Field size check
if (bpf_core_field_size(skb->len) == 4) { ... }

// Field offset relocation (implicit, libbpf handles it)
data = skb->data;  // offset resolved at load time

// Enum value relocation
if (bpf_core_enum_value(enum skb_drop_reason, SKB_DROP_REASON_NOT_SPECIFIED) == 1) { ... }

// Type size relocation
if (bpf_core_type_size(struct sk_buff) > 200) { ... }

// Type existence
if (bpf_core_type_exists(struct bpf_timer)) { ... }

These macros compile down to BPF instructions with special relocations ( BPF_CORE_READ , BPF_CORE_WRITE , etc.) that libbpf resolves at load time.

8.2 BPF Program Load with libbpf

#include <bpf/libbpf.h>
#include <bpf/bpf.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char **argv) {
    struct bpf_object *obj;
    struct bpf_program *prog;
    struct bpf_link *link;
    int err;

    // Step 1: Open and load the BPF object file
    obj = bpf_object__open_file("myprog.bpf.o", NULL);
    if (libbpf_get_error(obj)) {
        fprintf(stderr, "Failed to open BPF object\n");
        return 1;
    }

    // Step 2: Load the program (verification + JIT + maps)
    err = bpf_object__load(obj);
    if (err) {
        fprintf(stderr, "Failed to load BPF object: %d\n", err);
        return 1;
    }

    // Step 3: Find the program by section name
    prog = bpf_object__find_program_by_name(obj, "my_prog");
    if (!prog) {
        fprintf(stderr, "Program not found\n");
        return 1;
    }

    // Step 4: Attach the program (depends on program type)
    link = bpf_program__attach(prog);
    if (libbpf_get_error(link)) {
        fprintf(stderr, "Failed to attach program\n");
        return 1;
    }

    // Step 5: Main loop — read from BPF maps, poll ring buffers
    printf("BPF program loaded and attached. Press Ctrl-C to exit.\n");
    while (1) {
        sleep(1);
    }

    // Step 6: Cleanup (automatic if using bpf_link)
    bpf_link__destroy(link);
    bpf_object__close(obj);
    return 0;
}

9. eBPF Concurrency

eBPF programs can run concurrently across multiple CPU s. The verifier assumes concurrent execution and enforces safety.

9.1 Per-CPU Maps

 ┌──────────────+──────────────+──────────────┐
 │   CPU 0       │   CPU 1       │   CPU 2       │
 │ ┌──────────┐ │ ┌──────────┐ │ ┌──────────┐ │
 │ │ Per-CPU  │ │ │ Per-CPU  │ │ │ Per-CPU  │ │
 │ │ Array[0] │ │ │ Array[1] │ │ │ Array[2] │ │
 │ └──────────┘ │ └──────────┘ │ └──────────┘ │
 └──────────────+──────────────+──────────────┘

Per- CPU maps give each CPU its own copy of the data. Reads and writes are always local and lock-free. Aggregation is done in user space.

// BPF-side: bpf_get_smp_processor_id() returns current CPU
u32 cpu = bpf_get_smp_processor_id();
u64 *counter = bpf_map_lookup_elem(&percpu_counters, &cpu);
if (counter)
    (*counter)++;

9.2 Spin Locks in Maps

BPF supports spin locks stored inside map values for shared data protection:

struct map_value {
    struct bpf_spin_lock lock;
    int counter;
    u64 last_update;
};

SEC("kprobe/sys_execve")
int trace_exec(struct pt_regs *ctx) {
    u32 key = 0;
    struct map_value *val = bpf_map_lookup_elem(&shared_map, &key);
    if (!val)
        return 0;

    bpf_spin_lock(&val->lock);
    val->counter++;
    val->last_update = bpf_ktime_get_ns();
    bpf_spin_unlock(&val->lock);

    return 0;
}

The verifier enforces that spin locks are held for bounded code regions, properly paired (lock/unlock), and not held across helper calls that might sleep.

10. Tail Calls and Function Calls

10.1 Tail Calls

A tail call jumps from one BPF program to another without returning. The target program is looked up from a BPF_MAP_TYPE_PROG_ARRAY map. Tail calls are limited to 33 nested calls to prevent infinite recursion.

// Jump table
struct {
    __uint(type, BPF_MAP_TYPE_PROG_ARRAY);
    __uint(max_entries, 4);
    __uint(key_size, sizeof(u32));
    __uint(value_size, sizeof(u32));
} jump_table SEC(".maps");

SEC("xdp")
int xdp_entry(struct xdp_md *ctx) {
    u32 action = parse_packet(ctx);
    // Tail call to handler based on parsed action
    bpf_tail_call(ctx, &jump_table, action);
    // If tail call fails (no entry), fall through
    return XDP_PASS;
}

SEC("xdp/0")
int handle_tcp(struct xdp_md *ctx) {
    // TCP-specific logic
    return XDP_PASS;
}

10.2 Function Calls (BPF-to-BPF)

Since Linux 4.16, BPF programs can define and call functions within the same program:

static __always_inline int compute_hash(const void *data, u32 len) {
    u32 hash = 0;
    for (u32 i = 0; i < len; i++)
        hash = hash * 31 + ((u8 *)data)[i];
    return hash;
}

SEC("xdp")
int xdp_prog(struct xdp_md *ctx) {
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    if (data + 20 > data_end)
        return XDP_DROP;

    int h = compute_hash(data, 20);
    // ... use hash ...
    return XDP_PASS;
}

The callee-saved registers (R6-R9) are preserved across calls. Stack frame per function is allocated from the 512-byte stack. Recursion is forbidden.

11. eBPF for Security - LSM Hooks

BPF_PROG_TYPE_LSM allows eBPF programs to attach to Linux Security Module (LSM) hooks - the same hooks used by SELinux and AppArmor. This enables dynamic, programmable security policies without a kernel module.

SEC("lsm/file_open")
int BPF_PROG(restrict_open, struct file *file, int ret) {
    // Allow only read-only opens on sensitive files
    char path_buf[256];
    bpf_d_path(&file->f_path, path_buf, sizeof(path_buf));

    if (strncmp(path_buf, "/etc/shadow", 11) == 0) {
        // Check the flags
        int flags = file->f_flags;
        if (flags & (O_WRONLY | O_RDWR)) {
            bpf_printk("Blocked write open on %s", path_buf);
            return -EPERM;
        }
    }

    return 0; // allow
}

LSM hooks available through BPF include: - file_open , file_permission , file_ioctl - inode_create , inode_unlink , inode_mkdir - task_alloc , task_fix_setuid - socket_create , socket_connect , socket_bind - bpf , bpf_map , bpf_prog - ptrace_access_check , ptrace_traceme

Both bpfilter (the BPF-based firewall replacement for iptables) and Cilium's network policy engine use LSM and TC/XDP hooks for programmable security.

    return 0;
}

13. Writing a Custom Loader with libbpf

// loader.c — custom BPF loader
#include <bpf/libbpf.h>
#include <bpf/bpf.h>
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <unistd.h>

static volatile sig_atomic_t running = 1;
void sig_handler(int sig) { running = 0; }

int main(int argc, char **argv) {
    struct bpf_object *obj;
    struct bpf_program *prog;
    struct bpf_link *link;
    int map_fd;
    int err;

    if (argc != 2) {
        fprintf(stderr, "Usage: %s <bpf_object.o>\n", argv[0]);
        return 1;
    }

    // 1. Open BPF object from file
    DECLARE_LIBBPF_OPTS(bpf_object_open_opts, open_opts,
        .relaxed_maps = true,
    );
    obj = bpf_object__open_file(argv[1], &open_opts);
    if (libbpf_get_error(obj)) {
        fprintf(stderr, "ERROR: opening BPF object: %ld\n", libbpf_get_error(obj));
        return 1;
    }

    // 2. Load all programs and maps
    err = bpf_object__load(obj);
    if (err) {
        fprintf(stderr, "ERROR: loading BPF object: %d\n", err);
        return 1;
    }

    // 3. Attach all auto-attachable programs
    bpf_object__for_each_program(prog, obj) {
        link = bpf_program__attach(prog);
        if (libbpf_get_error(link)) {
            fprintf(stderr, "WARNING: bpf_program__attach failed: %ld\n",
                libbpf_get_error(link));
            continue;
        }
        printf("Attached program: %s\n", bpf_program__name(prog));
    }

    // 4. Find the counter map and poll it
    struct bpf_map *map = bpf_object__find_map_by_name(obj, "counter");
    if (!map) {
        fprintf(stderr, "Map 'counter' not found\n");
        return 1;
    }
    map_fd = bpf_map__fd(map);

    signal(SIGINT, sig_handler);
    signal(SIGTERM, sig_handler);

    printf("Polling counter map every second. Ctrl-C to exit.\n");
    while (running) {
        u32 key = 0;
        u64 value = 0;
        err = bpf_map_lookup_elem(map_fd, &key, &value);
        if (!err)
            printf("\rexecve calls: %llu", (unsigned long long)value);
        fflush(stdout);
        sleep(1);
    }

    printf("\nCleaning up...\n");
    bpf_object__close(obj);
    return 0;
}
