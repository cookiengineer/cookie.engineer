Stack

The call stack - frame structure, prologue/epilogue, System V AMD64 ABI, stack canaries, alignment, GDB inspection, and stack overflow.

Overview

The stack is the LIFO (Last In, First Out) memory region where a process keeps function call frames, return addresses, and local variables. This article covers the x86-64 frame layout, the System V AMD64 calling convention, stack alignment and the red zone, stack canaries, and how the kernel grows and guards the stack. By the end you can read a frame in GDB, name what each register holds, and explain how a stack overflow escapes the frame.

  • Virtual Memory - page tables, mmap, virtual address space
  • Processes - process memory layout, /proc

What the Stack Is

The stack is a LIFO (Last In, First Out) memory region that manages function execution. Every function call pushes a new stack frame; every return pops it. The CPU 's rsp register points to the current top of the stack. The stack grows downward on x86, x86-64, and ARM - meaning rsp decreases when data is pushed. 

High addresses (e.g., 0x7ffffffff000)
┌──────────────────────┐
│  Environment strings │
│  Argument strings    │
│  Auxiliary vectors   │
├──────────────────────┤
│  argv[] pointers     │
│  argc                │
├──────────────────────┤ <- Initial rsp at _start
│                      │
│  ┌────────────────┐  │
│  │ main()'s frame │  │ <- Frame 0 (highest)
│  │  saved rbp     │  │
│  │  return addr   │  │
│  │  local vars    │  │
│  ├────────────────┤  │
│  │ func1() frame  │  │ <- Frame 1
│  │  saved rbp     │  │   rbp -> caller's rbp
│  │  return addr   │  │
│  │  local vars    │  │
│  ├────────────────┤  │
│  │ func2() frame  │  │ <- Frame 2 (current)
│  │  saved rbp     │  │   rbp -> func1's rbp
│  │  return addr   │  │
│  │  local vars    │  │
│  ├────────────────┤  │
│  │  ...           │  │

│                      │
│     ◄── rsp         │
│                      │
│  [guard page]        │ <- Unmapped page; SEGV on access
└──────────────────────┘
Low addresses (e.g., 0x7ffffffe0000)

x86-64 Stack Frame Anatomy

A standard stack frame (without optimizations) has this structure:

        ┌──────────────────────┐
        │  Caller's rbp        │ <- Saved base pointer (+8 from callee rbp)
        ├──────────────────────┤
        │  Return address      │ <- Pushed by `call` instruction (+16 from callee rbp)
        ├──────────────────────┤
rbp ->   │  Saved rbp           │ <- Pushed by `push rbp` in prologue
        ├──────────────────────┤
        │  Local variable 1    │ <- At negative offset from rbp
        │  Local variable 2    │
        ├──────────────────────┤
        │  ...                 │
        ├──────────────────────┤
        │  Callee-saved regs   │ <- rbx, r12-r15 if modified
        ├──────────────────────┤
        │  Argument 7+ (stack) │ <- Beyond 6 register args
        ├──────────────────────┤
rsp ->   │  Red zone (128 B)   │ <- Scratch space below rsp
        └──────────────────────┘

Stack Operations: push, pop, call, ret

; push - decrement rsp, write value
push rax          ; rsp = rsp - 8; *(uint64_t*)rsp = rax

; pop - read value, increment rsp
pop rax           ; rax = *(uint64_t*)rsp; rsp = rsp + 8

; call - push return address, jump
call func         ; push rip_of_next_instruction; jmp func

; ret - pop return address, jump
ret               ; pop rip

; leave - restore frame (equivalent to)
mov rsp, rbp      ; Restore stack pointer
pop rbp           ; Restore base pointer

; enter - create frame (rarely used; slow)
enter N, 0        ; push rbp; mov rbp, rsp; sub rsp, N

Function Prologue and Epilogue

Consider this simple C function:

long add(long a, long b) {
    long result = a + b;
    return result;
}

The compiled assembly (without optimization):

add:
    ; ── PROLOGUE ──
    push   rbp              ; Save caller's base pointer
    mov    rbp, rsp         ; Set new frame base
    ; If local vars need space:
    ; sub    rsp, 16        ; Allocate stack for locals

    ; ── FUNCTION BODY ──
    mov    QWORD PTR [rbp-0x18], rdi   ; a -> local
    mov    QWORD PTR [rbp-0x20], rsi   ; b -> local
    mov    rax, QWORD PTR [rbp-0x18]   ; load a
    add    rax, QWORD PTR [rbp-0x20]   ; add b
    mov    QWORD PTR [rbp-0x8], rax    ; result -> local
    mov    rax, QWORD PTR [rbp-0x8]    ; return result

    ; ── EPILOGUE ──
    pop    rbp              ; Restore caller's base pointer
    ret                     ; Return (pop rip)

With optimization ( -O2 ): 

add:
    lea    rax, [rdi + rsi]  ; a + b -> rax in one instruction
    ret                      ; No frame at all - leaf function optimization
						
# Disassemble to see the frame
gcc -O0 -c -o /tmp/func.o -xc - <<<'long add(long a,long b){return a+b;}'
objdump -d -M intel /tmp/func.o

# With full optimization
gcc -O2 -c -o /tmp/func.o2 -xc - <<<'long add(long a,long b){return a+b;}'
objdump -d -M intel /tmp/func.o2

rsp vs rbp

Register Purpose
rsp Stack pointer - always points to the top of the stack (lowest address in use)
rbp Base pointer - points to the base of the current stack frame (optional, can be used as general-purpose register with-fomit-frame-pointer)
rip Instruction pointer - next instruction to execute

With -fomit-frame-pointer (default in -O1 and above on modern GCC), rbp is freed up as a general-purpose register. Stack variables are accessed relative to rsp instead, which the compiler tracks via frame size accounting. 

# Check if a binary uses frame pointers
readelf -S /usr/bin/ls | grep eh_frame
objdump -d /usr/bin/ls | grep -c 'push.*rbp'

System V AMD64 ABI - Calling Convention

The System V ABI specifies how function arguments are passed and the stack is managed on x86-64 Linux:

Integer/Pointer Arguments (in order)

Position Register
1st arg rdi
2nd arg rsi
3rd arg rdx
4th arg rcx
5th arg r8
6th arg r9
7th+ arg On stack (right-to-left push order)

Floating-point Arguments

Position Register
1st-8th xmm0 - xmm7
9th+ On stack

Return Value

Type Register(s)
Integer/Pointer (<=64 bits) rax
Integer (<=128 bits) rax (low) + rdx (high)
Float/Double xmm0
Float complex xmm0 + xmm1

Caller-saved (volatile) registers - the caller must save these before a call if their values are needed after: rax, rcx, rdx, rsi, rdi, r8-r11

Callee-saved (nonvolatile) registers - the callee must preserve these: rbx, rbp, r12-r15, rsp 

Caller before call:             Callee prologue:
  save volatile regs              push rbp
  put args in registers           mov rbp, rsp
  call func                       sub rsp, N          <- allocate locals
  ...                             ...
                                Callee epilogue:
  after return:                   leave / pop rbp
  restore volatile regs           ret

Stack Alignment

The x86-64 ABI requires the stack to be 16-byte aligned immediately before the call instruction executes. This means rsp % 16 == 0 when call pushes the 8-byte return address, making rsp % 16 == 8 at function entry. The prologue must adjust rsp to realign if needed. 

; Function that needs to call another function
; rsp % 16 == 8 at entry (due to return address)
sub rsp, 8        ; Now rsp % 16 == 0 - aligned for call
call other_func
add rsp, 8        ; Restore

Alignment matters because SSE/ AVX instructions ( movaps , movdqa ) fault on unaligned addresses. The compiler handles this automatically; you only need to worry when writing raw assembly that calls C functions.

The Red Zone

The System V AMD64 ABI defines a 128-byte red zone below rsp - memory the function can use without adjusting rsp . This is valid because signals are delivered on a separate stack (or above rsp ). The kernel guarantees it won't touch the red zone.

The Windows x64 ABI has no red zone - the equivalent region can be clobbered by interrupts at any time. 

; Linux: valid use of red zone
mov [rsp - 8], rax     ; Store in red zone - rsp unchanged
mov rax, [rsp - 8]     ; Load from red zone
ret

; Windows/other kernel: NOT safe - must adjust rsp first
sub rsp, 8
mov [rsp], rax
...
add rsp, 8
ret

Stack Canaries

GCC's -fstack-protector (enabled by default on ArchLinux) inserts a guard value (canary) between the stack frame's local variables and the saved return address. Before the function returns, it checks the canary. If a buffer overflow corrupts the canary, the program aborts. 

Without canary:                With canary:
┌──────────────────┐          ┌──────────────────┐
│  Local buffer    │          │  Local buffer    │
│  (vulnerable)    │          │  (vulnerable)    │
│  ...             │          ├──────────────────┤
├──────────────────┤          │  Canary (random) │ <- __stack_chk_guard
│  Saved rbp       │          ├──────────────────┤
│  Return address  │          │  Saved rbp       │
└──────────────────┘          │  Return address  │
                              └──────────────────┘

Stack Growth Direction

Most architectures use a downward-growing stack:

Architecture Direction Why
x86 / x86-64 Down (decreasing addresses) Historical: early x86, efficient addressing
ARM (AArch32/64) Down Convention
MIPS Down Convention
PA-RISC Up (increasing addresses) Historical design choice
SPARC Down Convention

On Linux, the stack sits at the high end of the user address space and grows downward toward the heap. Between stack and heap lies mmap territory (shared libraries, anonymous mappings). This layout is enforced by the kernel's ELF loader.

Stack Size Limit

# Soft limit (can be increased by user)
ulimit -s
# Default: 8192 kB (8 MiB) on ArchLinux

# Hard limit
ulimit -Hs

# Set new limit
ulimit -s 16384  # 16 MiB

# Kernel-managed stack growth:
# The kernel automatically extends the stack on page faults
# within the "stack expansion gap" (usually 1 MiB below current rsp)
cat /proc/$$/maps | grep stack
# Stack segment grows on-demand, up to ulimit -s

Thread stacks: Threads created with pthread_create() get their own stack. The default size is set by pthread_attr_setstacksize() . If not specified, glibc uses ulimit -s (typically 8 MiB).

alloca() - Dynamic Stack Allocation

alloca() allocates memory on the stack that is automatically freed when the function returns. It's faster than malloc() (no heap bookkeeping) but dangerous for large/variable sizes. 

#include <stdio.h>
#include <stdlib.h>
#include <alloca.h>

void dynamic_stack(int n) {
    // Allocate n ints on the stack
    int* arr = alloca(n * sizeof(int));

    for (int i = 0; i < n; i++)
        arr[i] = i * i;

    printf("Stack-allocated %zu bytes, array[%d] = %d\n",
           n * sizeof(int), n-1, arr[n-1]);
    // arr is automatically freed when this function returns
}

int main() {
    dynamic_stack(10);
    dynamic_stack(100);
    return 0;
}

alloca() is not part of the C standard; it's a platform extension. GCC implements it inline

  • it simply adjusts rsp by the requested amount. There's no freealloca() - memory is
reclaimed when the function's epilogue restores rsp .

Stack Overflow

A stack overflow occurs when the stack grows past its allocated region. On Linux, this is detected by the guard page mechanism: 

┌────────────────────┐
│  Stack region      │ (e.g., 8 MiB, r/w)
│  ...               │
│  rsp ->             │
│  ...               │
├────────────────────┤
│  Guard region      │ (typically 1 MiB, no access)
│                    │ <- Kernel extends stack into this on page fault
├────────────────────┤
│  Guard page        │ (1 page = 4 KiB, no access, no growth)
│                    │ <- SEGV if rsp enters this page
├────────────────────┤
│  Other mappings    │
└────────────────────┘

When rsp decrements into the guard region, a page fault occurs. The kernel checks if this is a legitimate stack expansion (within 1 MiB of the current stack boundary) and extends the mapping. If the access is past the guard page (into other mappings), the kernel sends SIGSEGV. 

// Exploding the stack - infinite recursion
void recurse(int n) {
    char bigbuf[1024*64];  // 64 KiB per frame
    printf("Depth: %d, rsp approx: %p\n", n, &bigbuf[0]);
    recurse(n + 1);
}

int main() {
    recurse(1);
    return 0;  // Never reached - SEGV
}
						
gcc -o stack-overflow stack-overflow.c && ./stack-overflow
# Observe: ~130 frames before SEGV (8 MiB / 64 KiB)

sigaltstack - Custom Signal Stack

Signals can be delivered on a separate stack to handle stack overflow scenarios or to avoid corrupting the normal stack when handling a SEGV caused by stack exhaustion: 

#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <string.h>
#include <unistd.h>

void segv_handler(int sig, siginfo_t* info, void* ctx) {
    const char* msg = "SIGSEGV caught on alternate stack\n";
    write(STDERR_FILENO, msg, strlen(msg));
    _exit(1);
}

int main() {
    stack_t ss;
    ss.ss_sp = malloc(SIGSTKSZ);   // Recommended size
    ss.ss_size = SIGSTKSZ;
    ss.ss_flags = 0;

    if (sigaltstack(&ss, NULL) == -1) {
        perror("sigaltstack");
        return 1;
    }

    struct sigaction sa = {0};
    sa.sa_sigaction = segv_handler;
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;  // Use alternate stack
    sigaction(SIGSEGV, &sa, NULL);

    // Trigger SEGV intentionally
    *(volatile int*)NULL = 0;
    return 0;
}
						
gcc -o sigaltstack-demo sigaltstack-demo.c && ./sigaltstack-demo

Verification Checklist

# 1. Check stack size limit
ulimit -s

# 2. Find the stack in your process memory map
cat /proc/$$/maps | grep stack

# 3. Dump the beginning of your stack
hexdump -C /proc/$$/mem -s 0x7ffffffe0000 -n 256 2>/dev/null || echo "Use gdb instead"

# 4. Check if binary uses stack canaries
readelf -s /usr/bin/ls | grep stack_chk_fail
# Or: checksec --file=/usr/bin/ls

# 5. Disassemble a function to see prologue/epilogue
gcc -O0 -g -o /tmp/disassemble -xc - <<<'int f(int x){return x*2;}'
objdump -d -M intel /tmp/disassemble | grep -A20 '<f>:'

# 6. Count stack-based locals in a binary (rough)
objdump -d /tmp/disassemble | grep -c 'sub.*rsp'

# 7. Verify stack alignment at function entry
python3 -c "
import os
pid = os.getpid()
# Read /proc/pid/stat for kstkesp (kernel stack pointer)
with open(f'/proc/{pid}/stat') as f:
    fields = f.read().split()
    print(f'kstkesp: {fields[28]}')
"

# 8. Inspect frame pointer usage
readelf -h /usr/bin/ls | grep -i 'frame'

# 9. Monitor stack growth in real time with perf
perf stat -e faults -e minor-faults ls /usr/share >/dev/null

Challenge

Write a Go tool that reports the mapped stack region and the kernel limit that bounds it. Read /proc/self/maps , find the [stack] mapping, and print its low address, high address, and size in KiB. Then read RLIMIT_STACK with syscall.Getrlimit and compare the soft limit with the mapping. Run it again after ulimit -s 1024 and after spawning a goroutine, and explain why the mapped main-thread stack can be smaller than the limit and why goroutine stacks are separate. 

package main

import (
	"bufio"
	"fmt"
	"os"
	"strconv"
	"strings"
	"syscall"
)

func main() {
	file, err := os.Open("/proc/self/maps")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer file.Close()

	scanner := bufio.NewScanner(file)
	for scanner.Scan() {
		line := scanner.Text()
		if strings.Contains(line, "[stack]") == false {
			continue
		}
		fields := strings.Fields(line)
		bounds := strings.Split(fields[0], "-")
		low, _ := strconv.ParseUint(bounds[0], 16, 64)
		high, _ := strconv.ParseUint(bounds[1], 16, 64)
		fmt.Printf("stack: 0x%x - 0x%x (%d KiB)\n", low, high, (high-low)/1024)
	}

	var limit syscall.Rlimit
	if err := syscall.Getrlimit(syscall.RLIMIT_STACK, &limit); err == nil {
		fmt.Printf("RLIMIT_STACK: soft=%d bytes hard=%d bytes\n", limit.Cur, limit.Max)
	} else {
		fmt.Fprintln(os.Stderr, err)
	}
}
