Certificate Management

PKI lifecycle management, from issuance through renewal to revocation, with operational security practices.

Overview

Certificates expire, keys leak, and revocation is hard. This article walks the X.509 lifecycle: key generation, CSR submission, issuance, deployment, renewal, and revocation. After reading it you can inspect a certificate chain, automate renewal with ACME, and react when a private key is compromised. The goal is that no certificate outage is ever a surprise.

Required Reading

  • TLS Protocol - handshake, cipher suites, certificate validation
  • Cryptography - hash functions, digital signatures, RSA /ECDSA
  • Public Key Cryptography - key pairs, signing, verification

Concept

Certificate management is the operational discipline of the X.509 PKI lifecycle: key generation, CSR submission, issuance, deployment, renewal, and revocation. Every expired certificate is a self-inflicted outage. Every leaked private key is a compromise of all sessions protected by that certificate.

The challenge scales with the number of certificates. A small shop with 3 domains might manage them manually. An enterprise with 10,000+ certificates across internal services, external endpoints, client auth, code signing, and email S/MIME needs full automation.

PKI Fundamentals

                 +--------------+
                 |  Root CA     |  <- Offline, air-gapped, HSM-protected
                 |  (self-signed|     Valid 10-20 years
                 |   cert)      |     Only used to sign Intermediate CAs
                 +------+-------+
                        | signs
                 +------v-------+
                 | Intermediate |  <- Online, but restricted access
                 |  CA          |     Valid 5-10 years
                 |              |     Signs end-entity certs
                 +------+-------+
                        | signs
            +-----------+-----------+
    +-------v------+ +--v------+ +--v----------+
    |  End-Entity  | | End-Ent | | End-Entity   |
    |  (webserver) | | (client)| | (S/MIME)     |
    |  Valid 90d   | | 1 year  | | 1 year       |
    +--------------+ +---------+ +--------------+

Trust chain validation steps:

  1. The end-entity cert signature is verified against its issuer (the intermediate certificate authority).
  2. The intermediate cert signature is verified against its issuer (the root certificate authority).
  3. The root cert is in the trust store, so the chain is trusted.
  4. Each cert is checked: not expired, not revoked, key usage matches, and the subject alternative name matches the hostname.

Certificate Types

Type Validation Issuance Use Case
DV (Domain Validated) Prove domain control (HTTP/DNS challenge) Minutes Websites, APIs
OV (Organization Validated) DV + verify org registration Days Business websites
EV (Extended Validation) DV + OV + physical/legal verification Days-weeks Banks, high-trust sites
Wildcard DV/OV for*.domain.com As above Multiple subdomains
Multi-Domain (SAN) DV/OV for multiple names As above Unified comms, Exchange
Code Signing Org validation + hardware token Days Signed executables
Client Auth DV/OV for identifying users/machines Varies mTLS, VPN auth
S/MIME Email address validation Varies Email encryption/signing

A single wildcard cert *.example.com means every subdomain is compromised when that key leaks. Prefer individual certs, or split wildcards across trust boundaries (production vs. development).

OpenSSL Inspection Toolkit

# Check a remote server's certificate
openssl s_client -connect example.com:443 -servername example.com \
  </dev/null 2>/dev/null | openssl x509 -text -noout

# Check certificate expiry date
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -enddate

# Check certificate chain
openssl s_client -connect example.com:443 -showcerts </dev/null 2>/dev/null

# Verify a certificate against a CA bundle
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert.pem

# Extract the public key from a certificate
openssl x509 -in cert.pem -pubkey -noout

# Compare a public key with its certificate (works for any key type)
openssl x509 -in cert.pem -pubkey -noout | openssl pkey -pubin -outform DER | openssl sha256
openssl pkey -in key.pem -pubout -outform DER | openssl sha256
# Both SHA-256 hashes must match

# For RSA keys only, compare moduli (does not work for ECDSA)
openssl x509 -in cert.pem -noout -modulus | openssl sha256
openssl rsa -in key.pem -noout -modulus | openssl sha256

# Convert certificate formats
openssl x509 -in cert.pem -outform DER -out cert.der     # PEM -> DER
openssl x509 -in cert.der -inform DER -out cert.pem       # DER -> PEM
openssl pkcs12 -export -in cert.pem -inkey key.pem -out cert.pfx  # PEM -> PKCS#12

# Generate a self-signed cert (testing/internal only)
openssl req -x509 -newkey rsa:4096 -sha256 -days 365 -nodes \
  -keyout key.pem -out cert.pem \
  -subj "/CN=test.internal" \
  -addext "subjectAltName=DNS:test.internal,DNS:*.test.internal"

Let's Encrypt / ACME

ACME (Automatic Certificate Management Environment) automates domain validation, issuance, and renewal.

How ACME Works

Client -> ACME Server (Let's Encrypt):
1. Account creation (generate key, register)
2. Order a certificate (specify domains)
3. Receive challenges (HTTP-01, DNS-01, TLS-ALPN-01)
4. Complete challenge (prove domain control)
5. Submit CSR
6. Receive signed certificate

DNS-01 Challenge

Preferred for wildcards and hosts without a public port. The client creates a TXT record named _acme-challenge.example.com with a server-provided token, and the CA resolves it. 

# Challenge: Create TXT record _acme-challenge.example.com with server-provided token
# Let's Encrypt verifies: dig TXT _acme-challenge.example.com

HTTP-01 Challenge

For simple webservers. The client serves a file under /.well-known/acme-challenge/ . 

# Challenge: Serve file at http://example.com/.well-known/acme-challenge/<token>
# Let's Encrypt verifies: curl http://example.com/.well-known/acme-challenge/<token>
						
# certbot - the reference ACME client
sudo pacman -S certbot

# Obtain a certificate (standalone mode starts a temporary webserver)
sudo certbot certonly --standalone -d example.com -d www.example.com

# Obtain with DNS challenge (supports wildcards)
sudo certbot certonly --manual --preferred-challenges dns \
  -d example.com -d '*.example.com'
# Follow prompts to create TXT records, then press Enter

# Renewal (certbot renew runs from a systemd timer)
sudo certbot renew --dry-run  # test renewal
sudo certbot renew             # renew all near-expiry certs

Alternative ACME Clients

# acme.sh - pure shell, zero dependencies, excellent for scripts
curl https://get.acme.sh | sh
acme.sh --issue -d example.com -w /var/www/html
acme.sh --install-cert -d example.com \
  --key-file /etc/nginx/ssl/key.pem \
  --fullchain-file /etc/nginx/ssl/fullchain.pem \
  --reloadcmd "systemctl reload nginx"

# lego - Go ACME client, good for CI/CD
sudo pacman -S lego
lego --email admin@example.com --dns cloudflare --domains example.com run

Automated Renewal

# /etc/systemd/system/cert-renewal.service

[Service]

[Install]
WantedBy=timers.target

cert-manager on Kubernetes

# cert-manager automates TLS in Kubernetes using ACME
# Install:
# kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml

# Issuer: represents a CA (Let's Encrypt staging/prod, internal CA)
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: admin@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - http01:
          ingress:
            class: nginx

---
# Certificate request: cert-manager handles the entire lifecycle
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: example-com-tls
spec:
  secretName: example-com-tls
  issuerRef:
    name: letsencrypt-prod
  dnsNames:
    - example.com
    - www.example.com
  # cert-manager auto-renews about 30 days before expiry

Certificate Transparency

CT is a system of append-only logs that record every publicly-trusted certificate. Browsers require CT proof (SCTs) before they trust a certificate.

CT matters for defenders because:

  • Monitoring the logs for your domains catches misissued certificates early.
  • Monitoring the logs for typo-squatted domains detects phishing infrastructure.
  • Every publicly issued certificate is public record (internal CA certs

are not).

# crt.sh - query CT logs via web or CLI
# Find all certificates for a domain
curl -s 'https://crt.sh/?q=%.example.com&output=json' | jq -r \
  '.[] | "\(.common_name) | Issued: \(.entry_timestamp) | Issuer: \(.issuer_name) | SHA256: \(.cert_sha256)"'

# Find recently issued certs for your org (monitor for misissuance)
curl -s 'https://crt.sh/?q=%.example.com&output=json' | jq '.[] | select(.entry_timestamp > "2026-06-01")'

# CertSpotter - alternative CT monitor
curl -s 'https://api.certspotter.com/v1/issuances?domain=example.com&include_subdomains=true&expand=dns_names' | jq .

# CT monitoring with certgraph (Go)
go install github.com/lanrat/certgraph@latest
certgraph google.com --depth 1

CT Monitoring Alert

#!/bin/bash
# ct-monitor.sh - alert on new certificates for monitored domains
# Run via cron every hour

DOMAINS="example.com api.example.com internal.example.com"
KNOWN_CERTS_FILE="/var/lib/ct-monitor/known-certs.txt"
mkdir -p "$(dirname "$KNOWN_CERTS_FILE")"

for domain in $DOMAINS; do
  curl -s "https://crt.sh/?q=%.${domain}&output=json" | jq -r '.[].cert_sha256' | sort > /tmp/ct-current-$$.txt

  if [ -f "$KNOWN_CERTS_FILE" ]; then
    NEW=$(comm -13 "$KNOWN_CERTS_FILE" /tmp/ct-current-$$.txt)
    if [ -n "$NEW" ]; then
      echo "ALERT: New certificate detected for $domain" | systemd-cat -t ct-monitor -p warning
    fi
  fi

  mv /tmp/ct-current-$$.txt "$KNOWN_CERTS_FILE"
done

Certificate Pinning

Pinning restricts which certificates or public keys are accepted for a domain. It protects against CA compromise but is operationally dangerous: replacing a pinned cert in an emergency requires an application update. 

# HTTP Public Key Pinning (HPKP) is deprecated and removed from browsers
# Prefer: Certificate Transparency monitoring plus the DANE protocol (DNSSEC-based)

# For mobile/desktop apps: pin the public key, not the certificate
# This allows cert renewal without app updates
openssl x509 -in cert.pem -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | openssl base64
# Output is the SPKI fingerprint - pin this, not the cert hash

Key Protection

Private keys must never exist unencrypted on disk. The protection hierarchy:

HSM (Hardware Security Module) -> Best
  FIPS 140-2 or 140-3 Level 3
  Keys generated inside, never leave
  PCI DSS requirement for payment keys

TPM (Trusted Platform Module) -> Good
  On-chip key generation and storage
  Sealed to PCRs (system state)
  Linux: tpm2-tools for key operations

PKCS#11 Token (smart card, YubiKey) -> Good
  Portable hardware token
  Keys generated on-device, require PIN to use

Encrypted file on disk -> Minimum acceptable
  openssl enc -aes-256-gcm for at-rest
  Unlocked with a password at service start
						
# TPM2: generate a key sealed to specific PCR values
# The key is only accessible if the system boots into the expected state
sudo pacman -S tpm2-tools

# Create a primary key in the TPM
tpm2_createprimary -C o -g sha256 -G rsa -c primary.ctx

# Authorize a policy that requires PCRs 0-7 (firmware + bootloader)
tpm2_startauthsession -S session.ctx
tpm2_policypcr -S session.ctx -l sha256:0,1,2,3,4,5,6,7 -L pcr.policy
tpm2_flushcontext session.ctx

# Create a key bound to that policy
tpm2_create -C primary.ctx -g sha256 -G rsa -u key.pub -r key.priv \
  -a 'fixedtpm|fixedparent|sensitivedataorigin|userwithauth|noDA' \
  -L pcr.policy

# Load and use the key
tpm2_load -C primary.ctx -u key.pub -r key.priv -c key.ctx

Cipher Suite Policies

Cipher suite configuration determines which algorithms are offered during the TLS handshake. Weak ciphers enable downgrade attacks. 

# nginx.conf - modern cipher suite (TLS 1.2+, strong ciphers)
ssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers on;

# TLS 1.3 ciphers (only 5 exist - all are strong)
ssl_conf_command Ciphersuites TLS_AES_256_GCM_SHA384:TLS_AES_128_GCM_SHA256:TLS_CHACHA20_POLY1305_SHA256;

# TLS 1.2 ciphers - only AEAD ciphers with ECDHE key exchange
ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;

Certificate Inventory

Maintain an inventory of every certificate your organization uses, including internal CA certs, code signing certs, and client auth certs, not just public-facing web certs. 

#!/bin/bash
# cert-inventory.sh - scan all known hosts and collect certificate info
# Input: hosts.txt (one hostname:port per line)

while IFS=: read -r host port; do
  port=${port:-443}
  echo | openssl s_client -connect "${host}:${port}" -servername "$host" \
    </dev/null 2>/dev/null | openssl x509 -noout \
    -subject -issuer -dates -fingerprint -sha256 2>/dev/null \
    | paste -sd '|' - \
    | awk -v host="$host" -v port="$port" '{print host, port, $0}'
done < hosts.txt > cert-inventory-$(date +%Y%m%d).txt

Emergency Procedures

Expiring Certificate

# 1. Manually renew
sudo certbot renew --force-renewal

# 2. If certbot failed, get a new cert
sudo certbot certonly --standalone -d example.com

# 3. If Let's Encrypt is down (rare), use ZeroSSL (also ACME)
lego --server https://acme.zerossl.com/v2/DV90 \
  --email admin@example.com --dns cloudflare --domains example.com run

# 4. Last resort: temporary self-signed cert
openssl req -x509 -newkey rsa:4096 -sha256 -days 7 -nodes \
  -keyout emergency-key.pem -out emergency-cert.pem \
  -subj "/CN=example.com" \
  -addext "subjectAltName=DNS:example.com"
# Note: browsers will show a warning - only for emergency use

Compromised Private Key

# 1. Revoke immediately
certbot revoke --cert-path /etc/letsencrypt/live/example.com/cert.pem \
  --reason keyCompromise

# 2. Reissue a new certificate with a NEW private key (certbot does this automatically)
certbot certonly --standalone -d example.com --force-renewal

# 3. Audit: what sessions were protected by the old key?
# Assume all traffic between last-known-good and revocation time is compromised
# Force password resets, session invalidation, and token rotation

Challenge

Write a Go tool that reads one or more PEM files, prints a one-line summary per certificate, and flags anything that is already expired or expires within a configurable number of days. It must also report whether each certificate is self-signed. 

package main

import (
	"crypto/x509"
	"encoding/pem"
	"fmt"
	"os"
	"strconv"
	"time"
)

func main() {
	if len(os.Args) < 2 {
		fmt.Fprintf(os.Stderr, "usage: %s warn-days cert.pem [chain.pem ...]\n", os.Args[0])
		os.Exit(2)
	}

	warnDays, err := strconv.Atoi(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, "warn-days must be an integer")
		os.Exit(2)
	}

	now := time.Now()

	for _, path := range os.Args[2:] {
		raw, err := os.ReadFile(path)
		if err != nil {
			fmt.Fprintln(os.Stderr, err)
			continue
		}

		for len(raw) > 0 {
			var block *pem.Block
			block, raw = pem.Decode(raw)
			if block == nil {
				break
			}
			if block.Type != "CERTIFICATE" {
				continue
			}

			cert, err := x509.ParseCertificate(block.Bytes)
			if err != nil {
				fmt.Fprintln(os.Stderr, err)
				continue
			}

			remaining := int(cert.NotAfter.Sub(now).Hours() / 24)
			selfSigned := cert.Subject.String() == cert.Issuer.String()

			status := "OK"
			if remaining < 0 {
				status = "EXPIRED"
			} else if remaining <= warnDays {
				status = "WARNING"
			}

			fmt.Printf("%-8s days=%-5d selfsigned=%-5v subject=%q\n",
				status, remaining, selfSigned, cert.Subject.String())

			for _, name := range cert.DNSNames {
				fmt.Printf("         SAN=%s\n", name)
			}
		}
	}
}
