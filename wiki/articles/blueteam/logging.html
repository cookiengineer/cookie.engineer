Logging

Building useful logs for security investigations with systemd-journald, rsyslog, auditd, and applications.

Overview

Logs are the only record of what actually happened on a system. Without them, an incident becomes a guessing game. A well-configured logging pipeline answers: who did what, from where, at what time, and with what result. The goal is not to log everything - that burns storage and creates noise. The goal is to log the right things, structured for machine querying, with integrity guarantees.

systemd-journald

Modern Linux distributions run journald as the primary log collector. It captures kernel messages, boot logs, stdout/stderr from services, and syslog messages. Unlike flat files, journald stores structured binary logs with indexed fields.

Configuration

# /etc/systemd/journald.conf
[Journal]
Storage=persistent
Compress=yes
Seal=yes
SystemMaxUse=2G
SystemKeepFree=500M
RuntimeMaxUse=200M
RateLimitIntervalSec=5s
RateLimitBurst=500
ForwardToSyslog=yes
MaxRetentionSec=90day

Key parameters: - Storage=persistent - writes to /var/log/journal ; survives reboots - Seal=yes

  • Forward Secure Sealing (FSS) signs log entries to detect tampering - RateLimitBurst - drops messages if a service exceeds N messages per RateLimitIntervalSec ; critical for noisy services
  • MaxRetentionSec - auto-purge logs older than this interval

Journalctl Queries

# View kernel messages since last boot
journalctl -k -b

# Show all logs from the sshd unit with priority err and above
journalctl -u sshd -p err

# JSON output for pipeline processing
journalctl -u nginx --since "2026-06-26 08:00:00" --until "2026-06-26 12:00:00" -o json

# Filter by binary path (all commands executed matching pattern)
journalctl _COMM=sshd

# Filter by SELinux context
journalctl _SELINUX_CONTEXT=system_u:system_r:sshd_t:s0

# Follow live, like tail -f
journalctl -f -u auditd

# Show logs with specific syslog identifier
journalctl SYSLOG_IDENTIFIER=sshd

# Kernel messages matching pattern
journalctl -k -g "firewall|netfilter|conntrack"

# Export all logs for forensic export
journalctl --export > /tmp/forensic-logs.journal

# Check FSS verification status
journalctl --verify

Forward Sealing (FSS)

FSS prevents an attacker from modifying logs then claiming they were never written. journald periodically signs the log file with a key pair. Any modification after sealing invalidates the signature. 

# Generate FSS key pair (store verification key securely offline)
journalctl --setup-keys

# Verify logs against FSS keys
journalctl --verify --verify-key=/etc/verification-key

# Show FSS status of journal files
journalctl --header | grep -i seal

rsyslog

rsyslog provides the traditional syslog server with modern extensions: TCP / TLS transport, message parsing, databases output, and queue-based buffering.

Facilities and Priorities

Syslog messages carry a facility (source subsystem) and priority (severity):

Facility Code Purpose
auth/authpriv 4/10 Authentication, sudo
cron 9 Scheduled jobs
daemon 3 Background services
kern 0 Kernel messages
local0-local7 16-23 Application-defined
mail 2 Mail subsystem
syslog 5 syslogd itself
user 1 User-level messages
Priority Value Meaning
emerg 0 System unusable
alert 1 Immediate action
crit 2 Critical condition
err 3 Error condition
warning 4 Warning
notice 5 Normal but significant
info 6 Informational
debug 7 Debug messages

rsyslog Configuration

# /etc/rsyslog.conf — Central log server example

# Modules
module(load="imuxsock")          # local system logging
module(load="imklog")            # kernel logging
module(load="imtcp")             # TCP receiver
input(type="imtcp" port="514")

# Templates — structured JSON output
template(name="jsonFormat" type="list") {
    constant(value="{")
    constant(value="\"@timestamp\":\"")  property(name="timereported" dateFormat="rfc3339")
    constant(value="\",\"host\":\"")     property(name="hostname")
    constant(value="\",\"facility\":\"") property(name="syslogfacility-text")
    constant(value="\",\"severity\":\"") property(name="syslogseverity-text")
    constant(value="\",\"program\":\"")  property(name="programname")
    constant(value="\",\"message\":\"")  property(name="msg" format="json")
    constant(value="\"}\n")
}

# Ruleset — route by facility.priority
# Log all auth messages at info+ to a dedicated file
auth,authpriv.info    /var/log/auth.log

# Log everything except mail at warn+ to syslog
*.warn;mail.none      /var/log/syslog

# Send all local6 (custom app) messages to SIEM via TCP
local6.*  @@central-siem.example.com:514;jsonFormat

# Drop noisy cron debug messages
cron.debug  ~

Remote Forwarding

# Send to remote rsyslog server over TCP/TLS
# /etc/rsyslog.d/50-remote.conf

$DefaultNetstreamDriverCAFile /etc/ssl/certs/ca-cert.pem
$ActionSendStreamDriver gtls
$ActionSendStreamDriverMode 1
$ActionSendStreamDriverAuthMode x509/name
$ActionSendStreamDriverPermittedPeer logserver.example.com

*.* @@(o)logserver.example.com:6514;jsonFormat

auditd

The Linux audit subsystem hooks into syscalls and records events based on user-defined rules. Unlike syslog, auditd captures the precise arguments of every monitored operation.

Audit Rules

# /etc/audit/rules.d/99-security.rules

# Delete all existing rules
-D

# Set buffer size (increase under heavy load)
-b 8192

# Fail closed — panic if audit daemon cannot write (for high-security)
-f 2

# Monitor all execve calls (process execution)
-a always,exit -F arch=b64 -S execve -k process_execution
-a always,exit -F arch=b32 -S execve -k process_execution

# Monitor writes to /etc/passwd and /etc/shadow
-w /etc/passwd -p wa -k identity_changes
-w /etc/shadow -p wa -k identity_changes
-w /etc/group -p wa -k group_changes
-w /etc/sudoers -p wa -k sudoers_changes

# Monitor privilege escalation syscalls
-a always,exit -F arch=b64 -S setuid -S setgid -S setreuid -S setregid -k privilege_change

# Monitor access to sensitive SSH keys
-w /root/.ssh -p rwa -k ssh_key_access
-w /home -p rwa -k home_access

# Monitor changes to cron directories
-w /etc/cron.d -p wa -k cron_changes
-w /etc/cron.daily -p wa -k cron_changes
-w /var/spool/cron -p wa -k cron_changes

# Monitor suspicious kernel module loading
-w /sbin/insmod -p x -k module_load
-w /sbin/modprobe -p x -k module_load
-w /sbin/rmmod -p x -k module_unload

# Track 64-bit syscalls that modify file attributes
-a always,exit -F arch=b64 -S chmod -S fchmod -S fchmodat -k file_permission_change

# Network configuration changes
-w /etc/hosts -p wa -k network_config
-w /etc/resolv.conf -p wa -k network_config

# Make rules immutable (requires reboot to change)
-e 2

Querying auditd Logs

# Search for execve events by key
ausearch -k process_execution

# Show events for a specific time range
ausearch -ts 06/26/2026 08:00:00 -te 06/26/2026 12:00:00 -k process_execution

# Filter by UID
ausearch -ua root -k privilege_change

# Find failed events (exit code != 0)
ausearch --success no

# Generate a summary report of authentication events
aureport -au

# Produce a report of all executable invocations
aureport -x --summary

# Show file access summary
aureport -f --summary

# List all syscall invocations for a PID
ausearch -p 1234 --raw | grep "type=SYSCALL"

# Parse audit.log with ausearch for failed exec attempts
ausearch -m SYSCALL -sc execve --success no

# JSON output (modern auditd)
ausearch -k process_execution --format text

Application Logging

Structured Logging

Plain text logs are miserable to query. Use structured formats - JSON is the industry default. Every log entry should carry consistent fields: 

{
  "timestamp": "2026-06-26T10:30:00.123Z",
  "severity": "info",
  "service": "auth-api",
  "correlation_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "user_id": "jdoe",
  "source_ip": "192.168.1.100",
  "action": "login",
  "result": "success",
  "duration_ms": 45,
  "message": "user jdoe authenticated via password"
}

Key fields every log should include: - correlation_id - links log entries across services for a single request - user_id / session_id - ties actions to an identity - source_ip

  • origin of the request (respect privacy laws) - action - standard, machine-readable action name
  • result - success, failure, denied, error
  • duration_ms - performance metric that also reveals timing anomalies

What NOT to Log

// NEVER log these fields — they create a secondary secrets store:
secrets, passwords, tokens, api_keys, session cookies, PII (SSN, credit cards),
auth headers (Authorization: Bearer ...), private keys, biometric data

Common Logging Libraries

// syslog(3) — POSIX standard
#include <syslog.h>

openlog("myapp", LOG_PID | LOG_NDELAY, LOG_LOCAL6);
syslog(LOG_INFO, "user %s authenticated from %s", username, source_ip);
closelog();
						
import logging
import json

logger = logging.getLogger("auth-api")
handler = logging.StreamHandler()
formatter = logging.Formatter(
    '{"timestamp":"%(asctime)s","severity":"%(levelname)s",'
    '"service":"auth-api","message":%(message)s}'
)
handler.setFormatter(formatter)
logger.addHandler(handler)

logger.info(json.dumps({
    "action": "login",
    "user_id": "jdoe",
    "source_ip": "192.168.1.100",
    "result": "success"
}))

Log Integrity

Forward Sealing with journald

Already covered above. The principle: once a log entry is sealed, any subsequent modification is detectable. Combine with an offline verification key stored on a different system.

Write-Once Storage

For high-assurance environments, forward logs to write-once storage:

# rsyslog → remote server that appends to WORM filesystem
# ZFS snapshot with readonly flag prevents tampering
zfs snapshot tank/logs@hourly-$(date +%Y%m%d-%H%M)
zfs set readonly=on tank/logs

# Or use a dedicated log server that immediately forwards to S3 with object lock
aws s3 cp /var/log/audit/audit.log s3://log-archive/ \
    --storage-class DEEP_ARCHIVE \
    --object-lock-mode GOVERNANCE \
    --object-lock-retain-until-date 2036-06-26

Log Retention

Tier Retention Storage Purpose
Hot 7-30 days SSD, local Active investigation, dashboards
Warm 3-12 months HDD, NAS Retrospective hunting
Cold 1-7 years Object storage, tape Compliance, legal hold
Frozen 7+ years Offline tape, Glacier Regulatory minimums

Retention is dictated by regulatory frameworks ( PCI -DSS: 1 year, H IP AA: 6 years, GDPR: "no longer than necessary"). Over-retention is a legal liability - if you don't have it, you can't be compelled to produce it.

Detection Examples

Brute Force Detection via journald

# Count failed SSH attempts per IP in the last hour
journalctl -u sshd --since "1 hour ago" | \
    grep "Failed password" | \
    awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head -20

# Monitor for sudo failures
journalctl _COMM=sudo --since "1 hour ago" | grep "incorrect password"

Suspicious Process Execution via auditd

# Find execve calls from /tmp or /dev/shm (common malware staging)
ausearch -k process_execution --raw | \
    grep 'type=EXECVE' | \
    grep -E 'a[0-9]+="/tmp/|a[0-9]+="/dev/shm/' | \
    ausearch --format interpret

# Detect reverse shells — processes with /bin/sh and socket in argv
ausearch -k process_execution | grep -E "bash -i|nc -e|/dev/tcp"
