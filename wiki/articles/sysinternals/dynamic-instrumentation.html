Dynamic Instrumentation

Runtime code modification techniques including function hooking, trampolines, detours, dynamic binary instrumentation, LD_PRELOAD, PLT/GOT overwriting, and ptrace-based syscall hooking.

Overview

Dynamic instrumentation is the art of modifying running code. Instead of compiling instrumentation into a binary (static instrumentation), dynamic techniques intercept, rewrite, or redirect execution at runtime without requiring source code or recompilation. This covers function hooking, binary translation frameworks, user-space probes, LD_PRELOAD shims, and advanced techniques like return-oriented hooking and GOT table overwriting.

1. Dynamic vs Static Instrumentation

Static Instrumentation:
  Source code → add probes → recompile → new binary
  Examples: -finstrument-functions, DTrace USDT, LTTng-UST tracepoints

Dynamic Instrumentation:
  Running binary → attach probe → intercept at runtime
  Examples: kprobes, uprobes, Frida, LD_PRELOAD, ptrace

┌─────────────────────────────────────────────────────────────┐
│                     Instrumentation Spectrum                  │
│                                                               │
│  Static ◄──────────────────────────────────────────► Dynamic │
│                                                               │
│  Source  Recompiled  USDT    uprobe    Frida    ptrace       │
│  compile with -g   probes  (kernel)  (userspace) (syscall)  │
│  -finstrument-functions     eBPF       hooking    hooking   │

│  Requires source ◄──────────────────────────► No source needed │
│  Production safe ◄──────────────────────────► Risky/detectable │

2. Function Interception

At the assembly level, intercepting a function means redirecting its execution flow before (or instead of) its original body.

Original function:
  target_func:
    55             push   rbp
    48 89 e5       mov    rbp, rsp
    ...
    c3             ret

After prologue overwrite (trampoline):
  target_func:
    e9 XX XX XX XX jmp    hook_func    ← 5-byte relative jmp
    ...                                ← original code relocated
    e9 XX XX XX XX jmp    target_func+5
    ...
    c3             ret

  hook_func:
    ... log/pre-process ...
    call trampoline  → relocated original code
    ... post-process ...
    ret

The trampoline technique requires: 1. Save the first 5+ bytes of the target function 1. Overwrite them with a jmp to the hook function 1. The hook function calls a trampoline that executes the saved bytes, then jumps back 1. This preserves the original function semantics while intercepting every call

2.1 Instruction Boundary Problem

x86 instructions are variable-length (1-15 bytes). You cannot overwrite the middle of an instruction:

BAD: overwrite 5 bytes starting mid-instruction
  target_func:
    48 89 e5       mov    rbp, rsp    ← 3 bytes
    48 83 ec 10    sub    rsp, 0x10   ← 4 bytes
    5-byte overwrite would split this instruction → CRASH

GOOD: use a disassembler to find instruction boundaries
  Overwrite the first 5 bytes (full instructions):
    48 89 e5       mov    rbp, rsp    ← 3 bytes
    48 83 ec 10    sub    rsp, 0x10   ← 4 bytes ... need 7 bytes total
  Solution: relocate first N bytes where N >= 5 and N ends on instruction boundary

This is why hooking libraries (Detours, MinHook, mhook) use length disassemblers like HDE (Hacker Disassembler Engine) or Zydis.

3. Binary Instrumentation Frameworks

These frameworks operate at the instruction level, inserting instrumentation between any arbitrary instructions.

3.1 Pin (Intel)

Pin Architecture:
  Application binary
       │
       ▼
  ┌─────────────┐
  │ Pin (loader) │   loads app into Pin VM
  └──────+──────┘
         │
         ▼
  ┌─────────────┐
  │ JIT Compiler │   translates app code basic block by basic block
  │ (Code Cache) │   inserting instrumentation calls
  └──────+──────┘
         │
         ▼
  ┌─────────────┐
  │ Pin Tool     │   user-written .so plugin (C++)
  │ (Pintool)    │   defines instrumentation and analysis routines
  └─────────────┘
						
// Example Pin tool: count instructions
#include "pin.H"
#include <iostream>

UINT64 icount = 0;

VOID docount() { icount++; }

VOID Instruction(INS ins, VOID *v) {
    INS_InsertCall(ins, IPOINT_BEFORE, (AFUNPTR)docount, IARG_END);
}

VOID Fini(INT32 code, VOID *v) {
    std::cout << "Executed " << icount << " instructions" << std::endl;
}

int main(int argc, char *argv[]) {
    PIN_Init(argc, argv);
    INS_AddInstrumentFunction(Instruction, 0);
    PIN_AddFiniFunction(Fini, 0);
    PIN_StartProgram();
    return 0;
}
						
# Build and run
pin -t obj-ia32/inscount.so -- /bin/ls

3.2 DynamoRIO

DynamoRIO is the open-source alternative to Pin. It uses a similar code cache / basic block translation approach:

DynamoRIO Architecture:
  Application → DynamoRIO Code Cache → Executed basic blocks
                     │
                     ▼
              Client (plugin .so)
              - dr_insert_clean_call() for instrumentation
              - drwrap_wrap() for function wrapping
						
// DynamoRIO client: count basic blocks
#include "dr_api.h"
#include "drmgr.h"

static void event_bb(void *drcontext, void *tag, instrlist_t *bb,
                     bool for_trace, bool translating) {

        (void *)inc_counter, false, 0);
}

DR_EXPORT void dr_client_main(client_id_t id, int argc, const char *argv[]) {
    drmgr_init();
    drmgr_register_bb_instrumentation_event(NULL, event_bb, NULL);

4. User-Space Probes (uprobes)

uprobes are the kernel's built-in mechanism for dynamic instrumenting user-space functions. They work by the same int3 replacement as kprobes.

uprobe mechanism:
  1. User specifies: /path/to/binary:symbol or binary:offset
  2. Kernel finds the inode and offset
  3. Kernel writes int3 at that offset in the process's text mapping
  4. When process hits int3:
     → trap to kernel
     → uprobe handler fires
     → original instruction single-stepped
     → process resumes

Key detail: uprobes work at the VMA (page) level.
All processes sharing the same inode+offset share the same uprobe.

4.1 Uprobe with eBPF

// trace_readline.bpf.c — trace bash readline calls
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} events SEC(".maps");

SEC("uretprobe//bin/bash:readline")
int trace_readline(struct pt_regs *ctx) {
    char *line = (char *)PT_REGS_RC(ctx);  // Return value = read line
    if (!line) return 0;

    char buf[256];
    long len = bpf_probe_read_user_str(buf, sizeof(buf), line);
    if (len > 0) {
        char *evt = bpf_ringbuf_reserve(&events, sizeof(buf), 0);
        if (evt) {
            __builtin_memcpy(evt, buf, len);
            bpf_ringbuf_submit(evt, 0);
        }
    }
    return 0;
}

5.2 Frida JavaScript API

// hook.js — hook open() to log file accesses
const openPtr = Module.findExportByName(null, 'open');
const open = new NativeFunction(openPtr, 'int', ['pointer', 'int']);

Interceptor.attach(openPtr, {
    onEnter(args) {
        this.filename = Memory.readCString(args[0]);
        this.flags = args[1].toInt32();
        console.log(`open(${this.filename}, 0x${this.flags.toString(16)})`);
    },
    onLeave(retval) {
        console.log(`  → returned fd=${retval.toInt32()}`);
    }
});

// Hook a function by parsing its address
const funcAddr = DebugSymbol.fromName('target_function');
Interceptor.attach(funcAddr, {
    onEnter(args) {
        console.log(`target_function(${args[0]}, ${args[1]}) called from:\n` +
            Thread.backtrace(this.context, Backtracer.ACCURATE)
                .map(DebugSymbol.fromAddress).join('\n'));
    }
});

// Modify function arguments
Interceptor.attach(Module.findExportByName(null, 'connect'), {
    onEnter(args) {
        // Block connections to 127.0.0.1:8080
        const sa = args[1];
        const family = sa.readU16();
        if (family === 2) {               // AF_INET
            const ip = sa.add(4).readByteArray(4);
            const port = sa.add(2).readU16();
            console.log(`connect: ${Array.from(new Uint8Array(ip)).join('.')}:${port}`);
            // Could overwrite sa to redirect
        }
    }
});

// Replace function entirely
Interceptor.replace(Module.findExportByName(null, 'getuid'),
    new NativeCallback(() => 0, 'int', []));

6. LD_PRELOAD Based Hooking

The simplest form of user-space hooking: override library functions by preloading a shared library that exports the same symbols.

LD_PRELOAD mechanism:
  Normal linking order:
    libc.so → malloc, free, open, read, write

  With LD_PRELOAD:
    hook.so → malloc, free, open, read, write (override versions)
    libc.so → (used as fallback)

  At link time: the dynamic linker resolves symbols from LD_PRELOAD first.
  Any function in LD_PRELOAD shadows the same symbol in libc.

6.1 Example: Hook malloc and free

// malloc_hook.c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>
#include <unistd.h>

void *malloc(size_t size) {
    static void *(*real_malloc)(size_t) = NULL;
    if (!real_malloc)
        real_malloc = dlsym(RTLD_NEXT, "malloc");

    void *ptr = real_malloc(size);
    fprintf(stderr, "malloc(%zu) = %p\n", size, ptr);
    return ptr;
}

void free(void *ptr) {
    static void (*real_free)(void *) = NULL;
    if (!real_free)
        real_free = dlsym(RTLD_NEXT, "free");

    fprintf(stderr, "free(%p)\n", ptr);
    real_free(ptr);
}
						
# Compile as shared library
gcc -shared -fPIC malloc_hook.c -o hook.so -ldl

# Use it
LD_PRELOAD=./hook.so ls
LD_PRELOAD=./hook.so ./myapp

# Check that the hook is loaded
LD_PRELOAD=./hook.so env | grep LD_PRELOAD

6.2 LD_PRELOAD Limitations

Limitation Explanation
Static binaries No dynamic linker - LD_PRELOAD has no effect
Setuid binaries Dynamic linker ignores LD_PRELOAD for security
Internal calls libc internally calls __libc_malloc directly - bypasses hook
Syscall bypass Process doing raw syscall (no libc) - LD_PRELOAD useless
Stripping protection RTLD_NEXT requires libdl to find the real symbol
Security checks /etc/ld.so.preload for system-wide, apparmor/SELinux can block

7. Hot Patching Concepts

Linux kernel modules use a technique called "hot patching" where running kernel functions are replaced at runtime.

Kernel hot patching (ftrace-based):
  1. Build kernel with -fpatchable-function-entry=5
  2. Each function starts with 5-byte NOP
  3. At patch time: NOP → call ftrace_regs_caller
  4. ftrace_regs_caller:
       Save all registers in pt_regs
       Call registered callbacks
       Call the replacement function (if any)
       Restore registers
       Return (if replacement handled it) or continue original

The __mcount_loc section:
  - Contains a table of all function entry addresses
  - Used by ftrace to find and patch NOPs
  - Readable via: objdump -j __mcount_loc vmlinux
						
__mcount_loc layout in vmlinux:
  ┌──────────────────────┐
  │ .text                 │  ... functions ...
  ├──────────────────────┤
  │ __mcount_loc          │
  │ [0] = .text + 0x100  │  address of function_1 entry
  │ [1] = .text + 0x240  │  address of function_2 entry
  │ [2] = .text + 0x398  │  address of function_3 entry
  │ ...                   │
  └──────────────────────┘

8. Syscall Hooking

Hooking at the syscall level catches everything that crosses the kernel boundary.

8.1 ptrace

// ptrace_based_syscall_hook.c — intercept syscalls
#include <sys/ptrace.h>
#include <sys/wait.h>
#include <sys/user.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    pid_t child = fork();

    if (child == 0) {
        ptrace(PTRACE_TRACEME, 0, NULL, NULL);
        kill(getpid(), SIGSTOP);
        execl("/bin/ls", "ls", NULL);
        return 0;
    }

    int status;
    waitpid(child, &status, 0);

    ptrace(PTRACE_SETOPTIONS, child, 0,
           PTRACE_O_TRACESYSGOOD);

    while (1) {
        // Wait for syscall entry
        ptrace(PTRACE_SYSCALL, child, NULL, NULL);
        waitpid(child, &status, 0);
        if (WIFEXITED(status)) break;

        // Read syscall number (x86-64: orig_rax)
        struct user_regs_struct regs;
        ptrace(PTRACE_GETREGS, child, NULL, &regs);
        printf("Syscall enter: %llu\n", regs.orig_rax);

        // Continue to syscall exit
        ptrace(PTRACE_SYSCALL, child, NULL, NULL);
        waitpid(child, &status, 0);

        // Read return value
        ptrace(PTRACE_GETREGS, child, NULL, &regs);
        printf("Syscall exit: %llu → %lld\n", regs.orig_rax, regs.rax);
    }
    return 0;
}

./ptrace_hook

8.2 seccomp Notify

Linux 5.0+ provides SECCOMP_RET_USER_NOTIF - the kernel pauses a syscall and notifies a supervisor process, which can inspect arguments and decide on the outcome.

// seccomp_notify.c — supervisor intercepts syscalls
#include <linux/seccomp.h>
#include <linux/filter.h>
#include <sys/ioctl.h>
#include <sys/prctl.h>
#include <sys/mman.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    // Setup seccomp filter to notify on openat
    struct sock_filter filter[] = {
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
                 offsetof(struct seccomp_data, nr)),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_openat, 0, 1),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_USER_NOTIF),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
    };

    struct sock_fprog prog = {
        .len = sizeof(filter) / sizeof(filter[0]),
        .filter = filter,
    };

    int listener_fd = -1;

    // Fork: child runs filtered, parent is supervisor
    pid_t child = fork();
    if (child == 0) {
        prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
        prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog);

        // Create a notification fd pair
        int fds[2];
        pipe(fds);
        listener_fd = fds[0];

        prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog);
        // ... execute target ...
    }

    // Parent: receive seccomp notifications and decide
    // (requires ioctl(SECCOMP_IOCTL_NOTIF_RECV) on listener_fd)
    // ...
}

8.3 KRSI (BPF LSM) for syscall hooking

eBPF LSM programs can hook security-sensitive operations including the bpf() syscall itself:

SEC("lsm/bpf")
int BPF_PROG(restrict_bpf, int cmd, union bpf_attr *attr, unsigned int size, int ret) {
    // Block BPF map creation for unauthorized processes
    if (cmd == BPF_MAP_CREATE) {
        u32 uid = bpf_get_current_uid_gid();
        if (uid != 0) return -EPERM;
    }
    return 0;
}

9. PLT/GOT Hooking

The PLT (Procedure Linkage Table) and GOT (Global Offset Table) are the dynamic linker's mechanism for lazy symbol resolution.

Normal PLT flow:
  Call puts@plt:
    → PLT[puts]:
        jmp *GOT[puts]            ← initially points to next instruction
        push $puts_got_index     ← push resolver args
        jmp PLT[0]               ← call dynamic linker resolver
    → Resolver: _dl_runtime_resolve()
    → GOT[puts] updated with actual libc puts address
    → jmp *GOT[puts] now goes directly to libc puts

GOT hooking:
  Overwrite GOT[puts] with hook_puts address:
    → All future calls to puts → hook_puts
    → hook_puts can call real puts via saved original address

10. Return-Oriented Hooking

When writable code regions are unavailable (NX enforced, no W+X pages), attackers and red-teamers find "unused" code bytes to construct trampolines.

Finding gadgets:
  Look for sequences of bytes in executable pages that decode to
  useful instructions when execution starts at a different offset.

  Example:
  Original:  89 d8          mov eax, ebx
              ff e0          jmp eax

  Gadget:    d8 ff           ... (could decode as something useful)
             e0 ...          when instruction pointer starts at d8

  ROPgadget and Ropper tools find these:
  $ ROPgadget --binary /bin/bash | head -20

This technique relies on code reuse rather than code injection.

11. Anti-Instrumentation

Every instrumentation technique leaves traces. Adversaries check for them.

Technique Detection Method
ptrace ptrace(PTRACE_TRACEME) fails if already traced; /proc/PID/status TracerPid != 0
LD_PRELOAD Check LD_PRELOAD in /proc/PID/environ; inspect /proc/PID/maps for unexpected libraries
Frida Check for frida-server process; look for linjector or frida-agent in /proc/PID/maps
GOT hooking Compare GOT entries against known libc addresses; checksum .got.plt section
Inline hook Compare function prologue bytes against known-good; memcmp(original_bytes, 5)
uprobe Check /sys/kernel/debug/tracing/uprobe_events
seccomp Check /proc/PID/status for Seccomp mode; prctl(PR_GET_SECCOMP)
eBPF Check loaded programs: bpftool prog list
DynamoRIO/Pin Check /proc/PID/maps for framework library
Breakpoints int3 (0xCC) in prologue; software breakpoint scan

objdump -d /bin/ls | grep '@plt>' | head -10
readelf -r /bin/ls | grep JUMP_SLOT | head -10

# 11. Find ROP gadgets in a binary
ROPgadget --binary /bin/ls 2>/dev/null | head -15 || echo "Install ROPgadget"

# 12. Verify no existing probes
sudo perf probe --list 2>/dev/null
