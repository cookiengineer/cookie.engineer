Least Privilege

Designing systems so processes and users operate with the minimum permissions necessary for their function.

Overview

A subject (user, process, or service) should hold exactly the permissions required to do its job and nothing more. This article audits the places where Linux hands out extra privilege: sudo rules, file capabilities, service accounts, POSIX ACL s, polkit, and filesystem permissions. After reading you can inspect each boundary, explain why it is dangerous, and reduce it to a minimal grant.

Required Reading

  • Unix Permissions - user/group/other, setuid, setgid, sticky bit
  • Capabilities - Linux capabilities, bounding sets, ambient sets
  • Authorization - authorization models, RBAC , ABAC, MAC

Concept

Least privilege means a subject (user, process, service) has exactly the permissions it needs to perform its function, and nothing more. No "just in case" access. No "it worked during development so we kept it." Every permission must be justified by a current operational requirement.

The failure mode of least privilege is not that it prevents functionality. It is that lazy administrators grant broad access rather than diagnosing exactly what is needed. The correct approach: enable audit logging for the failing operation, read the log to identify the denied permission, then grant only that specific permission.

Sudo Configuration

Sudo is the most pervasively misconfigured privilege escalation mechanism on Linux systems. The common ALL=(ALL:ALL) ALL rule grants every command as every user. This is a root shell with extra steps.

Sudoers Architecture

The main configuration lives in /etc/sudoers , but modern systems should use drop-in files in /etc/sudoers.d/ . On ArchLinux the default sudo package already includes the #includedir directive.

# Always use visudo to edit — it validates syntax before saving
sudo visudo -f /etc/sudoers.d/web-team

Principle: Command-Level Restrictions

Never grant open-ended command access. Specify the exact binary with exact arguments:

# WRONG — user can run any command as root
alice ALL=(ALL:ALL) ALL

# BAD — user can run systemctl restart anything
alice ALL=(root) /usr/bin/systemctl restart *

# CORRECT — only restart specific services
alice ALL=(root) /usr/bin/systemctl restart nginx
alice ALL=(root) /usr/bin/systemctl restart php-fpm

Sudoedit Without Shell Access

Granting vim , nano , or any editor via sudo gives the user a shell (all editors can execute shell commands). Use sudoedit instead:

# CORRECT — edit specific config files without shell
alice ALL=(root) sudoedit /etc/nginx/sites-available/*
alice ALL=(root) sudoedit /etc/nginx/conf.d/*

sudoedit copies the file to a temporary location owned by the invoking user, runs the user's $EDITOR as the user (not root), and copies back on save. No root shell is ever accessible.

Commands Never to Grant via Sudo

These commands can be trivially exploited to gain a root shell:

  • Editors : vim , nano , emacs , ed , ex - all have shell escapes ( :shell , !bash )
  • Pagers : less , more , most - !bash from within pager
  • Shells : bash , sh , zsh , dash - obviously
  • Script interpreters : python , perl , ruby , php , lua , node
  • File tools : cat , head , tail - can read any file (leak /etc/shadow )
  • Package managers : apt , pacman , yum - can install arbitrary packages
  • Service managers : systemctl with no argument restriction - can start arbitrary units
  • Compressors : tar with wildcards - can trigger path traversal
  • 'find' with '-exec' - arbitrary command execution
  • 'awk' with 'system()' - arbitrary command execution

Sudo Debugging and Auditing

# Test which commands a user can run
sudo -l -U alice

# Sudo logs all commands by default to journalctl
sudo journalctl -u sudo -f

# Enable detailed sudo logging (in sudoers):
Defaults log_input, log_output
Defaults iolog_dir=/var/log/sudo-io/%{user}

Linux Capabilities

Capabilities split the monolithic root privilege into discrete units. Instead of running a process as root to bind port 80, grant only CAP_NET_BIND_SERVICE .

Key Capabilities

Capability Allows Abuse Potential
CAP_SYS_ADMIN Near-root (mount, namespace, swapon) Extreme
CAP_SYS_PTRACE Debug arbitrary processes High (read memory)
CAP_SYS_MODULE Load kernel modules Extreme (ring 0)
CAP_NET_RAW Raw sockets, packet injection High
CAP_NET_ADMIN Interface config, firewall High
CAP_SYSLOG Read kernel log buffer Medium (info leak)
CAP_DAC_OVERRIDE Bypass file permissions High
CAP_DAC_READ_SEARCH Bypass file read/search perms Medium
CAP_CHOWN Change file ownership Medium
CAP_SETUID Set arbitrary UID Extreme
CAP_SETGID Set arbitrary GID Medium
CAP_NET_BIND_SERVICE Bind ports < 1024 Low
CAP_KILL Signal any process Medium
CAP_FOWNER Bypass file owner checks Medium

Querying and Setting Capabilities

# Check capabilities of a running process
getpcaps $(pgrep nginx)

# Decode capability masks
capsh --decode=0000000000003000

# Set capabilities on a binary (alternative to setuid root)
sudo setcap 'cap_net_bind_service=+ep' /usr/bin/my-server

# List all files with capabilities set
sudo getcap -r / 2>/dev/null

# Remove unnecessary capabilities
sudo setcap -r /usr/bin/some-binary

Capability Sets Explained

effective (e):  Currently active for the process
permitted (p):  Can be made effective (upper bound)
inheritable (i): Pass through execve()
bounding (b):   Hard limit — cannot be added back
ambient (a):    Preserved through execve() for non-SUID binaries

For a binary with cap_net_bind_service=+ep :

  • +e means the capability is in the effective set (active now).
  • +p means it is in the permitted set (can be re-enabled after it is dropped).
  • Both are added to the binary's file-based capability set.

Example: Capability-Aware Service

Instead of running as root to bind port 80, grant only the bind capability:

sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/web-server

And in the systemd unit:

[Service]
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=yes

Service Accounts

Every service must have a dedicated user account with minimal permissions:

# Create a system user — no login, no home directory, no shell
sudo useradd -r -M -s /usr/sbin/nologin \
  -c "My Application Service" \
  -d /var/lib/myapp \
  myapp

# Restrict the service directory
sudo chown -R myapp:myapp /var/lib/myapp
sudo chmod 750 /var/lib/myapp

# Verify the account
sudo passwd -S myapp    # Should show "L" (locked)
sudo chage -l myapp     # Check password aging

ACLs - Granular File Permissions

Linux ACL s extend the traditional owner/group/other model with per-user and per-group rules.

# Install ACL tools
sudo pacman -S acl

# Grant specific user read access to a protected directory
sudo setfacl -m u:alice:rx /var/log/myapp

# Grant specific group write access
sudo setfacl -m g:dev-team:rw /srv/shared

# View ACLs
getfacl /var/log/myapp

# Remove a specific ACL entry
sudo setfacl -x u:alice /var/log/myapp

# Set default ACLs on a directory (inherited by new files)
sudo setfacl -m d:g:dev-team:rwx /srv/shared

Verify filesystem supports ACL s:

# Check mount options — should not show "noacl"
mount | grep "$(df /path --output=source | tail -1)"

Privilege Boundaries

A privilege boundary is any interface where a lower-privilege subject interacts with a higher-privilege one. Each boundary must be explicitly reviewed:

[ Internet ] → [ Nginx (nginx user) ] → [ App (app user) ] → [ DB (postgres) ]
                    ↑                         ↑                    ↑
              Boundary 1                  Boundary 2           Boundary 3

Boundary 1 (Nginx -> Internet) : Validate request size, rate-limit, drop malformed HTTP .

Boundary 2 (App -> Nginx) : Unix socket with restricted permissions. App user cannot write to Nginx's config or cache.

Boundary 3 (DB -> App) : App connects as a dedicated DB user with permissions only on its schema. No SUPERUSER , no CREATE DATABASE .

Polkit

Polkit controls system-wide privileges for desktop and system actions. Overly permissive polkit rules are a common privilege escalation vector.

# List installed polkit actions
pkaction --verbose

# Check polkit rules
ls /usr/share/polkit-1/rules.d/
ls /etc/polkit-1/rules.d/

# Example restrictive rule — only wheel group can manage systemd units
						
// /etc/polkit-1/rules.d/99-restrict-systemd.rules
polkit.addRule(function(action, subject) {
    if (action.id.indexOf("org.freedesktop.systemd1.manage-unit") === 0) {
        if (subject.isInGroup("wheel")) {
            return polkit.Result.YES;
        }
        return polkit.Result.AUTH_ADMIN;
    }
});

Filesystem Permission Review

Run a comprehensive permissions audit periodically:

#!/bin/bash
# perms-audit.sh — find permission anomalies

echo "=== World-writable files ==="
find / -xdev -type f -perm -002 ! -type l 2>/dev/null | \
  grep -vE '^/(proc|sys|dev)'

echo "=== World-writable directories ==="
find / -xdev -type d -perm -002 2>/dev/null | \
  grep -vE '^/(proc|sys|dev)'

echo "=== Files not owned by any package ==="
pacman -Qo $(find /usr/bin /usr/lib /usr/sbin -type f 2>/dev/null) 2>&1 | \
  grep -i 'no package owns'

echo "=== SUID/SGID files ==="
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null

echo "=== User accounts with a login shell ==="
awk -F: '$7 !~ /(nologin|false)$/ {print $1, $7}' /etc/passwd

Detection Rules

# Sigma rule — New Service Account Created
title: New System Service Account Created
status: experimental
logsource:
  category: process_creation
  product: linux
detection:
  selection:
    Image|endswith: '/useradd'
    CommandLine|contains: '-r'
  condition: selection
---
# Auditd rule — monitor sudoers changes
-w /etc/sudoers -p wa -k sudoers_change
-w /etc/sudoers.d/ -p wa -k sudoers_change
-w /etc/security/ -p wa -k pam_config_change

# Auditd rule — monitor capability changes on binaries
-w /usr/bin/ -p x -k binary_capability_check
-a always,exit -F arch=b64 -S capset -k capability_change
