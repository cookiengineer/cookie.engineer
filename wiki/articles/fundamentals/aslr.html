ASLR - Address Space Randomization

How ASLR randomizes stack, heap, mmap, and executable base addresses per execution, its entropy limits, kernel configuration, and bypass techniques.

Overview

Without ASLR, every run of a program places its stack, heap, shared libraries, and (for non-PIE binaries) its code at predictable addresses, so a single leaked address reveals the whole layout. ASLR randomizes those bases per execution, forcing an attacker to obtain an information leak first. This article explains which regions are randomized, how much entropy each receives on x86-64, how the randomize_va_space sysctl controls it, and the leak and brute-force techniques used to bypass it.

  • Virtual Memory - virtual address space layout, page tables, mmap allocation
  • ELF - ELF loader, segments, program headers, base address
  • Dynamic Linking - how shared libraries are loaded

The Problem ASLR Solves

Without ASLR, every execution of a program maps its memory regions at identical, predictable virtual addresses. A standard 64-bit ELF executable loads at 0x400000 . The heap starts just after the BSS segment. Shared libraries load at deterministic offsets from 0x7ffff7ff5000 . The stack starts at a fixed high address (near 0x7ffffffff000 ).

This determinism means an exploit developed on the attacker's system works identically on the target - offsets, addresses, and layout are known in advance. A single leak of the binary format is a complete exploit blueprint.

ASLR introduces per-execution randomization: each time a process starts, its key memory regions

  • the stack, heap, mmap area (shared libraries), and (with PIE) the executable itself -
are placed at random offsets from their typical base addresses. The attacker can no longer hardcode addresses. A leaked address from one run is useless on the next.

What Gets Randomized

Memory region Randomized? Entropy (x86-64) Notes
Stack base Yes 22 bits Randomized at execve()
Heap base (brk) Yes 13 bits Randomized at first brk()
mmap base (libs, anon) Yes 28 bits Randomized at first mmap()
Executable base With PIE only 28 bits Non-PIE binaries load at fixed 0x400000
vDSO Yes 28 bits Kernel-provided shared object
vvar Fixed near vDSO 11 bits Kernel data page, adjacent to vDSO
TLS (Thread-Local Storage) Partial ~18 bits Via arch_prctl(ARCH_SET_FS)

The entropy numbers represent the number of bits that vary between runs. With 28 bits of entropy, the mmap base can land in any of 2^28~ 268 million possible positions. On a 4 KiB page-aligned address space, this means 28 bits of randomness in the upper address bits.

The randomize_va_space Knob

Linux exposes ASLR control via a single sysctl:

cat /proc/sys/kernel/randomize_va_space
Value Name Behavior
0 Disabled No randomization anywhere. All addresses fixed across runs.
1 Conservative Randomize stack, mmap, vDSO. Executables (even PIE) not randomized.
2 Full Randomize everything plus heap (brk area).Default on all modern distros.

The value is set early in kernel initialization (in arch/x86/kernel/process.c ) and can be changed at runtime (affects new processes, not existing ones): 

# Check current setting
sysctl kernel.randomize_va_space
# kernel.randomize_va_space = 2

# Disable ASLR (for debugging/learning)
echo 0 | sudo tee /proc/sys/kernel/randomize_va_space

# Re-enable full ASLR
echo 2 | sudo tee /proc/sys/kernel/randomize_va_space

# Make it persistent across reboots
echo "kernel.randomize_va_space = 2" | sudo tee /etc/sysctl.d/99-aslr.conf

On ArchLinux, the default /usr/lib/sysctl.d/50-default.conf sets this to 2.

How the Kernel Implements ASLR

ASLR is implemented across several kernel subsystems. The randomization happens at different points depending on the region:

Stack randomization - arch/x86/kernel/process.c:arch_align_stack() : The stack pointer is randomized when a new process starts (in load_elf_binary ). The kernel computes a random offset (up to 8 MiB on 32-bit and about 16 GiB on 64-bit, controlled by STACK_RND_MASK ) and subtracts it from the initial stack pointer. This shifts the entire stack region down by that random amount. 

// Simplified kernel logic for stack randomization
// From fs/binfmt_elf.c:randomize_stack_top()
unsigned long randomize_stack_top(unsigned long stack_top)
{
    unsigned long random_variable = get_random_long();
    // ARCH_STACK_RND_MASK = 0x3fffff on x86-64 (22 bits)
    random_variable &= STACK_RND_MASK;
    random_variable <<= PAGE_SHIFT;  // page-align the offset
    return stack_top - random_variable;
}

mmap randomization - arch/x86/mm/mmap.c:arch_mmap_rnd() : The mmap base address (where shared libraries and anonymous mappings are placed) is randomized using a larger entropy pool: 

// From arch/x86/mm/mmap.c
unsigned long arch_mmap_rnd(void)
{
    unsigned long rnd;
    // For 64-bit: 28 bits of entropy (CONFIG_ARCH_MMAP_RND_BITS=28)
    // For 32-bit: 8 bits
    rnd = get_random_long() & ((1UL << mmap_rnd_bits) - 1);
    return rnd << PAGE_SHIFT;
}

Heap (brk) randomization - arch/x86/kernel/process.c : The brk base (initial program break, where the heap starts) is offset from the end of the data segment: 

// The brk random offset is computed in arch_randomize_brk()
unsigned long arch_randomize_brk(struct mm_struct *mm)
{
    // On x86-64: 13 bits (32 MiB maximum shift on 4K pages)
    unsigned long rnd = get_random_long() & 0x1fff;
    return mm->brk + (rnd << PAGE_SHIFT);
}

Executable randomization requires PIE (Position-Independent Executable) - the binary must be compiled as ET_DYN and loaded by mmap rather than at a fixed address. See PIE .

vDSO randomization: The kernel maps its virtual dynamic shared object (linux-vdso.so.1) into each process. On x86-64, the vDSO is randomized alongside the mmap region, since it's mapped via arch_setup_additional_pages -> get_unmapped_area which respects the mmap randomization offset.

The Randomization Budget

The amount of entropy available for randomization depends on the size of the virtual address space for that region and architectural constraints:

x86-64 Address Space Layout

0x0000000000000000 ─────────────────────── NULL / unmapped guard
0x0000000000400000 ──┐ 
                     │ ~47 bits of user address space
0x00007fffffffffff ──┘ 
                     ── non-canonical hole (not addressable)
0xffff800000000000 ──┐
                     │ Kernel space
0xffffffffffffffff ──┘

Within the user portion:

0x0000000000400000 — 0x0000000000ffffff   Text/Data (non-PIE at 0x400000 fix)
0x0000000001000000 — 0x00007f7fffffff     Heap + mmap region (~48 TiB)
0x00007f8000000000 — 0x00007fffffffffff   Stack + mmap region (~512 GiB)
0x00007fffffffffff                         Stack top

The mmap region on x86-64 uses approximately 28 bits of entropy. The stack uses 22 bits. Why the difference? The stack must be adjacent to the top of user space and grow downward - its randomization range is constrained by the fixed STACK_TOP_MAX and the need to not collide with the mmap region. The mmap region has a larger address range to work with.

Verifying ASLR: Before and After

This program prints the addresses of key memory regions on each run:

// aslr_demo.c — observe ASLR in action
// Compile: gcc -o aslr_demo aslr_demo.c
// Run multiple times: for i in $(seq 1 5); do ./aslr_demo; echo "---"; done

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/mman.h>

// External symbols provided by the linker
extern char **environ;
extern char etext, edata, end;

int global_var = 0x41424344;  // initialized data (.data)
int bss_var;                    // uninitialized data (.bss)

void print_addr(const char *label, void *addr) {
    printf("%-24s %p\n", label, addr);
}

int main(int argc, char **argv) {
    int stack_var = 0;
    void *heap_ptr = malloc(64);
    void *mmap_ptr = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                          MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    void *libc_addr = dlsym(RTLD_NEXT, "printf");

    print_addr("main (code)",                 (void *)main);
    print_addr("global_var (.data)",          &global_var);
    print_addr("bss_var (.bss)",              &bss_var);
    print_addr("stack_var (stack)",           &stack_var);
    print_addr("heap_ptr (heap)",             heap_ptr);
    print_addr("mmap_ptr (mmap anon)",        mmap_ptr);
    print_addr("libc printf (mmap libs)",     libc_addr);
    print_addr("argv (stack)",                argv);
    print_addr("environ (stack)",             environ);

    // Print ASLR setting
    FILE *f = fopen("/proc/sys/kernel/randomize_va_space", "r");
    if (f) {
        int val;
        fscanf(f, "%d", &val);
        printf("\n%-24s %d\n", "randomize_va_space", val);
        fclose(f);
    }

    free(heap_ptr);
    munmap(mmap_ptr, 4096);
    return 0;
}

Compile and run:

gcc -o aslr_demo aslr_demo.c -ldl -no-pie  # -no-pie to see fixed code address

# With ASLR enabled:
for i in $(seq 1 3); do ./aslr_demo; echo "---"; done
# Observe: stack, heap, mmap, libc addresses CHANGE each run
# Observe: main, global_var, bss_var at FIXED addresses (non-PIE)

# Disable ASLR:
echo 0 | sudo tee /proc/sys/kernel/randomize_va_space
for i in $(seq 1 3); do ./aslr_demo; echo "---"; done
# Observe: ALL addresses remain IDENTICAL across runs

# Re-enable:
echo 2 | sudo tee /proc/sys/kernel/randomize_va_space

ASLR and PIE: The Missing Piece

Non-PIE executables load at a fixed base address - typically 0x400000 on x86-64. Even with ASLR at level 2, the main binary's .text, .data, and .bss segments are at fixed positions. This means:

  • Return addresses into the main binary are predictable (any ROP gadget in the binary has a fixed address).
  • GOT entries within the binary are at known addresses.
  • Function pointers within the binary (vtables, callback arrays) are at known addresses.

PIE compiles the main executable as position-independent, allowing the kernel to randomize its base address just like any shared library. See PIE for the full mechanism.

Checking if a binary is PIE

readelf -h /bin/ls | grep Type
# Type: DYN (Shared object file)  ← PIE (ASLR-randomized base)
# Type: EXEC (Executable file)    ← Non-PIE (fixed base 0x400000)

file /bin/ls
# /bin/ls: ELF 64-bit LSB pie executable, x86-64 ...
#                               ^^^ PIE indicator

# Bulk check:
readelf -h /usr/bin/* 2>/dev/null | grep -B1 'Type:.*EXEC'
# Lists non-PIE executables — should be empty on modern Arch

ASLR Entropy Limits

32-bit entropy crisis: On 32-bit x86, the virtual address space is only 4 GiB. The mmap randomization region is constrained to about 8 bits of entropy (256 possible positions). This makes brute-force attacks viable: 

x86-32 ASLR entropy (Linux, kernel 6.x):
  Stack:   ~11 bits (2048 positions, 8 MiB range)
  mmap:    ~8 bits  (256 positions)
  Heap:    ~13 bits (8192 positions)
  Exec/PIE:~8 bits

An exploit that crashes and restarts a service can brute-force the 8-bit mmap offset in~128 attempts on average, which takes seconds on a networked service.

The PaX ASLR approach (historical): The PaX project (precursor to modern Linux ASLR) used the x86 segment registers to shuffle address spaces more aggressively, creating up to 16 bits of entropy on 32-bit. Kernel stack randomization from this line of work was later merged into mainline as CONFIG_RANDOMIZE_KSTACK_OFFSET .

64-bit resistance: With 28 bits of mmap entropy on x86-64, brute-force requires~134 million attempts on average. Coupled with the process dying on crash (no infinite retries), this is not practical for most remote exploits.

Information Leaks: The ASLR Bypass

The primary bypass for ASLR is not brute force - it's information leakage . If an attacker can leak a single address from the target's address space, they can calculate all others because:

  1. Offset relationships are constant: The distance between system() and printf() in libc is fixed (determined at compilation). Leak printf 's address, compute system 's = printf_addr - printf_offset + system_offset .
  1. Addresses within a region share the same base: All shared libraries are loaded in the mmap region with a known ordering. Leak the address of one function in libc, compute the libc base, then compute any other symbol's address.
  1. Stack/heap pointers reveal layout: A leaked stack address reveals the stack's random offset. If the stack also contains heap pointers, those reveal the heap's random offset.

Demo: leaking an address to defeat ASLR

// fmtstr_leak.c — format string vulnerability leaking addresses
// Compile: gcc -o fmtstr_leak fmtstr_leak.c -no-pie -fno-stack-protector
// Disable ASLR for demo: echo 0 | sudo tee /proc/sys/kernel/randomize_va_space

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void vuln(char *input) {
    char buf[128];
    // Vulnerable: user input passed directly as format string
    strncpy(buf, input, 127);
    buf[127] = '\0';
    printf(buf);  // ← format string bug: leaks stack contents
    printf("\n");
}

int main(int argc, char **argv) {
    if (argc < 2) {
        fprintf(stderr, "Usage: %s <format-string>\n", argv[0]);
        fprintf(stderr, "  e.g.: %s '%%p.%%p.%%p.%%p.%%p.%%p.%%p.%%p.%%p.%%p'\n", argv[0]);
        return 1;
    }
    vuln(argv[1]);
    printf("libc printf is at: %p\n", (void *)printf);
    printf("main is at:        %p\n", (void *)main);
    return 0;
}
						
gcc -o fmtstr_leak fmtstr_leak.c -no-pie -fno-stack-protector
# Run with format string that leaks stack data:
./fmtstr_leak '%p.%p.%p.%p.%p.%p.%p.%p.%p.%p.%p.%p.%p.%p.%p'
# One of these values will be a libc address. The attacker identifies it
# by looking for values in the 0x7f... range (mmap region on x86-64).

Partial Overwrites

When the attacker doesn't have a full address leak but knows some bytes, they can use partial overwrites:

Scenario: A buffer overflow overwrites a pointer. The overflow is limited - only the least significant 2 bytes are controllable. The upper bytes (already on the stack/memory from the original pointer) remain.

On x86-64, addresses are 48-bit (sign-extended from bit 47). The lower 12 bits are the page offset (fixed, known). This leaves 36 bits of actual entropy. If the attacker can overwrite 2 bytes (16 bits), they reduce uncertainty by 16 bits - a 1-in-65536 brute force per attempt, which is practical for local exploits. 

// partial_overwrite_demo.c
// Compile: gcc -o partial_overwrite partial_overwrite_demo.c -no-pie

#include <stdio.h>
#include <stdint.h>

int main(void) {
    uintptr_t addr = (uintptr_t)&main;

    printf("Full address:    0x%016lx\n", addr);
    printf("Page offset (12): 0x%03lx\n", addr & 0xFFF);   // always same
    printf("Bits 12-15:        0x%01lx\n", (addr >> 12) & 0xF);
    printf("Low 2 bytes:     0x%04lx\n", addr & 0xFFFF);

    // On a non-PIE binary, only the stack/libc addresses are randomized.
    // A partial overwrite on a stack return address only needs to target
    // the low 2 bytes to redirect within the same code page.
    return 0;
}

On a non-PIE binary, main() is at 0x400000 + offset . If the attacker leaks the low 2 bytes of a return address into main , they know the binary base. With PIE, they'd also need to leak 2 bytes of the PIE base offset, making partial overwrites harder but still theoretically possible.

Heap Randomization and Its Limits

The heap (brk area) has only 13 bits of randomization on x86-64. This is because the brk area traditionally starts right after the data+BSS segments and grows upward. There isn't much room to shift it without running into the mmap region. 

// heap_aslr.c — demonstrate heap randomization
// Compile: gcc -o heap_aslr heap_aslr.c -no-pie
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    // sbrk(0) returns the current program break (heap end)
    void *brk_start = sbrk(0);
    void *heap1 = malloc(16);
    void *heap2 = malloc(16);
    void *heap3 = malloc(16);

    printf("brk (heap start):  %p\n", brk_start);
    printf("malloc #1:         %p\n", heap1);
    printf("malloc #2:         %p\n", heap2);
    printf("malloc #3:         %p\n", heap3);

    // On a non-PIE binary, the initial brk is data_end + random_offset.
    // The random_offset has only 13 bits of entropy.
    // Note the low 12 bits of brk_start are always 0x000 (page-aligned).

    // Large mallocs (>128 KiB) use mmap, not brk:
    void *big = malloc(1024 * 1024);  // 1 MiB
    printf("Large malloc:      %p  (via mmap, 28 bits entropy)\n", big);

    free(heap1); free(heap2); free(heap3); free(big);
    return 0;
}
						
gcc -o heap_aslr heap_aslr.c -no-pie
for i in $(seq 1 3); do ./heap_aslr; echo "---"; done
# Observe: brk and small mallocs shift slightly (~13 bits variation)
# Observe: large malloc addresses shift dramatically (~28 bits variation)

  • vvar is adjacent to vdso (kernel maps them as a pair)

Non-Randomized Regions

Some areas of the address space are not randomized:

vDSO/vvar pair: The vDSO (linux-vdso.so.1) is kernel-provided code mapped into every process. It is randomized along with the mmap region, but its internal layout is fixed - the offsets within the vDSO are known to an attacker (it's the same kernel on every machine). This is rarely useful for exploitation since the vDSO contains only a handful of syscall wrappers ( clock_gettime , getcpu , time , gettimeofday ).

NULL page (0x0): Always unmapped. The zero page guard prevents NULL pointer dereferences from turning into exploitable conditions.

vsyscall page (legacy): On older kernels, the vsyscall page at 0xffffffffff600000 was a fixed-address kernel page containing gettimeofday and time implementations. Modern kernels use vDSO instead, but the vsyscall page still exists in compatibility mode at a fixed address. Some exploits use it as a known-address code region. Check with: 

cat /proc/self/maps | grep vsyscall
# On modern ArchLinux, this doesn't appear — vDSO replaced it

Enabling/Disabling ASLR Per-Process

ASLR can be disabled per-process using personality(2) : 

// disable_aslr_per_process.c
// Compile: gcc -o disable_aslr_per_process disable_aslr_per_process.c
#define _GNU_SOURCE
#include <sys/personality.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    // ADDR_NO_RANDOMIZE = 0x0040000 — disable ASLR for this process
    personality(ADDR_NO_RANDOMIZE);

    void *p = malloc(64);
    void *q = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
                   MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);

    printf("stack:    %p\n", &p);
    printf("heap:     %p\n", p);
    printf("mmap:     %p\n", q);

    free(p);
    munmap(q, 4096);
    return 0;
}
						
gcc -o disable_aslr_per_process disable_aslr_per_process.c
# Run twice with personality override — addresses should be identical:
./disable_aslr_per_process
./disable_aslr_per_process

# Using setarch (wrapper utility):
setarch $(uname -m) -R ./disable_aslr_per_process  # -R = disable ASLR
setarch $(uname -m) -R ./disable_aslr_per_process  # same addresses

Kernel ASLR (KASLR)

The kernel itself is randomized at boot time. KASLR randomizes the kernel's base address in the upper half of the virtual address space: 

# Check if KASLR is enabled
cat /proc/cmdline | grep -o 'nokaslr'
# If "nokaslr" appears, KASLR is disabled

# Check kernel base address
sudo cat /proc/kallsyms | head -5
# The first entry (_text) shows the kernel base
# Compare across reboots — should differ (unless nokaslr)

# KASLR entropy on x86-64: ~9 bits (512 possible positions)
# Limited by physical memory layout and kernel size

Disable KASLR at boot by adding nokaslr to kernel command line (for debugging): 

# Edit /etc/default/grub
GRUB_CMDLINE_LINUX_DEFAULT="... nokaslr"
sudo grub-mkconfig -o /boot/grub/grub.cfg
# Reboot

Challenge

Write a Go tool that spawns the same child process many times and records the load address of a shared library from /proc/<pid>/maps . Run it once with randomize_va_space=0 and once with =2 , then estimate how many bits of entropy the observed spread represents. The snippet shows how to read the first libc mapping; extend it to loop and collect the results. 

package main

import (
	"bufio"
	"fmt"
	"os"
	"os/exec"
	"sort"
	"strings"
)

func mmapBase(pid int) (string, bool) {
	f, err := os.Open(fmt.Sprintf("/proc/%d/maps", pid))
	if err != nil {
		return "", false
	}
	defer f.Close()

	scanner := bufio.NewScanner(f)
	for scanner.Scan() {
		line := scanner.Text()
		if strings.Contains(line, "libc") {
			return strings.SplitN(line, "-", 2)[0], true
		}
	}
	return "", false
}

func main() {
	bases := make([]string, 0, 64)
	for i := 0; i < 64; i++ {
		cmd := exec.Command("sleep", "0.1")
		if err := cmd.Start(); err != nil {
			panic(err)
		}
		if base, ok := mmapBase(cmd.Process.Pid); ok {
			bases = append(bases, base)
		}
		_ = cmd.Wait()
	}
	sort.Strings(bases)
	fmt.Printf("%d samples, min=%s max=%s\n", len(bases), bases[0], bases[len(bases)-1])
}
