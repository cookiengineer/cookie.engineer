Public Key Cryptography

Public key cryptography with RSA and elliptic curves, digital signatures, GPG, and X.509, from mathematics to practical use.

Overview

Symmetric encryption has a distribution problem: both sides must already share a secret key. Public key cryptography removes that requirement by splitting a key pair into a public half that anyone can hold and a private half that stays secret. This article explains how RSA and elliptic curves achieve that, how signatures and key exchange use the same primitives, and how to generate, inspect, and deploy keys on Linux with OpenSSL , SSH , and GPG.

Required Reading

  • Cryptography - cryptographic primitives this article builds upon

Public key (asymmetric) cryptography solves the key distribution problem. With symmetric encryption, both parties must share a secret key beforehand. Public key cryptography uses mathematically linked key pairs: a public key that can be freely shared, and a private key that must be kept secret. The two keys are mathematically related, but deriving the private key from the public key is computationally infeasible.

This article covers the mathematics, the algorithms, key generation, and practical usage on Linux.

Three Uses of Asymmetric Keys

Public key cryptography serves three distinct purposes:

Purpose Operation Public Key Used For Private Key Used For
Encryption Encrypt(plaintext, pk) -> ciphertext Encrypt message Decrypt message
Digital Signature Sign(message, sk) -> signature Verify signature Create signature
Key Exchange DH(sk_a, pk_b) -> shared_secret Exchange (with peer private) Exchange (with peer public)

A single key pair can serve multiple purposes, but best practice is separate keys:

  • One key pair for encryption
  • One key pair for signing
  • One key pair for authentication

GPG enforces this separation with primary keys (certification) and subkeys (encryption, signing, authentication).

RSA Deep Dive

RSA security rests on the integer factorization problem: given n = p*q, find p and q. Multiplying two primes is easy. Factoring their product is, as far as we know, hard.

The Mathematics

Key Generation:
  1. Choose two large primes p, q (2048-bit each for 4096-bit RSA)
  2. n = p x q                          (modulus, public)
  3. phi(n) = (p-1)(q-1)                (Euler's totient, kept secret)
  4. Choose e: 1 < e < phi(n), gcd(e, phi(n)) = 1
     Standard: e = 65537 = 2^16 + 1     (Fermat prime, small Hamming weight)
  5. d = e^-1 mod phi(n)                (private exponent)
     Compute via Extended Euclidean Algorithm:
       Find x,y such that e*x + phi(n)*y = 1
       d = x mod phi(n)
  6. Optional: dP = d mod (p-1), dQ = d mod (q-1), qInv = q^-1 mod p
     (CRT parameters, for faster decryption)

  Public key:  (n, e)
  Private key: (n, d) or (p, q, dP, dQ, qInv) for CRT optimization

Encryption:
  c = m^e mod n

Decryption:
  m = c^d mod n

Why it works (Euler's theorem):
  By construction, e*d = 1 (mod phi(n)), so e*d = k*phi(n) + 1 for some k
  c^d = (m^e)^d = m^(e*d) = m^(k*phi(n)+1)
  = (m^phi(n))^k * m = 1^k * m = m (mod n)

  This relies on Euler's theorem: if gcd(a, n) = 1, then a^phi(n) = 1 (mod n)
  (For the edge case where gcd(m, n) != 1, i.e. m shares a factor with n,
   it still works by the Chinese Remainder Theorem, but this is negligibly rare.)

Why Factoring Is Hard

The best known classical factoring algorithm is the General Number Field Sieve (GNFS), with subexponential complexity:

L_n[1/3, c] = exp((c + o(1))(ln n)^(1/3)(ln ln n)^(2/3))

For RSA-2048 (n ~ 2^2048):
  ln(n) ~ 2048*ln(2) ~ 1420
  (ln n)^(1/3) ~ 11.2
  (ln ln n)^(2/3) ~ (7.26)^(2/3) ~ 3.75
  ~ exp(c * 11.2 * 3.75) operations

  With optimized parameters, this is roughly 2^112 operations.
  The Bitcoin network does ~2^68 SHA-256 per second.
  Estimated: billions of years with current technology.

For RSA-1024 (n ~ 2^1024):
  ~ 2^80 operations - considered breakable by well-resourced adversaries.

Shor's algorithm on a quantum computer factors in polynomial time:
  O((log n)^2 (log log n)(log log log n))
  A sufficiently large fault-tolerant quantum computer breaks ALL RSA,
  regardless of key size. This is why post-quantum cryptography (PQC) exists.

RSA Key Generation in Practice

Finding large primes uses probabilistic primality testing, primarily the Miller-Rabin test:

Miller-Rabin test for odd n > 3:
  1. Write n-1 = d*2^s where d is odd
  2. Choose random a: 2 <= a <= n-2
  3. x = a^d mod n
  4. If x = 1 or x = n-1: probably prime (continue with next witness)
  5. Repeat s-1 times:
     x = x^2 mod n
     if x = 1: COMPOSITE (nontrivial square root of 1)
     if x = n-1: probably prime (break loop)
  6. If loop completes without x = n-1: COMPOSITE

For random a, the probability of a false positive is at most 1/4.
With k independent trials: <= (1/4)^k

Typical: k = 40 for 2^-80 error bound, or k = 64 for 2^-128.
						
# Generate RSA key - see the process
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out rsa.key

# Examine the generated primes
openssl rsa -in rsa.key -text -noout | grep -A10 "prime1:"
# Shows p (prime1), q (prime2), exponents, CRT parameters

# Manual key generation with OpenSSL (for understanding)
# Step 1: Generate two random candidate primes
openssl prime -generate -bits 2048 -safe
# The -safe flag ensures p = 2q+1 (safe prime), adding protection
# against Pollard's p-1 factorization.

RSA Padding

Raw RSA (textbook RSA ) is insecure. Without padding:

  • Deterministic: same plaintext produces the same ciphertext
  • Malleable: c_1 * c_2 mod n decrypts to m_1 * m_2 mod n
  • Vulnerable to small-exponent attacks: if e=3 and m^3 < n , the cube root reveals m

PKCS#1 v1.5 Padding

Encoded = 0x00 || 0x02 || random_nonzero_bytes || 0x00 || message

0x02 indicates encryption. The random padding ensures probabilistic encryption. However, the structure creates a padding oracle: if a server reveals whether decrypted padding is valid, an attacker can recover plaintext via Bleichenbacher's attack (adaptive chosen ciphertext). This attack is practical and has been demonstrated against TLS , XML Encryption, and JWT implementations.

OAEP Padding

OAEP (Optimal Asymmetric Encryption Padding):

OAEP(m, label, r):
  1. m' = m || 0x00...0  (pad message with k1 zero bytes)
  2. mgf_seed = m' XOR MGF(r, k - k0)  (Mask Generation Function)
  3. masked_db = r XOR MGF(mgf_seed, k0)
  4. Encoded = 0x00 || masked_seed || masked_db

OAEP is provably secure in the random oracle model ( IND-CCA2 ). Always use OAEP over PKCS#1 v1.5 for encryption.

# RSA-OAEP encryption with OpenSSL
openssl pkeyutl -encrypt -pubin -inkey pubkey.pem \
    -pkeyopt rsa_padding_mode:oaep \
    -pkeyopt rsa_oaep_md:sha256 \
    -in plaintext.txt -out encrypted.bin

# RSA-OAEP decryption
openssl pkeyutl -decrypt -inkey privkey.pem \
    -pkeyopt rsa_padding_mode:oaep \
    -pkeyopt rsa_oaep_md:sha256 \
    -in encrypted.bin -out decrypted.txt

Elliptic Curve Cryptography

ECC offers equivalent security with dramatically smaller keys. A 256-bit ECC key provides~128-bit security, comparable to a 3072-bit RSA key.

The Curve

An elliptic curve over a finite field F_p is the set of points (x, y) satisfying:

y^2 = x^3 + ax + b  (mod p)
with 4a^3 + 27b^2 != 0 (mod p)  (non-singularity condition)

For Curve25519 (used in Ed25519 and X25519):

p = 2^255 - 19  (a 255-bit prime, hence "25519")
a = 486662
b = 1
Curve equation: y^2 = x^3 + 486662x^2 + x over F_p

For secp256r1 (NIST P-256, used in ECDSA):

p = 2^256 - 2^224 + 2^192 + 2^96 - 1
a = -3
b = 0x5AC635D8AA3A93E7B3EBBD55769886BC651D06B0CC53B0F63BCE3C3E27D2604B

Point Operations

The curve forms a group under point addition:

Point Addition (P + Q, where P != Q):
  lambda = (y_Q - y_P)(x_Q - x_P)^-1 mod p       (slope)
  x_R = lambda^2 - x_P - x_Q mod p
  y_R = lambda(x_P - x_R) - y_P mod p

Point Doubling (P + P):
  lambda = (3x_P^2 + a)(2y_P)^-1 mod p
  x_R = lambda^2 - 2x_P mod p
  y_R = lambda(x_P - x_R) - y_P mod p

Scalar Multiplication (k*P):
  Double-and-add algorithm:
    result = O (point at infinity)
    for bit in binary(k) from MSB to LSB:
      result = result + result  (double)
      if bit == 1:
        result = result + P     (add)
    return result

  For 256-bit scalar: up to 256 doubles and ~128 adds.
  Optimized with windowed methods for performance.

The Discrete Logarithm Problem

Given points P and Q where Q = d*P, find d (the scalar). This is the Elliptic Curve Discrete Logarithm Problem (ECDLP). The best known classical attack is Pollard's rho algorithm with complexity O(sqrt(n)) where n is the group order:

For a 256-bit curve (order ~ 2^256):
  Pollard's rho: ~2^128 operations (square root)
  This provides ~128-bit security.

No index calculus algorithm (like GNFS for RSA ) applies to general elliptic curves. This is why ECC keys can be so much smaller than RSA keys for equivalent security.

Common Curves

Curve Field Size Security Usage
secp256r1 (P-256) 256-bit ~128-bit ECDSA in TLS, JWT
secp384r1 (P-384) 384-bit ~192-bit Higher security ECDSA
secp521r1 (P-521) 521-bit ~256-bit Maximum NIST curve
Curve25519 255-bit ~128-bit ECDH (X25519), EdDSA (Ed25519)
Curve448 448-bit ~224-bit ECDH (X448), EdDSA (Ed448)

Curve25519 is preferred for most applications:

  • No NIST parameters (transparent constant selection)
  • Designed for constant-time implementation (no branching)
  • No cofactor complications (cofactor 8, handled via clamping)
  • Fast: 51-bit limbs on 64-bit processors
  • Montgomery form enables efficient X-only ECDH
# List supported curves in OpenSSL
openssl ecparam -list_curves

# Generate a curve-specific key
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 -out ecdsa.key
openssl genpkey -algorithm x25519 -out x25519.key
openssl genpkey -algorithm ed25519 -out ed25519.key

# Examine curve parameters
openssl ecparam -name prime256v1 -text -noout

Ed25519 - The Modern Standard

Ed25519 is an instantiation of EdDSA (Edwards-curve Digital Signature Algorithm) using Curve25519 in Edwards form.

Edwards Form

Curve25519 in Montgomery form (for ECDH):

By^2 = x^3 + Ax^2 + x

Curve25519 in Edwards form (for signing):

-x^2 + y^2 = 1 + dx^2y^2
where d = -121665/121666 mod p

The Edwards form enables a complete addition law (no special cases, no point at infinity handling), making constant-time implementation straightforward and eliminating the edge cases that plague ECDSA implementations.

Key Generation and Signing

KeyGen():
  1. sk = random(256 bits) from CSPRNG
  2. h = SHA-512(sk)
  3. a = h[0:32], clamp:
     a[0]  &= 248    (clear lowest 3 bits)
     a[31] &= 127    (clear highest bit)
     a[31] |= 64     (set second-highest bit)
  4. A = a*B         (B = base point)
  5. Public key: A (32 bytes)

Clamping ensures:
  - Scalar is a multiple of cofactor (8) - clears cofactor subgroup
  - Scalar is < 2^255 (fits in 255 bits)
  - High bit set for efficient multiplication

Sign(sk, message):
  1. h = SHA-512(sk)
  2. a = clamped(h[0:32])
  3. prefix = h[32:64]
  4. r = SHA-512(prefix || message) mod L  (L = order of base point)
  5. R = r*B
  6. S = r + SHA-512(R || A || message) * a mod L
  7. Signature = R || S (64 bytes)

Verify(A, message, signature):
  1. Parse R (first 32 bytes), S (last 32 bytes)
  2. h = SHA-512(R || A || message) mod L
  3. Check: S*B = R + h*A

  Proof: S*B = (r + h*a)*B = r*B + h*(a*B) = R + h*A

Ed25519 in Practice

# Generate Ed25519 SSH key
ssh-keygen -t ed25519 -C "user@host" -f ~/.ssh/id_ed25519

# The public key format
cat ~/.ssh/id_ed25519.pub
# ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... user@host

# Sign a file with ssh-keygen
echo "data to sign" > data.txt
ssh-keygen -Y sign -f ~/.ssh/id_ed25519 -n file data.txt
# Creates data.txt.sig

# Verify a signature
ssh-keygen -Y verify -f allowed_signers -I user@host \
    -n file -s data.txt.sig < data.txt

# GPG with Ed25519

# Select (9) ECC and ECC

GPG Key Structure

GPG keys have a hierarchical structure:

Primary Key (C) - Certification only
  +-- Subkey 1 (S) - Signing
  +-- Subkey 2 (E) - Encryption
  +-- Subkey 3 (A) - Authentication (for SSH)

Usage:
- Primary key signs other keys (certification). Keep offline.
- Signing subkey signs commits, emails, artifacts. Stored on dev machine.
- Encryption subkey decrypts messages. Stored on dev machine.
- Authentication subkey authenticates SSH connections. Stored on dev machine.

The primary key is the trust anchor. If it is compromised, the attacker can revoke all subkeys and generate new ones in your name. The primary key should be generated on an air-gapped machine and stored offline (hardware token, paper backup, encrypted USB ).

# Generate GPG key with subkeys
gpg --full-generate-key --expert
# Primary: ECC, Curve 25519, certify only (C)
# Then add subkeys:
gpg --edit-key KEYID
gpg> addkey
# Choose: (4) RSA (sign only) or (10) ECC (sign only)
# Choose: (6) RSA (encrypt only) or (12) ECC (encrypt only)
gpg> save

# List keys with subkeys
gpg -k KEYID
# pub   ed25519 2024-01-01 [C]
#       KEYID
# uid           [ultimate] User Name <user@example.com>
# sub   ed25519 2024-01-01 [S]
# sub   cv25519 2024-01-01 [E]

# Export public key
gpg --export --armor KEYID > public.asc

# Export private key (WARNING: handle with extreme care)
gpg --export-secret-keys --armor KEYID > private.asc

# Export subkeys only (for daily-use machine)
gpg --export-secret-subkeys --armor KEYID > subkeys.asc

Key Distribution Problem

How does Alice obtain Bob's authentic public key? An attacker can intercept the key and substitute their own ( MITM ).

Web of Trust

Alice signs Bob's key   -> Alice asserts "Bob's key is authentic"
Carol signs Bob's key   -> Carol also asserts Bob's key
Dave trusts Alice       -> Dave can verify Bob's key via Alice's signature

Trust model:
- Ownertrust: How much you trust a key to certify others
- Validity: Computed based on signatures and trust paths
- Marginal trust: Need multiple marginally trusted signatures

gpg --edit-key BOB_KEYID
gpg> trust
# 1 = Don't know
# 2 = I do NOT trust
# 3 = I trust marginally
# 4 = I trust fully
# 5 = I trust ultimately

Web of Trust is decentralized but requires user participation. It works well for developer communities (Linux kernel, Debian, Arch) but poorly for general users.

PKI and TLS/X.509

Certificate Authorities ( CA s) are trusted third parties that vouch for key ownership:

Root CA (self-signed) <- trust anchor
  +-- Intermediate CA (signed by Root CA)
       +-- Server Certificate (signed by Intermediate)
            +-- CN = example.com
            +-- SAN = www.example.com, *.example.com
						
# View a website's certificate chain
openssl s_client -connect example.com:443 -showcerts </dev/null 2>/dev/null | \
    openssl x509 -text -noout | grep -E "(Subject:|Issuer:|Not Before|Not After|DNS:)"

# Extract certificate
openssl s_client -connect example.com:443 -showcerts </dev/null 2>&1 | \
    awk '/BEGIN CERTIFICATE/,/END CERTIFICATE/' > cert.pem

# Verify chain against system trust store
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert.pem

# Check certificate expiration
openssl x509 -in cert.pem -noout -enddate

# Get certificate fingerprint
openssl x509 -in cert.pem -noout -fingerprint -sha256

Hardware Tokens

Storing private keys on general-purpose computers exposes them to malware. Hardware tokens (YubiKey, Nitrokey, Solokey) generate and store keys in tamper-resistant hardware. The private key never leaves the device; operations are performed on-device.

# Configure GPG with YubiKey
gpg --card-status
# Shows: card type, application IDs, key fingerprints

# Generate keys directly on YubiKey (keys never touch the host)
gpg --card-edit
gpg/card> admin
gpg/card> generate

# Or move existing subkeys to card
gpg --edit-key KEYID
gpg> key 1           # select signing subkey
gpg> keytocard
gpg> key 1           # deselect
gpg> key 2           # select encryption subkey
gpg> keytocard
gpg> save

# Use YubiKey for SSH
gpg --export-ssh-key KEYID > ~/.ssh/id_ed25519_yubikey.pub
ssh-add -L

# The SSH client uses gpg-agent, which forwards requests to the YubiKey
ssh user@host   # YubiKey blinks, touch to confirm

Building a Mini CA

# Create root CA
mkdir ca && cd ca
mkdir certs crl newcerts private
chmod 700 private
touch index.txt
echo 1000 > serial

# Root CA configuration (openssl.cnf)
cat > openssl.cnf << 'CNF'
[ca]
default_ca = CA_default

[CA_default]
dir          = .
certs        = $dir/certs
new_certs_dir = $dir/newcerts
database     = $dir/index.txt
serial       = $dir/serial
private_key  = $dir/private/ca.key.pem
certificate  = $dir/ca.cert.pem
default_md   = sha256
policy       = policy_strict

[policy_strict]
countryName            = match
stateOrProvinceName    = match
organizationName       = match
commonName             = supplied

[req]
default_bits     = 4096
string_mask      = utf8only
default_md       = sha256
prompt           = no
distinguished_name = req_distinguished_name

[req_distinguished_name]
countryName            = US
stateOrProvinceName    = California
organizationName       = My Org

[v3_ca]
basicConstraints       = critical, CA:TRUE
keyUsage               = critical, keyCertSign, cRLSign
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid:always,issuer

[v3_server]
basicConstraints       = critical, CA:FALSE
keyUsage               = critical, digitalSignature, keyEncipherment
extendedKeyUsage       = serverAuth
subjectAltName         = DNS:example.com, DNS:*.example.com
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid:always,issuer
CNF

# Generate root CA
openssl genpkey -algorithm ed25519 -out private/ca.key.pem
chmod 400 private/ca.key.pem
openssl req -config openssl.cnf -key private/ca.key.pem \
    -new -x509 -days 3650 -extensions v3_ca \
    -subj "/C=US/ST=California/O=My Org/CN=My Root CA" \
    -out ca.cert.pem

# Generate server certificate signed by CA
openssl genpkey -algorithm ed25519 -out private/server.key.pem
openssl req -config openssl.cnf -new -key private/server.key.pem \
    -subj "/C=US/ST=California/O=My Org/CN=example.com" \
    -out certs/server.csr.pem
openssl ca -config openssl.cnf -extensions v3_server -days 365 \
    -notext -in certs/server.csr.pem -out certs/server.cert.pem

# Verify chain
openssl verify -CAfile ca.cert.pem certs/server.cert.pem

Choosing an Algorithm

Asymmetric Cryptography Decision Tree:

Need to encrypt data for someone?
  -> Their public key for encryption, their private key for decryption
  -> Use RSA-OAEP or ECIES (hybrid: ECC + symmetric)

Need to prove you created a message?
  -> Your private key to sign, verifier uses your public key
  -> Use Ed25519 (preferred) or ECDSA

Need to establish a shared secret over insecure channel?
  -> Both parties generate ephemeral keypairs
  -> Use X25519 (ECDH over Curve25519)

Need long-term identity?
  -> Generate offline master key, create subkeys for daily use
  -> Store master key on hardware token or air-gapped machine

Need TLS/HTTPS?
  -> Generate CSR, get certificate from CA or Let's Encrypt
  -> Prefer ECC certificates (EC P-256 or P-384)

The choice between RSA and ECC is increasingly clear: ECC provides equivalent security with smaller keys, faster operations, and better side-channel resistance. Ed25519/X25519 specifically eliminate the major footguns (nonce generation, cofactor issues, timing side channels) that have caused real-world breaks. For new deployments, there is rarely a reason to choose RSA over Ed25519.

Challenge

Implement textbook RSA in Go with math/big : generate two primes, compute n , e , and d , then encrypt and decrypt a short message. Verify that decryption returns the original plaintext, then demonstrate the textbook weakness by showing that encrypting the same message twice produces identical ciphertexts (deterministic encryption), which OAEP padding fixes.

package main

import (
	"crypto/rand"
	"fmt"
	"math/big"
)

func main() {
	// Two small primes, for demonstration only.
	p, _ := new(big.Int).SetString("32416190071", 10)
	q, _ := new(big.Int).SetString("32416187567", 10)

	n := new(big.Int).Mul(p, q)

	pMinus1 := new(big.Int).Sub(p, big.NewInt(1))
	qMinus1 := new(big.Int).Sub(q, big.NewInt(1))
	phi := new(big.Int).Mul(pMinus1, qMinus1)

	e := big.NewInt(65537)
	d := new(big.Int).ModInverse(e, phi)

	message := big.NewInt(1234567)
	cipher := new(big.Int).Exp(message, e, n)
	plain := new(big.Int).Exp(cipher, d, n)

	fmt.Printf("n      = %s\n", n)
	fmt.Printf("plain  = %s\n", plain)

	// Textbook RSA is deterministic: same input, same output.
	second := new(big.Int).Exp(message, e, n)
	fmt.Printf("equal  = %v\n", cipher.Cmp(second) == 0)

	random := make([]byte, 8)
	rand.Read(random)
	fmt.Printf("random = %x\n", random)
}

go run rsa.go;
