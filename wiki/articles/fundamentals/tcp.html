TCP

The Transmission Control Protocol and its three-way handshake and connection state machine.

Overview

IP is unreliable by design. Datagrams can be lost, duplicated, reordered, or corrupted. IP provides a best-effort delivery service and nothing more. If a router's queue overflows, it drops the packet. If a link fails, packets silently disappear. IP does not detect loss, does not retransmit, and does not guarantee order.

The TCP protocol builds reliable, ordered, byte-stream communication on top of this unreliable foundation. The purpose of the TCP protocol is the following:

  • Every byte is delivered exactly once.
  • Every byte is delivered in-order.
  • The sender knows which bytes were received.
  • The receiver knows how much bytes are coming.
  • Both sides agree on connection state.

TCP achieves this through sequence numbers, acknowledgments, timers, retransmission, flow control, and a formal connection lifecycle.

TCP Segment Flags

Each flag triggers specific protocol behavior:

Flag Value Cause Effect
SYN 0x02 Connection initiation Synchronizes sequence numbers, starts a connection
ACK 0x10 Almost every segment after SYN Validates the Acknowledgment Number field
FIN 0x01 No more data to send Initiates graceful connection close
RST 0x04 Error, refusal, abort Immediately terminates the connection
PSH 0x08 Application wants immediate delivery Bypass buffering, deliver to application now
URG 0x20 Out-of-band data is present Urgent Pointer field indicates where urgent data ends
CWR 0x80 ECN: sender reduced congestion window Congestion notification from sender
ECE 0x40 ECN: receiver saw congestion Congestion notification to sender
NS 0x01 ECN nonce sum Experimental ECN nonce protection

Practical immediate and urgent flag use cases:

  • Telnet sets PSH flag on every keystroke segment so that the remote shell displays characters immediately.
  • Bulk data transfers (e.g. HTTP or FTP ) typically don't set the PSH flag, and the receiving TCP stack delivers data when the buffer is full or a timer expires.
  • The URG flag indicates the byte offset from the sequence number where the urgent data ends. It's actually not really used anymore and ignored by modern API s. Good attack vector for pentesting IoT implementations.

TCP Three-Way Handshake

The TCP handshake serves three purposes:

  1. Both sides agree a connection exists.
  2. Both sides exchange their Initial Sequence Numbers (ISN).
  3. Both sides negotiate TCP options ( MSS , Window Scale, SACK, Timestamps).

Control Flow of a TCP Three-Way Handshake:

Step Active Client Passive Server
1 seq=x,SYN ->
2 <- seq=y,ack=x+1,SYN,ACK
3 seq=x+1,ack=y+1,ACK ->
4
  1. Client sends packet with seq=x and SYN flag set. x is randomized. Client enters state SYN_SENT .
  2. Server receives packet and enters state SYN_RECEIVED . Server sends packet with seq=y , ack=x+1 and SYN and ACK flags set. y is randomized.
  3. Client receives packet and enters state ESTABLISHED . Client sends packet with seq=x+1 , ack=y+1 and ACK flag set.
  4. Server receives packet and enters state ESTABLISHED .

The Sequence number accounting is byte-oriented, meaning that the SYN flag consumes one sequence number even though it carries no data. This is why the ACK in Step 2 acknowledges x+1 , and the SYN consumed byte x . The SYN-ACK consumes sequence number y , so the client acknowledges y+1 in Step 3 .

With the programs nc and tcpdump we can observe a TCP handshake in the terminal: 

# Terminal 1: Start a listener
nc -l 1337;

# Terminal 2: Start packet capture
sudo tcpdump -i lo -nn -v 'tcp port 1337';

# Terminal 3: Connect
nc localhost 1337;
# Type "hello" and press Enter, then Ctrl+C to close

# Terminal 2 output:

TCP Sequencing

The ISN is the starting value for the sequence number counter on each side. Each side chooses its own ISN independently and randomly, they are not synchronized. If an attacker can predict the ISN that a server will use, they can inject data into a connection. Modern kernels use cryptographic hash functions based on the connection 4-tuple ( src IP , dst IP , src port , dst port ) and a secret key to generate unpredictable ISNs. 

# Check Linux if ISN generation is enabled
cat /proc/sys/net/ipv4/tcp_timestamps;
# 1 = timestamps enabled (provides additional ISN entropy)

# View the ISN of a connection
sudo tcpdump -i any -nn -c 1 'tcp[tcpflags] & tcp-syn != 0';

Sequence Numbers

Each byte of data increments the sequence number by 1. SYN and FIN flags each consume one sequence number. So a segment with SYN flag and 100 bytes of data would have seq=x , and the next expected sequence number would be x+101 ( 100 bytes for data and 1 byte for SYN ).

TCP sequence numbers wrap around at 2^32 bits . With modern high-speed networks ( 100 Gbps ), this wrap could occur in ~5.5 seconds . Timestamps (as defined in RFC 7323) protect against ambiguity from wrapped sequence numbers through PAWS .

Acknowledgment Numbers

The ACK field confirms that all bytes up to (but not including) the specified number have been received. The next byte after the ACK field is expected to be the specified number. A single ACK acknowledges all bytes up to a specified byte length. If the sender transmitted bytes 100-199 , 200-299 , and 300-399 , and segment 200-299 was lost, the receiver responds with ACK=200 (the first missing byte). The sender must retransmit from byte 200 onward. This is called the Go-Back-N retransmission.

Selective ACK , or the SACK option allows the receiver to acknowledge non-contigous blocks. For example, that segment 100-199 and 300-399 were received but 200-299 were lost along the way. The sender then retransmits only the missing segment. SACK is negotiated during the handshake via the SACK-permitted option. 

# Check if SACK is enabled
cat /proc/sys/net/ipv4/tcp_sack;
# 1 = enabled (default)

# Check statistics including retransmissions
ss -ti; # Show TCP info including retransmits, RTT, etc.

nstat -az | grep -i retrans;

TCP Four-Way Close

TCP is a full-duplex protocol. The data flows in both directions independently. Closing a TCP connection requires closing each direction separately, so it is necessary to transmit four segments for a mutual close.

Control Flow of a TCP Four-Way Close:

Step Active Passive
1 seq=u,FIN ->
2 <- seq=v,ack=u+1
3
4 <- seq=w,ack=u+1,FIN
5 seq=u+1,ack=w+1 ->
6
7
  1. Active closer sends packet with seq=u and FIN flag set. Active closer enters state FIN_WAIT_1 .
  2. Passive closer receives packet and enters state CLOSE_WAIT . Passive closer sends packet with seq=v and ack=u+1 .
  3. Active closer receives packet and enters state FIN_WAIT_2 . Active closer's connection is now half-closed. Passive closer's connection remains half-open.
  1. Passive closer sends packet with seq=w and ack=u+1 and FIN flag set. Passive closer enters state LAST_ACK .
  2. Active closer receives packet and enters state TIME_WAIT . Active closer sends packet with seq=u+1 and ack=w+1 set.
  3. Passive closer receives packet and enters state CLOSED . Passive closer's connection is closed now.
  4. After the timeout of 2 * MSL has been reached, active closer enters state CLOSED , too.

Maximum Segment Lifetime

On most systems, the MSL timeout value is defaulted with values between 60 and 120 seconds. The reason the TIME_WAIT state exists in TCP connections is the following:

  • If the active closer's ACK (step 4) is lost, the passive closer retransmits its FIN packet. The active closer must remain in TIME_WAIT to retransmit ACK the packet that retransmitted the FIN .
  • If the active closer transitioned directly to CLOSED , a retransmitted FIN would arrive at a port with no connection, and result in an RST packet which the passive closer would misinterpret as an error.
  • After a connection closes, delayed duplicate segments from that connection must expire before the same 4-tuple ( src IP , src port , dst IP , dst port ) can be reused.
  • MSL is the maximum time a segment can exist in the network along its paths. After the 2 * MSL timeout, any old segment from the previous communications of this 4-tuple has been destroyed.
# Check MSL on Linux
cat /proc/sys/net/ipv4/tcp_fin_timeout;
# Seconds in FIN_WAIT_2 before timeout (default 60)

# See TIME_WAIT connections
ss -tanp state time-wait;
netstat -tan | grep TIME_WAIT;

# Count connections per state
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn;

With the program ss we can observe changing TCP states in the terminal: 

ss -tanp;
# Output columns: State, Recv-Q, Send-Q, Local Address:Port, Peer Address:Port, Process

# Filter by state

ss -tanp state time-wait;
ss -tanp state listen;

# Count connections per state

Negotation of Options

The SYN and SYN-ACK segments carry TCP options that negotiate connection parameters. Options use a TLV format. Common options appear in the SYN in this order:

  1. MSS
  2. Window Scale
  3. SACK-Permitted
  4. Timestamps
  5. NOP (padding for 32-bit alignment)

Maximum Segment Size

The Maximum Segment Size option has Kind: 2 and Length: 4 bytes .

The largest TCP segment ( header + data ) the sender can receive is called MSS . Both sides announce their MSS . The connection uses the minimum of the two values. Typically the MSS is set to MTU - 40 . For an MTU of 1500 bytes that means:

  • MTU is 1500 bytes
  • 1500 bytes - 20 bytes ( IP header)
  • 1480 bytes - 20 bytes ( TCP header)
  • MSS is 1460 bytes
# Check MTU and derive MSS
ip link show eth0 | grep mtu;
# mtu 1500 → MSS = 1460 (minus IP header and TCP header)

# Force a specific MSS
sudo ip route change default via 192.168.1.1 dev eth0 advmss 1400;

If a router on the network path has a smaller MTU (for example PPPoE: 1492 bytes or VPN tunnel: ~1400 bytes ), then the packets exceeding that MTU must be fragmented or dropped. PMTUD uses the ICMP Fragmentation Needed messages to discover this, but PMTUD often breaks because firewalls block ICMP packets. MSS clamping at the firewall ensures that TCP connections stay within path MTU limits.

Window Scale

The Window Scale option has Kind: 3 and Length: 3 bytes .

The Window field in the TCP header is 16 bits , limiting the receive window to a maximum of 65535 bytes . On high-bandwidth, high-latency links, this limits throughput. Window Scale multiplies the window by 2^n where n is the scale factor set to 0-14 and which is negotiated during handshake.

cat /proc/sys/net/ipv4/tcp_window_scaling;
# 1 = enabled (default)

# Check BDP for your link
# BDP = bandwidth (bits/sec) * RTT (sec) / 8

# Example:
# 1 Gbps * 10ms RTT

Selective Acknowledgment

The Selective Acknowledgement option has either Kind: 4 and Length: 2 bytes in the handshake for SACK-permitted . Following SACK option fields have Kind: 5 and a variable byte length. The SACK-Permitted flag option in the SYN packet enables SACK for following segment transfers. During data transfer, SACK blocks specify the received byte ranges so that the sender retransmits only the missing segments, and not everything after a packet loss. 

# Verify SACK is active on a connection
ss -ti sport = :80;
# Look for "sack" in the output

# Kernel SACK settings
cat /proc/sys/net/ipv4/tcp_sack;  # Enable SACK (1)
cat /proc/sys/net/ipv4/tcp_dsack; # Duplicate SACK (1)
cat /proc/sys/net/ipv4/tcp_fack;  # Forward ACK (0 = disabled in newer kernels)

Timestamps

The Timestamp option has Kind: 8 and Length: 10 bytes where the TSval and TSecr have each a 4 byte encoded timestamp value. The TSecr value is the echo of the other peer's last TSval. This allows RTTM .

  1. The sender sends a packet with TSval set.
  2. The receiver responds with a packet that echoes the value as TSecr .
  3. The sender calculates RTT = now() - TSecr .

Additionally, timestamps prevent older delayed segments from being accepted after the sequence numbers have wrapped. A segment with a timestamp older than the most recent timestamp from that peer is discarded automatically. This mechanism is called PAWS . 

# Check timestamp settings
cat /proc/sys/net/ipv4/tcp_timestamps;
# 1 = enabled (default, required for high-performance TCP)

TCP Flow Control

TCP flow control prevents a fast sender from overwhelming a slow receiver. The receiver advertises its available buffer space in the Window field of every segment. 

  Sender's view:              Receiver's view:
+----------------------+    +---------------------+
| Bytes sent:     1000 |    | Bytes received: 500 |
| Bytes ACKed:     800 |    | Bytes read:     400 |
| Bytes in flight: 200 |    | Buffer used:    100 |
| Window:          500 |    | Window offered: 500 |
| Can send:        500 |    |                     |
+----------------------+    +---------------------+

Sliding Windows

The sender maintains: last_byte_sent - last_byte_acked <= receiver_window . When the receiver's window reaches 0 , the sender stops and waits. The receiver sends a window update when the application reads data. This is called the TCP sliding window protocol.

If the window update is lost, both sides deadlock. The sender periodically sends Zero Window Probes which are 1 byte segments that force the receiver to re-advertise its window. 

# Check current window sizes on connections
ss -tmi
# Look for "wscale:X,Y" where X = local scale, Y = peer scale

Fast Open

TCP Fast Open allows data to be sent during the three-way handshake, eliminating one RTT for repeat connections. The client obtains a cryptographic cookie from the server on the first connection. On subsequent connections, the client includes the cookie and data in the SYN packet. The server validates the cookie and delivers the data to the application before the handshake completes. 

# Enable TFO on Linux (requires kernel 3.7+)
echo 3 > /proc/sys/net/ipv4/tcp_fastopen
# 0 = disabled, 1 = client only, 2 = server only, 3 = both

# Verify TFO support with curl
curl --tcp-fastopen -o /dev/null https://example.com

# TFO handshake (simplified):
# First connection:
# Client: SYN + TFO cookie request
# Server: SYN-ACK + TFO cookie "abc123"
# Client: ACK
# (Data starts after handshake — 1 RTT penalty for first connection)
#
# Subsequent connections:
# Client: SYN + TFO cookie "abc123" + DATA "GET / HTTP/1.1\r\n..."
# Server: SYN-ACK + DATA (response)
# Client: ACK
# (Data in both directions during handshake — 0 RTT for repeat connections)

Simultaneous Open

Both sides send SYN to each other at the same time using a SYN_SENT packet. Each side receives a SYN packet, then transitions to SYN_RECEIVED , and then sends a SYN-ACK . Both end up with connection state ESTABLISHED with a single connection. This occurs rarely in practice but is specified in RFC 793 section 3.4 .

Simultaneous Close

Both sides send a FIN packet at the same time. Both enter the CLOSING connection state instead of transitioning to FIN_WAIT_1 and then to FIN_WAIT_2 . In the CLOSING connection state, each side waits for an ACK of its FIN flag before transitioning to TIME_WAIT .

Reset

The RST packet immediately aborts a connection. Unlike FIN , there is no graceful shutdown. The receiving side drops the connection immediately without notifying the application. The next read() call on the socket returns an ECONNRESET error.

Scenario RST From Behavior
SYNto a port with no listener Server RST-ACK
Data sent on a closed connection Receiver RST
Connection abort (SO_LINGERwithtimeout 0) Sender RSTinstead ofFIN
Half-open connection detected Either side RST
SYNreceived on an existing connection with wrong parameters Receiver RST 
# Demonstrate RST: connect to a closed port
nc -zv localhost 65432
# "Connection refused" = RST received

# Capture the RST
sudo tcpdump -i lo -nn -v 'tcp port 65432'
# Output: Flags [R.], seq 0, ack 1234567890
# RST does not consume a sequence number (seq=0 indicates no data)

TCP Debugging

ss -tanp;             # All TCP sockets with process info
