SIEM

Centralized security monitoring and correlation with Elastic Stack, Wazuh, correlation rules, and Sigma integration.

Overview

A SIEM collects logs from every host, network device, and application, normalizes them into a common schema, and correlates events that no single log source can connect. This article covers the collectors and ingestion pipelines of the Elastic Stack and Wazuh, the correlation rules that turn individual events into incidents, the Sigma format for portable detections, and the tuning and retention work that keeps the platform usable.

Required Reading

  • HTTP - HTTP methods, headers, REST API s
  • TLS - TLS handshake, certificate validation

Why SIEM

Individual log sources tell a fragmented story. A SIEM collects, normalizes, stores, and correlates logs from every system in the environment. When sshd on host-a logs a failed authentication, and nginx on host-b logs a 403 from the same IP 30 seconds later, a SIEM connects those events into a single incident.

Elastic Stack

The ELK stack (Elasticsearch, Logstash, Kibana) plus Beats is the most common open-source SIEM deployment. Elastic provides a free tier adequate for small environments.

Beats: Data Shippers

Lightweight agents that ship data to Logstash or directly to Elasticsearch.

# /etc/filebeat/filebeat.yml

Logstash: Processing Pipeline

Logstash ingests, parses, and transforms data. Its configuration uses three plugin types: input, filter, output. 

# /etc/logstash/conf.d/50-syslog-filter.conf
input {
  beats {
    port => 5044
  }
}

filter {
  # Parse syslog format (RFC 3164 / 5424)
  if [fields][log_type] == "syslog" {
    grok {
      match => { "message" => "%{SYSLOGTIMESTAMP:syslog_timestamp} %{SYSLOGHOST:syslog_hostname} %{DATA:syslog_program}(?:\[%{POSINT:syslog_pid}\])?: %{GREEDYDATA:syslog_message}" }
    }

    # Parse SSH auth messages
    if [syslog_program] == "sshd" {
      grok {
        match => { "syslog_message" => [
          "Failed password for %{WORD:auth_result} user %{USERNAME:auth_user} from %{IP:src_ip} port %{NUMBER:src_port} %{DATA:auth_protocol}",
          "Accepted password for %{USERNAME:auth_user} from %{IP:src_ip} port %{NUMBER:src_port} %{DATA:auth_protocol}",
          "Invalid user %{USERNAME:auth_user} from %{IP:src_ip} port %{NUMBER:src_port}"
        ]}
      }
    }

    # Normalize timestamp
    date {
      match => [ "syslog_timestamp", "MMM  d HH:mm:ss", "MMM dd HH:mm:ss", "ISO8601" ]
      target => "@timestamp"
    }
  }

  # GeoIP enrichment
  if [src_ip] {
    geoip {
      source => "src_ip"
      target => "geoip"
    }
  }

  # User-Agent parsing for HTTP logs
  if [fields][log_type] == "nginx_access" {
    grok {
      match => { "message" => "%{NGINXACCESS}" }
    }
  }

  # Add environment metadata
  mutate {
    add_field => {
      "[@metadata][index]" => "%{[fields][log_type]}-%{+YYYY.MM.dd}"
    }
  }
}

output {
  elasticsearch {
    hosts => ["elasticsearch.example.com:9200"]
    index => "%{[@metadata][index]}"
    manage_template => false
  }
}

Wazuh

Wazuh is an open-source SIEM / XDR built on the OSSEC engine. It combines host-based intrusion detection (FIM, rootcheck, anomaly detection), log collection, and compliance monitoring with its own OpenSearch-based indexer and dashboard.

Wazuh Architecture

Wazuh Agent (endpoint) → Wazuh Manager (analysis engine) → Wazuh Indexer (OpenSearch-based) → Wazuh Dashboard (OpenSearch Dashboards fork)

Install Wazuh Manager

git clone https://github.com/wazuh/wazuh-docker.git -b v4.9.0
cd wazuh-docker/single-node
podman-compose up -d

<!-- /var/ossec/etc/ossec.conf -->
<ossec_config>
  <client>
    <server>
      <address>wazuh-manager.example.com</address>
      <port>1514</port>
      <protocol>tcp</protocol>
    </server>
  </client>

  <!-- File integrity monitoring -->
  <syscheck>
    <frequency>43200</frequency>
    <directories check_all="yes" realtime="yes">/etc,/usr/bin,/usr/sbin</directories>
    <directories check_all="yes">/bin,/sbin,/boot</directories>
    <ignore>/etc/mtab</ignore>
    <ignore>/etc/hosts.deny</ignore>
  </syscheck>

  <!-- Rootcheck (rootkit detection) -->
  <rootcheck>
    <frequency>43200</frequency>
    <rootkit_files>/var/ossec/etc/shared/rootkit_files.txt</rootkit_files>
    <rootkit_trojans>/var/ossec/etc/shared/rootkit_trojans.txt</rootkit_trojans>
  </rootcheck>

  <!-- Active response (blocking) -->
  <active-response>
    <command>firewall-drop</command>
    <location>local</location>
    <rules_id>5710,5712,5716</rules_id>
    <timeout>600</timeout>
  </active-response>
</ossec_config>

Correlation Rules

Correlation is the SIEM 's core value proposition. A single failed login is noise. Five failed logins from the same IP across different hosts in 60 seconds is an incident.

Wazuh Brute Force Rule

<!-- /var/ossec/etc/rules/local_rules.xml -->
<group name="local,syslog,sshd,">

  <!-- Base rule: SSH authentication failure -->
  <rule id="100001" level="5">
    <decoded_as>sshd</decoded_as>
    <description>SSH authentication failure</description>
    <group>authentication_failed,sshd,</group>
  </rule>

  <!-- Escalation: 8 failures from same source within 5 minutes -->
  <rule id="100002" level="10" frequency="8" timeframe="300">
    <if_matched_sid>100001</if_matched_sid>
    <same_source_ip />
    <description>SSH brute force: 8 failures from same IP in 5 min</description>
    <group>authentication_failures,brute_force,</group>
    <mitre>
      <id>T1110</id>
    </mitre>
  </rule>

  <!-- Critical: 15 failures from same source within 5 minutes -->
  <rule id="100003" level="12" frequency="15" timeframe="300">
    <if_matched_sid>100001</if_matched_sid>
    <same_source_ip />
    <description>SSH brute force CRITICAL: 15 failures in 5 min</description>
    <group>authentication_failures,brute_force,</group>
  </rule>

  <!-- Success after failure: credential stuffing success -->
  <rule id="100004" level="12">
    <if_matched_sid>100001</if_matched_sid>
    <if_sid>5715</if_sid>  <!-- SSH authentication success -->
    <same_source_ip />
    <timeframe>300</timeframe>
    <description>SSH brute force succeeded — login after failures</description>
    <group>authentication_failures,brute_force_success,</group>
  </rule>

</group>

Data Onboarding

Getting data into the SIEM is the hardest part. Common patterns:

Syslog Input Pipeline

Source → Format (RFC 3164/5424) → Transport (UDP 514, TCP 514, TCP/TLS 6514) → Parser → Index
						
# Logstash grok pattern library for common log formats
# SSH
%{SYSLOGTIMESTAMP} %{HOSTNAME} sshd\[%{POSINT}\]: %{GREEDYDATA:sshd_message}

# Apache/Nginx Combined
%{IPORHOST:clientip} %{USER:ident} %{USER:auth} \[%{HTTPDATE:timestamp}\] "%{WORD:verb} %{DATA:request} HTTP/%{NUMBER:httpversion}" %{NUMBER:response} (?:%{NUMBER:bytes}|-) "(?:%{DATA:referrer}|-)" "%{DATA:user_agent}"

# Windows Event Log (XML)
<Event[^>]*><System>.*?<EventID[^>]*>(?<event_id>\d+)</EventID>.*?</System>.*?<EventData>(?<event_data>.*?)</EventData>

Sigma Rule Integration

Sigma is a generic, text-based rule format for SIEM detections. Rules are SIEM -agnostic and can be compiled with sigma-cli (the current converter, built on pySigma) to Elasticsearch queries, Splunk SPL, QRadar AQL, and other backends. The legacy sigmac script is deprecated. 

# sigma/rules/linux/process_creation/shell_suspicious_reverse_shell.yml
title: Suspicious Reverse Shell Connection
id: 3b1a0e3a-7e6e-4a5f-8b9c-0d1e2f3a4b5c
status: stable
description: Detects reverse shell command line patterns
author: SOC Team
date: 2026-06-26

logsource:
  product: linux
  category: process_creation

detection:
  selection:
    CommandLine|contains:
      - 'bash -i >& /dev/tcp/'
      - 'python -c "import socket'
      - 'nc -e /bin/sh'
      - 'sh -i >& /dev/tcp/'
      - 'python3 -c "import os,pty,socket'
      - 'mkfifo /tmp/'
      - 'socat exec:'
  condition: selection

falsepositives:
  - Legitimate administrative scripts using similar patterns
  - Penetration testing activities

level: critical
tags:
  - attack.execution
  - attack.t1059
  - attack.t1059.004
						
# Compile Sigma rule to an Elasticsearch Lucene query
sigma convert -t es-ql sigma/rules/linux/process_creation/shell_suspicious_reverse_shell.yml

# Compile to Splunk SPL
sigma convert -t splunk sigma/rules/linux/process_creation/shell_suspicious_reverse_shell.yml

Alert Tuning

The ratio of noise to signal in a raw SIEM is roughly 1000:1. Tuning reduces false positives to a manageable level. 

# Tuning strategies in order of effectiveness:

# 1. Exclude known-good patterns at the rule level
exceptions:
  - process.name: ["svchost.exe", "RuntimeBroker.exe"]
  - src_ip: ["10.0.0.0/8", "monitoring-server"]
  - interval: "outside business hours only"

# 2. Suppress by source attribute
suppression:
  - field: src_ip
    duration: 3600s  # suppress duplicate alerts from same IP for 1 hour

# 3. Threshold-based escalation
# Alert only if count > N within time window T

# 4. Risk scoring
# Assign scores per event; alert on cumulative risk exceeding threshold
event_score: { "failed_login": 1, "new_outbound_connection": 3, "privilege_escalation": 8 }
alert_threshold: 10

Deployment Checklist

  1. Collectors : Deploy Filebeat/Winlogbeat to every host. Start with system logs + auth logs.
  2. Parsers : Write Logstash grok patterns for every log source. Test with sample logs.
  3. Index Templates : Define mappings for each log type to avoid mapping explosions.
  4. Dashboards : Create per-source overviews ( SSH activity, web traffic, Windows events).
  5. Correlation Rules : Start with 5-10 high-value rules (brute force, privilege escalation, C2 beaconing).
  6. Alert Tuning : Run rules in "log only" mode for 2 weeks. Tune exclusions. Then enable notifications.
  7. Retention : Configure ILM policies aligned with regulatory requirements.
  8. Backup : Snapshot Elasticsearch indices daily. Test restoration quarterly.

Challenge

Write a Go tool that reads an auth log from standard input, extracts failed and successful SSH logins, and correlates them per source address. Print an alert when one address produces five failures inside a sixty second window, and print a second alert when that same address later succeeds. Each input line has the form <RFC3339 timestamp> <fail|success> <source ip> <user> . 

package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"
	"time"
)

const (
	window  = 60 * time.Second
	lockout = 5 * time.Minute
)

func main() {

	failures := make(map[string][]time.Time)

	scanner := bufio.NewScanner(os.Stdin)

	for scanner.Scan() {

		fields := strings.Fields(scanner.Text())

		if len(fields) != 4 {
			continue
		}

		stamp, err := time.Parse(time.RFC3339, fields[0])

		if err != nil {
			continue
		}

		action := fields[1]
		source := fields[2]
		user := fields[3]

		switch action {

		case "fail":
			recent := make([]time.Time, 0, len(failures[source])+1)

			for _, t := range failures[source] {
				if stamp.Sub(t) <= window {
					recent = append(recent, t)
				}
			}

			recent = append(recent, stamp)
			failures[source] = recent

			if len(recent) == 5 {
				fmt.Printf("[BRUTE FORCE] %s user=%s failures=%d\n", source, user, len(recent))
			}

		case "success":
			for _, t := range failures[source] {
				if stamp.Sub(t) <= lockout {
					fmt.Printf("[SUCCESS AFTER FAILURE] %s user=%s\n", source, user)
					break
				}
			}

		}

	}

	if err := scanner.Err(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

}
