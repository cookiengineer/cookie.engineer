PIE (Position-Independent Executable)

How PIE compiles the main executable as position-independent code so the kernel can load it at a random base address.

Overview

Without PIE the main executable loads at a fixed address, so every gadget, function pointer, and return address inside it is known to an attacker even when ASLR randomizes the stack, heap, and libraries. PIE compiles the executable as position-independent code so the kernel can map it at a random base, using RIP -relative addressing plus the GOT and PLT. This article covers the ET_DYN ELF type, the load process, how to check a binary, and how PIE is bypassed. After reading you can tell whether a binary is PIE and explain what an information leak buys an attacker.

Required Reading

  • ASLR - address space layout randomization and entropy
  • ELF - program headers, segments, and symbol tables
  • Dynamic Linking - GOT, PLT, lazy binding, and ld-linux.so

The Problem PIE Solves

Without PIE, every execution of a non-PIE binary loads the executable at the same fixed virtual address. On x86-64 Linux, this address is typically 0x400000 : 

0x400000  ─── .interp, .note, .gnu.hash
0x401000  ─── .text    (executable code — ALWAYS at 0x401000)
0x402000  ─── .rodata  (read-only data)
0x403000  ─── .data, .got, .bss  (writable, ALWAYS at 0x403000)

Every ROP gadget in the binary, every function pointer, every GOT entry, every return address targeting code in the main binary - all at fixed, known addresses. ASLR randomizes the stack, heap, and libraries, but not the executable itself. This means an attacker can find usable ROP gadgets in the binary without needing an information leak. An entire class of exploits (ret2plt, ret2csu, calling main-binary functions directly) requires zero address knowledge.

PIE compiles the main executable as position-independent code, identical in principle to how shared libraries (.so files) are compiled. The kernel's ELF loader can then place the binary at a random base address - the same 28 bits of entropy that shared libraries enjoy. Every address in the binary becomes unknown to an attacker who hasn't first leaked a PIE address.

Non-PIE vs PIE: ELF Header Difference

The fundamental difference is a single field in the ELF header: e_type . 

# Non-PIE binary (legacy, fixed address)
readelf -h /usr/bin/old_binary | grep Type
# Type: EXEC (Executable file)

# PIE binary (modern, randomized base)
readelf -h /bin/ls | grep Type
# Type: DYN (Shared object file)

A non-PIE executable is ET_EXEC (type 2). The kernel's ELF loader ( fs/binfmt_elf.c ) uses elf_map to load it at the fixed address specified in the program headers. The segments have absolute virtual addresses: 

Program Headers (non-PIE):
  Type       Offset             VirtAddr          PhysAddr          FileSiz  MemSiz   Flg Align
  LOAD       0x0000000000000000 0x0000000000400000 0x0000000000400000 0x000500 0x000500 R   0x1000
  LOAD       0x0000000000001000 0x0000000000401000 0x0000000000401000 0x000200 0x000200 R E 0x1000
  LOAD       0x0000000000002000 0x0000000000402000 0x0000000000402000 0x000100 0x000100 R   0x1000
  LOAD       0x0000000000002df0 0x0000000000403df0 0x0000000000403df0 0x000220 0x000220 RW  0x1000

Notice the absolute VirtAddr values - every run uses exactly 0x400000 , 0x401000 , etc.

A PIE executable is ET_DYN (type 3, same as a shared library). Its program headers use relative addresses (offset from load base), and the kernel's ELF loader maps it via mmap with a randomized base: 

Program Headers (PIE):
  Type       Offset             VirtAddr          PhysAddr          FileSiz  MemSiz   Flg Align
  LOAD       0x0000000000000000 0x0000000000000000 0x0000000000000000 0x000600 0x000600 R   0x1000
  LOAD       0x0000000000001000 0x0000000000001000 0x0000000000001000 0x01a000 0x01a000 R E 0x1000
  LOAD       0x000000000001b000 0x000000000001b000 0x000000000001b000 0x008000 0x008000 R   0x1000
  LOAD       0x0000000000023000 0x0000000000024000 0x0000000000024000 0x003000 0x003000 RW  0x1000

VirtAddr values are relative to the base (starting at 0). At runtime, the kernel adds the random base address to these offsets. The actual virtual address of .text becomes random_base + 0x1000 .

# Entry point address: 0x401020

echo "=== PIE ==="

# Type: DYN (Shared object file)
# Entry point address: 0x1020  (relative! runtime = base + 0x1020)

# Check dynamic section — PIE has interpreter and NEEDED entries

# 0x0000000000000001 (NEEDED)  Shared library: [libc.so.6]

# Non-PIE also has these — the difference is e_type, not dynamic linking

How Position-Independent Code Works

Position-independent code avoids absolute addresses in the instruction stream. Instead, it uses:

1. RIP-relative addressing for code and local data: The x86-64 ISA added RIP -relative addressing ( [rip + offset] ) specifically to support position-independent code. The CPU computes the target address as RIP + sign-extended-32-bit-offset , where RIP points to the next instruction. 

; Non-PIC (absolute addressing — fixed address embedded in instruction)
mov    rax, QWORD PTR [0x404020]    ; loads from fixed address 0x404020
call   0x401050                      ; call fixed address

; PIC (RIP-relative addressing — offset from current instruction)
mov    rax, QWORD PTR [rip+0x2f3f]  ; loads from rip + offset
call   QWORD PTR [rip+0x2f39]       ; indirect call via GOT entry

RIP -relative addressing has a +/-2 GiB range (32-bit signed offset), which is sufficient for a single shared library or executable image. It's the primary mechanism that makes PIE possible on x86-64.

2. GOT (Global Offset Table) for external/global data: The GOT is a table of pointers in the .got section. At load time, the dynamic linker fills in the actual addresses of all global symbols (functions and data). Code accesses globals through the GOT: 

// C source
extern int global_counter;     // defined in another .so or in .data
void increment(void) {
    global_counter++;
}

// PIE/PIC compilation (conceptual asm):
// mov rax, [rip + got_offset_for_global_counter]
// inc dword [rax]

The GOT itself is at a known offset from the code that references it (within the +/-2 GiB RIP -relative range). The GOT contains the absolute addresses resolved by the dynamic linker.

3. PLT (Procedure Linkage Table) for cross-module function calls: When calling a function from a shared library (or another DSO), the compiler generates a call to a PLT stub: 

; Calling puts() from a PIE binary:
call   puts@plt
; This jumps to a stub in .plt:
;   puts@plt:
;     jmp    [rip + GOT[puts]]     ; indirect jump through GOT entry
;     push   relocation_index      ; lazy binding: push index
;     jmp    .plt0                 ; lazy binding: call resolver

The PLT stub is in the same load module as the call site, so RIP -relative addressing works. At load time (or first call, with lazy binding), the GOT entry for puts is filled with the actual address in libc. After resolution, jmp [rip+GOT[puts]] goes directly to puts in libc.

The PIE Load Process

When the kernel executes a PIE binary:

  1. sys_execve -> do_execveat_common -> search_binary_handler -> load_elf_binary (fs/binfmt_elf.c)
  2. The ELF loader reads the program headers and sees ET_DYN
  3. elf_map is called, which uses vm_mmap (ultimately do_mmap ) to create mappings
  4. For ET_DYN , the base address passed to elf_map is 0 (let kernel choose), not the p_vaddr from program headers
  5. The kernel's mmap region allocator ( arch_get_unmapped_area_topdown ) picks a random address
  6. This random address becomes the ELF base ( load_bias )
  7. All segment virtual addresses = load_bias + p_vaddr

The dynamic linker ( ld-linux-x86-64.so.2 ) receives the ELF base through the auxiliary vector ( AT_BASE and AT_PHDR ): 

// The auxiliary vector (auxv) is placed on the stack by the kernel
// Relevant entries for PIE:
#define AT_PHDR    3   // Address of program headers (base-dependent)
#define AT_PHENT   4   // Size of a program header entry
#define AT_PHNUM   5   // Number of program headers
#define AT_BASE    7   // Base address of the dynamic linker (ld-linux.so)
#define AT_ENTRY   9   // Entry point of the program (base-dependent)
#define AT_EXECFD 22   // File descriptor of the executable

The startup code ( _start in crt1.o ) uses these to find the GOT and initialize the runtime: 

; crt1.o _start (simplified):
; On entry, the stack contains: argc, argv, envp, auxv
; The dynamic linker has already:
;   - Mapped all shared libraries
;   - Resolved GOT entries (if BIND_NOW) or set up lazy binding
;   - Transferred control to _start (via AT_ENTRY)

_start:
    xor    ebp, ebp            ; mark deepest stack frame
    mov    rdi, [rsp]          ; argc
    lea    rsi, [rsp+8]        ; argv
    ; ... find __libc_start_main via GOT ...
    call   __libc_start_main

Compilation Flags and the PIE Toolchain

gcc flag Effect
-fPIE Generate position-independent code (codegen)
-fpie Same as-fPIEbut may use smaller/faster code model
-pie Link as position-independent executable (linker flag)
-no-pie Link as fixed-address executable (non-PIE)
-fPIC Generate position-independent code for shared libraries
-fpic Same as-fPICwith smaller GOT constraints

Lowercase vs uppercase: - -fPIE / -fPIC uses the "large" code model - no limit on GOT size. Safe for any code size. - -fpie / -fpic uses the "small" code model - GOT limited to a smaller size for better performance. Fails if the GOT exceeds the limit. - On x86-64, both produce identical code in practice (the small model's limits are generous on 64-bit). Use -fPIE / -fPIC for maximum compatibility.

ArchLinux defaults: ArchLinux compiles all packages with PIE enabled by default. The makepkg configuration in /etc/makepkg.conf sets: 

CFLAGS="-march=x86-64 -mtune=generic -O2 -pipe -fno-plt -fexceptions \
        -Wp,-D_FORTIFY_SOURCE=3 -Wformat -Werror=format-security \
        -fstack-clash-protection -fcf-protection"
LDFLAGS="-Wl,-O1 -Wl,--sort-common -Wl,--as-needed -Wl,-z,relro -Wl,-z,now \
         -Wl,-z,pack-relative-relocs"

-fno-plt is an x86-64 optimization that bypasses the PLT for external function calls, using GOT-based indirect calls directly. This reduces lazy binding overhead and is usually combined with -z now (full RELRO).

PIE vs Non-PIE Address Comparison

// pie_demo.c — demonstrate PIE vs non-PIE address randomization
// Compile:
//   gcc -no-pie -o pie_demo_nopie pie_demo.c
//   gcc -pie   -o pie_demo_pie   pie_demo.c

#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

int global_init = 42;
int global_bss;

__attribute__((noinline))
void my_function(void) {
    printf("Inside my_function at %p\n", (void *)my_function);
}

int main(void) {
    void *handle = dlopen(NULL, RTLD_LAZY);
    printf("=== Binary Identity ===\n");
    printf("main:          %p\n", (void *)main);
    printf("my_function:   %p\n", (void *)my_function);
    printf("global_init:   %p  (value=%d)\n", (void *)&global_init, global_init);
    printf("global_bss:    %p  (value=%d)\n", (void *)&global_bss, global_bss);
    printf("printf@plt:    %p\n", (void *)&printf);
    printf("printf@libc:   %p\n", dlsym(RTLD_NEXT, "printf"));
    printf("environ (stack):%p\n", (void *)&environ);

    // ELF type check
    Dl_info info;
    if (dladdr(main, &info)) {
        printf("\nBinary: %s\n", info.dli_fname);
        printf("Base:   %p\n", info.dli_fbase);
    }

    dlclose(handle);
    return 0;
}
						
# Compile both
gcc -no-pie -o pie_demo_nopie pie_demo.c -ldl
gcc -pie   -o pie_demo_pie   pie_demo.c -ldl

# Compare ELF type
readelf -h pie_demo_nopie | grep Type
# Type: EXEC (Executable file)
readelf -h pie_demo_pie | grep Type
# Type: DYN (Shared object file)

# Run non-PIE multiple times — same addresses every time
echo "=== Non-PIE (3 runs) ==="
for i in 1 2 3; do
    echo "--- Run $i ---"
    ./pie_demo_nopie | grep -E 'main|function|global_init|Base'
done
# main:          0x401146  ← SAME every run
# my_function:   0x401126  ← SAME every run
# global_init:   0x40401c  ← SAME every run
# Base:          0x400000  ← SAME every run

# Run PIE multiple times — addresses change
echo "=== PIE (3 runs) ==="
for i in 1 2 3; do
    echo "--- Run $i ---"
    ./pie_demo_pie | grep -E 'main|function|global_init|Base'
done
# main:          0x5b7a3c001149  ← changes
# my_function:   0x5b7a3c001129  ← changes
# global_init:   0x5b7a3c00401c  ← changes
# Base:          0x5b7a3c000000  ← changes
# BUT: offset from base is CONSTANT
#   main - base = 0x1149 every time
#   global_init - base = 0x401c every time

Key insight: With PIE, the base changes but all internal offsets are fixed. An attacker who leaks a single PIE address (e.g., main ) can compute all other PIE addresses by adding/subtracting known offsets. This is why PIE alone is not a complete mitigation - it must be combined with other defenses that prevent address leaks.

Debugging PIE in GDB

GDB disables ASLR by default (via personality(ADDR_NO_RANDOMIZE) on the debuggee) to make addresses reproducible across runs. This also disables PIE randomization. To work with PIE randomization in GDB: 

# GDB with ASLR enabled
gdb -ex "set disable-randomization off" ./pie_demo_pie

# Inside GDB:
(gdb) start
# Temporary breakpoint at main...
# Note the address — it changes between GDB sessions

(gdb) info proc mappings
# Shows randomized base and all mappings

# The GDB 'piebase' command (from pwndbg/gef) shows the PIE base
(gdb) piebase
# Calculated as: &main - main_offset_in_elf

# Manual calculation:
(gdb) p/x (unsigned long)&main - (unsigned long)&main
# GDB resolves &main to the absolute address
# Get the file offset with:
(gdb) shell readelf -s ./pie_demo_pie | grep ' main$'
# Gives the offset within the binary. Subtract from GDB's &main = base.

# pwntools checksec:
pwn checksec ./pie_demo_pie
# Arch:     amd64-64-little
# RELRO:    Full RELRO
# Stack:    No canary found
# NX:       NX enabled
# PIE:      PIE enabled

Debugging PIE binaries without ASLR

# PIE binary without randomization loads at a fixed base
# (but still uses position-independent code internally)
setarch $(uname -m) -R gdb ./pie_demo_pie
(gdb) start
# Base will be at a fixed, predictable address (usually 0x555555554000)
# This address is determined by the kernel's default ET_DYN base

PIE Code Generation: Assembly Deep Dive

Compare the disassembly of the same function compiled with and without PIE:

// sample.c
extern int external_var;
int global_var = 0x539;

int get_global(void) {
    return global_var;
}

int get_external(void) {
    return external_var;
}

Non-PIE (gcc -no-pie -O2)

# objdump -d sample_nopie.o
get_global:
    mov    eax, DWORD PTR [rip+0x0]   # actually: [rip + 0x2e35]
    # The linker will patch 0x0 with the absolute address of global_var
    ret

get_external:
    mov    rax, QWORD PTR [rip+0x0]   # GOT entry for external_var
    # Actually: [rip + offset_to_GOT_EXTERNAL_VAR]
    mov    eax, DWORD PTR [rax]
    ret

PIE (gcc -pie -fPIE -O2)

# objdump -d sample_pie.o  (identical at .o stage!)
get_global:
    mov    eax, DWORD PTR [rip+0x0]   # resolved by linker: RIP-relative
    ret

get_external:
    mov    rax, QWORD PTR [rip+0x0]   # GOT entry, resolved by linker
    mov    eax, DWORD PTR [rax]
    ret

The .o files are similar - the difference emerges at link time. The linker for PIE generates .got , .got.plt , and appropriate relocations. For non-PIE, the linker hardcodes absolute addresses (or uses the .got but with R_X86_64_RELATIVE relocations that the dynamic linker resolves at load time by adding the base).

Linker relocations for PIE

readelf -r ./pie_demo_pie | head -40
# Relocation section '.rela.dyn' at offset 0x540 contains 12 entries:
#   Offset          Info           Type           Sym. Value    Sym. Name + Addend
# 000000003d98  000800000008 R_X86_64_RELATIVE                    1140
# 000000003da0  000800000008 R_X86_64_RELATIVE                    1100
# 000000004010  000800000008 R_X86_64_RELATIVE                    4010
# 000000003fc8  000200000007 R_X86_64_JUMP_SLOT 0000000000000000 puts@GLIBC_2.2.5 + 0
# 000000003fd0  000300000007 R_X86_64_JUMP_SLOT 0000000000000000 printf@GLIBC_2.2.5 + 0
# ...

R_X86_64_RELATIVE relocations mean: "at this GOT address, store (load_base + addend)". The dynamic linker processes these before transferring control to _start . This is how PIE resolves its own internal references.

Performance Overhead

PIE introduces measurable but small overhead from the extra indirection:

Operation Non-PIE PIE Overhead
Call external function (1st) call addr-> PLT -> resolver same 0%
Call external function (cached) call addr-> PLT ->jmp [GOT] same 0%
Call local function call imm32(direct) call imm32(direct, RIP-relative) 0%
Access global variable mov eax, [abs_addr](1 insn) mov rax, [rip+got]; mov eax, [rax](2 insns) ~1 instruction
Access static local mov eax, [rip+offset] mov eax, [rip+offset] 0%

The primary overhead comes from accessing global variables: PIE requires loading the GOT entry first, then dereferencing it. This is one extra load instruction per global variable access. For non-PIE, the absolute address is embedded directly.

Measured overhead on real workloads (Phoronix benchmarks, 2017):~1-3% on x86-64. This small cost is why most distributions enable PIE by default - the security benefit vastly outweighs the performance impact.

The -fno-plt optimization (enabled on ArchLinux by default) eliminates PLT indirection for external function calls, reducing some of the overhead. With -fno-plt , calls go through GOT entries directly, skipping the PLT jump. It is usually combined with -z now (full RELRO, no lazy binding).

PIC vs PIE: The Distinction

PIC (Position-Independent Code) PIE (Position-Independent Executable)
Target Shared libraries (.so) Main executables
gcc flags -fPIC -shared -fPIE -pie
ELF type ET_DYN(type 3) ET_DYN(type 3)
Symbol preemption Interposable by default None by default (executables do not export symbols)
GOT size Larger (supports interposition) Smaller (no interposition for unexported symbols)
Startup _init/_finicalled by ld-linux _start->__libc_start_main->main
Entry point None (or_init) _start(from crt1.o)
Can have `main`? No Yes

The internal mechanism is identical. Both use RIP -relative addressing, GOT, and PLT. The practical difference is how the linker treats symbol visibility and interposition. Shared libraries must support symbol interposition (LD_PRELOAD overriding of functions), which requires all external symbols to go through the GOT even for intra-library calls. PIE executables use -Bsymbolic (or -Bsymbolic-functions ), which binds intra-binary references directly, skipping the GOT for local symbols.

Static-PIE

A recent development (supported since binutils 2.31 and glibc 2.27) is -static-pie . This produces a statically linked executable that is still position-independent: 

gcc -static-pie -o static_pie_demo pie_demo.c -ldl

readelf -h static_pie_demo | grep Type
# Type: DYN (Shared object file)  ← still PIE

readelf -d static_pie_demo | head
# No NEEDED entries, no INTERP — fully static

readelf -l static_pie_demo | grep -E 'LOAD|DYNAMIC'
# LOAD segments still present, DYNAMIC segment for self-relocation

A static-PIE binary performs its own relocations at startup (in _start before calling __libc_start_main ). This combines the security of ASLR with the simplicity of static linking - no shared libraries, no dynamic linker, single-file deployment.

Tools for Checking PIE Status

# 1. readelf — most authoritative
readelf -h binary | grep -E 'Type:'
# Type: DYN  → PIE
# Type: EXEC → non-PIE

# 2. file command
file /bin/ls
# /bin/ls: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV)...
#                              ^^^

# 3. hardening-check (from devscripts package, Debian/Ubuntu)
hardening-check /bin/ls
# Position Independent Executable: yes

# 4. scanelf (from pax-utils on Arch)
scanelf -e /bin/ls
# TYPE   STACK/RELRO  FILE
# ET_DYN RW- R--      /bin/ls
# ^^^^^^
# ET_DYN = PIE

# 5. checksec (pwntools)
pwn checksec /bin/ls
# [*] '.../bin/ls'
#     Arch:     amd64-64-little
#     RELRO:    Full RELRO
#     Stack:    Canary found
#     NX:       NX enabled
#     PIE:      PIE enabled

# 6. Bulk audit — find non-PIE binaries on the system
for bin in /usr/bin/*; do
    if [ -f "$bin" ] && [ -x "$bin" ]; then
        type=$(readelf -h "$bin" 2>/dev/null | grep 'Type:' | awk '{print $2}')
        if [ "$type" = "EXEC" ]; then
            echo "non-PIE: $bin"
        fi
    fi
done
# On modern ArchLinux, this should return nothing

Disabling PIE for Learning

When studying binary exploitation, non-PIE binaries simplify the learning process by providing fixed, predictable addresses: 

# Compile without PIE
gcc -no-pie -o vulnerable vulnerable.c

# The binary loads at a fixed base:
#   .text:  0x401000
#   .data:  0x404000
#   .bss:   0x404020+

# All function addresses are known at compile time:
objdump -d vulnerable | grep '<main>:'
# 0000000000401146 <main>:
# main is ALWAYS at 0x401146 on every run

# GDB shows the same addresses every session:
gdb -q ./vulnerable
(gdb) p main
# $1 = {int (int, char **)} 0x401146 <main>

Re-enabling PIE in your own projects

# GCC defaults to -pie on ArchLinux. Only use -no-pie for learning.
# For production code:
gcc -fPIE -pie -o production_binary source.c
# OR rely on the default (ArchLinux enables PIE by default)
gcc -o production_binary source.c  # PIE by default on Arch

PIE Bypass Techniques

Technique How it defeats PIE Defense
Info leak of a PIE address Leak return address or GOT entry -> compute base -> all addresses known Control-flow integrity, stack canaries
Partial overwrite of return address Overwrite only low 1-2 bytes of a PIE return address -> jump within same page Stack canaries, shadow stacks
Brute-force PIE base 28 bits entropy too high for brute force alone, but combined with partial leaks can reduce search space Fork rate limiting, crash detection
Data-only attack Modify data-only state (no code pointers touched) -> PIE irrelevant Data flow integrity (DFI)
ret2plt Call PLT entries from the binary (fixed offsets from base) without knowing base RELRO, ASLR on libc
ret2dlresolve Forge fake relocation entries to call arbitrary functions via the dynamic linker Full RELRO (-z now)

Partial overwrite demo against PIE

// pie_partial_overwrite.c — demonstrate PIE's protection against partial overwrites
// Compile: gcc -pie -fPIE -o pie_partial pie_partial_overwrite.c
//          gcc -no-pie   -o nopie_partial pie_partial_overwrite.c

#include <stdio.h>

void target_function(void) {
    printf("target_function called!\n");
}

__attribute__((noinline))
void benign_function(void) {
    printf("benign_function: %p\n", (void *)benign_function);
}

int main(void) {
    printf("target_function:  %p\n", (void *)target_function);
    printf("benign_function:  %p\n", (void *)benign_function);

    // With non-PIE, the low bytes of these addresses are different
    // but the high bytes are the same (0x000000000040...).
    // A 2-byte partial overwrite can redirect benign → target.
    //
    // With PIE, the high bytes are randomized. A 2-byte partial overwrite
    // preserves the high bytes, so you can only redirect WITHIN the same
    // 64 KiB region — target and benign must be within 0x10000 of each other.

    unsigned long t = (unsigned long)target_function;
    unsigned long b = (unsigned long)benign_function;
    printf("Difference:       0x%lx\n", b > t ? b - t : t - b);
    printf("Low 2 bytes of target: 0x%04lx\n", t & 0xFFFF);
    printf("Low 2 bytes of benign: 0x%04lx\n", b & 0xFFFF);

    // For non-PIE, target=0x401146, benign=0x401156 — diff=0x10
    //   A 1-byte overwrite of the return address LSB changes 0x56→0x46
    // For PIE, target=0x55d4...1146, benign=0x55d4...1156 — same low bytes
    //   BUT: to redirect to target, you must know the PIE base
    //   Without a leak, the high bytes (0x55d4...) are unknown
    return 0;
}

The Auxiliary Vector and PIE

The kernel communicates the PIE base to the dynamic linker through the auxiliary vector. This can be observed: 

// print_auxv.c — display auxiliary vector entries
// Compile: gcc -o print_auxv print_auxv.c
#define _GNU_SOURCE
#include <stdio.h>
#include <elf.h>
#include <sys/auxv.h>

int main(int argc, char **argv, char **envp) {
    // Walk past envp to find auxv
    char **ep = envp;
    while (*ep) ep++;
    ep++;  // NULL terminator

    Elf64_auxv_t *auxv = (Elf64_auxv_t *)ep;

    printf("Auxiliary Vector:\n");
    for (int i = 0; auxv[i].a_type != AT_NULL; i++) {
        switch (auxv[i].a_type) {
        case AT_PHDR:   printf("AT_PHDR:   %p\n", (void *)auxv[i].a_un.a_val); break;
        case AT_PHENT:  printf("AT_PHENT:  %lu\n", auxv[i].a_un.a_val); break;
        case AT_PHNUM:  printf("AT_PHNUM:  %lu\n", auxv[i].a_un.a_val); break;
        case AT_BASE:   printf("AT_BASE:   %p\n", (void *)auxv[i].a_un.a_val); break;
        case AT_ENTRY:  printf("AT_ENTRY:  %p\n", (void *)auxv[i].a_un.a_val); break;
        case AT_EXECFN: printf("AT_EXECFN: %s\n",  (char *)auxv[i].a_un.a_val); break;
        case AT_RANDOM: printf("AT_RANDOM: %p  (16 random bytes)\n",
                               (void *)auxv[i].a_un.a_val); break;
        }
    }

    // Show actual PIE base via dladdr
    Dl_info info;
    dladdr(main, &info);
    printf("\ndli_fbase: %p  (actual PIE load base)\n", info.dli_fbase);

    return 0;
}

Note that AT_BASE is the dynamic linker's base address, not the PIE executable's base. The PIE base can be computed as AT_PHDR - p_offset_of_phdr or AT_ENTRY - entry_point_offset .

Linux Kernel Support for PIE

The kernel doesn't explicitly know about "PIE" - it only knows about ET_DYN vs ET_EXEC . The ELF loader in fs/binfmt_elf.c treats both similarly: 

// Simplified kernel ELF loading logic:
if (elf_ex->e_type == ET_EXEC) {
    // Fixed-address executable: load at p_vaddr
    load_bias = 0;
    // elf_map() uses MAP_FIXED at the p_vaddr from headers
} else if (elf_ex->e_type == ET_DYN) {
    // PIE or shared library: load at randomized address
    load_bias = 0;  // let the kernel choose via mmap
    // elf_map() passes 0 as addr → kernel picks random location
    // load_bias is calculated after mmap: actual_base - p_vaddr
}

For ET_DYN , the kernel uses ELF_ET_DYN_BASE (architecture-dependent) as a hint for the mmap allocator. On x86-64, this is typically 0x555555554000 when ASLR is disabled, and fully randomized when ASLR is active. This is why PIE binaries load at 0x55... addresses in GDB (without ASLR disabling) vs 0x7f... for shared libraries - the mmap allocator separates executables from libraries.

PIE in Defense in Depth

PIE is a foundational mitigation that extends ASLR to the executable itself. Its effectiveness depends on the attacker's ability to leak addresses:

  • Without an info leak: PIE adds 28 bits of entropy to the binary's code and data. Brute force is impractical on 64-bit.
  • With an info leak: PIE provides zero security - all PIE addresses are computable once one is known.
  • Combined with ASLR + DEP + RELRO + canaries: PIE forces the attacker to succeed at multiple steps: achieve a write primitive, leak at least one address, bypass canaries, and chain ROP gadgets from known offsets.

PIE does not eliminate exploitation. It raises the cost and complexity. In a defense-in-depth architecture, PIE forces attackers to combine an information leak with their primary exploit

  • a significantly harder problem than simply hardcoding addresses.

Challenge

Write a Go tool that classifies an ELF file as non-PIE, PIE, or a shared library. The debug/elf package exposes the ELF type and program headers directly. The DF_1_PIE flag in DT_FLAGS_1 identifies a PIE even when it is statically linked, so use it first and fall back to a PT_INTERP program header. 

package main

import (
	"debug/elf"
	"fmt"
	"os"
)

func classify(path string) (string, error) {
	file, err := elf.Open(path)
	if err != nil {
		return "", err
	}
	defer file.Close()

	switch file.Type {
	case elf.ET_EXEC:
		return "ET_EXEC (non-PIE, fixed base)", nil
	case elf.ET_DYN:
		if flags, err := file.DynValue(elf.DT_FLAGS_1); err == nil {
			for _, flag := range flags {
				if flag&uint64(elf.DF_1_PIE) != 0 {
					return "ET_DYN (PIE, randomized base)", nil
				}
			}
		}
		for _, prog := range file.Progs {
			if prog.Type == elf.PT_INTERP {
				return "ET_DYN (PIE, randomized base)", nil
			}
		}
		return "ET_DYN (shared library, no interpreter)", nil
	default:
		return fmt.Sprintf("%s (not an executable)", file.Type), nil
	}
}

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "usage: %s <elf-binary>\n", os.Args[0])
		os.Exit(1)
	}

	result, err := classify(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, "error:", err)
		os.Exit(1)
	}

	fmt.Printf("%s: %s\n", os.Args[1], result)
}

Run it against /bin/ls and against a binary built with gcc -no-pie . Extend it to print the entry point and to report whether the binary has a PT_GNU_RELRO segment and a PT_GNU_STACK segment without execute permission.
