Tracing Frameworks

Comparison of every major Linux tracing framework - ftrace, perf, eBPF /bpftrace, SystemTap, LTTng, DTrace, ETW, EventPipe - feature matrix, overhead analysis, decision flowcharts, and practical commands

Overview

The Linux kernel is arguably the most instrumented kernel in history, but the instrumentation is fractured across several frameworks, each with different tradeoffs, audiences, and philosophies. This article maps the landscape: what each framework does, how it works internally, what it is good at, and when you should pick it. It compares ftrace, perf, eBPF and bpftrace, SystemTap, LTTng, and the DTrace Linux port, then covers Windows ETW and .NET EventPipe for cross-platform context.

3. Ftrace

Ftrace is the original Linux kernel tracer, built directly into the kernel. It lives entirely within tracefs ( /sys/kernel/debug/tracing/ ) and requires no external tools.

3.1 Architecture

tracefs: /sys/kernel/debug/tracing/

Available tracers: function, function_graph, blk, mmiotrace, hwlat, nop

How function tracer works:
  At compile time (-pg / -fpatchable-function-entry):
    Each function has a NOP at its entry point.

  When function tracer is enabled:
    NOP → call _mcount() → ftrace trampoline → record timestamp + caller

  When disabled:
    NOP stays NOP — zero overhead

Filesystem interface:
  current_tracer   = function_graph
  set_ftrace_filter = do_sys_open
  set_ftrace_pid   = 1234
  tracing_on       = 1
  trace_pipe       ← streaming output
  trace            ← snapshot output

3.2 Ftrace Internals: The Trampoline

Normal function:
  do_sys_open:
    nop        ← 5-byte NOP (-fpatchable-function-entry=5)
    nop
    push rbp
    ...

Ftrace enabled:
  do_sys_open:
    call ftrace_caller  ← NOPs overwritten
    push rbp
    ...

The ftrace_caller:
  1. Save registers
  2. Read parent RIP to identify calling function
  3. Record event: timestamp, PID, function pointer, depth
  4. Call registered callbacks (function_graph, etc.)
  5. Restore registers
  6. Return to traced function

3.3 Ftrace Commands

# List available tracers
cat /sys/kernel/debug/tracing/available_tracers

# Function tracer for a specific function
echo do_sys_open > /sys/kernel/debug/tracing/set_ftrace_filter
echo function > /sys/kernel/debug/tracing/current_tracer
echo 1 > /sys/kernel/debug/tracing/tracing_on
cat /sys/kernel/debug/tracing/trace | head -50

# Wildcard filtering
echo 'vfs_*' > /sys/kernel/debug/tracing/set_ftrace_filter
echo 'ext4_*' >> /sys/kernel/debug/tracing/set_ftrace_filter

# Filter by PID
echo 1234 > /sys/kernel/debug/tracing/set_ftrace_pid

# Function graph: entry/exit with duration
echo function_graph > /sys/kernel/debug/tracing/current_tracer
cat /sys/kernel/debug/tracing/trace
# Output:
#  0)               |  SyS_write() {
#  0)   0.103 us    |    __fdget_pos();
#  0)   0.066 us    |    vfs_write();
#  0) + 10.387 us   |  }

# trace-cmd: user-friendly ftrace frontend
trace-cmd record -p function_graph -l 'vfs_*' myapp
trace-cmd report trace.dat
kernelshark trace.dat

# Dynamic kprobe events via tracefs
echo 'p:myprobe do_sys_open filename=%si' >> /sys/kernel/debug/tracing/kprobe_events
echo 1 > /sys/kernel/debug/tracing/events/kprobes/myprobe/enable
cat /sys/kernel/debug/tracing/trace
echo '-:myprobe' >> /sys/kernel/debug/tracing/kprobe_events

4. Perf

Perf provides access to hardware PMU counters, software events, tracepoints, and sampling via the perf_event_open() syscall.

4.1 Architecture

User space: perf tool
  perf record (sampling)
  perf stat   (counting)
  perf top    (live view)
  perf report (analysis)
  perf annotate (source interleave)
       │
       ▼
  perf_event_open() syscall
       │
       ▼
Kernel: Perf Event Subsystem
  ├── Hardware Events (PMU): cycles, instructions, cache-misses, branch-misses
  ├── Software Events: cpu-clock, page-faults, context-switches, cpu-migrations
  ├── Tracepoint Events: sched:*, syscalls:*, kmem:*, block:*
  ├── Probe Events: kprobe:*, uprobe:*
  ├── Cache Events: L1-dcache-load, LLC-load-misses, etc.
  └── BPF Programs: custom eBPF attached to any event
       │
       ▼
  Ring Buffer (per-CPU) → mmap'd to user space

4.2 Perf Commands

# === Counting (perf stat) ===
perf stat ls /
perf stat -e cycles,instructions,cache-misses,branch-misses ls /
perf stat -r 10 ls /                    # repeat 10x with stats
perf stat -a -A sleep 1                 # per-CPU breakdown
perf stat --topdown ls /                # top-down analysis (Intel)

# === Sampling (perf record) ===
perf record -F 99 -a -g -- sleep 30     # 99 Hz, all CPUs, call graph
perf record -F 99 -p 1234 -g -- sleep 30 # specific PID
perf record -e cache-misses -a -g -- sleep 30 # event-based
perf record -F 99 -a --call-graph dwarf -- sleep 30 # DWARF unwinding
perf record -b -a -- sleep 10           # LBR (Last Branch Record)

# === Reporting (perf report) ===
perf report                             # interactive TUI
perf report --stdio --sort comm,dso,symbol
perf annotate -s symbol_name            # disassemble + source

# === Live monitoring (perf top) ===
perf top
perf top -g                             # with call chains

# === Scripting (perf script) ===
perf script                             # dump raw samples
perf script --fields comm,pid,tid,time,event,ip,sym
perf script -s myscript.py              # Python scripting

# === Dynamic probes (perf probe) ===
perf probe --add 'vfs_read file=+0(%si):string count=%dx'
perf probe -x /bin/bash --add 'readline result=$retval'
perf probe --list
perf probe --del 'vfs_read'
perf record -e probe:vfs_read -a -- sleep 10
perf script | head -30

4.3 Perf Sampling Internals

Sampling at 99 Hz:
  Every ~10.1 ms, PMU counter overflows
  → PMU interrupt (NMI on x86)
  → perf NMI handler records:
      1. Instruction Pointer (RIP) — where CPU was
      2. Call chain (frame pointer or DWARF unwind)
      3. PID, TID, timestamp
      4. MMAP info (which binary at this address)
  → Sample written to per-CPU ring buffer
  → User space reads ring buffer via mmap

Call chain with frame pointer (-fno-omit-frame-pointer):
  Stack: [RBP+8]=return addr → caller RIP
         [RBP]=saved RBP     → caller RBP
         [RBP-8]=local var

Dwarf unwinding (no frame pointer needed):
  Uses .eh_frame ELF section to unwind register by register.
  Slower but works on -fomit-frame-pointer binaries.

5. eBPF and bpftrace

eBPF]{Extended Berkeley Packet Filter} tracing is covered in depth in [eBPF Tracing . Key differentiators:

Aspect Perf eBPF
Kernel code execution No (just samples) Yes (programmable)
Filtering Post-hoc (userspace) In-kernel (drop early)
Aggregation Post-hoc (userspace) In-kernel (maps)
Data volume Every event -> userspace Aggregated -> summary
Overhead for freq events High Very low
Flexibility Fixed events State machines, custom logic
Safety Safe Verified safe 
# eBPF one-liner examples
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
bpftrace -e 'kprobe:vfs_open { printf("%s opened %s\n", comm, str(((struct path *)arg1)->dentry->d_name.name)); }'
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); } interval:s:10 { exit(); }'
bpftrace -e 'profile:hz:99 { @[kstack] = count(); }'  # CPU flame graph data

6. SystemTap

SystemTap translates scripts into C kernel modules, compiles them, and loads them into the running kernel. It sits between eBPF and full kernel module programming in power and risk.

6.1 Architecture

SystemTap script (.stp)
     │
     ▼
  Translator (stap) — parse, resolve, type check
     │ C source
     ▼
  GCC → compile to .ko (kernel module)
     │
     ▼
  insmod → load into running kernel
     │
     ▼
  SystemTap runtime → relayfs → user-space consumer

6.2 SystemTap Scripting

# Trace file opens
probe syscall.openat {
    printf("%s(%d) opened %s\n", execname(), pid(), filename)
}

# Aggregate read I/O by process
global reads
probe syscall.read.return {
    if (retval > 0)
        reads[execname()] <<< retval
}
probe timer.s(10) {
    foreach (name in reads-)
        printf("%-20s count=%d avg=%d\n", name, @count(reads[name]), @avg(reads[name]))
    exit()
}

# Guru mode: embedded C
%{
#include <linux/sched.h>
%}
probe kernel.function("schedule") {
    printf("switching from %s(%d)\n", task_execname(task_current()), task_pid(task_current()))
}

# Tapset (libraries)
probe tcp.receive {
    printf("TCP: %s:%d -> %s:%d, %d bytes\n", saddr, sport, daddr, dport, size)
}

6.3 SystemTap Commands

# Install
sudo pacman -S systemtap  # (Arch)

# One-liner
stap -e 'probe syscall.open { printf("%s opened\n", execname()) }'
stap -e 'probe kernel.function("vfs_read") { printf("%s read %d bytes\n", execname(), $count) }'

# List probes
stap -l 'syscall.*'
stap -l 'kernel.function("*@fs/*.c")'
stap -l 'process("/bin/bash").function("*")'

# Cross-instrumentation (stap + perf)
stap -e 'probe perf.hw.instructions.1000000 { printf("1M instructions\n") }'

# Save compiled module
stap -p4 -m mystap script.stp

# Verbose (see generated C code)
stap -v -e 'probe begin { println("hello") exit() }'

7. LTTng

LTTng is designed for high-throughput, low-overhead production tracing with a custom ring buffer and CTF (Common Trace Format) binary output.

7.1 Architecture

User space:
  lttng-sessiond (session daemon)
    ├── lttng-consumerd (consumer daemon → CTF trace files)
    └── lttng-relayd (remote/network tracing)

  lttng create | enable-event | start | stop | destroy

  LTTng-UST (user space):
    - liblttng-ust.so linked into application
    - tracepoints compiled into app (lttng_ust_tracepoint())
    - ring buffer per CPU in shared memory

Kernel:
  lttng-modules kernel module
    - hooks kernel tracepoints
    - custom ring buffer (separate from ftrace)
    - zero-copy to consumer via shared memory

7.2 LTTng Commands

# Install
sudo pacman -S lttng-tools lttng-ust  # (Arch)

# Kernel tracing session
lttng create my-session --output=/tmp/my-trace
lttng enable-event --kernel sched_switch,sched_process_fork
lttng enable-event --kernel --syscall --all
lttng start

# ... wait for events ...
lttng stop
lttng destroy

# View the trace
babeltrace /tmp/my-trace
babeltrace2 /tmp/my-trace

# User-space tracing
lttng create my-ust-session
lttng enable-event --userspace myapp:tracepoint_name
lttng start
./myapp
lttng stop
lttng view
lttng destroy

# List available kernel events
lttng list --kernel

# List available userspace events (requires app to be running)
lttng list --userspace

8. DTrace (Linux Port)

DTrace originated on Solaris and was ported to Linux as a kernel module. It uses the D programming language for safe, dynamically-typed instrumentation. 

DTrace Architecture:
  D script → D compiler → DIF (DTrace Intermediate Format)
  → kernel module (dtrace.ko)
  → Providers (event sources): syscall, fbt, profile, pid, sdt, proc
  → Consumer: dtrace(1) CLI or libdtrace
						
# DTrace one-liners (on supported systems)
dtrace -n 'syscall::openat:entry { printf("%s opened %s\n", execname, copyinstr(arg1)); }'
dtrace -n 'fbt::vfs_read:entry { printf("vfs_read: %d bytes\n", arg2); }'
dtrace -n 'profile-99 /arg0/ { @[ustack()] = count(); }'

Linux port shortcomings: no stable kernel API , limited provider support, lacks many Solaris DTrace features.

9. Windows ETW

ETW is Windows' built-in instrumentation system, analogous to a combination of Linux tracepoints and LTTng. 

ETW Architecture:
  ┌──────────────┐  ┌──────────────────┐  ┌──────────────┐
  │  Provider     │  │  Controller      │  │  Consumer    │
  │  (event src)  │  │  (enable/disable)│  │  (read events)│
  └──────+───────┘  └────────+─────────┘  └──────+───────┘
         │                   │                   │
         └───────────────────+───────────────────┘
                             │
                   ┌─────────▼─────────┐
                   │  ETW Session       │
                   │  ┌──────────────┐  │
                   │  │ Trace buffers │  │
                   │  │ (per-CPU)     │  │
                   │  └──────────────┘  │
                   └────────────────────┘

Provider types: Manifest-based ( XML ), TraceLogging (self-describing), MOF (legacy). Consumed by: xperf, Windows Performance Recorder, PerfView, custom Tdh.dll consumers.

10. .NET EventPipe

EventPipe is .NET Core's cross-platform eventing subsystem. It is the equivalent of ETW for .NET applications on Linux and macOS. 

dotnet-trace collect --process-id PID
dotnet-counters monitor --process-id PID
dotnet-gcdump collect --process-id PID

11. Choosing a Framework

What do you need?

 Trace specific function?            → kprobe (bpftrace)
 Trace stable kernel events?        → tracepoints (bpftrace or perf)
 Sample CPU usage?                  → perf record -F 99 -g
 Count hardware events?             → perf stat
 Trace user-space application?      → uprobe (bpftrace) or LTTng-UST
 Production tracing (high volume)?  → LTTng
 Quick fire-and-forget one-liner?   → bpftrace
 Complex aggregation in-kernel?     → eBPF with maps
 Need dynamic C in kernel?          → SystemTap (guru mode)
 Zero external dependencies?        → ftrace (built-in)
 Multi-arch / embedded?             → ftrace or bpftrace
 Windows-specific?                  → ETW (xperf / WPR)
 .NET cross-platform?               → EventPipe (dotnet-trace)
 Already have DTrace scripts?       → DTrace port (limited)

12. Overhead Comparison

Overhead per event (log scale):

ftrace func_graph    ███████  ~100-1000 ns/event
perf tracepoint       █████    ~100-500 ns
perf sampling (99Hz)  ███      ~0.1-1% CPU total
eBPF (kprobe)         ██       ~50-200 ns
eBPF (in-kernel aggr) █         ~10-50 ns (aggregated output)
SystemTap             ████████ ~200-2000 ns
LTTng                 ██       ~30-100 ns per event
LTTng-UST             █         ~15-70 ns per event
DTrace                ██       ~50-200 ns

For high-frequency events (>100k/sec):
  Choose: eBPF with in-kernel aggregation or LTTng
  Avoid:  perf without filtering, SystemTap

For low-frequency events (<1k/sec):
  Any framework works — choose based on ease of use

13. Combining Frameworks

perf + BPF: use perf to record BPF program output
  perf record -e bpf-output/no-inherit/ -a -- myapp

ftrace + BPF: BPF program can use ftrace's function tracer
  cat /sys/kernel/debug/tracing/trace_pipe (while BPF program writes)

perf + LTTng: perf for CPU sampling, LTTng for event tracing
  (run simultaneously, output goes to separate files)

bpftrace + perf: bpftrace for live, perf for persistent recording
  bpftrace -e '...' (terminal) and perf record -e ... (background)
