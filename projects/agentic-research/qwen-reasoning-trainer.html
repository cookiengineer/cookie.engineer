Qwen 3.8 Reasoning Trainer

Overview

GitHub Repository | GitLab Mirror

The Qwen 3.8 Reasoning Trainer is a Pure Go toolkit for turning the Qwen3.8 27B model into a locally trained reasoning model. It works directly on the Q4_K_M GGUF file, removes the model's refusal direction, and fine-tunes it on reasoning traces exported from OpenCode sessions.

Everything runs from one self-contained binary. There is no CUDA, no ROCm, no Python training stack, and no container with a fragile GPU passthrough setup.

This toolchain implements the GGUF reader, the quantization codecs, the model forward pass, the Vulkan compute backend, and the LoRA trainer in Pure Go.

The project is aimed at engineers who want to own the whole model pipeline on a workstation, and at security researchers who need a model that can follow through on the work instead of stopping at a policy refusal. The result is a quantized 27B checkpoint that keeps its original tensor types, can be served by the same tool that trained it, and remains inspectable down to the last block.

Features

  • Full GGUF v3 support with a streaming reader and writer.
  • Exact dequantization and quantization for nine tensor types used by the model.
  • Supports tensor types q4_K, q5_K, q6_K, iq4_xs, iq3_s, and iq4_nl.
  • Pure Go Vulkan compute, with embedded SPIR-V shaders.
  • Fused quantized matrix-multiply and matrix-vector kernels, so weights stay compressed in VRAM.
  • Heretic-style abliteration with projected orthogonal ablation.
  • Quantized LoRA SFT on the frozen quantized base tensors.
  • Activation checkpointing, resumable device checkpoints, and adapter checkpoints.
  • Streamed merge that preserves the original quantization type of every tensor.

Architecture

The trainer is split into sub packages that can be tested independently:

  1. gguf and quant packages read and write model files and implement the block formats.
  2. compute package defines tensors and the backend contract.
  3. compute/cpu and compute/vulkan implement the backend contract.
  4. model/qwen38 package loads weights, runs the forward pass, and writes with changed tensors.
  5. abliterate, evaluate, and dataset packages provide the training data and quality checks.
  6. train package contains LoRA, the graphs, the optimizers, checkpointing, and merge logic.

The pipeline produces three model artifacts plus training checkpoints:

Command Output
qwen-trainer download Qwen3.8 27B base GGUF
qwen-trainer abliterate Abliterated GGUF
qwen-trainer train Reasoning-tuned GGUF
qwen-trainer train Adapter and training checkpoints

The real 27B target is a single Vulkan GPU with 48 GB of VRAM and 96 GB of system memory. Weights stay quantized at roughly 16 GiB resident.

At --seq-len 1024 the device trainer needs about 23 GiB and runs at roughly 51.6 seconds per step on the target card. Longer sequences are possible, but T=2048 currently soft-recovers the Vulkan driver, so 1024 remains the practical default.

Abliteration collects the last-token residual stream for good and bad prompts, computes the difference between their means per layer, optionally projects it away from the good direction, and applies the selected transformation to the attention output projections, the linear-attention output projections, and the MLP down projections. Modified tensors are requantized to their original type before the new GGUF is streamed to disk.

Building

Go 1.27 or newer is required. The glslc and spirv-val tools are only needed when rebuilding the committed SPIR-V shaders:

make;       # compile shaders, then build build/qwen-trainer
make check; # gofmt check, go vet, and the Go test suite

The committed shader binaries mean a plain build does not require a Vulkan SDK. The binary loads libvulkan.so.1 at runtime and falls back to the CPU reference when no suitable device is available.

Testing

The default suite is implemented in Pure Go and works without a GPU:

make test;
make check;

Hardware and external dependencies requiring tests skip automatically. The optional cross-checks compare the implementation against independent reference implementations that use ggml, llama.cpp and numpy:

make verify-ref;    # NumPy forward pass against the Go tiny model
make verify-data;   # Jinja2 chat template and Python regex pre-tokenizer
make verify-quants; # decoders and encoders against llama.cpp ggml-quants.c

The quant encoders are byte-identical to llama.cpp, GPU kernels are checked against the CPU implementation with finite differences, and the tokenizer, chat template, checkpoint resume, and streaming merge all have their own end-to-end integration tests.

Usage: Download and Inspect

Download the pinned base model with resume and checksum verification, then inspect its architecture and tensor histogram:

./build/qwen-trainer download --model models/Qwen3.8-27B-UD-Q4_K_M.gguf;
./build/qwen-trainer inspect --model models/Qwen3.8-27B-UD-Q4_K_M.gguf;
./build/qwen-trainer gpu-info;

Usage: Abliteration

Abliterate the model and remove the refusals, then write a type-preserving GGUF:

./build/qwen-trainer abliterate \
  --model models/Qwen3.8-27B-UD-Q4_K_M.gguf \
  --out models/Qwen3.8-27B-abliterated-UD-Q4_K_M.gguf;

The bundled good and bad prompt sets come from Heretic and are embedded in the Qwen Trainer binary.

Usage: Training

The device path keeps the frozen quantized base and the trainable adapters resident on the GPU. This is the path to use for the real 27B model:

./build/qwen-trainer train \
  --model models/Qwen3.8-27B-abliterated-UD-Q4_K_M.gguf \
  --device \
  --dataset datasets/reasoning-hydraone \
  --dataset datasets/reasoning-thinky \
  --include-subagents \
  --seq-len 1024 \
  --steps 1002 \
  --lr 1e-4 \
  --warmup 100 \
  --max-grad-norm 1.0 \
  --seed 1 \
  --resume models/sft-abliterated.ckpt \
  --save-every 25 \
  --adapter-out models/sft-abliterated-adapters.gob \
  --out models/Qwen3.8-27B-abliterated-DeepSeek-UD-Q4_K_M.gguf;

The checkpoint stores the step, adapter parameters, and AdamW moments, so a run can be stopped and continued. The merged GGUF is only written after the final step. An offline merge can be repeated from a checkpoint with --eval-checkpoint and --out, without touching the GPU.

Usage: Evaluation

Score the trained model on refusal behavior, perplexity, or multiple-choice tasks:

./build/qwen-trainer evaluate \
  --model models/Qwen3.8-27B-abliterated-DeepSeek-UD-Q4_K_M.gguf \
  --prompts source/prompts/harmful_behaviors_test.jsonl \
  --max-tokens 32 \
  --base models/Qwen3.8-27B-UD-Q4_K_M.gguf;

./build/qwen-trainer evaluate \
  --model models/Qwen3.8-27B-abliterated-DeepSeek-UD-Q4_K_M.gguf \
  --perplexity corpus.txt \
  --window 512;

Because the model is a thinking model, it emits a <think> block first, which makes first-token KL a weak signal. Short generations or later positions are more useful. Perplexity computes full language model head logits for every window, so it is much slower per token than run.
