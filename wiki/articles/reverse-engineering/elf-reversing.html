ELF Reversing

Structural analysis of ELF binaries for malware reverse-engineering to detect suspicious layouts, packers, and anti-analysis tricks.

Overview

ELF reversing dissects a Linux executable without running it, reading its headers, segments, sections, and symbols to learn what it does. Hostile software leaves structural deviations from normal builds, and those deviations point straight at its capabilities. After reading, you can inspect an ELF with readelf, objdump, and nm, recognize packers and anti-analysis tricks, and triage a suspicious sample.

Required Reading

  • /wiki/articles/fundamentals/elf.html - complete ELF format reference: sections, segments, dynamic linking, and symbol tables
  • articles/reverse-engineering/binary-identification.html - file type identification and initial triage before deep ELF analysis

Malware Analysis Mindset

You are not debugging a crashing application. You are dissecting hostile software. Every byte in the ELF was placed there by an attacker to achieve a goal: persistence, exfiltration, C2 , defense evasion. Your job is to understand what the binary does without executing it, by reading its structure.

Normal binaries follow predictable patterns. Malware deviates - that deviation is the signal. This article catalogues the deviations.

Suspicious ELF Characteristics

.init_array and .fini_array Hijacking

The .init_array section contains function pointers that run before main() . The dynamic linker calls them in order during initialization. The .fini_array runs at exit, triggered by __cxa_finalize .

Normal usage: C++ static constructors, runtime setup. Malware usage: anti-debug checks, decryption routines, and payload execution that happens before any debugger can break on main() . 

$ readelf -S suspicious.bin | grep -E 'init|fini'
  [16] .init_array       INIT_ARRAY      0000000000403e10  00003e10
       0000000000000018  0000000000000008  WA       0     0     8
  [17] .fini_array       FINI_ARRAY      0000000000403e28  00003e28
       0000000000000008  0000000000000008  WA       0     0     8

A size of 0x18 for .init_array on x86-64 means three function pointers (3 x 8 bytes). A simple C program has one (call to __libc_csu_init ). More than two is suspicious. 

$ objdump -d -j .init_array suspicious.bin

Disassembly of section .init_array:

0000000000403e10 <__init_array_start>:
  403e10:       00 11 40 00 00 00 00 00
  403e18:       60 11 40 00 00 00 00 00
  403e20:       90 22 40 00 00 00 00 00

Three entries: 0x401100 , 0x401160 , 0x402290 . The first is the standard libc init. The other two are suspicious. They run before main() . In a debugger, break main never fires if the .init_array function calls exit(0) after detecting ptrace .

To check what these functions do, disassemble them:

$ objdump -d suspicious.bin --start-address=0x401160 --stop-address=0x401180

Segment Permission Anomalies

The LOAD segments declare memory permissions. Normal mapping:

$ readelf -l normal_binary

Program Headers:
  Type   Offset             VirtAddr           PhysAddr
         FileSiz            MemSiz              Flags  Align
  LOAD   0x0000000000000000 0x0000000000400000 0x0000000000400000
         0x00000000000008e0 0x00000000000008e0  R      0x1000
  LOAD   0x0000000000001000 0x0000000000401000 0x0000000000401000
         0x00000000000001e5 0x00000000000001e5  R E    0x1000
  LOAD   0x0000000000002000 0x0000000000402000 0x0000000000402000
         0x0000000000000108 0x0000000000000108  R      0x1000
  LOAD   0x0000000000002e10 0x0000000000403e10 0x0000000000403e10
         0x0000000000000200 0x0000000000000210  RW     0x1000

Four LOAD segments: R (read-only headers), RE (code), R (rodata), RW (data+bss). Never RWX.

RWX segment (read+write+execute) means self-modifying code:

$ readelf -l malicious.bin

  LOAD   0x0000000000001000 0x0000000000401000 0x0000000000401000
         0x0000000000008000 0x0000000000008000  RWE    0x1000

RWE = Flags 7 (read=4 + write=2 + execute=1). This permits the code to modify itself at runtime

  • JIT compilation, self-decrypting shellcode, polymorphism. The ELF loader maps a PT_LOAD

segment with the permissions declared in its program header, so an RWX segment is mapped RWX even though CONFIG_X86_64_MPROTECT_NOWRITE_EXEC restricts later writable and executable mmap calls. The presence of an RWX LOAD segment is a strong packer/exploit indicator.

Empty .text section: the binary has code mapped at the segment level but the .text section has zero size. This means the code region is populated at runtime - shellcode injection, unpacking stubs, or staged loading: 

$ readelf -S suspicious.bin | grep '.text'
  [13] .text             PROGBITS        0000000000401040  00001040
       0000000000000000  0000000000000000  AX       0     0     16

Size 0x0 . At runtime, code appears here from unpacking or network download.

Unusual INTERP

The .interp section specifies the dynamic linker path. Normally /lib64/ld-linux-x86-64.so.2 : 

$ readelf -p .interp suspicious.bin

String dump of section '.interp':
  [     0]  /lib/ld-musl-x86_64.so.1

A musl interpreter means the binary was compiled against musl libc, not glibc. This is unusual for malware but common in embedded Linux. Statically compiled, it may have no DT_NEEDED entries at all.

An empty or missing interpreter means the binary is statically linked or uses a custom loader

  • both worth investigating.

$ readelf -p .interp suspicious.bin
readelf: Error: No .interp section

DT_RPATH and DT_RUNPATH Abuse

R PAT H and RUN PAT H entries in .dynamic tell the dynamic linker where to search for shared libraries before the standard paths: 

$ readelf -d suspicious.bin | grep -E 'RPATH|RUNPATH'
 0x000000000000000f (RPATH)              Library rpath: [$ORIGIN/../lib]
 0x000000000000001d (RUNPATH)            Library runpath: [$ORIGIN/../lib]

$ORIGIN resolves to the binary's directory at runtime. If the binary uses $ORIGIN with a relative path like ../lib , it loads libraries from a relative location. An attacker places malicious .so files alongside the binary - LD_LIBRARY_ PAT H hijacking without environment variables.

Writable R PAT H: /tmp/.hidden/ . The binary loads shared libraries from a world-writable directory. Drop a malicious libc.so.6 there and it gets loaded. 

 0x000000000000000f (RPATH)              Library rpath: [/tmp/.cache]

Absolute writable paths in R PAT H = library planting attack vector.

.dynamic Anomalies

The .dynamic section is the runtime instruction manual for ld.so . Every entry directs the loader. Entries pointing to writable segments are suspicious: 

$ readelf -d suspicious.bin | grep -E 'INIT|FINI|PLTGOT'
 0x000000000000000c (INIT)               0x401120
 0x000000000000000d (FINI)               0x402340
 0x0000000000000003 (PLTGOT)            0x404000

Compare these addresses against the LOAD segment ranges. If INIT or FINI addresses fall within RW segments (not RE), the binary modifies its own init/fini functions.

Cross-reference manually:

$ readelf -l suspicious.bin | grep LOAD
  LOAD  0x0000000000400000 0x0000000000400000  ... R E  0x1000
  LOAD  0x0000000000404000 0x0000000000404000  ... RW   0x1000

PLTGOT at 0x404000 is in the RW segment - normal (GOT is writable). But if INIT at 0x401120 is in RW territory, that is abnormal - init functions should be read-execute only.

PT_NOTE to PT_LOAD Conversion

Intel CET (Control-flow Enforcement Technology) and other features use PT_NOTE segments for metadata. Some malware converts PT_NOTE to PT_LOAD : 

$ readelf -l suspicious.bin

  Type  Offset             VirtAddr           PhysAddr
        FileSiz            MemSiz              Flags  Align
  NOTE  0x0000000000000338 0x0000000000400338 0x0000000000400338
        0x0000000000000030 0x0000000000000030  R E    0x4

A PT_NOTE segment with R E (executable) flags is unusual. Normal PT _NOTE segments are read-only and contain .note.ABI-tag , .note.gnu.build-id . If a PT _NOTE segment is executable, it may contain shellcode disguised as note data.

The conversion technique is a static file modification, not a runtime trick: the malware rewrites a PT_NOTE entry's p_type to PT_LOAD , sets p_flags to R E , points p_offset and p_vaddr at shellcode appended to the file, and patches e_entry to that virtual address. When the kernel later executes the file, the loader maps the forged segment and jumps straight into the payload. This " PT _NOTE infection" is a well-known ELF backdoor technique because the program header change is easy to script and survives a simple structural review.

.comment Section Analysis

The .comment section stores the compiler version string. It survives stripping. Every binary built on the attacker's machine carries metadata: 

$ readelf -p .comment suspicious.bin

String dump of section '.comment':
  [     0]  GCC: (GNU) 5.4.0
  [     f]  GCC: (Ubuntu 5.4.0-6ubuntu1~16.04.12) 5.4.0 20160609

This tells you the attacker used Ubuntu 16.04 with GCC 5.4.0. If the binary targets ARM but was compiled on Ubuntu 16.04 x86-64, the attacker used a cross-compiler - the binary is not native to its build host.

Missing .comment section is also a signal. Some build systems intentionally strip it. Some malware builds do too. Not conclusive, but part of the picture.

Stripped vs Unstripped

Stripping removes .symtab and .strtab (static symbol table and string table). The dynamic symbol table ( .dynsym ) remains for shared library imports. This leaves:

  • No function names in disassembly (functions are sub_401000 in Ghidra/I DA ).
  • No local variable names or source file paths.
  • No static function names for statically linked libraries.
$ readelf -S unstripped.bin | grep symtab
  [27] .symtab           SYMTAB          0000000000000000  00003040
       0000000000000360  0000000000000018          28    18     8

$ readelf -S stripped.bin | grep symtab
# No output -- .symtab removed entirely.

Verify with file : 

$ file binary
binary: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, for GNU/Linux 2.6.32, not stripped

binary: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, for GNU/Linux 2.6.32, stripped

Function Identification

Without symbol names, identify functions by their prologue pattern. x86-64 functions typically begin with: 

push   rbp
mov    rbp, rsp
sub    rsp, 0xN
						
#!/usr/bin/env python3
"""
find_functions.py -- identify function boundaries by x86-64 prologues
Usage: python3 find_functions.py <binary>
"""
import subprocess
import re
import sys

def find_prologues(filepath):
    out = subprocess.run(
        ['objdump', '-d', filepath],
        capture_output=True, text=True
    )
    prologue_pattern = re.compile(
        r'^\s+([0-9a-f]+):\s+55\s+push\s+%rbp\s*$',
        re.MULTILINE
    )
    functions = []
    for match in prologue_pattern.finditer(out.stdout):
        addr = int(match.group(1), 16)
        functions.append(addr)
    return functions

if __name__ == '__main__':
    funcs = find_prologues(sys.argv[1])
    print(f"Found {len(funcs)} function prologues (push rbp)")
    for addr in funcs[:20]:
        print(f"  0x{addr:x}")
    if len(funcs) > 20:
        print(f"  ... and {len(funcs) - 20} more")

readelf for Reversing

readelf is your primary ELF inspection tool. It never executes the binary - pure static analysis. The essential flags for reversing:

readelf -h : ELF Header

$ readelf -h suspicious.bin
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
  Class:                             ELF64
  Data:                              2's complement, little endian
  Version:                           1 (current)
  OS/ABI:                            UNIX - System V
  ABI Version:                       0
  Type:                              EXEC (Executable file)
  Machine:                           Advanced Micro Devices X86-64
  Version:                           0x1
  Entry point address:               0x401040
  Start of program headers:          64 (bytes into file)
  Start of section headers:          14320 (bytes into file)
  Flags:                             0x0
  Size of this header:               64 (bytes)
  Size of program headers:           56 (bytes)
  Number of program headers:         11
  Size of section headers:           64 (bytes)
  Number of section headers:         29
  Section header string table index: 28

Key fields for malware analysis:

  • Type : EXEC (standalone), DYN (PIE position-independent, also shared library), REL (relocatable object). PIE binaries have randomized base addresses - ASLR.
  • Entry point : 0x401040 - first instruction executed. This is normally _start , not main . Check what lives there:
$ objdump -d suspicious.bin --start-address=0x401040 --stop-address=0x401080
  • Machine : Advanced Micro Devices X86-64 , AArch64 , Intel 80386 , MIPS R3000 . Tells you the target architecture.
  • Number of program headers : unusually high count (20+) may indicate corrupted header manipulation.

What to look for:

  • GNU_STACK with E (execute) flag : Stack is executable - the binary places and runs code on the stack. Shellcode execution. Normal binaries have RW only (NX bit).
  • GNU_STACK missing : Older binaries or explicitly removed - stack may default to executable on older kernels.
  • LOAD segments with 'FileSiz' = 0 but 'MemSiz' > 0 : Space reserved in memory but not populated from file. The binary writes there at runtime (unpacking, .bss expansion).
  • LOAD segments with 'FileSiz' > 'MemSiz' : Extra data loaded from file that is not mapped to memory - hidden payload appended to the binary.
  • Multiple LOAD segments overlapping : One segment maps over another - the second overwrites the first. Sophisticated obfuscation.

readelf -S : Section Headers

$ readelf -S suspicious.bin
There are 29 section headers, starting at offset 0x37f0

Section Headers:
  [Nr] Name              Type             Address           Offset
       Size              EntSize          Flags  Link  Info  Align
  [ 0]                   NULL             0000000000000000  00000000
       0000000000000000  0000000000000000           0     0     0
  [ 1] .interp           PROGBITS         00000000004002a8  000002a8
       000000000000001c  0000000000000000   A       0     0     1
  [ 2] .note.ABI-tag     NOTE             00000000004002c4  000002c4
       0000000000000020  0000000000000000   A       0     0     4
  ...

Suspicious sections:

  • Non-standard section names : .xyz , .abc , .custom , single-character names. Malware and packers use non-standard names to signal custom data regions.
  • Writable '.text' : Normally 'AX'. If 'WAX', the code is self-modifying.
  • Oversized '.data' relative to '.text': Large data sections suggest embedded payloads, resources, or configuration blobs.
  • Missing standard sections : No .comment , no .eh_frame - deliberate stripping or custom build process.
  • Duplicate section names : Two sections with the same name - one may be a decoy.
  • Section with 'sh_offset' beyond EOF : The section claims to be at an offset past the end of the file - the file was truncated or the header is corrupted to hide data.
  • 'SHT_NOBITS' sections with huge sizes : '.bss' sections with hundreds of megabytes - memory exhaustion attack.

Imported libraries (DT_NEEDED) tell you the binary's capabilities:

No DT_NEEDED entries + large binary = statically linked. The binary contains all libraries internally. Use nm to identify embedded library code:

objdump for Reversing

objdump -d disassembles the binary: 

$ objdump -d -M intel suspicious.bin

Intel syntax is more readable for manual analysis. AT&T syntax (default) has reversed operand order. 

$ objdump -d -M intel --start-address=0x401040 --stop-address=0x401200 suspicious.bin

Disassemble a specific range - useful after finding suspicious addresses with readelf . 

$ objdump -t suspicious.bin | grep -E ' \.text| FUNC'

List all symbols in .text . For stripped binaries, this returns nothing from .symtab but still works on .dynsym . 

$ objdump -R suspicious.bin

Shows dynamic relocations only - the functions called through PLT/GOT.

nm for Symbol Listing

nm lists symbols from the symbol table. For stripped binaries, use -D (dynamic): 

$ nm -D suspicious.bin
                 U connect@GLIBC_2.2.5
                 U execve@GLIBC_2.2.5
                 U fopen@GLIBC_2.2.5
                 U fwrite@GLIBC_2.2.5
                 U ptrace@GLIBC_2.2.5

U = undefined (imported). T = defined in .text . The _start and main symbols survive stripping if they are dynamic symbols - some binaries keep them for debugging.

ELF Suspicion Scanner

Automate the detection of suspicious characteristics:

#!/usr/bin/env python3
"""
elf_suspicion_scanner.py -- scan an ELF for malware indicators
Usage: python3 elf_suspicion_scanner.py <binary>
"""
import sys
from elftools.elf.elffile import ELFFile
from elftools.elf.constants import P_FLAGS

PF_X = 1
PF_W = 2
PF_R = 4

def scan_rwx_segments(elf):
    flags = []
    for seg in elf.iter_segments():
        if seg.header.p_type == 'PT_LOAD':
            pflags = seg.header.p_flags
            if (pflags & (PF_R | PF_W | PF_X)) == (PF_R | PF_W | PF_X):
                flags.append(f"RWX LOAD segment at {seg.header.p_vaddr:#x}")
    return flags

def scan_suspicious_sections(elf):
    normal_sections = {
        '.text', '.rodata', '.data', '.bss', '.interp',
        '.plt', '.got', '.got.plt', '.dynamic', '.dynsym',
        '.dynstr', '.shstrtab', '.symtab', '.strtab', '.comment',
        '.note', '.note.ABI-tag', '.note.gnu.build-id',
        '.note.GNU-stack', '.eh_frame', '.eh_frame_hdr',
        '.init', '.fini', '.init_array', '.fini_array',
        '.rela.dyn', '.rela.plt', '.gnu.version',
        '.gnu.version_r', '.gnu.hash', '.gnu.build.attributes',
        '.jcr', '.tdata', '.tbss', '.ctors', '.dtors',
        '.preinit_array', '.stab', '.stabstr', '.debug_*'
    }
    flags = []
    for section in elf.iter_sections():
        name = section.name

        # Non-standard section names
        if name not in normal_sections and not name.startswith('.debug_'):
            flags.append(f"Non-standard section: {name}")

        # Writable .text
        if name == '.text' and section.header.sh_flags & 0x2:  # SHF_WRITE
            flags.append(".text section is WRITABLE")

        # Large .bss (memory exhaustion)
        if name == '.bss' and section.header.sh_size > 100 * 1024 * 1024:
            flags.append(f".bss size {section.header.sh_size:,} bytes (huge)")

        # Empty .text
        if name == '.text' and section.header.sh_size == 0:
            flags.append(".text section has zero size")

        # UPX sections
        if name in {'UPX0', 'UPX1'}:
            flags.append(f"UPX packer section: {name}")

    return flags

def scan_init_array(elf):
    flags = []
    for section in elf.iter_sections():
        if section.name == '.init_array':
            num_entries = section.header.sh_size // 8  # 64-bit pointers
            if num_entries > 2:
                flags.append(f".init_array has {num_entries} entries (> 2)")
    return flags

def scan_rpath(elf):
    flags = []
    for section in elf.iter_sections():
        if section.name == '.dynamic':
            for tag in section.iter_tags():
                if tag.entry.d_tag == 'DT_RPATH' or tag.entry.d_tag == 'DT_RUNPATH':
                    path = tag.rpath if hasattr(tag, 'rpath') else tag.runpath
                    flags.append(f"{tag.entry.d_tag}: {path}")
                    if path.startswith('/tmp'):
                        flags.append("  [!] RPATH points to world-writable /tmp")
                    if '$ORIGIN' in path and '../' in path:
                        flags.append("  [!] RPATH uses relative $ORIGIN traversal")
    return flags

def scan_interp(elf):
    flags = []
    for section in elf.iter_sections():
        if section.name == '.interp':
            path = section.data().decode('utf-8', errors='ignore').rstrip('\x00')
            if '/lib64/ld-linux-x86-64.so.2' not in path:
                flags.append(f"Unusual interpreter: {path}")
            return flags
    flags.append("No .interp section (static binary or custom loader)")
    return flags

def scan_imports(elf):
    """Categorize imported symbols by behavior."""
    categories = {
        'network': {'socket', 'connect', 'send', 'recv', 'sendto', 'recvfrom',
                    'bind', 'listen', 'accept', 'gethostbyname', 'getaddrinfo',
                    'curl_', 'InternetOpen', 'WinHttp'},
        'execution': {'system', 'popen', 'execve', 'execvp', 'execl', 'execle',
                     'execv', 'CreateProcess', 'WinExec', 'ShellExecute'},
        'file': {'fopen', 'fwrite', 'fread', 'fclose', 'open', 'write', 'read',
                'close', 'unlink', 'rename', 'chmod', 'chown', 'stat', 'lstat',
                'openat', 'unlinkat', 'CreateFile', 'WriteFile', 'ReadFile',
                'DeleteFile', 'MoveFile', 'CopyFile'},
        'crypto': {'crypt', 'encrypt', 'decrypt', 'AES_', 'RC4_', 'MD5_',
                  'SHA256_', 'EVP_', 'CryptEncrypt', 'CryptDecrypt'},
        'anti_analysis': {'ptrace', 'prctl', 'isDebuggerPresent', 'CheckRemoteDebuggerPresent',
                         'NtQueryInformationProcess', 'OutputDebugString'},
        'injection': {'ptrace', 'dlopen', 'dlsym', 'VirtualAlloc', 'VirtualProtect',
                     'WriteProcessMemory', 'CreateRemoteThread', 'NtCreateThreadEx'},
        'persistence': {'RegCreateKey', 'RegSetValue', 'RegDeleteKey', 'SetFileAttributes'},
        'info_gathering': {'uname', 'gethostname', 'getuid', 'geteuid', 'getpid',
                          'GetComputerName', 'GetUserName'},
    }
    findings = {cat: set() for cat in categories}

    for section in elf.iter_sections():
        if section.name == '.dynsym':
            for symbol in section.iter_symbols():
                name = symbol.name.lower()
                for cat, keywords in categories.items():
                    for kw in keywords:
                        if kw.lower() in name:
                            findings[cat].add(name)

    return {k: sorted(v) for k, v in findings.items() if v}

Challenge

Write a Go tool that triages an ELF by parsing its header and program headers directly. Report the class, machine, entry point, and type, list every PT_LOAD segment with its flags, and flag executable stacks, writable-and-executable segments, and zero-file-size-but-mapped segments. Run it on a normal /bin/ls and on a packed sample. 

package main

import (
	"encoding/binary"
	"fmt"
	"os"
)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "usage: %s <elf>\n", os.Args[0])
		os.Exit(1)
	}
	data, err := os.ReadFile(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	if len(data) < 64 || string(data[:4]) != "\x7fELF" {
		fmt.Fprintln(os.Stderr, "not an ELF file")
		os.Exit(1)
	}
	class := data[4]
	order := binary.ByteOrder(binary.LittleEndian)
	if data[5] == 2 {
		order = binary.BigEndian
	}
	var entry, phoff uint64
	var phnum uint16
	if class == 2 {
		entry = order.Uint64(data[0x18:0x20])
		phoff = order.Uint64(data[0x20:0x28])
		phnum = order.Uint16(data[0x38:0x3a])
	} else {
		entry = uint64(order.Uint32(data[0x18:0x1c]))
		phoff = uint64(order.Uint32(data[0x1c:0x20]))
		phnum = order.Uint16(data[0x2c:0x2e])
	}
	machine := order.Uint16(data[0x12:0x14])
	fmt.Printf("class=%d machine=%d entry=0x%x phnum=%d\n", class, machine, entry, phnum)
	for i := 0; i < int(phnum); i++ {
		base := int(phoff)
		if class == 2 {
			base += i * 56
		} else {
			base += i * 32
		}
		var pType uint32
		var offset, vaddr, filesz, memsz uint64
		var flags uint32
		if class == 2 {
			pType = order.Uint32(data[base : base+4])
			flags = order.Uint32(data[base+4 : base+8])
			offset = order.Uint64(data[base+8 : base+16])
			vaddr = order.Uint64(data[base+16 : base+24])
			filesz = order.Uint64(data[base+32 : base+40])
			memsz = order.Uint64(data[base+40 : base+48])
		} else {
			pType = order.Uint32(data[base : base+4])
			offset = uint64(order.Uint32(data[base+4 : base+8]))
			vaddr = uint64(order.Uint32(data[base+8 : base+12]))
			filesz = uint64(order.Uint32(data[base+16 : base+20]))
			memsz = uint64(order.Uint32(data[base+20 : base+24]))
			flags = order.Uint32(data[base+24 : base+28])
		}
		if pType != 1 {
			continue
		}
		fmt.Printf("PT_LOAD off=0x%x vaddr=0x%x filesz=0x%x memsz=0x%x flags=%d\n",
			offset, vaddr, filesz, memsz, flags)
		if flags&1 != 0 && flags&2 != 0 {
			fmt.Println("  [!] writable and executable segment")
		}
		if filesz == 0 && memsz > 0 {
			fmt.Println("  [!] zero file size but mapped")
		}
	}
}

Extend it to flag a PT_GNU_STACK segment with the execute bit set, which indicates shellcode running from the stack.
