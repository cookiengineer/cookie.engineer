Reading x86-64 Assembly

Systematic instruction-by-instruction decoding of x86-64 disassembly, covering Intel syntax, essential opcodes, control-flow patterns, function prologues, and manual decompilation.

Overview

Disassembly is the lowest-level view of a compiled program, and reading it fluently is the core skill of reverse engineering. This article teaches the small vocabulary of instructions that covers most real code, then shows how the compiler turns C control structures and functions into recognizable assembly patterns. After reading it you can take an objdump listing and reconstruct the original C logic by hand.

Required Reading

  • Calling Conventions - System V AMD64 ABI, argument placement, caller/callee-saved registers
  • Stack - stack frame anatomy, prologue/epilogue, rbp/rsp mechanics

Why Intel Syntax

Reverse engineering tools overwhelmingly use Intel syntax: Ghidra, I DA Pro, radare2, Binary Ninja, x64dbg, and LLDB's default on macOS. objdump defaults to AT&T but switches with -M intel . The difference matters.

AT&T syntax uses mov src, dst with register prefixes ( %rax , %rbx ), immediate prefixes ( $0x42 ), and size suffixes ( movl , movq ). Intel syntax uses mov dst, src with bare register names ( rax , rbx ), bare immediates ( 0x42 ), and memory operand form [base + index*scale + displacement] . Intel syntax reads left-to-right like C assignment: mov rax, rbx means rax = rbx . 

; AT&T (objdump default)
movq   %rax, -0x8(%rbp)      ; read: move rax into [rbp-8]

; Intel (objdump -M intel)
mov    QWORD PTR [rbp-0x8], rax  ; read: [rbp-8] = rax

Always use Intel syntax when reversing. Every modern tool outputs it. If you use objdump, always pass -M intel . 

objdump -d -M intel binary
objdump -d -M intel --no-show-raw-insn binary  # cleaner output

x86-64 Register Set

Before reading disassembly, you must know what each register holds and when it's safe to clobber. The mapping is not arbitrary - the ABI assigns roles.

Register Role (System V AMD64)
rax Return value from function call. Also accumulator for imul/idiv.
rbx Callee-saved general purpose.
rcx Fourth argument (rdi, rsi, rdx, rcx). Volatile.
rdx Third argument. Also upper half of 128-bit return (rdx:rax).
rsi Second argument. Source index for string ops.
rdi First argument. Destination index for string ops.
rbp Frame pointer (base pointer). Callee-saved.
rsp Stack pointer. Points to last pushed value.
r8 - r9 Fifth and sixth arguments. Volatile.
r10 - r11 Temporary/volatile. Used by syscall instruction.
r12 - r15 Callee-saved general purpose.
rip Instruction pointer. Cannot be directly accessed.
rflags Condition flags (ZF, SF, CF, OF, PF). Set by cmp/test/etc.
xmm0 - xmm7 Floating-point arguments and return (xmm0). Volatile.
xmm8 - xmm15 Floating-point temporaries.

Lower 32-bit, 16-bit, and 8-bit sub-register aliases exist but don't zero-extend to the full register. Writing to eax zero-extends to rax . Writing to ax , al , or ah leaves upper bits untouched. 

mov eax, 0          ; sets rax to 0 (zero-extension)
mov ax, 0           ; only sets lower 16 bits; upper 48 bits are preserved
mov al, 0           ; only sets lower 8 bits; upper 56 bits are preserved

This behavior causes subtle bugs. When reversing, xor eax, eax always zeroes the full rax . This is the canonical "set to zero" idiom because xor eax, eax is 2 bytes; mov rax, 0 is 7 bytes for the immediate.

Essential Instructions

You can understand 90% of typical disassembly with roughly 20 instructions. The rest are SSE/AVX vector ops, privileged instructions, or redundant mnemonics. Master these first.

Data Movement

Instruction Example Semantics
mov dst, src mov rax, [rbp-0x8] rax = *(local_var)
movzx dst, src movzx eax, byte [rdi] Zero-extend byte to dword
movsx dst, src movsx rax, word [rsi] Sign-extend word to qword
lea dst, [expr] lea rax, [rbp-0x10] rax = &local_var(address, NOT value)

lea is the most misunderstood instruction in x86-64 reversing. It computes an effective address but does NOT dereference memory. lea rax, [rbp-0x8] computes rbp - 8 and stores that pointer in rax. It never touches memory at [rbp-8] . Compare: 

int x = *ptr;        // mov eax, [rdi]     - loads value at ptr
int *p = &x;         // lea rax, [rbp-8]   - computes address of x
int y = x * 5;       // lea eax, [rax + rax*4] - compute without dedicated multiply

That last line is critical: lea is often used for arithmetic because it can compute base + index*scale + displacement in a single instruction without modifying flags. lea eax, [rax + rax*4] multiplies by 5. lea rax, [rdi + rsi*8] computes rdi + rsi * 8 - an array index.

Arithmetic

Instruction Example Semantics
add dst, src add rax, 1 rax += 1
sub dst, src sub rsp, 0x20 rsp -= 0x20
inc dst inc ecx ecx++
dec dst dec rbx rbx--
imul dst, src imul rax, rcx rax *= rcx(signed)
imul dst, src1, src2 imul eax, ebx, 13 eax = ebx * 13(3-operand form)
idiv src idiv rcx rdx:rax / rcx->rax=quotient, rdx=remainder
neg dst neg rax rax = -rax
cdq/cqo cqo Sign-extend rax -> rdx:rax (for idiv setup)

idiv is messy. Before idiv rcx , the 128-bit dividend is in rdx:rax . The typical pattern: 

mov    rax, [rbp-0x8]   ; dividend
cqo                      ; sign-extend rax -> rdx:rax
idiv   rcx               ; rax = quotient, rdx = remainder

Bitwise Operations

Instruction Example Semantics
and dst, src and eax, 0xff eax &= 0xff
or dst, src or rax, 1 rax |= 1
xor dst, src xor eax, eax eax ^= eax-> zero (canonical zero idiom)
not dst not rax rax = ~rax
shl dst, count shl eax, 3 eax <<= 3(logical left)
shr dst, count shr rax, cl rax >>= cl(logical right)
sar dst, count sar eax, 1 eax >>= 1(arithmetic right, preserves sign)

xor eax, eax is the canonical register zero. It's 2 bytes ( 31 c0 ) vs mov eax, 0 at 5 bytes ( b8 00 00 00 00 ). Any competent compiler uses xor-zeroing. In disassembly, whenever you see xor reg, reg , read it as reg = 0 .

Comparison and Test

Instruction Example Flags Set Use Case
cmp dst, src cmp eax, 0x7f ZF, SF, CF, OF dst - src, sets flags, discards result
test dst, src test al, al ZF, SF, PF dst & src, sets flags, discards result
cmpwith memory cmp [rdi+0x18], ebx ZF, SF, CF, OF Compare memory to register

cmp a, b computes a - b and sets flags. The key insight: the flags tell you the relationship between a and b. 

cmp eax, 0x42
je  somewhere    ; jump if eax == 0x42 (ZF=1)
jne somewhere    ; jump if eax != 0x42 (ZF=0)
jg  somewhere    ; jump if eax > 0x42  (signed, ZF=0 and SF=OF)
jl  somewhere    ; jump if eax < 0x42  (signed, SF≠OF)
ja  somewhere    ; jump if eax > 0x42  (unsigned, CF=0 and ZF=0)
jb  somewhere    ; jump if eax < 0x42  (unsigned, CF=1)

test reg, reg is the canonical null check. test eax, eax sets ZF=1 if eax == 0 . Equivalent to cmp eax, 0 but 2 bytes instead of 3.

Conditional Jumps - Decoding the Branch

Every conditional jump reads flags set by the immediately preceding cmp or test . The mnemonic tells you the condition:

Signed Unsigned Condition
je / jz je / jz Equal / Zero
jne / jnz jne / jnz Not equal / Not zero
jg ja > (greater/above)
jge jae / jnb >= (greater-or-equal)
jl jb / jc < (less/below)
jle jbe <= (less-or-equal)
js Sign flag set
jns Sign flag not set
jo Overflow flag set
jno Overflow flag not set
jp / jpe Parity even
jnp / jpo Parity odd
jcxz Jump if cx == 0

The signed/unsigned distinction is critical. If a disassembly shows jl after cmp , the comparison is signed. If it shows jb , it's unsigned. This tells you the type of the C variable: int (signed) vs unsigned int (unsigned).

Unconditional Jump, Call, Return

Instruction Stack Effect Semantics
jmp addr None rip = addr
call addr Push return address;rip = addr Function call
ret Pop return address -> rip Return from function
call [rax] Push return address;rip = *rax Indirect call (function pointer)
jmp [rax] None Indirect jump (tail call, switch)

call is equivalent to: 

push rip_of_next_instruction   ; implicit - not visible in disassembly
jmp target_function

ret is equivalent to: 

pop rip   ; also implicit - destination comes from stack

The return address pushed by call sits at [rsp] immediately after the call. This is why buffer overflows on the stack can overwrite return addresses: the return address is stored on the stack alongside local variables.

Stack Operations

Instruction Example Semantics
push src push rbp rsp -= 8; *(uint64_t*)rsp = rbp
pop dst pop rbp rbp = *(uint64_t*)rsp; rsp += 8
pushfq pushfq Push rflags
popfq popfq Pop rflags

Function Prologue And Epilogue

Every non-leaf function (a function that calls other functions) on x86-64 Linux, compiled without -fomit-frame-pointer , begins and ends with the same pattern. Recognizing this instantly tells you where functions start and end.

Prologue (function entry)

push   rbp              ; save caller's frame pointer
mov    rbp, rsp         ; set new frame pointer = current stack top
sub    rsp, 0x28        ; allocate 0x28 bytes of local variable space

After the prologue: - rbp points to the base of the current frame (where the saved old rbp sits) - rsp points to the bottom of the local variable area - Local variable N is at [rbp - N*8] (or the appropriate offset) - The return address is at [rbp + 0x8] - The saved caller's rbp is at [rbp] 

        High addresses
        ┌────────────────────┐
        │  7th arg (stack)   │  [rbp + 0x10]
        │  return address    │  [rbp + 0x8]
rbp ->   │  saved old rbp     │  [rbp]
        │  local var 1       │  [rbp - 0x8]
        │  local var 2       │  [rbp - 0x10]
        │  local var 3       │  [rbp - 0x18]
rsp ->   │  (next call)       │  [rbp - 0x28]
        └────────────────────┘
        Low addresses

Epilogue (function exit)

leave         ; mov rsp, rbp; pop rbp
ret           ; pop rip

leave is equivalent to: 

mov rsp, rbp    ; deallocate local variable space
pop rbp         ; restore caller's frame pointer

This is followed by ret which pops the return address and jumps to it.

When -fomit-frame-pointer is used (common with -O2 ), rbp is used as a general-purpose register (callee-saved). The compiler tracks offsets from rsp instead. Functions compiled this way have no push rbp / mov rbp, rsp - they directly sub rsp, imm and reference locals as [rsp + offset] . This is harder to read manually but saves a register and two instructions per call.

Annotated Disassembly Example

Write a small C program that exercises the patterns you need to recognize. Compile it. Disassemble it. Annotate every line. 

// example.c
#include <stdio.h>
#include <string.h>

int check_password(const char *input) {
    const char *secret = "1337haxor";
    return strcmp(input, secret) == 0;
}

int authenticate(const char *user, const char *pass) {
    if (strcmp(user, "root") != 0)
        return 0;

    if (check_password(pass))
        return 1;

    return 0;
}

int main(int argc, char **argv) {
    if (argc < 3) {
        printf("Usage: %s <user> <pass>\n", argv[0]);
        return 1;
    }

    if (authenticate(argv[1], argv[2])) {
        printf("Access granted.\n");
        return 0;
    }

    printf("Access denied.\n");
    return 1;
}

gcc -O0 -fno-stack-protector -no-pie -o example example.c

Disassemble:

Recognizing Control Flow Patterns

Every high-level control structure compiles to a specific pattern. When you see these patterns in disassembly, reconstruct the C.

if-else (diamond)

    cmp    rax, 0             ; if (condition)
    jne    .L_else            ; branch to else block if false
    ; then block
    mov    eax, 1
    jmp    .L_end
.L_else:
    ; else block
    mov    eax, 0
.L_end:
    ; code after if-else

Decompilation:

if (condition)
    result = 1;
else
    result = 0;

while loop (test at top)

.L_loop_top:
    cmp    DWORD PTR [rbp-0x4], 0xa   ; while (i < 10)
    jge    .L_loop_end
    ; loop body
    add    DWORD PTR [rbp-0x4], 0x1   ; i++
    jmp    .L_loop_top
.L_loop_end:

Decompilation:

while (i < 10) {
    // body
    i++;
}

do-while loop (test at bottom)

.L_do_top:
    ; loop body
    add    DWORD PTR [rbp-0x4], 0x1   ; i++
    cmp    DWORD PTR [rbp-0x4], 0xa   ; while (i < 10)
    jl     .L_do_top

Decompilation:

do {
    i++;
} while (i < 10);

for loop

    mov    DWORD PTR [rbp-0x4], 0x0   ; i = 0
    jmp    .L_for_check
.L_for_body:
    ; loop body
    add    DWORD PTR [rbp-0x4], 0x1   ; i++
.L_for_check:
    cmp    DWORD PTR [rbp-0x4], 0x9   ; i < 10?
    jle    .L_for_body

Decompilation:

for (int i = 0; i <= 9; i++) {
    // body
}

At -O2 , the for loop often converts to a do-while form (inversion optimization), eliminating the initial jmp to the check.

switch statement - jump table

    cmp    eax, 0x4              ; if (value > 4) goto default
    ja     .L_default
    mov    eax, eax              ; zero-extend (already done, but explicit)
    lea    rdx, [rip+0x1234]     ; rdx = &jump_table
    movsxd rax, DWORD PTR [rdx + rax*4]  ; rax = jump_table[value] (sign-extended offset)
    add    rax, rdx              ; rax = &jump_table + offset
    jmp    rax                   ; indirect jump into table

Decompilation:

switch (value) {
    case 0: ... break;
    case 1: ... break;
    case 2: ... break;
    case 3: ... break;
    case 4: ... break;
    default: ... break;
}

The jump table is an array of 32-bit signed offsets in the data section. The movsxd sign-extends the offset into a 64-bit register, then it's added to the table base to form an absolute address.

Optimization Effects - O0 vs O2

The same check_password function compiled with -O2 : 

gcc -O2 -fno-stack-protector -no-pie -o example_O2 example.c
						
00000000004011d0 <check_password>:
  4011d0:  sub    rsp, 0x8
  4011d4:  lea    rsi, [rip+0xe29]           ; rsi = &"1337haxor"
  4011db:  call   401050 <strcmp@plt>         ; strcmp(rdi, "1337haxor")
  4011e0:  test   eax, eax
  4011e2:  sete   al                         ; al = (strcmp == 0)
  4011e5:  add    rsp, 0x8
  4011e9:  movzx  eax, al
  4011ec:  ret

The prologue and frame pointer are gone, and the string pointer is loaded straight into rsi instead of being spilled to a local. The call is not a pure tail call, because strcmp returns 0 on a match and the function must return 1; sete al followed by movzx eax, al performs that conversion.

authenticate at -O2 inlines check_password and keeps only the values it needs across calls in a callee-saved register: 

00000000004011f0 <authenticate>:
  4011f0:  push   rbx                        ; preserve callee-saved rbx
  4011f1:  mov    rbx, rsi                   ; rbx = pass
  4011f4:  lea    rsi, [rip+0xe13]           ; rsi = &"root"
  4011fb:  call   401050 <strcmp@plt>         ; strcmp(user, "root")
  401200:  test   eax, eax
  401202:  jne    401220 <authenticate+0x30>  ; if (strcmp != 0) return 0
  401204:  mov    rdi, rbx                   ; rdi = pass
  401207:  lea    rsi, [rip+0xdf6]           ; rsi = &"1337haxor"
  40120e:  call   401050 <strcmp@plt>         ; inlined check_password(pass)
  401213:  pop    rbx
  401214:  test   eax, eax
  401216:  sete   al
  401219:  movzx  eax, al
  40121c:  ret
  40121d:  nop    DWORD PTR [rax]
  401220:  xor    eax, eax                   ; return 0
  401222:  pop    rbx
  401223:  ret

The compiler replaced the call to check_password with an inline strcmp against the secret string, so the second comparison never leaves authenticate . The only register saved across a call is rbx , which holds pass ; rdi is overwritten when the second call needs it. The test / sete / movzx sequence turns a comparison into a 0-or-1 return value without branching.

Hands-On - Manual Decompilation Exercise

Given this disassembly (a small, self-contained function, -O0 ), manually translate to C: 

0000000000401220 <mystery>:
  401220:  push   rbp
  401221:  mov    rbp, rsp
  401224:  mov    QWORD PTR [rbp-0x18], rdi    ; arg1 -> local_18
  401228:  mov    QWORD PTR [rbp-0x20], rsi    ; arg2 -> local_20
  40122c:  mov    DWORD PTR [rbp-0x4], 0x0     ; local_4 = 0
  401233:  jmp    401256 <.L_check>
  401235:  mov    eax, DWORD PTR [rbp-0x4]     ; eax = local_4
  401238:  movsxd rdx, eax                      ; rdx = (int64_t)local_4 (sign extend)
  40123b:  mov    rax, QWORD PTR [rbp-0x18]    ; rax = arg1
  40123f:  add    rax, rdx                      ; rax = arg1 + local_4
  401242:  movzx  eax, BYTE PTR [rax]           ; al = arg1[local_4] (zero-extend)
  401245:  movsx  eax, al                       ; sign-extend al -> eax
  401248:  cdqe                                 ; sign-extend eax -> rax
  40124a:  add    QWORD PTR [rbp-0x8], rax      ; local_8 += char
  40124e:  add    DWORD PTR [rbp-0x4], 0x1      ; local_4++
  401252:  add    DWORD PTR [rbp-0x4], 0x1      ; local_4++  (???)
  401256:  mov    eax, DWORD PTR [rbp-0x4]      ; eax = local_4
  401259:  movsxd rdx, eax                      ; sign-extend
  40125c:  mov    rax, QWORD PTR [rbp-0x20]     ; rax = arg2
  401260:  cmp    rdx, rax                      ; if ((int64_t)local_4 < arg2)
  401263:  jl     401235                        ;   goto loop
  401265:  mov    rax, QWORD PTR [rbp-0x8]      ; return local_8
  401269:  pop    rbp
  40126a:  ret

Step-by-step reconstruction:

  1. Function takes two args: rdi (pointer) and rsi (integer). Let's call them char *buf and long len .
  2. [rbp-0x4] is a local initialized to 0, incremented each iteration - int i = 0 .
  3. [rbp-0x8] is a local that accumulates buf[i] - long sum = 0 . The listing skips its

initialization; a real -O0 build emits mov QWORD PTR [rbp-0x8], 0x0 before the loop. 1. The loop runs while (int64_t)i < len . 1. Inside: sum += buf[i] , i += 2 (the add DWORD PTR [rbp-0x4], 0x1 appears twice).

Wait - the double increment at 40124e and 401252 looks like i += 2 , but that's unusual for a sum. Let me reconsider. Actually at -O0 , the compiler might generate redundant code. Looking more carefully: the two add instructions are sequential and both target [rbp-0x4] . This means the loop variable increments by 2 each iteration. This is summing every other character.

Decompilation:

long mystery(const char *buf, long len) {
    long sum = 0;
    int i;
    for (i = 0; (long)i < len; i += 2) {
        sum += (long)(signed char)buf[i];
    }
    return sum;
}

The function sums every other byte of the input buffer, treating each byte as a signed char, then casting to long. Not useful per se, but walking through the annotation shows how local variables map to [rbp-offset] and how array indexing compiles to [base + index] addressing.

Common Pitfalls

Confusing lea with mov

lea rax, [rbp-0x8]     ; rax = rbp - 8  (ADDRESS)
mov rax, [rbp-0x8]     ; rax = *(rbp - 8)  (VALUE at that address)

If you see lea rax, [rbp-0x8] followed by mov rdi, rax; call scanf , the function is passing the address of a local variable to scanf - the function wants to write to that variable.

Missing the red zone

The System V ABI defines a 128-byte "red zone" below rsp that functions may use without adjusting rsp . Leaf functions (functions that don't call other functions) can access [rsp-0x80] through [rsp-0x1] without a sub rsp, ... . If you see [rsp-0x8] in a leaf function without a corresponding sub rsp , the red zone is in use - not a bug.

Tail call optimization

call foo
; ... more code ...
ret

vs.

; ... code ...
jmp foo

When a function ends with jmp target instead of call target; ret , it's a tail call. The callee's ret will return directly to the original caller. This is legitimate and common at -O2 .

Function Boundaries In Stripped Bins

Without symbols, function boundaries become non-obvious. Look for: - The prologue pattern ( push rbp; mov rbp, rsp; sub rsp, ... ) - ret instructions (end of function) - Padding bytes ( 0xcc or nop sequences) between functions - Alignment to 16-byte boundaries

RIP-Relative String References

lea rdi, [rip+0xe93]   ; rdi = &"some string" (rip-relative)

This loads the address of a string in .rodata . The disassembler may already resolve the actual string and show it as a comment: 

lea rdi, [rip+0xe93]   # 402010 "Access granted."

Reading Stripped Disassembly

When you run objdump -d on a stripped binary, you get raw addresses without function names. The workflow:

  1. Find _start or the entry point (ELF header e_entry field)
  2. _start calls __libc_start_main with main as an argument - look for the rdi argument to that call
  3. That register holds the address of main . Navigate there.
  4. From main , trace calls to find all user-defined functions.

Alternatively, let Ghidra/I DA do function detection and then read their disassembly. But knowing how to do it manually matters when dealing with custom loaders or obfuscated binaries that confuse automated analysis. 

objdump -d -M intel stripped_binary | grep -A5 "<_start>:"

Then follow the chain: _start -> __libc_start_main -> main .

Summary

Reading x86-64 disassembly is pattern recognition. The patterns are small and composable:

Pattern Recognition Signature C Equivalent
Prologue push rbp; mov rbp, rsp; sub rsp, N Function entry
Epilogue leave; ret Function exit
Zero register xor eax, eax x = 0
Null check test rax, rax; je if (!ptr)
Signed compare cmp; jl if (a < b)(signed)
Unsigned compare cmp; jb if (a < b)(unsigned)
Array access mov rax, [rdi + rsi*8] arr[i]whererdi=arr, rsi=i
Address-of lea rax, [rbp-8] &local_var
Tail call jmp funcat end return func(args)
Jump table jmp [base + rax*8] switchstatement
String reference lea rdi, [rip+offset] "string literal"

The skill compounds. Each pattern you internalize makes the next disassembly faster to read. The goal is to reach the point where you look at the assembly and see the C - not translate instruction by instruction, but recognize the gestalt of loops, conditionals, and function boundaries instantly.

Challenge

Disassemble a binary with objdump -d -M intel --no-show-raw-insn binary > disasm.txt . Write a Go tool that parses that listing and, for every function, reports whether it has a standard prologue ( push rbp followed by mov rbp, rsp ), whether it has an epilogue ( leave ), and which functions it tail-calls through jmp . Compile the example from this article at -O0 and -O2 and compare the reports. 

package main

import (
	"bufio"
	"fmt"
	"os"
	"regexp"
	"strings"
)

var (
	reFunc    = regexp.MustCompile(`^([0-9a-f]+) <([^>]+)>:`)
	rePushRbp = regexp.MustCompile(`\bpush\s+rbp\b`)
	reMovRsp  = regexp.MustCompile(`\bmov\s+rbp,\s*rsp\b`)
	reLeave   = regexp.MustCompile(`\bleave\b`)
	reJmp     = regexp.MustCompile(`\bjmp\s+[0-9a-f]+\s+<([^>+]+)`)
)

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintf(os.Stderr, "usage: %s <disasm.txt>\n", os.Args[0])
		os.Exit(1)
	}

	file, err := os.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer file.Close()

	var current string
	var hasPush, hasFrame, hasLeave bool
	var tails []string

	flush := func() {
		if current == "" {
			return
		}
		fmt.Printf("%s\n", current)
		fmt.Printf("  prologue: %v\n", hasPush && hasFrame)
		fmt.Printf("  epilogue: %v\n", hasLeave)
		for _, tail := range tails {
			fmt.Printf("  tail call: %s\n", tail)
		}
		tails = tails[:0]
	}

	scanner := bufio.NewScanner(file)
	for scanner.Scan() {
		line := strings.TrimSpace(scanner.Text())

		if match := reFunc.FindStringSubmatch(line); match != nil {
			flush()
			current = match[2]
			hasPush, hasFrame, hasLeave = false, false, false
			continue
		}
		if current == "" {
			continue
		}
		if rePushRbp.MatchString(line) {
			hasPush = true
		}
		if reMovRsp.MatchString(line) {
			hasFrame = true
		}
		if reLeave.MatchString(line) {
			hasLeave = true
		}
		if match := reJmp.FindStringSubmatch(line); match != nil {
			tails = append(tails, match[1])
		}
	}
	flush()
}
