Linux Assembly Part 5: Addressing

Learn Linux assembly to work with memory, arrays and strings.

Overview

This is the fifth article of the Linux Assembly series, the previous article described the Linux Assembly Part 4: Arithmetic . This time, we will focus on how to read from and write to memory. We already touched on the [buffer] notation in the previous articles, but now we are going to take a closer look at the different addressing modes, how to work with arrays, and how the x86 string instructions make dealing with memory much easier.

Effective Addresses

So far we have mostly used registers to store values. But registers are limited in number, and larger amounts of data (like our strings and buffers) live in memory. In order to access that data, we need to know how to calculate the address of the data we want to read or write.

The x86_64 instruction set supports a handful of different addressing modes, all of which are written between square brackets. The general form of an effective address looks like this: 

[ base + index * scale + displacement ]

Every part is optional, which gives us these common combinations:

Addressing form Description
[rax] value at the address stored inrax
[rax + 8] value atrax + 8
[numbers + rcx * 8] value atnumbers + rcx * 8(array access)
[rax + rbx * 4 + 16] value atrax + rbx * 4 + 16

The scale is always one of 1 , 2 , 4 , or 8 , which corresponds nicely to the size of our data types ( byte , word , doubleword , and quadword ) from Linux Assembly Part 2 about Declaring Data .

When we write [numbers + rcx * 8] , we don't modify the numbers label or the rcx register. We only calculate the address, read or write the value stored there, and then throw the address away again. The result is that we can iterate over an array by incrementing rcx .

The LEA Instruction

There is one instruction that does the opposite: LEA (load effective address) calculates the address itself and stores it in a register, without touching the memory that the address points to. 

lea rax, [numbers + rcx * 8]  ; rax = address of numbers[rcx]
mov rax, [numbers + rcx * 8]  ; rax = value of numbers[rcx]

LEA is often abused by compilers as a fast way to do small calculations that don't have anything to do with memory, because it can compute base + index * scale + displacement in a single instruction without modifying any status flags: 

lea rax, [rbx + rbx * 2]  ; rax = rbx * 3
lea rax, [rbx + 8]        ; rax = rbx + 8

This is a common trick you will see a lot when you disassemble compiled programs.

Arrays

In Linux Assembly Part 2 about Declaring Data we learned how to declare data with the pseudo instructions DB , DW , DD , and DQ . When we declare multiple values separated by commas, NASM places them next to each other in memory, which effectively creates an array: 

numbers: dq 13, 37, 50, 24, 481

Each dq is 8 bytes long, so the numbers array occupies 5 * 8 = 40 bytes in memory. We can access the individual elements with a scaled index, because the n -th element lives at the address numbers + n * 8 : 

mov rcx, 2
mov rax, [numbers + rcx * 8]  ; rax = numbers[2] = 50

There is no bounds checking in assembly. If we use an index that is too large, we happily read or write whatever happens to be stored after the array, which is the root cause of most memory corruption bugs. We are going to exploit exactly that behavior later in this article series.

Array Sum Program

Now we know everything to iterate over an array and calculate the sum of all its elements. We reuse the print_number helper routine from the previous article to print the result: 

section .data
    numbers: dq 13, 37, 50, 24, 481
    numbers_len: equ 5

    label_sum: db "Sum: "
    newline:   db 0x0a

section .bss
    buffer resb 20

section .text
    global _start

_start:
    xor rax, rax ; sum = 0
    xor rcx, rcx ; index = 0

.sum_loop:
    add rax, [numbers + rcx * 8]
    inc rcx
    cmp rcx, numbers_len
    jl .sum_loop

    mov rsi, label_sum
    mov rdx, 5
    call .write
    call .print_number
    call .print_newline
    call .exit

; (...)

The loop keeps adding numbers[rcx] to rax until rcx reaches numbers_len . Note how the cmp / jl combination from Linux Assembly Part 3 about Control Flow is used as the loop condition.

The array sum program can also be downloaded from here . If we compile and run our program, we can see the sum of all array elements: 

nasm -f elf64 -o arrays.o arrays.asm;
ld -o arrays.bin arrays.o;
chmod +x arrays.bin;

./arrays.bin;

The output of the program should look like this:

Sum: 605

String Instructions

Because dealing with strings and buffers is so common, the x86 instruction set has a whole family of instructions that operate on memory directly. They all work on the pair of registers rsi (source index) and rdi (destination index), and they all have a variant that can be repeated with the REP prefixes:

Instruction Description
MOVSB copy a byte from[rsi]to[rdi]
MOVSW copy a word from[rsi]to[rdi]
MOVSQ copy a quadword from[rsi]to[rdi]
STOSB storealto[rdi]
LODSB load[rsi]intoal
SCASB compare[rdi]withaland set the flags
CMPSB compare[rsi]with[rdi]and set the flags

Each of these instructions automatically increments or decrements rsi and/or rdi by the size of the operation. Whether they go forward or backward depends on the direction flag inside the rflags register:

  • CLD clears the direction flag, so the pointers move forward.
  • STD sets the direction flag, so the pointers move backward.

The REP prefix repeats the following instruction rcx times, decrementing rcx each time. The REPE / REPZ prefix repeats while rcx is non-zero _and_ the zero flag is set, and REPNE / REPNZ repeats while rcx is non-zero _and_ the zero flag is not set. This is what makes searching for a byte inside a string a single instruction instead of a whole loop.

String Program

The following program demonstrates two of the most common string operations: finding the length of a null-terminated string with REPNE SCASB , and copying a string with REP MOVSB . 

section .data
    source: db "Hello, World!", 0
    source_len: equ $ - source ; 14 bytes (13 characters + null terminator)

    label_len:  db "Length: "
    label_copy: db "Copy:   "
    newline:    db 0x0a

section .bss
    dest resb 32
    buffer resb 20

section .text
    global _start

_start:
    ; strlen via repne scasb
    xor al, al       ; search for the null byte
    mov rdi, source  ; start scanning at source
    mov rcx, -1      ; scan "forever" (until a match is found)
    cld              ; clear direction flag (scan forward)
    repne scasb      ; decrement rcx and compare [rdi] with al

    ; rdi now points one byte past the null terminator
    mov rax, rdi
    sub rax, source
    dec rax          ; rax = length = 13

    mov rsi, label_len
    mov rdx, 8
    call .write
    call .print_number
    call .print_newline

    ; memcpy source -> dest via rep movsb
    mov rsi, source  ; source pointer
    mov rdi, dest    ; destination pointer
    mov rcx, source_len
    cld              ; copy forward
    rep movsb        ; copy rcx bytes from [rsi] to [rdi]

    mov rsi, label_copy
    mov rdx, 8
    call .write
    mov rsi, dest
    mov rdx, source_len - 1
    call .write
    call .print_newline

    call .exit

; (...)

The string program can also be downloaded from here . If we compile and run our program, we can see the length and the copied string: 

nasm -f elf64 -o strings.o strings.asm;
ld -o strings.bin strings.o;
chmod +x strings.bin;

./strings.bin;

The output of the program should look like this:

Length: 13
Copy:   Hello, World!

The REPNE SCASB instruction is worth understanding in detail, because it is what the C function strlen() compiles down to. We tell it to search for a null byte ( xor al, al ), set the count to "practically infinite" ( mov rcx, -1 ), and let it scan forward. Once the null byte is found, rdi points one byte past it, so we subtract the start address of the string and then 1 to get the actual length.
