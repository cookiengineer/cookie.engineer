Opencode Reasoning Extractor

Overview

GitHub Repository | GitLab Mirror

The Opencode Reasoning Extractor turns existing OpenCode session history into training data for smaller self-hosted models, specifically Qwen3.8 27B. It does not run a teacher model again, does not generate synthetic answers, and does not spend additional inference tokens on distillation.

The sessions are already there. A planner model drives the build or plan agent, hires smaller explore and general subagents, calls tools, reads results, and writes code or reports. Those transcripts contain the reasoning traces, tool calls, and tool outputs that supervised fine-tuning needs. The exporter collects them, classifies them by topic, removes refusals and secrets, and writes OpenAI-compatible datasets.

This makes post-training effectively free of extra inference cost. A body of real work in software development, exploit development, or cybersecurity can be reused instead of discarded. The project is intended for engineers who want their own model to learn from their own agent workflows, and for security teams that treat session history as a private asset rather than public benchmark material.

Features

  • Read-only access to an OpenCode data directory and its opencode.db.
  • Pure Go SQLite driver with no runtime dependencies.
  • Converts text, reasoning, tool calls, and tool results into OpenAI-compatible chat messages.
  • Preserves reasoning_content in its output, so that the chain of thought remains part of the training.
  • Pairs every tool call with its result and carries the resolved tool name and arguments.
  • Writes topic-partitioned per-session and per-assistant-turn records, with optional subagent trees.
  • Multi-label topic classification with weighted keywords over the title and chat history contents.
  • Built-in classification catalog for session categories, and a general fallback.
  • Refusal filtering drops sessions where a model denied the request, with strong and weak patterns.
  • Secret redaction for private keys, tokens and passwords.

Architecture

The extractor is a pipeline with a deliberately narrow data path:

  1. The store package opens opencode.db in read-only mode and exposes projects, sessions, messages, and parts.
  2. The model package parses the JSON payloads stored in the message and part rows.
  3. The convert package merges parts into chat messages and pairs tool calls with results.
  4. The classify package assigns one or more topics from a weighted keyword catalog.
  5. The compliance package rejects sessions that contain refusal language.
  6. The redact package scrubs credentials from every free-text field.
  7. The format package writes the partitioned JSON Lines files and the manifest.

The default classifier scores matches in each field with a different weight. A hit in the title counts more than a hit in a tool output, and a strong keyword counts twice as much as a weak one.

Scores are normalized to the best match, and every topic above the multi-label threshold is assigned. If nothing scores, the session goes to general. The catalog actually used is copied into the output directory, so an export can be reproduced later.

Refusal detection is intentionally separate from topic classification. Strong refusal patterns are anchored to the start of a sentence, so a quoted example in a writeup does not exclude the session. The detector scores assistant text and reasoning separately, drops the whole session when the threshold is crossed, and records the number of skipped sessions in the manifest and run summary. The refusal dictionary is shipped next to the output for auditability.

The exported tree is plain ASCII and easy to consume:

<output-dir>/
  manifest.json
  catalog.yaml
  refusals.yaml
  sft/<topic>/sessions.jsonl
  sft/<topic>/turns.jsonl
  subagents/<topic>/sessions.jsonl
  subagents/<topic>/turns.jsonl
  rl/metadata.jsonl

Each session also produces an entry in rl/metadata.jsonl with tool calls, tool errors, tool success rate, finish reasons, patches, files touched, tokens, cost, and quality flags. That gives a later reinforcement-learning stage a verifier-agnostic starting point.

Building

Go 1.27 or newer is required. The SQLite driver is pure Go, so no C toolchain is needed:

make build;   # build/opencode-extractor
make test;    # unit and end-to-end tests

Testing

The test suite uses a synthetic SQLite fixture and covers the whole extraction path:

It checks the store adapter, conversation conversion, tool-call pairing, system prompts, per-turn records, topic classification, multi-label selection, keyword boundaries, secret redaction, refusal detection, strict and rich output, dry runs, resume behavior, and the manifest contents.

make test;

Usage: Dry Run

Classify the database and print per-session decisions without writing any filesystem output:

./build/opencode-extractor \
  --dry-run \
  --verbose \
  ~/.local/share/opencode \
  ./out/reasoning-dataset;

The summary reports exported sessions, subagents, tool calls, tool errors, redactions, skipped refusals, topic counts, model counts, and agent counts. This is the cheapest way to check that the catalog and filters match the data before committing to a full export.

Usage: Export

Run the extraction against an OpenCode data directory:

./build/opencode-extractor \
  --force \
  ~/.local/share/opencode \
  ./datasets/reasoning-mycomputer;

The input may also be the opencode.db file itself. If the output directory already contains a manifest, the run refuses to overwrite it unless --force or --resume is given.

The --resume flah skips sessions already listed in an existing manifest, which is useful when a long export was interrupted or when you have multiple profiles you want to export as training data.

Usage: Training Dataset Layout

Inspect the result and pick a topic directory from the output or manifest:

find ./datasets/reasoning-mycomputer -maxdepth 3 -type f | sort;
sed -n '1p' ./datasets/reasoning-mycomputer/sft/software-development/sessions.jsonl;

A rich session record keeps the chat history and the metadata:

{
  "id": "ses_abc123",
  "topic": ["software-development"],
  "messages": [
    {"role": "user", "content": "Refactor the parser."},
    {"role": "assistant", "content": "I will split it.", "reasoning_content": "First inspect the call sites."}
  ],
  "meta": {
    "agent": "build",
    "model": "deepseek-v4-pro",
    "topic_scores": {"software-development": 1.0},
    "tools": [{"name": "read"}]
  }
}

The --strict-openai flag drops the reasoning content, tool schemas, and sidecar metadata and writes only the minimal messages array. Use that mode when a framework insists on standard OpenAI fine-tuning records.

The rich mode that contains the reasoning_content is the one that preserves the reasoning traces that the Qwen 3.8 Reasoning Trainer actually needs.

Usage: Qwen Training

The output is the input format expected by the Qwen 3.8 Reasoning Trainer. Build the trainer and point it at one or more exported datasets:

./build/qwen-trainer dataset \
  --model models/Qwen3.8-27B-UD-Q4_K_M.gguf \
  --dataset ./datasets/reasoning-mycomputer;

./build/qwen-trainer train \
  --model models/Qwen3.8-27B-abliterated-UD-Q4_K_M.gguf \
  --device \
  --dataset ./datasets/reasoning-mycomputer \
  --dataset ./datasets/reasoning-othercomputer \
  --include-subagents \
  --seq-len 1024 \
  --steps 1002 \
  --out models/Qwen3.8-27B-abliterated-DeepSeek-UD-Q4_K_M.gguf;

The trainer deduplicates sessions across topic files and across dataset roots, unions the tool registries, renders the model chat template, and builds the loss masks. The extractor therefore only has to produce honest, filtered session data; the model-specific formatting stays in the trainer.
