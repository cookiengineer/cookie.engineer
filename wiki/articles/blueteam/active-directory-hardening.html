Active Directory Hardening

Defending enterprise Windows environments through attack path analysis, tiered administration, and Kerberos security.

Overview

Active Directory is the identity backbone of most enterprise Windows environments. It controls authentication, authorization, group policy, certificate services, and DNS . Compromising it means controlling every domain-joined system. After reading this article you can map attack paths with BloodHound, apply the tiered administration model, and harden Kerberos and NTLM against the common credential-theft techniques.

Required Reading

  • Authentication - password hashing, credential storage, Kerberos fundamentals
  • Authorization - access control models, group membership, token-based auth

Concept

Active Directory is the identity backbone of most enterprise Windows environments. It controls authentication, authorization, group policy, certificate services, and DNS . Compromising AD means full control of every domain-joined system, every user session, and every service account. A single Domain Admin credential is effectively root on every domain-joined machine.

AD security is not about patching; it is about architecture. A correctly designed AD forest limits blast radius. An incorrectly designed one has paths from a helpdesk account to Enterprise Admin in three hops. BloodHound reveals these paths. Tiered administration eliminates them.

AD Architecture

                        |      Forest          |

Components

Component Role
Domain Controller (DC) Holds writable copy of domain database (NTDS.dit). Kerberos KDC, LDAP, DNS.
Global Catalog (GC) Partial read-only replica of every domain object in the forest. Required for forest-wide searches, universal group membership resolution.
FSMO Roles Schema Master, Domain Naming Master, RID Master, PDC Emulator, Infrastructure Master. Each has specific responsibilities.
Trusts Authentication path between domains. Parent-child (automatic, transitive). External trusts (non-transitive). Forest trust (between forests).
Organizational Unit (OU) Container for users/computers. GPOs are linked to OUs.

Security Boundaries

  • Forest: a security boundary. There is no automatic trust between forests, so a compromise in Forest A cannot reach Forest B without an explicit external trust.
  • Domain: an administrative boundary, not a security boundary. A Domain Admin in a child domain can often escalate to Enterprise Admin in the forest root through trust abuse.

Kerberos Security

Kerberos is the default authentication protocol in AD. Understanding it is foundational to both attack and defense. 

AS-REQ/AS-REP: Authentication Service
  Client -> KDC: AS-REQ (username, timestamp encrypted with password hash)
  KDC -> Client: AS-REP (TGT encrypted with krbtgt hash)

TGS-REQ/TGS-REP: Ticket Granting Service
  Client -> KDC: TGS-REQ (TGT + SPN of target service)
  KDC -> Client: TGS-REP (Service Ticket encrypted with target service's hash)

AP-REQ: Application Request
  Client -> Service: AP-REQ (Service Ticket + Authenticator)
  Service: Decrypts ticket using its own hash -> extracts session key -> verifies authenticator

Defensive Config

PAC Validation (Privilege Attribute Certificate):
  -> Ensures the PAC (claims about user/groups) is valid
  -> Prevents PAC spoofing (MS14-068 / "Golden PAC" attack)
  -> Required: HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Lsa\Kerberos\Parameters
               ValidatePac = 1

AES Encryption for Kerberos:
  -> RC4 is broken - enforce AES for ticket encryption
  -> Group Policy: Computer Configuration -> Policies -> Windows Settings ->
     Security Settings -> Local Policies -> Security Options ->
     Network security: Configure encryption types allowed for Kerberos
     -> AES256_HMAC_SHA1, AES128_HMAC_SHA1, FUTURE
     -> Uncheck: DES_CBC_CRC, DES_CBC_MD5, RC4_HMAC_MD5

Ticket Lifetime:
  -> TGT lifetime: default 10 hours - reduce for high-privilege accounts
  -> Service ticket lifetime: default 600 minutes - reduce for sensitive services
  -> Set via GPO: Kerberos Policy -> Maximum lifetime for user ticket

SID Filtering

  • SID filtering blocks SID history injection from trusted domains.
  • Enable it with netdom trust <trusted> /quarantine:yes .
  • Without SID filtering, an attacker can inject an Enterprise Admin SID into a ticket from a trusted domain.

Attack Paths

Kerberoasting

Attack: Request a service ticket for any SPN -> extract the ticket -> brute-force offline
         No special privileges required - any domain user can request any service ticket.

Defense:
  1. Use Group Managed Service Accounts (gMSA) - 120-character random password, auto-rotated
  2. If gMSA is impossible: service account passwords > 25 characters, random
  3. Audit SPNs: computer accounts (names ending in "$") often have SPNs but weak passwords
  4. Monitor: Event ID 4769 (Kerberos Service Ticket Operations) with Ticket Encryption Type 0x17 (RC4)
     -> RC4 service tickets = kerberoasting indicator

# Check for weak SPN accounts
Get-ADUser -Filter {ServicePrincipalName -ne "$null"} -Properties ServicePrincipalName,PasswordLastSet |
  Select-Object Name,PasswordLastSet,ServicePrincipalName |
  Export-Csv -Path spn-accounts.csv

AS-REP Roasting

Attack: Account with "Do not require Kerberos preauthentication" enabled
         -> Request AS-REP without pre-auth -> receive encrypted response -> brute-force offline

Defense:
  1. Leave "Do not require Kerberos preauthentication" unset on ALL accounts
     (pre-auth is required by default; only legacy interop needs the exception)
  2. Audit: Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true}

# Find accounts with pre-auth disabled
Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true} -Properties DoesNotRequirePreAuth

DCSync

Attack: Replicate domain data from a DC (like a legitimate DC replication)
         Requires: Replicating Directory Changes privileges (domain admin equivalent)
         "Mimikatz lsadump::dcsync /user:krbtgt" -> extracts the krbtgt hash

Defense:
  1. Limit Replicating Directory Changes to Domain Controllers ONLY (default)
     -> NEVER grant it to any other account or group
  2. Monitor: Event ID 4662 (Directory Service Access) for replication-specific GUIDs
     -> 1131f6aa-9c07-11d1-f79f-00c04fc2dcd2 = DS-Replication-Get-Changes
     -> 1131f6ad-9c07-11d1-f79f-00c04fc2dcd2 = DS-Replication-Get-Changes-All
     -> Any non-DC account triggering these = DCSync attack
  3. ATA / MDI: alerts on DCSync automatically

Golden Ticket

Attack: Possess the krbtgt hash -> forge a TGT with an arbitrary PAC (any user, any groups, any lifetime)
         krbtgt hash = domain controller equivalent, never expires

Defense:
  1. Rotate the krbtgt password TWICE (invalidates existing golden tickets)
     -> Requires waiting for replication + max ticket lifetime between rotations
     -> Script: Reset-krbtgtPassword.ps1 (from Microsoft)
  2. Monitor: TGT lifetime greater than the configured maximum -> forged ticket
  3. Monitor: TGT from an unexpected IP or workstation (anomaly)

Silver Ticket

Attack: Possess a service account hash -> forge a service ticket for that specific SPN
         Detected when PAC validation fails (the PAC contains real user info)

Defense:
  1. Validate PAC: configured above
  2. gMSA for all service accounts -> no static hash to steal
  3. Host isolation: service tickets are validated locally, so there is no network detection
     -> Defense: host-based monitoring (Sysmon Event ID 10, 11)

Pass-the-Hash

Attack: Possess an NTLM hash (not the password) -> authenticate to any system accepting NTLM
         Mimikatz: sekurlsa::pth /user:Administrator /domain:corp /ntlm:<hash>

Defense:
  1. Protected Users group - blocks NTLM entirely (Kerberos only)
  2. Disable NTLM where possible: Network security: Restrict NTLM
  3. Credential Guard: LSASS runs in a VBS enclave, hashes never exposed
  4. Monitor: Event ID 4624 (Logon) with LogonProcessName: NtLmSsp
     -> Any NTLM logon from a Protected User = alert

NTLM Relay

Attack: Intercept NTLM authentication, relay it to another server
         (no hash needed - just SMB signing disabled + a victim coerced to authenticate)

Defense:
  1. Enable SMB Signing: HKLM\SYSTEM\CurrentControlSet\Services\LanmanServer\Parameters
     -> RequireSecuritySignature = 1
  2. Enable LDAP Signing + Channel Binding
  3. Enable EPA (Extended Protection for Authentication): IIS, Exchange
  4. Disable LLMNR, NetBIOS Name Service, and mDNS (poisoning sources)

Common Misconfigurations

1. Unconstrained Delegation on non-DCs
   -> If an attacker compromises a host with unconstrained delegation,
      they can capture every TGT of every user who authenticates to it.
   -> Exploit: PrinterBug + unconstrained delegation = force a DC to authenticate -> capture DC TGT
   -> Fix: Remove unconstrained delegation. Use constrained delegation or gMSA.

2. Pre-Windows 2000 Compatible Access group
   -> Members can read every object in the domain (equivalent to pre-2000 anonymous access)
   -> Often contains "Authenticated Users" or "Everyone" -> massive overexposure
   -> Fix: Empty this group. Remove "Authenticated Users" and "Everyone."

3. Excessive Admin Count
   -> Every user who was ever a member of a protected group retains adminCount=1 permanently
   -> Their ACLs are different (inheritance disabled) even after removal from admin groups
   -> Fix: Regular audit + reset the adminSDHolder-inherited permissions

4. Service accounts in Domain Admins
   -> SQL Server service account in Domain Admins -> compromise SQL Server = compromise domain
   -> Fix: Service accounts should have least privilege. Never in Domain Admins.

5. Password not required (UserAccountControl PASSWD_NOTREQD)
   -> Accounts without passwords, often linked to legacy service migration
   -> Fix: Disable, set a password, or remove if unused.

Tiered Administration

The Microsoft-recommended model separates accounts and workstations by tier. An account at a lower tier cannot interact with assets at a higher tier. 

Tier 0 - Forest/Domain Administration:
  Assets: Domain Controllers, ADFS, AD Connect, PIM/PAM, PKI
  Accounts: Domain Admins, Enterprise Admins, Schema Admins, BUILTIN\Administrators
  Workstations: Tier 0 PAW (Privileged Access Workstation) - no internet, no email, no web
  Auth policy: Kerberos only, Smart Card required, no lateral movement from lower tiers

Tier 1 - Server Administration:
  Assets: All servers (not DCs), cloud infrastructure
  Accounts: Server Admins, local admin groups on servers
  Workstations: Tier 1 admin workstation (may have limited internet)
  Cannot interact with: Tier 0 assets

Tier 2 - Workstation Administration:
  Assets: End-user workstations, laptops, VDI
  Accounts: Helpdesk, desktop support, local admin on workstations
  Workstations: Standard corporate device
  Cannot interact with: Tier 0 or Tier 1 assets

Enforcement mechanisms:

  1. GPO "Deny logon locally" and "Deny logon through Remote Desktop": Tier 1 accounts are denied logon on Tier 0 machines, and Tier 2 accounts are denied on Tier 0 and Tier 1 machines.
  2. Authentication Policy Silos (Windows Server 2016+) restrict which hosts a tiered account can authenticate to; a Tier 0 account can only get a TGT on a Tier 0 workstation, which prevents pass-the-hash from a compromised Tier 1 host to a Tier 0 domain controller.
  3. Logon restrictions via New-ADAuthenticationPolicy .
# Create an Authentication Policy Silo for Tier 0
New-ADAuthenticationPolicySilo -Name "Tier0-Silo" `
  -UserAuthenticationPolicy "Tier0-AuthPolicy" `
  -ComputerAuthenticationPolicy "Tier0-AuthPolicy"

# Add Tier 0 accounts and workstations to the silo
Grant-ADAuthenticationPolicySiloAccess -Identity "Tier0-Silo" `
  -Account "Tier0-Admins-Group"
Grant-ADAuthenticationPolicySiloAccess -Identity "Tier0-Silo" `
  -Account "Tier0-Workstations-Group"

LAPS

L AP S (Local Administrator Password Solution) ensures every domain-joined computer has a unique, random, rotated local admin password stored in a confidential AD attribute. 

# Deploy LAPS (built into Windows since Server 2016 / Windows 10 1803+)

# 1. Extend the AD schema (one-time, Enterprise Admin):
Update-LapsADSchema

# 2. Configure the LAPS GPO:
# Computer Configuration -> Administrative Templates -> LAPS
#   Configure password backup directory: Active Directory
#   Password Settings: Password Complexity (large letters + small + numbers + specials)
#   Password Age (Days): 30
#   Name of administrator account to manage: Administrator (default)

# 3. Configure the ACL: who can read the LAPS password?
Set-LapsADReadPasswordPermission -Identity "OU=Workstations,DC=corp,DC=example,DC=com" `
  -AllowedPrincipals "LAPS-Readers-Group"

# 4. Retrieve the LAPS password (requires LAPS-Readers group membership):
Get-LapsADPassword -Identity "WORKSTATION01" -AsPlainText

# 5. Verify rotation:
Get-LapsADPassword -Identity "WORKSTATION01" | Select-Object PasswordLastSet
						
LAPS security properties:
- Windows LAPS stores the password in msLAPS-Password (or msLAPS-EncryptedPassword when encrypted)
- Legacy Microsoft LAPS stored it in ms-Mcs-AdmPwd
- Read permission is explicit: only designated groups
- Password rotated every 30 days (configurable) or triggered manually
- Each computer has a DIFFERENT password -> no lateral movement via local admin
- Without LAPS: the local admin password is the same across all computers (or blank) -> PtH paradise

Protected Users

Adding an account to the Protected Users group applies these protections automatically:

Domain-joined Windows Server 2012 R2+ / Windows 8.1+:
  [+] Kerberos only - NTLM, Digest, CredSSP disabled
  [+] AES only - RC4 disabled for Kerberos pre-authentication
  [+] No delegation - constrained and unconstrained delegation blocked
  [+] No cached credentials - cannot log in offline
  [+] TGT lifetime: 4 hours (instead of 10 hours)

Who should be in Protected Users:
  - Domain Admins
  - Enterprise Admins
  - Schema Admins
  - Service accounts with high privilege
  - Any account that should NEVER use NTLM

Caveats:
  - Linux/macOS devices joined to AD may break (no AES support in some Samba versions)
  - Legacy applications using NTLM will break
  - Test before broad deployment

Credential Guard

Credential Guard virtualizes LSASS . Instead of running in the OS kernel, it runs in VBS (Virtualization-Based Security), which uses the Hyper-V hypervisor to isolate secrets from the kernel. 

Without Credential Guard:
  LSASS.exe (user mode) -> credentials in memory -> Mimikatz reads them

With Credential Guard:
  LSAIso.exe (VBS enclave) <- credentials stored here
  LSASS.exe (user mode) <- only has RPC communication to LSAIso
  -> Even kernel-mode malware cannot extract credentials
  -> Mimikatz sees empty hashes

Enabling Credential Guard:
  Requirements: Windows 10 Enterprise/Education, Windows Server 2016+
                Hardware: VT-x, VT-d, TPM 2.0
                UEFI Secure Boot enabled

  GPO: Computer Configuration -> Administrative Templates ->
       System -> Device Guard -> Turn On Virtualization Based Security
       -> Secure Boot with DMA Protection
       -> Credential Guard Configuration: Enabled with UEFI lock

  Verify:
  Get-CimInstance -Namespace root\Microsoft\Windows\DeviceGuard -ClassName Win32_DeviceGuard |
    Select-Object SecurityServicesRunning
  # Should show: 1 (Credential Guard)

Defender for Identity

Microsoft Defender for Identity (MDI), formerly Azure Advanced Threat Protection (ATP), places sensors on DC s to monitor authentication traffic and detect attacks. 

Detections (non-exhaustive):
  - DCSync / Directory Services Replication
  - Golden Ticket (abnormal TGT lifetime, RC4 downgrade)
  - Pass-the-Hash (abnormal NTLM properties)
  - Overpass-the-Hash (Kerberos AS-REQ with RC4 from a user normally using AES)
  - Kerberoasting (excessive TGS-REQ with RC4)
  - Brute force (excessive auth failures, password spray patterns)
  - Suspicious LDAP queries (enumeration, SAMR queries)
  - DNS reconnaissance (AXFR requests)
  - Remote code execution (PsExec, WMI, PowerShell remoting from an unusual source)

Open-source alternative: Wazuh + custom AD rules, Zeek (Bro) for DC network traffic.

Group Policy Baselines

# Core GPO security settings (apply at domain or OU level)

# 1. Disable NTLM (on domain controllers first, then member servers)
#    Network security: Restrict NTLM: Incoming NTLM traffic -> Deny all accounts
#    Network security: Restrict NTLM: NTLM authentication in this domain -> Deny all
#    Network security: Restrict NTLM: Audit NTLM -> Enable all (audit before blocking!)

# 2. Disable legacy protocols
#    Network security: LAN Manager authentication level -> Send NTLMv2 only, refuse LM & NTLM
#    Microsoft network client: Digitally sign communications (always) -> Enabled
#    Microsoft network server: Digitally sign communications (always) -> Enabled

# 3. Restrict anonymous access
#    Network access: Do not allow anonymous enumeration of SAM accounts -> Enabled
#    Network access: Do not allow anonymous enumeration of SAM accounts and shares -> Enabled
#    Network access: Restrict anonymous access to Named Pipes and Shares -> Enabled

# 4. Enforce LDAP signing and channel binding
#    Domain controller: LDAP server signing requirements -> Require signing
#    Network security: LDAP client signing requirements -> Require signing

# 5. Disable NetBIOS over TCP/IP on all network interfaces
#    (Blocks LLMNR/NBT-NS poisoning)

# 6. Disable WPAD
#    Turn off automatic detection of intranet proxy -> Enabled
#    (Blocks Web Proxy Auto-Discovery poisoning -> credential capture)

# 7. LSA Protection
#    LSA protection: Enable Protected Process Light for LSA -> Enabled

# 8. Disable WDigest
#    Network security: WDigest Authentication -> Disabled
#    (WDigest stores cleartext passwords in memory)

# 9. Restrict Remote Desktop Services
#    Set client connection encryption level -> High Level
#    Require use of specific security layer for remote connections -> SSL

# 10. Account Lockout Policy (balance: DoS vs brute force)
#     Account lockout threshold: 10 invalid logon attempts
#     Account lockout duration: 15 minutes
#     Reset account lockout counter after: 15 minutes

Forest Recovery

Forest recovery is the nuclear option: you restore the entire Active Directory forest from backup because every DC is compromised. This is a "never practice this live" scenario. Microsoft publishes an official Forest Recovery Guide. 

Prerequisites:
  1. System State backups of at least 2 DCs per domain - on separate, secure storage
  2. Backup encryption keys stored offline (printed, in a safe)
  3. Documented recovery procedure - printed, not digital (digital may be encrypted)
  4. Tested at least once - tabletop exercise minimum

Recovery phases (simplified):
  Phase 1: Isolate all DCs from the network (air-gap)
  Phase 2: Identify a clean backup - the last known good state
  Phase 3: Recover one DC per domain in isolation (no network)
  Phase 4: Clean the recovered DC (remove persistence, reset krbtgt twice)
  Phase 5: Promote the recovered DCs as source of authority
  Phase 6: Rebuild all other DCs from media (not from recovery)
  Phase 7: Reset all user passwords and all service account passwords
  Phase 8: Rejoin all member servers and workstations to the domain

Detection Queries

# Run these daily - export results to the SIEM

# New Domain Admins (last 24h)
$yesterday = (Get-Date).AddDays(-1)
Get-ADGroupMember -Identity "Domain Admins" -Recursive |
  Where-Object { $_.whenCreated -gt $yesterday -or $_.whenChanged -gt $yesterday }

# New accounts with SPNs (potential kerberoasting targets)
Get-ADUser -Filter {ServicePrincipalName -ne "$null"} -Properties ServicePrincipalName,whenCreated |
  Where-Object { $_.whenCreated -gt $yesterday }

# Changes to privileged groups
$privileged_groups = @("Domain Admins", "Enterprise Admins", "Schema Admins", "Administrators")
foreach ($group in $privileged_groups) {
  Get-ADGroupMember -Identity $group | Select-Object @{N="Group";E={$group}},Name,SamAccountName
}

# New accounts with unconstrained delegation
Get-ADObject -Filter {UserAccountControl -band 0x80000} -Properties UserAccountControl

# Accounts with password never expires
Get-ADUser -Filter {PasswordNeverExpires -eq $true}

# Accounts where pre-auth is not required
Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true} -Properties DoesNotRequirePreAuth

# Computers without LAPS configured
Get-ADComputer -Filter * -Properties ms-Mcs-AdmPwd |
  Where-Object { -not $_.'ms-Mcs-AdmPwd' }

Hardening Roadmap

Week 1-2: Visibility
  - Deploy BloodHound -> map attack paths
  - Deploy MDI sensors on DCs (or Wazuh for an open-source equivalent)
  - Enable advanced audit logging (Event IDs: 4624, 4768, 4769, 4662, 4720, 4728)
  - Create a baseline: list all Domain Admins, SPNs, delegation configs

Week 3-4: Quick Wins
  - Add all Domain/Enterprise/Schema Admins to Protected Users
  - Deploy LAPS -> validate unique passwords on all workstations
  - Disable RC4 for Kerberos
  - Enable Credential Guard on admin workstations
  - Kerberoasting audit -> identify and fix weak SPN passwords (gMSA)

Month 2-3: Structural
  - Implement the Tiered Admin model (PAWs for Tier 0)
  - Authentication Policy Silos for Tier 0
  - Remove unconstrained delegation and excessive permissions
  - Rotate the krbtgt password twice
  - Disable NTLM (audit mode first, then enforce)

Month 4-6: Continuous
  - Regular BloodHound analysis -> close new paths
  - gMSA rollout for all service accounts
  - AD Forest recovery plan -> test
  - Purple team exercises: test detection efficacy

Challenge

Write a Go tool that reads a BloodHound-style privilege graph as JSON and finds the shortest attack path from a start principal to a target principal using breadth-first search. 

package main

import (
	"encoding/json"
	"fmt"
	"os"
)

type graph struct {
	Edges [][2]string `json:"edges"`
}

func neighbors(adj map[string][]string, node string) []string {
	return adj[node]
}

func shortestPath(adj map[string][]string, start, goal string) []string {
	queue := [][]string{{start}}
	seen := map[string]bool{start: true}

	for len(queue) > 0 {
		path := queue[0]
		queue = queue[1:]
		last := path[len(path)-1]

		if last == goal {
			return path
		}

		for _, next := range neighbors(adj, last) {
			if !seen[next] {
				seen[next] = true
				nextPath := make([]string, len(path), len(path)+1)
				copy(nextPath, path)
				queue = append(queue, append(nextPath, next))
			}
		}
	}
	return nil
}

func main() {
	if len(os.Args) != 4 {
		fmt.Fprintf(os.Stderr, "usage: %s <graph.json> <start> <goal>\n", os.Args[0])
		os.Exit(2)
	}

	raw, err := os.ReadFile(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	var g graph
	if err := json.Unmarshal(raw, &g); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	adj := make(map[string][]string)
	for _, e := range g.Edges {
		adj[e[0]] = append(adj[e[0]], e[1])
	}

	path := shortestPath(adj, os.Args[2], os.Args[3])
	if path == nil {
		fmt.Println("no path found")
		os.Exit(1)
	}

	for i, node := range path {
		if i > 0 {
			fmt.Print(" -> ")
		}
		fmt.Print(node)
	}
	fmt.Println()
}

Build a toy graph and confirm the result matches a hand-drawn path:

cat > graph.json <<'EOF'
{
  "edges": [
    ["user:helpdesk", "group:Helpdesk"],
    ["group:Helpdesk", "user:sqlsvc"],
    ["user:sqlsvc", "group:Domain Admins"],
    ["user:helpdesk", "group:Domain Admins"],
    ["user:intern", "group:Helpdesk"]
  ]
}
EOF

go run bloodpath.go graph.json user:intern 'group:Domain Admins'

Then extend it to weight edges by risk (for example, ForceChangePassword is riskier than group membership) so that it can print the highest-risk path instead of the shortest one.
