ELF (Executable and Linkable Format)

The ELF binary format on Linux - headers, segments, sections, the program header table, section header table, and how the kernel loads an executable into memory.

Overview

ELF is the container format Linux uses for executables, shared libraries, relocatable objects, and core dumps. It is deliberately split into two views: sections for the linker and segments for the kernel loader. Every binary you disassemble, patch, or exploit on Linux is an ELF file, so reading its headers by hand is a prerequisite for reverse engineering and memory-corruption work. After reading this article you can parse an ELF header from a hex dump, map segments and sections to their purposes, and explain how execve() turns a file into a running process.

Required Reading

  • Filesystems - how files are stored, inodes, and the VFS layer that loads ELF from disk
  • Processes - process creation, fork/execve, and how the kernel transitions from disk image to running process

Why ELF Exists

Before ELF, Unix used a.out (assembler output) and COFF (Common Object File Format). a.out had no dynamic linking support and assumed a fixed memory layout. COFF had limited extensibility and no 64-bit support. ELF replaced both with a single, extensible format that serves three purposes simultaneously: executables, shared libraries, and relocatable object files.

ELF's design separates the linker's view (Sections) from the loader's view (Segments). The linker reads the Section Header Table to combine .o files into an executable. The kernel reads the Program Header Table to map the executable into memory. This dual-view architecture is the key insight of ELF.

Magic Bytes and File Identification

Every ELF file begins with 16 bytes of identification in the ELF header:

00000000  7f 45 4c 46 02 01 01 00  00 00 00 00 00 00 00 00  |.ELF............|

The 4 magic bytes ( \x7fELF ) identify the file. Byte 4 specifies the class (1 = 32-bit, 2 = 64-bit). Byte 5 specifies endianness (1 = little, 2 = big). Byte 6 is the ELF header version (always 1). Byte 7 is the OS/ABI identifier:

Value OS/ABI
0x00 UNIX System V
0x03 Linux
0x06 Solaris
0x09 FreeBSD

File with hd : 

$ hd -n 32 /bin/ls
00000000  7f 45 4c 46 02 01 01 00  00 00 00 00 00 00 00 00  |.ELF............|
00000010  03 00 3e 00 01 00 00 00  40 41 00 00 00 00 00 00  |..>.....@A......|

Confirm with readelf : 

$ readelf -h /bin/ls | head -14

ELF Header Structure (C Definition)

The ELF header is defined in /usr/include/elf.h : 

#define EI_NIDENT 16

typedef struct {
    unsigned char e_ident[EI_NIDENT];  // Magic + identification
    uint16_t      e_type;              // Object file type
    uint16_t      e_machine;           // Target architecture
    uint32_t      e_version;           // Object file version
    Elf64_Addr    e_entry;             // Entry point virtual address
    Elf64_Off     e_phoff;             // Program header table file offset
    Elf64_Off     e_shoff;             // Section header table file offset
    uint32_t      e_flags;             // Processor-specific flags
    uint16_t      e_ehsize;            // ELF header size in bytes (64)
    uint16_t      e_phentsize;         // Program header entry size
    uint16_t      e_phnum;             // Program header entry count
    uint16_t      e_shentsize;         // Section header entry size
    uint16_t      e_shnum;             // Section header entry count
    uint16_t      e_shstrndx;          // Section name string table index
} Elf64_Ehdr;

e_type - what kind of ELF file this is

Value Type Description
0x00 ET_NONE No file type
0x01 ET_REL Relocatable file (.o)
0x02 ET_EXEC Executable file
0x03 ET_DYN Shared object file (.so or PIE)
0x04 ET_CORE Core dump

Modern Linux executables are usually ET_DYN (PIE) rather than ET_EXEC , because Position-Independent Executables are compiled with -fPIE -pie by default. You can verify: 

$ readelf -h /bin/ls | grep Type
  Type:                              DYN (Position-Independent Executable file)
$ readelf -h /bin/bash | grep Type
  Type:                              EXEC (Executable file)

Program Header Table - The Loader's View

The Program Header Table is an array of Elf64_Phdr entries. Each entry describes a segment

  • a contiguous region in the file that the kernel maps into memory.

typedef struct {
    uint32_t p_type;     // Segment type
    uint32_t p_flags;    // Segment flags (PF_R=4, PF_W=2, PF_X=1)
    Elf64_Off p_offset;  // File offset of segment data
    Elf64_Addr p_vaddr;  // Virtual address to map segment
    Elf64_Addr p_paddr;  // Physical address (unused on Linux)
    uint64_t p_filesz;   // Size of segment in file
    uint64_t p_memsz;    // Size of segment in memory
    uint64_t p_align;    // Alignment (must be power of 2)
} Elf64_Phdr;

Segment types (p_type)

Value Type Purpose
0x00 PT_NULL Unused entry
0x01 PT_LOAD Loadable segment - kernel mmaps this
0x02 PT_DYNAMIC Dynamic linking information
0x03 PT_INTERP Path to dynamic linker (ld.so)
0x04 PT_NOTE Auxiliary information (ABI, build ID)
0x05 PT_SHLIB Reserved
0x06 PT_PHDR Location of program header table itself
0x6474e550 PT_GNU_EH_FRAME GCC exception handler table
0x6474e551 PT_GNU_STACK Stack executability flag (NX)
0x6474e552 PT_GNU_RELRO Read-only after relocation
0x6474e553 PT_GNU_PROPERTY CET/IBT properties

PT_LOAD is the only segment type the kernel cares about during execve() . Everything else (DYNAMIC, INTERP, NOTE) is metadata consumed by the dynamic linker after the process starts.

PT_GNU_STACK - if the PF_X bit is absent, the kernel marks the stack as non-executable (NX). This is the hardware-enforced W^X policy. Without PT_GNU_STACK , the kernel defaults to executable stack (for ABI compatibility). 

$ readelf -lW /bin/ls | grep -A1 GNU_STACK
  GNU_STACK      0x000000 0x0000000000000000 0x0000000000000000
                 0x000000 0x000000              RW     0x10

RW without E means no-execute stack. RWE means executable stack (deprecated, rarely seen).

PT_GNU_RELRO - segments containing the GOT and .dynamic section must be writable during relocation so the dynamic linker can fill in addresses. After relocation, PT_GNU_RELRO tells the loader to mprotect() those pages as read-only, preventing GOT overwrite attacks.

Section Header Table - The Linker's View

The linker uses Sections. The Section Header Table is an array of Elf64_Shdr entries: 

typedef struct {
    uint32_t    sh_name;       // Offset into .shstrtab for section name
    uint32_t    sh_type;       // Section type
    uint64_t    sh_flags;      // Section flags
    Elf64_Addr  sh_addr;       // Virtual address (0 for relocatable)
    Elf64_Off   sh_offset;     // Offset in file
    uint64_t    sh_size;       // Size in bytes
    uint32_t    sh_link;       // Link to another section (symbol table index)
    uint32_t    sh_info;       // Extra info (section-specific)
    uint64_t    sh_addralign;  // Alignment
    uint64_t    sh_entsize;    // Entry size for fixed-size entry tables
} Elf64_Shdr;

.data and .bss

.data holds initialized writable globals and static variables with non-zero initial values. .bss holds uninitialized data: it takes memory at runtime but no space in the file, and the loader allocates and zeroes it: 

$ readelf -S /bin/ls | grep -E '\.(data|bss)'
  [24] .data             PROGBITS         000000000001c600  0001b600
  [25] .bss              NOBITS           000000000001c620  0001b620

.data is PROGBITS (actual bytes in file), .bss is NOBITS (no file bytes, zero-filled at load).

.plt (Procedure Linkage Table) - trampoline code for lazy function resolution:

Static vs Dynamic ELF

A statically linked ELF contains all library code in the executable itself. No dynamic linker, no shared libraries, no PLT/GOT. Produced with gcc -static : 

$ gcc -static -o hello_static hello.c
$ readelf -d hello_static
There is no dynamic section in this file.
$ ldd hello_static
        not a dynamic executable
$ ls -lh hello_static
-rwxr-xr-x 1 user user 893K Jun 26 12:00 hello_static

The kernel loads the static ELF directly - it mmaps the PT_LOAD segments, sets up the stack, and jumps to e_entry. No intermediary. The dynamic case is more complex: 

$ gcc -o hello_dyn hello.c
$ readelf -d hello_dyn | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
$ ldd hello_dyn
        linux-vdso.so.1 (0x00007ffff7fc1000)
        libc.so.6 => /usr/lib/libc.so.6 (0x00007ffff7c00000)
        /lib64/ld-linux-x86-64.so.2 (0x00007ffff7fc3000)

The kernel loads the dynamic ELF, but then hands control to ld.so (specified in .interp ), which resolves all shared library dependencies before jumping to the executable's entry point.

How the Kernel Loads an ELF

The execve() syscall triggers the ELF loader in the kernel ( fs/binfmt_elf.c ). The loading sequence: 

1. execve(path, argv, envp)
2. Kernel reads first 128 bytes into a buffer (to identify the format)
3. Checks magic bytes: if "\x7fELF", calls load_elf_binary()
4. Reads full ELF header (Elf64_Ehdr)
5. Validates e_ident, e_type, e_machine against current arch
6. Reads Program Header Table (e_phoff, e_phnum entries)
7. For each PT_LOAD segment:
   a. Calculates memory region: [vaddr, vaddr + memsz)
   b. mmap() with appropriate prot (from p_flags)
   c. Reads p_filesz bytes from file offset into memory
   d. Zero-fills remaining (memsz - filesz) bytes for .bss
8. If PT_INTERP exists, loads the interpreter ELF and hands control to it
9. Otherwise (static ELF), sets up stack, sets RIP = e_entry
10. Sets up the auxiliary vector (AT_ENTRY, AT_PHDR, AT_PHENT, ...)
11. Returns to userspace at entry point

The auxiliary vector is an array of key-value pairs pushed onto the stack before argv and envp . It communicates system parameters to the dynamic linker and the process:

Key Value Meaning
AT_PHDR address Program headers location
AT_PHENT size Program header entry size
AT_PHNUM count Number of program headers
AT_PAGESZ size System page size
AT_BASE address Interpreter base address
AT_ENTRY address Program entry point
AT_UID uid Real UID
AT_EUID euid Effective UID
AT_GID gid Real GID
AT_EXECFN string Executable filename
AT_RANDOM address 16 random bytes
AT_SECURE bool Setuid/setgid programs

The stack layout after execve, from high addresses to low:

  [null-terminated envp strings]
  [null-terminated argv strings]
  [environment pointers]     <- envp[n] = NULL
  [argument pointers]        <- argv[0], argv[1], ..., NULL
  [argument count argc]
  [auxiliary vector]         <- {AT_NULL, AT_NULL}
  [... stack frames ...]     <- RSP on entry

Relocations - Fixing Address References

Relocations are entries that tell the linker or dynamic linker "the address at this offset needs to be patched with the address of symbol X". Two formats:

Elf64_Rel - explicit addend stored at the target location: 

typedef struct {
    Elf64_Addr r_offset;   // Virtual address to patch
    uint64_t   r_info;     // Symbol index + relocation type
} Elf64_Rel;

Elf64_Rela - addend stored in the relocation entry itself: 

typedef struct {
    Elf64_Addr r_offset;   // Virtual address to patch
    uint64_t   r_info;     // Symbol index + relocation type
    int64_t    r_addend;   // Addend to add to symbol value
} Elf64_Rela;

x86-64 uses RELA. Common relocation types on x86-64:

Type Value Meaning
R_X86_64_NONE 0 No relocation
R_X86_64_64 1 S + A (direct 64-bit)
R_X86_64_PC32 2 S + A - P (32-bit PC-relative)
R_X86_64_GLOB_DAT 6 Absolute address in GOT
R_X86_64_JUMP_SLOT 7 PLT GOT entry
R_X86_64_RELATIVE 8 B + A (relative to image base)
R_X86_64_COPY 5 Copy data from shared object
R_X86_64_IRELATIVE 37 Indirect function (ifunc)

From Source to Executable

The full compilation pipeline:

hello.c ─[gcc -E]─-> hello.i ─[gcc -S]─-> hello.s ─[gcc -c]─-> hello.o ─[ld]─-> hello
 (source)          (preprocessed)      (assembly)      (relocatable)    (executable)

Examine each stage:

// hello.c
#include <stdio.h>
int main(int argc, char **argv) {
    printf("Hello, ELF\n");
    return 0;
}
						
# Preprocess (expand macros, include headers)
$ gcc -E hello.c -o hello.i
$ wc -l hello.i
847 hello.i

# Compile to assembly
$ gcc -S hello.i -o hello.s

# Assemble to object file
$ gcc -c hello.s -o hello.o
$ file hello.o
hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped

# Link to executable
$ gcc hello.o -o hello
$ file hello
hello: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked,
interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=..., for GNU/Linux 4.4.0, stripped

The assembler creates .o files - ET_REL ELF files with sections but no program headers (no segments, since they aren't loadable yet). The linker reads all .o files, resolves cross-references, lays out sections into segments, and writes the final executable.

Minimal ELF Parser in Python

A parser that reads the ELF header and prints the entry point and segment map:

#!/usr/bin/env python3
"""Minimal ELF parser - reads ELF header, prints entry point and segment map."""
import struct
import sys

ELF_MAGIC = b'\x7fELF'

ELFTYPE = {0: 'NONE', 1: 'REL', 2: 'EXEC', 3: 'DYN', 4: 'CORE'}
ELFMACHINE = {2: 'SPARC', 3: 'x86', 0x28: 'ARM', 0x3E: 'x86-64', 0xB7: 'AArch64', 0xF3: 'RISC-V'}
PT_TYPE = {0: 'NULL', 1: 'LOAD', 2: 'DYNAMIC', 3: 'INTERP', 4: 'NOTE',
           0x6474E550: 'GNU_EH_FRAME', 0x6474E551: 'GNU_STACK', 0x6474E552: 'GNU_RELRO'}

def parse_elf(path):
    with open(path, 'rb') as f:
        ident = f.read(16)
        if ident[:4] != ELF_MAGIC:
            print(f"Not an ELF file: {path}")
            return

        is_64bit = ident[4] == 2
        is_le = ident[5] == 1
        endian = '<' if is_le else '>'

        if is_64bit:
            ehdr_fmt = f'{endian}HHIQQQIHHHHHH'
            ehdr_size = 64
            phdr_fmt = f'{endian}IIQQQQQQ'
            phdr_size = 56
        else:
            ehdr_fmt = f'{endian}HHIIIIIHHHHHH'
            ehdr_size = 52
            phdr_fmt = f'{endian}IIIIIIII'
            phdr_size = 32

        e_type, e_machine, e_version, e_entry, e_phoff, e_shoff, \
        e_flags, e_ehsize, e_phentsize, e_phnum, e_shentsize, e_shnum, e_shstrndx = \
            struct.unpack(ehdr_fmt, f.read(ehdr_size - 16))

        print(f"ELF{'64' if is_64bit else '32'} {'LE' if is_le else 'BE'}")
        print(f"Type:      {ELFTYPE.get(e_type, hex(e_type))} ({e_type})")
        print(f"Machine:   {ELFMACHINE.get(e_machine, hex(e_machine))} ({hex(e_machine)})")
        print(f"Entry:     {hex(e_entry)}")
        print(f"PH offset: {hex(e_phoff)}, {e_phnum} entries")
        print(f"SH offset: {hex(e_shoff)}, {e_shnum} entries")
        print()

        print(f"{'Type':<16} {'Offset':<12} {'VirtAddr':<18} {'FileSz':<10} {'MemSz':<10} {'Flgs'}")
        print("-" * 80)

        f.seek(e_phoff)
        for i in range(e_phnum):
            phdr = struct.unpack(phdr_fmt, f.read(phdr_size))
            p_type, p_flags, p_offset, p_vaddr, p_paddr, p_filesz, p_memsz, p_align = phdr
            type_name = PT_TYPE.get(p_type, f"0x{p_type:08x}")
            flags = ''
            if p_flags & 4: flags += 'R'
            if p_flags & 2: flags += 'W'
            if p_flags & 1: flags += 'E'
            print(f"{type_name:<16} {hex(p_offset):<12} {hex(p_vaddr):<18} "
                  f"{hex(p_filesz):<10} {hex(p_memsz):<10} {flags}")

if __name__ == '__main__':
    if len(sys.argv) < 2:
        print(f"Usage: {sys.argv[0]} <elf-file>")
        sys.exit(1)
    parse_elf(sys.argv[1])

Stripping Debug Information

strip removes .symtab , .strtab , and debug sections. It preserves .dynsym and .dynstr because those are needed for dynamic linking: 

$ strip ./hello
$ file ./hello
hello: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked,
interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=..., for GNU/Linux 4.4.0, stripped

After stripping, readelf -s shows only dynamic symbols: 

$ readelf -s ./hello

Symbol table '.dynsym' contains 9 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     0: 0000000000000000     0 NOTYPE  LOCAL  DEFAULT  UND
     1: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND printf@GLIBC_2.2.5
     2: 0000000000000000     0 NOTYPE  WEAK   DEFAULT  UND __gmon_start__

The .symtab section (containing local function names, file-level statics, and non-exported symbols) is gone. The .dynsym section (imports like printf ) remains.

Check ELF Integrity

A quick script to verify an ELF file is well-formed:

#!/bin/bash
# elfcheck - validate ELF structure
ELF="$1"
[ -z "$ELF" ] && { echo "Usage: $0 <elf>"; exit 1; }

echo "=== File Identity ==="
file "$ELF"

echo
echo "=== Entry Point ==="
readelf -h "$ELF" | grep Entry

echo
echo "=== Program Headers (LOAD segments) ==="
readelf -l "$ELF" | grep -A1 'LOAD\|INTERP\|GNU_STACK\|GNU_RELRO'

echo
echo "=== Dynamic Dependencies ==="
ldd "$ELF" 2>/dev/null || echo "(static)"

echo
echo "=== Hardened? ==="
readelf -lW "$ELF" | grep -q 'STACK.*E ' && echo "WARN: Executable stack!" || echo "OK: Non-exec stack"
readelf -d "$ELF" 2>/dev/null | grep -q '(BIND_NOW)' && echo "OK: Full RELRO (BIND_NOW)" || echo "NOTE: Partial RELRO"
readelf -d "$ELF" 2>/dev/null | grep -q '(FLAGS_1).*PIE' && echo "OK: PIE" || echo "NOTE: Not PIE"

Challenge

The Python parser above is convenient, but Go ships an ELF parser in the standard library. Write a Go tool that reads the first 64 header bytes with encoding/binary , prints the class, OS/ABI, type, machine, and entry point, then opens the same file with debug/elf and dumps every program header. Add a hardening summary: PIE ( ET_DYN ), non-executable stack ( PT_GNU_STACK without PF_X ), and Full RELRO ( PT_GNU_RELRO plus DF_BIND_NOW ). 

package main

import (
	"debug/elf"
	"encoding/binary"
	"fmt"
	"os"
)

func main() {
	data, err := os.ReadFile(os.Args[1])
	if err != nil {
		panic(err)
	}
	if string(data[:4]) != "\x7fELF" {
		panic("not an ELF file")
	}
	fmt.Printf("magic=%x class=%d osabi=%d e_type=%d machine=%d entry=%#x\n",
		data[:4], data[4], data[7],
		binary.LittleEndian.Uint16(data[16:18]),
		binary.LittleEndian.Uint16(data[18:20]),
		binary.LittleEndian.Uint64(data[24:32]))

	f, err := elf.Open(os.Args[1])
	if err != nil {
		panic(err)
	}
	defer f.Close()

	for _, p := range f.Progs {
		fmt.Printf("%-12v off=%#08x vaddr=%#08x filesz=%#06x memsz=%#06x flags=%v\n",
			p.Type, p.Off, p.Vaddr, p.Filesz, p.Memsz, p.Flags)
	}
}
