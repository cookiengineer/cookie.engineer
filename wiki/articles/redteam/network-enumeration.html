Network Enumeration

Host discovery, network sweeping, port scanning, and network topology mapping with nmap, masscan, and ARP -level techniques.

Overview

Network enumeration answers which machines exist on a target network, which services they expose, and how the network is segmented. It is the first active phase of an engagement and the phase that generates the most detectable traffic. This article covers host discovery at Layers 2 and 3, port scanning, scan timing and evasion, and how to read nmap and traceroute output as a map of the defenses in front of you.

The Network Enumeration Model

Network enumeration answers one question: what machines exist on this network, and where are they? Before you can attack a service, you need to know there is a machine running it. Before you can pivot, you need to know the topology. Before you can evade defenses, you need to know where the firewalls are.

Enumeration proceeds in layers:

Layer 1: Host Discovery    -> Which IPs are alive?
Layer 2: Port Scanning      -> Which ports are open on those hosts?
Layer 3: Service Detection  -> What software is listening on those ports?
Layer 4: OS Fingerprinting  -> What operating system is the host running?

This article covers Layers 1 and 2. Service detection and OS fingerprinting are separate articles.

CIDR Notation and Subnet Calculation

Every target scope is defined in CIDR notation. If you cannot mentally convert between CIDR and IP ranges, you will make mistakes in your scan boundaries. 

# CIDR -> range
ipcalc 10.10.0.0/24
# Network:   10.10.0.0/24
# Netmask:   255.255.255.0 = 24
# HostMin:   10.10.0.1
# HostMax:   10.10.0.254
# Hosts/Net: 254

ipcalc 10.10.0.0/16
# HostMin:   10.10.0.1
# HostMax:   10.10.255.254
# Hosts/Net: 65534

# Quick reference for common subnet sizes
# /24 = 256 IPs (254 hosts)   - typical office VLAN
# /23 = 512 IPs               - larger office
# /22 = 1024 IPs              - building
# /21 = 2048 IPs              - campus
# /20 = 4096 IPs              - large campus
# /16 = 65536 IPs             - enterprise / regional block
# /8  = 16,777,216 IPs        - class A owner (Cloudflare, AWS, DoD)

# Convert IP range to CIDR
ipcalc 10.10.0.5 - 10.10.0.50
# -> 10.10.0.5/32, 10.10.0.6/31, 10.10.0.8/29, 10.10.0.16/28, 10.10.0.32/28, 10.10.0.48/31, 10.10.0.50/32

Host Discovery - Layer 1

Host discovery determines which IP addresses in a target range have a live system. It is the first active phase of any engagement and the first point where you generate detectable traffic.

ARP Scanning

On a local Ethernet segment, ARP resolution precedes any IP communication. ARP scans are fast, reliable, and invisible to most firewall rules because ARP never crosses a router. If you have a foothold on one machine inside the target network, ARP is the preferred discovery method. 

# nmap ARP scan - only works on same subnet
nmap -sn -PR 10.10.0.0/24

# Manual ARP scan with arping
sudo arping -c 1 10.10.0.5
# ARPING 10.10.0.5 from 10.10.0.100 eth0
# Unicast reply from 10.10.0.5 [AA:BB:CC:DD:EE:FF] 0.450ms

# Sweep an entire /24 with arping
for ip in $(seq 1 254); do
  sudo arping -c 1 -w 1 "10.10.0.$ip" 2>/dev/null | \
    grep 'Unicast reply' | awk '{print $4, $5}'
done

# arp-scan - dedicated ARP scanner
sudo pacman -S arp-scan
sudo arp-scan --localnet
sudo arp-scan 10.10.0.0/24 --interface eth0

# arp-scan OUI (vendor) identification
sudo arp-scan --localnet --ouifile=/usr/share/arp-scan/ieee-oui.txt
# 10.10.0.1    aa:bb:cc:dd:ee:ff    Cisco Systems, Inc
# 10.10.0.5    11:22:33:44:55:66    Dell Inc
# 10.10.0.10   77:88:99:aa:bb:cc    VMware, Inc.

ICMP Ping Sweep - Layer 3 Discovery

ICMP Echo Request (Type 8) is the classic "ping." Many modern networks block ICMP Echo at the perimeter but allow it internally. 

# nmap ICMP Echo sweep
nmap -sn -PE 10.10.0.0/24
# -sn: no port scan (host discovery only)
# -PE: ICMP Echo Request (Type 8)

# Manual ping sweep with fping
sudo pacman -S fping
fping -g 10.10.0.0/24 -a 2>/dev/null  # -a: show only alive
fping -g 10.10.0.0/24 -a -r 1 2>/dev/null  # -r 1: single retry

# Parallel ping sweep with bash /dev/tcp (no external tools)
# WARNING: this is slow for large ranges. Use nmap or fping.
ping_range() {
  for ip in $(seq 1 254); do
    (ping -c 1 -W 1 "10.10.0.$ip" > /dev/null 2>&1 && echo "10.10.0.$ip ALIVE") &
  done
  wait
}
ping_range

Non-ECHO ICMP Discovery

When ICMP Echo is blocked, other ICMP types often pass through: 

# nmap ICMP Timestamp Request (Type 13)
nmap -sn -PP 10.10.0.0/24
# -PP: ICMP Timestamp Request. Many firewalls block Echo but pass Timestamp.

# nmap ICMP Netmask Request (Type 17)
nmap -sn -PM 10.10.0.0/24
# -PM: ICMP Address Mask Request. Rarely filtered, rarely responded to.
# Useful against misconfigured routers that leak netmask info.

# Manual ICMP Timestamp
hping3 -1 --icmptype 13 10.10.0.5 -c 1
# ICMP Timestamp reply -> server responds with its local time
# Useful for: verifying host is alive when ICMP Echo is filtered
# But: reveals your system's time to the target. Reduce leakage by setting bogus timestamp.

# Manual ICMP Address Mask
hping3 -1 --icmptype 17 10.10.0.5 -c 1
# If reply includes subnet mask -> host is likely a network device (router/switch)

TCP SYN Ping - When ICMP Is Blocked

Sending a TCP SYN to a common port is often more effective than ICMP . Even if the port is closed, a RST response confirms the host exists. 

# nmap TCP SYN ping to port 443 (HTTPS) - most permissive port
nmap -sn -PS443 10.10.0.0/24

# Common "permissive" ports:
# 22 (SSH), 25 (SMTP), 80 (HTTP), 443 (HTTPS), 445 (SMB), 3389 (RDP), 8080 (HTTP-alt)
nmap -sn -PS22,80,443,445,8080,8443 10.10.0.0/24

# TCP ACK ping - requires root, sends ACK to port 80
# Most firewalls pass ACK flags (stateful filtering requires seeing the SYN first)
nmap -sn -PA80 10.10.0.0/24
# -PA: TCP ACK ping. Host responds with RST if port is unfiltered.

# Manual TCP SYN ping with hping3
hping3 -S -p 443 10.10.0.5 -c 1
# SYN flag set -> receives SA (SYN-ACK) if port open, RA (RST-ACK) if closed
# Even an RA response tells you the host is alive.

# Manual TCP ACK ping
hping3 -A -p 80 10.10.0.5 -c 1
# ACK to port 80 -> firewall passes (no SYN seen), host responds RST -> host is alive

UDP Ping

UDP is stateless. An open UDP port responds with data (or stays silent). A closed UDP port triggers an ICMP Port Unreachable (Type 3, Code 3). Firewalls often block the ICMP response, making UDP scanning unreliable. 

# nmap UDP ping
nmap -sn -PU53,123,161 10.10.0.0/24
# -PU: UDP ping to ports 53 (DNS), 123 (NTP), 161 (SNMP)

# Manual UDP ping
# Send empty UDP packet. ICMP Port Unreachable = response = host alive.
echo -n '' | nc -u -w 1 10.10.0.5 53
# No output from nc, but check with tcpdump:
sudo tcpdump -i eth0 -nn 'icmp[icmptype] == 3' and host 10.10.0.5

Combining Discovery Methods

nmap's default -sn uses multiple probes simultaneously: ICMP Echo, TCP SYN to port 443, TCP ACK to port 80, and ICMP Timestamp. This maximizes discovery across varied firewall configurations. 

# Maximal host discovery - all probes, all port combos
nmap -sn -PE -PP -PM -PS22,80,443,445,3389,8080 -PA80,443 -PU53,123,161,162 \
  --max-retries 1 --host-timeout 5s 10.10.0.0/24

# Interpret the output: nmap marks hosts as:
# "Host is up" - any probe received a response
# "Host is up (0.0010s latency)" - ICMP Echo responded
# Silent - no response to any probe (but host may still be alive behind a firewall)

# The absence of a response does NOT mean the host is down.
# It means your probes did not reach it OR its responses did not reach you.
# This is the fundamental scanning uncertainty principle.

IPv6 Neighbor Discovery

IPv6 uses Neighbor Discovery Protocol ( NDP ) instead of ARP . NDP operates via ICMP v6 (Type 133-137). On an IPv6 -enabled local segment, you can discover hosts without traditional scanning. 

# nmap IPv6 host discovery
nmap -6 -sn fe80::/64%eth0

# Manual IPv6 neighbor discovery with ping6
ping6 -c 1 -I eth0 ff02::1  # all-nodes multicast address
# Every IPv6 node responds to this

# List neighbors from the kernel's neighbor cache
ip -6 neigh show
# fe80::aabb:ccff:fedd:eeff dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE

# Multicast Listener Discovery (MLD) - like IGMP for IPv6
# Discover routers
ping6 -c 1 -I eth0 ff02::2  # all-routers multicast
						
# IPv6 network discovery is trivially fast because addresses follow patterns
# SLAAC (Stateless Address Autoconfiguration) uses MAC-derived interface IDs
# If you know one MAC address on a segment, you can predict IPv6 addresses

# Given MAC aa:bb:cc:dd:ee:ff
# SLAAC EUI-64 address: fe80::a8bb:ccff:fedd:eeff (insert ff:fe in middle, flip bit 7)
# This is deterministic and often guessable

Port Scanning

Once you know which hosts are alive, port scanning tells you which services are reachable. The TCP three-way handshake ( SYN -> SYN -ACK -> ACK) is the mechanism you are probing.

Open, Closed, and Filtered Ports

This distinction is the single most important concept in network enumeration. Misinterpreting these states leads to bad attack plans.

State TCP SYN Response Meaning
open SYN-ACK Service is listening and reachable. Attack surface.
closed RST-ACK Port is reachable but nothing is listening. Host exists.
filtered No response (or ICMP unreachable) Firewall/ACL dropped the packet silently. Host may or may not exist.
open|filtered No response UDP or uncommon scan: port might be open (no response is the response) or filtered (drop).
unfiltered RST-ACK (after ACK scan) Port is reachable but nmap cannot determine if open/closed. Rare.

The key insight: closed means reachable. filtered means blocked. open means exploitable. 

# Demonstrate: scan a filtered port vs a closed port
# On target machine with iptables:
#   iptables -A INPUT -p tcp --dport 12345 -j DROP    # filtered
#   # port 12346 has nothing listening                   # closed

# nmap scan
nmap -sS -p 12345,12346 10.10.0.5
# 12345/tcp filtered  unknown    <- SYN sent, no response (iptables DROP)
# 12346/tcp closed    unknown    <- SYN sent, RST-ACK received (kernel replied)

TCP SYN Scan (-sS) - The Workhorse

SYN scan (half-open scan) sends a SYN , receives a SYN -ACK (open) or RST (closed), then sends RST to tear down. The three-way handshake never completes, so the connection is not logged by most applications. 

# Default SYN scan (top 1000 ports)
nmap -sS 10.10.0.5

# Specific port range
nmap -sS -p 1-65535 10.10.0.5     # all 65535 ports
nmap -sS -p 22,80,443,8080 10.10.0.5  # specific ports
nmap -sS -p- 10.10.0.5            # shorthand for all ports
nmap -sS --top-ports 100 10.10.0.5  # top 100 most common

# Service/well-known port reference
nmap -sS -p U:53,67,68,123,161,500,T:21,22,23,25,53,80,110,111,135,139,143,443,445,993,995,1433,1521,3306,3389,5432,5900,6379,8080,8443,9090,27017 10.10.0.5

TCP Connect Scan

Connect scan completes the full three-way handshake. Use when: you lack raw socket access (no root), scanning through a proxy, or when SYN scan produces unreliable results. 

# Connect scan
nmap -sT -p 22,80,443 10.10.0.5

# Connect scan is logged by applications (Apache access log, SSH auth log)
# An Apache log entry looks like:
# 10.0.0.100 - - [26/Jun/2026:10:15:32] "-" 408 0 "-" "-"
# That 408 (Request Timeout) shows someone connected and then disconnected.
# SYN scan avoids this because no TCP connection is established.

Timing Templates

Timing controls the aggressiveness of the scan. Slower scans are stealthier and more reliable against rate-limited networks. Faster scans complete quicker but trigger IDS / IPS alerts.

Template Flag Scan Delay Parallelism Packet Rate Use Case
Paranoid -T0 5 minutes Serial, single port ~1 pkt/sec IDS evasion, extreme stealth
Sneaky -T1 15 seconds Serial, single port ~10 pkt/sec IDS evasion
Polite -T2 0.4 seconds Serial, serial probes ~100 pkt/sec Slow WAN links, fragile targets
Normal -T3 None Default Default Default
Aggressive -T4 None Parallel, 10ms timeout ~1000 pkt/sec Fast LAN, assumption of low loss
Insane -T5 None Parallel, 5ms timeout ~5000 pkt/sec Local network only, likely packet loss 
# Paranoid scan - scans one port at a time, 5-minute intervals between probes
# This takes approximately 24 hours per port. Use only for specific high-value ports.
nmap -sS -T0 -p 22,80,443 10.10.0.5

# Insane scan of a local /24 - expect 50%+ packet loss
nmap -sS -T5 10.10.0.0/24

# The practical tradeoff: T4 for local networks, T3 for remote
nmap -sS -T4 -p 1-10000 10.10.0.0/24
nmap -sS -T3 -p 80,443,8080 target.com

Decoys and Source Spoofing

Decoys obscure your real IP by mixing it with fake source addresses. The target sees N incoming probes from N different IP s, making attribution harder. 

# 5 decoys + 1 real (your IP). Position 3 means your IP is third in the list.
nmap -sS -D RND:5,ME -p 22,80,443 10.10.0.5
# RND:5 = 5 random decoy IPs, mixed with your real address
# ME = your actual IP, placed at a random position among the decoys

# Specify exact decoy IPs
nmap -sS -D 10.10.0.50,10.10.0.100,10.10.0.150,ME -p 22,80 10.10.0.5

# WARNING: Decoys double your traffic. 6 IPs x 1000 ports = 6000 packets sent.
# WARNING: Decoys from routable IPs you don't own is unethical in production.
# WARNING: Spoofed source IPs cannot receive responses, so nmap only sees YOUR responses.
#          If YOUR traffic is filtered, decoys won't help visibility.

# Source port spoofing - use a common permitted source port
nmap -sS --source-port 53 -p 22 10.10.0.5
# Some firewalls have rules like "allow from any port 53" (DNS response)
# Or more commonly: "allow from any:53 to any:53" (DNS)
nmap -sS --source-port 80 -p 1-1000 10.10.0.5

Fragmenting Packets and MTU Manipulation

Fragmenting SYN packets can bypass firewalls that inspect only the first fragment or that fail to reassemble fragments before filtering. 

# Fragment IP packets into 8-byte chunks
nmap -sS -f -p 80 10.10.0.5

# Double fragmentation (16-byte offset -> even smaller fragments)
nmap -sS -ff -p 80 10.10.0.5

# Set specific MTU (fragment at N bytes)
nmap -sS --mtu 16 -p 80 10.10.0.5
# MTU must be multiple of 8. Minimum: 8.

# Fragment evasion works against:
#   - Stateless firewall ACLs that inspect only the first fragment
#   - Legacy IDS that don't reassemble fragments
# Does not work against:
#   - Modern firewalls that reassemble and inspect
#   - Any SPI (Stateful Packet Inspection) firewall

UDP Scanning - The Enemy of Patience

UDP is connectionless. A closed UDP port responds with ICMP Port Unreachable (Type 3, Code 3). An open UDP port... stays silent. Or sometimes responds. The ambiguity makes UDP scanning slow and unreliable. 

# nmap UDP scan
nmap -sU -p 53,123,161,500,1900,5353 10.10.0.5

# Why UDP scanning takes forever:
# 1. No response -> retransmit. Is it open or filtered? Unknown.
# 2. ICMP rate limiting: many OSes limit ICMP unreachable to 1/sec
#    Linux: /proc/sys/net/ipv4/icmp_ratelimit (default 1000ms)
#    This means you can get at most 1 closed-port confirmation per second.
# 3. Firewalls often discard ICMP unreachable -> port appears "open|filtered"

# Speed up UDP scan: limit to common ports + aggressive timing
nmap -sU -p 53,67,68,69,123,135,137,138,139,161,162,445,500,514,520,631,1434,1900,5353 \
  --max-retries 1 --min-rate 100 10.10.0.5

# Manual UDP probe for DNS (port 53)
dig @10.10.0.5 google.com A +short
# If you get a response, port 53 is open and the server is a DNS resolver.

# Manual UDP probe for NTP (port 123)
ntpdate -q 10.10.0.5 2>/dev/null
# If you get stratum/offset data, port 123 is open.

# Manual UDP probe for SNMP (port 161)
snmpget -v1 -c public 10.10.0.5 1.3.6.1.2.1.1.5.0
# If you get a response, SNMP is open with community string "public".

Service Scan Integration

Service version detection (-sV) is the natural follow-up to port discovery. After finding open ports, you need to know what's running. 

# Find open ports first, then fingerprint services
nmap -sS -p- --min-rate 1000 10.10.0.5 -oA quick-sweep
# Parse open ports from XML output
grep 'portid=".*" state="open"' quick-sweep.xml | \
  grep -oP 'portid="\K[^"]+' | \
  tr '\n' ',' | sed 's/,$//' > open-ports.txt
# Then target only those ports for service detection
nmap -sV -p $(cat open-ports.txt) 10.10.0.5 -oA service-scan

Masscan - Internet-Scale Sweeping

nmap is for precision. Masscan is for speed. It can scan the entire IPv4 internet in under 6 minutes on a 10 Gbps link. Use it for large internal ranges where you need speed over stealth. 

# Scan entire /16 in ~30 seconds
masscan -p22,80,443,445,3389,8080,8443 10.10.0.0/16 --rate=10000 -oJ masscan-results.json

# Key parameters:
# --rate: packets per second (default 100, theoretical max ~10M at 10Gbps)
# --retries: number of retransmits (0 = send once, no retry)
# --wait: seconds to wait for responses after scan completes
# -oJ/-oL/-oG: JSON, list, or grepable output

# Extract open ports from JSON
jq -r '.[] | "\(.ip):\(.ports[].port)"' masscan-results.json | sort -u

# Pipe masscan results directly into nmap for service detection
masscan -p1-65535 10.10.0.0/24 --rate=5000 -oL - 2>/dev/null | \
  grep 'open' | awk '{print $4":"$3}' | \
  sed 's/\/tcp//' | sort -u > masscan-open.txt
# Feed to nmap
while IFS=: read ip port; do
  nmap -sV -p "$port" --script=banner "$ip"
done < masscan-open.txt

Interpreting nmap Output

Raw scan output tells you more about the target network than most tools reveal. Every response pattern is a fingerprint. 

# Host is up, port 80 open:
# Nmap scan report for 10.10.0.5
# PORT   STATE SERVICE
# 80/tcp open  http
# -> Web server, reachable, no filtering. Direct attack surface.

# Host is up, port 22 filtered:
# PORT   STATE    SERVICE
# 22/tcp filtered ssh
# -> SSH is firewalled from your position. Could be open internally.
# -> Try from a different source (pivot through another host on the same segment).

# Host is up, port 445 open|filtered:
# PORT    STATE         SERVICE
# 445/tcp open|filtered microsoft-ds
# -> No SYN-ACK, no RST. Either firewall drops (filtered) or host responds (open).
# -> Retry with different scan type: -sT (connect) instead of -sS (SYN).

# Different states for different ports on same host:
# PORT    STATE    SERVICE
# 80/tcp  open     http
# 443/tcp open     https
# 22/tcp  filtered ssh
# -> Host allows web traffic but blocks SSH. Firewall is application-aware or port-based.

# RST rate limiting pattern:
# If closed ports respond RST but with increasing delays, the OS is rate-limiting.
# This indicates either Linux (icmp_ratelimit) or a firewall/IDS doing response throttling.

Building a Network Diagram

Enumeration data is raw. A network diagram makes it actionable. Convert scan results into a topology map. 

# Quick ASCII network map from nmap XML
# Using nmap-to-table - basic approach
nmap -sn 10.10.0.0/24 -oX sweep.xml
# Extract hosts, classify by response type
xmlstarlet sel -t -m '//host' \
  -v 'address[@addrtype="ipv4"]/@addr' -o '|' \
  -v 'status/@state' -o '|' \
  -v 'address[@addrtype="mac"]/@addr' -o '|' \
  -v 'address[@addrtype="mac"]/@vendor' -n sweep.xml

# Build a ping matrix - which hosts can reach which hosts?
# Run from multiple positions in the network (if you have multiple footholds)
# This reveals network segmentation and routing boundaries.
						
           [Internet]
                |
          [Gateway .1]
          (10.10.0.1)
                |
      +---------+---------+
      |                   |
  [Switch]            [Switch]
      |                   |
  [Web .5]          [DB .10]
  (nginx)           (MySQL)
  80/tcp             3306/tcp
  443/tcp
      |
  [Dev .15]
  (Tomcat)
  8080/tcp
						
# Automated network mapper - visualize with graphviz
# Dump hosts and open ports, create dot file
nmap -sS -p 22,80,443,3306,5432,6379,8080 10.10.0.0/24 -oG - | grep 'open' | \
  awk '{
    ip=$2; gsub(/[()]/, "", ip)
    for (i=4; i<=NF; i++) {
      if ($i ~ /open/) {
        port=$i; gsub(/\/.*/, "", port)
        print "\""ip"\" -> \"port_"port"\""
      }
    }
  }' | sort -u

Traceroute Analysis

Traceroute maps the path packets take from you to the target. Each hop is a router. The hop sequence reveals network segmentation, ISP peering, and firewall placement. 

# Standard traceroute (UDP by default on Linux)
traceroute 10.10.0.5

# ICMP traceroute (avoids UDP filtering)
traceroute -I 10.10.0.5

# TCP traceroute - specify a port you know is open
traceroute -T -p 443 10.10.0.5
# This often pierces firewalls that block UDP/ICMP

# nmap traceroute integration
nmap -sS -p 80,443 --traceroute 10.10.0.5
# Shows the route for each port scanned
# Different routes to different ports = policy-based routing

# Analyze traceroute for:
# 1. Gap in hops (e.g., hop 5 -> hop 8) = firewall/proxy that doesn't decrement TTL
# 2. Hostname patterns: *.internal.example.com vs *.aws.com -> cloud boundary
# 3. Repeated IPs at different hops -> NAT or load balancer
# 4. * * * (no response) = hop filtering ICMP TTL exceeded -> firewall in path
						
# Firewall detection via traceroute
# If traceroute to port 80 succeeds but port 22 fails -> firewall blocks SSH
traceroute -T -p 80 10.10.0.5   # succeeds, full path
traceroute -T -p 22 10.10.0.5   # dies at hop 6 -> firewall at hop 6 blocks port 22

# If traceroute uses ICMP and dies but TCP works:
traceroute -I 10.10.0.5         # dies at hop 3 (* * *)
traceroute -T -p 443 10.10.0.5  # full path
# -> ICMP filtered, TCP allowed. Standard corporate egress filtering.

# Identify NAT boundaries:
# Compare internal RFC1918 hops to public IP hops
# A hop from 10.x.x.x to 203.x.x.x = NAT boundary = network perimeter

Operational Security

# 1. NEVER scan from your home IP
# Always route scans through a VPN or jump box:
ip route show  # verify default route goes through VPN interface

# 2. NEVER scan more than your scope
# Verify target CIDR against engagement scope before every scan:
echo "10.10.0.0/24" | grep -qE '^[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+/[0-9]+$' && \
  echo "Valid CIDR" || echo "INVALID - ABORT"

# 3. Understand what your scan looks like to a defender
# An nmap -sS -T4 scan from your IP generates:
#   - ~1000 SYN packets to sequential ports in ~5 seconds
#   - RST to tear down each detected open port
#   - ICMP Echo / Timestamp requests before the port scan
# This is the textbook nmap signature. Every IDS on the planet detects it.

# To be stealthier:
#   - Use -T2 or -T1
#   - Space scans across days
#   - Interleave with legitimate-looking traffic
#   - Use decoys or source from a compromised host

# 4. Notify your team when scanning
# A scan that triggers an IDS alert may cause the blue team to investigate.
# If you haven't told them, they'll think it's a real attack.
# Run: echo "[$(date)] Starting scan of $TARGET" >> scan-log.txt

# 5. Know the legal boundaries
# Scanning without authorization is illegal in most jurisdictions.
# Even "passive" DNS queries to an org's nameservers can constitute a CFAA violation
# if done without authorization. Always get written authorization.

Verification Commands

# Verify: your scan can reach the target
nmap -sn -PE 10.10.0.5 2>&1 | grep -q 'Host is up' && echo "OK: Host reachable" || echo "FAIL: Unreachable"

# Verify: scan rate is within expected bounds
# Run tcpdump while scanning to verify actual packet rate

Common Mistakes

  1. Scanning out of scope. nmap 10.10.0.0/8 when scope is 10.10.0.0/24 . Catastrophic.
  2. Assuming filtered == host down. The host is there. Your packets are blocked.
  3. Using -T5 on remote networks. 5000 pkt/sec will saturate your egress and lose responses.
  4. Not using -Pn when needed. -Pn skips host discovery. Use when hosts block pings but you know they exist.
  5. Scanning UDP without patience. UDP scanning is inherently slow. Use --host-timeout to prevent hangs.
  6. Forgetting that nmap resolves DNS by default. Add -n to skip DNS resolution and speed up scans.
