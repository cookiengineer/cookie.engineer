Race Conditions

A race condition is uncontrolled concurrent access to shared data, causing lost updates, TOCTOU bugs, and corrupted state.

Overview

Once two execution contexts share memory, the order in which their memory operations interleave becomes part of the program's behaviour. A missing lock rarely fails on every run, which makes these bugs expensive to debug and dangerous in production. This article starts from the lost-update pattern and builds up through mutexes, spinlocks, semaphores, atomic operations, and memory ordering, then applies the same reasoning to TOCTOU file operations and signal handlers.

Required Reading

  • Processes - process creation, fork, exec, inter-process resource sharing
  • Threads - pthreads, scheduling, shared address space, TCB layout

Definition

A race condition occurs when two or more execution contexts (threads, processes, interrupt handlers, signal handlers) access shared data concurrently and at least one access is a write, but the relative order of these accesses is not controlled. The program's output depends on interleaving

  • the specific sequence in which the hardware interleaves the memory operations of each context.

The defining property: non-determinism. Run the program 1000 times - get 100 correct results and 1 corruption. The corruption is not random noise; it follows a specific schedule that the developer did not anticipate.

The Read-Modify-Write Pattern

The canonical race: two threads increment a shared counter.

/* race_counter.c - lost increments */
#include <stdio.h>
#include <pthread.h>

#define ITERATIONS 100000

int counter = 0;  /* shared, no lock */

void *increment(void *arg) {
    for (int i = 0; i < ITERATIONS; i++) {
        counter++;   /* three operations: load, add, store */
    }
    return NULL;
}

int main() {
    pthread_t t1, t2;

    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, increment, NULL);

    pthread_join(t1, NULL);
    pthread_join(t2, NULL);

    printf("Expected: %d\n", 2 * ITERATIONS);
    printf("Actual:   %d\n", counter);
    printf("Lost:     %d\n", 2 * ITERATIONS - counter);

    return 0;
}
						
gcc -g -pthread -o race_counter race_counter.c
for i in {1..10}; do ./race_counter; echo "---"; done

# Expected: 200000
# Actual:   154237
# Lost:     45763
# ---
# Expected: 200000
# Actual:   137892
# Lost:     62108
# ---
# (different every run)

At the assembly level, counter++ decompiles to: 

; counter++ on x86-64 (non-atomic)
mov    eax, DWORD PTR [rip+0x2ea2]   ; load counter into eax
add    eax, 1                          ; increment register
mov    DWORD PTR [rip+0x2e9a], eax    ; store back to counter

The race window exists between load and store. If both threads load the same value before either stores, one increment is lost: 

Time ->
Thread A: load counter (value = 42)
Thread B:   load counter (value = 42)
Thread A: add 1 -> 43
Thread B:   add 1 -> 43
Thread A: store 43
Thread B:   store 43           <- counter should be 44, but is 43

Critical Sections and Mutual Exclusion

A critical section is a code region that accesses shared data and must not be interleaved with another thread's access to the same data. Mutual exclusion (mutex) serializes access: at most one thread can be inside the critical section at any time. 

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
int counter = 0;

void *increment_safe(void *arg) {
    for (int i = 0; i < ITERATIONS; i++) {
        pthread_mutex_lock(&lock);
        counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}
						
gcc -g -pthread -o race_fixed race_counter_fixed.c
./race_fixed

# Expected: 200000
# Actual:   200000
# Lost:     0

The cost: serialized counter increments. Each thread waits for the other at the mutex boundary. The throughput drops - but correctness is preserved.

Mutex Internals

pthread_mutex_t on Linux is backed by futex(2) - the fast userspace mutex syscall. The uncontended path is purely userspace: an atomic compare-and-swap tries to acquire the lock. If the lock is free, the CAS succeeds and the thread enters the critical section without a syscall.

If the lock is held, the thread calls futex(FUTEX_WAIT) which puts it to sleep. When the lock is released, the owner calls futex(FUTEX_WAKE) to wake one waiter. The kernel manages the wait queue. 

// Simplified userspace futex-based mutex (not the real glibc implementation)
typedef struct {
    int lock;   // 0 = free, 1 = taken, no waiters
} my_mutex_t;

void my_mutex_lock(my_mutex_t *m) {
    int c = 0;
    // Try to atomically swap 0 -> 1
    if (__atomic_compare_exchange_n(&m->lock, &c, 1, 0,
            __ATOMIC_ACQUIRE, __ATOMIC_RELAXED))
        return;  // acquired without syscall

    // Contended: try to set to 2 (taken + waiters), then sleep
    if (c != 2)
        c = __atomic_exchange_n(&m->lock, 2, __ATOMIC_ACQUIRE);

    while (c != 0) {
        syscall(SYS_futex, &m->lock, FUTEX_WAIT, 2, NULL, 0, 0);
        c = __atomic_exchange_n(&m->lock, 2, __ATOMIC_ACQUIRE);
    }
}

Spinlocks

A spinlock busy-waits (spins in a loop) instead of sleeping. Useful when the critical section is very short (a few instructions) and the overhead of a context switch outweighs the spin time. 

typedef volatile int spinlock_t;

static inline void spin_lock(spinlock_t *lock) {
    while (__atomic_test_and_set(lock, __ATOMIC_ACQUIRE))
        /* spin */;
}

static inline void spin_unlock(spinlock_t *lock) {
    __atomic_clear(lock, __ATOMIC_RELEASE);
}

On x86-64, __atomic_test_and_set compiles to a locked read-modify-write such as xchg or lock bts (Bit Test and Set with LOCK prefix). The PAUSE instruction is inserted in spin loops to reduce power consumption and improve SMT (hyper-threading) throughput: 

while (__atomic_test_and_set(lock, __ATOMIC_ACQUIRE))
    __builtin_ia32_pause();

Spinlocks in the Linux kernel use ticket locks or queued spinlocks to guarantee fairness - preventing starvation where one CPU repeatedly acquires the lock while others spin indefinitely.

Semaphores

A semaphore generalizes a mutex: instead of binary "locked/unlocked," it has a count. sem_wait() decrements the count (blocking if it reaches 0). sem_post() increments (waking a waiter). A semaphore initialized to 1 is functionally equivalent to a mutex. 

#include <semaphore.h>

sem_t sem;
sem_init(&sem, 0, 5);   // pshared=0 (threads only), initial count=5

// Producer-consumer bounded buffer with two semaphores:
sem_t empty_slots;   // count = buffer capacity
sem_t filled_slots;  // count = 0
pthread_mutex_t buf_lock;

void produce(int item) {
    sem_wait(&empty_slots);        // wait for an empty slot
    pthread_mutex_lock(&buf_lock);
    buffer[write_idx++] = item;
    pthread_mutex_unlock(&buf_lock);
    sem_post(&filled_slots);       // signal a new filled slot
}

int consume() {
    sem_wait(&filled_slots);       // wait for a filled slot
    pthread_mutex_lock(&buf_lock);
    int item = buffer[read_idx++];
    pthread_mutex_unlock(&buf_lock);
    sem_post(&empty_slots);        // signal a freed empty slot
    return item;
}

Atomic Operations

C11 introduced _Atomic and <stdatomic.h> . These guarantee that operations on the atomically-qualified variable are indivisible - no other thread can observe a partially-completed operation. 

#include <stdatomic.h>

atomic_int counter = 0;

void *increment_atomic(void *arg) {
    for (int i = 0; i < ITERATIONS; i++) {
        atomic_fetch_add(&counter, 1);
    }
    return NULL;
}

On x86-64, atomic_fetch_add compiles to lock xadd - a single atomic instruction. No load-add-store window exists. No mutex, no syscall, no spin - just hardware atomicity.

GCC builtins provide equivalent functionality without C11:

__atomic_add_fetch(&counter, 1, __ATOMIC_SEQ_CST);
__atomic_load_n(&flag, __ATOMIC_ACQUIRE);
__atomic_store_n(&flag, 1, __ATOMIC_RELEASE);
int expected = 0;
__atomic_compare_exchange_n(&flag, &expected, 1, 0,
    __ATOMIC_ACQUIRE, __ATOMIC_RELAXED);

Memory Ordering

Atomicity prevents torn reads/writes. Memory ordering prevents reordering - both by the compiler (instruction scheduling) and by the CPU (out-of-order execution, store buffers).

The C11 memory order constants:

Order Guarantee
memory_order_relaxed Atomicity only. No ordering guarantees. Compiler/CPU may reorder freely.
memory_order_acquire Load: prevent subsequent loads/stores from being reordered before this load.
memory_order_release Store: prevent prior loads/stores from being reordered after this store.
memory_order_acq_rel Combined acquire + release (for read-modify-write).
memory_order_seq_cst Sequentially consistent. Total global order of all seq_cst operations. Strongest, slowest.

On x86-64, the hardware provides relatively strong ordering (TSO - Total Store Order): loads are not reordered with other loads, stores are not reordered with other stores. The main reordering risk is store-load: a load can complete before a prior store becomes visible to other cores. mfence , lock -prefixed instructions, and xchg prevent this.

ARM64 and POWER have weaker memory models - more reordering is allowed. Acquire/release semantics are essential for portable code. 

/* Double-checked locking pattern - requires acquire/release */
atomic_int initialized = 0;
struct Config *global_config = NULL;

struct Config *get_config() {
    if (!atomic_load_explicit(&initialized, memory_order_acquire)) {
        pthread_mutex_lock(&init_lock);
        if (!atomic_load(&initialized)) {
            struct Config *cfg = parse_config_file();
            atomic_store_explicit(&global_config, cfg, memory_order_release);
            atomic_store_explicit(&initialized, 1, memory_order_release);
        }
        pthread_mutex_unlock(&init_lock);
    }
    return atomic_load(&global_config);
}

Without acquire/release, the compiler or CPU could reorder initialized = 1 before global_config = cfg - a thread sees initialized == 1 but reads a NULL global_config .

TOCTOU: The Classic Check-Then-Act

Time-of-Check to Time-of-Use (TOCTOU) is the most common race pattern across processes:

/* toctou_vuln.c */
if (access(path, W_OK) == 0) {   /* TIME OF CHECK: is file writable? */
    int fd = open(path, O_WRONLY);  /* TIME OF USE: open it */
    if (fd >= 0) {
        write(fd, data, len);
        close(fd);
    }
}

Between access() and open() , an attacker replaces the file at path with a symlink to /etc/passwd . access() checks the original file's permissions (which pass). open() follows the symlink and opens /etc/passwd with the victim's privileges.

The root cause: file path resolution is not atomic. The path "/tmp/userfile" is a name - it resolves to an inode at the moment of each syscall. Between two syscalls, the mapping from name to inode can change.

Signal Handler Races

Signal handlers execute asynchronously and can interrupt a thread at any instruction boundary (unless signals are masked). If a signal handler modifies a global variable that the main program also reads/modifies, a race exists: 

#include <signal.h>
#include <stdio.h>
#include <unistd.h>

volatile sig_atomic_t flag = 0;

void handler(int sig) {
    flag = 1;  /* async-signal-safe: atomic write on most platforms */
}

int main() {
    struct sigaction sa = { .sa_handler = handler };
    sigaction(SIGUSR1, &sa, NULL);

    while (1) {
        if (flag) {       /* non-atomic read-modify on non-_Atomic volatile */
            flag = 0;     /* the write here can race with handler's write */
            printf("got signal\n");
        }
        usleep(100);
    }
}

The rule: only volatile sig_atomic_t variables can be safely accessed from signal handlers. Anything larger (64-bit on 32-bit platforms, structs) can be torn. Anything more complex (linked list manipulation, printf , malloc ) is not async-signal-safe and can deadlock or corrupt heap state. 

// Safe pattern: sig_atomic_t flag + blocking main-loop check
volatile sig_atomic_t signal_received = 0;

void safe_handler(int sig) {
    signal_received = 1;  // atomic write (single instruction usually)
}

int main() {
    signal(SIGINT, safe_handler);
    while (1) {
        pause();  // or sigsuspend, or select with signal handling
        if (signal_received) {
            signal_received = 0;
            /* do non-trivial work OUTSIDE the signal handler */
        }
    }
}

fork() + Multithreading Dangers

fork() in a multi-threaded program creates a child process with a single thread (a copy of the calling thread). All other threads of the parent simply vanish in the child - while holding mutexes, in the middle of malloc , or in any inconsistent state. 

/* NEVER do this in a threaded program */
void dangerous_fork() {
    pthread_mutex_lock(&lock);   // thread A holds lock
    // ... thread B concurrently calls fork() ...
    // child process: has the mutex in locked state, but thread A doesn't exist
    // any attempt to lock the mutex in the child -> deadlock forever
}

The only safe pattern: fork() before any threads are created, or fork() + immediate exec() in the child (which replaces the process image, discarding stale mutex state). pthread_atfork() allows registering handlers that lock all mutexes before fork and unlock them after (in parent and child), but this is fragile and error-prone. 

void prepare_fork() { pthread_mutex_lock(&all_locks); }
void parent_after_fork() { pthread_mutex_unlock(&all_locks); }
void child_after_fork() { pthread_mutex_unlock(&all_locks); }

// Register once, at startup:
pthread_atfork(prepare_fork, parent_after_fork, child_after_fork);

Data Race Detection: TSan

gcc -g -fsanitize=thread -pthread -o race_tsan race_counter.c
./race_tsan

# WARNING: ThreadSanitizer: data race (pid 12345)
#   Write of size 4 at 0x... by thread T1:
#     #0 increment /path/race_counter.c:10
#
#   Previous write of size 4 at 0x... by thread T2:
#     #0 increment /path/race_counter.c:10
#
#   Location is global 'counter' of size 4 at ...

TSan instruments every memory access with a shadow cell. When two accesses conflict (at least one write, different threads, no happens-before relationship via synchronization), TSan reports the race. The overhead is 5x-15x in CPU and 5x-10x in memory - suitable for testing, not production.

Helgrind (Valgrind Tool)

gcc -g -pthread -o race_counter race_counter.c
valgrind --tool=helgrind ./race_counter

# Possible data race during read of size 4 at 0x... by thread #1
# Locks held: none
#   at 0x...: increment (race_counter.c:10)
#
# This conflicts with a previous write of size 4 by thread #2
# Locks held: none
#   at 0x...: increment (race_counter.c:10)

Helgrind also models the happens-before relationship by tracking every mutex lock/unlock and every thread creation/join. It is slower than TSan (20x-100x overhead) but reports richer diagnostics about lock ordering and deadlock potential.

GCC Warning Flags for Races

These flags catch implicit integer conversion bugs that often manifest as race-prone counters:

gcc -Wconversion -Wsign-compare -c race_counter.c
# warning: conversion to 'int' from 'long int' may alter its value

A 32-bit counter on a 64-bit platform, incremented by multiple threads, wraps earlier than expected. Combined with races, the wrap point becomes unpredictable.

Challenge

Write a Go program with two goroutines that each increment a shared int64 one million times. Run it with go run -race race.go and observe the WARNING: DATA RACE report. Then fix it twice - once with sync/atomic and once with a sync.Mutex - and confirm that both versions print 2000000 . 

package main

import (
	"fmt"
	"sync"
)

const iterations = 1000000

func main() {
	var counter int64
	var wg sync.WaitGroup

	for i := 0; i < 2; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < iterations; j++ {
				counter++
			}
		}()
	}

	wg.Wait()
	fmt.Printf("counter = %d (expected %d)\n", counter, 2*iterations)
}
						
go run -race race.go;

The atomic fix replaces counter++ with atomic.AddInt64(&counter, 1) and imports sync/atomic ; the mutex fix guards the increment with lock.Lock() and lock.Unlock() .
