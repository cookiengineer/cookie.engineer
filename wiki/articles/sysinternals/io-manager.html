I/O Manager

Windows I/O Manager architecture covering IRP s, device stacks, dispatch routines, IOCP , and buffering strategies, plus the Linux block layer comparison.

Overview

Every I/O request crosses a common subsystem before it reaches a device driver. Windows routes requests through the I/O Manager as I/O Request Packets; Linux routes them through the VFS and the block layer. This article dissects both paths, explains buffering and completion models, and shows how to observe them with iostat , iotop , and blktrace . After reading it you can trace a single write from the system call to the device.

Required Reading

  • System Calls - syscall mechanism, Linux syscall table, strace
  • Kernel Architecture - kernel architecture, subsystems, executive services

The I/O Problem

Every operating system must mediate access to hardware - disks, network cards, keyboards, GPU s. Without a centralized I/O subsystem, every driver would independently handle buffer management, asynchronous completion, cancellation, and access checks. Heterogeneous drivers lead to inconsistent behavior, deadlocks, and security vulnerabilities.

Windows solves this with the I/O Manager ( ntoskrnl.exe , source in io/ ). Linux solves it through the block layer ( block/ ), character device framework ( drivers/char/ ), and VFS ( fs/ ). Both designs share a fundamental insight: I/O is inherently asynchronous, and the OS must provide a uniform abstraction across diverse device types.

Windows IRP - I/O Request Packet

The fundamental unit of I/O in Windows is the IRP (I/O Request Packet). Every I/O operation

  • read, write, device control - is represented by an IR P allocated
from non-paged pool. The IR P travels down the device stack, with each driver adding its own parameters via an I/O stack location .

IRP Structure:
┌──────────────────────────────────────────────────────┐
│  IRP Header                                          │
│  ├── Type            (UINT16)       = IO_TYPE_IRP    │
│  ├── Size            (UINT16)                        │
│  ├── MdlAddress      (PMDL)         ← DMA buffer desc│
│  ├── Flags           (ULONG)                         │
│  ├── AssociatedIrp   (union)        ← master IRP link│
│  ├── ThreadListEntry (LIST_ENTRY)                    │
│  ├── IoStatus        (IO_STATUS_BLOCK)               │
│  │   ├── Status      (NTSTATUS)                      │
│  │   └── Information (ULONG_PTR)   ← bytes transferred│
│  ├── RequestorMode   (KPROCESSOR_MODE)               │
│  ├── PendingReturned (BOOLEAN)                       │
│  ├── StackCount      (CHAR)                          │
│  ├── CurrentLocation (CHAR)         ← current stack index│
│  ├── Cancel          (BOOLEAN)                       │
│  ├── CancelRoutine   (PDRIVER_CANCEL)                │
│  ├── UserBuffer      (PVOID)        ← user's buffer  │
│  └── Tail            (union)                         │
│      └── Overlay (contains:                          │
│          ├── Thread  (PETHREAD)      ← issuing thread │
│          ├── AuxiliaryBuffer (char*)                  │
│          └── DriverContext[4] (PVOID))                │
│                                                       │
│  IO_STACK_LOCATION[]  (one per driver in stack)       │
│  ├── StackLocation[0]          ← top of stack         │
│  │   ├── MajorFunction (UCHAR) (IRP_MJ_READ, etc.)   │
│  │   ├── MinorFunction (UCHAR)                        │
│  │   ├── Flags         (UCHAR)                        │
│  │   ├── Control       (UCHAR)                        │
│  │   ├── Parameters (union):                          │
│  │   │   ├── Create: SecurityContext, Options         │
│  │   │   ├── Read: Length, ByteOffset, Key            │
│  │   │   ├── Write: Length, ByteOffset, Key           │
│  │   │   └── DeviceIoControl: IoControlCode, ...      │
│  │   ├── DeviceObject  (PDEVICE_OBJECT)               │
│  │   ├── FileObject    (PFILE_OBJECT)                 │
│  │   └── CompletionRoutine (PIO_COMPLETION_ROUTINE)   │
│  ├── StackLocation[1]          ← middle driver(s)     │
│  └── StackLocation[N]          ← bottom (PDO)         │
└──────────────────────────────────────────────────────┘

The IR P is processed top-down (highest driver first) and completed bottom-up. CurrentLocation tracks which stack entry is active.

Device Stacks - Layered Driver Model

Windows drivers are layered - each layer adds or transforms functionality. A disk I/O might pass through five drivers:

                        │

┌────────────────────────────────────────────────┐

Linux uses a similar stacking model but with different abstractions:

Dispatch Routines: Major Function Codes

Every Windows driver registers dispatch routines for standard I/O operations. The MajorFunction field in the IR P stack location determines which dispatch routine handles the IR P:

MajorFunction Code Triggered By Purpose
IRP_MJ_CREATE 0x00 NtCreateFile() Open/create file or device
IRP_MJ_CREATE_NAMED_PIPE 0x01 CreateNamedPipe() Create named pipe
IRP_MJ_CLOSE 0x02 NtClose() Close handle
IRP_MJ_READ 0x03 NtReadFile() Read data
IRP_MJ_WRITE 0x04 NtWriteFile() Write data
IRP_MJ_QUERY_INFORMATION 0x05 NtQueryInformationFile() Get metadata
IRP_MJ_SET_INFORMATION 0x06 NtSetInformationFile() Set metadata
IRP_MJ_QUERY_EA 0x07 NtQueryEaFile() Query extended attributes
IRP_MJ_SET_EA 0x08 NtSetEaFile() Set extended attributes
IRP_MJ_FLUSH_BUFFERS 0x09 NtFlushBuffersFile() Flush caches
IRP_MJ_QUERY_VOLUME_INFORMATION 0x0A GetVolumeInformation() Volume metadata
IRP_MJ_SET_VOLUME_INFORMATION 0x0B SetVolumeInformation() Set volume metadata
IRP_MJ_DIRECTORY_CONTROL 0x0C NtQueryDirectoryFile() Enumerate directory
IRP_MJ_FILE_SYSTEM_CONTROL 0x0D FSCTL_* File system control
IRP_MJ_DEVICE_CONTROL 0x0E DeviceIoControl() Device-specific IOCTL
IRP_MJ_SHUTDOWN 0x10 System shutdown Cleanup before power-off
IRP_MJ_PNP 0x1B PnP Manager Plug and play events
IRP_MJ_POWER 0x16 Power Manager Power state transitions

I/O Completion and IOCP

Windows supports two completion models for asynchronous I/O:

  1. Completion Routines - a callback function registered in the IR P stack location. When a lower driver completes the IR P, the I/O Manager invokes the completion routine as the IR P bubbles back up the stack.
  1. I/O Completion Ports (IOCP) - a scalable, queue-based mechanism. Threads post completion packets to a port, and worker threads dequeue them. IOC P is the foundation of high-performance servers (IIS, SQL Server).

Buffering Strategies

Windows supports three I/O buffering strategies, selected by the driver when creating its device object:

1. Buffered I/O (METHOD_BUFFERED)
══════════════════════════════════════════════════════════════

User Buffer (user space)        System Buffer (non-paged pool)
┌──────────────────────┐       ┌──────────────────────┐
│    buf[4096]         │       │  Irp→AssociatedIrp.  │
│                      │ copy  │  SystemBuffer        │
│                      │◄─────►│                      │
└──────────────────────┘       └──────────────────────┘
  - I/O Manager copies between user buffer and system buffer
  - Driver works only with SystemBuffer
  - Safe: user cannot free/munmap the buffer during I/O
  - Overhead: double copy for reads (device→sys→user)
  - Used by: most simple drivers, serial, keyboard

2. Direct I/O (METHOD_IN_DIRECT / METHOD_OUT_DIRECT)
══════════════════════════════════════════════════════════════

User Buffer (user space)        MDL → Physical Pages
┌──────────────────────┐       ┌──────────────────────┐
│    buf[4096]         │ lock  │  Pfn0: 0x1234        │
│  (virtual address)   │──────►│  Pfn1: 0x5678        │
│                      │  MDL  │  Pfn2: 0x9ABC        │
└──────────────────────┘       └──────────────────────┘
  - I/O Manager locks user pages in memory (ProbeAndLockPages)
  - Creates Memory Descriptor List (MDL) with physical page numbers
  - Driver or DMA engine uses MDL for direct access
  - No copy overhead (device DMAs directly to/from user buffer)
  - Used by: disk and network drivers

3. Neither I/O (METHOD_NEITHER)
══════════════════════════════════════════════════════════════

User Buffer (user space)        Driver sees raw pointer
┌──────────────────────┐       ┌──────────────────────┐
│    buf[4096]         │ raw   │  Irp→UserBuffer      │
│  (virtual address)   │ ptr   │  = buf (va)          │
└──────────────────────┘       └──────────────────────┘
  - I/O Manager passes raw user virtual address to driver
  - Driver must call ProbeForRead/ProbeForWrite to validate
  - Driver must be in context of requesting thread (no DPC!)
  - Fastest: zero copy overhead, zero lock overhead
  - Dangerous if not properly validated
  - Used by: filesystem drivers (they do their own buffer management)

Linux buffering strategies comparison:

# Linux I/O buffering methods:

# 1. Buffered I/O (default) — kernel page cache
echo "hello" > /tmp/test_buf        # write() → page cache → (later) disk
cat /tmp/test_buf                    # read() → page cache

# 2. Direct I/O (O_DIRECT) — bypass page cache, DMA directly
dd if=/dev/zero of=/tmp/test_direct bs=4096 count=100 oflag=direct

# 3. Memory-mapped I/O (mmap) — pages mapped directly into address space
python3 -c "
import mmap, os
fd = os.open('/tmp/test_mmap', os.O_RDWR | os.O_CREAT)
os.ftruncate(fd, 4096)
m = mmap.mmap(fd, 4096, mmap.MAP_SHARED, mmap.PROT_WRITE)
m[0:11] = b'hello world'     # Write directly to memory
m.flush()                     # Force to disk
m.close()
os.close(fd)
"

# 4. Vectored I/O (readv/writev) — scatter/gather like MDL
# Multiple non-contiguous buffers in one syscall
python3 -c "
import os, struct
# writev: gather from multiple buffers into one operation
bufs = [b'hello ', b'world', b'!\\n']
# In C: struct iovec iov[3] = {...}; writev(fd, iov, 3)
"

# Show kernel's I/O mode for a specific fd
cat /proc/$$/fdinfo/3
# flags: 0100001  ← bit 0 = O_WRONLY, upper bits = O_DIRECT etc.

# Monitor direct I/O usage
sudo bpftrace -e '
kprobe:do_direct_IO { printf("Direct I/O: pid=%d comm=%s\n", pid, comm); }
'

Fast I/O Path

Windows provides a Fast I/O path that bypasses full IR P creation for cached, synchronous I/O. Instead of allocating an IR P, the I/O Manager directly calls the filesystem driver's FastIoRead/FastIoWrite routines:

Slow Path (Full IRP):              Fast Path:
══════════════════════              ═════════

NtReadFile()                       NtReadFile()
  │                                  │
  ▼                                  ▼
IoAllocateIrp() ← alloc              IoCheckFastIoRead()
  │                                  │
  ▼                                  ├── Hit: FsRtlCopyRead()
IoCallDriver(device, irp)            │     → copy from cache
  │                                  │     → return data
  ▼                                  │
driver→DispatchRead()                └── Miss: fall through to slow path
  │
  ▼
IoCompleteRequest(irp)
  │
  ▼
IoFreeIrp(irp)

Linux equivalent: the page cache hit path . When data is cached, read() returns directly from memory without going through the block layer:

# Trace fast vs slow I/O paths in Linux
sudo bpftrace -e '
kprobe:generic_file_read_iter {
    printf("VFS read (slow path entry): pid=%d\n", pid);
}
kprobe:filemap_read {
    printf("Page cache read: pid=%d\n", pid);
}
kprobe:submit_bio {
    printf("BLOCK LAYER (disk access): pid=%d comm=%s\n", pid, comm);
}
kretprobe:submit_bio /retval > 0/ {
    printf("  → submitted OK\n");
}
'

Cancel Routines and IRP Cancellation

Windows supports cancelling in-progress I/O. Threads call CancelIo() or CancelSynchronousIo() , which sets Irp->Cancel = TRUE and invokes the driver's cancel routine:

Cancellation Flow:
══════════════════════════════════════════════════════════════

User Thread                          I/O Manager        Driver
    │                                    │                 │
    │ CancelIoEx(hFile, &overlapped)     │                 │
    ├───────────────────────────────────►│                 │
    │                                    │                 │
    │                                    │ IoCancelIrp()   │
    │                                    ├────────────────►│
    │                                    │  (calls driver's│
    │                                    │  CancelRoutine) │
    │                                    │                 │
    │                                    │         ┌───────┤
    │                                    │         │ Mark  │
    │                                    │         │ IRP   │
    │                                    │         │ canceled│
    │                                    │         │ Release│
    │                                    │         │ queue │
    │                                    │         └───+───┤
    │                                    │             │
    │                                    │◄────────────┘
    │                                    │  IRP completed
    │◄───────────────────────────────────┤  with STATUS_CANCELLED

Linux has per-thread cancellation via signals, and io_uring supports request cancellation:

# Linux I/O cancellation mechanisms

# 1. Signals can interrupt blocking I/O
timeout 3 cat /dev/urandom > /dev/null  # Kills after 3s (SIGTERM)

# 2. aio_cancel() for POSIX AIO
# 3. io_uring_cqe_seen + IORING_OP_ASYNC_CANCEL in io_uring

# 4. Most block I/O operations are NOT interruptible in D state
# If in uninterruptible sleep (D state), signals are ignored
ps aux | awk '$8 ~ /D/ {print "Uninterruptible:", $2, $11}'

# 5. Cancel a stuck I/O (may not always work)
sudo kill -9 $(ps aux | awk '$8 ~ /D/ {print $2}' | head -1) 2>/dev/null

WDF - Windows Driver Framework

Modern Windows drivers use WDF instead of the legacy WDM (Windows Driver Model). WDF provides two frameworks:

Framework Purpose Key Abstraction
KMDF (Kernel-Mode Driver Framework) Kernel drivers State machines, power management defaults
UMDF (User-Mode Driver Framework) User-mode drivers Isolated, cannot crash kernel

KMDF wraps IR P handling - the driver doesn't see IR Ps directly. Instead, KMDF converts IR Ps into WDFREQUEST objects and calls the driver's EvtIoRead / EvtIoWrite callbacks. This eliminates boilerplate and prevents common bugs like: - Forgetting to complete an IR P - Completing an IR P from the wrong IR QL - Mishandling cancellation

sudo blktrace -d /dev/nvme0n1 -o - | blkparse -i -
# Detailed output:
# 259,0    0        1     0.000000000  1234  D  WS 2097152 + 256 [dd]
# 259,0    0        2     0.000042310  1234  C  WS 2097152 + 256 [0]
# D = issued to driver, C = completed
# WS = Write Sync (or W = write, R = read, WM = write metadata)
# 2097152 = sector number, 256 = sector count (128KB)

# ── Terminal 5: Syscall trace ──
strace -e trace=write,read -p $(pgrep dd)

Linux I/O Schedulers

The Linux block layer includes I/O schedulers that reorder, merge, and prioritize requests. This is analogous to Windows's Storport I/O prioritization:

# List available I/O schedulers
cat /sys/block/nvme0n1/queue/scheduler
# Output: [mq-deadline] kyber none bfq

# NVMe devices typically use "none" (no software scheduling — let hardware do it)
# SATA HDDs benefit from mq-deadline or bfq

# Scheduler characteristics:
# ───────────────────────────────────────────────────────
# none/mq-deadline: simple, low latency, good for SSDs
# kyber: latency target-based, self-tuning
# bfq: proportional share, fairness-focused (good for desktops)

# Change scheduler at runtime
echo kyber | sudo tee /sys/block/nvme0n1/queue/scheduler

# View scheduler-specific tunables
ls /sys/block/nvme0n1/queue/iosched/

# I/O merging statistics
cat /sys/block/nvme0n1/stat
# <reads> <reads_merged> <sectors_read> <read_ms>
# <writes> <writes_merged> <sectors_written> <write_ms>
# <io_in_progress> <io_ms> <weighted_io_ms>
# <discards> <discards_merged> <sectors_discarded> <discard_ms>
# <flush> <flush_ms>
