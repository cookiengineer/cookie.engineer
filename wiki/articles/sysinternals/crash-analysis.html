Crash Analysis

Linux kernel panic/oops anatomy - register dumps, crash dump formats, the crash utility, stack reconstruction, memory corruption root cause identification, and Windows bugcheck analysis.

Overview

A kernel crash leaves behind a register dump, a stack trace, and often a memory dump that must be read after reboot. This article decodes the fields of a Linux oops or panic, explains how kdump captures a vmcore, and shows how to reconstruct the faulting object with the crash utility. It also covers the sanitizer reports (KASAN, KCSAN) that catch memory corruption and races before they become crashes, and the equivalent Windows bugcheck workflow.

Required Reading

  • Kernel Debugging - kgdb, kdb, printk, ftrace
  • Kernel Memory - SLUB/SLAB allocators, page allocator, DMA
  • Synchronization - spinlocks, mutexes, RCU, lockdep
  • Virtual Memory - page tables, TLB, address translation

Anatomy of a Kernel Crash

A kernel crash on Linux comes in two severities: an oops (the kernel continues but the offending process is killed) and a panic (the kernel halts, all processor cores stop, and the system must reboot). On Windows, the equivalent is a bugcheck (Blue Screen of Death).

OS Severity Description
Linux Oops Kernel fault, process killed, system may continue in degraded state. Kernel tainted.
Linux Panic Unrecoverable error. System halts. Configurable: panic_on_oops, panic_on_warn, panic_timeout.
Windows Bugcheck 0xD1 DRIVER_IRQL_NOT_LESS_OR_EQUAL
Windows Bugcheck 0x50 PAGE_FAULT_IN_NONPAGED_AREA
Windows Bugcheck 0x1E KMODE_EXCEPTION_NOT_HANDLED
Windows Bugcheck 0x7E SYSTEM_THREAD_EXCEPTION_NOT_HANDLED
Windows Bugcheck 0x3B SYSTEM_SERVICE_EXCEPTION
Windows Bugcheck 0x8E KERNEL_MODE_EXCEPTION_NOT_HANDLED
Windows Bugcheck 0x9F DRIVER_POWER_STATE_FAILURE

Decoding the oops

# The crash happened at: my_write_handler+0x3a/0x50 [mydriver]
# Let's decode what instruction that is:

# 1. Find the module base address from the oops or /proc/modules
# 2. Disassemble the function
objdump -d mydriver.ko | grep -A30 '<my_write_handler>:'
# Look at offset 0x3a (58 bytes in)
# Matches: 48 8b 47 10 → mov rax, [rdi+0x10]
# Ah — RDI was 00000000, so [0x0 + 0x10] = address 0x10 → page fault!

# The fix: check if rdi is NULL before dereferencing

# For in-kernel crashes, use addr2line:
addr2line -e /usr/lib/debug/boot/vmlinux-$(uname -r) \
  -i ffffffff8123abc0
# Shows file:line for the crash address

Crash Dump Formats

To analyze a crash offline (after reboot), the system must save the kernel memory to persistent storage. Linux uses kexec + kdump for this; Windows uses memory.dmp.

┌──────────────────────────────────────────────────────────────────────┐
│                    CRASH DUMP ARCHITECTURE                             │
│                                                                      │
│  Normal boot:                                                         │
│    GRUB → kernel (production) → system runs                           │
│                                                                      │
│  Kdump/crash kernel boot:                                             │
│    GRUB → kernel (production) + crashkernel=256M                      │
│       │                                                               │
│       │  Kernel reserves 256 MB of RAM for crash kernel               │
│       │  (not usable by production kernel)                            │
│       ▼                                                               │
│    [System runs normally]                                             │
│       │                                                               │
│       │  Kernel panic!                                                │
│       ▼                                                               │
│    kexec loads crash kernel into reserved memory                      │
│    Crash kernel boots (minimal kernel, no hardware init)              │
│    Crash kernel saves /proc/vmcore → /var/crash/<timestamp>/vmcore   │
│    System reboots into production kernel                              │
│                                                                      │
│  Dump formats:                                                        │
│  ┌─────────────────+────────────────────────────────────────────--─┐ │
│  │  Format          │  Description                                  │ │
│  ├─────────────────+────────────────────────────────────────────--─┤ │
│  │  ELF vmcore      │  Full memory dump in ELF format               │ │
│  │                  │  Contains ELF headers + PT_LOAD segments       │ │
│  │                  │  Each PT_LOAD = a physical memory range        │ │
│  │                  │  Can be opened directly by 'crash' utility    │ │
│  ├─────────────────+────────────────────────────────────────────--─┤ │
│  │  makedumpfile    │  Compressed/filtered dump                      │ │
│  │  compressed      │  - zlib/lzo/snappy/zstd compression           │ │
│  │                  │  - Page filtering: zero pages, free pages,      │ │
│  │                  │    cache pages, user pages (excludable)         │ │
│  │                  │  - Typically 90%+ smaller than full dump        │ │
│  ├─────────────────+────────────────────────────────────────────--─┤ │
│  │  Kdump (flat)    │  Raw dump format (legacy)                      │ │
│  │                  │  Header + raw physical memory pages            │ │
│  └─────────────────+────────────────────────────────────────────--─┘ │
│                                                                      │
│  Windows dump types:                                                  │
│  ┌──────────────────+────────────────────────────────────────────┐   │
│  │  Complete memory │  All physical memory (size of RAM)          │   │
│  │  Kernel memory   │  Kernel-mode pages only (typically 100s MB) │   │
│  │  Small (minidump)│  64/128/256 KB containing: bugcheck info,   │   │
│  │                  │  loaded drivers, current thread stack, etc. │   │
│  │  Active memory   │  Kernel + user pages assigned to active    │   │
│  │                  │  processes (filtered by working set)       │   │
│  └──────────────────+────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────┘

Setting up kdump on Arch Linux

# 1. Install kexec-tools and kdump
sudo pacman -S kexec-tools

# 2. Configure crashkernel memory reservation
# Add to kernel command line in /etc/default/grub:
# crashkernel=256M (or 512M for systems with lots of RAM)
sudo vim /etc/default/grub
# GRUB_CMDLINE_LINUX_DEFAULT="... crashkernel=256M"
sudo grub-mkconfig -o /boot/grub/grub.cfg

# 3. Enable kdump service
sudo systemctl enable kdump.service
sudo systemctl start kdump.service

# 4. Check crash kernel memory reservation
cat /proc/cmdline | grep crashkernel
dmesg | grep -i crashkernel
# crashkernel reservation: 0x0000000058000000 - 0x0000000068000000 (256 MB)

# 5. Check crash kernel is loaded
cat /sys/kernel/kexec_crash_loaded
# 1 = crash kernel loaded and ready

# 6. Test crash kernel (WARNING: triggers kernel crash!)
echo c | sudo tee /proc/sysrq-trigger
# System will panic, crash kernel boots, saves vmcore, reboots

# 7. After reboot, find the crash dump
sudo ls /var/crash/
sudo ls /var/crash/<timestamp>/
# vmcore  vmcore-dmesg.txt

The Crash Utility Deep Dive

The crash utility is the primary tool for analyzing Linux kernel crash dumps. It provides a gdb-like interface for examining kernel data structures, backtraces, and memory.

┌──────────────────────────────────────────────────────────────────────┐
│                     CRASH UTILITY ARCHITECTURE                         │
│                                                                      │
│  crash requires two inputs:                                           │
│    - vmlinux: uncompressed kernel with debug symbols                  │
│    - vmcore:  kernel memory dump (ELF or compressed format)          │
│                                                                      │
│  $ sudo crash /usr/lib/debug/boot/vmlinux-$(uname -r) vmcore         │
│                                                                      │
│  crash> bt              ← backtrace of the active task                │
│  crash> bt -a            ← backtraces of ALL tasks                    │
│  crash> log              ← kernel log buffer (dmesg)                  │
│  crash> ps               ← process listing                           │
│  crash> files <PID>      ← open file descriptors for a process        │
│  crash> vm <PID>         ← virtual memory map (like /proc/PID/maps)  │
│  crash> kmem -i          ← kernel memory usage summary               │
│  crash> struct task_struct <addr>  ← display a kernel struct         │
│  crash> p <variable>     ← print value of a kernel variable          │
│  crash> sym <addr>       ← translate address to symbol               │

│  crash> mod              ← list loaded modules                       │
│  crash> dev              ← list character/block devices              │

│  crash> timer            ← kernel timers                            │
│  crash> runq             ← scheduler runqueue                        │
│  crash> mount            ← mounted filesystems                       │
│  crash> net              ← network device list                       │
│  crash> sys              ← system configuration info                 │
│  crash> mach             ← machine-specific info (CPU, memory)       │
│                                                                      │
│  gdb commands also available:                                         │
│  crash> whatis task_struct  ← type definition                        │
│  crash> print sizeof(struct file)  ← struct sizes                   │

Memory Corruption Analysis

Kernel memory corruption comes in several classic patterns. KASAN (Kernel Address Sanitizer) detects many of these dynamically:

┌──────────────────────────────────────────────────────────────────────┐
│                    MEMORY CORRUPTION PATTERNS                          │
│                                                                      │
│  1. Use-After-Free (UAF):                                            │
│     Object freed, but pointer still used.                             │
│     KASAN report: "use-after-free in function_name+0xNN/0xYY"        │
│     SLUB debug: freed object with POISON_FREE pattern overwritten     │
│                                                                      │
│  2. Double Free:                                                     │
│     Same object freed twice.                                          │
│     KASAN: "double-free" + stack trace of first free + second free   │
│     SLUB: freelist corruption, slab corruption                        │
│                                                                      │
│  3. Buffer Overflow (out-of-bounds write):                           │
│     Writing past end of allocated object.                             │
│     KASAN: "out-of-bounds write" + object info + redzone info        │
│     SLUB redzone: redzone bytes overwritten (detected on free)       │
│                                                                      │
│  4. Buffer Underflow (out-of-bounds read before object):              │
│     Reading from before start of allocation.                          │
│     KASAN: "out-of-bounds read"                                       │
│                                                                      │
│  5. Invalid Free:                                                    │
│     Freeing a pointer not from the slab allocator.                    │
│     SLUB: "invalid free of non-slab object"                          │
│     kmem_cache_free() called with wrong cache or stack pointer        │
│                                                                      │
│  6. Stale Stack Reference:                                           │
│     Returning pointer to stack-allocated variable.                    │
│     KASAN: "stack-out-of-bounds" or "use-after-scope"                │
│                                                                      │
│  SLUB debugging features:                                             │
│  ┌─────────────────+────────────────────────────────────────────┐    │
│  │  Feature         │  What It Detects                           │    │
│  ├─────────────────+────────────────────────────────────────────┤    │
│  │  Redzoning       │  Buffer overflow (pad object with guard    │    │
│  │                  │  bytes, check on free)                      │    │
│  │  Poisoning       │  Use-after-free (write magic pattern to    │    │
│  │                  │  freed memory, check on next allocation)   │    │
│  │  Sanity checks   │  Double-free, invalid free, corrupt slab   │    │
│  │  Tracing/Ftrace  │  Track allocation/free call sites          │    │
│  │  Object padding  │  Detect off-by-one errors (extra byte pad) │    │
│  └─────────────────+────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────────────┘

Reading a KASAN report

# Example KASAN report:
# ==================================================================
# BUG: KASAN: slab-out-of-bounds in my_driver_write+0x42/0x80
# Write of size 8 at addr ffff888100a3c020 by task writer/1234
#
# CPU: 3 PID: 1234 Comm: writer Not tainted 5.15.0+
# Call Trace:
#  dump_stack_lvl+0x34/0x48
#  print_address_description.constprop.0+0x2e/0x2b0
#  kasan_report+0x1a0/0x1d0
#  my_driver_write+0x42/0x80 [mydriver]    <- WHERE THE BUG IS
#  dev_attr_store+0x17/0x30
#  ...
#
# The buggy address belongs to the object at ffff888100a3c000
#  which belongs to the cache kmalloc-32 of size 32
# The buggy address is located 0 bytes to the right of 32-byte region
#  [ffff888100a3c000, ffff888100a3c020)
# The buggy address belongs to the page:
#  page:00000000a1b2c3d4 refcount:1 mapcount:0 ...
#
# Memory state around the buggy address:
#  ffff888100a3bf00: fc fc fc fc fc fc fc fc fc fc fc fc fc fc fc fc
#  ffff888100a3bf80: fc fc fc fc fc fc fc fc fc fc fc fc fc fc fc fc
#  ffff888100a3c000: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
# >ffff888100a3c020: fc fc fc fc fc fc fc fc fc fc fc fc fc fc fc fc
#                    ^^
#  ffff888100a3c040: fc fc fc fc fc fc fc fc fc fc fc fc fc fc fc fc
#
# Key: fc = redzone (guard), 00 = allocated and zeroed
# The object spans [0x000, 0x020), so the 8-byte write that starts at
# 0x020 begins one byte past the end of the allocation. KASAN flags any
# write whose first byte falls in the redzone, which is why the report
# points at 0x020 and says "0 bytes to the right of the region".

Race Condition Crashes

Race conditions and deadlocks produce distinctive crash patterns:

Root Cause Identification Workflow

┌──────────────────────────────────────────────────────────────────────┐
│                   ROOT CAUSE IDENTIFICATION FLOWCHART                    │
│                                                                      │
│  Step 1: Identify the crashing instruction from RIP                   │
│    ┌──────────────────────────────────────────────────────┐         │
│    │  crash> dis -r <RIP> 5                                │         │
│    │  → What instruction faulted?                          │         │
│    │  → Is it a memory access? Register-to-register?       │         │
│    └──────────────────────────────────────────────────────┘         │
│             │                                                        │
│             ▼                                                        │
│  Step 2: Determine the access type                                    │
│    ┌──────────────────────────────────────────────────────┐         │
│    │  Null pointer dereference:    CR2 ≈ 0x0-0xFFF        │         │
│    │  Invalid pointer:             CR2 = garbage value    │         │
│    │  Read fault:                  instruction loads      │         │
│    │  Write fault:                 instruction stores     │         │
│    │  Execute fault:               NX page (SMEP)         │         │
│    │  KPTI violation:              user addr in kernel    │         │
│    └──────────────────────────────────────────────────────┘         │
│             │                                                        │
│             ▼                                                        │
│  Step 3: Find the target address and reason                           │
│    ┌──────────────────────────────────────────────────────┐         │
│    │  crash> rd <CR2> 1     ← read address to verify      │         │
│    │  crash> vtop <CR2>     ← virtual→physical translation │         │
│    │  crash> kmem <CR2>     ← is page allocated? freed?    │         │
│    │  crash> p <reg>        ← what does source reg contain?│         │
│    └──────────────────────────────────────────────────────┘         │
│             │                                                        │
│             ▼                                                        │
│  Step 4: Trace the object lifetime (if applicable)                    │
│    ┌──────────────────────────────────────────────────────┐         │
│    │  If the object is from a slab cache:                  │         │
│    │  crash> kmem <addr>                                   │         │
│    │  → Shows: cache name, allocation site (if ftrace),    │         │
│    │    free status, redzone integrity                     │         │
│    │                                                        │         │
│    │  If SLUB_DEBUG was enabled:                            │         │
│    │  → Look at free_stack / alloc_stack traces            │         │
│    │  → Who allocated this? Who freed it? When?            │         │
│    └──────────────────────────────────────────────────────┘         │
│             │                                                        │
│             ▼                                                        │
│  Step 5: Identify the race partner (if applicable)                    │
│    ┌──────────────────────────────────────────────────────┐         │
│    │  Lockdep: was correct locking used?                   │         │
│    │  KCSAN: was there a concurrent access?                │         │
│    │  Crash dump: find other tasks accessing same address  │         │
│    │  crash> search <addr>    ← find other tasks referencing│         │
│    └──────────────────────────────────────────────────────┘         │
│             │                                                        │
│             ▼                                                        │
│  Step 6: Formulate the root cause                                     │
│    ┌──────────────────────────────────────────────────────┐         │
│    │  "Thread A freed object X while thread B still had   │         │
│    │   a pointer to it. Thread B dereferenced the freed   │         │
│    │   object at ffff888100a3c000+0x10. The free occurred │         │
│    │   in obj_release+0x35, the use in obj_handler+0x42. │         │
│    │   No lock protected the pointer between the two      │         │
│    │   threads. Fix: add refcounting or proper locking."  │         │
│    └──────────────────────────────────────────────────────┘         │
└──────────────────────────────────────────────────────────────────────┘

Common Crash Patterns

┌──────────────────────────────────────────────────────────────────────┐
│                    NULL POINTER DEREFERENCE                            │
│                                                                      │
│  struct my_obj *obj = NULL;  // forgot to allocate or check          │
│  obj->field = value;        // CRASH at offsetof(my_obj, field)     │
│                                                                      │
│  CR2 = 0x0000000000000028  (struct member at offset 0x28 was NULL)  │
│  Oops: unable to handle kernel NULL pointer dereference at 0x28     │
│  Fix: if (!obj) return -EINVAL;                                      │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│                    USE-AFTER-FREE                                     │
│                                                                      │
│  Thread A:        Thread B:                                          │
│  obj = kmalloc()  ...                                                │
│  ptr = obj;       ...                                                │
│  ...              kfree(obj);                                        │
│  ...              ...                                                │
│  ptr->field = x;  ← CRASH (ptr is now freed memory)                 │
│                                                                      │
│  KASAN: use-after-free in my_handler+0x42/0x70                      │
│  Memory at ffff888100a3c000 was freed in obj_release+0x35/0x60      │
│  Fix: add refcounting (kref) or use RCU                              │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│                    SLAB CORRUPTION (BUFFER OVERFLOW)                  │
│                                                                      │
│  char *buf = kmalloc(16, GFP_KERNEL);                                │
│  strcpy(buf, "This is way more than 16 bytes!");                     │
│  kfree(buf);  ← SLUB detects corrupted redzone → Oops               │
│                                                                      │
│  SLUB: slab corruption in kmalloc-32 cache                            │
│  Redzone 0x00-0x0f: 54 68 69 73 20 69 73 20 77 61 79 20 6d 6f 72 65 │
│  (Overwrote redzone bytes — buffer excess visible in hex)            │
│  Fix: use correct size, strlcpy/strscpy, or kmalloc(strlen+1)        │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│                    LIST CORRUPTION                                     │
│                                                                      │
│  list_del(&node);  // Thread A                                       │
│  list_del(&node);  // Thread B (double-unlink)                       │
│                                                                      │
│  list_del corruption: next->prev should be node, but was LIST_POISON2│
│  (LIST_POISON2 = 0x00200200, indicating already-freed list entry)    │
│  Fix: check list_empty() or protect with lock                        │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│                    PAGE FAULT IN NON-MAPPED REGION                     │
│                                                                      │
│  mmaped a device's MMIO region, then device is removed               │
│  Driver still tries to access the MMIO region → page fault           │
│                                                                      │
│  CR2 = 0xffffc90000123000 (vmalloc area, but unmapped)               │
│  Fix: check that the mapping is still valid before access             │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│                    DEADLOCK (CANNOT CRASH, BUT FREEZES)               │
│                                                                      │
│  No panic — system hangs.                                            │
│  sysrq-t shows blocked tasks in D state (uninterruptible sleep)      │
│  /proc/PID/stack shows stuck on mutex_lock()                         │
│  Lockdep output (if enabled) shows circular dependency               │
│  Fix: consistent lock ordering                                       │
└──────────────────────────────────────────────────────────────────────┘

Challenge

Write a Go tool that reads a kernel log from standard input and extracts every crash record by looking for the BUG, Oops, and Kernel panic markers, followed by the RIP line that names the faulting instruction. Feed it live kernel output and confirm the extracted addresses match the raw log.

package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"
)

func main() {
	scanner := bufio.NewScanner(os.Stdin)
	scanner.Buffer(make([]byte, 0, 64*1024), 1024*1024)

	inCrash := false
	for scanner.Scan() {
		line := scanner.Text()

		if strings.Contains(line, "BUG:") ||
			strings.Contains(line, "Oops:") ||
			strings.Contains(line, "Kernel panic") {
			inCrash = true
			fmt.Println("CRASH:", line)
			continue
		}

		if inCrash && strings.HasPrefix(strings.TrimSpace(line), "RIP:") {
			fmt.Println("  ", line)
		}
	}
}

Build it and run it against the current kernel log:

go build -o crashscan crashscan.go
dmesg | ./crashscan
journalctl -k | ./crashscan

Then inspect the crash configuration and available dumps by hand:

# 1. Check if kdump is configured
cat /proc/cmdline | grep -o 'crashkernel=[^ ]*'
cat /sys/kernel/kexec_crash_loaded
systemctl status kdump 2>/dev/null || echo "kdump service not found"

# 2. Check panic-related kernel parameters
cat /proc/sys/kernel/panic          # seconds before auto-reboot (0=hang)
cat /proc/sys/kernel/panic_on_oops  # 0=continue, 1=panic on oops
cat /proc/sys/kernel/panic_on_warn  # 0=no panic on WARN, 1=panic on WARN
cat /proc/sys/kernel/softlockup_panic
cat /proc/sys/kernel/hung_task_panic
cat /proc/sys/kernel/panic_print

# 3. Find debug kernel for crash analysis
ls /usr/lib/debug/boot/ 2>/dev/null || echo "No debug kernel installed"
# Install on Arch: sudo pacman -S linux-debug (optional, large)

# 4. List recent kernel crashes
sudo ls /var/crash/ 2>/dev/null || echo "No crash dumps found"
sudo find /var/crash -name vmcore -ls 2>/dev/null

# 5. Check kernel taint status
cat /proc/sys/kernel/tainted
# 0 = not tainted
# Non-zero: decode with: dmesg | grep -i taint

# 6. Check for BUG/Oops in current kernel log
dmesg | grep -i -E 'BUG:|Oops:|WARNING:|Call Trace|RIP:'

# 7. Check previously saved crash dumps
ls -lh /var/log/dmesg.* 2>/dev/null
sudo journalctl -k --grep="Oops" --no-pager 2>/dev/null | tail -20

# 8. Examine the current kernel's stack on each CPU

# 9. Inspect SLUB debugging information
