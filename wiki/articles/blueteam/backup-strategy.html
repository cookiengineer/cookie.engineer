Backup Strategy

Secure backup design with immutable storage, automated verification, and ransomware-resistant recovery planning.

Overview

A backup is only useful if it can be restored after the exact failure you designed it for. Modern ransomware targets backups first, so the design must assume the attacker already has administrator access to production. After reading this article you can choose a recovery point and recovery time objective, build an immutable repository with borg or restic , and prove a restore actually works.

Required Reading

  • Filesystems - mount options, snapshots, CoW filesystems (btrfs, ZFS)
  • Cryptography - symmetric encryption, AEAD, key management

Concept

A backup is not a copy of data. A backup is a tested, restorable, integrity-verified dataset that survives the failure mode you designed it to survive. If you have not tested the restore, you do not have a backup; you have a hope.

The adversaries have adapted: modern ransomware targets backups first. It deletes volume shadow copies, steals credentials from backup consoles, and encrypts mounted backup volumes. Your backup strategy must assume the attacker has admin access to your production network and is actively trying to destroy your ability to recover.

The 3-2-1 Rule

Classic 3-2-1:
  3 copies of data
  2 different media types
  1 copy offsite

Modern 3-2-1-1-0 (ransomware-hardened):
  3 copies
  2 different media types
  1 copy offsite
  1 copy immutable (WORM, append-only, air-gapped)
  0 errors (verified by automated restore testing)

What counts as "different media"?

  • Primary storage (SSD/HDD array).
  • External HDD or tape (different physical device).
  • Object storage such as S3 or Backblaze B2 (different failure domain).
  • Tape (LTO), which is a truly different technology and is immune to ransomware deletion.

Object storage with versioning and Object Lock is the practical sweet spot: cheap, accessible, API -driven, and able to enforce immutability.

Backup Types

Type What It Captures Speed Restore Complexity
Full Everything Slowest Single restore set
Incremental Changes since the last backup (any type) Fastest Combine all incrementals + full
Differential Changes since the last full Medium Full + last differential
Synthetic Full Server-side merge of the full and its incrementals into a new full Medium (server-side) Single restore set
Snapshot-based Filesystem/btrfs/ZFS snapshot Instant (in place) Not a true backup unless replicated off-host 
# Full backup with tar (simple, portable)
sudo tar cvzf /backup/full-$(date +%Y%m%d).tar.gz \
  --exclude=/proc --exclude=/sys --exclude=/dev --exclude=/tmp --exclude=/run \
  --exclude=/mnt --exclude=/media --exclude=/lost+found \
  /

# Incremental with tar (using snapshot/listed-incremental)
# First: full
sudo tar cvzf /backup/full-base.tar.gz --listed-incremental=/backup/snar.snar /etc /home /var

# Subsequent: incremental
sudo tar cvzf /backup/incr-$(date +%Y%m%d).tar.gz --listed-incremental=/backup/snar.snar /etc /home /var

RPO and RTO

RPO (Recovery Point Objective): Maximum acceptable data loss measured in time.
  RPO = 1 hour   -> you can lose up to 1 hour of data
  RPO = 24 hours -> you can lose up to 24 hours of data

RTO (Recovery Time Objective): Maximum acceptable time to restore service.
  RTO = 4 hours  -> service must be back within 4 hours
  RTO = 15 min   -> needs hot standby / automated failover
						
# Example RPO/RTO by service tier:

Tier 1 - Customer-facing, revenue-impacting:
  RPO: 1 hour (hourly incremental backups)
  RTO: 30 minutes (automated failover to DR site)
  Retention: 30 days hourly, 12 months daily, 7 years monthly

Tier 2 - Internal business applications:
  RPO: 24 hours (daily backups)
  RTO: 8 hours (restore from backup during business day)
  Retention: 90 days daily, 12 months monthly

Tier 3 - Non-critical:
  RPO: 7 days (weekly backups)
  RTO: 72 hours
  Retention: 6 months monthly

Linux Backup Tools

Borg

Borg is a deduplicating, compressing, and encrypting backup tool.

sudo pacman -S borg

# Initialize a repository (encrypted)
borg init --encryption=repokey-blake2 /backup/borg-repo
# Choose a strong passphrase - store it in a password manager or vault

# Create a backup
borg create --stats --progress --compression lz4 \
  /backup/borg-repo::host-{now:%Y%m%d-%H%M} \
  /etc /home /var/lib/postgresql /srv

# List backups (archives)
borg list /backup/borg-repo

# Check data integrity
borg check /backup/borg-repo

# Restore a specific file
borg extract /backup/borg-repo::host-20260626-0300 path/to/file

# Prune old backups (keep daily, weekly, monthly)
borg prune --keep-daily=7 --keep-weekly=4 --keep-monthly=12 \
  /backup/borg-repo

# Export the repo key for disaster recovery
borg key export /backup/borg-repo > /secure/location/borg-key-backup.txt
						
#!/bin/bash
# borg-backup.sh - automated daily backup script
# Called by a systemd timer or cron

export BORG_REPO="/backup/borg-repo"
export BORG_PASSPHRASE="$(vault kv get -field=passphrase secret/backup/borg)"

borg create --stats --compression lz4 \
  --exclude '/home/*/.cache' \
  --exclude '*.pyc' \
  --exclude '/var/tmp' \
  "${BORG_REPO}::$(hostname)-{now:%Y%m%d-%H%M}" \
  /etc /home /var/lib /srv /opt

borg prune --keep-daily=7 --keep-weekly=4 --keep-monthly=12 "${BORG_REPO}"

# Check integrity weekly
if [ "$(date +%u)" = "7" ]; then
  borg check "${BORG_REPO}"
fi

Restic

Restic is a cloud-native backup tool that speaks S3, B2, SFTP , and local repositories. 

sudo pacman -S restic

# Initialize repository (S3 example)
export RESTIC_REPOSITORY="s3:s3.amazonaws.com/backup-bucket/myhost"
export RESTIC_PASSWORD="strong-password-from-vault"
export AWS_ACCESS_KEY_ID="AKIA..."
export AWS_SECRET_ACCESS_KEY="..."

restic init

# Create a backup
restic backup /etc /home /var/lib /srv

# List snapshots
restic snapshots

# Restore
restic restore latest --target /restore/path

# Check integrity
restic check

# Prune old snapshots
restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --prune

rsync

rsync is a quick mirror for frequently-changing data. 

# Mirror a directory to a remote server
rsync -avz --delete /srv/data/ backup-server:/backup/srv-data/

# With bandwidth limiting (don't saturate the link)
rsync -avz --bwlimit=10000 --delete /srv/data/ backup-server:/backup/srv-data/

# Snapshot-based rotation with rsync + hardlinks
DIR="/backup/$(date +%Y%m%d-%H%M)"
LATEST=$(ls -1d /backup/20* 2>/dev/null | tail -1)

rsync -avz --delete --link-dest="$LATEST" /srv/data/ "$DIR/"
# --link-dest: unchanged files are hardlinked, only new/changed files take space

Immutable Backups

Immutability means that once data is written, it cannot be modified or deleted until the retention period expires, even by administrators with full credentials.

S3 Object Lock

Object Lock can only be enabled when a bucket is created; plan for it before you upload data.

# Create a bucket with Object Lock enabled
aws s3api create-bucket --bucket backup-bucket \
  --object-lock-enabled-for-bucket

# Configure a default retention rule
aws s3api put-object-lock-configuration \
  --bucket backup-bucket \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": {
      "DefaultRetention": {
        "Mode": "COMPLIANCE",
        "Days": 30
      }
    }
  }'

# Restore from the immutable backup
aws s3 cp s3://backup-bucket/myhost/2026-06-26/backup.tar.gz /restore/

# Object Lock in COMPLIANCE mode: NO ONE can delete during retention
# Governance mode: specific IAM permissions can override
# Use COMPLIANCE for critical backups

Borg Append-Only

# On the backup server, restrict the borg repo to append-only
# ~/.ssh/authorized_keys on the backup server:
# command="borg serve --append-only --restrict-to-path /backup/borg-repo",restrict ssh-rsa AAA... host-key
# This prevents the client from deleting or pruning archives
# Pruning is done directly on the backup server with separate credentials

Air-Gapped Backups

Air-gapped backups are offline and physically disconnected.

# Rotate external drives: one is always disconnected
# Mount -> backup -> unmount -> physically disconnect
sudo mount /dev/sdc1 /mnt/backup
borg create /mnt/backup/borg-repo::airgap-$(date +%Y%m%d) /critical/data
sudo umount /mnt/backup
# The drive is now physically disconnected - no ransomware can touch it

WORM (Write Once Read Many) storage options include LTO tape with its hardware write-protection tab, S3 Object Lock in COMPLIANCE mode, ZFS snapshots with hold , and the chattr +i immutable attribute (which root can still remove).

Backup Encryption

Backups contain your entire data corpus, so they must be encrypted both at rest and in transit.

# Borg: built-in encryption (repokey or keyfile mode)
borg init --encryption=repokey-blake2 /backup/repo
# repokey: encryption key stored IN the repo (encrypted with passphrase)
# keyfile: encryption key stored locally (keep this file safe!)

# Restic: built-in AES-256-CTR with Poly1305 authentication
export RESTIC_PASSWORD="$(vault kv get -field=password secret/backup/restic)"

# Manual encryption with GPG (for tar-based backups)
tar cz /data | gpg --symmetric --cipher-algo AES256 --output backup.tar.gz.gpg
# Decrypt: gpg --decrypt backup.tar.gz.gpg | tar xz

# Manual encryption with OpenSSL
tar cz /data | openssl enc -aes-256-gcm -pbkdf2 -iter 100000 \
  -pass pass:"$(cat /secure/backup-passphrase)" -out backup.tar.gz.enc

Critical rule: backup encryption keys must be stored separately from the backups themselves. If the attacker has access to both your backup storage and your key storage, encryption provides zero protection. 

# Key management for backups:
# 1. Primary key: in a password manager / vault
# 2. Recovery copy: printed on paper, in a physical safe (offsite)
# 3. Verification: quarterly test that you can decrypt a random backup using recovery materials

Backup Verification

Untested backups are not backups. Automated restore testing is non-negotiable.

#!/bin/bash
# verify-backups.sh - automated restore test
# Run weekly

BACKUP_DIR="/backup/borg-repo"
RESTORE_DIR="/tmp/restore-test-$$"
mkdir -p "$RESTORE_DIR"

# 1. Check repository integrity
borg check "$BACKUP_DIR" || { echo "INTEGRITY CHECK FAILED"; exit 1; }

# 2. Test that we can list archives
borg list "$BACKUP_DIR" > /dev/null || { echo "CANNOT LIST ARCHIVES"; exit 1; }

# 3. Restore a random sample of files
LATEST=$(borg list --short "$BACKUP_DIR" | tail -1)
borg extract "$BACKUP_DIR::$LATEST" "$RESTORE_DIR" --include 'etc/hostname'
# Verify the file exists and has content
if [ -f "$RESTORE_DIR/etc/hostname" ] && [ -s "$RESTORE_DIR/etc/hostname" ]; then
  echo "VERIFIED: $LATEST - $(cat "$RESTORE_DIR/etc/hostname")"
else
  echo "RESTORE TEST FAILED"
  exit 1
fi

# 4. Cleanup
rm -rf "$RESTORE_DIR"

echo "Backup verification: PASSED"
						
# Database backup verification (PostgreSQL example)
#!/bin/bash
# Check that DB dumps can actually be restored

pg_dump -Fc production_db > /tmp/test-dump-$$.dump

# Restore to a temporary database
createdb restore_test_$$
pg_restore -d restore_test_$$ /tmp/test-dump-$$.dump

# Run a query to verify data
psql -d restore_test_$$ -c "SELECT count(*) FROM critical_table;"

# Cleanup
dropdb restore_test_$$
rm /tmp/test-dump-$$.dump

Backup Access Control

Backup credentials must be separate from production credentials. The backup console is a prime target because it has access to everything. 

Principles:
1. Dedicated backup service accounts - never reuse admin credentials
2. MFA on the backup console - separate from production MFA
3. Network segmentation - backup VLAN isolated from production
4. Least privilege - the backup account can WRITE backups, cannot DELETE
5. Pull model - the backup server initiates connections to clients, not vice versa
						
# SSH-based pull backup (the backup server PULLS from clients)
# The client authorized_keys entry restricts access to borg serve --append-only
# The client has no access to the backup server

# On the backup server:
borg create \
  ssh://borg-user@client-host/./borg-repo::client-{now:%Y%m%d-%H%M} \
  /etc /home

# On the client:
# ~borg-user/.ssh/authorized_keys:
# command="borg serve --append-only --restrict-to-path /data/borg-repo",restrict ssh-ed25519 AAA...

Disaster Recovery Plan

A DR plan is a runbook that anyone on the team can execute under stress.

Disaster Recovery Runbook - Critical DB Server

Scenario: Production DB server unrecoverable
RPO: 1 hour  |  RTO: 4 hours

Prerequisites:
- Backup console access (separate from prod) - console.backup.internal:8443
- Backup passphrase - stored in Vault at secret/backup/borg
- DR server ready - dr-db-01.internal (kept warm, regular package updates)

Recovery Steps:
1. Declare the incident - notify the team via the #incidents channel.
2. Log into the backup console and verify the latest backup:
     borg list /backup/db-prod/borg-repo | tail -1
3. Verify backup integrity (about 5 min):
     borg check --verify-data /backup/db-prod/borg-repo
4. Prepare the DR server and confirm disks are mounted:
     ssh dr-db-01.internal "df -h /var/lib/postgresql"
5. Restore data (estimated 45 min for 500 GB):
     borg extract /backup/db-prod/borg-repo::db-prod-20260626-0300 \
       /var/lib/postgresql --progress
6. Start the database and verify:
     ssh dr-db-01.internal "systemctl start postgresql"
     ssh dr-db-01.internal "psql -c 'SELECT count(*) FROM critical_table;'"
7. Update DNS/load balancer to point at dr-db-01.
8. Validate application connectivity - run smoke tests.
9. Declare recovery complete and notify the team.

Communication Plan:
- Primary: Slack #incidents
- Escalation: phone tree (list in the password manager)
- Status page: update status.company.com

Tabletop Exercise

Run tabletop exercises quarterly. Give the team a scenario and walk through the recovery steps without actually executing them. Find gaps in documentation and assumptions.

Scenario: "It is Saturday 2 AM. The primary database server is encrypted by ransomware. The attacker also deleted the production backup server volumes. What do you do?"

  • Can the on-call person access the offsite backups?
  • Does the offsite restore require credentials the on-call person has?
  • How long would an actual restore take? Test this.
  • Are the DR runbook links and addresses still correct? They changed during the last network re-architecture.

Challenge

Write a Go tool that builds and verifies a backup manifest. manifest mode walks a directory and writes a file of sha256<TAB>path lines. verify mode re-hashes every file and reports missing, changed, and newly added files. This catches silent bit rot and tampering between backups. 

package main

import (
	"bufio"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"io"
	"os"
	"path/filepath"
	"sort"
	"strings"
)

func hashFile(path string) (string, error) {
	f, err := os.Open(path)
	if err != nil {
		return "", err
	}
	defer f.Close()

	h := sha256.New()
	if _, err := io.Copy(h, f); err != nil {
		return "", err
	}
	return hex.EncodeToString(h.Sum(nil)), nil
}

func walk(root string) (map[string]string, error) {
	files := make(map[string]string)
	err := filepath.Walk(root, func(path string, info os.FileInfo, err error) error {
		if err != nil {
			return err
		}
		if !info.Mode().IsRegular() {
			return nil
		}
		rel, err := filepath.Rel(root, path)
		if err != nil {
			return err
		}
		sum, err := hashFile(path)
		if err != nil {
			return err
		}
		files[filepath.ToSlash(rel)] = sum
		return nil
	})
	return files, err
}

func writeManifest(path string, files map[string]string) error {
	names := make([]string, 0, len(files))
	for name := range files {
		names = append(names, name)
	}
	sort.Strings(names)

	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer f.Close()

	for _, name := range names {
		fmt.Fprintf(f, "%s\t%s\n", files[name], name)
	}
	return nil
}

func readManifest(path string) (map[string]string, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()

	files := make(map[string]string)
	scanner := bufio.NewScanner(f)
	for scanner.Scan() {
		parts := strings.SplitN(scanner.Text(), "\t", 2)
		if len(parts) == 2 {
			files[parts[1]] = parts[0]
		}
	}
	return files, scanner.Err()
}

func main() {
	if len(os.Args) != 4 {
		fmt.Fprintf(os.Stderr, "usage: %s manifest|verify <dir> <manifest>\n", os.Args[0])
		os.Exit(2)
	}

	mode, dir, manifestPath := os.Args[1], os.Args[2], os.Args[3]

	files, err := walk(dir)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	switch mode {
	case "manifest":
		if err := writeManifest(manifestPath, files); err != nil {
			fmt.Fprintln(os.Stderr, err)
			os.Exit(1)
		}
		fmt.Printf("wrote %d entries to %s\n", len(files), manifestPath)
	case "verify":
		want, err := readManifest(manifestPath)
		if err != nil {
			fmt.Fprintln(os.Stderr, err)
			os.Exit(1)
		}
		bad := 0
		for name, sum := range want {
			got, ok := files[name]
			if !ok {
				fmt.Printf("MISSING %s\n", name)
				bad++
			} else if got != sum {
				fmt.Printf("CHANGED %s\n", name)
				bad++
			}
		}
		for name := range files {
			if _, ok := want[name]; !ok {
				fmt.Printf("ADDED   %s\n", name)
				bad++
			}
		}
		if bad > 0 {
			fmt.Printf("%d differences found\n", bad)
			os.Exit(1)
		}
		fmt.Println("manifest verified")
	default:
		fmt.Fprintln(os.Stderr, "mode must be manifest or verify")
		os.Exit(2)
	}
}

Test it against a small tree, then corrupt one file and confirm the verifier fails:

mkdir -p /tmp/data && echo hello > /tmp/data/a.txt
go run backup.go manifest /tmp/data /tmp/data.manifest
echo tampered > /tmp/data/a.txt
go run backup.go verify /tmp/data /tmp/data.manifest
