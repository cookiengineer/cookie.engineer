Tholian Scout

Automated Inventory Agent built for Agentic Cyber Defense

Overview

GitHub Repository | GitLab Mirror

Tholian Scout is the inventory agent for the Tholian Network. It answers the first question of every incident response and every asset audit: what is actually on this machine? It walks a system, reads what the operating system already knows, and writes one JSON report. There is no daemon, no central database, and no callback to a server.

It is built for blue teams, system administrators, and anyone who has to triage mixed Linux and BSD fleets. Instead of asking every distribution to report in its own dialect, Scout translates the host's native package manager, process table, devices, users, and logs into a single report format. A container, a router, a hypervisor, and a rack server all come back with the same shape.

The project exists because inventory should be boring and portable. A machine that cannot describe its own software, users, devices, and recent incidents is a machine you cannot defend with automation. Scout gives every host a standardized vocabulary for doing that, even when the underlying tools share nothing but an exit code.

Features

  • Collects distribution, kernel, BIOS, board, devices, drives, networks, packages, updates, programs, services, users, and incidents in one pass.
  • Normalizes everything into the System report from the open Tholian Core type system.
  • Collects packages through all package managers of all major Linux distributions.
  • Recognizes 24 distributions through /etc/os-release on Linux and /bin/freebsd-version on FreeBSD.
  • Separates packages from antiques. An antique is an available update that a running service or one of its dependencies actually uses.
  • Resolves program dependencies against the collected package list and reads program metadata through manifest adapters.
  • Correlates running processes with their environment, memory maps, command lines, and sockets to flag Destroy, Exfil, and Recon incidents.
  • Parses system logs and incidents from proc, procstat, syslog, and systemd.
  • Exposes a CollectIncidentsSince action for time-bounded incident collection.
  • Deduplicates incidents by identity and caps the findings per process.
  • Cross-compiles with no third-party dependencies via CGO_ENABLED=0.
  • Writes a single JSON System Report, or prints it to stdout.

Architecture

The Collect action is the start of the pipeline. It initializes the system fingerprint, runs each collector, resolves program dependencies against the package list, and finally computes the antiques that are required by running services.

Every collector is an available action that can be called remotely and that checks at runtime whether its tool exists, so a missing package manager disables one data source instead of failing the whole run.

# Can be called remotely via Tholian's Network Protocol
tholian-scout collect;
       |
       v
actions.Collect
       |
       +--> initSystem: /etc/os-release, uname, sysfs DMI, kenv
       |

       +--> CollectDevices ---> sysfs, pciconf, usbconfig
       +--> CollectNetworks --> net.Interfaces
       +--> CollectPackages --> apk, apt, dnf, dpkg, opkg, pacman, pkg, rpm, tdnf, zypper
       +--> CollectUpdates ---> same package managers
       +--> CollectPrograms --> procfs, procstat, ldd, npm
       +--> CollectServices --> procfs, procstat, npm
       +--> CollectUsers -----> shadow, master.passwd, systemd
       +--> CollectIncidents -> procfs, procstat, systemd, syslog, logread
       |
       +--> ResolveDependencies(system.Packages)
       +--> CollectAntiques: join updates with running services
       |
       v
structs.System (JSON report)

System Report

The System Report is the same structs.System type that the rest of the Tholian toolchain consumes. Scout does not invent a new inventory schema, and it does not ask other tools to understand ten package manager output formats. The same schema is used across the whole Tholian tech stack.

  • distribution, fingerprint, bios, board collects data from /etc/os-release, uname, sysfs DMI, kenv.
  • devices collects data from sysfs PCI and USB, pciconf, usbconfig.
  • drives collects data from df.
  • networks collects data from Go' net.Interfaces.
  • packages, updates collects data from apk, apt, dnf, dpkg, opkg, pacman, pkg, rpm, tdnf, zypper.
  • programs, services collects data from procfs, procstat, ldd, npm.
  • users collects data from /etc/shadow, /etc/master.passwd, systemd.
  • incidents collects data from procfs, procstat, journalctl, syslog files, logread.
  • antiques joins updates and services together, based on filesystem and package dependencies.

System Incidents

Incidents carry one of three types that Scout currently reports:

  • Recon represents probes, failed logins, scanners, exposed listeners.
  • Exfil represents active connections from shells or backdoors, successful remote access.
  • Destroy represents writable-path executables, deleted binaries, memfd maps, injected LD_* paths.

The Tholian Core type system also defines Intel, Conquer, and Persist for vulnerability and persistence findings. The sudo, su, and pam classifiers already recognize persistence-shaped events, but those findings need vulnerability context before the core type system will accept them, so the stable output today is the three types above.

Limitations

The honest limitations are part of the upstream operating system's design choices. Alpine Linux, FreeBSD, and OpenWrt report live process findings and syslog-based incidents, but not historical journal entries.

Building

The module expects tholian-core and tholian-insights to be checked out next to scout. The source/go.mod file uses relative replace directives, and the Makefile refuses to build without both directories.

cd /path/to/tholian-network;

# expected layout
# core/ insights/ scout/
ls;

cd ./scout;
make check;
make build;

make build cross-compiles the CLI automatically as standalone binaries with no linked dependencies:

ls ./build/linux;
# tholian-scout-amd64
# tholian-scout-arm64

ls ./build/freebsd;
# tholian-scout-amd64

Testing

cd /path/to/tholian-network/scout;

# formatting, vet, race-enabled unit tests, and a FreeBSD cross-build
make check;

# containerized end-to-end tests (requires Podman)
make test;

# specify which containerized tests to run
make test TEST_DISTRIBUTIONS="debian alpine";

# FreeBSD VM target (requires QEMU)
make test-freebsd;

The full targets do more than run the binary. They install a package, downgrade it to a pinned version, start the matching service, and then check that Scout sees the old version, reports the update, and finds the antique.

They then apply the update and verify that the update is gone. The rpm and dpkg targets only exercise package collection, and the openwrt target checks packages and updates because the minimal image does not run a full service stack.

The FreeBSD target runs the same idea in a QEMU-managed FreeBSD 15.1 VM with a locally generated two-version pkg repository, so it does not depend on a moving mirror.

Usage: Collect a System Report

cd /path/to/tholian-network/scout/build/linux;

# default path: /tmp/tholian-report.json
sudo ./tholian-scout-amd64 collect;

# explicit path
sudo ./tholian-scout-amd64 collect "/tmp/tholian-report.json";

# or via environment variable
sudo env THOLIAN_REPORT="/var/tmp/scout.json" ./tholian-scout-amd64 collect;

When passed as an argument, the path must end in .json and live under /home, /tmp, or /var; otherwise Scout falls back to THOLIAN_REPORT or prints the report to stdout.

The install action copies the binary into place:

sudo ./tholian-scout-amd64 install;
sudo tholian-scout collect;

Usage: Inventory Search

The search actions run the matching collectors against the live host and filters the results, so they do not need a previously written report. Matchers accept names, exact versions, and comparison operators. The serializable Matchers are also part of the open Tholian Core type system.

# which packages are installed at an exact version?
sudo tholian-scout search packages "glibc = 2.36";

# is a vulnerable library actually used by a running service?
sudo tholian-scout search antiques "log4j <= 2.14.1";

# recon findings, using the system:type syntax
sudo tholian-scout search incidents "any:Recon";

# which process owns a service, and with which arguments?
sudo tholian-scout search services nginx;

The exit code is 0 when at least one result matches and 1 when nothing matches, which makes the search actions usable in shell conditionals and automated scripts.
