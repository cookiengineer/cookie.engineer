Gobayashi

Overview

GitHub Repository | GitLab Mirror

The Gobayashi project is an experimental Linux malware dynamic analysis sandbox using eBPF for kernel-level observation and enforcement combined with Linux namespaces for process isolation.

The name comes from the Kobayashi Maru test in Star Trek, which is impossible to complete successfully, as it teaches the apprentice valueable lessons about how to react in critical situations that can't be escaped.

The goal is to provide an analysis environment where malware samples can be executed against a deliberately insecure-looking target system while their filesystem access, process activity, network connections, and DNS requests are intercepted and exposed to the analyst in real time.

Unlike a traditional sandbox that primarily records what happened after a sample has executed, Gobayashi is designed around interactive intervention.

Intercepted operations can be allowed, blocked, or spoofed while the malware is still running, making it possible to observe how an implant reacts to a controlled and dynamically modified environment.

Architecture

The sandbox is split into a privileged gobayashid daemon and an unprivileged gobayashi client. The daemon manages the eBPF programs, sandbox namespaces, network redirection, spoofing services, and malware lifecycle, while the client provides the terminal UI, policy engine, profile management, and analysis controls. Communication between both components uses JSON lines over a Unix domain socket, making sessions straightforward to inspect and replay.

The eBPF layer uses tracepoints for syscall, process, and network monitoring, socket filters and uprobes for DNS observation, and BPF LSM hooks for enforcing blocking decisions. The project currently targets Linux kernels 6.1+ LTS .

The sandbox itself uses isolated user, process, network, mount, and sandbox namespaces together with an overlay filesystem. This allows malware to interact with a filesystem that resembles a vulnerable server without directly modifying the analyst's host filesystem.

Features

The analysis environment is designed to provide visibility and intervention across the most important malware behaviors:

Name Type Mechanism
Filesystem File Operations eBPF tracepoints + LSM
Processes Process Lifecycle exec,fork,exittracing
Network Network Activity connect,sendto,recvfrom,bind
DNS DNS Resolution Socket filter +getaddrinfouprobe
Execution Binary Launch BPF LSMbprm_check_security
Ptrace Debugger Access BPF LSMptrace_access_check
HTTP/HTTPS Network Spoofing Local reverse proxy
DNS DNS Spoofing Local DNS honeypot
Filesystem Honeypot Data Generated decoy files
Profiles Analysis Rules YAML policies

The policy engine supports four decision types: allow , block , spoof , and custom . This makes it possible, for example, to prevent a ransomware sample from modifying real files while returning plausible fake data when it reads credential files. Rules can match paths, domains, IP addresses, processes, and event types using glob patterns.

The sandbox also contains deliberately attractive honeypot data such as fake SSH keys, AWS credentials, shell history, password files, and other documents. The intention is to make the environment behave more like a compromised corporate Linux server and therefore expose post-exploitation behavior that would otherwise depend on the presence of interesting files.

Analysis Profiles

Decisions made during an investigation can be persisted as YAML analysis profiles. Profiles can contain a default action, decision timeout, behavioral hints, MITRE ATT&CK techniques, and prioritized event matching rules.

This allows an interactive analysis session to be converted into a repeatable experiment. A profile developed while investigating one ransomware sample can for example be replayed against another sample to compare behavioral differences or identify common campaign characteristics.

The client also supports headless operation and replayable JSON -Lines sessions, which makes the same infrastructure useful for automated malware analysis and regression testing in addition to interactive reverse engineering.

Usage

The Gobayashi daemon requires root privileges because it manages eBPF programs, Linux namespaces, and the isolated network environment. The one-time setup needs to be performed again after a reboot, followed by building the daemon and client. 

cd /path/to/gobayashi;

# One-time setup after reboot
sudo ./scripts/setup.sh;

# Build the gobayashi daemon and client
make build;

The daemon can then be started in one terminal while the analysis client is used from another terminal: 

# Start gobayashi daemon
sudo ./bin/gobayashid --foreground --verbose;

# Analyze malware sample
./bin/gobayashi analyze ./samples/bin/fs_probe;

For automated validation, the repository also provides unit tests, BPF integration tests, end-to-end malware sample tests, and a Podman-based test suite.
