Containers

Linux namespaces, cgroups, OverlayFS, podman architecture, OCI runtime, rootless containers, and container security.

Overview

A container is a Linux process (or process tree) running in an isolated context built from kernel features: namespaces restrict what the process can see, cgroups restrict what it can consume, and layered filesystems provide a private root filesystem. The kernel is shared with the host; there is no hypervisor and no guest kernel. This article dissects how containers actually work, from namespaces and cgroups up to the OCI runtime, and shows how to audit a container's security posture with podman .

Containers vs VMs

VIRTUAL MACHINE:
  App A  |  App B  |  App C
  Bins/Libs  |  Bins/Libs  |  Bins/Libs
  Guest OS (Kernel)           |
  -----------------------------
  Hypervisor (KVM)
  -----------------------------
  Host OS Kernel
  -----------------------------
  Physical Hardware

CONTAINER:
  App A  |  App B  |  App C
  Bins/Libs  |  Bins/Libs  |  Bins/Libs
  --------------------------------
  Host OS Kernel  (shared by all)
  --------------------------------
  Physical Hardware

Isolation boundary Hypervisor Kernel namespaces + cgroups
Boot time 10-60 seconds 0.1 - 2 seconds
Memory overhead GBs (guest kernel + OS) MBs (process tree only)

Snapshoting Full VM snapshot Image layer commit
Density 10s of VMs per host 100s of containers per host

Linux Namespaces

Namespaces are the foundation of container isolation. Each namespace type restricts what a process sees of a specific kernel resource.

Namespace Types

Namespace Kernel Constant Isolates Created with
PID CLONE_NEWPID Process IDs PID 1 in container maps to some host PID
Mount CLONE_NEWNS Mount points Private/proc,/sys,/dev, rootfs
Network CLONE_NEWNET Network stack Private interfaces, routes, iptables rules
UTS CLONE_NEWUTS Hostname, domain hostnameinside container vs host
IPC CLONE_NEWIPC System V IPC, POSIX msg queues Isolated message queues and semaphores
User CLONE_NEWUSER UID/GID mapping UID 0 in container maps to UID 1000 on host
Cgroup CLONE_NEWCGROUP Cgroup root Container sees its own cgroup tree
Time CLONE_NEWTIME Clock offsets DifferentCLOCK_MONOTONIC,CLOCK_BOOTTIME

Inspecting Namespaces

# List namespaces of a process
ls -la /proc/$$/ns/
# Each entry is a symlink to a namespace identifier:
#   cgroup -> cgroup:[4026531835]
#   ipc -> ipc:[4026531839]
#   mnt -> mnt:[4026531841]
#   net -> net:[4026531840]
#   pid -> pid:[4026531836]
#   uts -> uts:[4026531838]
#   user -> user:[4026531837]

# The namespace identifier (inode number) identifies the namespace instance.
# Processes in the same namespace share the same inode number.

# Compare namespaces between host and container
HOST_PID=1
CONTAINER_PID=$(podman inspect --format '{{.State.Pid}}' mycontainer)

echo "Host PID namespace:    $(readlink /proc/$HOST_PID/ns/pid)"
echo "Container PID namespace: $(readlink /proc/$CONTAINER_PID/ns/pid)"

# Namespace persistence: bind-mount a namespace to keep it alive
touch /tmp/netns
mount --bind /proc/$$/ns/net /tmp/netns
# Even when the original process exits, this namespace survives.
# Used by ip netns and container runtimes.

Creating Namespaces

# Create a process in its own PID and mount namespace
unshare --pid --mount --fork --mount-proc /bin/bash

# Inside the new namespace:
echo $$           # PID 1 (in this namespace)
ps aux            # Only processes in this namespace
ls /proc          # Only this namespace's entries

# Create a process with its own network namespace
unshare --net /bin/bash
ip link           # Only loopback, no eth0
ip addr           # 127.0.0.1 only

# Create a user namespace with UID mapping
unshare --user --map-root-user /bin/bash
id                # uid=0(root) gid=0(root)
# This is root in the namespace only. On the host, it maps to the original UID.

# Combined: full container-like isolation
unshare \
    --pid --fork --mount-proc \
    --mount \
    --net \
    --uts \
    --ipc \
    --cgroup \
    --user --map-root-user \
    /bin/bash

UID Mapping

# UID mapping configuration
cat /proc/$$/uid_map
# Format: ID-inside-ns  ID-outside-ns  length
#   0          1000         1
# UID 0 in namespace -> UID 1000 on host (for 1 ID)

# Example: map 65536 UIDs
# echo "0 100000 65536" > /proc/$(pid)/uid_map

# The kernel enforces: writing to uid_map requires CAP_SETUID in the
# parent namespace. Without mapping, all UIDs appear as the overflow UID
# (typically 65534/nobody).

cgroups

If namespaces control what a process can see , cgroups control what a process can use . cgroups limit, account for, and isolate resource usage ( CPU , memory, disk I/O, network).

cgroup v2 Hierarchy

cgroup v2 has a unified hierarchy (single tree). All controllers are mounted together:

# cgroup v2 is mounted at /sys/fs/cgroup
mount | grep cgroup
# cgroup2 on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec,relatime,nsdelegate,memory_recursiveprot)

# List available controllers
cat /sys/fs/cgroup/cgroup.controllers
# cpuset cpu io memory hugetlb pids rdma misc

# List child cgroups
ls /sys/fs/cgroup/
# system.slice/  user.slice/  machine.slice/

Resource Control

# Create a cgroup for a container workload
CGROUP=/sys/fs/cgroup/containers/myapp
mkdir $CGROUP

# CPU: limit to 50% of one core
echo "50000 100000" > $CGROUP/cpu.max

# Memory: limit to 256 MiB
echo $((256 * 1024 * 1024)) > $CGROUP/memory.max
# 268435456 bytes

# Memory swap limit (0 = no swap for this cgroup)
echo 0 > $CGROUP/memory.swap.max

# IO: limit writes to 10 MB/s on device 8:0 (sda)
echo "8:0 wbps=10485760" > $CGROUP/io.max

# PIDs: limit to 100 processes
echo 100 > $CGROUP/pids.max

# Move a process into the cgroup by writing its PID
echo $PID > $CGROUP/cgroup.procs

# Move the shell into the cgroup to test limits
echo $$ > $CGROUP/cgroup.procs
# Now run memory-intensive program: it will be killed (OOM) at 256 MiB

# Verify limits are applied
cat /proc/$$/cgroup
# 0::/containers/myapp

cgroup Stats

# View current memory usage of a cgroup
cat $CGROUP/memory.current
# 45236224  (bytes)

# CPU usage statistics
cat $CGROUP/cpu.stat
# usage_usec 12345678
# user_usec 9876543
# system_usec 2469135

# Number of times the cgroup was OOM-killed
cat $CGROUP/memory.events
# low 0
# high 0
# max 5
# oom 5
# oom_kill 5

# Pressure stall information (PSI) - how much tasks are stalled
cat $CGROUP/cpu.pressure
# some avg10=1.23 avg60=0.45 avg300=0.12 total=4567890
# full avg10=0.00 avg60=0.00 avg300=0.00 total=0

OverlayFS

Container images use layered filesystems. Each layer is a directory of files. The OverlayFS kernel module stacks these layers, presenting a unified view to the container.

OverlayFS Layers

Merged View (what the container sees)
  = Upperdir (writable, container's changes)
    + Lowerdir (read-only, image layers)

Example with two lower layers:

Lower layer 1 (base image: archlinux):
  /etc/os-release
  /usr/bin/bash
  /usr/bin/ls

Lower layer 2 (app layer):
  /usr/bin/myapp
  /etc/myapp.conf

Upper layer (writable container layer):
  (starts empty)

Merged:
  /etc/os-release     (from lower1)
  /usr/bin/bash       (from lower1)
  /usr/bin/ls         (from lower1)
  /usr/bin/myapp      (from lower2)
  /etc/myapp.conf     (from lower2)
  /var/log/myapp.log  (created in upper, only in this container)

OverlayFS copy-up: when a file from a lower layer is modified, the entire file is copied to the upper layer first, then modified. This means the original in the lower layer is never touched

  • the container's changes are isolated in the upper layer.

Manual OverlayFS Setup

# Create layer directories
mkdir -p lower1 lower2 upper work merged

# Populate lower layers (simulating image layers)
echo "base file" > lower1/base.txt
echo "app file"  > lower2/app.txt

# Mount OverlayFS
mount -t overlay overlay \
    -o lowerdir=lower2:lower1,upperdir=upper,workdir=work \
    merged

# The merged view shows both layers' files
ls merged/
# app.txt  base.txt

# Write a new file - goes to upper layer
echo "container data" > merged/container.txt
ls upper/
# container.txt

# Modify a lower-layer file - copy-up to upper
echo "modified" > merged/base.txt
cat upper/base.txt
# modified
cat lower1/base.txt
# base file  (unchanged!)

# Cleanup
umount merged

The workdir is a technical requirement: OverlayFS uses it to prepare files before atomically moving them to the upper layer. It must be on the same filesystem as upperdir .

podman Architecture

podman implements the OCI container runtime specification without a daemon. Unlike Docker (which uses a persistent dockerd process), podman uses a fork-exec model: 

podman run creates conmon (container monitor) which forks container process

podman can exit, conmon stays to:
  - Forward logs
  - Report exit code
  - Handle terminal IO

DOCKER:
  client (docker) -> dockerd (daemon, always running) -> containerd -> runc -> container

PODMAN:
  client (podman) -> directly creates container process via fork/exec
                    No persistent daemon. podman CLI IS the runtime.

Advantages of the daemonless model:

  • No single point of failure (dockerd crash kills all containers under Docker)
  • No always-running root process with socket exposure
  • Better systemd integration (podman generates systemd unit files natively)
  • REST API available via podman system service (optional, on-demand)

Rootless Containers

Rootless mode is podman's default for non-root users. It uses user namespaces to map container UID 0 to the user's host UID: 

# Run a container as a regular user (no root required)
podman run --rm -it archlinux:latest /bin/bash

# Inside the container, you appear as root:
id
# uid=0(root) gid=0(root) groups=0(root)

# On the host, the container process runs as your UID:
ps aux | grep "container process"
# user  12345  ...  /bin/bash

# Rootless networking uses a userspace TCP/IP stack (slirp4netns or pasta):
#   - No CAP_NET_ADMIN required
#   - Network traffic goes through a userspace NAT
#   - Cannot bind privileged ports (less than 1024) without additional setup

User namespace allows the container to have "root" capabilities within the container, but these capabilities are scoped to the namespace and do not grant host root access.

Container Images

Image Structure

Container image (OCI format):
  index.json          (manifest list for multi-arch)
  oci-layout          (spec version)
  blobs/
    sha256/
      a1b2...     (config JSON: env, entrypoint, exposed ports)
      c3d4...     (layer 1: rootfs diff, gzip compressed tar)
      e5f6...     (layer 2)
      g7h8...     (layer 3)

Each layer is a tar archive containing the files added, modified, or deleted relative to the previous layer. Images are content-addressable: the filename is the SHA256 hash of the content.

Containerfile

# Containerfile - OCI-compatible, works with podman and docker

FROM archlinux:latest

LABEL org.opencontainers.image.title="My Application"
LABEL org.opencontainers.image.version="1.0.0"

ENV APP_HOME=/opt/myapp
ENV PATH=$APP_HOME/bin:$PATH

RUN pacman -Syu --noconfirm && \
    pacman -S --noconfirm python python-pip gcc make && \
    pacman -Scc --noconfirm

COPY . $APP_HOME/

RUN useradd --create-home --shell /bin/bash appuser && \
    chown -R appuser:appuser $APP_HOME

USER appuser
WORKDIR $APP_HOME

RUN pip install --user -r requirements.txt

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
    CMD curl -f http://localhost:8080/health || exit 1

ENTRYPOINT ["python", "-m", "myapp"]
CMD ["--host", "0.0.0.0", "--port", "8080"]

Layer Caching

Each instruction creates a new layer. Order instructions to maximize cache hits:

1. Base image           // rarely changes
2. Package manager updates // changes occasionally
3. Dependency install   // changes when dependencies change
4. Application code     // changes most frequently
5. Configuration        // changes occasionally

If you COPY code before installing dependencies, every code change invalidates the dependency cache. Always install dependencies first, then copy code. 

# Multi-stage build
FROM archlinux:latest AS builder
RUN pacman -Syu --noconfirm && pacman -S --noconfirm gcc make
COPY src/ /build/
RUN make -C /build

FROM archlinux:latest
COPY --from=builder /build/output/binary /usr/local/bin/myapp
ENTRYPOINT ["/usr/local/bin/myapp"]

Minimal Container in Bash

A minimal container runtime demonstrates how all these pieces fit together:

#!/bin/bash
# simple-container.sh - minimal container runtime
set -euo pipefail

ROOTFS="$1"
COMMAND="${2:-/bin/sh}"

if [ -z "$ROOTFS" ] || [ ! -d "$ROOTFS" ]; then
    echo "Usage: $0 <rootfs_directory> [command]"
    exit 1
fi

die() { echo "ERROR: $1" >&2; exit 1; }

# Create directories for the container
CGROUP_DIR="/sys/fs/cgroup/containers/simple-$$"
OVERLAY_UPPER=$(mktemp -d /tmp/simple-upper-XXXXX)
OVERLAY_WORK=$(mktemp -d /tmp/simple-work-XXXXX)
OVERLAY_MERGED=$(mktemp -d /tmp/simple-merged-XXXXX)

cleanup() {
    umount "$OVERLAY_MERGED" 2>/dev/null || true
    rmdir "$OVERLAY_MERGED" "$OVERLAY_UPPER" "$OVERLAY_WORK" 2>/dev/null || true
    [ -d "$CGROUP_DIR" ] && rmdir "$CGROUP_DIR" 2>/dev/null || true
}
trap cleanup EXIT

# Step 1: Setup OverlayFS
mount -t overlay overlay \
    -o "lowerdir=$ROOTFS,upperdir=$OVERLAY_UPPER,workdir=$OVERLAY_WORK" \
    "$OVERLAY_MERGED" || die "Failed to mount OverlayFS"

# Step 2: Create cgroup
mkdir -p "$CGROUP_DIR"
echo $((128 * 1024 * 1024)) > "$CGROUP_DIR/memory.max" 2>/dev/null || true
echo 100 > "$CGROUP_DIR/pids.max" 2>/dev/null || true

# Step 3: Create namespaces and enter container
unshare \
    --pid --fork --mount-proc \
    --mount \
    --uts --hostname container \
    --ipc \
    --cgroup \
    /bin/bash -c "
        # Mount /proc, /sys, /dev inside container
        mount -t proc proc /proc
        mount -t sysfs sys /sys
        mount -t tmpfs tmp /tmp

        # pivot_root to the merged overlay
        mkdir -p $OVERLAY_MERGED/proc $OVERLAY_MERGED/sys $OVERLAY_MERGED/.old_root
        pivot_root $OVERLAY_MERGED $OVERLAY_MERGED/.old_root
        cd /

        # Move ourselves into the cgroup
        [ -f $CGROUP_DIR/cgroup.procs ] && echo \$PPID > $CGROUP_DIR/cgroup.procs 2>/dev/null || true

        # Execute the command
        exec $COMMAND
    "

What Each Step Does

  1. OverlayFS mount : creates a writable view of the read-only rootfs
  2. cgroup creation : sets memory and process limits for the container
  3. unshare : creates PID, mount, UTS, IPC , and cgroup namespaces
  4. Mount /proc and /sys : makes these pseudo-filesystems available inside
  5. pivot_root : changes the process's root to the overlay mount point
  6. cgroup assignment : places the container process in its cgroup
  7. exec : replaces bash with the target command

Container Security

Default Restrictions

podman applies these restrictions by default:

# Inspect security settings applied to a container
podman inspect secure-container --format '{{.HostConfig}}'

# Equivalent podman run flags:
#   --security-opt no-new-privileges       Block privilege escalation
#   --security-opt seccomp=...             System call filter
#   --cap-drop ALL                         Drop all capabilities
#   --cap-add NET_BIND_SERVICE             Add only needed caps
#   --read-only                            Read-only rootfs
#   --read-only-tmpfs=false                Except for /tmp
#   --user 1000:1000                       Non-root user
podman run \
    --security-opt no-new-privileges \
    --security-opt seccomp=/usr/share/containers/seccomp.json \
    --cap-drop ALL \
    --cap-add NET_BIND_SERVICE \
    --read-only \
    --read-only-tmpfs=false \
    --user 1000:1000 \
    myimage

Capabilities

Containers start with a reduced capability set. Read the current set from /proc/self/status inside the container: 

# Default capabilities in a rootless podman container
podman run --rm alpine grep Cap /proc/self/status
# CapInh: 0000000000000000
# CapPrm: 0000000000000000
# CapEff: 0000000000000000
# CapBnd: 00000000a80425fb
# CapAmb: 0000000000000000

# Drop ALL capabilities
podman run --rm --cap-drop ALL alpine grep Cap /proc/self/status
# CapBnd: 0000000000000000

# Add specific capabilities
podman run --rm --cap-drop ALL --cap-add NET_BIND_SERVICE alpine grep Cap /proc/self/status

seccomp Profiles

seccomp (Secure Computing Mode) filters system calls. A container's default seccomp profile blocks roughly 44 syscalls: 

# The default seccomp profile (simplified)
# Located at /usr/share/containers/seccomp.json on Arch
# Blocked syscalls include:
#   - kexec_load          (kernel execution)
#   - mount               (restricted mounting)
#   - ptrace              (process tracing)
#   - perf_event_open     (performance events)
#   - bpf                 (BPF program loading)
#   - init_module         (kernel module loading)
#   - clock_settime       (time modification)

# Run without seccomp (dangerous)
podman run --rm --security-opt seccomp=unconfined alpine /bin/sh

# Custom seccomp profile
podman run --rm --security-opt seccomp=/path/to/custom.json alpine /bin/sh

Privileged Containers

--privileged disables all security features: 

# PRIVILEGED: all capabilities, all devices, no seccomp, no AppArmor
podman run --rm --privileged alpine /bin/sh

# This gives:
#   - ALL capabilities (including CAP_SYS_ADMIN)
#   - Access to all host devices (/dev/*)
#   - Disabled seccomp filtering
#   - Disabled AppArmor/SELinux confinement
#   - Access to host cgroup controllers

A privileged container is effectively root on the host. Never use --privileged unless you have a specific, well-understood need.

Escape Vectors

Vector Condition Mitigation
Kernel exploit in namespace/cgroup Any container Kernel patches, minimize attack surface
Mounted docker/podman socket /var/run/docker.sockbind-mount Never mount container socket
Host PID namespace --pid=host Never use host PID namespace
Host network namespace --net=host Avoid unless necessary
Privileged container --privileged Never use
CAP_SYS_ADMIN Explicitly added capability Drop ALL, add only needed
CVE-2019-5736 runc < 1.0-rc6, attacker overwrites /proc/self/exe Update container runtime

CVE-2019-5736 (runc escape) : An attacker with root inside a container could overwrite the host's runc binary by tricking it into opening /proc/self/exe (which pointed to the host binary when runc executed the container process). Fixed in runc >= 1.0-rc6 by using memfd to create a private copy of runc in memory.

OCI Standards

The Open Container Initiative defines two specifications:

runtime-spec: how to run a container
  - config.json: OCI runtime configuration
    * ociVersion, root (path, readonly)
    * process (terminal, user, args, env, cwd, capabilities, rlimits)
    * mounts, linux (namespaces, uidMappings, gidMappings, sysctl, seccomp)
    * hooks (prestart, poststart, poststop)
  - Defines lifecycle: create, start, kill, delete

image-spec: how to package a container image
  - oci-layout (version)
  - index.json (manifest list)
  - blobs/sha256/ (content-addressable blobs)
    * Config: JSON with image config
    * Manifest: JSON with layer references
    * Layers: tar+gzip filesystem diffs

Example config.json

{
  "ociVersion": "1.0.2",
  "process": {
    "terminal": true,
    "user": {"uid": 0, "gid": 0},
    "args": ["/bin/sh"],
    "env": ["PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin"],
    "cwd": "/",
    "capabilities": {
      "bounding": ["CAP_CHOWN", "CAP_NET_BIND_SERVICE"],
      "effective": ["CAP_CHOWN"]
    }
  },
  "root": {
    "path": "/var/lib/containers/storage/overlay/abc123/merged",
    "readonly": false
  },
  "linux": {
    "namespaces": [
      {"type": "pid"},
      {"type": "network"},
      {"type": "mount"},
      {"type": "uts"},
      {"type": "ipc"}
    ],
    "resources": {
      "memory": {"limit": 268435456},
      "cpu": {"shares": 1024}
    }
  }
}

Container Auditing

# List all containers (root + rootless)
podman ps -a
podman ps -a --external    # includes externally created containers

# Inspect a container's security posture
podman inspect mycontainer | jq '.[0].HostConfig | {privileged, capAdd, readonlyRootfs, pidMode, networkMode, usernsMode}'

# Check running containers' capabilities
for pid in $(podman ps -q | xargs -I{} podman inspect {} --format '{{.State.Pid}}'); do
    echo "PID $pid: $(getpcaps $pid 2>/dev/null || echo 'N/A')"
done

# Check cgroup resource limits
podman stats --no-stream

# Check image layers
podman image tree myapp:latest

# Show namespace information
podman inspect mycontainer | jq '.[0].State.Pid' | xargs ls -la /proc/{}/ns/

# Audit for dangerous mounts
podman inspect mycontainer | jq '.[0].Mounts[] | select(.Source | contains("docker.sock") or contains("podman.sock"))'

# Check for privileged containers
podman ps -a --format '{{.Names}} {{.ID}}' | while read name id; do
    priv=$(podman inspect $id --format '{{.HostConfig.Privileged}}')
    [ "$priv" = "true" ] && echo "PRIVILEGED: $name"
done

# Show seccomp profiles in use
podman inspect mycontainer | jq '.[0].HostConfig.SecurityOpt'

Summary

Containers are a composition of Linux kernel features, not virtualization:

Container = namespaces (visibility) + cgroups (resource limits)
            + OverlayFS (root filesystem) + OCI config (setup)

Security = capabilities (drop ALL, add needed) + seccomp (syscall filter)
            + user namespaces (rootless) + read-only rootfs
            + no-new-privileges + AppArmor/SELinux profile

Each feature addresses a specific isolation or security concern.
Disabling any one weakens the entire model.
--privileged disables them all.

The Virtualization article covers the next level of isolation - running entire guest operating systems with hardware-enforced boundaries.

Challenge

Write a Go tool that enumerates namespace inodes across all running processes and counts how many processes share each namespace. This is the same view podman and nsenter rely on when they decide which namespaces to join: 

package main

import (
	"fmt"
	"os"
	"path/filepath"
	"sort"
	"strings"
)

func main() {
	entries, err := filepath.Glob("/proc/[0-9]*/ns/*")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	counts := make(map[string]int)
	for _, entry := range entries {
		target, err := os.Readlink(entry)
		if err != nil {
			continue
		}
		key := filepath.Base(entry) + ":" + target
		counts[key]++
	}

	keys := make([]string, 0, len(counts))
	for key := range counts {
		keys = append(keys, key)
	}
	sort.Strings(keys)

	for _, key := range keys {
		parts := strings.SplitN(key, ":", 2)
		fmt.Printf("%-6s %-28s %d proc(s)\n", parts[0], parts[1], counts[key])
	}
}

Run it on the host, note the inode for the mnt namespace, then start a container with podman run -d alpine sleep 3600 and run the tool again. New inode numbers appear for the container's mount, PID, and network namespaces. Extend the tool to read /proc/PID/cgroup and report which cgroup each process belongs to.
