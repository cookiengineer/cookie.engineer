EDR

Endpoint Detection and Response fundamentals covering architecture, detection capabilities, evasion, and testing with Atomic Red Team.

Overview

An EDR agent records what processes do, not just what files exist on disk. This article covers the kernel callbacks and userland hooks that produce endpoint telemetry, the injection and credential-access patterns an EDR detects, the evasion techniques that test its coverage, and the Atomic Red Team workflow for measuring detection. After reading, you can map telemetry to MITRE ATT&CK techniques and run repeatable detection tests.

Why EDR

Antivirus checks files for known-bad signatures. EDR monitors behavior - what processes actually do after they execute. An EDR doesn't care if the binary is signed by Microsoft. It cares that winword.exe spawned cmd.exe , which ran powershell -enc ... , which attempted to open a handle to lsass.exe with PROCESS_VM_READ . That chain is malicious regardless of signature status.

Kernel Callbacks

EDR drivers register callback routines with the Windows kernel. These fire on specific events before the operation completes.

Callback API Event Detection Use
PsSetCreateProcessNotifyRoutine Process creation / termination Process lineage tracking
PsSetCreateThreadNotifyRoutine Thread creation / termination Remote thread injection
PsSetLoadImageNotifyRoutine DLL / EXE loaded into memory Reflective DLL injection
ObRegisterCallbacks Handle open / duplicate LSASS handle access (credential dumping)
CmRegisterCallback Registry read / write / create Persistence mechanism detection
FltRegisterFilter Minifilter: file I/O Ransomware (mass file writes), file-less malware
IoRegisterShutdownNotification System shutdown Log tampering, anti-forensics

Userland Hooks

Many EDR s hook ntdll.dll functions to intercept syscalls before they transition to kernel mode. Common hooked functions: 

ntdll!NtAllocateVirtualMemory  → detects process hollowing
ntdll!NtWriteVirtualMemory     → detects cross-process memory writes
ntdll!NtCreateThreadEx         → detects remote thread creation
ntdll!NtOpenProcess            → detects handle acquisition
ntdll!NtReadVirtualMemory      → detects credential dumping
ntdll!NtProtectVirtualMemory   → detects memory region permission changes (RWX)
ntdll!NtQueueApcThread         → detects APC injection
ntdll!NtSetContextThread       → detects thread hijacking

ETW (Event Tracing for Windows)

ETW provides kernel-level tracing that EDR s consume. Key providers: 

Microsoft-Windows-Kernel-Process  → process/thread events
Microsoft-Windows-Kernel-File     → file I/O
Microsoft-Windows-Kernel-Network  → TCP/UDP events
Microsoft-Windows-Kernel-Registry → registry operations
Microsoft-Windows-Threat-Intelligence → ETW-TI (new, anti-tampering)
Microsoft-Windows-DotNETRuntime   → .NET assembly loads

Detection Capabilities

Process Injection Detection

// Indicators EDRs look for:

// 1. VirtualAllocEx + WriteProcessMemory + CreateRemoteThread
// Classic process injection pattern

// 2. NtCreateSection + NtMapViewOfSection (shared section, not backed by file)
// Process hollowing / Doppelganging

// 3. NtSetContextThread on suspended thread
// Thread hijacking

// 4. NtQueueApcThread targeting alertable thread
// APC injection

// 5. NtCreateThreadEx with non-zero start address
// Direct remote thread creation

Event correlation example (Sysmon Event IDs):

Event ID 8  (CreateRemoteThread)    → remote thread created
Event ID 7  (ImageLoad)             → DLL loaded into target
Event ID 10 (ProcessAccess)         → handle opened with VM_WRITE/VM_OPERATION

LSASS Access (Credential Dumping)

// Detection pattern: non-LSA process opens LSASS with sensitive access rights
// GrantedAccess values:
// 0x1010 = PROCESS_VM_READ | PROCESS_QUERY_INFORMATION   → Mimikatz sekurlsa::logonpasswords
// 0x1410 = + PROCESS_DUP_HANDLE                          → Handle duplication
// 0x143A = + PROCESS_VM_WRITE | PROCESS_VM_OPERATION     → Full memory manipulation
// 0x1F0FFF = PROCESS_ALL_ACCESS                          → Procdump, comsvcs.dll
// 0x1FFFFF = + PROCESS_QUERY_LIMITED_INFORMATION

// Legitimate callers of LSASS:
// - svchost.exe (Service Control Manager)
// - csrss.exe (Client/Server Runtime)
// - wininit.exe (Windows Initialization)
// - winlogon.exe (Windows Logon)
// - lsass.exe itself (self-access)

// Everything else should trigger an alert.

Service Creation (Persistence)

Detection: Event ID 7045 (Service Control Manager) / Sysmon Event ID 16

Key indicators of malicious service creation:
- Binary path in user-writable directory (C:\Users\*, C:\ProgramData\*)
- Service name matches regex ^[A-Za-z0-9]{8,12}$ (PsExec pattern)
- Service type: SERVICE_WIN32_OWN_PROCESS with StartType: AUTOMATIC
- Binary not signed by Microsoft
- Service DLL loaded from non-system path

Scheduled Task Creation (Persistence)

Detection: Sysmon Event ID 1 with parent taskschd.msc or schtasks.exe

Patterns:
- Task path contains GUID or random string
- Action: executing from %APPDATA%, %TEMP%, or %PUBLIC%
- Trigger: At logon, At startup, On idle
- Privilege: HighestAvailable
- Author: not a known administrator

EDR Evasion Concepts

Understanding evasion is essential for evaluating whether your EDR is working.

Unhooking ntdll.dll

EDR s place inline hooks (JMP instructions) at the start of ntdll.dll functions. An attacker can reload a clean copy of ntdll.dll from disk and overwrite the hooked version in memory. 

// Evasion: reload clean ntdll.dll from known-good copy
HANDLE hFile = CreateFileA("C:\\Windows\\System32\\ntdll.dll", ...);
HANDLE hSection = NULL;
NtCreateSection(&hSection, SECTION_MAP_READ, ...);
// Map fresh copy, then overwrite .text section of loaded ntdll.dll

Detection countermeasure: EDR s should monitor for NtMapViewOfSection mapping ntdll.dll over an existing ntdll.dll mapping. ETW-TI (Threat Intelligence provider) makes this harder to bypass.

Direct Syscall Invocation

Instead of calling NtAllocateVirtualMemory through ntdll.dll (which passes through hooks), the attacker copies the syscall stub from ntdll and executes it directly. 

// Evasion: invoke syscall directly, bypassing ntdll hooks
__asm {
    mov r10, rcx
    mov eax, SSN_NtAllocateVirtualMemory  // syscall number
    syscall
    ret
}

Detection countermeasure: kernel callbacks ( PsSetCreateProcessNotifyRoutine ) fire regardless of how the syscall was invoked. ETW-TI can detect direct syscalls by monitoring the instruction pointer at syscall entry.

Process Hollowing

1. CreateProcess(..., CREATE_SUSPENDED, ...) — create legitimate process in suspended state
2. NtUnmapViewOfSection — unmap legitimate process's memory
3. NtAllocateVirtualMemory — allocate memory in target
4. NtWriteVirtualMemory — write malicious code into target
5. SetThreadContext — point entry point to malicious code
6. ResumeThread — execute

Detection: step 1 creates a process with a suspended thread; step 2 unmaps the legitimate PE; step 6 resumes. The pattern CreateProcess(SUSPENDED) -> NtUnmapViewOfSection -> ResumeThread is highly suspicious.

Open-Source EDR Comparison

Solution Architecture Strengths Weaknesses
Wazuh Agent (C) + Manager + Elastic FIM, rootcheck, compliance, active response Weak on memory-based detection, limited kernel telemetry
Elastic Defend(formerly Endgame) eBPF (Linux) / Kernel driver (Win) + Elastic Agent Kernel callbacks, process/network/file events, YARA, behavioral rules Resource-intensive if misconfigured
Microsoft Defender for Endpoint(MDE) Kernel driver + ETW + AMSI Deep Windows integration, ETW-TI, AIR (Automated Investigation & Response) Closed-source, Windows-only, requires licensing

Telemetry Sources Comparison

Source Type Data Gap
EDR kernel driver Push Process, thread, handle, image load, registry Vendor-specific, may miss syscall-stub bypass
Sysmon Push Process, network, image load, registry, WMI, DNS No memory scanning, userspace only
osquery Pull / Scheduled State queries, file metadata, network Interval-based gaps, no real-time event stream
ETW Push Kernel process/network/file/registry events Can be tampered with by attackers with admin
auditd (Linux) Push Syscall-level events, custom rules No memory-based detection, noisy without tuning

Best practice: deploy EDR + Sysmon + ETW logs. If the attacker evades one layer, the others provide coverage.

Response Capabilities

EDR s provide immediate containment actions. Test these in a lab before production. 

Process kill        — terminates malicious process by PID
Network isolate     — blocks all network traffic except to EDR cloud
File quarantine     — moves or deletes file, retains copy for analysis
Registry rollback   — reverts registry changes
Service stop/disable — stops malicious services
Wipe and re-image   — remote-initiated OS reinstallation

Evaluating EDR Effectiveness

Test matrix for evaluating any EDR product: 

1. Process Injection
   □ Classic CreateRemoteThread
   □ Process Hollowing
   □ APC Injection
   □ AtomBombing
   □ Process Doppelganging

2. Credential Access
   □ procdump.exe -accepteula -ma lsass.exe
   □ comsvcs.dll MiniDump
   □ Mimikatz sekurlsa::logonpasswords
   □ /etc/shadow read by non-root
   □ memory scraping via /proc/pid/mem

3. Persistence
   □ Registry Run key modification
   □ Scheduled task creation
   □ WMI event subscription
   □ Service creation
   □ crontab modification

4. Defense Evasion
   □ NTFS ADS (Alternate Data Streams)
   □ Timestomping (file time manipulation)
   □ Signed binary proxy execution (LOLBAS)
   □ Syscall direct invocation

5. Command and Control
   □ DNS beaconing
   □ HTTPS with custom certificate
   □ ICMP tunneling
   □ WebSocket-based C2

Challenge

Write a Go tool that reads Sysmon-style process-access records from standard input as CSV ( event_id,source_image,target_image,granted_access ) and flags every access to lsass.exe that requests memory-read or all-access rights. Sysmon Event ID 10 is the source of these records, and the granted-access values are the ones listed in this article. Feed it a mixed stream of legitimate and suspicious access events and check that only the suspicious ones alert. 

package main

import (
	"encoding/csv"
	"fmt"
	"os"
	"strconv"
	"strings"
)

var sensitive = map[uint32]string{
	0x1010:   "VM_READ | QUERY_INFORMATION",
	0x1410:   "VM_READ | QUERY_INFORMATION | DUP_HANDLE",
	0x143a:   "VM_READ | VM_WRITE | VM_OPERATION | QUERY_INFORMATION",
	0x1f0fff: "PROCESS_ALL_ACCESS",
	0x1fffff: "PROCESS_ALL_ACCESS | QUERY_LIMITED_INFORMATION",
}

func main() {
	reader := csv.NewReader(os.Stdin)
	reader.FieldsPerRecord = -1

	for {
		record, err := reader.Read()
		if err != nil {
			break
		}
		if len(record) < 4 || record[0] != "10" {
			continue
		}
		if !strings.EqualFold(record[2], "lsass.exe") {
			continue
		}

		value, err := strconv.ParseUint(strings.TrimPrefix(record[3], "0x"), 16, 32)
		if err != nil {
			continue
		}

		mask, ok := sensitive[uint32(value)]
		if !ok {
			continue
		}

		fmt.Printf("ALERT %s opened lsass.exe with %s (%s)\n", record[1], record[3], mask)
	}
}
						
go build -o lsass-watch lsass-watch.go

printf '10,powershell.exe,lsass.exe,0x1410\n10,svchost.exe,lsass.exe,0x1000\n' | ./lsass-watch
# ALERT powershell.exe opened lsass.exe with 0x1410 (VM_READ | QUERY_INFORMATION | DUP_HANDLE)
