Cryptography

Symmetric and asymmetric encryption, hash functions, HMAC , digital signatures, TLS , and randomness on Linux.

Overview

Cryptography is the mathematics of securing information. This article covers the fundamental primitives: symmetric and asymmetric encryption, hash functions, message authentication, digital signatures, key exchange, and randomness. Those primitives are combined to build protocols like TLS , SSH , and GPG. Each primitive has exactly one job, and using the wrong primitive - or combining them incorrectly - produces broken security. After reading, you can pick the right primitive for a problem and spot the common ways that choices go wrong.

Required Reading

  • Public Key Cryptography - RSA , ECC, and how keypairs relate
  • Password Hashing - KDFs, bcrypt, and Argon2
  • TLS - the protocol built from these primitives

Cryptographic Primitives

Primitive Purpose Input -> Output Reversible?
Symmetric encryption Confidentiality Plaintext + Key -> Ciphertext Yes (decrypt)
Asymmetric encryption Confidentiality (no shared secret) Plaintext + PublicKey -> Ciphertext Yes (decrypt with PrivateKey)
Cryptographic hash Integrity, fingerprint Arbitrary data -> Fixed-size digest No
HMAC / MAC Integrity + authenticity Message + Key -> Tag No (verification only)
Digital signature Authenticity + non-repudiation Message + PrivateKey -> Signature No (verify with PublicKey)
Key exchange Establish shared secret Private + Peer's Public -> Shared N/A (agreement)
CSPRNG Unpredictable bits Seed -> Random stream No

Symmetric Encryption

One key encrypts and decrypts. Both parties must possess the same key. This is the workhorse of data encryption: fast, suitable for bulk data.

AES

AES is a block cipher operating on 128-bit (16-byte) blocks. The key determines the number of transformation rounds:

Key Size Rounds Security Level
AES-128 10 128-bit security
AES-192 12 192-bit security
AES-256 14 256-bit security

Internally, each round consists of four operations:

  1. SubBytes - Nonlinear byte substitution (S-box lookup)
  2. ShiftRows - Cyclic shift of rows in the 4x4 state matrix
  3. MixColumns - Linear mixing of columns (omitted in final round)
  4. AddRoundKey - XOR with round key

The key schedule expands the cipher key into a set of round keys (one per round plus initial). AES -256 with 14 rounds and a 256-bit key is considered secure against all known classical attacks. Quantum attacks using Grover's algorithm reduce effective security to 128 bits, which remains infeasible.

Block Cipher Modes

A block cipher alone can only encrypt exactly one 16-byte block. Modes of operation extend it to arbitrary-length messages.

ECB (Electronic Codebook) - DO NOT USE: 

C_i = AES_K(P_i)

Each plaintext block P_i is independently encrypted.
Identical plaintext blocks -> identical ciphertext blocks.

This leaks patterns in the data. The classic "ECB penguin" demonstrates this vividly.

# ECB demonstration - the penguin problem
openssl enc -aes-256-ecb -in tux.bmp -out tux-ecb.bmp -K $(xxd -p -c32 key.bin)
# Compare the original BMP with the ECB-encrypted one.
# The penguin shape is still clearly visible because identical
# pixel regions produce identical ciphertext blocks.

CBC (Cipher Block Chaining) : 

C_0 = IV (Initialization Vector, random, sent with ciphertext)
C_i = AES_K(P_i XOR C_{i-1})

Each plaintext block is XORed with the previous ciphertext block before encryption. The IV must be unpredictable (random) for CBC . A predictable IV enables the BEAST attack. Decryption: P_i = AES_K^{-1}(C_i) XOR C_{i-1} . Note that decryption is parallelizable (each block depends only on C_i and C_{i-1}) but encryption is sequential.

CBC with a fixed/absent IV or without authentication is vulnerable to padding oracle attacks.

CTR (Counter Mode) : 

counter_i = nonce || i  (nonce + incrementing counter)
keystream_i = AES_K(counter_i)
C_i = P_i XOR keystream_i

CTR turns a block cipher into a stream cipher. Encryption and decryption are identical operations (XOR with keystream). Both are fully parallelizable. The counter must never repeat under the same key (nonce reuse is catastrophic - it XORs two plaintexts together). CTR requires no padding.

GCM (Galois/Counter Mode) :

GCM combines CTR mode for confidentiality with G MAC (Galois Message Authentication Code) for authenticity. It provides AEAD (Authenticated Encryption with Associated Data): the ciphertext is both encrypted and authenticated, preventing tampering. 

GCM-Encrypt(K, IV, P, A):
    C = CTR-Encrypt(K, IV, P)
    T = GHASH(H, A, C) XOR AES_K(IV || 0^31 1)
    return (C, T)  // ciphertext + authentication tag

GCM-Decrypt(K, IV, C, A, T):
    T' = GHASH(H, A, C) XOR AES_K(IV || 0^31 1)
    if T != T': FAIL  // authentication failure - DO NOT return plaintext
    P = CTR-Decrypt(K, IV, C)
    return P

Critical: if the authentication tag fails verification, the implementation must release no plaintext. Returning unauthenticated plaintext completely defeats AEAD.

ChaCha20-Poly1305

A modern stream cipher + MAC combination, designed for software performance (no AES -NI required) and resistance to timing side channels: 

ChaCha20: 256-bit key, 96-bit nonce, 32-bit counter
Internal state: 4x4 matrix of 32-bit words
Quarter-round operation: 4 additions, 4 XORs, 4 rotations per quarter-round
20 rounds total (10 double rounds)

Poly1305: one-time authenticator producing a 16-byte tag
Its (r, s) key material is the first 32 bytes of the ChaCha20 keystream
Tag = (poly1305(r, msg) + s) mod 2^128

OpenSSL Symmetric

openssl enc only supports the classic block-cipher modes. The AEAD modes such as GCM and ChaCha20-Poly1305 are not available through enc ; use a library (see the Challenge) for those. 

# AES-256-CBC encryption (authenticate the result separately with HMAC)
openssl enc -aes-256-cbc \
    -in secret.txt -out secret.enc \
    -K $(xxd -p -c32 key.bin) \
    -iv $(xxd -p -c16 iv.bin)

# AES-256-CBC decryption
openssl enc -d -aes-256-cbc \
    -in secret.enc -out secret.txt \
    -K $(xxd -p -c32 key.bin) \
    -iv $(xxd -p -c16 iv.bin)

# AES-256-CTR is a stream mode, no padding
openssl enc -aes-256-ctr \
    -in secret.txt -out secret.enc \
    -K $(xxd -p -c32 key.bin) \
    -iv $(xxd -p -c16 iv.bin)

# Derive a key from a password (PBKDF2)
openssl enc -aes-256-cbc -pbkdf2 -iter 100000 \
    -in secret.txt -out secret.enc
# Prompts for password; uses PBKDF2 with 100k iterations to derive key.

Asymmetric Encryption

Uses mathematically related key pairs: a public key for encryption, a private key for decryption. Eliminates the key distribution problem of symmetric encryption at the cost of being thousands of times slower.

RSA

RSA (Rivest-Shamir-Adleman) security relies on the difficulty of factoring the product of two large primes.

Key Generation : 

1. Choose two large primes p, q (random, similar size)
2. n = p * q                         (modulus, part of both keys)
3. phi(n) = (p-1) * (q-1)            (Euler's totient)
4. Choose e: 1 < e < phi(n), gcd(e, phi(n)) = 1
   Common: e = 65537 (0x10001)
5. d = e^-1 mod phi(n)               (modular multiplicative inverse)
6. Public key: (n, e)
7. Private key: (n, d)

Encryption : 

c = m^e mod n          (m must be < n)

Decryption : 

m = c^d mod n

Why this works, by Euler's theorem:

c^d = (m^e)^d = m^(ed) = m^(k*phi(n)+1) = (m^phi(n))^k * m = 1^k * m = m (mod n)

RSA Key Sizes

Key Size Security (bits) Status
1024 ~80 Broken - do not use
2048 ~112 Minimum acceptable
3072 ~128 Good
4096 ~140+ Conservative choice

NIST SP 800-57 recommends 2048 bits through 2030, 3072 beyond. Given the increasing power of factorization, 4096 provides margin. However, for most applications, ECC with 256-bit keys provides equivalent or greater security.

RSA with OpenSSL

# Generate RSA 4096 private key
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 \
    -out rsa_private.pem

# Generate RSA 4096 (traditional method)
openssl genrsa -out rsa_private.pem 4096

# Extract public key
openssl rsa -in rsa_private.pem -pubout -out rsa_public.pem

# Inspect RSA key
openssl rsa -in rsa_private.pem -text -noout
# Shows n (modulus), e (public exponent), d (private exponent), p, q, etc.

# Encrypt with RSA OAEP (limited to key_size/8 - padding bytes)
openssl pkeyutl -encrypt -pubin -inkey rsa_public.pem \
    -pkeyopt rsa_padding_mode:oaep \
    -in small_message.txt -out encrypted.bin

# Decrypt
openssl pkeyutl -decrypt -inkey rsa_private.pem \
    -pkeyopt rsa_padding_mode:oaep \
    -in encrypted.bin -out decrypted.txt

Diffie-Hellman

Allows two parties to agree on a shared secret over an insecure channel, even if an eavesdropper observes all messages.

Classic DH

Public parameters: large prime p, generator g (primitive root mod p)

Alice:                            Bob:
a = random(1, p-1)                b = random(1, p-1)
A = g^a mod p                     B = g^b mod p
         ---- A --->
         <--- B ----
shared = B^a mod p               shared = A^b mod p
       = (g^b)^a = g^(ab)              = (g^a)^b = g^(ab)

An eavesdropper sees g, p, A=g^a, B=g^b. Computing g^(ab) from this is the Computational Diffie-Hellman problem, believed as hard as the Discrete Logarithm Problem (given g and g^x, find x). No efficient classical algorithm is known for sufficiently large groups.

ECDH

Same concept, but using elliptic curve groups instead of integers modulo p. The Public Key Cryptography article covers the mathematics. 

# Generate ECDH parameters
openssl ecparam -name prime256v1 -out ecdh_params.pem

# Alice generates keypair
openssl ecparam -in ecdh_params.pem -genkey -out alice_key.pem

# Bob generates keypair
openssl ecparam -in ecdh_params.pem -genkey -out bob_key.pem

# Extract public keys
openssl ec -in alice_key.pem -pubout -out alice_pub.pem
openssl ec -in bob_key.pem -pubout -out bob_pub.pem

# Alice derives shared secret (using Bob's public key)
openssl pkeyutl -derive -inkey alice_key.pem \
    -peerkey bob_pub.pem -out alice_shared.bin

# Bob derives shared secret (using Alice's public key)
openssl pkeyutl -derive -inkey bob_key.pem \
    -peerkey alice_pub.pem -out bob_shared.bin

# They match
diff alice_shared.bin bob_shared.bin && echo "Shared secrets match"

DH Security

  • p should be at least 2048 bits (3072 recommended)
  • Safe prime: p = 2q+1 where q is also prime (resists small subgroup attacks)
  • g should be a generator of the subgroup of order q
  • Ephemeral keys: a, b must be fresh for each exchange. Key reuse enables attacks.
  • Validate public keys: reject A=0, A=1, A=p-1 (small subgroup confinement)

Hash Functions

A cryptographic hash function H maps arbitrary input to a fixed-size output (digest). Required properties:

  1. Preimage resistance : Given h, infeasible to find m such that H(m) = h
  2. Second preimage resistance : Given m1, infeasible to find m2 such that H(m1) = H(m2)
  3. Collision resistance : Infeasible to find any m1 != m2 such that H(m1) = H(m2)

Hash Comparison

Algorithm Output (bits) Rounds Status
MD5 128 64 Broken(collisions in seconds)
SHA-1 160 80 Broken(SHAttered, 2017)
SHA-256 256 64 Secure(part of SHA-2 family)
SHA-512 512 80 Secure
SHA-3-256 256 24 Secure(Keccak, different construction)
BLAKE3 256 (extendable) 7 Secure(newer, faster)

Merkle-Damgard

Message -> Pad to multiple of block size -> Split into blocks M_1 ... M_n
IV = fixed initial value
H_0 = IV
for i = 1 to n:
    H_i = Compression(H_{i-1}, M_i)
Digest = H_n

The compression function iterates over the block using bitwise operations
(majority, choose), rotations, and modular addition.

SHA-3 uses a fundamentally different sponge construction (Keccak) that absorbs input and then squeezes output, making it resistant to length extension attacks that affect SHA-2.

Hashing in Practice

# Compute SHA-256
sha256sum file.txt
openssl dgst -sha256 file.txt

# Compute SHA-512
sha512sum file.txt
openssl dgst -sha512 file.txt

# Compute BLAKE3 (install via cargo/pacman)
b3sum file.txt

# Stream-based hashing (piping)
cat /dev/urandom | head -c 1G | sha256sum

# HMAC (keyed hash)
openssl dgst -sha256 -hmac "secret_key" file.txt
echo -n "message" | openssl dgst -sha256 -hmac "secret_key"

# Verify file integrity (with known hash)
echo "abc123... file.txt" | sha256sum -c

Length extension attack on SHA-256 (why HMAC exists): 

Given H(secret || message), an attacker who knows len(secret) can compute
H(secret || message || padding || attacker_data) without knowing secret.

SHA-256 internally:
H_n = Compression(..., last_block)
The final H_n IS the hash output. It's also the internal state.

Attacker:
1. Know H(secret || message) = H_final
2. Set internal state to H_final
3. Continue hashing with attacker_data
4. Result: H(secret || message || original_padding || attacker_data)

This is valid without knowing secret! HMAC prevents this with
H(K XOR opad || H(K XOR ipad || message)), double-hashing breaking the chain.

HMAC

HMAC provides message integrity and authenticity using a shared secret: 

HMAC(K, m) = H( (K XOR opad) || H( (K XOR ipad) || m ) )

ipad = 0x36 repeated (inner padding)
opad = 0x5C repeated (outer padding)

If K > block size: K = H(K) (hash it first)
If K < block size: pad with zeros

HMAC -SHA256 produces a 256-bit authentication tag. An attacker who modifies the message cannot produce a valid tag without knowing K. Replay attacks are still possible - HMAC authenticates the message, not the freshness. Nonces/timestamps handle replay. 

# HMAC-SHA256
echo -n "data to authenticate" | openssl dgst -sha256 -hmac "the_secret_key"

# With hex key
KEY_HEX=$(echo -n "the_secret_key" | xxd -p)
echo -n "data" | openssl dgst -sha256 -mac HMAC -macopt hexkey:$KEY_HEX

# Verify HMAC (constant-time comparison)
python3 -c "
import hmac, sys
expected = sys.argv[1]
actual = sys.argv[2]
print('VALID' if hmac.compare_digest(expected, actual) else 'INVALID')
"

Digital Signatures

Digital signatures provide authenticity, integrity, and non-repudiation. Only the holder of the private key can create a valid signature. Anyone with the public key can verify it.

A digital signature scheme consists of three algorithms:

KeyGen() -> (sk, pk)        - generate keypair
Sign(sk, m) -> sigma        - produce signature
Verify(pk, m, sigma) -> {0,1}  - validate signature

ECDSA

Sign(sk=d, m):
    1. z = H(m) (truncated to curve order bit length)
    2. k = random(1, n-1)  <- THIS MUST BE UNIQUE PER SIGNATURE
    3. (x_1, y_1) = k * G
    4. r = x_1 mod n; if r = 0, go to step 2
    5. s = k^-1(z + r*d) mod n; if s = 0, go to step 2
    6. Signature = (r, s)

Verify(pk=Q, m, sigma=(r,s)):
    1. z = H(m)
    2. u_1 = z*s^-1 mod n
    3. u_2 = r*s^-1 mod n
    4. (x_1, y_1) = u_1*G + u_2*Q
    5. Valid if r = x_1 (mod n)

Critical: k must be a cryptographically random, unique nonce per signature. If k is reused, the private key is trivially recovered. If k is biased or predictable, the private key can be recovered via lattice attacks. This is exactly how the Sony PlayStation 3 ECDSA key was broken in 2010 - the implementation reused a constant nonce.

EdDSA and Ed25519

Ed25519 is a deterministic Schnorr-like signature scheme over Curve25519. It removes the nonce-generation pitfall of ECDSA by deriving the nonce deterministically from the private key and message hash: 

Sign(sk, m):
    1. h = SHA-512(sk)
    2. a = h[0:32] (clamped)  - private scalar
    3. prefix = h[32:64]      - nonce derivation material
    4. A = a*B               - public key (B = base point)
    5. r = SHA-512(prefix || m) mod l  - deterministic nonce
    6. R = r*B
    7. S = r + SHA-512(R || A || m)*a mod l
    8. Signature = (R, S) - 64 bytes

Verify(pk=A, m, sigma=(R,S)):
    1. h = SHA-512(R || A || m) mod l
    2. Check: S*B = R + h*A
    S*B = (r + h*a)*B = r*B + h*a*B = R + h*A

Ed25519 advantages over ECDSA:

  • Deterministic (no entropy required for signing)
  • Constant-time (resists timing side channels)
  • Small signatures (64 bytes vs 70-72 for ECDSA)
  • Fast verification
  • No cofactor issues (cofactor is cleared via clamping)
# Sign with Ed25519 (using SSH keypair)
openssl pkeyutl -sign -inkey ed25519_private.pem \
    -in message.txt -out signature.bin

# Verify
openssl pkeyutl -verify -pubin -inkey ed25519_public.pem \
    -sigfile signature.bin -in message.txt

# Sign and verify with GPG
gpg --sign --armor message.txt          # creates message.txt.asc
gpg --verify message.txt.asc            # verifies signature
gpg --detach-sign --armor message.txt   # creates message.txt.sig
gpg --verify message.txt.sig message.txt # verifies detached sig

TLS

TLS (Transport Layer Security) combines all the primitives above into a single protocol: 

TLS 1.3 Handshake:

Client                                  Server
  |                                       |
  |--- ClientHello --------------------->|
  |    (supported ciphers, key_share,     |
  |     random, session_id)               |
  |                                       |
  |<-- ServerHello ---------------------  |
  |    (chosen cipher, key_share, random)  |
  |    EncryptedExtensions                |
  |    Certificate                        |
  |    CertificateVerify                  |
  |    Finished                           |
  |                                       |
  |--- Finished ------------------------>|
  |                                       |
  |<== Encrypted Application Data =======>|

How keys are derived:
1. ECDHE: client_key_share + server_key_share -> shared_secret
   No single party chooses the key; both contribute randomness.

2. HKDF-Extract(shared_secret, 0s) -> early_secret
3. HKDF-Expand-Label(early_secret, "derived", "", hash_len) -> derived_secret
4. HKDF-Extract(derived_secret, 0s) -> handshake_secret
5. From handshake_secret, derive:
   - client_handshake_traffic_secret  (encrypts Finished, Certificate, etc.)
   - server_handshake_traffic_secret
6. HKDF-Expand-Label(handshake_secret, "derived", "", hash_len) -> derived
7. HKDF-Extract(derived, 0s) -> master_secret
8. From master_secret, derive:
   - client_application_traffic_secret
   - server_application_traffic_secret
9. Application data encrypted with AES-256-GCM or ChaCha20-Poly1305

Forward secrecy: Compromise of the server's long-term certificate key
does NOT compromise past sessions, because the ECDHE shared secret
is ephemeral and discarded after the session.

TLS 1.3 removed RSA key exchange (no forward secrecy), static DH, CBC mode ciphers, RC4, MD5, SHA-1 signatures, and a full round trip from the handshake. The entire handshake completes in 1- RTT (or 0- RTT with PSK).

Randomness

Cryptography depends fundamentally on unpredictable random numbers. A compromised random number generator (RNG) breaks everything built on top of it.

Entropy Sources

/dev/random - blocks until sufficient entropy is available (legacy, now same as urandom)
/dev/urandom - never blocks (modern: ChaCha20-based CSPRNG, reseeded from entropy pool)
getrandom() - syscall, blocks until CRNG is initialized (recommended for early boot)
getentropy() - glibc wrapper, max 256 bytes

The kernel entropy pool:
- Input sources: interrupt timing, disk I/O timing, mouse/keyboard, RDRAND/RDSEED
- Pool mixing: ChaCha20-based CRNG since Linux 4.8
- Reseeding: CRNG is reseeded regularly from the input pool
- Boot: Saved entropy seed from previous shutdown prevents boot-time entropy drought

Generating Random Data

# 32 random bytes (hex)
openssl rand -hex 32

# 32 random bytes (base64)
openssl rand -base64 32

# Generate a random password
tr -dc 'A-Za-z0-9!@#$%^&*()_+' < /dev/urandom | head -c 24; echo

# Generate a random 256-bit key
dd if=/dev/urandom bs=32 count=1 2>/dev/null | xxd -p

# Test randomness (ent package)
pacman -S ent
head -c 1M /dev/urandom | ent
# Chi-square, entropy (bits/byte), compression ratio, Monte Carlo pi, serial correlation

CSPRNG Requirements

A Cryptographically Secure Pseudo-Random Number Generator must:

  1. Pass statistical randomness tests (dieharder, TestU01)
  2. Be backtracking-resistant (knowing current state does not reveal previous outputs)
  3. Be prediction-resistant (knowing past outputs does not reveal future ones)
  4. Reseed from true entropy sources regularly

Never use rand() , random() , or Math.random() for cryptographic purposes. On Linux, always use /dev/urandom or getrandom(2) . 

// Correct random bytes in C
#include <sys/random.h>

uint8_t key[32];
if (getrandom(key, sizeof(key), 0) != sizeof(key)) {
    perror("getrandom");
    exit(1);
}
						
# Correct random bytes in Python
import secrets
key = secrets.token_bytes(32)
password = secrets.token_urlsafe(32)

Common Pitfalls

Pitfall Why It Fails Correct Approach
ECB mode Identical plaintext -> identical ciphertext Use GCM or CTR
CBC without MAC Padding oracle attacks Use AEAD (GCM, ChaCha20-Poly1305)
Fixed IV/nonce Reveals patterns, enables key recovery Generate fresh random IV per encryption
Nonce reuse in CTR/GCM XORs two plaintexts, breaks auth Incrementing counter, never repeat
Nonce reuse in ECDSA Private key recovery Use Ed25519 (deterministic)
rand()for keys Predictable (LFSR with known seed) Use CSPRNG (/dev/urandom)
AES-ECB as "password hashing" Reversible, not a hash function Use Argon2/bcrypt
Hardcoded keys Extracted by reverse engineering Key management (HSM, KMS, env vars)
Weak DH parameters (512/1024 bit) Discrete log feasible (Logjam) Minimum 2048-bit (3072 recommended)
RSA PKCS#1 v1.5 padding Bleichenbacher attack (adaptive chosen ciphertext) Use OAEP padding

# Check supported TLS ciphers on a server

# Test SSH host key fingerprint

# Verify GPG signature on a file

# "-----BEGIN ENCRYPTED PRIVATE KEY-----" = encrypted
# "-----BEGIN PRIVATE KEY-----" = unencrypted

Summary

Every cryptographic protocol is a composition of primitives, each doing exactly one job:

Confidentiality -> AES-GCM, ChaCha20-Poly1305 (symmetric)
Integrity       -> SHA-256, SHA-3, BLAKE3 (hashing)
Authentication  -> HMAC (symmetric), Ed25519/ECDSA (asymmetric)
Key Exchange    -> ECDHE over Curve25519/P-256
Randomness      -> getrandom(2), /dev/urandom
Identity        -> X.509 certificates, GPG keys (binding keys to identities)

Understanding these primitives in isolation is essential. Understanding how they compose - where the assumptions of one are violated by another - is where real cryptographic engineering lives. The Password Hashing article covers KDFs. The Public Key Cryptography article deepens the asymmetric side.

Challenge

Write a Go program that performs authenticated encryption with AES -256-GCM and verifies an HMAC in constant time. This is the composition the article describes: encrypt with an AEAD, authenticate separately when you need it, and never compare secrets with == : 

package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/hmac"
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

func main() {
	key := make([]byte, 32) // AES-256
	if _, err := rand.Read(key); err != nil {
		panic(err)
	}

	block, err := aes.NewCipher(key)
	if err != nil {
		panic(err)
	}

	gcm, err := cipher.NewGCM(block)
	if err != nil {
		panic(err)
	}

	nonce := make([]byte, gcm.NonceSize())
	if _, err := rand.Read(nonce); err != nil {
		panic(err)
	}

	plaintext := []byte("attack at dawn")
	sealed := gcm.Seal(nonce, nonce, plaintext, nil) // nonce || ciphertext || tag
	fmt.Println("ciphertext:", hex.EncodeToString(sealed))

	opened, err := gcm.Open(nil, sealed[:gcm.NonceSize()], sealed[gcm.NonceSize():], nil)
	if err != nil {
		panic("authentication failed")
	}
	fmt.Println("plaintext: ", string(opened))

	mac := hmac.New(sha256.New, key)
	mac.Write(plaintext)
	expected := mac.Sum(nil)

	// hmac.Equal is constant-time; 'expected == got' is not.
	fmt.Println("hmac ok:  ", hmac.Equal(expected, expected))
}

Run it, then deliberately flip one byte of sealed before calling gcm.Open and confirm that decryption fails instead of returning corrupted plaintext. Finally, extend the program to derive the encryption key from a password with golang.org/x/crypto/argon2 and compare the salt and parameter choices with the Password Hashing article.
