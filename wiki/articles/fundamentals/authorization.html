Authorization

Access control models, Linux permissions, SELinux, AppArmor, sudo, PolKit, JWT , and OAuth 2.0

Overview

Authorization determines what a verified identity is permitted to do. Authentication answers "Who are you?"; authorization answers "Are you allowed to do this?" These are separate concerns, and conflating them leads to broken security models. A properly authenticated user should still have access governed by the principle of least privilege: grant only what is necessary. This article covers DAC , MAC , RBAC , and ABAC, the Linux permission bits and ACL s, SELinux and AppArmor, Unix capabilities, sudo, PolKit, JWT claims, and OAuth 2.0.

Required Reading

  • Authentication - establishes the identity that authorization acts upon
  • Unix Permissions - owner/group/other bits, setuid, ACL s
  • Capabilities - splitting root into fine-grained privileges

1. Access Control Models

Four fundamental models exist, each with distinct tradeoffs:

Model Decision Basis Admin Burden Flexibility Examples
DAC Resource owner Low High Unix permissions, Windows NTFS
MAC System-wide policy High Low SELinux, AppArmor
RBAC Role membership Medium Medium Database roles, AWS IAM
ABAC Attributes of all entities High Very High XACML, AWS ABAC

1.1 DAC - Discretionary Access Control

The resource owner decides who gets access. The Unix permission model is the canonical DAC implementation:

-rw-r--r--  1 alice  developers  4096 Jun 21 12:00 report.txt
- ---------  - -----  ----------- ---- ---------- ----------
|    | | |   |   |        |        |       |         |
|    | | |   |   |        |        |       |         +-- filename
|    | | |   |   |        |        |       +------------ modification time
|    | | |   |   |        |        +-------------------- size
|    | | |   |   |        +----------------------------- group
|    | | |   |   +-------------------------------------- owner
|    | | |   +------------------------------------------ link count
|    | | +---------------------------------------------- other permissions (r--)
|    | +------------------------------------------------ group permissions (r--)
|    +-------------------------------------------------- owner permissions (rw-)
+------------------------------------------------------- file type (- = regular file)

Each file has 12 permission bits represented as a 4-digit octal number:

SUID SGID Sticky  User  Group  Other
 4    2     1      4 2 1  4 2 1  4 2 1
                  r w x  r w x  r w x

Example: 4755
  4 = SUID set
  7 = rwx for owner (4+2+1)
  5 = r-x for group (4+0+1)
  5 = r-x for others (4+0+1)
Bit Octal Meaning on files Meaning on directories
SUID 4000 Execute as file owner (rarely meaningful)
SGID 2000 Execute as file group New files inherit directory group
Sticky 1000 (not used on modern systems) Only file owner can delete files
Read 4 Open and read contents List directory entries
Write 2 Modify contents Create/delete files
Execute 1 Run as program Traverse (access files inside) 
# View permissions
ls -la /etc/passwd
stat /etc/shadow

# Change permissions
chmod 644 file.txt              # rw-r--r--
chmod u+x script.sh             # add execute for user
chmod g-w file.txt              # remove write for group
chmod o= file.txt               # clear all other permissions

# Change ownership
chown alice:developers file.txt # user:group
chown :developers file.txt      # group only
chown -R alice: /home/alice     # recursive

1.2 POSIX ACLs

DAC with only owner/group/other is insufficient for complex scenarios. POSIX ACL s add named users and groups:

# Install ACL tools
pacman -S acl

# View ACLs
getfacl report.txt
# file: report.txt
# owner: alice
# group: developers
# user::rw-
# user:bob:r--
# group::r--
# group:managers:rw-
# mask::rw-
# other::r--

# Set named user ACL
setfacl -m u:bob:rw report.txt

# Set named group ACL
setfacl -m g:managers:r report.txt

# Set default ACL (inherited by new files in directory)
setfacl -m d:g:developers:rwx shared/

# Remove an ACL entry
setfacl -x u:bob report.txt

# Remove all ACLs
setfacl -b report.txt

ACL s require filesystem mount with the acl option. Modern Arch Linux enables this by default for ext4, xfs, and btrfs.

1.3 MAC - Mandatory Access Control

MAC enforces system-wide policies that even the resource owner cannot override. The two dominant implementations on Linux are SELinux (type enforcement + labels) and AppArmor (path-based profiles).

2. SELinux

SELinux implements Mandatory Access Control via the Linux Security Module (LSM) framework. Every subject (process) and object (file, socket, device) carries a security context label. The kernel enforces allowed operations based on a policy database; even root is constrained.

2.1 SELinux Context

system_u:object_r:httpd_sys_content_t:s0
  |         |              |            |
  |         |              |            +-- MLS/MCS level (s0 = sensitivity 0)
  |         |              +--------------- type (domain for processes, type for objects)
  |         +------------------------------ role (object_r for files, sysadm_r for admins)
  +---------------------------------------- user (SELinux identity, mapped to Linux user)

Labels are stored as extended attributes on the filesystem:

ls -Z /var/www/html/index.html
# -rw-r--r--. root root system_u:object_r:httpd_sys_content_t:s0 index.html

ps -eZ | grep httpd
# system_u:system_r:httpd_t:s0    1234 ?  00:00:00 httpd

id -Z
# unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023

2.2 Mode Control

# Current mode (Enforcing = policy enforced, Permissive = logged only, Disabled)
getenforce

# Temporarily set permissive (for debugging)
setenforce 0

# Re-enable enforcing
setenforce 1

# Permanent configuration
cat /etc/selinux/config
SELINUX=enforcing
SELINUXTYPE=targeted

2.3 Type Enforcement Rules

The core SELinux mechanism: processes of type A can access files of type B only if the policy explicitly allows it.

Policy rule: allow httpd_t httpd_sys_content_t : file { read open getattr };

Meaning: Processes running as httpd_t can read, open, and get attributes
         of files labeled httpd_sys_content_t.

SELinux denies by default (default-deny). Everything not explicitly allowed is denied. This is the opposite of DAC .

2.4 Policy Debugging with audit2allow

# When something is denied, it's logged to the audit log
ausearch -m avc -ts recent

# Generate human-readable explanation
ausearch -m avc -ts recent | audit2why

# Generate policy module from denials (CAREFUL: understand before applying)
ausearch -m avc -ts today | audit2allow -M my_fix
semodule -i my_fix.pp

2.5 Common SELinux Boolean Toggles

# List all booleans
getsebool -a

# Allow Apache to connect to network databases
setsebool -P httpd_can_network_connect_db on

# Allow Apache to send email
setsebool -P httpd_can_sendmail on

# Allow users to run scripts from home directories
setsebool -P httpd_enable_homedirs on

# Restore default labels after moving files
restorecon -Rv /var/www/html/

2.6 SELinux on Arch Linux

SELinux is not the default on Arch (AppArmor is preferred in the Arch ecosystem). However, installation is straightforward:

# Install SELinux packages
pacman -S selinux-policy selinux-refpolicy-src checkpolicy setools

# Add selinux=1 security=selinux to kernel command line
# Edit /etc/default/grub:
# GRUB_CMDLINE_LINUX="... selinux=1 security=selinux"
grub-mkconfig -o /boot/grub/grub.cfg

# After reboot, relabel the filesystem
touch /.autorelabel
reboot

3. AppArmor

AppArmor is the default MAC on Arch Linux, Ubuntu, and SUSE. Unlike SELinux's label-based model, AppArmor uses path-based profiles: each program has a profile listing which filesystem paths it may access and with what permissions.

3.1 AppArmor Profile Syntax

# /etc/apparmor.d/usr.bin.evince
#include <tunables/global>

/usr/bin/evince {
    #include <abstractions/base>
    #include <abstractions/fonts>
    #include <abstractions/dbus-session>
    #include <abstractions/X>

    # Read access to home directory and PDFs
    owner @{HOME}/ r,
    owner @{HOME}/Documents/** r,
    owner @{HOME}/Downloads/** r,

    # Read-only access to system fonts and libraries
    /usr/share/fonts/** r,
    /usr/lib/** mr,

    # Network access
    network inet stream,
    network inet6 stream,

    # Execute with profile transition
    /usr/bin/gvfsd px,

    # Capabilities
    capability sys_admin,
    capability dac_override,

    # Deny writes to system directories
    deny /etc/** w,
    deny /usr/** w,
}

3.2 AppArmor Modes

# Check AppArmor status
aa-status

# List loaded profiles
aa-status --profiled

# Set profile to enforce mode (policy enforced)
aa-enforce /usr/bin/evince

# Set profile to complain mode (violations logged but allowed)
aa-complain /usr/bin/evince

# Generate profile from program behavior (learning mode)
aa-genprof /usr/local/bin/myapp
# Run myapp, exercise all functionality, then scan to generate rules

3.3 Profile Components

Rule Meaning
r Read
w Write (includes create, but not delete)
a Append
m Memory map executable
k File locking
l Hard link
x Execute (with profile transition)
ux Execute unconfined (remove AppArmor restrictions)
px Execute with a specific profile
ix Execute inheriting current profile
Px Execute with cleaned environment
deny Explicit denial rule

4. Unix Capabilities

Traditional Unix has the all-or-nothing root model: either you are root (UID 0) and can do everything, or you are not. Capabilities divide root's monolithic power into distinct, independently grantable units. See the Capabilities article for the full reference.

Key capabilities:

CAP_NET_RAW          - Use raw sockets (ping without setuid)
CAP_NET_BIND_SERVICE - Bind to ports < 1024
CAP_SYS_PTRACE       - Trace arbitrary processes
CAP_SYS_ADMIN        - A "catch-all" admin capability (very powerful)
CAP_SYS_TIME         - Set system clock
CAP_DAC_OVERRIDE     - Bypass file read/write/execute permission checks
CAP_CHOWN            - Change file ownership
CAP_SETUID           - Change UID
CAP_SETGID           - Change GID
						
# Check capabilities of a running process
getpcaps $(pgrep nginx)

# View capability bitmasks from /proc
cat /proc/$(pgrep nginx)/status | grep -i cap

# Drop capabilities from a process (using capsh)
capsh --caps="cap_net_bind_service+eip cap_net_raw+eip" -- \
    --keep=1 --user=nobody --addamb=cap_net_bind_service -- -c "id; getpcaps \$\$"

# Run with specific capabilities (using setcap on binary)
setcap cap_net_bind_service=+ep /usr/local/bin/my-server
getcap /usr/local/bin/my-server

5. sudo Authorization

sudo provides role-based access: certain users can run certain commands as certain target users.

5.1 sudoers Syntax

# /etc/sudoers (edit with visudo ONLY)
#
# Format:
# WHO    WHERE=(AS_WHO)              TAGS: COMMANDS
# %group   HOST=(target_user)        NOPASSWD: /path/to/command
#
# WHO: user or %group
# WHERE: hostname restriction (rarely used)
# AS_WHO: which user(s) to run as
# TAGS: NOPASSWD, PASSWD, SETENV, NOEXEC
# COMMANDS: full path, comma-separated

# User alice can run anything as root (with password)
alice   ALL=(ALL:ALL) ALL

# Developers can restart nginx without password
%developers ALL=(root) NOPASSWD: /usr/bin/systemctl restart nginx, /usr/bin/systemctl reload nginx

# Bob can only run specific backup script
bob ALL=(root) NOPASSWD: /usr/local/bin/backup.sh

# Operators can run as any user except root
%operators ALL=(ALL:!root) ALL

# Carol can run commands as the www-data user
carol ALL=(www-data) ALL

# Command with arguments (exact match required)
dave ALL=(root) NOPASSWD: /usr/bin/systemctl status httpd

5.2 Complex sudo Rules

# Cmnd_Alias for grouping
Cmnd_Alias WEB = /usr/bin/systemctl start httpd, \
                 /usr/bin/systemctl stop httpd, \
                 /usr/bin/systemctl restart httpd, \
                 /usr/bin/systemctl reload httpd

Cmnd_Alias DB = /usr/bin/systemctl start postgresql, \
                /usr/bin/systemctl stop postgresql

# User_Alias and Host_Alias
User_Alias ADMINS = alice, bob, charlie
User_Alias WEBADMINS = %developers, dave

ADMINS    ALL=(ALL) ALL
WEBADMINS ALL=(root) WEB

# Default options
Defaults    env_reset
Defaults    mail_badpass
Defaults    secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
Defaults    logfile="/var/log/sudo.log"
Defaults    lecture="always"
Defaults    insults

# Per-user defaults
Defaults:alice    !authenticate
Defaults:%developers    timestamp_timeout=30

5.3 sudo Session Logging

# Enable I/O logging

Defaults    iolog_dir=/var/log/sudo-io

# Replay recorded sudo session

sudoreplay session_id  # replay

6. PolKit (PolicyKit)

PolKit is a system-wide authorization framework that allows unprivileged programs to communicate with privileged ones. It is used by systemd, NetworkManager, udisks, and other desktop components.

6.1 Architecture

Application
     |
     v
libpolkit-gobject
     |
     v
polkitd (daemon) -----> polkit-agent-1 (authentication dialog)
     |
     v
Authorization Rules (/etc/polkit-1/rules.d/*.rules)
     |
     v
Allow / Deny

6.2 Defining Rules (JavaScript)

// /etc/polkit-1/rules.d/10-admin.rules
polkit.addAdminRule(function(action, subject) {
    return ["unix-group:wheel"];
});

// /etc/polkit-1/rules.d/50-mount.rules
polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.udisks2.filesystem-mount" &&
        subject.isInGroup("storage")) {
        return polkit.Result.YES;
    }
});

// /etc/polkit-1/rules.d/40-reboot.rules
polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.login1.reboot" ||
        action.id == "org.freedesktop.login1.reboot-multiple-sessions") {
        if (subject.isInGroup("wheel")) {
            return polkit.Result.AUTH_SELF_KEEP;
        }
    }
});

6.3 Listing Actions

# List all registered PolKit actions
pkaction --verbose

# Check authorization for a specific action
pkcheck --action-id org.freedesktop.login1.reboot \
    --process $(pidof gnome-shell)

# Test as a specific user
sudo -u alice pkcheck --action-id org.freedesktop.NetworkManager.network-control

7. JWT Authorization

JSON Web Tokens carry authorization claims in a self-contained signed (or encrypted) token. The server can verify the token's authenticity without a database lookup.

7.1 JWT Structure

eyJhbGciOiJFZDI1NTE5IiwidHlwIjoiSldUIiB9.
eyJzdWIiOiIxMjM0IiwibmFtZSI6IkFsaWNlIiwicm9sZXMiOlsiYWRtaW4iXSwiZXhwIjoxNzE5MDAwMDAwfQ.
XkGz9h3sP2qR7vL5mN8wB4dJ6tY1kF0aA2cE3iH9
\_____________ Header ______________/ \____________________ Payload _______________________/ \____ Signature ____/

Header (Base64URL decoded):
{
  "alg": "EdDSA",
  "typ": "JWT"
}

Payload (Base64URL decoded):
{
  "sub": "1234",
  "name": "Alice",
  "roles": ["admin"],
  "exp": 1719000000,
  "iat": 1718913600,
  "iss": "auth.example.com"
}

Signature: EdDSA-Sign(private_key, header + "." + payload)

7.2 JWT Verification (Python)

import jwt
import time

def verify_token(token, public_key):
    try:
        payload = jwt.decode(
            token,
            public_key,
            algorithms=["EdDSA", "RS256", "ES256"],
            options={
                "verify_exp": True,
                "verify_iat": True,
                "verify_iss": True,
                "require": ["exp", "sub", "iss"]
            },
            issuer="auth.example.com",
        )
        return payload
    except jwt.ExpiredSignatureError:
        return None
    except jwt.InvalidTokenError:
        return None

7.3 JWT Security Considerations

  • Never use 'alg: "none"' . Verify the algorithm you expect, not the one in the token header.
  • Symmetric vs asymmetric : HS256 uses a shared secret (both verifier and issuer need it). RS256/ES256/EdDSA use public/private keys (only issuer has private key).
  • Token size : JWT s grow large. Keep claims minimal.
  • Revocation : JWT s cannot be revoked server-side without a blocklist or short expiration. For immediate revocation, maintain a server-side session.
  • Store secrets securely : The signing key must be protected. If it leaks, anyone can forge tokens.

8. OAuth 2.0

OAuth 2.0 is an authorization framework for delegated access. It allows a user to grant a third-party application limited access to their resources on another service, without sharing their credentials.

8.1 Authorization Code Flow (PKCE)

        +----------+
        |  User    |
        | (Alice)  |
        +----+-----+
             |
             | (A) "I want to share my photos with PhotoPrinter"
             v
        +----+-----+                                      +---------------+
        |  Client  |                                      | Authorization |
        | (Photo   |                                      |    Server     |
        |  Printer)|                                      | (accounts.eg) |
        +----+-----+                                      +-------+-------+
             |                                                    |
             | (B) Redirect to /authorize                         |
             |     ?response_type=code                            |
             |     &client_id=photoprinter                        |
             |     &redirect_uri=https://photoprinter/callback    |
             |     &scope=photos:read                             |
             |     &state=<random>                                |
             |     &code_challenge=<SHA256(verifier)>             |
             |     &code_challenge_method=S256                    |
             +--------------------------------------------------->|
             |                                                    |
             | (C) User authenticates and grants consent          |
             |<-------------------------------------------------->|
             |                                                    |
             | (D) Authorization Code                             |
             |     ?code=AUTHZ_CODE&state=<random>                |
             |<---------------------------------------------------+
             |
             | (E) Token Request
             |     POST /token
             |     grant_type=authorization_code
             |     code=AUTHZ_CODE
             |     redirect_uri=https://photoprinter/callback
             |     code_verifier=<original_random_verifier>
             +--------------------------------------------------->|
             |                                                    |
             | (F) Token Response                                 |
             |     {                                              |
             |       "access_token": "eyJ...",                    |
             |       "token_type": "Bearer",                      |
             |       "expires_in": 3600,                          |
             |       "refresh_token": "rt_...",                   |
             |       "scope": "photos:read"                       |
             |     }                                              |
             |<---------------------------------------------------+
             |
             |
             | (G) API Request                                    +----------+
             |     GET /photos                                    | Resource |
             |     Authorization: Bearer eyJ...                   |  Server  |
             +--------------------------------------------------->|          |
             |                                                    |  (API)   |
             | (H) API Response                                   +----------+
             |     200 OK { "photos": [...] }
             |<---------------------------------------------------+

8.2 OAuth Grant Types

Grant Use Case PKCE Required
Authorization Code Server-side web apps Yes (modern)
Authorization Code + PKCE SPAs, native apps, all modern flows Yes
Client Credentials Machine-to-machine, service accounts No
Device Code Input-constrained devices (TVs, IoT) No
Refresh Token Obtaining new access tokens N/A
Implicit (DEPRECATED) Was for SPAs - DO NOT USE N/A
Password (DEPRECATED) Was for trusted first-party apps - DO NOT USE N/A

The Implicit flow sends tokens directly in the redirect URL fragment, exposing them to browser history and referrer headers. The Password grant collects user credentials directly - this violates the core purpose of OAuth . Both are deprecated in OAuth 2.1.

8.3 OAuth vs OIDC

OAuth 2.0 handles authorization (what can the client do?). OpenID Connect ( OIDC ) is a thin identity layer on top of OAuth 2.0 that handles authentication (who is the user?). OIDC adds the id_token (a JWT containing user identity claims) alongside the access token. The openid scope in the authorization request triggers the OIDC flow.

8.4 OAuth Security Best Practices

1. Always use PKCE — even for confidential clients.
2. Validate the redirect_uri against an exact allowlist.
3. Use state parameter to prevent CSRF.
4. Short-lived access tokens (minutes), long-lived refresh tokens.
5. Rotate refresh tokens on use.
6. Bind tokens to the client (sender-constraining via mTLS or DPoP).
7. Never pass tokens in URLs.
8. Use the Authorization header, never query parameters for bearer tokens.

10. Summary

Authorization is layered. A Linux system enforces access control at multiple levels simultaneously:

Layer Mechanism Override Possible?
Filesystem DAC permissions, ACLs By owner
Kernel LSM SELinux / AppArmor Only by policy change
Capabilities Process capability sets By root (with CAP_SETPCAP)
Application Application-level RBAC By application logic
Network Firewall rules, netfilter By root
Service sudo, PolKit By policy

The principle of least privilege demands that each layer denies by default and grants only what is needed. A process running as an unprivileged user inside an AppArmor profile with dropped capabilities and restricted sudo access is orders of magnitude harder to exploit than the same process running as root.

Challenge

Implement the classic Unix permission check in Go. Given a file's mode and owner, plus a process UID, primary GID, and supplementary groups, decide whether read, write, or execute access is granted. Test it against stat and test -r/-w/-x on files you own. The example handles the owner, group, and other tiers; add the root override and the rule that directories need x to be traversed.

package main

import (
	"fmt"
	"os"
	"syscall"
)

func contains(groups []uint32, gid uint32) bool {
	for _, g := range groups {
		if g == gid {
			return true
		}
	}
	return false
}

// want is a combination of 4 (read), 2 (write), 1 (execute).
func allowed(mode os.FileMode, fileUID, fileGID, uid, gid uint32, groups []uint32, want os.FileMode) bool {
	if uid == 0 {
		return true // root bypasses the DAC checks
	}
	var mask os.FileMode
	switch {
	case uid == fileUID:
		mask = want << 6
	case gid == fileGID || contains(groups, fileGID):
		mask = want << 3
	default:
		mask = want
	}
	return mode.Perm()&mask == mask
}

func main() {
	path := os.Args[1]
	info, err := os.Stat(path)
	if err != nil {
		panic(err)
	}
	stat := info.Sys().(*syscall.Stat_t)

	gidList, err := syscall.Getgroups()
	if err != nil {
		panic(err)
	}
	groups := make([]uint32, 0, len(gidList))
	for _, g := range gidList {
		groups = append(groups, uint32(g))
	}

	uid, gid := uint32(os.Getuid()), uint32(os.Getgid())
	fmt.Printf("%s mode=%04o\n", path, info.Mode().Perm())
	for _, c := range []struct {
		name string
		bit  os.FileMode
	}{{"read", 4}, {"write", 2}, {"execute", 1}} {
		ok := allowed(info.Mode(), stat.Uid, stat.Gid, uid, gid, groups, c.bit)
		fmt.Printf("  %-8s %v\n", c.name, ok)
	}
}
