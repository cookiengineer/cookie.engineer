Secrets Management

Protecting credentials, tokens and keys through lifecycle management, automated rotation, and leak detection.

Overview

Secrets are the credentials, keys, and tokens that grant access to systems and data. This article covers the secret-zero bootstrap problem, vault architecture, dynamic secrets, rotation, leak detection, and a challenge that audits a Git repository for leaked credentials.

Required Reading

  • Cryptography - symmetric/asymmetric encryption, hashing, key derivation
  • Authentication - password hashing, token types, session management

Concept

Secrets are any piece of data that grants access or proves identity: passwords, API keys, TLS private keys, SSH keys, database credentials, cloud provider tokens, encryption keys. Secrets management is the discipline of generating, storing, distributing, rotating, and revoking these credentials securely.

The fundamental tension: secrets must be available to authorized services at runtime, but inaccessible to everyone else - including developers, operators, and CI/CD systems. Every copy of a secret expands the attack surface.

Types of Secrets

Type Examples Rotation Frequency Storage
User passwords LDAP/AD, local accounts 90 days (NIST: only on compromise) hashed (bcrypt/argon2)
API keys GitHub tokens, AWS IAM keys, Stripe keys 30-90 days encrypted at rest
TLS private keys Web server, mutual TLS 1 year (or ACME auto: 90 days) HSM / restricted file
SSH keys Host keys, user keys 1 year encrypted on disk
Database credentials PostgreSQL, MySQL, MongoDB 30-90 days (dynamic: per session) vault, env, secret store
Cloud provider tokens AWS STS, GCP SA keys, Azure SP 1-24 hours (STS best) vault, metadata service
Encryption keys DEKs, KEKs, master keys annually or on compromise HSM, vault

The Secret Zero Problem

Every secret management system has a bootstrap problem: how do you securely deliver the first secret (the "secret zero") that unlocks all others?

Solutions ranked by maturity:

1. Platform-provided identity (best):
   - AWS IAM instance profile → no stored credential
   - GCP metadata server → service account token
   - Kubernetes service account → projected token

2. Hardware root of trust:
   - TPM-sealed bootstrap key
   - HSM-backed unwrapping key

3. Manual bootstrap (worst, but sometimes unavoidable):
   - Operator SSHes in and provides initial token
   - Recovery key in physical safe

4. Trusted execution environments:
   - AWS Nitro Enclaves → attestation-based secret release
   - Confidential VMs

Key concepts

  • Secret Engine: A component that generates, stores, or encrypts secrets. KV v2 is a key-value store. PKI engine generates TLS certs. Database engine creates dynamic DB credentials.
  • Auth Method: How clients authenticate to Vault. LDAP , OI DC , Kubernetes, AppRole, TLS certs.
  • Policy: HCL-based ACL specifying what paths a client can access and what operations they can perform.
  • Dynamic Secrets: Generated on-demand with a lease. Automatic revocation when lease expires. No long-lived credentials.
# Run Vault in dev mode for experimentation
podman run -d --cap-add=IPC_LOCK \
  -e 'VAULT_DEV_ROOT_TOKEN_ID=dev-root' \
  -p 8200:8200 \
  --name vault-dev \
  docker.io/hashicorp/vault:latest

export VAULT_ADDR='http://127.0.0.1:8200'
export VAULT_TOKEN='dev-root'

# Enable KV v2 secret engine
vault secrets enable -path=secret kv-v2

# Store a static secret
vault kv put secret/myapp/db username=appuser password='s3cur3-p4ssw0rd'

# Read it back
vault kv get secret/myapp/db

# Enable database dynamic secrets
vault secrets enable database

vault write database/config/postgres \
  plugin_name=postgresql-database-plugin \
  allowed_roles="readonly" \
  connection_url="postgresql://{{username}}:{{password}}@db-host:5432/postgres" \
  username="vault_admin" \
  password="vault_admin_pass"

vault write database/roles/readonly \
  db_name=postgres \
  creation_statements="CREATE USER \"{{name}}\" WITH PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl="1h" \
  max_ttl="24h"

# Now generate a dynamic, time-limited DB credential
vault read database/creds/readonly
# Returns username + password valid for 1 hour — auto-revoked after

# Policy example: allow reading only the app's own secrets
vault policy write myapp-policy - <<'EOF'
path "secret/data/myapp/*" {
  capabilities = ["read"]
}
path "database/creds/readonly" {
  capabilities = ["read"]
}
EOF
						
# AppRole: machine-to-machine authentication
vault auth enable approle

vault write auth/approle/role/myapp \
  secret_id_ttl=10m \
  token_ttl=1h \
  token_max_ttl=4h \
  policies="myapp-policy"

# Get Role ID (long-lived identifier)
ROLE_ID=$(vault read -field=role_id auth/approle/role/myapp/role-id)

# Get Secret ID (short-lived, wrapped for secure delivery)
SECRET_ID=$(vault write -f -field=secret_id auth/approle/role/myapp/secret-id)

# Authenticate with AppRole
vault write auth/approle/login role_id="$ROLE_ID" secret_id="$SECRET_ID"

Environment Variable Security

Environment variables are the most common secret injection method - and the most dangerous. Every child process inherits them. Crash dumps, debug endpoints, and /proc/<pid>/environ expose them.

# DANGEROUS: secrets in .bashrc or .env files
export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY  # NO

# BETTER: inject only for the specific process
AWS_SECRET_ACCESS_KEY=$(vault kv get -field=secret_key secret/aws) ./myapp

# BEST: don't use env vars at all — use platform identity
# AWS: IAM instance profile / IRSA (IAM Roles for Service Accounts)
# Vault Agent sidecar injects secrets into a shared memory volume
						
# /proc/<pid>/environ is world-readable to the same user (unless hidepid=2)
# Verify exposure:
cat /proc/$(pgrep myapp)/environ | tr '\0' '\n'

# Mitigation: mount proc with hidepid=2
# /etc/fstab
# proc /proc proc defaults,hidepid=2 0 0

Git Secret Scanning

Secrets committed to Git are secrets disclosed to everyone with repository access - forever. Even if you rewrite history, clones and forks persist.

# gitleaks — detect secrets in Git history
sudo pacman -S gitleaks

# Scan current state
gitleaks detect --source . --verbose

# Scan full Git history
gitleaks detect --source . --log-opts="--all" --verbose

# Scan before commit (pre-commit hook)
cat <<'EOF' > .git/hooks/pre-commit
#!/bin/bash
gitleaks protect --staged --verbose
if [ $? -ne 0 ]; then
  echo "Secret detected. Commit blocked."
  exit 1
fi
EOF
chmod +x .git/hooks/pre-commit
						
# trufflehog — verifies if found secrets are still valid
sudo pacman -S trufflehog

# Scan Git repo with verification
trufflehog git file:///path/to/repo --only-verified

# Scan GitHub organization (requires token)
trufflehog github --org=myorg --only-verified --json
						
# git-secrets — pattern-based detection for AWS, GCP, etc.
sudo pacman -S git-secrets

# Install hooks into a repo
cd /path/to/repo
git secrets --install
git secrets --register-aws    # AWS key patterns

# Scan history for AWS keys
git secrets --scan-history

Pre-receive Hook

# Server-side hook for Gitea / GitLab / GitHub Enterprise
cat <<'EOF' > /var/lib/gitea/repositories/myorg/myrepo.git/hooks/pre-receive.d/check-secrets
#!/bin/bash
# Run gitleaks against every pushed ref
while read oldrev newrev refname; do
  if [ "$newrev" = "0000000000000000000000000000000000000000" ]; then
    continue  # branch deleted
  fi
  git archive "$newrev" | gitleaks detect --no-git -v
  if [ $? -ne 0 ]; then
    echo "SECRET SCAN FAILED — push rejected"
    exit 1
  fi
done
EOF

Encrypted Secrets in Configuration

SOPS (Secrets OPerationS): Encrypts YAML / JSON /ENV/INI files. Supports AWS KMS, GCP KMS, Azure Key Vault, PGP, age.

sudo pacman -S sops age

# Generate an age keypair
age-keygen -o ~/.config/sops/age/keys.txt

# Encrypt a file
sops --encrypt --age $(awk '/public key:/{print $NF}' ~/.config/sops/age/keys.txt) \
  secrets.plain.yaml > secrets.enc.yaml

# Edit in-place (decrypts, opens $EDITOR, re-encrypts on save)
sops secrets.enc.yaml

# Decrypt for consumption
sops --decrypt secrets.enc.yaml > secrets.yaml
						
# .sops.yaml — config file specifying encryption keys
creation_rules:
  - path_regex: .*/dev/.*
    age: age1abc123...
  - path_regex: .*/prod/.*
    age: age1def456...

# Example secret file:
# api_key: ENC[AES256_GCM,data:VGhl...,iv:YW4g...,tag:ZXhh...,type:str]
# db_password: ENC[AES256_GCM,data:c2Vj...,iv:cmV0...,tag:bXBs...,type:str]

ansible-vault: Encrypts entire Ansible variable files.

# Encrypt a file
ansible-vault encrypt secrets.yml
# Prompts for password

# Edit in-place
ansible-vault edit secrets.yml

# Use in playbooks
ansible-playbook --ask-vault-pass deploy.yml

# Use a vault password file (automated)
ansible-playbook --vault-password-file /secure/path/vault-pass deploy.yml

Secret Rotation Automation

Rotation is the most important and most neglected aspect of secrets management. A static credential that lives for 3 years is near-equivalent to a hardcoded one.

#!/bin/bash
# rotate-db-password.sh — automated credential rotation
# Called by systemd timer or cron

SERVICE="myapp-db"
NEW_PASS=$(openssl rand -base64 32)

# Step 1: Generate new password, store in Vault
vault kv put secret/myapp/db password="$NEW_PASS"

# Step 2: Update database user password
psql -h db-host -U postgres -c "ALTER USER myapp WITH PASSWORD '$NEW_PASS';"

# Step 3: Reload application (picks up new password from Vault)
systemctl reload "$SERVICE"

# Step 4: Verify application can authenticate
sleep 2
if systemctl is-active --quiet "$SERVICE"; then
  echo "Rotation successful"
else
  echo "Rotation failed — rolling back to previous password"
  # Rollback logic
  systemctl stop "$SERVICE"
  psql -h db-host -U postgres -c "ALTER USER myapp WITH PASSWORD '$OLD_PASS';"
  systemctl start "$SERVICE"
fi

Rotation principles: 1. Generate new secret before revoking old one -> dual-credential overlap period 1. Wait for all consumers to pick up new secret before revoking old 1. Test authentication with new secret before declaring success 1. Never rotate all secrets simultaneously - stagger to limit blast radius

Service Accounts vs. User Accounts

Service Account User Account
Authentication API key, token, certificate Password, MFA, biometric
Interactive login Never Yes
Password lifespan 30-90 days (dynamic: per hour) 90-365 days
MFA Mutual TLS, IP restriction TOTP, FIDO2
Monitoring API call rate, scope creep Login anomalies
Deprovisioning Revoke token Disable account

Rule: services authenticate with tokens, humans authenticate with evidence. Never use a human's credential for automation, and never give a human a service account password.

Secret Injection Methods

Sidecar pattern (Kubernetes)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    metadata:
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "myapp"
        vault.hashicorp.com/agent-inject-secret-db-creds: "database/creds/readonly"
    spec:
      serviceAccountName: myapp
      containers:
        - name: myapp
          image: myapp:latest
          volumeMounts:
            - name: vault-secrets
              mountPath: /vault/secrets
      volumes:
        - name: vault-secrets
          emptyDir:
            medium: Memory  # secrets never touch disk

CSI driver (Kubernetes)

# Secrets appear as files in a mounted volume
# Managed by Secrets Store CSI Driver
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: vault-db-creds
spec:
  provider: vault
  parameters:
    vaultAddress: "http://vault.vault.svc:8200"
    roleName: "myapp"
    objects: |
      - objectName: "db-password"
        secretPath: "database/creds/readonly"
        secretKey: "password"
