Virtual File System

Linux VFS architecture - superblock, inode, dentry, file objects, pathname resolution, mount namespaces, filesystem registration, and procfs/sysfs as filesystem drivers

Overview

The Virtual File System is the single interface that lets dozens of filesystem types share one set of system calls. This article walks the four core objects (superblock, inode, dentry, and file), follows a pathname through resolution, and shows how filesystems register, how mount namespaces isolate views, and how procfs, sysfs, and fscrypt plug into the same layer.

  • /wiki/articles/fundamentals/filesystems.html - Linux VFS layer, inodes, ext4 internals, journaling, stat()
  • /wiki/articles/sysinternals/kernel-architecture.html - kernel architecture, subsystems, modular design

The VFS as Universal Interface

The Linux Virtual File System is the abstraction layer that allows dozens of filesystem types

  • ext4, btrfs, XFS, NFS, procfs, sysfs, tmpfs, FUSE - to coexist behind a single set of
system calls. Every open() , read() , write() , stat() , and mkdir() call passes through the VFS, which dispatches to the correct filesystem driver through function pointer tables embedded in kernel objects.

The VFS is not a filesystem itself. It is a set of data structures and function dispatch tables that filesystem drivers implement. From the kernel's perspective, /proc/self/status (procfs), /sys/class/net/lo/mtu (sysfs), and /home/user/file.txt (ext4) are all processed by the same code in fs/open.c and fs/read_write.c . The differences are hidden behind per-filesystem operation tables.

The Superblock

The super_block represents a single mounted instance of a filesystem. When you run mount -t ext4 /dev/sda1 /mnt , the kernel creates a new super_block and binds it to the mount point. Multiple mounts of the same block device each get their own super_block . 

// include/linux/fs.h — struct super_block (abbreviated)
struct super_block {
    struct list_head    s_list;         // global list of all superblocks
    dev_t               s_dev;          // device identifier
    unsigned long       s_blocksize;    // block size in bytes
    unsigned char       s_blocksize_bits;
    loff_t              s_maxbytes;     // max file size
    struct file_system_type *s_type;    // filesystem type (ext4, btrfs, ...)
    const struct super_operations *s_op; // operations table
    struct dentry       *s_root;         // dentry of filesystem root
    struct list_head    s_inodes;        // all inodes in this fs
    struct list_head    s_dirty_lists;   // dirty inodes
    struct list_head    s_inodes_wb;     // writeback inodes
    unsigned long       s_magic;         // filesystem magic number
    struct hlist_bl_head s_roots;       // alternate root dentries
    void                *s_fs_info;      // filesystem-private data (e.g., ext4_sb_info)
    unsigned long       s_flags;         // mount flags (MS_RDONLY, MS_NOATIME, ...)
    struct user_namespace *s_user_ns;    // user namespace
    // ...
};

struct super_operations {
    struct inode *(*alloc_inode)(struct super_block *sb);
    void (*destroy_inode)(struct inode *);
    void (*free_inode)(struct inode *);
    void (*dirty_inode)(struct inode *, int flags);
    int  (*write_inode)(struct inode *, struct writeback_control *wbc);
    int  (*drop_inode)(struct inode *);
    void (*evict_inode)(struct inode *);
    void (*put_super)(struct super_block *);
    int  (*sync_fs)(struct super_block *sb, int wait);
    int  (*statfs)(struct dentry *, struct kstatfs *);
    int  (*remount_fs)(struct super_block *, int *, char *);
    void (*umount_begin)(struct super_block *);
    // ...
};

The Inode

The inode is the kernel's representation of a filesystem object - file, directory, symlink, device, pipe, or socket. It encodes ownership, permissions, size, timestamps, and two critical operation tables:

  1. 'i_op' (inode_operations) - metadata operations: create, link, unlink, mkdir, rename
  2. 'i_fop' (file_operations) - data operations: read, write, llseek, mmap, iterate
// struct inode (include/linux/fs.h) — key fields
struct inode {
    umode_t             i_mode;         // S_IFREG, S_IFDIR, S_IFLNK, permissions
    unsigned short      i_opflags;
    kuid_t              i_uid;          // owner user ID
    kgid_t              i_gid;          // owner group ID
    unsigned int        i_flags;        // S_IMMUTABLE, S_APPEND, S_NOATIME, ...
    const struct inode_operations *i_op;
    struct super_block  *i_sb;
    struct address_space *i_mapping;    // page cache mapping
    unsigned long       i_ino;          // inode number
    loff_t              i_size;         // file size in bytes
    struct timespec64   i_atime;        // last access
    struct timespec64   i_mtime;        // last modification
    struct timespec64   i_ctime;        // last metadata change
    blkcnt_t            i_blocks;       // blocks allocated (512-byte units)
    unsigned short      i_bytes;        // bytes in last block
    struct hlist_node   i_hash;         // inode cache hash
    struct list_head    i_io_list;      // for writeback
    struct list_head    i_lru;          // LRU list
    struct list_head    i_sb_list;      // per-superblock list
    atomic_t            i_count;        // reference count
    unsigned long       i_state;        // I_NEW, I_FREEING, I_CLEAR, I_DIRTY_SYNC...
    // ...
};

struct inode_operations {
    struct dentry *(*lookup)(struct inode *, struct dentry *, unsigned int);
    int (*create)(struct mnt_idmap *, struct inode *, struct dentry *, umode_t, bool);
    int (*link)(struct dentry *, struct inode *, struct dentry *);
    int (*unlink)(struct inode *, struct dentry *);
    int (*symlink)(struct mnt_idmap *, struct inode *, struct dentry *, const char *);
    int (*mkdir)(struct mnt_idmap *, struct inode *, struct dentry *, umode_t);
    int (*rmdir)(struct inode *, struct dentry *);
    int (*rename)(struct mnt_idmap *, struct inode *, struct dentry *,
                  struct inode *, struct dentry *, unsigned int);
    int (*setattr)(struct mnt_idmap *, struct dentry *, struct iattr *);
    int (*getattr)(struct mnt_idmap *, const struct path *, struct kstat *, u32, unsigned int);
    struct posix_acl *(*get_inode_acl)(struct inode *, int, bool);
    // ...
};

The Dentry Cache

The dentry (directory entry) is the VFS cache that maps names to inodes. It's the most performance-critical cache in the kernel - every open() , stat() , and readlink() involves dentry lookups. The dcache is a hash table keyed by (parent dentry, name hash): 

Dentry Cache (dcache):
══════════════════════════════════════════════════════════════

dcache hash table (dentry_hashtable):
┌───+──────────────────────────────────────────────────────┐
│ 0 │ → dentry(a) → dentry(b) → ...                       │
│ 1 │ → dentry(c)                                         │
│ 2 │ → (empty)                                           │
│...│                                                      │
│ N │ → dentry(x) → dentry(y) → dentry(z)                 │
└───+──────────────────────────────────────────────────────┘

Lookup: __d_lookup(parent, name)
  1. Compute hash = full_name_hash(parent, name->name, name->len)
  2. Index = hash >> d_hash_shift (hashed dentry_hashtable bucket)
  3. Walk hash chain, comparing parent + name
  4. If found: dget(dentry), return
  5. If not: allocate new dentry, call parent→d_inode→i_op→lookup()

Path resolution: /home/user/file.txt
  start at root dentry (or AT_FDCWD for relative paths)
  │
  ├── component "home":  lookup(root, "home")  → dentry_home
  ├── component "user":   lookup(home, "user")  → dentry_user
  └── component "file.txt": lookup(user, "file.txt") → dentry_file
                                                                 
  Final: dentry_file, with d_inode pointing to the file's inode
						
# Dentry cache inspection
cat /proc/sys/fs/dentry-state
# <nr_dentry> <nr_unused> <age_limit> <want_pages> <dummy0> <dummy1>

# Watch dentry lookups in real-time
sudo bpftrace -e '
kprobe:__d_lookup {
    $dentry = (struct dentry *)arg0;
    $name = $dentry->d_name;
    printf("lookup: %s (len=%d)\n", str($name.name), $name.len);
}
kretprobe:__d_lookup /retval != 0/ {
    printf("  → HIT %p\n", retval);
}
kretprobe:__d_lookup /retval == 0/ {
    printf("  → MISS\n");
}
' &

# Trigger lookups
ls -la /etc/ > /dev/null
kill %1 2>/dev/null

# Dentry allocation tracking
sudo bpftrace -e '
kprobe:__d_alloc { @d_alloc[comm] = count(); }
interval:s:30 { print(@d_alloc); clear(@d_alloc); }
'

The File Object

While the dentry+inode represent the on-disk object, the struct file represents an open instance of that object. Multiple processes can open the same file, each getting their own struct file

  • each with an independent file position, access mode, and credentials:

file objects: one per open() call
══════════════════════════════════════════════════════════════

Process A (PID 1000)                    Process B (PID 2000)
  │                                       │
  │ fd=3 → struct file_A                  │ fd=4 → struct file_B
  │         f_pos=0                       │         f_pos=4096
  │         f_cred={uid=1000}             │         f_cred={uid=2000}
  │         f_mode=FMODE_READ             │         f_mode=FMODE_READ
  │         │                              │         │
  └─────────+──────────────────────────────+─────────┘
            │                              │
            ▼                              ▼
        struct file_operations (f_op) — SAME for both
            │
            ▼
        struct dentry → struct inode (shared by all file objects)

Pathname Resolution Walkthrough

Pathname resolution is the process of converting a string path ( /home/user/file.txt ) into a dentry pointing to the target inode. The core function is link_path_walk() , called by path_lookupat() : 

path_lookupat(dfd, name, flags, &path):
    │
    ├── 1. Determine starting point:
    │       if name[0] == '/': start = current->fs->root
    │       else if dfd == AT_FDCWD: start = current->fs->pwd
    │       else: start = file from dfd
    │
    ├── 2. link_path_walk(name, &nd):
    │       for each component in name:
    │       │
    │       ├── Handle "." and ".." specially
    │       │     ".": stay in same dentry
    │       │     "..": move to d_parent (with mountpoint crossing)
    │       │
    │       ├── If component ends with '/': must be a directory
    │       │     walk_component() → handle_lookup_down()
    │       │
    │       └── For regular components:
    │             │
    │             ├── lookup_fast(): try dcache hash
    │             │     ├── HIT: check dentry is still valid, return
    │             │     └── MISS: fall through
    │             │
    │             └── lookup_slow():
    │                   ├── Allocate new dentry
    │                   ├── Call parent->d_inode->i_op->lookup()
    │                   ├── Filesystem reads directory blocks, finds entry
    │                   ├── Return inode → set d_inode on dentry
    │                   └── Insert into dcache hash
    │
    ├── 3. Handle trailing symlinks:
    │       if final component is a symlink and LOOKUP_FOLLOW:
    │         read symlink target
    │         restart link_path_walk from target
    │         (repeat up to MAXSYMLINKS times)
    │
    └── 4. Set path->dentry and path->mnt, return 0
						
# Trace pathname resolution step by step
strace -e trace=openat,newfstatat ls /etc/hostname 2>&1

# Use namei to walk the path like the kernel does
namei -l /etc/ssl/certs/ca-certificates.crt

# Trace VFS path walking
sudo bpftrace -e '
kprobe:link_path_walk {
    printf("path_walk: %s (pid=%d)\n", str(arg1), pid);
}
kprobe:lookup_fast { @fast_lookups = count(); }
kprobe:__lookup_slow { @slow_lookups = count(); }
interval:s:10 {
    $fast = @fast_lookups;
    $slow = @slow_lookups;
    printf("fast=%d slow=%d hit_rate=%.1f%%\n", $fast, $slow,
           $fast * 100.0 / ($fast + $slow + 1));
}
'

Filesystem Registration

Filesystem drivers register themselves with the VFS using register_filesystem() . This adds the driver to the global file_systems linked list: 

// include/linux/fs.h
struct file_system_type {
    const char *name;                    // "ext4", "btrfs", "proc"
    int fs_flags;                        // FS_REQUIRES_DEV, FS_USERNS_MOUNT, ...
    struct dentry *(*mount)(struct file_system_type *, int,
                            const char *, void *);
    void (*kill_sb)(struct super_block *);
    struct module *owner;
    struct file_system_type *next;       // linked list
    struct hlist_head fs_supers;          // active superblocks
    // ...
};

// Example registration (simplified from fs/ext4/super.c):
static struct file_system_type ext4_fs_type = {
    .owner    = THIS_MODULE,
    .name     = "ext4",
    .mount    = ext4_mount,
    .kill_sb  = kill_block_super,
    .fs_flags = FS_REQUIRES_DEV | FS_ALLOW_IDMAP,
};

static int __init ext4_init_fs(void) {
    ...
    return register_filesystem(&ext4_fs_type);
}

Mount Namespaces and the Mount Tree

Linux mount namespaces provide per-process filesystem views. Each namespace has its own mount tree. This is the foundation of containers - each container sees a different root filesystem: 

Mount Namespace Architecture:
══════════════════════════════════════════════════════════════

Global Mount Tree (init namespace)
  /
  ├── /dev
  ├── /proc
  ├── /sys
  └── /var/lib/containers/ubuntu-rootfs/

Container Mount Namespace (nsenter'd)
  /                          ← bind-mounted from ubuntu-rootfs
  ├── /proc                  ← new proc mount
  ├── /sys                   ← new sysfs mount
  └── /etc/resolv.conf       ← bind-mounted config

struct mount {
    struct mount *mnt_parent;    // parent mount
    struct dentry *mnt_mountpoint; // dentry where mounted
    struct vfsmount mnt;          // embedded vfsmount
    struct list_head mnt_mounts;   // list of children
    struct list_head mnt_child;    // entry in parent's children list
    struct list_head mnt_instance; // superblock instance list
    // ...
};

fscrypt Encryption

Linux provides filesystem-level encryption via fscrypt (formerly ext4 encryption). It operates at the VFS layer, meaning any filesystem can opt in: 

fscrypt Architecture:
══════════════════════════════════════════════════════════════

Policy set on empty directory:
  fscrypt_set_policy(dir, &policy)  ← ioctl(FS_IOC_SET_ENCRYPTION_POLICY)

Key added to kernel keyring:
  keyctl add logon fscrypt:<identifier> <raw_key> @s

On file write:
  VFS → ext4_writepages()
    │
    ├── Check: inode has encryption context?
    │     YES → encrypt page contents before write
    │     NO  → write plaintext
    │
    └── submit_bio(encrypted data)

On file read:
  VFS → ext4_read_folio()
    │
    ├── Read ciphertext from disk
    ├── Decrypt into page cache
    └── VFS reads plaintext from page cache

Result:
  - Data at rest: encrypted on disk
  - Data in kernel page cache: plaintext (decrypted on read)
  - Filenames: encrypted ciphertext stored on disk (not readable as UTF-8)
  - Directory structure: NOT encrypted (just filenames)
						
# fscrypt overview (requires filesystem with encryption support)
# Check if your filesystem supports encryption
sudo tune2fs -l /dev/sda1 2>/dev/null | grep encrypt || echo "Check with: sudo tune2fs -l <dev>"

# On a supported ext4 with encryption enabled:
# sudo fscrypt setup            # one-time setup
# sudo fscrypt setup /mnt          # per-mountpoint setup
# sudo fscrypt encrypt /mnt/secret --name=mysecret
# sudo fscrypt unlock /mnt/secret

procfs, sysfs, debugfs

The beauty of the VFS design is that /proc , /sys , and /debugfs are full filesystem drivers

  • they implement the same VFS operations as ext4 or btrfs, but generate content dynamically:

procfs Implementation (fs/proc/):
══════════════════════════════════════════════════════════════

When you cat /proc/$$/status:
  1. VFS resolves path → dentry → inode
  2. Inode's i_fop→open() → proc_single_open()
  3. vfs_read() → seq_read() → proc_single_show()
  4. proc_single_show() calls the registered show function
  5. show function reads task_struct fields, formats output
  6. seq_read() copies to userspace buffer

Directory listing (ls /proc):
  1. VFS's iterate_dir() → proc_root_readdir()
  2. Iterates process list (task_struct linked list)
  3. For each task->pid, emits a directory entry
  4. Also emits fixed entries: self, thread-self, mounts, ...

No disk I/O occurs — all content generated from kernel data structures.

VFS Hooking and Security Modules

Linux Security Modules (LSMs) like SELinux and AppArmor hook into the VFS layer. Every inode operation, file open, and path resolution can be intercepted: 

// Security hooks in the VFS (simplified path for open()):

vfs_open(path, file):
    │
    ├── security_file_open(file)   ← LSM: may deny access
    ├── do_dentry_open(file, ...):
    │     │
    │     ├── security_inode_permission(inode, MAY_OPEN)  ← LSM check
    │     ├── f->f_op->open(inode, file)                   ← fs-specific
    │     └── security_file_post_open(file)                ← LSM post-check
    │
    └── fsnotify_open(file)        ← notify inotify/fanotify watchers
						
# Trace LSM hooks at VFS boundaries
sudo bpftrace -e '
kprobe:security_file_open    { printf("LSM: file_open     pid=%d comm=%s\n", pid, comm); }
kprobe:security_inode_create { printf("LSM: inode_create  pid=%d comm=%s\n", pid, comm); }
kprobe:security_inode_unlink { printf("LSM: inode_unlink  pid=%d comm=%s\n", pid, comm); }
'

# View current LSM configuration
cat /sys/kernel/security/lsm
