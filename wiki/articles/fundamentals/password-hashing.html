Password Hashing

Why passwords are hashed with a slow salted key derivation function instead of encrypted, and how bcrypt, scrypt, and Argon2 compare.

Overview

A password hash must be deliberately slow and salted so that stealing the database does not hand the attacker a list of usable passwords. Where SHA-256 processes gigabytes per second, a password hash should spend hundreds of milliseconds on a single password. This article explains why hashing beats encryption, compares bcrypt, scrypt, and Argon2id, and shows how salts, peppers, entropy, and /etc/shadow fit together. After reading you can choose sound parameters and audit a Linux password database.

Required Reading

  • Cryptography - hash functions and HMAC fundamentals
  • Authentication - how hashed passwords fit into authentication

1. Why Hash, Not Encrypt?

Encryption is reversible by design - given the ciphertext and the key, you recover the plaintext. If a server stored encrypted passwords, the server must possess the decryption key. When the server is compromised, the attacker obtains both the encrypted passwords and the key. The encryption provides zero protection.

Hashing is one-way. The server stores H(password + salt) . When a user logs in, the server computes H(provided_password + stored_salt) and compares it to the stored hash. The server never stores - and cannot recover - the plaintext password. 

ENCRYPTION (wrong for passwords):
  Store: E_K(password)
  Verify: D_K(stored) == provided  ← requires K to be on the server

HASHING (correct for passwords):
  Store: H(salt + password)
  Verify: H(salt + provided) == stored  ← no decryption key needed

The server does not need to know the password. It needs to know whether the provided password matches the one set during registration. A one-way function is sufficient.

2. Why General-Purpose Hashes Are Wrong

SHA-256 is designed for speed. On modern hardware:

$ openssl speed sha256
type             16 bytes     64 bytes    256 bytes   1024 bytes   8192 bytes  16384 bytes
sha256          65443.09k   162447.82k   355727.02k   530640.21k   665093.46k   685484.89k

~685 MB/s for 16KB blocks.

At that rate:
  1 password hash = 32 bytes
  685,484,890 bytes/s / 32 = 21,421,402 passwords/second

A six-character lowercase password has 26^6 = 308,915,776 combinations.
Time to exhaust: 308M / 21M = ~14 seconds.

Equipped with a GPU (RTX 4090):
  SHA-256: ~20 GH/s (20 billion hashes/second)
  8-character full ASCII (95^8 = 6.6 × 10^15):
    6.6 × 10^15 / 20 × 10^9 = ~3.8 days (offline)

Now compare with bcrypt at cost 12:
  ~200 hashes/second on the same GPU.
  Same 8-char space: 6.6 × 10^15 / 200 = 3.3 × 10^13 seconds ≈ 1 million years.

SHA-256 is too fast. A password hash must be slow enough that offline brute force is infeasible, but fast enough that legitimate login is not annoyingly slow. The sweet spot is 300 ms to 1000 ms per hash on production hardware.

3. Key Derivation Functions

KDFs are cryptographic algorithms designed to derive one or more keys from a master secret (password). They incorporate:

  • Cost parameters : configurable CPU and memory cost
  • Salt : prevents rainbow table and identical-password attacks
  • Key stretching : makes brute force slower

Modern password hashing is a specialized KDF use case.

3.1 KDF vs Hash Comparison

Algorithm Design Speed GPU Resistance Memory Hard? Status
SHA-256 Very fast (685 MB/s) None No Not for passwords
PBKDF2-SHA256 Medium, configurable None No Acceptable with high iterations
bcrypt Slow, configurable Good (4KB state per hash) No (but 4KB state) Good
scrypt Configurable Very good Yes (configurable) Good
Argon2id Configurable Excellent Yes (configurable) Best, recommended

4. bcrypt

bcrypt is based on the Blowfish block cipher, modified with an expensive key setup phase. The cost factor (logarithmic) controls the number of key setup iterations. 

bcrypt internals (simplified):

1. Input: password (up to 72 bytes), salt (128 bits), cost (4 ≤ cost ≤ 31)
2. Derive Blowfish key from password and salt:
   state = EksBlowfishSetup(cost, salt, password)
   This performs 2^cost iterations of the Blowfish key schedule,
   which includes expanding the key, encrypting a magic string,
   and modifying the S-boxes and P-array.
3. Encrypt magic string "OrpheanBeholderScryDoubt" 64 times
4. Output format: $2b$Cost$Base64SaltBase64Hash

Cost factor:
  iterations = 2^cost
  cost=10 → 1,024 iterations
  cost=12 → 4,096 iterations
  cost=14 → 16,384 iterations
  cost=16 → 65,536 iterations

4.1 bcrypt Output Format

$2b$12$LJ3m4ys3GZkXpPq.VxQzBuWp6X8sR2nJ1kL5mN8pQ2bR7vL5mN8p
 |  |  |                                                 |
 |  |  +-- 53 characters (22-char salt in Base64 + 31-char hash in Base64)
 |  +----- Cost factor (2^12 = 4096 iterations)
 +-------- Algorithm identifier
            $2a$ = original (minor bug with non-ASCII)
            $2b$ = fixed (use this)
            $2x$ = compatibility flag
            $2y$ = same as $2b$ (OpenBSD extension)

Each Base64 character encodes 6 bits. The 128-bit salt is encoded in 22 characters. The 184-bit hash is encoded in 31 characters.

4.2 bcrypt Limitations

  • 72-byte password limit : bcrypt truncates passwords longer than 72 bytes (not 72 characters - uses modified Base64)
  • No memory hardness : bcrypt uses only 4KB of state, which fits entirely in GPU L1 cache. GPU s can parallelize bcrypt better than memory-hard algorithms.
  • Fixed output : 184-bit hash output cannot be increased.

4.3 bcrypt on Arch Linux

# Generate bcrypt hash

print(salt)

print(hashed)
"

# Verify bcrypt hash
python3 -c "
import bcrypt
hashed = b'\$2b\$12\$LJ3m4ys3GZkXpPq.VxQzBuWp6X8sR2nJ1kL5mN8pQ2bR7vL5mN8p'
print(bcrypt.checkpw(b'super secret', hashed))
print(bcrypt.checkpw(b'wrong password', hashed))
"

pacman -S whois

5. scrypt

scrypt was designed to be both CPU -hard and memory-hard. It requires a configurable amount of RAM per hash, making GPU /ASIC/FPGA attacks exponentially more expensive because each parallel hashing instance needs its own large memory allocation. 

scrypt parameters:
  N: CPU/memory cost (must be power of 2, typically 2^14 to 2^20)
  r: Block size (typically 8)
  p: Parallelization factor (typically 1)

Memory usage: 128 × N × r bytes
  N=16384 (2^14), r=8, p=1 → 16 MB per hash
  N=1048576 (2^20), r=8, p=1 → 1 GB per hash

Core algorithm (ROMix):
  1. B[0] = PBKDF2-SHA256(P, S, 1, 128·r)
  2. for i = 1 to N:
       B[i] = BlockMix(B[i-1])
  3. for i = 0 to N:
       j = Integerify(B[N-1]) mod N
       B[N-1] = BlockMix(B[N-1] ⊕ B[j])
  4. Output: PBKDF2-SHA256(P, B[N-1], 1, dkLen)

BlockMix: processes 2·r blocks of 64 bytes each, mixing
  them through Salsa20/8 core to defeat time-memory tradeoffs.

The sequential memory-hard loop (step 3) forces the attacker to either use N * 128 * r bytes of memory (expensive per instance) or recompute on the fly (slow, because scrypt is designed to make recomputation nearly as expensive as storage).

5.1 scrypt Parameter Selection

Target Time N (CPU/Memory) r p Memory Use Case
<10 ms 1024 8 1 1 MB Low-security, interactive
~100 ms 16384 8 1 16 MB Medium security
~500 ms 65536 8 1 64 MB Recommended minimum
~1 s 262144 8 1 256 MB High security
~5 s 1048576 8 1 1 GB File encryption 
# Python scrypt example
python3 -c "
import hashlib, os
password = b'super secret'
salt = os.urandom(16)
# Parameters: N=16384, r=8, p=1
hashed = hashlib.scrypt(password, salt=salt, n=16384, r=8, p=1, dklen=64)
print(salt.hex())
print(hashed.hex())
"

6. Argon2

Argon2 won the Password Hashing Competition (PHC) in 2015. It incorporates lessons from bcrypt and scrypt while adding unique features: side-channel resistance mode, data-dependent/dependent-independent hybrid, and easy parameter tuning.

6.1 Three Variants

Variant Memory Access Best For Side-Channel Resistant?
Argon2d Data-dependent Cryptocurrency mining, backend hashing No (access pattern depends on password)
Argon2i Data-independent Key derivation, frontend hashing Yes (access pattern independent of password)
Argon2id Hybrid (first half i, second half d) Password hashing (recommended) Moderate

Argon2id uses Argon2i for the first half of iterations (memory-independent access pattern, resists side channels) and Argon2d for the second half (memory access depends on password and salt, maximizing GPU resistance). This hybrid defeats both side-channel attacks and tradeoff attacks.

6.2 Argon2 Internals

Input: password P, salt S, parameters (m, t, p)
  m: memory in KiB (e.g., 65536 for 64 MiB)
  t: iterations (time cost, e.g., 3)
  p: parallelism (lanes, e.g., 4)
  tagLen: output length (e.g., 32 for 256 bits)

Phase 1: Memory filling
  1. H0 = Blake2b(P, S, params)
  2. Build memory matrix M[0..p-1][0..(m/(4p))-1] of 1024-byte blocks
  3. Each block depends on previous blocks and optionally a reference block:
     For Argon2i: reference is determined by a counter (data-independent)
     For Argon2d: reference is determined by previous block's value (data-dependent)
     For Argon2id: first t/2 passes use i, remaining use d

Phase 2: Finalization
  4. XOR all column ends
  5. Blake2b of the XOR result → tagLen bytes

Memory access pattern (Argon2d):
  Each thread computes a new block B[i]:
    prev = B[i-1] (previous block)
    ref  = B[φ(i)] where φ(i) depends on prev's value
    B[i] = G(prev, ref)  ← G is a compression function based on Blake2b

  The compression function G mixes two 1024-byte blocks using
  Blake2b round operations over the internal state.

6.3 Argon2 Parameter Selection

# Install argon2 CLI
pacman -S argon2

# Interactive parameter calibration (find parameters for 0.5 second)
# Start with moderate values and benchmark:
time echo -n "test password" | argon2 "somesalt" -id -t 3 -m 12 -p 4 -l 32

# Parameters explained:
#   -id     : Argon2id variant (recommended)
#   -t 3    : 3 iterations (time cost)
#   -m 12   : 2^12 KiB = 4 MiB memory
#   -p 4    : 4 parallel lanes
#   -l 32   : 32-byte output (256 bits)

# Hash a password
echo -n "my secure password" | argon2 "$(openssl rand -base64 16)" -id -t 3 -m 16 -p 4 -l 32 -e

# Output format:
# $argon2id$v=19$m=65536,t=3,p=4$c2FsdHZhbHVl$hashoutputbase64
#   |         |    |        |       |    |           |
#   algorithm  version memory   time  parallelism  |
#              (19=1.3) (KiB) (iters) (lanes)    salt (base64)

6.4 Argon2 Parameter Guidelines

Security Target m (memory) t (iterations) p (parallelism) ~Time (modern CPU)
Interactive login 64 MiB (2^16) 3 4 ~500 ms
Moderate security 256 MiB (2^18) 4 4 ~1 s
High security 1 GiB (2^20) 5 4 ~3 s
File encryption 1 GiB (2^20) 10 4 ~10 s

The OWASP recommendation (2024): Argon2id with m=19 MiB (19* 2^10 = 19456 KiB~ 19 MiB), t=2, p=1.

For server-side password hashing:

  • Use Argon2id with at least 64 MiB memory
  • Tune iterations to match your server CPU budget
  • Test on your production hardware, not your development laptop
  • Reserve at least one CPU core for the hashing thread pool

6.5 Argon2 with Python

# Install: pip install argon2-cffi
from argon2 import PasswordHasher
from argon2.low_level import Type

# Using the high-level API
ph = PasswordHasher(
    time_cost=3,        # 3 iterations
    memory_cost=65536,  # 64 MiB (in KiB)
    parallelism=4,       # 4 lanes
    hash_len=32,        # 256-bit output
    salt_len=16,        # 128-bit salt
    type=Type.ID,       # Argon2id
)

# Hash a password
hash_str = ph.hash("my password")
print(hash_str)
# $argon2id$v=19$m=65536,t=3,p=4$salt...$hash...

# Verify
ph.verify(hash_str, "my password")    # True
ph.verify(hash_str, "wrong")          # raises VerifyMismatchError

# Check if hash needs rehashing (parameters changed)
if ph.check_needs_rehash(hash_str):
    # Parameters were increased; rehash the password
    new_hash = ph.hash(password)

7. Salt and Pepper

7.1 Salt

A salt is a random value, unique per password, stored alongside the hash. It provides two crucial protections:

  1. Different hashes for identical passwords : Alice and Bob both use "password123". Without salt, their hashes are identical. An attacker who cracks one cracks both. With unique salts, each hash is completely different.
  1. Defeats rainbow tables : Rainbow tables are precomputed tables mapping hashes to passwords. A 128-bit random salt makes each hash unique, rendering precomputation useless (the attacker would need a separate rainbow table for every possible salt - 2^128 tables).
Without salt:
  Alice:  H("password123") = a1b2c3...
  Bob:    H("password123") = a1b2c3...
  Attacker sees two identical hashes → both use the same password.

With salt:
  Alice:  H("random_salt_a" || "password123") = x1y2z3...
  Bob:    H("random_salt_b" || "password123") = p4q5r6...
  Attacker sees two completely different hashes.

Salt requirements:

  • At least 128 bits (16 bytes) of randomness from a cryptographically secure RNG
  • Unique per password (not per user - generate a new salt on each password change)
  • Stored in plaintext alongside the hash (for example in /etc/shadow or the database)
  • The salt is NOT secret. Its purpose is uniqueness, not secrecy.

7.2 Pepper

A pepper is a secret value added to the password before hashing, NOT stored with the hash. If the hash database is compromised ( SQL injection, backup leak), the attacker does not have the pepper and cannot begin brute force at all. 

Without pepper:
  H = Argon2(salt || password)
  Attacker steals DB → has everything needed to brute force

With pepper:
  H = Argon2(salt || password || pepper)
  Attacker steals DB → has salt and hash, but lacks pepper
  Attacker must also compromise the application server to obtain pepper

Pepper storage strategies:

  1. Environment variable : PEPPER=$(openssl rand -base64 32) in a systemd service file
  2. Separate config file : stored with restricted permissions (0400, owned by the service user)
  3. HSM / KMS : a cloud KMS or hardware security module holds the pepper
  4. HSM with MAC : the pepper is a key in an HSM and each hash includes HMAC(pepper, hash) for integrity

Pepper rotation is difficult because all existing hashes must be rehashed with the new pepper. Strategies:

  • Store the pepper version with each hash: $pepper_v1$argon2id$...
  • On login with an old pepper, rehash with the new pepper to rotate on the fly
  • Use a canary hash of a known plaintext to detect pepper compromise

8. /etc/shadow Format

Linux stores password hashes in /etc/shadow , readable only by root. 

username:$id$salt$hash:last_change:min:max:warn:inactive:expire:reserved
Field Example Description
username alice Login name
password $y$j9T$... Hashed password (! or* = locked)
last_change 19500 Days since 1970-01-01 password was last changed
min 0 Minimum days between password changes
max 99999 Maximum days password is valid
warn 7 Days before expiry to warn user
inactive -1 Days after expiry until account locked
expire -1 Account expiration date (days since epoch)
reserved Reserved for future use

8.1 Hash Algorithm Identifiers

ID Algorithm Status
$1$ MD5 Deprecated(trivially broken)
$2a$ bcrypt Acceptable (but use $2b$)
$2b$ bcrypt (fixed) Good
$5$ SHA-256crypt Acceptable

$argon2id$ Argon2id Best

8.2 yescrypt

yescrypt is a modern password hashing scheme that extends scrypt with additional features. It is the default in /etc/shadow on Arch Linux and many modern distributions (since libxcrypt 4.4). 

yescrypt features over scrypt:
  1. ROMix as the core memory-hard mixing function (similar to scrypt)
  2. Support for ROM (read-only memory) pre-initialization
  3. WORM (write-once read-many) cache
  4. Built-in pwxform (password hashing with XOR-form)
  5. Configurable flavors: YESCRYPT_RW (default), YESCRYPT_WORM
						
# Generate yescrypt hash
mkpasswd -m yescrypt 'my password'

# Check what algorithm /etc/shadow uses
grep "^$(whoami):" /etc/shadow | cut -d: -f2 | cut -d\$ -f2
# 'y' = yescrypt, '6' = SHA-512crypt

9. Password Strength and Entropy

Password strength is measured in bits of entropy:

entropy (bits) = log2(character_set_size ^ length)
               = length × log2(character_set_size)
Character Set Size log2(size)
Digits (0-9) 10 3.32
Lowercase (a-z) 26 4.70
Upper+lower (a-z, A-Z) 52 5.70
Alphanumeric (a-z, A-Z, 0-9) 62 5.95
Full printable ASCII 95 6.57
Diceware wordlist (7776 words) 7776 12.93

Randomly generated passwords :

Length Lowercase Alphanumeric Full ASCII
8 37.6 bits 47.6 bits 52.6 bits
10 47.0 bits 59.5 bits 65.7 bits
12 56.4 bits 71.5 bits 78.8 bits
16 75.2 bits 95.3 bits 105.1 bits
20 94.0 bits 119.1 bits 131.4 bits
24 112.8 bits 142.9 bits 157.7 bits

For online attacks (rate-limited, account lockout), 40-50 bits may suffice. For offline attacks (database compromise), aim for 80+ bits. For long-term secrets (master passwords, recovery keys), aim for 128+ bits.

9.1 Diceware

Diceware generates high-entropy passphrases from a wordlist using dice rolls:

Wordlist: 7776 words (6^5, each word corresponds to 5 dice rolls)
Entropy per word: log2(7776) = 12.92 bits

4 words: 4 × 12.92 = 51.7 bits  (adequate for online)
5 words: 5 × 12.92 = 64.6 bits  (borderline offline)
6 words: 6 × 12.92 = 77.5 bits  (good for offline)
7 words: 7 × 12.92 = 90.5 bits  (strong)
8 words: 8 × 12.92 = 103.4 bits (very strong)

Example (6 words):
  "unmoved spike helium ravioli vowel drawn"
  Entropy: 77.5 bits
  Memorizable: yes (story-based mnemonic)

Diceware passphrases are secure because the word list is known - the security comes from the random selection, not from the secrecy of the word list. 

# Install diceware generator
pacman -S diceware

# Generate a 6-word passphrase
diceware -n 6

# Using the EFF large wordlist (recommended)
curl -s https://www.eff.org/files/2016/07/18/eff_large_wordlist.txt | \
    shuf -n 6 | awk '{print $2}' | tr '\n' ' '

# ENCRYPT_METHOD SHA512    (older)

# List all user hashes (ROOT ONLY)

# Find accounts with weak/deprecated hash algorithms
awk -F: '{print $1, $2}' /etc/shadow | while read user hash; do
    algo=$(echo "$hash" | cut -d\$ -f2)
    case "$algo" in
        1) echo "[CRITICAL] $user: MD5" ;;
        2a) echo "[WARN] $user: bcrypt \$2a\$" ;;
        5) echo "[WARN] $user: SHA-256crypt" ;;
        6) echo "[OK] $user: SHA-512crypt" ;;
        y) echo "[OK] $user: yescrypt" ;;
        "") echo "[LOCKED/DISABLED] $user" ;;
        *) echo "[UNKNOWN] $user: $algo" ;;
    esac
done

# Find accounts without passwords (empty hash)
awk -F: '($2 == "" || $2 == "!" || $2 == "!!" || $2 == "*") { print $1, "NO PASSWORD" }' /etc/shadow

11. Implementation Checklist

When implementing password hashing in a server:

1. [ ] Use Argon2id (preferred) or bcrypt (acceptable).
2. [ ] Generate a unique 128-bit salt per password using CSPRNG.
3. [ ] Store a pepper in a separate security domain (env var, HSM, KMS).
4. [ ] Tune cost parameters for ~500ms on production hardware.
5. [ ] Use constant-time comparison for verification (hmac.compare_digest).
6. [ ] Limit password length (set a reasonable maximum, e.g., 128 chars).
7. [ ] Normalize Unicode (NFC normalization) before hashing.
8. [ ] Log failures without revealing whether the user exists or password is wrong.
9. [ ] Rate-limit login attempts (per-account and per-IP).
10. [ ] Pre-hash extremely long passwords with SHA-256 before feeding to bcrypt
      (bcrypt truncates at 72 bytes; SHA-256 reduces any input to 32 bytes).
11. [ ] Check passwords against Have I Been Pwned's Pwned Passwords API
      (k-anonymity model: send first 5 SHA-1 hex chars, receive suffix matches).
12. [ ] Support password rotation: store algorithm/cost with hash,
      rehash on successful login if parameters have been upgraded.

12. Summary

Password hashing is not about cryptographic strength of the hash function - it is about making brute force infeasible by controlling time, memory, and parallelism: 

Defense in depth for stored credentials:

Layer 1: Salt (unique per password) → defeats rainbow tables, hides duplicates
Layer 2: Slow KDF (Argon2id)       → CPU cost defends against brute force
Layer 3: Memory hardness (Argon2id) → GPU/ASIC resistance
Layer 4: Pepper (separate storage) → protects if DB is compromised
Layer 5: Rate limiting (application) → limits online attempts
Layer 6: Breached password check    → prevents known compromised passwords

Each layer adds cost to the attacker. Combined, they make password cracking
economically infeasible for all but the most determined and well-resourced
adversaries - and even then, only for the weakest passwords.

Challenge

Implement password hashing from scratch in Go and verify it in constant time. The program below builds PBKDF2 on top of HMAC and SHA-256 using only the standard library, stores the iteration count and salt next to the hash, and compares digests without leaking timing information. 

package main

import (
	"crypto/hmac"
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"strconv"
	"strings"
)

func pbkdf2(password, salt []byte, iterations, keyLen int) []byte {
	hashLen := sha256.Size
	blocks := (keyLen + hashLen - 1) / hashLen
	key := make([]byte, 0, blocks*hashLen)

	for block := 1; block <= blocks; block++ {
		mac := hmac.New(sha256.New, password)
		mac.Write(salt)
		mac.Write([]byte{byte(block >> 24), byte(block >> 16), byte(block >> 8), byte(block)})
		u := mac.Sum(nil)
		t := make([]byte, len(u))
		copy(t, u)

		for i := 1; i < iterations; i++ {
			mac.Reset()
			mac.Write(u)
			u = mac.Sum(nil)
			for j := range t {
				t[j] ^= u[j]
			}
		}
		key = append(key, t...)
	}

	return key[:keyLen]
}

func Hash(password string, iterations int) (string, error) {
	salt := make([]byte, 16)
	if _, err := rand.Read(salt); err != nil {
		return "", err
	}

	key := pbkdf2([]byte(password), salt, iterations, 32)
	return fmt.Sprintf("pbkdf2$%d$%s$%s", iterations,
		hex.EncodeToString(salt), hex.EncodeToString(key)), nil
}

func Verify(password, encoded string) bool {
	parts := strings.Split(encoded, "$")
	if len(parts) != 4 || parts[0] != "pbkdf2" {
		return false
	}

	iterations, err := strconv.Atoi(parts[1])
	if err != nil {
		return false
	}
	salt, err := hex.DecodeString(parts[2])
	if err != nil {
		return false
	}
	want, err := hex.DecodeString(parts[3])
	if err != nil {
		return false
	}

	got := pbkdf2([]byte(password), salt, iterations, len(want))
	return hmac.Equal(got, want)
}

func main() {
	encoded, _ := Hash("correct horse battery staple", 200000)
	fmt.Println(encoded)
	fmt.Println("correct:", Verify("correct horse battery staple", encoded))
	fmt.Println("wrong:  ", Verify("wrong password", encoded))
}

Run it and time the hash with time . Increase the iteration count until hashing takes about 500 ms on your machine, then explain why the salt is stored in plaintext. Extend the format to carry a pepper version, or replace the construction with a memory-hard function and compare the defender's cost with the attacker's.
