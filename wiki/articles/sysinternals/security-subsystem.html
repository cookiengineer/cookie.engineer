Security Subsystem

The Linux kernel's multi-layered security architecture - LSMs, capabilities, SELinux, AppArmor, seccomp, keyrings, audit, Landlock, IMA/E VM , and the Windows security model compared.

Overview

Kernel security is a stack of independent checks rather than one gate. This article walks the layers a syscall passes through: the LSM hook framework, capabilities, SELinux and AppArmor, seccomp, Landlock, keyrings, the audit subsystem, and IMA/E VM , then compares the Windows model. After reading it you can inspect and reason about each layer on a live system.

The Linux Security Model Stack

Linux security is not a single system but a stack of independent mechanisms, each operating at a different granularity. The kernel applies them in order, from coarse-grained to fine-grained:

Linux Security Module (LSM) Framework

The LSM framework provides hook points placed at every security-critical code path in the kernel. Each registered LSM can implement hooks to make access control decisions. The hooks are called in order, and if any hook denies access, the operation is blocked. 

LSM Architecture:

  struct security_hook_heads {
      struct hlist_head binder_set_context_mgr;
      struct hlist_head binder_transaction;
      struct hlist_head ptrace_access_check;
      struct hlist_head ptrace_traceme;
      struct hlist_head capget;
      struct hlist_head capset;
      struct hlist_head cred_alloc_blank;
      struct hlist_head cred_free;
      struct hlist_head cred_prepare;
      struct hlist_head cred_transfer;
      struct hlist_head kernel_act_as;
      struct hlist_head kernel_create_files_as;
      struct hlist_head kernel_module_request;
      struct hlist_head task_alloc;
      struct hlist_head task_free;
      struct hlist_head task_setrlimit;
      struct hlist_head task_kill;
      struct hlist_head inode_create;       // File creation check
      struct hlist_head inode_link;         // Hard link check
      struct hlist_head inode_unlink;       // File deletion check
      struct hlist_head inode_rename;       // File rename check
      struct hlist_head inode_permission;   // Read/write/execute check
      struct hlist_head file_open;          // open() check
      struct hlist_head file_ioctl;         // ioctl() check
      struct hlist_head mmap_addr;          // mmap() address check
      struct hlist_head mmap_file;          // mmap() file check

Hook call pattern

// include/linux/lsm_hooks.h — hook invocation
static inline int security_inode_permission(struct inode *inode, int mask)
{
    // Iterate all registered LSMs
    return call_int_hook(inode_permission, 0, inode, mask);
    //  ^^^^^^^^^^^^^^^^
    //  Returns first non-zero (deny) or 0 (allow)
}

// LSM registration (each LSM does this at init):
DEFINE_LSM(selinux) = {
    .name = "selinux",
    .init = selinux_init,
    .blobs = &selinux_blob_sizes,
};

Linux Capabilities Deep Dive

Capabilities break the monolithic root privilege into 40+ distinct bits. Each thread has five capability sets:

Capability Set Purpose
CapInh Inheritable - passed to children across exec
CapPrm Permitted - caps the thread could use
CapEff Effective - caps currently active
CapBnd Bounding set - hard upper bound (all threads)
CapAmb Ambient - preserved across non-setuid exec 
Capability Transition Rules (execve):

  1. Non-setuid-root exec:
     P'(permitted)   = P(inheritable) ∩ P(bounding)
     P'(effective)   = P'(ambient)   if P'(permitted) permits it, else empty
     P'(inheritable) = P(inheritable)  (unchanged)
     P'(ambient)     = P(ambient)      (unchanged if permitted)

  2. setuid-root / setcap exec (fI = file inheritable, fP = file permitted):
     P'(permitted)   = (P(inheritable) & B(inheritable)) |
                       (fP & B(permitted))
     P'(effective)   = fE ? P'(permitted) : 0
     P'(inheritable) = P(inheritable)
     P'(bounding)    = B(bounding)  (unchanged across exec — only init can narrow)

Key Capabilities

Capability Grants Ability To...
CAP_SYS_ADMIN Almost unrestricted (mount, swapon, sethost, setdomainname, pivot_root, clone(CLONE_NEW*))
CAP_SYS_PTRACE ptrace any process, read /proc/PID/mem
CAP_SYS_RAWIO iopl(), ioperm(), /dev/mem, /dev/port
CAP_NET_RAW Raw sockets (packet capture, spoofing)
CAP_NET_ADMIN Interface config, routing, iptables
CAP_SYS_MODULE Load/unload kernel modules

SELinux: Type Enforcement and MLS

SELinux implements Mandatory Access Control ( MAC ) using type enforcement. Every subject (process) and object (file, socket, etc.) is assigned a security context label. The policy defines which types can access which other types and in what ways. 

SELinux Security Context:

  system_u:object_r:httpd_sys_content_t:s0
  │        │        │                    │
  │        │        │                    └─ MLS level (s0 = SystemLow)
  │        │        └─ Type (the core identifier for TE rules)
  │        └─ Role (user_r, object_r, system_r)
  └─ User (system_u, unconfined_u, staff_u, user_u)

Type Enforcement Rule:
  allow httpd_t httpd_sys_content_t : file { read getattr open };
  │     │        │                    │    │
  │     │        │                    │    └─ Permissions
  │     │        │                    └─ Object class
  │     │        └─ Target type
  │     └─ Source type
  └─ Rule kind (allow, auditallow, dontaudit)

SELinux decision flow

  Userspace request: open("/var/www/index.html", O_RDONLY)
       │
       ▼
  DAC check (mode bits, uid/gid) ──► Denied? ──► EACCES (never reaches MAC)
       │ Approved
       ▼
  LSM hook: security_inode_permission()
       │
       ▼
  SELinux hook: selinux_inode_permission()
       │
       ▼
  AVC (Access Vector Cache) lookup:
  ┌──────────────────────────────────────────────────┐
  │ Query: { httpd_t, httpd_sys_content_t, file,     │
  │          { read getattr open } }                 │
  │                                                  │
  │ AVC cache hit?                                   │
  │   Yes → return cached decision                    │
  │   No  → Compute: query security server (policy)  │
  │         Decision → cache in AVC → return result   │
  └──────────────────────────────────────────────────┘
       │
       ▼
  Allowed → proceed    Denied → EACCES + AVC log:
    type=AVC msg=audit(1234567890.123:456): avc: denied { read }
    for pid=1234 comm="httpd" name="index.html"
    dev="sda1" ino=5678
    scontext=system_u:system_r:httpd_t:s0
    tcontext=system_u:object_r:httpd_sys_content_t:s0
    tclass=file permissive=0

AppArmor

AppArmor takes a path-based approach: profiles are attached to executables by path, and each profile lists the exact filesystem paths and operations permitted. 

AppArmor Profile Structure:

  /usr/bin/myapp {
      #include <abstractions/base>        # Base system access
      #include <abstractions/nameservice> # DNS resolution

      capability net_raw,              # Specific caps allowed
      capability setuid,

      /etc/myapp/** r,                 # Read config files
      /var/log/myapp/* w,              # Write logs
      /var/run/myapp.pid rw,           # Read/write PID file
      /tmp/myapp-* rwlk,               # r/w/link/lock in /tmp

      network inet stream,             # TCP sockets
      network inet dgram,              # UDP sockets

      signal peer=@{profile_name},     # Signal handling

      deny /etc/shadow r,              # Explicit deny overrides allow
      deny @{HOME}/.ssh/** rw,         # Protect SSH keys
  }

  Modes:
    complain: log violations but don't block (audit-only)
    enforce:  block violations and log
						
# AppArmor status
sudo aa-status

# List loaded profiles
sudo aa-status --profiled

# List processes with AppArmor profiles
sudo aa-status --processes

# Check if a specific binary is confined

# Profile management
sudo aa-complain /usr/bin/myapp   # Switch to complain mode
sudo aa-enforce /usr/bin/myapp    # Switch to enforce mode
sudo aa-disable /usr/bin/myapp    # Disable the profile

#   pid=1234 comm="myapp" requested_mask="r" denied_mask="r"

seccomp - Secure Computing Mode

seccomp restricts the system calls a process can make. There are two modes:

seccomp modes:

  SECCOMP_SET_MODE_STRICT (legacy):
    Only allowed syscalls: read, write, _exit, sigreturn
    Any other syscall → SIGKILL
    Simple but severely limited — only useful for compute-only tasks

  SECCOMP_SET_MODE_FILTER (seccomp-bpf):
    Syscall filtering via BPF programs
    Each syscall number + arguments can be checked
    Actions: ALLOW, KILL, TRAP, ERRNO, TRACE, LOG
    Nested filters combined by priority

seccomp-bpf Filter

// seccomp filter in Berkeley Packet Filter bytecode:
// Allow: write, read, exit, exit_group, rt_sigreturn
// Default: kill

// Generated by: scmp_bpf_sim -a x86_64
// Pseudo-C representation:
#include <linux/seccomp.h>
#include <linux/filter.h>

static struct sock_filter filter[] = {
    // Load architecture (ensure we're x86-64)
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, arch)),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_X86_64, 1, 0),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL),  // Wrong arch → kill

    // Load syscall number
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),

    // write(1) → allow
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_write, 4, 0),

    // read(0) → allow
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_read, 3, 0),

    // exit / exit_group / rt_sigreturn → allow
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_exit, 0, 1),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_exit_group, 1, 0),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_rt_sigreturn, 0, 1),

    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL),  // Default: kill
};

libseccomp - the practical API

#include <seccomp.h>
#include <stdio.h>

int main() {
    scmp_filter_ctx ctx;

    // Initialize with default action: kill process on disallowed syscall
    ctx = seccomp_init(SCMP_ACT_KILL);
    if (!ctx) { perror("seccomp_init"); return 1; }

    // Allow essential syscalls
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 0);
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read), 0);
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit), 0);
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit_group), 0);
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(rt_sigreturn), 0);

    // Allow write() only to fd 1 (stdout) and fd 2 (stderr)
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
        SCMP_A0(SCMP_CMP_EQ, 1));  // arg0 (fd) == 1

    seccomp_load(ctx);
    seccomp_release(ctx);

    // Now only baseline syscalls work
    printf("This uses write() → works\n");

    // Any other syscall → SIGKILL
    // open("/etc/passwd", O_RDONLY) → DEAD
    return 0;
}

User Namespaces and Cap Mapping

User namespaces allow an unprivileged user to be root inside a namespace. Capabilities are mapped between namespaces: 

┌─────────────────────────────────────────────────────────────────┐
│  Outer User Namespace (init_user_ns)                             │
│                                                                  │
│  UID 1000 (cookiengineer)                                       │
│    └── unshare(CLONE_NEWUSER) ──►                              │
│                                                                  │
│        ┌─────────────────────────────────────────────────────┐  │
│        │  Inner User Namespace                               │  │
│        │                                                     │  │
│        │  /proc/PID/uid_map:  0 1000 1                       │  │
│        │  /proc/PID/gid_map:  0 1000 1                       │  │
│        │                                                     │  │
│        │  Inner UID 0 ⟷ Outer UID 1000                       │  │
│        │  Process appears as root inside, cookiengineer outside│  │
│        │                                                     │  │

│        │  - Network: isolated by net namespace                │  │

Linux Audit Subsystem

The audit subsystem logs security-relevant events to a persistent log. Events can be generated by syscall auditing, file watches, LSM denials (AVC), and user-space messages: 

# Check audit status
sudo auditctl -s
# enabled 1, pid 345 (auditd), rate_limit 0, backlog_limit 8192

# List active audit rules
sudo auditctl -l

# Common audit rules:
# Watch /etc/shadow for writes
sudo auditctl -w /etc/shadow -p wa -k shadow_changes

# Audit all execve calls by UID 1000
sudo auditctl -a always,exit -F arch=b64 -S execve -F uid=1000 -k user_exec

# Audit all privilege escalations
sudo auditctl -a always,exit -F arch=b64 -S execve -F euid=0 -k root_exec

# Audit chmod on sensitive paths
sudo auditctl -a always,exit -F arch=b64 -S chmod,fchmod,fchmodat \
    -F dir=/etc -k etc_perms

# Search the audit log
sudo ausearch -k shadow_changes -ts today
sudo ausearch -m avc -ts recent   # SELinux denials
sudo ausearch -m syscall -sc execve -ui 1000
sudo ausearch -m user_avc        # AppArmor denials

# Generate a report
sudo aureport --summary
sudo aureport -x --summary       # Executable summary
sudo aureport -f --summary       # File access summary

Landlock Sandboxing

Landlock enables unprivileged processes to sandbox themselves by restricting which filesystem paths they can access. Unlike seccomp (syscall-level), Landlock operates at the filesystem level: 

// Landlock example: restrict process to read-only /tmp access
#include <linux/landlock.h>
#include <sys/prctl.h>
#include <sys/syscall.h>

int main() {
    int ruleset_fd;
    struct landlock_ruleset_attr ruleset_attr = {
        .handled_access_fs = LANDLOCK_ACCESS_FS_READ_FILE |
                             LANDLOCK_ACCESS_FS_WRITE_FILE |
                             LANDLOCK_ACCESS_FS_EXECUTE,
    };

    ruleset_fd = syscall(__NR_landlock_create_ruleset, &ruleset_attr,
                         sizeof(ruleset_attr), 0);
    if (ruleset_fd < 0) { perror("landlock_create_ruleset"); return 1; }

    // Allow read and execute on /tmp
    struct landlock_path_beneath_attr path_attr = {
        .allowed_access = LANDLOCK_ACCESS_FS_READ_FILE |
                          LANDLOCK_ACCESS_FS_EXECUTE |
                          LANDLOCK_ACCESS_FS_READ_DIR,
        .parent_fd = open("/tmp", O_PATH | O_CLOEXEC),
    };

    syscall(__NR_landlock_add_rule, ruleset_fd,
            LANDLOCK_RULE_PATH_BENEATH, &path_attr, 0);
    close(path_attr.parent_fd);

    // Enforce the ruleset (cannot be undone!)
    prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
    syscall(__NR_landlock_restrict_self, ruleset_fd, 0);
    close(ruleset_fd);

    // After this point:
    //   open("/etc/passwd", O_RDONLY) → EACCES
    //   open("/tmp/test.txt", O_RDONLY) → succeeds
    printf("Landlock sandbox active\n");
    return 0;
}

IMA and EVM

IMA measures files before they are executed or read, creating an integrity baseline. E VM protects file metadata (extended attributes) from offline tampering: 

IMA measurement flow:

  file_open() or file_mmap()
       │
       ▼
  ima_file_check()
       │
       ▼
  Check: is this file in the IMA policy?
       │ No → allow (no measurement)
       │ Yes
       ▼
  Compute file hash (SHA256 typically)
       │
       ▼
  Extend TPM PCR 10 with the hash
  Add entry to /sys/kernel/security/ima/ascii_runtime_measurements:
    PCR   template-hash   filename-hint   file-hash
    10    sha256:abcd...  /usr/bin/bash  sha256:ef01...

  IMA appraisal: verify the stored hash matches the expected hash
    (requires file signatures or ima-evm-utils signed xattrs)
						
# Check IMA status
sudo cat /sys/kernel/security/ima/policy
sudo cat /sys/kernel/security/ima/ascii_runtime_measurements | tail -20

# IMA appraisal (if enabled)
sudo cat /sys/kernel/security/ima/appraise

# EVM status
sudo cat /sys/kernel/security/evm

# Show IMA xattrs on a file
getfattr -m security.ima /usr/bin/bash 2>/dev/null
getfattr -m security.evm /usr/bin/bash 2>/dev/null

# Check TPM PCRs (requires tpm2-tools)
sudo tpm2_pcrread sha256:10 2>/dev/null

Windows Comparison

Windows security is fundamentally different - it is identity-based (SIDs) with ACL -based access control, layered with integrity levels and mandatory integrity control:

Concept Linux Windows
Identity UID/GID (16-bit/32-bit) SID (variable-length)
Primary ID Numeric UID Security Identifier (SID) S-1-5-21-DOMAIN-RID
Group model Primary + supplementary Token groups (SIDs)
Process token struct cred Access Token (kernel object)
Access check Mode bits (rwx for u/g/o) + POSIX ACLs (setfacl) DACL (Discretionary ACL); ACEs: Allow/Deny SID + Mask
Mandatory Access Ctl SELinux/AppArmor (optional); LSMs + capability bounding Mandatory Integrity Control; IL: Low, Medium, High, System
Capabilities CAP_* bits (40+); Per-process set Privileges (SE_* constants); Enabled/Disabled per token
Sandboxing seccomp, Landlock, namespaces Restricted tokens, AppCont.
Audit auditd + audit.rules Event Log + SACL entries
Integrity Verification IMA/EVM (file measurement); TPM-backed verification Code Integrity (CI), ELAM; Secure Boot -> Measured Boot
Keyring kernel keyring (keyctl) DPAPI, CNG key storage
Namespace User/PID/net/mount/... ns Silo (Server), AppContainer

Windows Integrity Levels

Level         SID                            Use
══════════    ═════════════════════════════  ═════════════════
Untrusted     S-1-16-0                      Anonymous logins
Low           S-1-16-4096                   IE Protected Mode, Edge
Medium        S-1-16-8192                   Standard user processes
High          S-1-16-12288                  Administrators (UAC)
System        S-1-16-16384                  Services, SYSTEM account
Installer     S-1-16-32768                  Trusted Installer

Rule: A process can write only to objects with equal or lower IL (no-write-up).
      Read-up is allowed by default; a mandatory label can deny read.
