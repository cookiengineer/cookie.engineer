Kernel Debugging

The kernel debugging stack covering KGDB, GDB with QEMU, kdump and crash, KDB, drgn, Oops analysis, debug symbols, and the KASAN, UBSAN, and KCSAN sanitizers.

Overview

A kernel bug can halt the whole machine, so debugging it needs different tools than a user-space program: an in-kernel debugger, a remote GDB stub, a reserved-memory crash dump, or a post-mortem analyzer. This article covers all four, plus how to read an Oops, where to find debug symbols, and which sanitizers catch memory and concurrency bugs early. After reading it you can stand up a QEMU plus GDB session and triage a vmcore .

Required Reading

  • Kernel Architecture - kernel layout, compilation, entry points, K PT I, MSRs, ring transitions
  • System Call Dispatch - syscall entry/exit, pt_regs, SYS CA LL_DEFINE macros, kernel stack layout

The Kernel Debugging Landscape

Debugging a kernel is fundamentally different from debugging user-space programs. There is no parent process, no core dump file by default, and a bug often means the machine is dead - no interactive GDB, no remote procfs, nothing. The tooling must work either on a live but degraded system (KDB), on a deliberately halted system (KGDB), or on a post-mortem memory image (crash/drgn on vmcore).

Debugging Approach Matrix:

Method Requires Best For Availability
KDB Serial/console Hung kernel Mainline
KGDB + GDB Serial + 2nd machine Interactive step-debug Mainline
Kdump + crash kexec + reserved RAM Post-mortem forensics Mainline
QEMU + GDB QEMU + guest kernel Development + testing Always
drgn /proc/kcore or vmcore Live inspection Mainline + external tool
kgdb over USB/NET Special HW Embedded Kernel patch
printk + dmesg Nothing Prod logs Always
/proc/kcore Nothing Live read Often disabled
bpftrace BPF kernel support Dynamic tracing 4.x+

KDB: Built-in Kernel Debugger

KDB is built directly into the kernel. When the kernel hits a breakpoint, oops, or you trigger it manually, KDB takes over the console. It's a single-threaded, assembly-level debugger that runs on the bare metal.

# Enable KDB at boot (kernel command line):
#   kdb=on   — KDB activated early
#   kgdboc=ttyS0,115200 — KDB I/O over serial
#   kgdbwait — halt at boot and wait for KGDB connection

# Trigger the debugger on a running system:
echo g > /proc/sysrq-trigger        # Enter KGDB/KDB
echo h > /proc/sysrq-trigger        # Print the sysrq help

# Enable sysrq-trigger:
echo 1 > /proc/sys/kernel/sysrq

KDB commands

KDB> help                          # List all commands
KDB> bt                            # Backtrace current CPU
KDB> btc                           # Backtrace all CPUs
KDB> ps                            # Process list (KDB version)
KDB> dmesg                         # Dump kernel log buffer
KDB> md <addr>                     # Memory dump (hex)
KDB> mdw <addr>                    # Memory dump (words)
KDB> rd                            # Register dump
KDB> rmregs                        # Register dump for all CPUs
KDB> bp <addr>                     # Set breakpoint
KDB> bph <addr>                    # Set hardware breakpoint
KDB> bc <num>                      # Clear breakpoint
KDB> bl                            # List breakpoints
KDB> ss                            # Single step
KDB> go                            # Continue execution
KDB> reboot                        # Reboot immediately
KDB> sr <proc>                     # Switch to process context
KDB> summary                       # System summary
KDB> pid <pid>                     # Show task_struct for PID
KDB> bta                           # Backtrace for all tasks
						
# Check if KDB is compiled in
zcat /proc/config.gz 2>/dev/null | grep CONFIG_KGDB
grep CONFIG_KGDB /boot/config-$(uname -r) 2>/dev/null

# Serial console setup for KDB/KGDB
sudo systemctl enable serial-getty@ttyS0.service 2>/dev/null
# Kernel cmdline: console=ttyS0,115200n8 kgdboc=ttyS0,115200

KGDB: Remote GDB Debugging

KGDB exposes the kernel to GDB over a serial line (or USB , or Ethernet). You need two machines: the "target" running the kernel under test, and the "host" running GDB connected via serial.

KGDB Architecture:
══════════════════

    Host Machine                         Target Machine
    ─────────────                        ──────────────
    GDB                                    Kernel
      │                                      │
      │  target remote /dev/ttyUSB0          │  kgdboc=ttyS0
      │──────────────────────────────────────►│
      │                                      │
      │  break do_sys_openat2                │  patched int3 at addr
      │──────────────────────────────────────►│
      │                                      │
      │  continue                             │
      │──────────────────────────────────────►│
      │                                      │  openat syscall → trap
      │                            CPU halted │
      │◄──────────────────────────────────────│
      │                                      │
      │  info registers                      │
      │──────────────────────────────────────►│
      │                                      │
      │◄───────── reg dump ──────────────────│
      │                                      │
      │  x/20i $rip                          │
      │──────────────────────────────────────►│
      │◄───────── disassembly ───────────────│
      │                                      │
      │  continue                             │
      │──────────────────────────────────────►│
      │                                      │  All CPUs resume

Setup procedure

# Target kernel cmdline (add to GRUB/SD-boot):
kgdbwait kgdboc=ttyS0,115200 nokaslr

# Host — connect GDB:
gdb /usr/lib/debug/boot/vmlinux-$(uname -r)
(gdb) set serial baud 115200
(gdb) target remote /dev/ttyUSB0
(gdb) continue

# Module debug symbols:
gdb /usr/lib/debug/boot/vmlinux-$(uname -r)
(gdb) add-symbol-file /path/to/module.ko <text_addr> \
    -s .data <data_addr> -s .bss <bss_addr>
# Get addresses from /sys/module/<name>/sections/.text

KGDB internals

// kernel/debug/kdb/kdb_main.c + kernel/debug/debug_core.c
// When kgdb_handle_exception() is called (from break, NMI, or panic):

static int kgdb_handle_exception(int evector, int signo,
                                  int ecode, struct pt_regs *regs)
{
    // 1. Halt all other CPUs via IPI (NMI)
    // 2. Enter KDB/KGDB prompt on primary CPU
    // 3. Poll the I/O driver (serial, USB, eth) for GDB commands
    // 4. Process GDB protocol: 'g' (read regs), 'm' (read mem),
    //    'Z0' (set breakpoint), 'c' (continue), 's' (step)
    // 5. On continue: remove single-step flags, resume all CPUs
    return 0;
}

QEMU + GDB Sandbox

For kernel development, QEMU's built-in GDB stub is the gold standard. No serial cable needed

  • -s opens a GDB server on :1234 .

QEMU Debugging Setup:
═════════════════════

    Terminal 1:                         Terminal 2:
    ───────────                         ───────────
    qemu-system-x86_64                  gdb vmlinux
      -kernel bzImage                     (gdb) target remote :1234
      -s              ← GDB stub on :1234 (gdb) hbreak start_kernel
      -S              ← Freeze at boot    (gdb) continue
      -append "nokaslr"                (gdb) info threads
      -initrd initramfs.img            (gdb) p *init_task
      -enable-kvm                       (gdb) bt
                                         (gdb) list
                                         (gdb) stepi
                                         (gdb) x/32i $rip
						
# Minimal QEMU kernel debugging lab:
# 1. Build or obtain a kernel
ls /boot/vmlinuz-linux     # Arch default kernel
cp /boot/vmlinuz-linux /tmp/bzImage

# 2. Create a minimal initramfs
mkdir -p /tmp/initramfs/{bin,dev,proc,sys}
cp /usr/bin/busybox /tmp/initramfs/bin/
cat > /tmp/initramfs/init << 'HEREDOC'
#!/bin/busybox sh
mount -t proc proc /proc
mount -t sysfs sysfs /sys
mount -t devtmpfs devtmpfs /dev
exec /bin/busybox sh
HEREDOC
chmod +x /tmp/initramfs/init
(cd /tmp/initramfs && find . | cpio -o -H newc | gzip > /tmp/initramfs.img)

# 3. Start QEMU with GDB stub
qemu-system-x86_64 \
    -kernel /tmp/bzImage \
    -initrd /tmp/initramfs.img \
    -append "console=ttyS0 nokaslr earlyprintk=serial" \
    -nographic \
    -s -S &
QEMU_PID=$!

# 4. Connect GDB
gdb /usr/lib/debug/boot/vmlinux-$(uname -r) \
    -ex "target remote :1234" \
    -ex "hbreak start_kernel" \
    -ex "continue"
# Kill QEMU when done:
kill $QEMU_PID 2>/dev/null

Useful GDB commands for kernel debugging

(gdb) target remote :1234            # Connect to QEMU GDB stub
(gdb) hbreak start_kernel             # Hardware breakpoint at boot
(gdb) hbreak do_syscall_64           # Break on every syscall entry
(gdb) break __x64_sys_openat         # Break on specific syscall
(gdb) condition 1 $rdi==3            # Only when fd==3
(gdb) info registers                  # Full register dump
(gdb) info threads                    # List CPUs (one thread per VCPU)
(gdb) thread 2                        # Switch to VCPU 2
(gdb) bt                             # Kernel stack backtrace
(gdb) p/x &init_task                 # Print address of init_task
(gdb) p *(struct task_struct *)0xffff12345 # Dump task struct
(gdb) x/32wx $rsp                    # 32 words at stack pointer
(gdb) monitor info cpus              # QEMU-specific: CPU info
(gdb) monitor info mem               # QEMU: memory regions
(gdb) monitor print $cr3             # QEMU: read control register
(gdb) continue
(gdb) stepi                          # Step one instruction
(gdb) finish                         # Finish current function
(gdb) info breakpoints
(gdb) delete 1
(gdb) disassemble /m __x64_sys_read  # Mixed source+asm

Crash Dumps: kdump + kexec

When the kernel panics, kdump uses kexec to boot a fresh "capture kernel" from a reserved memory region. The capture kernel copies the crashed kernel's memory to disk as /proc/vmcore .

kdump Flow:
══════════

    Normal Kernel                          Crash
    ─────────────                          ─────

    ┌─────────────────┐                   ┌─────────────────┐
    │  System RAM     │                   │ PANIC!          │
    │                 │                   │                 │
    │ ┌─────────────┐ │                   │ 1. panic()      │
    │ │  reserved    │ │                   │ 2. smp_send_stop()
    │ │  crashkernel │ │                   │ 3. machine_crash_
    │ │  memory      │ │──────────────────►│    shutdown()   │
    │ │              │ │                   │ 4. boot capture │
    │ │  (e.g. 256M) │ │                   │    kernel from  │
    │ └─────────────┘ │                   │    reserved mem  │
    │                 │                   │                 │
    │ ┌─────────────┐ │                   │ 5. capture kernel│
    │ │  production  │ │                   │    finds crashed │
    │ │  kernel +    │ │                   │    kernel's RAM  │
    │ │  userspace   │ │                   │    via ELF header│
    │ └─────────────┘ │                   │                 │
    └─────────────────┘                   │ 6. makedumpfile: │
                                          │    compress &    │
                                          │    copy to disk  │
                                          │                 │
                                          │ 7. reboot        │
                                          └─────────────────┘
                                          │
                                          ▼
                                    /var/crash/<ts>/vmcore
						
# Install kdump on Arch
sudo pacman -S kexec-tools
# Configure crashkernel memory (add to GRUB_CMDLINE_LINUX):
# crashkernel=256M
sudo grub-mkconfig -o /boot/grub/grub.cfg

# Enable kdump service
sudo systemctl enable kdump.service
sudo systemctl start kdump.service

# Verify crash kernel is reserved
cat /proc/cmdline | grep -o 'crashkernel=[^ ]*'
dmesg | grep -i crashkernel

# Test kdump (CAREFUL — this WILL reboot the machine!)
# sudo bash -c 'echo c > /proc/sysrq-trigger'
# After reboot, find vmcore:
ls -la /var/crash/

# Inspect vmcore
crash /usr/lib/debug/boot/vmlinux-$(uname -r) /var/crash/<timestamp>/vmcore

The crash Utility

crash is the standard tool for post-mortem crash dump analysis. It is built on top of GDB but adds kernel-aware commands.

crash session — (crash> prompt):

crash> bt                          # Backtrace of crashed task
PID: 0      TASK: ffff888100000000 CPU: 2   COMMAND: "swapper/2"
 #0 [fffffe0000008e88] panic at ffffffff81c12345
 #1 [fffffe0000008f30] __list_del at ffffffff813a5600
 #2 [fffffe0000008f58] do_exit at ffffffff810a1234
 ...

crash> ps                          # Process list (from memory image)
   PID    PPID  CPU  TASK         ST  %MEM  VSZ   RSS  COMM
   1      0      0  ffff888100001000 IN   0.0   4096  1024 systemd
   123    1      1  ffff888100002000 RU   0.1  16384  4096 sshd

crash> files <pid>                 # Open files of a process
crash> kmem -i                     # Memory usage summary
crash> kmem -s                     # Slab cache info
crash> mod                         # Loaded modules at crash time
crash> log                         # Kernel log buffer (dmesg at crash)
crash> mach                       # CPU / hardware info
crash> net                         # Network info
crash> dev                         # Block/char device list
crash> sys                         # System info (kernel ver, hostname, ...)
crash> foreach bt                  # Backtrace ALL tasks
crash> struct task_struct ffff888100001000  # Dump struct
crash> union thread_union ffff888100000000 # Dump union
crash> sig <pid>                   # Pending signals for process
crash> vm <pid>                    # Virtual memory mappings
crash> irq                         # IRQ statistics
crash> timer                       # Kernel timers
crash> runq                        # Runqueue contents
crash> help                        # HUGE list of commands
						
# Install crash
sudo pacman -S crash

# Get debug kernel (Arch)
sudo pacman -S linux-$(uname -r)-debug 2>/dev/null || \
    echo "Debug kernel not in repos — build from source"

# Example: analyze your own /proc/kcore (live analysis)
sudo crash /usr/lib/debug/boot/vmlinux-$(uname -r) /proc/kcore 2>/dev/null
# WARNING: /proc/kcore is often restricted on modern kernels (lockdown)

drgn: Programmable Kernel Debugger

drgn (pronounced "dragon") is a modern Python-based kernel debugger that works on both live systems (via /proc/kcore ) and vmcore files. It provides Python API s for kernel data structures, iterating tasks, and correlating memory.

#!/usr/bin/env python3
# drgn live inspection script
import drgn
from drgn.helpers.linux import (
    for_each_task, find_task, list_for_each_entry,
    pid, task_state_to_char, hlist_for_each_entry
)
from drgn.helpers.linux.mm import for_each_vma

prog = drgn.program_from_kernel()  # Attach to live kernel

# List all tasks
for task in for_each_task(prog):
    print(f"PID {task.pid.value_():6d} {task.comm.string_().decode():16s} "
          f"state={task_state_to_char(task)}")

# Find a specific task by PID
task = find_task(prog, 1)
print(f"systemd: {task.comm.string_().decode()}")

# Explore data structures
print(prog.type('struct task_struct'))           # Layout
print(prog['jiffies'].value_())                  # Global variable

# Walk dentry cache
for dentry in for_each_task(prog):
    break  # simplified — full examples in drgn docs

# Access vmcore
# prog = drgn.program_from_core_dump(vmlinux_path, vmcore_path)

# Iterate loaded modules
for mod in list_for_each_entry(
    'struct module', prog['modules'].address_of_(), 'list'
):
    print(f"Module: {mod.name.string_().decode()}")
						
# Install drgn
sudo pacman -S drgn
pip install drgn  # also available as Python module

# Live inspection (root required)
sudo drgn

# Analyze a vmcore
sudo drgn -s /usr/lib/debug/boot/vmlinux-$(uname -r) /var/crash/*/vmcore

# Scripted analysis
cat > /tmp/tasks.py << 'HEREDOC'
import drgn
from drgn.helpers.linux import for_each_task, task_state_to_char

prog = drgn.program_from_kernel()
for task in for_each_task(prog):
    print(f"{task.pid.value_():6d} {task.comm.string_().decode():20s} {task_state_to_char(task)}")
HEREDOC
sudo python3 /tmp/tasks.py

Live Debugging: /proc/kcore and /dev/mem

/proc/kcore — the kernel's memory as a file
════════════════════════════════════════════

    /proc/kcore is an ELF core file that maps the entire physical
    address space. Opening it gives read access to kernel memory
    (subject to lockdown restrictions).

    Size: equal to physical RAM + offset (appears enormous)
    $ ls -lh /proc/kcore
    -r-------- 1 root root 128T ... /proc/kcore

    It's sparse: only pages in RAM are accessible. Attempting to
    read unmapped physical addresses returns zeros.

    Kernel lockdown (confidentiality mode) blocks access entirely.

/dev/mem — physical memory device
═════════════════════════════════

    /dev/mem provides byte-addressable access to physical memory.
    Modern kernels heavily restrict it:
    - CONFIG_STRICT_DEVMEM: only first 1MB accessible (BIOS/legacy)
    - CONFIG_DEVMEM: may not exist at all
    - Kernel lockdown blocks it entirely
						
# Check /proc/kcore access
ls -la /proc/kcore
sudo readelf -h /proc/kcore 2>/dev/null | head -10
# If "Permission denied": lockdown is active

# Check /dev/mem access
ls -la /dev/mem
sudo dd if=/dev/mem of=/tmp/first_mb bs=1024 count=1024 2>&1
# If "Operation not permitted": STRICT_DEVMEM or lockdown

# Check lockdown level
cat /sys/kernel/security/lockdown 2>/dev/null

Debug Symbols and vmlinux

Debugging without symbols is near-impossible. The vmlinux file (uncompressed kernel ELF) contains the full symbol table, DWARF debug info, and source line mappings.

Symbol availability chain:
══════════════════════════

    vmlinux (ELf, ~600MB with debug)
        │
        ├──► stripped → bzImage (compressed, no debug info)
        │
        ├──► debug info → /usr/lib/debug/boot/vmlinux-<ver>
        │    Installed by linux-<ver>-debug package
        │
        └──► extract-vmlinux: decompress bzImage → vmlinux
             (no debug info, just symbols from kallsyms)

    Kernel config options:
    CONFIG_DEBUG_INFO=y               DWARF4 debug info
    CONFIG_DEBUG_INFO_DWARF4=y        (or DWARF5)
    CONFIG_DEBUG_INFO_REDUCED=n        Full debug (bigger)
    CONFIG_DEBUG_INFO_BTF=y            BPF Type Format (for CO-RE)
    CONFIG_KALLSYMS=y                  /proc/kallsyms
    CONFIG_KALLSYMS_ALL=y              All symbols, not just functions
						
# Obtain debug kernel (Arch)
sudo pacman -S linux-$(uname -r | sed 's/\./-/g')-debug 2>/dev/null
# or: linux-zen-$(uname -r)-debug

# Verify debug symbols exist
file /usr/lib/debug/boot/vmlinux-$(uname -r) 2>/dev/null
readelf -S /usr/lib/debug/boot/vmlinux-$(uname -r) 2>/dev/null | \
    grep -E '\.debug_'

# Check kallsyms availability
sudo cat /proc/kallsyms | tail -5
# t/T = text (function), lowercase = local, uppercase = global

# Extract vmlinux from bzImage (no debug info)
# Requires extract-vmlinux script from kernel source
scripts/extract-vmlinux /boot/vmlinuz-linux > /tmp/vmlinux-extracted
file /tmp/vmlinux-extracted
readelf -s /tmp/vmlinux-extracted | head -20

Oops Message Analysis

An "Oops" is the kernel's way of saying "something went wrong but we can try to limp forward." A "panic" means "we cannot continue safely." Understanding the Oops output is a critical forensics skill.

Anatomy of a Linux Kernel Oops:
════════════════════════════════

  BUG: unable to handle page fault at ffffdeadbeeffeed
  #PF: supervisor read access in kernel mode
  #PF: error_code(0x0000) - not-present page
  PGD 0 P4D 0
  Oops: 0000 [#1] PREEMPT SMP PTI         ← Oops number, config flags
  CPU: 3 PID: 1234 Comm: my-driver Not tainted 6.1.0-arch1 #1
  Hardware name: QEMU Standard PC (i440FX + PIIX, 1996), BIOS 1.16.0
  RIP: 0010:my_buggy_function+0x37/0x80 [my_module]
  Code: 48 8b 07 48 8b 40 10 48 85 c0 74 0a ...
  RSP: 0018:ffffc9000012fe38 EFLAGS: 00010246
  RAX: ffffdeadbeeffeed RBX: ffff888100300000 RCX: 0000000000000000
  RDX: 0000000000000000 RSI: ...
  RBP: ...
  R10: ... R11: ... R12: ... R13: ... R14: ...
  FS: 00007f1234567890(0000) GS:ffff888123450000(0000) knlGS:0000000000000000
  CS: 0010 DS: 0000 ES: 0000 CR0: 0000000080050033
  CR2: ffffdeadbeeffeed CR3: 0000000100a00001 CR4: 0000000000170ee0
  Call Trace:
   <TASK>
   my_module_init+0x45/0x60 [my_module]
   do_one_initcall+0x5a/0x1a0
   do_init_module+0x4b/0x200
   ...
   </TASK>
  Modules linked in: my_module(O+) ...
  ---[ end trace ]---

Key fields:
  RIP: faulting instruction address → [func]+offset/length [module]
  Call Trace: stack walk — who called what?
  CR2: address that caused the page fault
  error_code: bit 0=protection (1=protection fault, 0=not present)
              bit 1=write(1)/read(0), bit 2=user(1)/supervisor(0)
              bit 3=reserved bit violation, bit 4=instruction fetch
						
# Force an oops for testing
echo 1 > /proc/sys/kernel/panic_on_oops   # PANIC on oops (safer)
echo 1 > /proc/sys/kernel/panic           # Auto-reboot after N secs

# Capture oops messages
journalctl -k --no-pager | grep -A50 'BUG:\|Oops:'

# Decode oops addresses to function names + line numbers
sudo ./scripts/decode_stacktrace.sh vmlinux < oops.txt
# Requires: vmlinux with debug info, kernel source tree

# Alternative: manual decode
gdb /usr/lib/debug/boot/vmlinux-$(uname -r) \
    -ex "list *(my_buggy_function+0x37)" -ex "quit"

BUG(), WARN(), and panic()

These three macros are the kernel's internal assertion mechanisms:

// include/asm-generic/bug.h

// BUG() — unrecoverable error, kills the process or panics
#define BUG() do {                                          \
    instrumentation_begin();                                 \
    __BUG_FLAGS(BUGFLAG_TAINT(BUGFLAG_TAINT_WARN) |         \
                BUGFLAG_ONCE);                               \
    unreachable();                                           \
} while (0)
// Behavior: if CONFIG_BUG_ON_DATA_CORRUPTION → WARN + try to continue
//           else → panic (or kill current process if panic_on_oops=0)

// WARN()/WARN_ON(condition) — recoverable anomaly, dump stack, continue
#define WARN(condition, format...) ({                       \
    int __ret_warn_on = !!(condition);                       \
    if (unlikely(__ret_warn_on))                             \
        __WARN_printf(TAINT_WARN, format);                   \
    unlikely(__ret_warn_on);                                 \
})
// Prints a warning, stack trace, taints kernel with TAINT_WARN

// WARN_ON_ONCE(condition) — only once per boot

// panic() — unrecoverable: halt system
void panic(const char *fmt, ...);
// 1. smp_send_stop() — halt all other CPUs
// 2. kmsg_dump — save kernel log to storage
// 3. emergency_restart() or infinite loop
						
# Kernel configuration for BUG/WARN behavior
zcat /proc/config.gz 2>/dev/null | grep -E 'PANIC_ON_OOPS|BUG_ON_DATA_CORRUPTION'

# BUG/WARN count since boot
cat /proc/sys/kernel/oops_limit    # Max oops before panic (default: 10000)
cat /proc/sys/kernel/warn_limit    # Max warnings before panic (default: 0=unlimited)

# See recent bugs in kernel log
dmesg | grep -E 'BUG:|WARNING:|Oops:|PANIC:' | tail -20

Kernel Sanitizers

Modern kernels can be compiled with runtime sanitizers that detect memory corruption, data races, and undefined behavior:

Kernel sanitizer overview:

Sanitizer Detects Slowdown Config
KASAN Out-of-bounds, use-after-free, double-free on heap/stack/global ~2-5x CONFIG_KASAN=y
KCSAN Data races (concurrency bugs) Variable (~10% idle) CONFIG_KCSAN=y
UBSAN Undefined behavior: integer overflows, shift-out-of-bounds, misaligned access, null deref ~1.2x CONFIG_UBSAN=y
KFENCE Low-overhead KASAN alternative (sampling-based) ~1% CONFIG_KFENCE=y
KMSAN Uninitialized memory reads ~3x CONFIG_KMSAN=y
KTSAN Thread sanitizer (experimental) ~5-10x Work-in-progress
LOCKDEP Lock ordering violations, deadlock potential detection ~2x CONFIG_LOCKDEP=y
KMEMLEAK Unreferenced memory (leak detection) ~1.1x CONFIG_DEBUG_KMEMLEAK=y

KASAN (Kernel Address Sanitizer)

// How KASAN detects out-of-bounds:
// Every slab allocation is surrounded by redzones (poisoned memory).
// KASAN inserts checks before every memory access at compile time.

// Original code:
void buggy(char *buf) {
    buf[256] = 'X';  // buf is only 128 bytes
}

// KASAN-instrumented (conceptual):
void buggy(char *buf) {
