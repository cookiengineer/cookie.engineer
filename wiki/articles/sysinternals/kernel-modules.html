Kernel Modules

Anatomy of Linux kernel modules - .ko ELF format, loading, relocation, symbol resolution, parameters, dependencies, signing, reference counting, hiding techniques, and module ABI verification.

Overview

A kernel module is a relocatable ELF object that the running kernel links into itself on demand. This article follows a .ko file from disk through init_module() , covering relocation, symbol resolution, parameters, dependency tracking, signing, reference counting, and the techniques rootkits use to hide a loaded module from lsmod .

Required Reading

  • Device Drivers - character/block/network drivers, device model, ioctl, mmap
  • Kernel Architecture - kernel compilation units, kbuild, init sequence, kernel sources

Anatomy of a .ko File

A kernel module ( .ko ) is an ELF relocatable object file - NOT a shared library and NOT an executable. It is position-independent code (compiled with -fPIC ) that expects to be linked into the kernel's address space at load time by the kernel's built-in linker. 

ELF Header Layout of a .ko file
══════════════════════════════════

┌──────────────────┐
│ ELF Header       │  e_type = ET_REL (relocatable), e_machine = EM_X86_64
├──────────────────┤
│ Section Table    │  
├──────────────────┤
│ .text            │  Executable driver code
│ .data            │  Initialized global data
│ .bss             │  Zero-initialized data (no disk space)
│ .rodata          │  Read-only data (strings)
│ .rodata.str1.1   │  Packed string literals
│ __versions       │  Module versioning checksums (CRC)
│ __param          │  Module parameter declarations
│ .modinfo         │  Module metadata (author, license, description, aliases)
│ .gnu.linkonce.   │  Per-CPU and per-module data
│   this_module    │  struct module itself, pre-initialized
│ .rela.text       │  Relocations for .text section
│ .rela.data       │  Relocations for .data section
│ .symtab          │  Symbol table (local + exported)
│ .strtab          │  Symbol name strings
│ .note.Linux      │  Linux note section (build info)
│ .note.gnu.       │  GNU build attributes
│   build-id       │  Unique build hash
└──────────────────┘

Inspect any .ko file: 

# Basic ELF info
readelf -h /lib/modules/$(uname -r)/kernel/drivers/char/lp.ko 2>/dev/null || \
readelf -h /lib/modules/$(uname -r)/kernel/drivers/char/mem.ko

# File type: ET_REL — relocatable object (not shared lib or executable)

# Section headers
readelf -S /lib/modules/$(uname -r)/kernel/drivers/block/loop.ko | head -60

# Symbol table (the interesting part)
readelf -s /lib/modules/$(uname -r)/kernel/drivers/block/loop.ko 2>/dev/null | \
    awk '$4 == "UND" {undef++} $4 != "UND" && $4 != "ABS" {defined++}
          END {print "Undefined: " undef ", Defined: " defined}'

# .modinfo — human-readable metadata
objdump -s -j .modinfo /lib/modules/$(uname -r)/kernel/drivers/block/loop.ko

# Relocations — what addresses need fixing up?
readelf -r /lib/modules/$(uname -r)/kernel/drivers/block/loop.ko | head -30

Module Loading and init_module()

The userspace tool insmod reads the .ko from disk, mmap's it, then calls the init_module() syscall. The kernel's load_module() function does all the heavy lifting: 

insmod echo_driver.ko
    │
    ▼
[Userspace]  open(".ko", O_RDONLY | O_CLOEXEC)
    │
    ▼
[Userspace]  mmap() the file →  fd size, file contents
    │
    ▼
[Userspace]  init_module(image, len, "")   ← syscall number 175 (x86-64)
    │
    │  ┌─── Kernel space ─────────────────────────────────────────┐
    │  │                                                           │
    ▼  ▼                                                           │
load_module(info, uargs, flags)   ← kernel/module/main.c           │
    │                                                              │
    │  1. copy_module_from_user()  — copy ELF to kernel memory     │
    │  2. layout_and_allocate()    — allocate memory for sections   │
    │  3. parse_elf()              — validate ELF, build section map│
    │  4. apply_relocations()      — fix up symbol references      │
    │  5. resolve_symbols()        — link against kernel exports    │
    │  6. check_module_license_and_versions() — CRC check, taint   │
    │  7. simplify_symbols()       — cleanup internal symbols       │
    │  8. post_relocation()        — init per-cpu, module params    │
    │  9. sysfs_create_module()    — create /sys/module/<name>      │
    │ 10. call do_init_module()    →  mod->init() (module_init macro)│
    │                                                              │
    ▼                                                              │
[Userspace]  init_module() returns 0                               │
    │                                                              │
    ▼                                                              │
Module is live — /sys/module/<name>/ created, probe() called       │

The key source file is 'kernel/module/main.c' .

Relocation and Kernel Symbols

Since modules are compiled independently, all references to kernel functions and data are relocatable entries. At load time, apply_relocations() processes .rela.text and .rela.data sections.

x86-64 Relocation Types

Relocation Value Description
R_X86_64_PC32 2 32-bit PC-relative: call function +/-2 GiB
R_X86_64_PLT32 4 Same, with PLT relaxation
R_X86_64_32S 11 32-bit sign-extended absolute (data)
R_X86_64_64 1 64-bit absolute (data references)
R_X86_64_GOT_PCREL 9 GOT-relative offset (rare in .ko)
R_X86_64_REX_GOTPCRELX 42 GOTPCRELX (optimized GOT reference) 
# See exactly which relocations a module needs
readelf -r /lib/modules/$(uname -r)/kernel/drivers/block/loop.ko 2>/dev/null | \
    awk '{print $3}' | sort | uniq -c | sort -rn | head -20

# Undefined symbols = kernel functions/data the module needs
readelf -s /lib/modules/$(uname -r)/kernel/drivers/block/loop.ko 2>/dev/null | \
    awk '$4 == "UND" {print $8}' | sort | head -20

Symbol Tables and /proc/kallsyms

The kernel maintains a symbol table of all exported functions and data. Only symbols marked EXPORT_SYMBOL() or EXPORT_SYMBOL_GPL() are available to modules. 

// include/linux/export.h (simplified logic)

// Standard export — available to all modules
#define EXPORT_SYMBOL(sym)                      \
    extern typeof(sym) sym;                     \
    __EXPORT_SYMBOL(sym, "")

// GPL-only export — only loadable by GPL-licensed modules
#define EXPORT_SYMBOL_GPL(sym)                  \
    extern typeof(sym) sym;                     \
    __EXPORT_SYMBOL(sym, "_gpl")
						
Kernel Symbol Visibility:

    /proc/kallsyms entries (address type name):
    
    ffffffff81000000 T _stext              ← Text (code), visible
    ffffffff810a1234 T sys_read            ← Exported by EXPORT_SYMBOL
    ffffffff810b5678 T __x64_sys_clone     ← Not exported (kallsyms only)
    ffffffff820a9abc D jiffies             ← Data, exported
    ffffffff8210cdef D nr_cpu_ids          ← Data, exported
    ffffffff83000000 t internal_func       ← lowercase 't': local, NOT exported
    ffffffff83123456 d internal_data       ← lowercase 'd': local, NOT exported
    
    Capital letter: global/exported (accessible to modules)
    Lowercase letter: local/internal (inaccessible to modules)
						
# Count exported symbols
sudo cat /proc/kallsyms | grep -c '^[0-9a-f]\+ [TDBR] '

# Find GPL-only exports
sudo cat /proc/kallsyms | grep '_gpl$' | head -10
# (The suffix is in the CRC metadata, not kallsyms directly)
# Better: check the source
grep -r 'EXPORT_SYMBOL_GPL' /usr/src/linux/kernel/ 2>/dev/null | head -10

# What symbols does a loaded module use?
lsmod | awk 'NR>1{print $1}' | while read mod; do
    echo "Module: $mod"
    sudo cat /sys/module/$mod/coresize 2>/dev/null
done

# Show symbols provided BY a module (modules can export too!)
sudo cat /proc/kallsyms | grep -E '\[nvidia\]|\[vboxdrv\]' | head -10

# Find symbol address by name
sudo cat /proc/kallsyms | grep ' sys_call_table$'

Module Parameters and sysfs Interface

Module parameters allow runtime configuration via command line or sysfs.

// include/linux/moduleparam.h

// Basic usage
static int my_int = 42;
static char *my_string = "default";
static bool my_bool = true;

module_param(my_int, int, 0644);
MODULE_PARM_DESC(my_int, "An example integer parameter");

module_param(my_string, charp, 0644);
MODULE_PARM_DESC(my_string, "An example string parameter");

module_param(my_bool, bool, 0644);
MODULE_PARM_DESC(my_bool, "An example boolean parameter");

// Array parameter
static int my_arr[4] = {1, 2, 3, 4};
static int arr_argc = 4;
module_param_array(my_arr, int, &arr_argc, 0644);
MODULE_PARM_DESC(my_arr, "An example array parameter");

// Parsed at module init time. Values come from:
//   insmod echo.ko my_int=100 my_string="hello" my_bool=0
// or written later via sysfs (if perm != 0):
//   echo 100 > /sys/module/echo/parameters/my_int

Module Dependencies: depmod and modprobe

A module may depend on symbols exported by another module. depmod builds the dependency graph, and modprobe loads modules and all their dependencies. 

Dependency Chain Example:

    usb_storage.ko
        └──► usbcore.ko (provides usb_register_driver, usb_submit_urb, ...)
                └──► nls_base.ko (optional, for FAT filesystem support)

    modules.dep entry:
    kernel/drivers/usb/storage/usb-storage.ko: kernel/drivers/usb/core/usbcore.ko
    
    modules.symbols entry:
    alias symbol:usb_register_driver usbcore
    alias symbol:usb_submit_urb usbcore
						
# See all module dependencies
cat /lib/modules/$(uname -r)/modules.dep | head -20

# Dependency tree for a specific module
modprobe --show-depends usb_storage

# Reverse dependencies (what depends on this module?)
modprobe -r --dry-run usbcore 2>&1 | head -10

# Which module provides symbol X?
modprobe --resolve-alias symbol:usb_submit_urb

# Device aliases — hardware-driven auto-loading
cat /lib/modules/$(uname -r)/modules.alias | grep 'pci:v00008086' | head -5
# udev uses these: when a device appears, it matches the alias and loads
# the module via modprobe

# Builtin aliases (compiled into the module's .modinfo)
modinfo usb_storage | grep alias

Module Signing and Kernel Lockdown

Since root can load arbitrary code into ring 0, module signing and lockdown provide defense-in-depth. The chain is: 

Module Signing Flow:
═══════════════════
    1. Distribution maintains a private key (stored securely, never in kernel)
    2. At build time: sign-file signs the .ko with the private key
    3. Kernel configured with: CONFIG_MODULE_SIG=y
                               CONFIG_MODULE_SIG_FORCE=y (optional: reject unsigned)
    4. Kernel embeds the public key at build time (in vmlinux)
    5. At load time: the kernel verifies the signature against the embedded public key
    6. Failure → module rejected, kernel can taint or panic

    Secure Boot extends this chain:
    UEFI Secure Boot → shim → GRUB → signed kernel → signed modules
						
# Check if kernel enforces module signatures
cat /proc/cmdline | grep module.sig
cat /sys/module/module/parameters/sig_enforce  # 1 = enforced

# Inspect a module's signature
modinfo -F sig_key usb_storage        # Who signed it?
modinfo -F sig_hashalgo usb_storage   # SHA-256, SHA-512?
modinfo -F signer usb_storage         # Full signer info

# Verify signature on disk
modinfo -F sig_key /lib/modules/$(uname -r)/kernel/drivers/block/loop.ko

# Which key is embedded in the running kernel?
sudo keyctl list %:.builtin_trusted_keys 2>/dev/null

# Lockdown state
cat /sys/kernel/security/lockdown 2>/dev/null || \
cat /sys/kernel/security/lockdown 2>/dev/null
# none / integrity / confidentiality

Lockdown modes

Mode Description
none No restrictions
integrity Kernel image, initramfs, modules must be signed. /dev/mem, /dev/kmem blocked. kexec restricted. Hibernate restricted. PCI BAR access restricted.
confidentiality Integrity mode +: /proc/kcore blocked. User access to kernel addresses via /proc/kallsyms blocked. BPF restrictions. Trace restrictions.

Module Reference Counting

Modules can't be unloaded while code inside them is executing. The refcount system prevents this: 

// include/linux/module.h
struct module {
    // ...
    int num_exentries;          // Reference count from external users
    atomic_t refcnt;            // Internal reference count
    // ...
};

// Common API:
int try_module_get(struct module *mod);   // Increment refcount, fail if unloading
void module_put(struct module *mod);      // Decrement refcount

// Used primarily for cross-module callbacks. Example:
// If module A registers a callback with module B's infrastructure,
// module A must take a reference to module B so B can't unload
// while A's callback might fire.
						
# Module reference count
lsmod | awk '{print $1, $3, $4}' | head -10
# Column 3: size; Column 4: used by (ref count + dependent modules)

# Detailed view: what uses each module
lsmod | awk 'NR>1{printf "%-25s used by: %s\n", $1, $4}' | head -20

# Check if a module is safe to unload
sudo rmmod --dry-run loop

Module Initialization and Cleanup

// The two required entry/exit points

// 1. Init function — runs once at load time
//    Returns 0 for success, negative errno on failure
static int __init my_module_init(void)
{
    pr_info("Module loaded at %p\n", my_module_init);
    return 0;
}
module_init(my_module_init);

// __init — tells linker to put this function in .init.text section
//          which is freed after module init completes (memory saving)

// 2. Exit function — runs at unload
static void __exit my_module_exit(void)
{
    pr_info("Module unloaded\n");
}
module_exit(my_module_exit);

// __exit — discard after init if module is built-in (not a module)
//          puts function in .exit.text

// If no exit function: module is permanently loaded (cannot rmmod)

Module Device Table Auto-loading

When hardware appears, the kernel must find the right driver. The MODULE_DEVICE_TABLE() macro embeds device IDs into the module's .modinfo section. depmod extracts these into /lib/modules/<ver>/modules.alias . udev matches hardware against these aliases and calls modprobe . 

// PCI device table
static const struct pci_device_id my_pci_ids[] = {
    { PCI_DEVICE(0x1234, 0x5678) },  // Vendor:Device ID
    { PCI_DEVICE(0x1234, 0x9ABC) },
    { }  // Terminating zero entry
};
MODULE_DEVICE_TABLE(pci, my_pci_ids);

// USB device table
static const struct usb_device_id my_usb_ids[] = {
    { USB_DEVICE(0x1234, 0x5678) },
    { }
};
MODULE_DEVICE_TABLE(usb, my_usb_ids);

// ACPI table
static const struct acpi_device_id my_acpi_ids[] = {
    { "PNP0C0D", 0 },
    { }
};
MODULE_DEVICE_TABLE(acpi, my_acpi_ids);
						
# Device ID to module mapping (generated by depmod)
grep 'nvme' /lib/modules/$(uname -r)/modules.alias | head -5

# What udev sees during device discovery
sudo udevadm monitor --property --subsystem-match=pci &
sleep 1; echo "Trigger rescan..."; kill %1

# Simulate alias lookup
modprobe -c | grep 'alias pci:v00008086d' | head -5
# v0000XXXX = vendor, dXXXX = device

Module Hiding (Rootkit View)

Understanding offensive techniques is essential for detection. Kernel rootkits manipulate the data structures that lsmod and /proc/modules read.

The data structures

// kernel/module/internal.h
// Modules are stored in a linked list:
extern struct list_head modules;   // global module list

// And also in:
// mod_tree: a radix tree of module address ranges for quick lookup
// Used by is_module_address() and is_module_text_address()

// struct module itself is stored in its own .gnu.linkonce.this_module section

Detection Bypass Techniques

1. Unlink from module list:
   list_del(&mod->list);  → module vanishes from lsmod, /proc/modules
   BUT: still in mod_tree → still on /sys/module/<name>/, still functional

2. Hook /proc/modules:
   Intercept seq_read on /proc/modules, filter lines
   
3. Kernel code injection without a module:
   a) /dev/mem (if unlocked): write directly to kernel memory
   b) kprobes: attach probe that modifies kernel text
   c) eBPF: attach to kernel functions, writeable BPF maps
   d) Null deref + mmap: exploit CVE-2016-8655 style for arbitrary kernel write
   
4. Module signature bypass:
   a) Patch verification function in memory (needs write primitive first)
   b) Replace kernel's public key (needs write to rodata)
   c) Exploit a bug that sets module->sig_ok = true

Detection methods (defensive)

# Method 1: Compare mod_tree entries vs module list
# If module appears in /sys/module/ but NOT in lsmod → hidden via list_del
for m in /sys/module/*; do
    modname=$(basename $m)
    if ! lsmod | grep -q "^$modname "; then
        echo "POTENTIAL HIDDEN MODULE: $modname"
    fi
done

# Method 2: Memory forensics — scan kernel text for deviations
# Any executable region not belonging to vmlinux or a known module
sudo cat /proc/kallsyms | awk '{print $1}' | while read addr; do
    # (requires Volatility or LiME for full analysis)
    true
done

# Method 3: Check sysfs module directory has no orphan entries
diff <(lsmod | awk 'NR>1{print $1}' | sort) \
     <(ls /sys/module | sort) 2>/dev/null

# Method 4: Inline hook detection
# Compare in-memory function prologues against disk
# (requires kernel memory analysis tools)

# Method 5: Kernel thread anomalies
ps aux | grep -E '^\[.*\]$' | awk '{print $NF}' | grep -vE \
    '^\[(kworker|ksoftirqd|migration|rcu_|watchdog|kswapd|jbd2|loop|scsi|kthreadd|idle)\]'

ABI Verification and MODVERSIONS

The kernel ABI is unstable by design - internal structures change between versions. CONFIG_MODVERSIONS generates a CRC checksum for every exported symbol, derived from the type signature. If a module's CRC for a symbol doesn't match the kernel's, loading fails. 

modversions CRC generation pipeline:
════════════════════════════════════

    1. genksyms tool processes pre-processed source
    2. For EXPORT_SYMBOL(usb_submit_urb):
       genksyms sees: int usb_submit_urb(struct urb *, gfp_t)
       Generates: CRC = 0x8a3b2c9d
    3. CRC stored in .__versions section of vmlinux
    4. At module build time, same CRC generated from headers → .ko
    5. At load time, kernel compares CRCs:
       match → OK
       mismatch → "usb_submit_urb: disagrees about version of symbol"
                   → -ENOEXEC
						
# Check if kernel enforces module versions
zcat /proc/config.gz 2>/dev/null | grep MODVERSIONS || \
    grep MODVERSIONS /boot/config-$(uname -r)

# Inspect versioned symbols in a .ko
modprobe --dump-modversions /lib/modules/$(uname -r)/kernel/drivers/usb/core/usbcore.ko 2>/dev/null | head -10
# or:
objdump -s -j __versions /lib/modules/$(uname -r)/kernel/drivers/block/loop.ko 2>/dev/null | head -20

# See symbol CRC in running kernel (requires CONFIG_MODVERSIONS)
# Not directly exposed via sysfs — use modprobe --dump-modversions

struct module Internals

// include/linux/module.h — key fields (simplified)
struct module {
    enum module_state state;             // MODULE_STATE_LIVE, COMING, GOING
    struct list_head list;               // Entry in global module list
    char name[MODULE_NAME_LEN];          // Unique module name
    struct module_kobject mkobj;         // sysfs: /sys/module/<name>/
    const struct kernel_symbol *syms;    // Exported symbols
    const s32 *crcs;                     // CRC checksums
    unsigned int num_syms;
    struct kernel_param *kp;             // Module parameters
    unsigned int num_kp;
    const char **modinfo_attrs;          // .modinfo strings
    unsigned int modinfo_attrs_num;
    int (*init)(void);                   // Init function pointer
    struct module_layout core_layout;    // .text + .rodata + .data
    struct module_layout init_layout;    // .init.text + .init.data (freed)
    struct mod_tree_node mtn;            // Radix tree node
    // ... architecture-specific fields
};

// Initial values (pre-filled in .gnu.linkonce.this_module):
static struct module __this_module
__attribute__((section(".gnu.linkonce.this_module"))) = {
    .name = KBUILD_MODNAME,
};

Kernel Taint System

When a module loads, the kernel may set a "taint" bit. Some bits are informational; others restrict debugging or reporting.

Taint flags (include/linux/panic.h):

Flag Bit Meaning
P 1 Proprietary module loaded
F 2 Module force-loaded (modprobe --force)
S 4 Running on SMP with non-SMP CPU
R 8 Module force-unloaded
M 16 Machine check exception
B 32 Bad page reference
U 64 User-requested (sysrq-t)
D 128 Kernel OOPS (previous)
A 256 ACPI table override
W 512 Kernel warning (previous)
C 1024 Staging driver loaded
I 2048 Workaround for hardware bug applied
O 4096 Out-of-tree module loaded
E 8192 Unsigned module (with signing required)
L 16384 Soft lockup occurred
X 32768 Auxiliary kernel crash (e.g. Xen)
K 65536 Live patching applied 
# Check current taint state
cat /proc/sys/kernel/tainted

# Decode taint bits
python3 -c "
taints = {
    1:'P',2:'F',4:'S',8:'R',16:'M',32:'B',64:'U',128:'D',
    256:'A',512:'W',1024:'C',2048:'I',4096:'O',8192:'E',
    16384:'L',32768:'X',65536:'K'
}
val = int(open('/proc/sys/kernel/tainted').read().strip())
print('Active taints:', ''.join(c for b,c in taints.items() if val & b))
"

# Per-module taint
cat /sys/module/*/taint | grep -v '^0$' | while read f; do
    echo "$(dirname $(dirname $f)): $(cat $f)"
done

    <(lsmod | awk 'NR>1{print $1}' | sort) \
    <(ls /sys/module | sort) 2>/dev/null | while read m; do
        echo "Module in sysfs but not lsmod: $m"
    done

make
