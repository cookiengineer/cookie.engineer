Integer Overflows

How arithmetic wrap-around and signed undefined behavior turn size calculations into exploitable bugs.

Overview

An integer overflow happens when an arithmetic result does not fit the type that stores it. In C the result wraps for unsigned types and is undefined behavior for signed types, which lets the compiler delete the very bounds check meant to stop it. This article covers the representation, the size calculation patterns that cause most real bugs, and checked arithmetic that fails safely. After reading you can rewrite an unsafe size calculation with a checked one.

Required Reading

  • Buffer Overflows - how buffer size miscalculations lead to heap and stack overflows
  • Stack - stack frame layout and return address overwrite via overflow

The Arithmetic That Wraps

An integer overflow occurs when the result of an arithmetic operation exceeds the maximum value representable by the result type. The excess bits are silently discarded, wrapping the value around.

On 32-bit unsigned arithmetic: 0xFFFFFFFF + 1 = 0x00000000 . On 64-bit: 0xFFFFFFFFFFFFFFFF + 1 = 0 . No exception, no signal, no trap - the hardware sets the carry flag and continues. Software must explicitly check.

C defines overflow behavior differently for signed and unsigned types:

Type Behavior on overflow Standard
unsigned int,size_t Defined: wraps modulo 2^N C11 6.2.5p9
signed int Undefined behavior C11 6.5p5
signed char,short Undefined after integer promotion C11 6.3.1.1

Unsigned wraparound is well-defined and deterministic. Signed overflow is pure undefined behavior

  • the compiler may delete overflow checks, generate unreachable code, or assume the overflow

never happens.

Two's Complement Representation

Modern CPU s (x86-64, ARM64) use two's complement. The bit pattern for -1 is 0xFFFFFFFF (all bits set). Addition works identically for signed and unsigned at the hardware level - the difference is only in interpretation. 

Decimal    Unsigned 32-bit       Signed 32-bit
-------    -----------------     --------------
0          0x00000000            0
1          0x00000001            1
2147483647 0x7FFFFFFF            2147483647  (INT_MAX)
2147483648 0x80000000            -2147483648 (INT_MIN)
4294967295 0xFFFFFFFF            -1          (UINT_MAX)
4294967296 0x00000000            0           (wrap)

The wrap point for unsigned is UINT_MAX + 1 = 0 . For signed, INT_MAX + 1 overflows to INT_MIN but is undefined behavior - a conforming compiler may replace it with anything.

Undefined Behavior Optimizations

Because signed overflow is UB, compilers exploit this to optimize. Consider this security check:

int size = user_controlled + 16;
if (size < 0)    // compiler: user_controlled + 16 can't overflow (UB)
    abort();     // compiler: this path is dead code

char *buf = malloc(size);  // compiler: size is always positive

The compiler reasons: "signed overflow is undefined, therefore user_controlled + 16 cannot overflow. If it did overflow, anything is allowed, including removing this check. So size >= 0 always holds." The if (size < 0) check is eliminated as dead code. The overflow happens at runtime and malloc() receives a small positive value (the wrapped result).

Compile with -fwrapv to force signed wraparound (like unsigned) if you must use signed types for size calculations. Better: use unsigned types for sizes. 

# Check what the compiler actually did:
gcc -O2 -S -o - vulnerable.c | grep -A5 'user_controlled'
# The abort() call may be absent even with -O2

The Width x Height Pattern

Image processing libraries allocate a buffer based on image dimensions:

struct Image {
    unsigned int width;
    unsigned int height;
    unsigned char pixel_format;  // 3 for RGB, 4 for RGBA
};

void decode_image(struct Image *img, unsigned char *compressed_data) {
    size_t buf_size = img->width * img->height * img->pixel_format;

    /* width = 65536, height = 65536, pixel_format = 4
       65536 * 65536 = 0x100000000 → overflows 32-bit unsigned → 0
       0 * 4 = 0 → malloc(0) → returns valid small chunk */

    unsigned char *pixels = malloc(buf_size);
    if (!pixels) return;

    /* Decompression writes 65536 * 65536 * 4 = 16 GB of pixel data
       into a buffer that can hold maybe 24 bytes. */

    decompress_rows(compressed_data, pixels, img->width, img->height);
}
						
/* size_overflow_demo.c */
#include <stdio.h>
#include <stdlib.h>

int main() {
    unsigned int width  = 0x10000;  // 65536
    unsigned int height = 0x10000;  // 65536
    unsigned int elem   = 4;

    unsigned int size32 = width * height * elem;
    size_t      size64 = (size_t)width * height * elem;

    printf("width   = %u (0x%x)\n", width, width);
    printf("height  = %u (0x%x)\n", height, height);
    printf("elem    = %u\n", elem);
    printf("\n");
    printf("32-bit: width*height*elem = %u (0x%x)\n", size32, size32);
    printf("64-bit: (size_t)width*... = %zu (0x%zx)\n", size64, size64);

    printf("\n--- overflow detail ---\n");
    printf("width*height        = %u (0x%x)   [actual: %llu]\n",
           width*height, width*height,
           (unsigned long long)width * height);
    printf("a 16 GB buffer spans offsets 0 to %llu\n",
           4ULL * 65536 * 65536 - 1);
    printf("But malloc gets size = %u\n", size32);

    void *p = malloc(size32);
    printf("malloc(%u) = %p\n", size32, p);
    free(p);

    return 0;
}

malloc(0) in glibc returns a valid, allocation-sized pointer (implementation-defined, but glibc treats it as malloc(1) with minimum chunk size 0x20). The program proceeds to write gigabytes through this tiny allocation - a catastrophic heap overflow.

Integer Promotion and Narrowing

C's integer promotion rules introduce subtle overflow paths:

unsigned short a = 65535;
unsigned short b = 65535;
unsigned short c = a + b;   // a and b promoted to int (signed!)
                            // 65535 + 65535 = 131070 → fits in int (no overflow)
                            // result assigned to c → 131070 % 65536 = 65534
                            // c = 65534, no overflow warning

unsigned int a32 = 65535;
unsigned int b32 = 65535;
unsigned int c32 = a32 + b32;  // 131070, no overflow

unsigned short x = 40000;
unsigned short y = 40000;
unsigned short z = x * y;      // promoted to int: 40000 * 40000 = 1600000000
                               // fits in 32-bit signed int? INT_MAX = 2147483647
                               // Yes, 1.6B < 2.1B → no overflow
                               // Assigned to z → 1600000000 % 65536 rolling truncation

The rule: if int can represent all values of the operand type, the operand is promoted to int (signed). If not, it's promoted to unsigned int . Since unsigned short 's max (65535) fits in int (32-bit), both operands become int . The multiplication happens in signed int . If the result exceeds INT_MAX , that's signed overflow = UB. 

unsigned short s1 = 40000, s2 = 40000;
// s1 * s2:
//   1) promote s1, s2 → int 40000, int 40000
//   2) int * int → int 1600000000 (OK, < INT_MAX)
//   3) assign to unsigned short → wrap-around modulo 65536

unsigned short s3 = 65535, s4 = 2;
// s3 + s4:
//   1) promote s3 → int 65535, s4 → int 2
//   2) int + int → int 65537
//   3) assign to unsigned short → 65537 % 65536 = 1

On platforms where int is 16-bit (embedded), unsigned short equals unsigned int , no promotion occurs, and behavior differs. This platform-dependent behavior is a recurring source of bugs.

size_t vs int Mismatches

size_t is the unsigned type for sizes (64-bit on x86-64, 32-bit on x86). It can represent the largest possible object size. Mixing int (signed, 32-bit on LP64) with size_t introduces sign-extension bugs: 

int user_len = -1;   // attacker-controlled
if (user_len > 1024)
    return ERROR;

// Comparison: (int)-1 vs (int)1024 → -1 ≤ 1024 → check passes

size_t copy_len = user_len;  // implicit conversion: -1 → 0xFFFFFFFFFFFFFFFF
memcpy(dest, src, copy_len); // copies 18 exabytes (or segfaults first)

The fix:

if (user_len < 0 || (size_t)user_len > 1024)
    return ERROR;
// -1 < 0 → check catches it

Or use size_t or ssize_t throughout to avoid mixed-sign comparisons and conversions.

Check-Then-Overflow Pattern

Another classic: a bounds check that itself overflows, rendering the check useless:

void process_data(char *data, unsigned int len) {
    /* Add room for null terminator and header */
    unsigned int total = len + 1 + sizeof(header_t);

    if (total > MAX_BUFFER) {
        error("too large");
        return;
    }

    char *buf = malloc(total);
    memcpy(buf, data, len);   // if len was UINT_MAX, total=0 wraps
}

When len = UINT_MAX :

  • len + 1 wraps to 0
  • total becomes 0 + sizeof(header_t) , a small value
  • total > MAX_BUFFER is false
  • malloc(total) returns a small chunk
  • memcpy(buf, data, len) copies 4 GB into that small chunk

The check itself is the vulnerability because the addition overflowed before the comparison.

Safe Arithmetic with Compiler Builtins

GCC and Clang provide builtin functions that detect overflow without UB:

#include <stddef.h>

// gcc/clang builtins:
int __builtin_add_overflow(type a, type b, type *result);
int __builtin_sub_overflow(type a, type b, type *result);
int __builtin_mul_overflow(type a, type b, type *result);

// Returns true if overflow occurred.
// Works with int, long, long long, and their unsigned variants.
						
/* safe_arithmetic.c */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define MAX_SIZE (16 * 1024 * 1024)

void *safe_alloc(size_t width, size_t height, size_t elem_size) {
    size_t size;

    if (__builtin_mul_overflow(width, height, &size)) {
        fprintf(stderr, "overflow: width * height\n");
        return NULL;
    }
    if (__builtin_mul_overflow(size, elem_size, &size)) {
        fprintf(stderr, "overflow: (width * height) * elem_size\n");
        return NULL;
    }
    if (size > MAX_SIZE) {
        fprintf(stderr, "size %zu exceeds max %zu\n", size, MAX_SIZE);
        return NULL;
    }

    void *p = malloc(size);
    if (!p) {
        fprintf(stderr, "malloc(%zu) failed\n", size);
        return NULL;
    }
    return p;
}

int main() {
    /* Safe allocation: 1024 × 768 × 3 = 2.3 MB → OK */
    void *p1 = safe_alloc(1024, 768, 3);
    printf("p1 = %p (should be non-NULL)\n", p1);
    free(p1);

    /* Overflow: 65536 × 65536 × 4 → overflow detected */
    void *p2 = safe_alloc(65536, 65536, 4);
    printf("p2 = %p (should be NULL)\n", p2);

    /* Overflow: SIZE_MAX * 2 → overflow in the first multiplication */
    void *p3 = safe_alloc((size_t)-1, 2, 1);
    printf("p3 = %p (should be NULL)\n", p3);

    return 0;
}
						
gcc -o safe_arithmetic safe_arithmetic.c
./safe_arithmetic

# p1 = 0x5555555592a0 (should be non-NULL)
# overflow: width * height
# p2 = (nil) (should be NULL)
# overflow: width * height
# p3 = (nil) (should be NULL)

The builtins are architecture-aware - on x86-64 they compile to arithmetic instructions followed by jo (jump on overflow) or jc (jump on carry) checks. No software emulation, no performance cost beyond the branch.

C11 Annex K: Bounds-Checking Interfaces

C11 introduced optional bounds-checking functions ( _s suffix): 

errno_t memcpy_s(void *dest, rsize_t destsz, const void *src, rsize_t count);

rsize_t is size_t constrained to RSIZE_MAX (implementation-defined, often SIZE_MAX >> 1 ). These functions check for null pointers, overlapping regions, and sizes exceeding RSIZE_MAX . They are not widely implemented (glibc does not provide them), so portable code cannot rely on them.

malloc Edge Cases

malloc(0): glibc returns a valid pointer (minimum allocation unit, typically 0x20 bytes). P OSI X says the behavior is implementation-defined - some implementations return NULL. Never assume malloc(0) returns NULL.

malloc(SIZE_MAX - small): glibc uses mmap() for large allocations and brk() / sbrk() for smaller ones. A size near SIZE_MAX wraps in internal calculations. malloc(SIZE_MAX) returns NULL. But malloc(SIZE_MAX - 0x10) may pass internal size checks before wrapping in page-alignment arithmetic - behavior is inconsistent. 

#include <stdio.h>
#include <stdlib.h>

int main() {
    void *p0 = malloc(0);
    void *p1 = malloc(SIZE_MAX);
    void *p2 = malloc(SIZE_MAX - 0x1000);

    printf("malloc(0)          = %p\n", p0);
    printf("malloc(SIZE_MAX)   = %p\n", p1);
    printf("malloc(SIZE_MAX-4K)= %p\n", p2);

    free(p0);
    free(p1);  // NULL safe
    free(p2);
    return 0;
}

Kernel-Specific Integer Overflow

Linux kernel integer overflows follow the same patterns but with kernel-scale consequences:

Size calculation for DMA buffers. Drivers allocate DMA-coherent memory based on user-supplied dimensions. An overflow in width * height * bpp results in a DMA transfer that reads or writes past the allocated buffer into adjacent kernel memory.

Reference counter overflow. The kernel uses atomic_t (32-bit signed) for reference counts. Overflow from INT_MAX + 1 wraps to INT_MIN . A subsequent decrement back to 0 triggers free-while-in-use. This is a UAF on kernel objects triggered by integer overflow.

sat_add / checked_add in the kernel

// include/linux/overflow.h
bool __must_check check_add_overflow(u64 a, u64 b, u64 *d);
bool __must_check check_mul_overflow(u64 a, u64 b, u64 *d);

// array_size() and struct_size() use check_mul_overflow internally
void *p = kmalloc(array_size(n, sizeof(struct foo)), GFP_KERNEL);
// If n * sizeof(struct foo) overflows, returns SIZE_MAX, kmalloc fails

Fuzzing for Integer Overflows

AFL and libFuzzer can discover integer overflows indirectly - they observe heap buffer overflows caused by undersized allocations. To find the root cause overflow: 

# Compile with UBSan (UndefinedBehaviorSanitizer):
gcc -fsanitize=undefined -g -o fuzz_target fuzz_target.c
./fuzz_target < crash_input

# UBSan reports:
# fuzz_target.c:42:23: runtime error:
#   unsigned integer overflow: 65536 * 65536 cannot be represented in type 'unsigned int'
# SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior fuzz_target.c:42:23

UBSan catches unsigned wraparound (configurable: -fno-sanitize=unsigned-integer-overflow to disable) and signed overflow by default.

Static Analysis Rules

Tools like Clang Static Analyzer and CodeQL have specific checks:

  • unsigned overflow in malloc argument: malloc(a * b) where a * b can overflow.
  • signed overflow in bounds check: if (x + y < limit) where x + y might overflow (UB, check eliminated).
  • narrowing conversion: assignment of wider integer to narrower type without range check.
  • int / size_t comparison: implicit sign conversion in comparison.

Human review should focus on:

  1. Any multiplication before malloc() / calloc() .
  2. Any addition to a user-controlled value before a comparison.
  3. Any int used as array index or length (should be size_t ).

Summary

Integer overflow is an arithmetic wraparound that violates a programmer's size assumption. Unsigned overflow is defined as modulo 2^N; signed overflow is undefined behavior and invites compiler-eliminated security checks. The dominant exploit pattern is a size calculation that wraps to a small value, producing an undersized allocation that a subsequent write overflows. Prevention: use size_t for sizes, prefer __builtin_mul_overflow and __builtin_add_overflow over manual checks, and run UBSan during testing to catch wraparound at the point of occurrence.

Challenge

Write a Go program that computes width * height * channels for an image buffer without ever letting an unsigned multiplication wrap. Implement SafeMul and SafeAdd that return an error on overflow, and a PixelBufferSize helper that chains them. 

package main

import (
	"errors"
	"fmt"
)

var ErrOverflow = errors.New("integer overflow")

func SafeAdd(a, b uint64) (uint64, error) {
	sum := a + b
	if sum < a {
		return 0, ErrOverflow
	}
	return sum, nil
}

func SafeMul(a, b uint64) (uint64, error) {
	if a != 0 && b > ^uint64(0)/a {
		return 0, ErrOverflow
	}
	return a * b, nil
}

func PixelBufferSize(width, height, channels uint64) (uint64, error) {
	pixels, err := SafeMul(width, height)
	if err != nil {
		return 0, err
	}
	return SafeMul(pixels, channels)
}

func main() {
	if size, err := PixelBufferSize(1024, 768, 4); err == nil {
		fmt.Printf("accepted: %d bytes\n", size)
	}
	if _, err := PixelBufferSize(1<<32, 1<<32, 4); err != nil {
		fmt.Printf("rejected: %v\n", err)
	}
}

Then extend PixelBufferSize with a maximum allowed size, add a table-driven test with at least the boundary cases 0 , 1 , UINT32_MAX , and UINT64_MAX , and compare your SafeMul result against bits.Mul64 from math/bits .
