Performance Analysis

The USE method, perf and hardware PMU counters, flame graphs, and a workflow for locating CPU , memory, lock, and I/O bottlenecks.

Overview

Performance analysis is the scientific method applied to software: observe, hypothesize, measure, confirm. This article covers the USE method, the perf tool in depth, hardware performance counters, flame graphs, scheduling analysis, cache behavior, lock profiling, I/O profiling, and the end-to-end bottleneck identification workflow. Every measurement is reproducible with the commands provided.

Required Reading

  • Kernel Observability - kernel debug interfaces, /proc, /sys
  • Tracing Frameworks - perf, ftrace, eBPF comparison
  • eBPF - eBPF programs for custom profiling
  • Processes - process state, scheduling classes, CPU affinity
  • Threads - threading models, synchronization

1. The USE Method

USE (Utilization, Saturation, Errors) is a methodology for checking every resource in a system. For each resource, ask three questions: 

For each resource (CPU, memory, disk, network, ...):
  Utilization:  Is the resource busy? What % of capacity?
  Saturation:   Is there a queue of work waiting? What's the backlog?
  Errors:       Are there failures? Dropped packets, ECC errors, etc.

Resources to check:

Resource Utilization Saturation Errors
CPU %user/%sys/idle run queue length MCE, thermal
Memory used/total swap usage, OOM ECC, OOM kill
Disk I/O %util, tps avg queue size I/O errors
Network bandwidth % rx/tx drops, backlog errors, collisions
File desc used/max ENFILE/EMFILE leak checks
Cgroup cpu/mem limits throttle count OOM kills

1.1 Quick USE Check

# CPU utilization and saturation
top -bn1 | head -5
mpstat -P ALL 1 3
uptime                    # load average ≈ saturation

# Memory
free -h
vmstat 1 5                # si/so = swap in/out (saturation)

# Disk
iostat -xz 1 3            # %util, avgqu-sz (saturation), await

# Network
ip -s link show eth0      # RX/TX errors, drops
ss -s                     # socket summary

# File descriptors
cat /proc/sys/fs/file-nr  # allocated / max / limit
lsof | wc -l

# System errors
dmesg | tail -30          # kernel errors
journalctl -p 3 -xb --no-pager | tail -20

2. Perf Deep Dive

Perf is the primary performance analysis tool on Linux. It interfaces with hardware PMU (Performance Monitoring Unit) counters built into every modern CPU .

2.1 Hardware Performance Counters

Modern CPU s have a fixed set of architectural counters and a programmable set: 

x86-64 Architectural PMU Events (Intel/AMD):

Fixed counters (always counting these events):
  FIXED_CTR0:  INST_RETIRED.ANY       Instructions retired
  FIXED_CTR1:  CPU_CLK_UNHALTED.CORE   Core cycles (not halted)
  FIXED_CTR2:  CPU_CLK_UNHALTED.REF    Reference cycles (constant freq)

Programmable counters (4-8 per logical core, configurable):
  Common events:
    cpu-cycles                   ← total cycles
    instructions                 ← instructions retired
    cache-references             ← last-level cache accesses
    cache-misses                 ← last-level cache misses
    branch-instructions          ← branches executed
    branch-misses                ← mispredicted branches
    stalled-cycles-frontend      ← cycles stalled waiting for instructions
    stalled-cycles-backend       ← cycles stalled waiting for data/memory
    L1-dcache-loads / -misses    ← L1 data cache
    LLC-loads / -misses          ← Last Level Cache
    dTLB-loads / -misses         ← data TLB
    iTLB-loads / -misses         ← instruction TLB
    bus-cycles                   ← memory bus cycles

  The limitation: more events than counters.
  perf multiplexes automatically and scales counts (shown as a percentage);
  -M selects a named metric group, not multiplexing.

2.2 perf stat - Event Counting

# Baseline: count key events
perf stat ls /

# Output:
#  Performance counter stats for 'ls /':
#    1.23 msec  task-clock:u    #    0.714 CPUs utilized
#          0    context-switches
#          0    cpu-migrations
#        269    page-faults
#    3,421,987  cycles:u
#    2,345,678  instructions:u    #    0.69  insn per cycle
#      423,456  branches:u
#       12,345  branch-misses:u   #    2.91% of all branches

# Detailed multi-event counting
perf stat -e cycles,instructions,cache-references,cache-misses,branch-misses \
    -r 5 ./myapp               # repeat 5 times for statistical confidence

# Top-down analysis (Intel Broadwell+)
perf stat --topdown ./myapp
# Output:
#  Frontend Bound:   12.3%   ← waiting for instruction fetch
#  Backend Bound:    34.5%   ← waiting for data/memory
#  Bad Speculation:   5.2%   ← mispredicted branches
#  Retiring:         48.0%   ← doing useful work

# Per-CPU breakdown
perf stat -a -A -- sleep 1

# Cache hierarchy analysis
perf stat -e L1-dcache-loads,L1-dcache-load-misses,LLC-loads,LLC-load-misses \
    ./myapp

# Calculate IPC (instructions per cycle)
perf stat -e instructions,cycles ./myapp
# IPC = instructions / cycles
# IPC < 1.0 → memory-bound or branch-misprediction-bound
# IPC > 2.0 → compute-bound, well-optimized

2.3 perf record - Sampling

# CPU sampling at 99 Hz (avoiding lockstep with 100 Hz timers)
perf record -F 99 -a -g -- sleep 30

# Call graph options:
#   -g (default)  → frame pointer based (fast but needs -fno-omit-frame-pointer)
#   --call-graph dwarf → DWARF CFI unwinding (works without frame pointers, slower)
#   --call-graph lbr → LBR (Last Branch Record, hardware stack, Intel only)
perf record -F 99 -a --call-graph dwarf -- sleep 30

# Sampling on a specific event (not timer)
perf record -e cache-misses -a -g -- sleep 30

# Sampling with LBR for precise branch history
perf record -b -a -- sleep 10

# Sampling a specific PID only
perf record -F 99 -p $(pidof myapp) -g -- sleep 30

# Sampling with timestamp and precise IP
perf record -F 99 --timestamp --call-graph dwarf -a -- sleep 30

2.4 perf report - Analysis

# Interactive TUI
perf report

# Stdout: top functions
perf report --stdio --sort comm,dso,symbol -n

# Sort by different metrics
perf report --sort symbol
perf report --sort dso,symbol
perf report --sort pid,comm,symbol

# Call chain: show which functions call which
perf report --stdio --children -g graph

# Filter to a specific binary/DSO
perf report --dso myapp

# Annotate: see assembly with performance counters
perf annotate -s hot_function
# Shows assembly instructions with sample count per instruction

2.5 perf top - Live Analysis

# Live function-level profiling
perf top

# With call chains
perf top -g

# Filter to a specific DSO
perf top --dso libc.so.6

# Filter to user-space only
perf top -e cycles:u

# Annotate symbols live (press 'a' in perf top)

2.6 perf script - Raw Data Export

# Dump samples for external processing
perf script > samples.txt

# Filter fields
perf script -F comm,pid,tid,time,event,ip,sym,dso

# Generate stack collapse for flame graphs
perf script | stackcollapse-perf.pl > stacks.folded

# Python scripting on perf data
perf script -s myscript.py

3. Flame Graphs

Flame graphs visualize stack trace samples. The width of each frame represents its proportion of samples. They answer: "What is consuming CPU ?" 

Flame Graph:
  ┌──────────────────────────────────────────────────────────────┐
  │ func_g                                                     │
  │ ┌──────────────┐                                            │
  │ │   func_d     │ func_e                                     │
  │ ├──────+───────┤ ┌────────────┐                              │
  │ │func_a│func_b │ │  func_f    │ func_g                      │
  │ │      │       │ │            │                              │
  │ │      │       │ │            │                              │
  │ └──────+───────┘ └────────────┘                              │
  │ func_a = 60 samples   func_g = 100 samples (root)           │
  │ func_b = 40 samples                                         │
  └──────────────────────────────────────────────────────────────┘

Wide frames = many samples = hot code path
Tall stacks = deep call chains

3.1 Generating Flame Graphs

# Install flamegraph tools
git clone https://github.com/brendangregg/FlameGraph.git /opt/FlameGraph
export PATH=$PATH:/opt/FlameGraph

# Capture CPU profile
perf record -F 99 -a -g -- sleep 30

# Generate flame graph
perf script | stackcollapse-perf.pl | flamegraph.pl > flamegraph.svg

# Open in browser
firefox flamegraph.svg

# Differential flame graph (compare before/after)
perf script -i perf_before.data | stackcollapse-perf.pl > before.folded
perf script -i perf_after.data  | stackcollapse-perf.pl > after.folded
difffolded.pl before.folded after.folded | flamegraph.pl > diff.svg

3.2 Flame Graph Types

On-CPU flame graph:     shows what's consuming CPU time
  Generated from:  perf record -F 99 -g

Off-CPU flame graph:    shows what's blocking/waiting
  Generated from:  offcputime (bcc) or perf sched record

Memory flame graph:     shows memory allocation paths
  Generated from:  stackcount (bcc) on malloc/mmap

Hot/Cold flame graph:   function → callee breakdown
  Generated from:  flamegraph.pl --colors=chain

Differential flame graph:  before/after comparison
  Red   = increased samples  (regression)
  Blue  = decreased samples  (improvement)

4. Scheduling Analysis

The scheduler decides which task runs on which CPU and when. Poor scheduling causes tail latency, uneven load, and wasted CPU .

4.1 perf sched

# Record scheduling events
perf sched record -- sleep 10

# Show scheduling latency
perf sched latency
# Output: Task | Runtime(ms) | Switches | Avg delay(ms) | Max delay(ms)
# Max delay = longest time a task was runnable but not scheduled

# Visualize scheduling timeline
perf sched map
# Output: CPU-by-CPU timeline showing which task ran when
# . = idle, * = task running, 1 = task on CPU 1, etc.

# Show task wakeup information
perf sched timehist
# Shows when each task was scheduled, its wait time, and wakeup source

# Replay scheduling trace
perf sched replay

4.2 Scheduling Metrics

# Context switch rate
perf stat -e context-switches -a -- sleep 5

# Involuntary context switches (time slice exhausted)
perf stat -e context-switches -e cpu-migrations -a -- sleep 5

# Per-process scheduling stats
cat /proc/PID/sched
# Shows: nr_switches, nr_voluntary_switches, nr_involuntary_switches,
#        se.sum_exec_runtime, se.statistics.wait_sum

# Run queue length (saturation indicator)
cat /proc/loadavg
vmstat 1 5 | awk '{print $1}'  # 'r' column = run queue length

# Per-CPU run queue
sar -q 1 5

# CPU affinity and isolation
taskset -cp PID                    # show current affinity
taskset -cp 0-3 PID               # pin to CPUs 0-3

5. Cache Behavior Analysis

Modern CPU s spend 50-80% of their time waiting for memory. Understanding cache behavior is essential for performance. 

Memory Hierarchy (latency in cycles):
  L1 cache:    ~4 cycles   (32 KB, per-core)
  L2 cache:    ~12 cycles  (256-512 KB, per-core)
  L3 cache:    ~40 cycles  (8-32 MB, shared)
  Local DRAM:  ~100-200 ns (~300-600 cycles @ 3 GHz)
  Remote DRAM: ~200-400 ns (NUMA)
  Disk:        ~1-10 ms    (millions of cycles)

5.1 Cache Event Counting

# Overall cache miss rate
perf stat -e cache-references,cache-misses ./myapp
# cache-misses / cache-references = miss rate

# L1 data cache
perf stat -e L1-dcache-loads,L1-dcache-load-misses,L1-dcache-stores ./myapp

# Last Level Cache (L3)
perf stat -e LLC-loads,LLC-load-misses,LLC-stores,LLC-store-misses ./myapp

# TLB (Translation Lookaside Buffer)
perf stat -e dTLB-loads,dTLB-load-misses,iTLB-loads,iTLB-load-misses ./myapp

# Cache line bouncing (false sharing indicator)
perf stat -e L1-dcache-load-misses -e LLC-load-misses -p PID sleep 5

# Memory bandwidth estimation
perf stat -e uncore_imc/data_reads/,uncore_imc/data_writes/ -a -- sleep 5
# (Intel-specific uncore events — requires root)

5.2 Sampling on Cache Misses

# Record samples where L3 cache misses occur
perf record -e LLC-load-misses -a -g -- sleep 10
perf report --stdio --sort symbol

# Record samples where TLB misses occur
perf record -e dTLB-load-misses -a -g -- sleep 10

5.3 False Sharing Detection

False sharing occurs when two unrelated variables on the same cache line are written by different CPU s: 

False Sharing:
  CPU 0 writes to var_A (cache line 0x100)
  CPU 1 writes to var_B (same cache line 0x100)
  → Cache line bounces between caches
  → perf stat shows high L1-dcache-load-misses despite no shared data

Detection:
  perf c2c record -a -- sleep 5
  perf c2c report
  # Shows cache-to-cache transfers, identifies the hot cache lines
  # and the data structures involved
						
# Cache-to-cache analysis
perf c2c record -a -- sleep 10
perf c2c report --stdio

# Look for:
# - High "HITM" (Hit Modified) count → cache line bouncing
# - The data symbol and offset → which struct field
# - The CPUs involved → which threads cause bouncing

6. Branch Prediction Analysis

Modern CPU s predict branches to keep the pipeline full. Mispredictions flush the pipeline (15-20 cycle penalty). 

# Branch prediction efficiency
perf stat -e branches,branch-misses ./myapp
# branch-misses / branches = misprediction rate
# < 1% = good,   1-5% = acceptable,   > 5% = investigate

# Branch misprediction breakdown
perf stat -e branch-instructions,branch-misses,branch-loads,branch-load-misses \
    ./myapp

# Sample on branch misses
perf record -e branch-misses -a -g -- sleep 10
perf report --stdio

# Common causes of high branch miss rate:
#  1. Binary search / switch with unpredictable data
#  2. Linked list traversal (pointer chasing)
#  3. Virtual function calls on heterogeneous objects
#  4. Unpredictable if-else (compiler can generate cmov for simple cases)

7. Memory Access Pattern Analysis

7.1 perf mem

# Record memory access samples
perf mem record -a -- sleep 10

# Report memory access latency
perf mem report
# Shows: memory operation (load/store), latency, data symbol,
#        which instruction, TLB hit/miss, cache level hit

# Filter to specific latency buckets
perf mem report --sort=mem,sym,dso,symbol_daddr

# Key metrics:
#   Local RAM latency  = 100-200 ns
#   Remote RAM latency  = 200-400 ns (NUMA miss)
#   L3 hit latency     = 40-50 cycles
#   L2 hit latency     = 12 cycles

7.2 NUMA Analysis

# NUMA topology
numactl --hardware
lstopo                         # graphical topology (hwloc)

# Per-node memory and CPU stats
numastat
numastat -p PID                # per-process NUMA stats

# Check process NUMA memory policy
cat /proc/PID/numa_maps | head -20

# Measure remote memory access ratio
perf stat -e node-loads,node-load-misses,node-stores,node-store-misses \
    -p PID -- sleep 5

# Bind process to NUMA node
numactl --cpunodebind=0 --membind=0 ./myapp

# Check NUMA balancing (automatic page migration)
cat /proc/sys/kernel/numa_balancing   # 0=off, 1=on

8. Lock Profiling

Lock contention is a primary source of tail latency in multithreaded programs.

8.1 perf lock

# Record lock events
perf lock record -a -- sleep 10

# Report lock contention
perf lock report
# Shows: lock name, wait time, hold time, number of contentions

# Contention call graph
perf lock report -g

# Key metrics:
#   wait_time_total / wait_count = average wait time per contention
#   hold_time_total / acquisitions = average hold time
#   Long wait time + short hold time → fine-grained contention
#   Long wait time + long hold time → lock held too long

8.2 Lock Stat Tools

# mutrace: mutex contention analysis (user-space)
mutrace ./myapp        # requires mutrace package

# Kernel lock statistics
cat /proc/lock_stat
# Shows: class name, contentions, wait-time-min/max/total, hold-time

# Reset lock stats
echo 0 | sudo tee /proc/sys/kernel/lock_stat

# Wait for events
sleep 30

# View results
sudo cat /proc/lock_stat | head -20

# Per-function lockdep info
sudo cat /proc/lockdep_stats

9. I/O Profiling

9.1 Block I/O

# Block I/O statistics per device
iostat -xz 1 5

# Key metrics:
#   r/s, w/s         — I/O operations per second
#   rkB/s, wkB/s     — throughput
#   await            — average I/O completion time (ms)
#   r_await, w_await — read/write-specific
#   avgqu-sz         — average queue length (saturation)
#   %util            — device busy percentage (may exceed 100% for SSDs)

# Per-process I/O
iotop -oP             # I/O top (requires root)
pidstat -d 1 5        # per-process I/O stats

# Trace I/O latency with perf
perf trace -e block:block_rq_issue,block:block_rq_complete -a -- sleep 10

# BPF-based I/O latency histogram
bpftrace -e '
    tracepoint:block:block_rq_issue { @start[args->dev] = nsecs; }
    tracepoint:block:block_rq_complete /@start[args->dev]/ {
        @latency_us = hist((nsecs - @start[args->dev]) / 1000);
        delete(@start[args->dev]);
    }
    interval:s:10 { exit(); }'

# Per-disk latency percentiles
# Requires bcc-tools
biolatency -D 1 10

9.2 Filesystem Operations

# Trace filesystem operations
perf trace -e 'syscalls:sys_enter_*at*' -a -- sleep 5

# BPF-based VFS latency
bpftrace -e '
    kprobe:vfs_read { @start[tid] = nsecs; @reads = count(); }
    kretprobe:vfs_read /@start[tid]/ {
        @read_us = hist((nsecs - @start[tid]) / 1000);
        delete(@start[tid]);
    }
    interval:s:10 { exit(); }'

# File system stat
find /proc/*/fd -ls 2>/dev/null | awk '{print $NF}' | sort | uniq -c | sort -rn | head -20
# Shows most-opened files

10. Profiling at Scale

10.1 CPU Sampling Overhead

Sampling frequency vs overhead:
  1 Hz:       negligible overhead (< 0.01%)
  99 Hz:      ~0.1% overhead (standard choice)
  999 Hz:     ~1% overhead
  9999 Hz:    ~10% overhead (overwhelms PMU)

Sampling on events vs timer:
  Timer (F 99):              always fires, good baseline
  Event-based (cache-misses): fires only on the event, zero overhead when idle
  Always use event-based for rare events

10.2 System-Wide vs Per-Process

# System-wide: captures everything (interrupt handlers, kernel threads)
perf record -F 99 -a -g -- sleep 30

# Per-process: only samples when PID is scheduled
perf record -F 99 -p PID -g -- sleep 30

# Per-CPU: one sample per CPU per interval
perf record -F 99 -C 0,1 -g -- sleep 30

# CPU vs PID mode:
#   -a: samples all CPUs (system-wide)
#   -p PID: counts events only when PID is running
#   For I/O events: use -p so events are attributed to the right process

11. Bottleneck Identification Workflow

Systematic bottleneck identification:

1. USE check (60 seconds)
   ┌────────────────────────────────┐
   │ uptime, vmstat, iostat, mpstat │
   │ Look for saturated resources   │
   └────────────+───────────────────┘
                │
                ▼
2. Identify resource type
   ┌────────────────────────────────────────────────┐
   │ CPU saturated?  → step 3 (CPU profiling)       │
   │ Memory saturated? → step 4 (memory analysis)    │
   │ I/O saturated?   → step 5 (I/O profiling)      │
   │ Network saturated? → step 6 (network profiling) │
   └────────────+───────────────────────────────────┘
                │
                ▼
3. CPU bottleneck
   ┌──────────────────────────────────────┐
   │ perf top → identify hot function(s)   │
   │ perf record -F 99 -g → flame graph    │
   │ perf stat --topdown → classify        │
   │   Frontend Bound → I-cache misses    │
   │   Backend Bound → memory bound       │
   │   Bad Speculation → branch mispredict │
   │   Retiring → actually computing      │
   └──────────────────────────────────────┘

4. Memory bottleneck
   ┌──────────────────────────────────────┐
   │ perf stat cache-misses → miss rate    │
   │ perf record -e cache-misses -g       │
   │ perf mem record → access latency     │
   │ perf c2c → false sharing             │
   │ numastat → NUMA imbalance            │
   └──────────────────────────────────────┘

5. I/O bottleneck
   ┌──────────────────────────────────────┐
   │ iostat -xz 1 → await, avgqu-sz       │
   │ pidstat -d 1 → which process         │
   │ bpftrace → I/O latency histogram     │
   │ perf trace → syscall breakdown       │
   └──────────────────────────────────────┘

6. Lock/contention bottleneck
   ┌──────────────────────────────────────┐
   │ perf lock record → contention report  │
   │ offwaketime → who wakes who          │
   │ perf sched latency → scheduling delay │
   └──────────────────────────────────────┘

7. Verify fix
   ┌──────────────────────────────────────┐
   │ Re-run perf stat → compare IPC       │
   │ Re-run flame graph → narrower frames │
   │ Re-run stress test → improved p99    │
   └──────────────────────────────────────┘

12. Workload Generation

To profile effectively, you need a reproducible workload:

# CPU-intensive workload
dd if=/dev/zero of=/dev/null bs=1M count=10000

# Memory-intensive workload
stress-ng --vm 2 --vm-bytes 2G --vm-keep --timeout 30s

# I/O-intensive workload
dd if=/dev/urandom of=/tmp/testfile bs=4k count=100000 conv=fdatasync

# Network-intensive workload
iperf3 -c localhost -t 30

# Mixed workload
stress-ng --cpu 4 --io 2 --vm 2 --timeout 30s

# Capture perf during workload
perf stat -e cycles,instructions,cache-misses,branch-misses \
    stress-ng --cpu 1 --timeout 10s
