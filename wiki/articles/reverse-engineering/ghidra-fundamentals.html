Ghidra Fundamentals

A practical tour of Ghidra from project setup and auto-analysis to decompilation, renaming, and patching.

Overview

Ghidra is a free software reverse engineering suite that disassembles, decompiles, and annotates binaries. This article walks through installation, project setup, the interface, data type recovery, cross-references, the decompiler, and patching, then applies all of it to a complete workflow on an unknown binary. After reading, you can load a binary, navigate to main , recover types, rename functions, and document findings so another analyst can follow your work.

Required Reading

  • Control Flow Reconstruction - basic blocks, CFG construction, loop detection
  • ELF Reversing - ELF structure, sections, segments, symbol tables

What Ghidra Is

Ghidra is a software reverse engineering framework developed by the NSA Research Directorate and released as open source in 2019. It provides disassembly, decompilation, scripting (Java/Python), graphing, and collaborative analysis, making it roughly equivalent to IDA Pro with the Hex-Rays decompiler, but free.

Ghidra operates as a local analysis platform: the binary is loaded into a project, analyzed by a suite of "analyzers" (auto-analysis), and presented through multiple coordinated views. The key distinction from simple tools like objdump: Ghidra builds a semantic model of the binary

  • tracking data types, cross-references, calling conventions, and control flow - and maintains

it as you rename, retype, and annotate.

Installation on ArchLinux

The recommended path:

yay -S ghidra

This installs Ghidra and the required JDK (OpenJDK 17 or later). If you prefer manual installation:

# Download from https://github.com/NationalSecurityAgency/ghidra/releases
unzip ghidra_11.x_PUBLIC_YYYYMMDD.zip -d /opt
# Install JDK
pacman -S jdk17-openjdk
# Set JAVA_HOME if not auto-detected
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk
# Launch
/opt/ghidra_11.x_PUBLIC/ghidraRun

Ghidra requires a JDK because it's written in Java with a Swing GUI . The decompiler is C++ (SLEIGH specification compiled to native code), called via JNI.

Creating a Project

Ghidra organizes work into projects containing multiple binaries. Each project has a root folder; you create subfolders for organization.

File -> New Project -> Non-Shared Project -> Name: "MalwareAnalysis"
File -> Import File -> Select binary (ELF, PE, Mach-O, raw bytes)

On import, Ghidra asks for:

  • Format : Usually auto-detected (ELF, PE). For firmware or raw dumps, select "Raw Binary" and specify the base address.
  • Language : Auto-detected from the binary header ( x86:LE:64:default for x86-64 ELF).
  • Destination Folder : Choose a folder within your project.

After import, Ghidra asks: "Would you like to analyze now?" Select Yes and keep the default analyzers. For malware analysis, enable all analyzers. For large binaries (100MB+), selectively enable:

Essential analyzers (always enable):
  - Disassemble Entry Points
  - Function Start Search (pattern-based)
  - Function ID (library function recognition)
  - Call Convention ID
  - Stack Analysis
  - Data Reference
  - Decompiler Parameter ID
  - ASCII Strings
  - Create Address Tables (for switch statements)
  - Shared Return Calls
  - Subroutine References

Optional (enable for thorough analysis):
  - ARM/Thumb Disassembler
  - Constant Propagation
  - DWARF Line Number
  - PDB/MSDIA (Windows symbols)
  - Windows x86 PE Exception Handling
  - Variadic Function Signature Override

Auto-analysis runs in the background. The progress bar at the bottom shows: disassembly, function identification, stack frame building, data reference creation. Open the "Console" window (Window -> Console) to see errors or warnings - missing sections, failed disassembly at indirect jumps, corrupted data.

Interface Tour

The default layout has several coordinated panes:

Program Trees (left top): Hierarchical view of memory blocks. Each node is a memory region (.text, .data, .rodata, .bss, .plt, imported segments). Double-click to navigate the Listing to that region.

Symbol Tree (left middle): All named symbols - imports (external functions from libc, etc.), exports (functions the binary provides), labels (user-created names), functions (every detected function), namespaces, classes.

Listing (Disassembly View) (center): The main display. Shows memory addresses, raw bytes, labels, instructions, and EOL comments. This is where you spend most of your time.

Decompile Window (right, or detached): C-like pseudocode generated by Ghidra's decompiler. Updates live as you rename variables and retype data. Toggle with Ctrl+E.

Data Type Manager (bottom, or docked): All known data types - built-in (int, char, long, pointer), parsed from header files, and user-defined structs, enums, typedefs.

Additional windows are accessible from the Window menu:

  • Function Call Graph (Ctrl+Shift+F12): Visual graph of caller-callee relationships.
  • Bookmarks (Ctrl+B): User-saved locations with notes.
  • Register Manager : Current register values (if debugging, otherwise static).
  • Bytes View : Hex dump of a selected memory range.

Navigation

Ghidra's navigation model is link-heavy: double-click anywhere to follow.

Action Shortcut Effect
Double-click name Double-click Navigate to definition or reference

Back Alt+Left Return to previous location
Forward Alt+Right Forward after Back
Next/Prev function Ctrl+Down/Up Navigate between functions
Function list Ctrl+Shift+F Filterable list of all functions

Cross-references are the most important navigation tool. Given an address, you can answer:

  • Show References to - Who jumps to/calls this address? Who reads this data? Who writes to this data?
  • Show References from - What addresses does this instruction reference?

From the Listing, right-click an address, label, or instruction, then choose References -> Show References to Address. A table appears listing every instruction that references this address, the type of reference (READ, WRITE, CA LL, JUMP, DA TA), and the referencing function.

Column meanings:

Column Content
00401162 Virtual address (adjusted per binary's base address)
55 Raw bytes (hex) of the instruction
PUSH Instruction mnemonic
RBP Operand
; save arg1 Auto-generated or user EOL comment
[RBP + local_20] Named stack variable (Ghidra auto-assigned during stack analysis)
s_1337haxor_00402008 Auto-generated name for string at 0x402008

Ghidra names follow conventions: - LAB_XXXXXXXX - unnamed code label (target of a branch)

  • DAT_XXXXXXXX - unnamed data label
  • FUN_XXXXXXXX - unnamed function
  • s_<content>_XXXXXXXX - string at address X, auto-named from its content
  • local_NN - stack variable defined by its offset from the frame pointer ( local_8 , local_10 )
  • param_NN - stack parameter passed by the caller ( param_1 , param_2 )

Data Type Recovery

Ghidra initially marks undefined data as ?? (byte). You must tell it what data lives where.

Setting a data type on a scalar :

Position the cursor on an undefined byte or a label, press T , and choose: - byte , word , dword , qword - unsigned integers - char , short , int , long , long long - signed integers - float , double - IEEE 754

  • pointer - increments size based on architecture (8 bytes on x86-64)
  • string - null-terminated (choose ASCII, UTF-8, UTF-16, etc.)
  • Custom types you've defined in the Data Type Manager

Alternatively: Right-click -> Data -> Choose Data Type.

Creating a string at an address :

Right-click -> Data -> TerminatedCString

Ghidra creates the string, marks the null terminator as undefined, and creates a label. Strings referenced by code automatically get cross-references. If a string isn't auto-detected (e.g., XOR-encoded), you can manually create it after decoding.

Creating an array :

Place cursor at array start. Right-click -> Data -> Create Array. - Data type : Element type (int, pointer, struct) - Number of elements : Count - Element length : For fixed-size elements, auto-detected

This creates a contiguous typed region with [0] , [1] , [2] annotations.

Creating a structure :

Open Data Type Manager (Window -> Data Type Manager). Right-click the program's data type folder -> New -> Structure. Name it, then add fields:

Offset  Size  Type        Name
0       4     int         id
4       8     char *      name
12      4     int         flags
16      4     int         count
Total: 20 bytes

Now when you place the cursor on 20 undefined bytes and press T -> select your struct, Ghidra overlays the structure fields. Code that accesses [rax+offset] now shows field names.

Creating an enum :

Data Type Manager -> New -> Enum. Define values:

0 = STATE_IDLE
1 = STATE_CONNECTING
2 = STATE_CONNECTED
3 = STATE_ERROR

Apply an enum to a comparison: if the disassembly shows cmp dword [rbp-0x4], 2 and you know 2 means STATE_CONNECTED , retype [rbp-0x4] to your enum. The disassembly now shows cmp dword [rbp-0x4], STATE_CONNECTED .

Renaming

The most frequent operation in reverse engineering is replacing Ghidra's auto-generated names with semantically meaningful ones.

Rename a Function

Click the function name in the Listing or Symbol Tree, press L , and type the new name.

FUN_00401196 -> authenticate

Rename a Variable

In the Decompile window, right-click a variable name and choose Rename Variable. This renames the stack offset everywhere it appears.

local_18 -> user_ptr
local_20 -> secret

Rename a Label

Click LAB_XXXXXXXX and press L .

LAB_004011c4 -> authenticate_inner_check

Rename a Data Location

Click DAT_XXXXXXXX or s_XXXX and press L .

s_1337haxor_00402008 -> SECRET_PASSWORD

Comments

Type Key Use
EOL comment ; Attached to a specific instruction line
Pre-comment Ctrl+Shift+; Block comment above an instruction
Post-comment Ctrl+Alt+; After a function (rare)
Plate comment Ctrl+Shift+P Multi-line block comment at address
Repeatable comment Ctrl+Shift+R Comment that appears at every reference to this address

EOL comments are the most common. Select an instruction, press ; , type:

CALL strcmp     ; compare input against "root"

Plate comments are useful for summarizing a code block's purpose. Press Ctrl+Shift+P at the block start:

Plate Comment:
This loop iterates over the input buffer,
XORs each byte with 0xAA, and writes
the result to the output buffer.
Output length is stored in [rbp-0x8].

Function Signature Editing

Right-click a function name -> Edit Function Signature. The dialog shows:

Return Type: int
Calling Convention: __stdcall / __cdecl / __thiscall / __fastcall
Parameters:
  param_1  char *     Name: user
  param_2  char *     Name: password

Set the correct return type and parameter types. This feeds the decompiler, which uses parameter types to generate more accurate pseudocode. If a function takes a void * but you know it's a struct socket_info * , setting the correct type makes the decompiler dereference struct fields automatically.

The calling convention field matters more on Windows (stdcall vs cdecl vs fastcall). On Linux x86-64, System V AMD64 ABI is the default and correct for nearly all user-space code.

Cross-References in Depth

Cross-references are the primary mechanism for understanding data flow and call relationships.

Data cross-references :

Given a global variable at 0x404060 , right-click -> References -> Show References to 0x404060 . The table shows:

Address      Type  Function      Operand
004011a9     W     authenticate  MOV dword ptr [DAT_00404060], EAX
004011b8     R     authenticate  CMP dword ptr [DAT_00404060], 0x1f4
00401234     R     main          MOV EAX, dword ptr [DAT_00404060]
  • W = Write reference (instruction modifies this address)
  • R = Read reference (instruction reads this address)
  • RW = Read-modify-write

This tells you who sets the variable and who checks it - the equivalent of "Find All References" in an IDE .

Call cross-references :

Right-click on strcmp -> References -> Show References to strcmp . Shows every call site. This is the primary method for finding potentially dangerous function calls: all calls to system() , popen() , execve() , dlopen() .

Finding strings that reference an address :

If you have an address and want to find every string in the binary that mentions it (format strings, log messages), Search -> Program Text -> enter the address in hex.

The Decompiler

Press Ctrl+E on any function to open the Decompile window. The decompiler reads the disassembly and produces structured C-like pseudocode.

Given the authenticate function from the reading-assembly article, the decompiler output:

int authenticate(char *user, char *password)
{
  int iVar1;
  
  iVar1 = strcmp(user, "root");
  if (iVar1 != 0) {
    return 0;
  }
  iVar1 = check_password(password);
  if (iVar1 != 0) {
    return 1;
  }
  return 0;
}

The decompiler infers: - The function takes two char * arguments (from how they're passed to strcmp ) - iVar1 is an int (from strcmp return type) - The control flow is if-then-else with early returns

Decompiler output is NOT original source code. It's a reconstruction. Variable names are synthetic ( iVar1 , uVar2 , lVar3 - Hungarian notation for type: i=int, u=unsigned, l=long, p=pointer). You must rename them to understand the logic.

Why the decompiler sometimes fails :

  • Indirect calls (function pointers): The decompiler can't resolve the target at compile time. It shows (*ptr)() or a register call. You must annotate what function lives at that pointer.
  • Variable reuse : At -O2 , a register may hold different values at different points. The decompiler may split a single C variable into multiple synthetic variables ( iVar1 , iVar2 ) because it can't prove they're the same high-level variable.
  • Inlined functions : The decompiler sees the inlined code and treats it as part of the caller. No function call edge exists.
  • Compiler idioms : Some instruction sequences don't map cleanly to C. The sbb ebx, ebx; neg ebx sequence from the optimized authenticate function is decompiled as (check_password(password) ? 0 : -1) + 1 - correct behavior, but ugly expression.
  • Jump tables : The decompiler must recognize the switch pattern. Enabling "Create Address Tables" analyzer helps. Manually, you can right-click the indirect jump and select "Create/Edit Switch Table".

Patching the decompiler input :

The decompiler works better when you provide accurate type information. Before relying on decompiler output: 1. Set correct parameter types on imported functions (right-click -> Edit Function Signature)

  1. Create structs for complex data types
  2. Rename global variables to their correct types
  3. Set the calling convention if non-default

Patching Instructions

Ghidra allows modifying the binary's disassembly - useful for NOP-ing out anti-debug checks or modifying behavior for testing.

Right-click instruction -> Patch Instruction

Type new assembly and press Enter. Ghidra reassembles and updates the disassembly. The byte encoding changes, and subsequent analysis updates.

Example - replacing a conditional jump with an unconditional one to force a code path:

Original:  JZ   LAB_00401200  (74 0E)
Patch to:  JMP  LAB_00401200  (EB 0E)

Or NOP-ing out an anti-debugging ptrace check:

Original:  CALL ptrace  (e8 xx xx xx xx)
Patch to:  NOP; NOP; NOP; NOP; NOP  (90 90 90 90 90)

The patched binary can be exported:

File -> Export Program -> Format: ELF (or Original)

Bookmarks

Mark interesting locations for quick navigation:

Ctrl+B -> Create Bookmark
Type: "Note", Description: "This checks if ptrace is attached - anti-debug"

View all bookmarks: Window -> Bookmarks. Double-click to navigate. Bookmarks persist in the project - they survive Ghidra restarts.

Search Capabilities

Search Memory (S):

Search -> Memory
- Format: Hex, String, or Regular Expression
- Search in: Loaded Blocks, All Blocks, Selection

Byte pattern example: find all 55 48 89 E5 sequences (function prologues).

String search example: find all occurrences of HTTP or /bin/sh .

Search Program Text (Ctrl+Shift+E):

Searches the disassembly listing text - instruction mnemonics, operands, labels, comments.

  • CALL system - find all calls to system()
  • XOR EAX, EAX - find all register-zeroing instructions
  • ; TODO - find all comments tagged TODO

Search for Direct References :

Search -> For Direct References -> enter an address

Finds every instruction that references that specific address - equivalent to right-click -> References -> Show References To.

Practical Workflow

Here is the standard workflow for analyzing an unknown Linux binary, end to end.

Import and Analyze

File -> Import File -> select binary -> OK
Analyze? -> Yes -> Default analyzers -> Analyze

Wait for the progress bar to complete (bottom right). If the binary is large (50+ MB), auto-analysis may take minutes. The Console window will show warnings - note anything about "failed to disassemble" or "could not create function" - those indicate potential obfuscation or corrupted code.

Orient Yourself

Open Symbol Tree -> Imports. Scroll through. Note imported functions:

socket, connect, send, recv   -> network client
socket, bind, listen, accept  -> network server
fopen, fread, fwrite          -> file I/O
dlopen, dlsym                 -> dynamic library loading (possible unpacker)
system, popen, execve         -> command execution (high value target)
ptrace                         -> anti-debug
crypt, AES_*, MD5_*           -> cryptography

Find entry or _start in the Symbol Tree -> Functions. Click it. The Listing shows _start . Ghidra has already identified main - it's the first argument to __libc_start_main :

MOV RDI, <address_of_main>    ; arg1 to __libc_start_main
CALL __libc_start_main

Note the address being moved into RDI - that's main . Double-click it.

Understand main

Open the Decompile window (Ctrl+E). Read the pseudocode. Identify: - What arguments does main process? (argc, argv) - What's the high-level logic? (parse args -> validate -> connect -> send -> cleanup) - Where does the binary branch? (error handling paths, success paths)

If main is large, scroll through to get a sense of its structure before diving into details. Look for string references: LEA RDI, [s_"Usage:_..."] - format strings tell you command-line parsing. CMP argc, 3 - expecting 2 arguments plus program name.

Identify Key Functions

L -> rename main -> "main"
L -> rename FUN_00401196 -> "authenticate"
L -> rename FUN_00401162 -> "check_password"
L -> rename DAT_00402008 -> "ROOT_USERNAME"
L -> rename s_1337haxor_00402010 -> "SECRET_PASSWORD"

As you rename, Ghidra updates all cross-references - CALL FUN_00401196 becomes CALL authenticate . Comments in the disassembly now make semantic sense.

Trace Imports

Right-click connect in Symbol Tree -> References -> Show References to connect . Navigate to each call site. Read the surrounding disassembly to understand:

  • What socket address structure is being built? ( AF_INET = 2 , SOCK_STREAM = 1 )
  • What IP /port is being connected to?
  • Is the address hardcoded or user-supplied?

By understanding each imported function's usage, you build a picture of the binary's behavior.

Find Suspicious Functions

Use the Function Call Graph (Window -> Function Call Graph or Ctrl+Shift+F12). Click main

  • the graph shows main -> authenticate -> strcmp, check_password .

Functions that call multiple high-risk imports (system, connect, fopen) are key targets. Functions that are small with no callers may be dead code or rarely-used features.

Cross-reference analysis: any function that reads/writes to a global variable that stores authentication state. Search -> Program Text -> type the global variable's name -> find all references.

Document Findings

; at 0x401196:
; authenticate(user, password) - validates credentials
; Returns 1 on success, 0 on failure
; user must be "root" (strcmp to ROOT_USERNAME)
; password checked via check_password()
; check_password compares against SECRET_PASSWORD
; Both comparisons via strcmp - no hashing, no timing safety

Ctrl+Shift+P at entry to authenticate:
"""
authenticate - Credential Validation (WEAK)

Checks username against hardcoded "root".
Checks password against hardcoded "1337haxor".
Uses plain strcmp - both username and password
are stored as cleartext strings in .rodata.

VULNERABILITY: Credentials are stored in cleartext.
VULNERABILITY: Single constant-time string comparison
               makes brute-force trivial.
"""

Ctrl+B -> Bookmark: "Credential validation - hardcoded cleartext root:1337haxor"

Repeat for All Functions

Not every function needs deep analysis. Triage: 1. Functions that handle user input (buffer operations before/after recv, read, fgets) 1. Functions that perform authentication or authorization

  1. Functions that construct and execute commands (system, exec family)
  2. Functions that open/read/write files
  3. Functions with crypto constants (see Ghidra Scripting article for automated detection)

Functions that are pure computation (math, string formatting, data structure manipulation) can be tagged with a comment and revisited if needed.

Ghidra vs Other Tools

Tool Strengths Limitations
Ghidra Free decompiler, scripting, collaborative server, headless mode Java performance on huge (500MB+) binaries, less mature plugin ecosystem
IDA Pro De facto standard, most tutorials/examples, mature plugin ecosystem Expensive ($$$), decompiler costs extra, closed source
Binary Ninja Modern UI, excellent API, good decompiler (medium precision) Commercial ($), smaller community
radare2/rizin Terminal-based, extremely scriptable, free No built-in decompiler (r2dec is usable but primitive), steep learning curve
objdump Fast, always available, no installation No analysis, no cross-refs, manual everything

For Linux malware analysis, Ghidra is the recommended starting point. It's free, its decompiler is production-quality, and its scripting API covers all common automation needs. When Ghidra's decompiler fails on a complex function, fall back to reading the disassembly directly (see reading-assembly article).

Common Ghidra Issues and Fixes

Function Not Detected

Auto-analysis missed a function. Manually create it:

Navigate to the function's start address -> Right-click -> Create Function

If the function uses a non-standard prologue (or is obfuscated), you may need to define the function body manually: right-click -> Disassemble (D), then select the range and Create Function.

Decompiler Failure

Possible causes: - Indirect jump without switch table: Ghidra can't resolve possible targets. Right-click the indirect jump -> Create/Edit Switch Table, specify the table address and case count. - Function too complex: The decompiler times out. Break it into smaller functions manually (split at call instructions). - Anti-disassembly tricks: Overlapping instructions, junk bytes inserted into code. Manually fix the disassembly (press D to disassemble at the correct offset).

Wrong Calling Convention

On Linux x86-64, the System V AMD64 ABI is the default. If Ghidra assigns the wrong convention, right-click the function -> Edit Function Signature -> change Calling Convention.

Data Interpreted as Code

Ghidra may interpret data in .rodata as code and create phantom functions. Right-click -> Clear Flow and Repair, then re-apply the correct data type (Ctrl+T).

Corrupted Decompiler Output

After patching instructions, right-click -> Clear Flow and Repair, then re-create the function. This forces Ghidra to re-analyze control flow.

Exporting Results

File -> Export Program -> Format selection:
- ELF (Original): Patched binary
- Intel Hex: For embedded firmware flashing
- C/C++: Header with function signatures and data structures
- CSV: Symbol table export
- HTML: Annotated disassembly with comments and cross-refs

For reporting, the C/C++ export gives a reasonable skeleton. For collaboration, export the entire Ghidra project as a .gar archive:

File -> Archive Project -> Select project -> OK

Other analysts can restore the archive and see all your names, comments, bookmarks, and data types.

Summary

Ghidra is the primary static reverse engineering tool for this course. The core workflow is cyclic:

  1. Import -> binary is parsed, analyzers run
  2. Navigate -> find entry point, trace to main, identify imports
  3. Rename -> replace synthetic names with semantic ones
  4. Retype -> apply correct data types to variables, structs, enums
  5. Document -> comments and bookmarks capture findings
  6. Repeat -> for every function of interest

The decompiler accelerates understanding but is not infallible. When it fails, read the disassembly directly. The two views are complementary - the disassembly shows ground truth, the decompiler shows best-effort reconstruction.

Challenge

Write a Go tool that reproduces the Symbol Tree outside Ghidra. Use the debug/elf package to list every function symbol in a binary, sorted by address, and mark symbols with address zero as imports. Run it on a static binary and on a stripped binary, compare the output with Ghidra's Symbol Tree, and explain which symbols survive strip and why.

package main

import (
	"debug/elf"
	"fmt"
	"os"
	"sort"
)

type symbol struct {
	name string
	addr uint64
	size uint64
}

func isFunc(s elf.Symbol) bool {
	return elf.ST_TYPE(s.Info) == elf.STT_FUNC
}

func main() {
	if len(os.Args) != 2 {
		fmt.Fprintln(os.Stderr, "usage: symdump <elf-binary>")
		os.Exit(1)
	}

	f, err := elf.Open(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, "open:", err)
		os.Exit(1)
	}
	defer f.Close()

	var symbols []symbol

	// .symtab exists only when the binary is not fully stripped.
	if syms, err := f.Symbols(); err == nil {
		for _, s := range syms {
			if isFunc(s) {
				symbols = append(symbols, symbol{s.Name, s.Value, s.Size})
			}
		}
	}

	// .dynsym survives strip and lists imported and exported functions.
	if dynsyms, err := f.DynamicSymbols(); err == nil {
		for _, s := range dynsyms {
			if isFunc(s) {
				symbols = append(symbols, symbol{s.Name, s.Value, s.Size})
			}
		}
	}

	sort.Slice(symbols, func(i, j int) bool { return symbols[i].addr < symbols[j].addr })

	for _, s := range symbols {
		kind := "defined"
		if s.addr == 0 {
			kind = "import"
		}
		fmt.Printf("0x%08x %-8s %6d  %s\n", s.addr, kind, s.size, s.name)
	}
	fmt.Printf("\n%d function symbols\n", len(symbols))
}

Build and run it against a normal and a stripped copy of the same binary:
